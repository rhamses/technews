That, in turn, has had an impact downstream: overwhelming the people responsible for all the other steps in the SDLC. This ranges from open-source maintainers bombarded with thousands of pull requests and issues, to production engineers trying to save production from falling over as the rate of software delivery increases orders of magnitude.</p><p>We are all trying to save our systems, our customers, and ourselves from slop.</p><figure><p><img src=\"https://blog.cloudflare.com/_image?href=https%3A%2F%2Fblog.cloudflare.com%2F_emdash%2Fapi%2Fmedia%2Ffile%2F01KZ6A6DRX3WD507M2ZM4JJ353.png&w=715&h=336&f=webp&fit=cover&position=center\" srcset=\"https://blog.cloudflare.com/_image?href=https%3A%2F%2Fblog.cloudflare.com%2F_emdash%2Fapi%2Fmedia%2Ffile%2F01KZ6A6DRX3WD507M2ZM4JJ353.png&w=640&h=301&f=webp&fit=cover&position=center 640w, https://blog.cloudflare.com/_image?href=https%3A%2F%2Fblog.cloudflare.com%2F_emdash%2Fapi%2Fmedia%2Ffile%2F01KZ6A6DRX3WD507M2ZM4JJ353.png&w=715&h=336&f=webp&fit=cover&position=center 715w, https://blog.cloudflare.com/_image?href=https%3A%2F%2Fblog.cloudflare.com%2F_emdash%2Fapi%2Fmedia%2Ffile%2F01KZ6A6DRX3WD507M2ZM4JJ353.png&w=750&h=352&f=webp&fit=cover&position=center 750w, https://blog.cloudflare.com/_image?href=https%3A%2F%2Fblog.cloudflare.com%2F_emdash%2Fapi%2Fmedia%2Ffile%2F01KZ6A6DRX3WD507M2ZM4JJ353.png&w=828&h=389&f=webp&fit=cover&position=center 828w, https://blog.cloudflare.com/_image?href=https%3A%2F%2Fblog.cloudflare.com%2F_emdash%2Fapi%2Fmedia%2Ffile%2F01KZ6A6DRX3WD507M2ZM4JJ353.png&w=1080&h=508&f=webp&fit=cover&position=center 1080w, https://blog.cloudflare.com/_image?href=https%3A%2F%2Fblog.cloudflare.com%2F_emdash%2Fapi%2Fmedia%2Ffile%2F01KZ6A6DRX3WD507M2ZM4JJ353.png&w=1280&h=602&f=webp&fit=cover&position=center 1280w, https://blog.cloudflare.com/_image?href=https%3A%2F%2Fblog.cloudflare.com%2F_emdash%2Fapi%2Fmedia%2Ffile%2F01KZ6A6DRX3WD507M2ZM4JJ353.png&w=1430&h=672&f=webp&fit=cover&position=center 1430w\" alt=\"image1.png\"></p></figure><p>The answer — paradoxically — is to empower agents to do more. It’s only fair! You’d never let an engineer on your team write code, expect someone else to validate it, merge it, deploy it, hold the pager in production, and triage incoming bugs. But that’s what most companies are doing right now with agents. Models have improved remarkably, and agents are running over longer time horizons, able to take on much larger tasks. But they are not yet used evenly across the SDLC.</p><p>Cloudflare treats agents as our customers. They can <a href=\"https://blog.cloudflare.com/agents-stripe-projects/\" target=\"_blank\"><u>buy domains</u></a>, create <a href=\"https://blog.cloudflare.com/temporary-accounts/\" target=\"_blank\"><u>temporary accounts</u></a> and <a href=\"https://blog.cloudflare.com/code-mode-mcp/\" target=\"_blank\"><u>use the entire Cloudflare API</u></a>. We know that agents need APIs and tools to be able to manage the full SDLC on behalf of our customers — not just the start of it.</p><p>And so today we’re introducing the start of a new set of tools that let agents step beyond just generating code and take on more of the SDLC. We’re sharing what we’ve built and learned trying to solve this for ourselves:</p><ul><li><a href=\"https://blog.cloudflare.com/ci-workflows\" target=\"_blank\"><strong><u>@cloudflare/ci</u></strong></a> —&#160;a new way to run CI/CD across millions of repos, that can self-heal and spawn agents to do much more complex tasks, build on Cloudflare Workflows.</li><li><a href=\"https://blog.cloudflare.com/local-tracing\" target=\"_blank\"><strong><u>OpenTelemetry traces in local dev</u></strong></a> — giving agents the same observability they have in production, built into Wrangler and the Cloudflare Vite plugin.</li><li><a href=\"http://blog.cloudflare.com/agents-on-cloudflare\" target=\"_blank\"><strong><u>Introducing: Cloudflare Agents and Agent Traces</u></strong></a> —&#160;a new home for observing, maintaining and improving agents, centered around OpenTelemetry traces from agents.</li><li><a href=\"http://blog.cloudflare.com/engineering-standards-enforcement\" target=\"_blank\"><strong><u>How Cloudflare enforces engineering standards using AI</u></strong></a> — our own experience enforcing best practices across all of our products’ and systems’ repositories and specs.</li><li><a href=\"https://blog.cloudflare.com/astro-issue-triage\" target=\"_blank\"><strong><u>How we built a software factory to drive Astro’s GitHub issue count to zero</u></strong></a> — our own experience building systems to automatically triage, reproduce, verify and fix issues for a large and growing open source project.</li></ul><p>There’s something bigger here though. When we look at the SDLC, even with the best automation, its assumptions do not scale for the volume of code agents can write and the pace at which software engineering teams must move to compete. We think it’s time to replace the SDLC with the ADLC — the Agent Development Lifecycle.</p><h2>The SDLC is for software teams. The ADLC is for software factories.</h2><p>Right now, <a href=\"https://x.com/zachlloydtweets/status/2069789929073262945\" target=\"_blank\"><u>everyone</u></a> <a href=\"https://x.com/matanSF/status/2066578088184680920\" target=\"_blank\"><u>is</u></a> <a href=\"https://x.com/dexhorthy/status/2081797628552270027\" target=\"_blank\"><u>talking</u></a> <a href=\"https://x.com/bcherny/status/2077929390806073807\" target=\"_blank\"><u>about</u></a> <a href=\"https://x.com/gokulr/status/2032271386161684665\" target=\"_blank\"><u>building</u></a> “software factories” —&#160;agent-driven systems that take input and autonomously build, improve, deploy and manage software. Take an input, whether it’s a production error, a bug report from a customer, or an idea for a new feature, and delegate it entirely to an agent.</p><p>Even with agents, most software projects are constrained by human-in-the-loop steps. Humans prompting agents, telling them to keep going, instructing agents to apply feedback from a code review, constantly babysitting many agents and giving them instruction. On most software teams, the human still manages each step in the SDLC model — the only change is that they delegate tasks within each step to an agent.</p><p>And so the dream behind software factories is: what if you reimagined this approach and built a factory for the entire process of building software? How can we shift more human time towards the things that truly require human inspiration, taste, and judgement? It would leave us more time to design, to talk to customers, and to dream bigger.</p><p>A software factory has to manage the same steps in the SDLC, but it demands much more from the platform it is built on. Because when you hand over the keys and let the agent drive, every manual step that previously relied on a human must be adapted to be:</p><ul><li><strong>Programmatic</strong> —&#160;”ClickOps” was bad practice for humans, but it’s a non-starter for agents. Every last operation needs APIs that agents can call, debug, and rely on.</li><li><strong>Horizontally scalable</strong> — preview deployments were a nice-to-have when humans stared at the screen while building or manually took over a staging server to catch issues before production. For agents to drive, every agent must have its own preview that matches production.</li><li><strong>Reproducible</strong> — what happens if there’s a bug that you can only reproduce when simulating 4G on an iPhone 15? Or from an IP in a certain country? Typical unit testing and integration testing tools aren’t going to help here.</li><li><strong>Real-time, push based</strong> — relying on humans to look at the right dashboard has always been a bad way to know if things are working, but it completely breaks down with agents. You need an event that triggers an agent to do work.</li><li><strong>Atomic</strong> — every change needs to be independently testable, releasable, observable, and reversible without affecting unrelated behavior.</li><li><strong>Permissioned</strong> — you know you probably shouldn’t, but today you give a few trusted engineers the keys to SSH into prod in case things really go haywire. There’s no way you let an agent do that — but without the ability to escalate and get more permissions, how can it do its job?</li><li><strong>Self-improving</strong> —&#160;people learn from experience. The first week ship or the first on-call rotation, humans are slow and need to shadow someone else, but then get better and faster. Agents, too, need ways to learn from experience.</li></ul><p>We need something new if we are going to make software factories safe to use for real production software. Software factories face the same challenge that other autonomous systems like self-driving cars do — the challenge of going from working successfully 80% of the time, to some number of nines past 99%.</p><h2>To give agents the keys to drive the SDLC, you can’t give them a car designed for humans</h2><p>An autonomous vehicle is loaded with sensors and technology that a regular car doesn’t have. Lidar sensors, cameras, powerful compute to run inference, and connectivity to a central command system that can take over remotely if needed.</p><p>For an autonomous vehicle to be 80% as good as a human at driving, we probably don’t need all of this. Self-driving got to around 80% as good as humans 10 years ago. But that’s not the bar to clear — the bar is to be much better and safer than a human driver. That’s what we expect when we hand over the keys to a machine, in order to feel safe taking a nap driving down the 101 at 60 mph. And that’s why autonomous vehicles have technology that is purpose-built for self-driving — it’s what builds trust and handles the edge cases that cannot be designed for upfront.</p><p>The same is true of self-driving software. Ask yourself — why <em>haven’t</em> you yet just let your agent auto-approve and merge its own PRs to your production services? The higher the stakes of what you build, the longer your list of reasons almost surely is.</p><p>When you start to unpack not only all the things that can go catastrophically wrong in this process, but also that are necessary to building the right thing for customers, it is remarkably complex. It doesn’t fit into a linear set of steps in a GitHub Actions YAML file, and it goes way beyond running traditional automated tests. Even a small change to a dashboard can span roles, specializations and org structures, and subjective changes are the hardest to test and to delegate. Most of these things are probably not part of your CI/CD pipeline at all today. But they will need to be, if you want them to still happen, while giving full control to the agents running the software factory.</p><p>To let agents drive the whole process, we need a better way to orchestrate these dynamic series of steps. We think that is a <a href=\"https://blog.cloudflare.com/ci-workflows\" target=\"_blank\"><u>Workflow</u></a>, with the capability to spawn containers, agents and browsers. A Workflow that can set feature flags and enable them for a test user, investigate logs and traces, observe production metrics as a change gradually rolls out, and do everything else that is needed in order to ship safely.</p><h2>A CI/CD pipeline is just a Workflow. Agents can write code faster than teams can review, deploy, and maintain it. Today we’re introducing the Agent Development Lifecycle and the Cloudflare primitives that underpin it
