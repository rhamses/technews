contentHtml: "<p>For legal and compliance teams, auditing a repository of thousands of contracts for a single regulatory obligation shouldn’t take weeks. But with keyword search, it often does. A search for “inadvertent access notification” returns exact matches while missing functionally equivalent clauses such as “security incident disclosure” or “unauthorized access reporting.” This creates two problems:</p> \n<p><strong>Discovery gap:</strong> Critical risk exposure goes undetected because keyword search cannot match semantically equivalent terms across different contracts.</p> \n<p><strong>Review latency:</strong> After finding relevant contracts, legal counsel must manually scan lengthy documents to locate the specific clauses that matter. This process can stretch from minutes to hours per document.</p> \n<p><a href=\"https://aws.amazon.com/opensearch-service/\" target=\"_blank\" rel=\"noopener\">Amazon OpenSearch Service</a> is a fully managed search and analytics service that configures, manages, and scales OpenSearch clusters in the AWS Cloud. It supports use cases from log analytics and application monitoring to full-text search and real-time security analytics. It also supports AI-powered semantic search.</p> \n<p>Amazon OpenSearch Service addresses both problems through two capabilities:</p> \n<ul> \n <li><a href=\"https://docs.aws.amazon.com/opensearch-service/latest/developerguide/semantic-search.html\" target=\"_blank\" rel=\"noopener\">Semantic search</a> retrieves contracts based on meaning rather than exact keyword matches, closing the discovery gap.</li> \n <li><a href=\"https://docs.aws.amazon.com/opensearch-service/latest/developerguide/cfn-template.html#cfn-template-semantic-highlighting\" target=\"_blank\" rel=\"noopener\">Semantic highlighting</a> pinpoints the exact clauses within retrieved contracts that answer the query, reducing review time from hours of manual scanning to seconds of targeted reading.</li> \n</ul> \n<p>In this post, you build a contract compliance search system that combines semantic search with semantic highlighting in Amazon OpenSearch Service. You deploy the solution using two <a href=\"https://aws.amazon.com/cloudformation/\" target=\"_blank\" rel=\"noopener\">AWS CloudFormation</a> stacks, test it with synthetic contract documents, and see how a single query surfaces both the right contracts and the right clauses within them.</p> \n<h2 id=\"solution-overview\">Solution overview</h2> \n<p>The solution uses a two-stage retrieval and extraction pipeline. First, semantic search identifies relevant contracts across the repository. Then, semantic highlighting marks the specific clauses within those contracts that match the query intent.</p> \n<p>The following diagram illustrates the solution architecture:</p> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/20/BDB-5750-1-1.png\" alt=\"Solution architecture showing contracts flowing from Amazon S3 through OpenSearch Ingestion and Amazon Bedrock embeddings to semantic search and Amazon SageMaker AI highlighting\" width=\"800\"></p> \n<ol type=\"1\"> \n <li><strong>Upload contracts to</strong> <a href=\"https://aws.amazon.com/pm/serv-s3/\" target=\"_blank\" rel=\"noopener\">Amazon Simple Storage Service (Amazon S3)</a> – Contract documents (JSON format) are uploaded to an Amazon S3 bucket, which serves as the centralized document repository.</li> \n <li><a href=\"https://docs.aws.amazon.com/opensearch-service/latest/developerguide/ingestion.html\" target=\"_blank\" rel=\"noopener\">Amazon OpenSearch Ingestion (OSI)</a> <strong>reads from S3</strong> – A serverless OSI pipeline detects new documents in the S3 bucket and reads them for processing.</li> \n <li><strong>OpenSearch ingest pipeline generates embeddings through Amazon Bedrock</strong> – As documents arrive, the ingest pipeline’s <code>text_embedding</code> processor invokes Amazon Titan Text Embeddings V2 through an ML Commons Bedrock connector. This converts contract text into 1024-dimension vector representations, stored in a k-NN index that uses the faiss engine.</li> \n <li><strong>User submits a search query</strong> – A user queries the system with natural language (for example, “data protection regulations”) through a test <a href=\"https://aws.amazon.com/pm/lambda/\" target=\"_blank\" rel=\"noopener\">AWS Lambda</a> function that forwards the request to OpenSearch using the neural query type.</li> \n <li><strong>OpenSearch generates the query embedding</strong> – OpenSearch converts the user’s natural language query into a vector embedding using the same machine learning (ML) Commons Amazon Bedrock connector and Amazon Titan V2 model.</li> \n <li><strong>Amazon OpenSearch Service performs semantic search</strong> – OpenSearch uses k-NN vector similarity to retrieve contracts that are semantically relevant to the query, even when exact terminology differs.</li> \n <li><strong><a href=\"https://aws.amazon.com/sagemaker/ai\" target=\"_blank\" rel=\"noopener\">Amazon SageMaker AI</a> performs semantic highlighting</strong> – The <code>opensearch-semantic-highlighter-v1</code> model, hosted on an Amazon SageMaker AI GPU endpoint, scores sentence relevance using cross-encoder inference and wraps the matching clauses in <code>&lt;em&gt;</code> tags for targeted reading.</li> \n</ol> \n<h3 id=\"how-semantic-search-and-semantic-highlighting-work-together\">How semantic search and semantic highlighting work together</h3> \n<p>The system processes queries in two steps:</p> \n<p><strong>Step 1</strong> –&nbsp;<strong>Semantic search (document discovery)</strong>: You query the contract corpus using natural language. The system retrieves contracts with semantically similar concepts, even when exact terminology differs. For example, searching for “force majeure” returns contracts discussing “natural disasters” or “unforeseeable circumstances” because the system understands these concepts are related.</p> \n<p><strong>Step 2</strong> –&nbsp;<strong>Semantic highlighting (clause identification):</strong> After relevant contracts are retrieved, semantic highlighting automatically marks the clauses that semantically match your search intent. Instead of scanning pages of legal text, you immediately see the specific paragraphs that answer your question.</p> \n<p>The difference between standard <a href=\"https://docs.opensearch.org/latest/search-plugins/searching-data/highlight/\" target=\"_blank\" rel=\"noopener\">keyword highlighting</a> and <a href=\"https://docs.opensearch.org/latest/tutorials/vector-search/semantic-highlighting-tutorial/\" target=\"_blank\" rel=\"noopener\">semantic highlighting</a> is significant:</p> \n<ul> \n <li>Keyword highlighting wraps individual matching words: <code>&lt;em&gt;termination&lt;/em&gt;</code> and <code>&lt;em&gt;rights&lt;/em&gt;</code>.</li> \n <li>Semantic highlighting wraps entire relevant clauses: <code>&lt;em&gt;Upon termination, the consultant must return all confidential information and proprietary materials within 15 business days.&lt;/em&gt;</code>.</li> \n</ul> \n<p>This reduces false positives, cuts review time, and provides explainability for why each document was retrieved.</p> \n<h3 id=\"semantic-highlighting-model-deployment\">Semantic highlighting model deployment</h3> \n<p>Before the system can highlight clauses based on meaning, the <code>opensearch-semantic-highlighter-v1</code> model must be deployed to an Amazon SageMaker AI GPU endpoint and registered with the OpenSearch ML Commons plugin through a remote connector.</p> \n<p>Stack 2 of the CloudFormation deployment automates this process. It performs the following steps:</p> \n<ol type=\"1\"> \n <li>Downloads the model artifact from an AWS-managed source and deploys it to an Amazon SageMaker AI endpoint (<code>ml.g5.xlarge</code>).</li> \n <li>Creates a remote ML Commons connector in OpenSearch that points to the SageMaker endpoint.</li> \n <li>Registers the model with the <code>QUESTION_ANSWERING</code> function so that OpenSearch can use the model’s cross-encoder capabilities to score sentence relevance at query time.</li> \n</ol> \n<p>The equivalent manual registration call (handled automatically by the stack) is:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-plaintext\">POST /_plugins/_ml/models/_register?deploy=true\n{\n  \"name\": \"amazon/sentence-highlighting/opensearch-semantic-highlighter-v1\",\n  \"version\": \"1.0.0\",\n  \"model_format\": \"TORCH_SCRIPT\",\n  \"function_name\": \"QUESTION_ANSWERING\"\n}</code></pre> \n</div> \n<p>You don’t need to run this manually. The deployment script and CloudFormation stack handle model registration end-to-end. The resulting model ID is automatically passed to the query Lambda function for use in semantic highlighting requests.</p> \n<h3 id=\"index-configuration\">Index configuration</h3> \n<p>The index uses a k-NN vector field with 1024 dimensions (matching the Amazon Titan V2 output) and the faiss engine with HNSW method. The mapping includes both a <code>knn_vector</code> field for semantic retrieval and a standard <code>text</code> field for keyword matching and highlighting. When you search for “liability limits,” OpenSearch first retrieves documents through vector similarity, then uses the Amazon SageMaker AI model to identify and wrap the specific relevant sentences in <code>&lt;em&gt;</code> tags.</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-plaintext\">PUT /legal-contracts-index\n{\n  \"settings\": { \"index.knn\": true },\n  \"mappings\": {\n    \"properties\": {\n      \"clause_text\": { \"type\": \"text\" },\n      \"clause_embedding\": {\n        \"type\": \"knn_vector\",\n        \"dimension\": 1024,\n        \"method\": {\n          \"name\": \"hnsw\",\n          \"engine\": \"faiss\",\n          \"space_type\": \"l2\"\n        }\n      }\n    }\n  }\n}</code></pre> \n</div> \n<h2 id=\"implementation-steps\">Implementation steps</h2> \n<p>This section walks you through deploying the solution using two AWS CloudFormation stacks and two shell scripts.
