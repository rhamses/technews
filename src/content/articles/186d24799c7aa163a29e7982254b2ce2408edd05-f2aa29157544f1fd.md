contentHtml: "<p>When you upgrade your <a href=\"https://aws.amazon.com/redshift/\" target=\"_blank\" rel=\"noopener\">Amazon Redshift</a> DC2 (Dense Compute) clusters to <a href=\"https://aws.amazon.com/es/redshift/features/rg/\" target=\"_blank\" rel=\"noopener\">RG instances</a> powered by <a href=\"https://aws.amazon.com/ec2/graviton/\" target=\"_blank\" rel=\"noopener\">AWS Graviton</a>, you gain access to capabilities that were never available on DC2. These include <a href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/managing-cluster-operations.html\" target=\"_blank\" rel=\"noopener\">managed storage</a>, <a href=\"https://docs.aws.amazon.com/redshift/latest/dg/datashare-overview.html\" target=\"_blank\" rel=\"noopener\">data sharing</a>, <a href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/zero-etl-using.html\" target=\"_blank\" rel=\"noopener\">zero-ETL integrations</a>, <a href=\"https://docs.aws.amazon.com/redshift/latest/dg/materialized-view-streaming-ingestion.html\" target=\"_blank\" rel=\"noopener\">streaming ingestion</a>, and <a href=\"https://aws.amazon.com/about-aws/whats-new/2026/03/amazon-redshift-increases-performance-for-new-queries/\" target=\"_blank\" rel=\"noopener\">faster query compilation</a>. You also gain availability zone (AZ) features such as <a href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/managing-cluster-recovery.html\" target=\"_blank\" rel=\"noopener\">cross-AZ cluster relocation</a> for disaster recovery (DR) and <a href=\"https://docs.aws.amazon.com/redshift/latest/dg/concurrency-scaling.html\" target=\"_blank\" rel=\"noopener\">concurrency scaling</a> for writes. RG also adds a built-in data lake engine for querying Apache Iceberg and Parquet tables directly on your cluster nodes.</p> \n<p>This post covers the new features you gain when upgrading from DC2 to RG, the node mapping guidance for sizing your new cluster, the upgrade methods available, and validation options including <a href=\"https://github.com/aws/redshift-test-drive\" target=\"_blank\" rel=\"noopener\">Amazon Redshift Test Drive</a>.</p> \n<h2 id=\"why-upgrade-from-dc2-to-rg-instances\">Why upgrade from DC2 to RG instances</h2> \n<p>As data volumes grow, DC2 customers face a choice: add extra compute nodes only to get more storage, or offload data elsewhere. The local SSD capacity on each node is fixed, and there is no managed storage tier to absorb growth. Both RA3 and RG instances solve this with <a href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/managing-cluster-operations.html\" target=\"_blank\" rel=\"noopener\">Amazon Redshift Managed Storage</a>, which decouples storage from compute. You can scale data volume independently of node count, paying only for the storage you use with no fixed ceiling per node. This means you no longer need to over-provision compute to accommodate data growth.</p> \n<p>RG is the recommended upgrade path over RA3. RG instances run on AWS Graviton processors, delivering higher throughput for data warehouse and data lake workloads at a lower price per vCPU compared to RA3. Because both RA3 and RG share the same managed storage architecture and feature set, RG provides more performance for less cost. For current pricing details, visit <a href=\"https://aws.amazon.com/redshift/pricing/\" target=\"_blank\" rel=\"noopener\">Amazon Redshift pricing</a>.</p> \n<p>Amazon Redshift RG instances run on AWS Graviton processors. These processors provide more compute cores and lower memory latency compared to the previous-generation hardware behind DC2. This can translate to faster query execution for data warehouse workloads, particularly for large scans where memory throughput is the bottleneck. Exact performance improvements depend on workload characteristics, cluster size, and query complexity. Use Redshift Test Drive to measure the difference for your specific workload.</p> \n<h3 id=\"data-lake-access-new-with-rg\">Data lake access: New with RG</h3> \n<p>DC2 clusters can query data in <a href=\"https://aws.amazon.com/s3/\" target=\"_blank\" rel=\"noopener\">Amazon Simple Storage Service (Amazon S3)</a> through <a href=\"https://docs.aws.amazon.com/redshift/latest/dg/c-spectrum-overview.html\" target=\"_blank\" rel=\"noopener\">Amazon Redshift Spectrum</a>. However, Spectrum adds a per-TB scanning cost on top of your cluster pricing, and does not support <a href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/enhanced-vpc-enabling-cluster.html\" target=\"_blank\" rel=\"noopener\">enhanced VPC routing</a> on DC2 provisioned clusters (requiring additional configuration for secure S3 access).</p> \n<p>RG addresses these constraints with an <a href=\"https://docs.aws.amazon.com/redshift/latest/dg/querying-iceberg.html\" target=\"_blank\" rel=\"noopener\">integrated data lake engine</a> that processes queries directly on your cluster’s dedicated compute nodes:</p> \n<table border=\"1px\" width=\"100%\" cellpadding=\"10px\"> \n <tbody> \n  <tr> \n   <td></td> \n   <td><strong>DC2 (Spectrum)</strong></td> \n   <td><strong>RG (Integrated Engine)</strong></td> \n  </tr> \n  <tr> \n   <td>Data lake query cost</td> \n   <td>Extra $5/TB scanned on top of cluster cost</td> \n   <td>Included in node pricing, no extra charge</td> \n  </tr> \n  <tr> \n   <td>Apache Iceberg</td> \n   <td>Queries via Spectrum</td> \n   <td>Native queries on cluster compute, no Spectrum needed</td> \n  </tr> \n  <tr> \n   <td>Apache Iceberg Statistics</td> \n   <td>Manual collection</td> \n   <td><a href=\"https://aws.amazon.com/about-aws/whats-new/2025/11/amazon-redshift-jit-analyze-apache-iceberg-tables/\" target=\"_blank\" rel=\"noopener\">JIT-Analyze auto-collects statistics</a></td> \n  </tr> \n  <tr> \n   <td>VPC routing</td> \n   <td>Not compatible with enhanced VPC routing</td> \n   <td>No conflict, runs on the cluster itself</td> \n  </tr> \n </tbody> \n</table> \n<p>With RG, you can consolidate warehouse and data lake workloads on a single cluster with no extra per-query charges for data lake access.</p> \n<h3 id=\"features-available-with-rg\">Features available with RG</h3> \n<p>Upgrading from DC2 to RG gives you access to the full set of modern Amazon Redshift capabilities. Three of the most impactful for DC2 customers are data sharing, zero-ETL integrations, and managed storage. With data sharing, you can query live data from other Amazon Redshift clusters or accounts without copying or moving data, reducing storage duplication and keeping consumers always up to date. Zero-ETL integrations automatically replicate data from <a href=\"https://aws.amazon.com/rds/aurora/\" target=\"_blank\" rel=\"noopener\">Amazon Aurora</a>, <a href=\"https://aws.amazon.com/rds/\" target=\"_blank\" rel=\"noopener\">Amazon Relational Database Service (Amazon RDS)</a>, and <a href=\"https://aws.amazon.com/dynamodb/\" target=\"_blank\" rel=\"noopener\">Amazon DynamoDB</a> into Amazon Redshift without building or maintaining ETL pipelines. This reduces operational overhead and data freshness lag. Managed storage scales independently from compute, so you can grow your data without adding nodes and only pay for the storage you use.</p> \n<p>Additional capabilities available with RG:</p> \n<ul> \n <li><strong>Streaming ingestion</strong> – ingest data from <a href=\"https://aws.amazon.com/kinesis/data-streams/\" target=\"_blank\" rel=\"noopener\">Amazon Kinesis Data Streams</a> and <a href=\"https://aws.amazon.com/msk/\" target=\"_blank\" rel=\"noopener\">Amazon Managed Streaming for Apache Kafka (Amazon MSK)</a> in near real-time, so you can build dashboards and analyze the latest data without batch delays.</li> \n <li><strong>Concurrency scaling for writes</strong> – automatically add transient capacity during burst write workloads, so ingest operations don’t slow down your analytical queries.</li> \n <li><strong>Cross-AZ cluster relocation</strong> – relocate your cluster to another Availability Zone with no endpoint changes, supporting disaster recovery without the cost of a standby cluster.</li> \n <li><strong>Multi-AZ deployments</strong> – run your cluster across multiple Availability Zones as a single database delivering high availability (HA) and automatic failover without a passive standby.</li> \n <li><strong>Faster query compilation</strong> – queries compile faster on Graviton processors, reducing cold-start latency for new or modified queries.</li> If automated snapshots are disabled, create a manual snapshot before starting. Visit <a href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/working-with-snapshots.html\" target=\"_blank\" rel=\"noopener\">Amazon Redshift snapshots</a> for more information.</li> \n <li><strong>Network configuration</strong> — verify that your virtual private cloud (VPC), subnet groups, and security groups are configured to support the new RG cluster. If you use enhanced VPC routing, confirm your S3 endpoint and route table configuration. Check the <a href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/cluster-versions.html\" target=\"_blank\" rel=\"noopener\">release notes</a> for minimum version requirements.</li> \n</ul> \n<h2 id=\"upgrade-methods\">Upgrade methods</h2> \n<p>Three methods are available for migrating from DC2 to RG instances. The right choice depends on your operational constraints: whether you need write access during migration, whether the target configuration supports <a href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/managing-cluster-operations.html\" target=\"_blank\" rel=\"noopener\">elastic resize</a>, and how much downtime your workload can tolerate.</p> \n<h3 id=\"elastic-resize-recommended\">Elastic resize (recommended)</h3> \n<p>Elastic resize is the fastest and most efficient path. Amazon Redshift creates a snapshot, provisions the RG cluster, and redirects the endpoint automatically. The cluster remains in read-only mode for a few minutes during the operation, and the endpoint doesn’t change, meaning no application-side updates are required. This is the recommended method when the target configuration is supported by elastic resize.</p> \n<h3 id=\"classic-resize\">Classic resize</h3> \n<p>Use <a href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/managing-cluster-operations.html\" target=\"_blank\" rel=\"noopener\">classic resize</a> when the target configuration is not available through elastic resize, or when you need data slice rebalancing. Downtime is similar to elastic resize (a few minutes of read-only mode in Stage 1). In Stage 2, data redistributes to its original distribution patterns in the background without blocking queries. The advantage of classic resize is that it rebalances data slices evenly across nodes. This matters when you move to a different node type that might require a different number of <a href=\"https://docs.aws.amazon.com/redshift/latest/dg/c_high_level_system_architecture.html\" target=\"_blank\" rel=\"noopener\">slices</a>. Stage 2 can take time on busy clusters, and the duration depends on data volume, cluster utilization, and target cluster size. Queries might run slower until redistribution completes.</p> \n<h3 id=\"snapshot-and-restore-with-cluster-identifier-swap\">Snapshot and restore with cluster identifier swap</h3> \n<p>This method uses <a href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/working-with-snapshots.html\" target=\"_blank\" rel=\"noopener\">snapshot and restore</a> of the existing DC2 cluster to provision a new RG cluster with a different identifier. After validating the new cluster, you swap the cluster identifiers to redirect application traffic without changing the endpoint. This approach provides these benefits:</p> \n<ul> \n <li>Test and validate the RG cluster while the DC2 cluster continues serving production traffic.</li> \n <li>Roll back by reversing the identifier swap if issues arise.</li> \n <li>No application-side endpoint changes required after the swap.</li> \n</ul> \n<p>The trade-off is that data written to the source cluster after the snapshot requires manual synchronization before the cutover. If your migration plan includes a write-freeze window, you can take the final snapshot at the start of that window and avoid synchronization entirely.</p> \n<p>This <a href=\"https://aws.amazon.com/cli/\" target=\"_blank\" rel=\"noopener\">AWS Command Line Interface (AWS CLI)</a> command illustrates restoring a DC2 snapshot to an RG cluster:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-bash\">aws redshift restore-from-cluster-snapshot \\\n    --cluster-identifier my-cluster-rg \\\n    --snapshot-identifier my-dc2-snapshot \\\n    --node-type rg.4xlarge \\\n    --number-of-nodes 3 \\\n    --cluster-subnet-group-name my-subnet-group \\\n    --vpc-security-group-ids sg-abc123 \\\n    --cluster-parameter-group-name my-param-group \\\n    --port 5439 \\\n    --no-publicly-accessible \\\n    --enhanced-vpc-routing \\\n    --iam-roles 'arn:aws:iam::111122223333:role/RedshiftRole'</code></pre> \n</div> \n<p>After restoring, validate your workload on the new cluster. When ready, swap the cluster identifiers:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-bash\">aws redshift modify-cluster \\\n    --cluster-identifier my-cluster \\\n    --new-cluster-identifier my-cluster-dc2-old\n\naws redshift modify-cluster \\\n    --cluster-identifier my-cluster-rg \\\n    --new-cluster-identifier my-cluster</code></pre> \n</div> \n<h2 id=\"validating-your-target-configuration\">Validating your target configuration</h2> \n<p>Before migrating production clusters, validate that your target RG configuration meets performance requirements. There are several ways to approach this depending on your needs:</p> \n<p><strong>Run your existing QA process on a test cluster.</strong> Create an RG cluster from a snapshot, then execute the same test suites and validation scripts you would use for any code or infrastructure change. This approach helps confirm basic compatibility and catch regressions.</p> \n<p><strong>Use lower environments first.</strong> Migrate your development or staging clusters to RG before production. This gives your team hands-on experience with the new instance type and surfaces any configuration differences in a low-risk setting.</p> \n<p><strong>Replay production workloads with Redshift Test Drive.</strong> For production-level validation with real traffic patterns, <a href=\"https://github.com/aws/redshift-test-drive\" target=\"_blank\" rel=\"noopener\">Redshift Test Drive</a> is an open source utility that automates workload replay across multiple target configurations. It extracts queries from your source cluster’s <a href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/db-auditing.html\" target=\"_blank\" rel=\"noopener\">audit logs</a> and replays them against the target, then provides a comparison UI for latency, errors, and deviation.</p> \n<p>For a detailed walkthrough, read <a href=\"https://aws.amazon.com/blogs/big-data/find-the-best-amazon-redshift-configuration-for-your-workload-using-redshift-test-drive/\" target=\"_blank\" rel=\"noopener\">Find the best Amazon Redshift configuration for your workload using Redshift Test Drive</a>.</p> \n<h2 id=\"best-practices\">Best practices</h2> \n<p><strong>Before migrating</strong>, run <a href=\"https://docs.aws.amazon.com/redshift/latest/dg/advisor.html\" target=\"_blank\" rel=\"noopener\">Amazon Redshift Advisor</a> on your current cluster to identify optimization opportunities such as unused tables, missing sort keys, or distribution style changes. Drop unnecessary tables to reduce data transfer time, and schedule the migration during off-peak hours for minimal business impact. Removing tables that are no longer used (for example, tables with suffixes like <code>_bkp</code>, <code>_tmp</code>, or <code>_old</code>) also speeds up classic resize. These unused tables would otherwise be rebalanced across nodes during Stage 2, adding time to a process that delivers no value for data no one queries.</p> \n<p><strong>During migration,</strong> communicate the cutover window to stakeholders. Because the DC2 cluster remains active until the identifier swap, coordinate a brief write-freeze period before the final snapshot to minimize data synchronization effort.</p> \n<p><strong>After migration</strong>, monitor the cluster for 48–72 hours to identify any performance deviations and adjust node count if needed. Update your runbooks and operational documentation with the new cluster details, node types, and any endpoint changes if you used the snapshot and restore method. Once the migration is considered successful you may <a href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/rs-mgmt-shutdown-delete-cluster.html\" target=\"_blank\" rel=\"noopener\">delete</a> the DC2 cluster.</p> \n<h2 id=\"conclusion\">Conclusion</h2> \n<p>Upgrading from Amazon Redshift DC2 to RG instances powered by AWS Graviton gives you a Graviton-based architecture with managed storage and improved query performance. The snapshot restore and cluster identifier swap method provides a safe migration path with built-in rollback. Use Redshift Test Drive to validate your target configuration with real workload data before committing.</p> \n<p>To get started, review the <a href=\"https://aws.amazon.com/redshift/pricing/\" Upgrading your Amazon Redshift DC2 clusters to AWS Graviton-based RG instances unlocks managed storage, data sharing, zero-ETL, and an integrated data lake engine. This post covers the new features, node-mapping guidance for sizing, the available upgrade methods, and how to validate your target configuration with Amazon Redshift Test Drive.
