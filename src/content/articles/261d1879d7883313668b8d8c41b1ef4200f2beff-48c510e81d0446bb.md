For details, see the <a href=\"https://aws.amazon.com/blogs/big-data/introducing-apache-spark-upgrade-agent-for-amazon-emr/\" target=\"_blank\" rel=\"noopener\">introduction post</a>.</p> \n<h2 id=\"architecture-how-it-works\">Architecture: How it works</h2> \n<p>The architecture follows a least-privilege security model:</p> \n<ul> \n <li><strong>Scoped IAM roles</strong> — <a href=\"https://aws.amazon.com/iam/\" target=\"_blank\" rel=\"noopener\">AWS IAM</a> roles are scoped to only MCP server calls, Amazon Simple Storage Service (<a href=\"https://aws.amazon.com/s3/\" target=\"_blank\" rel=\"noopener\">Amazon S3</a>) staging bucket access, and <a href=\"https://aws.amazon.com/emr/\" target=\"_blank\" rel=\"noopener\">Amazon EMR</a> job submission.</li> \n <li><strong>Local source code</strong> — Your source code stays local, with only minimal diagnostic information transmitted.</li> \n <li><strong>Encryption in transit</strong> — All data is encrypted in transit.</li> \n <li><strong>Audit trail</strong> — <a href=\"https://aws.amazon.com/cloudtrail/\" target=\"_blank\" rel=\"noopener\">AWS CloudTrail</a> records every tool invocation for full auditability.</li> \n</ul> \n<h2 id=\"example-use-case-enterprise-scale-spark-migration\">Example use case: Enterprise-scale Spark migration</h2> \n<p>To illustrate the capabilities of the agent at scale, consider a real-world migration scenario from a large company. This company runs a data processing platform with thousands of Spark jobs across Scala, PySpark, and Spark SQL workloads, with a code base spanning Spark 3.3 and 3.5.</p> \n<p>The data engineering team faces a migration across three workload types with different complexity profiles:</p> \n<ul> \n <li><strong>Spark SQL applications:</strong> The most portable, but still requiring validation of behavioral changes in the query optimizer and join strategies introduced in Spark 4.0.</li> \n <li><strong>PySpark workloads:</strong> Requiring updates to UDF serialization patterns, Arrow-based optimizations, and DataFrame API changes.</li> \n <li><strong>Scala applications:</strong> The most complex, involving build system updates (Maven and SBT), API deprecations, and recompilation against new Spark 4.0 JARs.</li> \n</ul> \n<p>To tackle this, the team uses the Spark Upgrade Agent to migrate all three workload types to Spark 4.0 on Amazon EMR 8.x. For each workload, the agent is invoked directly from <a href=\"https://kiro.dev/\" target=\"_blank\" rel=\"noopener\">Kiro</a> or <a href=\"https://github.com/cline/cline\" target=\"_blank\" rel=\"noopener\">VS Code with Cline</a>, applying targeted transformations and immediately validating results against a live Amazon EMR 8.x Serverless application running Spark 4.0.</p> \n<p>Migrations that would traditionally require months of manual engineering effort complete in a fraction of the time. The agent follows an iterative refinement loop: it performs local validation, then submits the job to a remote Amazon EMR cluster. This loop catches and resolves runtime failures automatically, reducing the need for manual debugging cycles. Build configuration files (<code>pom.xml</code> and <code>build.sbt</code>) are updated automatically by the agent, eliminating a common source of migration errors.</p> \n<h2 id=\"solution-walkthrough\">Solution walkthrough</h2> \n<p>The following sections walk through the complete migration workflow, from initial setup through advanced code transformations and validation.</p> \n<h2 id=\"setup\">1.
