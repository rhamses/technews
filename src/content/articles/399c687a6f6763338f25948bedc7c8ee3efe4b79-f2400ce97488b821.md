contentHtml: "<p>Organizations running large-scale <a href=\"https://spark.apache.org/\" target=\"_blank\" rel=\"noopener\">Apache Spark</a> workloads often face a trade-off between achieving lower cost and job reliability. These tradeoffs are more prominent when using <a href=\"https://aws.amazon.com/ec2/spot/\" target=\"_blank\" rel=\"noopener\">Amazon Elastic Compute Cloud (Amazon EC2) Spot Instances</a> or when their jobs process highly skewed datasets. Three shuffle-related challenges drive the pain:</p> \n<ol type=\"1\"> \n <li><strong>Spot interruptions trigger costly recomputation</strong>: Spot instances can reduce compute spend by up to 90 percent compared to <a href=\"https://aws.amazon.com/ec2/pricing/on-demand/\" target=\"_blank\" rel=\"noopener\">On-Demand instances</a>, but they can be reclaimed with only two minutes of notice. When a Spark executor on a Spot Instance is interrupted, its local shuffle data is lost, and Spark must recompute entire upstream stages to regenerate that data. For shuffle-heavy jobs processing terabytes of data, frequent interruptions cause cascading recomputation and runtime delays, quickly eroding the savings that made Spot attractive in the first place.</li> \n <li><strong>Local shuffle storage causes cluster-wide over-provisioning</strong>: In YARN-based Hadoop architectures, including <a href=\"https://docs.aws.amazon.com/emr/latest/ManagementGuide/emr-what-is-emr.html\" target=\"_blank\" rel=\"noopener\">Amazon EMR on EC2</a>, the External Shuffle Service (ESS) stores shuffle data locally on each Node Manager’s node alongside the Spark executor that produced it. Every node must carry large memory and disk allocations to accommodate shuffle output, yet only a few EC2 nodes perform most of the shuffle work. The rest sit oversized and underused. This is a classic coupled storage-compute problem. By decoupling shuffle storage to a dedicated, storage-optimized tier, you can right-size your compute for actual demands.</li> \n <li><strong>Shuffle data protection leaves compute idle</strong>: To guard against local shuffle data loss, Spark’s scaling logic prevents nodes that still hold shuffle data from scaling down. EC2 nodes sit idle long after Spark tasks complete. Data skew amplifies this effect: tail-end tasks run far longer than typical ones, delaying shuffle reads and postponing scale-down across the cluster.</li> \n</ol> \n<p>Together, these challenges force a difficult choice: cheaper infrastructure or predictable jobs. In this post, we show how Apache Celeborn resolves this trade-off for <a href=\"https://docs.aws.amazon.com/emr/latest/EMR-on-EKS-DevelopmentGuide/emr-eks.html\" target=\"_blank\" rel=\"noopener\">Amazon EMR on EKS</a> and Amazon EMR on EC2, improving job reliability while unlocking additional cost savings.</p> \n<h2 id=\"what-is-apache-celeborn\">What is Apache Celeborn?</h2> \n<p><a href=\"https://celeborn.apache.org/\" target=\"_blank\" rel=\"noopener\">Apache Celeborn</a> is an open-source Remote Shuffle Service (RSS) that solves the preceding problems by decoupling shuffle data from the executor lifecycle entirely. It uses a <em>Leader-Worker-Client</em> architecture: Leader nodes manage metadata, Workers read and write shuffle blocks, and Clients integrate with compute engines. Instead of writing shuffle output to local disks, Spark executors push data to a shared, storage-optimized Celeborn cluster that persists shuffle data independently of executor location. This means EMR executor nodes can run on 100% Spot Instances. Spot reclamations no longer cause shuffle data loss. Executors scale in and out freely without triggering upstream recomputation.</p> \n<p>Celeborn also provides <a href=\"https://raft.github.io/\" target=\"_blank\" rel=\"noopener\">Raft</a>-based high availability, per-job data replication, and a pluggable shuffle manager that replaces Spark’s default mechanism with minimal configuration changes. With its push-based model, Spark executors send shuffle data directly to Celeborn workers, which cache and consolidate partitions. This reduces the N×M network connections during the read phase, improving both performance and stability at scale.</p> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/09/BDB-5115-1.png\" alt=\"Push-based remote shuffle service where Spark executors on Amazon EMR push shuffle data to a shared Celeborn cluster\" width=\"800\"></p> \n<p>Image 1: Push-based Remote Shuffle Service for Spark on EMR</p> \n<h2 id=\"overview-of-solution\">Overview of solution</h2> \n<p>In this post, we show you how to deploy a Celeborn cluster alongside EMR on EKS and EMR on EC2. The solution also includes an observability stack to provide operational visibility into the Celeborn cluster. Metrics are collected by the <a href=\"https://aws-otel.github.io/\" target=\"_blank\" rel=\"noopener\">AWS Distro for OpenTelemetry (ADOT)</a> collector and routed to two monitoring paths. The AWS managed option uses <a href=\"https://docs.aws.amazon.com/prometheus/latest/userguide/what-is-Amazon-Managed-Service-Prometheus.html\" target=\"_blank\" rel=\"noopener\">Amazon Managed Service for Prometheus</a> and <a href=\"https://docs.aws.amazon.com/grafana/latest/userguide/what-is-Amazon-Managed-Service-Grafana.html\" target=\"_blank\" rel=\"noopener\">Amazon Managed Grafana</a>. The open source option uses self-managed <a href=\"https://prometheus.io/\" target=\"_blank\" rel=\"noopener\">Prometheus</a> with a built-in <a href=\"https://grafana.com/oss/grafana/\" target=\"_blank\" rel=\"noopener\">Grafana</a>.</p> \n<p>Apache Celeborn can be deployed in several ways depending on your operational requirements and scale. These two deployment patterns are the main ones:</p> \n<ul> \n <li><strong>Co-located on the same cluster:</strong> Celeborn runs on the same compute environment as Spark. This is the most straightforward operational model, with no cross-cluster networking. The main constraint is shared cluster lifecycle: any upgrade or termination affects Celeborn and running Spark jobs simultaneously.</li> \n <li><strong>Separate Celeborn cluster</strong>: Celeborn runs on its own EC2 or EKS cluster, fully isolated from Spark compute. This is the most operationally flexible model and is the focus of this post.</li> \n</ul> \n<p>In this solution, Celeborn runs on a dedicated Amazon Elastic Kubernetes Service (Amazon EKS) cluster, separate from the EMR Spark environments. The two workloads have different resource profiles. Celeborn is storage and network I/O intensive, while Spark is CPU and memory intensive. By separating them, each cluster can use instance types optimized for its workload. It also improves independent lifecycle management, so you can upgrade or scale Celeborn clusters without disrupting Spark jobs, and the other way around.</p> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/09/BDB-5115-2.png\" alt=\"Solution architecture with EMR on EKS and EMR on EC2 connecting to a shared Celeborn cluster through an internal Network Load Balancer\" width=\"800\"></p> \n<p>Image 2: Solution Architecture</p> \n<p>As the architecture diagram shows, two types of EMR deployment models, EMR on EKS and EMR on EC2, connect to a shared Celeborn cluster through an internal Network Load Balancer (NLB). Behind the scenes, Spark executors register their shuffle partitions to Celeborn workers through this connection, while reducers read consolidated data back during the fetch phase.</p> \n<p>The following are the key design considerations for this solution:</p> \n<ul> \n <li><strong>Streamlined operation by a shared RSS model:</strong> Celeborn runs on a dedicated EKS cluster. This provides lifecycle independence, allows each cluster to use workload-optimized instance types, and allows a single Celeborn cluster to serve multiple EMR clusters as a shared service.</li> \n <li><strong>Cross-cluster connectivity:</strong> Clusters reside in the same Amazon Virtual Private Cloud (Amazon VPC) and share private subnets. The <a href=\"https://docs.aws.amazon.com/eks/latest/userguide/aws-load-balancer-controller.html\" target=\"_blank\" rel=\"noopener\">AWS Load Balancer Controller</a> on the Celeborn cluster provisions an internal NLB exposing its active primary pods on ports 9097 (RPC) and 9098 (dashboard). The NLB DNS name is VPC-resolvable, so any EMR cluster in the same VPC can reach Celeborn by setting <code>spark.celeborn.master.endpoints</code> to the NLB address.</li> \n <li><strong>Restricted and secured networking:</strong> The Celeborn cluster only allows inbound traffic from the EMR on EC2 and EMR on EKS clusters, sending shuffle data and metrics over the network to the Celeborn cluster.</li> \n <li><strong>State persistence:</strong> Primary nodes maintain Celeborn’s coordination state through Raft consensus, which requires storage that survives pod restarts. Deploying them as <a href=\"https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/\" target=\"_blank\" rel=\"noopener\">StatefulSets</a> with EBS-backed <a href=\"https://kubernetes.io/docs/concepts/storage/persistent-volumes/\" target=\"_blank\" rel=\"noopener\">persistent volume claims (PVC)</a> lets a restarted primary pod recover its Raft log and identity from durable storage rather than starting from scratch. Workers keep shuffle data on local NVMe instance store for performance, but this is ephemeral. To protect data loss on workers, each shuffle partition is replicated to two other workers by setting <code>spark.celeborn.client.push.replicate.enabled=true</code>.</li> \n <li><strong>Observability:</strong> ADOT collector is deployed on the Celeborn EKS cluster. It scrapes Prometheus metrics from Celeborn’s pods, and simultaneously remote writes them to two monitoring backends. <strong>Option 1</strong> uses Amazon Managed Service for Prometheus as the metrics store, with Amazon Managed Grafana surfacing pre-built dashboards for Celeborn cluster health and Java Virtual Machine (JVM) metrics. This option requires <a href=\"https://docs.aws.amazon.com/singlesignon/latest/userguide/what-is.html\" target=\"_blank\" rel=\"noopener\">AWS IAM Identity Center</a>. <strong>Option 2</strong> deploys a self-managed Prometheus stack with a built-in Grafana on the Celeborn EKS cluster, with Prometheus configured as a remote-write receiver for the same ADOT collector. This option suits environments without IAM Identity Center or those preferring a single open-source tooling.</li> \n</ul> \n<h2 id=\"critical-configurations\">Critical configurations</h2> \n<p>The following two tables list the key configurations that make up the solution.</p> \n<ul> \n <li><strong>Spark configuration (RSS client):</strong> Tells the Spark client to use Celeborn as the shuffle manager in place of Spark’s built-in implementation.</li> \n <li><strong>Celeborn configuration (RSS server):</strong> Controls how the primary and worker Celeborn pods operate on Kubernetes.</li> \n</ul> \n<p><strong>Note:</strong> The values in the following tables are reference defaults used in this walkthrough. Before taking this pattern to production, consider the following areas.</p> \n<h3 id=\"security\">1. Security</h3> \n<p>The following considerations help you secure a Celeborn deployment across data isolation, encryption, and access control.</p> \n<h4 id=\"shuffle-data-isolation-between-teams\">1.1. Shuffle data isolation between teams</h4> \n<p>Celeborn partitions shuffle data by application ID, which is designed to prevent jobs from accidentally reading each other’s data. This is sufficient when all jobs share the same trust boundary. For multi-team deployments where data privacy is required, a <em>dedicated Celeborn cluster per team</em> is the most effective isolation boundary: each team gets its own NLB and security group, and shuffle data never co-mingles at the infrastructure level.</p> \n<h4 id=\"data-in-transit\">1.2. Data in transit</h4> \n<p>In our implementation, shuffle data travels over plain TCP between Spark executors and Celeborn workers. Access is restricted to nodes using security groups. The internal NLB isn’t reachable outside the VPC, and security group rules block all other intra-VPC traffic.</p> \n<p>For workloads requiring encryption in transit, Celeborn supports TLS on both RPC and data channels through the <code>celeborn.ssl.*</code> configuration. This is a cluster-wide setting that applies to all jobs on the cluster and must be enabled server-side in <a href=\"https://github.com/aws-samples/sample-emr-celeborn-shuffle-service/blob/main/celeborn/helm/values.yaml#L161\" target=\"_blank\" rel=\"noopener\">celeborn-defaults.conf.</a></p> \n<h4 id=\"data-at-rest\">1.3. Data at rest</h4> \n<p>EBS volumes (used for Celeborn leader pod Raft state) are encrypted with the shared AWS KMS key. NVMe instance store volumes on Celeborn worker nodes are ephemeral and not encrypted by default. Shuffle data written to NVMe is not protected by AWS KMS. For compliance requirements mandating encryption at rest, consider using EBS-backed worker storage instead of instance store, where worker pods mount <a href=\"https://kubernetes.io/docs/concepts/storage/persistent-volumes/#persistentvolumeclaims\" target=\"_blank\" rel=\"noopener\">PersistentVolumeClaim</a> (through <a href=\"https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/#volume-claim-templates\" target=\"_blank\" rel=\"noopener\">volumeClaimTemplates</a>) that reference the <a href=\"https://github.com/kubernetes-sigs/aws-ebs-csi-driver/blob/master/docs/parameters.md\" target=\"_blank\" rel=\"noopener\">encrypted gp3 StorageClass</a>. This comes at the cost of lower I/O throughput compared to local NVMe.</p> \n<h4 id=\"eks-secrets-encryption\">1.4. EKS secrets encryption</h4> \n<p>EKS clusters encrypt Kubernetes secrets at rest using AWS KMS (<a href=\"https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-eks-cluster-encryptionconfig.html\" target=\"_blank\" rel=\"noopener\">EncryptionConfig</a> in the cluster CloudFormation templates). This covers Kubernetes API objects but not application-level shuffle data.</p> \n<h4 id=\"application-level-authorization\">1.5. Application-level authorization</h4> \n<p>Our deployment enforces access control in the network layer (that is, VPC and security group rules). Celeborn also provides an application-level authorization framework, which is disabled by default. Turning it on adds a second level of security control where only applications presenting valid credentials can register with the cluster. This is recommended for production deployments where multiple workloads or teams share the same VPC subnets, ensuring that network proximity alone does not grant shuffle service access.</p> \n<p>Configuration for the Celeborn server:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-plaintext\">celeborn.auth.enabled true # Enable SASL application authentication\nceleborn.internal.port.enabled true # Required when enabling SASL authentication</code></pre> \n</div> \n<p>Configuration to enable authentication in every Spark app:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-bash\">--conf spark.celeborn.auth.enabled=true</code></pre> \n</div> \n<h3 id=\"autoscaling\">2. Autoscaling</h3> \n<p>You can scale Celeborn workers or primary pods using <code>kubectl</code>. For example:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-bash\">kubectl scale statefulsets celeborn-worker -n celeborn --replicas=6\nkubectl scale statefulsets celeborn-master -n celeborn --replicas=2</code></pre> \n</div> \n<ul> \n <li><strong>Celeborn workers</strong> register with a primary node when they start, so scaling out is safe even while the cluster is running. Scaling in, however, requires more care. Removing a worker pod during an active job may cause shuffle data loss unless <code>celeborn.client.push.replicate.enabled=true</code> is enabled. To reduce the risk of accidental disruption during node scale-in or upgrades, add a <a href=\"https://kubernetes.io/docs/concepts/workloads/pods/disruptions/#pod-disruption-budgets\" target=\"_blank\" rel=\"noopener\">Pod Disruption Budget</a> to prevent multiple workers from being evicted at the same time.</li> \n <li><strong>Spark executors</strong>: Dynamic Resource Allocation (DRA) is enabled in sample Spark jobs (<code>spark.dynamicAllocation.enabled=true</code>). This means the number of executors can scale automatically within the configured <code>minExecutors</code> and <code>maxExecutors</code> range.</li> \n</ul> \n<h3 id=\"resiliency\">3. Resiliency</h3> \n<ul> \n <li><strong>Primary Node HA:</strong> 3-replica Raft quorum with EBS-backed durable state is designed to tolerate one leader node failure without job interruption.</li> \n <li><strong>Worker replication:</strong> the setting <code>celeborn.client.push.replicate.enabled=true</code> copies each shuffle partition to two workers, designed to tolerate a single worker failure mid-job. Without replication, a worker failure causes a fetch failure and job retry.</li> \n <li><strong>Pod Disruption Budgets (PDB):</strong> not configured in this demo. Add PDBs for Celeborn’s StatefulSets to prevent simultaneous eviction during node upgrades or scale-in.</li> \n <li><strong>Multi-AZ placement:</strong> <code>podAntiAffinity</code> (preferred, weight 100) spreads pods across nodes and Availability Zones. For strict Availability Zone isolation, switch to <code>requiredDuringSchedulingIgnoredDuringExecution</code>.</li> \n</ul> \n<h3 id=\"monitoring-and-alerting\">4. Monitoring and alerting</h3> \n<p>Consider extending the Grafana dashboards with the alerting rules on:</p> \n<ul> \n <li>Active shuffle partition count: indicator of job load.</li> \n <li>Worker disk utilization: prevent shuffle storage exhaustion.</li> \n <li>Push failure rate: early signal of connectivity or capacity issues.</li> \n <li>Celeborn primary node failover: leadership changes indicate Raft instability.</li> \n</ul> \n<h2 id=\"conclusion\">Conclusion</h2> \n<p>In this post, we showed how to deploy Apache Celeborn as a Remote Shuffle Service on Amazon EKS and integrate it with Amazon EMR on EKS and Amazon EMR on EC2. By decoupling shuffle storage from Spark’s compute, this architecture delivers resilience to node failures, eliminates disk contention, and enables independent scaling of storage and compute tiers.</p> \n<p>Running Celeborn on a dedicated cluster gives you lifecycle independence from Spark, lets multiple EMR clusters share a single shuffle service, and provides fault tolerance through push-based shuffling, Raft-based high availability, and per-job data replication. It also provides automatic fallback to Spark’s built-in shuffle during maintenance windows. Stop choosing between cost and reliability.
