contentHtml: "<p>As enterprise lakehouses grow to thousands of tables across multiple business domains and regions, scaling fine-grained access control becomes a critical governance challenge. Data governance teams spend significant time manually granting table-level permissions, only to face permission drift, inconsistent enforcement, and limited auditability. Without a scalable approach, each new dataset requires manual policy updates, increasing the risk of unauthorized access and slowing time-to-insight for analysts and data scientists.</p> \n<p>In this post, we show you how to solve this problem by combining <a href=\"https://aws.amazon.com/iam/identity-center/\" target=\"_blank\" rel=\"noopener\">AWS IAM Identity Center</a>, <a href=\"https://aws.amazon.com/lake-formation/\" target=\"_blank\" rel=\"noopener\">AWS Lake Formation</a> <a href=\"https://docs.aws.amazon.com/lake-formation/latest/dg/tag-based-access-control.html\" target=\"_blank\" rel=\"noopener\">tag-based access control (TBAC)</a>, and <a href=\"https://docs.aws.amazon.com/sagemaker-unified-studio/latest/adminguide/trusted-identity-propagation.html\" target=\"_blank\" rel=\"noopener\">trusted identity propagation</a> in <a href=\"https://aws.amazon.com/sagemaker/unified-studio/\" target=\"_blank\" rel=\"noopener\">Amazon SageMaker Unified Studio</a>. You deploy a complete governance architecture using <a href=\"https://aws.amazon.com/cdk/\" target=\"_blank\" rel=\"noopener\">AWS Cloud Development Kit (AWS CDK)</a> that classifies data with LF-Tags, maps IAM Identity Center groups to tag-based policies, and enforces permissions at query time across analytics engines. The solution uses <a href=\"https://docs.aws.amazon.com/prescriptive-guidance/latest/apache-iceberg-on-aws/what-is-iceberg.html\" target=\"_blank\" rel=\"noopener\">Apache Iceberg</a> tables stored in <a href=\"https://aws.amazon.com/s3/\" target=\"_blank\" rel=\"noopener\">Amazon Simple Storage Service (Amazon S3)</a> and registered in the <a href=\"https://aws.amazon.com/glue/\" target=\"_blank\" rel=\"noopener\">AWS Glue Data Catalog</a>.</p> \n<h2 id=\"the-core-governance-challenge\">The core governance challenge</h2> \n<p>As organizations mature their lakehouse environments, governance complexity increases with each new dataset. Several challenges commonly emerge:</p> \n<ul> \n <li><strong>Explosive dataset growth</strong>: Iceberg-based lakehouses often contain thousands of tables distributed across raw, curated, and conformed zones. Each new dataset introduces additional governance requirements, making table-level permission grants operationally expensive.</li> \n <li><strong>Multi-domain data ownership</strong>: Enterprise lakehouses typically serve multiple business domains such as commercial analytics, clinical research, and regulatory reporting. These domains require strict isolation while still supporting controlled data sharing.</li> \n <li><strong>Regional data sovereignty</strong>: Organizations operating globally must enforce geographic boundaries for sensitive datasets. EU clinical trial data might be restricted by GDPR regulations, whereas US commercial datasets follow different compliance frameworks.</li> \n <li><strong>Sensitivity-based access controls</strong>: Within each domain, datasets vary in sensitivity. Pricing strategies, drug discovery research, and patient-related datasets require stricter access controls than standard operational data.</li> \n <li><strong>Role explosion</strong>: Pure RBAC approaches attempt to encode these dimensions into roles, leading to role proliferation. Manual Lake Formation grants at the table level create permission drift and limited scalability.</li> \n</ul> \n<p>To address these challenges, enterprise lakehouse governance must satisfy several criteria:</p> \n<ul> \n <li>Least-privilege access.</li> \n <li>Dynamic scalability as new datasets are onboarded.</li> \n <li>Multi-dimensional enforcement across domain, region, and sensitivity.</li> \n <li>Auditability traceable to individual users.</li> \n <li>Automation-ready, configuration-driven workflows.</li> \n</ul> \n<p>TBAC addresses each of these challenges directly. Instead of granting permissions on individual tables, you define tag-based policies that automatically apply to any resource matching the tag expression. New datasets inherit access rules through tag inheritance, eliminating manual policy updates (solving explosive dataset growth). Domain and region tags enforce strict isolation between business units (solving multi-domain ownership and regional sovereignty). Sensitivity tags control access within domains without role proliferation (solving sensitivity-based controls and role explosion). The following sections describe the architecture that implements this model and walk you through deploying it end to end.</p> \n<h2 id=\"reference-architecture-overview\">Reference architecture overview</h2> \n<p>The governance model integrates identity, metadata, and lakehouse services into a unified access architecture that enforces fine-grained permissions consistently across analytics and machine learning (ML) workloads. The architecture consists of five layers, each handling a distinct responsibility in the access control flow.</p> \n<p>The following diagram illustrates the end-to-end architecture, showing how user identity flows from IAM Identity Center through SageMaker Unified Studio to Lake Formation for tag-based policy evaluation against the AWS Glue Data Catalog and Amazon S3 storage layer.</p> \n<div style=\"width: 810px\" class=\"wp-caption alignnone\">\n <img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/BDB-5820-1.png\" alt=\"Architecture linking IAM Identity Center, SageMaker Unified Studio, Lake Formation, the Glue Data Catalog, and Amazon S3\" width=\"800\">\n <p class=\"wp-caption-text\"><br>Figure 1: End-to-end governance architecture for the enterprise lakehouse</p>\n</div> \n<p><strong>1. Identity and authentication layer</strong>: IAM Identity Center manages user identities and group memberships, integrates with corporate identity providers, and provides centralized lifecycle management for enterprise users. IAM Identity Center groups represent business roles and serve as the principals that receive Lake Formation permissions.</p> \n<p><strong>2. Unified analytics and ML access layer</strong>: <a href=\"https://docs.aws.amazon.com/sagemaker-unified-studio/latest/userguide/what-is-sagemaker-unified-studio.html\" target=\"_blank\" rel=\"noopener\">Amazon SageMaker Unified Studio</a> serves as the primary interface where analysts, data scientists, and ML engineers discover datasets, run queries, and build ML workflows. Because SageMaker Unified Studio integrates with multiple compute engines, including <a href=\"https://aws.amazon.com/athena/\" target=\"_blank\" rel=\"noopener\">Amazon Athena</a>, <a href=\"https://aws.amazon.com/glue/\" target=\"_blank\" rel=\"noopener\">AWS Glue</a>, <a href=\"https://aws.amazon.com/emr/\" target=\"_blank\" rel=\"noopener\">Amazon EMR</a>, and <a href=\"https://aws.amazon.com/redshift/\" target=\"_blank\" rel=\"noopener\">Amazon Redshift</a>, users can access data using their preferred analytics tools while maintaining consistent governance.</p> \n<p><strong>3. Governance and authorization layer</strong>: AWS Lake Formation provides fine-grained access control across AWS Glue catalog resources using <a href=\"https://docs.aws.amazon.com/lake-formation/latest/dg/TBAC-overview.html\" target=\"_blank\" rel=\"noopener\">LF-Tags</a>. Instead of granting permissions directly on databases and tables, Lake Formation evaluates LF-Tag policies dynamically and grants or denies access at query time. Governance teams define access rules once, and Lake Formation automatically applies them to new datasets as they are onboarded.</p> \n<p><strong>4. Governance automation layer</strong>: Two <a href=\"https://aws.amazon.com/lambda/\" target=\"_blank\" rel=\"noopener\">AWS Lambda</a> functions automate tag assignment and permission provisioning. JSON metadata configuration files drive both pipelines, so governance teams manage access control through configuration rather than manual console operations.</p> \n<p><strong>5. Metadata and storage layer</strong>: Apache Iceberg tables stored in Amazon S3 form the foundation of the lakehouse. You register these tables in the AWS Glue Data Catalog, which provides centralized metadata management and interoperability across analytics services. Lake Formation evaluates governance decisions at the catalog level rather than independently by each analytics engine.</p> \n<h2 id=\"end-to-end-access-flow\">End-to-end access flow</h2> \n<p>When a user queries a dataset from SageMaker Unified Studio, the following sequence occurs:</p> \n<ol type=\"1\"> \n <li>The user authenticates through IAM Identity Center and accesses SageMaker Unified Studio.</li> \n <li>SageMaker passes the user’s identity context to downstream analytics services using trusted identity propagation.</li> \n <li>The analytics engine requests data access from Lake Formation.</li> \n <li>Lake Formation evaluates LF-Tag policies against the user’s IAM Identity Center group membership.</li> \n <li>Access is granted or denied dynamically at query time.</li> \n</ol> \n<p>Because authorization decisions are centralized in Lake Formation, governance remains consistent regardless of which analytics engine the user employs.</p> \n<h2 id=\"hybrid-rbac-abac-governance-model\">Hybrid RBAC + ABAC governance model</h2> \n<p>The governance model combines identity context from IAM Identity Center with metadata-driven classification using LF-Tags. The following table summarizes how each layer contributes to the overall governance workflow.</p> \n<table border=\"1px\" width=\"100%\" cellpadding=\"10px\"> \n <tbody> \n  <tr> \n   <td><strong>Governance capability</strong></td> \n   <td><strong>IAM Identity Center contribution</strong></td> \n   <td><strong>Lake Formation LF-Tag contribution</strong></td> \n   <td><strong>Governance outcome</strong></td> \n  </tr> \n  <tr> \n   <td>Identity context</td> \n   <td>Organizes users into groups aligned with business roles</td> \n   <td>Evaluates permissions using group membership</td> \n   <td>Role-aligned access boundaries</td> \n  </tr> \n  <tr> \n   <td>Data classification</td> \n   <td>Provides role eligibility for data access</td> \n   <td>Classifies datasets by domain, region, sensitivity, and layer</td> \n   <td>Attribute-aware authorization</td> \n  </tr> \n  <tr> \n   <td>Scalability</td> \n   <td>Simplifies user lifecycle management</td> \n   <td>Automatically applies policies to newly tagged datasets</td> \n   <td>Governance that scales with dataset growth</td> \n  </tr> \n  <tr> \n   <td>Operational model</td> \n   <td>Centralizes role lifecycle operations</td> \n   <td>Enables metadata-driven policy automation</td> \n   <td>Reduced administrative overhead</td> \n  </tr> \n </tbody> \n</table> \n<p>IAM Identity Center defines who can request access, LF-Tags define what datasets are eligible, and Lake Formation enforces policies dynamically at query time.</p> \n<h2 id=\"enterprise-lf-tag-data-model\">Enterprise LF-Tag data model</h2> \n<p>A structured tagging strategy is the foundation of scalable Lake Formation governance. In this solution, the solution classifies datasets across four governance dimensions.</p> \n<table border=\"1px\" width=\"100%\" cellpadding=\"10px\"> \n <tbody> \n  <tr> \n   <td><strong>Tag Key</strong></td> \n   <td><strong>Tag Values</strong></td> \n   <td><strong>Purpose</strong></td> \n   <td><strong>Example Usage</strong></td> \n  </tr> \n  <tr> \n   <td>region</td> \n   <td>us, eu, global</td> \n   <td>Geographic data location</td> \n   <td>Enforce GDPR compliance for EU data</td> \n  </tr> \n  <tr> \n   <td>domain</td> \n   <td>commercial, clinical_research, regulatory</td> \n   <td>Business domain</td> \n   <td>Separate commercial from clinical data</td> \n  </tr> \n  <tr> \n   <td>data_class</td> \n   <td>standard, sensitive, regulated</td> \n   <td>Data sensitivity level</td> \n   <td>Restrict access to sensitive pricing data</td> \n  </tr> \n  <tr> \n   <td>layer</td> \n   <td>raw, curated, conformed</td> \n   <td>Data processing stage</td> \n   <td>Grant analysts access to curated data only</td> \n  </tr> \n </tbody> \n</table> \n<p>Together, these dimensions enable multi-dimensional authorization policies that reflect both organizational structure and regulatory requirements.</p> \n<h2 id=\"tag-inheritance-and-evaluation\">Tag inheritance and evaluation</h2> \n<p>LF-Tags can be applied at three resource levels within the Glue Data Catalog: database, table, and column. In this implementation, database-level tags define broad governance attributes (<code>domain</code>, <code>region</code>, <code>layer</code>), table-level tags capture dataset-specific sensitivity (<code>data_class</code>), and column-level tags can further restrict access to individual fields. Lake Formation evaluates the effective tag set at query time by combining inherited and explicitly assigned tags.</p> \n<p>For example, a database tagged <code>domain=commercial</code>, <code>region=us</code>, <code>layer=raw</code> automatically applies those tags to all tables within it. A table-level <code>data_class=sensitive</code> tag supplements the inherited tags to distinguish sensitive pricing data from standard sales data. This inheritance model means new tables automatically receive governance coverage without manual tag assignment. To learn more, refer to <a href=\"https://docs.aws.amazon.com/lake-formation/latest/dg/TBAC-best-practices.html\" target=\"_blank\" rel=\"noopener\">Lake Formation tag-based access control best practices</a>.</p> \n<h2 id=\"prerequisites\">Prerequisites</h2> \n<p>Before deploying the solution, complete the following setup in the <code>us-east-1</code> Region. \n</ol> \n<p>Both pipelines log execution details to Amazon CloudWatch for monitoring and troubleshooting.</p> \n<p>Two metadata JSON configuration files drive the asset tagging Lambda that
