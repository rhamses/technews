contentHtml: "<p>Amazon.com receives millions of visits every day, and behind every product recommendation on our website is a system that needs to process customer signals, run machine learning (ML) models, and deliver results before the next visit. Doing this across global marketplaces for millions of customers at tens of thousands of requests per second, while keeping experimentation fast and infrastructure costs bounded, is an orchestration challenge as much as a machine learning one.</p> \n<p>Our team built a system that addresses this challenge. This post shows how we did it using a batch-first architecture with <a href=\"https://aws.amazon.com/lake-formation/\" target=\"_blank\" rel=\"noopener\">AWS Lake Formation</a>, <a href=\"https://aws.amazon.com/managed-workflows-for-apache-airflow/\" target=\"_blank\" rel=\"noopener\">Amazon Managed Workflows for Apache Airflow (Amazon MWAA)</a>, <a href=\"https://aws.amazon.com/athena/\" target=\"_blank\" rel=\"noopener\">Amazon Athena</a>, <a href=\"https://aws.amazon.com/glue/\" target=\"_blank\" rel=\"noopener\">AWS Glue</a>, <a href=\"https://aws.amazon.com/sagemaker/\" target=\"_blank\" rel=\"noopener\">Amazon SageMaker</a>, and <a href=\"https://aws.amazon.com/dynamodb/\" target=\"_blank\" rel=\"noopener\">Amazon DynamoDB</a>, and how we later extended it with <a href=\"https://aws.amazon.com/memorydb/\" target=\"_blank\" rel=\"noopener\">Amazon MemoryDB</a> for real-time vector similarity search when we needed to incorporate more real-time signals.</p> \n<h2 id=\"architecture-overview\">Architecture overview</h2> \n<div style=\"width: 810px\" class=\"wp-caption alignnone\">\n <img loading=\"lazy\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/22/BDB-6077-1.jpg\" alt=\"Data flow from the Lake Formation data lake and Athena through Airflow-orchestrated pipelines using Glue and SageMaker into DynamoDB for batch serving and MemoryDB for real-time inference\" width=\"800\" height=\"711\">\n <p class=\"wp-caption-text\">Data flows from the centralized data lake (Lake Formation and Athena) through Airflow-orchestrated pipelines using Glue for processing and SageMaker for ML workloads, into DynamoDB for batch serving and MemoryDB for real-time inference</p>\n</div> \n<h2 id=\"the-data-lake-foundation-centralized-access-with-lake-formation\">The data lake foundation: Centralized access with Lake Formation</h2> \n<p>Every recommendation pipeline starts with data. We built a centralized data lake to create a single source of truth that any pipeline or consumer can access without duplicating data or building bespoke extract, transform, and load (ETL) pipelines.</p> \n<h3 id=\"golden-datasets-shared-once-used-everywhere\">Golden datasets: Shared once, used everywhere</h3> \n<p>Before the data lake, each recommendation pipeline independently extracted and transformed its own copy of product catalog, transaction history, and embeddings. This led to subtle inconsistencies: one pipeline might use a slightly different join logic or a stale snapshot, making it difficult to compare model performance or debug discrepancies across pipelines.</p> \n<p>Now, we publish curated, validated datasets once, and every consumer (Airflow DAGs, ML notebooks, analytics dashboards) reads from the same tables through the same governed access. This means:</p> \n<ul> \n <li><strong>New pipelines start faster.</strong> A new recommendation model does not need its own data extraction logic. It queries the existing golden datasets from day one.</li> \n <li><strong>Consistency across models.</strong> When we compare model A to model B, we know both models are trained and inferred on the same underlying data.</li> \n <li><strong>Cross-team collaboration.</strong> Multiple teams share the same tables as a single source of truth.</li> \n <li><strong>Two-way data flow.</strong> The data lake serves as both source and destination. Our pipelines read golden datasets as inputs and write computed outputs (model scores, feature sets, intermediate results) back to the lake, where they become inputs for other pipelines. This creates a compounding effect: each new pipeline enriches the lake for the next one.</li> \n</ul> \n<h3 id=\"why-lake-formation\">Why Lake Formation?</h3> \n<p>Our data is stored in <a href=\"https://aws.amazon.com/s3/\" target=\"_blank\" rel=\"noopener\">Amazon Simple Storage Service (Amazon S3)</a>, partitioned by marketplace. Our data consumers (Airflow pipelines, ML notebooks, analytics tools) live in separate AWS accounts from the data producers. We chose <a href=\"https://aws.amazon.com/lake-formation/\" target=\"_blank\" rel=\"noopener\">AWS Lake Formation</a> because it adds governance on top of S3 without requiring data migration:</p> \n<ul> \n <li><strong>Fine-grained cross-account access.</strong> Grant table-level permissions per consumer role, without managing bucket policies manually.</li> \n <li><strong>Schema governance through <a href=\"https://docs.aws.amazon.com/glue/latest/dg/catalog-and-crawler.html\" target=\"_blank\" rel=\"noopener\">AWS Glue Data Catalog</a>.</strong> Scheduled Glue crawlers infer schemas from files in S3, keeping the catalog current as data evolves.</li> \n <li><strong>Multi-Region consistency.</strong> We deploy identical infrastructure across multiple AWS Regions using AWS Cloud Development Kit (AWS CDK), each Region serving its local marketplaces.</li> \n</ul> \n<h2 id=\"orchestration-amazon-managed-workflows-for-apache-airflow-amazon-mwaa\">Orchestration: Amazon Managed Workflows for Apache Airflow (Amazon MWAA)</h2> \n<p>We chose <a href=\"https://aws.amazon.com/managed-workflows-for-apache-airflow/\" target=\"_blank\" rel=\"noopener\">Amazon Managed Workflows for Apache Airflow (Amazon MWAA)</a> as our orchestration layer. MWAA removes the operational burden of managing Airflow infrastructure: automatic scaling of workers, built-in high availability, and managed upgrades mean our team focuses on pipeline logic rather than cluster maintenance. MWAA lets us define complex multi-step workflows with rich dependencies in Python code, and its operator model lets us encapsulate team-specific conventions into reusable building blocks.</p> \n<p>Each recommendation pipeline follows a consistent pattern:</p> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/22/BDB-6077-2.jpg\" alt=\"The consistent recommendation pipeline pattern moving from data extraction through model training, batch inference, vector search, ranking, and publishing\" width=\"800\"></p> \n<p>We built a library of reusable custom Airflow operators, each encapsulating one of our core compute engines. This reduced new pipeline development from weeks to days in our team’s experience.</p> \n<h3 id=\"athena-and-aws-glue-data-access-and-processing\">Athena and AWS Glue: Data access and processing</h3> \n<p><a href=\"https://aws.amazon.com/athena/\" target=\"_blank\" rel=\"noopener\">Amazon Athena</a> is how our pipelines read from Lake Formation. Our custom operator runs SQL queries against the Glue Data Catalog and automatically runs <code>UNLOAD</code> to write results to S3: serverless, no infrastructure to manage, and integrated with the Lake Formation permission model.</p> \n<p><a href=\"https://aws.amazon.com/glue/\" target=\"_blank\" rel=\"noopener\">AWS Glue</a> handles compute-intensive data transformations through PySpark: joining datasets, filtering, deduplication, aggregation, and formatting ML outputs into final recommendation lists. We configure Glue with Auto Scaling worker pools (for example, 2–50 workers of <code>G.8X</code> type) so jobs scale with data volume per marketplace. All jobs run ephemerally: they read from S3, write to S3, and require no long-running clusters.</p> \n<h3 id=\"amazon-sagemaker-training-inference-and-vector-search\">Amazon SageMaker: Training, inference, and vector search</h3> \n<p><a href=\"https://aws.amazon.com/sagemaker/\" target=\"_blank\" rel=\"noopener\">Amazon SageMaker</a> powers the ML-intensive stages of our pipelines across three workload types, all orchestrated as steps within our Airflow DAGs:</p> \n<h4 id=\"training\">Training</h4> \n<p>We use SageMaker Training Jobs to train our recommendation models on GPU instances (for example, <code>ml.g5</code>). Training data is prepared by upstream Glue jobs and staged in S3. Our custom Airflow operator submits the training job, monitors its progress, and registers the resulting model artifact in S3. Once training completes, the artifact is immediately available for batch inference or endpoint deployment within the same DAG run. This means a single DAG can go from raw data to trained model to deployed inference without manual handoffs, and we can retrain it on fresh data every pipeline cycle with zero operator intervention.</p> \n<h4 id=\"batch-inference\">Batch inference</h4> \n<p>SageMaker Batch Transform runs our trained models at scale, generating the outputs that feed into downstream ranking and publishing steps. Our batch inference operator handles job submission, polls for completion, and writes the output location to the DAG’s S3 convention so the next Glue step can pick it up automatically. Batch Transform lets us run inference without provisioning persistent infrastructure, and we can scale instance count and type independently for every pipeline based on data volume.</p> \n<h4 id=\"vector-search\">Vector search</h4> \n<p>Generating recommendations for millions of customers requires searching across hundreds of thousands of candidate products per customer. Exact search at this scale is prohibitively expensive, so we use approximate nearest neighbor (ANN) search using <a href=\"https://github.com/facebookresearch/faiss\" target=\"_blank\" rel=\"noopener\">FAISS</a> to find similar products efficiently, run as <a href=\"https://docs.aws.amazon.com/sagemaker/latest/dg/processing-job.html\" target=\"_blank\" rel=\"noopener\">SageMaker Processing Jobs</a>.</p> \n<p>The workflow:</p> \n<ol type=\"1\"> \n <li>Build a FAISS index over the candidate catalog.</li> \n <li>Query the index with per-customer vectors to find top-K nearest neighbors.</li> \n <li>Return ranked candidate lists per customer.</li> \n</ol> \n<p>We distribute query vectors across the SageMaker Processing fleet using S3-based sharding (<code>ShardedByS3Key</code>). Each instance receives the full candidate index but only a fraction of the query vectors. Every instance builds an identical FAISS index, searches its shard of queries, and writes results to S3. The downstream Glue step merges all shards into the final recommendation lists. This lets us scale horizontally by adding instances without changing any code.</p> \n<h4 id=\"why-sagemaker-inside-mwaa\">Why SageMaker inside MWAA?</h4> \n<p>Running SageMaker jobs as MWAA tasks (rather than standalone) gives us:</p> \n<ul> \n <li><strong>End-to-end lineage.</strong> Every model training run, inference job, and vector search is tracked as part of a DAG execution. We can trace a recommendation in DynamoDB back to the exact training run, data snapshot, and ANN search that produced it.</li> \n <li><strong>Retry and failure handling.</strong> If a SageMaker job fails (spot instance preemption, transient capacity errors), Airflow retries it automatically with backoff. No manual re-runs.</li> \n <li><strong>Resource sequencing.</strong> Training must finish before inference, inference before ANN search. The Airflow dependency model handles this naturally without polling scripts or step function state machines.</li> \n <li><strong>Unified monitoring.</strong> One Airflow dashboard shows the health of all pipelines: Glue ETL, SageMaker training, SageMaker inference, and DynamoDB publishing. No context-switching between consoles.</li> \n</ul> \n<h3 id=\"putting-it-together-a-complete-pipeline-example\">Putting it together: A complete pipeline example</h3> \n<p>Our recommendation generation pipeline illustrates the full flow:</p> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/22/BDB-6077-3.jpg\" alt=\"The complete recommendation generation pipeline: data lake extraction, model training, batch inference, vector search, merge and rank with Glue, and publishing to DynamoDB\" width=\"800\"></p> \n<p>Note that the operators shown (<code>GlueSQLOperator</code>, <code>VectorSearchOperator</code>, and others) are custom internal operators built on top of the Airflow AWS provider, not open-source libraries. Here is a simplified version of what this looks like in code:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-python\">from airflow import DAG\nfrom airflow.models.baseoperator import chain\nfrom airflow.utils.task_group import TaskGroup\n\ndag = DAG(\"recommendation_generator\", schedule=\"0 18 * * 4\")  # Weekly\ntask_groups = []\n\nfor marketplace in [...]:  # global marketplaces\n    with TaskGroup(group_id=marketplace, dag=dag) as group:\n\n        # Step 1: Extract data from lake\n        candidates = GlueSQLOperator(\n            task_id=\"select_candidates\",\n            tables=[f\"{marketplace}.catalog\", f\"{marketplace}.products\"],\n            sql=\"select_candidates.sql\", dag=dag)\n\n        customer_history = GlueSQLOperator(\n            task_id=\"select_customer_history\",\n            tables=[f\"{marketplace}.transactions\"],\n            sql=\"select_customer_vectors.sql\", dag=dag)\n\n        customers = AthenaSQLOperator(\n            task_id=\"select_customers\", database=marketplace,\n            query=\"select_customer_cohort.sql\", dag=dag)\n\n        # Step 2: Train model\n        train = ModelTrainingOperator(\n            task_id=\"train_model\",\n            training_input={\"task_id\": customer_history.task_id},\n            instance_type=\"ml.g5\", dag=dag)\n\n        # Step 3: Batch inference\n        inference = BatchInferenceOperator(\n            task_id=\"batch_inference\",\n            model={\"task_id\": train.task_id},\n            input_data={\"task_id\": candidates.task_id}, dag=dag)\n\n        # Step 4: Vector search via SageMaker Processing Job\n        ann_search = VectorSearchOperator(\n            task_id=\"ann_search\",\n            index_input={\"task_id\": inference.task_id},\n            query_input={\"task_id\": customer_history.task_id},\n            k=60, instance_count=10, dag=dag)\n\n        # Step 5: Merge and rank with Glue\n        merge_and_rank = GlueSparkOperator(\n            task_id=\"merge_and_rank\",\n            script=\"merge_results.py\", dag=dag)\n\n        # Step 6: Publish to DynamoDB\n        publish = DynamoDBPublishOperator(\n            task_id=\"publish_recommendations\",\n            table_name=\"Recommendations\", dag=dag)\n\n        # Task dependencies\n        [candidates, customer_history] &gt;&gt; train &gt;&gt; inference\n        [inference, customers] &gt;&gt; ann_search &gt;&gt; merge_and_rank &gt;&gt; publish\n\n    task_groups.append(group)\n\nchain(*task_groups)  # Execute marketplaces sequentially</code></pre> \n</div> \n<h3 id=\"key-patterns-in-this-dag\">Key patterns in this DAG</h3> \n<ul> \n <li><strong>Marketplace isolation.</strong> Each marketplace runs in its own <code>TaskGroup</code>. A failure in one does not block the others.</li> \n <li><strong>Parallel data extraction.</strong> Independent Athena/Glue queries run concurrently before converging at the training step.</li> \n <li><strong>Sequential marketplace execution.</strong> <code>chain()</code> runs marketplaces one at a time to avoid resource contention across large SageMaker and Glue jobs.</li> \n <li><strong>Reusable operators.</strong> We built custom operators like <code>GlueSQLOperator</code>, <code>VectorSearchOperator</code>, and <code>DynamoDBPublishOperator</code> that encode our team’s conventions (cross-account access, S3 staging, retry logic, metrics) into shared building blocks. New pipelines are mostly configuration rather than infrastructure code, and these operators are shared across dozens of pipelines.</li> \n <li><strong>Implicit data passing.</strong> Each operator writes its output to a convention-based S3 path and downstream operators automatically resolve the upstream output location. No hard-coded paths between steps.</li> \n</ul> \n<p>This pattern powers hundreds of pipelines across global marketplaces, with each marketplace as an isolated <code>TaskGroup</code> in the DAG.</p> \n<h2 id=\"serving-layer-dynamodb-ecs\">Serving layer: DynamoDB + ECS</h2> \n<p>Our Java-based <a href=\"https://aws.amazon.com/ecs/\" target=\"_blank\" rel=\"noopener\">Amazon Elastic Container Service (Amazon ECS)</a> service reads pre-computed recommendations from <a href=\"https://aws.amazon.com/dynamodb/\" target=\"_blank\" rel=\"noopener\">Amazon DynamoDB</a> at request time:</p> \n<ol type=\"1\"> \n <li>Receive request with customer ID, marketplace, customer context, and page context.</li> \n <li>Read pre-computed recommendations from DynamoDB.</li> \n <li>Apply real-time filters (availability, eligibility constraints).</li> \n <li>Re-rank based on real-time context signals.</li> \n <li>Return the response.</li> \n</ol> \n<p>Amazon DynamoDB is designed to provide single-digit millisecond reads at our scale and time-to-live (TTL) for automatic cleanup of stale recommendations.</p> \n<h2 id=\"extending-to-real-time\">Extending to real-time</h2> \n<p>In recommendation system terms, our batch pipeline handles the retrieval stage offline. Although this covers the majority of our traffic, we identified scenarios where weekly freshness was not enough to capture what customers are doing right now. The real-time extension adds an online retrieval and ranking path for signals that cannot wait for the next batch cycle.</p> \n<p>To address these, we extended our system with <a href=\"https://aws.amazon.com/memorydb/\" target=\"_blank\" rel=\"noopener\">Amazon MemoryDB</a> (which now supports Valkey as its open-source engine) for real-time vector similarity search and <a href=\"https://docs.aws.amazon.com/sagemaker/latest/dg/realtime-endpoints.html\" target=\"_blank\" rel=\"noopener\">SageMaker real-time endpoints</a> for on-demand embedding generation. The same Airflow pipelines that publish to DynamoDB also publish product vectors to MemoryDB (through our MemoryDB publish operator), and the same model in our batch pipeline is deployed to a SageMaker endpoint for single-item inference at request time.</p> \n<p>At serving time, when we want to incorporate fresh signals, the service calls the SageMaker endpoint to generate an embedding on the fly, then queries MemoryDB for the nearest neighbors. These fresh signals include recent search queries, cart additions, and other in-session activity that changes faster than our weekly batch cycle. In our workloads, this gives us sub-millisecond vector search latency without re-running the full batch pipeline. Critically, the batch pipeline keeps the MemoryDB product index fresh. Our Airflow DAG includes a MemoryDB publish operator that refreshes the full product vector index weekly, so real-time queries always search against an up-to-date index.</p> \n<p>Batch and real-time are not competing approaches: batch handles slow-moving signals (purchase history, catalog relationships) while real-time handles fast-moving ones (current session, new arrivals, trending items). Both paths share the same models, the same data lake, and the same serving service.</p> \n<p>For a detailed deep-dive on this real-time architecture, see <a href=\"https://aws.amazon.com/blogs/database/real-time-personalized-recommendations-with-amazon-sagemaker-and-amazon-managed-valkey/\" target=\"_blank\" rel=\"noopener\">Real-time personalized recommendations with Amazon SageMaker and Amazon Managed Valkey</a>.</p> \n<h2 id=\"security-and-access-control\">Security and access control</h2> \n<p>Security is a foundational concern for a system that spans multiple AWS accounts, processes customer behavioral data, and runs across multiple AWS Regions.</p> \n<p><strong>Cross-account access:</strong> Lake Formation grants are issued to consumer-account AWS Identity and Access Management (IAM) roles, ensuring consumers can query tables without direct S3 bucket access. Each consumer role receives only the permissions it needs for its specific tables.</p> \n<p><strong>IAM execution roles:</strong> Each compute engine (MWAA, Glue, SageMaker) runs under a dedicated least-privilege IAM role.</p> \n<p><strong>Network isolation:</strong> MWAA environments and the ECS serving layer are deployed within virtual private clouds (VPCs), with separate VPC configurations per Region.</p> \n<h2 id=\"reliability-and-failure-handling\">Reliability and failure handling</h2> \n<p><strong>Regional isolation:</strong> Each AWS Region runs an independent copy of the system. DynamoDB tables are regional, each populated by the local batch pipeline. MemoryDB clusters are regional, with the product vector index refreshed by the local Airflow DAG. This means a regional failure or pipeline delay in one Region does not affect other Regions.</p> \n<p><strong>Batch pipeline failures:</strong> If a pipeline fails mid-run, the previous DynamoDB data remains live and continues serving recommendations until the next successful run. Airflow retries failed tasks automatically with configurable backoff. TTL on DynamoDB records bounds how long stale data persists. Failed pipeline runs trigger automated alerting so the on-call engineer can investigate.</p> \n<p><strong>Real-time path resilience:</strong> MemoryDB is deployed in a multi-AZ configuration with automatic failover. The real-time path is an extension of the batch system, and batch recommendations from DynamoDB remain available regardless of real-time path availability.</p> \n<h2 id=\"lessons-learned\">Lessons learned</h2> \n<ol type=\"1\"> \n <li><strong>Start batch, add real-time incrementally.</strong> Batch pipelines are easier to debug, cheaper to operate, and sufficient for most recommendation scenarios. Add real-time path only when you have clear indication that specific customer signals (for example, in-session activity, search queries) need sub-hour freshness to remain relevant.</li> \n <li><strong>Match the serving path to signal velocity.</strong> Not every signal needs real-time processing. Categorize your signals by how quickly they change, and route accordingly: batch for slow signals, real-time for fast ones, re-ranking for in-between.</li> \n <li><strong>Freshness does not always require re-computation.</strong> A batch-generated candidate set remains largely valid between runs. What changes is relative relevance. Re-ranking at serving time with recent customer activity gives the impression of real-time without the cost of real-time candidate generation.</li> \n <li><strong>A centralized data lake accelerates everything.</strong> Golden datasets eliminated weeks of per-pipeline data extraction work, made model comparisons trustworthy, and let new team members ship their first pipeline in days instead of weeks. The upfront investment in Lake Formation governance paid for itself within the first quarter.</li> \n <li><strong>Invest in reusable operators.</strong> Custom Airflow operators encapsulating Athena/Glue/SageMaker patterns let teams ship new pipelines in days. The operators encode best practices (retry logic, cross-account access, metrics) so pipeline authors can focus on business logic.</li> \n <li><strong>Separate compute from storage.</strong> S3 as the universal intermediate layer + ephemeral Glue/SageMaker jobs means you pay only for active computation. No idle clusters between weekly pipeline runs.</li> \n</ol> \n<h2 id=\"conclusion\">Conclusion</h2> \n<p>We built this system because every customer interaction is an opportunity to surface the right product at the right time. Serving tens of thousands of requests per second across millions of customers in global marketplaces, our batch-first architecture uses <a href=\"https://aws.amazon.com/lake-formation/\" target=\"_blank\" rel=\"noopener\">AWS Lake Formation</a> for governed data access, <a href=\"https://aws.amazon.com/managed-workflows-for-apache-airflow/\" target=\"_blank\" rel=\"noopener\">Amazon MWAA</a> for orchestration, <a href=\"https://aws.amazon.com/athena/\" target=\"_blank\" rel=\"noopener\">Amazon Athena</a> for data lake queries, <a href=\"https://aws.amazon.com/glue/\" target=\"_blank\" rel=\"noopener\">AWS Glue</a> for distributed processing, <a href=\"https://aws.amazon.com/sagemaker/\" target=\"_blank\" rel=\"noopener\">Amazon SageMaker</a> for training, inference, and vector search, and <a href=\"https://aws.amazon.com/dynamodb/\" target=\"_blank\" rel=\"noopener\">Amazon DynamoDB</a> for low-latency serving. When we needed to incorporate more real-time signals, we added <a href=\"https://aws.amazon.com/memorydb/\" target=\"_blank\" rel=\"noopener\">Amazon MemoryDB</a> vector search paired with SageMaker real-time endpoints for on-demand embedding generation, extending into real-time without replacing the batch foundation.</p> \n<p>The architecture choices we have made, batch for efficiency and real-time for freshness, all serve the goal of helping customers discover what they need faster. If you are building personalized experiences at scale, we hope these patterns give you a useful starting point.</p> \n<p>This would not have been possible without the Everyday Essentials engineering team, whose collective effort turned these ideas into a production system serving customers every day.
