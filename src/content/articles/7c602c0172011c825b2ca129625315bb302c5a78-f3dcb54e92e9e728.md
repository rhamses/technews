contentHtml: "<p>Time series data workloads in Amazon OpenSearch Service can present unique challenges for organizations, especially when dealing with continuously growing datasets. Many customers struggle with heavily loaded single indices that lead to high query latency, degraded performance, and unnecessary costs. In this post, we show you how to implement <a href=\"https://docs.opensearch.org/latest/im-plugin/data-streams/\" target=\"_blank\" rel=\"noopener\">data streams</a> with <a href=\"https://docs.opensearch.org/latest/im-plugin/ism/index/\" target=\"_blank\" rel=\"noopener\">Index State Management (ISM)</a> in Amazon OpenSearch Service. This approach automatically manages your time series data lifecycle and optimizes both performance and costs. Data streams distribute incoming data across multiple backing indices, helping to reduce single-index bottlenecks, while ISM policies automate rollover, retention, and storage tiering to help manage costs.</p> \n<h2 id=\"the-challenge\">The challenge</h2> \n<p>While Amazon OpenSearch Service has long provided tools like Index State Management (ISM) for time series data management, many organizations still struggle with implementing optimal patterns for their continuously growing datasets. Common challenges include:</p> \n<ul> \n <li><strong>Performance degradation from index growth:</strong> As single indices grow unbounded, query latency increases, you might find shard sizes more difficult to manage, and you might experience strain on your cluster resources.</li> \n <li><strong>Manual index management overhead</strong>: Without automation, you must invest significant operational effort to manage index lifecycles, rollover, and retention.</li> \n <li><strong>Complex setup</strong>: Coordinating index templates, aliases, and ISM policies manually can be error-prone.</li> \n <li><strong>Inefficient resource utilization</strong>: All data residing in hot storage regardless of access patterns, leading to unnecessarily high costs.</li> \n</ul> \n<h2 id=\"solution-overview\">Solution overview</h2> \n<p>As illustrated in Figure 1, our solution uses Amazon OpenSearch Service data streams combined with Index State Management to automatically distribute data across multiple indices and manage the data lifecycle. A <a href=\"https://docs.aws.amazon.com/opensearch-service/latest/developerguide/data-streams.html\" target=\"_blank\" rel=\"noopener\">data stream</a> is an abstraction layer that simplifies time series data ingestion. It provides a single, consistent endpoint for writes while automatically managing multiple backing indices behind the scenes. Instead of writing directly to individual indices, applications write to the data stream, which routes data to the appropriate backing index.</p> \n<p>Here’s how it works:</p> \n<ul> \n <li>Data streams provide a single write index when data is first ingested, which can help streamline time series data ingestion.</li> \n <li>When the backing index ages or grows to meet your defined criteria, ISM automatically performs the rollover operation.</li> \n <li>You can use ISM policies to automatically transition your aged data to different storage tiers based on rules you define and configure.</li> \n <li>You can automate the entire process through rules you define in the index template and ISM policies.</li> \n</ul> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/17/BDB-5323-1-1.png\" alt=\"Architecture diagram showing time series data flowing into an Amazon OpenSearch Service data stream, which routes writes to multiple backing indices while ISM transitions aged indices from hot to UltraWarm storage\" width=\"800\"></p> \n<p><em>Figure 1 — Time series data workflow using Amazon OpenSearch Service data streams</em></p> \n<p>Data ingests into an index according to your index template configuration. Over time, a data stream creates new indices automatically. Amazon OpenSearch Service manages the lifecycle, transitioning data from hot to warm storage according to the ISM policy configuration you define.</p> \n<h2 id=\"when-to-use-this-solution\">When to use this solution</h2> \n<p>This approach is ideal when:</p> \n<ul> \n <li>You’re ingesting time series data such as logs, metrics, traces, or Internet of Things (IoT) events.</li> \n <li>Your data is append-only and immutable.</li> \n <li>You’re ingesting millions of documents daily with long-term retention requirements.</li> \n <li>You want to reduce storage costs through storage tiering (<a href=\"https://docs.aws.amazon.com/opensearch-service/latest/developerguide/ultrawarm.html\" target=\"_blank\" rel=\"noopener\">UltraWarm</a>, <a href=\"https://docs.aws.amazon.com/opensearch-service/latest/developerguide/cold-storage.html\" target=\"_blank\" rel=\"noopener\">Cold</a> storage), as outlined in the blog post <a href=\"https://aws.amazon.com/blogs/big-data/decrease-your-storage-costs-with-amazon-opensearch-service-index-rollups/\" target=\"_blank\" rel=\"noopener\">Decrease your storage costs with Amazon OpenSearch Service index rollups</a>.</li> \n</ul> \n<h2 id=\"implementation-steps\">Implementation steps</h2> \n<h3 id=\"prerequisites\">Prerequisites</h3> \n<p>Before you begin, make sure that you have the following:</p> \n<ul> \n <li>OpenSearch Service domain with UltraWarm nodes (<a href=\"https://docs.aws.amazon.com/opensearch-service/latest/developerguide/ultrawarm.html#ultrawarm-enable\" target=\"_blank\" rel=\"noopener\">Sample CLI command to create a domain with UltraWarm nodes enabled</a>).</li> \n</ul> \n<p>The following steps walk through implementing a time series data solution, using a web server logs database as an example. You can run these steps using any of the following:</p> \n<ul> \n <li><a href=\"https://docs.opensearch.org/latest/dashboards/visualize/run-queries/\" target=\"_blank\" rel=\"noopener\">OpenSearch Dashboards Dev Tools Console</a>.</li> \n <li><a href=\"https://docs.opensearch.org/latest/getting-started/communicate/\" target=\"_blank\" rel=\"noopener\">Direct API calls using curl or any REST client</a>.</li> \n <li><a href=\"https://docs.opensearch.org/latest/im-plugin/ism/index/\" target=\"_blank\" rel=\"noopener\">OpenSearch Dashboards ISM interface (for policy management)</a>.</li> \n</ul> \n<p>For this post, we use the Dev Tools Console in OpenSearch Dashboards. To access it:</p> \n<ul> \n <li>Log in to OpenSearch Dashboards.</li> \n <li>Navigate to Dev Tools (usually found on the menu under Management).</li> \n <li>Use the interactive console to run the commands.</li> \n</ul> \n<h3 id=\"section-1-create-data-stream\">Section 1: Create data stream</h3> \n<ol type=\"1\"> \n <li><a href=\"https://docs.opensearch.org/latest/im-plugin/ism/api/#create-policy\" target=\"_blank\" rel=\"noopener\">Create an ISM policy</a></li> \n</ol> \n<p>First, create an ISM policy that defines the rules for index rollover and storage tier transitions. The following policy defines two states (hot and warm) and sets rules for when indices transition between them. The policy triggers a rollover when the document count reaches 1,000 and moves indices to warm storage after 2 minutes.</p> \n<p><strong>Note:</strong> The rollover and transitions configurations are only for demo purposes.</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-plaintext\">PUT _plugins/_ism/policies/ds-ism-policy\n{\n\"policy\": {\n\"description\": \"rollover policy when index is large\",\n\"default_state\": \"hot\",\n\"ism_template\": [\n{\n\"index_patterns\": [\"webserver-logs-data-stream*\"],\n\"priority\": 300\n}\n],\n\"states\": [\n{\n\"name\": \"hot\",\n\"actions\": [\n{\n\"rollover\": {\n\"min_doc_count\": 1000\n}\n}\n],\n\"transitions\": [\n{\n\"state_name\": \"warm\",\n\"conditions\": {\n\"min_index_age\": \"2m\"\n}\n}\n]\n},\n{\n\"name\": \"warm\",\n\"actions\": [\n{\n\"retry\": {\n\"count\": 3,\n\"backoff\": \"exponential\",\n\"delay\": \"1m\"\n},\n\"warm_migration\": {}\n}\n]\n}\n]\n}\n}</code></pre> \n</div> \n<ol start=\"2\" type=\"1\"> \n <li>Create an <a href=\"https://docs.opensearch.org/latest/im-plugin/index-templates/\" target=\"_blank\" rel=\"noopener\">index template</a> for the data stream</li> \n</ol> \n<p>An index template matches indices by a regex pattern and applies predefined settings and schema at index creation. The following template maps the required timestamp field for the data stream and associates matching indices with the ISM policy we created.</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-plaintext\">PUT _index_template/webserver-logs-data-stream-template\n{\n\"index_patterns\": [\"webserver-logs-data-stream*\"],\n\"data_stream\": {\n\"timestamp_field\": {\n\"name\": \"timestamp\"\n}\n},\n\"template\": {\n\"settings\": {\n\"plugins.index_state_management.policy_id\": \"ds-ism-policy\"\n},\n\"mappings\": {\n\"properties\": {\n\"timestamp\": {\n\"type\": \"date\"\n}\n}\n}\n}\n}</code></pre> \n</div> \n<ol start=\"3\" type=\"1\"> \n <li>Create data stream</li> \n</ol> \n<p>In this step, you create the data stream that handles the time series data. The data stream provides a single, unified write target for ingesting data while managing multiple backing indices behind the scenes.</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-plaintext\">PUT _data_stream/webserver-logs-data-stream</code></pre> \n</div> \n<ol start=\"4\" type=\"1\"> \n <li>Validate ISM policy mapping</li> \n</ol> \n<p>Verify that the ISM policy is correctly associated with the data stream that was created in the earlier step. This validation step confirms that automatic lifecycle management works as expected.</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-plaintext\">GET _plugins/_ism/explain/webserver-logs-data-stream</code></pre> \n</div> \n<p><strong>Output</strong></p> \n<p>Confirm that policy_id matches the ISM policy name you created earlier and that <strong>enabled</strong> is set to <strong>true</strong>.</p> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/17/BDB-5323-2-1.png\" alt=\"OpenSearch explain output showing the ISM policy_id mapped to the data stream with enabled set to true\" width=\"800\"></p> \n<h3 id=\"section-2-ingesting-data-to-data-stream\">Section 2: Ingesting data to data stream</h3> \n<p>In real-world scenarios, log data is typically collected and streamed directly to Amazon OpenSearch Service data streams. However, to demonstrate rollover and migration scenarios in this post, we take a different approach. We first load sample log data into a standard OpenSearch Service index, then reindex and migrate that data to a data stream.</p> \n<p>To get started, run the <a href=\"https://github.com/aws-samples/sample-webserver-logs-dataset\" target=\"_blank\" rel=\"noopener\">commands</a> in the Dev Tools console to create an index and populate it with sample log data.</p> \n<ol type=\"1\"> \n <li>Reindex existing data</li> \n</ol> \n<p>This step shows how to migrate existing data in a traditional index to the new data stream. The reindex operation includes a script that confirms each document has a valid timestamp field (timestamp). Documents without a timestamp field are skipped by the reindex operation to maintain data integrity.</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-plaintext\">POST _reindex\n{\n\"source\": {\n\"index\": \"webserver-logs\"\n},\n\"dest\": {\n\"index\": \"webserver-logs-data-stream\",\n\"op_type\": \"create\"\n},\n\"script\": {\n\"source\": \"\"\"\ntry {\n// Validate timestamp field exists and has a value\nif (ctx._source.timestamp == null || ctx._source.timestamp.empty) {\nctx.op = 'noop';\n}\n} catch (Exception e) {\n// Skip this document on any error\nctx.op = 'noop';\n}\n\"\"\"\n},\n\"conflicts\": \"proceed\"\n}</code></pre> \n</div> \n<ol start=\"2\" type=\"1\"> \n <li>Monitor index rollover</li> \n</ol> \n<p>As shown in Figure 2, after reindexing, monitor the creation of backing indices. The ISM policy evaluates indices every 5 minutes by default. Rollover occurs based on the defined conditions (1,000 documents or 2 minutes of age). Verify this using the following command.</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-plaintext\">GET _cat/indices/.ds-*?v&amp;h=index,status,health,pri,rep,docs.count,store.size,creation.date&amp;s=index</code></pre> \n</div> \n<p>The output should look like the following:</p> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/17/BDB-5323-3-1.png\" alt=\"_cat/indices output listing the .ds backing indices with their status, health, and document counts\" width=\"800\"></p> \n<p>You can also validate this from OpenSearch Dashboards by navigating to Index Management, Data streams, webserver-logs-data-stream.</p> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/17/BDB-5323-4-1.png\" alt=\"OpenSearch Dashboards Index Management page showing the webserver-logs-data-stream and its backing indices\" width=\"800\"></p> \n<p>*Figure 2 — Combined view of the _cat/indices CLI output and the OpenSearch Dashboards data stream details, showing a successful index rollover across multiple backing indices*</p> \n<ol start=\"3\" type=\"1\"> \n <li>Validate warm transition</li> \n</ol> \n<p>Verify that indices are correctly transitioning from hot to warm storage based on the ISM policy conditions. You can monitor this through OpenSearch Dashboards or API queries in the Dev Tools console.</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-plaintext\">GET _plugins/_ism/explain/webserver-logs-data-stream</code></pre> \n</div> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/17/BDB-5323-5-1.png\" alt=\"OpenSearch explain output showing backing indices transitioning from the hot state to the warm state\" width=\"800\"></p> \n<ol start=\"4\" type=\"1\"> \n <li>Verify ingested data</li> \n</ol> \n<p>Run a search against the data stream to confirm your documents were successfully indexed:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-plaintext\">GET webserver-logs-data-stream/_search\n{\n\"size\": 1\n}</code></pre> \n</div> \n<p><strong>Output</strong></p> \n<p>You should see your ingested documents returned in the <strong>hits.hits</strong> array, with the <strong><span class=\"citation\" data-cites=\"timestamp\">timestamp</span></strong> field and other fields you defined in the index template. A non-zero <strong>hits.total.value</strong> confirms data is flowing correctly through the data stream.</p> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/17/BDB-5323-6-1.png\" alt=\"Search results showing an ingested document with the @timestamp field and a non-zero hits.total.value\" width=\"800\"></p> \n<ol start=\"5\" type=\"1\"> \n <li>Clean up</li> \n</ol> \n<p>If needed, these commands remove the data stream and its template.</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-plaintext\">DELETE _data_stream/webserver-logs-data-stream\nDELETE _index_template/ webserver-logs-data-stream-template</code></pre> \n</div> \n<p>Delete the sample data.</p> \n<h2 id=\"conclusion\">Conclusion</h2> \n<p>OpenSearch data streams with ISM offer capabilities for managing time series data at scale. Organizations that implement this approach can see improved query performance through distributed load and smaller, time-based backing indices that support efficient time-range queries. Automated index management reduces operational overhead. Storage tiering automatically moves aged data to UltraWarm storage, which significantly lowers costs without sacrificing access to historical data. Combined with better scalability for growing datasets, this solution simplifies index management while delivering improved performance and a more cost-effective, maintainable infrastructure.</p> \n<hr> \n<h2>About the authors</h2> \n<footer> \n <div class=\"blog-author-box\"> \n  <div class=\"blog-author-image\"> \n   <p><img loading=\"lazy\" class=\"alignleft size-full\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/17/BDB-5323-7-1.png\" alt=\"Praveen Krishnamoorthy Ravikumar\" width=\"100\" height=\"100\"></p> \n  </div> \n  <h3 class=\"lb-h4\">Praveen Krishnamoorthy Ravikumar</h3> \n  <p>Praveen is an Analytics Specialist Solutions Architect at AWS. In this post, we show you how to implement data streams with Index State Management (ISM) in Amazon OpenSearch Service. This approach automatically manages your time series data lifecycle and optimizes both performance and costs. Data streams distribute incoming data across multiple backing indices, helping to reduce single-index bottlenecks, while ISM policies automate rollover, retention, and storage tiering to help manage costs.
