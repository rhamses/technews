contentHtml: "<p>Debugging a failed Apache Spark application on <a href=\"https://docs.aws.amazon.com/emr/latest/EMR-on-EKS-DevelopmentGuide/emr-eks.html\" target=\"_blank\" rel=\"noopener\">Amazon EMR on EKS</a> often means correlating signals from several places at once. These signals include Spark driver and executor pod logs, Spark event logs, and container termination signals that surface as pod exit codes rather than clear Spark errors. For example, a single out-of-memory failure can appear as a Kubernetes exit code 137 with no obvious link back to the line of code or configuration that caused it. This cross-system investigation can extend a single incident’s mean-time-to-resolution (MTTR) to days and requires deep Spark and Kubernetes expertise.</p> \n<p>We recently announced <a href=\"https://aws.amazon.com/about-aws/whats-new/2026/07/amazon-emr-eks-spark-troubleshooting/\" target=\"_blank\" rel=\"noopener noreferrer\">Amazon EMR on EKS now supports Apache Spark troubleshooting agent</a> extending the <a href=\"https://docs.aws.amazon.com/emr/latest/ReleaseGuide/spark-troubleshoot.html\" target=\"_blank\" rel=\"noopener noreferrer\">Apache Spark troubleshooting agent</a> to support Amazon EMR on EKS. The agent already helps data engineers diagnose Spark failures on Amazon EMR on EC2, Amazon EMR Serverless, and AWS Glue using natural language prompts. With this launch, you can now point the same workflow at a failed Amazon EMR on EKS job run. From a single natural language prompt, the agent automatically retrieves your Spark logs from Amazon Simple Storage Service (Amazon S3) or Amazon CloudWatch (depending on your job’s logging configuration) along with Spark History Server Event log data, identifies the root cause, and recommends a fix when the failure is code-related. This can help reduce incident MTTR from days to minutes. Amazon EMR on EKS customers can use the agent at no additional cost. You only pay for your existing Amazon EMR on EKS resources.</p> \n<p>In this post, we show you how to set up the agent for Amazon EMR on EKS and walk through troubleshooting a failed job run. We demonstrate the workflow from both the Amazon EMR console and an AI assistant that supports the <a href=\"https://modelcontextprotocol.io/docs/getting-started/intro\" target=\"_blank\" rel=\"noopener\">Model Context Protocol (MCP)</a>, an open standard for connecting AI assistants to external tools and data.</p> \n<h2 id=\"how-the-troubleshooting-agent-works-on-amazon-emr-on-eks\">How the troubleshooting agent works on Amazon EMR on EKS</h2> \n<p>The troubleshooting agent exposes a single interface to diagnose failed Spark applications across Amazon EMR on EKS, Amazon EMR on EC2, Amazon EMR Serverless, AWS Glue, and Amazon SageMaker notebooks. Instead of navigating different consoles, APIs, and log locations for each service, you describe your failed job in natural language, and the agent handles the rest. You can reach the agent from the Amazon EMR console or from MCP-compatible AI assistants, such as Kiro CLI, Kiro IDE, or Claude Code. We walk through both later in this post.</p> \n<p>The troubleshooting agent runs as a fully managed MCP server, so you do not need to deploy or maintain a local MCP server. It uses a single-tenant design to keep your application data and code isolated. Operations are read-only and governed by <a href=\"https://aws.amazon.com/iam\" target=\"_blank\" rel=\"noopener\">AWS Identity and Access Management (IAM)</a> permissions. The agent can only access the resources and actions your IAM role grants. Tool calls are automatically logged to <a href=\"https://aws.amazon.com/cloudtrail/\" target=\"_blank\" rel=\"noopener\">AWS CloudTrail</a> for complete auditability.</p> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/29/BDB-6061-1.jpg\" alt=\"Architecture of the Spark troubleshooting agent running as a managed MCP server with read-only IAM access and CloudTrail logging\" width=\"800\"></p> \n<p>What’s specific to Amazon EMR on EKS is how the agent gathers its inputs. On Amazon EMR on EKS, your Spark driver and executor logs can be delivered to Amazon S3, Amazon CloudWatch Logs, or both, depending on your job’s monitoring configuration. The agent handles both sources automatically:</p> \n<ul> \n <li><strong>Driver and executor pod logs in Amazon S3</strong> – When your job is configured with S3 monitoring, the agent reads the Spark event logs and the per-container <code>stderr</code>/<code>stdout</code> logs from your S3 log location, including discovering executor pod logs.</li> \n <li><strong>Driver and executor container logs in Amazon CloudWatch</strong> – When your job is configured with CloudWatch monitoring, the agent reads the driver and executor container log streams directly from your CloudWatch log group.</li> \n <li><strong>Spark History Server (SHS) data through the Amazon EMR Persistent UI</strong> – For the richer SHS signals (query plans, executor timelines, stage metrics, and configurations), the agent connects to the Amazon EMR Persistent UI for your job run, the same mechanism used for Amazon EMR on EC2.</li> \n</ul> \n<p>Drawing on years of AWS experience running millions of Spark applications at scale, the agent extracts the relevant features and signals from these sources, work that would otherwise require manual correlation across Amazon S3, Amazon CloudWatch, and the Spark UI. It then uses a large language model on <a href=\"https://aws.amazon.com/bedrock/\" target=\"_blank\" rel=\"noopener\">Amazon Bedrock</a>, grounded in a managed knowledge base of Spark and AWS troubleshooting expertise through Retrieval Augmented Generation (RAG), to produce a root cause analysis and, when the failure is code-related, a code recommendation.</p> \n<p>The large language model (LLM), the knowledge base, and the retrieval that connects them are fully managed as part of the agent. There’s nothing for you to provision, host, or tune. This managed inference is provided at no additional cost for Amazon EMR on EKS. You pay only for the AWS resources you already use to run your Spark applications and to validate recommended changes.</p> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/29/BDB-6061-2.jpg\" alt=\"The agent extracting signals from Amazon S3 and Amazon CloudWatch and using an Amazon Bedrock model with a knowledge base to produce a root cause analysis\" width=\"800\"></p> \n<h2 id=\"getting-started\">Getting started</h2> \n<p>You can use the agent from either the Amazon EMR console or an MCP client. Both rely on setting up a single IAM role. The following sections walk through creating that role and then troubleshooting a failed job run with each method.</p> \n<h3 id=\"set-up-iam-permissions\">Set up IAM permissions</h3> \n<p>The IAM role grants the agent read access to the diagnostic sources it analyzes, such as your Amazon EMR on EKS job runs, the Amazon EMR Persistent UI, and your Spark logs in Amazon S3 and Amazon CloudWatch. Creating this role is the only setup required for the console experience. The MCP client path has a few additional prerequisites, covered later in the section on troubleshooting from an MCP client.</p> \n<p>To run the commands in this section, you need the <a href=\"https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html#getting-started-install-instructions\" target=\"_blank\" rel=\"noopener\">AWS Command Line Interface (AWS CLI)</a> (version 2.30.0 or later) installed and configured with your AWS credentials. For instructions, see <a href=\"https://docs.aws.amazon.com/cli/latest/userguide/getting-started-quickstart.html\" target=\"_blank\" rel=\"noopener\">Setting up the AWS CLI</a>.</p> \n<h4 id=\"step-1-create-the-iam-role\">Step 1: Create the IAM role</h4> \n<p>The agent uses your IAM role to authorize operations at the AWS service level. It can only access what your role allows. Create a role your account can assume, then attach a policy granting the permissions the agent needs for Amazon EMR on EKS.</p> \n<p>First, set some variables for the commands that follow. <code>ACCOUNT_ID</code> is derived from your configured credentials. Set <code>REGION</code> to the AWS Region where you run your Amazon EMR on EKS workloads:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-bash\">ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)\nREGION=us-east-2   # replace with your Region</code></pre> \n</div> \n<p>Create a trust policy that allows your account to assume the role, and create the role:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-bash\">cat &gt; mcp-trust-policy.json &lt;&lt; EOF\n{\n  \"Version\": \"2012-10-17\",\n  \"Statement\": [\n    {\n      \"Sid\": \"AllowAccountToAssumeRole\",\n      \"Effect\": \"Allow\",\n      \"Principal\": { \"AWS\": \"arn:aws:iam::${ACCOUNT_ID}:root\" },\n      \"Action\": \"sts:AssumeRole\"\n    }\n  ]\n}\nEOF\n\naws iam create-role \\\n  --role-name SparkTroubleshootingMCPRole \\\n  --assume-role-policy-document file://mcp-trust-policy.json</code></pre> \n</div> \n<h4 id=\"step-2-attach-amazon-emr-on-eks-permissions\">Step 2: Attach Amazon EMR on EKS permissions</h4> \n<p>Create and attach a policy granting the agent read access to your Amazon EMR on EKS job runs, the Amazon EMR Persistent UI, and your S3 and CloudWatch logs. Replace <code>amzn-s3-demo-logging-bucket</code> with the name of your logging bucket and replace <code>my_log_group_name</code> and <code>my_log_stream_prefix</code> with your CloudWatch log group name and log stream prefix, respectively.</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-bash\">cat &gt; emr-eks-policy.json &lt;&lt; EOF\n{\n  \"Version\": \"2012-10-17\",\n  \"Statement\": [\n    {\n      \"Sid\": \"EMREKSReadAccess\",\n      \"Effect\": \"Allow\",\n      \"Action\": [\n        \"emr-containers:DescribeJobRun\",\n        \"emr-containers:DescribeVirtualCluster\",\n        \"emr-containers:ListJobRuns\",\n        \"emr-containers:ListVirtualClusters\"\n      ],\n      \"Resource\": [\"*\"]\n    },\n    {\n      \"Sid\": \"EMREKSPersistentApp\",\n      \"Effect\": \"Allow\",\n      \"Action\": [\n        \"elasticmapreduce:CreatePersistentAppUI\",\n        \"elasticmapreduce:DescribePersistentAppUI\",\n        \"elasticmapreduce:GetPersistentAppUIPresignedURL\"\n      ],\n      \"Resource\": [\"*\"]\n    },\n    {\n      \"Sid\": \"EMREKSS3LogAccess\",\n      \"Effect\": \"Allow\",\n      \"Action\": [\"s3:GetObject\", \"s3:ListBucket\"],\n      \"Resource\":[\n        \"arn:aws:s3:::amzn-s3-demo-logging-bucket\",\n        \"arn:aws:s3:::amzn-s3-demo-logging-bucket/*\"\n      ]\n    },\n    {\n      \"Sid\": \"EMREKSCloudWatchLogAccess\",\n      \"Effect\": \"Allow\",\n      \"Action\": [\n        \"logs:GetLogEvents\",\n        \"logs:DescribeLogGroups\",\n        \"logs:DescribeLogStreams\"\n      ],\n      \"Resource\": [\n        \"arn:aws:logs:*:*:log-group:my_log_group_name:log-stream:my_log_stream_prefix/*\"\n      ]\n    }\n  ]\n}\nEOF\n\naws iam put-role-policy \\\n  --role-name SparkTroubleshootingMCPRole \\\n  --policy-name EMREKSTroubleshootingAccess \\\n  --policy-document file://emr-eks-policy.json</code></pre> \n</div> \n<p><strong>Note:</strong> If you prefer an automated setup, an AWS CloudFormation template that creates this role with the required permissions is available in the <a href=\"https://docs.aws.amazon.com/emr/latest/ReleaseGuide/spark-troubleshooting-agent-setup.html\" target=\"_blank\" rel=\"noopener\">setup documentation</a>. The previous CLI steps give you the same result with finer control over each permission.</p> \n<h2 id=\"troubleshooting-a-failed-amazon-emr-on-eks-job-run\">Troubleshooting a failed Amazon EMR on EKS job run</h2> \n<p>You can reach the troubleshooting agent two ways: directly from the Amazon EMR console, or from an MCP-compatible AI assistant such as Claude Code. We walk through both, using two different failures to show the range of what the agent diagnoses.</p> \n<h3 id=\"option-1-troubleshoot-from-the-amazon-emr-console\">Option 1: Troubleshoot from the Amazon EMR console</h3> \n<p>The console offers the fastest path. Once you’ve created the IAM role in the Set up IAM permissions section, no additional setup is required. Here we troubleshoot a job that failed with a driver out-of-memory error. The application generates a large dataset and calls <code>collect()</code> to pull it back to the driver, exceeding the configured <code>spark.driver.maxResultSize</code> of 512 MiB.</p> \n<ol type=\"1\"> \n <li>Open the <a href=\"https://console.aws.amazon.com/emr/\" target=\"_blank\" rel=\"noopener\">Amazon EMR console</a>, choose <strong>Virtual clusters</strong> (under Amazon EMR on EKS), and select the virtual cluster that ran your job.</li> \n <li>In the <strong>Jobs</strong> list, find your failed job run and choose its <strong>Failed</strong> status. This opens a popover with a <strong>Troubleshoot with AI</strong> button.</li> \n</ol> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/29/BDB-6061-3.jpg\" alt=\"The failed job run popover in the Amazon EMR console with the Troubleshoot with AI button\" width=\"800\"></p> \n<ol start=\"3\" type=\"1\"> \n <li>Choose <strong>Troubleshoot with AI</strong>. The agent analyzes the job and returns its findings directly on the console, namely the analysis insights, a root cause, and a recommendation. For this job, it identifies that the <code>collect()</code> operation on line 24 attempts to materialize the full result set on the driver, exceeding the <code>spark.driver.maxResultSize</code> safety limit. This fails the job before an actual driver out-of-memory crash. Because the failure stems from the application code, the agent also returns a <strong>code recommendation</strong>: a before-and-after diff that replaces the <code>collect()</code> call with a distributed write to the destination path. Executors then persist their partitions in parallel instead of funneling the data through the driver.</li> \n</ol> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/29/BDB-6061-4.jpg\" alt=\"Agent results in the console showing the root cause and a before-and-after code recommendation for the collect() failure\" width=\"800\"></p> \n<h3 id=\"option-2-troubleshoot-from-an-mcp-client-claude-code\">Option 2: Troubleshoot from an MCP client (Claude Code)</h3> \n<p>You can also use the agent from MCP-compatible AI assistants. This option requires a one-time setup to connect the assistant to the agent’s MCP servers, and it unlocks a conversational workflow where the agent chains from analysis into a concrete code fix. In this walkthrough, we use <a href=\"https://code.claude.com/docs/en/overview\" target=\"_blank\" rel=\"noopener\">Claude Code</a>.</p> \n<h4 id=\"prerequisites\">Prerequisites</h4> \n<p>In addition to the IAM role from the Set up IAM permissions section, the MCP client path requires:</p> \n<ul> \n <li>Python 3.10 or higher.</li> \n <li>The <code>uv</code> package manager. For instructions, see <a href=\"https://docs.astral.sh/uv/getting-started/installation/\" target=\"_blank\" rel=\"noopener\">Installing uv</a>.</li> \n <li>Claude Code installed. For instructions, see <a href=\"https://code.claude.com/docs/en/setup#install-claude-code\" target=\"_blank\" rel=\"noopener\">Install Claude Code</a>. You can also use another MCP-compatible AI assistant such as Kiro CLI or Kiro IDE.</li> \n</ul> \n<h4 id=\"configure-an-aws-cli-profile\">Configure an AWS CLI profile</h4> \n<p>Configure a profile that assumes the IAM role you created, so the MCP servers call AWS with the agent’s permissions:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-bash\">export IAM_ROLE=arn:aws:iam::${ACCOUNT_ID}:role/SparkTroubleshootingMCPRole\nexport SMUS_MCP_REGION=${REGION}\n\naws configure set profile.smus-mcp-profile.role_arn ${IAM_ROLE}\naws configure set profile.smus-mcp-profile.source_profile default\naws configure set profile.smus-mcp-profile.region ${SMUS_MCP_REGION}</code></pre> \n</div> \n<h4 id=\"add-the-mcp-servers\">Add the MCP servers</h4> \n<p>The troubleshooting agent provides two tools through two MCP servers: <code>analyze_spark_workload</code> (workload analysis and root cause) and <code>spark_code_recommendation</code> (code fixes). Add both to your assistant.</p> \n<p>For Claude Code:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-bash\">claude mcp add sagemaker-unified-studio-mcp-troubleshooting \\\n    -- uvx mcp-proxy-for-aws@latest \\\n    https://sagemaker-unified-studio-mcp.${SMUS_MCP_REGION}.api.aws/spark-troubleshooting/mcp \\\n    --service sagemaker-unified-studio-mcp --profile smus-mcp-profile \\\n    --region ${SMUS_MCP_REGION} --read-timeout 180\n\nclaude mcp add sagemaker-unified-studio-mcp-code-rec \\\n    -- uvx mcp-proxy-for-aws@latest \\\n    https://sagemaker-unified-studio-mcp.${SMUS_MCP_REGION}.api.aws/spark-code-recommendation/mcp \\\n    --service sagemaker-unified-studio-mcp --profile smus-mcp-profile \\\n    --region ${SMUS_MCP_REGION} --read-timeout 180</code></pre> \n</div> \n<p>Verify your setup by running the <code>/mcp</code> command in Claude Code to confirm the <code>sagemaker-unified-studio-mcp-troubleshooting</code> and <code>sagemaker-unified-studio-mcp-code-rec</code> servers are connected and their tools are available.</p> \n<p>For Kiro CLI:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-bash\"># Add the Spark Troubleshooting MCP server\nkiro-cli-chat mcp add \\\n    --name \"sagemaker-unified-studio-mcp-troubleshooting\" \\\n    --command \"uvx\" \\\n    --args \"[\\\"mcp-proxy-for-aws@latest\\\",\\\"https://sagemaker-unified-studio-mcp.${SMUS_MCP_REGION}.api.aws/spark-troubleshooting/mcp\\\", \\\"--service\\\", \\\"sagemaker-unified-studio-mcp\\\", \\\"--profile\\\", \\\"smus-mcp-profile\\\", \\\"--region\\\", \\\"${SMUS_MCP_REGION}\\\", \\\"--read-timeout\\\", \\\"180\\\"]\" \\\n    --timeout 180000 \\\n    --scope global\n\n# Add the Spark Code Recommendation MCP server\nkiro-cli-chat mcp add \\\n    --name \"sagemaker-unified-studio-mcp-code-rec\" \\\n    --command \"uvx\" \\\n    --args \"[\\\"mcp-proxy-for-aws@latest\\\",\\\"https://sagemaker-unified-studio-mcp.${SMUS_MCP_REGION}.api.aws/spark-code-recommendation/mcp\\\", \\\"--service\\\", \\\"sagemaker-unified-studio-mcp\\\", \\\"--profile\\\", \\\"smus-mcp-profile\\\", \\\"--region\\\", \\\"${SMUS_MCP_REGION}\\\", \\\"--read-timeout\\\", \\\"180\\\"]\" \\\n    --timeout 180000 \\\n    --scope global</code></pre> \n</div> \n<p>Verify with the <code>/tools</code> command in Kiro CLI to confirm the <code>analyze_spark_workload</code> and <code>spark_code_recommendation</code> tools are available.</p> \n<h4 id=\"run-the-agent\">Run the agent</h4> \n<p>For this walkthrough, we troubleshoot a different failure to show how the agent chains from analysis into a concrete code fix. The job is a small PySpark application that reads a CSV file into a DataFrame and registers it as a temporary view named <code>people</code>. It runs a Spark SQL query to uppercase the <code>Name</code> column before displaying the results. The job run failed because the query calls <code>UPPERX</code>, a function that doesn’t exist in Spark SQL (it’s a typo for the built-in <code>UPPER</code>).</p> \n<p>From the Claude Code terminal (or MCP-compatible assistants), describe your failed job run in natural language, providing the virtual cluster ID and job run ID:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-plaintext\">Debug my EMR on EKS job with job run id &lt;jr-id&gt; and virtual cluster id &lt;vc-id&gt; in &lt;region&gt;</code></pre> \n</div> \n<p>The agent invokes the <code>analyze_spark_workload</code> tool, which automatically:</p> \n<ol type=\"1\"> \n <li>Calls the Amazon EMR on EKS API to retrieve your job run’s configuration and determine where its logs are stored.</li> \n <li>Retrieves your Spark logs from Amazon S3 or Amazon CloudWatch, depending on your job’s logging configuration.</li> \n <li>Connects to the Amazon EMR Persistent UI to extract Spark UI features such as the execution plan, stage metrics, and executor timelines.</li> \n <li>Analyzes the correlated signals and returns a root cause explanation.</li> \n</ol> \n<p>For this job, the agent returns:</p> \n<p><strong>Root cause: SQL function error.</strong> Your Spark SQL query references a function <code>UPPERX</code> that doesn’t exist in an available function catalog (<code>system.builtin</code>, <code>system.session</code>, or <code>spark_catalog.default</code>). Category: <code>SQL_ERROR</code>. The job failed because the function name can’t be resolved. <code>UPPERX</code> is almost certainly a typo for the built-in <code>UPPER</code> function.</p> \n<p>Because the failure is code-related, the agent then chains into the <code>spark_code_recommendation</code> tool, which produces a concrete before-and-after fix:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-diff\">  df.createOrReplaceTempView(\"people\")\n\n- result = spark.sql(\"SELECT UPPERX(Name) FROM people\")\n+ result = spark.sql(\"SELECT UPPER(Name) FROM people\")\n  result.show()\n\n  spark.stop()</code></pre> \n</div> \n<p>The two tools work together. <code>analyze_spark_workload</code> identifies the root cause, and when the failure stems from the application code, <code>spark_code_recommendation</code> returns the exact edit to make. You review the recommendation and apply it with full control over the change. The agent only provides the analysis and recommendations.</p> \n<h2 id=\"supported-failure-categories\">Supported failure categories</h2> \n<p>The troubleshooting agent diagnoses a wide range of Apache Spark failures on Amazon EMR on EKS, including:</p> \n<ul> \n <li><strong>Out-of-memory and resource exhaustion</strong> – Driver and executor out-of-memory errors, including driver-side failures from operations like <code>collect()</code> and executor terminations that surface as Kubernetes pod exit codes (such as exit code 137).</li> \n <li><strong>Data skew and shuffle issues</strong> – Uneven partitioning and shuffle failures that concentrate work on a few executors.</li> \n <li><strong>Configuration errors</strong> – Misconfigured Spark settings that lead to failures or inefficiency.</li> \n <li><strong>Code-level issues</strong> – Problems such as incorrect API usage, unbounded <code>collect()</code> calls, and user-defined function (UDF) errors, for which the agent can recommend code fixes.</li> \n</ul> \n<p>Code recommendations are supported for PySpark workloads on Amazon EMR on EKS, Amazon EMR on EC2, Amazon EMR Serverless, and AWS Glue.</p> \n<h2 id=\"conclusion\">Conclusion</h2> \n<p>With support for Amazon EMR on EKS, the Apache Spark troubleshooting agent gives platform and data engineering teams a shared workflow for investigating failed Spark applications. By bringing together Spark and Kubernetes diagnostic signals, the agent can reduce manual investigation and repeated handoffs between teams, helping engineers identify likely causes and corrective actions faster.</p> \n<p>There’s no additional charge for using the troubleshooting agent, including the large language model used through Amazon Bedrock. You pay only for the AWS resources used to run your Spark applications and validate recommended changes.</p> \n<p>To get started:</p> \n<ul> \n <li>Follow the setup guide in the <a href=\"https://docs.aws.amazon.com/emr/latest/ReleaseGuide/spark-troubleshoot.html\" target=\"_blank\" rel=\"noopener\">Apache Spark troubleshooting agent documentation</a>.</li> \n <li>Configure the MCP servers in Kiro CLI, Kiro IDE, or Claude Code, and try troubleshooting a failed Amazon EMR on EKS job run.</li> \n</ul> \n<hr> \n<h2>About the authors</h2> \n<footer> \n <div class=\"blog-author-box\"> \n  <div class=\"blog-author-image\"> \n   <p><img loading=\"lazy\" class=\"alignleft size-full\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/29/BDB-6061-5.jpg\" alt=\"Vara Bonthu\" width=\"100\" height=\"100\"></p> \n  </div> \n  <h3 class=\"lb-h4\">Vara Bonthu</h3> \n  <p><a href=\"https://www.linkedin.com/in/varaprofile/\" target=\"_blank\" rel=\"noopener\">Vara</a> is a Principal Open Source Specialist SA leading Data on EKS at AWS, driving open source initiatives and helping AWS customers to diverse organizations.
