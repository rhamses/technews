contentHtml: "<p>Modern organizations processing vast amounts of data on <a href=\"https://docs.aws.amazon.com/emr/latest/ManagementGuide/emr-what-is-emr.html\" target=\"_blank\" rel=\"noopener\">Amazon EMR</a> with <a href=\"https://docs.aws.amazon.com/emr/latest/ReleaseGuide/emr-spark.html\" target=\"_blank\" rel=\"noopener\">Apache Spark</a> face a growing cost challenge. As the number of encrypted Amazon Simple Storage Service (Amazon S3) objects grows, AWS Key Management Service (AWS KMS) decrypt API calls multiply rapidly, driving up operational costs. Consider a retail organization processing hundreds of terabytes of customer transaction data daily in S3 encrypted with AWS KMS. Each Spark task accessing an encrypted S3 object triggers an AWS KMS decrypt API call. At scale, these calls accumulate into significant and often unexpected cost increases. This is especially true for workloads that require key auditability and cannot switch to <a href=\"https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-key.html\" target=\"_blank\" rel=\"noopener\">S3 Bucket Keys</a>. S3 Bucket Keys reduce AWS KMS request costs by decreasing the number of calls from S3 to AWS KMS. However, S3 Bucket Keys limit per-object key auditability in AWS CloudTrail, which might not meet the compliance requirements of some organizations.</p> \n<p>This post introduces practical techniques to reduce AWS KMS decrypt costs. You can reduce API call volume and lower costs without compromising encryption. It covers three techniques: optimizing file formats (including Apache Iceberg), aggregating data, and using AWS Glue Data Catalog partition indexes.</p> \n<h2 id=\"optimization-techniques\">Optimization techniques</h2> \n<p>The following sections describe three techniques you can apply independently or together to reduce the number of AWS KMS decrypt API calls.</p> \n<h3 id=\"use-data-aggregation\">Use data aggregation</h3> \n<p>Data aggregation reduces redundant AWS KMS decrypt API calls by consolidating smaller files into larger blocks. When Spark reads many small files from S3, each file triggers its own decrypt call. By combining multiple small files into fewer, larger files, you can reduce the total number of AWS KMS API invocations. This technique is effective for read-heavy workloads that involve numerous small files stored on S3.</p> \n<p>You can use AWS CloudTrail to monitor changes in API call frequency and validate the effectiveness of data aggregation in reducing costs.</p> \n<h4 id=\"step-1-benchmark-baseline-performance\">Step 1: Benchmark baseline performance</h4> \n<p>Before applying optimizations, establish baseline metrics to quantify improvements.</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-python\">from pyspark.sql import SparkSession\nimport time\n\nspark = SparkSession.builder.appName(\"Baseline Job\").getOrCreate()\nstart_time = time.time()\ndata = spark.read.format(\"csv\").load(\"s3://amzn-s3-demo-bucket/data/\")\nend_time = time.time()\nload_time = end_time - start_time\nprint(f\"Load time: {load_time:.2f} seconds\")\ndata_count = data.count()\nprint(f\"AWS KMS calls triggered: {data_count} rows processed\")</code></pre> \n</div> \n<p>The following figure shows the number of AWS KMS Decrypt API calls captured in AWS CloudTrail. id=\"optimize-file-formats-and-compression\">Optimize file formats and compression</h3> \n<p>Selecting appropriate file formats and applying compression minimizes the amount of data read from S3 and the number of AWS KMS decrypt operations.</p> \n<h4 id=\"columnar-formats-parquetorc\">Columnar formats (Parquet/ORC)</h4> \n<p>Columnar file formats like Parquet and ORC let Spark read only the required columns for analysis, which improves performance for analytical queries. For example, you can convert raw CSV data to Parquet to benefit from better I/O efficiency and query optimization.</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-python\">df = spark.read.format(\"csv\") \\\n    .option(\"header\", \"true\") \\\n    .option(\"inferSchema\", \"true\") \\\n    .load(\"s3://emr-kms-demo/data/\")\n\n# Set compression for Parquet files\nspark.conf.set(\"spark.sql.parquet.compression.codec\", \"snappy\")\n\ndf.write.format(\"parquet\").save(\"s3://amzn-s3-demo-bucket/parquet-data/\")</code></pre> \n</div> \n<h4 id=\"iceberg-format\">Iceberg format</h4> \n<p>Apache <a href=\"https://docs.aws.amazon.com/emr/latest/ReleaseGuide/emr-iceberg.html\" target=\"_blank\" rel=\"noopener\">Iceberg</a> is a modern table format designed for large-scale analytic datasets. It supports schema evolution, snapshot isolation, and time travel, making it an excellent choice for data lakes on S3. When used with <a href=\"https://docs.aws.amazon.com/glue/latest/dg/aws-glue-programming-python.html\" target=\"_blank\" rel=\"noopener\">PySpark</a>, Apache Iceberg simplifies data management by automatically optimizing file layouts, handling partitions, and integrating with Spark catalogs.</p> \n<p>The following PySpark example uses Iceberg with Amazon EMR and S3:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-bash\">pyspark \\\n  --packages org.apache.iceberg:iceberg-spark-runtime-3.4_2.12:1.4.2 \\\n  --conf spark.sql.extensions=org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions \\\n  --conf spark.sql.catalog.spark_catalog=org.apache.iceberg.spark.SparkSessionCatalog \\\n  --conf spark.sql.catalog.spark_catalog.type=hadoop \\\n  --conf spark.sql.catalog.spark_catalog.warehouse=s3://amzn-s3-demo-bucket/iceberg-warehouse \\\n  --conf spark.sql.defaultCatalog=spark_catalog</code></pre> \n</div> \n<div class=\"hide-language\"> \n <pre><code class=\"language-python\">df = spark.read.format(\"csv\") \\\n    .option(\"header\", \"true\") \\\n    .option(\"inferSchema\", \"true\") \\\n    .load(\"s3://amzn-s3-demo-bucket/data/\")\n\nspark.conf.set(\"spark.sql.parquet.compression.codec\", \"snappy\")\n\n# Write data to Iceberg table\ndf.writeTo(\"iceberg_from_emr_data\").using(\"iceberg\").create()\n\n# Read from Iceberg table\nspark.read.table(\"iceberg_from_emr_data\").show()</code></pre> \n</div> \n<h4 id=\"compression\">Compression</h4> \n<p>Using compression reduces data size and speeds up reads and writes between S3 and Spark. Using AWS Glue Data Catalog partition indexes reduces scanning overhead and the number of AWS KMS API calls.</p> \n<p>Without a partition index, when Spark queries a partitioned table, AWS Glue Data Catalog returns all partitions by calling the GetPartitions API. Spark then reads every S3 object across all returned partitions. Because each S3 object is individually encrypted, Spark must call the AWS KMS Decrypt API once per object. More objects mean more decrypt calls and higher costs. With a partition index, AWS Glue performs server-side partition filtering, returning only matching partitions.</p> \n<h4 id=\"step-1-baseline-query-without-partition-index\">Step 1: Baseline query without partition index</h4> \n<p>Using an Amazon EMR Spark job:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-python\">spark.sql(\"SELECT * FROM default.`kms-demoevents` WHERE year='2000' AND month='04'\").count()</code></pre> \n</div> \n<p>Then check CloudTrail for the <code>kms:Decrypt</code> call count.</p> \n<p>The following figure shows the AWS KMS Decrypt API call count when running the baseline query without a partition index.
