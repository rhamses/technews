They have no built-in way to coordinate workflows between their separate Amazon Managed Workflows for Apache Airflow (<a href=\"https://aws.amazon.com/managed-workflows-for-apache-airflow/\" target=\"_blank\" rel=\"noopener\">Amazon MWAA</a>) environments, where each team or business unit manages its own isolated environment. Cross-environment orchestration has traditionally relied on time-based polling, complex custom sensors, or API-based triggers that introduce latency and reliability concerns. The Apache Airflow Datasets feature (introduced in version 2.4) added data-aware scheduling of Directed Acyclic Graphs (DAGs, the workflow definitions that specify tasks and their execution order) within a single Amazon MWAA environment. However, teams running Airflow across multiple accounts still had no way to coordinate workflows between environments.</p> \n<p>With Apache Airflow 3.0, now available on <a href=\"https://aws.amazon.com/about-aws/whats-new/2025/10/apache-airflow-3-amazon-mwaa/\" target=\"_blank\" rel=\"noopener\">Amazon MWAA 3.0</a>, you get event-driven cross-account orchestration that responds to upstream events as they happen, without polling overhead or tight environment coupling. Using Amazon Simple Queue Service (<a href=\"https://aws.amazon.com/sqs/\" target=\"_blank\" rel=\"noopener\">Amazon SQS</a>) as the message broker, Asset Watchers replace polling-based sensors with event-driven triggers. This approach reduces orchestration latency from minutes to seconds and reclaims worker resources previously consumed by polling sensors. It also improves message reliability, because Amazon SQS retains coordination signals even when the consumer environment is temporarily unavailable.</p> \n<p>In this post, you learn how to design and deploy cross-account orchestration patterns using asset-based scheduling in Airflow 3.0 with Amazon SQS integration. Verify that the triggerer is healthy and running in consumer Amazon MWAA environment before expecting event-driven DAG triggers. If the triggerer is down, Amazon SQS messages will accumulate in the queue but won’t trigger downstream DAGs until the triggerer recovers. For more information, read the <a href=\"https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/event-scheduling.html\" target=\"_blank\" rel=\"noopener\">Asset Watchers documentation</a>.</li> \n <li>Amazon SQS messages have a default retention period of 4 days (configurable up to 14 days). If the consumer environment is unavailable for longer than the retention period, messages will be lost. Consider configuring a dead-letter queue to capture messages that fail processing, and adjust the <code>MessageRetentionPeriod</code> based on recovery requirements.</li> \n <li>Cross-account Amazon SQS access requires both an IAM identity policy on the producer’s execution role and a resource-based policy on the Amazon SQS queue. If either policy is missing or misconfigured, message delivery will silently fail. For guidance on cross-account access patterns, refer to <a href=\"https://aws.amazon.com/blogs/security/four-ways-to-grant-cross-account-access-in-aws/\" target=\"_blank\" rel=\"noopener\">Four ways to grant cross-account access on AWS</a>.</li> \n <li>Set the Amazon SQS <code>VisibilityTimeout</code> higher than the expected time for the Asset Watcher to process a message. If the timeout is too short, messages might be redelivered and trigger duplicate DAG runs. Review the <a href=\"https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html\" target=\"_blank\" rel=\"noopener\">Amazon SQS visibility timeout documentation</a> when tuning this value.</li> \n <li>Each Amazon MWAA environment has limits on the number of DAGs, triggerers, and concurrent DAG runs. If you plan to scale to multiple Asset Watchers monitoring different Amazon SQS queues, check the current Amazon MWAA quotas before making design decisions.</li> \n <li>Asset URIs must match exactly between the Asset Watcher definition and the consumer DAG’s <code>schedule</code> parameter. A mismatch, even in casing or trailing characters, will prevent the consumer DAG from being triggered. Define assets in a single DAG file to avoid inconsistencies.</li> \n <li>Pin the provider packages <code>apache-airflow-providers-amazon</code> and <code>apache-airflow-providers-common-messaging</code> to versions compatible with Airflow. Incompatible versions might cause import errors that prevent the triggerer from starting. Use a constraints file as described in this post to avoid dependency conflicts.</li> \n</ul> \n<h2 id=\"agent-skills\">Agent skills</h2> \n<p>AI coding assistants are most useful when they have context about your specific architecture and constraints, not only general programming patterns. When they are, they introduce operational considerations that differ from sensor-based polling approaches.</p> \n<p>This section covers how to choose the right cross-environment orchestration pattern, how to configure the infrastructure that Asset Watchers depend on (IAM, Amazon VPC, dependencies), and how to design producer and consumer DAGs that are reliable in production.</p> \n<h3 id=\"cross-account-iam\">Cross-account IAM</h3> \n<ul> \n <li>Producer execution role needs <code>sqs:SendMessage</code> and <code>sqs:GetQueueUrl</code> scoped to the specific queue ARN to avoid <code>sqs:*</code>.</li> \n <li>Amazon SQS queue resource policy must allow the producer role for <code>sqs:SendMessage</code> and consumer role for <code>sqs:ReceiveMessage</code>, <code>sqs:DeleteMessage</code>, <code>sqs:GetQueueAttributes</code>, and <code>sqs:GetQueueUrl</code>.</li> \n <li>Test cross-account access with the AWS CLI before deploying DAGs. Debugging AWS IAM through Airflow task logs is much harder and slower than catching misconfigurations at the CLI level.</li> \n <li>Enable Amazon SQS server-side encryption for production queues.</li> \n</ul> \n<h3 id=\"triggerer-health\">Triggerer health</h3> \n<ul> \n <li>Airflow Asset Watchers run in the triggerer, not the scheduler. Verify triggerer health in the Airflow UI after deploying consumer DAGs.</li> \n <li>The health API can report <em>healthy</em> even when components are broken. Cross-check by verifying Amazon CloudWatch log streams exist for the Triggerer log group.</li> \n <li>Monitor <code>airflow-&lt;ENV&gt;-Triggerer</code> CloudWatch logs for <code>ClientError</code>, <code>QueueDoesNotExist</code>, or <code>ImportError</code>.</li> \n <li>Set Amazon CloudWatch alarms on Amazon SQS <code>ApproximateNumberOfMessagesVisible</code> and the depth of your dead-letter queue (DLQ), which captures messages that fail processing after the maximum number of receive attempts.</li> \n <li>Pin provider versions with a constraints file to prevent dependency conflicts.</li> \n</ul> \n<h3 id=\"amazon-vpc-networking\">Amazon VPC networking</h3> \n<ul> \n <li>Private subnets must route 0.0.0.0/0 to a NAT Gateway. Without it, workers and triggerers silently fail while the web server appears healthy.</li> \n <li>Use two NAT Gateways (one per Availability Zone) for production high availability.</li> \n <li>For private routing mode, use Amazon VPC Endpoints (Amazon S3, Amazon SQS, Amazon CloudWatch Logs, and Amazon Elastic Container Registry (Amazon ECR)) instead of NAT.</li> \n <li>Confirm Amazon CloudWatch log streams exist for Scheduler, Worker, DAGProcessing, and Triggerer. Empty log groups mean containers aren’t running.</li> \n <li>Security group must allow self-referencing inbound traffic and unrestricted outbound.</li> \n</ul> \n<h3 id=\"dependency-management\">Dependency management</h3> \n<ul> \n <li>Pin provider versions with == and use a constraints file. Unpinned versions break on environment updates.</li> \n <li>Test dependencies locally with <a href=\"https://github.com/aws/amazon-mwaa-docker-images\" target=\"_blank\" rel=\"noopener\">MWAA Docker images</a> before deploying.</li> \n <li>Check the <code>requirements_install_ip</code> log stream after updates. If networking was unavailable at creation, force reinstall with a new <code>requirements-s3-object-version</code>.</li> \n <li>Review pre-installed base packages before adding to <code>requirements.txt</code> to avoid version conflicts.</li> \n</ul> \n<h3 id=\"choosing-an-orchestration-pattern\">Choosing an orchestration pattern</h3> \n<p>Not every cross-environment dependency warrants an Asset Watcher. Data engineering teams running Apache Airflow across multiple AWS accounts have no built-in way to coordinate workflows between separate Amazon MWAA environments. With Airflow 3.0 on Amazon MWAA, you can use asset-based scheduling and Asset Watchers with Amazon SQS to build event-driven, cross-account orchestration that replaces polling with near real-time triggers.
