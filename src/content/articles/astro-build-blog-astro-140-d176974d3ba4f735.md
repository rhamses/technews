contentHtml: "<article>\n<p>We just released Astro 1.4.0, featuring:</p>\n<ul>\n<li><strong><a target=\"_blank\" href=\"https://astro.build/blog/astro-140/#astro-cookies\">Astro.cookies</a></strong>: A simplified approach to manipulating cookies within Astro pages and API routes.</li>\n<li><strong><a target=\"_blank\" href=\"https://astro.build/blog/astro-140/#strict-dependency-installation\">Support for strict dependency installation</a></strong>: pnpm users can now have the benefits of its default semi-strict dependency installation strategy in Astro projects.</li>\n<li><strong><a target=\"_blank\" href=\"https://astro.build/blog/astro-140/#better-control-over-style-ordering\">Better control over style ordering</a></strong>: We’ve fixed style ordering so that styles defined in Astro components are lower in bundled CSS than global styles you import.</li>\n<li><strong><a target=\"_blank\" href=\"https://astro.build/blog/astro-140/#jsx-support-in-vue\">JSX support in Vue</a></strong>: Vue users can now define components using JSX and TSX.</li>\n</ul>\n<p>You can update your projects by running <code>npm install astro@latest</code>.</p>\n<h2 id=\"astrocookies\">Astro.cookies</h2>\n<img src=\"https://astro.build/_image?href=%2F_astro%2Fastro-cookies.Dxm4_Sob.webp&w=1536&h=1141&f=webp\" srcset=\"https://astro.build/_image?href=%2F_astro%2Fastro-cookies.Dxm4_Sob.webp&w=768&h=571&f=webp 768w, https://astro.build/_image?href=%2F_astro%2Fastro-cookies.Dxm4_Sob.webp&w=1500&h=1114&f=webp 1500w\" alt=\"Code example that shows off using Astro.cookies\"><p>Sites built with <abbr title=\"Server-side rendering\">SSR</abbr> are able to read and set cookies in Astro. Previously, reading cookies required reading the <code>cookie</code> header in the request (<code>Astro.request</code> in pages) and then parsing it using a library. Writing cookies required serializing into <code>Set-Cookie</code> headers in the returned Response.</p>\n<p>Given the importance of cookies in stateful and authenticated apps, we felt a simplified abstraction for cookies would make all of this easier.</p>\n<p>With <code>Astro.cookies</code> you can read and write cookies with a <a target=\"_blank\" href=\"https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Map\">Map</a>-like API. In the above example, we check if a <code>prefs</code> cookie exists and set a default value if it doesn’t. We then get its value and use it in our template.</p>\n<p>Check out <a target=\"_blank\" href=\"https://docs.astro.build/en/reference/api-reference/#astrocookies\">the docs</a> for the full API reference.</p>\n<h2 id=\"strict-dependency-installation\">Strict dependency installation</h2>\n<p>If you are using <a target=\"_blank\" href=\"https://pnpm.io/\">pnpm</a> in your Astro project, you can now install your dependencies using its strict dependency algorithm. Since Astro runs code on your behalf, you previously needed to <a target=\"_blank\" href=\"https://pnpm.io/blog/2020/10/17/node-modules-configuration-options-with-pnpm#the-worst-case---hoisting-to-the-root\">hoist packages to the root</a>, which meant that most of your dependencies (and <em>their</em> dependencies) were installed into the top-level <code>node_modules/</code> folder.</p>\n<p>A stricter installation is more <em>correct</em>, in that a package can only import dependencies it defines in its own <code>package.json</code>. A stricter installation is also faster, as Node.js does not need to look in as many folders to find packages.</p>\n<p>This feature comes for free in Astro 1.4.0 for new projects. Existing projects can remove hoisting configuration they might have in a <code>.npmrc</code> file.</p>\n<h2 id=\"better-control-over-style-ordering\">Better control over style ordering</h2>\n<p>When Astro 1.0 was released, we changed our CSS scoping mechanism to use the <a target=\"_blank\" href=\"https://developer.mozilla.org/en-US/docs/Web/CSS/:where\"><code>:where()</code> pseudo-class</a>. This allowed you to better control specificity with the usual means, such as adding class names.</p>\n<p>Making this switch, we didn’t realize that the default ordering of styles wasn’t ideal: styles defined directly in a component came before imported styles in the CSS output, giving component styles a lower precedence than imported styles.</p>\n<p>In 1.4.0, styles you write in Astro components will come <em>after</em> global styles imported. In practice, this means that if you write a component like so:</p>\n<p><strong>Title.astro</strong></p>\n<div><figure><pre><code><div><p><span>---</span></p></div><div><p><span>import</span><span> </span><span>\"../styles/global-titles.css\"</span></p></div><div><p><span>---</span></p></div><div><p><span>&lt;</span><span>h1</span><span>&gt;</span><span>{</span><span>Astro</span><span>.</span><span>props</span><span>.</span><span>title</span><span>}</span><span>&lt;/</span><span>h1</span><span>&gt;</span></p></div><div><p><span>&lt;</span><span>style</span><span>&gt;</span></p></div><div><p><span>  </span><span>h1</span><span> {</span></p></div><div><p><span><span>    </span></span><span>color: aliceblue;</span></p></div><div><p><span><span>  </span></span><span>}</span></p></div><div><p><span>&lt;/</span><span>style</span><span>&gt;</span></p></div></code></pre></figure></div>\n<p>When your site is built and the CSS is bundled you get something like the following:</p>\n<div><figure><pre><code><div><p><span>h1</span><span> {</span></p></div><div><p><span><span>  </span></span><span>color: onyx;</span></p></div><div><p><span>}</span></p></div><div><p><span>/* /src/components/Title.astro */</span></p></div><div><p><span>h1</span><span>:where</span><span>(</span><span>.astro-1234</span><span>)</span><span> {</span></p></div><div><p><span><span>  </span></span><span>color: aliceblue;</span></p></div><div><p><span>}</span></p></div></code></pre></figure></div>\n<p>Given that these selectors both have the same specificity, the one listed later—the one scoped to your Title.astro component—will prevail. Within that component, the <code>h1</code> will have <code>color: aliceblue</code>, but any <code>h1</code> defined outside of your component will be <code>onyx</code>.</p>\n<p>You get the best of both worlds: styles defined in Astro are better prioritized if they have the same specificity, but you can override this by increasing specificity when needed.</p>\n<p>The output CSS order is now (from lowest to highest precedence):</p>\n<ol>\n<li>CSS in your <code>public/</code> folder added as <code>&lt;link&gt;</code> tags in the head.</li>\n<li>CSS imported in your frontmatter, in the order of your import statements (depth-first).</li>\n<li>CSS defined in Astro style tags.</li>\n</ol>\n<p>We’re currently writing up full documentation to explain how CSS ordering works and how you can control CSS priority via ordering and specificity.</p>\n<h2 id=\"jsx-support-in-vue\">JSX support in Vue</h2>\n<img src=\"https://astro.build/_image?href=%2F_astro%2Fvue-jsx.BmPzHAXY.webp&w=1536&h=984&f=webp\" srcset=\"https://astro.build/_image?href=%2F_astro%2Fvue-jsx.BmPzHAXY.webp&w=768&h=492&f=webp 768w, https://astro.build/_image?href=%2F_astro%2Fvue-jsx.BmPzHAXY.webp&w=1500&h=961&f=webp 1500w\" alt=\"Code example that shows a JSX component defined with Vue\">\n<p>You can now use JSX and TSX with the <a target=\"_blank\" href=\"https://github.com/withastro/astro/blob/d08093f7d4f9762c0edc71e14c796d7ea8038cda/packages/integrations/vue/README.md\">Vue integration</a>. Setting <code>jsx: true</code> in the integrations options enables the <a target=\"_blank\" href=\"https://github.com/vitejs/vite/tree/main/packages/plugin-vue-jsx\">@vitejs/plugin-vue-jsx</a> Vite plugin, which does most of the work, and you can use any of its options.</p>\n<hr>\n<p>Thanks to everyone that contributed to this outstanding release. In addition to these new features there were also a bunch of bug fixes throughout the core packages and integrations. See the <a target=\"_blank\" href=\"https://github.com/withastro/astro/pull/4903\">release notes</a> to learn more.</p></article>"
