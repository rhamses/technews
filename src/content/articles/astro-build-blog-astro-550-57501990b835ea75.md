Alternatively, upgrade manually by running the upgrade command for your package manager:</p>\n<div><figure><pre><code><div><p><span># Recommended:</span></p></div><div><p><span>npx</span><span> </span><span>@astrojs/upgrade</span></p></div><div><p><span># Manual:</span></p></div><div><p><span>npm</span><span> </span><span>install</span><span> </span><span>astro@latest</span></p></div><div><p><span>pnpm</span><span> </span><span>upgrade</span><span> </span><span>astro</span><span> </span><span>--latest</span></p></div><div><p><span>yarn</span><span> </span><span>upgrade</span><span> </span><span>astro</span><span> </span><span>--latest</span></p></div></code></pre></figure></div>\n<h2 id=\"better-support-for-diagramming-tools-in-markdown\">Better support for diagramming tools in Markdown</h2>\n<p>Tools like Mermaid and D2 let you define charts and diagrams in code blocks in Markdown, which are then rendered inside the content. Until now, using these in Astro could be tricky, because Astro’s default syntax highlighting would interfere with how the code blocks were rendered.</p>\n<p>Astro 5.5 introduces a new <a target=\"_blank\" href=\"https://docs.astro.build/en/reference/configuration-reference/#markdownsyntaxhighlightexcludelangs\"><code>excludeLangs</code></a> option in your Markdown configuration that makes it possible to skip syntax highlighting for specific language code blocks. This unlocks the ability to use tools like these without disabling syntax highlighting for other blocks.</p>\n<p>Here’s an example of how to configure Astro to disable highlighting for the <code>mermaid</code> language after installing the <a target=\"_blank\" href=\"https://github.com/remcohaszing/rehype-mermaid\"><code>rehype-mermaid</code> plugin</a>:</p>\n<div><figure><pre><code><div><p><span>import</span><span> { </span><span>defineConfig</span><span> } </span><span>from</span><span> </span><span>'astro/config'</span><span>;</span></p></div><div><p><span>import</span><span> </span><span>rehypeMermaid</span><span> </span><span>from</span><span> </span><span>'rehype-mermaid'</span><span>;</span></p></div><div><p><span>export</span><span> </span><span>default</span><span> </span><span>defineConfig</span><span>({</span></p></div><div><p><span>  </span><span>markdown</span><span>: {</span></p></div><div><p><span>    </span><span>syntaxHighlight</span><span>: {</span></p></div><div><p><span>      </span><span>type</span><span>: </span><span>'shiki'</span><span>,</span></p></div><div><p><span>      </span><span>excludeLangs</span><span>: [</span><span>'mermaid'</span><span>, </span><span>'math'</span><span>],</span></p></div><div><p><span><span>    </span></span><span>},</span></p></div><div><p><span>    </span><span>rehypePlugins</span><span>: [</span><span>rehypeMermaid</span><span>],</span></p></div><div><p><span><span>  </span></span><span>},</span></p></div><div><p><span>});</span></p></div></code></pre></figure></div>\n<p>Then, you can create diagrams directly in your Markdown content:</p>\n<div><figure><pre><code><div><p><span>```mermaid</span></p></div><div><p><span>graph TD</span></p></div><div><p><span><span>    </span></span><span>A[Start] --&gt; B{Is it working?}</span></p></div><div><p><span><span>    </span></span><span>B --&gt;|Yes| C[Great!]</span></p></div><div><p><span><span>    </span></span><span>B --&gt;|No| D[Debug]</span></p></div><div><p><span><span>    </span></span><span>D --&gt; B</span></p></div><div><p><span>```</span></p></div></code></pre></figure></div>\n<p>This will then render as a diagram in your page.</p>\n<p>Massive thanks to <a target=\"_blank\" href=\"https://github.com/chrisirhc\">Chris Chua</a> for this contribution.</p>\n<h2 id=\"type-safe-experimental-sessions\">Type-safe experimental sessions</h2>\n<p>Astro 5.5 adds support for proper TypeScript typing for your session data, letting you banish <code>any</code> mistakes. Experimental support for session storage was added in Astro 5.1, but previously all session data was untyped. Now you can define the types of your session data by extending the global <code>App.SessionData</code> interface in your project’s <code>src/env.d.ts</code> file:</p>\n<div><figure><pre><code><div><p><span>declare</span><span> </span><span>namespace</span><span> </span><span>App</span><span> {</span></p></div><div><p><span>  </span><span>interface</span><span> </span><span>SessionData</span><span> {</span></p></div><div><p><span>    </span><span>user</span><span>: {</span></p></div><div><p><span>      </span><span>id</span><span>: </span><span>string</span><span>;</span></p></div><div><p><span>      </span><span>email</span><span>: </span><span>string</span><span>;</span></p></div><div><p><span><span>    </span></span><span>};</span></p></div><div><p><span>    </span><span>lastLogin</span><span>: </span><span>Date</span><span>;</span></p></div><div><p><span><span>  </span></span><span>}</span></p></div><div><p><span>}</span></p></div></code></pre></figure></div>\n<p>This is optional, and any keys not defined in this interface will be treated as <code>any</code>. However, defining the types will provide accurate type checking and autocomplete when working with session data in your site:</p>\n<div><figure><pre><code><div><p><span>---</span></p></div><div><p><span>const</span><span> </span><span>user</span><span> = </span><span>await</span><span> </span><span>Astro</span><span>.</span><span>session</span><span>.</span><span>get</span><span>(</span><span>'user'</span><span>);</span></p></div><div><p><span>// `user` is properly typed as `{ id: string; email: string; } | undefined`</span></p></div><div><p><span>const</span><span> </span><span>something</span><span> = </span><span>await</span><span> </span><span>Astro</span><span>.</span><span>session</span><span>.</span><span>get</span><span>(</span><span>'something'</span><span>);</span></p></div><div><p><span>// `something` is typed as `any` since it's not defined in the interface</span></p></div><div><p><span>// TypeScript will catch this error:</span></p></div><div><p><span>Astro</span><span>.</span><span>session</span><span>.</span><span>set</span><span>(</span><span>'user'</span><span>, </span><span>1</span><span>); </span><span>// Error: Type 'number' is not assignable to type '{ id: string; email: string; }'</span></p></div><div><p><span>---</span></p></div></code></pre></figure></div>\n<p>This improvement makes working with sessions in Astro more reliable and helps catch potential errors at development time rather than at runtime.</p>\n<p>For more information, see the <a target=\"_blank\" href=\"https://docs.astro.build/en/reference/experimental-flags/sessions/#session-data-types\">experimental sessions docs</a>.</p>\n<h2 id=\"improved-heading-id-compatibility\">Improved heading ID compatibility</h2>\n<p>Astro 5.5 introduces a new <a target=\"_blank\" href=\"https://docs.astro.build/en/reference/experimental-flags/heading-id-compat/\"><code>experimental.headingIdCompat</code></a> flag that generates heading IDs consistent with other common Markdown processors like those used by GitHub and npm.</p>\n<p>By default, Astro removes trailing dashes from the end of IDs it generates for headings containing special characters. This behavior differs from other common Markdown processors, which can cause inconsistencies when linking to headings across different platforms.</p>\n<p>With the new configuration flag, you can now ensure your heading IDs follow the same convention as other platforms:</p>\n<div><figure><pre><code><div><p><span>import</span><span> { </span><span>defineConfig</span><span> } </span><span>from</span><span> </span><span>'astro/config'</span><span>;</span></p></div><div><p><span>export</span><span> </span><span>default</span><span> </span><span>defineConfig</span><span>({</span></p></div><div><p><span>  </span><span>experimental</span><span>: {</span></p></div><div><p><span>    </span><span>headingIdCompat</span><span>: </span><span>true</span><span>,</span></p></div><div><p><span><span>  </span></span><span>},</span></p></div><div><p><span>});</span></p></div></code></pre></figure></div>\n<p>This is particularly useful for sites that might have anchor links shared between GitHub, npm documentation, and your Astro website.</p>\n<p>Experimental flags aren’t only for cool new features. Sometimes, things just have to <em>change</em>.  We also use experimental flags to carefully introduce you to breaking changes that will eventually become the new default behavior. <a target=\"_blank\" href=\"https://docs.astro.build/en/reference/experimental-flags/preserve-scripts-order/\"><code>experimental.preserveScriptOrder</code></a> is one of them!</p>\n<p>When rendering multiple <code>&lt;style&gt;</code> and <code>&lt;script&gt;</code> tags on the same page, Astro currently reverses their order in your generated HTML output. This can give unexpected results, for example CSS styles that apply in development mode being overridden by earlier style tags once your site is built.</p>\n<p>You can enable it in your configuration like this:</p>\n<div><figure><pre><code><div><p><span>import</span><span> { </span><span>defineConfig</span><span> } </span><span>from</span><span> </span><span>'astro/config'</span><span>;</span></p></div><div><p><span>export</span><span> </span><span>default</span><span> </span><span>defineConfig</span><span>({</span></p></div><div><p><span>  </span><span>experimental</span><span>: {</span></p></div><div><p><span>    </span><span>preserveScriptOrder</span><span>: </span><span>true</span><span>,</span></p></div><div><p><span><span>  </span></span><span>},</span></p></div><div><p><span>});</span></p></div></code></pre></figure></div>\n<p>With the new <code>preserveScriptOrder</code> flag set to <code>true</code>, Astro will generate your styles and scripts in the order they are defined. If you were previously compensating for Astro’s behavior by writing these out of order, you will need to update your code.</p>\n<p>We think this change makes sense in the long run for everyone, so we encourage you to test this now to ensure it works before it becomes the default behavior.</p>\n<p>Thanks to <a target=\"_blank\" href=\"https://github.com/withastro/astro/issues/12264\">JaneSmith</a> for first identifying this issue, and <a target=\"_blank\" href=\"https://github.com/TheOtterLord\">Reuben Tier</a> for contributing the compiler fix!</p>\n<h2 id=\"bug-fixes\">Bug fixes</h2>\n<p>As always, we’ve been working hard on fixing issues since the <a target=\"_blank\" href=\"https://astro.build/blog/astro-540\">5.4 release</a>.
