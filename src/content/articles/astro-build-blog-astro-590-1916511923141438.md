By default, web pages can load whichever scripts and styles they want, from wherever they want. The most powerful defense against XSS attacks is to limit this. A Content Security Policy (CSP) lets you do that, with tools to lock down the page to a list of trusted resources.</p>\n<p>While these are powerful tools, they can be tricky to implement by hand: it’s much easier if your framework can do it for you. Astro 5.9 introduces experimental support for CSP out of the box, making it easier to secure your Astro projects. This is Astro’s most upvoted feature request so far, and we certainly took our time to implement it. We hope this is worth the wait!</p>\n<p>We designed the feature to work in all Astro render modes (static pages, dynamic pages and single page applications),\nwith maximum flexibility and type-safety in mind. You heard that right! You can ditch the unpleasant <code>unsafe-inline</code> workaround, use all the Astro features that you like,\nany adapter for any runtime, and add an extra layer of security to your site.</p>\n<h3 id=\"how-it-works\">How it works</h3>\n<p>One of the reasons why users like Astro is because it works everywhere – static hosts, serverless hosts, Node.js, edge runtimes, and with\nmany frontend libraries (React, Vue, Svelte, etc). Because of this, an Astro CSP solution must work everywhere with any library.</p>\n<p>We started by considering two common approaches to supporting CSP:</p>\n<ul>\n<li>The <a target=\"_blank\" href=\"https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP#nonces\"><code>nonce</code> header</a>, which generates a random value for each request and injects it into the HTML.</li>\n<li>Calculating <a target=\"_blank\" href=\"https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP#hashes\">hashes</a> of all the resources shipped to the browser, ensuring that only the scripts and styles that you expect to run will be executed.</li>\n</ul>\n<p>While the <code>nonce</code> header is straightforward to implement, it requires a server/edge function that is able to generate\nthe random value of <code>nonce</code>, add the <code>Content-Security-Policy</code> header to the <code>Response</code> object, and rewrite the HTML to inject the <code>nonce</code> value for each <code>&lt;script&gt;</code> and <code>&lt;style&gt;</code> element.\nThis solution wouldn’t work for websites that are served from static hosts e.g. GitHub pages, and it wouldn’t work for Single Page Applications (SPAs)\nwhere scripts and styles might be injected dynamically during the lifecycle of the application.</p>\n<p>The generation of hashes is more complex to implement because it requires knowing the exact content of every script and stylesheet on the page. However, it can support more use cases than the <code>nonce</code> header, so our choice was clear even though another fork in the road was waiting for us.</p>\n<p>The CSP standard allows hashes to be provided to the browser either via the <code>Response</code> header called <code>Content-Security-Policy</code>, or using a <code>&lt;meta&gt;</code> element called <code>http-equiv='content-security-policy'</code>. As you may have guessed, using the <code>Response</code> header wouldn’t work for Astro, because it would leave out static websites and SPAs. For this reason, we decided to use the <code>&lt;meta&gt;</code> element to provide the CSP to the browser.</p>\n<p>The end result is that Astro’s CSP will generate the <code>&lt;meta&gt;</code> element for you, with all the hashes of the scripts and styles that will be used in the page, <em>even the ones that will be loaded dynamically</em>!</p>\n<h3 id=\"usage\">Usage</h3>\n<p>To try out Astro’s CSP in your own projects today, enable the new experimental flag:</p>\n<div><figure><pre><code><div><p><span>import</span><span> { </span><span>defineConfig</span><span> } </span><span>from</span><span> </span><span>\"astro/config\"</span></p></div><div><p><span>export</span><span> </span><span>default</span><span> </span><span>defineConfig</span><span>({</span></p></div><div><p><span>    </span><span>experimental</span><span>: {</span></p></div><div><p><span>        </span><span>csp</span><span>: </span><span>true</span></p></div><div><p><span><span>    </span></span><span>}</span></p></div><div><p><span>})</span></p></div></code></pre></figure></div>\n<p>If you already use the <code>Content-Security-Policy</code> header in your website via middleware or other means, you can still use it, and the browser will use the stricter policy of the header and the <code>&lt;meta&gt;</code> element.</p>\n<p>But we didn’t stop there! content loaders</h2>\n<p>Astro content collections have always supported rendering Markdown files using the <a target=\"_blank\" This could be confusing as it was inconsistent with how Markdown was rendered in other parts of your site, and didn’t use the same Markdown configuration.</p>\n<p>Astro 5.9 adds a new helper function to the loader context - <code>renderMarkdown</code> - that allows you to render Markdown content directly within your loaders. In most cases this is what you want – and they are applied with low specificity so your own styles override them.</p>\n<p>However in some cases you may want to disable these default styles entirely. This is particularly useful when using Tailwind 4, because it uses CSS cascade layers to apply styles, making it difficult to override Astro’s default styles.</p>\n<p>Astro 5.8.1 added a new <code>image.experimentalDefaultStyles</code> boolean configuration option for applying these default styles.
