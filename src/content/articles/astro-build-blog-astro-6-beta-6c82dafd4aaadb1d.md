If you need a website that loads fast with great SEO, then Astro is for you.</p>\n<p><strong>The new Astro 6 development server refactor brings Astro’s development and production codepaths much closer together and increases stability for Astro on all runtimes</strong>. Now, you can develop your Astro project using the same runtime as production. Notably, this unlocks first-class support for Astro on <a target=\"_blank\" href=\"https://developers.cloudflare.com/workers/\">Cloudflare Workers</a>, with more access to runtime-specific primitives and a more true-to-life development experience.</p>\n<p>To try Astro 6 Beta, run the <code>create astro</code> command:</p>\n<div><figure><pre><code><div><p><span>npm</span><span> tool:</p>\n<div><figure><pre><code><div><p><span># Recommended:</span></p></div><div><p><span>npx</span><span> </span><span>@astrojs/upgrade</span><span> v6 upgrade guide</a> for full details and migration guidance for breaking changes.</p>\n<h2 id=\"a-redesigned-astro-dev\">A redesigned <code>astro dev</code></h2>\n<p>The headline feature of Astro 6 is a completely redesigned development server (<code>astro dev</code>).</p>\n<p>Astro 6 was the chance to significantly improve how Astro manages different environments (client, server, and prerender) with an internal refactor to use <strong><a target=\"_blank\" href=\"https://vite.dev/guide/api-environment\">Vite’s Environment API</a></strong> which closes the gap between prod and dev.</p>\n<p>Previously, code that worked locally could behave somewhat differently once deployed. Platform-specific features often couldn’t be tested until after deployment. In some cases, Astro even had separate logic paths for “dev” and “prod,” increasing the chance of edge-case bugs.</p>\n<p>By leveraging this API internally, Astro can now run your web application inside the same runtime you deploy to, with the same JavaScript engine, the same globals, and the same platform APIs available during development.</p>\n<p>This refactor enables Astro to:</p>\n<ol>\n<li><strong>Run against real runtimes</strong> – Development can execute inside the same runtime as production.</li>\n<li><strong>Support more platforms</strong> – Cloudflare Workers today, with a foundation that supports additional runtimes in the future.</li>\n</ol>\n<p>By unifying the development and production code paths we’ve already discovered and fixed numerous subtle bugs that existed only in development or only in production.</p>\n<p>This change makes Astro 6 more stable for projects on all runtimes, including non-Node.js environments. All users of Astro will enjoy greater stability and reliability as a result of this upgrade!</p>\n<h2 id=\"spotlight-astro-6-on-cloudflare-workers\">Spotlight: Astro 6 on Cloudflare Workers</h2>\n<p>Cloudflare Workers are the most complete example of what the new <code>astro dev</code> makes possible today.</p>\n<p>Until now, the Astro Cloudflare integration simulated the Workers runtime during development. You’d work against special Astro-specific APIs like <code>Astro.locals.runtime</code> that provided polyfills and mocks of Cloudflare’s platform, then deploy and hope everything behaved the same in production.</p>\n<p>With Astro 6 Beta, <code>astro dev</code> can now run your entire application using <strong>workerd</strong>, Cloudflare’s open-source JavaScript runtime. This is the same runtime that powers Cloudflare Workers in production—not a simulation or polyfill.</p>\n<p>In Astro 6, you can now develop directly against real platform APIs, catching issues during development rather than after deployment. The special simulation APIs like <code>Astro.locals.runtime</code> are no longer needed.</p>\n<p>When you run <code>astro dev</code> with Cloudflare support, you now have access to:</p>\n<ul>\n<li><strong>Durable Objects</strong> – Test stateful serverless objects locally</li>\n<li><strong>KV Namespaces</strong> – Develop against real key-value storage</li>\n<li><strong>R2 Storage</strong> – Work with object storage in dev</li>\n<li><strong>Workers Analytics Engine</strong> – Test analytics collection</li>\n<li><strong>Environment variables &amp; secrets</strong> – Full config support</li>\n<li><strong>Hot Module Replacement (HMR)</strong> – Real-time updates while running inside workerd</li>\n</ul>\n<p>Access your Cloudflare bindings directly using the <code>cloudflare:workers</code> module:</p>\n<div><figure><pre><code><div><p><span>---</span></p></div><div><p><span>import</span><span> { </span><span>env</span><span> } </span><span>from</span><span> </span><span>\"cloudflare:workers\"</span><span>;</span></p></div><div><p><span>// Access KV storage directly - works in both dev and production</span></p></div><div><p><span>const</span><span> </span><span>kv</span><span> = </span><span>env</span><span>.</span><span>MY_KV_NAMESPACE</span><span>;</span></p></div><div><p><span>await</span><span> </span><span>kv</span><span>.</span><span>put</span><span>(</span><span>\"visits\"</span><span>, </span><span>\"1\"</span><span>);</span></p></div><div><p><span>const</span><span> </span><span>visits</span><span> = </span><span>await</span><span> </span><span>kv</span><span>.</span><span>get</span><span>(</span><span>\"visits\"</span><span>);</span></p></div><div><p><span>---</span></p></div><div><p><span>&lt;</span><span>p</span><span>&gt;Visits: </span><span>{</span><span>visits</span><span>}</span><span>&lt;/</span><span>p</span><span>&gt;</span></p></div></code></pre></figure></div>\n<p>The Cloudflare adapter has also been significantly enhanced alongside the new dev server:</p>\n<ul>\n<li><strong><code>astro preview</code></strong> now works with Cloudflare, letting you test your built application locally before deploying</li>\n<li><strong>Integration API updates</strong> for custom entrypoints and dev server configuration</li>\n<li><strong>Improved error messages</strong> when your code differs from production behavior</li>\n</ul>\n<p>We’re actively refining Cloudflare support as we work toward the stable Astro 6 release. Currently, prerendered (static) builds do not run through workerd, but they will before v6 is released.</p>\n<p>If you encounter issues or unexpected behavior, please let us know. This feedback is especially important as we expand runtime support beyond Node.js.</p>\n<p>See the <a target=\"_blank\" href=\"https://v6.docs.astro.build/en/guides/integrations-guide/cloudflare/#upgrading-to-v13-and-astro-6\">Cloudflare adapter upgrade guide</a> for more information, and the <a target=\"_blank\" href=\"https://github.com/withastro/astro/blob/next/packages/integrations/cloudflare/CHANGELOG.md\">Cloudflare adapter changelog</a> for the full list of changes and improvements.</p>\n<h2 id=\"live-collections-stable\">Live Collections (Stable)</h2>\n<p>Astro 5.10’s experimental live content collections are now stable in Astro 6. now stable in Astro 6. CSP helps protect your site against cross-site scripting (XSS) and other code injection attacks by controlling which resources can be loaded.</p>\n<p>This was Astro’s most upvoted feature request so far, and we carefully designed the feature to work in all Astro render modes (static pages, dynamic pages, and single-page applications), with maximum flexibility and type-safety in mind.</p>\n<p>This feature is compatible with all of Astro’s official adapters (Cloudflare, Netlify, Node, Vercel). Astro will generate the CSP header or <code>&lt;meta&gt;</code> element for you, including hashes of scripts and styles used on a page, even those that are loaded dynamically!</p>\n<p>You can now set <code>csp: true</code> in your Astro config for default protection, or you can further customize your security policy by enabling this feature with a configuration object that includes additional options:</p>\n<div><figure><pre><code><div><p><span>import</span><span> { </span><span>defineConfig</span><span> } </span><span>from</span><span> </span><span>'astro/config'</span><span>;</span></p></div><div><p><span>export</span><span> </span><span>default</span><span> </span><span>defineConfig</span><span>({</span></p></div><div><p><span>  </span><span>csp</span><span>: {</span></p></div><div><p><span>    </span><span>scriptDirective</span><span>: {</span></p></div><div><p><span>      </span><span>resources</span><span>: [</span></p></div><div><p><span>        </span><span>\"'self'\"</span><span>, </span><span>\"https://cdn.example.com\"</span></p></div><div><p><span><span>      </span></span><span>]</span></p></div><div><p><span><span>    </span></span><span>}</span></p></div><div><p><span><span>  </span></span><span>}</span></p></div><div><p><span>});</span></p></div></code></pre></figure></div>\n<p>See the <a target=\"_blank\" href=\"https://v6.docs.astro.build/en/reference/configuration-reference/#securitycsp\">CSP configuration reference</a> for all available options.</p>\n<h2 id=\"breaking-changes--migration\">Breaking Changes &amp; Migration</h2>\n<p>Astro 6 includes several breaking changes as we clean up deprecated APIs and align with new standards. Key changes:</p>\n<ul>\n<li><strong>Removed APIs</strong>: <code>Astro.glob()</code>, <code>emitESMImage()</code>, deprecated <code>&lt;ViewTransitions /&gt;</code> component, legacy content collections</li>\n<li><strong>Node version</strong>: Requires Node 22+ (dropped Node 18 &amp; 20 support)</li>\n<li><strong>Integration API</strong>: Updates to adapter interfaces, route data, and SSR manifest</li>\n<li><strong>Cloudflare adapter</strong>: Breaking changes to <code>Astro.locals.runtime</code> and custom entrypoint patterns</li>\n<li><strong>i18n</strong>: Changed default behavior for <code>i18n.redirectToDefaultLocale</code></li>\n<li><strong>Zod 4</strong>: Upgraded to Zod 4, Zod 3 no longer supported</li>\n</ul>\n<p>See the <a target=\"_blank\" href=\"https://v6.docs.astro.build/en/guides/upgrade-to/v6/\">upgrade guide</a> for detailed migration steps for each change.</p>\n<h2 id=\"stability--roadmap\">Stability &amp; Roadmap</h2>\n<p><strong>Astro 6 is currently beta software.</strong> This is our initial release of these features, and we’ll be refining them before the stable v6.0 release.
