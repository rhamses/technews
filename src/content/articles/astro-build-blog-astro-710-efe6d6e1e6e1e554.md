multiple dev servers at once</h2>\n<p>Sometimes you want a second dev server without giving up the one you already have running. For example, you’re debugging something and want to temporarily start another instance with verbose logging, while keeping your regular dev server (and its state) exactly as it is.</p>\n<p>Astro 7 introduced a lockfile so that AI coding agents don’t accidentally spin up duplicate dev servers for the same project. As a side effect, running <code>astro dev</code> while another instance was already active would just error out, even when you started it yourself on purpose.</p>\n<p>Astro 7.1 brings that workflow back with a new <code>--ignore-lock</code> flag that skips the lockfile check, so you can start as many dev servers as you like for the same project:</p>\n<div><figure><pre><code><div><p><span>astro</span><span> </span><span>dev</span><span> </span><span>--ignore-lock</span></p></div></code></pre></figure></div>\n<p>The instance started with <code>--ignore-lock</code> runs independently of the others, which means <code>astro dev stop</code>, <code>astro dev status</code>, and <code>astro dev logs</code> won’t know about it. It’s for cases like this one, where you just need a quick, throwaway second server, not another one you’ll manage long-term.</p>\n<h2 id=\"lower-memory-usage-for-large-content-collections\">Lower memory usage for large content collections</h2>\n<p>The <code>glob()</code> loader renders your Markdown entries as soon as it syncs your content collection, and caches the rendered HTML so it doesn’t have to do that work again on the next build. For most sites, that’s a great trade: sync is a little more expensive, but rebuilds are fast.</p>\n<p>That trade gets more expensive as a collection grows, or as rendering produces more output than its source Markdown. Caching all of that rendered HTML in memory during sync adds up.</p>\n<p>You can now opt individual collections out of eager rendering with the <code>deferRender</code> option:</p>\n<div><figure><pre><code><div><p><span>import</span><span> { </span><span>defineCollection</span><span> } </span><span>from</span><span> </span><span>'astro:content'</span><span>;</span></p></div><div><p><span>import</span><span> { </span><span>glob</span><span> } </span><span>from</span><span> </span><span>'astro/loaders'</span><span>;</span></p></div><div><p><span>const</span><span> </span><span>docs</span><span> = </span><span>defineCollection</span><span>({</span></p></div><div><p><span>  </span><span>loader</span><span>: </span><span>glob</span><span>({ </span><span>pattern</span><span>: </span><span>'**/*.md'</span><span>, </span><span>base</span><span>: </span><span>'src/content/docs'</span><span>, </span><span>deferRender</span><span>: </span><span>true</span><span> }),</span></p></div><div><p><span>});</span></p></div></code></pre></figure></div>\n<p>With <code>deferRender: true</code>, entries are stored without being rendered during sync. Rendering happens later, on demand, when a page actually needs it, the same way <code>.mdx</code> files have always worked. You give up caching rendered HTML across builds, but for large, heavy collections that’s a worthwhile trade for lower memory usage during sync.</p>\n<h2 id=\"logger-improvements\">Logger improvements</h2>\n<p>Custom loggers can now be configured consistently with other APIs you might be using (e.g. fonts or sessions).
