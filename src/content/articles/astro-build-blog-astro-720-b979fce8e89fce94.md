This release also adds a way to opt out of session support, a background mode for <code>astro preview</code>, and a smaller way to point at a custom logger.</p>\n<p>Explore what’s new in this release:</p>\n<ul>\n<li><strong><a target=\"_blank\" href=\"https://astro.build/blog/astro-720/#experimental-incremental-static-builds\">Experimental: incremental static builds</a></strong></li>\n<li><strong><a target=\"_blank\" href=\"https://astro.build/blog/astro-720/#opt-out-of-session-support\">Opt out of session support</a></strong></li>\n<li><strong><a target=\"_blank\" href=\"https://astro.build/blog/astro-720/#background-mode-for-astro-preview\">Background mode for astro preview</a></strong></li>\n<li><strong><a target=\"_blank\" href=\"https://astro.build/blog/astro-720/#relative-logger-entrypoints\">Relative logger entrypoints</a></strong></li>\n<li><strong><a target=\"_blank\" href=\"https://astro.build/blog/astro-720/#community\">Community</a></strong></li>\n</ul>\n<p>To upgrade an existing project, use the automated <code>@astrojs/upgrade</code> CLI tool. Alternatively, upgrade manually by running the upgrade command for your package manager:</p>\n<div><figure><pre><code><div><p><span># Recommended:</span></p></div><div><p><span>npx</span><span> </span><span>@astrojs/upgrade</span></p></div><div><p><span># Manual:</span></p></div><div><p><span>npm</span><span> </span><span>install</span><span> </span><span>astro@latest</span></p></div><div><p><span>pnpm</span><span> </span><span>upgrade</span><span> </span><span>astro</span><span> </span><span>--latest</span></p></div><div><p><span>yarn</span><span> </span><span>upgrade</span><span> </span><span>astro</span><span> </span><span>--latest</span></p></div></code></pre></figure></div>\n<h2 id=\"experimental-incremental-static-builds\">Experimental: incremental static builds</h2>\n<p>Astro is often used to build large static sites: docs, blogs, and marketing sites that can run to thousands of pages. On those sites, a few dynamic routes, like <code>[...slug].astro</code>, usually account for the bulk of the pages, each rendering an entry from a content collection. As the content grows, so does the build, even when a given build only changes a handful of pages.</p>\n<p><a target=\"_blank\" href=\"https://astro.build/blog/astro-7/\">Astro 7</a> already made the bundling phase much faster with Rolldown and a Rust-based Markdown pipeline. What was left is the generation phase, where Astro renders each prerendered route to HTML. Until now Astro re-rendered every static page on every build, even when nothing about that page had changed. Incremental static builds targets that phase.</p>\n<p>Turn it on with the <code>experimental.incrementalBuild</code> flag:</p>\n<div><figure><pre><code><div><p><span>import</span><span> { </span><span>defineConfig</span><span> } </span><span>from</span><span> </span><span>'astro/config'</span><span>;</span></p></div><div><p><span>export</span><span> </span><span>default</span><span> </span><span>defineConfig</span><span>({</span></p></div><div><p><span>  </span><span>experimental</span><span>: {</span></p></div><div><p><span>    </span><span>incrementalBuild</span><span>: </span><span>true</span><span>,</span></p></div><div><p><span><span>  </span></span><span>},</span></p></div><div><p><span>});</span></p></div></code></pre></figure></div>\n<p>A route opts in by returning a <code>cacheKey</code> for each path from <code>getStaticPaths()</code>. The <code>cacheKey</code> should change whenever the data used to render that path changes. For content collections, <code>entry.digest</code> is a good fit, since it changes whenever the entry’s content changes:</p>\n<div><figure><pre><code><div><p><span>---</span></p></div><div><p><span>import</span><span> { </span><span>getCollection</span><span> } </span><span>from</span><span> </span><span>'astro:content'</span><span>;</span></p></div><div><p><span>export</span><span> </span><span>async</span><span> </span><span>function</span><span> </span><span>getStaticPaths</span><span>() {</span></p></div><div><p><span>  </span><span>const</span><span> </span><span>posts</span><span> = </span><span>await</span><span> </span><span>getCollection</span><span>(</span><span>'blog'</span><span>);</span></p></div><div><p><span>  </span><span>return</span><span> </span><span>posts</span><span>.</span><span>map</span><span>((</span><span>post</span><span>) </span><span>=&gt;</span><span> ({</span></p></div><div><p><span>    </span><span>params</span><span>: { </span><span>slug</span><span>: </span><span>post</span><span>.</span><span>id</span><span> },</span></p></div><div><p><span>    </span><span>props</span><span>: { </span><span>post</span><span> },</span></p></div><div><p><span>    </span><span>cacheKey</span><span>: </span><span>post</span><span>.</span><span>digest</span><span>,</span></p></div><div><p><span><span>  </span></span><span>}));</span></p></div><div><p><span>}</span></p></div><div><p><span>const</span><span> { </span><span>post</span><span> } = </span><span>Astro</span><span>.</span><span>props</span><span>;</span></p></div><div><p><span>---</span></p></div><div><p><span>&lt;</span><span>h1</span><span>&gt;</span><span>{</span><span>post</span><span>.</span><span>data</span><span>.</span><span>title</span><span>}</span><span>&lt;/</span><span>h1</span><span>&gt;</span></p></div></code></pre></figure></div>\n<p>The <code>cacheKey</code> covers your data. Astro handles the code side for you: during the build it hashes each route’s full module graph, including its template, layouts, components, imported assets, and the package code they pull in. If any of that changes, the hash changes and every path on the route is re-rendered. A page is only reused when both this module hash and its <code>cacheKey</code> match the previous build.</p>\n<p>Paths without a <code>cacheKey</code> are always rendered, so opting a route in is an explicit decision and existing projects build exactly as they do today until you choose otherwise. The cache lives in <code>cacheDir</code> (by default <code>node_modules/.astro/</code>) next to the content layer and image caches, so CI systems that already persist that directory can reuse it across runs.</p>\n<p>This is an early, experimental feature and we want to hear how it holds up on real sites. To read the full design or leave feedback, see the <a target=\"_blank\" href=\"https://github.com/withastro/roadmap/pull/1404\">incremental static builds RFC</a>.</p>\n<h2 id=\"opt-out-of-session-support\">Opt out of session support</h2>\n<p>When a session driver is configured, Astro bundles its session runtime into your SSR output. That is what you want if you use <code>Astro.session</code>, but projects that never touch sessions were still paying for the code to be parsed on every cold start.</p>\n<p>Astro 7.2 adds a <code>session: false</code> option to opt out entirely:</p>\n<div><figure><pre><code><div><p><span>import</span><span> { </span><span>defineConfig</span><span> } </span><span>from</span><span> </span><span>'astro/config'</span><span>;</span></p></div><div><p><span>export</span><span> </span><span>default</span><span> </span><span>defineConfig</span><span>({</span></p></div><div><p><span>  </span><span>session</span><span>: </span><span>false</span><span>,</span></p></div><div><p><span>});</span></p></div></code></pre></figure></div>\n<p>With <code>session: false</code>, the adapters for Cloudflare, Netlify, and Node skip wiring up their default session driver, and the session runtime is removed from the bundle. <code>Astro.session</code> is <code>undefined</code>, which is a state its type already allowed, so existing <code>if (Astro.session)</code> checks keep working without a new error to handle. See <a target=\"_blank\" href=\"https://docs.astro.build/en/guides/sessions/#disabling-sessions\">Disabling sessions</a> in the docs for the details.</p>\n<p>You don’t have to set the flag to benefit. Astro now tree-shakes the session runtime out of any project where no driver is wired, whether that’s <code>session: false</code>, no <code>session</code> config at all, or a <code>session</code> object without a driver. Projects that do configure a driver see no change.</p>\n<h2 id=\"background-mode-for-astro-preview\">Background mode for astro preview</h2>\n<p>Astro 7 added a background mode for <code>astro dev</code> so you (or an AI coding agent) could start the dev server, keep working, and manage it with follow-up commands. Astro 7.2 brings the same to <code>astro preview</code>:</p>\n<div><figure><pre><code><div><p><span>astro</span><span> </span><span>preview</span><span> </span><span>--background</span></p></div></code></pre></figure></div>\n<p>The preview server runs in the background and writes to its own log file. You can then check on it or shut it down with the matching subcommands:</p>\n<div><figure><pre><code><div><p><span>astro</span><span> </span><span>preview</span><span> </span><span>status</span></p></div><div><p><span>astro</span><span> </span><span>preview</span><span> </span><span>logs</span></p></div><div><p><span>astro</span><span> </span><span>preview</span><span> </span><span>stop</span></p></div></code></pre></figure></div>\n<p><code>astro dev</code> and <code>astro preview</code> share the same background machinery, so the two behave consistently, including automatic background mode when an agent is driving.</p>\n<h2 id=\"relative-logger-entrypoints\">Relative logger entrypoints</h2>\n<p>Astro 7.1 let you configure a custom logger by passing a URL to <code>logger.entrypoint</code>. Astro 7.2 adds support for a plain relative string, matching how other entrypoint-style options work:</p>\n<div><figure><pre><code><div><p><span>import</span><span> { </span><span>defineConfig</span><span> } </span><span>from</span><span> </span><span>'astro/config'</span><span>;</span></p></div><div><p><span>export</span><span> </span><span>default</span><span> </span><span>defineConfig</span><span>({</span></p></div><div><p><span>  </span><span>logger</span><span>: {</span></p></div><div><p><span>    </span><span>entrypoint</span><span>: </span><span>'./src/custom-logger.js'</span><span>,</span></p></div><div><p><span><span>  </span></span><span>},</span></p></div><div><p><span>});</span></p></div></code></pre></figure></div>\n<p>The URL form still works. This is a small convenience so you don’t have to reach for <code>new URL(..., import.meta.url)</code> when a relative path is all you need.</p>\n<h2 id=\"other-improvements\">Other
