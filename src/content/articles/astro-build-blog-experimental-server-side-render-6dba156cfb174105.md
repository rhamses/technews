contentHtml: "<article><p>Today we are thrilled to announce experimental support for server-side rendering (SSR) in Astro. With SSR in Astro, we’ve unlocked entirely new use-cases (E-commerce, anyone?) and scale that just weren’t possible before. Our SSR implementation combines Astro’s unique server-first approach with dynamic features like user authentication, login flows, database access, data-fetching and more.</p>\n<p>If you’re ready to jump in, head over to <a target=\"_blank\" href=\"https://docs.astro.build/en/guides/server-side-rendering/\">the docs</a> and get started.</p>\n<h2 id=\"motivation\">Motivation</h2>\n<p>We heard you! One of the questions we get most often is “Can Astro do SSR?”</p>\n<p>When we set out to build Astro, we decided to focus on the prebuilt, static site architecture popularly called “Jamstack” (also known static-site generation or SSG). This approach let us iterate and launch new features quickly, but came with some important limitations:</p>\n<ul>\n<li>Large sites can’t pre-render to static HTML without introducing longer build times or slower, client-side rendering of dynamic content.</li>\n<li>Dynamic sites can’t pre-render to static HTML without forcing you to rebuild and redeploy some portion of your site whenever your data changes.</li>\n<li>Interactive sites can’t pre-render to static HTML without moving all user-individualized data to the client. User names, avatars, and permissions all get more complicated when you’re dealing with static, pre-built HTML.</li>\n</ul>\n<p>E-commerce is especially hurt by all three of the above problems. In an industry where every millisecond of load performance counts, how can you get the awesome performance of static HTML without the limitations?</p>\n<p>From Day 1, we knew that Astro’s approach to island architecture was uniquely positioned to solve this problem. Islands allow pages to load quickly and become interactive lazily; the user sees and is able to interact with the most important parts of the page, faster.</p>\n<h2 id=\"enter-server-side-rendering-ssr\">Enter: Server-Side Rendering (SSR)</h2>\n<p>Server-side rendering is a well-understood solution to scaling large websites, going back to the earliest days of the internet. SSR is no silver bullet, but, when done right, SSR is an invaluable tool for certain use-cases.</p>\n<p>Take user authentication for instance. With static site generation, you have a couple different approaches:</p>\n<ol>\n<li>\n<p>Check for a cookie or JWT in localStorage, then redirect to a login page if the user doesn’t have one. If using a cookie this prevents using <code>HttpOnly</code>, opening you to malicious JavaScript attacks.</p>\n<div><figure><pre><code><div><p><span>&lt;</span><span>script</span><span>&gt;</span></p></div><div><p><span>  </span><span>if</span><span> (!</span><span>parseCookie</span><span>(</span><span>document</span><span>.</span><span>cookie</span><span>).</span><span>auth</span><span>) {</span></p></div><div><p><span>    </span><span>window</span><span>.</span><span>location</span><span> = </span><span>\"/login\"</span></p></div><div><p><span><span>  </span></span><span>}</span></p></div><div><p><span>&lt;/</span><span>script</span><span>&gt;</span></p></div></code></pre></figure></div>\n<p>Additionally, what do you do if the token is not valid? You still need to check and respond in that case.</p>\n</li>\n<li>\n<p>Call an API that will check if a user is logged in, like <code>/api/auth</code>. Going this route is going to mean that you need to show loading spinners in each of your islands while you wait on the response.</p>\n<div><figure><pre><code><div><p><span>function</span><span> </span><span>App</span><span>() {</span></p></div><div><p><span>  </span><span>const</span><span> </span><span>auth</span><span> = </span><span>useAuth</span><span>()</span></p></div><div><p><span>  </span><span>if</span><span> (</span><span>auth</span><span>.</span><span>loading</span><span>) </span><span>return</span><span> &lt;</span><span>AnnoyingLoadingSpinner</span><span> /&gt;</span></p></div><div><p><span>  </span><span>if</span><span> (!</span><span>auth</span><span>.</span><span>loggedIn</span><span>) </span><span>return</span><span> &lt;</span><span>LoginPage</span><span> /&gt;</span></p></div><div><p><span>  </span><span>return</span><span> &lt;</span><span>UserProfile</span><span> </span><span>user</span><span>=</span><span>{</span><span>auth</span><span>.</span><span>user</span><span>}</span><span> /&gt;</span></p></div><div><p><span>}</span></p></div></code></pre></figure></div>\n</li>\n</ol>\n<p>No matter your approach, going client-side for authentication is always going to mean:</p>\n<ul>\n<li>Things won’t run if JavaScript is disabled.</li>\n<li>Your server can only respond with <code>200 OK</code> response codes.</li>\n<li>It’s just plain slow. The user has to wait for the full HTML response (including JS, CSS, etc) even if they then immediately redirect. This creates multiple page requests before the user lands on the correct page.</li>\n</ul>\n<h3 id=\"astro-ssr-designed-to-be-simple\">Astro SSR: Designed to be Simple</h3>\n<p>Next.js, Nuxt, Gatsby, SvelteKit, and the whole gang of modern JavaScript meta-frameworks have some idea of SSR already. What makes Astro SSR so special?</p>\n<p>Astro has one key advantage over the current set of JavaScript-focused meta-frameworks who have tackled SSR before us: <strong>Astro was designed to run on the server.</strong></p>\n<p>With Astro you are free to write your server code how it works in your mind, free from the unnecessary abstractions that come with other, “universal” SPA-first frameworks. While SPA-first thinking might be great for super stateful web applications (think dashboards, apps, portals) it’s a cost that most content-focused websites would be better off not paying.</p>\n<p>Here’s how user authentication works in Astro SSR, using only 5 lines of </p>\n<div><figure><pre><code><div><p><span>---</span></p></div><div><p><span>// In an Astro component (*.astro), you write server code directly</span></p></div><div><p><span>// in the component front matter (this space between the two --- fences).</span></p></div><div><p><span>// 1. Since it’s a function call you can handle the request, fetch data to be fed into the template, and exit early (as with the redirect) if needed.</p>\n<h3 id=\"api-routes\">API Routes</h3>\n<p>Astro’s HTML-first approach to web development will get you pretty far on its own, but Astro also supports interactive UI using your favorite framework (like React). When you build for the client, you often need endpoints to read and write data between the user and the server. Built-in API routes are here to deliver that need.</p>\n<p>In Astro, an API route is a <code>.js</code> or <code>.ts</code> file in the <code>src/pages/</code> folder, that takes a request and returns a response. API routes were designed for maximum flexibility:</p>\n<ul>\n<li>Build a form submission handler for JS-free form submission.</li>\n<li>Build an upload handler for user file submissions.</li>\n<li>Build a JSON-based REST API for the client to talk to.</li>\n<li>Build a dynamic asset route to return any file type, including images and videos.</li>\n</ul>\n<p>API routes work by exporting a function that implements an HTTP method. Developers expect frameworks to integrate with their favored providers, without too much configuration or setup.</p>\n<p>When we built Astro SSR, we evaluated the different ways that other frameworks tackle this problem. In the end, we decided to follow in the footsteps of <a target=\"_blank\" href=\"https://kit.svelte.dev/\">SvelteKit</a> and <a target=\"_blank\" href=\"https://remix.run/\">Remix</a> and adopt the idea of <strong><em>pluggable host</em></strong> <strong><em>adapters</em></strong>. Adapters are simple, pluggable integrations that automatically configure your build for your favorite host.</p>\n<p>Not only is the adapter model easy for developers to set up, but it also lets us support as many different kinds of hosts as possible, including:</p>\n<ul>\n<li>Run entirely on the edge with <strong>Cloudflare</strong> and <strong>Deno Deploy</strong>.</li>\n<li>Run on a modern dev platform like <strong>Netlify</strong> and <strong>Vercel</strong>.</li>\n<li>Run on a bare-metal serverless function on <strong>AWS</strong>, <strong>Azure</strong>, and <strong>Google Cloud</strong>.</li>\n<li>Run on a JavaScript server runtime can deploy yourself like <strong>Node.js</strong> and <strong>Deno.</strong></li>\n</ul>\n<p>SSR support in Astro is still experimental. Over the next two months, we’re excited to work with all of the major hosting providers to launch more adapters and partnerships for every platform that our users care about. If you are a hosting provider interested in building your own Adapter for Astro, please reach out to us on Discord or via email: <a target=\"_blank\" href=\"mailto:partner@astro.build\">partner@astro.build</a>.</p>\n<p>To celebrate this announcement, we were lucky enough to work with our launch partner (and official hosting sponsor) Netlify, to launch an official, day-one adapter for the Netlify platform. The Netlify adapter configures your Astro SSR build to run on Netlify Functions with just one line of code:</p>\n<div><figure><pre><code><div><p><span>import</span><span> { </span><span>defineConfig</span><span> } </span><span>from</span><span> </span><span>\"astro/config\"</span></p></div><div><p><span>import</span><span> </span><span>netlify</span><span> </span><span>from</span><span> </span><span>\"@astrojs/netlify/functions\"</span></p></div><div><p><span>export</span><span> </span><span>default</span><span> </span><span>defineConfig</span><span>({</span></p></div><div><p><span>  </span><span>adapter</span><span>: </span><span>netlify</span><span>(),</span></p></div><div><p><span>})</span></p></div></code></pre></figure></div>\n<p>To deploy, run your <code>astro build</code> and then deploy to Netlify:</p>\n<video controls><source src=\"https://astro.build/assets/blog/experimental-ssr/netlify-deploy-2.mp4\" type=\"video/mp4\"><p>Sorry, your browser doesn’t support embedded videos.</p></video>\n<h2 id=\"next-steps\">Next Steps</h2>\n<p>Server-side rendering is available today as an experimental API in the Astro 1.0 Beta. This release is focused on providing the low-level primitives and a foundation to build upon.</p>\n<p>To learn more:</p>\n<ul>\n<li>Check out <a target=\"_blank\" href=\"https://docs.astro.build/en/guides/server-side-rendering/\">the docs</a> to learn the SSR API.</li>\n<li>Visit our <a target=\"_blank\" href=\"https://discord.com/channels/830184174198718474/852168748353060875\">Discord channel</a> for support and to contribute to stabilizing the APIs.</li>\n<li>Follow us <a target=\"_blank\" href=\"https://twitter.com/astrodotbuild\">on Twitter</a> where we’ll be posting more guides on SSR later this week.</li>\n</ul></article>"
