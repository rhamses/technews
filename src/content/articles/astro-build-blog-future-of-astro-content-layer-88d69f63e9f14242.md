contentHtml: "<article><p><strong>This is Part 2 of our series on <em>“The Future of Astro”</em>, covering three major advancements we have planned for the Astro web framework in 2024. This post introduces a more powerful Content Layer to Astro: a new way to work with your local and remote content sources.</strong></p>\n<p>In Astro 2.0, we released the original <a target=\"_blank\" href=\"https://docs.astro.build/en/guides/content-collections/\">Content Collections API</a>. Content Collections were designed around our own experiences and frustrations struggling to scale up large Markdown projects in modern web frameworks, including Astro at the time. Our goal was to make it easier to work with local content (Markdown, MDX, etc.) in Astro than any other web framework.</p>\n<p>Content Collections brought built-in content management features to Astro like content schemas, frontmatter validation, and a fully TypeScript-enabled query API:</p>\n<div><figure><pre><code><div><p><span>import</span><span> { </span><span>getCollection</span><span>, </span><span>getEntry</span><span> } </span><span>from</span><span> </span><span>'astro:content'</span><span>;</span></p></div><div><p><span>// Get all entries from a collection.</span></p></div><div><p><span>// Requires the name of the collection as an argument.</span></p></div><div><p><span>// Example: retrieve `src/content/blog/**`</span></p></div><div><p><span>const</span><span> </span><span>allBlogPosts</span><span> = </span><span>await</span><span> </span><span>getCollection</span><span>(</span><span>'blog'</span><span>);</span></p></div><div><p><span>// Get a single entry from a collection via the request URL.</span></p></div><div><p><span>// Requires the name of the collection and an entry ID slug.</span></p></div><div><p><span>// Example: retrieve `src/content/blog/future-of-astro-content-layer.mdx`</span></p></div><div><p><span>const</span><span> </span><span>blogPostEntry</span><span> = </span><span>await</span><span> </span><span>getEntry</span><span>(</span><span>'blog'</span><span>, </span><span>Astro</span><span>.</span><span>params</span><span>.</span><span>slug</span><span>);</span></p></div></code></pre></figure></div>\n<p>Content is an essential primitive in Astro. But building content-driven websites with Astro should be easy no matter where your content lives. We already solved this for local Markdown, now what about larger projects where content lives outside of your repo? In a remote API? In your favorite CMS?</p>\n<p><strong>We are beginning to explore a new, more powerful Content Layer API for Astro.</strong> The new Content Layer will build on our existing Content Collections functionality to make working with your content in Astro easier than ever before. Lets dive into how it works.</p>\n<h2 id=\"a-more-powerful-content-engine\">A More Powerful Content Engine</h2>\n<p>One of the current limitations of Content Collections is that our current data structure is stored entirely in memory. This works well enough for static sites, but loading all of that data into memory can wreak havoc on cold-start times in serverless SSR environments.</p>\n<p>We are currently exploring <a target=\"_blank\" href=\"https://github.com/tursodatabase/libsql\">LibSQL</a> (SQLite) as a new underlying storage mechanism for content in Astro. By embedding SQLite inside of Astro, we could scale up to millions of content entries in a project without breaking a sweat. Plus, SQLite’s file storage would dramatically speed up both development and build performance by allowing us to cache content across builds.</p>\n<p>For developers, direct access to a SQL database would also introduce more powerful query API for those who need it. We specifically designed our own <code>getCollection</code> and <code>getEntry</code> APIs to be intentionally simple, and these APIs aren’t going anywhere. However, this has always left the responsibility of filtering and sorting to the user. An internal SQL database would help us bridge that gap and offer more advanced built-in querying to anyone who needs it.</p>\n<h2 id=\"a-more-flexible-content-source\">A More Flexible Content Source</h2>\n<p>Breaking content out of the current <code>src/content</code> directory requires rethinking how we define collections&#160;in Astro. Instead of a hard-coded filesystem loader like the one built into Astro today, we are exploring a new, more flexible data loader for the <code>defineCollection()</code> API.</p>\n<div><figure><pre><code><div><p><span>defineCollection</span><span>({</span></p></div><div><p><span>  </span><span>name</span><span>: </span><span>'my-portfolio'</span><span>,</span></p></div><div><p><span>  </span><span>data</span><span>: (</span><span>db</span><span>: </span><span>DB</span><span>, </span><span>watcher</span><span>: </span><span>FileSystemWatcher</span><span>) </span><span>=&gt;</span><span> {</span></p></div><div><p><span>    </span><span>// 1. fetch your data</span></p></div><div><p><span>    </span><span>// 2. insert it into the database</span></p></div><div><p><span>    </span><span>// 3. optional: handle content updates during development</span></p></div><div><p><span>    </span><span>//    (a file change, CMS websocket notification)</span></p></div><div><p><span><span>  </span></span><span>},</span></p></div><div><p><span>})</span></p></div></code></pre></figure></div>\n<p>With this new API, you can:</p>\n<ul>\n<li>Read files from the file system (like we already do today)</li>\n<li>Provide a simple array of&#160;hardcoded, inline data</li>\n<li>Load data from a remote API using <code>fetch()</code></li>\n<li>Load content from an external CMS like Storyblok</li>\n</ul>\n<p>This will also enable composability across the larger Astro developer ecosystem. Anyone can publish a loader to npm. As an Astro developer, that means that you will be able to leverage a community ecosystem full of pluggable and reusable content loaders.</p>\n<div><figure><pre><code><div><p><span>// Example: An (imagined) Instagram profile loader for Astro</span></p></div><div><p><span>import</span><span> </span><span>instagram</span><span> </span><span>from</span><span> </span><span>'some-instagram-astro-content-loader'</span><span>;</span></p></div><div><p><span>defineCollection</span><span>({</span></p></div><div><p><span>  </span><span>name</span><span>: </span><span>'my-portfolio'</span><span>,</span></p></div><div><p><span>  </span><span>data</span><span>: </span><span>instagram</span><span>({ </span><span>/* ... */</span><span> }),</span></p></div><div><p><span>})</span></p></div></code></pre></figure></div>\n<p>We’ll be exploring this pluggable ecosystem story in parallel with the new Content Layer API. We are excited to give Astro users something that will unlock entirely new opportunities for composable content without sacrificing the ease of our current built-in Markdown support that you know and love.</p>\n<h2 id=\"next-steps\">Next Steps</h2>\n<p>Keep an eye out for experimental support coming to Astro later this year. We often launch new features behind experimental flags before they are stable, which gives our developer community plenty of time to try out new APIs and leave feedback.</p>\n<p>To learn more about the Content Layer proposal and leave early feedback, you can visit <a target=\"_blank\" href=\"https://github.com/withastro/roadmap/issues/946\">the ongoing discussion in our open roadmap repo</a>. We’ll continue to post updates there and in <a target=\"_blank\" href=\"https://astro.build/chat\">our Discord</a> as we begin work on the official implementation.</p></article>"
