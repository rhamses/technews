contentHtml: "<article>\n<p><strong>This is Part 3 of our series on “The Future of Astro” covering the three major features we have planned for Astro in 2024. This post introduces Server Islands: a new island architecture primitive that lets you deliver static, CDN-cached HTML page shells with injected dynamic content.</strong></p>\n<p>In 2021, Astro pioneered a new frontend architecture called <a target=\"_blank\" href=\"https://docs.astro.build/en/concepts/islands/\">Islands</a>. Islands are unique because they allow Astro to automatically strip all unused JavaScript from your page, delivering faster performance without forcing you to give up your favorite UI components at dev time (React, Svelte, Vue, etc).</p>\n<p>But frontend performance isn’t the only performance problem you’ll run into on the web. <em>How</em> you deliver a website to the user can be even more impactful than <em>what</em> you deliver, and developers are often forced to make a difficult choice: performance, or personalization?</p>\n<p><strong>Performance:</strong> Serve pages as static HTML, and cache aggressively. You won’t be able to personalize pages to the user, but the performance benefits, cost-savings, and simplicity of static CDN deployments are impossible to match.</p>\n<p><strong>Personalization:</strong> Serve pages as dynamic HTML, rendered on-demand. This forces your request through some data center that may be halfway around the world, which slows performance and increases your likelihood of failing Google’s <a target=\"_blank\" href=\"https://web.dev/articles/vitals\">Core Web Vitals</a>. However, the level of control and personalization that you unlock with dynamic responses can be hard to turn down.</p>\n<p><strong>Performance and personalization shouldn’t be mutually exclusive.</strong> We believe that Islands architecture holds the answer to this problem as well, and we are currently working on a new feature to bring you the best of both worlds: <strong>Server Islands.</strong></p>\n<h2 id=\"server-islands\">Server Islands</h2>\n<p>Server Islands are a new primitive that we are exploring for Astro, building on our existing island frontend architecture. You define a server island the same way you would a client island, but instead of using a <code>client:*</code> directive you would use the new <code>server:defer</code> directive instead:</p>\n<div><figure><pre><code><div><p><span>&lt;</span><span>UserButton</span><span> </span><span>server:defer</span><span> /&gt;</span></p></div></code></pre></figure></div>\n<p>This tells Astro to skip rendering this component in the initial response and “defer” its render to later. This lets you cache the static page behind a CDN with some initial placeholder content. When the dynamic HTML has loaded, it replaces the server island on the page with the HTML result of the deferred render.</p>\n<p>You can see this running in the prototype below. The static page loads instantly with the majority of your page content (21ms, in this example running on <a target=\"_blank\" href=\"https://vercel.com/\">Vercel</a>). The dynamic deferred component HTML then renders separately, and Astro stitches it all back together when the deferred render is complete.</p>\n<video autoplay loop muted><source src=\"https://astro.build/assets/blog/future-of-astro/ServerDefer.mp4\" type=\"video/mp4\"><p>Sorry, your browser doesn’t support embedded videos.</p></video>\n<p>Conceptually this is similar to the concept of Suspense in React, Solid, etc. but with the key difference that the deferred island is rendered as a separate HTTP request. We have intentionally avoided streaming the static content <em>and</em> the islands back in a single response to simplify things for your CDN of choice.</p>\n<img src=\"https://astro.build/_image?href=%2F_astro%2Fdark-mode-server-islands-diag.CCPm1I4W.webp&w=1536&h=507&f=webp\" srcset=\"https://astro.build/_image?href=%2F_astro%2Fdark-mode-server-islands-diag.CCPm1I4W.webp&w=768&h=254&f=webp 768w, https://astro.build/_image?href=%2F_astro%2Fdark-mode-server-islands-diag.CCPm1I4W.webp&w=1536&h=507&f=webp 1536w\" alt=\"A diagram showing the server island population parts of the page from the server.\">\n<p>By moving all of your dynamic HTML into deferred server islands, you’re left with the best of both worlds:</p>\n<ul>\n<li><strong>Performance:</strong> An instant, static page shell of HTML, cached in a global CDN.</li>\n<li><strong>Personalization:</strong> Dynamic content injected anywhere you’d like on the page.</li>\n</ul>\n<p>Server islands won’t make sense for every use case. Some pages may require so much dynamic content that it still makes sense to render the entire page on the server. Other sites may still wish to fetch dynamic content as JSON from API endpoints instead.</p>\n<p>However, we believe that server islands make sense for the vast majority of personalized content in content-driven websites. The websites that we see built with Astro often mix dynamic and static content on the page. For these sites that currently can’t leverage CDN caching, server islands will likely deliver big performance wins.</p>\n<h2 id=\"next-steps\">Next Steps</h2>\n<p>We’re in the <a target=\"_blank\" href=\"https://github.com/withastro/roadmap/issues/945\">design phase</a> of this feature and are thinking about trade-offs for different implementations, but prototyping is already underway.</p>\n<p>Keep an eye out for experimental support for Server Islands in Astro in the near future. We often launch new features behind experimental flags before they are stable, which gives our users plenty of time to try out new APIs and give feedback. If you’d like to get involved earlier than that, check out the <a target=\"_blank\" href=\"https://github.com/withastro/roadmap/issues/945\">RFC</a> and participate in the discussions now.</p></article>"
