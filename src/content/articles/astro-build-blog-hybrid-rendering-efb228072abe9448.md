contentHtml: "<article>\n<p>Since the initial launch of Astro 1.0, developers have had to choose between generating <a target=\"_blank\" href=\"https://docs.astro.build/en/core-concepts/routing/#static-ssg-mode\">static (SSG)</a> or <a target=\"_blank\" href=\"https://docs.astro.build/en/guides/server-side-rendering/\">server (SSR)</a> output. Static websites offer incredible performance by building your pages ahead-of-time. Servers leverage their dynamic power to generate HTML on-demand, unique for every request.</p>\n<p>Until now, this had been an all-or-nothing decision—is this fully static or should I deploy a server?</p>\n<p><a target=\"_blank\" href=\"https://astro.build/blog/astro-2\">Astro 2.0</a> unlocks the best of both worlds with <strong>hybrid rendering</strong>. Choose between the performance of static pages or the full flexibility of server rendering for each page of your website.</p>\n<p>In this post, we’ll go over how hybrid rendering works by exploring just a few of the new features and performance improvements made possible in Astro 2.0.</p>\n<h2 id=\"how-does-astros-build-process-work\">How does Astro’s build process work?</h2>\n<p>Astro’s build process happens in multiple stages, beginning with a server-side JavaScript bundle generated by <a target=\"_blank\" href=\"https://vitejs.dev/\">Vite</a>. To simplify things a bit, the output of this bundle includes:</p>\n<ul>\n<li><strong>Server-side JavaScript</strong> used to render HTML</li>\n<li>A <strong>client manifest</strong> which uses static analysis to collect all components needed for client-side interactivity</li>\n<li><strong>CSS and other assets</strong> for the client</li>\n</ul>\n<p>Next, Astro uses the client manifest to initiate a second build process which bundles optimized client-side JavaScript.</p>\n<p>If your configured <a target=\"_blank\" href=\"https://docs.astro.build/en/reference/configuration-reference/#output\"><code>output</code></a> is <code>static</code>, Astro will execute the server-side JavaScript and write the output to <code>.html</code> files. The server-side JavaScript is then discarded.</p>\n<img src=\"https://astro.build/_image?href=%2F_astro%2Fstatic.C0I_Dov4.webp&w=1536&h=801&f=webp\" srcset=\"https://astro.build/_image?href=%2F_astro%2Fstatic.C0I_Dov4.webp&w=768&h=401&f=webp 768w, https://astro.build/_image?href=%2F_astro%2Fstatic.C0I_Dov4.webp&w=1500&h=782&f=webp 1500w\" alt=\"Flow diagram of Astro's static build process\">\n<p>If your configured <a target=\"_blank\" href=\"https://docs.astro.build/en/reference/configuration-reference/#output\"><code>output</code></a> is <code>server</code>, Astro passes the server-side JavaScript to an <a target=\"_blank\" href=\"https://docs.astro.build/en/reference/configuration-reference/#adapter\"><code>adapter</code></a> for further processing.\nAdapters ensure that your server-side JavaScript is compatible with a particular hosting provider’s JavaScript runtime. Note that in this case, the final output is not a set of <code>.html</code> files, but the JavaScript code necessary to render HTML.</p>\n<img src=\"https://astro.build/_image?href=%2F_astro%2Fserver.D2Qe3bq5.webp&w=1536&h=801&f=webp\" srcset=\"https://astro.build/_image?href=%2F_astro%2Fserver.D2Qe3bq5.webp&w=768&h=401&f=webp 768w, https://astro.build/_image?href=%2F_astro%2Fserver.D2Qe3bq5.webp&w=1500&h=782&f=webp 1500w\" alt=\"Flow diagram of Astro's server build process\">\n<p>Unfortunately, this setup was quite rigid and didn’t allow mixing static and dynamic routes in the same project. What we really needed was a process that enabled both patterns in parallel.</p>\n<h2 id=\"how-does-hybrid-rendering-work\">How does hybrid rendering work?</h2>\n<p>In Astro 2.0, we’ve revamped the <code>astro build</code> pipeline to handle hybrid rendering.\nDuring the initial bundling process, a new static analysis step determines which pages should be prerendered.\nThis allows us to split your routes into separate chunks, depending on <em>when</em> they should be rendered.</p>\n<p>Much like the original <code>static</code> process, the prerendered chunk is executed and the output is written to <code>.html</code> files. The chunk is then discarded.</p>\n<p>Much like the original <code>server</code> process, the server chunk is passed to an <a target=\"_blank\" href=\"https://docs.astro.build/en/reference/configuration-reference/#adapter\"><code>adapter</code></a> for further processing. It will ultimately be deployed as a Serverless or Edge function, depending on your adapter.</p>\n<img src=\"https://astro.build/_image?href=%2F_astro%2Fhybrid.BUuwbKmd.webp&w=1536&h=933&f=webp\" srcset=\"https://astro.build/_image?href=%2F_astro%2Fhybrid.BUuwbKmd.webp&w=768&h=467&f=webp 768w, https://astro.build/_image?href=%2F_astro%2Fhybrid.BUuwbKmd.webp&w=1500&h=911&f=webp 1500w\" alt=\"Flow diagram of Astro's new hybrid build process\">\n<h2 id=\"why-use-static-analysis\">Why use static analysis?</h2>\n<p>Static analysis is a technique used to analyze your source code without actually executing it.\nAstro relies on this approach in many places, but it is especially critical during the build process.\nFor performance reasons, Astro must be able to categorize your pages without executing their source code.\nFor smaller projects, execution might not be a concern, but at scale it quickly becomes a bottleneck.</p>\n<p>Hybrid rendering was specifically designed with static analysis in mind, though we did <a target=\"_blank\" href=\"https://github.com/withastro/roadmap/blob/main/proposals/0029-prerender-api.md#alternatives\">entertain alternative APIs</a>.\nAstro’s build process is able to check for the presence of an <code>export const prerender = true</code> statement to determine which pages should be prerendered.\nTo do this efficiently, we rely on the wonderful <a target=\"_blank\" href=\"https://github.com/guybedford/es-module-lexer\"><code>es-module-lexer</code></a> library, which is also used internally in Node.</p>\n<div><figure><pre><code><div><p><span>---</span></p></div><div><p><span>// This route should be generated at build time!</span></p></div><div><p><span>export</span><span> for hybrid rendering</h2>\n<p>Hybrid rendering unlocks a whole new set of possible use cases, but we wanted to highlight a few that we’re particularly excited about.</p>\n<h2 id=\"use-case-improve-render-performance-of-popular-pages\">Use case: improve render performance of popular pages</h2>\n<p>Consider a small/medium e-commerce site built with Astro, with thousands of different possible products and variations. If you were to use static site generation, you’d be stuck rebuilding your website every time one of these products changed or went out of stock.</p>\n<p>This kind of project calls for server-side rendering, which would allow your product pages to be generated fresh on every request. But now we have a new problem: your homepage is no longer static. Loading performance is still critical for driving sales, and your homepage doesn’t have any dynamic content that actually requires it to be rebuilt fresh on every request.</p>\n<p>Hybrid rendering solves our performance problem by rendering the homepage to static HTML ahead-of-time, while keeping the rest of your website rendering on-demand.</p>\n<h2 id=\"use-case-add-an-api-to-your-existing-static-site\">Use case: add an API to your existing static site</h2>\n<p>As your static website grows, you may find the need to host a public API. Historically, adding an API to a static site has required host-specific configuration, but in Astro 2.0, we can add <a target=\"_blank\" href=\"https://docs.astro.build/en/core-concepts/endpoints/#server-endpoints-api-routes\">server endpoints (API routes)</a> without sacrificing the performance of our static pages.</p>\n<p>In fact, server endpoints can be added automatically by our <a target=\"_blank\" href=\"https://docs.astro.build/en/reference/integrations-reference/\">Integrations API</a>’s <a target=\"_blank\" href=\"https://docs.astro.build/en/reference/integrations-reference/#injectroute-option\"><code>injectRoute</code></a> hook. We’re excited to foster a powerful third-party integration ecosystem with these new primitives!</p>\n<h2 id=\"use-case-improve-build-performance-of-large-sites\">Use case: improve build performance of large sites</h2>\n<p>Static generation can be difficult to scale to thousands of pages, since every page must be rendered during the build process. Server-side rendering defers page rendering until request-time, removing a potential bottleneck from your build process.</p>\n<p>When there are hundreds of routes generated by <code>getStaticPaths</code>, server-side rendering can lead to significant performance gains. In our internal testing, we saw build times improve by up to 30% by switching dynamic routes to server-side rendering.</p>\n<h2 id=\"getting-started-with-hybrid-rendering\">Getting started with hybrid rendering</h2>\n<p>Hybrid rendering is available today in Astro 2.0! You can head to our <a target=\"_blank\" href=\"https://docs.astro.build/en/guides/server-side-rendering/\">server-side rendering guide</a> to learn more about Astro’s SSR features. Astro’s official adapters have also been updated to support hybrid rendering, so be sure to install the latest version of your <a target=\"_blank\" href=\"https://docs.astro.build/en/guides/server-side-rendering/#adding-an-adapter\">adapter</a>.</p>\n<p>To celebrate the launch, our friends at <a target=\"_blank\" href=\"https://sst.dev/\">SST</a> just launched <a target=\"_blank\" href=\"https://www.npmjs.com/package/astro-sst\">astro-sst</a>, their official AWS Adapter for Astro. Check out their <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=AFP3ZHxO7Gg\">announcement video &amp; walkthrough</a> to learn more and get started with AWS + SST.</p>\n<p>We welcome your feedback! We collected some wonderful input during the <a target=\"_blank\" href=\"https://github.com/withastro/roadmap/blob/main/proposals/0029-prerender-api.md\">Prerender API RFC</a> and invite you to propose future ideas using our new <a target=\"_blank\" href=\"https://github.com/withastro/roadmap\">public roadmap</a> or <a target=\"_blank\" href=\"https://astro.build/chat/\">Discord community</a>.</p></article>"
