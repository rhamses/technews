contentHtml: "<p>Since the launch of Fortnite in 2017, <a href=\"https://www.epicgames.com/site/home?sessionInvalidated=true\" target=\"_blank\" rel=\"noopener\">Epic Games</a> has reached hundreds of millions of players worldwide. <a href=\"https://aws.amazon.com/solutions/case-studies/innovators/epic-games/\" target=\"_blank\" rel=\"noopener\">Fortnite runs on Amazon Web Services (AWS)</a>, and takes advantage of services such as <a href=\"https://aws.amazon.com/opensearch-service/\" target=\"_blank\" rel=\"noopener\">Amazon OpenSearch Service</a> to power certain internal analytics and drive decision making at scale.</p> \n<p>Amazon OpenSearch Service has been helpful in understanding the game ecosystem. OpenSearch Service powers two types of use cases: search workloads and analytics workloads. A team at Epic Games had a use case for storing and analyzing a sliding window of game event data. This involves supporting complex queries and multilayered aggregations that feed analytical results into other internal systems, helping them power an evolving player experience. At the scale of a game like Fortnite with a large player base, these queries run against a significant volume of incoming data.</p> \n<p>These insights help identify emerging gameplay trends, understand how players engage with new content, and reveal more about the Fortnite ecosystem. They inform live operation decisions and help surface relevant content to players based on aggregated activity across the community.</p> \n<p>As Epic Games’ infrastructure handles billions of telemetry events, the team identified opportunities to optimize their OpenSearch Service cluster for better performance and cost efficiency. This post details how Epic Games partnered with AWS to transform their OpenSearch Service deployment, achieving significant improvements in query latency and resource utilization while reducing operational costs.</p> \n<h2 id=\"the-challenge\">The challenge</h2> \n<p>Epic Games runs an OpenSearch Service domain that handles continuous high-volume writes alongside CPU-intensive batch aggregation jobs. Ideally, these aggregation jobs would run more frequently to keep analytics fresh. Shorter job intervals mean fresher data for identifying gameplay trends, detecting anomalies, and informing live operations decisions. But the existing configuration couldn’t support this without scaling the domain beyond what the workload justified, driving up costs. Epic Games worked with AWS to identify where improvements could be made, focusing on areas such as hardware utilization, sharding strategy, index mappings, and query behavior.</p> \n<h2 id=\"observations\">Observations</h2> \n<p>The cluster was running on r7g memory-optimized data nodes, with 48 vCPUs and 384 GiB of memory per node. Of each node’s available memory, only a fraction (32 GiB) was allocated to Java Virtual Machine (JVM) heap, set at the maximum recommended for <a href=\"https://www.baeldung.com/jvm-compressed-oops\" target=\"_blank\" rel=\"noopener\">compressed oops</a>. The remainder (off-heap memory) was used for the filesystem cache and the operating system. System memory was not fully utilized across the data nodes (Figure 1).</p> \n<div id=\"attachment_93061\" style=\"width: 1760px\" class=\"wp-caption alignnone\">\n <img aria-describedby=\"caption-attachment-93061\" class=\"size-full wp-image-93061\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/Screenshot-2026-08-03-at-11.02.22 AM.png\" alt=\"\" width=\"1750\" height=\"232\">\n <p id=\"caption-attachment-93061\" class=\"wp-caption-text\">Figure 1: System memory utilization across data nodes</p>\n</div> \n<p>As shown in the preceding figure, utilization stays well below 100% throughout the observation period, confirming that much of the off-heap memory allocated to these nodes goes unused. The excess capacity could be safely exchanged for additional compute resources.</p> \n<p>JVM memory pressure is shown in Figure 2, and the correlating garbage collection metrics (both count and time) are shown in Figure 3.</p> \n<div id=\"attachment_93063\" style=\"width: 1763px\" class=\"wp-caption alignnone\">\n <a href=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/Screenshot-2026-08-03-at-11.03.08 AM.png\" target=\"_blank\" rel=\"noopener\"><img aria-describedby=\"caption-attachment-93063\" loading=\"lazy\" class=\"wp-image-93063 size-full\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/Screenshot-2026-08-03-at-11.03.08 AM.png\" alt=\"\" width=\"1753\" height=\"504\"></a>\n <p id=\"caption-attachment-93063\" class=\"wp-caption-text\">Figure 2: JVM memory pressure</p>\n</div> \n<div id=\"attachment_93064\" style=\"width: 2414px\" class=\"wp-caption alignnone\">\n <a href=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/image-jvm-3.png\" target=\"_blank\" rel=\"noopener\"><img aria-describedby=\"caption-attachment-93064\" loading=\"lazy\" class=\"wp-image-93064 size-full\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/image-jvm-3.png\" alt=\"\" width=\"2404\" height=\"723\"></a>\n <p id=\"caption-attachment-93064\" class=\"wp-caption-text\">Figure 3: JVM garbage collection metrics, count (top) and time (bottom)</p>\n</div> \n<p>These charts show that JVM memory pressure remains below critical thresholds, and both garbage collection count and time are low and stable, indicating healthy JVM utilization across the domain.</p> \n<p>While cluster-level CPU metrics appeared healthy at first glance (Figure 4), zooming into node-level metrics revealed clear node hotspots. The root cause of the node hotspots was the cluster’s sharding strategy.</p> \n<div id=\"attachment_93065\" style=\"width: 1722px\" class=\"wp-caption alignnone\">\n <a href=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/Screenshot-2026-08-03-at-10.56.56 AM.png\" target=\"_blank\" rel=\"noopener\"><img aria-describedby=\"caption-attachment-93065\" loading=\"lazy\" class=\"wp-image-93065 size-full\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/Screenshot-2026-08-03-at-10.56.56 AM.png\" alt=\"\" width=\"1712\" height=\"226\"></a>\n <p id=\"caption-attachment-93065\" class=\"wp-caption-text\">Figure 4: Cluster-level CPU utilization</p>\n</div> \n<p>The cluster had data nodes distributed across multiple Availability Zones. Each index used a set number of primary shards with replicas, rolling over after shards reached a certain size. At first glance, the configuration appeared well-balanced, with shard copies distributed across Availability Zones and each node holding a manageable share of the data.</p> \n<p>However, the primary shard count was lower than the total data node count. This meant that searches targeting the latest data, which is the most common access pattern, would only execute across a subset of available nodes. As a result, some nodes developed consistent CPU-based hotspots while the rest remained underutilized (Figure 5).</p> \n<div id=\"attachment_93067\" style=\"width: 1780px\" class=\"wp-caption alignnone\">\n <a href=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/Screenshot-2026-08-03-at-11.06.50 AM.png\" target=\"_blank\" rel=\"noopener\"><img aria-describedby=\"caption-attachment-93067\" loading=\"lazy\" class=\"wp-image-93067 size-full\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/Screenshot-2026-08-03-at-11.06.50 AM.png\" alt=\"\" width=\"1770\" height=\"302\"></a>\n <p id=\"caption-attachment-93067\" class=\"wp-caption-text\">Figure 5: Node-level CPU utilization showing hotspots</p>\n</div> \n<p>As shown in the preceding figure, some nodes reach as high as 90 percent CPU utilization while several others remain under 20 percent, highlighting the uneven distribution of query execution across the cluster.</p> \n<h2 id=\"recommendations-and-implementation\">Recommendations and implementation</h2> \n<p>Based on these observations, AWS worked together with Epic Games on a set of targeted optimizations spanning hardware selection, sharding strategy, index mappings, and query behavior. The following sections detail each recommendation and how it was implemented.</p> \n<h3 id=\"right-sizing-the-cluster\">Right-sizing the cluster</h3> \n<p>Because aggregation queries are CPU-intensive by nature and the cluster’s JVM memory pressure was well within acceptable ranges, AWS recommended migrating from memory-optimized r7g instances to compute-optimized c7g instances. The c7g family offers a higher ratio of vCPU to RAM, which is better suited for workloads where processing power rather than memory capacity is the binding constraint.</p> \n<p>The proposed architecture called for a larger number of c7g nodes than the existing r7g count. This migration achieved approximately 33 percent more aggregate CPU capacity across the cluster while operating with two-thirds of the original memory. The net effect was a meaningful cost reduction of approximately 10 percent, delivering more processing power at lower cost by aligning the instance profile with the actual nature of the workload (Table 1).</p> \n<p>&nbsp;</p> \n<table border=\"1px\" width=\"100%\" cellpadding=\"10px\"> \n <tbody> \n  <tr> \n   <td></td> \n   <td><strong>R7g (Before)</strong></td> \n   <td><strong>c7g (After)</strong></td> \n   <td><strong>Net Impact</strong></td> \n  </tr> \n  <tr> \n   <td><strong>Instance Family</strong></td> \n   <td>Memory Optimized</td> \n   <td>Compute Optimized</td> \n   <td>Better CPU-to-RAM alignment for aggregation workloads</td> \n  </tr> \n  <tr> \n   <td><strong>vCPUs per Node</strong></td> \n   <td>Same</td> \n   <td>Same</td> \n   <td>Same per-node CPU. This distributes both the write-heavy load and the batch aggregation search query load evenly on all the available data nodes.</p> \n<p>The team employed <a href=\"https://docs.aws.amazon.com/opensearch-service/latest/developerguide/ism.html\" target=\"_blank\" rel=\"noopener\">ISM</a> (Index State Management) policies to manage shard sizing through rollover, targeting shard sizes within recommended bounds using <code>min_primary_shard_size</code>. This kept shard counts bounded and predictable, providing a clear scaling pattern: adjust the node count, then update the ISM policy accordingly.</p> \n<p>After implementation, node-level CPU utilization showed a much more even distribution (Figure 6).</p> \n<table style=\"border: 0;border-collapse: collapse;margin: 0 auto;width: 100%\"> \n <tbody> \n  <tr> \n   <td style=\"border: 0;padding: 0 4px;text-align: center;width: 50%\"></td> \n   <td style=\"border: 0;padding: 0 4px;text-align: center;width: 50%\"></td> \n  </tr> \n </tbody> \n</table> \n<div id=\"attachment_93066\" style=\"width: 1783px\" class=\"wp-caption alignnone\">\n <a href=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/Screenshot-2026-08-03-at-11.12.01 AM-1.png\" target=\"_blank\" rel=\"noopener\"><img aria-describedby=\"caption-attachment-93066\" loading=\"lazy\" class=\"wp-image-93066 size-full\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/Screenshot-2026-08-03-at-11.12.01 AM-1.png\" alt=\"\" width=\"1773\" height=\"627\"></a>\n <p id=\"caption-attachment-93066\" class=\"wp-caption-text\">Figure 6: Node-level CPU utilization after sharding optimization</p>\n</div> \n<p>As shown in Figure 6, all nodes in the domain are working at similar CPU utilization levels, confirming that data and traffic are well distributed across the cluster with no node hotspots.</p> \n<h3 id=\"mapping-optimization\">Mapping optimization</h3> \n<p>The index mappings had both <code>text</code> and <code>keyword</code> field types enabled on many fields, even though access patterns showed those fields were only used for aggregation, sorting, or filter context, and never for full-text match queries. Removing the redundant <code>text</code> field type reduced storage overhead and improved query performance by eliminating unnecessary analysis at index time.</p> \n<p>For high-cardinality string fields, the <code>murmur3</code> field type does a compute-once-and-store optimization for cardinality aggregation. Instead of hashing keyword values at query time, <code>murmur3</code> computes the hash once at index time and stores it as a numeric <code>doc_value</code>, so the aggregation can skip the expensive string hashing step at query time (the cardinality estimate itself is still computed at query time).</p> \n<p>The following example illustrates the mapping changes:</p> \n<table style=\"height: 683px\" border=\"1px\" width=\"718\" cellpadding=\"5px\"> \n <tbody> \n  <tr> \n   <td>Before:</td> \n   <td>After:</td> \n  </tr> \n  <tr> \n   <td style=\"vertical-align: top\"> \n    <div class=\"hide-language\"> \n     <pre><code class=\"language-json\">\"some_field\": {\n  \"type\": \"text\",\n  \"fields\": {\n    \"keyword\": {\n      \"ignore_above\": 256,\n      \"type\": \"keyword\"\n    }\n  }\n},\n\"another_field\": {\n  \"type\": \"text\",\n  \"fields\": {\n    \"keyword\": {\n      \"ignore_above\": 256,\n      \"type\": \"keyword\"\n    }\n  }\n},\n\"cardinality_field\": {\n  \"type\": \"text\",\n  \"fields\": {\n    \"keyword\": {\n      \"ignore_above\": 256,\n      \"type\": \"keyword\"\n    }\n  }\n},</code></pre> \n    </div> </td> \n   <td style=\"vertical-align: top\"> \n    <div class=\"hide-language\"> \n     <pre><code class=\"language-json\">\"some_field\": {\n  \"type\": \"keyword\"\n},\n\"another_field\": {\n  \"type\": \"keyword\"\n},\n\"cardinality_field\": {\n  \"type\": \"keyword\",\n  \"fields\": {\n    \"hash\": {\n      \"type\": \"murmur3\"\n    }\n  }\n},</code></pre> \n    </div> </td> \n  </tr> \n </tbody> \n</table> \n<p>These mapping changes reduced overall storage, lowered shard count (which reduced CPU requirements), and reduced cluster manager node state size.</p> \n<h3 id=\"index-optimization\">Index optimization</h3> \n<p>Additional index-level optimizations were applied to improve query performance and reduce overhead. Index sorting was configured to default to the primary date field, which improves performance for time-based access patterns by aligning the physical data layout with the most common query order. The ISM policy was updated to <a href=\"https://docs.opensearch.org/latest/im-plugin/ism/policies/#force_merge\" target=\"_blank\" rel=\"noopener\">force merge</a> indices down to 1 segment after rollover, reducing segment overhead on read-only indices. Finally, the refresh interval was tuned to balance indexing throughput with search freshness.</p> \n<h3 id=\"upgrading-from-opensearch-service-2.17-to-3.1\">Upgrading from OpenSearch Service 2.17 to 3.1</h3> \n<p>The domain was upgraded from OpenSearch Service 2.17 to 3.1, which reduced error counts and improved throughput at the Amazon OpenSearch Ingestion pipeline level. The performance gains were notable: p99 latency on sum aggregations dropped by 40–50 percent after the upgrade alone, and large 96-hour cardinality aggregations saw p95 drop over 40 percent. General query performance improved across all query types, and thread pool pressure was reduced significantly, leading to far fewer 429 errors (Figure 7).</p> \n<div id=\"attachment_93068\" style=\"width: 1704px\" class=\"wp-caption alignnone\">\n <a href=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/image-40.png\" target=\"_blank\" rel=\"noopener\"><img aria-describedby=\"caption-attachment-93068\" loading=\"lazy\" class=\"wp-image-93068 size-full\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/08/04/image-40.png\" alt=\"\" width=\"1694\" height=\"265\"></a>\n <p id=\"caption-attachment-93068\" class=\"wp-caption-text\">Figure 7: Query performance before and after the OpenSearch Service 3.1 upgrade</p>\n</div> \n<h3 id=\"upgrading-from-graviton-3-to-graviton-4\">Upgrading from Graviton 3 to Graviton 4</h3> \n<p>The instance types were upgraded from c7g (Graviton 3) to c8g (Graviton 4). The performance gains were immediate:</p> \n<ul> \n <li>p99 on all queries: 380 ms to 250 ms.</li> \n <li>p95 on all queries: 245 ms to 230 ms.</li> \n <li>p90 on all queries: 225 ms to 200 ms.</li> \n <li>p50 on all queries: 100 ms to 70 ms.</li> \n</ul> \n<p>Date-windowed cardinality queries saw their p99 halved from 220 ms to 98 ms, with sum-based aggregations experiencing similar gains. Overall throughput increased by 16 percent.</p> \n<h3 id=\"tiered-caching\">Tiered caching</h3> \n<p>With the upgrade to OpenSearch Service 3.1, the team enabled <a href=\"https://opensearch.org/docs/latest/search-plugins/caching/tiered-cache/\" target=\"_blank\" rel=\"noopener\">tiered caching</a>. Tiered caching extends the default on-heap request cache with a disk-based tier. When items are evicted from the on-heap cache, they spill into a larger disk cache on the node’s local SSD rather than being discarded. This allows the cluster to retain cached results for a much larger set of queries without increasing JVM heap usage.</p> \n<p>The batch aggregation jobs in Epic Games’ workload issue repeated queries over overlapping time windows. The on-heap cache alone was too small to retain results across successive job runs, so expensive aggregations were recomputed each time. With the disk tier enabled, results from longer time-window aggregations (such as the 96-hour cardinality queries) persisted between runs. This produced more consistent and faster results on some of the larger aggregation queries, particularly those spanning longer time windows.</p> \n<h2 id=\"results-summary\">Results summary</h2> \n<p>The following table summarizes the impact of each optimization.</p> \n<table border=\"1px\" width=\"100%\" cellpadding=\"10px\"> \n <tbody> \n  <tr> \n   <td><strong>Optimization Strategy</strong></td> \n   <td><strong>Impact</strong></td> \n  </tr> \n  <tr> \n   <td>Right-sizing (r7g to c7g)</td> \n   <td>33% more CPU, 10% cost reduction</td> \n  </tr> \n  <tr> \n   <td>Sharding rebalance</td> \n   <td>Eliminated CPU hotspots across nodes</td> \n  </tr> \n  <tr> \n   <td>Mapping optimization</td> \n   <td>Reduced storage, shard count, and cluster state size</td> \n  </tr> \n  <tr> \n   <td>OpenSearch Service 2.17 to 3.1</td> \n   <td>p99 sum aggs reduced 40-50%, fewer 429 errors</td> \n  </tr> \n  <tr> \n   <td>Graviton 3 to Graviton 4</td> \n   <td>p99 380 ms to 250 ms, 16% higher throughput</td> \n  </tr> \n  <tr> \n   <td>Tiered caching</td> \n   <td>More consistent results on large aggregation queries</td> \n  </tr> \n </tbody> \n</table> \n<p><em>Table 2: Results summary</em></p> \n<h2 id=\"conclusion\">Conclusion</h2> \n<p>By optimizing their OpenSearch Service deployment, a team at Epic Games reduced p99 query latency from 380 ms to 250 ms, increased throughput by 16 percent, and lowered costs by 10 percent.
