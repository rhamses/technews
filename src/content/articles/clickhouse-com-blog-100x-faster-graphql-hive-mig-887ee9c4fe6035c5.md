Read on to find out why they are using ClickHouse and their journey from Elasticsearch to ClickHouse.</em></p>\n<h2 id=\"what-is-graphql-hive\"></h2>\n<p>GraphQL Hive is a Schema Registry, Monitoring, and Analytics solution for GraphQL APIs.</p>\n<p>As a fully open-source tool, GraphQL Hive helps you to track the history of changes,prevents breaking the API and analyzes the traffic of your API.</p>\n<p>GraphQL Hive makes you aware of how your GraphQL API is used and what is the experience of its final users.</p>\n<h2 id=\"what-is-graphql\"></h2>\n<p>For those unfamiliar with GraphQL, it’s a communication protocol between the front and back end. We recommend reading “<a target=\"_blank\" href=\"https://graphql.org/learn/\">Introduction to GraphQL</a>” written by the GraphQL Foundation, where we, as The Guild, are members.</p>\n<p><span><img alt=\"GraphQL.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FGraph_QL_1eb711ebe4.png&w=2048&q=75\"></span></p>\n<p>As you can see, only a small part of data was fetched, leaving project’s name and contributors untouched. This is what GraphQL Hive is about, studying and analyzing the usage of GraphQL API.</p>\n<h2 id=\"a-database-for-graphql-api-monitoring\"></h2>\n<p>Let’s start by explaining the kinds of data GraphQL Hive operates on.</p>\n<p>We could group them into three buckets:</p>\n<ul>\n<li>Schema Registry</li>\n<li>Monitoring</li>\n<li>Analytics</li>\n</ul>\n<p>This article will mainly focus on monitoring and analytics features which ended up being the most challenging part to scale.</p>\n<p>GraphQL Hive tries to answer the following questions:</p>\n<ul>\n<li>Who are the consumers of GraphQL API?</li>\n<li>What part of GraphQL API is consumed and by whom?</li>\n<li>What is the performance of GraphQL API?</li>\n</ul>\n<p>To answer those questions, GraphQL Hive analyses every HTTP request and collects:</p>\n<ul>\n<li>name and version of an API consumer</li>\n<li>a list of requested types and fields (like User, Comment, User.id, User.name)</li>\n<li>an overall latency</li>\n<li>a body of the request</li>\n</ul>\n<p>GraphQL Hive stores the details of every HTTP request.</p>\n<h2 id=\"previously-in-graphql-hive\"></h2>\n<p>This kind of data is not meant to be mutated, requires a Time to Live mechanism and a set of functions for analytics and data aggregation.</p>\n<p>We decided to use Elasticsearch because it checked all the boxes and was flexible enough to evolve the product over time.</p>\n<h2 id=\"problems-with-elasticsearch\"></h2>\n<p>My biggest concern with Elasticsearch was the query language. Everyone at The Guild (the company behind GraphQL Hive) is familiar with SQL, so the JSON-based language meant a steep learning curve.</p>\n<p>At some point during the preview program, we reached the first scaling issues.</p>\n<p>The average response time was getting slower as we stored more and more data.</p>\n<p>The other problem was related to indexing. One big user affected the query performance of other smaller users.</p>\n<p>We tried to improve it by creating an index per user, but because the overall speed of Elasticsearch was way below what we expected, we started looking for an alternative.</p>\n<h2 id=\"alternatives-to-elasticsearch\"></h2>\n<p>When looking for an alternative, these were the requirements:</p>\n<ul>\n<li>Easy to learn and maintain</li>\n<li>Superb performance</li>\n<li>Good for analytics and aggregation of data</li>\n<li>Built-in TTL</li>\n<li>Type System</li>\n<li>No issue with high cardinality</li>\n</ul>\n<p>We must say, there are more databases than people and even more benchmarks with different conclusions.</p>\n<p>After researching, We decided to test <strong>InfluxDB</strong>, <strong>TimescaleDB</strong>, <strong>Druid</strong>, and <strong>ClickHouse</strong>.</p>\n<p>We created a dataset of 20M rows in which one user owned half of them. To measure the performance, we tried to calculate a few high percentiles and see if one big user affects the query performance of the other, smaller users.</p>\n<h2 id=\"the-baseline-was-10s-with-elasticsearch\"></h2>\n<p>We had big expectations for <strong>InfluxDB</strong>, it seemed like an extremely fast time-series database. Unfortunately, like many time-series databases, it struggles with the <a target=\"_blank\" href=\"https://clickhouse.com/resources/engineering/high-cardinality-slow-observability-challenge\">high-cardinality data</a> common in modern observability platforms.. Every collected HTTP request in GraphQL Hive could be labeled with an infinite number of values across all users.</p>\n<p>It was also really hard for us to get started.</p>\n<p><strong>The query time was ~5s.</strong></p>\n<p>Next was <strong>TimescaleDB</strong>. We liked the fact that it speaks SQL and supports relations between tables. The overall performance was much better than what we experienced with Elasticsearch.</p>\n<p><strong>The response time was close to 3 seconds.</strong></p>\n<p>At the time of our research (April 2021), <strong>ClickHouse</strong> felt very mysterious to us. We haven’t heard much about it, and we found only a few case studies. It seemed very similar to TimescaleDB but offered a much wider set of functions for data analytics, and the collection of table engines was perfect for our use case.</p>\n<p><strong>The query time was… ~100ms.</strong></p>\n<p>We haven’t tested Druid, it felt too complex. Even though it may be capable of handling an enormous amount of data, we wanted to find something simple yet powerful, and ClickHouse seemed like a perfect fit.</p>\n<p><span><img alt=\"average_read_time.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Faverage_read_time_1e59bdec8f.png&w=2048&q=75\"></span></p>\n<h2 id=\"migrating-from-elasticsearch\"></h2>\n<p>The migration from Elasticsearch to ClickHouse was done gradually and wasn’t complex.</p>\n<p>During the preview program, the Time to Live for collected data was only 30 days.</p>\n<p>That’s why we decided to write data to both destinations at once, for a full month. This allowed us to seamlessly shift the read operations to ClickHouse, with zero downtime.</p>\n<h2 id=\"graphql-hive-and-clickhouse\"></h2>\n<p>After the switch, we saw a 100x improvement on average compared to the previous data pipeline.</p>\n<blockquote>\n<p>ClickHouse helped us to scale from millions to billions of rows monthly without headaches.</p>\n</blockquote>\n<p>If you’re curious about our database structure and how we use ClickHouse, we recommend you to check out the source code <a target=\"_blank\" href=\"https://github.com/kamilkisiela/graphql-hive/blob/64e53f207b413f8bb222eabd6aeb437e3300dbfd/packages/services/storage/migrations/clickhouse.ts#L4-L189\">on GitHub</a>.</p>\n<p>We also wrote a much more <a target=\"_blank\" href=\"https://the-guild.dev/blog/graphql-hive-and-clickhouse\">in-depth article</a> explaining our ClickHouse setup and how we are able to process billions or GraphQL requests monthly.</p>\n<h2 id=\"taking-it-to-the-next-level-with-clickhouse-cloud\"></h2>\n<p>Our current data pipeline uses a single instance of ClickHouse.
