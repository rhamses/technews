For more information you can consult the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/understanding-query-execution-with-the-analyzer\">query analyzer documentation</a>.&#160;</p>\n<p>From a very high-level standpoint, when ClickHouse executes a query, the following happens:&#160;</p>\n<ul>\n<li><strong>Query parsing and analysis</strong></li>\n</ul>\n<p>The query is parsed and analyzed, and a generic query execution plan is created.&#160;</p>\n<ul>\n<li><strong>Query optimization</strong></li>\n</ul>\n<p>The query execution plan is optimized, unnecessary data is pruned, and a query pipeline is built from the query plan.&#160;</p>\n<ul>\n<li><strong>Query pipeline execution</strong></li>\n</ul>\n<p>The data is read and processed in parallel. This is the stage where ClickHouse actually executes the query operations such as filtering, aggregations, and sorting.&#160;</p>\n<ul>\n<li><strong>Final processing</strong></li>\n</ul>\n<p>The results are merged, sorted, and formatted into a final result before being sent to the client.</p>\n<p>In reality, many <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/concepts/why-clickhouse-is-so-fast\">optimizations</a> are taking place, and we will discuss them a bit more in this guide, but for now, those main concepts give us a good understanding of what is happening behind the scenes when ClickHouse executes a query.&#160;</p>\n<p>With this high-level understanding, let’s examine the tooling ClickHouse provides and how we can use it to track the metrics that affect query performance.&#160;</p>\n<h2 id=\"demo-environment\"></h2>\n<p>As discussed in the introduction, we recently deployed the <a target=\"_blank\" href=\"https://sql.clickhouse.com/\">ClickHouse Playground</a> demo environment for anyone to play with different datasets using ClickHouse. In those systems, primary keys enforce uniqueness and data integrity. Instead, it is designed to optimize query performance. The primary key defines the order in which the data is stored on disk and is implemented as a sparse index that stores pointers to the first row of each granule.</p>\n<blockquote>\n<p>Granules in ClickHouse are the smallest units of data read during query execution. They contain up to a fixed number of rows, determined by index_granularity, with a default value of 8192 rows. Granules are stored contiguously and sorted by the primary key.&#160;</p>\n</blockquote>\n<p>Selecting a good set of primary keys is important for performance, and it's actually common to store the same data in different tables and use different sets of primary keys to speed up a specific set of queries.&#160;</p>\n<p>Other options supported by ClickHouse, such as Projection or Materialized view, allow you to use a different set of primary keys on the same data.
