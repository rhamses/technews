Next, let’s map those IDs to real user <a target=\"_blank\" href=\"https://docs.bsky.app/docs/advanced-guides/resolving-identities\">handles</a> in real-time.</p>\n<p>The JSON documents for post, repost, like events, and similar Bluesky actions do not contain user handles or names—only their DIDs:</p>\n<p><span><img alt=\"Blog-bluesky-faster.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_bluesky_faster_001_80577d40e2.png&w=2048&q=75\"></span></p>\n<p>Unlike DIDs, handles and names can change at any time due to <code>identity</code> events in Bluesky:</p>\n<p><span><img alt=\"Blog-bluesky-faster.002.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_bluesky_faster_002_821026cca7.png&w=2048&q=75\"></span></p>\n<p>Fortunately, ClickHouse offers a perfect solution for this scenario: <strong>updatable in-memory dictionaries</strong>, allowing efficient real-time lookups and seamless updates.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries\">Dictionaries</a> are a <a target=\"_blank\" href=\"https://clickhouse.com/blog/faster-queries-dictionaries-clickhouse\">key feature</a> of ClickHouse providing in-memory <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Key%E2%80%93value_database\">key-value</a> representation of data from various internal and external sources, optimized for super-low latency lookup queries.</p>\n<p>The diagram below illustrates how, in our dashboard scenarios, an in-memory dictionary is created and loaded to enable efficient real-time lookups for dynamic metadata, such as user handles, allowing dashboards to be enriched on-the-fly with up-to-date information at query time:</p>\n<p><span><img alt=\"Blog-bluesky-faster.011.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_bluesky_faster_011_0aab10dc01.png&w=2048&q=75\"></span></p>\n<p>We create (see below) an ① handle_per_user_dict dictionary to map persistent, long-term Bluesky user identifiers (<a target=\"_blank\" href=\"https://docs.bsky.app/docs/advanced-guides/resolving-identities\">DIDs</a>) to their latest corresponding user handles. When a user changes their handle, the Bluesky API streams an <code>identity</code> JSON document. By grouping these documents by DID value, we use the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/aggregate-functions/reference/argmax\">argMax</a> aggregate function in ClickHouse to retrieve the handle from the latest identity document per unique DID—forming the basis of the ② dictionary load query.</p>\n<p>Like refreshable materialized views, a dictionary can be periodically updated atomically—ensuring that queries performing lookups remain unaffected—by periodically executing its load query.</p>\n<p>To avoid repeatedly running the <code>argMax</code> aggregation on the ever-growing 4+ billion-row Bluesky dataset, we introduce an <strong>efficiency optimization</strong>, as illustrated in the next diagram:</p>\n<p><span><img alt=\"Blog-bluesky-faster.012.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_bluesky_faster_012_c328034409.png&w=2048&q=75\"></span></p>\n<p>We introduce an ① additional incremental materialized view that runs the argMax aggregation only on newly inserted blocks of rows, storing the pre-aggregated data in a ② ReplacingMergeTree table. This table’s <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges#replacing-merges\">background merges</a> ensure that only the latest handle per unique DID is retained. The dictionary’s ③ load query then runs against this smaller table, using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/select/from#final-modifier\">FINAL</a> modifier to finalize row replacements from unmerged parts at query time.</p>\n<p>Next, we present the DDL statements to set this up.</p>\n<p>This is the DDL for the incremental materialized view’s target table:</p>\n<div><pre><code><span><span>CREATE TABLE</span> bluesky.handle_per_user</span>\n<span>(</span>\n<span>    did String,</span>\n<span>    handle String</span>\n<span>)</span>\n<span>ENGINE <span>=</span> ReplacingMergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (did);</span></code></pre></div>\n<!-- -->\n<p>This is the incremental materialized view:</p>\n<div><pre><code><span><span>CREATE</span> MATERIALIZED <span>VIEW</span> bluesky.handle_per_user_mv </span>\n<span><span>TO</span> bluesky.handle_per_user</span>\n<span><span>AS</span> </span>\n<span><span>SELECT</span></span>\n<span>    data.identity.did::String <span>AS</span> did,</span>\n<span>    argMax(data.identity.handle, bluesky_ts) <span>AS</span> handle</span>\n<span><span>FROM</span> bluesky.bluesky</span>\n<span><span>WHERE</span> (kind <span>=</span> <span>'identity'</span>)</span>\n<span><span>GROUP</span> <span>BY</span> did;</span></code></pre></div>\n<!-- -->\n<p>Finally, we create the in-memory dictionary with a query against the materialized view’s target table to load its content. We also set a time interval (in seconds) for updates, allowing ClickHouse to randomly distribute the update time within this range—helping to balance the load when updating across a large number of servers:</p>\n<div><pre><code><span><span>CREATE</span> DICTIONARY bluesky.handle_per_user_dict</span>\n<span>(</span>\n<span>    did String,</span>\n<span>    handle String</span>\n<span>)</span>\n<span><span>PRIMARY KEY</span> (did)</span>\n<span>SOURCE(CLICKHOUSE(QUERY $query$</span>\n<span>    <span>SELECT</span> did, handle</span>\n<span>    <span>FROM</span> bluesky.handle_per_user <span>FINAL</span></span>\n<span>$query$))</span>\n<span>LIFETIME(MIN <span>300</span> MAX <span>360</span>)</span>\n<span>LAYOUT(complex_key_hashed());</span></code></pre></div>\n<!-- -->\n<p>Note that dictionaries are either loaded at server startup or at first use, depending on the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/server-configuration-parameters/settings#dictionaries_lazy_load\">dictionaries_lazy_load</a> setting.</p>\n<p>Users can also manually trigger a load by running a SYSTEM command. When used with the ON CLUSTER clause, this ensures that all compute nodes in our Cloud service load the dictionary into memory:</p>\n<div><pre><code><span><span>SYSTEM</span> RELOAD DICTIONARY bluesky.handle_per_user_dict <span>ON</span> cluster <span>default</span>;</span></code></pre></div>\n<!-- -->\n<p>Now the dictionary is ready to be used ad-hocly in our dashboard queries for mapping DIDs to user handles, for example:</p>\n<div><pre><code><span><span>SELECT</span> dictGet(<span>'bluesky.handle_per_user_dict'</span>, <span>'handle'</span>, <span>'did:plc:emtmklr75yrbuuth4avvutos'</span>) <span>AS</span> handle;</span></code></pre></div>\n<p>Static result for the query above from March 2025:</p>\n<div><pre><code><span>┌─handle──────────────┐</span>\n<span>│ agbogho.bsky.social │</span>\n<span>└─────────────────────┘</span>\n<span></span>\n<span>1 row in set.
