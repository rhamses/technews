Accomplishing this takes two steps:</p>\n<ol>\n<li>Deduct $10 from the origin’s account balance</li>\n<li>Add $10 to the destination’s account balance</li>\n</ol>\n<p>It’s important that these two updates occur together or not at all. Otherwise, the bank may be left in a state where $10 is unaccounted for! (In the case where #1 is successful, and #2 fails).</p>\n<p>These types of <em>transactional</em> guarantees are the main focus of OLTP databases.</p>\n<p>Given these requirements, OLTP databases typically hit performance limitations when used for analytical queries over large datasets.</p>\n<p>OLAP, or <em>online analytical processing</em> databases, are designed to meet those needs — to manage <em>analytical</em> workloads.</p>\n<p>The primary objective of these databases is to ensure that engineers can efficiently query and aggregate over vast datasets. <em>Real-time</em> OLAP systems like ClickHouse allow this analysis to happen as data is ingested in real-time.</p>\n<h2 id=\"when-is-each-most-appropriate\"></h2>\n<p>OLTP databases excel when queries aim to retrieve a specific set of rows, potentially accessing a higher number of columns, and when data is subject to frequent updates that must be executed in real-time. By optimizing for high-speed transactions and concurrency, OLTP databases permit data to be accessed and modified simultaneously without conflicts. These access patterns make OLTP databases ideal for storing the <strong>data that maintains the application state</strong> and enables user interactivity. Postgres’ ability to respond rapidly despite high query concurrency under these workloads has made it the OLTP database of choice for applications, powering a wide range of use cases from e-commerce and financial trading platforms to customer service systems.</p>\n<p>Conversely, OLAP databases, such as ClickHouse, excel at <strong>analytical queries</strong> that access many rows but few columns. These queries typically summarize billions (if not trillions) of rows using GROUP BY operations and analytical functions over several very large tables. These workloads are typically associated with larger datasets where query times of less than 50ms are still required. In order to deliver this high performance, OLAP databases typically sacrifice certain functionality such as transactions, support for limited query concurrency, update support, and requiring users to perform inserts in batches.</p>\n<p>While ClickHouse can be categorized as an OLAP database, it also supports real-time analytical workloads, where query concurrency is typically much higher. This makes ClickHouse perfect for adding analytics to your application!</p>\n<h2 id=\"a-real-world-ish-example\"></h2>\n<p>To help users understand these principles, we decided to build an application utilizing each database appropriately. With billions, if not trillions, of rows in ClickHouse, pulling the source data into Postgres is infeasible. Developers don’t need to worry about maintaining complex ETL pipelines.</li>\n<li>Transactional/operational data can be joined with analytics data in ClickHouse, exposing new features such as in our HouseClick example.</li>\n<li>Reduction of infrastructure to manage as well as savings in setup time and bandwidth.</li>\n</ul>\n<p>Adding a Foreign ClickHouse table to Supabase is trivial. These views can be used with table functions, which specify the name of the view as the function name and the parameter values as its arguments.
