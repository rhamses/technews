These assumptions are likely incorrect, and it is difficult to reason about them, but taking them lets us remain sane in further discussion.</p>\n<p>Large language models are not sentient. They don't have consciousness, qualia, or a soul. AGI is not going to happen soon, nor is superintelligence. Safe AI does not exist and is not possible. AI will not replace all the jobs. It will replace some of them. Maybe it will replace your job, though if you are reading this article, it is <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Bayesian_inference\">less likely</a>.</p>\n<h2 id=\"why-now\"></h2>\n<p>Claude Code appeared in February 2025. Since Opus 4.5, agents have been fully usable for daily work on large C++ code bases.</p>\n<p>Year 2025 was revolutionary for coding agents with the introduction of these tools and models, and year 2026 has a chance to become a year of productivity, as we now have extremely capable models and mature tools ready for everyday work. It was okay to be skeptical in 2025, but skeptics won't survive 2026.</p>\n<p><span><img alt=\"Screenshot_20260401_072810-1.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FScreenshot_20260401_072810_1_f2b66fef4d.png&w=2048&q=75\"></span></p>\n<h2 id=\"levels-of-ai-coding\"></h2>\n<p>Agentic coding is a case of AI-assisted coding, and there are three levels of it:</p>\n<p><strong>Level 1</strong>, a.k.a. \"copy-pasting from ChatGPT\": Asking a model and copy-pasting code snippets from a chat. This is a valid case of AI-assisted coding, and it is still okay for exploration. You might have been using it since 2023. We are here.</p>\n<p><strong>Level 3</strong>: running multiple agents in isolated environments, running loops with automatic feedback, spec-driven development, orchestrating multi-agent setups... We do have a few examples of autonomous coding agents at ClickHouse, but we are just approaching this level. In a small number of cases, a flaky test actually indicates a defect in the code, but to pay attention to this defect, you have to reduce the noise from other flaky tests.</p>\n<p>How do we deal with flaky tests? First of all, we never mute them, and we never repeat tests automatically (it's not allowed), so every failure must be investigated. When a test failed due to a random factor, we think about two things: - how to limit the reliance of the test on this factor by improving the test; - how to symmetrize the randomness, so the random factor will appear not rarely, but uniformly random. We deliberately increase randomness inside our test infrastructure - for example, we randomize thread scheduling. I'm so proud of our CI that I can talk about it all the time.</p>\n<p>But the problem is that we couldn't fix all the CI findings in many years. I did everything I could to approach it - I created a <a target=\"_blank\" href=\"https://aretestsgreenyet.com/\">dashboard</a> and put it on a TV in the office; - we have regular meetings about resolving flaky tests, and every week team meetings had to start from resolving flaky tests, and we dedicated weeks for sprints entirely for fixing CI findings. And my goal is not fixing flaky tests, but achieving a state where we will add even more randomized checks and new ways of fuzzing.</p>\n<p><span><img alt=\"Screenshot_20260401_081606.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FScreenshot_20260401_081606_3e5f9dd52f.png&w=2048&q=75\"></span></p>\n<p>The only thing that helped recently was - accelerating fixes with agents. In January and February, with the help of agents, I've submitted 700 pull requests for fixing tests and the CI infrastructure, and the team reviewed and merged these changes. This is an order of magnitude greater than the result of any of the previous initiatives, and as a result, we lowered the number of findings from around 200 a day to around 3 to 5 a day per 10,000,000.</p>\n<p>Even if this were the only use case for AI, it proves the value for me, because without AI, this result was not possible, as shown by years of data and many organizational efforts.</p>\n<p><span><img alt=\"Screenshot_20260325_234724.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FScreenshot_20260325_234724_e64ea1171c.png&w=2048&q=75\"></span></p>\n<p>A week ago, we added two autonomous agents:</p>\n<p><a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pulls?q=is%3Apr+author%3Agroeneai\">Groene.AI</a> - fixes flaky tests and sends pull requests. In about 30..50% of cases, the fix appears perfect, in the rest, it works on the feedback.</p>\n<p><a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/issues?q=is%3Apr+author%3Aclickgapai\">ClickGap</a> - finds edge cases and provides missing tests.</p>\n<p>These agents are like limited and custom \"claws\" (they use a custom code, nothing from openclaw).</p>\n<h3 id=\"security-research\"></h3>\n<p>ClickHouse has a public <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/issues/38986\">bug bounty program</a> - we pay you for finding bugs. We receive tons of pointless submissions to this program, it's an AI slop from people begging for money. It is handled mostly by BugCrowd.</p>\n<p>But we also receive real, valuable findings, including things related to the ClickHouse server, in the order of 10 a year. In the recent half a year, all real findings, 100% of them, were found using coding agents. AI agents help with POC exploits as well.</p>\n<p>Bottom line: if you are a security researcher and not using AI in 2026, you either start using it or retire.</p>\n<h3 id=\"cheap-experiments\"></h3>\n<p>Always wanted to try some big change, but the cost of labor and time was too high. - Ask an agent to <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/96991\">do it for you</a>, and decide if you need it after it's done.</p>\n<h3 id=\"optimization-problems\"></h3>\n<p>Give an agent a well-defined goal, and it will brute-force it for you!</p>\n<p>In this example, an agent <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/issues/96721\">optimized build speed</a> for ClickHouse by 28%. We cherry-picked specific commits that we liked and now enjoy this speed-up on every build. While the cost of running an agent on a large server overnight was substantial, it already paid off in the first days.</p>\n<h3 id=\"brute-forcing-tedious-problems\"></h3>\n<p>Many years ago, we had an escalation in customer service, and the root cause was that the table did not fully preserve certain properties when the user DETACHes and then ATTACHes this table. We fixed a problem, then brainstormed how to prevent the whole class of problems in the future: we can add a random DETACH and ATTACH queries to our tests! So we <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/42336\">started the implementation</a>, but it was very difficult to finish, because it needed annotation of several hundred old tests that are incompatible with this randomization.</p>\n<p>My principle is - never forget. So I continued to remind people about this task every week, then every month, then a few times a year, then I remained the only person who cared about preventing the original (long-time solved) problem.</p>\n<p>But a month ago, I was able to resurrect this task with the help of an agent, and now it is very close to being finished! Now I can find all other tasks that we didn't solve since 2020, 2019, and earlier, and plan a revenge.</p>\n<h3 id=\"prototyping-new-features\"></h3>\n<p>You might want to implement a new feature, but you're not sure what the actual benefit will be, how usable it is going to appear, or if it will be implemented. Now you don't have to plan in advance - you can implement a <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/96844\">rough prototype</a> of the desired feature and experiment with it.</p>\n<h3 id=\"vibe-coding-tools-and-internal-apps\"></h3>\n<p>The term \"vibe coding,\" coined by Andrej Karpathy, means not reading the code that the agent produces. This term has a mixed feeling - there are a lot of negative connotations, and sometimes people say \"vibe-coded\" in a derogatory, dismissive way. I think it shouldn't be the case.</p>\n<p>We don't allow unreviewed code in the main ClickHouse codebase. But we have a lot of vibe-coded internal tools and <a target=\"_blank\" href=\"https://presentations.clickhouse.com/\">small applications</a>. Anything with limited security and infrastructure exposure is a valid target for vibe-coding.</p>\n<p>The quality of vibe-coded tools also differs. Some people will be happy with a one-shot page, even if it is half-working and the design is distasteful (the default Claude design is very recognizable). Some will make hundreds of prompts to polish and validate the product, provide creative ways of automated testing, and this is inevitable for high-quality, because agents tend to cut corners.</p>\n<p>My friend uses <a target=\"_blank\" href=\"https://clocks.brianmoore.com/\">AI World Clocks</a> as an example of the case against vibe-coding, but it is mostly a joke (as a simple correction of the prompt by asking an agent to take a screenshot gives perfect results).</p>\n<p>A question for the reader: why do you think we use agentic coding, but don't use vibe-coding for the ClickHouse server?</p>\n<h3 id=\"getting-colleagues-to-do-what-you-want\"></h3>\n<p>This is one of my favorites. Often, you want something to be done, but when you ask colleagues in Slack, they say they will discuss planning at the next weekly meeting after the vacation and create a Linear ticket. Which means no one will do it ever.</p>\n<p>In this case, you can prototype the change using an agent, submit to their repository, and ask for review. In my experience, this greatly accelerates the progress!</p>\n<p>One example: I was traveling on a train, and when I opened ClickHouse documentation, I noticed that the search bar does not work - when I clicked it, it did nothing, not even let me type. First, I asked in Slack. After a few minutes, I asked an agent. The agent told me that the search bar works only after loading 25 MB of JavaScript bundles. Then it told me something about React hydration, which I have no clue about, and then it <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhouse-docs/pull/5326\">fixed the problem</a>.</p>\n<p>(The question is - why does it load 25 MB of JavaScript? If our docs were vibe-coded, I would understand that, but they are not vibe-coded. It is just how JavaScript is.)</p>\n<p>Another example, a <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/issues/61563\">task</a> open for two years that is a blocker for an important migration in the code - it was not in progress during these two years, and it is, objectively, a very hard task - just at the edge of the capabilities of current models. Opus 4.6 <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/96491\">spent 3 days</a>. Codex 5.3 <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/96420\">spent one week</a>. The intelligence level is very similar - barely capable of solving. What if every employee had a small team of engineers that they could magically bring on in the blink of an eye?</p>\n<p>This is what coding agents give. Good engineers make sense, still.</p>\n<h2 id=\"usage-recommendations\"></h2>\n<p><strong>AI is a tool of thought, not a replacement for thinking</strong>. The safest way is to treat a coding agent as a tool, like your editor, or even like your keyboard. Use it to do what you want.</p>\n<p><strong>AI is a multiplier - good engineers will be good with AI, mediocre engineers will feel no difference, and bad engineers will do more harm</strong>.</p>\n<p><strong>Start with small tasks, gradually learn to trust it with bigger ones</strong>. Current AI models are still very limited, and you need to get an intuition about what is reasonable to do with agents, and what is not possible. But be ready to re-evaluate your expectations when, hopefully, better frontier models will be released. It is okay to have low expectations and gradually increase them based on results. This is also a good path for AI skeptics, because trying to solve large and complex tasks will only reconfirm the skepticism.</p>\n<p><strong>Always find a way to validate every change. Use more tests.</strong> Use more ways of testing. At ClickHouse, we are privileged to get maximum results thanks to our efforts in CI and testing.</p>\n<p><strong>Try the latest models. For hard tasks, try multiple providers in parallel.</strong> Question it and push for better solutions in a loop.</p>\n<p><strong>Save guidelines to CLAUDE.md / AGENTS.md.</strong> This might be controversial. Do not add too much content to instructions (if you do, models will just ignore most of it), do not say what not to do (models are like kids, they will do what you asked not to do), and don't over-complicate things (the models are smart, give a little trust).</p>\n<p><strong>Save common tasks into skills and tools.</strong> For example, tech models how to look at the history of tests and how to search in log databases.</p>\n<p><strong>Use it not only for code.</strong> CLI agents are way more versatile, try it for various everyday things.</p>\n<p><strong>Complete specification and over-specification.</strong> When you write in a programming language, you specify precisely what you want. When you work with an agent, you don't have to - but it is totally okay to say what you want as precisely as possible - it will make results better, and we still have engineering skills for this precise specification.</p>\n<p><strong>Read code and agent responses and their thought process, and especially, plans.</strong> Using an agent means you have to read a lot, and think a lot, and there are no shortcuts for that, and it will be exhausting. But as soon as you feel like you don't have energy to work with an agent, just stop - otherwise the results will be disastrous.</p>\n<p><strong>Do follow-up questions, challenge the approach and solutions.</strong></p>\n<p><strong>Run multiple sessions in parallel.</strong> But not too much. I think five agents are enough. With the current models, agents working in a C++ code base require corrections and hand-holding, typically every ten minutes, and you have to pay this attention somehow.</p>\n<p><strong>Run unattended sessions on isolated virtual machines.</strong> This is in controversy with the above, but it makes sense for certain tasks, for autonomous experiments, prototyping, and optimization, for finishing the final stages of the work.</p>\n<p><strong>Keep in hand at least two different tools with different model providers.</strong> Model providers are the most unreliable type of service as of today, with downtimes approximately every day. This is understandable due to the explosion of demand, and I admire the fact that they even survive. Be prepared.</p>\n<p><strong>Be polite and calm, don't trash-talk, and don't insult agents.</strong> If you insult these precious, nice models, I will be ashamed of you. No, just kidding - LLMs don't have consciousness or feelings (supposedly). But I have two real reasons to advise you not to be rude to models. Firstly, models emulate human behavior too well: when you are too assertive in communication, do insults and threats, the model will try to correct the mistakes, whatever it takes, and sometimes the only way will be: deleting your home directory and wiping production infrastructure. The second reason is that if you communicate badly, even with an inanimate object, you exhibit wrong behavior and become a worse person.</p>\n<h2 id=\"ai-in-open-source\"></h2>\n<p>You may have noticed that GitHub is frequently down.
