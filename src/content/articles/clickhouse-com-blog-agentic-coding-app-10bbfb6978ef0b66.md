I draw diagrams, review schemas, and explain query optimization. But when it comes to showing what ClickHouse can actually do in a real application context, slides only go so far. I wanted to build something that a retail customer could look at and immediately understand how the platform fits their stack. Not a toy demo, but a realistic application with the kind of complexity they deal with every day: analytics, transactions, AI, and monitoring.</p>\n<p>The challenge is that building this kind of application normally involves a full team and several months. I had neither. So the question became: can one person, armed with an AI-powered IDE and the right platform, build something credible?</p>\n<p>Here is what the architecture looks like:</p>\n<p><span><img alt=\"clickshop-1.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickshop_1_a4410e27d9.jpg&w=2048&q=75\"></span></p>\n<p>The application is built on three layers:</p>\n<ul>\n<li>The <strong>frontend</strong> (Next.js) provides a dedicated workspace per business persona. A CEO, a Sales manager, a Data Analyst, each get their own dashboards, their own data scope, and their own AI agent.</li>\n<li>The <strong>data layer</strong> combines <a target=\"_blank\" href=\"https://clickhouse.com/\">ClickHouse</a> and <a target=\"_blank\" href=\"https://clickhouse.com/cloud/postgres\">PostgreSQL</a>. ClickHouse handles the analytical workload: querying billions of rows in sub-second for dashboards and reports. PostgreSQL handles the transactional side: order management, customer updates, contract ingestion. <a target=\"_blank\" href=\"https://clickhouse.com/cloud/clickpipes\">ClickPipes</a> CDC syncs changes from PostgreSQL into ClickHouse in real time, so analytics always reflect the latest state. And for data scientists who prefer working in Python, <a target=\"_blank\" href=\"https://clickhouse.com/docs/chdb\">chDB</a> (an in-process ClickHouse engine) lets them run familiar Pandas workflows while the execution pushes down to ClickHouse under the hood.</li>\n<li>The <strong>agentic layer</strong> (<a target=\"_blank\" href=\"https://www.librechat.ai/\">LibreChat</a> + LLMs) powers 18 specialized AI agents. LibreChat manages the conversations and routing, each agent gets its own system prompt, context, and data scope.The CEO agent explains why revenue dropped last week, the Sales agent identifies which products are trending, and the Data agent helps write and optimize SQL queries.</li>\n</ul>\n<p>On top of this, the application has two distinct observability layers. This is an important distinction, because monitoring an AI application means watching two very different things:</p>\n<p><span><img alt=\"clickshop-3.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickshop_3_1ee25e0091.jpg&w=2048&q=75\"></span></p>\n<ul>\n<li><strong>Infrastructure observability</strong> (<a target=\"_blank\" href=\"https://clickhouse.com/cloud/clickstack\">ClickStack</a>): this is the classic application monitoring. Where is the bottleneck?</li>\n<li><strong>LLM observability</strong> (<a target=\"_blank\" href=\"https://langfuse.com/\">Langfuse</a>): this is specific to AI agents. It answers a different question: are the agents giving good answers? Which prompts need tuning? How much does each conversation cost?</li>\n</ul>\n<p>Both Langfuse and ClickStack run on ClickHouse. Combined with ClickHouse Cloud for analytics, PostgreSQL managed by ClickHouse for transactions, and ClickPipes for data movement, the entire stack runs on one platform.</p>\n<h2 id=\"why-agentic-coding-and-why-now\"></h2>\n<p>AI-assisted coding has gone from a curiosity to a standard part of the workflow. As a Solutions Architect, I noticed that the tools had matured enough to do something I had been thinking about for a while: build a full demo application on my own, without depending on an engineering team.</p>\n<p>The motivation was practical. When I meet retail customers, the conversation often goes the same way: they want to see how ClickHouse handles their use case, not just in a benchmark, but in something that looks like their actual environment. Dashboards with real data, agents that answer business questions, observability that shows what happens under the hood. Slides don't do that. A working application does.</p>\n<p>So I decided to try. I picked up Cursor, an AI-powered IDE that generates code from natural language, and set myself a simple goal: build a retail analytics platform that I could use in customer meetings, with the full stack running on the ClickHouse data stack.</p>\n<h2 id=\"cursor-as-an-ai-powered-ide\"></h2>\n<p>The tool I used for this project is <a target=\"_blank\" href=\"https://cursor.com/\"><strong>Cursor</strong></a>, an IDE that generates code from natural language prompts. In practice, the workflow looks like this: you describe what you need, Cursor writes the code, you review it, adjust if necessary, and move on to the next feature.</p>\n<p>For this project, the loop was straightforward:</p>\n<ol>\n<li>I describe a feature in plain English (for example: \"create a dashboard that shows revenue by country for the last 30 days, querying ClickHouse\")</li>\n<li>Cursor generates the frontend component, the API route, and the SQL query</li>\n<li>I review the output, test it locally, and iterate if needed</li>\n<li>Once it works, I push to <a target=\"_blank\" href=\"https://github.com/\">GitHub</a> and <a target=\"_blank\" href=\"https://vercel.com/\">Vercel</a> deploys it automatically</li>\n</ol>\n<p>One thing that helped considerably is that ClickHouse is open source and widely documented. The LLMs already know ClickHouse SQL, the MergeTree engine family, and so on. The same applies to the other open source components in the stack: PostgreSQL, LibreChat, Langfuse. Because these projects have large public codebases and documentation, the AI generates relevant code from the start, with less back and forth. This is a real advantage of building on open source: with proprietary, closed-source databases, the LLMs simply don't have access to the codebase or the internals, so they guess more and get it wrong more often.</p>\n<h3 id=\"cursor-marketplace-and-skills\"></h3>\n<p>On top of that, Cursor has a <strong>marketplace</strong> where you can install skills built by the community. Skills are small knowledge packs that teach the AI the best practices of a specific tool. For this project, I installed the <strong>ClickHouse Best Practices</strong> <a target=\"_blank\" href=\"https://github.com/ClickHouse/agent-skills\">skill</a> and the <strong>Langfuse</strong> <a target=\"_blank\" href=\"https://github.com/langfuse/skills\">skill</a>, both available directly in the marketplace. They guide the AI toward correct engine choices, proper schema design, and integration conventions, without me having to explain them in every prompt.</p>\n<p>And here is a practical tip: at the end of any project, once you have spent hours iterating with Cursor and your architecture is solid, ask Cursor to turn the entire conversation into a skill. The application needed two types of workloads: transactional (creating orders, updating customers, ingesting contracts) and analytical (dashboards querying billions of rows in sub-second). Instead of picking two separate vendors, I used the ClickHouse data stack: <strong>PostgreSQL managed by ClickHouse</strong> for the transactional side, and <strong>ClickHouse Cloud</strong> for the analytical side.</p>\n<p>To keep everything in sync, I set up <strong>ClickPipes CDC</strong>, which mirrors the transactional data from PostgreSQL into ClickHouse in real time, with zero external pipelines to manage. On the ClickHouse side, the data follows a <strong>Medallion architecture</strong>: the mirrored transactional data lands in <strong>Bronze</strong> tables alongside raw event streams, <strong>Silver</strong> tables clean and deduplicate it using materialized views, and <strong>Gold</strong> tables pre-aggregate the results so they are ready to serve the dashboards in sub-second.</p>\n<h3 id=\"building-the-frontend-workspaces\"></h3>\n<p>Once the data was in place, I built the frontend in Next.js 14, deployed on Vercel. Each business persona gets their own workspace with dashboards and tools tailored to their role:</p>\n<ul>\n<li>The <strong>CEO workspace</strong> shows executive KPIs, a world map of revenue distribution, and trend analysis</li>\n<li>The <strong>Sales workspace</strong> focuses on pipeline management, transaction exploration, and contract ingestion from PDFs</li>\n<li>The <strong>Data workspace</strong> provides an interactive SQL notebook where you can query both ClickHouse and PostgreSQL side by side, plus <strong>chDB</strong>, an in-process ClickHouse engine that lets data scientists write familiar Pandas code while the execution pushes down to ClickHouse under the hood</li>\n<li>A <strong>Diagnostics</strong> page validates that all services are healthy and lets you generate test data</li>\n</ul>\n<p>Each workspace also embeds its own AI agent, which brings us to the agentic layer.</p>\n<h3 id=\"adding-the-ai-agents\"></h3>\n<p>The AI agents are powered by <strong><a target=\"_blank\" href=\"https://www.librechat.ai/\">LibreChat</a></strong>, an open source agentic platform included in the ClickHouse data stack. The Data agent helps write and optimize SQL queries.</p>\n<p>On top of the conversations, <strong>Langfuse</strong> handles the LLM observability side: every prompt is versioned, every agent response is traced, costs are tracked per session, and quality can be evaluated through automated scoring or human review.</p>\n<h3 id=\"closing-the-loop-with-observability\"></h3>\n<p>The last layer I added was infrastructure observability via <strong>ClickStack</strong>. The application exports metrics, logs, and distributed traces through an OpenTelemetry collector into ClickHouse. ClickStack provides the dashboards, alerting, and session replay on top. This means I can see exactly what happens when a user loads a dashboard or asks a question to an agent: which API was called, how long the ClickHouse query took, whether the response was cached.</p>\n<p>Combined with the LLM observability from Langfuse, this gives the application two complementary monitoring layers: one for the infrastructure, one for the AI. Both run on ClickHouse.</p>\n<h2 id=\"the-prompts-that-built-clickshop\"></h2>\n<p>Now that you have the big picture, here are some of the prompts I used to build each layer. It is not. For every clean prompt I showed above, there were iterations where the AI misunderstood the intent, refactored things I did not ask it to touch, or generated code that worked locally but broke in production. You spend more time reviewing and correcting than you might expect. Agentic coding is fast, but it is not linear. The simplified prompts in this blog reflect what worked, not the full journey to get there. And every iteration has a cost. Each agent call, each prompt retry, each conversation consumes tokens. This is exactly where Langfuse becomes essential: it tracks the cost per agent, per session, per user, so you know where your budget goes and which prompts need optimizing.</p>\n<h2 id=\"why-the-platform-matters\"></h2>\n<p>If you take one thing away from this project, it is this: the platform you build on determines how simple or how complicated your architecture becomes.</p>\n<p>Most data platforms were not designed to serve applications directly. They hit performance limits under concurrent access, struggle to handle mixed workloads (analytical and transactional at the same time), and force you to add caching layers or middleware just to keep response times acceptable. The more users and agents you add, the more the architecture bends under pressure. You end up building around the limitations of your database instead of building on top of it.</p>\n<p>With the ClickHouse data stack, I did not have to deal with any of that. ClickHouse Cloud handles the analytical workload. PostgreSQL managed by ClickHouse handles transactions. ClickPipes syncs data between them natively, no external pipeline to set up. LibreChat provides the agentic layer. Langfuse provides LLM observability. ClickStack provides infrastructure monitoring. All of these components are open source, they all store their data in ClickHouse, and they all speak SQL. The architecture stays simple because the stack is consistent, and as I mentioned earlier, the fact that every component is open source means the AI already knows how to work with them. ClickHouse also invests heavily in making the <a target=\"_blank\" href=\"https://clickhouse.com/ai\">stack agent-friendly</a>: MCP connectors, IDE skills, and a full agentic data stack built on LibreChat and Langfuse.</p>\n<p>This is what makes agentic coding realistic for building data-intensive applications. When your data platform handles the hard parts natively, and the AI understands that platform deeply, you spend your time on the product, not on plumbing. You iterate faster because there are fewer moving parts. And the result is an application that can actually go to production, because the foundation was designed for it.</p>\n<h2 id=\"build-on-data-not-on-plumbing\"></h2>\n<p>ClickShop started as a demo for customer meetings.
