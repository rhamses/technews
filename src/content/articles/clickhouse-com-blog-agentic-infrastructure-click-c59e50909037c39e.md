contentHtml: "<div><p>In my last post I built a full-stack retail app, <a target=\"_blank\" href=\"https://clickhouse.com/blog/agentic-coding-app\">ClickShop</a>, with a coding agent and the ClickHouse stack. That project was about writing application code. This one is about something different: standing up and operating real infrastructure.</p>\n<p>I gave the agent a single command-line tool, <a target=\"_blank\" href=\"https://clickhouse.com/docs/interfaces/cli\"><code>clickhousectl</code></a>, and one goal: a multi-region observability platform with three ClickHouse Cloud services in the US, Europe, and Japan, each ingesting OpenTelemetry logs, traces, and metrics, and one global view in Europe.</p>\n<p>What I want to share is less the result than the experience of building it. When your platform speaks a clean CLI, an agent can operate it the same way it edits code: it runs a command, reads the JSON it gets back, and decides the next step. That is what turned a multi-region setup into an afternoon of work.</p>\n<h2 id=\"the-use-case\"></h2>\n<p>As an SA I keep seeing the same starting point at customers: the application is already distributed. You run close to your users in the US, Europe, and Asia, for latency and often for compliance. And the moment the app is spread out, its telemetry is too. Shipping every log line from Tokyo into one central cluster is slow, costly, and frequently not allowed.</p>\n<p>So you live with a tension. Each region has to keep its own logs, traces, and metrics where they are produced, yet the on-call engineer still needs one screen that answers a single question: is the whole system healthy, everywhere?</p>\n<p>The point of this project was to show you don't have to choose between the two. My scenario was deliberately small:</p>\n<ul>\n<li>A ClickHouse Cloud service in the US (<code>us-east-1</code>), one in Europe (<code>eu-west-1</code>), and one in Japan (<code>ap-northeast-1</code>).</li>\n<li>Each service ingests the OpenTelemetry data from its own region.</li>\n<li>Europe carries one consolidated view over all three, and only reaches the other regions when that view is actually queried.</li>\n</ul>\n<p><span><img alt=\"image2.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fimage2_36e14dcc08.png&w=2048&q=75\"></span></p>\n<p><em>Figure 1. Distributed storage, one global view. Each region keeps its telemetry local while Europe exposes a single view that is queried on demand and read by the ClickStack UI.</em></p>\n<h2 id=\"the-architecture\"></h2>\n<p>Ingestion is regional and self-contained. In each region the app sends OTel data to a local collector, which writes into the ClickHouse service sitting next to it. Nothing crosses a border on the write path.</p>\n<p>Europe does one extra job. It hosts a small <code>otel_global</code> database that presents the three regions as a single set of tables, and the ClickStack UI reads from there. Two ordinary ClickHouse features do all the work:</p>\n<ul>\n<li><code>remoteSecure()</code> is a secure pointer to a table on another service. It stores nothing of its own; when you read through it, ClickHouse fetches the rows from the remote region at query time.</li>\n<li>The <code>Merge</code> engine exposes several tables as one. In Europe I merge the local EU table with the two remote pointers, so a single <code>SELECT</code> can span three continents.</li>\n</ul>\n<p>A query on EU data stays inside Europe; the US and Japan services are contacted only when a query genuinely needs them.</p>\n<p><span><img alt=\"image1.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fimage1_f6618db4eb.png&w=2048&q=75\"></span></p>\n<p><em>Figure 2. The full setup. Each region ingests through its own OpenTelemetry collector into a local ClickHouse service, and Europe federates the three with remoteSecure and the Merge engine behind the ClickStack UI.</em></p></div><div><h2 id=\"putting-clickhousectl-to-work\"></h2>\n<p><code>clickhousectl</code> is <a target=\"_blank\" href=\"https://clickhouse.com/blog/introducing-clickhousectl-official-cli-for-clickhouse-local-and-cloud\">the CLI for ClickHouse local and cloud</a> that allows agents to prototype locally on your laptop, and stand up production infrastructure in ClickHouse Cloud.</p>\n<p>For one service I might have clicked through the Cloud console. For three services in three regions, each with its own connection details and SQL to run, clicking is the wrong tool. An agent with the CLI can run through the entire flow much faster. Every step the build needed, create a service, wait for it, read its connection details, run SQL, tear it all down, is one command, and every command can answer in JSON.</p>\n<div><pre><code><span><span># Install the ClickHouse Agent Skills to give agents a headstart</span></span>\n<span>clickhousectl skills</span>\n<span><span># authenticate (an API key is what an agent or a CI job uses)</span></span>\n<span>clickhousectl cloud auth login --api-key &lt;KEY&gt; --api-secret &lt;SECRET&gt;</span>\n<span></span>\n<span><span># create, inspect, and query a service, each able to answer in JSON</span></span>\n<span>clickhousectl cloud service create --org-id &lt;ORG_ID&gt; --name otel-eu \\</span>\n<span>  --provider aws --region eu-west-1 --num-replicas 1 --json</span>\n<span>clickhousectl cloud service get &lt;SERVICE_ID&gt; --json</span>\n<span>clickhousectl cloud service query --name otel-eu --query <span>\"SELECT count() FROM otel_logs\"</span></span></code></pre></div>\n<h2 id=\"building-it-step-by-step\"></h2>\n<p>These are the prompts I used, trimmed to the essentials. As before, the trick is to brief the agent like a colleague and bake the domain knowledge into the ask.</p>\n<h3 id=\"provisioning-the-three-services\"></h3>\n<blockquote>\n<p>\"Use <code>clickhousectl</code> to create three Cloud services, one each in US east, EU west, and Japan, and keep each service's ID and connection details so the later steps can reuse them.\"</p>\n</blockquote>\n<p>The agent wrote a short loop over the three regions, called <code>service create</code>, and parsed the response with <code>jq</code> to pull out exactly the fields it needed next:</p>\n<div><pre><code><span>out=$(clickhousectl cloud service create \\</span>\n<span>  --org-id <span>\"<span>$ORG_ID</span>\"</span> --name <span>\"<span>$name</span>\"</span> --provider aws --region <span>\"<span>$region</span>\"</span> \\</span>\n<span>  --num-replicas 1 --json)</span>\n<span></span>\n<span>sid=$(<span>echo</span>  <span>\"<span>$out</span>\"</span> | jq -r <span>'.service.id'</span>)</span>\n<span>host=$(<span>echo</span> <span>\"<span>$out</span>\"</span> | jq -r <span>'.service.endpoints[] | select(.protocol==\"https\") | .host'</span>)</span></code></pre></div>\n<p>It then polled <code>service get</code> until each service reported <code>running</code> before moving on, so nothing downstream started against a service that wasn't ready. The script became the documentation: re-run it and you get the same three services.</p>\n<h3 id=\"sending-opentelemetry-to-each-region\"></h3>\n<blockquote>\n<p>\"In each region, instrument the application with OpenTelemetry and point its collector at that region's ClickHouse service. The app is a set of microservices (frontend, cart, payment) that emit correlated logs, traces, and metrics, with each service tagged by its region, like <code>frontend-us</code>.\"</p>\n</blockquote>\n<p>The collector creates the OTel tables on its own. Each service emits proper client and server spans so the service map renders, logs that carry the same trace IDs, and metrics with matching labels. The regions don't behave identically either: each runs at its own error rate, enough variation that the data tells a story worth alerting on.</p>\n<h3 id=\"the-global-view\"></h3>\n<blockquote>\n<p>\"On the EU service create <code>otel_global</code>. For each OTel table, add <code>remoteSecure</code> wrappers to the US and JP services, then a <code>Merge</code> table over the local EU table plus those wrappers.\"</p>\n</blockquote>\n<p>The agent ran the whole thing through <code>clickhousectl cloud service query</code>:</p>\n<div><pre><code><span><span>CREATE TABLE</span> otel_global.otel_logs_us <span>AS</span></span>\n<span>  remoteSecure(<span>'&lt;US_HOST&gt;:9440'</span>, <span>'default'</span>, <span>'otel_logs'</span>, <span>'default'</span>, <span>'&lt;US_PASSWORD&gt;'</span>);</span>\n<span></span>\n<span><span>CREATE TABLE</span> otel_global.otel_logs_jp <span>AS</span></span>\n<span>  remoteSecure(<span>'&lt;JP_HOST&gt;:9440'</span>, <span>'default'</span>, <span>'otel_logs'</span>, <span>'default'</span>, <span>'&lt;JP_PASSWORD&gt;'</span>);</span>\n<span></span>\n<span><span>CREATE TABLE</span> otel_global.otel_logs_all</span>\n<span>  ENGINE <span>=</span> <span>Merge</span>(REGEXP(<span>'^(default|otel_global)$'</span>), <span>'^otel_logs(_us|_jp)?$'</span>);</span></code></pre></div>\n<p>Query <code>otel_logs_all</code> and ClickHouse reads the EU rows locally and pulls the other two regions over a secure connection on the spot. Data residency and a global view, in a few lines of plain SQL.</p>\n<h3 id=\"one-screen-for-three-continents\"></h3>\n<p>I pointed the ClickStack UI in Europe at the <code>otel_global.*_all</code> tables. Because those already merge the regions, the UI needs to know nothing about the topology. To the on-call engineer it looks like a single backend: one search returns logs from all three regions, the service map shows <code>frontend-us</code>, <code>cart-eu</code>, and <code>payment-jp</code> together, and a trace that begins in one region is followed end to end.</p>\n<p>Then I asked for alerts in two forms: a set of SQL rules (error rate per region, payment failures, latency, an out-of-stock spike, and a dead-man switch for a region that goes silent) with a small script to evaluate them for cron or CI, and the same rules as native <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/overview\">ClickStack</a> alerts that run every minute. Because one region is deliberately noisier than the others, the alerts fire on sight, which is exactly what you want in a demo.</p>\n<h2 id=\"why-the-cli-mattered\"></h2>\n<p>The interface your platform exposes decides how much an agent can take off your plate. A web console is built for a human doing something once. An agent cannot loop over it, read a button, or put a click in a script. The moment the task is three regions and a setup you'll want to run again next week, the console becomes the bottleneck.</p>\n<p>Three things made <code>clickhousectl</code> easy to hand over. It is safe by default: the agent gets read access from a browser login, but it needs an API key I grant before it can create or delete anything. It is one tool from my laptop to production, so the agent never changes context between local and cloud work. And it disappears into automation, because the commands it ran by hand are the same ones a pipeline can run at 3am, with nothing rewritten in between.</p>\n<p>That is what let the agent treat infrastructure as just another part of the codebase: something to script, review, and re-run without surprises.</p>\n<h2 id=\"build-from-the-terminal\"></h2>\n<p>This started as a way to show customers a distributed architecture. It ended as a reminder that the best agent experience often isn't a polished UI; it is a well-designed command-line tool that returns clean JSON and clear errors.</p>\n<p>Install <a target=\"_blank\" href=\"https://clickhouse.com/docs/interfaces/cli\"><code>clickhousectl</code></a> however best suits you:</p>\n<div><pre><code><span><span>curl</span> https://clickhouse.com/<span>cli</span> | sh</span>\n<span><span># or</span></span>\n<span>npm install <span>-g</span> clickhousectl</span>\n<span><span># or</span></span>\n<span>pip install clickhousectl</span>\n<span><span># or</span></span>\n<span>pipx install clickhousectl</span>\n<span><span># or</span></span>\n<span>uv tool install clickhousectl</span>\n<span><span># or</span></span>\n<span>cargo install clickhousectl</span></code></pre></div>\n<p>Then authenticate with an API key, and ask your agent to create a service. Watch it run the command, read the endpoint, and connect without ever opening a browser, then point it at something real and let it script the rest.</p></div>"
