href=\"https://clickhouse.com/blog/clickhouse-release-25-07#lightweight-updates\">introduced in ClickHouse 25.7</a>.</p>\n<p>They’re powered by a <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/update\">lightweight patch-part mechanism</a>, and, unlike classic mutations, which rewrite full columns, these updates write only tiny “patch parts” that slide in instantly with minimal impact on query performance.</p>\n<p>If we want to update a row, we can now write a query like this:</p>\n<div><pre><code><span><span>UPDATE</span> orders</span>\n<span><span>SET</span> discount <span>=</span> <span>0.2</span></span>\n<span><span>WHERE</span> quantity <span>&gt;=</span> <span>40</span>;</span></code></pre></div>\n<p>Behind the scenes, ClickHouse inserts a compact patch part that will patch data parts during merges, <strong>applying only the changed data</strong>.</p>\n<p><span><img alt=\"Blog-release-25.7.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_7_001_d9f45d41b0.png&w=2048&q=75\"></span></p>\n<p>Merges were already running in the background anyway, but now apply patch parts, updating the base data efficiently as parts are merged.</p>\n<p>Updates show up right away - not-yet-merged patch parts are matched and applied independently for each data range in each data stream in a surgical, targeted way, ensuring that updates are applied correctly without disrupting parallelism:</p>\n<p><span><img alt=\"Blog-release-25.7.002.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_7_002_ec850c7205.png&w=2048&q=75\"></span></p>\n<p>Similarly, you can delete data using standard SQL syntax:</p>\n<div><pre><code><span><span>DELETE</span> <span>FROM</span> orders</span>\n<span><span>WHERE</span> order_id <span>=</span> <span>1001</span></span>\n<span><span>AND</span> item_id <span>=</span> <span>'mouse'</span>;</span></code></pre></div>\n<p>ClickHouse creates a patch part that sets <code>_row_exists = 0</code> for the deleted rows. The row is then dropped during the next background merge.</p>\n<p>You can read more about this feature in the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-07#lightweight-updates\">ClickHouse 25.7 release blog post</a>. And if you want to go even deeper, see Tom Schreiber’s 3-part blog series on fast UPDATEs in ClickHouse:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-1-purpose-built-engines\">Part 1: Purpose-built engines</a><br>\nLearn how ClickHouse sidesteps slow row-level updates using insert-based engines, such as ReplacingMergeTree, CollapsingMergeTree, and CoalescingMergeTree.</li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-2-sql-style-updates\">Part 2: Declarative SQL-style UPDATEs</a><br>\nExplore how we brought standard UPDATE syntax to ClickHouse with minimal overhead using patch parts.</li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-3-benchmarks\">Part 3: Benchmarks</a><br>\nSee how fast it really is. The first experimental version appeared back in 22.9, thanks to the work of Arthur Filatenkov, Vladimir Makarov, Danila Mishin, Nikita Vasilenko, Alexander Piachonkin, Nikita Evsiukov, and Hakob Sagatelyan.</p>\n<p>A year later, in 23.8, Davit Vardanyan integrated the USearch library, bringing more robust vector similarity capabilities to the platform.</p>\n<p>The real momentum picked up this year. 25.1 introduced significant performance improvements to vector indices, courtesy of Shankar Iyer, Robert Schulze, and Michael Kolupaev. By 25.5, the feature hit beta status with the addition of prefiltering, postfiltering, and rescoring - critical features for production use cases - developed by Shankar Iyer and Robert Schulze.</p>\n<p>Finally, in 25.8, vector search reached general availability with index-only reading, fetch multiplier support, and binary quantization for even better performance and efficiency.</p>\n<p>At the time of writing, the only supported approximate search method is HNSW, a popular and state-of-the-art technique for approximate vector search based on hierarchical proximity graphs. We can define a vector index on a column like this:</p>\n<div><pre><code><span><span>CREATE TABLE</span> wikiEmbeddings (</span>\n<span>  id Int32,</span>\n<span>  title String,</span>\n<span>  text String,</span>\n<span>  url String,</span>\n<span>  wiki_id Int32,</span>\n<span>  views Float32,</span>\n<span>  paragraph_id Int32,</span>\n<span>  langs Int32,</span>\n<span>  emb <span>Array</span>(Float32),</span>\n<span>  INDEX emb_hnsw emb TYPE vector_similarity(<span>'hnsw'</span>, <span>'L2Distance'</span>, <span>768</span>)</span>\n<span>)</span>\n<span><span>ORDER</span> <span>BY</span> id;</span></code></pre></div>\n<p>We can then write a query that uses the index:</p>\n<div><pre><code><span><span>WITH</span> (<span>SELECT</span> emb <span>FROM</span> wikiEmbeddings <span>WHERE</span> id <span>=</span> <span>120356</span>) <span>AS</span> lookup</span>\n<span><span>SELECT</span> id, title, text, url, L2Distance(emb, lookup) <span>AS</span> dist</span>\n<span><span>FROM</span> wikiEmbeddings</span>\n<span><span>ORDER</span> <span>BY</span> dist</span>\n<span>LIMIT <span>3</span></span>\n<span>FORMAT Vertical;</span></code></pre></div>\n<p>Another interesting development in this area is the introduction of <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-10#qbit-data-type\">QBit</a> by Raufs Dunamalijevs, a data type for vector embeddings that enables runtime tuning of search precision.</p>\n<p>We can create a column that uses this type:</p>\n<div><pre><code><span><span>CREATE TABLE</span> vectors (</span>\n<span>    id UInt64, name String, ...</span>\n<span>    vec QBit(BFloat16, <span>1536</span>)</span>\n<span>) <span>ORDER</span> <span>BY</span> ();</span></code></pre></div>\n<p>And at query time, we specify how many (most significant) bits to take:</p>\n<div><pre><code><span><span>SELECT</span> id, name <span>FROM</span> vectors</span>\n<span><span>ORDER</span> <span>BY</span> L2DistanceTransposed(vector, target, <span>10</span>)</span>\n<span>LIMIT <span>10</span>;</span></code></pre></div>\n<h2 id=\"query-condition-cache\"></h2>\n<p>Introduced in ClickHouse 25.3, the <a target=\"_blank\" href=\"https://clickhouse.com/blog/introducing-the-clickhouse-query-condition-cache\">query condition cache</a> enables ClickHouse to remember which ranges of granules in data parts satisfy the condition in the WHERE clause and reuse this information as an ephemeral index for subsequent queries.</p>\n<p>This makes it a valuable addition for real-world workloads, such as dashboards, alerts, or interactive analytics, which often run the same filters (WHERE conditions) repeatedly against the same data or against continuously growing data, as in observability scenarios.</p>\n<p>This cache is <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#use_query_condition_cache\">enabled by default</a>, and in our experiments, it results in an order of magnitude improvement in query performance.</p>\n<p>We ran the following query on a BlueSky dataset of 100 million rows with and without the query condition cache:</p>\n<div><pre><code><span><span>SELECT</span> <span>count</span>()</span>\n<span><span>FROM</span> bluesky</span>\n<span><span>WHERE</span></span>\n<span>    data.kind <span>=</span> <span>'commit'</span></span>\n<span>    <span>AND</span> data.commit.operation <span>=</span> <span>'create'</span></span>\n<span>    <span>AND</span> data.commit.collection <span>=</span> <span>'app.bsky.feed.post'</span></span>\n<span>    <span>AND</span> data.commit.record.text <span>LIKE</span> <span>'%????%'</span></span></code></pre></div>\n<p>On the first run, the query takes 0.481 sec, but subsequent runs with the query condition cache enabled take around 0.037 sec, which is more than 10 times quicker.</p>\n<h2 id=\"join-reordering\"></h2>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-09#join-reordering\">ClickHouse 25.9</a> introduced a long-awaited feature for many ClickHouse users - automatic global join reordering.</p>\n<p>ClickHouse can now reorder complex join graphs spanning dozens of tables across the most common join types (inner, left outer, right outer, cross, semi, and anti). Automatic global join reordering uses the fact that joins between more than two tables are <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Associative_property\">associative</a>.</p>\n<p>Two new settings control the global join reordering:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#query_plan_optimize_join_order_limit\">query_plan_optimize_join_order_limit</a> - Value is the max number of tables to apply the reordering to.</li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#allow_statistics_optimize\">allow_statistics_optimize</a> - Allows using statistics to optimize join order</li>\n</ul>\n<p>We tested this functionality out on a query that joins six tables from the TPC-H join benchmark. The query was ~1,450 times faster than before and used ~25 times less memory.</p>\n<p>You can read more about join reordering in the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-09#join-reordering\">25.9 release post</a>.</p>\n<h2 id=\"lazy-reading-materialization\"></h2>\n<p>ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-04#lazy-materialization\">25.4</a> introduced <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-gets-lazier-and-faster-introducing-lazy-materialization\">lazy materialization</a>. This means that instead of reading data for a column, we track the information about what data should be read, and then read the data only when needed.</p>\n<p>The column values can be carried around, filtered, but not used in calculations before the latest stages of the query pipeline.</p>\n<p>We tried this functionality out on a query that finds the Amazon reviews with the highest number of helpful votes, returning the top 3 along with their title, headline, and full text.</p>\n<div><pre><code><span><span>SELECT</span> helpful_votes, product_title, review_headline, review_body</span>\n<span><span>FROM</span> amazon.amazon_reviews</span>\n<span><span>ORDER</span> <span>BY</span> helpful_votes <span>DESC</span></span>\n<span>LIMIT <span>3</span></span>\n<span>FORMAT <span>Null</span>;</span></code></pre></div>\n<p>Without lazy materialization, this query took 219 seconds. With lazy materialization, it took 0.14 seconds. That's a 1,576 times speedup, and it also used 40 times less I/O and 300 times less memory.</p></div>"
