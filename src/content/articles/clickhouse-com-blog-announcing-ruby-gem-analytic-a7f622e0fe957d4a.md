Much like pip for Python, Ruby developers install packages with a simple command - <code>gem install rails</code>.</p>\n<p>Behind the scenes, this triggers a request to RubyGems.org, Ruby Central's central package registry. It also captures technical details of the request and response, including TLS versions, HTTP status codes, response times, and caching behavior. This makes it ideal for exploring download trends, adoption patterns, and usage contexts across the Ruby ecosystem.</p>\n<p>As well as being the largest dataset at over 180 billion rows (as of April 2025), with data available from 2017, the download logs were also the one we aspired to maintain as up-to-date as possible. Each row includes the package name, the date, the number of downloads that occurred on that day (<code>daily_downloads</code>), and the cumulative total up to that point (<code>total_downloads</code>). This dataset is periodically updated and can be <a target=\"_blank\" href=\"https://github.com/segiddins/gem-daily-downloads\">downloaded from github</a>. While not having the granularity and breadth of metadata as the above dataset, this pre-aggregated version is useful for quick analysis, making it easy to analyze trends over time without scanning raw download logs.</p>\n<blockquote>\n<p>Experienced ClickHouse users may be wondering why we need this dataset if we have the raw data? These provide a richer view of the Ruby ecosystem beyond just download counts:</p>\n<ul>\n<li><strong>attestations</strong> – contains signed metadata for specific gem versions, including SBOMs and security attestations, stored as JSON blobs.</li>\n<li><strong>deletions</strong> – tracks removed gem versions, recording the gem name, version, platform, and the user who deleted it.</li>\n<li><strong>dependencies</strong> – captures declared gem dependencies along with their version requirements and scopes (e.g. runtime or development).</li>\n<li><strong>gem_downloads</strong> – stores the total download count for each gem version, enabling point-in-time snapshots of popularity.</li>\n<li><strong>linksets</strong> – includes links associated with each gem, such as homepage, documentation, source code, and issue tracker URLs.</li>\n<li><strong>rubygems</strong> – the master list of all gems, with basic metadata including name, creation date, and organization info.</li>\n<li><strong>versions</strong> – detailed records of every published gem version, including authors, descriptions, licenses, requirements, checksums, and whether it has been yanked.</li>\n</ul>\n<p>These datasets make it easy to analyze package metadata, dependencies, and trends over time - powering everything from dashboards to supply chain insights.</p>\n<p>The latter of these two datasets are usually updated weekly in github. We, therefore, use the S3queue engine in <code>unordered</code> mode. This requires the table engine to track all files (in Keeper) vs exploiting a natural ordering (<code>ordered mode</code>).</p>\n<p>Use of ordered mode requires a guarantee that the files are delivered in order. This mode works by maintaining a cursor of the highest lexicographical name, using this to identify new files on each iteration. Should files be delivered out of order, it can therefore potentially miss files. The current export logic of the files does not currently provide such guarantees - hence the use of <code>unordered</code> mode.</p>\n<p>While the ordered mode is more efficient for import (tracking only the last-seen file), it places additional constraints on how files are exported. Given the volume (almost 200 billion rows), the Ruby Central team wanted to ensure any export was performed in parallel. This makes ordering impractical: they receive one file per Fastly region per hour, and each arrival triggers a Lambda function that processes the file independently. These Lambda invocations happen concurrently, and there's no reliable or desirable way to serialize their delivery.</p>\n<p>Given the possible out-of-order delivery, we thus use unordered mode with S3Queue.</p>\n</li>\n<li>\n<p>We create a new S3Queue and materialized view each day, also dropping the queue and view from the 2 days ago. This ensures each queue doesn't need to track an excessive number of files (less than a 1000). Each day's queue also thus has a 48 hour gratuitous period, in case files are delivered late.</p>\n</li>\n<li>\n<p>We adjust the queue defaults, increasing the minimum and maximum polling time as well as increasing the number of tracked files to 2000.</p>\n</li>\n<li>\n<p>Note the pattern <code>**/*.json.gz</code> provides recursive processing of files.</p>\n</li>\n<li>\n<p>Our <a target=\"_blank\" href=\"https://sql.clickhouse.com/\">sql.clickhouse.com</a> environment into which we are loading this data has three nodes, each with 60 vCPUs. The setting <code>s3queue_processing_threads_num</code> assigns the number of threads for file processing per server. It loops through each subsequent day, checks if a file exists, and if so, ingests it using native ClickHouse commands. This ensures the dataset stays up-to-date with minimal logic and no need for external orchestration.</p>\n<p>Unlike the download logs, which are streamed via GCS and the S3Queue engine, this dataset is smaller, pre-aggregated, and only updated weekly - making it ideal for a simple pull-and-load pattern. By combining ClickHouse’s ability to query remote files and ingest them in place, the script keeps things lightweight while ensuring continuity in the public dataset hosted at <a target=\"_blank\" href=\"https://sql.clickhouse.com/\">sql.clickhouse.com</a>.</p>\n<p>We run this script in <a target=\"_blank\" href=\"https://cloud.google.com/run?hl=en\">Google Cloud Run</a>.</p>\n<p><strong>This dataset is around 600m rows as of April 2025.</strong></p>\n<h3 id=\"weekly-data-dumps\"></h3>\n<p>The weekly data dumps are also held in Github but are updated in their entirety i.e. all files are replaced for each update. All files belonging to a dataset can be found in a single folder e.g. the <a target=\"_blank\" href=\"https://github.com/segiddins/rubygems-org-db-dumps/tree/main/tables/rubygems\">full list of Ruby Gems and their metadata</a>.</p>\n<p>This makes the files easy to consume. This same approach can be used for both the initial and incremental load.</p>\n<p><span><img alt=\"refreshable-mv-simple.gif\" week reading the Ruby Gems package files from a <a target=\"_blank\" href=\"https://raw.githubusercontent.com/segiddins/rubygems-org-db-dumps/refs/heads/main/tables/rubygems/part_%7B0..100%7D.csv\">github folder</a> using the <a target=\"_blank\" rubygems.rubygems_mv</span>\n<span>REFRESH <span>EVERY</span> <span>1</span> WEEK APPEND <span>TO</span> rubygems.rubygems</span>\n<span>(</span>\n<span>\t`id` UInt32,</span>\n<span>\t`name` String,</span>\n<span>\t`created_at` DateTime64(<span>6</span>),</span>\n<span>\t`updated_at` DateTime64(<span>6</span>),</span>\n<span>\t`indexed` LowCardinality(String),</span>\n<span>\t`organization_id` LowCardinality(String)</span>\n<span>)</span>\n<span><span>AS</span> <span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> url(<span>'https://raw.githubusercontent.com/segiddins/rubygems-org-db-dumps/refs/heads/main/tables/rubygems/part_{0..100}.csv'</span>, <span>'CSVWithNames'</span>)</span></code></pre></div>\n<p>This view sends the data to the <code>rubygems.rubygems</code> table:</p>\n<div><pre><code><span><span>CREATE TABLE</span> rubygems.rubygems</span>\n<span>(</span>\n<span>\t`id` UInt32,</span>\n<span>\t`name` String,</span>\n<span>\t`created_at` DateTime64(<span>6</span>),</span>\n<span>\t`updated_at` DateTime64(<span>6</span>),</span>\n<span>\t`indexed` above table and run <code>INSERT INTO SELECT * FROM url('https://raw.githubusercontent.com/segiddins/rubygems-org-db-dumps/refs/heads/main/tables/rubygems/part_{0..100}.csv', 'CSVWithNames')</code>. This means all rows are <strong>appended</strong> to the target table <code>rubygems.rubygems</code> vs. the default strategy of replacement.</p>\n<p>The above policy means the Ruby Gems data will contain duplicates. To address this, we use a ReplacingMergeTree, which de-duplicates data based on unique values of the ordering key (<code>name</code> and <code>id</code> in the above case - these uniquely identify a package). This deduplication process is eventual with duplicates removed through a background merge process.</p>\n<p>To address this we can either use the <code>FINAL</code> keyword when querying these tables, which removes any outstanding duplicates at query time, or ensure we aggregate by the ordering keys. The overhead here is expected to be negligible as the volume of data is low ~ millions.</p>\n<p>Note that these tables are all relatively small (for ClickHouse), with them predominantly providing metadata. As we demonstrate below, this can be useful for joining the data with other datasets:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>\tname,</span>\n<span>\tformatReadableQuantity(total_rows) <span>AS</span> total_rows,</span>\n<span>\tformatReadableSize(total_bytes_uncompressed) <span>AS</span> total_size</span>\n<span><span>FROM</span> system.tables</span>\n<span><span>WHERE</span> (database <span>=</span> <span>'rubygems'</span>) <span>AND</span> (engine <span>LIKE</span> <span>'%ReplacingMergeTree'</span>)</span></code></pre></div>\n<h2 id=\"materialized-views\"></h2>\n<p>Similar to ClickPy we wanted to create incremental materialized views to accelerate common queries for users.</p>\n<p>In its simplest form, an incremental materialized view is simply a query that triggers when an insert is made to a table.</p>\n<p>Key to this is the idea that Materialized views don't hold any data themselves. They simply execute a query on the inserted rows and send the results to another \"target table\" for storage.</p>\n<p>Importantly, the query that runs can aggregate the rows into a smaller result set, allowing queries to run faster on the target table. This approach effectively moves work from <strong>query time to insert time</strong>.</p>\n<p>\nAs an example, we can recreate our daily aggregate downloads using the data from our raw download logs.\n</p>\n<blockquote>\n<p>The main motivation here is that the aggregate logs are actually estimates and updated weekly, whereas the results from our materialized view will be precise and updated hourly. This also represents a simple example :)&#160;</p>\n</blockquote>\n<div><pre><code><span><span>CREATE</span> MATERIALIZED <span>VIEW</span> rubygems.downloads_per_day_mv <span>TO</span> rubygems.downloads_per_day</span>\n<span><span>AS</span> <span>SELECT</span></span>\n<span>\ttoDate(<span>timestamp</span>) <span>AS</span> <span>date</span>,</span>\n<span>\tgem,</span>\n<span>\t<span>count</span>() <span>AS</span> count</span>\n<span><span>FROM</span> rubygems.downloads</span>\n<span><span>GROUP</span> <span>BY</span></span>\n<span>\t<span>date</span>,</span>\n<span>\tgem</span></code></pre></div>\n<p>This view executes the aggregation below on blocks of data as they are inserted into the <code>downloads</code> table.</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>\ttoDate(<span>timestamp</span>) <span>AS</span> <span>date</span>,</span>\n<span>\tgem,</span>\n<span>\t<span>count</span>() <span>AS</span> count</span>\n<span><span>FROM</span> rubygems.downloads</span>\n<span><span>GROUP</span> <span>BY</span></span>\n<span>\t<span>date</span>,</span>\n<span>\tgem</span></code></pre></div>\n<p>The result is sent to the \"target table\" <code>rubygems.downloads_per_day</code>. Rows with the same project value will be asynchronously merged, and the count will be summed - hence \"Summing.\" This summing behavior means it can be incrementally updated as new data arrives in the <code>downloads</code> table.</p>\n<p>To show how this is useful, suppose we wished to look at the downloads per day for the bundler gem. Using the original <code>downloads</code> table:</p>\n<div><pre><code><span><span>SELECT</span> toDate(<span>timestamp</span>) <span>as</span> <span>date</span>, <span>count</span>() <span>AS</span> count</span>\n<span><span>FROM</span> rubygems.downloads <span>WHERE</span> gem <span>=</span> <span>'bundler'</span></span>\n<span><span>GROUP</span> <span>BY</span> gem, <span>date</span> <span>ORDER</span> <span>BY</span> <span>date</span> <span>ASC</span></span></code></pre></div>\n<p>For most of you, this query probably took around 7-10s to run. Contrast with the equivalent query using the materialized view table <code>dowloads_per_day</code>:</p>\n<div><pre><code><span><span>SELECT</span> <span>date</span>, <span>sum</span>(count) <span>AS</span> count</span>\n<span><span>FROM</span> rubygems.downloads_per_day <span>WHERE</span> gem <span>=</span> <span>'bundler'</span></span>\n<span><span>GROUP</span> <span>BY</span> gem, <span>date</span> <span>ORDER</span> <span>BY</span> <span>date</span> <span>ASC</span></span></code></pre></div>\n<p>Just a little bit faster I'm sure!
