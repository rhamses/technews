We even have an internal slack channel, aptly named \"data lovers\" for sharing interesting datasets for experimentation and testing of features! While we also made many of these datasets available in a public ClickHouse instance, also referenced from our documentation, this used the classic Play interface packaged with ClickHouse.</p>\n<p><span><img alt=\"old_play.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fold_play_36776bd4f7.png&w=2048&q=75\"></span></p>\n<p>This Play interface is deliberately simple and ideal for getting started: it has no dependencies and is a single HTML file.</p>\n<p>However, this didn’t provide the rich user experience we wanted for our playground. Ideally, we wanted something where users could navigate and save example queries while supporting syntax highlighting, autocomplete, query parameters, results export, basic charting, and rich sharing features. These features would allow users to explore datasets and hopefully help users get started with ClickHouse and share their problems.</p>\n<p>Fortunately, we recently built a UI for our<a target=\"_blank\" href=\"https://crypto.clickhouse.com/\"> CryptoHouse demo</a>, where users can query over 100TB of blockchain data for free - including Solana, Ethereum, and Polymarket. This UI was also built to be reusable, benefiting from reusing some of the experiences and code from our own ClickHouse Cloud SQL console. With a few enhancements, we were able to quickly re-purpose this demo, and we also used the opportunity to re-organize and catalog our existing demo datasets. With over 35 datasets totaling 60 TB (and growing!), we’ve also loaded all of the 220 example queries from our docs and blogs to help users get started.</p>\n<p><span><img alt=\"migration.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmigration_ea13d9bcdd.png&w=2048&q=75\"></span></p>\n<p>Our documentation and blogs will increasingly reference this environment moving forward, with the recent MTA blog already benefiting from this new playground.</p>\n<blockquote>\n<p>Users who prefer to use the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/cli\">clickhouse-client</a>, or wish to integrate the service into their own applications, can connect directly to the ClickHouse instance at<a target=\"_blank\" href=\"https://sql-clickhouse.clickhouse.com/\"> sql-clickhouse.clickhouse.com</a> e.g. <code>clickhouse client --host sql-clickhouse.clickhouse.com --secure --user demo --password ''</code></p>\n</blockquote>\n<h2 id=\"building-a-ui-with-clickhouse-made-simple\"></h2>\n<p>The demo-ui remains a single-page application built using NextJS and React, where the client makes all requests. As we<a target=\"_blank\" href=\"https://clickhouse.com/blog/building-single-page-applications-with-clickhouse-and-http\"> </a>described in detail in our <a target=\"_blank\" href=\"https://clickhouse.com/blog/building-single-page-applications-with-clickhouse-and-http\">blog post about building single-page applications</a>, this is made possible by some key ClickHouse features:</p>\n<ul>\n<li><strong><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/http\">HTTP interface &amp; REST API</a></strong>- makes it trivial to query ClickHouse with SQL from Javascript. By default, ClickHouse listens on port 8123 or 8443 (if SSL), with the latter exposed in ClickHouse Cloud. This interface includes support for HTTP compression and sessions.</li>\n<li><strong><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/formats\">Output formats</a></strong> - support for over 70 output data formats, including 20 sub formats for JSON allowing easy parsing with Javascript.</li>\n<li><strong><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/http#cli-queries-with-parameters\">Query parameters</a></strong> - allowing queries to be templated and remain robust to SQL injections.</li>\n<li><strong><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/access-rights\">Role-Based Access Control</a></strong> - allowing administrators to limit access to specific tables and rows.</li>\n<li><strong><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/query-complexity\">Restrictions on query complexity</a></strong>—We restrict users to read-only and limit the query complexity and resources available. In Playground, we limit users to reading 10 billion rows per query and returning 1000 in a result set.</li>\n<li><strong><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/quotas\">Quotas</a></strong> - to limit the number of queries from any specific client (keyed off IP Address), thus preventing rogue or malicious clients from overwhelming the database. Users are limited to 60 queries per hour in Playground.</li>\n</ul>\n<p>The latter three are particularly important here as they allow us to expose the ClickHouse Cloud instance behind the demo to the public internet and safely expose the read-only credentials. For further details on the exact configuration of ClickHouse used, see <a target=\"_blank\" href=\"https://www.google.com/url?q=https://github.com/ClickHouse/sql.clickhouse.com/blob/main/setup.sql&sa=D&source=docs&ust=1730198543729593&usg=AOvVaw1O5DKnMhE6BCYGeCl_joSz\">here</a>.</p>\n<p>The UI also heavily uses our component library,<a target=\"_blank\" href=\"https://click-ui.vercel.app/?path=/docs/introduction--docs\"> click-ui</a>. This library provides a set of React components that align with our own brand and provide an opinionated set of behaviors. This library is the backbone of our Cloud UI and rapidly accelerates development, avoiding spending hours “pixel pushing” to achieve just the right appearance. This is particularly useful when you want to move fast for a demo!</p>\n<p>Finally, we’d like to mention <a target=\"_blank\" href=\"https://echarts.apache.org/en/index.html\">Apache Echarts</a>. This charting library is easy to integrate and extremely well documented, allowing us to provide charting capabilities with minimal effort.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/chart_building_55a44d32d5.gif\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fchart_building_55a44d32d5.gif&w=2048&q=75\"></span></a></p>\n<h2 id=\"running-cost-efficient-demo-playgrounds\"></h2>\n<p>While a demo playground is essential to any OSS database, we must also provide the service cost-efficiently.<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/quotas\"> Quotas</a> are a component of this, ensuring fair usage and preventing one user from consuming all the resources. The service also benefits from ClickHouse Cloud’s separation of storage and compute, with the data backed on object storage. This minimizes the data storage cost and allows us to scale infinitely as we add more demo datasets.</p>\n<p><span><img alt=\"clickhouse-cloud.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickhouse_cloud_8a0b9c8971.png&w=2048&q=75\"></span></p>\n<p>While ClickHouse Cloud does support auto-scaling, the cluster is currently fixed at 3 nodes of 30vCPUs each—predominantly because we expect a fairly constant query load if our users adopt the demo. We monitor and alert on resource consumption and will review these resources based on demand, either scaling vertically or horizontally as required.</p>\n<p>Finally, while our current datasets are static, our next efforts will focus on ensuring as many of them are kept up-to-date as possible. This is likely to exploit two key ClickHouse Cloud features:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/cloud/clickpipes\">ClickPipes</a> - a managed integration platform that makes ingesting data into ClickHouse simple. While this will require us to ensure dataset changes are periodically made available on either Kafka or object storage, it should greatly simplify data loading.</li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/reference/compute-compute-separation\">Compute-compute separation</a> - currently in preview, this provides the flexibility to create multiple compute node groups, each with its own endpoint, while sharing the same object storage. This architecture enables isolation between various types of workloads, allowing for fine-tuned resource allocation. For the playground, this means we can allocate dedicated compute for writes, isolating this workload from user queries (and thus not impacting their performance) and allowing it to be scaled independently achieving better cost efficiency.</li>\n</ul>\n<h2 id=\"a-few-technical-highlights\"></h2>\n<p>Although the demo UI is simple, there is one feature that’s worth sharing the implementation details. New users to ClickHouse often comment on how the active query feedback provided in the <code>clickhouse-client</code> is one of the highlights when first running a query.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/run_query_aa277b6260.gif\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frun_query_aa277b6260.gif&w=2048&q=75\"></span></a></p>\n<p>This feedback becomes increasingly essential as users write more complex queries - not only to estimate how long the query will take but also for its performance and resource consumption. We were keen to ensure a similar experience was available to users in the playground, as well as support for canceling if it was apparent a query was likely to exhaust complexity limits (e.g., 10 billion rows scanned) and never complete.</p>\n<p>While the HTTP interface of ClicKHouse will <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#send_progress_in_http_headers\">send response headers</a> as a query executes, these are not supported in browsers' fetch API and are tricky to read. Although alternatives exist, e.g., using the formats that return progress in the response stream, such as <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/formats#jsoneachrowwithprogress\">JSONEachRowWithProgress</a>, these are also not ideal and incur an overhead. Instead, we explicitly assign a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/http#default-database\">query ID</a> to each query and use a separate query run on a fixed interval (every 100ms), which checks the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/processes\">system.processes table</a>:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>\t<span>sum</span>(read_rows) <span>AS</span> read_rows,</span>\n<span>\t<span>sum</span>(total_rows_approx) <span>AS</span> total_rows,</span>\n<span>\t<span>sum</span>(read_bytes) <span>AS</span> read_bytes,</span>\n<span>\tread_rows <span>/</span> <span>max</span>(elapsed) <span>AS</span> rps,</span>\n<span>\tread_bytes <span>/</span> <span>max</span>(elapsed) <span>AS</span> bps,</span>\n<span>\tformatReadableQuantity(read_rows) <span>AS</span> formatted_rows,</span>\n<span>\tformatReadableQuantity(total_rows) <span>AS</span> formatted_total_rows,</span>\n<span>\tformatReadableSize(read_bytes) <span>AS</span> formatted_bytes,</span>\n<span>\tformatReadableQuantity(rps) <span>AS</span> formatted_rps,</span>\n<span>\tformatReadableSize(bps) <span>AS</span> formatted_bps</span>\n<span><span>FROM</span> clusterAllReplicas(<span>default</span>, system.processes)</span>\n<span><span>WHERE</span> (initial_user <span>=</span> <span>'demo'</span>) <span>AND</span> startsWith(query_id, {uuid:String})</span></code></pre></div>\n<p>This query runs under a <code>monitor</code> user, which has lower complexity limits concerning the number of rows it can read but a higher quota for the number of queries allowed per hour. This allows us to provide rich details on the progress of a query as it runs:</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/run_query_demo_ui_82a5db1cfd.gif\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frun_query_demo_ui_82a5db1cfd.gif&w=2048&q=75\"></span></a></p>\n<h2 id=\"contributing-queries-and-datasets\"></h2>\n<p>The playground allows users to save queries (and their configured chart) locally.
