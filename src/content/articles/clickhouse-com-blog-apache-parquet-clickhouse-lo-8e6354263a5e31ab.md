contentHtml: "<article><div><h2 id=\"introduction\"></h2>\n<p>This post is the 2nd part of our Parquet and ClickHouse blog series. In this post, we explore the Parquet format in more detail, highlighting key details to consider when reading and writing files with ClickHouse. For more experienced Parquet users, we also discuss optimizations that users can make when writing Parquet files to maximize compression, as well as some recent developments to optimize read performance using parallelization.</p>\n<p>For our examples, we continue to utilize the UK house price dataset. This contains data about prices paid for real estate property in England and Wales from 1995 to the time of writing. We distribute this in Parquet format in the public s3 bucket <code>s3://datasets-documentation/uk-house-prices/parquet/</code>. We read and write local and S3 hosted Parquet files using ClickHouse Local. ClickHouse Local is an easy-to-use version of ClickHouse that is ideal for developers who need to perform fast processing on local and remote files using SQL without having to install a full database server. Most importantly, ClickHouse Local and ClickHouse Server share the same code for Parquet reading and writing, so any details apply to both. For further details, see our <a target=\"_blank\" href=\"https://clickhouse.com/blog/apache-parquet-clickhouse-local-querying-writing\">previous post in this series</a> and other <a target=\"_blank\" href=\"https://clickhouse.com/blog/extracting-converting-querying-local-files-with-sql-clickhouse-local\">recent dedicated </a>content.</p>\n<h2 id=\"parquet-format-overview\"></h2>\n<h3 id=\"structure\"></h3>\n<p>Understanding the Parquet file format allows users to make decisions when writing files, which will directly impact the level of compression and subsequent read performance. The below description is a simplification but sufficient for most users.</p>\n<p>The Parquet format relies on three principal concepts that are hierarchically related: <strong>row groups</strong>, column <strong>chunks</strong>, and <strong>pages</strong>.</p>\n<p>At its high level, a file is separated into <strong>row groups</strong>. This contains up to N rows, determined at the time of writing. Within each row group, we have a <strong>chunk</strong> per column - with each containing the data for its respective column and thus providing the column orientation. While it is theoretically possible for the number of rows to be different per column chunk, we assume this is identical for simplification. These chunks are composed of  <strong>pages</strong>. It is within these data pages that the raw data is stored. The maximum size of each data page is potentially configurable but not currently exposed in ClickHouse, which uses the default value of 1MB. Data blocks are also compressed (see below) prior to writing.</p>\n<p>We visualize these concepts and the logical structure below. For illustration purposes, we assume a row group size of 6, with 11 rows in total, each with 3 columns. We assume our data page size results in consistently 3 values per page (except for the last chunk in each page for the second row group):</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Parquet_Structure_f3825bde92.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FParquet_Structure_f3825bde92.png&w=2048&q=75\"></span></a></p>\n<p>There are two types of pages: data pages and dictionary pages. Dictionary pages result when <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/data-pages/encodings/#dictionary-encoding-plain_dictionary--2-and-rle_dictionary--8\">dictionary encoding</a> is applied to values in a data page. For ClickHouse, this is enabled by default when Parquet files are written. For data pages that have been dictionary encoded, they will be preceded by the dictionary page. This effectively means dictionary and data pages alternate, as shown below. A limit can be imposed on the <a target=\"_blank\" href=\"https://arrow.apache.org/docs/python/generated/pyarrow.parquet.ParquetWriter.html\">dictionary page size</a>, which defaults to 1MB. If this is exceeded, the writer reverts to <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/data-pages/encodings/#a-nameplainaplain-plain--0\">writing plain data pages containing the values</a>.</p>\n<p><span><img alt=\"data page.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fdata_page_1_4f71a9f2e9.png&w=2048&q=75\"></span>\n</p>\n<p>The above is a simplification of the Parquet format. For users looking for a deeper understanding, we recommend reading about <a target=\"_blank\" href=\"https://blog.twitter.com/engineering/en_us/a/2013/dremel-made-simple-with-parquet\">repetition and definition levels</a>, as these are also essential in fully understanding how the data page works with respect to Arrays and Nested types as well as Null values.</p>\n<p>Note that while Parquet is officially described as column-based, the introduction of row groups and the sequential storage of chunks of columns means it is often described as a Hybrid-base format. This allows readers of the format to easily implement projections and pushdowns as described below.</p>\n<p>In addition to storing data values, the Parquet format includes <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/metadata/\">metadata</a>. This is written at the <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/\">end of the file</a> in the footer to facilitate single-pass writing (more efficient) and includes references back to the row groups, chunks, and pages.</p>\n<div>\n<p><span><img alt=\"parquet-metadata.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fparquet_metadata_04e1af45dc.png&w=2048&q=75\"></span></p><p>Credit: https://parquet.apache.org/docs/file-format/</p>\n</div>\n<p>As well as storing the data schema, and information to assist with decoding, e.g., offset values and encodings used, Parquet includes information that query engines can exploit to skip column chunks. A reader is first expected to read the file metadata to find all the column chunks they are interested in before only reading those required sequentially. This is known as a <strong>projection pushdown</strong> and is designed to minimize I/O.</p>\n<p>Furthermore, statistics can be included at the row group level describing each column's minimum and maximum value. This allows a reader to consider this information against any predicate (WHERE clause if querying in SQL), further skipping column chunks. This <strong>predicate pushdown</strong> is not currently implemented in ClickHouse but is planned for addition<a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/issues/48725\">[1][2][3]</a>. Finally, the official specification allows for separate metadata files referencing multiple Parquet files, e.g., one per column. ClickHouse doesn't currently support this although we plan to add support.</p>\n<h3 id=\"reading-and-writing-row-groups\"></h3>\n<p>When writing Parquet files with ClickHouse, users may wish to control the number of row groups that are written to increase the amount of parallelization in reads - see “Parallelised Reads” for more details. As of the time of writing, we recommend users use the <code>INSERT INTO FUNCTION &lt;file/s3&gt;</code> syntax should they wish to control the number of row groups when writing. The settings for this syntax allow the number of row groups to be reasoned about easily, with the number of rows equal to the minimum of:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#min-insert-block-size-bytes\">min_insert_block_size_bytes</a> - Sets the minimum number of bytes in the block, with smaller-sized blocks are squashed into bigger ones. This effectively limits the number of rows by a size in bytes. Defaults to 256MB uncompressed.</li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#min-insert-block-size-rows\">min_insert_block_size_rows</a> - The minimum number of rows in the block that is passed to the arrow client, with smaller-sized blocks squashed into bigger ones. Defaults to 1m.</li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/formats#output_format_parquet_row_group_size\">output_format_parquet_row_group_size</a>. Row group size in rows, defaults to 1m.</li>\n</ul>\n<p>Users can tune these values based on your total number of rows, their average size and the target number of row groups.</p>\n<p>For <code>SELECT</code> queries using the <code>FORMAT</code> clause e.g. <code>SELECT * FROM uk_price_paid FORMAT Parquet</code>, as well as the <a target=\"_blank\" href=\"https://clickhouse.com/docs/knowledgebase/file-export#using-into-outfile-clause\"><code>INTO OUTFILE</code></a> clause, the factors determining the group size are more complex. Most importantly, these approaches tend to result in a very large number of row groups in files - potentially negatively impacting compression and read performance. For these reasons we currently recommend using the <code>INSERT INTO FUNCTION</code> approach.</p>\n<p>The differences in these two approaches to exporting Parquet files can lead to varying file sizes depending on the approach and the resulting effective compression. For readers returning from our previous blog post, this addresses why different queries produced variable file sizes - smaller row group sizes don’t compress as well. In general, we recommend the <code>INSERT INTO FUNCTION &lt;file/s3&gt;</code> approach to writing as it utilizes more sensible defaults and allows row group sizes to be controlled easily. In future releases, we plan to address any inconsistencies in behavior.</p>\n<p>Other tools, as well as the official Apache Arrow libraries (used by ClickHouse) for writing Parquet files, allow the number of row groups to also be configured. For how the row group size potentially can impact read performance read on.</p>\n<h3 id=\"types-and-encoding\"></h3>\n<p>Parquet is a binary format where column values are stored with a specific type of <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/types/\">either boolean, numeric(int32, int64, int96, float, double), byte array(binary), or fixed length binary</a>. These primitive types can be annotated with information specifying how they should be interpreted to create “logical types” such as String and Enum. For example, the logical String type is encoded in a byte array with an annotation indicating UTF8 encoding. See <a target=\"_blank\" href=\"https://github.com/apache/parquet-format/blob/master/LogicalTypes.md\">here</a> for further details.</p>\n<p>Since its initial inception, Parquet has had numerous extensions, not at least around how data can be encoded. This includes:</p>\n<ul>\n<li>Dictionary encoding builds a dictionary of all the distinct values of a column, replacing the original value with its respective index in the dictionary. This is particularly effective on low cardinality columns and helps deliver consistent performance across column types. This can be applied to numeric and byte array-based types.</li>\n<li><a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Dictionary_coder\">Dictionary-encoded </a>values, booleans, and repetition and definition levels are <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Run-length_encoding\">Run Length Encoded </a>(RLE). This compresses columns by replacing consecutive repeating values with one occurrence and a number indicating the repetition. In this case, higher compression is achieved when more of the same values occur consecutively. The cardinality of a column thus also directly impacts compression efficiency. Note that this RLE is combined with <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/data-pages/encodings/#a-namerlearun-length-encoding--bit-packing-hybrid-rle--3\">Bit Packing</a> to minimize the number of bits required for storage.</li>\n<li><a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/data-pages/encodings/#a-namedeltaencadelta-encoding-delta_binary_packed--5\">Delta encoding</a> can be applied to integer values. In this case, the delta between values is stored instead of the real value (except the first value). This is particularly effective when consecutive values have small or constant variations, such as DateTime values with millisecond granularity, since the deltas occupy fewer bits.</li>\n<li>Other encoding techniques are also now available, including <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/data-pages/encodings/#a-namedeltaencadelta-encoding-delta_binary_packed--5\">Byte Stream Split.</a></li>\n</ul>\n<p>Currently, ClickHouse utilizes the default encodings when writing Parquet files, which enables dictionary encoding by default. The encoding used for a column cannot be controlled with settings, preventing the use of delta encoding for integers, although this is being considered as part of future improvements (see below).</p>\n<p>Parquet types must be converted to ClickHouse types during reading and vice versa during writing. A full list of supported Parquet logical types and their equivalent ClickHouse type can be found <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/formats#data-types-matching-parquet\">here</a>, with some pending<a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/issues/40580\"> implementation</a>.</p>\n<h4 id=\"strings\"></h4>\n<p>Files written by ClickHouse will also utilize the primitive <code>BYTE_ARRAY</code> type for strings. This is sufficient if you intend to later read these files with ClickHouse, as this aligns with our own internal<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/data-types/string#encodings\"> representation of strings</a> where bytes are stored as-is (with separate variations of functions that work under the assumption that the string contains a set of bytes representing a UTF-8 encoded text, e.g., <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/string-functions#lengthutf8\">lengthUTF8)</a>. However, some applications may require strings to be represented by the<a target=\"_blank\" href=\"https://github.com/apache/parquet-format/blob/master/LogicalTypes.md#string-types\"> logical type String</a>. In these cases, you can set the setting <code>output_format_parquet_string_as_string=1</code> prior to writing files.</p>\n<h4 id=\"enums\"></h4>\n<p>ClickHouse Enums will be serialized as Int8/Int16 when writing Parquet files in future versions of ClickHouse thanks to <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/48126\">recent improvements</a> (support is pending to allow them to be written as strings). Conversely, when reading files, these integer types can be converted to ClickHouse Enums. Strings in Parquet files will also be converted to ClickHouse Enums where possible. <a target=\"_blank\" href=\"https://github.com/apache/parquet-format/blob/master/LogicalTypes.md#enum\">Parquet Enums</a> can be read as either string or a compatible ClickHouse Enum.</p>\n<h3 id=\"inspecting-parquet-metadata\"></h3>\n<p>To inspect the structure of a Parquet file, users would historically need to use third-party tooling such as <a target=\"_blank\" href=\"https://github.com/ktrueda/parquet-tools\">parquet-tools</a>. Logically, this compression technique can thus be improved by simply ordering the data when writing using the <code>ORDER BY</code> query clause. This approach has its limitations if writing a large number of rows from a table since arbitrary sort orders can be memory bound: the amount of memory spent is proportional to the volume of data for sorting. The user has several options in this case:</p>\n<ul>\n<li>Utilize the setting <code>max_bytes_before_external_sort</code>. If it is set to 0 (the default), external sorting is disabled. If it is enabled, when the volume of data to sort reaches the specified number of bytes, the collected data is sorted and dumped into a temporary file. This will be considerably slower than an in-memory sort. This value should be set conservatively and less than the <code>max_memory_usage</code> setting.</li>\n<li>If the <code>ORDER BY</code> expression has a prefix that coincides with the table sorting key, you can use the <code>optimize_read_in_order</code> setting. This is enabled by default and means the ordering of the data is exploited, avoiding memory issues. Note that there are performance benefits to disabling this setting, specifically for queries with a large LIMIT and where many rows need to be read before the WHERE condition matches.</li>\n</ul>\n<p>In most cases, ordering the ClickHouse table (via the ORDER BY clause on table creation) will have been optimized for query performance and compression. For example, the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/table-functions/s3Cluster\">s3Cluster</a> function requires multiple files to distribute reads across all nodes in the cluster, with the initiator node creating a connection to all nodes in the cluster before dispatching each file that matches the glob pattern dynamically. This can also potentially also impact S3 charges. When requesting data from S3, a GET request is issued per column chunk. Again this is mitigated when requesting consecutive columns, as requests will be coalesced and should be balanced against the potential for parallelized decoding. Users will need to experiment to optimize for cost/performance.</p>\n<h2 id=\"multiple-files-and-data-lake-formats\"></h2>\n<p>While Parquet has established itself as the data file format of choice for data lakes, tables would typically be represented as a set of files located in a bucket or folder. While ClickHouse can be used to read multiple Parquet files in a directory, it is typically only sufficient for ad-hoc querying. Managing large datasets becomes cumbersome and means table abstractions by tools such as ClickHouse are loosely established at best, with no support for schema evolution or write consistency. Most importantly for ClickHouse, this approach would rely on file listing operations - potentially expensive on object stores such as s3. Filtering of data requires all data to be opened and read, other than limited abilities to restrict files by using glob patterns on a naming schema.</p>\n<p>Modern data formats such as Apache Iceberg aims to address these challenges by bringing SQL table-like functionality to files in a data lake in an open and accessible manner, including features such as:</p>\n<ul>\n<li>Schema evolution to track changes to a table over time</li>\n<li>The ability to create snapshots of data that define a specific version. These versions can be queried, allowing users to \"time travel\" between generations.</li>\n<li>Support for rolling back to prior versions of data quickly</li>\n<li>Automatic partitioning of files to assist with filtering - historically, users would need to do this error-prone task by hand and maintain it across updates.</li>\n<li>Metadata that query engines can use to provide advanced planning and filtering.</li>\n</ul>\n<p>These table capabilities are usually provided by manifest files. These manifests maintain a history of the underlying data files with a complete description of their schema, partitioning, and file information. This abstraction allows for the support of immutable snapshots, organized efficiently in a hierarchical structure that tracks all changes in a table over time.</p>\n<p>We defer an exploration of these file formats and how they can be used with ClickHouse, to a later blog post. Stay tuned.</p>\n<h2 id=\"conclusion-and-future-work\"></h2>\n<p>This blog post has explored the Parquet format in detail as well as important ClickHouse settings and considerations when reading and writing files.
