contentHtml: "<div><p>ClickHouse is <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/faq/general/why-clickhouse-is-so-fast\">designed to be fast</a> not just for queries but also for inserts. ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family\">tables</a> are intended to receive millions of row inserts per second and store substantial (100s of Petabytes) volumes of data. A very high ingest throughput traditionally requires appropriate client-side data <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/bulk-inserts\">batching</a>.</p>\n<p>In this post, we will describe the motivation and mechanics behind an alternative way of ingesting data with high throughput: ClickHouse asynchronous data inserts shift the batching of data from the client side to the server side and support use cases where client-side batching is not feasible. We will look under the hood of asynchronous inserts and use an example application simulating realistic scenarios to demonstrate, benchmark, and tune traditional synchronous and asynchronous inserts with different settings.</p>\n<h2 id=\"synchronous-data-inserts-primer\"></h2>\n<p>With traditional <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/insert-into\">inserts</a> into tables of the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family\">merge tree engine</a> family, data is <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/about-us/distinctive-features#real-time-data-updates\">speedily</a> written to the database storage in the form of a new data <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#mergetree-data-storage\">part</a> synchronously to the reception of the insert query. The following diagram illustrates this:\n<span><img alt=\"async_inserts_01.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_inserts_01_1eee7d9d75.png&w=2048&q=75\"></span>\nWhen ClickHouse ① receives an insert query, then the query’s data is ② immediately (synchronously) written in the form of (at <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-max_insert_block_size\">least</a>) one new data part (<a target=\"_blank\" href=\"https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse#poorly-chosen-partitioning-key\">per</a> partitioning key) to the database storage, and after that, ③ ClickHouse acknowledges the successful execution of the insert query</p>\n<p>In parallel (and in any order) ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/server-configuration-parameters/settings#max_thread_pool_size\">can</a> receive and execute other insert queries (see ④ and ⑤ in the diagram above).</p>\n<h2 id=\"data-needs-to-be-batched-for-optimal-performance\"></h2>\n<p>In the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/server-configuration-parameters/settings#background_pool_size\">background</a>, for incrementally optimizing the data for reads, ClickHouse is continuously <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=QDAJTKZT8y4&t=428s\">merging</a> data parts into <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/merge-tree-settings#max-bytes-to-merge-at-max-space-in-pool\">larger</a> parts. The merged parts are marked as <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/parts\">inactive</a> and finally deleted after a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/merge-tree-settings#old-parts-lifetime\">configurable</a> number of minutes. Creating and merging data parts requires cluster resources. Files <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#mergetree-data-storage\">are</a> created and handled for each part, and in wide format each table column <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#mergetree-data-storage\">is</a> stored in a separate file. In a <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=vBjCJtw_Ei0&t=2s\">replicated setup</a>, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/sre/keeper/clickhouse-keeper\">ClickHouse Keeper</a> entries <a target=\"_blank\" href=\"https://youtu.be/vBjCJtw_Ei0?t=1150\">are</a> created for each data part. Furthermore, data is <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">sorted</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/about-us/distinctive-features#data-compression\">compressed</a> when a new part is written. When parts are merged, the data needs to be decompressed and merge-sorted. Also, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family\">table engine</a> specific optimizations are <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=QDAJTKZT8y4&t=428s\">applied</a> before the merged data is compressed and written to storage again.</p>\n<p>Users should <a target=\"_blank\" href=\"https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse#many-small-inserts\">avoid</a> creating too many small inserts and too many small initial parts, respectively. As this creates (1) overhead on the creation of files, (2) increasing <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Write_amplification\">write amplification</a> (leading to higher CPU and I/O usage), and (3) overhead on ClickHouse Keeper requests. These leads to degradation of ingestion performance in case of frequent small inserts due to high CPU and I/O usage overhead. Leaving fewer resources available for other operations like queries.</p>\n<p>ClickHouse actually has a built-in <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/merge-tree-settings#parts-to-throw-insert\">safeguard</a> to protect itself from spending too many resources for creating and merging parts: It will return a <code>Too many parts</code> error to an insert query for a table <code>T</code> when there are more than 300 active parts within a single <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/custom-partitioning-key\">partition</a> of <code>T</code>. To prevent that from happening, we recommend sending fewer but larger inserts instead of many small inserts by buffering data client-side and inserting data as batches. Ideally, with at least <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/about-us/performance/#performance-when-inserting-data\">1000 rows</a>, or more. By <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-max_insert_block_size\">default</a>, a single new part can contain up to ~1 million rows. And, if a single insert query contains more than 1 million rows, ClickHouse will create more than one new part for the query’s data.</p>\n<p>Generally, ClickHouse is capable of providing a very high ingest throughput with traditional synchronous inserts. Users choose ClickHouse especially because of this capability. Uber is using ClickHouse for ingesting <a target=\"_blank\" href=\"https://www.uber.com/en-ES/blog/logging/\">millions of logs per second</a>, Cloudflare stores <a target=\"_blank\" href=\"https://blog.cloudflare.com/http-analytics-for-6m-requests-per-second-using-clickhouse/\">11 million rows per second</a> in ClickHouse, and Zomato ingests up to <a target=\"_blank\" href=\"https://www.zomato.com/blog/building-a-cost-effective-logging-platform-using-clickhouse-for-petabyte-scale\">50 TB of log data per day</a>.</p>\n<p>\nUsing ClickHouse is like driving a high-performance Formula One car 🏎. A copious amount of raw horsepower is available, and you can reach top speed. But, to achieve maximum performance, you need to shift up into a high enough gear at the right time and batch data appropriately, respectively.\n</p>\n<h2 id=\"sometimes-client-side-batching-is-not-feasible\"></h2>\n<p>There are scenarios where client-side batching is not feasible. Imagine an <a target=\"_blank\" href=\"https://clickhouse.com/blog/storing-log-data-in-clickhouse-fluent-bit-vector-open-telemetry\">observability</a> use case with 100s or 1000s of single-purpose agents sending logs, metrics, traces, etc., where real-time transport of that data is key to detect issues and anomalies as quickly as possible. Furthermore, there is the risk of event spikes in observed systems, potentially causing large memory spikes and related issues when trying to buffer observability data client-side.</p>\n<h2 id=\"example-application-and-benchmark-setup\"></h2>\n<p>To demonstrate and benchmark a scenario where client-side batching is not feasible, we <a target=\"_blank\" href=\"https://github.com/nellicus/upclick-gcp\">implemented</a> a simple example application coined <code>UpClick</code> for monitoring the global latency of <a target=\"_blank\" href=\"https://clickhouse.com/\">clickhouse.com</a> (or any other website). The following diagram sketches the architecture of UpClick:\n<span><img alt=\"async_inserts_02.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_inserts_02_cc71778dc4.png&w=2048&q=75\"></span>\nWe are using a straightforward serverless Google <a target=\"_blank\" href=\"https://cloud.google.com/functions/\">cloud function</a> that gets scheduled and executed every <code>n</code> seconds (<code>n</code> is configurable) and then does the following:\n<code>① Ping <a target=\"_blank\" href=\"https://clickhouse.com/\">clickhouse.com</a> (the URL is configurable, and the function could be easily adapted to support an array of URLs)<br><br>\n② Via <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/http\">HTTP interface</a> ingest the result from ① together with the cloud function’s geo location into a target table within a <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> service\n</code></p>\n<p>We are using a <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud service</a> with a service size of 24 GiB of main memory and 6 CPU cores for benchmarks. This service <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/reference/architecture\">consists</a> of 3 compute nodes with 8 GiB of main memory and 2 CPU cores.</p>\n<p>Additionally, we ③ implemented a real-time <a target=\"_blank\" href=\"https://grafana.com/\">Grafana</a> dashboard that updates itself each <code>n</code> seconds and displays on a geo map the average latency for the last <code>m</code> seconds for all locations in Europe, North America, and Asia, where a cloud function is deployed. The following screenshot shows the latencies in Europe:\n<span><img alt=\"async_inserts_03.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_inserts_03_6bb0ade5ca.png&w=2048&q=75\"></span>\nIn the dashboard screenshot above, we can see by the color coding that the access latency to clickhouse.com was below the (configurable) <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Performance_indicator\">KPI</a> in the Netherlands and Belgium and above in London and Helsinki.</p>\n<p>We will use the UpClick application to compare synchronous and asynchronous inserts with different settings.</p>\n<p>In order to match realistic observability scenarios, we use a load generator that can create and drive an arbitrary amount of simulated cloud function instances. With that, we created and scheduled <code>n</code> instances of the cloud function for benchmark runs. Each instance is getting executed once per <code>m</code> seconds.</p>\n<p>After each benchmark run, we used three SQL queries over the ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-debugging-issues-with-system-tables\">system tables</a> to introspect (and visualize) the changes over time of the:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/1abb84d5da6a257e2879edd81e5278a6\">number of active parts</a> in the cloud function’s target table</li>\n<li><a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/abe37a8a0883a586514a392a9ce1a6c9\">number of all parts</a> (active + inactive) in the cloud function’s target table</li>\n<li><a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/dfe8db5a241473dd450a33c1478ffff7\">CPU utilization</a> of the ClickHouse Cloud service</li>\n</ul>\n<p>Note that some of these queries must be executed on a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/distributed#distributed-clusters\">cluster with a specific name</a> by utilizing the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/table-functions/cluster\">clusterAllReplicas</a> table function.</p>\n<h2 id=\"synchronous-inserts-benchmark\"></h2>\n<p>We run a benchmark with the following parameters:\n<code>\n• 200 UpClick cloud function instances<br>\n• Once every 10 seconds schedule/execution per cloud function\n</code></p>\n<p>Effectively 200 inserts are sent to ClickHouse every 10 seconds, resulting in ClickHouse creating 200 new parts every 10 seconds. With 500 cloud function instances, ClickHouse would create 500 new parts every 10 seconds. And so on. What can possibly go wrong here?</p>\n<p>The following three charts visualize the number of active parts, the number of all parts (active and inactive) in the cloud function’s target table, and the CPU utilization of the ClickHouse cluster during the benchmark run:\n<span><img alt=\"async_inserts_04.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_inserts_04_8a3772afc9.png&w=2048&q=75\"></span>\n<span><img alt=\"async_inserts_05.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_inserts_05_3f76150e30.png&w=2048&q=75\"></span>\n<span><img alt=\"async_inserts_06.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_inserts_06_a89ffa4a99.png&w=2048&q=75\"></span></p>\n<p>\n5 minutes after the start of the benchmark, the number of active parts was reaching the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/merge-tree-settings#parts-to-throw-insert\">threshold</a> mentioned above for the <code>Too many parts</code> error, and we aborted the benchmark. With ~200 new parts created per second, ClickHouse couldn’t merge the target table’s parts fast enough to stay below the 300 active parts threshold, protecting itself from spiraling into an unmanageable situation. When the <code>Too many parts</code> error was raised, almost 30k parts existed in total (active and inactive) for the cloud function’s table. Remember that merged parts are marked inactive and deleted after a few minutes. As mentioned above, creating and merging (too many) parts is resource intensive. We are trying to drive our Formula One car 🏎 at top speed, but in a too low gear, by sending very small inserts too frequently.\n</p>\n<p>Note that client-side batching is not a feasible design pattern for our cloud function. We could have used an <a target=\"_blank\" href=\"https://clickhouse.com/blog/storing-log-data-in-clickhouse-fluent-bit-vector-open-telemetry#architectures\">aggregator or gateway architecture</a> instead to batch the data. However, that would have complicated our architecture and require additional third-party components. Luckily, ClickHouse already comes with the perfect built-in solution for our issue.\n<br><br>\nAsynchronous inserts.</p>\n<h2 id=\"asynchronous-inserts\"></h2>\n<h3 id=\"description\"></h3>\n<p>With traditional insert queries, data is inserted into a table synchronously: When the query gets received by ClickHouse, the data is immediately written to the database storage.</p>\n<p>With asynchronous inserts, data is inserted into a buffer first and then written to the database storage later or asynchronously, respectively. The following diagram illustrates this:\n<span><img alt=\"async_inserts_07.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_inserts_07_e3cc129767.png&w=2048&q=75\"></span>\nWith <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/asynchronous-inserts#enabling-asynchronous-inserts\">enabled</a> asynchronous inserts, when ClickHouse ① receives an insert query, then the query’s data is ② immediately written into an in-memory buffer first. Asynchronously to ①, only when ③ the next buffer flush takes place, the buffer’s data is <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">sorted</a> and written as a part to the database storage. Note, that the data is not searchable by queries before being flushed to the database storage; the buffer flush is <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/asynchronous-inserts\">configurable</a> and we show some examples later.</p>\n<p>Before the buffer gets flushed, the data of other asynchronous insert queries from the same or other clients can be collected in the buffer. The part created from the buffer flush will potentially contain the data from several asynchronous insert queries. Generally, these mechanics shift the batching of data from the client side to the server side (ClickHouse instance). Perfect for our UpClick use case.</p>\n<h4 id=\"there-can-be-multiple-parts\"></h4>\n<p>The table rows buffered in the asynchronous insert buffer can potentially contain several different <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/custom-partitioning-key\">partitioning key</a> values, and therefore, during buffer flush, ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse#poorly-chosen-partitioning-key\">will</a> create (at <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-max_insert_block_size\">least</a>) one new part per distinct partitioning key value contained in the buffer. Also, for tables without a partitioning key, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-max_insert_block_size\">depending</a> on the number of rows collected in the buffer, a buffer flush can result in multiple parts.</p>\n<h4 id=\"there-can-be-multiple-buffers\"></h4>\n<p>There will be one buffer per insert query <code>shape</code> (the syntax of the insert query excluding the values clause / the data) and settings. And on a multi-node cluster (like ClickHouse Cloud), the buffers will exist per node. The following diagram illustrates that:\n<span><img alt=\"async_inserts_08.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_inserts_08_59bf1253cd.png&w=2048&q=75\"></span>\nQueries ①, ②, and ③ (and ④) have the same target table T but different syntactical <code>shapes</code>. Queries ③ and ④ have the same shape but different settings. Query ⑤ has a different shape because it is targeting table T2. Therefore there will be a separate asynchronous insert buffer for all 5 queries. And when the queries are targeting a multi-node cluster via a distributed table (Self-managed cluster) or load balancer (ClickHouse Cloud), the buffers will be per node.</p>\n<p>The per settings buffer enables different flush times for data for the same table. In our UpClick example application, there could be important sites that should be monitored in near real-time (with a low <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert-busy-timeout-ms\">async_insert_busy_timeout_ms</a> setting) and less important sites whose data can be flushed with higher time granularity (with a higher async_insert_busy_timeout_ms setting) resulting in less resource usage for this data.</p>\n<h4 id=\"idempotent-inserts\"></h4>\n<p>For tables in the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family\">MergeTree engine</a> family, ClickHouse automatically <a target=\"_blank\" href=\"https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse#5-deduplication-at-insert-time\">deduplicates</a> synchronous inserts by <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#insert_deduplicate\">default</a>.</p>\n<p>For asynchronous inserts, deduplication can also be <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#async_insert_deduplicate\">enabled</a>.</p>\n<p>This makes asynchronous inserts <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Idempotence\">idempotent</a>, ensuring failure tolerance in cases like the following:</p>\n<ol>\n<li>\n<p>If the node containing the buffer crashes for some reason before the buffer got flushed, the insert query will time out (or get a more specific error) and not get an acknowledgment.</p>\n</li>\n<li>\n<p>If the data got flushed, but the acknowledgment can’t be returned to the sender of the query because of network interruptions, the sender will either get a time-out or a network error.</p>\n</li>\n</ol>\n<p>From the client's perspective 1. and 2. can be hard to distinguish. However, in both cases, the unacknowledged insert can just immediately be retried. As long as the retried insert query contains the same data in the same order, ClickHouse will automatically ignore the retried asynchronous insert if the (unacknowledged) original insert succeeded.</p>\n<h4 id=\"insert-errors-can-occur-during-buffer-flush\"></h4>\n<p>Insert errors can happen when the buffer gets flushed: Also with asynchronous inserts, the <code>Too many parts</code> error can occur. For example, with a <a target=\"_blank\" href=\"https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse#poorly-chosen-partitioning-key\">poorly chosen partitioning key</a>. Or the cluster node where the buffer flush takes place has some operational issues at the moment in time when the buffer flushes. Furthermore, the data from an asynchronous insert query is only parsed and validated against the target table's schema when the buffer gets flushed. If some row values from an insert query can’t be inserted because of parsing or type errors, then none of the data from that query is flushed (the flushing of data from other queries is unaffected by this). ClickHouse will write detailed error messages for insert errors during buffer flushes into log files and system tables. We will discuss later how clients can handle such errors.</p>\n<h3 id=\"asynchronous-inserts-vs-buffer-tables\"></h3>\n<p>With the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/buffer\">buffer table engine</a>, ClickHouse provides a data insert mechanism similar to asynchronous inserts. Buffer tables buffer the received data in the main memory and periodically flush it to a target table. There are major differences between buffer tables and asynchronous inserts, though:</p>\n<ul>\n<li>\n<p>Buffer tables need to be explicitly created (on each node in a multi-node cluster) and connected to a target table. Asynchronous inserts can be switched on and off with a simple <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert\">setting</a> change.</p>\n</li>\n<li>\n<p>Insert queries need to target the buffer table explicitly instead of the <code>real</code> target table. With asynchronous inserts, that is not the case.</p>\n</li>\n<li>\n<p>Buffer Tables require DDL changes whenever the target table's DDL changes. That is not required with asynchronous inserts.</p>\n</li>\n<li>\n<p>Data in the buffer table would be lost in a node crash, similar to asynchronous inserts in <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#fire-and-forget-return-behavior\">fire and forget</a> mode. That is not the case for asynchronous inserts in <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#default-return-behavior\">default</a> mode.</p>\n</li>\n<li>\n<p>As described <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#there-can-be-multiple-buffers\">above</a>, asynchronous inserts provide a buffer per insert query <code>shape</code> and settings even if all insert queries target the same table. Enabling granular data flush policies for different data within the same table. Buffer tables don’t have such a mechanism.</p>\n</li>\n</ul>\n<p>Generally, compared to buffer tables, from the client’s perspective, the buffering mechanism of asynchronous inserts is completely transparent and entirely managed by ClickHouse. Asynchronous inserts can be considered as a successor to buffer tables.</p>\n<h3 id=\"supported-interfaces-and-clients\"></h3>\n<p>Asynchronous inserts are supported by both the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/http\">HTTP</a> and the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/tcp\">native</a> interface, and popular clients like the Go client have either <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/integrations/go#async-insert\">direct</a> support for asynchronous inserts or support them indirectly when <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/asynchronous-inserts#enabling-asynchronous-inserts\">enabled</a> on the query setting or user setting, or connection setting level.</p>\n<h2 id=\"configuring-the-return-behavior\"></h2>\n<p>You can choose when an asynchronous insert query returns to the sender of the query and when the acknowledgment of the insert takes place, respectively. Configurable via the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#wait-for-async-insert\">wait_for_async_insert</a> setting:</p>\n<ul>\n<li>\n<p>The default return behavior is that the insert query only returns to the sender after the next buffer flush occurs and the inserted data resides on disk, respectively.</p>\n</li>\n<li>\n<p>Alternatively, by setting the setting to <code>0</code>, the insert query returns immediately after the data just got inserted into the buffer. We call this the <code>fire and forget</code> mode in the following.</p>\n</li>\n</ul>\n<p>Both modes have pretty significant pros and cons. Therefore we will discuss these two modes in more detail in the following two sections.</p>\n<h2 id=\"default-return-behavior\"></h2>\n<h3 id=\"description\"></h3>\n<p>This diagram sketches the default return behavior (<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#wait-for-async-insert\">wait_for_async_insert</a> = <code>1</code>) for asynchronous inserts:\n<span><img alt=\"async_inserts_09.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_inserts_09_b1f8388956.png&w=2048&q=75\"></span>\nWhen ClickHouse ① receives an insert query, then the query’s data is ② immediately written into an in-memory buffer first. When ③ the next buffer flush takes place, the buffer’s data is <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">sorted</a> and written as one <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#there-can-be-multiple-parts\">or more</a> data parts to the database storage. Before the buffer gets flushed, the data from other insert queries can be collected in the buffer. ④ Only after the next regular buffer flush occurred, the insert query from ① returns to the sender with an acknowledgment of the insert. Or in other words, the client-side call that is sending the insert query is <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Blocking_(computing)\">blocked</a> until the next buffer flush takes place. Therefore the sketched 3 inserts in the diagram above <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#disadvantage\">can't</a> stem from the same single-threaded insert loop but from different multi-threaded parallel insert loops or different parallel clients/programs.</p>\n<h4 id=\"advantages\"></h4>\n<p>The advantage of this mode is the durability guarantee + easy way to identify failed batches:</p>\n<ol>\n<li>\n<p><strong>Durability guarantee</strong>: When a client gets the acknowledgment for the insert, the data is guaranteed to be written to database storage (and is searchable by queries).</p>\n</li>\n<li>\n<p><strong>Insert errors are returned</strong>: When insert errors <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#insert-errors-can-occur-during-buffer-flush\">occur</a> during buffer flush, the sender of the query gets a detailed error message returned instead of an acknowledgment. Because ClickHouse waits to return an acknowledgment for an insert until the buffer got flushed.</p>\n</li>\n<li>\n<p><strong>Identifying failed data sets is easy</strong>: Because, as mentioned above, insert errors are returned in a timeliness fashion, it is easy to identify the sets of data that couldn’t be inserted.</p>\n</li>\n</ol>\n<h4 id=\"disadvantage\"></h4>\n<blockquote>\n<p>Since ClickHouse release 24.2 this disadvantage is resolved by <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-24-02#adaptive-asynchronous-inserts\">adaptive asynchronous inserts</a>.</p>\n</blockquote>\n<p>A con is that this mode can create <a target=\"_blank\" href=\"https://medium.com/@jayphelps/backpressure-explained-the-flow-of-data-through-software-2350b3e77ce7\">back pressure</a> in scenarios where a single client is used for ingesting data with a single-threaded insert loop:<br>\n<code>1. Get the next batch of data<br>2. Send insert query with the data to ClickHouse<br><strong>Now the call is <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Blocking_(computing)\">blocked</a> until the next buffer flush takes place</strong><br>3. Receive acknowledgment that the insert succeeded<br>4. Go to 1</code></p>\n<p>In such scenarios, ingest throughput can be increased by appropriately <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/bulk-inserts\">batching</a> the data client-side and using multi-threaded parallel insert loops.</p>\n<h3 id=\"benchmark\"></h3>\n<p>We run two benchmarks.</p>\n<p>Benchmark 1:<br>\n<code>\n• 200 UpClick cloud function instances<br>\n• Once every 10 seconds schedule/execution per cloud function<br>\n• 1 second buffer flush time\n</code></p>\n<p>Benchmark 2:<br>\n<code>\n• 500 UpClick cloud function instances<br>\n• Once every 10 seconds schedule/execution per cloud function<br>\n• 1 second buffer flush time\n</code></p>\n<p>We use the following <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#asynchronous-insert-settings\">asynchronous insert settings</a> for both benchmark runs:<br><br>\n<code>① <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert\">async_insert</a> = 1<br>② <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#wait-for-async-insert\">wait_for_async_insert</a> = 1<br>③ <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert-busy-timeout-ms\">async_insert_busy_timeout_ms</a> = 1000<br>④ <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert-max-data-size\">async_insert_max_data_size</a> = 1_000_000<br>⑤ <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert-max-query-number\">async_insert_max_query_number</a> = 450</code></p>\n<p>① Enables asynchronous inserts. With ② we set the default return behavior described above for asynchronous inserts. We configured that the buffer should be flushed either ③ once per second, or if  ④ 1 MB of data, or ⑤  the data from 450 insert queries are collected. Whatever happens first triggers the next buffer flush. ②, ③, ④, ⑤ are the default values in ClickHouse (③ has <code>200</code> as default value in OSS and <code>1000</code> in ClickHouse Cloud).</p>\n<p>The following three charts visualize the number of active parts, the number of all parts (active and inactive) in the cloud function’s target table, and the CPU utilization of the ClickHouse cluster during the first hour of both benchmark runs:\n<span><img alt=\"async_inserts_10.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_inserts_10_a2540f821b.png&w=2048&q=75\"></span>\n<span><img alt=\"async_inserts_11.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_inserts_11_026346847b.png&w=2048&q=75\"></span>\n<span><img alt=\"async_inserts_12.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_inserts_12_8c2f0816e9.png&w=2048&q=75\"></span>\nYou can see that the number of active parts stays stable below 8 independently of how many cloud function instances we are running. Regardless of how many cloud function instances we are running - 200 or 500, or even 1000 and more - ClickHouse will batch the data received from the cloud functions and create one new part per second. Because we set  <code>async_insert_busy_timeout_ms</code> to <code>1000</code>. We are driving our Formula One car 🏎 at top speed in a high enough gear, respectively. That minimizes I/O and CPU cycles used for the data ingestion. The CPU utilization for the benchmark run with 500 parallel clients is higher than for the benchmark run with 200 parallel clients. With 500 clients the buffer contains more data when flushed once per second. And ClickHouse needs to spend more CPU cycles sorting and compressing that data when a new part is created during the buffer flush and when the larger parts merge.\n</p>\n<p>Note that <code>async_insert_max_data_size</code> or  <code>async_insert_max_query_number</code> could trigger a buffer flush before one second has passed, especially with a high amount of cloud functions or clients, respectively. You could set these two settings to an artificially high value to ensure that only the time setting triggers buffer flushes for the sacrifice of potentially higher primary memory usage as more data needs to be buffered temporarily.</p>\n<h2 id=\"fire-and-forget-return-behavior\"></h2>\n<h3 id=\"description\"></h3>\n<p>This diagram illustrates the optional <code>fire-and-forget</code> return behavior (<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#wait-for-async-insert\">wait_for_async_insert</a> = <code>0</code>) for asynchronous inserts:\n<span><img alt=\"async_inserts_13.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_inserts_13_25908c0890.png&w=2048&q=75\"></span>\nWhen ClickHouse ① receives an insert query, the query’s data is ② immediately written into an in-memory buffer first. After that, ③ the insert query returns to the sender with an acknowledgment of the insert. ④ When the next regular buffer flush takes place, the buffer’s data is <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">sorted</a> and written as one <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#there-can-be-multiple-parts\">or more</a> data parts to the database storage. Before the buffer gets flushed, the data from other insert queries can be collected in the buffer.</p>\n<h4 id=\"advantage\"></h4>\n<p>An advantage of this mode is the very high ingest throughput (with minimal cluster resource utilization) that clients with a single-threaded insert loop can achieve:<br>\n<code>1. Get the next batch of data<br>2. Send insert query with the data to ClickHouse<br>3. <strong>Immediately receive an acknowledgment that the insert got buffered</strong><br>4. Go to 1</code></p>\n<h4 id=\"disadvantages\"></h4>\n<p>However, this mode also comes with disadvantages:</p>\n<ol>\n<li>\n<p><strong>No durability guarantee</strong>: Even when a client gets the acknowledgment for the insert query, that doesn’t necessarily mean that the query’s data is or will be written to database storage. An insert error can <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#insert-errors-can-occur-during-buffer-flush\">occur</a> later during the buffer flush. And data loss can happen when a ClickHouse node crashes or is shut down before the next regular flush of the in-memory buffers occurs. And worse, it can be silent data loss, as it is tricky for clients to find out about such events, as the original inserts into the buffers got successfully acknowledged. For a graceful shutdown of a ClickHouse node, there is a SYSTEM <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/49160\">command</a> which flushes all asynchronous insert buffers. Additionally, a server-side <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/49160\">setting</a> determines whether to flush asynchronous insert buffers on graceful shutdown automatically.</p>\n</li>\n<li>\n<p><strong>Insert errors are not returned</strong>: When insert errors <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#insert-errors-can-occur-during-buffer-flush\">occur</a> during buffer flush, the original insert into the buffer still got successfully acknowledged to the client. Clients can only discover these insert errors in hindsight by inspecting log files and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-debugging-issues-with-system-tables\">system tables</a>. In a second post, we will provide guidance for that.</p>\n</li>\n<li>\n<p><strong>Identifying failed data sets is complex</strong>: In the case of the aforementioned silent insert errors, identifying such failed data sets is tricky and complex. ClickHouse doesn’t currently log these failed data sets anywhere. A dead-letter queue for failed async inserts in <code>fire and forget</code> mode <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/issues/46791\">could</a> help to identify the data sets that couldn’t be inserted in hindsight.</p>\n</li>\n</ol>\n<p>Generally, asynchronous inserts in <code>fire-and-forget</code> mode, as the name suggests, should only be used in scenarios where data loss is acceptable.</p>\n<h3 id=\"benchmark\"></h3>\n<p>We run two benchmarks.</p>\n<p>Benchmark 1:<br>\n<code>\n• 500 UpClick cloud function instances<br>\n• Once every 10 seconds
