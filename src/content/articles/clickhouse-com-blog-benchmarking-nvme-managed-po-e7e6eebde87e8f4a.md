contentHtml: "<div><p>We launched <a target=\"_blank\" href=\"https://clickhouse.com/blog/postgresbench\">PostgresBench</a>, a fully reproducible, open-source benchmark for managed PostgreSQL services, a few months ago. It was well received, and we received valuable <a target=\"_blank\" href=\"https://clickhouse.com/blog/postgresbench-ha\">feedback</a> from the community on how to evolve it.</p>\n<p>One of the most common requests was to include locally NVMe-backed PostgreSQL services such as PlanetScale Postgres alongside ClickHouse Managed Postgres. Based on that feedback, we recently added PlanetScale Postgres (their Metal offering) to PostgresBench.</p>\n<p>This blog presents the benchmark results and analyzes why the two services performed differently, even though both ClickHouse Managed Postgres and PlanetScale Postgres are built on similar NVMe-backed infrastructure.</p>\n<p><span><img alt=\"blog-screenshot.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fblog_screenshot_fb1e854de4.png&w=2048&q=75\"></span></p>\n<h2 id=\"benchmark\"></h2>\n<p>PostgresBench uses <strong>pgbench</strong>, PostgreSQL's standard benchmarking tool, with a TPC-B-like workload consisting of short, highly concurrent transactions with frequent inserts, updates, and deletes. To ensure the benchmark is not network-bound, we use PostgreSQL databases with <strong>100 GB</strong> and <strong>500 GB</strong> of data. Below is the <code>pgbench</code> command used for the benchmark.</p>\n<p>The benchmark uses the following command:</p>\n<div><pre><code><span>pgbench -c 256 -j 16 -T 600 -M prepared -P 30 \\</span>\n<span>  -s <span>$SCALE_FACTOR</span> \\</span>\n<span>  -h <span>$PGHOST</span> -p <span>$PGPORT</span> -U <span>$PGUSER</span> -d <span>$PGDATABASE</span></span></code></pre></div>\n<h2 id=\"hardware\"></h2>\n<p>To ensure a fair comparison, both services were benchmarked using <strong>identical hardware</strong>.</p>\n<ul>\n<li><strong>AWS r8gd.xlarge</strong> and <strong>r8gd.4xlarge</strong> instances</li>\n<li>Local <strong>NVMe</strong> storage</li>\n<li>One primary with <strong>two synchronous standbys</strong> using quorum replication for high availability</li>\n<li><strong>us-west-2</strong> AWS region</li>\n</ul>\n<p>The benchmark client ran on a dedicated <strong>16 vCPU, 64 GB</strong> instance in the same region, ensuring the client was never the bottleneck.</p>\n<p><strong>In short, both services were tested on the same VM family, instance sizes, region, and benchmark configuration.</strong></p>\n<h2 id=\"results\"></h2>\n<h3 id=\"100-gb-dataset-scale-6849\"></h3>\n<div><table><thead><tr><th>System</th><th>Machine</th><th>TPS</th><th>Avg latency (ms)</th><th>P95 (ms)</th><th>P99 (ms)</th></tr></thead><tbody><tr><td>PlanetScale Metal</td><td>16vCPU, 128GB RAM</td><td>16,887.23</td><td>15.144</td><td>25.729</td><td>32.894</td></tr><tr><td>ClickHouse Managed Postgres</td><td>16vCPU, 128GB RAM</td><td>25,429.48</td><td>10.073</td><td>20.228</td><td>29.146</td></tr><tr><td>PlanetScale Metal</td><td>4vCPU, 32GB RAM</td><td>4,675.85</td><td>54.714</td><td>81.073</td><td>103.579</td></tr><tr><td>ClickHouse Managed Postgres</td><td>4vCPU, 32GB RAM</td><td>6,242.29</td><td>41.050</td><td>80.137</td><td>115.215</td></tr></tbody></table></div>\n<p>The results show that ClickHouse Managed Postgres consistently outperformed PlanetScale Metal across both instance sizes. On the <strong>16 vCPU / 128 GB</strong> configuration, ClickHouse delivered <strong>25,429 TPS</strong>, about <strong>51% higher throughput</strong> than PlanetScale's <strong>16,887 TPS</strong>, while reducing average latency from <strong>15.1 ms</strong> to <strong>10.1 ms</strong>, <strong>~33% lower</strong>.</p>\n<p>On the <strong>4 vCPU / 32 GB</strong> configuration, ClickHouse achieved <strong>6,242 TPS</strong> vs <strong>4,676 TPS</strong>, a ~34% higher throughput and reduced average latency from <strong>54.7 ms</strong> to <strong>41.1 ms</strong> (~25% lower).</p>\n<p>Tail latencies (P95/P99) were comparable on the smaller instance and consistently lower on the larger instance.</p>\n<h3 id=\"500-gb-dataset-scale-34247\"></h3>\n<div><table><thead><tr><th>System</th><th>Machine</th><th>TPS</th><th>Avg latency (ms)</th><th>P95 (ms)</th><th>P99 (ms)</th></tr></thead><tbody><tr><td>PlanetScale Metal</td><td>16vCPU, 128GB RAM</td><td>14,046.42</td><td>18.239</td><td>30.756</td><td>38.608</td></tr><tr><td>ClickHouse Managed Postgres</td><td>16vCPU, 128GB RAM</td><td>21,693.71</td><td>11.809</td><td>23.859</td><td>31.369</td></tr></tbody></table></div>\n<p>The same trend continued with the larger <strong>500 GB</strong> dataset. On the <strong>16 vCPU / 128 GB</strong> configuration, ClickHouse Managed Postgres delivered <strong>21,694 TPS</strong>, compared to <strong>14,046 TPS</strong> for PlanetScale Metal, a <strong>54% improvement in throughput</strong>. At the same time, average latency dropped from <strong>18.2 ms</strong> to <strong>11.8 ms</strong>, with P95 and P99 latencies also consistently lower.</p>\n<h2 id=\"why-is-clickhouse-managed-postgres-faster-than-planetscale-postgres\"></h2>\n<p>The difference isn't the hardware. Both services were benchmarked on identical AWS r8gd instances with local NVMe storage, configured with one primary and two synchronous standbys using quorum replication. Both also acknowledge commits after one standby confirms the write (<code>ANY 1</code>), with <code>synchronous_commit</code> enabled.</p>\n<p>The performance difference comes from how the services are engineered around PostgreSQL.</p>\n<p>ClickHouse Managed Postgres applies several system-level optimizations that reduce CPU, memory, and I/O overhead. For example, it reserves memory using 2 MB huge pages, which reduces page-table overhead under highly concurrent workloads. On identical hardware, we <a target=\"_blank\" href=\"https://clickhouse.com/blog/huge-pages-clickhouse-managed-postgres\">measured</a> this optimization alone improving throughput by about 12%.</p>\n<p>The write path is also optimized. We enable <code>wal_compression = lz4</code> and configure <code>max_wal_size</code> based on the instance size (up to 256 GB), reducing WAL volume and checkpoint frequency. This lowers the amount of data written to local NVMe and synchronously replicated to standbys.</p>\n<p>Based on the PostgreSQL settings exposed by PlanetScale Metal, we observed that <code>huge_pages</code> and <code>wal_compression</code> are disabled, and <code>max_wal_size</code> is set to 8 GB. There may be additional implementation differences that are not externally visible through <code>pg_settings</code>.</p>\n<p>Every subsystem gets the same treatment: wal-g is configured per machine, with upload concurrency and S3 part sizes computed from the vCPUs, memory, and NVMe layout it lands on; backups read the disk with direct I/O so the page cache stays with Postgres; writes are throttled when WAL archiving falls behind so the disk never fills. We have written up some of this so far: <a target=\"_blank\" href=\"https://clickhouse.com/blog/huge-pages-clickhouse-managed-postgres\">huge pages</a>, <a target=\"_blank\" href=\"https://clickhouse.com/blog/strict-memory-overcommit-for-postgres\">strict memory overcommit</a>, <a target=\"_blank\" href=\"https://clickhouse.com/blog/pgbouncer-clickhouse-managed-postgres\">the PgBouncer fleet</a>, <a target=\"_blank\" href=\"https://clickhouse.com/blog/walrus-postgres-backups-in-rust\">WAL-RUS</a>. There is more coming. Keep an eye on the <a target=\"_blank\" href=\"https://clickhouse.com/blog\">ClickHouse blog</a>.</p>\n<p>These results are based on the PostgresBench workload. While we expect the same engineering optimizations to benefit many real-world OLTP workloads, every application is different. We recommend validating performance with your own workload as part of a proof of concept.</p></div>"
