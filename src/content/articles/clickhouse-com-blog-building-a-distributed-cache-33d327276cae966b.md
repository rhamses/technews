In this setup, ClickHouse relies on the operating system’s <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Page_cache\">page cache</a>, which transparently and automatically caches the column file segments loaded from disk during query processing.</p>\n<p>The following animation illustrates how this works (click to view in fullscreen):</p>\n<p><span><img alt=\"animation-01.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fanimation_01_f638eedb98.gif&w=2048&q=75\"></span></p>\n<p><strong>① Query arrives:</strong><br>\nA query reaches the ClickHouse server. The server <a target=\"_blank\" href=\"https://clickhouse.com/docs/primary-indexes\">analyzes index files</a> to determine which compressed column blocks are needed to satisfy the query.</p>\n<p><strong>② Data loading:</strong><br>\nIf the <em>needed</em> blocks aren’t already cached, they are read from local SSD (e.g., NVMe Gen3) and automatically placed into the OS page cache.</p>\n<p><strong>③ In-memory processing:</strong><br>\nCompressed blocks are streamed from the OS page cache into the query engine at 50–100 GB/s, limited by memory bandwidth rather than disk. ClickHouse processes the data entirely in memory, block by block, in a streaming fashion. It uses multiple independent <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/query-parallelism\">parallel lanes</a> to decompress, filter, aggregate, and sort the data.</p>\n<p>The number of these lanes is controlled by the <code>max_threads</code> setting, which by default matches the number of available CPU cores.</p>\n<blockquote>\n<p>This same setting also determines how many concurrent streams are used to read data from disk when it’s not already cached, enabling parallel loading and maximizing throughput, as shown in the animation.</p>\n</blockquote>\n<p><strong>④ Result generation:</strong><br>\nThe processed data is <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#-multi-core-parallelization\">merged</a> and limited as needed, and the final query result is returned to the client.</p>\n<h3 id=\"in-memory-caching-strategies\"></h3>\n<p>ClickHouse relies on the OS page cache, which works transparently for both reads and writes. This enables <strong>read-through caching</strong>, keeping data in memory after it’s read, and <strong>write-through caching</strong>, where newly written data is cached immediately, making it queryable without hitting disk. As long as the data fits in RAM, it stays cached; otherwise, the OS evicts the least recently used pages to make room for new ones.</p>\n<p>To further reduce latency, ClickHouse also offers an optional <strong><a target=\"_blank\" href=\"https://www.youtube.com/watch?v=-N6N-WKEiLs&t=202s\">uncompressed blocks cache</a></strong>. This keeps uncompressed versions of frequently accessed blocks in memory, eliminating decompression overhead for hot data. While decompression is fast, skipping it entirely can reduce latency and increase throughput in case of frequent short queries.</p>\n<p>This cache is <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#use_uncompressed_cache\">off</a> by default, as uncompressed blocks use significantly more memory than compressed ones, especially given ClickHouse’s typically high compression ratios.</p>\n<blockquote>\n<p>Interestingly, as Alexey Milovidov shows in <a target=\"_blank\" href=\"https://presentations.clickhouse.com/2021-meetup53/optimizations/\">this presentation</a>, <strong>in-memory processing of compressed data can often be faster than in-memory processing of uncompressed data</strong>.</p>\n</blockquote>\n<p>These optimizations work well when data lives on local disks in traditional shared-nothing deployments. But what happens when the storage isn’t local anymore?</p>\n<h2 id=\"stage-2-local-cache-on-cloud-compute-nodes\"></h2>\n<p>In ClickHouse Cloud, caching works differently than in traditional shared-nothing clusters. Compute and storage are <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates#clickhouse-cloud-enters-the-stage\">decoupled</a>, and all compute nodes read from the same shared object storage. Instead of managing separate shards, they act as replicas reading from a single, virtually limitless shard.</p>\n<p>But shared storage brings new challenges, especially when it comes to performance.</p>\n<h3 id=\"the-real-bottleneck-of-object-storage-latency\"></h3>\n<p>While object storage can offer decent throughput, its high access latency is often the real performance bottleneck. To mitigate this, ClickHouse Cloud uses compute nodes with directly attached SSDs that act as a local <a target=\"_blank\" href=\"https://youtu.be/-N6N-WKEiLs?si=YPu4rElfPOkC86Vd&t=354\">filesystem cache</a>, providing a middle ground between slow-but-durable object storage and fast-but-volatile memory.</p>\n<p>Here’s how these layers compare:</p>\n<div><table><thead><tr><th>Layer</th><th>Latency (99.99%)</th><th>IOPS</th><th>Throughput</th></tr></thead><tbody><tr><td>S3</td><td>500 ms</td><td>5K</td><td>2 GB/sec</td></tr><tr><td>SSD</td><td>1 ms</td><td>100K</td><td>4 GB/sec</td></tr><tr><td>Memory</td><td>250 ns</td><td>100M</td><td>100 GB/sec</td></tr></tbody></table></div>\n<blockquote>\n<p>Completely separate from the distributed cache work described in this post, we are also experimenting with integrating the <strong>Amazon S3 Express One Zone</strong> storage class, the fastest cloud object storage class on AWS, offering <strong>single-digit millisecond latency</strong>, into both our <strong>primary storage</strong> and <strong>caching layers</strong> to explore potential performance and cost improvements. <a target=\"_blank\" href=\"https://aws.amazon.com/blogs/storage/clickhouse-cloud-amazon-s3-express-one-zone-making-a-blazing-fast-analytical-database-even-faster/\">Read more →</a></p>\n</blockquote>\n<p>As the table shows, memory is millions of times faster than S3 in tail latency (99.99th percentile) and orders of magnitude faster in throughput. SSDs sit in the middle, much faster than S3 but still far behind memory.</p>\n<p>And while the <strong>throughput gap</strong> between S3 and SSD (on typical EC2 machines, like m7gd.16xlarge) may look small—2 GB/s vs. 4 GB/s in typical ClickHouse Cloud setups—that already reflects heavy optimization.</p>\n<blockquote>\n<p>Raw S3 throughput is typically just a few hundred MB/s per thread. ClickHouse uses <strong>multi-threaded reads</strong> and <strong>asynchronous prefetching</strong> to achieve multi-GB/s performance. For more details, see <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=gA5U6RZOH_o&list=PL0Z2YDlm0b3iNDUzpY1S3L_iV4nARda_U&index=17\">Kseniia’s deep-dive talk</a>, she’s the core developer behind the filesystem cache described in this section.</p>\n</blockquote>\n<p>But even so, the <strong>latency gap is massive</strong>: hundreds of milliseconds vs. microseconds or nanoseconds. Unlike throughput, latency is much harder to hide or parallelize. No amount of multi-threaded reading helps when each read still takes hundreds of milliseconds. Object storage is just slow to access. Full stop.</p>\n<p>That’s why latency becomes the dominant bottleneck in many real-world analytical queries. You simply can’t fan out enough I/O to hide the delay.</p>\n<ul>\n<li><strong>Short-running queries</strong> often touch just a few compressed blocks.</li>\n<li><strong>Scattered access patterns</strong> involve many small, disjoint reads.</li>\n</ul>\n<p>In both cases, bandwidth doesn’t help, <strong>latency is the limit</strong>.</p>\n<p>That’s why <strong>caching hot data close to the query engine</strong> is so critical, not just for bandwidth, but for speed that feels instant. The filesystem cache does exactly that, shielding queries from the high latency of object storage.</p>\n<h3 id=\"filesystem-cache-beyond-hot-data\"></h3>\n<p>In addition to caching hot table data, the disk-based filesystem cache in ClickHouse Cloud also:</p>\n<ul>\n<li>\n<p><strong>Caches table metadata</strong>, such as secondary<a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/skipping-indexes\"> data skipping indexes</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes#mark-files-are-used-for-locating-granules\">mark files</a>.</p>\n</li>\n<li>\n<p><strong>Stores intermediate query data</strong> for aggregation, sorting, and joins (i.e., spill-to-disk).</p>\n</li>\n<li>\n<p><strong>Caches external files</strong> from remote sources (e.g., when <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-and-parquet-a-foundation-for-fast-lakehouse-analytics\">querying Parquet files</a>).</p>\n</li>\n</ul>\n<h3 id=\"how-the-filesystem-cache-works\"></h3>\n<p>The filesystem cache handles both reads and writes:</p>\n<ul>\n<li>\n<p><strong>Write-through caching:</strong> When new data is written, it’s stored in both the filesystem cache and object storage. This includes not just inserts, but also merged parts produced during <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges\">background merges</a>. While this ensures durability, it doesn’t mask object storage’s write latency. Fortunately, the OS page cache automatically holds recently written files in memory, creating a fast two-level cache: SSD + RAM.</p>\n</li>\n<li>\n<p><strong>Read-through caching:</strong> When data is streamed from object storage (e.g., S3), it’s saved to the local filesystem cache. This avoids repeat downloads and gives future queries local-disk-speed access to remote data.</p>\n</li>\n</ul>\n<p>If the cache disk fills up, the filesystem cache evicts the least recently used data to make room. And because column files in ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">table parts</a> are immutable, there’s generally no need for explicit cache invalidation.</p>\n<p>The animation below shows how read-through caching works in practice (click to view in fullscreen):</p>\n<p><span><img alt=\"animation-02.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fanimation_02_156e1149a3.gif&w=2048&q=75\"></span></p>\n<p>The high-level flow of hot table data in ClickHouse Cloud resembles that of traditional shared-nothing servers, but with important differences:</p>\n<p><strong>① Query arrives</strong><br>\nA query is routed to a compute node in ClickHouse Cloud. Unlike traditional servers, this node accesses shared data stored in object storage (e.g., S3) rather than local disk.</p>\n<p><strong>② Data loading from object storage</strong><br>\nIf the required data is not already cached, it is streamed from shared object storage, using multi-threaded reads and asynchronous prefetching, as shown in the animation above, and written to the disk-based filesystem cache.</p>\n<p><strong>③ Memory caching</strong><br>\nAs blocks are loaded from the filesystem cache, the OS page cache automatically accelerates future access, just like on traditional local-disk setups.</p>\n<p><strong>④ ⑤ In-memory execution</strong><br>\nThe query engine processes data in parallel, block by block, streaming from the OS page cache into execution lanes at ~50–100 GB/s, limited by memory bandwidth.</p>\n<h3 id=\"why-we-needed-something-better\"></h3>\n<p>The animation below illustrates a fundamental limitation of traditional hot data caching in ClickHouse Cloud (click to view in fullscreen):</p>\n<p><span><img alt=\"animation-03.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fanimation_03_bb8f9f8001.gif&w=2048&q=75\"></span></p>\n<p>Here’s what the animation shows:</p>\n<p><strong>Query routing</strong> (①–②)<br>\nA query arrives at the ClickHouse Cloud load balancer and is routed to a compute node (e.g., node 2, both node 1 and node 2 start with a cold cache for this query).</p>\n<p><strong>Local caching</strong> (③)<br>\nNode 2 processes the query, fetches the required hot table data from object storage, and stores it in its local filesystem cache and OS page cache.</p>\n<h3 id=\"cache-isolation\"></h3>\n<p>If a ④ later query is ⑤ routed to node 1, it has no access to the data cached by node 2. It must re-fetch the same data from object storage and warm up its own cache from scratch.</p>\n<p>Local, per-node filesystem caches work well for single-node stability. But in a world of elastic, stateless compute, they fall short:</p>\n<ul>\n<li><strong>Hot data isn’t portable</strong>: Each node has its own isolated cache.</li>\n<li><strong>Caching effort isn’t shared</strong>: Work done on one node can’t help others.</li>\n<li><strong>Scaling means starting over</strong>: Adding or replacing nodes discards all hot data.</li>\n</ul>\n<p>In practice, that means:</p>\n<ul>\n<li>You scale up to a larger node, but it starts cold with no cached data.</li>\n<li>You add a node to scale out, but it has to re-fetch everything from object storage.</li>\n<li>Queries that were fast seconds ago stall while waiting for data to stream in again.</li>\n<li>Hot data becomes cold the moment your compute topology changes.</li>\n</ul>\n<p>In short, local caching improves repeat performance, but only for the node that did the work. To make caching effective in a cloud-native world, we needed something shared.</p>\n<h2 id=\"stage-3-the-distributed-cache\"></h2>\n<p>Isolated caches, repeated work, and cold starts blocked cloud-native elasticity. So we built the distributed cache: a shared network service that wraps the filesystem cache and makes hot data fast accessible across all ClickHouse compute nodes. Instead of rebuilding caches locally, nodes now send read and write requests to a single, shared cache.</p>\n<p>Let’s look under the hood and see what makes the distributed cache fast, scalable, and cloud-ready.</p>\n<h3 id=\"a-new-layer-in-the-stack-the-network\"></h3>\n<p>ClickHouse Cloud turns the local filesystem cache into a shared network service, something that’s feasible thanks to the high bandwidth and low latency of modern networks.</p>\n<p>In AWS, intra-zone network latency can be as low as 100–250 µs, hundreds of times faster than S3’s ~500 ms tail latency. Network throughput typically ranges from 1.5 to 12.5 GB/s, often matching or exceeding local SSD performance. High-throughput instances can reach up to 100 Gbps (12.5 GB/s), and specialized configurations can go even further.</p>\n<p>Here’s how the network layer compares to other storage tiers on latency and throughput:</p>\n<div><table><thead><tr><th>Layer</th><th>Latency</th><th>IOPS</th><th>Throughput</th></tr></thead><tbody><tr><td>S3</td><td>500 ms</td><td>5K</td><td>2 GB/sec</td></tr><tr><td>SSD</td><td>1 ms</td><td>100K</td><td>4 GB/sec</td></tr><tr><td>Network</td><td>100–250 µs</td><td></td><td>1.5–12.5 GB/sec</td></tr><tr><td>Memory</td><td>250 ns</td><td>100M</td><td>100 GB/sec</td></tr></tbody></table></div>\n<p>Thanks to these characteristics, the distributed cache, accessed over the network, delivers latencies that fall neatly between SSD and memory. And like the local filesystem cache before it, it <strong>solves the core bottleneck</strong> of object storage: latency.</p>\n<p><strong>It also scales.</strong> Because hot table data is now <strong>distributed across multiple cache nodes</strong>, ClickHouse can fetch blocks in <strong>parallel</strong>, maximizing throughput. With enough nodes, this <strong>compound throughput</strong> can rival memory speeds, <strong>tens or even hundreds of GB/sec</strong> (more on how this works in a bit).</p>\n<p>Like its predecessor, the distributed cache brings hot data closer to the query engine, first to SSDs, then straight into compute node RAM, powering the low-latency execution real-time analytics demand.</p>\n<h3 id=\"built-for-stateless-compute\"></h3>\n<p>This architecture allows ClickHouse compute nodes to be diskless, stateless machines, while the distributed cache nodes are disk-optimized and purpose-built to manage and serve hot data at high throughput with low latency.</p>\n<h3 id=\"per-zone-deployment\"></h3>\n<p>The distributed cache runs per availability zone to avoid cross-zone traffic and its costs. It can operate as zone-local (lower latency) or cross-zone (higher hit rate, but more latency and cost). The cache is shared across multiple ClickHouse Cloud services, but each is fully isolated with proper authentication and encryption.</p>\n<h3 id=\"beyond-table-data\"></h3>\n<p>The distributed filesystem cache also serves the same additional roles as the local cache did before: caching table metadata (like secondary data skipping indexes and mark files), storing temporary data (e.g., spill-to-disk), and caching external files (including data lake table files).</p>\n<h3 id=\"how-it-works\"></h3>\n<p>Just like the local per-node filesystem cache before it, the distributed cache uses both <strong>read-through caching</strong> (to populate itself during queries) and <strong>write-through caching</strong> (to keep new data hot and query-ready after inserts, and table part merges).</p>\n<p>The next animation illustrates read-through caching for the distributed cache in ClickHouse Cloud (click to view in fullscreen):</p>\n<p><span><img alt=\"animation-04.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fanimation_04_3e2f8be0e5.gif&w=2048&q=75\"></span></p>\n<p><strong>① Query arrives:</strong><br>\nA query reaches the ClickHouse Cloud service. A load balancer selects which compute node will process it.</p>\n<p><strong>② Node selection:</strong><br>\nThe query is routed to a compute node (e.g., node 2). Both node 1 and node 2 have a cold cache for this query initially.</p>\n<p><strong>③ Cache lookup and load:</strong><br>\nIf the needed data isn’t in the compute node’s memory (see “Userspace page cache” below), it’s fetched from the distributed cache. This service runs across multiple dedicated cache nodes in the same availability zone. Each node owns a portion of the hot table data (via <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Consistent_hashing\">consistent hashing</a>), fetches missing blocks from object storage, stores them on local SSD, and transparently, in memory via the OS page cache.</p>\n<p><strong>④ Parallel data fetch:</strong><br>\nThe compute node pulls needed blocks from multiple cache nodes in parallel. As discussed earlier, warm cache data can be fetched with access latencies between SSD and memory, and aggregate throughput can exceed local SSDs, reaching 50–100 GB/s or more.</p>\n<h3 id=\"instant-cache-reuse-by-other-nodes\"></h3>\n<p>Once warm, the real power of the distributed cache is that any compute node can instantly reuse cached data. If ⑤ the next query is ⑥ routed to another node (e.g., node 1), it can fetch the hot data from the low-latency distributed cache, no high-latency object storage access required.</p>\n<h3 id=\"ram-caching-with-the-userspace-page-cache\"></h3>\n<p>RAM is still the fastest layer, so caching hot data in memory is essential for query speed. Since ClickHouse Cloud compute nodes no longer use local disks for caching, and thus can’t rely on the OS page cache, we introduced the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/userspace-page-cache\">userspace page cache</a>: an in-memory layer for caching data read from or written to the distributed cache or remote files.</p>\n<p>This completes the picture: a fully decoupled caching architecture that delivers low latency, scales with parallelism, and supports stateless compute.</p>\n<p>Now let’s see how the full
