Bluesky is a social network like X, but unlike them, it's fully open-source and decentralized!</p>\n<p>Bluesky, built on the<a target=\"_blank\" href=\"https://docs.bsky.app/docs/advanced-guides/atproto\"> AT Protocol (ATProto)</a>, is a decentralized social media platform that allows users to host their content independently. By default, data resides on the Bluesky Personal Data Server (PDS), but users can choose to host these servers (and their content) themselves. This approach reflects a shift back to the principles of the early web, where individuals had control over their content and connections instead of relying on centralized platforms that dominate and own user data.</p>\n<p>Each user's data is managed in a lightweight, open-source framework, with a<a target=\"_blank\" href=\"https://github.com/bluesky-social/atproto/pull/1705\"> single SQLite database handling storage</a>. This setup enables interoperability and ensures that content ownership remains with the individual, even if a central platform goes offline or changes its policies. We recommend this article for users interested in the underlying architecture and its evolution.</p>\n<p>Most importantly for us, like Twitter of old, Bluesky offers a free way to retrieve events e.g. posts, in real-time, unlocking potentially a huge dataset for analytics as the network grows in popularity.</p>\n<h2 id=\"reading-bluesky-data\"></h2>\n<p>To ingest Bluesky data, we use the recently released<a target=\"_blank\" href=\"https://docs.bsky.app/blog/jetstream\"> Jetstream API</a>, which simplifies the consumption of Bluesky events by providing JSON-encoded streams. Unlike the original firehose, which requires handling binary CBOR data and CAR files, Jetstream reduces complexity, making it accessible for developers working on real-time applications. This API aligns perfectly with our use case, allowing us to filter and process thousands of events per second from Bluesky posts while addressing common challenges like malformed data and high duplication rates.</p>\n<p>For our implementation, we connect to a public Jetstream instance, consuming a continuous stream of JSON-encoded events for ingestion. For this, we use a simple bash that processes the live stream of JSON events from Jetstream. The full script can be found<a target=\"_blank\" href=\"https://github.com/ClickHouse/sql.clickhouse.com/blob/main/load_scripts/bluesky/ingest.sh\"> here</a>. In summary, this:</p>\n<ol>\n<li>Checks a GCS bucket for the most recent .csv.gz file, extracts its timestamp (used as the cursor), and uses it to resume the Jetstream subscription from the correct position. This ensures data continuity and minimizes duplication.</li>\n<li>The<a target=\"_blank\" href=\"https://github.com/vi/websocat\"> <code>websocat</code></a> tool is used to connect to the Jetstream API, subscribe to events, and pipe the JSON stream for processing. The <code>wantedCollections</code> parameter filters for relevant events, and the <code>cursor</code> ensures incremental data retrieval i.e. <code>websocat -Un --max-messages-rev $MAX_MESSAGES \"$WS_URL/subscribe?wantedCollections=app.*&amp;cursor=$cursor\" &gt; \"$OUTPUT_FILE\"</code></li>\n<li>Incoming JSON data is split into chunks of 500k lines, with each chunk representing a file with the last timestamp used as the file identifier. We use<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/utilities/clickhouse-local\"> <code>clickhouse-local</code></a> to convert the file to CSV and compress this to <code>gz</code> file, before uploading the file to a GCS bucket using<a target=\"_blank\" href=\"https://cloud.google.com/storage/docs/gsutil\"> <code>gsutil</code></a>.</li>\n</ol>\n<p>This script runs within a<a target=\"_blank\" href=\"https://github.com/ClickHouse/sql.clickhouse.com/blob/main/load_scripts/bluesky/Dockerfile\"> ClickHouse Docker container</a>, executing every 3 minutes using a Google Cloud Run Job.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Medallion_with_Bluesky_02_ce19c982eb.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FMedallion_with_Bluesky_02_ce19c982eb.png&w=2048&q=75\"></span></a></p>\n<p>Note that the files are naturally ordered with their names using the timestamp of their last event. This is essential for the later efficient incremental reading of the GCS bucket. This script also doesn’t guarantee that all Bluesky events will be captured.</p>\n<h2 id=\"sampling-the-data\"></h2>\n<p>At the time of writing this post, we have almost 1.5 billion row events captured after collecting data for around 21 days. The <code>kind</code> column largely dictates the subsequent structure with the API delivering <code>commit,</code> <code>identity</code>, and <code>account</code> event types. Full details of these event types can be found<a target=\"_blank\" href=\"https://skyware.js.org/docs/jetstream/enums/EventType/\"> here</a>, but in summary, these represent:</p>\n<ul>\n<li><code>commit</code>: A commit event indicates either a create, update, or delete of a record. This should represent most events and include posts, likes, and follows.</li>\n<li><code>identity</code>: An account's identity was updated.</li>\n<li><code>account</code>: An account's status was updated.</li>\n</ul>\n<p>We'll explore this data further once it is loaded into the Bronze layer.</p>\n<h2 id=\"challenges-with-bluesky-data\"></h2>\n<p>The Bluesky data, as it's delivered by JetStream API has a number of challenges, including:</p>\n<ul>\n<li><strong>Malformed JSON</strong> - We occasionally see<a target=\"_blank\" href=\"https://pastila.nl/?0008448f/c8bda6e9869af1babb8389390861fb18#epNRk1llYbYND/FcRwY60A==\"> malformed JSON events</a>. While these are rare these can disrupt the processing of a file. We exclude these using the function <code>isValidJSON</code>, limiting ingestion into the Bronze layer to those rows which return 1.</li>\n<li><strong>Inconsistent structure</strong> - While the crawl timestamp is consistent for each event (the <code>time_us</code> field), the JSON path containing the time for when the event occurred depends on the event type. Our workflow needs to extract a consistent timestamp column based on these conditions. A simple analysis suggests that:\n<ul>\n<li><code>commit.record.createdAt</code> can be used for commit events</li>\n<li><code>identity.time</code> for identity events</li>\n<li><code>account.time</code> for account events</li>\n</ul>\n</li>\n<li><strong>Future or invalid timestamps</strong> - Some events have future timestamps. For example, <a target=\"_blank\" href=\"https://pastila.nl/?00213dff/a624b1222524486f6bc735071fdecad1#4rDoLclW6QnZLKtacqzhFA==\">42k commit events</a> had future times when sampling the events at the time of writing. A<a target=\"_blank\" href=\"https://pastila.nl/?0b5cf55d/7c388c221ef9e4b857666b3c8cd71f42#tyBLhpsHhwfgrBfKUxwu9A==\"> further 4 million commit events</a> had timestamps before<a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Bluesky\"> even the launch of Bluesky as a service</a>.</li>\n<li><strong>Repeated structures</strong> - There are cases where the JSON contains what appear to be<a target=\"_blank\" href=\"https://pastila.nl/?001a2a93/571ae3faf9e5ca3d6036e98d78358eca#hcM3zAI7qhJoEh/UbZl/Jw==\"> deeply recursive structures</a>. This produces over<a target=\"_blank\" href=\"https://pastila.nl/?00002557/56def99bbb09c1ada04fb11c03378608#vaw2ZWnNDGAlxg+eyH4M3g==\"> 1800 unique JSON paths</a>, most of which likely add little value to the content.</li>\n<li><strong>Duplicates</strong> - Despite our efforts to maintain a cursor, the Jetstream API<a target=\"_blank\" href=\"https://pastila.nl/?02904849/d7507aa69a1691971f6e446fdeede386#Sf9qbeSt5Y1+UUW7ROIYsw==\"> produces duplicates</a> (where the content is identical except the crawl timestamp). Surprisingly, these can occur over a wide time range - in some cases up to<a target=\"_blank\" href=\"https://pastila.nl/?002f3b9c/e66fb13bc906cdcd493d349089714468#HBoYIdgvgBenSMP/BlpxLQ==\"> 24 hours apart</a>. An important observation when exploring the data was that most duplicates occur<a target=\"_blank\" href=\"https://pastila.nl/?00d6750c/dfb434e2a1a7967544ff7da4e538647d#adr+P0WnnfTnxv+rz3PdNw==\"> within a 20 minute time window</a>.</li>\n</ul>\n<p>The above does not represent an exhaustive list of data quality issues - we continue to discover challenges with the data! However, for example, purposes and in the interest of brevity, we focus on the above for our example Medallion workflow.</p>\n<h2 id=\"the-json-data-type\"></h2>\n<p>JSON plays a key role in implementing the Medallion architecture for Bluesky data, enabling the system to store highly dynamic and semi-structured nature in the bronze layer. The new JSON data type in ClickHouse, introduced in version 24.8, addressed key challenges faced by <a target=\"_blank\" href=\"https://clickhouse.com/blog/a-new-powerful-json-data-type-for-clickhouse#challenge-1-true-column-oriented-storage\">earlier implementations</a>.</p>\n<p>Unlike traditional approaches that infer a single type for each JSON path, often leading to type enforcement or coercion, ClickHouse’s JSON type stores values for each unique path and type in separate sub-columns. This ensures efficient storage, minimizes unnecessary I/O, and avoids the pitfalls of query-time type casting.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Medallion_with_Bluesky_03_fed469d780.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FMedallion_with_Bluesky_03_fed469d780.png&w=2048&q=75\"></span></a></p>\n<p>For example, when two JSON paths are inserted with differing types, ClickHouse stores the values of each<a target=\"_blank\" href=\"https://clickhouse.com/blog/a-new-powerful-json-data-type-for-clickhouse#storage-extension-for-dynamically-changing-data\"> concrete type in distinct sub-columns</a>. These sub-columns can be accessed independently, minimizing unnecessary I/O. Note that when querying a column with multiple types, its values are still returned as a single columnar response.</p>\n<p>Additionally, by<a target=\"_blank\" href=\"https://clickhouse.com/blog/a-new-powerful-json-data-type-for-clickhouse#dense-data-storage\"> leveraging offsets</a>, ClickHouse ensures that these sub-columns remain dense, with no default values stored for absent JSON paths. This approach maximizes compression and further reduces I/O.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Medallion_with_Bluesky_04_7e8743e550.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FMedallion_with_Bluesky_04_7e8743e550.png&w=2048&q=75\"></span></a></p>\n<p>Furthermore, the type does not suffer from sub-column explosion issues resulting from a higher number of unique JSON paths. This is particularly important in the Bluesky data, which has over 1800 unique paths if no filtering is applied. Note that this doesn’t prevent storage of these paths; rather, it simply stores new paths in a single shared data column if limits are exceeded (with statistics to accelerate queries).</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Medallion_with_Bluesky_05_b1c1b69a07.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FMedallion_with_Bluesky_05_b1c1b69a07.png&w=2048&q=75\"></span></a></p>\n<p>This optimized handling of JSON ensures that complex, semi-structured datasets like Bluesky’s can be efficiently stored in the Bronze layer of the architecture. For users curious about the implementation of this new column type, we recommend reading our<a target=\"_blank\" href=\"https://clickhouse.com/blog/a-new-powerful-json-data-type-for-clickhouse\"> detailed blog post here</a>.</p>\n<h2 id=\"bronze-layer-for-raw-data\"></h2>\n<p>While the original description of the Bronze layer doesn’t promote any filtering or transformation, we are less dogmatic here and believe that minimal filtering and data transformations, which are not destructive, can be useful in issue investigation and allowing data to be replayed in the future. For transformations, we recommend limiting these to those achievable with the <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=3H-_pwSp34I\">Materialized columns</a> as shown below in our Bronze layer schema:</p>\n<div><pre><code><span><span>CREATE TABLE</span> bluesky.bluesky_raw</span>\n<span>(</span>\n<span>\t`data` JSON(<span>SKIP</span> `commit.record.reply.root.record`, <span>SKIP</span> `commit.record.value.value`),</span>\n<span>\t`_file` LowCardinality(String),</span>\n<span>\t`kind` LowCardinality(String) MATERIALIZED getSubcolumn(data, <span>'kind'</span>),</span>\n<span>\t`scrape_ts` DateTime64(<span>6</span>) MATERIALIZED fromUnixTimestamp64Micro(<span>CAST</span>(getSubcolumn(data, <span>'time_us'</span>), <span>'UInt64'</span>)),</span>\n<span>\t`bluesky_ts` DateTime64(<span>6</span>) MATERIALIZED multiIf(getSubcolumn(data, <span>'kind'</span>) <span>=</span> <span>'commit'</span>, parseDateTime64BestEffortOrZero(<span>CAST</span>(getSubcolumn(data, <span>'commit.record.createdAt'</span>), <span>'String'</span>)), getSubcolumn(data, <span>'kind'</span>) <span>=</span> <span>'identity'</span>, parseDateTime64BestEffortOrZero(<span>CAST</span>(getSubcolumn(data, <span>'identity.time'</span>), <span>'String'</span>)), getSubcolumn(data, <span>'kind'</span>) <span>=</span> <span>'account'</span>, parseDateTime64BestEffortOrZero(<span>CAST</span>(getSubcolumn(data, <span>'account.time'</span>), <span>'String'</span>)), toDateTime64(<span>0</span>, <span>6</span>)),</span>\n<span>\t`dedup_hash` String MATERIALIZED cityHash64(arrayFilter(p <span>-</span><span>&gt;</span> ((p<span>.1</span>) <span>!=</span> <span>'time_us'</span>), JSONExtractKeysAndValues(<span>CAST</span>(data, <span>'String'</span>), <span>'String'</span>)))</span>\n<span>)</span>\n<span>ENGINE <span>=</span> ReplacingMergeTree</span>\n<span><span>PRIMARY KEY</span> (kind, bluesky_ts)</span>\n<span><span>ORDER</span> <span>BY</span> (kind, bluesky_ts, dedup_hash)</span></code></pre></div>\n<!-- -->\n<p>Some important notes on this schema:</p>\n<ul>\n<li><strong>JSON type</strong> - The <code>data</code> column uses the new JSON type and contains the entire event. We use the<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/data-types/newjson\"> <code>SKIP</code> clause to exclude specific paths from the JSON</a>, which analysis showed was responsible for the repetition in structure noted earlier.</li>\n<li><strong>Metadata preservation</strong> - The <code>_file</code> column will contain a reference to the file the row originated from.</li>\n<li><strong>Materialized columns</strong> - The rest of our columns are materialized and computed from the data column at insert time. The <code>scrape_ts</code> contains the time at which the event was delivered and is extracted from the JSON field <code>time_us</code>. Our <code>kind</code> column describes the event type, as noted earlier. The <code>bluesky_ts</code> column performs conditional logic, extracting the event timestamp based on the <code>kind</code> - this handles our inconsistency in structure and ensures all events have a consistent timestamp. Finally, we compute the hash of the event in the column <code>dedup_hash</code>. For this, we produce an array of all JSON paths and their values, excluding the <code>time_us</code> (which differs across duplicate events), using the function <code>JSONExtractKeysAndValues</code>. The cityHash64 function consumes this array, producing a unique hash.</li>\n<li><strong>ReplacingMergeTree</strong> - The<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/replacing-merge-tree\"> ReplacingMergeTree engine</a> is used here to eliminate duplicate entries sharing the same sorting key values (<code>ORDER BY</code>), with deduplication occurring asynchronously during background merges. These merges happen at indeterminate times and cannot be directly controlled - deduplication is eventual only, therefore. In our schema, the <code>ORDER BY</code> key includes <code>kind</code> and <code>bluesky_ts</code>, allowing efficient reads and ensuring strong compression by clustering rows with similar attributes. We append <code>dedup_hash</code> to uniquely identify rows for deduplication without including it in the <code>PRIMARY KEY</code>. This latter configuration is an optimization that prevents the index for  <code>dedup_hash</code> from being loaded into memory - a sensible choice as we do not query directly on the hash. A detailed guide on the ReplacingMergeTree can be found<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/replacing-merge-tree\"> here</a>.</li>\n</ul>\n<p>Our Bronze layer performs minimal data transformation through materialized columns while providing data deduplication capabilities. Importantly, the choice of ReplacingMergeTree here is optional and decoupled from future layers. Users may prefer a standard MergeTree to inspect duplicates. Our choice here is mainly driven by a desire to minimize storage overhead.</p>\n<h3 id=\"ingesting-data-from-object-storage\"></h3>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Medallion_with_Bluesky_06_6f7832a7a4.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FMedallion_with_Bluesky_06_6f7832a7a4.png&w=2048&q=75\"></span></a></p>\n<p>As described above, our ingestion pipeline uses the <a target=\"_blank\" href=\"https://github.com/vi/websocat\"><code>websocat</code></a> tool to stream data from the JetStream API, storing events as <code>.csv.gz</code> files in Google Cloud Storage (GCS). This intermediate step provides a few benefits: it enables data replay, retains an original copy of the raw data, and mirrors how many users ingest data from object storage.</p>\n<p>To read these files from GCS into our Bronze <code>bluesky_raw</code> table, we use the<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/integrations/s3queue\"> S3Queue table engine</a>. This engine reads data from S3-compliant object storage, automatically processing new files as they are added to a bucket, and inserts them into a designated table through a materialized view. Creating this table requires a little DDL:</p>\n<div><pre><code><span><span>CREATE TABLE</span> bluesky.bluesky_queue</span>\n<span>(</span>\n<span>\t`data` Nullable(String)</span>\n<span>)</span>\n<span>ENGINE <span>=</span> S3Queue(<span>'https://storage.googleapis.com/pme-internal/bluesky/*.gz'</span>, <span>''</span>, <span>''</span>, <span>'CSVWithNames'</span>)</span>\n<span>SETTINGS mode <span>=</span> <span>'ordered'</span>, s3queue_buckets <span>=</span> <span>30</span>, s3queue_processing_threads_num <span>=</span> <span>10</span>;</span></code></pre></div>\n<!-- -->\n<p>Note how we specify the GCS bucket containing the gzipped files and how each row is defined as being a String via the schema declaration. Importantly, we enable \"ordered mode\" via the setting <code>mode = 'ordered</code>. This forces files to be processed in lexicographic order, ensuring sequential ingestion. While this means files added with earlier sort orders are ignored, it maintains efficient and incremental processing and avoids the need to perform large set differences as required if files have no natural ordering.</p>\n<blockquote>\n<p>Our earlier use of timestamps for files ensures our data is processed in order and new files can be identified quickly by the S3Queue table engine.</p>\n</blockquote>\n<p>Our<a target=\"_blank\" href=\"http://sql.clickhouse.com/\"> sql.clickhouse.com</a> environment into which we are loading this data has three nodes, each with 60 vCPUs. The setting <code>s3queue_processing_threads_num</code> assigns the number of threads for file processing per server. In addition, the ordered mode also introduces the setting <code>s3queue_buckets</code>.<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/integrations/s3queue#ordered-mode\"> As recommended</a>, we set this to equal a multiplication of the number of replicas (3) by the number of processing threads (10).</p>\n<p>To consume rows from this queue, we need to attach an Incremental Materialized View. This layer addresses data quality issues, performing more filtering, standardizing schemas, performing transformations, and ensuring all duplicates are removed. With ClickHouse, we typically see bronze tables directly mapped to silver equivalents.</p>\n<p>We know duplicates will have the same <code>bluesky_ts</code> (and other columns), only different <code>scrape_ts</code> values, with the latter potentially much later - although we established earlier that the majority of<a target=\"_blank\" href=\"https://pastila.nl/?00d6750c/dfb434e2a1a7967544ff7da4e538647d#adr+P0WnnfTnxv+rz3PdNw==\"> duplicates occur within a 20-minute window</a>. To ensure no duplicates are delivered to our gold layer, we introduce the concept of a finite duplication window in our silver layer. Events will be assigned to these duplication windows, which will be offset from the current time based on their <code>bluesky_ts</code> value.  These “windows” will periodically be flushed to our gold layer, with a guarantee that only one copy of each event is transferred.</p>\n<p>These duplication windows mean we don’t need to de-duplicate events over an infinite period. This can save significant resources and make the problem more manageable - as we show this can be efficiently implemented in ClickHouse.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Medallion_with_Bluesky_07_b5491ba977.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FMedallion_with_Bluesky_07_b5491ba977.png&w=2048&q=75\"></span></a></p>\n<p>Assigning events to a deduplication window, which tracks real-time and is periodically flushed, relies on data being delivered promptly without a significant delay.</p>\n<p>We can establish by querying our bronze table that:</p>\n<ul>\n<li>90% of events have a <code>bluesky_ts</code> that<a target=\"_blank\" href=\"https://pastila.nl/?0102378d/242240b7ac7225004a0fa4e522db8837#UdkLeR2XIumBfqtVW+apmg==\"> is within 20 minutes from their arrival time</a> in the bronze tier. Here, we assume the \"arrival time\" is the time extracted from the filename on GCS. This relies on:\n<ul>\n<li>The processing of 1m messages at a time does not introduce a significant delay.</li>\n<li>The processing and read time from the S3Queue is not significant. We can check this processing time using the system tables.</li>\n<li>The time extracted from the filename is close to the upload time. We can confirm this with a query against GCS.</li>\n</ul>\n</li>\n<li>For over 94% of events the difference between the<a target=\"_blank\" href=\"https://pastila.nl/?00fb6091/f95b30a064eeeeec2391be4adc57470b#gx+UbwZj1usY4sPyTRCPEg==\"> <code>scrape_ts</code> and the <code>bluesky_ts</code> is less than 20 minutes</a> (in<a target=\"_blank\" href=\"https://pastila.nl/?0721a811/bc9f93d3cf93c52579d0cc658d893a55#ANCrjF+T3stZryoFv6FuSQ==\"> 90% of cases it's even less than 10s</a>). This implies the <code>scrape_ts</code> is also not significantly delayed from the arrival time.</li>\n</ul>\n<p>Knowing that our events are typically delivered within 20 min of their <code>bluesky_ts</code>, we can reliably create deduplication windows in our silver tier. To do this, we create a partition in ClickHouse for every 20-minute interval - a partition effectively equates to a window. Events are assigned to each partition based on which interval they fall into, using the <code>toStartOfInterval(bluesky_ts, toIntervalMinute(20))</code> function. Our resulting silver table schema:</p>\n<div><pre><code><span><span>CREATE TABLE</span> bluesky.bluesky_dedup</span>\n<span>(</span>\n<span>\t`data` JSON(<span>SKIP</span> `commit.record.reply.root.record`, <span>SKIP</span> `commit.record.value.value`),</span>\n<span>\t`kind` LowCardinality(String),</span>\n<span>\t`scrape_ts` DateTime64(<span>6</span>),</span>\n<span>\t`bluesky_ts` DateTime64(<span>6</span>),</span>\n<span>\t`dedup_hash` String</span>\n<span>)</span>\n<span>ENGINE <span>=</span> ReplacingMergeTree</span>\n<span><span>PARTITION</span> <span>BY</span> toStartOfInterval(bluesky_ts, toIntervalMinute(<span>20</span>))</span>\n<span><span>ORDER</span> <span>BY</span> dedup_hash</span>\n<span>TTL toStartOfMinute(bluesky_ts) <span>+</span> toIntervalMinute(<span>1440</span>) SETTINGS ttl_only_drop_parts<span>=</span><span>1</span></span></code></pre></div>\n<!-- -->\n<p>Although we use a ReplacingMergeTree we will own deduplicate events within each partition i.e. merging will only occur within a partition. Note we use<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/ttl\"> a TTL to expire data</a> after it is older than 1440 seconds (24 hours). The setting <code>ttl_only_drop_parts=1</code> ensures parts are only dropped if all rows in that part have expired.</p>\n<blockquote>\n<p>A higher number of partitions can cause issues with large part counts, causing query performance issues and<a target=\"_blank\" href=\"https://clickhouse.com/docs/knowledgebase/exception-too-many-parts\"> \"Too many parts\" errors</a>. We mitigate this by only keeping a day's worth of partitions (72 in total) in the silver table, using<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/ttl\"> TTL rules</a> to expire older data.</p>\n</blockquote>\n<h3 id=\"incremental-materialized-views-for-filtering\"></h3>\n<p>When applying filtering and de-duplication rules to Bronze data, users often preserve negative matches by sending these to a Dead-Letter table for further analysis. Given we plan to periodically send recent partitions in our silver tier to our gold tier, we don't want events arriving too late. For this reason, and to demonstrate a dead letter queue principle, we'll send any events from the bronze layer where the difference between the <code>scrape_ts</code> and <code>bluesky_ts</code> is greater than 20 minutes to a dead letter queue. Events with a \"delay\" less than this will be inserted into their partition in the silver table shown above.</p>\n<p>To achieve this, we use two incremental materialized views. Each view runs a <code>SELECT</code> query on rows inserted into the <code>bluesky_raw</code> Bronze table, sending results to either the dead letter queue or <code>bluesky_dedup</code> silver table. The difference between these views, other than their target table, is their filter criteria.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Medallion_with_Bluesky_08_2463687143.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FMedallion_with_Bluesky_08_2463687143.png&w=2048&q=75\"></span></a></p>\n<p>Our view for sending rows to the silver JSON,</span>\n<span>\t`kind` LowCardinality(String),</span>\n<span>\t`scrape_ts` DateTime64(<span>6</span>),</span>\n<span>\t`bluesky_ts` DateTime64(<span>6</span>),</span>\n<span>\t`dedup_hash` String</span>\n<span>)</span>\n<span><span>AS</span> bluesky.bluesky_raw</span>\n<span><span>WHERE</span> <span>abs</span>(timeDiff(scrape_ts, bluesky_ts)) <span>&lt;</span> <span>1200</span></span></code></pre></div>\n<!-- -->\n<p>Our dead-letter queue table schema and its associated materialized view:</p>\n<div><pre><code><span><span>CREATE TABLE</span> bluesky.bluesky_dlq</span>\n<span>(</span>\n<span>\t`data` JSON(<span>SKIP</span> standard MergeTree for our dead letter queue.</p>\n<h3 id=\"sending-data-to-gold-layer\"></h3>\n<p>The above process leaves partitions populated in our silver tier. Periodically, we want to transfer data from these, guaranteeing events have been fully deduplicated, to our gold tier. We want this to occur reasonably promptly so as to ensure recent data is available in our gold tier for analytics.</p>\n<p>We achieve this periodic flushing using a<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/materialized-view/refreshable-materialized-view\"> Refreshable Materialized View</a>. These views execute periodically against silver layer tables and enable advanced transformations, such as complex joins, that denormalize the data before it is written to Gold layer tables.</p>\n<p>In our case, we want to simply periodically insert data from the latest partition, which shouldn’t receive any more data, to the gold table. This query should be executed with the <code>FINAL</code> clause to ensure all events are deduplicated. While this is typically computationally more expensive than a normal query, we can exploit two properties here:</p>\n<ul>\n<li>The query is only executed periodically - in our case every 20 minutes, shifting the cost to the ingest layer away from the users query.</li>\n<li>We are targeting a single partition with each execution. We can limit query time deduplication to the target partition with the setting<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/replacing-merge-tree#exploiting-partitions-with-replacingmergetree\"> <code>do_not_merge_across_partitions_select_final=1</code></a>, further optimizing this query and reducing the work required.</li>\n</ul>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Medallion_with_Bluesky_09_15f7878bcb.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FMedallion_with_Bluesky_09_15f7878bcb.png&w=2048&q=75\"></span></a></p>\n<p>This only requires us to identify the partition to flush to the gold tier each time. Our logic here is captured by the diagram above, but in summary:</p>\n<ol>\n<li>We identify the latest partition in the silver table <code>bluesky_dedup</code> using the _partition_id metadata field. We subtract 40 mins from this partition_id (which is a timestamp) giving us the partition 2 time windows ago i.e. X - 2. We refer to this as the <code>current_partition</code>.</li>\n<li>Our target gold layer table <code>bluesky</code> includes a <code>_rmt_partition_id</code> column populated by the refreshable materialized view, which records from which silver partition each event originated. We use this to identify the most recent partition which was successfully transferred. We add 20mins to this to identify the next partition to process, referring to this as <code>next_to_process</code>.</li>\n<li>If <code>next_to_process</code> is equal to 1200 we know <code>bluesky</code> was empty (0 + 1200 seconds = 1200) and no events have been inserted to the gold tier yet i.e. first execution of the view. In this case, we simply use the value of <code>current_partition</code> and insert all events where the <code>_partition_id = current_partition</code>.</li>\n<li>If <code>next_to_process</code> is greater than 1200, we know we have already transferred partitions. In this case, if the <code>current_partition</code> is &gt;= <code>next_to_process</code>, then we know we are least 40 mins behind (2 partitions) the latest partition and use the value of <code>next_to_process</code> -  inserting all events where the <code>_partition_id = next_to_process</code>. If <code>current_partition</code>  &lt; <code>next_to_process</code>, then return a <code>noop</code> (0) and don’t move data.</li>\n</ol>\n<p>The above logic is designed to be robust to cases where execution is not perfect every 20 minutes e.g. repeated executions or cases where execution is delayed or fails. Our resulting Refreshable Materialized View encapsulating the above logic in its <code>SELECT</code> statement is shown below:</p>\n<div><pre><code><span><span>CREATE</span> MATERIALIZED <span>VIEW</span> bluesky.blue_sky_dedupe_rmv</span>\n<span>REFRESH <span>EVERY</span> <span>20</span> <span>MINUTE</span> APPEND <span>TO</span> bluesky.bluesky</span>\n<span>(</span>\n<span>\t`data` JSON(<span>SKIP</span> `commit.record.reply.root.record`, <span>SKIP</span> `commit.record.value.value`),</span>\n<span>\t`kind` LowCardinality(String),</span>\n<span>\t`bluesky_ts` DateTime64(<span>6</span>),</span>\n<span>\t`_rmt_partition_id` LowCardinality(String)</span>\n<span>)</span>\n<span><span>AS</span> <span>WITH</span></span>\n<span>\t(</span>\n<span>          <span>--step 1</span></span>\n<span>    \t  <span>SELECT</span> toUnixTimestamp(subtractMinutes(<span>CAST</span>(_partition_id, <span>'DateTime'</span>), <span>40</span>))</span>\n<span>    \t  <span>FROM</span> bluesky.bluesky_dedup</span>\n<span>    \t  <span>GROUP</span> <span>BY</span> _partition_id</span>\n<span>    \t  <span>ORDER</span> <span>BY</span> _partition_id <span>DESC</span></span>\n<span>    \t  LIMIT <span>1</span></span>\n<span>\t) <span>AS</span> current_partition,</span>\n<span>\t(</span>\n<span>          <span>--step 2</span></span>\n<span>    \t  <span>SELECT</span> toUnixTimestamp(addMinutes(<span>CAST</span>(<span>max</span>(partition_id), <span>'DateTime'</span>), <span>20</span>))</span>\n<span>    \t  <span>FROM</span> bluesky.latest_partition</span>\n<span>\t) <span>AS</span> next_to_process</span>\n<span><span>SELECT</span></span>\n<span>\tdata,</span>\n<span>\tkind,</span>\n<span>\tbluesky_ts,</span>\n<span>\t_partition_id <span>AS</span> _rmt_partition_id</span>\n<span><span>FROM</span> bluesky.bluesky_dedup</span>\n<span><span>FINAL</span></span>\n<span><span>--step 3 &amp; 4</span></span>\n<span><span>WHERE</span> _partition_id <span>=</span> <span>CAST</span>(if(next_to_process <span>=</span> <span>1200</span>, current_partition, if(current_partition <span>&gt;=</span> next_to_process, next_to_process, <span>0</span>)), <span>'String'</span>)</span>\n<span>SETTINGS do_not_merge_across_partitions_select_final <span>=</span> <span>1</span></span></code></pre></div>\n<!-- -->\n<p>This view executes every 20 minutes, delivering clean, deduplicated data to our Gold layer. Note that the data incurs a delay of 40 minutes until it is available here, although users can query the silver layer for more recent data if required.</p>\n<p>An astute reader may notice that our query in step 2, and in the earlier diagram, uses the table <code>latest_partition</code> rather than querying <code>_rmt_partition_id</code> in the bluesky gold table. This table is produced by an incremental materialized view and an optimization, which makes identifying the next partition more efficient. This view, shown below, tracks the latest partition from inserts to the gold table.</p>\n<div><pre><code><span><span>CREATE</span> MATERIALIZED <span>VIEW</span> bluesky.latest_partition_mv <span>TO</span> bluesky.latest_partition</span>\n<span>(</span>\n<span>\t`partition_id` UInt32</span>\n<span>)</span>\n<span><span>AS</span> <span>SELECT</span> <span>max</span>(<span>CAST</span>(_rmt_partition_id, <span>'UInt32'</span>)) <span>AS</span> partition_id</span>\n<span><span>FROM</span> bluesky.bluesky</span>\n<span></span>\n<span><span>CREATE TABLE</span> bluesky.latest_partition</span>\n<span>(</span>\n<span>\t`partition_id` SimpleAggregateFunction(max, UInt32)</span>\n<span>)</span>\n<span>ENGINE <span>=</span> AggregatingMergeTree</span>\n<span><span>ORDER</span> <span>BY</span> tuple()</span></code></pre></div>\n<!-- -->\n<h2 id=\"gold-layer-for-data-analysis\"></h2>\n<p>The above refreshable materialized view periodically sends data to our gold tier table <code>bluesky</code>. The schema of this table is shown below:</p>\n<div><pre><code><span><span>CREATE TABLE</span> bluesky.bluesky</span>\n<span>(</span>\n<span>\t`data` JSON(<span>SKIP</span> `commit.record.reply.root.record`, <span>SKIP</span> `commit.record.value.value`),</span>\n<span>\t`kind` LowCardinality(String),</span>\n<span>\t`bluesky_ts` DateTime64(<span>6</span>),</span>\n<span>\t`_rmt_partition_id` LowCardinality(String)</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>PARTITION</span> <span>BY</span> toStartOfInterval(bluesky_ts, toIntervalMonth(<span>1</span>))</span>\n<span><span>ORDER</span> <span>BY</span> (kind, bluesky_ts)</span></code></pre></div>\n<!-- -->\n<p>With data fully de-duplicated prior to its insertion, we can use a standard MergeTree. Our ordering key here is chosen exclusively on the access patterns of our consumers and to optimize for compression. Our table here is partitioned by month, principally for data management, and since we expect most queries to read the most recent data.</p>\n<p>Note that while we still exploit the JSON type a this tier, we could perform more transformations on the data in the earlier refreshable materialized view e.g. extracting commonly queried columns to the root, or using ALIAS columns, to simplify query syntax.</p>\n<h3 id=\"materialized-views-for-common-queries\"></h3>\n<p>This gold layer should be entirely optimized for querying by downstream applications and consumers. While our ordering key aims to facilitate this, not all access patterns will be the same. Until now the most common application for incremental materialized views has been to perform filtering and data insertion between layers. However, our earlier use of a view to compute the next partition, hinted out how else we might optimize other queries.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Medallion_with_Bluesky_10_412cff2857.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FMedallion_with_Bluesky_10_412cff2857.png&w=2048&q=75\"></span></a></p>\n<p>As well as allowing filtering and sending subsets of data to a target table with different ordering keys (optimized for other access patterns), materialized views can be used to precompute aggregates at insert time when rows are added to the gold table. These aggregations results will be a smaller representation of the original data (a partial sketch in the case of aggregations). As well as ensuring the resulting query for reading the results from the target table is simple, it ensures query times are faster than if the same computation was performed on the original data, shifting computation (and thus query latency) from query time to insert time. A full guide on materialized views can be found<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/materialized-view\"> here</a>.</p>\n<p>As an example, consider our earlier query, which computes the most common types of commit events:</p>\n<div><pre><code><span><span>SELECT</span> data.commit.collection <span>AS</span> collection, <span>count</span>() <span>AS</span> c, uniq(data.did) <span>AS</span> users</span>\n<span><span>FROM</span> bluesky</span>\n<span><span>WHERE</span> kind <span>=</span> <span>'commit'</span></span>\n<span><span>GROUP</span> <span>BY</span> <span>ALL</span></span>\n<span><span>ORDER</span> <span>BY</span> c <span>DESC</span></span>\n<span>LIMIT <span>10</span></span>\n<span></span>\n<span>┌─collection───────────────┬─────────c─┬───users─┐</span>\n<span>│ app.bsky.feed.like   \t   │ <span>269979403</span> │ <span>5270604</span> │</span>\n<span>│ app.bsky.graph.follow\t   │ <span>150891706</span> │ <span>5631987</span> │</span>\n<span>│ app.bsky.feed.post   \t   │  <span>46886207</span> │ <span>3083647</span> │</span>\n<span>│ app.bsky.feed.repost \t   │  <span>33249341</span> │ <span>1956986</span> │</span>\n<span>│ app.bsky.graph.block \t   │   <span>9789707</span> │  <span>993578</span> │</span>\n<span>│ app.bsky.graph.listitem  │   <span>3231676</span> │  <span>102020</span> │</span>\n<span>│ app.bsky.actor.profile   │   <span>1731669</span> │ <span>1280895</span> │</span>\n<span>│ app.bsky.graph.listblock │\t<span>263667</span> │  <span>105310</span> │</span>\n<span>│ app.bsky.feed.threadgate │\t<span>215715</span> │   <span>49871</span> │</span>\n<span>│ app.bsky.feed.postgate   │ \t <span>99625</span> │   <span>19960</span> │</span>\n<span>└──────────────────────────┴───────────┴─────────┘</span>\n<span></span>\n<span><span>10</span> <span>rows</span> <span>in</span> set. Elapsed: <span>6.445</span> sec. Processed <span>516.53</span> million <span>rows</span>, <span>45.50</span> GB (<span>80.15</span> million <span>rows</span><span>/</span>s., <span>7.06</span> GB<span>/</span>s.)</span>\n<span>Peak memory usage: <span>986.51</span> MiB.</span></code></pre></div>\n<!-- -->\n<p>For 500 million events, this query takes around 6 seconds. To convert this to an incremental materialized view, we need to prepare a table to receive the incremental aggregation results:</p>\n<div><pre><code><span><span>CREATE TABLE</span> bluesky.top_post_types</span>\n<span>(</span>\n<span>\t`collection` LowCardinality(String),</span>\n<span>\t`posts` SimpleAggregateFunction(sum, UInt64),</span>\n<span>\t`users` AggregateFunction(uniq, String)</span>\n<span>)</span>\n<span>ENGINE <span>=</span> AggregatingMergeTree</span>\n<span><span>ORDER</span> <span>BY</span> collection</span></code></pre></div>\n<!-- -->\n<p>Note how we need to use an AggregatingMergeTree and specify the ordering key to be our grouping key - aggregation results with the same value for this column will be merged. The incremental results need to be stored under a special column types <code>SimpleAggregateFunction</code> and  <code>AggregateFunction</code> - for this we need to specify the function and associated type.</p>\n<p>Our corresponding materialized view, which populates this table as rows are inserted into the gold table, is shown below. Notice how we use the <code>-State</code> suffix to explicitly generate an aggregation state:</p>\n<div><pre><code><span><span>CREATE</span> MATERIALIZED <span>VIEW</span> top_post_types_mv <span>TO</span> top_posts_types</span>\n<span><span>AS</span></span>\n<span><span>SELECT</span> data.commit.collection <span>AS</span> collection, <span>count</span>() <span>AS</span> posts,</span>\n<span>\tuniqState(<span>CAST</span>(data.did, <span>'String'</span>)) <span>AS</span> users</span>\n<span><span>FROM</span> bluesky</span>\n<span><span>WHERE</span> kind <span>=</span> <span>'commit'</span></span>\n<span><span>GROUP</span> <span>BY</span> <span>ALL</span></span></code></pre></div>\n<!-- -->\n<p>When querying this table, we use the <code>-Merge</code> suffix to merge aggregation states.</p>\n<div><pre><code><span><span>SELECT</span> collection,</span>\n<span>       <span>sum</span>(posts) <span>AS</span> posts,</span>\n<span>       uniqMerge(users) <span>AS</span> users</span>\n<span><span>FROM</span> top_post_types</span>\n<span><span>GROUP</span> <span>BY</span> collection</span>\n<span><span>ORDER</span> <span>BY</span> posts <span>DESC</span></span>\n<span>LIMIT <span>10</span></span>\n<span></span>\n<span><span>10</span> <span>rows</span> <span>in</span> set. Elapsed: <span>0.042</span> sec.</span></code></pre></div>\n<!-- -->\n<p>Our query performance has improved by over 150x!</p>\n<p>Our final architecture diagram showing all of our layers:</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Medallion_with_Bluesky_11_009af5408a.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FMedallion_with_Bluesky_11_009af5408a.png&w=2048&q=75\"></span></a></p>\n<h3 id=\"example-queries-and-visuals-at-sql-clickhouse-com\"></h3>\n<p>The above represents a very simple example.
