contentHtml: "<article><div><p>The founding team behind Dash0 has deep roots in Instana, a company known for its innovations in observability tooling. And where Instana, in its early days, heavily relied on Cassandra and ElasticSearch as storage solutions, as the platform evolved, the team transitioned to leveraging ClickHouse as one of its core database technologies. This shift addressed our need for greater efficiency and scalability as both customer demands and feature requirements grew.</p>\n<p><span><img alt=\"dash0_dashboard.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fdash0_dashboard_7bd7a80c83.png&w=2048&q=75\"></span></p>\n<p>When we founded Dash0, evaluating ClickHouse as our primary storage solution was a natural first step, especially since two of our founders had worked at ClickHouse helping to build their cloud offering. Fast-forward to today, where ClickHouse serves as our main storage for all OpenTelemetry data, with PostgreSQL being the only other database used, handling just customer-specific settings and related data.</p>\n<p>In this blog post, I'll share our ClickHouse journey—from initial evaluation through technical implementation details—highlighting the key features that make Dash0 possible.</p>\n<h2 id=\"decision-phase\"></h2>\n<p>The goal of Dash0 is to be <a target=\"_blank\" href=\"https://www.dash0.com/blog/opentelemetry-native-the-future-of-observability#what-does-an-open-telemetry-native-observability-tool-look-like\">OpenTelemetry native</a>, leveraging the full broadness of information that the OpenTelemetry signals provide:</p>\n<ul>\n<li><strong>Cross-Signal Correlation</strong>: Engineers can start with metrics, drill down to relevant traces, and examine associated logs in a single workflow</li>\n<li><strong>Service Health Monitoring</strong>: The platform preserves OpenTelemetry's semantic conventions to automatically generate meaningful dashboards or create actionable alerts</li>\n<li><strong>Simplified Troubleshooting</strong>: By maintaining connections between signals, Dash0 significantly reduces mean time to resolution during incidents</li>\n</ul>\n<p>These features naturally have certain implications that trickle down to the storage layer:</p>\n<ul>\n<li>Handle and store all the various signals: Metrics, Logs and Spans</li>\n<li>Be able to reference one signal via another, either via Resource attributes or other fields such as via the TraceId and SpanId for a log (<a target=\"_blank\" href=\"https://opentelemetry.io/docs/specs/otel/logs/#log-correlation\">https://opentelemetry.io/docs/specs/otel/logs/#log-correlation</a>)</li>\n<li>High cardinality data due to attributes, which are present both on the Resource level and on a signal level</li>\n</ul>\n<p>Consolidating all data in a single system makes the most sense for these requirements. This approach enables <code>JOIN</code> s directly on the tables to combine various signals and leverages ClickHouse's proven scalability for monitoring workloads.</p>\n<p>ClickHouse's columnar architecture excels at handling high-cardinality data from OpenTelemetry attributes (key-value pairs that provide additional context and metadata about telemetry data). While attributes can be stored as <code>Map(String, String)</code> types, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter/column#materialize-column\">materialized columns</a> extract <a target=\"_blank\" href=\"https://opentelemetry.io/docs/specs/semconv/\">frequently-queried attributes</a> like <code>service.name</code> into dedicated columns for faster lookups. Additionally, with the recent addition of <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/newjson\">native JSON support</a>, ClickHouse now addresses the storage of complex dynamic structures even more efficiently. This promises the flexibility of Map with the performance of materialized columns, further simplifying configuration.</p>\n<p>ClickHouse also provides robust <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/integrations/language-clients\">client libraries for both Java and Golang</a>—languages essential to our tech stack. While the Dash0 engineering team is well-versed in Java, Golang is also a natural choice due to the various OpenTelemetry and related libraries and integrations written in this language. For example, the <a target=\"_blank\" href=\"https://opentelemetry.io/docs/collector/\">OpenTelemetry Collector</a>, which we envisioned to use for the processing incoming data, is written in Golang and already includes a <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/exporter/clickhouseexporter/\">ClickHouse exporter</a> in its control repository.</p>\n<h2 id=\"operating-clickhouse\"></h2>\n<p>Beyond the table schemas needed to support Dash0's features (which will be covered further down), we've carefully optimized ClickHouse's operational aspects based on our experience. These optimizations balance maintainability, performance, and cost efficiency. Naturally, we continuously <a target=\"_blank\" href=\"https://www.dash0.com/hub/integrations/int_clickhouse_cloud/overview\">monitor ClickHouse via Dash0</a> itself as well to ensure it also keeps running smoothly.</p>\n<h3 id=\"storage\"></h3>\n<p>For any observability platform, data volume grows rapidly with larger customer accounts, making storage costs a critical consideration. This naturally creates tension with query performance requirements. And while perhaps logs and spans may lose relevance after a few weeks, at Dash0 we wanted to preserve metrics for over a year to enable seasonal trend analysis.</p>\n<p>With the experience gathered during our tenure at ClickHouse, we implemented a hybrid storage approach combining AWS S3 storage with temporary local storage. A setup that is well <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/storing-data\">supported by ClickHouse</a>. Customer usage patterns show that data from the past 1-2 days receives the most frequent queries, which aligns with use-cases like viewing dashboards or incident investigation based on <a target=\"_blank\" href=\"https://www.dash0.com/distributed-tracing\">tracing signals</a>.</p>\n<p>Thanks to the high compression rates that ClickHouse manages, the urgency to move data from hot to cold storage is deferred, making 1-2 days of hot storage easily possible.</p>\n<p>Our multi-tiered disk configuration consists of:</p>\n<ul>\n<li>1-2 days local storage</li>\n<li>Data moved to AWS S3</li>\n<li>Local storage for query cache</li>\n</ul>\n<p>This query cache allows data retrieved from S3 to remain available locally for some time, accelerating subsequent queries on the same data while reducing S3 GET request costs.</p>\n<p>The disk configuration looks something like:</p>\n<div><pre><code><span>&lt;,[object Object],&gt;</span>\n<span>   &lt;,[object Object],&gt;</span>\n<span> id=\"ordering-in-table-schemas\"></h3>\n<p>Without going fully into the table schemas, the <code>ORDER BY</code> , <code>PARTITION BY</code> and <code>TTL</code> definitions are related to the storage.</p>\n<p>The <code>TTL</code> clause ensures that ClickHouse moves the data correctly to the S3 disk:</p>\n<div><pre><code><span>TTL toDateTime(<span>Timestamp</span>) <span>+</span> <span>INTERVAL</span> <span>25</span> <span>HOUR</span> <span>TO</span> VOLUME <span>'n_2_cold'</span>,</span>\n<span>   toDateTime(<span>Timestamp</span>) <span>+</span> <span>INTERVAL</span> <span>13</span> <span>MONTH</span> <span>DELETE</span></span></code></pre></div>\n<p>The <code>ORDER BY</code> clause is important for two reasons:</p>\n<ul>\n<li>Querying the data</li>\n<li>Compression of the data</li>\n</ul>\n<p>When designing our ClickHouse schemas, we made strategic trade-offs with primary key selection. Unlike the <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/bb534937e13c605cb3bf3e90c5358d859c5c7b5a/exporter/clickhouseexporter/exporter_logs.go#L160\">ClickHouse Exporter</a> that uses <code>service.name</code> in the primary key for all signals, we generate a hash of all attributes called <code>ResourceHash</code> that serves a similar purpose. Our primary key consists of <code>ResourceHash</code> followed by the <code>Timestamp</code> field.</p>\n<p>Placing the <code>ResourceHash</code> / <code>service.name</code> before the <code>Timestamp</code> in the <code>ORDER BY</code> clause offers two key advantages:</p>\n<ul>\n<li><strong>Optimized Filtering</strong>: With OpenTelemetry data, filtering by resource attributes - and thus <code>ResourceHash</code> - is common when correlating signals.This ordering allows ClickHouse to select fewer marks, reducing the number of records that need to be processed.</li>\n<li><strong>Better Compression</strong>: Signals from the same service or process typically share similar characteristics - especially resource attributes, but also e.g. log bodies, and span names. Ordering by <code>ResourceHash</code> groups similar data together, significantly improving ClickHouse's compression efficiency compared to <code>Timestamp</code> -first ordering.</li>\n</ul>\n<p>There's also a case to be made for reversing the order, first <code>Timestamp</code> and then <code>ResourceHash</code>. Since all Dash0 queries require a time frame, using first the <code>Timestamp</code> would efficiently narrow down the number of records that need to be selected, while a <code>ResourceHash</code> / <code>service.name</code> might not always be used for filtering. However, we mitigated this concern by using the day (from the <code>Timestamp</code>) as <code>PARTITION BY</code> key, which ensures ClickHouse only selects those parts within the specified time range for reading.</p>\n<p>Although ClickHouse supports multiple primary keys for the same table through <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/alter/projection\">projections</a>, we opted against this approach due to increased storage costs.</p>\n<h3 id=\"replication-and-sharding\"></h3>\n<p>With our ClickHouse cluster setup, we decided, at least for now, to use multiple replicas and only a single shard. While at some point in the future we might still move to a multi-shard setup, for now this setup is simpler and sufficient for our needs.</p>\n<p>With multiple shards, <a target=\"_blank\" href=\"https://clickhouse.com/docs/architecture/cluster-deployment\">table migrations need to be executed for every shard individually</a>. Also, other changes to the cluster are more complex.</p>\n<h2 id=\"dash0-functionality-on-top-of-clickhouse\"></h2>\n<p>In this section we’ll go into the table schemas more, and some of the other ClickHouse features we use to support the Dash0 features.</p>\n<h3 id=\"metrics-metadata\"></h3>\n<p>The standard ClickHouse Exporter for the OpenTelemetry Collector stores all metrics information <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/d1d4d693eee7f81752c8270f8777fa585a480579/exporter/clickhouseexporter/internal/gauge_metrics.go#L20\">per record and in separate tables based on metric type</a>. This approach is inefficient because:</p>\n<ol>\n<li>Metadata like <code>MetricName</code>, <code>MetricDescription</code>, and <code>MetricUnit</code> remain consistent across data points. Repeating this data for every data point results in significant data duplication. Even for the attributes per data point, these often share identical or similar attributes (e.g., <code>http.response.status_code</code> values of <code>200</code> and <code>500</code>) and thus could be deduplicated.</li>\n<li>Map-type columns for the attributes are slow to process and suboptimal as primary key components</li>\n<li>Querying for a metric without knowing its type (sum, gauge, histogram, etc) requires searching across five different tables</li>\n</ol>\n<p>To address these issues, we adopted a strategy already used by the Prometheus Remote Write library for ClickHouse and also implemented in ClickHouse's own <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/time_series#target-tables\">Time-Series engine</a>: storing metadata in a separate table with an ID that references the actual values.</p>\n<p>While we still maintain separate tables for different metric types (as they require different column structures), this approach dramatically improves compression. A simplified version of our gauge table looks like this:</p>\n<div><pre><code><span><span>CREATE TABLE</span> IF <span>NOT</span> <span>EXISTS</span> otel.otel_metrics_gauge</span>\n<span>(</span>\n<span> `MetricHash` UInt64 Codec(LZ4),</span>\n<span> `StartTimeUnix` DateTime64(<span>9</span>) CODEC(Delta, LZ4),</span>\n<span> `TimeUnix` DateTime64(<span>9</span>) CODEC(Delta, LZ4),</span>\n<span> `<span>Value</span>` Float64 CODEC(LZ4),</span>\n<span>)</span>\n<span>ENGINE MergeTree</span>\n<span><span>PARTITION</span> <span>BY</span> toDate(TimeUnix)</span>\n<span><span>ORDER</span> <span>BY</span> (MetricHash, TimeUnix)</span></code></pre></div>\n<p>The <code>MetricHash</code> acts as the join column with the metadata table, further described below.</p>\n<p>Since metrics normally are collected at a fixed rate - for example, every 15 seconds - the <code>Delta</code> compression on the <code>TimeUnix</code> column works really well. And also values themselves usually don't change that much ensuring change values are small, resulting in good compression.</p>\n<p>The metrics metadata table looks like this:</p>\n<div><pre><code><span><span>CREATE TABLE</span> IF <span>NOT</span> <span>EXISTS</span> otel.otel_metrics_metadata</span>\n<span>(</span>\n<span> `TimeUnix` <span>Date</span> CODEC(Delta, (TimeUnix, MetricName, MetricHash)</span></code></pre></div>\n<p>There's a few things in there that will likely need some explanation :)</p>\n<p>One of our most significant design choices is using <code>AggregatingMergeTree</code> for our metrics metadata table—the same approach ClickHouse employs for its <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/time_series#inner-table-engines\">Tags table, part of the TimeSeries table engine</a>. This engine ensures continuous deduplication of data despite constant writes to the table. Since <code>Resource-</code>, <code>Scope-</code>, and <code>Metric</code> attributes rarely change between data points, deduplicating this information significantly reduces the data volume ClickHouse must process when searching by these attributes.</p>\n<p>The <code>MetricHash</code> field, which encapsulates the most critical attributes and fields, allows us to safely apply the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/aggregate-functions/reference/anylast\"><code>anyLast</code> aggregation</a> function because we know certain properties (like <code>ResourceAttributes</code>) cannot change for the same <code>MetricHash</code> value.</p>\n<p>Our <code>FirstSeen</code> and <code>LastSeen</code> columns use <code>min</code> and <code>max</code> aggregation functions to track when a particular time series was active. This information helps us filter out metrics that weren't present during specific query timeframes, again improving query efficiency.</p>\n<p>The same reasoning applies to the choice of using the  <code>TimeUnix</code> field as part of the <code>ORDER BY</code> clause—a design choice that may seem counterintuitive at first. Since we partition metadata by month to keep this information in hot storage longer, without any time-based field in the primary key, queries might scan metrics for an entire month. By adding <code>TimeUnix</code> (<code>Date</code> type with day granularity) to the primary key, we reduce the number of matching rows. Because all our queries include time ranges, we can easily include an explicit filter on this <code>TimeUnix</code> column alongside the <code>FirstSeen</code> and <code>LastSeen</code> columns.</p>\n<p>Using <code>AggregatingMergeTree</code> comes with an important caveat for querying: data merges aren't guaranteed to occur before query execution. This detail is easily overlooked but can lead to incorrect results when queries are not adjusted appropriately. For instance, when no data is received for some time for a specific time series, the <code>FirstSeen</code> / <code>LastSeen</code> ranges of unmerged records might appear as follows:</p>\n<p><span><img alt=\"Blog_BuildingAnObservabilitySolutionDiagram_202504_V1.0_2 of 4.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Building_An_Observability_Solution_Diagram_202504_V1_0_2_of_4_f750fab2b6.png&w=2048&q=75\"></span></p>\n<p>Clearly, when not merging records, then <em>Time Series A</em> would never get selected even though it was present before and after the queried range. Therefore, when running queries on an <code>AggregatedMergeTree</code>, this always needs to be done either using a <code>GROUP BY</code> with similar merge functions as on the table definition or using <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/from#final-modifier\">the FINAL keyword</a> with the table (where a simple <code>GROUP BY</code> is normally preferred).</p>\n<h3 id=\"sampling\"></h3>\n<p>At Dash0, we prioritize data correctness and use sampling selectively. We primarily employ sampling to provide customers with quick initial results for longer-running queries, while executing the complete query in the background, as used within our <a target=\"_blank\" href=\"https://www.dash0.com/blog/triage-the-quickest-way-to-finding-the-needle-in-the-haystack\">triage feature</a> which we recently released.</p>\n<p>To use the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/select/sample\"><code>SAMPLING</code> clause</a> in ClickHouse queries the table schema must be specifically designed to support this. And since the sampling column must be part of the sorting key, this often requires creating new tables rather than modifying existing ones. This presents the main challenge when using sampling: finding the optimal <code>ORDER BY</code> clause that works well with both regular or sampled queries.</p>\n<p>When implementing sampling, we recommend:</p>\n<ol>\n<li>Thoroughly benchmarking various options to ensure existing performance doesn't degrade</li>\n<li>Using <code>EXPLAIN indexes=1 &lt;query&gt;</code> to analyze how selection of parts and granules is affected by different table sorting keys and secondary indexes</li>\n</ol>\n<p>Another thing that is good to be aware of, is that the potentially sampling rates depend on the type chosen. This can be any type from <code>UInt8</code> to <code>UInt64</code>. That also means decreasing the number of 'groups' in favour of better ordering, e.g. as <code>xxh3(SpanId) % 10</code> to create just 10 groups, does not work. Even if using <code>UInt8</code>, ClickHouse assumes 256 ‘groups’ and selecting a 0.1 sample rate would result in a query <code>WHERE &lt;sample_column&gt; &lt; 26</code>, which as you see would still select 100% of the records.</p>\n<p>Thus, the type chosen for the column also determines the maximum sample ratio that can be chosen. With <code>UInt8</code>, the lowest sample rate is ~ 0.003. If you try to go lower, ClickHouse determines it cannot do sampling and instead will scan all records.</p>\n<h4 id=\"our-approach\"></h4>\n<p>Given the sorting key we had and the above information about sampling (some of which we found out during the benchmarking), we had a few different sorting keys in mind that we wanted to evaluate. Our original sorting key for the spans table was <code>ORDER BY (ResourceHash, Timestamp)</code></p>\n<p>The <code>ORDER BY</code> clauses we thought could work:</p>\n<ul>\n<li>(traces2)<code> toStartOfHour(Timestamp), ResourceHash, xxh3(SpanId)</code></li>\n<li>(traces3)<code> ResourceHash, SpanName, xxh3(SpanId)</code></li>\n<li>(traces4)<code> ResourceHash, toStartOfHour(Timestamp), xxh3(SpanId)</code></li>\n<li>(traces5)<code> xxh3(SpanId) % 256, ResourceHash, Timestamp</code></li>\n</ul>\n<p>For each of these sorting keys, we created a separate table and loaded 3 days of data. We determined we wanted to verify a few things:</p>\n<ul>\n<li>Compression ratio, to ensure storage costs would not dramatically increase for the new schemas</li>\n<li>Query times for existing, so non-sampled queries</li>\n<li>Query times when using sampling</li>\n<li>Validate primary and secondary (data-skipping) index usage to cross-check numbers from previous queries make sense</li>\n</ul>\n<p>To easily run the benchmarking (for which <code><a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/utilities/clickhouse-benchmark\">clickhouse-benchmark</a></code> works great), we collected some common queries and put them into separate SQL files, such like this one (getting a list of spans ordered by timestamp):</p>\n<div><pre><code><span><span>WITH</span> subtractHours(toDateTime(<span>'${QUERY_TS}'</span>), ${QUERY_DURATION} <span>+</span> <span>1</span>) <span>AS</span> startTime, subtractHours(toDateTime(<span>'${QUERY_TS}'</span>), <span>1</span>) <span>AS</span> endTime</span>\n<span><span>SELECT</span></span>\n<span>    ResourceHash,</span>\n<span>    <span>Timestamp</span>,</span>\n<span>    SpanAttributes,</span>\n<span>    SpanName</span>\n<span><span>FROM</span> ${QUERY_TABLE} ${QUERY_SAMPLE}</span>\n<span><span>WHERE</span> (<span>Timestamp</span> <span>&gt;=</span> startTime) <span>AND</span> (<span>Timestamp</span> <span>&lt;=</span> endTime) <span>AND</span> (ParentSpanId <span>=</span> <span>''</span>)</span>\n<span><span>ORDER</span> <span>BY</span></span>\n<span>    <span>Timestamp</span> <span>ASC</span></span>\n<span>LIMIT <span>50</span></span>\n<span>FORMAT <span>Null</span></span>\n<span>SETTINGS use_query_cache<span>=</span><span>false</span>;</span></code></pre></div>\n<p>By using variables, which we replace via a script (see below), we can easily run the script for different durations and tables, etc.</p>\n<p>Additionally, if using <code>FORMAT Null</code> there is no actual data returned by the query. to minimize JOINs whenever possible (although the ClickHouse team is heavily investing in this area, so stay tuned!) In most scenarios, ClickHouse performs better with sub-selects rather than JOINs. However, when JOINs are needed, consider these recommendations:</p>\n<ul>\n<li><strong>Use the correct type of JOIN</strong>. If a value on the left-hand side matches multiple values on the right-hand side, the JOIN will return multiple rows - the so-called cartesian product. If your use case doesn't need all matches from the right-hand side but just any single match, you can use <code>ANY</code> JOINs (e.g. <code>LEFT ANY JOIN</code>). They are faster and use less memory than regular JOINs. Consult ClickHouse's documentation and blog articles for guidance on selecting optimal JOIN types.</li>\n<li><strong>Reduce the sizes of JOINed tables.</strong> The runtime and memory consumption of JOINs grows proportionally with the sizes of the left and right tables. To reduce the amount of processed data by the JOIN, add additional filter conditions in the <code>WHERE</code> or <code>JOIN ON</code> clauses of the query. ClickHouse pushes filter conditions as deep as possible down in the query plan, usually before JOINs. If the filters are not pushed down automatically (confirm with <code>EXPLAIN</code>), rewrite one side of the JOIN as a sub-query to force pushdown. You can also try including relevant filters directly in the JOIN condition to reduce the data volume e.g. <code>JOIN … ON a.ServiceName = b.ServiceName AND b.Timestamp &gt; startTime AND b.Timestamp &lt; endTime</code> . The ClickHouse team is investing in supporting automatic predicate pushdown, so this advice is subject to change.</li>\n<li><strong>Default values as no-match markers in outer JOINs</strong>. Left/right/full outer joins include all values from the left/right/both tables. If no join partner is found in the other table for some value, ClickHouse replaces the join partner with a special marker. The SQL standard mandates that databases use NULL as such a marker. In ClickHouse, this requires wrapping the result column in Nullable, creating an additional memory and performance overhead. As an alternative, you can configure the setting <code>join_use_nulls = 0</code> and use the default value of the result column data type as a marker.</li>\n</ul>\n<blockquote>\n<p>As the ClickHouse team invests heavily in JOIN performance, we expect the above recommendations to change and become redundant.
