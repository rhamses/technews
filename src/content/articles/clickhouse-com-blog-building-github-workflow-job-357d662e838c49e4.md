contentHtml: "<article><div><p>In a <a target=\"_blank\" href=\"https://clickhouse.com/blog/monitor-github-action-workflow-job-queues\">previous post</a> I introduced how you can build a table in ClickHouse containing all of the data from your GitHub Actions using GitHub Webhooks. We do this for the ClickHouse organization, to provide essential metrics on the internal queue of workflow jobs.</p>\n<p>Just having this and doing nothing with it would be a huge waste of gemstone data, so a couple of months ago the data was used to implement a lambda to quickly inflate and deflate our workers on demand. This has improved the responsiveness of our job launching, reacting to an increase in scheduled tests, as well as saving us compute when the workload is lower. Let's discuss how we achieved this!</p>\n<h2 id=\"the-idea\"></h2>\n<p>We have all events in our database for when a workflow job was created, started or finished. Consider this query from the previous post, which returns the current ClickHouse queue size for self-managed GitHub Runners:</p>\n<pre><p>\nSELECT\n    last_status,\n    count() AS queue,\n    labels\nFROM\n(\n    SELECT\n        argMax(status, updated_at) AS last_status,\n        labels,\n        id,\n        html_url\n    FROM default.workflow_jobs\n    WHERE has(labels, 'self-hosted') AND (started_at &gt; (now() - toIntervalHour(3)))\n    GROUP BY ALL\n    HAVING last_status != 'completed'\n)\nGROUP BY ALL\nORDER BY\n    labels ASC,\n    last_status ASC\n</p> \n</pre>\n<p><span><img alt=\"query-result.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fquery_result_1ebbf3568f.png&w=2048&q=75\"></span></p>\n<p>Knowing this allows us proactively to scale-up the runners to cover the demand, or scale-down to free unnecessary resources.</p>\n<p>The new desired capacity is calculated based on the current number of runners and jobs in progress and queue. If there is a deficit, we increase the capacity proportional to it (usually, deficit / 5). And for the unnecessary reserve, we quickly deflate the group (reserve / 2).</p>\n<h2 id=\"an-old-system\"></h2>\n<p>The officially recommended approach in AWS to trigger scaling up/down is assigning CloudWatch alarms to Auto-Scaling Groups (ASG.) So, whenever an alarm is in an alarm state, the ASG adds or removes some instances.</p>\n<p>We used to monitor how many instances of each ASG were in a busy state using the GitHub runners API. If there were more than 97% busy runners for 5 minutes, another one runner was added. For scaling out the rule was less than 70%.</p>\n<p>The system used to be very reactive and inert. To warm up groups with 50+ runners it required a few hours.</p>\n<h2 id=\"improvements-and-statistics\"></h2>\n<p>After switching to our new system, we both achieved faster jobs launching and a saving of compute time after the job was done. You can see how it affected the runners on the graphs:</p>\n<p>The old system:</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/old_system_8e1bd87afb.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fold_system_8e1bd87afb.png&w=2048&q=75\"></span></a></p>\n<p>The new system:</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/new_system_232c534dda.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fnew_system_232c534dda.png&w=2048&q=75\"></span></a></p>\n<p>We can see how the Busy and Active Runners are more tightly correlated in the new system, indicating that provisioned workers are more heavily utilized. The code used here is all available in <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/2ab313e6b4272f5888bc7d3b54533b3f8ba86fba/tests/ci/autoscale_runners_lambda/app.py\">our repository</a>. Hopefully others can make similar improvements and savings!</p></div></article>"
