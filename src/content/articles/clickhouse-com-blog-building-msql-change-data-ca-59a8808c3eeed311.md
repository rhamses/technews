contentHtml: "<div><h2 id=\"introduction\"></h2>\n<p>Change Data Capture (CDC) is a critical pattern in modern data architectures that require real-time data integration. In this technical deep dive, we'll explore how ClickPipes—the native data integration solution in ClickHouse Cloud—implements CDC for MySQL databases. This article presents the internals of our MySQL CDC implementation for engineers and architects who want to understand the mechanisms that power reliable, high-performance database replication.</p>\n<h2 id=\"mysql-replication-fundamentals\"></h2>\n<p>Let’s start by going over the fundamentals of replication in MySQL.</p>\n<h3 id=\"binary-logs-the-foundation-of-mysql-cdc\"></h3>\n<p>MySQL's binary log (binlog) is the cornerstone of its replication architecture. It records all changes to database data and structure sequentially, as shown in the diagram below:</p>\n<p><span><img alt=\"01.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F01_a677bd56ca.png&w=2048&q=75\"></span></p>\n<p>The binary log contains events representing:</p>\n<ul>\n<li>Data manipulation (INSERT, UPDATE, DELETE)</li>\n<li>Data definition (CREATE, ALTER, DROP)</li>\n<li>Transaction boundaries (BEGIN, COMMIT, ROLLBACK)</li>\n</ul>\n<p>Each binary log event has an event header with metadata (timestamp, server ID, etc.) and an event body with the actual change data.</p>\n<h3 id=\"binary-log-formats\"></h3>\n<p>MySQL offers three binlog formats:</p>\n<ol>\n<li><strong>STATEMENT</strong>: Logs SQL statements\n<ul>\n<li>Small log size</li>\n<li>Non-deterministic functions may cause replication issues</li>\n<li>Not suitable for CDC</li>\n</ul>\n</li>\n<li><strong>ROW</strong>: Logs changed rows\n<ul>\n<li>Records before/after images of changed rows</li>\n<li>Highest fidelity but larger log size</li>\n<li><strong>Required for CDC</strong></li>\n</ul>\n</li>\n<li><strong>MIXED</strong>: Uses STATEMENT by default, switches to ROW when needed\n<ul>\n<li>Not suitable for CDC</li>\n</ul>\n</li>\n</ol>\n<p><strong>Prerequisite — binlog_row_image = FULL</strong></p>\n<p>ClickPipes needs every row change in the MySQL binary log to carry the complete before- and after-image, so the source must run with binlog_row_image='FULL' (this is the default in MySQL 8.x). Lighter modes such as MINIMAL or NOBLOB drop unchanged columns to save space, but they prevent ClickPipes from replaying updates idempotently and from handling primary-key rewrites safely. The change to binlog_row_image = FULL mainly increases UPDATE-heavy binlogs, while inserts and deletes stay the same, so the overhead is usually modest.</p>\n<h3 id=\"global-transaction-identifiers-gtids\"></h3>\n<p>GTIDs provide a consistent way to identify transactions across servers:</p>\n<div><pre><code><span>GTID = source_id:transaction_id</span></code></pre></div>\n<p>Example GTID set: <code>123e4567-e89b-12d3-a456-426614174000:1-1000,2000-3000</code></p>\n<p>Benefits of GTID-based replication:</p>\n<ul>\n<li>Transaction tracking across server restarts</li>\n<li>Simpler failover and high availability</li>\n<li>Easier replication topology changes</li>\n</ul>\n<h2 id=\"clickpipes-mysql-cdc-architecture\"></h2>\n<p>ClickPipes implements CDC for MySQL through a robust architecture that handles both initial data loading and continuous replication.</p>\n<h3 id=\"architecture-overview\"></h3>\n<p>The diagram below shows the architecture of MySQL CDC in ClickPipes:</p>\n<p><span><img alt=\"02.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F02_a591171ab6.png&w=2048&q=75\"></span></p>\n<p>The ClickPipes MySQL CDC pipeline consists of several key components:</p>\n<ol>\n<li><strong>Connection Management</strong>: Establishes and maintains connections to the source MySQL database</li>\n<li><strong>Binlog Syncer</strong>: Connects to MySQL's binary log stream</li>\n<li><strong>Event Processor</strong>: Processes binary log events into structured change records</li>\n<li><strong>Schema Registry</strong>: Tracks the structure of source tables</li>\n<li><strong>Checkpointing</strong>: Records progress to enable resumption after failures</li>\n<li><strong>Transformation Layer</strong>: Converts MySQL types to ClickHouse types</li>\n<li><strong>Sink Layer</strong>: Writes data to ClickHouse efficiently</li>\n</ol>\n<h3 id=\"connection-and-setup\"></h3>\n<p>When a MySQL CDC flow starts, ClickPipes:</p>\n<ol>\n<li>Validates MySQL configurations\n<ul>\n<li>Ensures binlog_format = 'ROW'</li>\n<li>Checks binlog_row_image = 'FULL'</li>\n<li>Verifies binlog retention settings</li>\n</ul>\n</li>\n<li>Examines replication capabilities\n<ul>\n<li>Detects GTID support</li>\n<li>Establishes replication position</li>\n</ul>\n</li>\n<li>Extracts table schemas\n<ul>\n<li>Retrieves column definitions and types</li>\n<li>Identifies primary keys</li>\n<li>Maps MySQL types to ClickHouse types</li>\n</ul>\n</li>\n</ol>\n<h3 id=\"initial-data-loading\"></h3>\n<p>Before streaming changes, ClickPipes performs an initial snapshot:</p>\n<p><span><img alt=\"442909790-f9daa28f-1445-42fb-8cfb-3f801aca6e07.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F442909790_f9daa28f_1445_42fb_8cfb_3f801aca6e07_28bcc7019d.png&w=2048&q=75\"></span></p>\n<p>This process:</p>\n<ol>\n<li>Creates a consistent snapshot of the data</li>\n<li>Sets up the target tables in ClickHouse</li>\n<li>Records the binlog position or GTID to start streaming from</li>\n</ol>\n<h3 id=\"streaming-changes\"></h3>\n<p>After initial loading, ClickPipes streams changes continuously:</p>\n<p><span><img alt=\"442909792-be7c8e3c-6e63-49ac-b563-38330378f10c.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F442909792_be7c8e3c_6e63_49ac_b563_38330378f10c_14c5224d05.png&w=2048&q=75\"></span></p>\n<p>The streaming process:</p>\n<ol>\n<li>Connects to MySQL's binlog stream</li>\n<li>Processes events in transaction order</li>\n<li>Converts row events to structured change records</li>\n<li>Applies changes to ClickHouse</li>\n<li>Updates checkpoints to track progress</li>\n</ol>\n<h2 id=\"gtid-vs-binlog-position-based-replication\"></h2>\n<p>ClickPipes supports both replication methods:</p>\n<h3 id=\"gtid-based-replication\"></h3>\n<p>GTIDs provide a logical, consistent way to track transactions. When a transaction completes, the GTID set is updated and stored in the checkpoint. This mechanism supports efficient resumption and is resilient to server restarts or topology changes.</p>\n<h3 id=\"binlog-position-based-replication\"></h3>\n<p>Traditional binlog position tracking works with file names and positions. When a file rotation event occurs, the position is updated with the new file name and position. Though effective, this approach is less resilient to server changes and more complex to manage in high-availability setups. In case of fail-over you will have to resync a pipe.</p>\n<h2 id=\"processing-binary-log-events\"></h2>\n<p>ClickPipes processes several types of binlog events:</p>\n<h3 id=\"row-events\"></h3>\n<p><span><img alt=\"442909788-f2a647f4-b22d-41a6-abf5-e5c6580fb78b.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F442909788_f2a647f4_b22d_41a6_abf5_e5c6580fb78b_0c1f373155.png&w=2048&q=75\"></span></p>\n<p>The pipeline handles:</p>\n<ol>\n<li><strong>INSERT operations</strong>: Extracts column values and creates insert records</li>\n<li><strong>UPDATE operations</strong>: Captures both before/after values and creates update records</li>\n<li><strong>DELETE operations</strong>: Extracts column values and creates delete records</li>\n</ol>\n<h3 id=\"schema-change-events\"></h3>\n<p>ClickPipes detects and processes schema changes by parsing DDL statements. The system:</p>\n<ol>\n<li>Uses TiDB's SQL parser to parse DDL statements</li>\n<li>Extracts schema changes (especially column additions)</li>\n<li>Updates the schema registry</li>\n<li>Propagates changes to target tables</li>\n</ol>\n<h2 id=\"type-mapping-and-conversion\"></h2>\n<p>ClickPipes handles the full range of MySQL data types:</p>\n<div><table><tbody><tr><td><strong>MySQL
