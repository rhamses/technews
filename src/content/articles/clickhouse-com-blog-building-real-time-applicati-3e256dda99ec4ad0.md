As Hex continues to enhance features, we expect this to evolve into a fully-fledged interactive application builder.</p>\n<h2 id=\"data-collection\"></h2>\n<p>Users with ClickHouse installed will immediately have access to the <code>git-import</code> tool. This command line utility generates three files: <code>commits.tsv</code>, <code>file_changes.tsv</code>, and <code>line_changes.tsv</code> when run in the root directory of any cloned repository. The contents of these files are  handily explained by the tool's inbuilt help:</p>\n<div><pre><code><span>ClickHouse % clickhouse-git-import -h</span>\n<span></span>\n<span>A tool to extract information from Git repository for analytics.</span>\n<span></span>\n<span>It dumps the data for the following tables:</span>\n<span>- commits - commits with statistics;</span>\n<span>- file_changes - files changed in every commit with the info about the change and statistics;</span>\n<span>- line_changes - every changed line in every changed file in every commit with full info about the line and the information about previous change of this line.</span>\n<span></span>\n<span>The largest and the most important table is \"line_changes\".</span>\n<span></span>\n<span>Run this tool inside your git repository. It will create .tsv files that can be loaded into ClickHouse (or into other DBMS if you dare).</span></code></pre></div>\n<p>The generated TSV files provide a detailed history of the repository and can be indexed directly into ClickHouse using the client, assuming the tables have been created (note <code>clickhouse-git-import</code> provides the schemas required via help):</p>\n<div><pre><code><span>clickhouse<span>-</span>client <span>--query 'INSERT INTO git.commits FORMAT TSV' &lt; commits.tsv</span></span></code></pre></div>\n<p>You can generate this data for any repository on Github and analyze your own projects using the questions <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/github\">here</a> for inspiration. If you don't have time to generate the data yourself, we've loaded our own data for ClickHouse into <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=DCQPNPAIMAQXRLHYURLKVJ\">sql.clickhouse.com</a> (note the database is <code>git_clickhouse</code>) so our community can play with some <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/github#queries\">example queries</a>.</p>\n<p>Our aspiration to collect the top 100k repositories on Github requires a little more work. For this, we utilize a queue-worker model where each job represents a repository. Workers claim jobs/repos off this queue, clone the associated repository (if it doesn't exist on disk), invoke <code>git-import</code>, and index the data into ClickHouse. In our simple approach, the workers share a common disk. If a repository has been previously indexed and thus already cloned, we simply run a <code>git pull</code>, only ever inserting the differences on the main branch. This sharing of the disk, and cloned repositories, avoids unnecessary re-cloning and network/disk IO. The above process is visualized below:</p>\n<p><span><img alt=\"worker_model.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fworker_model_7de62c48e3.png&w=2048&q=75\"></span></p>\n<p>Provided we have sufficient compute and disk resources, we can scale this approach by simply adding more worker processes.</p>\n<h2 id=\"using-the-keepermap-table-engine\"></h2>\n<p>With this approach, a repository should only ever be processed by one worker at any moment in time. Two workers cloning the same repository, or running <code>git-import</code>, at the same disk location, would likely result in errors and inconsistencies. Furthermore, we may wish to prioritize some jobs/repositories above others and ensure these are processed first by workers.</p>\n<p>To achieve the above, we wanted our queue to:</p>\n<ul>\n<li>Prohibit duplicate jobs (keyed off repository name) from being scheduled</li>\n<li>Ensure that a job is only ever claimed by one worker</li>\n</ul>\n<p>There are many queuing technologies that could be configured to address this - <a target=\"_blank\" href=\"https://aws.amazon.com/sqs/\">Amazon SQS, </a>for example. Wanting to keep dependencies minimal, however, as well as to push the boundaries of ClickHouse, we decided to see if we could model a queue using a table powered by the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/keeper-map\">KeeperMap </a>engine. This engine utilizes a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/sre/keeper/clickhouse-keeper#implementation-details\">ClickHouse Keeper</a> instance under the hood, offering a consistent key-value store with linearizable writes and sequentially consistent reads. This engine type is also enabled in Cloud, allowing us to write our application with no dependencies besides ClickHouse.</p>\n<p>While Keeper Map gave us linearizable writes and sequentially consistent reads, there was no means of achieving atomic updates - required for a worker to claim a job exclusively. For example, consider the table schema for our queue.</p>\n<div><pre><code><span><span>CREATE TABLE</span> git.work_queue</span>\n<span>(</span>\n<span>    `repo_name` String,</span>\n<span>    `scheduled` DateTime,</span>\n<span>    `priority` Int32,</span>\n<span>    `worker_id` String,</span>\n<span>    `started_time` DateTime</span>\n<span>)</span>\n<span>ENGINE <span>=</span> KeeperMap(<span>'git_queue'</span>)</span>\n<span><span>PRIMARY KEY</span> repo_name</span></code></pre></div>\n<p>Note how the <code>repo_name</code> is the unique primary key. Assuming jobs are queued with <code>worker_id</code> being empty, a worker needs to set the <code>worker_id</code> column on a row to claim the job and its associated repository. This can be achieved with an <code>ALTER TABLE git.work_queue UPDATE worker_id=&lt;worker_id&gt;, started_time=&lt;started_time&gt; WHERE worker_id=’’</code> command. At the time of initial development, KeeperMap had no guarantees that an update to a row would be atomic, potentially allowing two workers to claim the job. Furthermore, we needed to ensure no repository could be inserted on the queue more than once - ensuring only one row existed for any single repository. Once a job is completed and the data for a repository is updated in ClickHouse, the row can be deleted.</p>\n<p>After speaking with our development team (thanks <a target=\"_blank\" href=\"https://github.com/antonio2368\">Antonio Andelic</a>) and a <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/48293\">few</a> <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/48354\">PRs</a> later, ClickHouse now has <code>keeper_map_strict_mode</code>. When set to true, this:</p>\n<ul>\n<li>Prevents a row identified by the primary key (repo_name) from being inserted more than once. Attempts to do so cause an exception.</li>\n<li>Fetching and updating of a row via ALTER will succeed only if it's executed atomically, i.e., the version hasn't changed between the operations.</li>\n<li>Deleting rows requires a fetch and delete. Again this will only succeed if it can be done atomically.</li>\n</ul>\n<p>With these properties in place, we could implement our queue. The full scheduling and worker code can be found <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhub\">here</a>. We visualize the full process below:</p>\n<p><span><img alt=\"keeper_map_updates.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fkeeper_map_updates_578d816540.png&w=2048&q=75\"></span></p>\n<p>A few important notes:</p>\n<ul>\n<li>If a worker fails to issue an <code>ALTER</code> on a row because another worker has succeeded first, another job is attempted. Workers attempt to claim N times before backing off and sleeping to retry later.</li>\n<li>Once a job is completed, its row is deleted.</li>\n<li>The <code>ALTER</code> is conditioned with a match on the <code>repo_name</code> and <code>worker_id</code>, the latter of which must be empty. This statement will succeed if no rows match. This can happen if the job has already been claimed and the <code>worker_id</code> is set. On achieving a successful <code>ALTER</code>, we therefore also check that the <code>worker_id</code> is set to the value of the current worker with a <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhub/blob/main/repo/importer.py#L150\">simple SELECT</a>. This is shown above as the “Confirm Job” step.</li>\n<li>Before a worker updates a repository via a <code>git pull</code>, it first checks the last commit that has already been inserted into ClickHouse. This is achieved by a query to the <code>commits</code> table to identify the latest time for the commits data. This time is then used to filter out rows i.e. only <code>commits</code>, <code>file_changes</code>, and <code>line_changes</code> with a time greater than this value are sent to ClickHouse.</li>\n</ul>\n<p>For inserting data generated by <code>git-import</code>, we simply use the <code>clickhouse-client</code> and <a target=\"_blank\" href=\"https://clickhouse.com/blog/extracting-converting-querying-local-files-with-sql-clickhouse-local\"><code>clickhouse-local</code></a> tools - see below.</p>\n<h2 id=\"a-few-schema-tweaks\"></h2>\n<p>The tables <code>commits</code>, <code>file_changes</code>, and <code>line_changes</code> all have very distinct schemas. Rather than deciding on a database per repository (or tables with repo-identifying suffixes/prefixes), we decided to store all data for all repositories in the same three tables. This should mean we can potentially scale to millions of repositories in the future. However, the default schemas for the <code>commits</code>, <code>line_changes</code>, and <code>file_changes</code> tables have no column which identifies the repository name. We thus add this to the rows at insert time. Given the repository name will be the main filter in our application, we also make this the first entry in the primary key for all our tables - thus adhering to <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#using-multiple-primary-indexes\">ClickHouse best practices</a> and aligning with our access patterns. Finally, we add a <code>updated_at</code> materialized column which is always set to the value of <code>now()</code> when a row is inserted. This allows us to easily identify when repositories were last updated (we use this when keeping the data up-to-date). Below we show the schema for the commits table. Full schemas for the other tables can be found <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhub/\">here</a>.</p>\n<div><pre><code><span><span>CREATE TABLE</span> git.commits</span>\n<span>(</span>\n<span>    `hash` String,</span>\n<span>    `author` LowCardinality(String),</span>\n<span>    `<span>time</span>` DateTime,</span>\n<span>    `message` String,</span>\n<span>    `files_added` UInt32,</span>\n<span>    `files_deleted` UInt32,</span>\n<span>    `files_renamed` UInt32,</span>\n<span>    `files_modified` UInt32,</span>\n<span>    `lines_added` UInt32,</span>\n<span>    `lines_deleted` UInt32,</span>\n<span>    `hunks_added` UInt32,</span>\n<span>    `hunks_removed` UInt32,</span>\n<span>    `hunks_changed` UInt32,</span>\n<span>    `repo_name` LowCardinality(String),</span>\n<span>    `updated_at` DateTime MATERIALIZED now()</span>\n<span>)</span>\n<span>ENGINE <span>=</span> ReplacingMergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (repo_name, <span>time</span>, hash)</span></code></pre></div>\n<p>Note that we use a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/replacingmergetree\">ReplacingMergeTree</a>. This table engine removes duplicate rows (having the same primary key) asynchronously during background merges. This ensures any duplicates are eventually removed, e.g., in the event our earlier approach of using the max time of the commits in ClickHouse, to filter out already inserted rows during repository updates fails. This is eventual deduplication and should be sufficient for our analytical needs. Other tables thus have <code>ORDER BY</code> keys which provide the required unique row identification.</p>\n<p>Finally, using <code>updated_at</code>, we periodically identify the repositories with the oldest time and thus need to be updated. These are then scheduled to the queue for processing.</p>\n<h2 id=\"the-datasets\"></h2>\n<p>After running with 25 workers for around 24hrs on a 48-core machine with 16TB of disk space, we cloned and inserted the full commit history for 50k repositories.</p>\n<div><pre><code><span><span>SELECT</span> uniqExact(repo_name)</span>\n<span><span>FROM</span> git.commits</span>\n<span></span>\n<span>┌─uniqExact(repo_name)─┐</span>\n<span>│               <span>50035</span>  │</span>\n<span>└──────────────────────┘</span></code></pre></div>\n<p>This consumes around 8TB of disk space (cloned repositories).</p>\n<div><pre><code><span>/dev/nvme1n1    16T  8.2T  7.9T  51% /data</span></code></pre></div>\n<p>In ClickHouse, we can see the generated data compresses well:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    formatReadableSize(<span>sum</span>(data_compressed_bytes)) <span>AS</span> compressed_size,</span>\n<span>    formatReadableSize(<span>sum</span>(data_uncompressed_bytes)) <span>AS</span> uncompressed_size,</span>\n<span>    round(<span>sum</span>(data_uncompressed_bytes) <span>/</span> <span>sum</span>(data_compressed_bytes), <span>2</span>) <span>AS</span> ratio</span>\n<span><span>FROM</span> system.columns</span>\n<span><span>WHERE</span> database <span>=</span> <span>'git'</span></span>\n<span></span>\n<span>┌─compressed_size─┬─uncompressed_size─┬─ratio─┐</span>\n<span>│ <span>890.80</span> GiB      │ <span>12.39</span> TiB         │ <span>14.24</span> │</span>\n<span>└─────────────────┴───────────────────┴───────┘</span>\n<span></span>\n<span><span>1</span> <span>row</span> <span>in</span> set.
