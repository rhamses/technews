contentHtml: "<article><div><p>Fuzzing has become a scorching <a target=\"_blank\" href=\"https://www.techscience.com/cmc/v78n1/55370\">research topic</a> in the last few years to find issues in software, including crashes, bad output, and security vulnerabilities. Databases are no exception, and many research tools have been developed.</p>\n<p>ClickHouse is also actively tested with fuzzers -  over the years, several fuzzers, including SQLancer, SQLsmith, <a target=\"_blank\" href=\"https://clickhouse.com/blog/fuzzing-click-house\">AST fuzzer</a>, and, more recently, <a target=\"_blank\" href=\"https://clickhouse.com/blog/fuzzing-wingfuzz\">WINGFUZZ</a> fuzzer, have been used to test ClickHouse.</p>\n<p>Since I joined ClickHouse, I have been reviewing the existing testing infrastructure in ClickHouse and noticed a notorious gap in their fuzzers. None of them was capable of generating a wide complexity of queries while keeping query correctness in mind.</p>\n<p>Therefore, over the past 5 months, I developed BuzzHouse, a new fuzzer to complement the existing gap in the existing testing infrastructure. BuzzHouse already has found about <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/issues?q=is%3Aopen+label%3Afuzz+author%3APedroTadim\">100 new issues</a> in ClickHouse, and in this blog post, I am showing what to consider when fuzzing databases.</p>\n<p><span><img alt=\"Fuzz_01.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FFuzz_01_2f5ac9f93f.png&w=2048&q=75\"></span></p>\n<h2 id=\"what-is-fuzzing-or-fuzz-testing\"></h2>\n<p>Before discussing why fuzzing databases is hard, let’s briefly define what fuzzing is. Fuzzing, or fuzz testing, is a software testing technique that involves providing random, unexpected, or invalid inputs to a program to uncover bugs, crashes, or vulnerabilities. By simulating unpredictable user behavior, fuzzing helps identify edge cases that might otherwise go unnoticed during standard testing. It’s widely used to improve the robustness and security of software, from operating systems to compilers and databases.</p>\n<h2 id=\"why-fuzzing-databases-is-hard\"></h2>\n<p>A database is a complex system encompassing query processing and optimization, data storage, buffer management, and, for cases such as ClickHouse, distributed processing over multiple nodes. With such a level of complexity, building a fuzzer to test a database is no simple task. At the same time, attempting to test all the layers of a database system becomes more challenging because more diversified inputs are required.</p>\n<h3 id=\"how-to-generate-queries\"></h3>\n<p>We can start by looking at the top-most layer, ie input client’s query parsing and processing. Most databases, including ClickHouse, use SQL as their input language, and most database fuzzers are developed to produce SQL queries. The very first design question is how we are going to generate queries. Some fuzzers do it completely randomly, while others use a backlog strategy in mind. While both approaches are correct, depending on the chosen approach, some cases won’t be generated, and some bugs may not be found. Let’s take a look at <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/tpch\">TPC-H</a> Q5 as an example:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    n_name,</span>\n<span>    <span>sum</span>(l_extendedprice <span>*</span> (<span>1</span> <span>-</span> l_discount)) <span>AS</span> revenue</span>\n<span><span>FROM</span></span>\n<span>    customer,</span>\n<span>    orders,</span>\n<span>    lineitem,</span>\n<span>    supplier,</span>\n<span>    nation,</span>\n<span>    region</span>\n<span><span>WHERE</span></span>\n<span>    c_custkey <span>=</span> o_custkey</span>\n<span>    <span>AND</span> l_orderkey <span>=</span> o_orderkey</span>\n<span>    <span>AND</span> l_suppkey <span>=</span> s_suppkey</span>\n<span>    <span>AND</span> c_nationkey <span>=</span> s_nationkey</span>\n<span>    <span>AND</span> s_nationkey <span>=</span> n_nationkey</span>\n<span>    <span>AND</span> n_regionkey <span>=</span> r_regionkey</span>\n<span>    <span>AND</span> r_name <span>=</span> <span>'ASIA'</span></span>\n<span>    <span>AND</span> o_orderdate <span>&gt;=</span> <span>DATE</span> <span>'1994-01-01'</span></span>\n<span>    <span>AND</span> o_orderdate <span>&lt;</span> <span>DATE</span> <span>'1994-01-01'</span> <span>+</span> <span>INTERVAL</span> <span>'1'</span> <span>year</span></span>\n<span><span>GROUP</span> <span>BY</span></span>\n<span>    n_name</span>\n<span><span>ORDER</span> <span>BY</span></span>\n<span>    revenue <span>DESC</span>;</span></code></pre></div>\n<!-- -->\n<p>When users write such a query, they expect all tables and columns to be valid. However, if the fuzzer only generates valid identifiers, bugs from inexisting tables and columns will never be found.</p>\n<p>Another interesting case here is the grouping case. SQL has complex semantics that make random query generation harder. In this case, we must make sure the projection either uses the <code>n_name</code> column or any other column inside an aggregate function to be correct. Other rules may also be applied, such as not using aggregates in WHERE clause and window functions cannot be inside aggregate functions. With these semantics in mind, it becomes difficult to generate correct queries randomly. If we take these restrictions, we will decrease the domain of queries generated, plus the number of bugs we can potentially find.</p>\n<p>Some statements, such as DROP and DETACH, make tables unavailable. The fuzzer should potentially be aware of this to use valid tables in queries. We can keep track of changes made by these statements, but later, it becomes complex to handle this information when more features are added, such as SQL views that may depend on tables.</p>\n<p>As we add more features to be tested, e.g. SQL functions, SQL query clauses, SQL types, number of tables/columns/databases to use, other statements such as INSERT or OPTIMIZE in ClickHouse, or more table engines, the number of combinations will increase sharply. This becomes a relevant issue when we attempt to generate correct queries or test a new feature in the fuzzer. As I said before, we can either try to avoid these errors and restrict the generated domain or ignore them and improve query correctness. In BuzzHouse I try to generate the correct output for most cases while fallbacking to the random case a few times.</p>\n<h3 id=\"finding-wrong-results\"></h3>\n<p>With current state-of-the-art research, we can find queries with wrong results in BuzzHouse which is not possible in other fuzzers such as SQLsmith. The strategies include:</p>\n<ul>\n<li>Dump a table and read it back again, so we can test formats as well.</li>\n<li>Run and compare equivalent queries using an oracle. This strategy was pioneered by SQLancer.</li>\n<li>Run the same query with different settings, such as the number of threads, enable/disable external sorting or grouping, or set a different join algorithm.</li>\n<li>Swap tables with a table from another relational database, then push predicates into it, and then compare computation results with either the same ordering clause or a global aggregate query.</li>\n</ul>\n<p>The following issue was found after dumping and re-inserting values into a table. The block order was different after the insert, thus impacting sorting with the <code>LowCardinality</code> type.</p>\n<div><pre><code><span><span>SET</span> allow_suspicious_low_cardinality_types <span>=</span> <span>1</span>;</span>\n<span><span>CREATE TABLE</span> t0 (c0 LowCardinality(Nullable(<span>Int</span>))) ENGINE <span>=</span> MergeTree()</span>\n<span><span>ORDER</span> <span>BY</span> (c0) SETTINGS allow_nullable_key <span>=</span> <span>1</span>;</span>\n<span><span>INSERT INTO</span> <span>TABLE</span> t0 (c0) <span>VALUES</span> (<span>1</span>);</span>\n<span><span>INSERT INTO</span> <span>TABLE</span> t0 (c0) <span>VALUES</span> (<span>0</span>), (<span>NULL</span>);</span>\n<span><span>SELECT</span> c0 <span>FROM</span> t0 <span>ORDER</span> <span>BY</span> c0 <span>DESC</span> <span>NULLS LAST</span>;</span>\n<span><span>-- 1</span></span>\n<span><span>-- NULL</span></span>\n<span><span>-- 0</span></span></code></pre></div>\n<!-- -->\n<h3 id=\"use-code-coverage\"></h3>\n<p>Current state-of-the-art techniques in fuzzers such as AFL and libFuzzer use code coverage to find new code paths while fuzzing. This sounds promising at first, but with the complexity of databases, finding new paths becomes increasingly more difficult. First, the SQL language has many semantics to follow as explained above. Second, many issues require more inputs, such as multiple clients or server restarts. Third, code coverage fuzzing becomes much slower, and due to each mutation doing a small change to a query at each loop, the diversity of queries generated is much lower. At the same time, it’s advised to backup the generated corpus to continue the same session later.  In BuzzHouse, we decided not to use code coverage at the moment to complement existing fuzzers with this feature.</p>\n<h3 id=\"frequency-of-events\"></h3>\n<p>The next important decision is the randomness of the events. Every decision a fuzzer performs will be based on probabilities. Conforming to the probabilities set, the fuzzer gets restricted to the possibility of events it can generate. Let’s take an example for the case a fuzzer has to choose the next query to generate:</p>\n<ul>\n<li>10% chance to create a table.</li>\n<li>50% chance to run a SELECT query (these happen more often in analytical databases so we should generate more).</li>\n<li>20% chance to insert into a table.</li>\n<li>5% to drop a table.</li>\n<li>5% to delete from a table (a lightweight delete in ClickHouse).</li>\n<li>10% for an ALTER statement.</li>\n</ul>\n<p>This probability chart may sound plausible, however, at every 20 queries, one DROP statement will be generated. What is the consequence of this? Due to the number of combinations, a DROP statement has a higher chance of succeeding than a CREATE TABLE. There’s also a possibility to drop all the tables in the catalog, while none is created. Furthermore, it becomes difficult to do long-term testing on a table that persists on the server while many INSERT/UPDATE/DELETE statements are issued over time. These small decisions may impact what the fuzzer will ever be capable of doing.</p>\n<h2 id=\"designing-a-fuzzer-for-clickhouse\"></h2>\n<p>Besides everything mentioned above, there are other design decisions when building a fuzzer. Here are some questions and what was implemented:</p>\n<ul>\n<li>Should many clients run in parallel? If so, how to synchronize between them? At the moment, only a single client in BuzzHouse.</li>\n<li>All the fuzzers run on the client side. What about fuzzing the server? Use a separate fuzzer for the server.</li>\n<li>Not all the issues are about crashes, we have to look for wrong results in queries, the quality of error messages, and performance. BuzzHouse detects some wrong results. For performance, later we can benchmark consecutive query runs and compare them.</li>\n<li>By looking at TPC-H Q5, what should the size of the queries generated by the fuzzer be? How many tables should we join? Look at cross-products, they generate large intermediates and turn the fuzzer slower. BuzzHouse has “depth” and “width” parameters that can be tuned for this.</li>\n<li>For how long should a fuzzer keep a table in the catalog on average? What about updating the table metadata? BuzzHouse will always keep at least 3 tables in the catalog. Alter statements run for every table except for the ones with peers in other databases.</li>\n<li>Look at error messages, some bugs output strange error messages instead of crashing the server. Also sometimes an error message may be right or wrong. In the future, we could keep a list of expected error messages to be thrown by the server.</li>\n<li>For slow queries, which ones are legitimately slow and which aren’t? This is a difficult question to answer. However, we can compare the performance with other databases.</li>\n</ul>\n<p>Taking all the points above, it becomes very difficult to build a fuzzer that will cover all the cases, and then find all existing issues. Making a simple design decision will impact what the fuzzer will be capable of generating.</p>\n<p>BuzzHouse attempts to generate the most correct queries as possible by using syntax assumptions such as:</p>\n<ul>\n<li>Always generate the correct number of arguments for a function.</li>\n<li>Use columns from tables present in queries.</li>\n<li>Back up the catalog with CREATE/ALTER/DROP changes.</li>\n<li>Keep query syntax always correct.</li>\n</ul>\n<p>However, the codebase becomes more complex to handle all these assumptions, plus requires to be updated whenever new features are added. Also don’t forget some trivial queries such as <code>SELECT 1 FROM idontexist;</code> won’t be generated.</p>\n<h2 id=\"summary\"></h2>\n<p>BuzzHouse was developed to address critical gaps in the fuzzing landscape used for ClickHouse.</p>\n<p>By focusing on generating complex yet correct queries and identifying issues beyond simple crashes, it complements the current suite of tools used to test databases:</p>\n<ul>\n<li>Use AFL and libFuzzer for code coverage-guided fuzzing.</li>\n<li>SQLsmith (<a target=\"_blank\" href=\"https://github.com/anse1/sqlsmith\">https://github.com/anse1/sqlsmith</a>) for complex query generation.</li>\n<li>SQLancer (<a target=\"_blank\" href=\"https://github.com/sqlancer/sqlancer\">https://github.com/sqlancer/sqlancer</a>) for query correctness.</li>\n<li>Pstress (<a target=\"_blank\" href=\"https://github.com/Percona-QA/pstress\">https://github.com/Percona-QA/pstress</a>) for heavy load. Planned to possibly integrate it in ClickHouse CI later.</li>\n<li>Sysbench (<a target=\"_blank\" href=\"https://github.com/akopytov/sysbench\">https://github.com/akopytov/sysbench</a>) for a continuous workload (+1 hour). Also in the plans for CI.</li>\n<li>BuzzHouse for randomly generated catalog-backed queries.</li>\n<li>AST fuzzer to mutate queries from tests, and possibly other fuzzers.</li>\n<li>A custom script to fuzz the server and plug any other existing fuzzer into it.</li>\n</ul>\n<p>BuzzHouse’s ability to uncover already over 100 new issues underscores its value and the importance of diverse fuzzing approaches in improving the robustness and reliability of databases like ClickHouse.</p>\n<p>BuzzHouse is set to be merged into the ClickHouse source code soon. If you’re curious, feel free to explore the <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/71085\">pull request</a>.</p></div></article>"
