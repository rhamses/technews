contentHtml: "<div><p>Since launching <a target=\"_blank\" href=\"https://clickhouse.com/blog/announcing-general-availability-of-clickhouse-bring-your-own-cloud-on-aws\">BYOC on AWS</a>, we've seen organizations adopt it because they want the operational simplicity of a fully managed ClickHouse service, but they need their data to stay inside their own cloud account. With today's announcement, Google Cloud users can now get exactly that : no waitlist, no private preview access request.</p>\n<h2 id=\"user-content-what_is_byoc\"></h2>\n<p>BYOC splits the control plane and data plane into separate VPCs.\"</p>\n<ul>\n<li><strong>ClickHouse-managed control plane</strong>: Runs in ClickHouse's own VPC. Handles orchestration, scaling, upgrades, monitoring, and billing. It never touches your query data.</li>\n<li><strong>Your data plane</strong>: Runs entirely inside your Google Cloud project. Your GKE cluster, ClickHouse servers, object storage (Google Cloud Storage), backups, and metrics all live within your account boundary.</li>\n</ul>\n<p>The control plane communicates with your environment over a Tailscale zero-trust tunnel -  outbound-only, encrypted, and scoped to orchestration traffic only. ClickHouse engineers with support access are restricted to system tables, with time-bound and audited sessions.</p>\n<p>The result: you get a fully managed service without giving up data residency.</p>\n<h2 id=\"user-content-why_google_cloud\"></h2>\n<p>Google Cloud is home to a significant share of enterprise data infrastructure. Organizations running BigQuery, Dataflow, and Pub/Sub pipelines naturally want their high-performance OLAP layer in the same environment - with the same IAM primitives, the same VPC controls, and the same compliance perimeter.</p>\n<p>BYOC on Google Cloud makes ClickHouse native to  that environment. Your service runs on GKE, stores data and backups in your GCS buckets, and connects to the rest of your Google Cloud workloads over private networking - no data crosses account or project boundaries.</p>\n<p>ClickHouse BYOC is already available across all public ClickHouse Cloud Google regions. Over time we will expand support to additional Google Cloud regions.</p>\n<h2 id=\"user-content-initial_set_up\"></h2>\n<p>Onboarding uses a three-step Terraform-based setup:</p>\n<p><strong>1. Account setup:</strong> Run a Terraform module that creates the IAM roles and trust permissions needed for the BYOC controller to manage infrastructure in your Google Cloud project. We follow least-privilege principles - the controller gets only what it needs to provision and maintain the cluster.</p>\n<p><strong>2. Infrastructure provisioning:</strong> In the ClickHouse BYOC console, select your Google Cloud region, configure your VPC CIDR range, and align availability zones. We recommend a dedicated Google Cloud project for BYOC - this gives you clean cost attribution and a clear resource isolation boundary.</p>\n<p><strong>3. Service creation:</strong> Specify a service name, select your BYOC environment and region, choose CPU/memory allocation, and configure replica count for high availability. Your GKE cluster, ClickHouse nodes, and monitoring stack are provisioned automatically.</p>\n<p>If you have custom networking requirements or want to integrate with an existing VPC, reach out to ClickHouse Support - we support customized onboarding for those configurations.</p>\n<h2 id=\"user-content-whats_included\"></h2>\n<p>BYOC on Google Cloud ships with the full set of capabilities you need to run production ClickHouse workloads:</p>\n<ul>\n<li><strong>SharedMergeTree</strong> for efficient distributed storage</li>\n<li><strong>Managed backups and restore</strong> : stored in your GCS buckets, never leaving your project</li>\n<li><strong>Vertical and horizontal scaling</strong> : adjust replica count and node size per workload</li>\n<li><strong>Auto Idling / Wake up</strong> : automatically idle services during quiet periods to reduce costs</li>\n<li><strong>Compute-compute separation</strong> via <a target=\"_blank\" href=\"https://clickhouse.com/blog/introducing-warehouses-compute-compute-separation-in-clickhouse-cloud\">Warehouses</a> - isolate different query workloads across dedicated compute groups</li>\n<li><strong>Prometheus / Grafana / AlertManager</strong> monitoring stack</li>\n<li><strong>Datadog integration</strong> for teams with centralized observability pipelines</li>\n<li><strong>VPC Peering and Private Service Connect</strong> for enterprise network configurations</li>\n</ul>\n<h2 id=\"user-content-upgrades_and_maintenance\"></h2>\n<p>ClickHouse handles both ClickHouse database upgrades and supporting infrastructure upgrades (Kubernetes operator, Istio, monitoring components) in the background via ArgoCD. Database upgrades follow a <a target=\"_blank\" href=\"https://clickhouse.com/blog/make-before-break-faster-scaling-mechanics-for-clickhouse-cloud\">make-before-break strategy</a>: updated replicas are added before old ones are removed, minimizing disruption. You can select Fast, Regular, or Slow release channels, with upgrades aligned to your configured maintenance window.</p></div>"
