This blog dives into the details and challenges of building such a product. For those of you who just want a working out-of-the-box CDC solution for ClickHouse, we are pleased to recommend Streamkap as a hosted service.</p>\n</blockquote>\n<p>We’re excited to announce our new ClickHouse connector for streaming CDC data into <a target=\"_blank\" href=\"https://clickhouse.com/\">ClickHouse</a> from databases such as PostgreSQL, MySQL, SQL Server, Oracle &amp; MongoDB.</p>\n<p>Streamkap recently switched to ClickHouse to process all of our logs and metrics in real-time after we found that other solutions failed to achieve the query performance we required. Upon adopting ClickHouse ourselves, we wished to start offering a ClickHouse CDC integration but found issues with the existing connectors available, so we set out to build a new connector that addresses these issues.</p>\n<p>In this post, we assume you’re familiar with the ClickHouse database and the concept of Change Data Capture (CDC), but if not, you can learn more by reading about <a target=\"_blank\" href=\"https://streamkap.com/blog/change-data-capture-for-streaming-etl\">Change Data Capture in Streaming</a>.</p>\n<p>We will dive into the challenges of building a CDC solution for ClickHouse and how we have addressed these, discussing how we handle schema evolution, data consistency, and snapshotting. Finally, we show this can all be achieved while maintaining a performant streaming pipeline.</p>\n<h2 id=\"technologies\"></h2>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/\">ClickHouse</a> is an open-source column-oriented database. A column-oriented structure means data is stored and retrieved by columns rather than by rows. ClickHouse has become the de-facto choice for building real-time applications due to its ability to ingest large volumes as well as materialize the data at write instead of at read time. This results in significantly faster queries, making ClickHouse suitable for serving real-time applications.</p>\n<p><a target=\"_blank\" href=\"https://streamkap.com/\">Streamkap</a> is a serverless streaming platform enabling real-time Change Data Capture (CDC) ingestion into ClickHouse. Under the hood, technologies such as <a target=\"_blank\" href=\"https://kafka.apache.org/\">Kafka</a>, <a target=\"_blank\" href=\"https://debezium.io/\">Debezium</a>, <a target=\"_blank\" href=\"https://flink.apache.org/\">Flink</a> are combined with production-grade connectors/pipelines.</p>\n<p>Here is an overview of how Streamkap streams from a database to ClickHouse.</p>\n<p><span><img alt=\"streamkap_architecture.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fstreamkap_architecture_19cc03bc3b.png&w=2048&q=75\"></span></p>\n<h2 id=\"challenges\"></h2>\n<p>When we first looked to stream CDC data to ClickHouse, we went looking for existing connectors we could use. After reviewing the official ClickHouse Kafka Connect connector, as well as others on the market, we soon realized that we would need to modify them extensively to support varying use cases. Realizing these connectors would need extensive modifications, we set about building our own solution. Below are some key requirements we needed to ensure were addressed before we could bring our solution to production.</p>\n<h3 id=\"data-typing\"></h3>\n<p>Data types were not well supported by existing solutions:</p>\n<ul>\n<li>Nested Struct</li>\n<li>Nested Array, arrays containing nested Struct</li>\n<li>Timestamp with microsecond precision</li>\n<li>Time with microsecond precision</li>\n<li>Date without time information (days since epoch)</li>\n<li>JSON transported as plain string fields</li>\n</ul>\n<h3 id=\"metadata\"></h3>\n<p>When dealing with CDC data, it’s helpful to add additional metadata columns such as timestamps and type of CDC record. This allows for simpler and more powerful post-ingestion transformations as well as diagnosing any issues in latency.</p>\n<h3 id=\"insert-upserts\"></h3>\n<p>At Streamkap we see an equal split of customers wishing to use inserts or upserts. Inserts being append-only mode and therefore maintaining a history of all changes, while upserts result in only the final data being visible (inserts + updates). While most companies are used to this ability with batch ETL, it is a new concept when combined with streaming ETL. Learn more at <a target=\"_blank\" href=\"https://streamkap.com/blog/batch-processing-vs-real-time-stream-processing\">Batch vs Real-Time Processing</a></p>\n<h3 id=\"schema-evolution\"></h3>\n<p>When a source table is changed, we need the destination table to be updated to handle this schema drift and not result in a broken pipeline.</p>\n<h3 id=\"semi-structured-data\"></h3>\n<p>Sources like MongoDB/Elasticsearch allow inconsistencies within complex nested record structures which need to be reconciled by the ingest pipeline prior to insertion into ClickHouse. For example:</p>\n<ul>\n<li>Date/Time represented as a number (sec/ms since epoch) in some records and as a string (ISO format) in other records</li>\n<li>Nested fields that are strings in some records and a more complex nested struct in other records</li>\n<li>Deeply nested complex semi-structured data usually needs preprocessing before insertion into ClickHouse, with mapping to the appropriate types e.g. Tuples, Nested.</li>\n</ul>\n<h2 id=\"our-approach\"></h2>\n<p>Now let’s dig into our connector and how we addressed each of these challenges.</p>\n<h3 id=\"data-types\"></h3>\n<p>We found the default approach was often to just insert data into ClickHouse as JSON and then transform the data post-loading.</p>\n<p>We’ve built-in support for the table:</p>\n<ul>\n<li><code>_streamkap_ts_ms</code>: CDC event timestamp</li>\n<li><code>_streamkap_deleted</code>: if the current CDC event is a delete update, d delete, r snapshot, t truncate)</li>\n</ul>\n<h3 id=\"inserts-upserts\"></h3>\n<p>The Streamkap connector supports two modes of data ingestion into ClickHouse: <strong>Inserts</strong> (append) and <strong>Upserts</strong>.</p>\n<p>Upsert mode is our connector's default mode and is used when ClickHouse tables are required to contain the latest version of the source data.</p>\n<h4 id=\"insert-append-mode\"></h4>\n<p>Insert mode results in every change being tracked and inserted as a new row in ClickHouse while delete events will be marked in ClickHouse as deleted using the meta value <code>_streamkap_deleted</code>.</p>\n<p>This is useful with larger volumes to keep latency low as well as maintain a history of changes.</p>\n<p>For example, Streamkap uses insert mode when collecting our metrics, as only immutable data is inserted.</p>\n<p>We then use <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/cascading-materialized-views\">Materialized Views</a> on top of the metrics table to create a number of aggregates for time series analysis upon ingestion. A suitable <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/ttl\">TTL</a> on this table is set so that ClickHouse handles the delete operations for us while providing enough historical data to investigate any issues or if we have to rebuild the Materialized Views for some reason.</p>\n<p>To use Insert (Append) mode, the ClickHouse engine <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree\">MergeTree</a> is used.</p>\n<p><span><img alt=\"appends_streamkap.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fappends_streamkap_6c1b60b712.png&w=2048&q=75\"></span></p>\n<h4 id=\"upsert-mode\"></h4>\n<p>Upserts are both inserts and updates combined. If there is a match on the primary key of the row, the value will be overwritten. Conversely, if there is no match, the event will be inserted.</p>\n<p>Upsert mode is implemented using ClickHouse's <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/replacingmergetree\">ReplacingMergeTree</a> engine.</p>\n<p>The ReplacingMergeTree engine de-duplicates data during periodic background merges based on the ordering key, allowing old records to be cleaned up. The asynchronous nature of this process means there could be a small window where you are left with older records in the view.
