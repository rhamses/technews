Just the Pandas code you (and your LLM) already know how to write, running on one of the fastest analytical engines in the world.</p>\n<h2 id=\"user-content-the-problem-with-eager-execution\"></h2>\n<p>Consider a typical Pandas workflow:</p>\n<div><pre><code><span><span>import</span> pandas <span>as</span> pd</span>\n<span></span>\n<span>df = pd.read_parquet(<span>\"users.parquet\"</span>)</span>\n<span>df = df[df[<span>\"age\"</span>] &gt; <span>30</span>]</span>\n<span>df = df.sort_values(<span>\"salary\"</span>, ascending=<span>False</span>)</span>\n<span>df = df.head(<span>100</span>)</span></code></pre></div>\n<p>Simple enough. But here's what actually happens under the hood:</p>\n<ol>\n<li><strong>The entire Parquet file is loaded into memory</strong> — depending on data types and compression, the in-memory representation can be significantly larger than the compressed on-disk size. For highly compressed string-heavy data, this inflation can reach 4x or more; for dense numeric columns, it may be closer to 1.5–2x.</li>\n<li>A full-table filter is applied, producing a second copy.</li>\n<li>A full sort is performed.</li>\n<li>Finally, only 100 rows are kept.</li>\n</ol>\n<p>Pandas executes each step eagerly and independently, with no global view of the pipeline. While <code>pd.read_parquet()</code> does support a <code>filters</code> parameter for row-group-level predicate pushdown (via PyArrow) and a <code>columns</code> parameter for column pruning, these optimizations require the user to explicitly specify them at read time — they aren't inferred from downstream operations. A chained pipeline like the one above won't benefit from them automatically. Every intermediate step materializes a new DataFrame in memory.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fchdb4_mar2026_image4_8ad20b9096.png&w=2048&q=75\"></span></p>\n<p>This is fine for small datasets on a laptop. Every call returns a lazy object instead of executing immediately.</p>\n<p><strong>Layer 2</strong> records these operations as a chain of <code>LazyOp</code> objects — filter, select, assign, apply, and more — without touching any data.</p>\n<p><strong>Layer 3</strong> waits for a natural trigger like <code>print()</code>, <code>len()</code>, or <code>.columns</code>, then hands the operation chain to the <code>QueryPlanner</code>, which also determines how to split the pipeline into segments and route each to the appropriate engine.</p>\n<p>Finally, <strong>Layer 4</strong> executes the plan, with each segment running on either the chDB (ClickHouse) engine or the Pandas engine, and cached DataFrames flowing between them via Python's <code>memoryview</code> to minimize data copying.</p>\n<p>Let's see this in action.</p>\n<h3 id=\"user-content-lazy-execution\"></h3>\n<p>Instead of running each operation immediately, Data Store records your Pandas-style operations as a lazy pipeline and only executes when you actually need results:</p>\n<div><pre><code><span><span>from</span> chdb <span>import</span> DataStore</span>\n<span></span>\n<span>ds = DataStore.from_file(<span>\"users.parquet\"</span>)</span>\n<span>ds = ds[ds[<span>\"age\"</span>] &gt; <span>30</span>]</span>\n<span>ds = ds.sort_values(<span>\"salary\"</span>, ascending=<span>False</span>)</span>\n<span>ds = ds.head(<span>100</span>)</span>\n<span></span>\n<span><span># Nothing has executed yet.</span></span>\n<span><span># Execution happens here — compiled to optimized SQL, run on ClickHouse:</span></span>\n<span><span>print</span>(ds)</span></code></pre></div>\n<p>At execution time, the full pipeline is compiled into ClickHouse SQL with optimizations like <strong>filter pushdown</strong>, <strong>column pruning</strong>, and <strong>limit propagation</strong>. One particularly interesting challenge is <strong>row ordering</strong>.</p>\n<p>ClickHouse is a massively parallel engine. When you read a file, multiple threads process different chunks simultaneously. Without an explicit <code>ORDER BY</code>, the result order is non-deterministic — whichever thread finishes first contributes its rows first. This is expected behavior for a database, but Pandas users expect <code>df.head(10)</code> to always return the <em>first</em> 10 rows from the source.</p>\n<p>Data Store preserves source ordering by default using internal row-ID tracking, ensuring that Pandas-style operations produce identical results regardless of ClickHouse's parallel execution. That said, some edge-case differences between ClickHouse and Pandas semantics are worth noting:</p>\n<ul>\n<li><strong>NaN vs NULL</strong>: Pandas uses <code>NaN</code> for missing floating-point values, while ClickHouse distinguishes between <code>NaN</code> and <code>NULL</code>. Data Store normalizes these where possible, but subtle differences may appear in operations that distinguish between the two.</li>\n<li><strong>String sorting</strong>: ClickHouse sorts strings in byte order (effectively UTF-8), which may differ from Pandas' default locale-sensitive sorting in certain edge cases.</li>\n<li><strong>Integer overflow</strong>: ClickHouse silently wraps on integer overflow, while Pandas (with NumPy backend) also wraps but may behave differently with nullable integer types.</li>\n</ul>\n<p>For the vast majority of data science workflows, these differences are invisible.
