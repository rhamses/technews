contentHtml: "<article><div><h2 id=\"user-content-the_shape_of_the_problem\"></h2>\n<p>A chatbot is one request and one response. An <strong>agent</strong> is a loop: it plans, calls a tool, reads the result, reasons, calls another tool, and repeats — typically <strong>5 to 20 tool calls per turn</strong>, very often <em>sequential</em>. A large share of those calls are data access: <em>recall what the user told me earlier, look up the recent events, join this against the catalog.</em></p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fch_DB_Local_Data_Engine_1_ad33555d2a.png&w=2048&q=75\"></span></p>\n<p>Two things happen when that data lives on the other side of a network:</p>\n<ol>\n<li><strong>Latency compounds.</strong> 50 ms of round-trip time times ten calls is half a second of dead air the user feels as \"the agent is slow\" — before the model has done any thinking. Multi-call turns are the fat tail that dominates an agent's p95 task time. <a target=\"_blank\" href=\"https://clickhouse.com/blog/chdb-agents-local-data-engine#sources\">[7]</a></li>\n<li><strong>Instability becomes a cost center.</strong> Networks jitter and occasionally fail. A single dropped packet triggers a TCP retransmit that adds 200 ms–1 s; a 0.1% packet-loss event alone has been measured to add ~2 s at p99.9. <a target=\"_blank\" href=\"https://clickhouse.com/blog/chdb-agents-local-data-engine#sources\">[1][3]</a> And in an agent, \"the query failed\" doesn't end there — it kicks off a retry loop that re-bills the whole context window, and then a detour. That is where the tokens go. <a target=\"_blank\" href=\"https://clickhouse.com/blog/chdb-agents-local-data-engine#sources\">[5][6]</a></li>\n</ol>\n<p>chDB attacks both at the root: it puts a full ClickHouse query engine <em>inside the agent's process</em>. The data layer travels with the agent, so insight latency is bounded by CPU, not by the network.</p>\n<p>This article lays out the three ways that matters — <strong>local agent memory</strong>, <strong>a federation hub</strong>, and <strong>stability/token savings</strong> — and backs the third with a first-principles argument plus a table of independent, real-world data.</p>\n<hr>\n<h2 id=\"user-content-1_chdb_as_local_agent_memory\"></h2>\n<p>Within a single session an agent hammers the same small working set: it revisits <em>today's</em> data, it recalls older data the moment the user references it, and it stores distilled preferences and decisions to act on later. Every one of those wants a fast, deterministic local query — not a trip to a warehouse.</p>\n<p>First, get clear on what memory is. Here is an all-too-familiar agent failure: <em>yesterday</em> it hit a constraint and worked out a fix that stuck; <em>today</em>, facing the same task, it reads only the prompt — not yesterday's fix — so it runs the failed plan again and burns tool calls on retries. The model isn't dumb — the right context just wasn't <strong>queryable at the moment it was needed</strong>.</p>\n<p>An agent's context is just a pile of data: instructions, working data, memory, eval history. \"Memory\" was never about stuffing more into the prompt — it is about <strong>pulling the few rows that matter <em>right now</em> with a single query</strong>. Recall is a query, not a bigger prompt.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fch_DB_Local_Data_Engine_2_eb65d031bc.jpg&w=2048&q=75\"></span></p>\n<p>chDB is a good fit because it inherits the <strong>ClickHouse kernel</strong>, which natively handles, in one engine:</p>\n<ul>\n<li><strong>Structured data</strong>, <strong>time-series</strong>, and <strong>vector storage + vector search</strong>, plus inverted indexes for text.</li>\n<li>Pair that with a <strong>local embedding model</strong> (here, Alibaba's Qwen) and chDB's purely local storage, and you have an efficient, fully on-box memory: embed and recall without anything leaving the machine.</li>\n</ul>\n<p>This is the crux of \"why a database, not a vector store\": <strong>vector search is just an index; agent memory is the whole database around it.</strong> SQLite holds small state but has no columnar scans, no vectors, and can't read remote files; Pandas is great in memory but dies past RAM and can't query files you never loaded; a pure vector DB only does similarity — it can't filter + JOIN + aggregate + audit in the <em>same query</em>. Pulling out \"the few memories that matter now\" needs exactly that union of capabilities.</p>\n<p><strong>Archive the raw, search the compressed.</strong> The industry consensus is to keep the rawest data as an archive — like the deep stacks of a library: rarely read, but there for the moment the agent needs to go dig. ClickHouse compresses raw data <em>and searches on the compressed data efficiently</em>, so archiving costs almost nothing in retrieval speed.</p>\n<p>That unlocks a tidy ingestion pattern. An agent produces memories as a continuous trickle of small batches — which is exactly the workload that <em>wrecks</em> an online OLAP warehouse if you write it directly. Instead:</p>\n<div><pre><code><span><span># Hot memory lives locally, written at trickle speed with no warehouse pressure</span></span>\n<span>sess = chdb.session.Session(<span>\"/tmp/agent\"</span>)</span>\n<span>sess.query(<span>\"INSERT INTO memory VALUES (...)\"</span>)   <span># cheap, local, no network</span></span>\n<span></span>\n<span><span># Then sync to the warehouse on a sane cadence — hourly / daily archival</span></span>\n<span><span># (relieving the online warehouse from a storm of tiny writes)</span></span></code></pre></div>\n<p><strong>Memory should be a history — so don't <em>update</em> it, <em>append</em> to it.</strong> Agent memory has a lifecycle: <em>remember</em> (an explicit decision) → <em>recall</em> (similarity + filter) → <em>conflict</em> (new information that's similar to, but differs from, an old belief) → <em>revise</em> (the better belief wins). Say the old memory is \"this repo uses Poetry,\" and it later becomes \"this repo standardizes on uv\" — you usually want not just the current answer, but <strong>how that belief evolved</strong>.</p>\n<p><span><img alt=\"chDB Local Data Engine Revised (1).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fch_DB_Local_Data_Engine_Revised_1_f25f27ce8e.png&w=2048&q=75\"></span></p>\n<p>To keep that revision trail intact, the right move is the plainest <strong>MergeTree + append-only</strong>: every revision is a new immutable row with a <code>version</code> (or timestamp) column; deletes are a soft <code>is_deleted</code> flag, not a real delete. The belief's evolution is preserved in full, and append-only happens to be ClickHouse's fastest, zero-write-amplification path.</p>\n<div><pre><code><span><span>CREATE TABLE</span> Add a few <code>WHERE</code> / <code>JOIN</code> lines. And if you read the current state very often and don't want to scan history every time, the cleanest approach is a Materialized View that projects the current state into a ReplacingMergeTree mirror table: <strong>the base table (MergeTree) keeps the full history for audit and retrospection, while the mirror serves only the hot-path current state</strong> — far cleaner than forcing one engine to do both.</p>\n<p><strong>Memory ≈ Observability ≈ History.</strong> Here is the elegant part. The data an agent keeps <em>for memory</em> overlaps heavily with what an observability stack keeps. With ClickHouse's acquisition of <strong>Langfuse</strong> (LLM observability), chDB can serve all three locally — observability traces, agent memory, and conversation history — as a <em>single query surface</em>. Three concepts collapse into one, and on serverless pricing that becomes a genuinely clever architecture.</p>\n<p>And the three are isomorphic by nature: an observability trace is never <em>rewritten</em> — it is append-only by construction, the same shape as the memory model above. Columnar + append-only both dodges the write amplification of in-place UPDATEs and keeps the full history as an audit trail. Langfuse choosing to build LLM observability on ClickHouse is a sideways confirmation of exactly this.</p>\n<p><strong>This pattern is already packaged as open source.</strong> The whole thing — lifecycle, recall, local-first — is open-sourced as <a target=\"_blank\" href=\"https://github.com/auxten/clickmem\"><code>auxten/clickmem</code></a> (built on chDB): create a memories table → write explicit decisions → recall with \"similarity + filter\" → evaluate which memory actually helped; embeddings run locally with <code>Qwen/Qwen3-Embedding-0.6B</code>, nothing leaving the box. Want to build the core yourself? Use it as a template.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fch_DB_Local_Data_Engine_4_3b2028419a.jpg&w=2048&q=75\"></span></p>\n<hr>\n<h2 id=\"user-content-2_a_federation_hub_data_access_becomes_a_function_call\"></h2>\n<p>chDB inherits ClickHouse's support for <strong>80+ data formats</strong> (CSV — including dirty CSV with schema sniffing — Parquet, ORC, JSON, Arrow, and more) and a wide range of access paths: <strong>local files, HTTP/HTTPS, S3/GCS/Azure, FTP, HDFS</strong>, even a CSV inside a zip behind a URL. It just reads them.</p>\n<p>That makes chDB a <strong>data federation hub</strong>: one SQL statement can join a local file, a remote ClickHouse table, an in-process Pandas DataFrame, and a third-party database (MySQL, PostgreSQL, MongoDB, Redis) — each treated as a table.</p>\n<div><pre><code><span><span># One query. Pandas is the lingua franca of Python data science — Spark and most modern dataframe libraries were shaped by it — and LLMs write it extremely well. So an agent can express local + remote filtering and shaping <em>in the idiom it is best at</em>, and chDB compiles it down to the optimized engine.</li>\n<li><strong>SQL is declarative — it describes intent, not mechanism.</strong> That is arguably <em>the</em> reason SQL has survived for decades: you say <em>what</em> you want, not <em>how</em> to compute it. ClickHouse's extensions follow the same philosophy. The payoff for agents is focus: the agent spends its tokens on <em>business intent</em>, not on hand-writing brittle ETL and data-plumbing code.</li>\n</ul>\n<hr>\n<h2 id=\"user-content-3_stability_and_token_optimization_the_part_that_matters_most\"></h2>\n<p>Localizing data removes network uncertainty. A local query has no wire to traverse, so its return is fast and — the word that matters — <strong>stable</strong>. And stability is not merely a latency nicety. In an agent loop, <strong>stability is a token problem.</strong></p>\n<h3 id=\"user-content-why_a_flaky_data_call_costs_tokens_not_just_milliseconds\"></h3>\n<p>When a tool call fails, an agent does not shrug it off the way a microservice does. The documented behavior is:</p>\n<ol>\n<li>The model receives the error and <strong>retries</strong> — and in an agent loop, <em>every retry re-sends the full conversation context to the LLM</em>. A retry costs a whole context window, not one cheap HTTP round-trip. <a target=\"_blank\" href=\"https://clickhouse.com/blog/chdb-agents-local-data-engine#sources\">[6]</a></li>\n<li>If retries keep failing, the model \"gets creative\" and <strong>takes a detour</strong> — trying a different query, a different tool, a different plan. More tokens, more latency, for data it already needed.</li>\n</ol>\n<p>In production traces this waste is pervasive and usually invisible, because the turn eventually <em>succeeds</em> — the cost only shows up on the bill. <a target=\"_blank\" href=\"https://clickhouse.com/blog/chdb-agents-local-data-engine#sources\">[5]</a></p>\n<h3 id=\"user-content-a_concrete_detour\"></h3>\n<blockquote>\n<p>A customer-support agent is mid-session and needs the user's recent preference history to answer. It issues a query to the warehouse. The warehouse is briefly busy — a <code>Server busy</code>, a disk stall, a dropped packet. The model gets the error, <strong>re-sends its 14k-token context</strong> and retries. Still slow. It retries again. Then it \"reroutes\": maybe it queries a different table, or asks for a broader slice and filters in its own head. Several thousand tokens and several seconds later, it has the answer it could have had instantly.</p>\n<p>The same agent backed by chDB calls <code>sess.query(...)</code>, gets the rows in <strong>sub-millisecond time, deterministically, every single time</strong>, and never enters the retry/detour spiral at all.</p>\n</blockquote>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fch_DB_Local_Data_Engine_5_2e7180206b.jpg&w=2048&q=75\"></span></p>\n<h3 id=\"user-content-think_it_through_why_local_is_necessarily_more_stable\"></h3>\n<p><strong>A local query is a function call.</strong> Its latency distribution is a tall, narrow spike set by CPU and memory bandwidth — no RTT, no jitter, no packet loss, no server-side queueing. Its p50 and p99 are practically the same number. <strong>Determinism</strong> is the point: the same speed every time.</p>\n<p><strong>A remote query, however fast the server, still has to cross the wire.</strong> Base RTT + jitter + the occasional TCP retransmit + server-side contention stack up, which means its p99/p999 is set not by compute but by the worst network event. In other words, the remote tail is <strong>structural</strong> — you can't optimize it away, because it isn't in your process at all.</p>\n<p><strong>And the killer is compounding.</strong> Let the success probability of a single call be <code>(1 − p)</code>. Then a turn of N <em>sequential</em> calls all succeeds with probability <code>(1 − p)^N</code>. At N = 10, even with p of just 2%, about <strong>18%</strong> of turns hit at least one failure — which lines up neatly with the field observation that a \"2% tool error rate → ~20% agent failure.\" <a target=\"_blank\" href=\"https://clickhouse.com/blog/chdb-agents-local-data-engine#sources\">[4]</a> And each failure isn't a cheap HTTP retry; it's a retry that <strong>re-bills the entire context window</strong>, usually followed by a detour. <a target=\"_blank\" href=\"https://clickhouse.com/blog/chdb-agents-local-data-engine#sources\">[6]</a></p>\n<p>So the causal chain is clear: <strong>network instability → token-priced retries → even-more-token detours</strong> — and where it finally shows up is the invoice, not the latency chart. Localizing the hot path cuts the chain at its source.</p>\n<h3 id=\"user-content-this_isnt_theory_it_shows_up_in_the_wild\"></h3>\n<p>Every link in that argument is grounded in independent, public engineering write-ups. Memory and hot data that get queried over and over within a session are exactly the things that should be <strong>local</strong>.</p>\n<hr>\n<h2 id=\"user-content-4_bringing_it_to_aws_chdb_aws_lambda_microvms\"></h2>\n<p>The architecture gets concrete here — and it is not just an idea. <strong>chDB is the only data-infrastructure launch partner invited for <a target=\"_blank\" href=\"https://aws.amazon.com/lambda/lambda-microvms/\">AWS Lambda MicroVMs</a>.</strong> <a target=\"_blank\" href=\"https://clickhouse.com/blog/chdb-agents-local-data-engine#sources\">[9]</a></p>\n<p><strong>What Lambda MicroVMs is.</strong> It is a new serverless compute primitive that fuses three things: VM-level isolation, near-instant launch and resume, and state persistence across interactions. It is built on the same <strong>Firecracker</strong> virtualization that powers <strong>15 trillion+</strong> Lambda invocations a month, purpose-built to run user- or AI-generated code. You start a MicroVM, connect over a <strong>dedicated HTTPS endpoint</strong>, and begin executing code — each MicroVM has its own kernel, memory, and disk state, retained for up to <strong>8 hours</strong>, automatically <strong>suspended</strong> when idle and <strong>resumed</strong> on demand, with <strong>no charge while suspended</strong>. <a target=\"_blank\" href=\"https://clickhouse.com/blog/chdb-agents-local-data-engine#sources\">[9]</a></p>\n<p><strong>Why it and chDB are a perfect match.</strong> This is exactly where the article's three pillars land in the cloud:</p>\n<ul>\n<li><strong>One private chDB per isolated workload.</strong> Firecracker hardware isolation + snapshot-based fast starts + suspend/resume let every MicroVM carry its own <em>private</em> chDB engine — hot from the first millisecond, billed only while it actually runs. There's no shared database to scale, and nothing for a thousand agents to overload at once.</li>\n<li><strong>Small questions in, small answers out.</strong> chDB pushes compute down to the data and returns only small results — a natural fit for that dedicated endpoint: the heavy lifting happens inside the VM, and all that crosses the endpoint is a small request and a small answer.</li>\n<li><strong>\"Thinking in place,\" with zero network round-trips.</strong> Inside the MicroVM, the agent and chDB share one process; memory, federated SQL, and vector search all happen at CPU speed — the \"network instability → token waste\" chain from Section 3 is physically severed here.</li>\n</ul>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fch_DB_Local_Data_Engine_6_c14609e44a.jpg&w=2048&q=75\"></span></p>\n<p><strong>We're building a set of reference architectures on this combination:</strong></p>\n<ul>\n<li><strong>A federated query hub</strong> — inside a single MicroVM, one query joins local data, S3, a CDN, and Postgres.</li>\n<li><strong>Isolated CI/CD runners</strong> — every test gets a clean chDB, with no shared server to drag down.</li>\n<li><strong>On-demand sandboxes</strong> — an AI agent can spend hours reproducing a bug inside a disposable VM.</li>\n<li><strong>A per-session \"agent brain\"</strong> — chDB is the local memory and federation layer the agent thinks with, suspended and resumed right alongside the user's session.</li>\n</ul>\n<p><strong>See it running.</strong> <a target=\"_blank\" href=\"https://github.com/nklmish/chdb-lambda-microvm-demo\"><code>nklmish/chdb-lambda-microvm-demo</code></a> is a worked example of exactly this — a natural-language <em>NYC Taxi analytics agent</em> that carries its own in-process chDB inside a Lambda MicroVM: local append-only memory, single-SQL federation out to S3 / PostgreSQL / ClickHouse Cloud, and sub-millisecond recall, with each MicroVM snapshot-hot and billed only while it runs.</p>\n<p>In code, stateless and stateful are each just two lines:</p>\n<div><pre><code><span><span># Stateless: one-shot federated query — an ad-hoc agent tool call, or ETL inside the MicroVM</span></span>\n<span>chdb.query(<span>\"SELECT ...
