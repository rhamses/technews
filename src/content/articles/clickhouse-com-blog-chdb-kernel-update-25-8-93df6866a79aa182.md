Recently, we completed a major kernel upgrade (<a target=\"_blank\" href=\"https://github.com/chdb-io/chdb/pull/383\">PR #383</a>), upgrading the ClickHouse kernel from v25.5 to v25.8.2.29. Its architecture can be summarized in the following layers:</p>\n<p><span><img alt=\"Image 511556138 2776x2790.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FImage_511556138_2776x2790_1bbb194323.jpg&w=2048&q=75\"></span></p>\n<p>Unlike the traditional client/server architecture, chDB has no independent server process:</p>\n<ul>\n<li><strong>Zero-copy data passing</strong>: Uses Python <code>memoryview</code> and C++ <code>WriteBufferFromVector</code> for zero-copy data transfer</li>\n<li><strong>Embedded design</strong>: ClickHouse engine runs directly in the Python process, avoiding inter-process communication overhead</li>\n<li><strong>Multi-format support</strong>: Native support for 60+ formats including Parquet, CSV, JSON, Arrow, ORC</li>\n</ul>\n<h3 id=\"1-2-code-structure\"></h3>\n<p>chDB's code structure is inherited from ClickHouse but <code>libpybind11nonlimitedapi_chdb_3.8.so</code>. While this design seems complex, it solves the core problem of multi-Python version compatibility.</p>\n<h3 id=\"2-1-multi-python-version-compatibility-challenge\"></h3>\n<p>The Python ecosystem has multiple active versions (<code>3.8</code>, <code>3.9</code>, <code>3.10</code>, <code>3.11</code>, <code>3.12</code>, <code>3.13</code>), each with subtle differences in their C API. Traditional Python C extensions require compiling independent binaries for each Python version, which is unacceptable for a massive project like chDB (single .so file exceeds 120MB after stripping and compression).</p>\n<h3 id=\"2-2-dual-dynamic-library-architecture\"></h3>\n<p>chDB adopts a clever separation design:</p>\n<p><strong>_chdb.abi3.so (Stable ABI layer)</strong></p>\n<ul>\n<li>Uses Python Limited API</li>\n<li>Only depends on Python's stable ABI interface</li>\n<li>Can be reused across Python versions</li>\n<li>Size: ~120MB (contains the complete ClickHouse engine)</li>\n<li>Includes: ClickHouse core, query execution engine, format parsers</li>\n</ul>\n<p><strong>libpybind11nonlimitedapi_chdb_3.x.so (Version-specific layer)</strong></p>\n<ul>\n<li>Uses complete Python C API (Non-limited API)</li>\n<li>Needs separate compilation for each Python version</li>\n<li>Size: ~10-20MB</li>\n<li>Contains: pybind11 binding code, Python object conversion</li>\n</ul>\n<p>The build script <code>build_pybind11.sh</code> handles building the <code>libpybind11</code> library for each Python version:</p>\n<div><pre><code><span><span># Build independent binding libraries for Python 3.8-3.13</span></span>\n<span><span>for</span> version <span>in</span> 3.8 3.9 3.10 3.11 3.12 3.13; <span>do</span></span>\n<span>    cmake -DPYBIND11_NONLIMITEDAPI_PYTHON_HEADERS_VERSION=<span>${version}</span> ..</span>\n<span>    ninja pybind11nonlimitedapi_chdb_<span>${version}</span></span>\n<span><span>done</span></span></code></pre></div>\n<p>Advantages of this design:</p>\n<ol>\n<li><strong>Storage optimization</strong>: 120MB core engine downloaded once, each Python version only needs ~15MB extra</li>\n<li><strong>Build efficiency</strong>: Core engine compiled once (takes hours), version-specific layer builds quickly (minutes)</li>\n<li><strong>Maintenance simplification</strong>: Unified core logic, only binding layer needs adaptation for different Python versions</li>\n</ol>\n<h3 id=\"2-3-jemalloc-and-memory-management-challenges\"></h3>\n<p>However, this design also brings new challenges. Referring to <a target=\"_blank\" href=\"https://auxten.com/the-birth-of-chdb/\">The birth of chDB</a>, we encountered serious memory management issues during early development.</p>\n<h3 id=\"2-3-1-problem-discovery-and-nature\"></h3>\n<p><strong>Problem scenario</strong>:</p>\n<p>When integrating the Python extension, chDB frequently encountered segmentation faults. Core dump analysis showed crashes occurring during memory deallocation:</p>\n<div><pre><code><span>Program received signal SIGSEGV, Segmentation fault.</span>\n<span><span>0x00007ffff7a9e123</span> <span>in</span> je_free () from /path/to/_chdb<span>.</span>abi3<span>.</span>so</span>\n<span>(gdb) <span>bt</span></span>\n<span>#<span>0</span>  je_free (<span>ptr</span>=<span>0x7fffe8001000</span>)</span>\n<span>#<span>1</span>  __wrap_free (<span>ptr</span>=<span>0x7fffe8001000</span>) <span>at</span> AllocationInterceptors<span>.</span>cpp:<span>451</span></span>\n<span>#<span>2</span>  <span>0x00007ffff7e8a456</span> <span>in</span> PyMem_Free (<span>ptr</span>=<span>0x7fffe8001000</span>)</span>\n<span>#<span>3</span>  <span>0x00007ffff7dab234</span> <span>in</span> list_dealloc ()</span></code></pre></div>\n<p><strong>Deep root cause analysis</strong>:</p>\n<p>This is a classic <strong>cross-boundary memory management problem</strong>:</p>\n<p><span><img alt=\"Image from GitHub (3).jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FImage_from_Git_Hub_3_156b54b340.jpg&w=2048&q=75\"></span></p>\n<p><strong>Root cause</strong>:</p>\n<p>The C/C++ memory management rule: <strong>whoever allocates, deallocates, and must use the same allocator</strong>. Mixing different memory allocators leads to:</p>\n<ol>\n<li><strong>Metadata corruption</strong>: jemalloc tries to find its own metadata before glibc-allocated memory blocks, reading random data</li>\n<li><strong>Heap structure destruction</strong>: Different allocators have completely different heap management structures, cross-freeing destroys internal data structures</li>\n<li><strong>Undefined behavior</strong>: Best case is immediate crash, worst case is silently corrupting data leading to subsequent strange errors</li>\n</ol>\n<p><strong>Common trigger scenarios</strong>:</p>\n<div><pre><code><span><span>// Scenario 1: Objects returned from Python C API</span></span>\n<span>PyObject* obj = <span>PyList_New</span>(<span>10</span>);  <span>// Python uses malloc</span></span>\n<span><span>// ... used in C++</span></span>\n<span><span>delete</span> obj;  <span>// chDB's operator delete uses je_free → crash!</span></span>\n<span></span>\n<span><span>// Scenario 2: Memory allocated by glibc functions</span></span>\n<span><span>char</span>* cwd = <span>getcwd</span>(<span>NULL</span>, <span>0</span>);  <span>// glibc internally uses malloc</span></span>\n<span><span>// ...</span></span>\n<span><span>free</span>(cwd);  <span>// wrapped to je_free → crash!</span></span>\n<span></span>\n<span><span>// Scenario 3: Third-party libraries (e.g., libhdfs)</span></span>\n<span>hdfsFile file = <span>hdfsOpenFile</span>(...);  <span>// libhdfs uses system malloc</span></span>\n<span><span>hdfsCloseFile</span>(fs, file);  <span>// internally calls free, wrapped → crash!</span></span></code></pre></div>\n<h3 id=\"2-3-2-limitations-of-traditional-solutions\"></h3>\n<p><strong>Solution 1: Completely disable <code>jemalloc</code></strong></p>\n<div><pre><code><span>-DENABLE_JEMALLOC=0</span></code></pre></div>\n<ul>\n<li>❌ <strong>Performance loss</strong>: ClickHouse has extensive <code>jemalloc</code> optimizations, disabling it reduces performance by 20-30%</li>\n</ul>\n<p><strong>Solution 2: LD_PRELOAD global replacement</strong></p>\n<div><pre><code><span>LD_PRELOAD=/usr/lib/libjemalloc.so python chdb_example.py</span></code></pre></div>\n<p>Make the entire process (including Python interpreter) use <code>jemalloc</code> through <code>LD_PRELOAD</code>.</p>\n<ul>\n<li>❌ <strong>Distribution difficulty</strong>: Users must run in specific environments</li>\n</ul>\n<h3 id=\"2-3-3-chdb-s-solution\"></h3>\n<p>chDB adopts a <strong>runtime memory source detection + smart routing</strong> approach, balancing performance and compatibility. The core of this solution is using the <strong>linker's <code>--wrap</code> mechanism</strong> to intercept all memory allocation/deallocation calls and dynamically determine memory source at runtime.</p>\n<p><strong>Technical foundation: Linker's wrap mechanism</strong></p>\n<p>The linker provides the <code>--wrap</code> option to intercept symbol calls at link time:</p>\n<div><pre><code><span><span># Add wrap parameters at link functions</span></span></code></pre></div>\n<p>How it works:</p>\n<div><pre><code><span>Application code calls:  free(ptr)</span>\n<span>      ↓</span>\n<span>Linker redirects:  __wrap_free(ptr)  ← Our implementation</span>\n<span>      ↓</span>\n<span>Callback when needed:  __real_free(ptr)  ← Original glibc implementation</span></code></pre></div>\n<p>This way, all calls to <code>free()</code> are redirected to our own implementation of <code>__wrap_free()</code>, where we can insert checking logic and call the original <code>__real_free()</code> when needed.</p>\n<p><strong>Key prerequisite: Disable jemalloc symbol renaming</strong></p>\n<p>For this solution to work, chDB needs to distinguish between <code>free()</code> and <code>je_free()</code>, so we must **disable ClickHouse's original <code>jemalloc</code> symbol renaming feature<code>** and preserve the original </code>jemalloc` symbol names:</p>\n<div><pre><code><span><span># ClickHouse default config: Rename jemalloc symbols</span></span>\n<span><span>--with-jemalloc-prefix</span>=je_</span>\n<span><span># Effect: malloc → je_malloc, free → je_free</span></span>\n<span></span>\n<span><span># chDB config: Disable renaming</span></span>\n<span><span>-DJEMALLOC_PREFIX</span>=<span>\"\"</span></span>\n<span><span># Effect: Preserve je_malloc, je_free and other original symbol names</span></span></code></pre></div>\n<p>This allows us to:</p>\n<ul>\n<li>Detect memory source in <code>__wrap_free()</code></li>\n<li>Call <code>je_free(ptr)</code> for jemalloc-allocated memory</li>\n<li>Call <code>__real_free(ptr)</code> for glibc-allocated memory (original glibc free)</li>\n</ul>\n<p><strong>Core mechanism: Memory allocator fingerprint                      &amp;arena_ind, &amp;sz,     <span>// Output: arena index</span></span>\n<span>                         &amp;ptr, <span>sizeof</span>(ptr));  <span>// Input: memory pointer</span></span>\n<span></span>\n<span>    <span>// arena_ind == 0: special value, indicates memory doesn't belong to jemalloc</span></span>\n<span>    <span>// arena_ind &gt; 0:  memory belongs function</strong>:</p>\n<div><pre><code><span><span><span>inline</span> ALWAYS_INLINE <span>bool</span> <span>tryFreeNonJemallocMemory</span><span>(<span>void</span> * ptr)</span> </span>{</span>\n<span>    <span>if</span> (<span>unlikely</span>(ptr == <span>nullptr</span>))</span>\n<span>        <span>return</span> <span>true</span>;</span>\n<span></span>\n<span>    <span>// (<span>tryFreeNonJemallocMemory</span>(ptr))</span>\n<span>        <span>return</span>;</span>\n<span></span>\n<span>    <span>// Use jemalloc to release</span></span>\n<span>    AllocationTrace jemalloc's <code>arenas.lookup</code>: <strong>when receiving memory pointers not allocated by jemalloc, the memory detector crashes</strong>.</p>\n<p>This isn't a bug, but rather <code>jemalloc's</code> original design—it assumes incoming pointers are all valid heap memory pointers. However, for chDB's mixed memory allocation scenario, we need <code>arenas.lookup</code> to safely handle arbitrary pointers. To address this, @Auxten Wang  submitted a patch to the jemalloc project to enhance boundary checking:</p>\n<div><pre><code><span><span>// Before: Assumes pointer is valid, directly accesses metadata → invalid pointer crashes</span></span>\n<span><span>// After: First checks pointer validity, safely returns result</span></span>\n<span><span>if</span> (ptr == <span>NULL</span> || !isValidPointer(ptr)) {</span>\n<span>    <span>return</span> EINVAL;  <span>// Return error code instead of crashing</span></span>\n<span>}</span></code></pre></div>\n<p>This improvement has been accepted by <code>jemalloc</code> officially and merged into the main branch, making @Auxten Wang  an official <code>jemalloc</code> contributor.</p>\n<h2 id=\"3-kernel-upgrade-wrap-mechanism-changes-and-adaptation\"></h2>\n<h3 id=\"3-1-clickhouse-new-version-wrap-mechanism-conflict\"></h3>\n<p>After upgrading to v25.8.2.29, we encountered an issue: <strong>ClickHouse's new version also started using the wrap mechanism to intercept memory allocation and deallocation functions for more precise memory tracking</strong>.</p>\n<p>This directly conflicted with chDB's existing wrap approach:</p>\n<div><pre><code><span>chDB's wrap (introduced in Section 2):</span>\n<span>  free(ptr) → __wrap_free() (chDB implementation)</span>\n<span>            → Check memory source (je_mallctl)</span>\n<span>            → Route to je_free or __real_free</span>\n<span></span>\n<span>ClickHouse new version's wrap:</span>\n<span>  free(ptr) → __wrap_free() (ClickHouse implementation)</span>\n<span>            → Update MemoryTracker statistics</span>\n<span>            → Call je_free</span>\n<span></span>\n<span>Conflict:</span>\n<span>  Two __wrap_free implementations cannot coexist!</span></code></pre></div>\n<p><strong>Root cause of conflict</strong>:</p>\n<p>The linker's wrap mechanism only allows one wrap implementation per symbol. When both ClickHouse kernel and chDB's binding layer try to define <code>__wrap_free</code> and other functions, the linker cannot decide which one to use.</p>\n<h3 implementation:</p>\n<p><strong>Solution approach</strong>:</p>\n<ol>\n<li><strong>Keep chDB's wrap implementation</strong> as the final intercept point</li>\n<li><strong>Call ClickHouse's MemoryTracker within chDB's wrap</strong></li>\n<li><strong>Decide whether to check memory source based on scenario</strong></li>\n</ol>\n<p><strong>Final implementation effect</strong>:</p>\n<p>Fused <code>__wrap_free</code> implementation:</p>\n<div><pre><code><span><span>extern</span> <span>\"C\"</span> <span>void</span> __wrap_free(<span>void</span> * ptr) <span>// (<span>tryFreeNonJemallocMemory</span>(ptr))</span>\n<span>        <span>return</span>;  <span>// Already handled glibc-allocated memory via __real_free</span></span>\n<span><span>#<span>endif</span></span></span>\n<span>    <span>// ClickHouse logic: Update MemoryTracker statistics</span></span>\n<span>    <span>size_t</span> actual_size <span>je_free</span>(ptr);</span>\n<span><span>#<span>else</span></span></span>\n<span>    <span>// If jemalloc not enabled, use system free</span></span>\n<span> <code>tryFreeNonJemallocMemoryConditional</code></li>\n<li><strong><code>_chdb.abi3.so</code> uses <code>jemalloc</code></strong>: Goes through normal MemoryTracker and <code>jemalloc</code> release
