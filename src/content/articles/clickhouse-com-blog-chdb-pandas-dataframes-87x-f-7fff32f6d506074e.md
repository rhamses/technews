Most problems arose from performance issues when interacting between C++ and Python.</p>\n<p>For example, when reading in-memory Pandas DataFrames in chDB, it is inevitable to call parts of CPython (the C implementation of Python, which is also the mainstream Python implementation). This leads to two significant challenges: the GIL and Object Reference Counting.</p>\n<h3 id=\"fly-with-gil\"></h3>\n<p>Due to the existence of the Python GIL (Global Interpreter Lock), any CPython function call requires acquiring the GIL first. If the GIL’s granularity is too large, it will directly cause ClickHouse’s multi-threaded engine to degrade into serial execution under the GIL’s constraints; if the GIL granularity is too small, frequent lock contention between threads will occur, which might even make the execution slower than a single-threaded program.</p>\n<blockquote>\n<p>In CPython, the <strong>global interpreter lock</strong>, or <strong>GIL</strong>, is a mutex that protects access to Python objects, preventing multiple threads from executing Python bytecodes at once. The GIL prevents race conditions and ensures thread safety. A nice explanation of <a target=\"_blank\" href=\"https://python.land/python-concurrency/the-python-gil\">how the Python GIL helps in these areas can be found here</a>. In short, this mutex is necessary mainly because CPython's memory management is not thread-safe.</p>\n<p>--- <a target=\"_blank\" href=\"https://wiki.python.org/moin/GlobalInterpreterLock\">https://wiki.python.org/moin/GlobalInterpreterLock</a></p>\n</blockquote>\n<h3 id=\"avoid-ref-counting\"></h3>\n<p>Python has automatic garbage collection, which makes it very easy to write code in Python. However, if you accidentally reference an existing Python object in memory or create a new one, you must control the reference counter; otherwise, it may lead to double-free errors or memory leaks.</p>\n<p>Therefore, for chDB, the only viable approach is to avoid calling CPython API functions to read CPython objects as much as possible. Does this sound crazy?!</p>\n<p>Let me briefly explain what we did to make chDB one of the fastest SQL engines on Pandas DataFrame despite Python dragging its feet.</p>\n<h2 id=\"performance-optimizations\"></h2>\n<p>At the start of the blog post, we mentioned that chDB v1 required at least four extra serialization and deserialization steps, which resulted in every query in ClickBench taking over 30 seconds.</p>\n<p>The first optimization was to reduce this overhead and read Python objects directly. This dramatically improved the time taken by most of the ClickBench queries. For the most time-consuming Q23 query, the time was reduced by nearly four times to 8.6 seconds.</p>\n<p><span><img alt=\"7_Getting to parity (1).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F7_Getting_to_parity_1_e8fb586ab5.png&w=2048&q=75\"></span></p>\n<p>Still, we wanted to make it even faster to maintain ClickHouse’s performance despite the presence of Python’s GIL and GC. We managed to achieve this by doing the following things:</p>\n<ol>\n<li>Minimized the number of CPython API function calls. When unavoidable, we handled them in a concentrated manner to avoid calling any CPython functions after the pipeline construction was complete and started running.</li>\n<li>Batched data copying as much as possible, utilizing ClickHouse’s SIMD-optimized memcpy.</li>\n<li>Rewrote the Python string encoding and decoding logic in C++.</li>\n</ol>\n<p>The last point might be a bit hard to understand, so let me elaborate:</p>\n<h3 id=\"python-string-encoding\"></h3>\n<p>Due to historical reasons, the data structure of Python’s str is extremely complex. It can be stored in UTF-8, UTF-16, UTF-32, or even more obscure encodings. When users further manipulate the str, Python’s runtime may convert them all to UTF-8 encoding and possibly cache them in the str structure.</p>\n<p>This results in many cases that need to be handled. As mentioned, any call to a CPython function requires acquiring the GIL first. If you use Python’s internal implementation to convert to UTF-8, only one thread can work at a time. So, out of necessity, we re-implemented the str encoding conversion logic in C++.</p>\n<p>Our efforts directly led to another significant performance leap for Q23, reducing the time from 8.6 seconds to 0.56 seconds—a 15x improvement! ????????????</p>\n<p>Now that we’ve addressed these issues, we thought we should see how well chDB performs against DuckDB, a popular in-process analytics database.</p>\n<p>The chart below shows the two databases' performance when querying DataFrames that contain 10 million rows of ClickBench data:</p>\n<p><span><img alt=\"8_SQL on Dataframe benchmak results after improvements (1).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F8_SQL_on_Dataframe_benchmak_results_after_improvements_1_aa4d1adc6f.png&w=2048&q=75\"></span></p>\n<p>Note: 1.
