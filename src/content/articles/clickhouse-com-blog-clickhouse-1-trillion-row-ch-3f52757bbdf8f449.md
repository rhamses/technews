contentHtml: "<div><p>Last month, we responded officially to the hugely successful 1 billion row challenge set by <a target=\"_blank\" href=\"https://github.com/gunnarmorling/1brc\">Gunnar Morling from Decodable</a>. This challenge requires users to write a Java program to compute each city's minimum, average, and maximum temperatures from a text file containing 1 billion measurements. Our response to this challenge obviously used ClickHouse, which, despite being constrained by not being a specialized solution to the problem, posted a very respectable time of around 19 seconds using the exact hardware profile stipulated by the rules.</p>\n<p>As any experienced ClickHouse user will know, 1 billion rows is quite small for ClickHouse, with users frequently performing aggregations over datasets in the trillions. So when the challenge was <a target=\"_blank\" href=\"https://medium.com/coiled-hq/one-trillion-row-challenge-5bfd4c3b8aef\">extended recently to 1 trillion rows by Dask</a>, our curiosity was piqued.</p>\n<p>In this blog post, <strong>we submit our attempt at querying the 1 trillion row dataset - completing the query in under 3 minutes for $0.56!</strong> While our original solution used moderate hardware, this larger challenge is a little trickier to perform on a laptop or machine equivalent to a small workstation.</p>\n<p>Instead, we resort to using <a target=\"_blank\" href=\"https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/using-spot-instances.html\">spot instances in AWS</a> while aiming to find a compromise between cost and performance. Thanks to a largely linear pricing model from AWS, this is a straightforward task: we simply identify the best value instances in AWS that minimize the query performance. Using a Pulumi script, we can spin up a ClickHouse cluster, run the query, and shut down the resources - all for $0.56!</p>\n<blockquote>\n<p>For those curious, if this data is loaded into a MergeTree, the query can be answered in 16 seconds! This incurs a load time, which we consider cheating, however :)</p>\n</blockquote>\n<h2 id=\"dataset\"></h2>\n<p>The structure of the data provided by Dask is consistent with the original challenge, with a city and temperature column. As discussed in their original blog, data of this size requires a format offering better compression than the CSV used for the 1 billion row challenge. They, therefore, provide the data in Parquet format in the following requester-pays bucket, i.e., users downloading this will need to provide an access key for AWS and incur transfer charges.</p>\n<p><code>s3://coiled-datasets-rp/1trc</code></p>\n<p>However, provided we ensure our ClickHouse cluster is deployed in the same region as this bucket (<code>us-east-1</code>) we can avoid data transfer charges while also optimizing the network bandwidth and latency.</p>\n<p>The full dataset consists of 2.4TiB of parquet files available as 100k files, each with 10m rows at around 23-24MiB.</p>\n<h2 id=\"querying-in-place\"></h2>\n<p>Frequently accessed datasets can be loaded into an analytical database like ClickHouse for fast queries. But for infrequently used datasets, it’s sometimes helpful to leave them in a “lake house” like S3 and have the ability to run ad-hoc analytical queries on them in place. In the AWS ecosystem, users may be familiar with technologies such as Amazon Athena, which offers the ability to analyze data directly in Amazon S3 using standard SQL.</p>\n<blockquote>\n<p>Technologies capable of querying both lakehouses and performing as a real-time analytical database can be considered <a target=\"_blank\" href=\"https://clickhouse.com/blog/the-unbundling-of-the-cloud-data-warehouse\">real-time data warehouses</a>.</p>\n</blockquote>\n<p>ClickHouse offers both of these capabilities. For the purposes of our challenge, we only need to execute this query once. As noted in our <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-one-billion-row-challenge\">1 billion row challenge results</a>, while the final query will be faster once the data has been loaded into ClickHouse, the actual load time will offset any benefit. We, therefore, utilize ClickHouse's <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/table-functions/s3\">s3 function</a> to query the data \"in-place\".</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    <span>count</span>() <span>as</span> num_rows,</span>\n<span>    uniqExact(_file) <span>as</span> num_files</span>\n<span><span>FROM</span> s3(<span>'https://coiled-datasets-rp.s3.us-east-1.amazonaws.com/1trc/measurements-*.parquet'</span>, <span>'AWS_ACCESS_KEY_ID'</span>, <span>'AWS_SECRET_ACCESS_KEY'</span>, headers(<span>'x-amz-request-payer'</span> <span>=</span> <span>'requester'</span>))</span>\n<span></span>\n<span>┌──────num_rows─┬─num_files─┐</span>\n<span>│ <span>1000000000000</span> │    <span>100000</span> │</span>\n<span>└───────────────┴───────────┘</span></code></pre></div>\n<p>As a simple example, we can confirm the total number of rows and files with a simple query.</p>\n<blockquote>\n<p>To access a requester-pays bucket, a header <code>'x-amz-request-payer' = 'requester'</code> must be passed in any requests. This is achieved in the above call by passing the parameter <code>headers('x-amz-request-payer' = 'requester')</code> to the s3 function.</p>\n</blockquote>\n<h2 id=\"a-simple-query\"></h2>\n<p>Our previous query for the 1 billion row challenge contained a few optimizations to minimize string formatting and to ensure the data was returned in the correct format. Thanks to the Parquet format, we aren’t required to do any string parsing. Our query is, therefore, a simple <code>GROUP BY</code>.</p>\n<h2 id=\"minimizing-aws-costs\"></h2>\n<p>To keep costs to an absolute minimum for our query, we can exploit <a target=\"_blank\" href=\"https://aws.amazon.com/ec2/spot/\">AWS’ spot instances</a>. These instance types allow you to use spare EC2 compute for which you can bid (a minimum spot price is set) through the AWS API. While potentially, these instances can be interrupted and reclaimed by AWS (e.g., if the spot price exceeds the bid), they come at up to a 90% discount. For current spot prices, we recommend this <a target=\"_blank\" href=\"https://instances.vantage.sh/\">resource</a> from Vantage.</p>\n<blockquote>\n<p>These spot prices are not as linear for each instance type, unlike on-demand pricing. For example, at the time of writing, a <a target=\"_blank\" href=\"https://instances.vantage.sh/aws/ec2/c7g.xlarge\">c7g.xlarge</a> with four vCPUs is $0.0693 per hour (&gt; 50% cheaper than on demand), which is more than ½ the price of a <a target=\"_blank\" href=\"https://instances.vantage.sh/aws/ec2/c7g.2xlarge\">c7g.2xlarge</a> with eight cores at $0.1157. Long-term trends in supply and demand for EC2 spare capacity ultimately determine prices.</p>\n</blockquote>\n<p>The next challenge was to minimize the time any instances were active. We need to:</p>\n<ol>\n<li>Claim our instances and wait for them to be available - usually around 30s</li>\n<li>Install ClickHouse and configure to form a cluster</li>\n<li>Run the query</li>\n<li>Immediately stop the instances.</li>\n</ol>\n<p>This is a simplification of what needs to be done and doesn’t consider the need to configure supporting AWS resources, including a VPC, subnet, internet gateway, and an appropriate security group such that instances can communicate with each other.</p>\n<p>To perform the AWS orchestration work and to configure a ClickHouse cluster, we chose <a target=\"_blank\" href=\"https://www.pulumi.com/\">Pulumi</a>, principally because it allows the infrastructure provisioning code to be written in Python, making it very readable, as well as allowing all the work to be done in one tool. We've extended this with a <a target=\"_blank\" href=\"https://www.pulumi.com/docs/concepts/resources/dynamic-providers/\">Dynamic ResourceProvider</a> to support querying the cluster once it's ready. This allows us to do all of the above work in a single script <a target=\"_blank\" href=\"https://github.com/ClickHouse/1trc/tree/main/aws-starter\">available here</a>.</p>\n<p>To reproduce these tests, users simply need to clone the above repository and modify the Pulumi stack configuration file shown below, specifying the region, zone, number of instances, and their respective type before running <code>./run.sh</code>.</p>\n<div><pre><code><span><span>config:</span></span>\n<span> <span>aws:region:</span> <span>us-east-1</span></span>\n<span> <span>1trc:aws_zone:</span> <span>us-east-1d</span></span>\n<span> <span>1trc:instance_type:</span> <span>\"c7g.4xlarge\"</span></span>\n<span> <span>1trc:number_instances:</span> <span>16</span></span>\n<span> <span># this must exist as a key-pair in AWS</span></span>\n<span> <span>1trc:key_name:</span> <span>\"&lt;key-pair-name&gt;\"</span></span>\n<span> <span># change as needed</span></span>\n<span> <span>1trc:cluster_password:</span> <span>\"clickhouse_admin\"</span></span>\n<span> <span># AMD ami (us-east-1)</span></span>\n<span> <span>1trc:ami:</span> <span>\"ami-05d47d29a4c2d19e1\"</span></span>\n<span> <span># Intel AMI (us-east-1)</span></span>\n<span> <span># 1trc:ami: \"ami-0c7217cdde317cfec\"</span></span>\n<span> <span># query to run on the cluster</span></span>\n<span> <span>1trc:query:</span> <span>\"SELECT 1\"</span></span></code></pre></div>\n<p>This script will invoke <code>Pulumi up</code>. This causes the instances to be provisioned and configured, executing the defined query as the final step. Once the query completes, <code>Pulumi down</code> is issued to teardown the infrastructure with a final timing reported.</p>\n<p>We should stress that this script is in no way a substitute for proper provisioning code for a production ClickHouse cluster. We accepted some compromises given the ephemeral nature of the instances (less than 5 mins) but which would be severely limiting in a production cluster. Specifically:</p>\n<ul>\n<li>We don’t provision any storage as we query the data in place in S3.</li>\n<li>While access is limited to the IP from which the Pulumi code was run, the cluster is exposed over HTTP on port 8213 so we can run the required query. For the period the cluster is alive, this represents a minimal risk, but the lack of SSL would not be recommended for production environments. Our network settings for inter-instance communication are also too loose.</li>\n<li>The configuration of the cluster is extremely limited, with no consideration given to the need to modify, expand, or upgrade the cluster. Our ClickHouse configurations are also minimal and not customizable.</li>\n<li>Zero tests were performed, and no consideration is given to extensibility.</li>\n<li>We don’t handle potential spot <a target=\"_blank\" href=\"https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-best-practices.html#prep-instances-for-interruptions\">interruptions</a> that are always possible on AWS with spot instances. We also assume a homogeneous set of instance types (which is against <a target=\"_blank\" href=\"https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-best-practices.html#be-instance-type-flexible\">AWS best practices</a>) since this makes things easier to reason about and test.</li>\n</ul>\n<p>While limited, the above script does allow us to spin up ClickHouse clusters cheaply, run a query, and destroy the infrastructure immediately. This ephemeral cluster deployment can be used to run queries that might otherwise be computationally out of reach for a laptop. For example, to run 32 instances of a <a target=\"_blank\" href=\"https://instances.vantage.sh/aws/ec2/c7g.4xlarge\"><code>c7g.4xlarge</code></a> (16 cores, 32GiB RAM) for 5 minutes, we would pay approximately <code>0.2441 * (5/60) * 32 = $0.65</code> - ClickHouse can query a lot of data in S3 with this amount of resources!</p>\n<h2 id=\"choosing-an-aws-instance-type\"></h2>\n<p>Before performing any testing and query tuning we wanted to identify an instance type, mainly to avoid an exhaustive set of tests which would prove time consuming. We based this on simple reasoning with the aim of producing a competitive result without expending enormous resources to find the perfect hardware profile.</p>\n<p>As a simple aggregation query, where the station has a relatively low cardinality (1000s), we suspected this query would be either CPU- or network-bound. Further increases in the <code>max_threads</code> beyond 128 resulted in CPU contention and CPU wait time - reducing overall throughput.</p>\n<p><span><img alt=\"optimal_single_node_1trillion.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Foptimal_single_node_1trillion_b7550ab716.png&w=2048&q=75\"></span></p>\n<p>At this point, we were content that we were CPU bound and did not believe further tuning would deliver significant gains; our final query time was 138 seconds or around 2 minutes to query all 111 billion rows.</p>\n<p>A single instance is obviously not sufficient to give us a reasonable runtime on a dataset almost 10x the size. However, confident our individual c7g.12xlarge will not be network bound, and with sensible settings for our query, we scale horizontally and tackle our larger 1 trillion row problem.</p>\n<blockquote>\n<p>When we run our query across a cluster, these same settings can be passed to each node, along with a subset of the data to process, thus optimizing the performance of each.</p>\n</blockquote>\n<h2 id=\"using-a-cluster\"></h2>\n<p>To query a cluster and use all nodes, we had to change our query a little, using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/table-functions/s3Cluster\">s3Cluster</a> rather than the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/table-functions/s3\">s3 function</a>. This allows us to use all nodes in our cluster to process the query.</p>\n<p>Unlike the standard s3 function, which executes the query on the receiving node only, this function ① first performs a listing of the bucket. The coordinating node uses this list to ② send files to be processed to every node in the cluster, thus allowing the work to be parallelized ③. The coordinating node then ④ collates intermediate results from each of the nodes in the cluster to ⑤ provide the final response. We visualize this below:</p>\n<p><span><img alt=\"s3cluster.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fs3cluster_ba84f2ba7a.png&w=2048&q=75\"></span></p>\n<p>Our final query:</p>\n<div><pre><code><span><span>SELECT</span> station,</span>\n<span>\t<span>min</span>(measure),</span>\n<span>\t<span>max</span>(measure),</span>\n<span>\tround(<span>avg</span>(measure), <span>2</span>)</span>\n<span><span>FROM</span> s3Cluster(<span>'default'</span>, <span>'https://coiled-datasets-rp.s3.us-east-1.amazonaws.com/1trc/measurements-*.parquet'</span>, <span>'AWS_ACCESS_KEY_ID'</span>, <span>'AWS_SECRET_ACCESS_KEY'</span>, headers(<span>'x-amz-request-payer'</span> <span>=</span> <span>'requester'</span>))</span>\n<span><span>GROUP</span> <span>BY</span> station</span>\n<span><span>ORDER</span> <span>BY</span> station <span>ASC</span></span>\n<span>FORMAT `<span>Null</span>`</span>\n<span>SETTINGS max_download_buffer_size <span>=</span> <span>52428800</span>, max_threads <span>=</span> <span>110</span></span></code></pre></div>\n<p>In our example above, as in all ClickHouse Cloud clusters, we <a target=\"_blank\" href=\"https://github.com/ClickHouse/1trc/blob/3ed9c01e0fbce6cf3e31438b5c39bab95c97593b/aws-starter/config.py#L90\">name our cluster 'default'.</a></p>\n<h2 id=\"final-timing-and-costs\"></h2>\n<p>While the query time should reduce linearly with the number of instances we deploy, thus keeping cost constant, we were also restricted as to how many instances we could realistically provision. AWS generally recommends <a target=\"_blank\" href=\"https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-best-practices.html#be-instance-type-flexible\">mixed instance types</a> and EC2 scaling groups instead of our <a target=\"_blank\" href=\"https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-best-practices.html#use-sf-asg-for-aggregate-capacity\">homogenous approach to scaling</a>. Our current script also restricts us to a single availability zone (although this is an obvious improvement, it complicates the code a little). A little testing revealed eight instances could be reliably obtained, giving us a total of 384 vCPUs. Our final configuration was thus:</p>\n<div><pre><code><span><span>config:</span></span>\n<span>  <span>aws:region:</span> <span>us-east-1</span></span>\n<span>  <span>1trc:aws_zone:</span> <span>us-east-1b</span></span>\n<span>  <span>1trc:instance_type:</span> <span>\"c7g.12xlarge\"</span></span>\n<span>  <span>1trc:number_instances:</span> <span>8</span></span>\n<span>  <span>1trc:key_name:</span> <span>\"dalem\"</span></span>\n<span>  <span>1trc:cluster_password:</span> <span>\"a_super_password\"</span></span>\n<span>  <span># AMD ami (us-east-1)</span></span>\n<span>  <span>1trc:ami:</span> <span>\"ami-05d47d29a4c2d19e1\"</span></span>\n<span>  <span>1trc:query:</span> <span>\"SELECT station, min(measure), max(measure), round(avg(measure), 2) FROM s3Cluster('default','https://coiled-datasets-rp.s3.us-east-1.amazonaws.com/1trc/measurements-*.parquet', 'AWS_ACCESS_KEY_ID', 'AWS_SECRET_ACCESS_KEY', headers('x-amz-request-payer' = 'requester')) GROUP BY station ORDER BY station ASC SETTINGS max_download_buffer_size = 52428800, max_threads=128\"</span></span></code></pre></div>\n<p>Note we use <code>us-east-1b</code> as our availability zone.
