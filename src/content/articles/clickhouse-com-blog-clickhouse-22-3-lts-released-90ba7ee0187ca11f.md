This is a long-term support release (LTS) — it will receive security updates and important bug fixes through March 2023.</p>\n<p>The release includes 1308 new commits from 86 contributors, including 25 new contributors:</p>\n<p>1lann, Anish Bhanwala, Eugene Galkin, HaiBo Li, Hongbin, Jianmei Zhang, LAL2211, Lars Eidnes, Miel Donkers, NikitaEvs, Nir Peled, Robert Schulze, SiderZhang, Varinara, Xudong Zhang, Yong Wang, cwkyaoyao, heleihelei, kashwy, lincion, metahys, rfraposa, shuchaome, tangjiangling, zhangyifan27.</p>\n<p>The changes in 22.3 are mostly focused on feature maturity, security and reliability. A few experimental features have become ready for production usage:</p>\n<h2 id=\"clickhouse-keeper\"></h2>\n<p>ClickHouse Keeper is our replacement for ZooKeeper. It implements the ZooKeeper protocol and data model; and works as a drop-in replacement of ZooKeeper (up to version 3.5) with ClickHouse and with other applications. It can work as a dedicated component or embedded into clickhouse-server.</p>\n<p>We are proud that it is passing Jepsen tests with continuous integration. This includes the tests for ZooKeeper and additional tests for better coverage. In addition, it is passing ClickHouse functional and integration tests, stress tests and fuzzing.</p>\n<p>Since version 22.3 we ensure that it is faster than ZooKeeper on both reads and writes while consuming less memory. Disk usage for logs and snapshots is also lower. The data on disk and in transfer is checksummed to protect from hardware failures. Higher percentiles of request latencies are lower. This has been made possible by contributions of <strong>Zhang Li Star</strong> and <strong>Alexander Sapin</strong>.</p>\n<p>As of release 22.3 ClickHouse Keeper is production ready! In fact, it is already being used in production for more than half a year, so you will not be the first production user.</p>\n<h2 id=\"arm-architecture-support\"></h2>\n<p>64bit ARM CPU architecture (AArch64) has become increasingly popular for server applications in the cloud, as well as for laptops and workstations. Ever considered ClickHouse on network devices and mobile? You know what? ClickHouse runs on all of them and squeezes every bit of performance out of them.</p>\n<p>We started porting ClickHouse to AArch64 in Feb 2016, and since that time we have checked 13 different CPU models: APM X-Gene; Cavium ThunderX 1, 2; Raspberry Pi; Pinebook; Google Pixel; Apple M1, M1 Max; Huawei Taishan; AWS Graviton 1, 2, 3; Ampere Altra. There is a huge diversity among ARM CPU manufacturers and we are happy to support it. We also maintain the collection of <a target=\"_blank\" href=\"https://clickhouse.com/benchmark/hardware/\">comparative benchmarks of different hardware</a>.</p>\n<p>Release 22.3 has two major milestones for AArch64 support:</p>\n<ol>\n<li>Continuous integration with 100% functional tests passing.</li>\n<li>Full support for release builds: deb, rpm, apk, tgz, single-binary and Docker.</li>\n</ol>\n<p>This has been made possible by work of <strong>Mikhail Shiryaev</strong>. Since the release 22.3 ClickHouse on AArch64 is production ready!</p>\n<p>ClickHouse has more specific optimizations for x86_64 instruction set architecture and only a couple AArch64-specific optimizations, and even despite this fact, it gives better price/performance on AArch64 in the major cloud providers.</p>\n<p>Some x86-specific features are disabled on AArch64: support for Hyperscan, support for hardware metrics from <a target=\"_blank\" href=\"https://perfmon-events.intel.com/\">PMU</a>. Some features are not included in the build, like GRPC API support. Running mixed architecture clusters is not recommended, although there are no known issues as of now.</p>\n<p>What to expect next? We have ongoing development for PowerPC 64 little-endian and for RISC-V 64. If you are interested in some other CPU architecture, please let us know.</p>\n<h2 id=\"virtual-filesystem-over-s3\"></h2>\n<p>Experimental support for VFS over S3 exists for around two years. This is the story:</p>\n<ul>\n<li>s3 functions for data import and export by <strong>Vladimir Chebotarev</strong></li>\n<li>disks, volumes and storage policies by <strong>Igor Mineev</strong> and <strong>Alexander Sapin</strong></li>\n<li>automatic and user-triggered movement of data parts between disks by <strong>Vladimir Chebotarev</strong></li>\n<li>virtual file system interface by <strong>Alexander Burmak</strong></li>\n<li>implementation of VFS over s3 by <strong>Pavel Kovalenko</strong>, <strong>Grigory Pervakov</strong> and <strong>Anton Ivashkin</strong></li>\n<li>asynchronous reads by <strong>Alexey Milovidov</strong>, <strong>Kseniia Sumarokova</strong> and <strong>Alexander Sapin</strong></li>\n<li>full functional test coverage, correctness and reliability by <strong>Alexander Sapin</strong></li>\n</ul>\n<p>As of 22.3 we ensure maximum query performance on top of s3 and continuous testing for every commit. Support for MergeTree and ReplicatedMergeTree operation over s3 is ready for production.</p>\n<p>Although some new features are not production ready: “zero-copy replication” (ensure one copy of data if there are more than one replica in a region) and the local cache. Testing has been performed for AWS S3 and Minio. There are known issues on GCP.</p>\n<h2 id=\"secure-build-infrastructure\"></h2>\n<p>For previous versions we have used servers in Yandex Cloud. Since release 22.3 we have migrated our infrastructure to different locations.</p>\n<p>Continuous integration and testing moved to AWS data centers in the US. We also have released all the build and test runners in <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/tree/master/.github/workflows\">open-source</a>. The build process has been made <a target=\"_blank\" href=\"https://reproducible-builds.org/\">reproducible</a>. You can run the build by yourself and get the binaries that are byte-identical and indistinguishable to the official binaries. The build process is hermetic and does not depend on the OS distribution and the environment. The final release builds are stored in <a target=\"_blank\" href=\"https://www.jfrog.com/\">JFrog Artifactory</a>, and available on <a target=\"_blank\" href=\"https://packages.clickhouse.com/\">packages.clickhouse.com</a>.</p>\n<p>The work has been done by <strong>Mikhail Shiryaev</strong>, <strong>Alexander Sapin</strong> and <strong>Alexey Milovidov</strong>.</p>\n<p>Please read the <a target=\"_blank\" href=\"https://clickhouse.com/blog/we-stand-with-ukraine/\">motivation for these changes</a>.</p>\n<h2 id=\"security-features\"></h2>\n<p>Authentication with X.509 client certificates has been contributed by <strong>Eungenue</strong>. And two features contributed by <strong>Heena Bansal</strong>: a switch to disable plaintext password or no password for users; filtering outgoing connections in MySQL, PostgreSQL federated queries.</p>\n<h2 id=\"more-testing-and-fuzzing\"></h2>\n<p>We believe <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Fuzzing\">fuzzing</a> is the absolute need to build reliable software. And the main principle of fuzzing is: there should be more fuzzing. So, we have many fuzzing methods in ClickHouse CI: LLVM’s libFuzzer, AST based query fuzzer, Ad-hoc SQL function fuzzer, Randomization of thread scheduling order, Randomization of timezones, SQLancer (logical fuzzer), Stress tests, and Jepsen tests.</p>\n<p>But this is not enough.</p>\n<p>Since version 22.3 we have added <em>randomization of query settings in functional tests</em>. So, we can run the tests under every combination of different settings.</p>\n<p>We have also added automated tests for backward compatibility. It is trying to create every possible database, table and dictionary, then install the previous ClickHouse version and check if it will startup successfully. This allows us to be aware if a new feature will prevent version downgrade.</p>\n<p>We are so keen on testing that we decided to add automated tests for tests. Whenever someone contributes a bugfix we automatically check that it contains tests and these tests fail on previous ClickHouse versions.</p>\n<h2 id=\"semistructured-data\"></h2>\n<p>Okay, I spent 15 minutes of your time telling about security, reliability, compliance, transparency… but where is <strong>the fun</strong>?</p>\n<p>In version 22.3 we have a new experimental feature — support for dynamic subcolumns and semistructured data!</p>\n<p>Suppose you have a bunch of JSON and want to analyze it — without specifying the data types in your table. And you want your table to automatically adapt for the schema changes, to automatically add new columns. And everything with hierarchical objects and arrays with deep nesting! Now it is possible and it works like magic.</p>\n<p>Let me demonstrate it with an example using GitHub API.</p>\n<p>I obtained the list of GitHub repositories ordered by the number of stars from <a target=\"_blank\" href=\"https://ghe.clickhouse.tech/\">GH Explorer</a>. Not bad.</p>\n<p>Let me explain how dynamic subcolumns work:</p>\n<p>There is the new <code>JSON</code> data type. You can also write it as <code>Object('JSON')</code>. This data type can parse arbitrary JSON and it contains dynamic subcolumns. You can have both regular types and <code>JSON</code> types in the same table. Dynamic subcolumns are created on insertion and are stored in column-oriented format just like regular columns, so querying these subcolumns is as efficient as regular columns. The data types are inferred automatically and can be converted during background merges, so you can have different schemas in different INSERTs. Queries are using natural syntax like <code>data.license.name[1]</code> instead of <code>JSONExtractString(data, 'license', 'name', 1)</code> or <code>JSON_QUERY(data, '$.license.name[1]')</code>.</p>\n<p>This feature is implemented by <strong>Anton Popov</strong>. It is available for preview in version 22.3. We will be happy to hear your feedback.</p>\n<h2 id=\"performance-improvements\"></h2>\n<p>There are so many performance optimizations in ClickHouse and every new release ClickHouse becomes even faster.</p>\n<p><strong>Maksim Kita</strong> has improved performance of insertion into MergeTree tables up to two times by sorting optimizations (if the order key is represented by several numeric columns).</p>\n<p>If you have SELECT queries with a huge list in WHERE IN, these queries will work up to 3 times faster in ClickHouse 22.3:</p>\n<div><pre><code><span>SELECT * FROM table</span>\n<span>WHERE key IN (111, 222, ... a megabyte of something)</span></code></pre></div>\n<h2 id=\"local-cache-for-remote-filesystem\"></h2>\n<p>When ClickHouse is reading from the local filesystem, the data is cached by the OS in the page cache. Typical performance of reading from page cache from multiple threads on a server with multi-channel memory is around 50 GB/sec, so the hot queries are really fast.</p>\n<p>But if ClickHouse is reading from a remote filesystem, the OS does not see these reads and cannot use page cache. So, we need our own page cache in ClickHouse. Since version 22.3, ClickHouse has a cache for remote filesystem, implemented by <strong>Ksenia Sumarokova</strong>. This feature is available for preview.</p>\n<p>It gives <a target=\"_blank\" href=\"https://youtu.be/GzeANZzPras?t=389\">tremendous improvements in performance</a>. The cache is hybrid — it is using both the local disks and RAM.</p>\n<h2 id=\"what-else\"></h2>\n<p>Read the <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/master/CHANGELOG.md\">full changelog</a> for the 22.3 release and follow <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/issues/32513\">the roadmap</a>.</p></div></article>"
