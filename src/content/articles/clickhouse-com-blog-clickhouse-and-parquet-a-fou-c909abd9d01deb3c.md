Combined with the ClickHouse query engine, it’s the key component behind the high performance of direct Parquet file queries.</p>\n<h3 id=\"how-the-parquet-reader-works-today-and-what-s-next\"></h3>\n<p>Fun fact: While MergeTree remains the native data storage format, ClickHouse has been actively tuning and optimizing for Parquet for over three years. It’s all part of our goal to make ClickHouse the fastest engine in the world for querying Parquet at scale.</p>\n<p>The <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/775b7d30c814bf9f28614b472d4ae8c10b39fa92/src/Processors/Formats/Impl/ParquetBlockInputFormat.h#L14\">current Parquet reader</a> uses the <a target=\"_blank\" href=\"https://github.com/apache/arrow/tree/main/cpp\">Arrow library</a> to parse files into <a target=\"_blank\" href=\"https://arrow.apache.org/\">Arrow</a> format, then <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/775b7d30c814bf9f28614b472d4ae8c10b39fa92/src/Processors/Formats/Impl/ArrowColumnToCHColumn.cpp\">copies</a> the data into ClickHouse’s native in-memory format for execution. In the next sections, we’ll explore the capabilities of this reader.</p>\n<p>A new native Parquet reader is already in the <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/78380\">works</a>, designed to eliminate the Arrow layer entirely and read files directly into ClickHouse’s native in-memory format. It also brings better parallelism and I/O efficiency. The project is fittingly called <strong>Yet Another Parquet Reader</strong>, because, well, it is. This is ClickHouse’s third native Parquet reader implementation. The first (<code>input_format_parquet_use_native_reader</code>) was started but never completed. The second (v2) made it to a <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/70611\">pull request</a>, but stalled before reaching production. And now, <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/78380\">v3</a> is underway.</p>\n<blockquote>\n<p>We could’ve waited to publish this post until the new reader was finished, but benchmarking the current reader gives us a great baseline. In a future follow-up, we’ll highlight how the new reader improves performance and efficiency.</p>\n</blockquote>\n<p>Parquet file query performance in ClickHouse is primarily determined by two factors:</p>\n<ol>\n<li>\n<p><strong>Level of parallelism</strong>: The more files, and the more non-overlapping regions within those files, that ClickHouse can read and process in parallel, the higher the throughput and the faster the queries complete.</p>\n</li>\n<li>\n<p><strong>Degree of I/O reduction</strong>: The less unnecessary work (such as scanning and processing irrelevant data) is done, the faster queries complete.</p>\n</li>\n</ol>\n<p>In the next two sections, we’ll break down how the query engine and current Parquet reader work together to achieve parallelism and I/O reduction, and highlight upcoming improvements in the native reader. We’ll also cover tuning settings that let you influence these behaviors for performance tuning.</p>\n<h3 id=\"parallelism-how-the-engine-scales\"></h3>\n<p>Before explaining how ClickHouse currently achieves parallelism when querying Parquet files, we first need to briefly look at the physical on-disk structure of a Parquet file. The way Parquet organizes data fundamentally determines how efficiently the data can be split into independent units of work, and thus how much parallelism can be applied during query execution.</p>\n<p>The following diagram shows a simplified view of how data from a web analytics dataset (used later in our benchmark) is <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/\">organized</a> on disk when stored as Parquet files:</p>\n<p><span><img alt=\"Blog-FormatsReads.005.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_Reads_005_3fd2648fb1.png&w=2048&q=75\"></span></p>\n<p>In Parquet, our <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-and-parquet-a-foundation-for-fast-lakehouse-analytics#benchmark-setup-hardware-dataset-and-software\">test dataset</a>, consisting logically of rows and columns, is stored in one or more <strong>files</strong>. Each file organizes the data hierarchically as follows:</p>\n<p>① <strong>Row groups</strong>: The stored data is divided into one or more horizontal partitions called row groups. By default, when Parquet files are written with ClickHouse, each row group contains <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/formats#output_format_parquet_row_group_size\">1 million rows</a> or <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/formats#output_format_parquet_row_group_size_bytes\">~500 MB of data</a> (before compression).</p>\n<p>② <strong>Column chunks</strong>: Each row group is further divided vertically into column chunks, one for each column in the dataset. Each chunk stores the values for that column across all rows in the row group.</p>\n<p>③ <strong>Data pages</strong>: Inside each column chunk, the actual values are stored in data pages. By default, ClickHouse writes data pages of <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/formats#output_format_parquet_data_page_size\">1 MB</a> (before compression). A page stores a fixed or variable number of <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/data-pages/encodings/\">encoded</a> and <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/data-pages/compression/\">compressed</a> values, depending on the column’s data type and the encoding scheme used.</p>\n<p>Note: For readability, the diagram above shows row groups containing six rows and data pages containing three values per column.</p>\n<p>With the data layout clear, we can now look at how the ClickHouse query engine, together with the current Parquet reader, parallelizes data processing across available CPU cores to maximize query performance.</p>\n<p>ClickHouse doesn’t just run anywhere and query anything, it also <strong>parallelizes almost everything</strong>, especially when querying Parquet. The following diagram shows how different layers of parallelism come together within the Parquet reader and the ClickHouse query engine during query execution:</p>\n<p><span><img alt=\"Blog-FormatsReads.006.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_Reads_006_91953859fe.png&w=2048&q=75\"></span></p>\n<p>① <strong>Parallel prefetch threads</strong>: Within a Parquet file, the Parquet file reader reads multiple row groups in parallel (<em>intra-file</em>, <em>inter–row group parallelism</em>). By default, row group prefetching is <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/formats#input_format_parquet_enable_row_group_prefetch\">enabled</a> with four parallel prefetch threads (controlled by the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#max_download_threads\">max_download_threads</a> setting) and kicks in either when parsing reaches its maximum parallelism (explained below) or when parsing would otherwise stall, such as when data must first be loaded over a network connection.</p>\n<p>② <strong>Parallel parsing threads</strong>: Parsing threads read and parse data from multiple row groups within the same file in parallel (<em>intra-file, inter–row group parallelism</em>). If prefetching is active, they read from the prefetch buffer; otherwise, they read directly from the file. The number of parsing threads (across all file streams, see below) is controlled by the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#max_parsing_threads\">max_parsing_threads</a> setting, which by default matches the number of available CPU cores.</p>\n<p>③ <strong>Parallel file streams</strong>: Different Parquet files are processed concurrently, each with their own parallel prefetch and parsing threads, to maximize throughput across files (<em>inter-file parallelism</em>). The number of file streams is determined dynamically during query compilation (see below).</p>\n<p>④ <strong>Parallel processing lanes</strong>: As data is passed from the Parquet reader component to the query engine <a target=\"_blank\" href=\"https://clickhouse.com/docs/development/architecture#block\">block</a>-wise and in a streaming fashion, filtering, aggregation, and sorting happen across independent <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/query-parallelism#distributing-work-across-processing-lanes\">lanes</a> for maximum concurrency (inter- and intra-operator parallelism). The number of parallel processing lanes is determined by the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#max_threads\">max_threads</a> setting, which by default matches the number of CPU cores available to the ClickHouse query engine.</p>\n<p>Whether you’re querying many small files or a single large file, ClickHouse automatically balances the Parquet file processing such that query execution remains efficient. To achieve this, the file path pattern used to select Parquet files (e.g. with the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/table-functions/file\">file table function</a>) is resolved during query compilation, and the number of matching files (<code>num_files</code>) directly influences the physical query plan:</p>\n<ul>\n<li>Many small files are parsed with one thread per file across many file streams.</li>\n<li>A single large file is parsed with many threads operating in parallel on a single stream.</li>\n</ul>\n<p>The calculations for this follow simple rules:</p>\n<ul>\n<li>\n<p>Number of parallel file streams <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/d66f2f168249888d7672045389350493a05a98fe/src/Storages/StorageFile.cpp#L1677-L1686\">=</a> <code>min(max_threads, num_files)</code></p>\n</li>\n<li>\n<p>The available parallel parsing threads (<code>max_parsing_threads</code>) is then evenly spread over the file streams with <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/d66f2f168249888d7672045389350493a05a98fe/src/Storages/StorageFile.cpp#L1442\">this</a> formula:  <code>max(max_parsing_threads / num_files, 1)</code>\nHere, <code>/</code> denotes integer division (rounding down), and <code>max()</code> ensures that at least one parsing thread is assigned per file.</p>\n</li>\n</ul>\n<p>Let’s briefly look at three examples to see how this balancing of file streams and parsing threads works in practice.</p>\n<h3 id=\"parallelism-in-practice-3-examples\"></h3>\n<p>In the following, we use the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/explain#explain-pipeline\">EXPLAIN</a> clause to inspect the <a target=\"_blank\" href=\"https://clickhouse.com/docs/academic_overview#4-2-multi-core-parallelization\">physical operator plan</a>—also known as the “query pipeline”—for three different runs of <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickBench/blob/f1178a21fbfdf3b2f9c71e7ed1602bb171d0cb2a/clickhouse/queries.sql#L11\">ClickBench query 11</a>, executed over a web analytics dataset (used later in our benchmark) stored as Parquet files. This query filters, aggregates, and sorts the data before applying a LIMIT. With the <code>graph</code> option, ClickHouse outputs the plan in <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/DOT_(graph_description_language)\">DOT</a> format, which can be rendered to a PDF using <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Graphviz\">Graphviz</a>.</p>\n<h4 id=\"example-1-one-parquet-file-4-cores\"></h4>\n<p>As a first example, <strong>we set max_threads and max_parsing_threads to 4</strong> (simulating a 4-core machine and keeping the plan readable) and use a path pattern matching <strong>exactly one Parquet file</strong>:</p>\n<div><pre><code><span>clickhouse local --query \"</span>\n<span>EXPLAIN Pipeline graph = 1, compact = 0</span>\n<span>SELECT MobilePhoneModel, COUNT(DISTINCT UserID) AS u</span>\n<span>FROM file('./output/Parquet/100000000/1000000/sorted/zstd/chunk_00.parquet')</span>\n<span>WHERE MobilePhoneModel &lt;&gt; ''</span>\n<span>GROUP BY MobilePhoneModel</span>\n<span>ORDER BY u DESC LIMIT 10</span>\n<span>SETTINGS max_threads = 4, max_parsing_threads = 4;</span>\n<span>\" | dot -Tpdf &gt; pipeline.pdf</span></code></pre></div>\n<p><span><img alt=\"Blog-FormatsReads.007.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_Reads_007_e7a34f6398.png&w=2048&q=75\"></span></p>\n<p>As you can see, the query engine uses one file stream (based on the <code>min(max_threads = 4, num_files = 1)</code> formula), and 4 parallel processing lanes (<code>max_threads = 4</code>) for running the query over the data of one Parquet file.</p>\n<p>The visualization above flows left to right. A <code>Resize</code> operator evenly distributes parsed file data across four processing lanes, where filtering and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#-multi-core-parallelization\">partial aggregation</a> is performed. A second <code>Resize</code> rebalances the streams to maintain even CPU utilization, crucial when data ranges have different predicate selectivities, which could otherwise overload some lanes and leave others idle. This dynamic redistribution ensures faster lanes assist slower ones, improving overall performance. Sorting proceeds in <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-just-in-time-compiler-jit#clickhouse-compilation-of-sorting\">three stages</a>:</p>\n<ol>\n<li><code>PartialSortingTransform</code> sorts individual blocks in each lane.</li>\n<li><code>MergeSortingTransform</code> maintains a local sorted stream per lane via <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/K-way_merge_algorithm\">2-way merges</a>.</li>\n<li><code>MergingSortedTransform</code> performs a <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/K-way_merge_algorithm\">k-way merge</a> across lanes, followed by a <code>LIMIT</code> to produce the final result.</li>\n</ol>\n<p>There’s no direct logging or easy way to introspect the number of parallel parsing threads per file. However, based on the <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/d66f2f168249888d7672045389350493a05a98fe/src/Storages/StorageFile.cpp#L1442\">formula in the source code</a>: <code>max(max_parsing_threads / num_files, 1)</code>, we can infer that with one file and <code>max_parsing_threads = 4</code>, multiple row groups are parsed in parallel using four threads.</p>\n<h4 id=\"example-2-two-parquet-files-4-cores\"></h4>\n<p>In the second example, we keep <code>max_threads</code> and <code>max_parsing_threads</code> set to 4 but change the file path pattern to match exactly 2 Parquet files:</p>\n<div><pre><code><span>clickhouse local --query \"</span>\n<span>EXPLAIN Pipeline graph = 1, compact = 0</span>\n<span>SELECT MobilePhoneModel, COUNT(DISTINCT UserID) AS u</span>\n<span>FROM file('./output/Parquet/100000000/1000000/sorted/zstd/chunk_0{0..1}.parquet')</span>\n<span>WHERE MobilePhoneModel &lt;&gt; ''</span>\n<span>GROUP BY MobilePhoneModel</span>\n<span>ORDER BY u DESC LIMIT 10</span>\n<span>SETTINGS max_threads = 4, max_parsing_threads = 4;</span>\n<span>\" | dot -Tpdf &gt; pipeline.pdf</span></code></pre></div>\n<p><span><img alt=\"Blog-FormatsReads.008.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_Reads_008_b0a439b7b2.png&w=2048&q=75\"></span></p>\n<p>Now the query engine uses two parallel file streams ( = <code>min(max_threads = 4, num_files = 2)</code> , and 4 parallel processing lanes (<code>max_threads = 4</code>) for running the query over the data of two Parquet files.</p>\n<p>The number of parallel parsing threads per file stream is 2 instead of 4 though (<code>max(max_parsing_threads = 4 / num_files = 2, 1)</code>).</p>\n<h4 id=\"example-3-100-parquet-files-32-cores\"></h4>\n<p>Finally we show an example without artificially restricted <code>max_threads</code> and <code>max_parsing_threads</code> thresholds. On our <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-and-parquet-a-foundation-for-fast-lakehouse-analytics#benchmark-setup-hardware-dataset-and-software\">test machine</a> with 32 CPU cores both are set to <code>32</code> by default. The file path pattern matches all <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-and-parquet-a-foundation-for-fast-lakehouse-analytics#generating-files-from-the-dataset\">100</a> Parquet files of the example dataset:</p>\n<div><pre><code><span>clickhouse local --query \"</span>\n<span>EXPLAIN Pipeline graph = 1, compact = 0</span>\n<span>SELECT MobilePhoneModel, COUNT(DISTINCT UserID) AS u</span>\n<span>FROM file('./output/Parquet/100000000/1000000/sorted/zstd/chunk_*.parquet')</span>\n<span>WHERE MobilePhoneModel &lt;&gt; ''</span>\n<span>GROUP BY MobilePhoneModel</span>\n<span>ORDER BY u DESC LIMIT 10;</span>\n<span>\" | dot -Tpdf &gt; pipeline.pdf</span></code></pre></div>\n<p><span><img alt=\"Blog-FormatsReads.009.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_Reads_009_9af83ce703.png&w=2048&q=75\"></span></p>\n<h3 id=\"scaling-out-cluster-wide-execution\"></h3>\n<p>So far, we’ve shown how a single ClickHouse query engine instance parallelizes Parquet processing across CPU cores. In <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-03#automatic-parallelization-for-external-data\">parallel cluster engine mode</a>, the query engine distributes the work across all available CPU cores of all available nodes, scaling parallelism across the entire cluster:</p>\n<p><span><img alt=\"Blog-FormatsReads.010.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_Reads_010_49b4ff82b5.png&w=2048&q=75\"></span></p>\n<p>The query engine on the initiator node—the server that receives the query—resolves the file glob pattern, connects to engines on the other nodes, and dynamically assigns files. As remote nodes finish processing, they request more files from the initiator until all files are processed.</p>\n<h3 id=\"what-s-next-for-performance-smarter-and-finer-grained-parallelism\"></h3>\n<p>The <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/78380\">upcoming native Parquet reader</a> not only removes the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-and-parquet-a-foundation-for-fast-lakehouse-analytics#how-the-parquet-reader-works-today-and-whats-next\">Arrow dependency</a>, eliminating the in-memory copy from Arrow data into ClickHouse’s internal format, saving time and memory, but also enables more fine-grained and adaptive parallelism:</p>\n<ul>\n<li>\n<p><strong>Column-level parallelism within row groups</strong>: Instead of only processing entire row groups in parallel, the new reader can read different columns from the same row group concurrently, enabling better CPU utilization when fewer row groups are available.</p>\n</li>\n<li>\n<p><strong>Merged I/O requests</strong>: By pre-registering expected file ranges, the reader can detect small, adjacent I/O operations and merge them into fewer, larger read requests, improving throughput, especially on high-latency storage.</p>\n</li>\n<li>\n<p><strong>Parallelism-aware scheduling</strong>: The engine can assign different degrees of parallelism depending on the stage and memory footprint, e.g., using high parallelism for small structures like <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-and-parquet-a-foundation-for-fast-lakehouse-analytics#io-reduction-what-we-skip-and-how\">Bloom filters</a>, and more conservative parallelism for bulk column data to reduce memory pressure.</p>\n</li>\n</ul>\n<p>These changes are designed to better exploit system resources and maintain throughput consistency across workloads of varying size and complexity.</p>\n<p>With parallelism covered, we now turn to the second key factor for fast Parquet queries in ClickHouse: minimizing unnecessary I/O. The less irrelevant data we scan, parse, or process, the faster queries run. In the next section, we’ll look at the I/O reduction techniques ClickHouse applies today, and those coming soon with the native reader.</p>\n<h3 id=\"i-o-reduction-what-we-skip-and-how\"></h3>\n<p>To understand how ClickHouse minimizes unnecessary reads, let’s look at the I/O reduction techniques enabled by Parquet’s file structure.</p>\n<p><strong>Column projection</strong><br>\nParquet is a columnar format, so the reader and ClickHouse query engine only access the columns needed by a query.</p>\n<p><strong>Compression and encoding</strong><br>\nBy encoding data (e.g., using dictionaries or run-length encoding) and compressing it column-by-column, Parquet reduces the amount of data stored and read from disk. This not only saves space but also speeds up queries. ClickHouse can scan less data, decompress only what’s needed, and skip entire sections based on encoded metadata (see below).</p>\n<p>Parquet supports a variety of encoding and compression schemes at the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-and-parquet-a-foundation-for-fast-lakehouse-analytics#parallelism-how-the-engine-scales\">page</a> level:</p>\n<ul>\n<li>\n<p>Page encoding: Parquet defines several <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/data-pages/encodings/\">encoding schemes</a> for efficient value storage. Common examples include dictionary encoding (see below) and run-length encoding.</p>\n</li>\n<li>\n<p>Page compression: After encoding, pages can be <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/data-pages/compression/\">compressed</a> using algorithms like Snappy, LZ4, and ZSTD to further reduce file size and I/O.</p>\n</li>\n</ul>\n<p><strong>Predicate pushdown</strong><br>\nParquet enables coarse-grained <a target=\"_blank\" href=\"https://homepages.cwi.nl/~boncz/msc/2018-BoudewijnBraams.pdf\">predicate pushdown</a> through metadata stored at multiple levels of granularity. This metadata wasn’t shown <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-and-parquet-a-foundation-for-fast-lakehouse-analytics#parallelism-how-the-engine-scales\">earlier</a>; the diagram below now includes it, again using our <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-and-parquet-a-foundation-for-fast-lakehouse-analytics#parallelism-how-the-engine-scales\">web analytics dataset</a> for illustration. Again, for clarity, it shows row groups with just six rows and data pages with only three values per column:</p>\n<p><span><img alt=\"Blog-FormatsReads.011.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_Reads_011_7333b20d77.png&w=2048&q=75\"></span></p>\n<p>Below, we describe the metadata elements added in the diagram above in more detail.</p>\n<p>① <strong>Column chunk-level dictionary filtering</strong>: For low-cardinality columns, Parquet uses <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/data-pages/encodings/\">dictionary encoding</a>. Each column chunk includes a dictionary page that maps unique values. When queries filter on a specific value, like <code>WHERE status = 'cancelled'</code>, readers can check the dictionary first to decide whether the chunk contains that value and can be skipped entirely if not.</p>\n<p>② <strong>Page-level min/max filtering</strong>: Parquet pages can <a target=\"_blank\" href=\"https://github.com/apache/parquet-format/blob/3ce0760933b875bc8a11f5be0b883cd107b95b43/src/main/thrift/parquet.thrift#L691\">include statistics</a> such as the <a target=\"_blank\" href=\"https://github.com/apache/parquet-format/blob/3ce0760933b875bc8a11f5be0b883cd107b95b43/src/main/thrift/parquet.thrift#L306\">minimum and maximum values</a> for the column data stored on each page. When queries filter on a specific range, like <code>WHERE amount &gt; 1000</code>, readers can use these stats to skip over pages where all values fall below the threshold. This is especially effective on sorted data, where large blocks can often be ruled out early.</p>\n<p>③ <strong>Column chunk-level bloom filters</strong>: Optionally, Parquet files may include a <a target=\"_blank\" href=\"https://parquet.apache.org/docs/file-format/bloomfilter/\">Bloom filter</a> per column per row group. Readers can use these filters to efficiently check whether a value might exist and skip reading column data when it definitely doesn’t.</p>\n<p>④ <strong>Column chunk-level min/max filtering</strong>: Similar to page-level stats, Parquet can <a target=\"_blank\" href=\"https://github.com/apache/parquet-format/blob/3ce0760933b875bc8a11f5be0b883cd107b95b43/src/main/thrift/parquet.thrift#L912\">store</a> min/max statistics at the row group level per column. This allows readers to skip entire columns within a row group if they’re guaranteed to be irrelevant for a query.</p>\n<p>So, how much of this does the ClickHouse Parquet reader support today?</p>\n<p>The current Parquet reader in ClickHouse supports<br>\n③ <strong><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-02#writing-bloom-filters-for-parquet\">Bloom filters</a></strong> (enabled via <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/formats#input_format_parquet_bloom_filter_push_down\">input_format_parquet_bloom_filter_push_down</a> setting) and<br>\n④ <strong><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-23-08#reading-files-faster-michael-kolupaevpavel-kruglov\">row group–level min/max filtering</a></strong> (controlled via <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/formats#input_format_parquet_filter_push_down\">input_format_parquet_filter_push_down</a> setting).</p>\n<p>The upcoming native reader will add support for</p>\n<p>① dictionary filtering and<br>\n② page-level min/max filtering.</p>\n<p>In addition to these built-in Parquet optimizations, the new native reader will also integrate ClickHouse-specific I/O reduction techniques—most notably <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/prewhere\">PREWHERE</a> and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-gets-lazier-and-faster-introducing-lazy-materialization\">lazy materialization</a>—to further reduce unnecessary reads and improve performance.</p>\n<p>With that, we’ve covered how the current Parquet reader in ClickHouse achieves performance through parallelism and I/O reduction, and what improvements are on the horizon.
