Well-integrated into the GCP ecosystem, BigQuery has been applied to a wide range of reporting and batch analytical use cases.</p>\n<p>There is a growing number of scenarios where users need sub-second interactive performance on top of high-throughput streaming data sources. In working to meet these requirements, we increasingly see users <a target=\"_blank\" href=\"https://clickhouse.com/blog/hifis-migration-from-bigquery-to-clickhouse\">deploying ClickHouse alongside BigQuery</a> to speed up queries powering customer-facing applications and internal analytics. This includes both moving data in bulk as well as continuously appending new data using BigQuery scheduled queries and <a target=\"_blank\" href=\"https://cloud.google.com/dataflow\">Google DataFlow</a> (a runner for <a target=\"_blank\" href=\"https://beam.apache.org/\">Apache Beam</a>). We also introduce you to basic data analytics using ClickHouse.</p>\n<h2 id=\"comparing-clickhouse-and-bigquery-use-cases\"></h2>\n<p>BigQuery excels at delivering predictable performance on a diverse range of query access patterns over petabytes of data. Its ability to share compute, shuffle data, and spill to disk means even the most complex deep-analytical queries are served in an acceptable time for analysts and business reports. These capabilities are ideal for ad-hoc querying in low(er) queries-per-second (QPS) scenarios associated with classic data warehousing, especially when query access patterns are unknown or highly variable.</p>\n<p>In contrast, ClickHouse is optimized for use cases that require:</p>\n<ul>\n<li><strong>Sub-second analytical queries</strong> for user-facing applications, where the access patterns are known and predictable. This can sometimes be a subset of the data in Big Query or even the entire dataset for a set of focused analytical queries. Note that whilst never “slow”, BigQuery typically delivers performance in the order of seconds, making building dynamic real-time applications more challenging.</li>\n<li><strong>Potentially unbounded queries per second</strong> as the application usage grows. ClickHouse is designed to serve queries with high concurrency and without enforced limits on the number of parallel queries.</li>\n<li><strong>Support for high insert rates</strong> while still achieving low-latency concurrent queries on recent data, for which data warehouses like BigQuery have not traditionally been optimized.</li>\n</ul>\n<p>These properties are commonly required in external or internal facing applications needing to surface near-real time analytics.</p>\n<p>Pricing models can also be a factor in making technology choices. BigQuery charges for the amount of data scanned, which works well for ad-hoc analytical queries, but can be seen as costly for real-time analytical workloads. Instead, ClickHouse is <a target=\"_blank\" href=\"https://clickhouse.com/clickhouse\">open source</a> and can be deployed on your own infrastructure, or hosted in <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> which charges only based on consumed compute and storage. Note that some of these pricing challenges can be addressed by <a target=\"_blank\" href=\"https://cloud.google.com/bigquery/docs/reservations-intro\">reserving BigQuery slots</a>, but this requires high thresholds of usage not realistic for all users.</p>\n<h2 id=\"setup-and-dataset\"></h2>\n<p>Examples in this blog post utilize <a target=\"_blank\" href=\"https://clickhouse.cloud/signUp?ajs_aid=b44bb600-929d-4c35-9f15-21edd1872094\">ClickHouse Cloud</a>, which has a free trial that allows the completion of the scenarios we cover. Should exports fail and then be fixed, this script can be run as many times as required to fill the missing hours and catch up.</p>\n<p>In its current form, the earlier script means Ethereum data in ClickHouse is at most 85 minutes behind the blockchain - assuming we execute our cron 10 minutes after the incremental export finishes. This would require us to adapt our above import script, likely using a filter - an exercise left to the reader, or consider another tool…</p>\n<h2 id=\"using-dataflow-for-streaming-data-between-bigquery-and-clickhouse\"></h2>\n<p><a target=\"_blank\" href=\"https://cloud.google.com/dataflow\">Google Cloud Dataflow</a> is a fully managed service (<a target=\"_blank\" href=\"https://beam.apache.org/documentation/basics/#runner\">a Runner</a>) for executing Apache Beam pipelines within the Google Cloud Platform ecosystem. <a target=\"_blank\" href=\"https://beam.apache.org/\">Apache Beam</a> is an open-source unified programming model (developed by Google) to define and execute data processing pipelines, including ETL, batch, and stream (continuous) processing. Based on the <a target=\"_blank\" href=\"http://www.vldb.org/pvldb/vol8/p1792-Akidau.pdf\">Dataflow model paper</a>, Dataflow allows users to develop pipelines in either <a target=\"_blank\" href=\"https://beam.apache.org/documentation/sdks/python/\">Python</a>, <a target=\"_blank\" href=\"https://beam.apache.org/documentation/sdks/go/\">Go</a> or <a target=\"_blank\" href=\"https://beam.apache.org/documentation/sdks/java/\">Java</a> and deploy these to GCE to run. These pipelines consist of <a target=\"_blank\" href=\"https://beam.apache.org/documentation/io/connectors/\">I/O connectors</a> that connect to data sources and provide read (source) and write (sink) operations, as well as <a target=\"_blank\" href=\"https://beam.apache.org/documentation/programming-guide/#applying-transforms\">transform operations</a> that facilitate data processing. The key is this framework provides primitives that allow these pipelines and their operations to be <a target=\"_blank\" href=\"https://beam.apache.org/documentation/runtime/model/\">executed in parallel </a>in either a batch or a streaming manner. We strongly recommend users read the <a target=\"_blank\" href=\"https://beam.apache.org/documentation/basics/#runner\">basic concepts</a> if interested in this approach.</p>\n<p>While other datasets may need more transformational logic, we simply want to stream data between BigQuery and ClickHouse. Other than grouping rows into batches (for efficient ClickHouse insertion), no other transformations are required. BigQuery is supported by a <a target=\"_blank\" href=\"https://beam.apache.org/documentation/io/built-in/google-bigquery/\">core I/O connector</a> which provides a <a target=\"_blank\" href=\"https://beam.apache.org/documentation/io/built-in/google-bigquery/#reading-from-bigquery\">simple source interface for reading rows</a>. ClickHouse is supported in Apache Beam through an <a target=\"_blank\" href=\"https://beam.apache.org/releases/javadoc/2.10.0/org/apache/beam/sdk/io/clickhouse/ClickHouseIO.html\">official IO connector</a> for the Java SDK only. Currently, this only offers sink support and requires the target table to exist. While the python SDK does not have built-in support for ClickHouse, Beam provides an easy way to write a <a target=\"_blank\" href=\"https://beam.apache.org/documentation/io/developing-io-overview/#sinks\">sink connector via a ParDo</a> transform. <a target=\"_blank\" href=\"https://medium.com/google-cloud/installing-python-dependencies-in-dataflow-fe1c6cf57784\">Apache Beam’s support for external libraries</a> allows us to use the ClickHouse python client to perform the insertion to ClickHouse. Finally, a simple <a target=\"_blank\" href=\"https://beam.apache.org/releases/pydoc/2.22.0/apache_beam.transforms.util.html#apache_beam.transforms.util.BatchElements\">BatchElements</a> transformation allows us to produce group rows before insertion into ClickHouse. However, a streaming pipeline requires an <a target=\"_blank\" href=\"https://beam.apache.org/documentation/basics/#pcollection\">unbounded source</a>, and since the BigQuery source is bounded, it cannot be used in streaming pipelines. Instead, we use a batch pipeline runs until completion based on a snapshot and then stops. The easiest solution here is to have the pipeline identify the current max timestamp in ClickHouse on start, and use this as filter criteria to BigQuery. This work could also be done as a parallelized ParDo.</li>\n<li>We batch using the <a target=\"_blank\" href=\"https://beam.apache.org/releases/pydoc/2.22.0/apache_beam.transforms.util.html#apache_beam.transforms.util.BatchElements\">BatchElements transform</a> with a fixed size of 10000k. Other datasets may need to adapt this. Note that this transformation can also do adaptive batching.</li>\n<li>We provide dependencies through a requirements.txt file. This is the simplest means to get started, but isn’t recommended in <a target=\"_blank\" href=\"https://medium.com/google-cloud/installing-python-dependencies-in-dataflow-fe1c6cf57784\">production settings</a>.</li>\n</ul>\n<h2 id=\"note-on-continuous-data-loading\"></h2>\n<p>Our approaches to implementing continuous data loading for this specific dataset could in reality be achieved a little more easily, as Google have made it available through other means. The Ethereum data is <a target=\"_blank\" href=\"https://medium.com/google-cloud/live-ethereum-and-bitcoin-data-in-google-bigquery-and-pub-sub-765b71cd57b5\">published by Google on a public Pub/Sub topic</a> where the data can be consumed as it is made available.
