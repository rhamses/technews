The former is where Postgres shines, while the latter can be 100-1000x faster in ClickHouse.</p>\n<p><span><img alt=\"chb_pgonly_diag.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fchb_pgonly_diag_8a9fd8e7ea.jpg&w=2048&q=75\"></span></p>\n<p>With Postgres + ClickHouse, your application backend can send queries to the right database for the job. You avoid needing to oversize Postgres or fight with replication, and improve the user-facing performance and experience. Prototyping the new architecture can take a few weeks, particularly if it's your first time with ClickHouse, while you identify the right queries to migrate, setup data synchronization, and update backend integration. Building this prototype is where clickhouse.build can help.</p>\n<p><span><img alt=\"chb_pg_and_ch_diag.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fchb_pg_and_ch_diag_b7774d3bf6.jpg&w=2048&q=75\"></span></p></div><div><h2 id=\"how-clickhouse-build-works\"></h2>\n<p>The clickhouse.build CLI uses multiple, task-specific agents to migrate Postgres-backed TypeScript apps to a Postgres+ClickHouse architecture. These agents can be used independently, or called via an all-in-one workflow. A Quality Assurance (QA) sub-agent checks every proposed code change, which has been augmented with high-quality reference examples.</p>\n<p>There are 3 primary agents:</p>\n<h3 id=\"scanner\"></h3>\n<p>The scanner agent scans your TypeScript code base and looks for Postgres queries. It currently works whether you use a direct Postgres driver with queries in code, or using the query builders of Prisma and Drizzle ORMs.</p>\n<p>When it finds queries, it will inspect them to determine whether the query is better suited for Postgres or ClickHouse: single-row lookups and insert/update/delete operations are typically best fit for Postgres, while COUNTs, SUMs and GROUP BYs are more optimal in ClickHouse. The scanner agent produces a structured output report with the identified queries that should be migrated to ClickHouse.</p></div><div><p><em>A demo of the scanner agent, called on its own outside of the all-in-one workflow</em></p>\n<h3 id=\"data-migrator\"></h3>\n<p>The data migrator agent assists in syncing the necessary Postgres tables to ClickHouse. Based on the queries identified by the scanner agent, it determines which tables ClickHouse needs to serve the queries. It then generates the relevant ClickPipes API payloads to configure the <a target=\"_blank\" href=\"https://clickhouse.com/docs/integrations/clickpipes/postgres\">ClickPipes Postgres CDC connector</a>. This connector keeps ClickHouse in sync with Postgres, first backfilling all historical data, and then maintaining a continuous, real-time flow of changes from Postgres to ClickHouse.</p></div><div><p><em>A demo of the data migrator agent, called on its own outside of the all-in-one workflow</em></p>\n<h3 id=\"code-migrator\"></h3>\n<p>The code migrator agent handles the job of updating queries and code. It can adjust SQL syntax to be correct for ClickHouse (queries between Postgres and ClickHouse are often compatible without change, but not always, especially if ORM query builders are used), and update TypeScript code to call ClickHouse via the <a target=\"_blank\" href=\"https://clickhouse.com/docs/integrations/javascript\">official ClickHouse JS client</a>. This agent will pause the migrations after each significant step, requesting input for the human to accept or reject the changes proposed. It’s also possible to accept all changes in one command.</p>\n<p>Rather than remove your existing, working Postgres queries, the code migrator uses a backwards compatible indirection pattern. The queries for each database are moved to separate utility files, and a feature flag lets you pick which backend to use at run time. This means you can easily toggle between the two modes to compare performance and correctness while you evaluate your resulting application.</p>\n<h4 id=\"qa-agent\"></h4>\n<p>The QA agent is a sub-agent of the code migrator, which validates any changes made. The code migrator will suggest what it wants to do, and then ask the QA agent if the change is appropriate. The QA agent scans the change and runs checks and validations comparing patterns against patterns from a series of reference code bases that already use Postgres+ClickHouse successfully.</p></div><div><p><em>A demo of the code migrator agent, called on its own outside of the all-in-one workflow</em></p>\n<h3 id=\"all-in-one-workflow\"></h3>\n<p>While each agent can be used on its own, the CLI has an all-in-one workflow that invokes each agent in the correct order (scanner -&gt; data migrator -&gt; code migrator). This is generally the recommended way to use the CLI for your PoC, but we won’t hold it against you if you want to call the agents yourself.</p>\n<h2 id=\"using-clickhouse-build\"></h2>\n<p>You can get the CLI from the <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhouse.build\">clickhouse.build GitHub repo</a>. The README contains detailed instructions on setting up and configuring the CLI.</p>\n<p>With the CLI configured, <strong>we recommend creating a new branch in your application repository to work in</strong>. You can then run the all-in-one migration workflow:</p>\n<div><pre><code><span>uv run main.py migrate /path/to/your/repo --replication-mode cdc</span></code></pre></div>\n<p>This will walk through all agents in order: scanner -&gt; data migrator -&gt; code migrator. <strong>The agents are not fully autonomous</strong> by default. The CLI will prompt you to review and accept/deny changes as you go, though you can choose to “accept all” if you wish.</p>\n<p>The scanner agent will go through your code, discover your Postgres queries, and output a structured JSON file of the queries, a description, and their file location. The data migrator agent will read this scan file and extract the names of tables that need to be replicated into ClickHouse. With the <code>--replication-mode cdc</code> option set, the <strong>data migrator agent will produce the <code>curl</code> commands needed to configure ClickPipes Postgres CDC</strong> via the <a target=\"_blank\" href=\"https://clickhouse.com/docs/cloud/manage/api/api-overview\">ClickHouse Cloud API</a>.</p>\n<p>Currently, <strong>the ClickPipes configuration commands require some manual input</strong>. Along with the command, the output contains some environment variables you’ll need to complete some details about your ClickHouse Cloud account and Postgres instance. With these details completed, you’ll need to run the <code>curl</code> commands yourself.</p></div><div><p><em>A demo of running the ClickPipes configuration commands and validating the running ClickPipes service in ClickHouse Cloud</em></p>\n<p>The code migrator agent is the final piece of the workflow. It begins by loading the scan file and installing the <a target=\"_blank\" href=\"https://clickhouse.com/docs/integrations/javascript\">clickhouse.js driver</a> using your project’s package manager. After loading some reference examples of Postgres+ClickHouse implementations in its context, the agent begins analysing your code base to build a plan of what to change.</p>\n<p>The agent aims to implement the ‘strategy pattern’, where the specific backend implementation is abstracted. This pattern means you can toggle between using the original Postgres backend or the new ClickHouse+Postgres backend with a simple feature flag. A file for each of Postgres and ClickHouse is created under <code>lib/strategies</code> which contains the logic for serving your queries via each of the respective databases. The agent will attempt to find the correct way to integrate this into your project, which means the next step can vary a bit. A common pattern is to create a database configuration at <code>lib/db.ts</code> which implements the logic to toggle between these strategies, and then update your existing routes to use the backend as configured in <code>db.ts</code>.</p>\n<p>With each step, you’ll be asked to review the changes (unless you have chosen to accept all), and the QA sub-agent will automatically review changes for baseline quality against the reference examples.</p>\n<p>The workflow will wrap up by ensuring your project builds, producing a summary of the changes it made, and instructions on how to use the feature flag to toggle between strategies. You can now evaluate the impact of using ClickHouse in your application.</p>\n<h3 id=\"evaluating-the-result\"></h3>\n<p>You can run your application as normal, and it should continue to use your existing Postgres implementation by default. To use the new ClickHouse implementation, <strong>add the new feature flag to your environment variables: <code>USE_CLICKHOUSE=true</code></strong>. You can flip this flag to <code>false</code> to switch back.</p></div><div><p><em>A demo of an application being switched between Postgres and ClickHouse backends, showing a 3x gain in performance.</em></p>\n<p>We recommend testing the normal flows of your application, having new rows inserted into Postgres to test replication, and comparing the performance of features with and without the ClickHouse feature flag enabled.</p>\n<p>In many cases, the difference is immediately obvious; you should see that stats, charts, and tables that display analytics load several times faster without perceptible latency. Though it can be more fun to put some logging in and see the real numbers!</p>\n<p>The change in performance you’ll see can be variable, but generally, the larger your data, the bigger the performance gain.</p>\n<h2 id=\"the-clickhouse-build-design-principles\"></h2>\n<p>clickhouse.build is a highly opinionated implementation. Its design is informed by lessons we have learned building agents for <a target=\"_blank\" href=\"https://clickhouse.com/blog/ai-first-data-warehouse\">data warehousing</a>, <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=og8ieNxixp4\">for SREs</a>, and <a target=\"_blank\" href=\"https://clickhouse.com/blog/agent-facing-analytics\">agentic analytics</a>.</p>\n<p>We believe that the best agentic flows <strong>keep the human in the loop</strong>, not only keeping you informed, but also involved in the actions that are taken. <strong>Backwards compatibility</strong> ensures we can validate correctness and assess the real impact of changes.</p>\n<p>Agentic workflows are new, our understanding is still evolving, and we should approach changes to production with caution, but <strong>agents are an obvious accelerator in development and proof of concepts</strong>.</p>\n<p>Agents can be tuned for different tasks by supplying specific context and instructions, which means <strong>we can have one agent optimised to make changes, and another optimised to validate those changes</strong>. We’ve seen that this can be effective in reducing errors, but it isn’t always perfect - that’s why we keep the human around, too.</p>\n<p><strong>Evaluations might just be the highest impact and under-explored area</strong> that we see in agentic workflows today. Getting to an 80% level of quality can be achieved relatively easily, but going beyond this barrier takes significant effort. We think this is where evaluations become critical, allowing us to constantly review, assess, and improve. But they can also be hard to do, and easy to forget. To mitigate this, we aim to bake evaluations into the workflow itself, adopting new techniques and tooling as the space develops.</p>\n<p><strong>Open-source is the way forward.</strong> There’s no secret sauce behind clickhouse.build.
