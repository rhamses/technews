id=\"introduction\"></h2>\n<p>ClickHouse is the fastest and most resource-efficient database for real-time applications and analytics. Tables from the family of MergeTree table engines are a core component of ClickHouse’s fast data processing capabilities. In this post, we describe the motivation and mechanics behind a new member of this family – the SharedMergeTree table engine.</p>\n<p>This table engine is a more efficient drop-in replacement for the ReplicatedMergeTree table engine in <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> and is engineered and optimized for cloud-native data processing. We look under the hood of this new table engine, explain its benefits, and demonstrate its efficiency with a benchmark. And we have one more thing for you. We are introducing lightweight updates which have a synergy effect with the SharedMergeTree.</p>\n<h2 id=\"mergetree-table-engines-are-the-core-of-clickhouse\"></h2>\n<p>Table engines from the MergeTree family are the main <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines\">table engines</a> in ClickHouse. They are responsible for storing the data received by an insert query, merging that data in the background, applying engine-specific data transformations, and more. Automatic <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/replication\">data replication</a> is supported for most tables in the MergeTree family through the replication mechanism of the <code>ReplicatedMergeTree</code> base table engine.</p>\n<p>In traditional <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Shared-nothing_architecture\">shared-nothing</a> ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/company/events/scaling-clickhouse\">clusters</a>, replication via ReplicatedMergeTree is used for data availability, and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/architecture/horizontal-scaling\">sharding</a> can be used for cluster scaling. <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> took a new approach to build a cloud-native database service based on ClickHouse, which we describe below.</p>\n<h2 id=\"clickhouse-cloud-enters-the-stage\"></h2>\n<p>ClickHouse Cloud <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-public-beta\">entered</a> public beta in October 2022 with a radically different <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/reference/architecture\">architecture</a> optimized for the cloud (and we <a target=\"_blank\" href=\"https://clickhouse.com/blog/building-clickhouse-cloud-from-scratch-in-a-year\">explained</a> how we built it from scratch in a year). By storing data in virtually limitless <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Shared-disk_architecture\">shared</a> <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Object_storage\">object storage</a>, storage and compute are separated: All <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Scalability#Horizontal_or_scale_out\">horizontally</a> and <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Scalability#Vertical_or_scale_up\">vertically</a> scalable ClickHouse servers have access to the same physical data and are effectively multiple replicas of a single limitless <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/architecture/horizontal-scaling#shard\">shard</a>:<br>\n<span><img alt=\"smt_01.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsmt_01_d28f858be6.png&w=2048&q=75\"></span></p>\n<h3 id=\"shared-object-storage-for-data-availability\"></h3>\n<p>Because ClickHouse Cloud stores all data in shared object storage, there is no need to create physical copies of data on different servers explicitly. Object storage implementations like Amazon AWS <a target=\"_blank\" href=\"https://aws.amazon.com/s3/\">Simple Storage Service</a>, Google GCP <a target=\"_blank\" href=\"https://cloud.google.com/storage\">Cloud Storage</a>, and Microsoft Azure <a target=\"_blank\" href=\"https://azure.microsoft.com/en-us/products/storage/blobs/\">Blob Storage</a> ensure storage is highly available and fault tolerant.</p>\n<p>Note that ClickHouse Cloud services feature a multi-layer <a target=\"_blank\" href=\"https://en.wiktionary.org/wiki/read-through\">read-through</a> and <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Cache_(computing)#WRITE-THROUGH\">write-through</a> cache (on local <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Non-volatile_memory\">NVM</a>e SSDs) that is designed to work natively on top of object storage to provide fast analytical query results despite the slower access latency of the underlying primary data store. Object storage exhibits slower access latency, but provides highly concurrent throughput with  large aggregate bandwidth. ClickHouse Cloud exploits this by <a target=\"_blank\" href=\"https://clickhouse.com/docs/knowledgebase/async_vs_optimize_read_in_order#asynchronous-data-reading\">utilizing</a> multiple I/O threads for accessing object storage data, and by asynchronously <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/whats-new/cloud#performance-and-reliability-3\">prefetching</a> the data.</p>\n<h3 id=\"automatic-cluster-scaling\"></h3>\n<p>Instead of using sharding for scaling the cluster size, ClickHouse Cloud allows users to simply increase the size and number of the servers operating on top of the shared and virtually infinite object storage. This increases the parallelism of data processing for both INSERT and SELECT queries.</p>\n<p>Note that the ClickHouse Cloud servers are effectively multiple replicas of a single limitless shard, but they are not like replica servers in shared-nothing clusters. Instead of containing local copies of the same data, these servers have access to the same data stored in shared object storage. This turns these servers into dynamic compute units or compute nodes, respectively, whose size and number can be easily adapted to workloads. Either manually or fully <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/reference/architecture#compute\">automatically</a>. This diagram illustrates that:\n<span><img alt=\"smt_02.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsmt_02_a2d0b54be6.png&w=2048&q=75\"></span>\n① Via scale up and ② scale down operations, we can change the size (amount of CPU cores and RAM) of a node. And per ③ scale out, we can increase the number of nodes participating in parallel data processing. Without requiring any physical resharding or rebalancing of the data, we can freely add or remove nodes.</p>\n<p>For this cluster scaling approach, ClickHouse Cloud needs a table engine supporting higher numbers of servers accessing the same shared data.</p>\n<h2 id=\"challenges-with-running-replicatedmergetree-in-clickhouse-cloud\"></h2>\n<p>The ReplicatedMergeTree table engine isn’t ideal for the intended architecture of ClickHouse Cloud since its replication mechanism is designed to create physical copies of data on a small number of replica servers. Whereas ClickHouse Cloud requires an engine with support for a high amount of servers on top of shared object storage.</p>\n<h3 id=\"explicit-data-replication-is-not-required\"></h3>\n<p>We briefly explain the replication mechanism of the ReplicatedMergeTree table engine. This engine uses <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/sre/keeper/clickhouse-keeper\">ClickHouse Keeper</a> (also referred to as “Keeper”) as a coordination system for data replication via a <a target=\"_blank\" href=\"https://youtu.be/vBjCJtw_Ei0?t=1150\">replication log</a>. Keeper acts as a central store for replication-specific metadata and table schemas and as a <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Consensus_(computer_science)\">consensus</a> system for distributed operations. Keeper ensures sequential block numbers are assigned in order for part names. Assignment of <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#data-needs-to-be-batched-for-optimal-performance\">merges</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter#mutations\">mutations</a> to specific replica servers is made with the consensus mechanisms that Keeper provides.</p>\n<p>The following diagram sketches a shared-nothing ClickHouse cluster with 3 replica servers and shows the data replication mechanism of the ReplicatedMergeTree table engine:\n<span><img alt=\"smt_03.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsmt_03_21a5b48f65.png&w=2048&q=75\"></span>\nWhen ① server-1 receives an insert query, then ② server-1 creates a new data <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#mergetree-data-storage\">part</a> with the query's data on its local disk. ③ Via the replication log, the other servers (server-2, server-3) are informed that a new part exists on server-1. At ④, the other servers independently download (“fetch”) the part from server-1 to their own local filesystem. After creating or receiving parts, all three servers also update their own metadata describing their set of parts in Keeper.</p>\n<p>Note that we only showed how a newly created part is replicated. Part merges (and mutations) are replicated in a similar way. If one server decides to merge a set of parts, then the other servers will automatically execute the same merge operation on their local part copies (or just <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/merge-tree-settings#always_fetch_merged_part\">download</a> the merged part).</p>\n<p>In case of a complete loss of local storage or when new replicas are added, the ReplicatedMergeTree clones data from an existing replica.</p>\n<p>ClickHouse Cloud uses durable shared object storage for data availability and doesn’t need the explicit data replication of the ReplicatedMergeTree.</p>\n<h3 id=\"sharding-for-cluster-scaling-is-not-needed\"></h3>\n<p>Users of shared-nothing ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/company/events/scaling-clickhouse\">clusters</a> can use replication in combination with <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/architecture/horizontal-scaling\">sharding</a> for handling larger datasets with more servers. The table data is split over multiple servers in the form of <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/architecture/horizontal-scaling#shard\">shards</a> (distinct subsets of the table’s data parts), and each shard usually has 2 or 3 replicas to ensure storage and data availability. Parallelism of data ingestion and query processing can be <a target=\"_blank\" href=\"https://clickhouse.com/company/events/scaling-clickhouse\">increased</a> by adding more shards. Note that ClickHouse abstracts clusters with more complex topologies under a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/distributed\">distributed table</a> so that you can do distributed queries in the same way as local ones.</p>\n<p>ClickHouse Cloud doesn’t need sharding for cluster scaling, as all data is stored in virtually limitless shared object storage, and the level of parallel data processing can be simply increased by adding additional servers with access to the shared data. However, the replication mechanism of the ReplicatedMergeTree is designed initially to work on top of local filesystems in shared-nothing cluster architectures and with a small number of replica servers. Having a high number of replicas of ReplicatedMergeTree is an <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Anti-pattern\">anti-pattern</a>, with the servers creating too much <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Resource_contention\">contention</a> on the replication log and overhead on the inter-server communication.</p>\n<h2 id=\"zero-copy-replication-does-not-address-the-challenges\"></h2>\n<p>ClickHouse Cloud offers automatic vertical scaling of servers – the number of CPU cores and RAM of servers is automatically adapted to workloads based on CPU and memory pressure. We started with each ClickHouse Cloud service having a fixed number of 3 servers and eventually introduced horizontal scaling to an arbitrary number of servers.</p>\n<p>In order to support these advanced scaling operations on top of shared storage with ReplicatedMergeTree, ClickHouse Cloud used a special modification called <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/storing-data#zero-copy\">zero-copy replication</a> for adapting the ReplicatedMergeTree tables’ replication mechanism to work on top of shared object storage.</p>\n<p>This adaptation uses almost the same original replication model, except that only one copy of data is stored in object storage. Hence the name zero-copy replication. Zero data is replicated between servers. Instead, we replicate just the metadata:\n<span><img alt=\"smt_04.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsmt_04_712af233a0.png&w=2048&q=75\"></span>\nWhen ① server-1 receives an insert query, then ② the server writes the inserted data in the form of a part to object storage, and ③ writes metadata about the part (e.g., where the part is stored in object storage) to its local disk. ④ Via the replication log, the other servers are informed that a new part exits on server-1, although the actual data is stored in object storage. And ⑤ the other servers independently download (“fetch”) the metadata from server-1 to their own local filesystem. To ensure data is not deleted until all the replicas remove metadata pointing to the same object, a distributed mechanism of reference counting is used: After creating or receiving metadata, all three servers also update their own metadata set of parts info in ClickHouse Keeper.</p>\n<p>For this, and for assigning operations like merges and mutations to specific servers, the zero-copy replication mechanism relies on creating exclusive <a target=\"_blank\" href=\"https://zookeeper.apache.org/doc/r3.1.2/recipes.html#sc_recipes_Locks\">locks</a> in Keeper. Meaning that these operations can block each other and need to wait until the currently executed operation is finished.</p>\n<p>Zero-copy replication does not sufficiently address the challenges with ReplicatedMergeTree on top of shared object storage:</p>\n<ul>\n<li>Metadata is still coupled with servers: metadata storage is not separated from compute. Zero-copy replication still requires a local disk on each server for storing the metadata about parts. Local disks are additional points of failure with reliability depending on the number of replicas, which is tied to compute overhead for high availability.</li>\n<li>Durability of zero-copy replication depends on guarantees of 3 components: object storage, Keeper, and local storage. This number of components adds complexity and overhead as this stack was built on top of existing components and not reworked as a cloud-native solution.</li>\n<li>This is still designed for a small number of servers: metadata is updated using the same replication model designed initially for shared-nothing cluster architectures with a small number of replica servers. A high number of servers creates too much contention on the replication log and creates a high overhead on locks and inter-server communication. Additionally, there is a lot of complexity in the code implementing the replication and cloning of data from one replica to another. And it is impossible to make atomic commits for all replicas as metadata is changed independently.</li>\n</ul>\n<p>We decided (and <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/issues/44767\">planned</a> from the beginning) to implement a new table engine from scratch for ClickHouse Cloud called <span>Shared</span>MergeTree – designed to work on top of a <span>shared</span> storage. The SharedMergeTree is the cloud-native way for us to (1) make the MergeTree code more straightforward and maintainable, (2) to <a target=\"_blank\" href=\"https://clickhouse.com/blog/changes\">support</a> not only vertical but also horizontal auto-scaling of servers, and (3) to enable future features and improvements for our Cloud users, like higher consistency guarantees, better durability, point-in-time restores, time-travel through data, and more.</p>\n<p>Here we describe briefly how the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/shared-merge-tree\">SharedMergeTree</a> natively supports ClickHouse Cloud's automatic cluster scaling <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates#automatic-cluster-scaling\">model</a>. As a reminder: the ClickHouse Cloud servers are compute units with access to the same shared data whose size and number can be automatically changed. For this mechanism, the SharedMergeTree completely separates the storage of data and metadata from the servers and uses interfaces to Keeper to read, write and modify the shared metadata from all servers. Each server has a local cache with subsets of the metadata and gets automatically informed about data changes by a subscription mechanism.</p>\n<p>This diagram sketches how a new server is added to the cluster with the SharedMergeTree:\n<span><img alt=\"smt_05.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsmt_05_a45df09927.png&w=2048&q=75\"></span>\nWhen server-3 is added to the cluster, then this new server ① subscribes for metadata changes in Keeper and fetches parts of the current metadata into its local cache. This doesn't require any locking mechanism; the new server basically just says, \"Here I am. Please keep me up to date about all data changes\". The newly added server-3 can participate in data processing almost instantly as it finds out what data exists and where in object storage by fetching only the necessary set of shared metadata from Keeper.</p>\n<p>The following diagram shows how all servers get to know about newly inserted data:\n<span><img alt=\"smt_06.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsmt_06_dbf29bf0dc.png&w=2048&q=75\"></span>\nWhen ① server-1 receives an insert query, then ② the server writes the query’s data in the form of a part to object storage. ③ Server-1 also stores information about the part in its local cache and in Keeper (e.g., which files belong to the part and where the blobs corresponding to files reside in object storage). After that, ④ ClickHouse acknowledges the insert to the sender of the query. The other servers (server-2, server-3) are ⑤ automatically notified about the new data existing in object storage via Keeper’s subscription mechanism and fetch metadata updates into their local caches.</p>\n<p>Note that the insert query’s data is durable after step ④. Even if Server-1 crashes, or any or all of the other servers, the part is stored in highly available object storage, and the metadata is stored in Keeper (which has a highly available setup of at least 3 Keeper servers).</p>\n<p>Removing a server from the cluster is a straightforward and fast operation too. For a graceful removal, the server just deregisters himself from Keeper in order to handle ongoing distributed queries properly without warning messages that a server is missing.</p>\n<h2 id=\"benefits-for-clickhouse-cloud-users\"></h2>\n<p>In ClickHouse Cloud, the SharedMergeTree table engine is a more efficient drop-in replacement for the ReplicatedMergeTree table engine. Bringing the following powerful benefits to ClickHouse Cloud users.</p>\n<h3 id=\"seamless-cluster-scaling\"></h3>\n<p>ClickHouse Cloud stores all data in virtually infinite, durable, and highly available shared object storage. The SharedMergeTree table engine adds shared metadata storage for all table components. It enables virtually limitless scaling of the servers operating on top of that storage. Servers are effectively stateless compute nodes, and we can almost instantly change their size and number.</p>\n<h4 id=\"example\"></h4>\n<p>Suppose a ClickHouse Cloud user is currently using three nodes, as shown in this diagram:\n<span><img alt=\"smt_07.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsmt_07_9e7ecdd514.png&w=2048&q=75\"></span>\nIt is straightforward to (manually or automatically) double the amount of compute by either doubling the size of each node or (for example, when the maximum size per node is reached) by doubling the number of nodes from three to six:\n<span><img alt=\"smt_08.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsmt_08_a32f622149.png&w=2048&q=75\"></span>\nThis <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates#sharedmergetree-in-action\">doubles</a> the ingest throughput. For SELECT queries, increasing the number of nodes increases the level of parallel data processing for both the execution of concurrent queries and the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-23-03#parallel-replicas-for-utilizing-the-full-power-of-your-replicas-nikita-mikhailov\">concurrent execution of a single query.</a> Note that increasing (or decreasing) the number of nodes in ClickHouse Cloud doesn’t require any physical resharding or rebalancing of the actual data. We can freely add or remove nodes with the same effect as manual sharding in shared-nothing clusters.</p>\n<p>Changing the number of servers in a shared-nothing cluster requires more effort and time. If a cluster currently consists of three shards with two replicas per shard:\n<span><img alt=\"smt_09.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsmt_09_52c758d36c.png&w=2048&q=75\"></span>\nThen doubling the number of shards requires resharding and rebalancing of the currently stored data:\n<span><img alt=\"smt_10.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsmt_10_43b84bbb96.png&w=2048&q=75\"></span></p>\n<h3 id=\"automatic-stronger-durability-for-insert-queries\"></h3>\n<p>With the ReplicatedMergeTree, you can use the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-insert_quorum\">insert_quorum</a> setting for ensuring data durability. You can configure that an insert query only returns to the sender when the query’s data (meta-data in case of zero-copy replication) is stored on a specific number of replicas. For the SharedMergeTree, insert_quorum is not needed. As shown above, when an insert query successfully returns to the sender, then the query’s data is stored in highly available object storage, and the metadata is stored centrally in Keeper (which has a highly available setup of at least 3 Keeper servers).</p>\n<h3 id=\"more-lightweight-strong-consistency-for-select-queries\"></h3>\n<p>If your use case requires consistency guarantees that each server is delivering the same query result, then you can run the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/system#sync-replica\">SYNC REPLICA</a> system statement, which is a much more lightweight operation with the SharedMergeTree. Instead of syncing data (or metadata with zero-copy replication) between servers, each server just needs to fetch the current version of metadata from Keeper.</p>\n<h3 id=\"improved-throughput-and-scalability-of-background-merges-and-mutations\"></h3>\n<p>With the SharedMergeTree, there is no performance degradation with higher amounts of servers. The throughput of background merges scales with the number of servers as long as Keeper has enough resources. The same is true for <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter#mutations\">mutations</a> which are implemented via explicitly triggered and (by <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#mutations_sync\">default</a>) asynchronously executed merges.</p>\n<p>This has positive implications for other new features in ClickHouse, like <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates#introducing-lightweight-updates-powered-by-sharedmergetree\">lightweight updates</a>, which get a performance boost from the SharedMergeTree. Similarly, engine-specific <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/cascading-materialized-views\">data transformations</a> (aggregations for <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/aggregatingmergetree\">AggregatingMergeTree</a>, deduplication for <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/replacingmergetree\">ReplacingMergeTree</a>, etc.) benefit from the better merge throughput of the SharedMergeTree. These transformations are incrementally applied during background part merges. To ensure correct query results with potentially unmerged parts, users need to merge the unmerged data at query time by utilising the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/from#final-modifier\">FINAL</a> modifier or using explicit GROUP BY clauses with aggregations. In both cases, the execution speed of these queries benefits from better merge throughput. Because then the queries have less query-time data merge work to do.</p>\n<h2 id=\"the-new-clickhouse-cloud-default-table-engine\"></h2>\n<p>The SharedMergeTree table engine is now generally available as the default table engine in ClickHouse Cloud for new Development tier services. Please reach out to us if you would like to create a new Production tier service with the SharedMergeTree table engine.</p>\n<p>All table engines from the MergeTree family that are <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/whats-new/cloud-compatibility#database-and-table-engines\">supported</a> by ClickHouse Cloud are automatically based on the SharedMergeTree. A mutation is a heavyweight operation that rewrites parts, either synchronously or asynchronously.</p>\n<h4 id=\"synchronous-mutations\"></h4>\n<p><span><img alt=\"smt_20.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsmt_20_fc56fe2e17.png&w=2048&q=75\"></span>\nIn our example scenario above, ClickHouse ① receives an insert query for an initially empty table, ② writes the query’s data into a new data part on storage, and ③ acknowledges the insert. Next, ClickHouse ④ receives an update query and executes that query by ⑤ mutating Part-1. The part is loaded into the main memory, the modifications are done, and the modified data is written to a new Part-2 on storage (Part-1 is deleted). Only when that part rewrite is finished, ⑥ the acknowledgment for the update query is returned to the sender of the update query.  Additional update queries (which can also delete data) are executed in the same way. For larger parts, this is a very heavy operation.</p>\n<h4 id=\"asynchronous-mutations\"></h4>\n<p>By <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#mutations_sync\">default</a>, update queries are executed asynchronously in order to fuse several received updates into a single mutation for mitigating the performance impact of rewriting parts:\n<span><img alt=\"smt_21.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsmt_21_f1b7f214ce.png&w=2048&q=75\"></span>\nWhen ClickHouse ① receives an update query, then the update is added to a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/mutations\">queue</a> and executed asynchronously, and ② the update query immediately gets an acknowledgment for the update.</p>\n<p>Note that SELECT queries to the table don’t see the update before it ⑤ gets materialized with a background mutation.</p>\n<p>Also, note that ClickHouse can fuse queued updates into a single part rewrite operation. For this reason, it is a best practice to batch updates and send 100s of updates with a single query.</p>\n<h3 id=\"lightweight-updates\"></h3>\n<p>The aforementioned explicit batching of update queries is no longer necessary, and from the user's perspective, modifications from single update queries, even when being materialized asynchronously, will occur instantly.</p>\n<p>This diagram sketches the new lightweight and instant update <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/lightweght-update\">mechanism</a> in ClickHouse:\n<span><img alt=\"smt_22.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsmt_22_e303a94b55.png&w=2048&q=75\"></span>\nWhen ClickHouse ① receives an update query, then the update is added to a queue and executed asynchronously. ② Additionally, the update query’s update expression is put into the main memory. The update expression is also stored in Keeper and distributed to other servers.  When ③ ClickHouse receives a SELECT query before the update is materialized with a part rewrite, then ClickHouse will execute the SELECT query as usual - use the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes\">primary index</a> for reducing the set of rows that need to be streamed from the part into memory, and then the update expression from ② is applied to the streamed rows on the fly. That is why we call this mechanism <code>on [the] fly</code> mutations. When ④ another update query is received by ClickHouse, then ⑤ the query’s update (in this case a delete) expression is again kept in main memory, and ⑥ a succeeding SELECT query will be executed by applying both (②, and ⑤) update expressions on the fly to the rows streamed into memory. The on-the-fly update expressions are removed from memory when ⑦ all queued updates are materialized with the next background mutation. ⑧ Newly received updates and ⑩ SELECT queries are executed as described above.</p>\n<p>This new mechanism can be enabled by simply setting the <code>apply_mutations_on_fly</code> setting to <code>1</code>.</p>\n<h4 id=\"benefits\"></h4>\n<p>Users don’t need to wait for mutations to materialize. ClickHouse delivers updated results immediately, while using less resources. Furthermore, this makes updates easier to use for ClickHouse users, who can send updates without having to think about how to batch them.</p>\n<h4 id=\"synergy-with-the-sharedmergetree\"></h4>\n<p>From the user's perspective, modifications from lightweight updates will occur instantly, but users will experience slightly reduced SELECT query performance until updates are materialized because the updates are executed at query time in memory on the streamed rows. As updates are materialized as part of merge operations in the background, the impact on query latency goes away. The SharedMergeTree table engine comes with <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates#improved-throughput-and-scalability-of-background-merges-and-mutations\">improved throughput and scalability of background merges and mutations</a>, and as a result, mutations complete faster, and SELECT queries after lightweight updates return to full speed sooner.</p>\n<h4 id=\"what-s-next\"></h4>\n<p>The mechanics of lightweight updates that we described above are just the first step.
