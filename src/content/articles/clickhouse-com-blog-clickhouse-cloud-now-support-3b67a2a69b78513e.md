Historically, users wanting to monitor ClickHouse Cloud would rely on querying system tables for the metrics they needed. This represented friction for many infrastructure engineers who would need to explore and extract metrics from system tables using SQL. Even if proficient in SQL, in many cases, constructing the correct queries in ClickHouse and finding the appropriate system table could be time-consuming. This could be overcome with some careful configuration and use of the clusterAllReplicas function, these integrations would also suffer a common problem: their continued polling for metrics via SELECT queries would mean instances would never idle.</p>\n<p>Given that our users rely on the ability of ClickHouse Cloud instances to idle when not used, thus minimizing compute costs, this behavior, which coupled with monitoring usage, was highly undesirable and a blocker for many users.</p>\n<p>Finally, the Prometheus format is now almost a standard for this form of data and is supported by popular tools such as Grafana and Datadog with out-of-box integrations.</p>\n<p>A simple endpoint that delivered Prometheus metrics for an instance without preventing unused instances from idling or waking up was clearly the preferred solution.</p>\n<h2 id=\"a-simple-and-elegant-design\"></h2>\n<p>Any endpoint thus had some quite simple requirements:</p>\n<ul>\n<li><strong>Deliver metrics in Prometheus format</strong> - compatible with existing commonly used monitoring agents.</li>\n<li><strong>No waking of idling instances</strong> - these should just return a simple message denoting their state.</li>\n<li><strong>Not prevent instances from idling</strong> - requests to this endpoint should not be considered  when determining whether an instance should be idled.</li>\n</ul>\n<p>While we could have possibly delivered this capability through configuration for each ClickHouse instance, e.g. using the existing ability to configure a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/server-configuration-parameters/settings#prometheus\">Prometheus endpoint in ClickHouse</a>, this represented an imperfect solution for our users. Ensuring these requests were not forwarded when an instance was idle was technically not elegant to implement. Furthermore, it meant users would need to create a user with appropriate roles and permissions for each instance and distribute these credentials to their agent. For many organizations, this would represent a security risk and seem unnecessarily complicated.</p>\n<p>The logical place for this endpoint to sit was our <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/manage/api/api-overview\">existing Cloud API</a>. This API already allows users to create and configure instances. Furthermore, it provides an organizational-level access control where users can create (and revoke!) API keys with a few clicks. By exposing this endpoint through the Cloud API, we could minimize the security attack surface and provide a simple-to-use endpoint that requires no knowledge of ClickHouse or SQL!</p>\n<p>We have, therefore, provided a single simple Cloud API endpoint where users can securely request Prometheus metrics for a specific organization and instance.</p>\n<p><span><img alt=\"prometheus_01.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fprometheus_01_a5a8008aad.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p>API keys are organization level and can be defined as either \"Developer\" or \"Admin\". Developer access permissions are sufficient for the Prometheus endpoints, ensuring compromise credentials do not allow services to be created or disrupted.</p>\n</blockquote>\n<h2 id=\"implementation\"></h2>\n<p>The decision to implement the endpoint through the Cloud API meant the implementation remained simple. The Cloud API is already aware of the state of each instance, allowing it to not issue the request to idling instances. Assuming the instance is running, the request is made using a specific user with limited permission scope. The requests from this user are subsequently ignored by the data plane when considering whether to idle instances.</p>\n<h3 id=\"efficient-metric-collection\"></h3>\n<p>This just left the appropriate query for the system tables to be formulated. Given that the metrics we expected users would be interested in collecting were spread across many system tables, the resulting query is quite complex and has an appreciable overhead. To avoid issuing this query on every request to the endpoint, we exploit a recently released <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-23-12#refreshable-materialized-views\">ClickHouse feature: Refreshable Materialized Views</a>.</p>\n<p>This view periodically (currently every minute) executes the query, sending the results to a target table <code>system.custom_metrics</code>, and atomically its current rows. This target table, which contains only the result set, uses the Memory engine and can be efficiently queried by the Cloud API. For the curious reader, we show the table and a sample of the view below:</p>\n<div><pre><code><span><span>CREATE TABLE</span> system.custom_metrics</span>\n<span>(</span>\n<span>\t`name` String,</span>\n<span>\t`<span>value</span>` Float64,</span>\n<span>\t`help` String,</span>\n<span>\t`labels` Map(String, String),</span>\n<span>\t`type` String</span>\n<span>)</span>\n<span>ENGINE <span>=</span> Memory</span></code></pre></div>\n<div><pre><code><span><span>CREATE</span> MATERIALIZED <span>VIEW</span> system.custom_metrics_refresher</span>\n<span>REFRESH <span>EVERY</span> <span>1</span> <span>MINUTE</span> <span>TO</span> system.custom_metrics</span>\n<span>(</span>\n<span>\t`name` String,</span>\n<span>\t`<span>value</span>` Nullable(Float64),</span>\n<span>\t`help` String,</span>\n<span>\t`labels` Map(String, String),</span>\n<span>\t`type` String</span>\n<span>)</span>\n<span><span>AS</span> <span>SELECT</span></span>\n<span>\tconcat(<span>'ClickHouse_'</span>, event) <span>AS</span> name,</span>\n<span>\ttoFloat64(<span>value</span>) <span>AS</span> <span>value</span>,</span>\n<span>\tdescription <span>AS</span> help,</span>\n<span>\tmap(<span>'hostname'</span>, hostName(), <span>'table'</span>, <span>'system.events'</span>) <span>AS</span> labels,</span>\n<span>\t<span>'counter'</span> <span>AS</span> type</span>\n<span><span>FROM</span> system.events</span>\n<span><span>UNION</span> <span>ALL</span></span>\n<span><span>/</span><span>/</span>other metrics</span></code></pre></div>\n<p>With this approach the refresh rate of the materialized view controls how often the query is executed, ensuring it is run at most once every 60s by default.
