contentHtml: "<div><blockquote>\n<p><strong>TL;DR</strong><br><br>\nClickHouse Cloud compute is now fully stateless. This post introduces the final piece that made it possible: a new in-memory database engine powered by a <strong>Shared Catalog</strong> that removes the last dependency on local disks.<br><br>We’ll walk through how we got here, what the Shared Catalog unlocks, and how this powers stateless compute over anything, including data lakes.</p>\n</blockquote>\n<h2 id=\"stateless-compute-complete\"></h2>\n<p>ClickHouse Cloud no longer needs disks. Compute nodes don’t store anything locally. No syncing. No warm-up. Just fast, elastic, stateless compute that spins up, runs your query, and disappears.</p>\n<p>That’s not a prototype. That’s today.</p>\n<p>Since <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-public-beta\">launching</a> ClickHouse Cloud in October 2022, we’ve been stripping away every last bit of local state from the compute layer. In this post, we’ll walk you through that journey, stage by stage, and show how we got to fully stateless compute.</p>\n<p>The final building block is a <strong>Shared Catalog</strong> that decouples database metadata from disk.</p>\n<p>This unlocks immediate benefits, all of which we’ll explore in more detail later:</p>\n<ul>\n<li>\n<p><strong>New DDL capabilities</strong>, including atomic INSERT … SELECT, cross-db renames, and UNDROP</p>\n</li>\n<li>\n<p><strong>Resilient DROP operations</strong> that don’t depend on active compute nodes</p>\n</li>\n<li>\n<p><strong>Built for fast, no-warm-up provisioning</strong>, laying the foundation for low-latency scale-out, scale-up, and rapid wake-ups.</p>\n</li>\n<li>\n<p><strong>Stateless compute across both native and open formats</strong>, including Iceberg and Delta Lake</p>\n</li>\n</ul>\n<p>This is the architecture that now powers ClickHouse Cloud deployments.</p>\n<p>Let’s rewind to where it started: Nodes with everything stored locally.</p>\n<h2 id=\"stage-0-where-clickhouse-started\"></h2>\n<p>ClickHouse began with a classic <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Shared-nothing_architecture\">shared-nothing architecture</a> that tightly coupled storage and compute. Each server stores and accesses its own data on local disk, and scale-out is achieved through <a target=\"_blank\" href=\"https://clickhouse.com/docs/shards\">sharding</a>.</p>\n<p>The diagram below shows how query processing works in this setup.</p>\n<blockquote>\n<p>As we walk through each stage of the architecture, we’ll progressively adapt this diagram, until we reach the fully stateless, cloud-native end state.</p>\n</blockquote>\n<p><span><img alt=\"Blog-shared_catalog.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_shared_catalog_001_7222d4b8f9.png&w=2048&q=75\"></span></p>\n<p><strong>① DDL statements and catalog lookups: handled by the Atomic database engine</strong></p>\n<p>In earlier ClickHouse versions, DDL statements and metadata queries like SHOW TABLES or SHOW CREATE TABLE were handled by the<a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/database-engines/atomic\"> Atomic database engine</a>, which became the default in<a target=\"_blank\" href=\"https://clickhouse.com/docs/whats-new/changelog/2020#clickhouse-release-v2010330-2020-10-28\"> version 20.10</a>  (replacing the earlier <code>Ordinary</code> engine).</p>\n<p>Atomic assigns each table a persistent UUID, decoupling data from names and enabling safe, atomic DDL operations. It stores all metadata (definitions are saved as .sql files) on local disk, tying every compute node to persistent state.</p>\n<p><em>(Not shown in the diagram: In clusters, DDL statements like CREATE, DROP, ALTER, and RENAME can be broadcast using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/distributed-ddl\">ON CLUSTER</a> clause, coordinated via <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-keeper-a-zookeeper-alternative-written-in-cpp\">Keeper</a>. This mechanism appends DDL commands to a  DDL log/queue, not tied to any specific database engine. However, Keeper doesn’t store the full metadata state, so when a new node joins, it won’t know what happened before and requires manual setup to recreate tables.)</em></p>\n<p>This worked fine in small clusters, but made it hard to scale dynamically. To go stateless, we had to remove this local dependency.</p>\n<p><strong>② Data storage: handled by a MergeTree table engine</strong></p>\n<p>Everything related to table data itself (inserts, deletes, updates) is handled by a table engine from the <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/mergetree-family\">MergeTree family</a>, which organizes data on disk as a collection of immutable <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">data parts</a>.</p>\n<p>The ReplicatedMergeTree table engine enables high availability by automatically <a target=\"_blank\" href=\"https://clickhouse.com/docs/shards#what-are-table-replicas-in-clickhouse\">replicating</a> data to other nodes, coordinated via a replication log in Keeper.</p>\n<p><strong>③ In-memory query execution: using the OS page cache</strong></p>\n<p>For SQL SELECT queries, all necessary data is processed entirely in memory. If it isn’t already cached, it’s read from local disk and transparently placed into the <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Page_cache\">OS page cache</a>. From there, data is streamed into the <a target=\"_blank\" href=\"https://clickhouse.com/docs/academic_overview#4-query-processing-layer\">query engine</a> and processed in a <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/query-parallelism\">highly parallel fashion</a>, leveraging CPU and memory bandwidth for maximum performance.</p>\n<p>This setup made sense for single-node or small-cluster deployments, but tightly coupling metadata and data to local disks became a bottleneck in the cloud. To break that coupling, and support stateless compute, we had to rethink how ClickHouse manages metadata and data at every layer.</p>\n<p>But first, let’s clarify a foundational concept that underpins everything we’re about to walk through.</p>\n<p>Before we dive into the evolution of stateless compute in ClickHouse Cloud, it’s worth clarifying a key concept: the separation between <strong>database engines</strong> and <strong>table engines</strong>.</p>\n<ul>\n<li>\n<p>A <strong><a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/database-engines\">database engine</a></strong> manages database and table definitions. It handles DDL operations like CREATE, DROP, and RENAME, and powers metadata lookups like SHOW TABLES. In clusters, depending on the engine, it may also replicate DDL changes across nodes.</p>\n</li>\n<li>\n<p>A <strong><a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines\">table engine</a></strong> manages the table’s actual data: how it’s stored, indexed, read, and written. This includes operations like INSERT, DELETE, and UPDATE, and access to storage, local or remote.</p>\n</li>\n</ul>\n<p>Decoupling metadata management from data storage enables greater flexibility, scalability, and specialization at each layer. This separation is core to ClickHouse Cloud’s architecture, especially in the journey toward stateless compute.</p>\n<p>As we’ll see, making compute fully stateless required innovation on both sides: <strong>table engines that decouple data</strong>, and <strong>database engines that decouple metadata</strong>.</p>\n<p>Let’s walk through that evolution, stage by stage, by decoupling data, cache, and metadata.</p>\n<p>The first major step toward stateless compute was separating data storage from compute. It started with <strong>SharedMergeTree</strong>, a table engine for object storage, and <strong>Replicated</strong>, a database engine that simplified bootstrapping.</p>\n<p>Here’s how each layer contributed:</p>\n<p><span><img alt=\"Blog-shared_catalog.002.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_shared_catalog_002_2bf35d5d5d.png&w=2048&q=75\"></span></p>\n<p><strong>① DDL statements and catalog lookups: handled by the Replicated database engine</strong></p>\n<p>Separating storage from compute enables each to scale independently. To support elastic compute in ClickHouse Cloud, where nodes can be added or swapped at will, we introduced a new database engine in version 21.3: <strong><a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/database-engines/replicated\">Replicated</a></strong>. It first appeared experimentally before ClickHouse Cloud, and was later refined and made production-ready for the cloud.</p>\n<p>Replicated builds on the Atomic engine by still storing metadata locally as .sql files, but also replicates metadata changes, like CREATE, DROP, or RENAME, across nodes via a DDL log written to Keeper, automatically and without requiring the ON CLUSTER clause.</p>\n<p>(<em>Note: The Replicated engine uses a DDL log in Keeper to replicate metadata changes. The diagram omits this for clarity. Also not shown: table metadata is cached on disk, and both accessed table and database metadata are transparently cached in memory via the OS page cache for fast access.</em>)</p>\n<p>Unlike the previous mechanism with a simple, length-limited DDL log, the Replicated database engine stores the full metadata state per database in Keeper, allowing new nodes to fully bootstrap themselves (per pre-created database) without further manual setup.</p>\n<p><strong>② Table metadata access: handled by the SharedMergeTree table engine</strong></p>\n<p>Table storage is decoupled from compute with the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates\">SharedMergeTree table engine</a>, which coordinates access to shared object storage through a table metadata layer in Keeper. This layer tracks which data parts exist for each table and where the corresponding files are located in object storage.</p>\n<blockquote>\n<p><strong>Milestone:</strong> When ClickHouse Cloud launched, we started with ReplicatedMergeTree. All new services have used SharedMergeTree for some time, but as we publish this post, all existing services have been migrated too. Shared storage is now the foundation across the board.</p>\n</blockquote>\n<p><strong>③ Shared table data: stored in object storage</strong></p>\n<p>With the SharedMergeTree table engine, table data is no longer tied to local disk. Instead, it’s stored in shared object storage, durable, virtually unlimited, and accessible from any compute node. This enables elastic scaling, fault tolerance, and simplified operations, as compute nodes no longer need to replicate or manage local copies of data.</p>\n<blockquote>\n<p><strong>Under the hood:</strong> To deliver the performance users expect from ClickHouse, we go far beyond basic object storage access. The system performs <strong>aggressive retries</strong>, <strong>splits large objects into parallel chunks</strong>, and uses <strong>multi-threaded reads with asynchronous prefetching</strong>, all to <strong>maximize throughput and resilience</strong>. <em>(For more on the read-side optimizations, see the talk<a target=\"_blank\" href=\"https://youtu.be/gA5U6RZOH_o?si=uBS9EY_Q4VXSyVhw\"> Reading from object storage 100× faster</a>.)</em></p>\n</blockquote>\n<p><strong>④ Query acceleration: via filesystem cache to hide object storage latency</strong></p>\n<p>Object storage is durable and scalable, but has high access latency. To shield queries from this latency, ClickHouse Cloud introduced a local <a target=\"_blank\" href=\"https://clickhouse.com/blog/building-a-distributed-cache-for-s3#stage-2-local-cache-on-cloud-compute-nodes\">filesystem cache</a>: when data is streamed from object storage, it is cached locally for future reuse. This cache works in tandem with the OS page cache, enabling memory-speed execution on repeated queries.</p>\n<p><strong>⑤ Query execution: in memory using the OS page cache</strong></p>\n<p>Just like on classic shared-nothing servers, ClickHouse Cloud processes data entirely in memory. It’s streamed through the OS page cache into the query engine for fast, parallel execution.</p>\n<p>While local filesystem caching sped up repeated queries, it only benefited the same compute node that ran them. But in a world of elastic compute, caching tied to a single node was no longer enough.</p>\n<h2 id=\"stage-2-decoupling-cache-with-a-distributed-cache\"></h2>\n<p>Caching hot data close to the query engine is one of the most effective ways to speed up analytics. But so far in ClickHouse Cloud, that caching happened locally, tied to a specific compute node. To make caching cloud-native and elastic, we needed to go further. So we built a distributed cache.</p>\n<p>The diagram below shows how the distributed cache fits into the ClickHouse Cloud architecture, decoupling hot data from compute and making it instantly accessible across all nodes.</p>\n<blockquote>\n<p>To make each stage easier to follow, we highlight the new components in full color, and dim those we’ve already explained. You’ll see this pattern continue in the next stages as the architecture evolves.</p>\n</blockquote>\n<p><span><img alt=\"Blog-shared_catalog.003.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_shared_catalog_003_5fbea01cb0.png&w=2048&q=75\"></span></p>\n<p><strong>① Shared hot data: cached in a distributed cache service</strong></p>\n<p>The <a target=\"_blank\" href=\"https://clickhouse.com/blog/building-a-distributed-cache-for-s3\">distributed cache</a> is a shared network service that stores accessed table data across dedicated cache nodes. Compute nodes fetch needed data from it in parallel, avoiding object storage latency and making previously cached data instantly reusable, even across different nodes.</p>\n<p><strong>② In-memory execution: accelerated by a userspace page cache</strong></p>\n<p>Local RAM is still the fastest layer, so caching hot data in memory is essential for query speed. Since ClickHouse Cloud compute nodes no longer use local disks for caching, and thus can’t rely on the OS page cache, we introduced the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/userspace-page-cache\">userspace page cache</a>: an in-memory layer for caching data read from the distributed cache.</p>\n<p>With hot data caching now fully decoupled from compute, one dependency remained: database metadata still lived on local disk. To complete the stateless architecture, we had to rethink that too.</p>\n<p>The <strong>Replicated database engine</strong> made it easier to elastically add or swap compute nodes in ClickHouse Cloud. Nodes could automatically bootstrap their view of what tables exist in a database. But it still wasn’t fully cloud-native:</p>\n<ul>\n<li>\n<p><strong>Tied to local disk and manual orchestration:</strong> Metadata was stored on local filesystems, and databases had to be pre-created on each node.</p>\n</li>\n<li>\n<p><strong>Fragile failure recovery:</strong> Crashes could leave behind orphaned or inconsistent metadata.</p>\n</li>\n<li>\n<p><strong>Missing scalable DDL support:</strong> DROP required all nodes to be online, and features like cross-database RENAME or atomic INSERT … SELECT were hard to implement cleanly, so we didn’t.</p>\n</li>\n</ul>\n<p>Therefore, just like with the SharedMergeTree table engine, we went back to the drawing board and designed a new cloud-native, stateless <a target=\"_blank\" href=\"https://clickhouse.com/docs/cloud/reference/shared-catalog#shared-database-engine\">Shared database engine</a>, powered by a <a target=\"_blank\" href=\"https://clickhouse.com/docs/cloud/reference/shared-catalog\">Shared Catalog</a>.</p>\n<p>Before diving into how the Shared database engine and catalog work, the next diagram shows how they fit into the larger system: decoupling database metadata from local disk and enabling truly stateless compute nodes:</p>\n<p><span><img alt=\"Blog-shared_catalog.004.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_shared_catalog_004_233b0fd1ce.png&w=2048&q=75\"></span></p>\n<p>The Shared database engine remains responsible for ① handling all DDL statements and catalog lookups, now backed by the Shared Catalog rather than local files.</p>\n<p>This architectural shift unlocks the next key principle behind the Shared engine: fully stateless, diskless compute.</p>\n<p><strong>Truly stateless: no disks, no problem</strong></p>\n<p>The database metadata managed by the old Replicated engine was the last reason compute nodes needed local disks. The new Shared database engine removes that dependency entirely: it’s a purely in-memory engine. With that, <strong>compute nodes no longer require disks at all, just CPU and memory</strong>.</p>\n<p><strong>Centralized metadata: replicated and versioned in Keeper</strong></p>\n<p>The Shared database engine stores all database and table definitions in a central <em>Shared Catalog</em> backed by Keeper. Instead of writing to local disk, it maintains a single <em>versioned</em> <em>global state</em> shared across all compute nodes.</p>\n<p>Each node tracks only the last applied version and, on startup, fetches the latest state, no local files, no manual setup, just fast, consistent bootstrapping.</p>\n<p><em>(While not shown in the diagram, metadata is also transparently cached in memory. This accelerates metadata queries like SHOW TABLES or DESCRIBE. We’ll revisit this in the animated “Architecture in action” section below.)</em></p>\n<p>With this shift, ClickHouse Cloud compute became truly stateless. And the benefits go far beyond diskless bootstraps.</p>\n<p>With metadata now centralized and versioned, we could rethink how DDL works at scale. The result? A new model for coordination and object lifecycles, enabling:</p>\n<ol>\n<li>\n<p><strong>Cloud-scale DDL</strong>, even under high concurrency</p>\n</li>\n<li>\n<p><strong>Resilient deletion and new DDL operations</strong></p>\n</li>\n<li>\n<p><strong>Fast spin-up and wake-ups</strong> as stateless nodes now launch with no disk dependencies</p>\n</li>\n<li>\n<p><strong>Stateless compute across both native and open formats</strong>, including Iceberg and Delta Lake</p>\n</li>\n</ol>\n<p>We’ll walk through each of these next.</p>\n<blockquote>\n<p><strong>Heads-up: Things get deep from here</strong><br>The next two sections take a deep dive into how the shared database engine and catalog actually work, covering coordination, consistency, and all the gnarly edge cases we had to solve.<br><br>If you’re curious how the magic happens under the hood, read on and enjoy!<br>If you’re just here for the high-level takeaways, feel free to <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-stateless-compute#3-provisioning-built-for-speed-and-getting-faster\">skip ahead</a>, we won’t be offended.</p>\n</blockquote>\n<h3 id=\"1-cloud-scale-ddl-through-fine-grained-coordination\"></h3>\n<p>The first capability this unlocks: <strong>cloud-scale DDL coordination</strong>, even under high concurrency and node churn.</p>\n<h4 id=\"the-challenge-fast-consistent-coordination-of-metadata-across-many-nodes\"></h4>\n<p>Different clients may send DDL commands concurrently to different nodes, so the system must maintain a consistent global metadata state, both across all existing nodes and for any new nodes that join (whether scaling vertically or horizontally). This coordination must be (1) fast and (2) support high concurrency.</p>\n<p>A straightforward approach is to use a global lock: whichever node holds it first fetches the latest metadata state to avoid conflicts (e.g., renaming a database just dropped by another node), applies its DDL changes, then releases the lock. While correct, this serializes all DDLs, which is <a target=\"_blank\" href=\"https://youtu.be/ZOZQCQEtrz8?si=Ju6ac-8-w223CTCv&t=37\">not optimal</a> and fails to meet both (1) fast coordination and (2) high concurrency.</p>\n<h4 id=\"selective-invalidation-a-smarter-solution\"></h4>\n<p>Rather than using global locks, we use a smarter approach: each type of DDL command only invalidates a specific subset of other concurrently issued DDLs, those that might conflict, until those nodes fetch and apply the latest state.</p>\n<h4 id=\"how-keeper-guarantees-correctness-under-concurrency\"></h4>\n<p>The Shared Catalog makes this work by applying all DDL updates through <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-keeper-a-zookeeper-alternative-written-in-cpp\">Keeper</a>’s consensus algorithm, which guarantees <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Linearizability\">linearizable</a> writes. Each compute node sends its DDL changes as a <a target=\"_blank\" href=\"https://zookeeper.apache.org/doc/r3.4.3/api/org/apache/zookeeper/ZooKeeper.html#multi(java.lang.Iterable)\">multi-write transaction</a>. Keeper ensures that one node’s transaction is always applied first. If another node submits a conflicting change, its multi-write request will fail because it references outdated object versions. The node can then fetch and apply the updated state first. This guarantees consistency without sacrificing concurrency.</p>\n<h4 id=\"the-architecture-in-action\"></h4>\n<p>The following animation sketches our approach. It shows the global state of the Shared Catalog, which is stored in Keeper. This state consists of three main Keeper nodes:</p>\n<ul>\n<li><code>/uuids</code>: maps UUIDs to object metadata (e.g. CREATE queries, versions)</li>\n<li><code>/names</code>: maps object names to UUIDs (for lookup and rename)</li>\n<li><code>/replicas</code>: tracks each compute node’s latest applied metadata version</li>\n</ul>\n<p>The global DB metadata state version is the <a target=\"_blank\" href=\"https://zookeeper.apache.org/doc/r3.4.6/zookeeperOver.html\">Znode-version</a> of the <code>/uuids</code> node. This is the single source of truth.</p>\n<p>Above the Shared Catalog, you’ll see three compute nodes, each with its local in-memory DB metadata. These nodes subscribe to catalog changes and stay up to date using Keeper’s <a target=\"_blank\" href=\"https://zookeeper.apache.org/doc/current/zookeeperProgrammers.html#ch_zkWatches\">watch</a>-based notification mechanism.</p>\n<p><span><img alt=\"_blog_animation01.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fblog_animation01_22ab77476b.gif&w=2048&q=75\"></span></p>\n<p><strong>① Node 3 receives and runs a DDL command</strong></p>\n<p>Node 3 receives a DDL command to create table <code>tbl</code> in <code>db2</code>, where one column <code>val</code> uses a DEFAULT expression, computed at insert time via a dictionary lookup in the existing <code>dic</code> dictionary from <code>db1</code>.</p>\n<p>To run this, Node 3’s <strong>DDL execution thread</strong> sends a Keeper multi-request that:</p>\n<ul>\n<li>\n<p><strong>② Validates dependencies</strong>: Checks that all required objects (db1, dic, db2) exist and are at the expected version. If another node had just renamed or dropped one, the version check would fail, and the operation would return an error to the user. However, in the meantime, the node fetches and applies the updated metadata state in the background, so it’s ready to rerun the operation if the user retries.</p>\n</li>\n<li>\n<p><strong>③ Bumps versions</strong>: Increments the version of each dependent object. This acts as a <strong>fine-grained lock</strong>: only the specific objects touched by the DDL command have their versions incremented. Other nodes modifying those same objects will detect a version mismatch and abort. The rest of the global state remains untouched, enabling high concurrency.</p>\n</li>\n<li>\n<p><strong>④ Applies the change</strong>: Writes the new table tbl to the global state and increments the global metadata version (e.g., from 5 to 6), notifying all other nodes (via Keeper watch notification, see below).</p>\n</li>\n</ul>\n<p><strong>⑤ Background threads update states on all compute nodes</strong></p>\n<p>Every compute node runs a <strong>background thread</strong> that listens for changes via Keeper’s watch mechanism. When it sees that the global state version bumped (e.g., from 5 to 6), it:</p>\n<ul>\n<li>Fetches the new state from Keeper.</li>\n<li>Merges changes into local memory.</li>\n<li>Updates its <code>/replicas</code> version in Keeper to signal it’s up-to-date.</li>\n</ul>\n<p>In our case, node 3 made the change, so it doesn’t merge changes; only the version marker needs updating.</p>\n<blockquote>\n<p><strong>Guaranteeing DDL visibility across nodes</strong>: The <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#distributed_ddl_output_mode\">distributed_ddl_output_mode</a> setting controls what the DDL execution thread does after applying changes (step ④). For example, it can wait until all (or all active) compute nodes have updated their local metadata, i.e., completed the final update step (⑤) with their separate background threads, before returning success to the client. The maximum wait time is governed by the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#distributed_ddl_task_timeout\">distributed_ddl_task_timeout</a> setting.</p>\n</blockquote>\n<p>For simplicity, we glossed over some internal details in Step ④. Each object goes through a lifecycle of stages, like “intention to create” → “created”, which are stored in the object’s stage field (as just sketched in the animation above). In the next section, we’ll explain why this staged approach matters, and what it enables.</p>\n<h3 id=\"2-reliable-deletion-and-ddl-through-a-staged-metadata-lifecycle\"></h3>\n<p>The Shared database engine introduces a <strong>staged object lifecycle</strong>, a new internal mechanism that tracks each object’s state explicitly. This solves long-standing problems with reliable deletion, recovery, and cross-object consistency that arose from older engines tightly coupling compute and metadata.</p>\n<p>Let’s start with deletion. In earlier engines, it was tightly coupled to node liveness:</p>\n<ul>\n<li>\n<p><strong>MergeTree table engine:</strong> The node running the DROP command was responsible for deleting the data immediately, since data was stored on local disk.</p>\n</li>\n<li>\n<p><strong>SharedMergeTree table engine:</strong> In a multi-node setup using shared storage, the last node to replicate the DROP was responsible for deleting the data. Because SharedMergeTree uses shared storage, this deferral ensures that data is only deleted once it’s no longer needed by any node.</p>\n</li>\n</ul>\n<p>This was fragile in <a target=\"_blank\" href=\"https://clickhouse.com/blog/introducing-warehouses-compute-compute-separation-in-clickhouse-cloud\">compute-compute separation</a> setups. If one service issued a DROP, the table was logically removed for that service, but physical deletion was delayed until all nodes acknowledged it. If even one node (or another service) was idle or stuck, deletion stalled, sometimes for weeks.</p>\n<p>The staged design solves this by making deletion lifecycle-aware and handled asynchronously by independent background threads. Let’s walk through the lifecycle.</p>\n<h4 id=\"understanding-the-object-lifecycle\"></h4>\n<p>Each object in the Shared Catalog progresses through a small set of well-defined stages (tracked in an object’s <code>stage</code> field, as seen in the “Architecture in action” animation above), ensuring safe transitions from creation to deletion:</p>\n<p><span><img alt=\"Blog-shared_catalog.005.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_shared_catalog_005_20df1dbcfb.png&w=2048&q=75\"></span></p>\n<p><strong>① INTENTION: Prepare to create</strong></p>\n<p>This is the initial stage for any object. For example, when a CREATE TABLE is issued, the DDL execution thread writes the new table’s metadata (e.g. the <code>create_query</code> statement) to Keeper with the stage set to INTENTION. At this point, the table doesn’t yet exist.</p>\n<ul>\n<li>\n<p>If creation succeeds, the stage is updated to <strong>② CREATED</strong>.</p>\n</li>\n<li>\n<p>If it fails, the stage is set to <strong>④ DROP_IN_PROGRESS</strong>, and the metadata is cleaned up.</p>\n</li>\n</ul>\n<blockquote>\n<p><strong>No more orphaned metadata:</strong> If the DDL thread crashes (e.g. due to a node failure or Keeper disconnect), the object stays in INTENTION. A separate background cleanup thread monitors such cases and deletes metadata that remains stuck in this stage for too long.<br><br>This guarantees no metadata is left behind, unlike the Replicated database engine, where orphaned entries could linger in Keeper indefinitely.</p>\n</blockquote>\n<p><strong>② CREATED: Object is live</strong></p>\n<p>This is the normal, active stage for a metadata object after successful creation.</p>\n<ul>\n<li>\n<p>A DETACH command moves the object to stage <strong>⑤ DETACHED</strong>, and an ATTACH command moves it back to <strong>CREATED</strong>.</p>\n</li>\n<li>\n<p>A DROP command transitions it to <strong>③ DROP_SCHEDULED</strong>, where deletion is handled asynchronously, and an UNDROP command moves it back to <strong>CREATED</strong> (see below).</p>\n</li>\n</ul>\n<p><strong>③ DROP_SCHEDULED: Soft-deleted, grace-period active</strong></p>\n<p>The object (e.g., a table) is no longer visible to compute nodes; it has been logically dropped.</p>\n<ul>\n<li>\n<p>After a configurable timeout (e.g., 8 hours), a background deletion thread, running independently of any compute node, physically removes the object’s data.</p>\n</li>\n<li>\n<p>This delayed deletion allows the table to be safely <strong>UNDROPped</strong> during the grace period, since both its metadata and data still exist. If UNDROP succeeds, the object returns to stage <strong>② CREATED</strong>.</p>\n</li>\n</ul>\n<blockquote>\n<p><strong>Truly decoupled deletion:</strong> The system no longer depends on any specific node to finish the deletion job, avoiding the liveness issues of prior engines.</p>\n</blockquote>\n<p><strong>④ DROP_IN_PROGRESS: Final deletion in progress</strong></p>\n<p>This is the point of no return, the object can no longer be revived. It signals that the background deletion thread is actively removing the object: first, its data from object storage, then its metadata from Keeper.</p>\n<h4 id=\"new-ddl-operations-powered-by-lifecycle-stages\"></h4>\n<p>This staged model enables clean, reliable implementations of DDL features that were previously fragile or hard to implement cleanly.</p>\n<p><strong>UNDROP</strong>: <br>Tables in DROP_SCHEDULED can be safely recovered while both metadata and data still exist.</p>\n<p><strong>Atomic CREATE TABLE AS SELECT (CTAS)</strong>:<br>Previously, CTAS could leave behind partially created tables if the SELECT failed. Now:</p>\n<ul>\n<li>\n<p>Start with the table in the INTENTION stage</p>\n</li>\n<li>\n<p>Fill it with data</p>\n</li>\n<li>\n<p>Promote it to CREATED if successful</p>\n</li>\n<li>\n<p>Otherwise, discard it by moving to DROP_IN_PROGRESS</p>\n</li>\n</ul>\n<p>Result: <strong>all-or-nothing semantics</strong>, no manual cleanup.</p>\n<p><strong>Cross-database RENAME</strong>:<br>Older engines stored metadata in per-database logs, making cross-db operations hard to coordinate. The Shared Catalog solves this with single-source metadata and multi-write transactions via Keeper.</p>\n<p>All of these benefit from the same guarantee: lifecycle-aware metadata ensures clean transitions, no matter how distributed your workload.</p>\n<p>But lifecycle coordination is just one part of what the Shared Catalog enables. It also removes the last bottleneck to instant provisioning, letting compute nodes spin up faster than ever.</p>\n<h3 id=\"3-provisioning-built-for-speed-and-getting-faster\"></h3>\n<p>Reducing startup latency has been the goal since day one of ClickHouse Cloud, and this release lays the foundation for making it a reality.
