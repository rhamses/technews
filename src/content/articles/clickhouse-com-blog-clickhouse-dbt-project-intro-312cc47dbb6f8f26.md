contentHtml: "<article><div><p><span><img alt=\"dbt_clickhouse.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDBT_Post_0e9aeb08ea.png&w=2048&q=75\"></span></p>\n<h2 id=\"introduction\"></h2>\n<p>As a company dedicated to the ethos of open-source, it is important that we accept not only requests from the community but also features and new integrations.</p>\n<p>Last week we <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=16VBGdNuHv8\">delivered a webinar</a> on such a project - the <a target=\"_blank\" href=\"https://github.com/ClickHouse/dbt-clickhouse\"><code>dbt-clickhouse</code></a> plugin.</p>\n<p>Initially created by a community contributor to address their needs and released in the spirit of OSS, this plugin has seen increasing adoption as users utilize dbt's capabilities with ClickHouse.</p>\n<p>In this blog post, we explore dbt, the value it potentially brings when combined with ClickHouse, and a small tale of evolving support for more advanced capabilities leveraging new capabilities recently released in ClickHouse.</p>\n<h2 id=\"what-is-dbt\"></h2>\n<p><strong>dbt</strong> (data build tool) enables analytics engineers to transform data in their warehouses by simply writing select statements. dbt handles materializing these select statements into objects in the database in the form of tables and views - performing the T of<a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Extract,_load,_transform\"> Extract Load and Transform (ELT)</a>. Users can create a model defined by a SELECT statement.</p>\n<p>Within dbt, these models can be cross-referenced and layered to allow the construction of higher-level concepts. The boilerplate SQL required to connect models is automatically generated. Furthermore, dbt identifies dependencies between models and ensures they are created in the appropriate order using a directed acyclic graph (DAG).</p>\n<p>In summary, users can define a model representing a concept, e.g., a summary of actor appearances <strong>as SQL</strong>. These models can then be materialized* as either views or tables. These models can then be combined to produce more complex models.</p>\n<p>In our recent webinar, we presented the following data schema for IMDB movie data. From this, we utilize dbt to create two models: one summarizing directors and another providing an overview of every actor, e.g., the number of movie appearances, their average rating, the director they have mostly worked with, etc. In this case, the actor's model is dependent on the director's model. dbt allows these models to be defined as SQL statements, with a Jinja templating language to connect and reference them. Note how some data sources aren’t even in ClickHouse, with the movie_genres and movie_director tables in S3 and Postgres respectively. This final model is then represented in ClickHouse as either a view or table named <code>actor_summary</code>.</p>\n<p><span><img alt=\"model.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmodel_76d75387fd.png&w=2048&q=75\"></span></p>\n<h2 id=\"how-is-this-supported-in-clickhouse\"></h2>\n<p>dbt supports an <a target=\"_blank\" href=\"https://docs.getdbt.com/guides/dbt-ecosystem/adapter-development/1-what-are-adapters\">adapter plugin API</a> to allow users to connect to data platforms that are not included in the <a target=\"_blank\" href=\"https://docs.getdbt.com/docs/supported-data-platforms\">core offering</a>. In <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=9YHSK62D6WHC5ARCBOJEO7\">early 2021</a> a member of the ClickHouse community, <a target=\"_blank\" href=\"https://github.com/silentsokolov\">Dmitriy Sokolov</a>, <a target=\"_blank\" href=\"https://github.com/clickHouse/dbt-clickhouse\">created a plugin</a> to support ClickHouse for his requirements and kindly open-sourced his work. In response to growing adoption and a little <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=1IXC5PU4QCXSH5DHGQRU6F\">over a year later</a>, this project was transferred to ClickHouse and officially made a vendor-supported plugin. We continue to invest in this plugin to support the dbt latest features and utilize the best practices of ClickHouse to expose this functionality.</p>\n<p>We test this plugin rigorously against ClickHouse Cloud and ensure the <a target=\"_blank\" href=\"https://docs.getdbt.com/guides/dbt-ecosystem/adapter-development/4-testing-a-new-adapter\">current dbt plugin test </a>suite passes.</p>\n<h2 id=\"how-is-it-useful-to-clickhouse-users\"></h2>\n<p>We primarily see users using dbt with ClickHouse for a number of tasks:</p>\n<ul>\n<li>Data analysts serving requests for views on the data, e.g., to the business for BI purposes or data scientists who need a specific view for their latest model. It is essential to manage these views and models and ensure they are tracked, minimized, tested, documented, and versioned.</li>\n<li>Users have data in various systems, such as Postgres, MySQL, and S3, and wish to model these data as a set of tables or views in ClickHouse. Using ClickHouse’s table functions and engines, users create dbt models to manage this data migration process. They, in turn, benefit from dbt representing these data integration tasks as code which can then be versioned, documented, and tested - again using dbt features.</li>\n<li>User’s often need to <a target=\"_blank\" href=\"https://clickhouse.com/blog/migrating-data-between-clickhouse-postgres\">migrate data from other OLTP databases</a>, such as Postgres, to ClickHouse to serve real-time analytical workloads. In simple cases, this can be achieved using native <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/table-functions/\">ClickHouse table functions</a>. However, ClickHouse tables represented by many source tables subject to updates typically require <a target=\"_blank\" href=\"https://www.striim.com/blog/change-data-capture-cdc-what-it-is-and-how-it-works/\">Change data capture processes</a>. Dbt can assist with the <a target=\"_blank\" href=\"https://davidsj.substack.com/p/data-activated\">management and modeling</a> of the queries required in this process.</li>\n<li>Users may alternatively need to track changes to rows in ClickHouse - a form of change capture- to answer questions concerning a former state in the database. Dbt offers features <a target=\"_blank\" href=\"https://docs.getdbt.com/blog/change-data-capture\">such as incremental models and snapshots</a> that can assist with these requirements.</li>\n</ul>\n<h2 id=\"model-types\"></h2>\n<p>The process of persisting the results of a model’s SQL query is known as “materializing the model”. Models can be materialized in a number of ways. The <code>clickhouse-dbt</code> plugin ensures this is achieved using the most appropriate ClickHouse functionality and best practices:</p>\n<ul>\n<li><strong><a target=\"_blank\" href=\"https://docs.getdbt.com/docs/build/materializations#view\">View Materialization</a></strong> - the simplest and default approach. Here the model is simply created in ClickHouse using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/view/#normal-view\">CREATE VIEW AS</a> as syntax. Changes to the model cause the view to be recreated when dbt is run.</li>\n<li><strong><a target=\"_blank\" href=\"https://docs.getdbt.com/docs/build/materializations#table\">Table Materialization</a></strong>- The results from the model’s SQL query are streamed into a new table with the appropriate schema, using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/insert-into/#inserting-the-results-of-select\"><code>INSERT INTO table SELECT &amp;lt;model_query&gt;</code></a> statement. The user pays the storage cost of representing the model as a table for the benefit of improved performance.</li>\n<li><strong><a target=\"_blank\" href=\"https://docs.getdbt.com/docs/build/incremental-models\">Incremental materialization</a></strong>- Provides a means to materialize a model as a table but maintain updates. Subsequent runs of the model identify changes in the source data using a unique key field and condition (e.g., based on a timestamp), and ensure this is reflected in the target table in ClickHouse. This is extremely powerful for the event-type data associated with ClickHouse.</li>\n<li><strong><a target=\"_blank\" href=\"https://docs.getdbt.com/docs/build/materializations#ephemeral\">Ephemeral materialization</a></strong> - Represents the model as a CTE, which can then be referenced in other models.</li>\n</ul>\n<p>Models of different types can be combined to produce more complex models, allowing component <a target=\"_blank\" href=\"https://docs.getdbt.com/docs/build/tests\">parts to be tested</a> and <a target=\"_blank\" href=\"https://docs.getdbt.com/docs/collaborate/documentation\">documented</a>. A simple table materialization for the actors model, as used on the webinar, is shown below:</p>\n<div><pre><code><span><span>{{ config(order_by='director_id', engine='MergeTree()', materialized='table') }}</span><span></span></span>\n<span><span></span></span>\n<span><span></span></span>\n<span><span>WITH directors AS (</span></span>\n<span><span>   SELECT directors.id as director_id, movie_id, first_name, last_name FROM </span><span>{{ source('imdb', 'movie_directors') }}</span><span> OUTER JOIN </span><span>{{ source('imdb', 'directors') }}</span><span> ON </span><span>{{ source('imdb', 'movie_directors') }}</span><span>.director_id = </span><span>{{ source('imdb', 'directors') }}</span><span>.id</span></span>\n<span><span>)</span></span>\n<span><span></span></span>\n<span><span>select *</span></span>\n<span><span>from directors</span></span></code></pre></div>\n<p>For further details, see the <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=16VBGdNuHv8\">webinar recording</a> or our <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/integrations/dbt/dbt-intro\">documentation</a>, which contains similar examples.</p>\n<h2 id=\"recent-developments\"></h2>\n<p>Incremental materializations represent the most complex model type to implement in ClickHouse. Historically ClickHouse has had only limited support for updates and deletes in the form of asynchronous <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/mutations/\">mutations</a>. These need to be <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/bestpractices/avoid-mutations/\">used carefully</a> since they rewrite all of the affected data parts and can be extremely IO-intensive as a result.</p>\n<p><span><img alt=\"model-update.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmodel_update_663c7ca903.png&w=2048&q=75\"></span></p>\n<p>Suppose we have an original table, <code>X</code>, which represents a materialized model. To implement the incremental semantics required by dbt, <code>dbt-clickhouse</code>, by default, creates a new temporary table <code>T</code> with the new records identified by a condition the user specifies e.g. <code>select max(updated_at) from {{this}}</code>. A new table, <code>N</code>, is then created with the same schema as the original. Data is streamed into table <code>N</code> from the original table, using an <code>INSERT INTO SELECT</code> with a check to ensure the records aren't in <code>T</code>. Finally, we stream the records from <code>T</code> into <code>N</code> and do an atomic table exchange with <code>X</code> and <code>N</code> to expose the new realized model. This is visualized below:</p>\n<p><span><img alt=\"incremental-old-generic.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fincremental_old_generic_b5b954c847.png&w=2048&q=75\"></span></p>\n<p>While this approach works, it involves a complete duplication of the data being created for each dbt run and capture of the changes. Ideally, we would avoid this overhead and only write the new record,s. The above process is complicated as it supports duplicates and updates in the source data. If the user is comfortable with handling duplicates themselves in ClickHouse or is confident their source data is immutable and append-only, the incremental model can be <a target=\"_blank\" href=\"https://github.com/ClickHouse/dbt-clickhouse#the-append-strategy\">configured to use an <code>append-only</code> strategy</a>. In this case, the changes are simply identified in the source data and streamed directly into the existing table, as shown below</p>\n<p>While improving the situation for a subset of cases, we remain dissatisfied with the current solution for the case where duplicates were a possibility. Fortunately, in 22.8 ClickHouse added <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/delete/\">lightweight deletes</a> as an experimental feature. Lightweight deletes are significantly faster than <code>ALTER TABLE ... DELETE</code> operations because they don't require rewriting ClickHouse data parts. “Tombstones” are simply added to deleted rows which allow records to be automatically excluded at query time. These deleted records are, in turn, merged away during normal merge processes. Armed with deletes that don’t consume as much IO and threaten cluster stability, we could add a new approach known as <code>delete+insert</code> to incremental materializations.</p>\n<p>In summary, this approach:</p>\n<ol>\n<li>Creates a temporary table <code>T</code>. Rows that have changed are streamed into this table. A <code>DELETE</code> is issued against the current table <code>X</code>, deleting rows by id based on the values in <code>T</code>.</li>\n<li>The rows from <code>T</code> are inserted into the current table <code>X</code> using an <code>INSERT INTO X SELECT * FROM T</code>.</li>\n</ol>\n<p>We visualize this below:</p>\n<p><span><img alt=\"incremental-new-generic.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fincremental_new_generic_8dd05c2454.png&w=2048&q=75\"></span></p>\n<p>Our testing suggests this approach performs significantly better than the \"legacy\" strategy. However, there are important caveats to using this strategy:</p>\n<ul>\n<li>The setting <code>allow_experimental_lightweight_delete</code> must be enabled on your ClickHouse server or included in the custom_settings for your ClickHouse profile.</li>\n<li>As suggested by the setting name, lightweight delete functionality is still experimental and is not quite considered production-ready, so usage should be limited to datasets that are easily recreated.</li>\n<li>This strategy operates directly on the affected table/relation (without creating any intermediate or temporary tables), so if there is an issue during the operation, the data in the incremental model is likely to be in an invalid state</li>\n</ul>\n<p>While the first two of these issues are likely to be addressed soon with lightweight deletes expected to GA soon, the latter requires further development work. What about transactions, you say? Well, that's a good idea…</p>\n<h2 id=\"conclusions\"></h2>\n<p>In this post, we have introduced dbt and the ClickHouse plugin. We have covered the value of dbt to ClickHouse users and discussed some of the key features before presenting recent developments based on new capabilities in ClickHouse. For more details, we recommend the <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=16VBGdNuHv8\">recent webinar</a> and examples in <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/integrations/dbt/dbt-intro\">our documentation</a>. Happy modeling.</p></div></article>"
