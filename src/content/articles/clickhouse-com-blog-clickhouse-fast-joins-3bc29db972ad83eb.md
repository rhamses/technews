Together, they made the same TPC-H SF100 join-heavy workload another 6× faster.</p>\n<p><span><img alt=\"Blog-JOINS-improvements.002.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_JOINS_improvements_002_0f8d32bb46.png&w=2048&q=75\"></span></p>\n<p>The rest of this post walks through those four improvements:</p>\n<p>① <strong>Correlated subqueries in JOINs</strong> — support more real-world SQL directly.</p>\n<p>② <strong>Lazy column replication</strong> — avoid copying repeated values produced by joins.</p>\n<p>③ <strong>Runtime filters</strong> — skip probe-side rows before expensive hash-table lookups.</p>\n<p>④ <strong>Statistics-based join reordering</strong> — choose better join plans automatically.</p>\n<p>All examples use <a target=\"_blank\" href=\"https://clickhouse.com/docs/getting-started/example-datasets/tpch\">TPC-H SF100</a> on the same hardware, an AWS EC2 m6i.8xlarge instance (32 vCPUs, 128 GiB RAM), so the improvements are easy to compare.</p>\n<p>Two years ago, the problem was not just that some joins were slower than we wanted them to be. Some important join-heavy queries could not run at all.</p>\n<h4 id=\"why-this-mattered\"></h4>\n<p>In the TPC-H benchmark section of our <a target=\"_blank\" href=\"https://www.vldb.org/pvldb/vol17/p3731-schulze.pdf\">first research paper</a>, presented at VLDB 2024, we had to exclude seven queries: Q2, Q4, Q13, Q17, and Q20–Q22. Because they used correlated subqueries, which ClickHouse did not fully support at the time.</p>\n<p>TPC-H Q4 is a good example. It contains an inner query over <code>lineitem</code> that references <code>orders</code>, the table from the outer query:</p>\n<p><span><img alt=\"Blog-JOINS-improvements.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_JOINS_improvements_001_d351241bde.png&w=2048&q=75\"></span></p>\n<p>This is what makes it a <strong>correlated subquery</strong>: the inner query cannot be understood in isolation, because it depends on values from the outer query.</p>\n<h4 id=\"from-row-by-row-execution-to-set-oriented-plans\"></h4>\n<p>Correlated subqueries are common because they are natural to write. They are also increasingly common in generated SQL, including queries produced by agentic systems. But for a database engine, they are hard to execute efficiently.</p>\n<p>The naive plan is to evaluate the inner query once for every row from the outer query. That is simple, but often disastrous for performance. To make these queries fast, the optimizer has to decorrelate them: rewrite the query into an equivalent set-oriented plan, typically using joins, aggregations, semi joins, or anti joins.</p>\n<p>That rewrite must preserve SQL semantics around duplicates, aggregates, and NULLs, which makes it much harder than it looks.</p>\n<h4 id=\"result\"></h4>\n<blockquote>\n<p>Correlated subqueries are now first-class SQL in ClickHouse. Queries that previously required manual rewrites - including the excluded TPC-H queries - now run directly.</p>\n</blockquote>\n<br>\n<h3 id=\"lazy-column-replication-in-joins\"></h3>\n<p>Lazy column replication reduces CPU and memory usage when JOINs logically repeat the same values many times.</p>\n<h4 id=\"the-problem-logical-repetition-becomes-physical-copying\"></h4>\n<p>In JOIN results, one input row can produce many output rows. In TPC-H, for example, each customer can have multiple orders. When we join <code>orders</code> with <code>customer</code>, the customer columns are logically repeated once for every matching order.</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    o.o_orderkey,</span>\n<span>    o.o_orderdate,</span>\n<span>    c.c_name,</span>\n<span>    c.c_address,</span>\n<span>    c.c_comment</span>\n<span><span>FROM</span> orders <span>AS</span> o</span>\n<span><span>INNER</span> <span>JOIN</span> customer <span>AS</span> c</span>\n<span>    <span>ON</span> o.o_custkey <span>=</span> c.c_custkey;</span></code></pre></div>\n<!-- -->\n<p>Logically, the result looks like this:</p>\n<p><span><img alt=\"Blog-JOINS-improvements.004.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_JOINS_improvements_004_3a121d9e14.png&w=2048&q=75\"></span></p>\n<p>Conceptually, this is the correct result: the same customer values appear next to each matching order.</p>\n<p>The expensive part is physical replication. If ClickHouse copies wide values such as c_address or c_comment into every joined row, the join spends CPU cycles and memory bandwidth duplicating the same data again and again. And if later operators like aggregations discard most of those rows, much of that copying was unnecessary.</p>\n<h4 id=\"lazy-column-replication-avoids-that-eager-copying\"></h4>\n<p>Instead of physically replicating repeated values during the join, ClickHouse keeps the original values once in a small dictionary data structure and represents the joined column as a compact index value pointing back to them:</p>\n<p><span><img alt=\"Blog-JOINS-improvements.005.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_JOINS_improvements_005_5694c466bf.png&w=2048&q=75\"></span></p>\n<p>If a later query step needs the fully materialized column, ClickHouse can still produce it. But many analytical operations can work directly on the compact representation, so the repeated values never need to be copied at all.</p>\n<p>This is especially useful for JOINs that duplicate wide columns, such as strings.</p>\n<h4 id=\"benchmark-avoiding-physical-replication\"></h4>\n<p>For the benchmark, we use a self-join on <code>orders</code>  to create many repeated <code>o_comment</code> values, and then immediately consume them with <code>cityHash64</code>.</p>\n<p>First, we ran the following example join without lazy replication.</p>\n<div><pre><code><span><span>SELECT</span> <span>sum</span>(cityHash64(t1.o_comment))</span>\n<span><span>FROM</span> orders <span>AS</span> t1</span>\n<span><span>INNER</span> <span>JOIN</span> orders <span>AS</span> t2</span>\n<span>    <span>ON</span> t1.o_custkey <span>=</span> t2.o_custkey</span>\n<span>SETTINGS</span>\n<span>    enable_lazy_columns_replication <span>=</span> <span>0</span>,</span>\n<span>    allow_special_serialization_kinds_in_output_formats <span>=</span> <span>0</span>;</span></code></pre></div>\n<!-- -->\n<p>Fastest of three runs:</p>\n<div><pre><code><span>1 row in set. Processed 300.00 million rows, 8.89 GB (55.36 million rows/s., 1.64 GB/s.)</span>\n<span>Peak memory usage: 5.27 GiB.</span></code></pre></div>\n<p>Then, we ran the same query with lazy columns replication enabled.</p>\n<p>This is the ideal case for lazy replication: <code>o_comment</code> is only needed as input to a function, so ClickHouse can evaluate <code>cityHash64</code> over the compact representation without physically materializing the repeated string column.</p>\n<div><pre><code><span><span>SELECT</span> <span>sum</span>(cityHash64(t1.o_comment))</span>\n<span><span>FROM</span> orders <span>AS</span> t1</span>\n<span><span>INNER</span> <span>JOIN</span> orders <span>AS</span> t2</span>\n<span>    <span>ON</span> t1.o_custkey <span>=</span> t2.o_custkey</span>\n<span>SETTINGS</span>\n<span>    enable_lazy_columns_replication <span>=</span> <span>1</span>,</span>\n<span>    allow_special_serialization_kinds_in_output_formats <span>=</span> <span>1</span>;</span></code></pre></div>\n<!-- -->\n<p>Fastest of three runs:</p>\n<div><pre><code><span>1 row in set. ClickHouse introduces a similar idea for the default parallel hash join algorithm.</p>\n<p>As a reminder, the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#parallel-hash-join\">parallel hash join algorithm</a> is a variation of <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#hash-join\">hash join</a> that splits the input data to build several hash tables concurrently, speeding up the build phase.</p>\n<p>In the example below, we set <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#max_threads\">max_threads</a> = 2, so ClickHouse builds two hash tables in parallel. In practice, max_threads is usually derived from the number of available CPU cores.</p>\n<p>The diagram shows the physical query plan, called the query pipeline in ClickHouse, for a TPC-H query joining orders with customer.</p>\n<p><span><img alt=\"Blog-JOINS-improvements.006.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_JOINS_improvements_006_d7c0b8e7ae.png&w=2048&q=75\"></span></p>\n<p>① The predicate on <code>customer</code> is pushed down and applied before the join.</p>\n<p>② During the build phase, the filtered <code>customer</code> rows, the right side of the join, are split into two buckets because <code>max_threads = 2</code>. Each bucket is used to build one in-memory hash table.</p>\n<p>③ During the probe phase, <code>orders</code> rows, the left side of the join, are streamed in parallel and routed to the corresponding hash table for lookup.</p>\n<h4 id=\"the-problem-wasted-probe-side-work\"></h4>\n<p>Note that in step ②, only a subset of customer keys is inserted into the hash tables during the build phase. However, in step ③, ClickHouse still processes all orders rows. For orders whose customer was removed by the customer filter, the lookup can never succeed. Those rows still consume CPU and memory bandwidth before the join rejects them.</p>\n<h4 id=\"the-idea-filter-probe-rows-before-lookup\"></h4>\n<p>Runtime filters address exactly this wasted work.</p>\n<p>While ClickHouse builds the hash tables (in DRAM) from the filtered customer rows, it also creates a compact filter (bloom filter or min/max values) from the join keys that actually made it into the build side. In our example, that means only customer keys that survived c_nation = 'DE'.</p>\n<p>That filter is applied to the orders side before the hash-table lookup. If an orders row has an o_custkey that is not present in the filtered build side, ClickHouse can discard it early instead of routing it into the join.</p>\n<p>The runtime filter is much smaller than the hash tables themselves, so it can stay close to the CPU, typically in L1 or L2 cache.</p>\n<h4 id=\"how-runtime-filters-fit-into-the-query-pipeline\"></h4>\n<p>The updated pipeline looks like this:</p>\n<p><span><img alt=\"Blog-JOINS-improvements.007.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_JOINS_improvements_007_1cf7d0baf0.png&w=2048&q=75\"></span></p>\n<p>The updated pipeline adds two steps:</p>\n<p>② While reading the filtered customer rows, ClickHouse builds a runtime filter from their join keys.</p>\n<p>④ Before probing the hash tables, ClickHouse applies that runtime filter to the orders rows.</p>\n<p>⑤ Only rows that pass the runtime filter continue to the hash-table lookup.</p>\n<p>The parallel hash join structure stays the same, but many probe-side rows are removed before the expensive lookup.</p>\n<p>This keeps the parallel hash join structure unchanged, but removes probe-side rows that could never match. In selective joins, this can significantly reduce CPU work and memory bandwidth.</p>\n<h4 id=\"how-it-appears-in-the-query-plan\"></h4>\n<p>We can see this in the logical query plan with EXPLAIN The result is the same, but the runtime can be dramatically different.</p>\n<h4 id=\"the-problem-join-order-matters\"></h4>\n<p>The diagram below shows three different join orders for the same join query and the resulting hash join trees. The query result will be the same in all three cases.</p>\n<p><span><img alt=\"Blog-JOINS-improvements.008.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_JOINS_improvements_008_6eab572778.png&w=2048&q=75\"></span></p>\n<p>The more tables a query joins, the more important the join order becomes.</p>\n<p>As explained in the previous section, in a hash join, the right side is used to build an in-memory hash table, and the left side probes it. Placing the smaller input on the build side is usually much more efficient.</p>\n<p>In some cases, <strong>good and bad join orders can differ by many orders of magnitude in runtime</strong>!</p>\n<h4 id=\"finding-a-good-join-order\"></h4>\n<p>Finding a good join order is hard because the search space grows extremely quickly. With 12 joined tables, there are already <strong>28 trillion</strong> possible join orders.</p>\n<p>ClickHouse therefore, uses a join order optimizer. At a high level, it enumerates candidate join trees, estimates their cost, and picks a good one.</p>\n<p><span><img alt=\"Blog-JOINS-improvements.009.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_JOINS_improvements_009_b14a1bc01e.png&w=2048&q=75\"></span></p>\n<h4 id=\"column-statistics-make-the-optimizer-effective\"></h4>\n<p>The optimizer needs cardinality estimates: how many rows each intermediate join result is expected to contain after filters and join predicates.</p>\n<p>Those estimates come from <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/mergetree-family/mergetree#available-types-of-column-statistics\">column statistics</a>. Since 26.4, ClickHouse generates those statistics automatically for all tables, which makes statistics-based join reordering effective with default settings.</p>\n<p>For small join graphs, ClickHouse can use exhaustive dynamic programming (DPSize) to find the optimal order. For larger join graphs, it uses a greedy search that is much faster but not guaranteed to find the optimum.</p>\n<p><span><img alt=\"Blog-JOINS-improvements.010.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_JOINS_improvements_010_3fb770935a.png&w=2048&q=75\"></span></p>\n<h4 id=\"benchmark-from-one-hour-to-2-7-seconds\"></h4>\n<p>To measure
