Even though queries are typically fast enough with little to no tuning, we believe in the principle that no miliseconds should be waisted! In this post we'll give you some tips on how to accelerate your ClickHouse queries and make them even faster than ever, using some practical examples.</p>\n<h2 id=\"a-quick-clickhouse-query-processing-primer\"></h2>\n<p>Tables in ClickHouse are designed to receive millions of row inserts per second and to store very large (100s of Petabytes) volumes of data.</p>\n<p>Fast query speed in ClickHouse is usually achieved by properly utilizing a table’s (sparse) <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/improving-query-performance/sparse-primary-indexes\">primary index</a> in order to drastically limit the amount of data ClickHouse needs to read from disk and in order to prevent resorting of data at query time which also can enable short-circuiting when a LIMIT clause is used.</p>\n<p>The <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/improving-query-performance/sparse-primary-indexes/sparse-primary-indexes-design\">design</a> of the ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/improving-query-performance/sparse-primary-indexes/sparse-primary-indexes-design#the-primary-index-has-one-entry-per-granule\">primary index</a> is based on the <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Binary_search_algorithm\">binary search algorithm</a>, that efficiently (<a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Time_complexity\">time complexity</a> of O(log2 n)) finds the position of a target value within a sorted array.</p>\n<p>For example, consider the sorted array in the diagram below, where the binary search algorithm is used to find the value 42. The algorithm compares the target value 42 to the middle element of the array. If they are not equal, the half in which the target cannot lie is eliminated, and the search continues on the remaining half, again taking the middle element to compare to the target value, and repeating this until the target value is found:</p>\n<p><span><img alt=\"speed_01.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fspeed_01_18537e0585.png&w=2048&q=75\"></span></p>\n<p>Finding rows in a ClickHouse table with the table’s primary index works in the same way.</p>\n<p>The table’s rows are <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/improving-query-performance/sparse-primary-indexes/sparse-primary-indexes-design#data-is-stored-on-disk-ordered-by-primary-key-columns\">stored</a> on disk ordered by the table’s <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/improving-query-performance/sparse-primary-indexes/sparse-primary-indexes-design#a-table-with-a-primary-key\">primary key</a> column(s).</p>\n<p>Based on that row order, the primary index (which is a sorted array like in the diagram above) <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/improving-query-performance/sparse-primary-indexes/sparse-primary-indexes-design#the-primary-index-has-one-entry-per-granule\">stores</a> the primary key column value(s) from each <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree/#index_granularity\">8192nd</a> row of the table.</p>\n<p>In the diagram below, we assume a table with a column ‘numbers’, which is also the primary key column:</p>\n<p><span><img alt=\"speed_02.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fspeed_02_c0badb49a2.png&w=2048&q=75\"></span></p>\n<p>Instead of indexing individual rows, the ClickHouse primary index is indexing blocks of rows (so-called <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/improving-query-performance/sparse-primary-indexes/sparse-primary-indexes-design#data-is-organized-into-granules-for-parallel-data-processing\">granules</a>).</p>\n<p>With such a primary index, terabytes or even petabytes of data can be skipped and thus searched in a matter of (sub-) seconds.</p>\n<p>The following diagram shows how ClickHouse typically executes a query:</p>\n<p><span><img alt=\"speed_03.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fspeed_03_e81146e79a.png&w=2048&q=75\"></span></p>\n<p>Step 1: The primary index from the involved table is loaded into the main memory.</p>\n<p>Step 2:  <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/improving-query-performance/sparse-primary-indexes/sparse-primary-indexes-design/#the-primary-index-is-used-for-selecting-granules\">Typically, via a binary search over the index entries</a>, ClickHouse selects blocks of rows that potentially contain rows matching the query’s WHERE clause.</p>\n<p>Step 3: The selected blocks of rows are streamed in parallel into the ClickHouse query engine for further processing, and the query result is streamed to the caller.</p>\n<p>There are three main tuning knobs for speeding up this query execution workflow in ClickHouse:</p>\n<p>The less data ClickHouse needs to stream from disk to main memory, the faster the query’s execution time will be. The amount of data required to be streamed from disk can be minimized by (1) properly utilizing primary indexes and (2) pre-computing aggregates.</p>\n<p>The streaming and actual processing of the data can be sped up by (3) increasing the level of parallelism used inside the ClickHouse query processing engine.</p>\n<h2 id=\"1-properly-utilize-primary-indexes\"></h2>\n<p>Lets first look at how we can ensure primary indexes are fully utilized to ensure optimal query performance.</p>\n<h3 id=\"utilize-indexes-for-minimizing-the-amount-of-data-to-be-streamed-into-clickhouse\"></h3>\n<p>As a running example, we use the table from our <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/uk-price-paid/\">UK Property Price Paid tutorial</a> with 27.64 million rows. This dataset is available within our <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=6IDMHK3OMR1C97J6M9EUQS\">sql.clickhouse.com</a> environment.</p>\n<p>We run a query that lists the counties in London for the three highest paid prices:</p>\n<pre><p>\nSELECT\n    county,\n    price\nFROM uk_price_paid\nWHERE town = 'LONDON'\nORDER BY price DESC\nLIMIT 3\n┌─county─────────┬─────price─┐\n│ GREATER LONDON │ 594300000 │\n│ GREATER LONDON │ 569200000 │\n│ GREATER LONDON │ 448500000 │\n└────────────────┴───────────┘\n3 rows in set. Elapsed: 0.044 sec. Processed 27.64 million rows, 44.21 MB (634.60 million rows/s., 1.01 GB/s.)\n</p> <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=TEH4J3REPN2FNDRGCYDNM6\">✎</a>\n</pre>\n<p>ClickHouse is doing a full table scan!</p>\n<p>Because the primary index of the table can’t be properly utilized for the query.</p>\n<p>We check the primary key of the table:</p>\n<pre><p>\nSHOW CREATE TABLE uk_price_paid\nCREATE TABLE default.uk_price_paid\n(\n    `price` UInt32,\n    `date` Date,\n    `postcode1` LowCardinality(String),\n    `postcode2` LowCardinality(String),\n    `type` Enum8('other' = 0, 'terraced' = 1, 'semi-detached' = 2, 'detached' = 3, 'flat' = 4),\n    `is_new` UInt8,\n    `duration` Enum8('unknown' = 0, 'freehold' = 1, 'leasehold' = 2),\n    `addr1` String,\n    `addr2` String,\n    `street` LowCardinality(String),\n    `locality` LowCardinality(String),\n    `town` LowCardinality(String),\n    `district` LowCardinality(String),\n    `county` LowCardinality(String),\n    `category` UInt8\n)\nENGINE = ReplicatedMergeTree('/clickhouse/tables/fb100991-4cae-4a92-995a-1ca11416879e/{shard}', '{replica}')\nORDER BY (postcode1, postcode2, addr1, addr2)\nSETTINGS index_granularity = 8192\n1 row in set. Elapsed: 0.001 sec.\n</p> <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=6CZ8TRMMKWHYDE91A3KETE\">✎</a>\n</pre>\n<p>The tables ORDER BY clause determines how the data is ordered on disk, and the primary index entries. The columns in the ORDER BY are postcode1, postcode2, addr1, and addr2.</p>\n<p>Note that ClickHouse uses the sorting key (defined by the ORDER BY clause) as the primary key if the latter is not defined explictly i.e. via a  PRIMARY KEY clause.</p>\n<p>That doesn’t help for the query with the <code>town = 'LONDON'</code> predicate.</p>\n<p>If we want to significantly speed up our sample query that filters for rows with a specific town, then we need to use a primary index optimized for that query.</p>\n<p>One <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/improving-query-performance/sparse-primary-indexes/sparse-primary-indexes-multiple#options-for-creating-additional-primary-indexes\">option</a> is to create a second table with a different row order based on a different primary key.</p>\n<p>Because a table can only have one physical order on disk, we need to duplicate the table data into another table.</p>\n<p>We create a second table with the same schema as the original table but with a different primary key, and we copy the data between the tables:</p>\n<pre><p>\nCREATE TABLE uk_price_paid_oby_town_price\n(\n    price UInt32,\n    date Date,\n    postcode1 LowCardinality(String),\n    postcode2 LowCardinality(String),\n    type Enum8('terraced' = 1, 'semi-detached' = 2, 'detached' = 3, 'flat' = 4, 'other' = 0),\n    is_new UInt8,\n    duration Enum8('freehold' = 1, 'leasehold' = 2, 'unknown' = 0),\n    addr1 String,\n    addr2 String,\n    street LowCardinality(String),\n    locality LowCardinality(String),\n    town LowCardinality(String),\n    district LowCardinality(String),\n    county LowCardinality(String),\n    category UInt8\n)\nENGINE = MergeTree\nORDER BY (town, price);\nINSERT INTO uk_price_paid_oby_town_price\nSELECT * FROM uk_price_paid;\n0 rows in set. Elapsed: 13.033 sec. Processed 52.50 million rows, 2.42 GB (4.03 million rows/s., 185.58 MB/s.)\n</p>\n</pre>\n<p>We run the query on the second table:</p>\n<pre><p>\nSELECT\n    county,\n    price\nFROM uk_price_paid_oby_town_price\nWHERE town = 'LONDON'\nORDER BY price DESC\nLIMIT 3\n┌─county─────────┬─────price─┐\n│ GREATER LONDON │ 594300000 │\n│ GREATER LONDON │ 569200000 │\n│ GREATER LONDON │ 448500000 │\n└────────────────┴───────────┘\n3 rows in set. Elapsed: 0.005 sec. Processed 81.92 thousand rows, 493.76 KB (15.08 million rows/s., 90.87 MB/s.)\n</p> <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=DXP1BNTN6YUGWXRZJET4AM\">✎</a>\n</pre>\n<p>Much better.</p>\n<h3 id=\"utilize-indexes-for-preventing-resorting-and-enabling-short-circuiting\"></h3>\n<p>In our previous example, ClickHouse is not only streaming much less data from disk but is applying an additional optimization.</p>\n<p>The query is:</p>\n<ul>\n<li>Filtering rows for town = ‘London’</li>\n<li>Ordering the matching rows by price descending</li>\n<li>Getting the top 3 rows</li>\n</ul>\n<p>For this, normally, ClickHouse:</p>\n<ul>\n<li>uses the primary index for selecting blocks that potentially contain ‘London’ rows and streams these rows from disk</li>\n<li>orders these rows in main memory by price</li>\n<li>streams the top 3 rows as the result to the caller</li>\n</ul>\n<p>But, because the ‘London’ rows on disk are stored already ordered by price (see the table DDL’s ORDER BY clause), ClickHouse can just skip the resorting in main memory.</p>\n<p>And ClickHouse can do short-circuiting. All ClickHouse has to do, is to stream the selected blocks of rows from disk in reverse order, and once three matching (town = ‘London’) rows have been streamed, the query is done.</p>\n<p>This is exactly what the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings/#optimize_read_in_order\"><code>optimize_read_in_order</code></a> optimization is doing in this case - <span>preventing resorting of the rows</span> and enabling <span>short-circuiting</span>.</p>\n<p>This optimization is enabled by default, and when we inspect the logical query plan of the query via <a target=\"_blank\" href=\"https://clickhouse.com/company/events/query-performance-introspection\">EXPLAIN</a>, we can see ReadType: InReverseOrder at the bottom of the plan:</p>\n<pre><p>\nEXPLAIN actions = 1\nSELECT\n    county,\n    price\nFROM uk_price_paid_oby_town_price\nWHERE town = 'LONDON'\nORDER BY price DESC\nLIMIT 3\n Expression (Projection)\n Actions: INPUT :: 0 -&gt; price UInt32 : 0\n                INPUT :: 1 -&gt; county LowCardinality(String) : 1\n       Positions: 0 1\n         Filter (WHERE)\n         Filter column: equals(town, 'LONDON') (removed)\n         Actions: INPUT :: 0 -&gt; Elapsed: 0.002 sec.\n</p> <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=5INADD1EKJOHLERC8VMGAP\">✎</a>\n</pre>\n<p>The <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings/#optimize_read_in_order\"><code>optimize_read_in_order</code></a> setting can be disabled via the SETTINGS clause of the query. This will cause ClickHouse to stream 2.17 million rows instead of 81.92 thousand rows from disk (still better than a full table scan). The following diagram visualizes the difference in query processing steps:</p>\n<p><span><img alt=\"speed_04.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fspeed_04_7942a7d4b2.png&w=2048&q=75\"></span></p>\n<p>One remaining issue with using a second table with a different row order is keeping the tables in sync. Further below, we will discuss a handy solution for this problem.</p>\n<h2 id=\"2-pre-compute-aggregates\"></h2>\n<p>We execute an aggregation query that lists the U.K. counties with the three highest average paid prices:</p>\n<pre><p>\nSELECT\n    county,\n    avg(price)\nFROM uk_price_paid\nGROUP BY county\nORDER BY avg(price) DESC\nLIMIT 3\n┌─county──────────────────────────────┬─────────avg(price)─┐\n│ WINDSOR AND MAIDENHEAD              │ 383843.17329304793 │\n│ BOURNEMOUTH, CHRISTCHURCH AND POOLE │  383478.9135281004 │\n│ GREATER LONDON                      │  376911.4824869095 │\n└─────────────────────────────────────┴────────────────────┘\n3 rows in set. Elapsed: 0.020 sec. Processed 26.25 million rows, 132.57 MB (1.33 billion rows/s., 6.69 GB/s.)\n</p> <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=AEZD2XA3HDMMAJDYTJCZLD\">✎</a>\n</pre>\n<p>In this case, ClickHouse is doing a full table scan because the query aggregates all existing table rows. Therefore the primary index can’t be used to reduce the amount of data streamed from disk.</p>\n<p>However, we could drastically reduce the amount of data streamed from disk (by sacrificing additional disk space) if we could pre-compute the aggregate values for all existing 130 U.K counties in a separate table and update that separate table, whenever the original table data changes.</p>\n<p>The following diagram visualizes this idea:</p>\n<p><span><img alt=\"speed_05.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fspeed_05_087f1266a5.png&w=2048&q=75\"></span></p>\n<p>ClickHouse has a handy new turnkey feature implementing this idea: <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-22-2-released/\">Projections</a>!</p>\n<h2 id=\"use-projections-for-1-and-2\"></h2>\n<p>A ClickHouse table can have (multiple) <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree/#projections\">projections</a>.</p>\n<p>A projection is an additional (hidden) table that is automatically kept in sync with the original table. The projection can have a different row order (and therefore a different primary index) than the original table, as well as automatically and incrementally pre-compute aggregate values.</p>\n<p>When a query is targeting the original table, then ClickHouse automatically chooses (by sampling the primary keys) a table that can generate the same correct result, but requires the least amount of data to be read. We visualize this concept here:</p>\n<p><span><img alt=\"speed_06.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fspeed_06_b7fe19ed6f.png&w=2048&q=75\"></span></p>\n<p>Projections are somewhat similar to <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/view#materialized-view\">Materialized Views</a>, which also allow you to have incremental aggregation and multiple row orders. But unlike Materialized Views, projections are updated atomically and kept consistent with the main table with ClickHouse automatically choosing the optimal version at query time.</p>\n<p>For the original example table <code>uk_price_paid</code>, we will create (and populate) two projections.</p>\n<p>In order to keep things tidy and simple in our playground, we first duplicate the table<code> uk_price_paid</code> as <code>uk_price_paid_with_projections</code>:</p>\n<pre><p>\nCREATE TABLE uk_price_paid_with_projections AS uk_price_paid;\nINSERT INTO uk_price_paid_with_projections SELECT * FROM uk_price_paid;\n0 rows in set. Elapsed: 4.410 sec. Processed 52.50 million rows, 2.42 GB (11.90 million rows/s., 548.46 MB/s.)\n</p></pre>\n<p>We create and populate projection <code>prj_oby_town_price</code> – an additional (hidden) table with a primary index, ordering by town and price, to optimize the query that lists the counties in a specific town for the highest paid prices:</p>\n<pre><p>\nALTER TABLE uk_price_paid_with_projections\n    ADD PROJECTION prj_oby_town_price\n    (\n        SELECT\n            *\n        ORDER BY\n          town, price\n    );\nALTER TABLE uk_price_paid_with_projections\n    MATERIALIZE PROJECTION prj_oby_town_price SETTINGS mutations_sync = 1;\n0 rows in set. Elapsed: 6.028 sec.\n</p></pre>\n<p>We create and populate projection <code>prj_gby_county</code> – an additional (hidden) table that incrementally pre-computes the avg(price) aggregate values for all existing 130 U.K counties:</p>\n<pre><p>\nALTER TABLE uk_price_paid_with_projections\n    ADD PROJECTION prj_gby_county\n    (\n        SELECT\n            county,\n            avg(price)\n        GROUP BY\n           county\n    );\nALTER TABLE uk_price_paid_with_projections\n    MATERIALIZE PROJECTION prj_gby_county SETTINGS mutations_sync = 1;\n0 rows in set. Elapsed: 0.123 sec.\n</p></pre>\n<p>Note that If there is a GROUP BY clause used in a projection (like in the <code>prj_gby_county</code> above), the underlying storage engine for the (hidden) table <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree/#projection-storage\">becomes</a> <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/aggregatingmergetree/\">AggregatingMergeTree</a>, and all aggregate functions are converted to <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/data-types/aggregatefunction\">AggregateFunction</a>. This ensures proper incremental data aggregation.</p>\n<p>Also, note the SETTINGS clause that <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings/#mutations_sync\">forces synchronous execution</a>.</p>\n<p>This is a visualization of the main table <code>uk_price_paid_with_projections</code> and its two projections:</p>\n<p><span><img alt=\"speed_07.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fspeed_07_58a7dc0285.png&w=2048&q=75\"></span></p>\n<p>If we now run the query that lists the counties in London for the three highest paid prices, we see a dramatic difference in performance:</p>\n<pre><p>\nSELECT\n    county,\n    price\nFROM uk_price_paid_with_projections\nWHERE town = 'LONDON'\nORDER BY price DESC\nLIMIT 3\n┌─county─────────┬─────price─┐\n│ GREATER LONDON │ 594300000 │\n│ GREATER LONDON │ 569200000 │\n│ GREATER LONDON │ 448500000 │\n└────────────────┴───────────┘\n3 rows in set. Elapsed: 0.026 sec. Processed 2.17 million rows, 13.03 MB (83.14 million rows/s., 499.14 MB/s.)\n</p> <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=DXP1BNTN6YUGWXRZJET4AM\">✎</a>\n</pre>\n<p>Likewise, for the query that lists the U.K. counties with the three highest average paid prices:</p>\n<pre><p>\nSELECT\n    county,\n    avg(price)\nFROM uk_price_paid_with_projections\nGROUP BY county\nORDER BY avg(price) DESC\nLIMIT 3\n┌─county──────────────────────────────┬─────────avg(price)─┐\n│ WINDSOR AND MAIDENHEAD              │  398334.9180566017 │\n│ GREATER LONDON                      │  396401.2740568222 │\n│ BOURNEMOUTH, CHRISTCHURCH AND POOLE │ 387441.28323942184 │\n└─────────────────────────────────────┴────────────────────┘\n3 rows in set. Elapsed: 0.007 sec.\n</p> <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=DXP1BNTN6YUGWXRZJET4AM\">✎</a>\n</pre>\n<p>Note that both queries target the original table, and that both queries resulted in a full table scan (all 27.64 million rows got streamed from disk) before we created the two projections.</p>\n<p>Also, note that the query that lists the counties in London for the three highest paid prices is streaming 2.17 million rows.
