contentHtml: "<div><blockquote>\n<p><strong>TL;DR</strong><br><br>We redesigned the ClickHouse full-text index to work efficiently on object storage.<br><br>The new layout favors sequential access and can answer many queries directly from the index without reading the indexed text column at all.<br><br>This post is a deep dive into the new design, written by the engineers who built it.</p>\n</blockquote>\n<h2 id=\"rethinking-full-text-search-for-object-storage\"></h2>\n<p>Full-text search in ClickHouse has gone through several iterations as we worked to bring fast, native text indexing to a columnar analytical database. Each iteration improved performance, usability, and integration with the query engine.</p>\n<p>With ClickHouse Cloud, a new constraint appeared.</p>\n<blockquote>\n<p>The text index must deliver the same high performance even when data is stored on object storage rather than on local disks.</p>\n</blockquote>\n<p>Data reads and writes on remote object storage have fundamentally different performance characteristics. Designs that require random reads or frequent lookups of a few bytes become a bottleneck at scale.</p>\n<p>We redesigned the new text index with these constraints in mind.</p>\n<p>In this post, we first walk through the internal design of the new text index and how it is used by the query engine during full-text searches. In the second half, we move from implementation details to configuration and usage.</p>\n<p><em>For a high-level overview of full-text search in ClickHouse and when to use it, see our <a target=\"_blank\" href=\"https://clickhouse.com/blog/full-text-search-ga-release\">GA announcement</a>.</em></p>\n<h2 id=\"design-of-the-new-text-index\"></h2>\n<p>As <a target=\"_blank\" href=\"https://clickhouse.com/blog/building-a-distributed-cache-for-s3#the-real-bottleneck-of-object-storage-latency\">discussed</a> in our earlier work on caching in ClickHouse Cloud, latency (not bandwidth) is in practice the real bottleneck when data lives on remote object storage.</p>\n<blockquote>\n<p>Object storage provides high throughput but significantly higher access latency than local disks.</p>\n</blockquote>\n<p>The <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-full-text-search\">previous text index</a> relied on <strong>scattered lookup patterns</strong> that were efficient on local disks but became slow on object storage, as many small, disjoint lookups amplify latency.</p>\n<p>To maintain high performance on object storage, we redesigned the text index to favor <strong>sequential access patterns</strong>, allowing efficient use of object storage without regressing the performance of full-text search on local disks.</p>\n<p>To see how this is implemented, we will now walk through all relevant index data structures, starting with how the index is stored on disk.</p>\n<p>As a reminder, ClickHouse stores table data on disk as a collection of <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">data parts</a>.</p>\n<p>Each data part contains a sparse <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes\">primary index</a> used for range pruning, and may also contain additional secondary <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/skipping-indexes\">data skipping indexes</a> such as minmax, set, or bloom filter indexes.</p>\n<p>The text index belongs to this second category of indexes. Like other data skipping indexes, it is defined per column whose textual content should be indexed for fast full-text search, and it is stored inside each data part alongside the column files and the primary index, as illustrated in the diagram below.</p>\n<p><span><img alt=\"Blog-FTS_v3.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_FTS_v3_001_52473058de.png&w=2048&q=75\"></span></p>\n<p>As shown in the diagram above, the text index internally consists of three main components, each of which is stored as a separate file per part:</p>\n<p>① the <strong>dictionary</strong> file (text_idx.dct.idx)<br>\n② the <strong>sparse dictionary index</strong> file (text_idx.idx)<br>\n③ the <strong>posting list</strong> file (text_idx.pst.idx)</p>\n<p>The filenames are used in the diagrams below for clarity.</p>\n<p>We go through each of the index components one by one in the following sections.</p>\n<h3 id=\"dictionary-layout-for-object-storage\"></h3>\n<p>The dictionary is the part of the text index that stores all indexed tokens, and for each token a reference to a corresponding posting list, representing all row positions that contain the token.</p>\n<p>The dictionary in earlier text index versions was based on a data structure known as <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Finite-state_transducer\">Finite State Transducer (FST)</a> - essentially a trie with prefix and suffix compression. FSTs provides compact storage and fast lookups on local SSDs. However, FSTs also rely on many small random reads, which become incredibly inefficient when the index is stored on object storage.</p>\n<p>This led us to redesign the dictionary layout with two goals: First, we wanted to <strong>favor sequential access patterns</strong> over random reads. Second, since random lookups cannot be entirely avoided in index lookups, we wanted to keep their number per query at least as small as possible. This keeps end-to-end query latencies small and predictable as the indexed datasets grow.</p>\n<p>To achieve this, the new text index dictionary uses a block-based layout: tokens are sorted alphabetically and grouped into fixed-size blocks of <code>dictionary_block_size</code> entries (default 512).</p>\n<p>This enables <strong>sequential reads</strong>, <strong>efficient compression</strong>, and <strong>fast access to posting lists</strong>, as described in the following sections.</p>\n<h4 id=\"sequential-reads-from-dictionary-blocks\"></h4>\n<p>The diagram below shows multiple dictionary blocks located at different offsets within the same dictionary file (text_idx.dct.idx).</p>\n<p><span><img alt=\"Rethinking full-text search for object storage #1514 Open.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FRethinking_full_text_search_for_object_storage_1514_Open_e0eee154ef.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p>Each block is a self-contained chunk of sorted tokens that can be read sequentially.</p>\n</blockquote>\n<p>Reading blocks sequentially avoids scattered random accesses and keeps lookups efficient even when the index files reside on object storage.</p>\n<h4 id=\"front-coded-compression-within-blocks\"></h4>\n<p>Looking at the blocks, we can immediately observe that consecutive tokens often share a common prefix — for example, \"algo\", \"algorithm\", and \"algorithmic\". Storing the full string for every token would be wasteful.</p>\n<p>To keep dictionary blocks compact without forgoing the sequential layout, the new design compresses the tokens using front-coding. This compression method stores the first token of each block unchanged. All following tokens are each replaced by the length of the prefix they share with the previous token and their suffix.</p>\n<p>Front-coding significantly reduces block size on disk.</p>\n<p>In the diagram below, the token column is shown only for readability; on disk, only the encoded (prefix_length, suffix) values (highlighted in violet) are stored.</p>\n<p><span><img alt=\"Rethinking full-text search for object storage #1514 Open (1).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FRethinking_full_text_search_for_object_storage_1514_Open_1_32c15c69a7.png&w=2048&q=75\"></span></p>\n<h4 id=\"posting-list-offsets-in-dictionary-blocks\"></h4>\n<p>During text search, once a token is found in the dictionary, the engine must locate the rows where that token appears. These row positions of each token is stored in a posting list.</p>\n<p>Each dictionary entry therefore stores a byte offset into the posting list file (text_idx.pst.idx), allowing ClickHouse to jump directly to the posting list of a token.</p>\n<p><span><img alt=\"Rethinking full-text search for object storage #1514 Open (2).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FRethinking_full_text_search_for_object_storage_1514_Open_2_5ce960efd9.png&w=2048&q=75\"></span></p>\n<p>For simplicity, the diagram shows the data organization only conceptually; we implemented special cases for storing the actual posting lists which we describe in more detail later.</p>\n<p>So far, we have looked at the dictionary layout, the first of the three main components that make up the new text index. Next, we look at the sparse index, which allows ClickHouse to find the correct dictionary block quickly without scanning the entire dictionary file.</p>\n<h3 id=\"sparse-index-for-fast-dictionary-lookups\"></h3>\n<p>With potentially millions of tokens spread across thousands of dictionary blocks, we need a fast way to find the right dictionary block that contains a given token.</p>\n<p>Of course, we could load or scan all dictionary blocks (or do a binary search in them), but that would be unacceptably slow.</p>\n<p>The sparse index solves this by recording the first token of each dictionary block together with the byte offset of this block within the dictionary file (text_idx.dct.idx).</p>\n<p>The sparse index itself is stored in a separate file (text_idx.idx). Compared to the dictionary blocks and the posting lists, the sparse index is so small that it remains loaded in memory at all times.</p>\n<p>The diagram below shows the sparse index file (text_idx.idx) pointing to dictionary blocks located at different offsets within the dictionary file.</p>\n<p><span><img alt=\"Rethinking full-text search for object storage #1514 Open (3).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FRethinking_full_text_search_for_object_storage_1514_Open_3_4426fabc31.png&w=2048&q=75\"></span></p>\n<p>This design will look familiar to you if you know how ClickHouse's <a target=\"_blank\" href=\"https://clickhouse.com/docs/primary-indexes\">primary key index</a> works — in fact, both indexes perform this kind of “sparse indexing”: they store for each block an entry point, allow to jump to the right neighborhood, and scan sequentially from there on. The difference is that, here, the blocks contain dictionary tokens instead of row values.</p>\n<blockquote>\n<p>The sparse index and dictionary blocks minimize random I/O and allow lookups to proceed mostly sequentially, keeping dictionary access efficient on both local disks and object storage.</p>\n</blockquote>\n<p>With the dictionary blocks and sparse index in place, the engine can locate a token efficiently.</p>\n<p>The next step is to read the posting list, which stores the row positions on which a token appears.</p>\n<h3 id=\"posting-lists-mapping-tokens-to-row-positions\"></h3>\n<p>In the previous section, we used a simplified layout to show how dictionary entries reference posting lists on disk.</p>\n<p>In practice, posting lists can vary enormously in size. Some tokens appear only once or twice in the dataset, while others may appear in millions of rows.</p>\n<p>To represent posting lists of all sizes efficiently, the new text index in ClickHouse uses different posting list representations, depending on the posting list size:</p>\n<ul>\n<li><strong>Roaring bitmap</strong> posting lists — used for posting lists with more than 12 row IDs</li>\n<li><strong>VarInt-encoded</strong> posting lists — used for posting lists with 7 to 12 row IDs</li>\n<li><strong>Embedded</strong> posting lists — used for posting lists with 6 or fewer row IDs</li>\n</ul>\n<p>We describe each representation below.</p>\n<h4 id=\"roaring-bitmap-posting-lists-12-row-ids\"></h4>\n<p>A posting list with more than 12 contained rows is stored as a so-called Roaring Bitmap.</p>\n<p>A Roaring Bitmap is a compressed bitmap that can hold a large set of 32-bit integers while still supporting fast intersections and unions. Both operations are important for SQL functions like hasAnyTokens() and hasAllTokens() that combine multiple posting lists.</p>\n<p><strong>Internal layout</strong></p>\n<p>Roaring Bitmaps split the 32-bit integer space into two halves. The upper half is based on the upper 16 bits of the row IDs, representing 65,536 different possible values.</p>\n<p>The lower halves are stored in one of three different containers. Containers choose the most compact internal representation depending on the number of contained row IDs:</p>\n<ul>\n<li>Array container — used for sparse chunks</li>\n<li>Bitmap container — used for dense chunks</li>\n<li>Run-length container — used for chunks with many consecutive runs</li>\n</ul>\n<p>This adaptive layout allows Roaring Bitmaps to compress posting lists with very different internal data distributions efficiently while still allowing for fast set operations.</p>\n<p><strong>Example</strong></p>\n<p>To see why this matters, consider the token <code>connect</code> in a large text dataset. Suppose <code>connect</code> appears in row IDs 65,536, 65,538, 65,539, 65,542, and tens of thousands more row IDs scattered across the table. Storing these numbers as a plain sorted array of 32-bit integers would cost 4 bytes per entry, that is ~200 KB just for storing 50,000 matching rows.</p>\n<p>With Roaring Bitmaps, the upper 16 bits (0x0001) of each value identify the container — a bucket responsible for the row IDs in range 65,536–131,071. The lower 16 bits (0x0006) are the values stored inside that container. In this example, all four row IDs fall into the same container.</p>\n<p>Each container independently chooses its internal layout based on the distribution of row IDs it contains:</p>\n<p><span><img alt=\"Rethinking full-text search for object storage #1514 Open (4).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FRethinking_full_text_search_for_object_storage_1514_Open_4_8b12a7766b.png&w=2048&q=75\"></span></p>\n<p><strong>On-disk layout</strong></p>\n<p>For large posting lists Roaring Bitmaps work extremely well: they provide good compression and enable efficient query operations such as intersecting multiple posting lists during search.</p>\n<p>Internally, Roaring Bitmaps posting lists and are further divided into blocks (controlled by <code>posting_list_block_size</code>). Each block records the minimum and maximum row ID it contains. This metadata allows the query engine to skip decompressing blocks whose row ranges have already been ruled out by other predicates, reducing unnecessary work during search.</p>\n<p><strong>Limitations</strong></p>\n<p>However, Roaring bitmaps have a non-trivial minimum size due to their mandatory metadata. This overhead is negligible for large posting lists but it becomes wasteful for smaller posting lists. It is therefore important to introduce specialized representations for sparse tokens which are frequent in natural language and text datasets. ClickHouse’s inverted index uses two additional representations for such cases.</p>\n<h4 id=\"varint-encoded-posting-lists-7-12-row-ids\"></h4>\n<p>For small posting lists between 7 and 12 contained row IDs, the text index stores row IDs as a plain sequence of VarInt-compresed integers.</p>\n<p>VarInt splits every byte into 7 bits of data “payload” bits and a continuation bit. As a result, values below 128 require only a single byte, values below 16,384 require two bytes, and so on.</p>\n<p><span><img alt=\"Rethinking full-text search for object storage #1514 Open (5).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FRethinking_full_text_search_for_object_storage_1514_Open_5_7d53933506.png&w=2048&q=75\"></span></p>\n<p>Because row IDs in small posting lists are often relatively small integers, this VarInt encoding compresses on average really well. For example, a posting list with 12 row IDs typically consumes only a few dozen bytes.</p>\n<p><strong>Why not use Roaring here</strong></p>\n<p>Using Roaring for such posting lists would be inefficient because the serialized structure has a minimum size of roughly 48 bytes caused by its header and container metadata. A simple list of VarInts is therefore the smaller and simpler alternative.</p>\n<h4 id=\"embedded-posting-lists-6-row-ids\"></h4>\n<p>During development of the text index, we found that in real-world datasets, the vast majority of distinct tokens has very low cardinality. We looked at two large and very different datasets:</p>\n<ul>\n<li>\n<p>An internal log file dataset with 21.79 billion distinct tokens</p>\n</li>\n<li>\n<p>A natural language web corpus (Fineweb, <a target=\"_blank\" href=\"https://huggingface.co/datasets/HuggingFaceFW/fineweb\">https://huggingface.co/datasets/HuggingFaceFW/fineweb</a>) with 25.51 billion distinct tokens</p>\n<p>The results were consistent across both datasets:</p>\n</li>\n</ul>\n<ol>\n<li>94.5%, respectively, 90.2% of all tokens appear in six or fewer rows.</li>\n<li>The median token cardinality is 2, respectively, 1.</li>\n<li>Only 3%, respectively, 6.1% of all tokens have a cardinality &gt;12, i.e. the threshold below which Roaring Bitmaps have a static overhead.</li>\n<li>The threshold of six for embedded posting lists, chosen for memory layout reasons, turns out to capture 90% of tokens at P90 in both datasets (an accidental but near-perfect empirical fit).</li>\n</ol>\n<p><strong>Why storing small posting lists separately is wasteful</strong></p>\n<p>For most tokens, the full machinery of a Roaring Bitmap — with its container metadata and separate file entry — would constitute a significant overhead. For posting lists with six or less elements; the index could avoid writing into the posting list file entirely.</p>\n<p><strong>Embedded layout</strong></p>\n<p>Instead, if a token appears in six rows or fewer, the row IDs are embedded directly into the dictionary entry in place of the byte offset into the posting list file. As a result, the entire posting list can be read without an additional indirection and disk access.</p>\n<p><strong>Relation to small-object optimizations</strong></p>\n<p>This idea is inspired by the so-called small-object optimization (e.g. SSO, Short String Optimization) in systems programming, where very small values are stored inline rather than in a separate location. For rare tokens — which are extremely common in natural language datasets — this approach eliminates both the storage overhead and the extra I/O.</p>\n<p><span><img alt=\"Rethinking full-text search for object storage #1514 Open (6).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FRethinking_full_text_search_for_object_storage_1514_Open_6_78f9df3f3e.png&w=2048&q=75\"></span></p>\n<p>We have now covered the three main data structures of the new text index: dictionary blocks, the sparse index, and posting lists.</p>\n<p>Before we look at how these pieces work together during query execution, we briefly detour into part merges, where the text index layout also plays an important role.</p>\n<h2 id=\"efficient-merges-of-text-indexes\"></h2>\n<p>As mentioned earlier, the text index is stored inside each data part as three separate files: the dictionary, the sparse index, and the posting lists.</p>\n<p>ClickHouse continuously <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges\">merges</a> smaller data parts into larger ones in the background, rewriting all files of the merged parts. When these files reside on object storage, merge performance depends heavily on the access pattern.</p>\n<p>The new text index layout is designed to support efficient sequential access during merges. Because dictionary blocks are already stored in sorted order, the text index does not need to be rebuilt from scratch. Instead, ClickHouse can merge them using the same <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-1-purpose-built-engines#merges-are-fast-thanks-to-sorted-parts\">single merge pass</a> that ClickHouse uses for table row data.</p>\n<p>During the merge, the dictionaries of both parts are read sequentially and interleaved into a new sorted dictionary, avoiding random I/O and making index merges efficient even when index files reside on object storage.</p>\n<p>The animation below shows a merge of two data parts. To keep the illustration focused, we only show the merge of the dictionary files, while <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">the other files of the data part</a> are merged in the same pass but not displayed.</p></div><div><p>Not shown in the animation above — posting lists in the posting list file (text_idx.pst.idx) are updated in the same pass by remapping row numbers using the row-id mapping produced during the main part merge, so the original text columns do not need to be read again.</p>\n<p>As a result, merging text indexes is lightweight and scales with the size of the index itself, not with the size of the original text data.</p>\n<p>Also not shown in the animation above — the sparse index file (text_idx.idx) is rebuilt for the merged part from the merged dictionary blocks.</p>\n<p>With part merges covered, we now return to query execution and look at how the dictionary blocks, sparse index, and posting lists work together during search.</p>\n<h2 id=\"how-the-query-engine-uses-the-text-index\"></h2>\n<p>Consider the following table with a text index</p>\n<div><pre><code><span><span>CREATE TABLE</span> docs</span>\n<span>(</span>\n<span>    `key` UInt64,</span>\n<span>    `doc` String,</span>\n<span>    INDEX idx(doc) TYPE text(tokenizer <span>=</span> splitByNonAlpha)</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree()</span>\n<span><span>ORDER</span> <span>BY</span> key;</span></code></pre></div>\n<!-- -->\n<p>and the following query</p>\n<div><pre><code><span><span>SELECT</span> <span>count</span>() <span>FROM</span> docs <span>WHERE</span> hasToken(doc, <span>'clickhouse'</span>);</span></code></pre></div>\n<!-- -->\n<p>Here, we are searching for a token <code>clickhouse</code>.</p>\n<p>Let's walk through what happens internally when this query runs.</p>\n<h3 id=\"step-1-finding-matching-row-numbers\"></h3>\n<p>We first need to understand which dictionary block contains the token <code>clickhouse</code>.</p>\n<p>Scanning all blocks sequentially would be too costly. Instead, we utilize the sparse index to find the right block.</p>\n<p>Since the sparse index holds only the first token of each block, we run a binary search using the upper bound to locate the candidate block. The search token usually does not appear in the sparse index itself, but the upper bound tells us which block it would fall into if it was indexed.</p>\n<p>Note that the sparse index is comparatively small and kept in main memory all the time. Therefore, the binary search itself takes only a few microseconds.</p>\n<p>In the diagram below, the sparse index lookup returns the entry whose dictionary block may contain <code>clickhouse</code>. Its offset tells us which block to read from the dictionary file.</p>\n<p><span><img alt=\"Rethinking full-text search for object storage #1514 Open (7).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FRethinking_full_text_search_for_object_storage_1514_Open_7_5a031aa537.png&w=2048&q=75\"></span></p>\n<p>We next read the found dictionary block sequentially and scan its tokens.</p>\n<blockquote>\n<p>Since the dictionary is stored on object storage, a block scan is about as fast as a point lookup in the block  - the runtime is dominated by the latency to make a request and retrieve its result.</p>\n</blockquote>\n<p>In the diagram below, the sparse index gives us the offset of the candidate dictionary block within the dictionary file. We read this block sequentially and scan it until <code>clickhouse</code> is found.</p>\n<p><span><img alt=\"Rethinking full-text search for object storage #1514 Open (8).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FRethinking_full_text_search_for_object_storage_1514_Open_8_dc22ad458c.png&w=2048&q=75\"></span></p>\n<p>Once <code>clickhouse</code> is found in the dictionary block, we read the associated posting list from the posting list file.</p>\n<p>In the diagram below, the candidate dictionary block gives us the offset of the posting list within the posting lists file. We then retrieve that posting list.</p>\n<p><span><img alt=\"Rethinking full-text search for object storage #1514 Open (9).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FRethinking_full_text_search_for_object_storage_1514_Open_9_82cf0a82e3.png&w=2048&q=75\"></span></p>\n<p>The retrieved posting list contains the matching row numbers.</p>\n<p>The engine must now decide how to apply them during execution.</p>\n<h3 id=\"step-2-choosing-the-execution-mode\"></h3>\n<p>The index lookup returns the row numbers of matching rows as offsets inside data part columns.</p>\n<p>Depending on the query shape and the text search functions used, ClickHouse can apply these offsets in three different ways, from most efficient to least efficient.</p>\n<ul>\n<li>\n<p>The engine can build a virtual column from the offsets and either</p>\n<ul>\n<li>avoid reading the indexed text columns entirely, or</li>\n<li>use the virtual column to narrow the candidate set before checking the remaining rows.</li>\n</ul>\n</li>\n<li>\n<p>For more complex search patterns, it falls back to classical skip index evaluation, where the index is only used to skip granules that cannot contain matches.</p>\n</li>\n</ul>\n<p>In the following three sections, we describe these three approaches.</p>\n<h3 id=\"step-2a-direct-read-mode\"></h3>\n<p>The text index is special among ClickHouse's skip indexes: its posting list contains the <em>exact</em> row numbers that match the query — no false positives, no further filtering needed.</p>\n<p>Since we already know the exact rows, we can skip the usual filtering step and go straight to row-level masking.</p>\n<p><strong>Row-level masking with a virtual column</strong></p>\n<p>We use the row IDs in the posting list to construct an virtual boolean column (an internal column that only exists for the duration of the query) and set all matching rows to <code>1</code> and all other rows to <code>0</code>.</p>\n<p><span><img alt=\"Rethinking full-text search for object storage #1514 Open (10).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FRethinking_full_text_search_for_object_storage_1514_Open_10_5373ab657b.png&w=2048&q=75\"></span></p>\n<p><strong>PREWHERE Query rewrite</strong></p>\n<p>ClickHouse then rewrites the query automatically to filter the virtual column. For example, query</p>\n<div><pre><code><span><span>SELECT</span> <span>count</span>() <span>FROM</span> docs <span>WHERE</span> hasToken(doc, <span>'clickhouse'</span>);</span></code></pre></div>\n<!-- -->\n<p>is rewritten to</p>\n<div><pre><code><span><span>SELECT</span> <span>count</span>() <span>FROM</span> docs PREWHERE _text_index_virtual_idx <span>=</span> <span>1</span>;</span></code></pre></div>\n<!-- -->\n<p><strong>PREWHERE evaluation</strong></p>\n<p>The <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/prewhere\">PREWHERE</a> clause evaluates its condition before other WHERE conditions are evaluated, meaning that only matching rows are passed to the next processing step (WHERE). Unmatched rows are eliminated as early as possible, reducing both I/O and the number of rows processed by subsequent operators.</p>\n<p><strong>Multiple tokens</strong></p>\n<p>When a query involves multiple tokens — for example, multiple <code>hasToken</code> conditions or a multi-token <code>hasAnyTokens/hasAllTokens</code> call — each token goes through the same lookup process independently, producing its own posting list. The virtual column is then filled using bitwise operations across these posting lists: <code>AND</code> for conjunctive conditions (all tokens must match), <code>OR</code> for disjunctive conditions (any token must match). This keeps the row filtering fast and avoids per-row string evaluation.</p>\n<p><strong>Why this is called direct read mode</strong></p>\n<p>What we just described is called “direct read” mode internally within ClickHouse. It is the most natural and most efficient way to utilize the text index.</p>\n<blockquote>\n<p>The indexed text column is not read at all because the query is answered solely using the row-level information stored in the text index.</p>\n</blockquote>\n<p><strong>Limitations and supported functions</strong></p>\n<p>Direct read is only safe when the index tokens correspond exactly to the searched values and no false positives are possible.This is the case for SQL functions <code>hasToken</code>, <code>hasAnyTokens</code>, and <code>hasAllTokens</code>.</p>\n<h3 id=\"step-2b-direct-read-with-hint\"></h3>\n<p>For certain predicates, normal direct read is not possible. For example, consider the query</p>\n<div><pre><code><span><span>SELECT</span> col1, col2 <span>FROM</span> <span>table</span> <span>WHERE</span> col3 <span>LIKE</span> <span>'%clickhouse performance%'</span></span></code></pre></div>\n<!-- -->\n<p><strong>Using the index as a hint</strong></p>\n<p>To use the text index here, ClickHouse tokenizes the search pattern and looks up the tokens clickhouse and performance in the index. But a row containing both tokens is not guaranteed to match the full pattern. The words might appear far apart (<code>clickhouse has great performance</code>) or in a different order (<code>the performance of clickhouse</code>). In other words, relying just on the index alone can produce false positives. We can however use the index as a “hint” to rule out rows that don’t contain both tokens <code>clickhouse</code> and <code>performance</code>.</p>\n<blockquote>\n<p>If most rows in a part do not contain both tokens, the index can eliminate the majority of candidates before the expensive LIKE evaluation runs on the column.</p>\n</blockquote>\n<p><strong>Direct read with hint mode</strong></p>\n<p>We call this “direct read with hint” mode - the virtual column narrows the candidate set, afterwards the original LIKE predicate is evaluated on the surviving rows.</p>\n<p><strong>Cost of reading posting lists</strong></p>\n<p>One challenge that comes with this trick is that reading posting lists is not free; it requires seeks and decompression. For example, if the token “clickhouse” appears in 80% of rows, the index would eliminate only relatively few rows, while still paying the I/O cost for all the rows. In that case it is better to avoid the index read entirely and evaluate the LIKE predicate directly on the column.</p>\n<p><strong>Selectivity-based decision</strong></p>\n<p>To make this decision, ClickHouse estimates the cardinality of the matching set using the per-token cardinalities already available from the dictionary, without reading any posting list payloads. If the estimate falls at or below <strong>text_index_hint_max_selectivity × N</strong> (default: 20% of total rows in the part), the hint is accepted: posting lists are read, the virtual column is filled, and non-matching rows are filtered before the LIKE check runs. Else, if  the estimate exceeds the threshold, the hint is discarded: the virtual column is set to all-ones, no index I/O happens, and the original predicate carries the full filtering load.</p>\n<p><strong>Observability</strong></p>\n<p>The two outcomes are exposed as profile events — TextIndexUseHint and TextIndexDiscardHint — which can be observed in query logs to understand whether the index is contributing to a given query.</p>\n<p><strong>Supported functions</strong></p>\n<p>Supported SQL functions: <code>like</code>, <code>startsWith</code>, <code>endsWith</code>, <code>mapContainsKeyLike</code>/<code>ValueLike</code></p>\n<h3 id=\"step-2c-skipping-index-mode\"></h3>\n<p>When a predicate cannot take any advantage of the direct read optimization or hint mode, the optimizer assigns it to execute in fallback read mode using ClickHouse’s skipping index infrastructure, and the predicate is evaluated normally against the column.</p>\n<p>This technique is utilized for more complex patterns like: <code>match</code>, <code>multiSearchAll</code>, <code>multiSearchAny</code>.</p>\n<p>Consider for example this query:</p>\n<div><pre><code><span><span>SELECT</span> col1, col2 <span>FROM</span> <span>table</span> <span>WHERE</span> <span>match</span>(col3, <span>'connect.*timeout'</span>)</span></code></pre></div>\n<!-- -->\n<p>A regex predicate like this cannot be decomposed into a reliable set of tokens — the pattern expresses a sequence and proximity constraint that the index has no way to verify. The optimizer evaluates it in classical read mode:</p>\n<blockquote>\n<p>The text index is used at a granule level by checking whether each granule contains tokens that could plausibly satisfy the pattern, and skipping those that cannot.</p>\n</blockquote>\n<p><strong>Why this is slower than direct read</strong></p>\n<p>For every granule that passes this coarse filter, the engine must decompress col3 in full and scan it row by row to evaluate the regex on the actual string data. Text columns are typically wide and expensive to decompress, and a pattern matching a common word can leave most granules as candidates. The index reduces I/O at the granule boundary, but the dominant cost (decompressing and scanning the column) remains.</p>\n<p>This is precisely the gap that direct read closes for the predicates that support it: instead of decompressing the column to confirm what the index already knows, the posting list result is used directly.</p>\n<p>At this point we have covered the internal design of the text index and how queries execute against it.</p>\n<p>In the next section, we move from implementation details to configuration and usage.</p>\n<h2 id=\"defining-the-text-index\"></h2>\n<p><em>If you want a quick practical introduction before diving into the details below, the short video below walks through how to create and use a text index in ClickHouse.</em></p>\n<p>Before looking at how to create a text index, let’s first see which column types can be indexed.</p>\n<p>A text index can be defined on columns of type  <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/string\">String</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/fixedstring\">FixedString</a>, as well as <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/array\">Array</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/map\">Map</a> columns containing strings.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/nullable\">Nullable</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/lowcardinality\">LowCardinality</a> strings are also supported, and all the aforementioned data types can be mixed and matched, e.g. <code>Array(Nullable(FixedString))</code>.</p>\n<p>Let's now see how to create a text index.</p>\n<h3 id=\"creating-a-text-index\"></h3>\n<p>There are two ways to add an index to a table, during table creation as part of the CREATE TABLE query or by running ALTER QUERY on an existing table. See <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/mergetree-family/textindexes#creating-a-text-index\">the documentation</a> for more details.</p>\n<p>Syntax:</p>\n<div><pre><code><span><span>CREATE</span><span>/</span><span>ALTER TABLE</span> </span>\n<span>...</span>\n<span>   INDEX text_idx(str) TYPE text(</span>\n<span>                               <span>-- Mandatory parameters:</span></span>\n<span>                               tokenizer <span>=</span> splitByNonAlpha</span>\n<span>                                           <span>|</span> splitByString[(S)]</span>\n<span>                                           <span>|</span> ngrams[(N)]</span>\n<span>                                           <span>|</span> sparseGrams[(min_length[, max_length[, min_cutoff_length]])]</span>\n<span>                                           <span>|</span> <span>array</span></span>\n<span>                               <span>-- Optional parameters:</span></span>\n<span>                               [, preprocessor <span>=</span> expression(str)]</span>\n<span>                               <span>-- See documentation for optional advanced parameters</span></span>\n<span>\t\t\t\t    ...</span>\n<span>                           )</span>\n<span>...</span></code></pre></div>\n<!-- -->\n<p>For example:</p>\n<div><pre><code><span><span>CREATE TABLE</span> my_table</span>\n<span>(</span>\n<span>   key UInt64,</span>\n<span>   str String,</span>\n<span>   INDEX text_idx(str) TYPE MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> key</span></code></pre></div>\n<!-- -->\n<p>This creates a text index that will first lowercase any strings inserted into the ‘str’ column and then split them on non-alphanumeric characters and store them in the search-optimized text index structure described above. E.g. ‘HeLlo my1!!!NAME&amp;is,234234’ will be split into [‘hello’, ‘my1’, ‘name’, ‘is’, ‘234234’] and will allow fast searching for these tokens.</p>\n<p>Before we do any searching, let’s first take a look at the index parameters, specifically the tokenizer and preprocessor.</p>\n<h3 id=\"index-parameters-and-tokenization\"></h3>\n<p>Tokenization and preprocessing are two critical aspects of the text index that set it apart from other indexes and enable easy, fast searching over noisy text data. Together, these two components allow powerful, automated data transformation on INSERT, and can facilitate intuitive search results such as searching for <code>cafe</code> and matching ‘cafe’, ‘café’, ‘Café’, ‘CAFÉ’, etc.!</p>\n<p>Let’s look at them in more detail.</p>\n<h4 id=\"preprocessing\"></h4>\n<p>This the proprocessor is executed on the input column prior to tokenization. Unlike functions applied directly to the input column when creating the index (e.g. <code>INDEX idx(lower(col))</code>), ClickHouse automatically applies preprocessor expressions also to the input in specialized text search functions (when run on the same indexed  column):  <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/functions/string-search-functions#hasToken\">hasToken</a>, <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/functions/string-search-functions#hasAllTokens\">hasAllTokens</a>, and <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/functions/string-search-functions#hasAnyTokens\">hasAnyTokens</a>. When combined with ClickHouse’s <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/functions/string-functions\">extensive list of string functions</a> we get a powerful preprocessing pipeline that can <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/functions/string-functions#lower\">lowercase text</a>, <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/functions/string-functions#removeDiacriticsUTF8\">remove accents</a>, <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/functions/string-functions#extractTextFromHTML\">process HTML</a>, <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/functions/string-functions#normalizeUTF8NFC\">apply UTF8 normalization</a>, and more!</p>\n<p>The syntax for the pre-processor is as follows:</p>\n<div><pre><code><span>preprocessor <span>=</span> expression(<span>&lt;</span><span>column</span><span>-</span>name<span>&gt;</span>)</span></code></pre></div>\n<!-- -->\n<p>Some notes:</p>\n<ul>\n<li><code>expression()</code> can be as simple or complex as desired, it can contain any number of nested functions (although keep in mind that they will be run on each inserted row).</li>\n<li>The expression functions **must **be deterministic.</li>\n<li><code>&lt;column-name&gt;</code> must match the index definition, aka if your index was defined with <code>INDEX &lt;idx-name&gt;(lower(col1))</code> then the preprocessor expression must also be called on <code>lower(col1)</code>, this is enforced.</li>\n</ul>\n<h6 id=\"examples\"></h6>\n<p>Scenario 1: Input data is human-generated text, containing mixed-case characters and punctuation. The index lowercases the text, allowing for case-insensitive matching during search.</p>\n<div><pre><code><span>preprocessor <span>=</span> <span>lower</span>(col)</span>\n<span></span>\n<span>Input:       <span>'Hello World! My_Name IS John123'</span></span>\n<span>Preprocessed: <span>'hello world! my_name is john123'</span></span></code></pre></div>\n<!-- -->\n<p>Scenario 2: Input data contains multi-line strings, but only the first string is relevant for search.</p>\n<div><pre><code><span>preprocessor <span>=</span> substringIndex(col, <span>'\\n'</span>, <span>1</span>)</span>\n<span></span>\n<span>Input:       <span>'Hello World\\nSecond Line\\nThird Line'</span></span>\n<span>Preprocessed: <span>'Hello World'</span></span></code></pre></div>\n<!-- -->\n<p>Scenario 3: Input data consists of HTML strings, the preprocessor is used to first remove HTML elements (replacing them with whitespace), then the result is lowercased.</p>\n<div><pre><code><span>preprocessor <span>=</span> <span>lower</span>(extractTextFromHTML(col))</span>\n<span></span>\n<span>Input: <span>'Hello WorldMy ,[object Object], IS Sarah456'</span></span>\n<span>Preprocessed: <span>'hello world my name is sarah456'</span></span></code></pre></div>\n<!-- -->\n<p>Scenario 4: Input data contains mixed-case, accented text (e.g. French, German, etc.). First <a target=\"_blank\" href=\"https://unicode-org.github.io/icu/userguide/transforms/casemappings.html#case-folding\">case folding</a> is applied to the text, then the resulting text is stripped of diacritics (accents).</p>\n<div><pre><code><span>preprocessor <span>=</span> removeDiacriticsUTF8(caseFoldUTF8(col))</span>\n<span></span>\n<span>Input:       <span>'Héllo Wörld ÑOÑO Ångström'</span></span>\n<span>Preprocessed: <span>'hello world nono angstrom'</span></span></code></pre></div>\n<!-- -->\n<p>With preprocessing in place, we now look at tokenization, which defines how the input text is split into tokens for indexing.</p>\n<h4 id=\"tokenization\"></h4>\n<p>This is the final piece of the puzzle, the tokenizer specifies how the column rows should be split into tokens. This is a critical decision because it will affect which queries match the index and which don’t. For example, an index that splits the data by whitespace will not match parts of words (e.g. ‘caf’ will not match ‘cafe’) but an index using the ngram tokenizer with an ngram length of 3 <strong>will</strong> match ‘caf’ to ‘cafe’.</p>\n<p>There are a few broad types of tokenizers:</p>\n<h5 id=\"splitby-tokenizers\"></h5>\n<p>The ‘splitByNonAlpha’ and ‘splitByString’ tokenizers, as their names suggest, split  the input by non-alphanumeric characters or custom separators. This is useful for most natural language text such as product reviews, or for splitting domain-specific strings with consistent delimiters.</p>\n<p>Examples:</p>\n<div><pre><code><span><span>-- splitByNonAlpha</span></span>\n<span>‘hello my1<span>!</span><span>!</span><span>!</span>name<span>&amp;</span><span>is</span>,<span>234234</span>’ <span>-</span><span>&gt;</span> [‘hello’, ‘my1’, ‘name’, ‘<span>is</span>’, ‘<span>234234</span>’]</span>\n<span></span>\n<span><span>-- splitByString with default ' ' separator</span></span>\n<span><span>'hello my name is John'</span> <span>-</span><span>&gt;</span> [<span>'hello'</span>, <span>'my'</span>, <span>'name'</span>, <span>'is'</span>, <span>'John'</span>]</span>\n<span></span>\n<span><span>-- splitByString with custom separators [', ', '; ', '\\n']</span></span>\n<span><span>'apples, oranges; bananas\\npears'</span> <span>-</span><span>&gt;</span> [<span>'apples'</span>, <span>'oranges'</span>, <span>'bananas'</span>, <span>'pears'</span>]</span>\n<span></span>\n<span><span>-- splitting csv data (custom separator ',')</span></span>\n<span><span>'hello,world,foo,bar'</span> <span>-</span><span>&gt;</span> [<span>'hello'</span>, <span>'world'</span>, <span>'foo'</span>, <span>'bar'</span>]</span></code></pre></div>\n<!-- -->\n<h5 id=\"-gram-tokenizers\"></h5>\n<p>The ‘ngrams’ and ‘sparseGrams’ tokenizers split strings into constant-length and variable-length tokens, respectively. Now that we have an index set up on a column, let’s populate it with some data and try searching for some text!</p>\n<p>While common string search functions such as =, IN, and LIKE (the full list is provided further down) will leverage the text index by default, we recommend using the new text search functions hasAnyTokens and hasAllTokens for best results.</p>\n<h3 id=\"using-the-recommended-search-functions\"></h3>\n<p>Functions <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/functions/string-search-functions#hasAnyTokens\">hasAnyTokens</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/functions/string-search-functions#hasAllTokens\">hasAllTokens</a> match against one or all of the given tokens, respectively.
