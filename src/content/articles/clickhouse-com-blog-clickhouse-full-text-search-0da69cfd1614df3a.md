Each row contains a natural language document, i.e. a text written by human or a machine that follows a natural language grammar (no random IDs, no hash values).</p>\n<p>Because ClickHouse is a <strong>column-oriented database</strong>, we store these documents one after another in a column of type<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/data-types/string/\"> String</a>. Each row holds a single document, which we can later search.</p>\n<p>To make the content searchable, we split every document into a series of <strong>tokens</strong>, typically words. For example, the sentence:</p>\n<p><code>All cats like mice</code></p>\n<p>…would be tokenized as:</p>\n<p><code>[All, cats, like, mice]</code></p>\n<p>The default tokenizer splits strings by spaces or punctuation. More advanced tokenizers can split log messages into their components, for example, timestamp, severity, and message fields, or even extract <strong>n-grams</strong> for fuzzy search.</p>\n<p>A <strong>full-text search</strong> then retrieves documents that contain a specific token. For example, to find the rows which mention <code>cat</code>, we might run:</p>\n<div><pre><code><span><span>SELECT</span> [...] <span>FROM</span> [...] <span>WHERE</span> documents <span>LIKE</span> <span>'% cat %'</span></span></code></pre></div>\n<!-- -->\n<p>(Notice the spaces — without them, we might accidentally match “edu<span>cat</span>e” or “multipli<span>cat</span>ion.”)</p>\n<p>Full-text search can be implemented in two ways:</p>\n<ul>\n<li>\n<p><strong>Full scans</strong> – scan every row (slow)</p>\n</li>\n<li>\n<p><strong>Inverted indexes</strong> – map each token to its containing rows (fast)</p>\n</li>\n</ul>\n<p>Inverted indexes make it possible to search massive datasets in milliseconds, and that’s exactly what ClickHouse now supports natively, with scale and performance in mind.</p>\n<p>Before we dive into the details of how it works, let’s unpack the name “inverted index”, a simple idea that flips the usual document → terms mapping on its head, but can seem counter-intuitive if you’ve never worked with search engines before.</p>\n<h3 id=\"why-is-it-called-an-inverted-index\"></h3>\n<p>When you read multiple documents from beginning to end, you can remember for each document the (unique) terms it contains. This <code>document → terms</code> mapping is sometimes called forward index.</p>\n<p>An <strong>inverted index</strong> search flips that around: It stores a <strong>term → documents mapping</strong>. Given a term, it allows you to find all documents that contain it.</p>\n<p>It’s like the back of a book: instead of reading pages to find a word, you look up the word to see which pages it’s on. That reverse lookup is what makes search engines fast, and it’s built into ClickHouse.</p>\n<p>Now that we know what an inverted index is, it’s worth looking at where ClickHouse started. ClickHouse has always had ways to speed up text lookups, but these were approximations. To see why a true inverted index was needed, let’s trace the evolution from our earlier Bloom-filter-based approach to the new design.</p>\n<h2 id=\"from-bloom-filters-to-real-indexes\"></h2>\n<p>Before introducing native text indexes, ClickHouse already supported full-text search using the \"bloom_filter\" \"tokenbf_v1\" and \"ngrambf_v1\" indexes. These are based on Bloom filters, a probabilistic data structure for checking whether the indexed documents contain a value.</p>\n<p>Compared to inverted indexes, Bloom filters come with a few key limitations:</p>\n<ul>\n<li>\n<p><strong>Hard to tune:</strong> Using a Bloom filter requires manual tuning of the byte size, the number of hash functions, and an understanding how they affect the false positive rate. This often requires deep expertise.</p>\n</li>\n<li>\n<p><strong>False positives:</strong> Bloom filters may answer that a value <em>might</em> exist even when it doesn’t. This means that additional rows have to be scanned, reducing efficiency of the search.</p>\n</li>\n<li>\n<p><strong>Limited functionality:</strong> Bloom filter indexes only support a small subset of expressions in the WHERE clause, while inverted indexes are, in principle, more versatile.</p>\n</li>\n</ul>\n<p>Inverted indexes solve all three of these issues, and that’s why they now power full-text search in ClickHouse.</p>\n<h2 id=\"how-the-new-text-index-works\"></h2>\n<p>To understand how the new engine achieves its speed and precision, we first need to look at how the index is organized on disk and how queries interact with its building blocks.</p>\n<h3 id=\"index-structure-dictionaries-posting-lists\"></h3>\n<p>ClickHouse’s full-text search is powered by a <strong>native inverted index</strong>, also known as a <em>text index</em>. Conceptually, this index consists of two key components:</p>\n<ol>\n<li>\n<p><strong>A dictionary</strong>, storing all unique tokens across all documents.</p>\n</li>\n<li>\n<p><strong>Posting lists</strong>, which record the row numbers of documents that contain each token.</p>\n</li>\n</ol>\n<p>Here’s how it works:</p>\n<ul>\n<li>\n<p>When you search for a token, ClickHouse looks it up in the dictionary.</p>\n</li>\n<li>\n<p>If it is found, the dictionary returns the location of the corresponding posting list.</p>\n</li>\n<li>\n<p>The <strong>posting list</strong> is simply a list of row numbers — i.e., the documents — that contain that token.</p>\n<p>Example:</p>\n</li>\n<li>\n<p>The token <code>wind</code> might appear in documents 12, 15, 99, 100, and 141.</p>\n</li>\n<li>\n<p>The token <code>winter</code> might appear in documents 12, 514, 678, and 2583.</p>\n</li>\n</ul>\n<p>This index design makes token lookups fast and efficient — even at massive scale.</p>\n<p>Below is a simplified diagram of this structure:</p>\n<p><span><img alt=\"Full-text search 16.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FFull_text_search_16_77b912e274.png&w=2048&q=75\"></span></p>\n<p>Under the hood, ClickHouse stores and compresses both the dictionary and the posting lists using advanced data structures, which we’ll explore next.</p>\n<h3 id=\"fsts-space-efficient-dictionaries\"></h3>\n<p>To find a token quickly, we need an efficient dictionary structure.</p>\n<p>The most basic approach for this is a sorted list of (token → posting list) pairs. This lets us do a fast binary search to find a token. Assuming that the documents are written in natural language, this opens up another useful optimization opportunity: <strong>prefix sharing</strong>.</p>\n<p>For example, many tokens start with the same prefix:</p>\n<ul>\n<li>\"<span>win</span>d\", \"<span>win</span>ter\"</li>\n<li>\"<span>click</span>\", \"<span>click</span>house\"</li>\n</ul>\n<p>A plain list of tokens doesn’t take advantage of this - but a <strong>Finite State Transducer (FST)</strong> does.</p>\n<h4 id=\"what-is-an-fst\"></h4>\n<p>An FST is a compact automaton—essentially a graph of characters—that encodes the dictionary in a highly compressed manner. It was originally designed to translate strings from one language to another, but it is also a great fit for text indexing. Systems like <a target=\"_blank\" href=\"https://burntsushi.net/transducers/\">Lucene</a> and ClickHouse use FSTs to represent sorted dictionaries.</p>\n<p>Instead of storing each token as a string, an FST:</p>\n<ul>\n<li>\n<p>Represents shared prefixes and suffixes only once</p>\n</li>\n<li>\n<p>Encodes each token as a path through a graph</p>\n</li>\n<li>\n<p>Emits an <em>output</em> (e.g. the address of a posting list) when a path reaches a final “accepting” state.</p>\n</li>\n</ul>\n<p>This makes the dictionary extremely compact, especially when tokens share common parts.</p>\n<h4 id=\"mapping-tokens-to-posting-lists\"></h4>\n<p>The FST doesn’t store the posting lists themselves — just how to find them. For that, we associate each token with a <strong>posting list offset</strong>: the byte position where it begins in a separate file.</p>\n<p>To retrieve the offset for a token, we walk the FST from the start state to an accepting state. Each transition may emit an integer, and we sum them all to get the final offset. This sounds a bit magical, but it’s how the standard FST construction algorithm works (<a target=\"_blank\" href=\"https://link.springer.com/chapter/10.1007/3-540-44674-5_18\">ref</a>).</p>\n<h4 id=\"example\"></h4>\n<p>Suppose we have three tokens:</p>\n<p><code>ClickBench</code>, <code>ClickHouse</code>, <code>JSONBench</code></p>\n<p>We’ll build the FST for the following small dictionary and see how the FST looks visually.</p>\n<p><span><img alt=\"Full-text search 17.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FFull_text_search_17_84233af09d.png&w=2048&q=75\"></span></p>\n<p>The FST encodes the tokens as transitions between characters. Shared prefixes like \"Click\" reuse the same path. At the end of each token, the FST emits its corresponding offset (10, 20, 30):</p>\n<p><span><img alt=\"Full-text search 18.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FFull_text_search_18_4c25ecaaec.png&w=2048&q=75\"></span></p>\n<p>So the FST serves two roles:</p>\n<ul>\n<li>\n<p>It lets us <strong>quickly check</strong> whether a token exists.</p>\n</li>\n<li>\n<p>It lets us <strong>compute the byte offset</strong> for that token’s posting list.</p>\n</li>\n</ul>\n<p>Together, this allows ClickHouse to store large token dictionaries in a compact and searchable manner.</p>\n<h3 id=\"roaring-bitmaps-fast-set-operations\"></h3>\n<p>Each <strong>posting list</strong> stores the row numbers of documents that contain a given token.</p>\n<p>We want to store these row numbers in a way that’s:</p>\n<ul>\n<li>\n<p><strong>Compact</strong> – to save space.</p>\n</li>\n<li>\n<p><strong>Efficient</strong> – so we can quickly compute intersections and unions between posting lists.</p>\n</li>\n</ul>\n<p>Posting list intersections and unions matter when queries involve <strong>multiple tokens</strong> and combine them with logical operators, e.g.:</p>\n<div><pre><code><span><span>LIKE</span> <span>'% cat %'</span> <span>AND</span> <span>LIKE</span> <span>'% dog %'</span></span></code></pre></div>\n<!-- -->\n<h4 id=\"why-compression-matters\"></h4>\n<p>The traditional approach for compressing posting lists is to combine:</p>\n<ul>\n<li>\n<p><strong>Delta encoding</strong> – to calculate the differences between neighboring values.</p>\n</li>\n<li>\n<p><strong>Golomb-Rice encoding</strong> – to compress the deltas efficiently.</p>\n</li>\n</ul>\n<p>This scheme offers excellent compression for typical natural language documents (a few frequent tokens and many rare ones). However, it processes data <strong>bit by bit</strong>, which isn’t ideal for modern CPUs that benefit from pipelining and SIMD instructions.</p>\n<h4 id=\"enter-roaring-bitmaps\"></h4>\n<p>To keep things fast, ClickHouse uses<a target=\"_blank\" href=\"https://roaringbitmap.org/\"> Roaring bitmaps</a>, a modern, high-performance format for storing large sets of integers.</p>\n<p>The idea is simple:</p>\n<ul>\n<li>\n<p>Think of a posting list as a <strong>bitmap</strong>, e.g., <code>[3, 5, 8]</code> → <code>000101001</code></p>\n</li>\n<li>\n<p>Divide the bitmap into <strong>chunks</strong> of 65,536 values (2¹⁶).</p>\n</li>\n<li>\n<p>Store each chunk in a specialized <strong>container</strong>, based on its content:</p>\n<ul>\n<li>\n<p><strong>Array</strong> – for sparse data (few values)</p>\n</li>\n<li>\n<p><strong>Bitmap</strong> – for dense data</p>\n</li>\n<li>\n<p><strong>Run-length encoding</strong> – for long consecutive sequences</p>\n</li>\n</ul>\n</li>\n</ul>\n<p>This design keeps storage compact and enables extremely fast set operations — including all combinations of AND, OR, and NOT between posting lists. Roaring bitmaps also use specialized SIMD-accelerated code paths for maximum speed.</p>\n<h4 id=\"visual-breakdown\"></h4>\n<p>Roaring bitmaps split each 32-bit row number into two 16-bit parts:</p>\n<ul>\n<li>\n<p>The <strong>upper 16 bits</strong> select the container.</p>\n</li>\n<li>\n<p>The <strong>lower 16 bits</strong> are stored inside the container.</p>\n</li>\n</ul>\n<p>For example:</p>\n<ul>\n<li>\n<p>Row number:     <code>124586</code></p>\n</li>\n<li>\n<p>Binary:         <code>00000000 00000001 11100110 11101010</code></p>\n</li>\n<li>\n<p>Upper 16 bits:  <code>00000000 00000001</code> → selects container</p>\n</li>\n<li>\n<p>Lower 16 bits:  <code>11100110 11101010</code> → value stored in container</p>\n</li>\n</ul>\n<p><span><img alt=\"Full-text search 19.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FFull_text_search_19_01a4f43a5a.png&w=2048&q=75\"></span></p>\n<p>Each container holds values for a specific range and is stored using the most space-efficient format. This makes it possible to scan, merge, and filter billions of row numbers with blazing speed.</p>\n<p>We now have the two core building blocks of ClickHouse’s text index:</p>\n<ul>\n<li>\n<p>FSTs for compact, prefix-sharing token dictionaries</p>\n</li>\n<li>\n<p>Roaring bitmaps for fast, compressed posting lists</p>\n</li>\n</ul>\n<p>We’ve now covered the two core structures — the dictionary and the posting lists — and how they’re stored efficiently. Let’s put these pieces together and see how the index is organized on disk.</p>\n<h2 id=\"storage-layout-segments-granules-and-files\"></h2>\n<p>Let’s put all the pieces together.</p>\n<p>An inverted index consists of five files on disk:</p>\n<ol>\n<li>\n<p>An <strong>ID</strong> file — stores the segment ID and version. (see below what \"segment\" means)</p>\n</li>\n<li>\n<p>A <strong>metadata</strong> file — tracks all the segments.</p>\n</li>\n<li>\n<p>A <strong>bloom filter</strong> file — stores bloom filters to avoid loading dictionary and posting list files.</p>\n</li>\n<li>\n<p>A <strong>dictionary</strong> file — stores all segment dictionaries as FSTs.</p>\n</li>\n<li>\n<p>A <strong>posting list</strong> file — stores all posting lists as compressed sequences of integers.</p>\n</li>\n</ol>\n<p><em>See the next diagram for an overview of how these pieces are laid out on disk.</em></p>\n<h4 id=\"how-the-data-is-organized\"></h4>\n<p>The index is built per <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">part</a> and recreated during <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges\">merges</a>. Internally, it’s split into <strong>segments</strong>, each of which contains:</p>\n<ul>\n<li>\n<p>A dictionary (as an FST)</p>\n</li>\n<li>\n<p>Posting lists (as roaring bitmaps), one per token</p>\n</li>\n</ul>\n<p>The metadata file keeps track of:</p>\n<ul>\n<li>\n<p>The segment ID</p>\n</li>\n<li>\n<p>The starting row ID</p>\n</li>\n<li>\n<p>Offsets into the Bloom filter file, dictionary file, and posting list file</p>\n</li>\n</ul>\n<p><span><img alt=\"Full-text search 20.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FFull_text_search_20_25cba11855.png&w=2048&q=75\"></span></p>\n<p>In the diagram above, arrows marked <strong>①</strong>, <strong>②</strong>, and <strong>③</strong> represent the order in which files are loaded during lookups.</p>\n<p>We shape the file sizes to match their content:</p>\n<ul>\n<li>\n<p><strong>Bloom filters</strong> are the smallest,</p>\n</li>\n<li>\n<p><strong>Dictionaries</strong> are mid-sized,</p>\n</li>\n<li>\n<p><strong>Posting lists</strong> are the largest.</p>\n</li>\n</ul>\n<h4 id=\"what-s-a-segment-and-what-s-an-index-granule\"></h4>\n<p>To understand segments, we need to introduce <strong>index <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes#data-is-organized-into-granules-for-parallel-data-processing\">granules</a></strong>.</p>\n<ul>\n<li>\n<p>An <strong>index granule</strong> is the unit of indexing in ClickHouse (typically 8192 rows).</p>\n</li>\n<li>\n<p>A <strong>segment</strong> is a substructure within the granule, created to make indexing more memory-efficient.</p>\n</li>\n</ul>\n<p>Segments are split by dictionary size, not by row count. This makes sure that each segment holds FST dictionaries of roughly the same size. This approach avoids out-of-memory errors during index creation on large datasets.</p>\n<p>Each segment is self-contained and holds:</p>\n<ul>\n<li>\n<p>A row ID range</p>\n</li>\n<li>\n<p>An FST dictionary</p>\n</li>\n<li>\n<p>A set of posting lists</p>\n</li>\n</ul>\n<p>Smaller segments reduce memory pressure, but may lead to higher storage usage due to redundant storage of tokens in multiple segment FST dictionaries. Segmenting is off by default but can be enabled for advanced workloads.</p>\n<h4 id=\"what-happens-during-an-index-lookup\"></h4>\n<p>Here’s how ClickHouse finds rows for a search token:</p>\n<ol>\n<li><strong>Traverse all dictionaries</strong>:</li>\n</ol>\n<p>The token is searched in every segment’s FST. When the FST reaches its accepting state, we know the token exists in that segment.</p>\n<ol>\n<li><strong>Sum up FST output values</strong>:</li>\n</ol>\n<p>These values give us the offset into the posting list file.</p>\n<ol>\n<li>\n<p><strong>Load the posting list</strong>:</p>\n<ul>\n<li>\n<p>If it’s a cold run, the posting list is read from disk.</p>\n</li>\n<li>\n<p>If it’s a hot run, it’s already cached in memory.</p>\n</li>\n</ul>\n<p><em>Note: The row IDs stored in posting lists are <strong>relative</strong> to the segment’s starting row. They’re extrapolated to full granule row numbers during lookup. (More on that in direct index usage optimization below.)</em></p>\n</li>\n</ol>\n<p>With the fundamentals in place, let’s look at the major improvements we’ve made to the text index in this release, covering everything from API design to memory footprint and smarter granularity.</p>\n<h2 id=\"recent-improvements\"></h2>\n<p>Over the past three months, we’ve made significant improvements to full-text search in ClickHouse, from user-facing changes to deep storage optimizations. Elapsed: <span>0.003</span> sec.</span></code></pre></div>\n<!-- -->\n<p><strong>Key takeaway:</strong></p>\n<p>Use the split tokenizer when you need <strong>exact, separator-based tokenization</strong> and want to preserve multi-line or unusual token boundaries.</p>\n<h3 id=\"3-smaller-index-footprint\"></h3>\n<p>We made major improvements to reduce the memory and disk footprint of text indexes:</p>\n<ul>\n<li>\n<p><strong>PFOR compression for posting lists</strong> Fast intersection and union operations on posting lists are only performed on posting lists in memory. For posting lists stored on disk, we can sacrifice this requirement in favor of higher compression ratios. We therefore now use PFOR (Patched Frame of Reference) on top of Delta encoding. This change alone reduced their storage footprint by up to 30%.</p>\n</li>\n<li>\n<p><strong>Zstd compression for FSTs</strong> FSTs are now Zstd-compressed when written to disk, lowering their average size by an additional <strong>10%</strong>.</p>\n</li>\n</ul>\n<h3 id=\"4-cloud-compatibility\"></h3>\n<p>The text index is now fully compatible with ClickHouse Cloud, including support for the packed part format used in cloud storage.</p>\n<h3 id=\"5-smarter-granularity\"></h3>\n<p>We increased the <strong>default index granularity</strong> from <strong>1</strong> to <strong>64</strong>.</p>\n<p>The index granularity determines how many rows are covered by each index granule:</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/skipping-indexes\">Granularity docs →</a></p>\n<ul>\n<li>\n<p><strong>Smaller granularity</strong>: More precise filtering, but higher memory usage and I/O due to redundant storage of tokens in multiple FSTs.</p>\n</li>\n<li>\n<p><strong>Larger granularity</strong>: Less overhead, better performance for most terms, but slightly less precision for very rare or clustered tokens.</p>\n</li>\n</ul>\n<p>Through extensive experiments, a setting of 64 delivered strong performance across both typical and edge-case workloads, making it the new default.</p>\n<p>Beyond these core improvements, we’ve also added new capabilities to make lookups faster and lighter, starting with bloom filters as a pre-filtering layer.</p>\n<h3 id=\"6-bloom-filters-as-pre-filters\"></h3>\n<p>Bloom filters are lightweight, probabilistic data structures that support efficient “one-way” set membership tests. They can quickly tell you:</p>\n<ul>\n<li>\n<p><strong>Definitely not in the set</strong>, or</p>\n</li>\n<li>\n<p><strong>Possibly in the set</strong> (with a tunable false-positive rate)</p>\n</li>\n</ul>\n<p>Because they never return false negatives, bloom filters are useful for cheaply ruling things out before doing more expensive work.</p>\n<p>In ClickHouse, we added bloom filters as <strong>pre-filters</strong> for the text index. This means we can check whether a token is <em>definitely not</em> in the dictionary <strong>before</strong> scanning the FST. That helps reduce disk I/O and CPU overhead. Since bloom filters are small, they can stay in memory at all times.</p>\n<h4 id=\"text-index-vs-bloom-filter-index-what-s-the-difference\"></h4>\n<p>There are two ways to use bloom filters in full-text search:</p>\n<ol>\n<li>\n<p>A <strong>bloom filter text index</strong>, where tokens are inserted directly into the bloom filter</p>\n</li>\n<li>\n<p>A <strong>bloom filter on top of a text index segment</strong>, initialized from the segment dictionary</p>\n</li>\n</ol>\n<p>We mentioned the disadvantages of bloom-filter based indexes above - the most important downside is that these indexes require manual tuning.</p>\n<p>The second way is fully automatic based on the indexed data and a configurable false positive rate (default: 0.1%) - no manual tuning is needed, meaning it easy to use and suitable for most scenarios.</p>\n<blockquote>\n<p>In general, <strong>we recommend using text indexes over bloom filters</strong> unless you have specific accuracy needs.</p>\n</blockquote>\n<p>While bloom filters speed up the decision of whether to check a dictionary, we’ve also improved how you query the index with new search functions.</p>\n<h3 id=\"7-new-search-functions-searchany-and-searchall\"></h3>\n<p><strong>Modern problems require modern solutions.</strong></p>\n<p>As ClickHouse added additional tokenizers and tokenizer-specific parameters, it turned out that the existing “hasToken” function is limited: it always uses the <strong>default tokenizer</strong> to tokenize the search term, not the tokenizer used to build the index. That can be unintuitive, and we’ve fixed it.</p>\n<p>We’ve introduced two new functions for full-text search: searchAny and searchAll.</p>\n<h4 id=\"a-simple-example\"></h4>\n<p>Let’s say we create a table like this:</p>\n<div><pre><code><span><span>SET</span> allow_experimental_full_text_index <span>=</span> <span>1</span>;</span>\n<span></span>\n<span><span>CREATE TABLE</span> tab (</span>\n<span>  id Int64,</span>\n<span>  str String,</span>\n<span>  INDEX idx_str(str) TYPE text(tokenizer <span>=</span> <span>'ngram'</span>, ngram_size <span>=</span> <span>5</span>)</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree()</span>\n<span><span>ORDER</span> <span>BY</span> id;</span>\n<span></span>\n<span><span>INSERT INTO</span> tab (id, str) <span>VALUES</span></span>\n<span>  (<span>1</span>, <span>'Click House'</span>),</span>\n<span>  (<span>2</span>, <span>'ClickHouse'</span>);</span></code></pre></div>\n<!-- -->\n<p>Now, using the old hasToken function:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> tab <span>WHERE</span> hasToken(str, <span>'Click'</span>);</span>\n<span>┌─id─┬─str─────────┐</span>\n<span>│  <span>1</span> │ Click House │</span>\n<span>└────┴─────────────┘</span></code></pre></div>\n<!-- -->\n<p>Why?</p>\n<p>hasToken requires a non-alphanumeric separator before and after the token. Since “ClickHouse” has no separator, it’s not matched.</p>\n<p>Try <code>searchAny</code> instead:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> tab <span>WHERE</span> searchAny(str, [<span>'Click'</span>]);</span></code></pre></div>\n<!-- -->\n<p>Returns both rows:</p>\n<div><pre><code><span>┌─id─┬─str─────────┐</span>\n<span>│  <span>1</span> │ Click House │</span>\n<span>│  <span>2</span> │ ClickHouse  │</span>\n<span>└────┴─────────────┘</span></code></pre></div>\n<!-- -->\n<p><code>searchAll</code> would do the same in this case.</p>\n<h4 id=\"why-are-these-better\"></h4>\n<p><strong>No separator requirement</strong></p>\n<p>The new functions don’t require special characters around tokens. They use the tokenizer from the index itself.</p>\n<p><strong>Support for multiple tokens</strong></p>\n<p>Instead of writing:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> tab <span>WHERE</span> hasToken(str, <span>'Click'</span>) <span>AND</span> hasToken(str, <span>'House'</span>);</span>\n<span></span>\n<span><span>SELECT</span> <span>*</span> <span>FROM</span> tab <span>WHERE</span> hasToken(str, <span>'Click'</span>) <span>OR</span> hasToken(str, <span>'House'</span>);</span></code></pre></div>\n<!-- -->\n<p>You can now write:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> tab <span>WHERE</span> searchAll(str, [<span>'Click'</span>, <span>'House'</span>]);</span>\n<span></span>\n<span><span>SELECT</span> <span>*</span> <span>FROM</span> tab <span>WHERE</span> searchAny(str, [<span>'Click'</span>, <span>'House'</span>]);</span></code></pre></div>\n<!-- -->\n<p><strong>Cleaner syntax and fewer surprises</strong></p>\n<p>These functions always use the tokenizer and settings defined in the index.</p>\n<blockquote>\n<p><code>searchAny</code> and <code>searchAll</code> only work with columns that have a full-text index. See<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/string-search-functions#searchany\"> searchAny docs</a> and<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/string-search-functions#searchall\"> searchAll docs</a> for more.</p>\n</blockquote>\n<p>These new functions make searching more flexible and intuitive, but the biggest performance leap comes from a new optimization that skips reading the text column entirely.</p>\n<h2 id=\"fast-row-level-search-without-text-column-reads\"></h2>\n<p>ClickHouse's inverted index is at its core a skip index. As such, it is used at the beginning of a search to filter out non-matching granules. The \"surviving\" potentially matching granules are then loaded in a second step from disk and filtered row-by-row. In the case of the inverted index, this works well if the user searches a rare term. However, frequent terms cause many, potentially all, granules to survive and effectively a full scan in the second step.</p>\n<h3 id=\"what-s-new\"></h3>\n<p>We’ve now eliminated that bottleneck.</p>\n<p>The inverted index can now <strong>filter directly using the index, down to the row level</strong>.</p>\n<p>This means we no longer need to read the text column at all.</p>\n<p>It builds on the existing granule-level filtering logic and introduces a <strong>new match engine</strong> that’s completely transparent to users.</p>\n<h3 id=\"example\"></h3>\n<p>Consider the query:</p>\n<div><pre><code><span><span>SELECT</span> col1, col2 <span>FROM</span> <span>table</span> <span>WHERE</span> searchAny(col3, [<span>'hello'</span>])</span></code></pre></div>\n<!-- row.</p>\n</li>\n<li>\n<p>Even with index filtering at the granule level, this still involved reading and scanning many rows.</p>\n</li>\n<li>\n<p>That’s slow, especially since text columns are large,
