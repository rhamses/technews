contentHtml: "<article><div><p><span><img alt=\"header.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fheader_051b18afd6.png&w=2048&q=75\"></span></p>\n<p>This blog post is part of a series:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part1\">Join Types supported in ClickHouse</a></li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2\">ClickHouse Joins Under the Hood - Hash Join,&#160;Parallel Hash Join,&#160;Grace Hash Join</a></li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3\">ClickHouse Joins Under the Hood - Full Sorting Merge Join, Partial Merge Join</a></li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-direct-join-part4\">ClickHouse Joins Under the Hood - Direct Join</a></li>\n</ul>\n<p>In the previous three posts, we did a deep dive on the 6 different join algorithms that have been developed for ClickHouse. In this final post, we will summarize and directly compare the execution times and memory usage of all ClickHouse join algorithms. Based on this, we will provide decision trees as well as  a join type support overview that you can use for deciding which join algorithm fits best into your specific scenario.</p>\n<h2 id=\"overview-of-clickhouse-join-algorithms\"></h2>\n<p>The following 6 join algorithms have been developed for ClickHouse so far:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-direct-join-part4#direct-join\">Direct join</a></li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2#hash-join\">Hash join</a></li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2#parallel-hash-join\">Parallel hash join</a></li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#grace-hash-join\">Grace hash join</a></li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part3#full-sorting-merge-join\">Full sorting merge join</a></li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part3#partial-merge-join\">Partial merge join</a></li>\n</ul>\n<p>These algorithms dictate the manner in which a join query is planned and executed. By <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-join_algorithm\">default</a>, ClickHouse is using the direct or the hash join algorithm, based on used <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part1#join-types-supported-in-clickhouse\">join type</a> and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part1#join-types-supported-in-clickhouse\">strictness</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines\">engine</a> of the joined tables. Alternatively, ClickHouse can be configured to <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/about-us/distinctive-features#adaptive-join-algorithm\">adaptively</a> choose and dynamically change the join algorithm to use at runtime, depending on resource availability and usage: When <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-join_algorithm\">join_algorithm</a> is set to <code>auto</code>, ClickHouse tries the hash join algorithm first, and if that algorithm’s <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/query-complexity#settings-max_bytes_in_join\">memory limit</a> is violated, the algorithm is switched on the fly to partial merge join. You can observe which algorithm was chosen via <a target=\"_blank\" href=\"https://clickhouse.com/docs/knowledgebase/send_logs_level\">trace logging</a>. ClickHouse also allows users to <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-join_algorithm\">specify</a> the desired join algorithm themselves. This chart gives an overview of the ClickHouse join algorithms based on their relative memory consumption and execution time:\n<span><img alt=\"algorithms.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Falgorithms_caf4c65123.png&w=2048&q=75\"></span></p>\n<p>The <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-direct-join-part4#direct-join\">Direct join</a> is ClickHouse’s fastest join algorithm and is applicable when the underlying <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines\">storage</a> for the right-hand side table supports low-latency <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Key%E2%80%93value_database\">key-value</a> requests, and when <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part1#left--right--inner-any-join\">LEFT ANY JOIN</a> semantics is adequate. Especially with large right-hand side tables, the direct join <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-how-to-choose-the-right-algorithm-part5#comparisons\">beats</a> all other ClickHouse join algorithms with a significant improvement in execution time.</p>\n<p>Three of the ClickHouse join algorithms are based on in-memory <a target=\"_blank\" href=\"https://clickhouse.com/blog/hash-tables-in-clickhouse-and-zero-cost-abstractions\">hash tables</a>:</p>\n<ul>\n<li>The <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2#hash-join\">Hash join</a> is fast but memory-bound, and the most generic join algorithm supporting all <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part1#join-types-supported-in-clickhouse\">join types</a> and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part1#join-types-supported-in-clickhouse\">strictness settings</a>. The algorithm can be constrained by high memory usage. Plus, the creation of the in-memory hash table from the right-hand side table of the join <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#query-pipeline-1\">is</a> single-threaded and can become a bottleneck in terms of join execution time if the right-hand side table is very large.</li>\n<li>The <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2#parallel-hash-join\">Parallel hash join</a> can be faster with large right-hand side tables, by <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#description-1\">building</a> several hash tables concurrently, but it requires even more memory.</li>\n<li>The <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#grace-hash-join\">Grace hash join</a> is a non-memory bound version that spills data temporarily to disk without requiring any sorting of the data. This overcomes some of the performance challenges of other non-memory bound ClickHouse join algorithms, that spill data temporarily to disk but require prior sorting of the data.</li>\n</ul>\n<p>ClickHouse offers two additional non-memory bound join algorithms based on <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/External_sorting\">external sorting</a>:</p>\n<ul>\n<li>The <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part3#full-sorting-merge-join\">Full sorting merge join</a> is based on in-memory or external sorting and can take advantage of the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">physical row order</a> of the joined tables and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3#utilizing-physical-row-order\">skip</a> the sorting phase. In such cases, the join performance can be competitive with some of the hash join algorithms from the chart above while generally requiring significantly less main memory.</li>\n<li>The <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part3#partial-merge-join\">Partial merge join</a> is optimized for minimizing memory usage when large tables are joined and always fully sorts the right table first via external sorting. The left table is also always sorted, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#setting-max_block_size\">block-wise</a> in-memory. The join matching process runs more efficiently if the physical row order of the left table matches the join key sorting order.</li>\n</ul>\n<h2 id=\"choosing-the-right-join-algorithm\"></h2>\n<p>The join algorithm choice mainly depends on three factors:</p>\n<ul>\n<li>Performance</li>\n<li>Memory</li>\n<li>Join type support</li>\n</ul>\n<p>The following three sections provide guidance for these factors.</p>\n<h3 id=\"performance\"></h3>\n<p>Next to the overview chart from above, you can use this decision tree for choosing the right join algorithm when the main criteria is executing joins as fast as possible:\n<span><img alt=\"choosing_join_1.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fchoosing_join_1_49e51159c2.png&w=2048&q=75\"></span></p>\n<p>① If the data from the right-hand side table can be pre-loaded into an in-memory low-latency key-value data structure, e.g., a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries\">dictionary</a>, and if the join key matches the key attribute of the underlying key-value storage, and if <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part1#left--right--inner-any-join\">LEFT ANY JOIN</a> semantics is adequate - then the <strong>direct join</strong> is applicable and offers the fastest approach.</p>\n<p>② If your table’s <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">physical row order</a> matches the join key sort order, then it depends. In this case, the <strong>full sorting merge join</strong> <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3#utilizing-physical-row-order\">skips</a> the sorting phase resulting in significantly reduced memory usage plus, depending on data size and join key value distribution, <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-how-to-choose-the-right-algorithm-part5#imdb-x-large-join-runs\">faster</a> execution times than some of the hash join algorithms. However, if ③ the right table fits into memory, even with the additional memory usage <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#summary\">overhead</a> of the <strong>parallel hash join</strong>, then this algorithm or the <strong>hash join</strong> can be faster. This depends on data size, data types, and value distribution of the join key columns.</p>\n<p>④ If the right table doesn’t fit into memory, then it depends again. ClickHouse offers three non-memory bound join algorithms. All three temporarily spill data to disk. <strong>Full sorting merge join</strong> and <strong>partial merge join</strong> require prior sorting of the data. <strong>Grace hash join</strong> is building hash tables from the data instead. Based on the volume of data, the data types and the value distribution of the join key columns, there can be scenarios where building hash tables from the data is faster than sorting the data. And vice versa.</p>\n<p>Partial merge join is optimized for minimizing memory usage when large tables are joined, at the expense of join speed which is quite slow. This is especially the case when the physical row order of the left table doesn’t match the join key sorting order.</p>\n<p>Grace hash join is the most flexible of the three non-memory-bound join algorithms and offers good control of memory usage vs. join speed with its <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/23.5/src/Core/Settings.h#L759\">grace_hash_join_initial_buckets</a> setting. Depending on the data volume the grace hash can be <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-how-to-choose-the-right-algorithm-part5#imdb-large-join-runs\">faster</a> or <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-how-to-choose-the-right-algorithm-part5#imdb-x-large-join-runs\">slower</a> than the partial merge algorithm, when the amount of <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#description-2\">buckets</a> is chosen such that the memory usage of both algorithms is approximately aligned. When the memory usage of grace hash join is configured to be approximately aligned with the memory usage of <code>full sorting merge</code>, then full sorting merge was always faster in our <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-how-to-choose-the-right-algorithm-part5#comparisons\">test runs</a>.</p>\n<p>Which one of the three non-memory-bound algorithms is the fastest depends on the volume of data, the data types and the value distribution of the join key columns. It is always best to run some benchmarks with realistic data volumes of realistic data in order to determine which algorithm is the fastest.</p>\n<h3 id=\"memory\"></h3>\n<p>If you want to optimize a join for the lowest memory usage instead of the fastest execution time, then you can use this decision tree instead:\n<span><img alt=\"choosing_join_2.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fchoosing_join_2_727dfc9731.png&w=2048&q=75\"></span></p>\n<p>① If your table’s physical row order matches the join key sort order, then the memory usage of the <strong>full sorting merge join</strong> <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-how-to-choose-the-right-algorithm-part5#comparisons\">is</a> as low as it gets. With the additional benefit of good join speed because the sorting phase is <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3#utilizing-physical-row-order\">disabled</a>.</p>\n<p>② The <strong>grace hash join</strong> can be tuned for very low memory usage by <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/23.5/src/Core/Settings.h#L759\">configuring</a> a high number of <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#description-2\">buckets</a> at the expense of join speed. The <strong>partial merge join</strong> intentionally uses a low amount of main memory. The <strong>full sorting merge join</strong> with external sorting enabled generally uses <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-how-to-choose-the-right-algorithm-part5#comparisons\">more</a> memory than the partial merge join (assuming the row order does not match the key sort order), with the benefit of significantly <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-how-to-choose-the-right-algorithm-part5#comparisons\">better</a> join execution time.</p>\n<h3 id=\"join-type-support\"></h3>\n<p>Not only execution speed and memory consumption are factors in choosing the right join algorithm. It also depends on if your required <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part1#join-types-supported-in-clickhouse\">join type</a> is supported by the join algorithm. For that, we created this overview chart:\n<span><img alt=\"choosing_join_3.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fchoosing_join_3_06784eadcc.png&w=2048&q=75\"></span></p>\n<h2 id=\"comparisons\"></h2>\n<p>We are now going to compare the execution times and peak memory consumptions of all ClickHouse join algorithms.</p>\n<h3 id=\"test-setup\"></h3>\n<p>We will use the tables that we <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#test-data-and-resources\">introduced</a> in the second post.</p>\n<p>For all join query runs we use the default setting of max_threads. following section, we will present charts comparing runs of the example query with each join algorithm over the tables of both databases.</p>\n<h3 id=\"direct-join-is-a-bit-special\"></h3>\n<p>Note that we are using separate charts for the direct join algorithm because it only makes sense to compare this algorithm with similar, memory-bound non-sorting algorithms like hash and parallel hash. As mentioned in the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-direct-join-part4\">previous post</a>, a direct join with a dictionary-backed right-hand side table is also effectively a LEFT ANY JOIN:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> actors <span>AS</span> a</span>\n<span><span>LEFT</span> <span>ANY</span> <span>JOIN</span> roles <span>AS</span> r <span>ON</span> a.id <span>=</span> r.actor_id</span>\n<span>FORMAT `<span>Null</span>`</span>\n<span>SETTINGS join_algorithm <span>=</span> ...;</span></code></pre></div>\n<h3 id=\"imdb-large-join-runs\"></h3>\n<p>The following chart summarizes the peak memory usage and execution time of the same <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-how-to-choose-the-right-algorithm-part5#join-query\">example join query</a> using the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-how-to-choose-the-right-algorithm-part5#imdb-large-tables\">imdb_large</a> tables with:</p>\n<ul>\n<li>the larger table on the right-hand side of the join</li>\n<li>different join algorithm settings</li>\n<li>a node with <code>30 CPU cores</code> and the default setting of 30 for <code>max_threads</code></li>\n</ul>\n<p>Note that the 10 query runs are ordered by execution time, starting with the fastest query run on the left-hand side of the chart:\n<span><img alt=\"imdb_large.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fimdb_large_5b5d3f45ee.png&w=2048&q=75\"></span></p>\n<p>For our sample tables, the fastest join algorithms (see ① and ②) use the highest amount of memory. With the significant exception of the ③ <code>full sorting merge</code>. When the sorting phase can be <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3#utilizing-physical-row-order\">skipped</a> because the table's physical row order on disk is matching the join key sort order, then the full sorting merge’s execution time becomes competitive (or better - see the next chart below) with the hash join algorithms while requiring significantly less memory. In this case, because the data from both tables <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3#description\">is</a> streamed through the query engine <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#setting-max_block_size\">block-wise</a> and in order, just a few data blocks are in memory at the same time for merging.</p>\n<p>With ④ in-memory sorting of both joined tables, the full sorting merge join has higher memory consumption. With ⑤ external sorting (sorted data is spilled to disk instead of in-memory sorting), the memory consumption is reduced at the expense of execution speed.</p>\n<p><code>Grace hash</code> is one of the three non-memory bound join algorithms that temporarily spill data to disk to reduce memory consumption. In contrast to the other two algorithms - <code>full sorting merge</code> and <code>partial merge</code> - grace hash allows one to control its memory usage based on the configured amount of <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#description-2\">buckets</a>.  We were interested in comparing the join speed of grace hash when it uses approximately the same and less memory amount as the other two non-memory bound algorithms. For this we run grace hash with three different <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/23.5/src/Core/Settings.h#L759\">bucket amounts</a>. In run ⑥ with 4 buckets, we aligned the grace hash memory usage with the <code>full sorting merge</code> run ⑤. In this case, the grace hash was slower than the full sorting merge for joining our two example tables. In run ⑦ with 8 buckets we aligned the memory usage approximately with the <code>partial merge</code> run in ⑨. Here the grace hash run is two times faster. An additional run ⑧ with 32 buckets reduced the memory usage below the partial merge runs while still running faster.</p>\n<p>For joining our example tables, the <code>partial merge</code> runs (see ⑨ and ⑩) are the slowest. <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3#partial-merge-join\">Remember</a> that the partial merge join fully sorts the right table and stores their sorted blocks, together with min-max index files temporarily to disk first. It then sorts and compares each block from the left table with the sorted blocks from the right table on disk while utilizing the min-max indexes for skipping non-matching blocks. For our example tables this is memory efficient but slow. Especially in run ⑩ when the physical row order of the left table <a target=\"_blank\" href=\"https://pastebin.com/G6XDueBR\">doesn’t</a> match the join key sorting order.</p>\n<p>Generally, we can see that explicitly sorting the tables prior to identifying join matches is more expensive regarding execution time than just building hash tables from one of the tables.</p>\n<p>However, keep in mind that we only benchmarked joins over one particular imdb dataset. Based on the volume of data, the data types and the value distribution of the join key columns, there can be scenarios where the sorting of data blocks is faster than building hash tables.
