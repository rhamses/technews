As a reminder: These algorithms dictate the manner in which a join query is planned and executed. ClickHouse can be configured to <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/about-us/distinctive-features#adaptive-join-algorithm\">adaptively</a> choose and dynamically change the join algorithm to use at runtime, depending on resource availability and usage. However, ClickHouse also allows users to <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-join_algorithm\">specify</a> the desired join algorithm themselves. This chart gives an overview of these algorithms based on their relative memory consumption and execution time:\n<span><img alt=\"algorithms.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Falgorithms_199193002c.png&w=2048&q=75\"></span></p>\n<p>In our <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2\">second post</a>, we described and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2#summary\">compared</a> in detail the three ClickHouse join algorithms from the chart above that are based on in-memory <a target=\"_blank\" href=\"https://clickhouse.com/blog/hash-tables-in-clickhouse-and-zero-cost-abstractions\">hash tables</a>:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2#hash-join\">Hash join</a></li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2#parallel-hash-join\">Parallel hash join</a></li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2\">Grace hash join</a></li>\n</ul>\n<p>As a reminder: <strong>Hash join</strong> and <strong>parallel hash join</strong> are fast but memory-bound. The joined data from the right-hand side table needs to fit into memory. <strong>Grace hash join</strong> is a non-memory bound version that spills data temporarily to disk, without requiring any sorting of the data. This overcomes some of the performance challenges of other join algorithms that spill data to disk and require prior sorting of the data.</p>\n<p>In the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part3\">third post</a> we explored and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part3#summary\">compared</a> the two algorithms from the chart above that are based on <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/External_sorting\">external sorting</a>:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part3#full-sorting-merge-join\">Full sorting merge join</a></li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part3#partial-merge-join\">Partial merge join</a></li>\n</ul>\n<p>As a reminder: The <strong>Full sorting merge join</strong> is non-memory bound and based on in-memory or external sorting, and can take advantage of the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">physical row order</a> of the joined tables and skip the sorting phase. In such cases, the join performance can be competitive with some of the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2\">hash join algorithms</a> from the chart above, while generally requiring significantly less main memory. The <strong>partial merge join</strong> is optimized for minimizing memory usage when large tables are joined, and always fully sorts the right table first via external sorting. The left table is also always sorted, block-wise in-memory. The join matching process runs more efficiently if the physical row order of the left table matches the join key sorting order.</p>\n<p>We kept the best for the end and will finish our exploration of the ClickHouse join algorithms in this post by describing ClickHouse’s fastest join algorithm from the chart above:</p>\n<ul>\n<li>Direct join</li>\n</ul>\n<p>The direct join algorithm can be applied when the underlying <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines\">storage</a> for the right-hand side table supports low latency <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Key%E2%80%93value_database\">key-value</a> requests. Especially with large right tables, direct join beats all other ClickHouse join algorithms with a significant improvement in execution time.</p>\n<h2 id=\"test-setup\"></h2>\n<p>We are using the same two tables and the same <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> service instance that we introduced in the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2\">second post</a>.</p>\n<p>For all example query runs we use the default setting of <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-max_threads\">max_threads</a>. The node executing the queries has 30 CPU cores and therefore a default <code>max_threads</code> setting of 30. For all <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#query-pipeline\">query pipeline</a> visualizations, in order to keep them succinct and readable, we artificially limit the level of parallelism used within the ClickHouse query pipeline with the setting <code>max_threads = 2</code>.</p>\n<h2 id=\"direct-join\"></h2>\n<h3 id=\"description\"></h3>\n<p>The direct join algorithm can be applied when the underlying storage for the right-hand side table supports low latency key-value requests. ClickHouse has three <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines\">table engines</a> providing this: <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/join\">Join</a> (that is basically a pre-calculated <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2#hash-join\">hash table</a>), <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/integrations/embedded-rocksdb\">EmbeddedRocksDB</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/dictionary\">Dictionary</a>. We will describe the direct join algorithm here based on dictionaries, but the mechanics are the same for all three engines.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries\">Dictionaries</a> are a <a target=\"_blank\" href=\"https://clickhouse.com/blog/faster-queries-dictionaries-clickhouse\">key feature</a> of ClickHouse providing in-memory <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Key%E2%80%93value_database\">key-value</a> representation of data from various internal and external <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries#dictionary-sources\">sources</a>, optimized for super-low latency lookup queries.</p>\n<p>This is handy in various scenarios e.g., for enriching ingested data on the fly without slowing down the ingestion process, as well as for improving the performance of queries in general with JOINs particularly benefiting.</p>\n<p>We sketch the direct join algorithm's <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#query-pipeline\">query pipeline</a> below:\n<span><img alt=\"direct_1.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fdirect_1_185d6c76d1.png&w=2048&q=75\"></span>\nThe direct join algorithm requires that the right table is backed by a dictionary, such that the to-be-joined data from that table is already present in memory in the form of a low-latency key-value data structure. Then ① all data from the left table is streamed in parallel by 2 streams (because <code>max_threads = 2</code>) into the query engine and the rows are ② joined in parallel by two join stages by doing lookups into the underlying dictionary of the right table.</p>\n<h3 id=\"supported-join-types\"></h3>\n<p>Only LEFT ANY join <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/join#supported-types-of-join\">type</a> is supported. Note that the join key needs to match the key attribute of the underlying key-value storage.</p>\n<h3 id=\"examples\"></h3>\n<p>In order to demonstrate the direct join, we need to create a dictionary first. For this, we need to <a target=\"_blank\" href=\"https://clickhouse.com/blog/faster-queries-dictionaries-clickhouse#choosing-a-layout\">choose</a> a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries#ways-to-store-dictionaries-in-memory\">layout</a> that determines the way how the dictionary content is stored in memory. We will use the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries#flat\">flat</a> option, and for comparison, also the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries#hashed\">hashed</a> layout. Both layouts require the key attribute’s data type to be compatible with the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/data-types/int-uint\">UInt64</a> type. The flat layout provides the best performance among all layout options and allocates an in-memory <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Array_(data_structure)\">array</a> with room for as many entries as the largest value of the key attribute. For example, if the largest value is 100k, then the array will have room for 100k entries. This data layout allows extremely fast key-value lookups with <code>O(1)</code> <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Time_complexity\">time complexity</a> as only ​​a simple array offset lookup is required. The offset is simply the value of the provided key, with the entry at that offset position within the array containing the corresponding values. This is well suited for our actors and roles data where we have dense and monotonically increasing values starting at 0 in the key columns (<code>id</code> and <code>actor_id</code>, respectively) in our source tables. Therefore each allocated array entry will be used. With the hashed layout the dictionary content is stored in a <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Hash_table\">hash table</a>. The hashed layout is more generally applicable. E.g. no unnecessary space gets allocated in memory for non dense key attribute values not starting at 0. However, as we will see later, access speeds are 2-5 times slower.</p>\n<p>We <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/dictionary\">create</a> a dictionary with a flat layout that loads the content from the roles table completely into memory for low latency key-value lookups. We are using actor_id as the key attribute. Note that we use the <code>max_array_size</code> setting for specifying the initial and max array size (the default value of 500,000 would be too small). We also disable <a target=\"_blank\" href=\"https://clickhouse.com/blog/faster-queries-dictionaries-clickhouse\">content updates</a> of the dictionary by setting <code>LIFETIME</code> to 0:</p>\n<div><pre><code><span><span>CREATE</span> DICTIONARY imdb_large.roles_dict_flat</span>\n<span>(</span>\n<span>    created_at DateTime,</span>\n<span>    actor_id   UInt32,</span>\n<span>    movie_id   UInt32,</span>\n<span>    role       String</span>\n<span>)</span>\n<span><span>PRIMARY KEY</span> actor_id</span>\n<span>SOURCE(CLICKHOUSE(db <span>'imdb_large'</span> <span>table</span> <span>'roles'</span>))</span>\n<span>LIFETIME(<span>0</span>)</span>\n<span>LAYOUT(FLAT(INITIAL_ARRAY_SIZE <span>1</span>_000_000 MAX_ARRAY_SIZE <span>1</span>_000_000));</span></code></pre></div>\n<p>Next, we create a similar dictionary but with a hashed layout:</p>\n<div><pre><code><span><span>CREATE</span> DICTIONARY imdb_large.roles_dict_hashed</span>\n<span>(</span>\n<span>    created_at DateTime,</span>\n<span>    actor_id   UInt32,</span>\n<span>    movie_id   UInt32,</span>\n<span>    role       String</span>\n<span>)</span>\n<span><span>PRIMARY KEY</span> actor_id</span>\n<span>SOURCE(CLICKHOUSE(db <span>'imdb_large'</span> <span>table</span> <span>'roles'</span>))</span>\n<span>LIFETIME(<span>0</span>)</span>\n<span>LAYOUT(hashed());</span></code></pre></div>\n<p>Note that in <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a>, the dictionaries will automatically be created on all nodes. For OSS, this behavior is possible if using a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/database-engines/replicated/\">Replicated</a> database. Other configurations will require the creation of the dictionary on all nodes manually or through the use of the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/distributed-ddl\">ON CLUSTER</a> clause.</p>\n<p>We query the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/dictionaries\">dictionaries system table</a> for checking some metrics:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    name,</span>\n<span>    status,</span>\n<span>    formatReadableSize(bytes_allocated) <span>AS</span> memory_allocated,</span>\n<span>    formatReadableTimeDelta(loading_duration) <span>AS</span> loading_duration</span>\n<span><span>FROM</span> system.dictionaries</span>\n<span><span>WHERE</span> startsWith(name, <span>'roles_dict_'</span>)</span>\n<span><span>ORDER</span> <span>BY</span> name;</span>\n<span></span>\n<span></span>\n<span>┌─name──────────────┬─status─┬─memory_allocated─┬─loading_duration─┐</span>\n<span>│ roles_dict_flat   │ LOADED │ <span>1.52</span> GiB         │ <span>12</span> seconds       │</span>\n<span>│ roles_dict_hashed │ LOADED │ <span>128.00</span> MiB       │ <span>6</span> seconds        │</span>\n<span>└───────────────────┴────────┴──────────────────┴──────────────────┘</span></code></pre></div>\n<p>The <code>loading_duration</code> column shows how long it took to load the source table content into the memory layout of the dictionaries. The <code>status</code> indicates that the loading is finished. And we can see how much main memory space is allocated for the dictionaries.</p>\n<p>Creating a dictionary with the above dictionary DDL automatically creates a table with a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/dictionary\">dictionary table engine</a> backed by the dictionary. We verify that by querying the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/tables\">tables</a> system table:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    name,</span>\n<span>    engine</span>\n<span><span>FROM</span> system.tables</span>\n<span><span>WHERE</span> startsWith(name, <span>'roles_dict_'</span>)</span>\n<span><span>ORDER</span> <span>BY</span> name;</span>\n<span></span>\n<span></span>\n<span>┌─name──────────────┬─engine─────┐</span>\n<span>│ roles_dict_flat   │ Dictionary │</span>\n<span>│ roles_dict_hashed │ Dictionary │</span>\n<span>└───────────────────┴────────────┘</span></code></pre></div>\n<p>With such a table the dictionary can be worked with as a first-class table entity and data read directly using familiar SELECT clauses.</p>\n<p>Note that in contrast to normal (<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family\">MergeTree engine family</a>) ClickHouse tables, the key attribute is (automatically) unique in a dictionary. For example, the roles table contains many rows with the same <code>actor_id</code> value, since generally an actor/actress has more than one role. When these rows are loaded into the dictionary with the <code>actor_id</code> as the key attribute, then rows with the same key value overwrite each other. Effectively only the data from the last row inserted for a specific <code>actor_id</code>, is contained in the dictionary.</p>\n<p>We can verify this by selecting the count from both the dictionary’s <code>roles</code> source table and the automatically created dictionary table:</p>\n<div><pre><code><span><span>SELECT</span> formatReadableQuantity(<span>count</span>()) <span>as</span> count <span>FROM</span> roles;</span>\n<span></span>\n<span>┌─count──────────┐</span>\n<span>│ <span>100.00</span> million │</span>\n<span>└────────────────┘</span>\n<span></span>\n<span><span>SELECT</span> formatReadableQuantity(<span>count</span>()) <span>as</span> count <span>FROM</span> roles_dict_flat;</span>\n<span></span>\n<span>┌─count────────┐</span>\n<span>│ <span>1.00</span> million │</span>\n<span>└──────────────┘</span></code></pre></div>\n<p>1 million is exactly the amount of unique actors in the <code>actors</code> table. Meaning that the roles dictionary contains the data from one role per actor/actress:</p>\n<div><pre><code><span><span>SELECT</span> formatReadableQuantity(<span>count</span>()) <span>as</span> count <span>FROM</span> actors;</span>\n<span></span>\n<span>┌─count────────┐</span>\n<span>│ <span>1.00</span> million │</span>\n<span>└──────────────┘</span></code></pre></div>\n<p>Now we use the dictionary for enriching the rows from the <code>actors</code> table with info from the <code>roles</code> table. Note that we are using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/ext-dict-functions#dictget-dictgetordefault-dictgetornull\">dictGet</a> function for performing the low-latency key-value lookups. For each row from the <code>actors</code> table, we perform a lookup in the dictionary with the value from the <code>id</code> column and request the <code>created_at</code>, <code>movie_id</code>, and <code>role</code> values in the form of a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/data-types/tuple\">tuple</a>:</p>\n<div><pre><code><span><span>WITH</span> T1 <span>AS</span> (</span>\n<span>    <span>SELECT</span></span>\n<span>        id,</span>\n<span>        first_name,</span>\n<span>        last_name,</span>\n<span>        gender,</span>\n<span>        dictGet(<span>'roles_dict_flat'</span>, (<span>'created_at'</span>, <span>'movie_id'</span>, <span>'role'</span>), id) <span>as</span> t</span>\n<span>    <span>FROM</span> actors)</span>\n<span><span>SELECT</span></span>\n<span>    id,</span>\n<span>    first_name,</span>\n<span>    last_name,</span>\n<span>    gender,</span>\n<span>    id <span>AS</span> actor_id,</span>\n<span>    t<span>.1</span> <span>AS</span> created_at,</span>\n<span>    t<span>.2</span> <span>AS</span> movie_id,</span>\n<span>    t<span>.3</span> <span>AS</span> role</span>\n<span><span>FROM</span> T1</span>\n<span>LIMIT <span>1</span></span>\n<span>FORMAT Vertical;</span>\n<span></span>\n<span><span>Row</span> <span>1</span>:</span>\n<span>──────</span>\n<span>id:         <span>393216</span></span>\n<span>first_name: Wissia</span>\n<span>last_name:  Breitenreiter</span>\n<span>gender:     F</span>\n<span>actor_id:   <span>393216</span></span>\n<span>created_at: <span>2023</span><span>-05</span><span>-12</span> <span>13</span>:<span>03</span>:<span>09</span></span>\n<span>movie_id:   <span>373614</span></span>\n<span>role:       Gaston Binet</span>\n<span></span>\n<span><span>1</span> <span>row</span> <span>in</span> set. Elapsed: <span>0.019</span> sec. Processed <span>327.68</span> thousand <span>rows</span>, <span>12.74</span> MB (<span>17.63</span> million <span>rows</span><span>/</span>s., <span>685.25</span> MB<span>/</span>s.)</span></code></pre></div>\n<p>Note that if the dictionary doesn’t contain a key entry for a specific actor <code>id</code> value, then the configured <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/table#default-values\">default values</a> are returned for the requested attributes. Also because, as mentioned above, the dictionary deduplicates the loaded data based on the <code>actor_id</code> column, effectively only the first found match is returned. Therefore the behavior of the query above is equivalent to the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins#left--right--inner-any-join\">LEFT ANY JOIN</a>.</p>\n<p>There is an easier and much more compact way in ClickHouse to formulate the above query. We showed earlier that when a dictionary with a specific name is created, ClickHouse automatically creates a table of the same name backed by the dictionary via the dictionary table engine. This table allows us to express the same logic as the query above by using a join query with the <code>direct</code> join algorithm:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> actors <span>AS</span> a</span>\n<span><span>JOIN</span> roles_dict_flat <span>AS</span> r <span>ON</span> a.id <span>=</span> r.actor_id</span>\n<span>LIMIT <span>1</span></span>\n<span>SETTINGS join_algorithm<span>=</span><span>'direct'</span></span>\n<span>FORMAT Vertical;</span>\n<span></span>\n<span></span>\n<span><span>Row</span> <span>1</span>:</span>\n<span>──────</span>\n<span>id:         <span>393216</span></span>\n<span>first_name: Wissia</span>\n<span>last_name:  Breitenreiter</span>\n<span>gender:     F</span>\n<span>actor_id:   <span>393216</span></span>\n<span>created_at: <span>2023</span><span>-05</span><span>-12</span> <span>13</span>:<span>03</span>:<span>09</span></span>\n<span>movie_id:   <span>373614</span></span>\n<span>role:       Gaston Binet</span>\n<span></span>\n<span><span>1</span> <span>row</span> <span>in</span> set. Elapsed: <span>0.023</span> sec. Processed <span>327.68</span> thousand <span>rows</span>, <span>12.74</span> MB (<span>14.28</span> million <span>rows</span><span>/</span>s., <span>555.30</span> MB<span>/</span>s.)</span></code></pre></div>\n<p>Internally, ClickHouse is implementing the join using efficient key-value lookups into the dictionary backing the right-hand side table. This is similar to the query above using the <code>dictGet</code> function for lookups. We can verify this by introspecting the <a target=\"_blank\" href=\"https://youtu.be/hP6G2Nlz_cA\">query plan</a> for the join query, using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/explain#explain-plan\">EXPLAIN PLAN</a> clause:</p>\n<div><pre><code><span>EXPLAIN PLAN</span>\n<span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> actors <span>AS</span> a</span>\n<span><span>JOIN</span> roles_dict_flat <span>AS</span> r <span>ON</span> a.id <span>=</span> r.actor_id</span>\n<span>SETTINGS join_algorithm<span>=</span><span>'direct'</span>;</span>\n<span></span>\n<span></span>\n<span>┌─explain───────────────────────────────────────────────┐</span>\n<span>│ Expression ((Projection <span>+</span> Before <span>ORDER</span> <span>BY</span>))           │</span>\n<span>│   FilledJoin (<span>JOIN</span>)                                   │</span>\n<span>│     Expression ((<span>Convert</span> <span>JOIN</span> columns <span>+</span> Before <span>JOIN</span>)) │</span>\n<span>│       ReadFromMergeTree (imdb_large.actors)           │</span>\n<span>└───────────────────────────────────────────────────────┘</span></code></pre></div>\n<p>We can see that ClickHouse is using a special <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/23.4/src/Processors/QueryPlan/JoinStep.h#L44\">FilledJoin</a> step indicating that nothing needs to be done to prepare or load the right-hand side table, as its content is already existing in memory in the form of a very fast key-value lookup data structure. Ready and ideal for executing the join.</p>\n<p>For comparison, we can introspect the query plan for the same join query using a hash algorithm:</p>\n<div><pre><code><span>EXPLAIN
