The joined data from the right-hand side table needs to fit into memory. <strong>Grace hash join</strong> is a non-memory bound version that spills data temporarily to disk, without requiring any sorting of the data, and therefore overcomes some of the performance challenges of other join algorithms that spill data to disk and require prior sorting of the data. Which brings us to this post.</p>\n<p>We’ll continue the exploration of the ClickHouse join algorithms in this post and describe the two algorithms from the chart above that are based on <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/External_sorting\">external sorting</a>:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part3#full-sorting-merge-join\">Full sorting merge join</a></li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part3#partial-merge-join\">Partial merge join</a></li>\n</ul>\n<p>Both algorithms are non-memory bound and use a join strategy that requires the joined data to first be sorted in order of the join keys before join matches can be identified.</p>\n<p>With the <strong>full sorting merge join</strong> the rows from both tables are then joined by interleaved linear scans and merges of the sorted streams of blocks of rows from both tables:\n<span><img alt=\"full_sorting_merge_abstract.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Ffull_sorting_merge_abstract_d0cda56e1d.png&w=2048&q=75\"></span></p>\n<p>With the <strong>partial merge join</strong> the rows from both tables are join matched by merging each sorted block of rows from the left table with the sorted blocks of rows from the right table:\n<span><img alt=\"partial_merge_abstract.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpartial_merge_abstract_11706c66c7.png&w=2048&q=75\"></span></p>\n<p>The full sorting merge join can take advantage of the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">physical row order</a> of one or both tables, allowing sorting to be skipped. In such cases, the join performance can be competitive with the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2\">hash join algorithms</a> from the chart above, while generally requiring significantly less memory. Otherwise, the full sorting merge join needs to fully sort the rows of the tables prior to identifying join matches. The sorting can take place in memory (if the data fits in) or externally on disk.</p>\n<p>The partial merge join is optimized for minimizing memory usage when large tables are joined. The right table is always fully sorted first via external sorting. In order to minimize the amount of data being processed in-memory when join matches are identified, special index structures are created on disk. The left table is always sorted block by block in-memory. But if the physical row order of the left table matches the join key sort order, then the in-memory identification of join matches is more efficient.</p>\n<p>We will finish our exploration of the ClickHouse join algorithms in the next <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-direct-join-part4\">post</a> where we will describe ClickHouse’s fastest join algorithm from the chart above:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-direct-join-part4#direct-join\">Direct join</a></li>\n</ul>\n<h2 id=\"test-setup\"></h2>\n<p>We are using the same two tables and <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> service instance that we introduced in the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2\">previous post</a>.</p>\n<p>For all example query runs we use the default setting of <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-max_threads\">max_threads</a>. href=\"https://en.wikipedia.org/wiki/Sort-merge_join\">sort-merge join</a> integrated into the ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#query-pipeline\">query pipeline</a>.</p>\n<p>The ClickHouse version of the sort-merge join provides several performance optimizations.</p>\n<ul>\n<li>The joined tables can be filtered by each other's join keys prior to any sort and merge operations, in order to minimize the amount of processed data.</li>\n<li>And if the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">physical row order</a> of one or both tables matches the join key sort order, then the sorting phase will be skipped for the corresponding table(s).</li>\n</ul>\n<p>We will discuss these optimizations in detail later.</p>\n<p>The following diagram shows the general version of the full sorting merge join algorithm without any optimization applied:</p>\n<p><span><img alt=\"full_sorting_merge_1.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Ffull_sorting_merge_1_ff88fa186c.png&w=2048&q=75\"></span></p>\n<p>① All data from the right table are streamed <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#setting-max_block_size\">block-wise</a> in parallel by 2 stream stages (because <code>max_threads = 2</code>) into memory. These sorted blocks are spilled to <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/server-configuration-parameters/settings#tmp-path\">temporary storage</a> by two parallel spill stages.</p>\n<p>② Concurrently to ①, all data from the left table is streamed block-wise in parallel by 2 threads ( <code>max_threads = 2</code>), and similar to ①, each block is sorted and spilled to disk.</p>\n<p>③ With one stream per table, the sorted blocks are read from disk and merge-sorted, with join matches identified by merging (interleaved scanning) the two sorted streams.</p>\n<h3 id=\"supported-join-types\"></h3>\n<p>INNER, LEFT, RIGHT, and FULL  join <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/join#supported-types-of-join\">types</a> for ALL and ANY <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-join_default_strictness\">strictness</a> are <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/512b27ef27ffa5950406e3450047366b35d849cb/src/Interpreters/MergeJoin.cpp#L1147-L1160\">supported</a>.</p>\n<h3 id=\"examples\"></h3>\n<p>In order to first demonstrate the general version of the full sorting merge join algorithm without any optimizations applied, we use a join query that finds all actors whose first names are used as role names in movies. We will discuss these next.</p>\n<h3 id=\"optimizations\"></h3>\n<h4 id=\"filtering-tables-by-each-others-join-key-values-before-joining\"></h4>\n<p>The joined tables can be filtered by each other's join keys prior to any sort and merge operations in order to minimize the amount of data that needs to be sorted and merged. For this, and if possible (see below), ClickHouse builds an in-memory <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Set_(mathematics)\">set</a> containing the (unique) join key column values of the right table and uses this set for filtering out all rows from the left table that can’t possibly have join matches. And vice versa. This works especially well if one table is much smaller than the other and the table’s unique join key column values fit in memory.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2\">Hash join</a> also will perform well in such a scenario. But full sorting merge join works for both left and right tables in the same way, and in the case of both tables being larger than the available memory it will just fall back on external sorting automatically. This optimization is an attempt to bring hash join performance to full sorting merge join for this particular use case. The <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/23.4/src/Core/Settings.h#L389\">max_rows_in_set_to_optimize_join</a> setting controls the optimization. This means that if both sets together stay below the threshold, then the optimization will be applied to both tables. If both sets together are above the threshold, then it can still be that one of the two sets is below the threshold, and the optimization will be applied to just one table. As we will see in the trace logs below, ClickHouse will sequentially try to build the sets for both tables and revert and skip building a set if the limit is exceeded.</p>\n<p>Our example join query The classical sort-merge join fully sorts both joined tables by join keys first and then merges the sorted results. The ClickHouse partial merge join is optimized for minimizing memory usage when large tables are joined and only fully sorts the right table first via external sorting. In order to minimize the amount of data being processed in memory, it creates min-max indexes on disk. The left table is always sorted, block-wise and in-memory. But if the physical row order of the left table matches the join key sort order, then the in-memory identification of join matches is more efficient.</p>\n<p>This diagram sketches the details of how ClickHouse implements the partial merge join:</p>\n<p><span><img alt=\"partial_merge_1.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpartial_merge_1_077d65a57c.png&w=2048&q=75\"></span></p>\n<p>The query pipeline looks very similar to the pipeline of the ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2#hash-join\">hash join algorithm</a>. This is no coincidence. The partial merge join is reusing the hash join pipeline because, as the hash join, it has a build and a scan phase. Remember that the hash join first builds a hash table from the right table and then scans the left table. Similarly, the partial merge join first builds a sorted version of the right table and then scans the left table:</p>\n<p>① First, all data from the right table is streamed <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#setting-max_block_size\">block-wise</a> in parallel by 2 streams (because <code>max_threads = 2</code>) into the memory.  Via fill stages, the rows within each streamed block are sorted by the join key column values and spilled to <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/server-configuration-parameters/settings#tmp-path\">temporary storage</a> together with a min-max index for each sorted block. A min-max index stores, for each sorted block, the minimum and maximum join key values that the block contains. These min-max indexes are used in step ② for minimizing the amount of data being processed in-memory when join matches are identified.</p>\n<p>② Then all data from the left table is streamed block-wise in parallel by 2 streams (<code>max_threads = 2</code>).  Each block is sorted on the fly by the join keys and then ③  matched against the sorted blocks on disk from the right table. The min-max indexes are used for loading only right table blocks from disk that can possibly contain join matches.</p>\n<p>This join processing strategy is very memory efficient. Regardless of the size and physical row order of the joined tables. In step ① above only a few blocks from the right table are streamed through memory at the same time before being written to temporary storage. In step ② only a few blocks from the left table are streamed through memory at the same time. The min-max indexes created in step  ① help minimize the number of right table blocks that are loaded into memory from temporary storage for identifying join matches.</p>\n<p>Note that if the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">physical row order</a> of the left table matches the join key sort order, then this min-max index based skipping of non-matching right table blocks is most effective.</p>\n<p>However, it is most expensive to use the partial merge join algorithm when the data blocks of the left table have some general distribution of join key values. Because if each block of the left table contains a large subset of generally distributed join key values, then the min-max indexes of the sorted blocks from the right table don’t help, and effectively a cross product is created between the blocks of both tables: for each block of the left table, a large set of sorted blocks from the right table is loaded from disk.</p>\n<h3 id=\"supported-join-types\"></h3>\n<p>INNER, LEFT, RIGHT, FULL join <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/join#supported-types-of-join\">types</a> with ALL <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-join_default_strictness\">strictness</a> and INNER, LEFT join types with ANY and SEMI strictness are <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/512b27ef27ffa5950406e3450047366b35d849cb/src/Interpreters/MergeJoin.cpp#L1147-L1160\">supported</a>.</p>\n<h3 id=\"examples\"></h3>\n<p>We run our example join query (using join keys which are prefixes of the joined table’s sorting keys to benefit from the above min-max index based performance optimization) with the partial merge algorithm:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> actors <span>AS</span> a</span>\n<span><span>INNER</span> <span>JOIN</span> roles <span>AS</span> r <span>ON</span> a.id <span>=</span> r.actor_id</span>\n<span>FORMAT `<span>Null</span>`</span>\n<span>SETTINGS join_algorithm <span>=</span> <span>'partial_merge'</span>;</span>\n<span></span>\n<span><span>0</span> <span>rows</span> <span>in</span> set.
