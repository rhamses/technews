This very fast lookup capability makes the in-memory hash table a <a target=\"_blank\" href=\"https://clickhouse.com/blog/hash-tables-in-clickhouse-and-zero-cost-abstractions\">natural general choice in ClickHouse</a> for implementing joins when it is not possible or feasible to take advantage of table sorting.</p>\n<p>The hash join algorithm is the most generic of the available join implementations in ClickHouse. We illustrate the <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Hash_join\">hash join algorithm</a> integrated into the ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#query-pipeline\">query pipeline</a> below:</p>\n<p><span><img alt=\"hash.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fhash_4131734f7e.png&w=2048&q=75\"></span>\nWe can see that:</p>\n<p>① All data from the right-hand side table is streamed (in parallel by 2 threads because max_threads = 2) into the memory, and then ClickHouse fills an in-memory hash table with this data.</p>\n<p>② Data from the left-hand side table is streamed (in parallel by 2 threads because max_threads = 2) and ③ joined by doing lookups into the hash table.</p>\n<p>Note that because ClickHouse takes the right-hand side table and creates a hash table for it in RAM, it is more memory efficient to place the smaller table on the right-hand side of the JOIN. We will demonstrate that below.</p>\n<p>Also note that the <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Hash_table\">Hash table</a> is a <a target=\"_blank\" href=\"https://clickhouse.com/blog/hash-tables-in-clickhouse-and-zero-cost-abstractions\">key data structure</a> in ClickHouse. Based on each specific query and, for join queries specifically, based on join key column types and join <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-join_default_strictness\">strictness</a>, ClickHouse automatically <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/concepts/why-clickhouse-is-so-fast#attention-to-low-level-details\">chooses</a> one of 30+ variations.</p>\n<h3 id=\"supported-join-types\"></h3>\n<p>All join <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/join#supported-types-of-join\">types</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-join_default_strictness\">strictness</a> settings are supported. In addition, currently, only the hash join supports multiple join keys that are combined with OR in the ON clause.</p>\n<p>For readers wanting to dive even deeper, the source code contains a very <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/23.3/src/Interpreters/HashJoin.h#L79\">detailed description</a> of how these types and settings are implemented by the hash join algorithm.</p>\n<h3 id=\"examples\"></h3>\n<p>We demonstrate the hash join algorithm with two query runs.</p>\n<p>Smaller table on the right-hand side:</p>\n<pre><p>\nSELECT *\nFROM roles AS r\nJOIN actors AS a ON r.actor_id = a.id\nFORMAT `Null`\nSETTINGS join_algorithm = 'hash';\n0 rows in set. The reason for this is that the hash table size is initially chosen and <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/23.3/src/Common/HashTable/HashTable.h#L234\">dynamically</a> <a target=\"_blank\" href=\"https://godbolt.org/z/cKjaTe3Mf\">increased</a> based on the types of the join key columns and in multiples of a specific internal hash table buffer size. The <code>memory_usage</code> metric counts the overall memory reserved for the hash table, though it may not be completely filled.</p>\n<p>For the execution of both queries, ClickHouse reads the same amount of total rows (and data):\n100 million rows from the roles table + 1 million rows from the actors table. However, the join query with the larger roles table on the right-hand side is five times slower. This is because the default hash join is not thread-safe for inserting the right table's rows into the hash table. Therefore the fill stage for the hash table runs in a single thread. Two additional parallel stream stages ② and two parallel join stages ③ are used for streaming and joining the data from the left-hand side table.</p>\n<p>As mentioned above, the default hash join algorithm is not thread-safe for inserting the right-hand side table's rows into the hash table. Therefore a resize stage is used in the pipeline above for reducing the two threads streaming the data from the right-hand side table into a single-threaded fill stage. This can become a bottleneck for the query runtime. If the right-hand side table is large - see our two query runs above where the query with the large <code>roles</code> table on the right-hand side of the join was five times slower.</p>\n<p>However, <a target=\"_blank\" href=\"https://presentations.clickhouse.com/release_22.7/#14\">since</a> ClickHouse version 22.7 the process of building the hash table from the right-hand side table can be significantly sped up for large tables by using the parallel hash algorithm.</p>\n<h2 id=\"parallel-hash-join\"></h2>\n<h3 id=\"description\"></h3>\n<p>The parallel hash join algorithm is a variation of a hash join that splits the input data to build several hash tables concurrently in order to speed up the join at the expense of higher memory overhead. We sketch this algorithm's <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#query-pipeline\">query pipeline</a> below:</p>\n<p><span><img alt=\"parallel_hash.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fparallel_hash_6e944127fa.png&w=2048&q=75\"></span></p>\n<p>The diagram above shows that:</p>\n<p>① All data from the right table is streamed (in parallel by 2 threads because <code>max_threads = 2</code>) into the memory. The data is streamed <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=hP6G2Nlz_cA&feature=youtu.be\">block-wise</a>. The rows from each streamed block are split into 2 buckets ( <code>max_threads = 2</code>)  by applying a hash function to the join keys of every row. We sketch this with the orange and blue colors in the diagram above. In parallel, one in-memory hash table is filled per bucket using a single thread.  Note that the hash function for splitting the rows into buckets is different from the one that is used in the hash tables internally.</p>\n<p>② Data from the left table is streamed (in parallel by 2 threads because <code>max_threads = 2</code>), and the same ‘bucket hash function’ from step ① is applied to the join keys of each row for determining the corresponding hash table and the rows are ③ joined by doing lookups into the corresponding hash table.</p>\n<p>Note that the <code>max_threads</code> setting determines the number of concurrent hash tables. We will demonstrate that later by introspecting concrete query pipelines.</p>\n<h3 id=\"supported-join-types\"></h3>\n<p>INNER and LEFT join <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/join#supported-types-of-join\">types</a> and all <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-join_default_strictness\">strictness</a> settings except ASOF are <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/23.3/src/Interpreters/TableJoin.cpp#L745\">supported</a>.</p>\n<h3 id=\"examples\"></h3>\n<p>We will now compare the runtimes and peak memory consumption of  the hash and parallel hash algorithms for the same query.</p>\n<p>Hash join with a larger table on the right-hand side:</p>\n<pre><p>\nSELECT *\nFROM actors AS a\nJOIN roles AS r ON a.id = r.actor_id\nFORMAT `Null`\nSETTINGS join_algorithm = 'hash';\n0 rows in set. This means that, as we will demonstrate below, 30 concurrent hash tables were used. As mentioned before, the size for each hash table is initially chosen and dynamically increased based on the types of the join key columns and in multiples of a specific internal hash table buffer size. The hash tables are most likely not completely filled, but the <code>memory_usage</code> metric counts the overall memory reserved for the hash tables.</p>\n<h3 id=\"query-pipeline\"></h3>\n<p>We mentioned that the <code>max_threads</code> setting determines the number of concurrent hash tables. We can verify this by introspecting the concrete query pipelines.</p>\n<p>First, we introspect the query pipeline for the parallel hash join query with <code>max_threads</code> set to 2:</p>\n<pre><div><p>\n./clickhouse client --host ekyyw56ard.us-west-2.aws.clickhouse.cloud --secure --port 9440 --password </p><!-- --><p> --database=imdb_large --query \"\nEXPLAIN pipeline graph=1, compact=0\nSELECT *\nFROM actors a\nJOIN roles r ON a.id = r.actor_id\nSETTINGS max_threads = 2, join_algorithm = 'parallel_hash';\" | dot -Tpdf &gt; pipeline.pdf\n</p></div>\n</pre>\n<p>As usual, we have annotated the pipeline with the same circled numbers used in the abstract diagram above, slightly simplified the names of the main stages, and added the two joined tables in order to align the two diagrams:</p>\n<p><span><img alt=\"parallel_hash_pipeline_1.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fparallel_hash_pipeline_1_2f1c9a0007.png&w=2048&q=75\"></span></p>\n<p>We can see that two concurrent fill stages exist for filling two hash tables with data from the right-hand side table in parallel. Furthermore, two concurrent join stages are used for joining (in the form of hash table lookups) the data from the left-hand side table.</p>\n<p>Note that resize stages are used in the query pipeline above for defining explicit connections between all fill and all join stages: All join stages should wait until all fill stages are finished.</p>\n<p>Next, we introspect the query pipeline for the parallel hash join query with <code>max_threads</code> set to 4:</p>\n<pre><div><p>\n./clickhouse client --host ekyyw56ard.us-west-2.aws.clickhouse.cloud --secure --port 9440 --password </p><!-- --><p> --database=imdb_large --query \"\nEXPLAIN pipeline graph=1, compact=0\nSELECT *\nFROM actors a\nJOIN roles r ON a.id = r.actor_id\nSETTINGS max_threads = 4, join_algorithm = 'parallel_hash';\" | dot -Tpdf &gt; pipeline.pdf\n</p></div>\n</pre>\n<p><span><img alt=\"parallel_hash_pipeline_2.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fparallel_hash_pipeline_2_9475d24433.png&w=2048&q=75\"></span></p>\n<p>Now four concurrent fill stages are used for filling four hash tables with data from the right-hand side table in parallel. And four concurrent join stages are used for joining the data from the left-hand side table.</p>\n<p>Measurements in the original <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/36415\">PR</a> indicate that the speedup is almost linearly correlated to the degree of parallelism.</p>\n<h2 id=\"grace-hash-join\"></h2>\n<h3 id=\"description\"></h3>\n<p>Both the hash and parallel hash join algorithms described above are fast but memory-bound. If the right-hand side table doesn’t fit into the main memory, ClickHouse will raise an OOM exception. In this situation, ClickHouse users can sacrifice performance and use a (partial) merge algorithm (described in the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3\">next post</a>) that (partially) sorts the table's data into external storage before merging it.</p>\n<p>Luckily, ClickHouse 22.12 <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-22-12\">introduced</a> another join algorithm called ‘grace hash’ that is non-memory bound, but hash table based, and therefore doesn’t require any sorting of the data. This overcomes some of the performance challenges of the (partial) merge algorithm.</p>\n<p>The algorithm utilizes a two-phased approach to joining the data. Our implementation differs slightly from the <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=GRONctC_Uh0\">classic algorithmic description</a> in order to fit our <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#query-pipeline\">query pipeline</a>. The following diagram shows the first phase:</p>\n<p><span><img alt=\"grace_hash_1.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fgrace_hash_1_97a605582f.png&w=2048&q=75\"></span></p>\n<p>① All data from the right table is streamed block-wise (in parallel by 2 threads because <code>max_threads = 2</code>) into the memory. The rows from each streamed block are split into 3 buckets (because <code>grace_hash_join_initial_buckets = 3</code>)  by applying a hash function to the join keys of every row. We sketch this with the orange, blue, and green colors in the diagram above. An in-memory hash table is filled with rows from the first (orange) bucket. The joining of the other two (green and blue) buckets from the right_table is delayed by saving them to <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/server-configuration-parameters/settings#tmp-path\">temporary storage</a>.</p>\n<p>Note that if the in-memory hash table grows beyond the memory limit (as set by <code>max_bytes_in_join</code>), ClickHouse dynamically increases the number of buckets and recomputes the assigned bucket for each row. Any rows which don’t belong to the current bucket are flushed and reassigned.</p>\n<p>Also note that ClickHouse <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/23.3/src/Interpreters/GraceHashJoin.cpp#L289\">rounds</a> the set value for <code>grace_hash_join_initial_buckets</code> up to the closest power of two. Therefore as 3 is rounded up to 4, and 4 initial buckets are used. We use 3 buckets in our diagrams for readability, and there is no crucial difference to the inner workings with 4.</p>\n<p>② Data from the left table is streamed in parallel by 2 threads ( <code>max_threads = 2</code>), and the same ‘bucket hash function’ from step ① is applied to the join keys of each row for determining the corresponding bucket. Rows corresponding to the first bucket are ③ joined (as the corresponding hash table is in memory). The joining of the other buckets is delayed by saving them to temporary storage.</p>\n<p>The key in steps ① and ②  is that the ‘bucket hash function’ will consistently assign values to the same bucket, thereby effectively partitioning the data and solving the problem by <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Lossless_join_decomposition\">decomposition</a>.</p>\n<p>In a second phase, ClickHouse processes the remaining buckets on disk. The remaining buckets are processed sequentially. The following two diagrams sketch this. The first diagram shows how the blue bucket gets processed first. The second diagram shows the processing of the final green bucket.</p>\n<p><span><img alt=\"grace_hash_2.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fgrace_hash_2_633536e992.png&w=2048&q=75\"></span></p>\n<p><span><img alt=\"grace_hash_3.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fgrace_hash_3_723d5b5030.png&w=2048&q=75\"></span></p>\n<p>①  ClickHouse builds the hash table for each bucket from the right-hand side table data.</p>\n<p>Again, if ClickHouse runs out of memory, it dynamically increases the number of buckets.</p>\n<p>②  Once a hash table has been built from a right-hand side table bucket, ClickHouse streams the data from the corresponding left-hand side table bucket and ③ completes the join for this pair.</p>\n<p>Note that during this phase, there can be some rows that belong to another bucket other than the current one, due to them being saved to temporary storage before the number of buckets was dynamically increased. In this case, ClickHouse saves them to the new actual buckets and processes them further.</p>\n<p>This process is repeated for all of the remaining buckets.</p>\n<h3 id=\"supported-join-types\"></h3>\n<p>INNER and LEFT join <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/join#supported-types-of-join\">types</a> and all <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-join_default_strictness\">strictness</a> settings except ASOF are <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/23.3/src/Interpreters/GraceHashJoin.cpp#L305\">supported</a>.</p>\n<h3 id=\"examples\"></h3>\n<p>Below we compare the runtimes and peak memory consumptions of the same join query run using the hash join and grace hash join algorithms.</p>\n<p>Hash join with larger table on the right-hand side:</p>\n<pre><p>\nSELECT *\nFROM actors AS a\nJOIN roles AS r ON a.id = r.actor_id\nFORMAT `Null`\nSETTINGS join_algorithm = 'hash';\n0 rows in set.
