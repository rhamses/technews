We examine client-side optimizations—most importantly, the choice of input format—to accelerate server-side processing.</p>\n<p>First, we briefly review ClickHouse’s MergeTree insert mechanics and key client-side tuning options:</p>\n<p><span><img alt=\"Blog-Formats.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_001_43eeb7a388.png&w=2048&q=75\"></span></p>\n<p>The diagram above illustrates how a client ingests data batches into a table on a remote ClickHouse server. We describe all the processing steps below.</p>\n<h3 id=\"client-side-steps\"></h3>\n<p>For optimal performance, data must be ① <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#data-needs-to-be-batched-for-optimal-performance\">batched</a>, making batch size the <strong>first decision</strong>. If batching isn’t feasible, <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse\">asynchronous inserts</a> can be used, but the server-side insert process remains the same—only a buffer is introduced between step ⑦ (data decompression) and step ⑧ (data parsing).</p>\n<p>ClickHouse stores inserted data on disk, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/best-practices/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">ordered</a> by the table’s primary key column(s). The <strong>second decision</strong> is whether to ② pre-sort the data before transmission to the server. If a batch arrives pre-sorted by primary key column(s), ClickHouse can <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/94ce8e95404e991521a5608cd9d636ff7269743d/src/Storages/MergeTree/MergeTreeDataWriter.cpp#L595\">skip</a> the ⑨ sorting step, speeding up ingestion. How much of a performance boost does this provide? And is it worth the extra effort on the client side? We’ll demonstrate this later in the post—stay tuned.</p>\n<p>If the data to be ingested has no predefined format, the <strong>key decision</strong> is choosing a format. ClickHouse supports inserting data in <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/formats\">over 70 formats</a>. However, when using the ClickHouse command-line client or programming language clients, this choice is often handled automatically—selecting an efficient format by default, as we’ll discuss later. If needed, this automatic selection can also be overridden explicitly.</p>\n<p>The next <strong>major decision</strong> is ④ whether to compress data before transmission to the ClickHouse server. Compression reduces transfer size and improves network efficiency, leading to faster data transfers and lower bandwidth usage, especially for large datasets.</p>\n<p>The data is ⑤ transmitted to a ClickHouse network interface—either the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/tcp\">native</a> or <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/http\">HTTP</a> interface (which we <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-input-format-matchup-which-is-fastest-most-efficient#clickhouse-client-defaults\">compare</a> later in this post).</p>\n<h3 id=\"server-side-steps\"></h3>\n<p>After ⑥ receiving the data, ClickHouse ⑦ decompresses it if compression was used, then ⑧ parses it from the originally sent format.</p>\n<p>Using the values from that formatted data and the target table’s <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/table\">DDL</a> statement, ClickHouse ⑨ builds an in-memory <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/development/architecture#block\">block</a> in the MergeTree format, ⑩ <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/parts#what-are-table-parts-in-clickhouse\">sorts</a> rows by the primary key columns if they are not already pre-sorted, ⑪ creates a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/best-practices/sparse-primary-indexes\">sparse primary index</a>, ⑫ applies <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/parts#what-are-table-parts-in-clickhouse\">per-column compression</a>, and ⑬ writes the data as a new ⑭ <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/parts\">data part</a> to disk.</p>\n<h2 id=\"client-side-tuning-options-for-inserts\"></h2>\n<p>After examining the inner workings of ClickHouse insert processing, we now have the foundation to outline client-side tuning options—key optimizations that improve server-side ingestion performance by reducing the server’s workload. <strong>The core idea is to offload work to the client to maximize efficiency on the server</strong>:</p>\n<p><strong>① Batch the data</strong> to reduce insert overhead and improve processing efficiency.</p>\n<p><strong>② Presort the data</strong> to eliminate the sorting step on the server.</p>\n<p><strong>③ Convert data into a format</strong> that is efficient for the server to process.</p>\n<p><strong>④ Compress the data</strong> to reduce transfer size and improve network efficiency.</p>\n<p>These optimizations improve server-side ingestion efficiency and throughput, typically requiring appreciable additional client-side resources.</p>\n<p>However, as we will demonstrate, choosing an efficient format (③) has the greatest impact, followed by compression (④). Pre-sorting (②) helps in specific cases but is less critical, while batching (①) is orthogonal to the other optimizations—it reduces insert overhead but does not directly affect format efficiency, compression, or sorting.</p>\n<p>With these key optimizations in mind, the next step is understanding ClickHouse’s available input formats, as format choice plays such a crucial role in ingestion performance. In the next section, we provide a brief overview of ClickHouse input formats before diving into our benchmark, which quantifies the impact of format selection, compression, pre-sorting, and batching on ingestion efficiency.</p>\n<h2 id=\"clickhouse-input-formats\"></h2>\n<p>ClickHouse supports various data <a target=\"_blank\" href=\"https://clickhouse.com/docs/interfaces/formats\">formats</a> for input (and output). When clients continuously collect data without a predefined format, it must first be ① formatted before being ② sent to the server, where it is transformed and stored in the <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">MergeTree table format</a>:</p>\n<p><span><img alt=\"Blog-Formats.002.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_002_9afe7111d5.png&w=2048&q=75\"></span></p>\n<p>As shown in the diagram, ClickHouse’s <a target=\"_blank\" href=\"https://clickhouse.com/docs/interfaces/formats\">70+ input formats</a> fall into three broad categories:</p>\n<p><strong>Text-based</strong> formats (e.g. variants of CSV, TSV, and JSON) and <strong>binary</strong> formats, which are further divided into <strong>column-oriented</strong> (e.g. Native, Parquet, Arrow, etc.) and <strong>row-oriented</strong> (e.g. RowBinary, Protobuf, Avro) formats. ClickHouse provides built-in support for all these formats, enabling seamless <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part2\">data loading</a> without third-party tools.</p>\n<p>In scenarios where a client continuously pushes data to the server and efficiency is important, the practical choices narrow significantly. ClickHouse’s <a target=\"_blank\" href=\"https://clickhouse.com/docs/interfaces/formats/Native\">Native</a> format stands out as the most efficient option, as we will demonstrate later. This format is designed for high-performance and low-latency processing, offering high compression ratios for efficient network transport and minimal server-side processing overhead. For example, as shown in the diagram, the columnar structure of the Native format closely matches the MergeTree table format, reducing the need for additional server-side transformations.</p>\n<p>To quantify these efficiencies and determine the fastest input formats for high-throughput ingestion, we conducted the FastFormats benchmark. The next section provides a brief overview of its methodology and key mechanics.</p>\n<h2 id=\"fastformats-benchmark\"></h2>\n<p>To systematically evaluate the client-side optimizations outlined earlier, we developed <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/\">FastFormats</a>—a dedicated benchmark designed to measure ingestion speed and hardware efficiency across different input formats, as well as the impact of pre-sorting, compression, and batching.</p>\n<p>FastFormats focuses on pure server-side processing times, ensuring that only metrics taken after client-side work is completed are used for comparison. href=\"https://avro.apache.org/docs/1.7.6/spec.html\">Avro</a> and <a target=\"_blank\" href=\"https://arrow.apache.org/docs/python/feather.html?utm_source=chatgpt.com\">Arrow</a>) or at the <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/1705a83c301faf6657798b1077098c682202f98a/main.sh#L22\">apply</a> the appropriate compression <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/1705a83c301faf6657798b1077098c682202f98a/main.sh#L138\">skip</a> the usual compression step before sending it to ClickHouse, as double compression provides little to no gain in ratio but unnecessarily increases CPU usage.</p>\n<h3 id=\"formats-that-are-unsupported-or-redundant\"></h3>\n<p>Not all formats are suitable for our dataset, target table, or purpose. For example, <strong>LineAsString</strong> only works with a single String field, <strong>Npy</strong> is designed for NumPy arrays, and <strong>JSONAsObject</strong> requires a single JSON field. Some formats, like <strong>ProtobufSingle</strong>, are meant for individual messages rather than batches and don’t fit our use case. These have been commented out in the benchmark’s test loop. Additionally, some formats are just synonyms—for instance, <strong>NDJSON</strong> and <strong>JSONLines</strong> are aliases for <strong>JSONEachRow</strong>, and <strong>TSV</strong> is a synonym for <strong>TabSeparated</strong>—so we included only one in each case to avoid redundancy.</p>\n<h3 id=\"clickhouse-native-vs-http-interface\"></h3>\n<p>Only the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-input-format-matchup-which-is-fastest-most-efficient#http-interface\">HTTP interface</a> allows benchmarking of server-side ingestion performance for any input format in isolation. The <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-input-format-matchup-which-is-fastest-most-efficient#native-interface\">native interface</a>, in contrast, only accepts Native format.</p>\n<p>For completeness, our benchmark includes an <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/1705a83c301faf6657798b1077098c682202f98a/main.sh#L354\">inner loop</a> testing both the HTTP and native interfaces. However, results from our <a target=\"_blank\" href=\"https://fastformats.clickhouse.com/\">online dashboard</a> are not directly comparable. We use <code>curl</code> to send pre-sorted, fully formatted, and compressed data over HTTP, so server-side ingestion metrics <strong>exclude</strong> client-side work like sorting, formatting, and compression. This aligns with our goal: evaluating how different formats, compression, and sorting affect server-side performance, <strong>independent</strong> of data preparation costs.</p>\n<p>For the native interface, we use <code>clickhouse-client</code>, which (1) applies block-level network compression in a streaming fashion and (2) <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-input-format-matchup-which-is-fastest-most-efficient#native-interface\">always</a> converts input to Native format before transmission. Consequently, server-side ingestion metrics (1) always reflect the server-side processing of <strong>only</strong> the Native format and (2) inherently <strong>include</strong> compression time.</p>\n<h3 id=\"hardware-used-for-our-test-runs\"></h3>\n<p>We used a dedicated AWS EC2 <code>m6i.8xlarge</code> instance (32 CPU cores, 128 GiB RAM) as the client machine for FastFormats and a ClickHouse Cloud cluster with three compute nodes (each with 30 CPU cores and 120 GiB RAM) as the server system. This is because inserts from concurrent clients do not arrive exactly simultaneously at the server, and smaller inserts are processed <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/c6457ff17be6016d7b59543b62ad332b6f382858/results/http_native_10000_unsorted_lz4.json#L38\">quickly</a>. As a result, server-side processing overlaps only occasionally, leading to periodic spikes in CPU and memory usage rather than a consistent linear increase:</p>\n<p><span><img alt=\"Blog-Formats.006.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_006_ebdf28f9e0.png&w=2048&q=75\"></span></p>\n<p>With larger inserts, server-side processing takes <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/c6457ff17be6016d7b59543b62ad332b6f382858/results/http_native_1000000_unsorted_lz4.json#L38\">longer</a>, increasing the likelihood of overlapping execution and leading to more sustained CPU and memory usage growth:</p>\n<p><span><img alt=\"Blog-Formats.007.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_007_796691913c.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p>For small inserts, CPU and memory scale sub-linearly with concurrent clients. As insert size and number of concurrent clients increases, resource usage grows more steeply, peaking when all clients’ inserts are processed simultaneously, reaching the product of per-client usage and concurrency.</p>\n</blockquote>\n<p>Finally, we analyze the impact of batch size on server-side processing efficiency.</p>\n<h2 id=\"impact-of-batch-sizes\"></h2>\n<p>\nWe mentioned it <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#data-needs-to-be-batched-for-optimal-performance\">elsewhere</a>–Using ClickHouse is like driving a high-performance Formula One car 🏎. You have a copious amount of raw horsepower, and you can reach top speed. But to achieve maximum performance, you need to shift up into a high enough gear at the right time and batch data appropriately. The following chart highlights this:\n</p>\n<p><span><img alt=\"Blog-Formats.008.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_008_46a9b7912f.png&w=2048&q=75\"></span></p>\n<p>The chart displays the total server-side processing time for ingesting 10M rows from our test dataset using inserts of varying sizes, always in the Native format and LZ4-compressed.</p>\n<p>With larger batch sizes, ingestion becomes significantly more efficient, but at the cost of higher per-insert resource usage:</p>\n<ul>\n<li>At <strong>10k rows per insert</strong> (1000 inserts for 10M rows), total ingestion takes <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/c6457ff17be6016d7b59543b62ad332b6f382858/results/http_native_10000_unsorted_lz4.json#L29\">131 seconds</a>. Each insert consumes <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/c6457ff17be6016d7b59543b62ad332b6f382858/results/http_native_10000_unsorted_lz4.json#L71\">32 MiB</a> of memory, with <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/c6457ff17be6016d7b59543b62ad332b6f382858/results/http_native_10000_unsorted_lz4.json#L74\">5.5%</a> CPU usage.</li>\n<li>Increasing to <strong>100k rows per insert</strong> (100 inserts for 10M rows) cuts ingestion time nearly in half to <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/c6457ff17be6016d7b59543b62ad332b6f382858/results/http_native_100000_unsorted_lz4.json#L29\">64 seconds</a>, but memory usage jumps to <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/c6457ff17be6016d7b59543b62ad332b6f382858/results/http_native_100000_unsorted_lz4.json#L71\">254 MiB</a> per insert, and CPU utilization rises to <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/c6457ff17be6016d7b59543b62ad332b6f382858/results/http_native_100000_unsorted_lz4.json#L74\">44%</a>.</li>\n<li>Pushing <strong>1M rows per insert</strong> (just 10 inserts for 10M rows) drives ingestion time down to <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/c6457ff17be6016d7b59543b62ad332b6f382858/results/http_native_1000000_unsorted_lz4.json#L29\">46 seconds</a>. However, each insert now demands <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/c6457ff17be6016d7b59543b62ad332b6f382858/results/http_native_1000000_unsorted_lz4.json#L71\">730 MiB</a> of memory, with CPU usage rising to <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/c6457ff17be6016d7b59543b62ad332b6f382858/results/http_native_1000000_unsorted_lz4.json#L74\">456%</a>, using multiple cores in parallel.</li>\n</ul>\n<blockquote>\n<p>We recommend batching as large as your available memory and CPU allow, considering factors like concurrent clients and overall system load. Optimizing batch sizes can significantly improve ingestion speed, but balancing resource constraints is key to maintaining stable performance.</p>\n</blockquote>\n<p>Now that we’ve explored and demonstrated the performance and efficiency of common ClickHouse input formats, let’s examine how ClickHouse clients optimize inserts by default—likely more than you might expect.</p>\n<h2 id=\"clickhouse-client-defaults\"></h2>\n<p>The ClickHouse command-line client and language-specific clients automatically select an efficient input format (e.g. Native) based on their typical use cases and the interface in use. The next two sections explore the two interfaces in detail.</p>\n<h3 id=\"native-interface\"></h3>\n<p>To sketch the native interface’s capabilities, we use <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/cli\">clickhouse-client</a>, the most advanced client leveraging the full potential of the native interface.</p>\n<p>This diagram shows the ingest processing when using the clickhouse-client for sending the data to a ClickHouse server:</p>\n<p><span><img alt=\"Blog-Formats.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_001_a0d69d766b.png&w=2048&q=75\"></span></p>\n<p>The clickhouse-client exclusively uses the <a target=\"_blank\" href=\"https://clickhouse.com/docs/interfaces/tcp\">native interface</a>, adhering to the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-input-format-matchup-which-is-fastest-most-efficient#client-side-tuning-options-for-inserts\">core principle</a>  of offloading work to the client to maximize server efficiency. Instead of sending raw data (e.g. TSV or JSON), it ① first parses  and ③ converts input to the efficient Native format, ensuring <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-input-format-matchup-which-is-fastest-most-efficient#insert-performance-of-common-input-formats\">optimal compression</a> for network transport and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-input-format-matchup-which-is-fastest-most-efficient#insert-performance-of-common-input-formats\">minimal</a> server-side processing.</p>\n<p>Since the Native format and MergeTree tables <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-input-format-matchup-which-is-fastest-most-efficient#clickhouse-input-formats\">share</a> the same true columnar structure, ingestion is streamlined via a simple 1:1 copy, minimizing transformation overhead at server-side step ⑧. Native is the only format supported by the native interface.</p>\n<p>Additionally, the native interface supports block-wise compression and decompression—clickhouse-client ④ always compresses with <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#network_compression_method\">either</a> LZ4 (default) or ZSTD  and ⑤ streams data blocks, optimizing transmission efficiency.</p>\n<h3 id=\"client-side-materialized-and-default-value-computations\"></h3>\n<p>The automatic conversion of input data to Native format in any case applied by clickhouse-client required additional engineering effort and is only possible thanks to the native interface’s advanced communication mechanisms with the server.</p>\n<p>Consider a scenario where data is inserted into a table on the server created with the following DDL statement:</p>\n<div><pre><code><span><span>CREATE TABLE</span> test </span>\n<span>(</span>\n<span>  data JSON,</span>\n<span>  c String MATERIALIZED data.b.c</span>\n<span>) </span>\n<span><span>ORDER</span> <span>BY</span>();</span></code></pre></div>\n<!-- -->\n<p>To construct the data block in MergeTree table format in step ⑧, the ClickHouse server would need access to the original JSON input. This is necessary to compute the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/create/table#materialized\">MATERIALIZED</a> values for column c, which depend on extracting values from the nested path <code>b.c</code> in the JSON data.</p>\n<p>To solve this, the clickhouse-client uses the native interface to retrieve the target table’s DDL statement from the server, and then offloads the MATERIALZED (or <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/create/table#default\">DEFAULT</a>) value computation from server-side step ➇ to the client-side step ②. It also uses the native interface to instruct the server to skip computing these values, enabling the use of the more efficient Native format instead of JSON. By computing materialized and default values locally, the client sends fully prepared data in the most efficient format:</p>\n<p><span><img alt=\"Blog-Formats.010.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_010_437b47d697.png&w=2048&q=75\"></span></p>\n<p>Note that, currently, only clickhouse-client implements client-side computation of MATERIALIZED and DEFAULT values to always use the Native format.</p>\n<blockquote>\n<p>The ClickHouse server is engineered for high efficiency and speed, and clickhouse-client follows the same principle. The native interface enables advanced techniques to optimize inserts, ensuring efficient transport and minimal server-side processing.</p>\n</blockquote>\n<h3 id=\"http-interface\"></h3>\n<p>We illustrate the HTTP interface by using <a target=\"_blank\" href=\"https://curl.se/\">curl</a> as the client:</p>\n<p><span><img alt=\"Blog-Formats.011.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Formats_011_07446330be.png&w=2048&q=75\"></span></p>\n<p>Unlike the native interface, the <a target=\"_blank\" href=\"https://clickhouse.com/docs/interfaces/http\">HTTP interface</a> supports sending data in any of the supported input formats, not just Native.</p>\n<p>For that the HTTP interface supports the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/insert-into\">FORMAT</a> clause but not the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/insert-into\">COMPRESSION</a> type clause and also does not automatically detect compression. To enable compression for HTTP inserts, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/http#compression\">HTTP compression</a> must be used with the <a target=\"_blank\" href=\"https://github.com/ClickHouse/FastFormats/blob/13fe23acc64d37e720f7d1f42c1651574b8d6e0c/ingest.sh#L64\">Content-Encoding header</a>. The entire data batch is compressed before transmission.</p>\n<p>Note that while the HTTP interface also supports sending data in the Native format, it lacks the advanced communication mechanisms needed for clients to handle MATERIALIZED and DEFAULT values when the target table’s DDL depends on a specific format like JSON. Unlike the native interface, which allows retrieval of the table’s DDL and instructs the server to skip computing these values, the HTTP interface does not support such interactions. As a result, clients using HTTP cannot always automatically convert input data to the Native format.</p>\n<blockquote>\n<p>The HTTP interface provides greater flexibility than the native interface for selecting input formats sent to the server. It also supports additional compression options beyond LZ4 and ZSTD.</p>\n</blockquote>\n<h3 id=\"support-matrix\"></h3>\n<p>In the previous sections, we used <code>clickhouse-client</code> to illustrate the native interface and <code>curl</code> for the HTTP interface. This must be implemented manually, which is potentially less efficient than the server-side sorting process.</p>\n<blockquote>\n<p>Client capabilities vary based on the typical workload patterns of applications. Languages like C++ and Go are commonly used for high-throughput inserts, whereas languages like JavaScript are more often used for query-heavy applications. This distinction is reflected in the feature set of each language-specific client.</p>\n</blockquote>\n<h2 id=\"summary\"></h2>\n<p>This post examined ClickHouse’s input formats to identify the most efficient option for server-side ingestion.</p>\n<p>A key principle for optimizing inserts sent by clients is <strong>offloading work to the client to reduce server-side processing</strong>. The most impactful factor is <strong>selecting an efficient input format</strong>. Based on <a target=\"_blank\" href=\"https://fastformats.clickhouse.com/\">FastFormats</a>, our benchmark comparing ingestion speed and resource efficiency across all supported formats, we found that:</p>\n<ul>\n<li><strong>Native is the most efficient format</strong> across all tested scenarios, offering the best compression, low resource usage, and minimal server-side processing overhead.</li>\n<li><strong>Compression is essential</strong>. However, ClickHouse sorts data efficiently, often faster than the client. Pre-sorting is beneficial if data is already nearly ordered and client-side resources allow it.</li>\n<li><strong>Batching significantly improves efficiency</strong>. We recommend batching as large as memory and CPU allow, as larger batches reduce insert overhead and improve throughput.</li>\n</ul>\n<p>ClickHouse clients optimize efficiency by selecting formats suited to their typical use cases, with those designed for high-throughput inserts automatically choosing Native.</p></div></article>"
