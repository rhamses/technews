contentHtml: "<div><h2 id=\"introduction\"></h2>\n<p>Many organizations have standardized on data lakes built on open table formats like Apache Iceberg and Delta Lake. As the cost of cloud storage dropped and the pain of vendor lock-in grew, open formats gave teams a way to store data once and query it from anywhere. The benefit is that data stays open, portable, and queryable by multiple engines, giving organizations the freedom to choose the tools that best fit their stack. But that flexibility comes at a cost for real-time analytics.</p>\n<p>Teams hit a wall because lake formats were designed for open storage and interoperability, not for speed. Without the specialized indexes, caching, and tight query engine optimizations required for real-time workloads, queries in data lakes quickly become slow and expensive at scale.</p>\n<p>Today, we're announcing that ClickHouse is <a target=\"_blank\" href=\"https://clickhouse.com/clickhouse-for-data-lakes\">data lake ready</a>. You can query your data in place, pointing ClickHouse directly at your Iceberg and Delta Lake files or through any number of vendor or open-source catalogs. You can accelerate your analytics by loading data into ClickHouse's native storage engine for sub-second, high-concurrency queries. And you can write results back to open formats, keeping your entire ecosystem interoperable.</p>\n<p><span><img alt=\"writes.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fwrites_a12d9106db.png&w=2048&q=75\"></span></p>\n<h2 id=\"the-road-to-data-lake-ready\"></h2>\n<p>Two years of engineering went into making this possible. Here's how we got here.</p>\n<p>To be truly data lake ready, a query engine needs to do three things well: process Parquet files quickly, work with open table formats like Iceberg and Delta Lake, and integrate with the catalogs that sit on top. Here's how we've built out each of these capabilities over the past two years.</p>\n<p>We started by shipping initial support for the Apache Iceberg format (<a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-23-02#iceberg-right-ahead---support-for-apache-iceberg-ucasfl\">23.3</a>), allowing the data to be read natively on object storage and giving users their first way to use <strong>ClickHouse as a query engine for lake data</strong>. We followed that with Parallel Replicas (<a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-08\">25.8</a>), enabling query execution to be distributed across multiple nodes for lake-scale workloads.</p>\n<p>From there, we invested heavily in <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-and-parquet-a-foundation-for-fast-lakehouse-analytics\">Parquet</a>, the foundational file format underneath Iceberg and Delta Lake tables. We added row group skipping using Parquet metadata <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-23-08\">(23.8)</a>, enabled fast counts, and allowed file name metadata to be used in filters to avoid unnecessary file reads. In (<a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-23-07#parquet-writing-improvements-michael-kolupaev\">23.7</a>)we improved Parquet write performance. On the storage side, we extended support to Azure Blob Storage (<a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-23-05\">23.5</a>), so ClickHouse wasn't limited to S3 and GCS.</p>\n<p>In <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-24-12\">24.12</a>, we introduced our first catalog support with Unity Catalog, along with schema evolution. Users could now query Iceberg data from a catalog managed by an external service, with ClickHouse automatically detecting when columns were added, removed, renamed, or their types changed. The Polaris catalog was supported as well.</p>\n<p>We also put significant effort in integrating the Delta Rust Kernel into ClickHouse, replacing our original Delta Lake reader. Rather than reinventing the wheel, we built on the community's open-source kernel, and in doing so unlocked Delta Lake reads, writes, changed data feed support, schema evolution, time travel, partition pruning, and statistic-based pruning.</p>\n<p>Catalog support kept expanding in <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-03\">25.3</a> where we added AWS Glue and Delta Lake support for the Unity Catalog. Since then we've added support for Microsoft OneLake, Iceberg REST Catalog, and AWS Glue, providing a truly catalog-agnostic solution, letting users decide how they wish to manage their tables. In <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-04\">25.4</a>, we added time travel for Iceberg, letting users query previous snapshots of their data. This is especially important for data warehouse-style workloads where auditability and point-in-time queries matter. In <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-06\">25.6</a>, we shipped JSON in Parquet support and deeper Iceberg history introspection, giving users more visibility into how their tables evolve over time.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-08\">25.8</a> was one of the most significant releases for our data lake evolution. A new native Parquet reader brought page-level parallelism and removed the extra Arrow layer, reading Parquet files directly into ClickHouse's in-memory format. The result? <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-08#parquet-reader-performance\">1.8x faster reads</a> on average across ClickBench and blazing fast performance.</p>\n<p><span><img alt=\"benchmark.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fbenchmark_f10303f9c7.png&w=2048&q=75\"></span></p>\n<p>We also added full support for insert, delete, update, and alter schema operations on Iceberg tables, enabling interactive DML without importing data into ClickHouse. Investments continued in our support for underlying object storage, with significant performance improvements for Azure Blob Storage.</p>\n<p>In <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-09#data-lake-improvements\">(25.9)</a>, we focused on stability across Iceberg, Delta Lake, and cloud storage integrations, with improvements to schema resolution and metadata consistency.</p>\n<p>And we're not done. Later this year, we'll ship even more catalog support and continue investing in performance and interoperability. Lots of exciting developments ahead!</p>\n<p>So what does all of this engineering work add up to?</p>\n<h2 id=\"three-ways-to-use-clickhouse-with-your-data-lake\"></h2>\n<p><span><img alt=\"3ways.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F3ways_72f6222a5b.png&w=2048&q=75\"></span></p>\n<p>Your data lake now gets the full power of ClickHouse. Same SQL, same experience, no matter which catalog or cloud you’re on. But when you need sub-second response times at high concurrency, reading files over the network becomes a bottleneck. That’s when you load your data into MergeTree, ClickHouse’s native storage engine. It applies indexing, compression, and smart data skipping. The same query that took seconds scanning files on S3 now runs orders of magnitude faster.</p>\n<p>Think about what that unlocks. Say you’re building a customer-facing analytics dashboard. Your users expect sub-second response times, and you’ve got hundreds of them querying concurrently. Querying files directly on object storage for every query isn’t going to cut it. Milliseconds of latency matter.</p>\n<p>Once the data is stored in MergeTree, ClickHouse can apply a range of optimizations designed specifically for analytical workloads. <a target=\"_blank\" href=\"https://clickhouse.com/docs/primary-indexes\">Sparse primary indexes</a> ensure only the relevant data granules are read instead of scanning entire datasets. <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/caches\">Multiple layers of caching</a>, including query result caching, predicate-level caching, local SSD caching, and <a target=\"_blank\" href=\"https://clickhouse.com/blog/building-a-distributed-cache-for-s3\">distributed caches</a>, further reduce the amount of data that needs to be read from storage.</p>\n<p>Just as importantly, the data format and query engine are designed together. MergeTree supports rich data types, including <a target=\"_blank\" href=\"https://clickhouse.com/blog/json-data-type-gets-even-better\">efficient JSON handling</a>, and enables engine-level optimizations that simply aren’t possible when querying open files directly. The result is the difference between offering analytics and delivering real-time, sub-second analytics at scale.</p>\n<p>Let's have a look at what the acceleration workflow with BigLake looks like.
