Optimization passes can be configured, and you can also vary optimization level based on your specific use cases. For example, you can first compile your code without optimizations and later recompile it with optimizations.</li>\n<li>Dynamic Linker that is used to resolve <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Relocation_(computing)\">relocations</a>, allocate necessary code and data sections, and prepare compiled object files for execution.</li>\n<li>LLVM IR (LLVM intermediate language representation).</li>\n<li>A lot of LLVM toolings like IR and assembly printers. Special JIT tooling to support GDB and perf. MCJIT, ORCJIT JIT compilers. In ClickHouse, we do not use them, but you can check out their implementation to understand how things work inside them.</li>\n</ul>\n<p>LLVM IR is an intermediate language representation used in LLVM.</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Static_single-assignment_form\">Static Single Assignment</a>. Each variable is assigned only once.</li>\n<li>Strongly typed. Compilation will fail during the IR verification stage, if you do not get the types right.</li>\n<li>Allows to map high-level constructions into low-level representation. LLVM IR has support for modules, functions, and structures.</li>\n</ul>\n<p>Let’s see how it looks like:</p>\n<div><pre><code><span><span><span>int64_t</span> <span>sum</span><span>(<span>int64_t</span> value_1, <span>int64_t</span> value_2)</span></span></span>\n<span><span></span>{</span>\n<span>    <span>return</span> value_1 + value_2;</span>\n<span>}</span></code></pre></div>\n<div><pre><code><span>/usr/bin/clang++-12 -S -emit-llvm jit_example.cpp</span>\n<span></span>\n<span>; Function Attrs: noinline nounwind optnone uwtable mustprogress</span>\n<span>define dso_local i64 @_Z3sumll(i64 %0, i64 %1) <span>#0 {</span></span>\n<span>  %3 = alloca i64, align 8 /// alloca - allocate memory on stack</span>\n<span>  %4 = alloca i64, align 8</span>\n<span>  store i64 %0, i64* %3, align 8 /// store - store value <span>in</span> pointer</span>\n<span>  store i64 %1, i64* %4, align 8</span>\n<span>  %5 = load i64, i64* %3, align 8 /// load - load value from pointer</span>\n<span>  %6 = load i64, i64* %4, align 8</span>\n<span>  %7 = add nsw i64 %5, %6 /// nsw - No Signed Wrap</span>\n<span>  ret i64 %7</span>\n<span>}</span></code></pre></div>\n<p>We will not use a lot of LLVM IR later in this post, but I highly encourage you to check the LLVM IR documentation.</p>\n<p>Now let’s take a look at LLVM high-level components.</p>\n<ul>\n<li>TargetMachine - machine target specific information. Allowed CPU instructions, data layout, etc.</li>\n<li>LLVMContext - context for LLVM global data.</li>\n<li>IRBuilder - builder for LLVM IR.</li>\n<li>Value - base class for all computed values (local variables, global variables, function arguments, constants).</li>\n<li>Function - function container for BasicBlocks.</li>\n<li>BasicBlock - container for LLVM IR instructions executed sequentially until termination instruction (return, jump).</li>\n<li>Module - container for IR objects, including functions and global variables. It also stores information about target characteristics.</li>\n<li>PassManager - module pass manager.</li>\n<li>FunctionPassManager - function pass manager.</li>\n<li>PassManagerBuilder - builder for module and function optimization passes, used to populate PassManager and FunctionPassManager.</li>\n<li>ObjectFile - object file.</li>\n<li>RuntimeDyld - dynamic linker, takes object file and starts a dynamic linking process, allocates and fills code and data sections, resolves <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Relocation_(computing)\">relocations</a>.</li>\n<li>RTDyldMemoryManager - dynamic linker memory manager. Allocates necessary code and data sections during linking. Owner of memory allocated during linkage.</li>\n<li>JITSymbolResolver - resolve external symbols during dynamic linking.</li>\n</ul>\n<p>Strategy for JIT code compilation using LLVM high-level components:</p>\n<ol>\n<li>Create a Module and fill it with Functions. Apply optimizations using PassManagerBuilder, FunctionPassManager, and PassManager.</li>\n<li>Setup passes in PassManager to emit an ObjectFile from Module using TargetMachine.</li>\n<li>Create JITSymbolResolver for resolving external symbols, for example <code>memset</code>.</li>\n<li>Create RTDyldMemoryManager for the RuntimeDyld dynamic linker.</li>\n<li>Resolve <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Relocation_(computing)\">relocations</a> and create necessary code and data sections for ObjectFile using RuntimeDyld dynamic linker.</li>\n<li>Get function symbols pointers from compiled code using RuntimeDyld dynamic linker.</li>\n</ol>\n<p>Our wrapper interface around JIT compilation looks like this:</p>\n<div><pre><code><span><span>class</span> <span>CHJIT</span></span>\n<span>{</span>\n<span>    <span>struct</span> <span>CompiledModule</span></span>\n<span>    {</span>\n<span>        <span>/// Size of compiled module code in bytes</span></span>\n<span>        <span>size_t</span> size;</span>\n<span></span>\n<span>        <span>/// Module identifier. It has column-oriented storage and a vectorized query execution engine.</p>\n<p>In column-oriented storage, data is physically stored by columns.</p>\n<ul>\n<li>Only necessary columns are read from the disk during the query.</li>\n<li>Better compression because similar data lies nearly.</li>\n</ul>\n<p>Both factors significantly reduce the amount of IO during query execution.</p>\n<p>Vectorized query execution engine process data in blocks. Block contains multiple columns with max_block_size rows (65505 by default).
