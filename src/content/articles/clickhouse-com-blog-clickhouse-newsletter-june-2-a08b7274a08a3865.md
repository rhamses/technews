It consists of a soft and a hard limit, allowing queries to burst beyond the soft limit when possible, making it easier to run very different queries on the same ClickHouse instance. In 22.5, memory overcommit is <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/35921\">turned on by default</a> and the old <code>max_memory_usage</code> setting has been removed from the default settings.</li>\n<li><strong><a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/36415\">Parallel hash joins</a></strong> A new join type splits a join into multiple blocks and executes them in parallel. Try it with your join queries by setting <code>join_algorithm = 'parallel_hash'</code>.</li>\n<li><strong><a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/33631\">Grouping sets</a></strong> GROUP BY has a new modifier <code>GROUPING SETS</code> which allows you to specify aggregating by any columns. We’ll leave it up to you to find out what it is. Don’t use it in production.</li>\n</ol>\n<p>Take a  look at the <a target=\"_blank\" href=\"https://presentations.clickhouse.com/release_22.5/\">release webinar slides</a>, the <a target=\"_blank\" href=\"https://youtu.be/jkXmXrmjaKQ?t=469\">recording</a> and please upgrade (unless you want to stay on an LTS release).</p>\n<h2 id=\"query-of-the-month-materialized-but-still-real-time\"></h2>\n<p>ClickHouse is often used to store high frequency time series data. For example, financial tick data (prices of stocks, bonds, crypto, etc.) or sensor data.</p>\n<p>One of the characteristics of this kind of data is that to get a complete and accurate picture it is often necessary to look potentially far back. For example, not every tick record for a stock is going to have all information needed to display a real-time summary of a stock on a financial website or mobile app – usually that’s at least the current price as well as most recent open, low/high, 52-week low/high price and the volume. This is for a variety of reasons, but mostly it’s because much of this data does not change – the open price is the same throughout the day, so there is no reason to include it in every record.</p>\n<p>Similarly, an IoT device or sensor might report a variety of metrics, e.g. several temperature values in different places, pressure, voltage, flow rate and/or many other things. This data can often be incomplete at a given point in time – data arrives late, devices go temporarily or permanently offline, not all information is measured all of the time, etc.</p>\n<p>To still be able to get an accurate picture of the data using ClickHouse it is often necessary to employ “point-in-time queries” that start at a given timestamp – this could be the current time, or at some meaningful point in the past. A common way to write queries in ClickHouse that will find the most recent values for different metrics stored as separate columns is to use the <code>argMax(arg, val)</code> function. For a given column <code>val</code> it will find the maximum value and return the corresponding <code>arg</code> column. With a time series dataset this would be something like <code>argMax(temp, timestamp)</code> finding the most recent temperature reading.</p>\n<p>Because frequent queries like threshold alert triggers might not just be looking at a single column, queries will often end up looking something like this:</p>\n<div><pre><code><span><span>SELECT</span> device_id, <span>timestamp</span>,</span>\n<span>\targMax(temp1, <span>timestamp</span>),</span>\n<span>\targMax(pressure, <span>timestamp</span>),</span>\n<span>\targMax(flowRate, <span>timestamp</span>)</span>\n<span><span>FROM</span> readings</span>\n<span><span>WHERE</span> device_id <span>IN</span> (<span>&lt;</span>list_of_devices<span>&gt;</span>)</span>\n<span><span>GROUP</span> <span>BY</span> device_id</span></code></pre></div>\n<p>Turns out, this is a very expensive query! For every <code>device_id</code> and <code>argMax</code> function, ClickHouse needs to scan all records until it finds the most recent value.</p>\n<p>A common way to speed up this kind of query is to use a materialized view, pre-aggregating the most recent values for all devices for a given time period. However, this only works well if all metrics are known beforehand (no new columns are ever added) and it will reduce the granularity of the data no longer allowing accurate point-in-time queries for an arbitrary timestamp. Instead, you can combine the two and achieve both the performance improvement of a materialized view and the flexibility of querying raw data. The approach is to generate a materialized view and use it to query all historical data, but combine it with the real-time data up to the most recent requested timestamp.</p>\n<p>Start by creating a summary table that the materialized view will write 15-minute summaries of the data to (or any other interval that makes sense, e.g. 5 minutes or 1 hour):</p>\n<div><pre><code><span>CREATE TABLE readings_15min</span>\n<span>\tdevice_id <span>LowCardinality</span><span>(String)</span>,</span>\n<span>\ttimestamp_start DateTime64,</span>\n<span>\ttemp <span>AggregateFunction</span><span>(argMax, Nullable(Float64)</span>, DateTime64),</span>\n<span>\tpressure <span>AggregateFunction</span><span>(argMax, Nullable(Float64)</span>, DateTime64),</span>\n<span>\tflowRate <span>AggregateFunction</span><span>(argMax, Nullable(Float64)</span>, DateTime64)</span>\n<span>ENGINE = AggregatingMergeTree</span>\n<span>ORDER <span>BY</span> <span>(timestamp_start, device_id)</span></span></code></pre></div>\n<p>Create the materialized view:</p>\n<div><pre><code><span><span>CREATE</span> MATERIALIZED <span>VIEW</span> readings_mv <span>TO</span> readings_15min </span>\n<span><span>AS</span> <span>SELECT</span> toStartOfFifteenMinutes(<span>timestamp</span>) <span>AS</span> timestamp_start,</span>\n<span>\tdevice_id,</span>\n<span>\targMaxState(temp, <span>timestamp</span>) <span>AS</span> temp,</span>\n<span>\targMaxState(pressure, <span>timestamp</span>) <span>AS</span> pressure,</span>\n<span>\targMaxState(flowRate, <span>timestamp</span>) <span>AS</span> flowRate</span>\n<span><span>FROM</span> readings</span>\n<span><span>GROUP</span> <span>BY</span> device_id, toStartOfFifteenMinutes(<span>timestamp</span>)</span></code></pre></div>\n<p>When querying, combine data from both the materialized view and the most recent data from the raw data, combining the results in a final aggregation to get the correct result:</p>\n<div><pre><code><span><span>WITH</span> <span>'2022-06-06 15:02:00'</span>::DateTime64 <span>as</span> point_in_time</span>\n<span><span>SELECT</span></span>\n<span>\tdevice_id,</span>\n<span>\targMax(temp, timestamp_outer) <span>as</span> temp,</span>\n<span>\targMax(pressure, timestamp_outer) <span>as</span> pressure,</span>\n<span>\targMax(flowRate, timestamp_outer) <span>as</span> flowRate</span>\n<span><span>FROM</span></span>\n<span>\t(<span>SELECT</span> <span>max</span>(timestamp_start) <span>as</span> timestamp_outer,</span>\n<span>       device_id,</span>\n<span>       argMaxMerge(temp) <span>as</span> temp,</span>\n<span>       argMaxMerge(pressure) <span>as</span> pressure,</span>\n<span>       argMaxMerge(flowRate) <span>as</span> flowRate</span>\n<span>\t<span>FROM</span> readings_15min </span>\n<span>\t<span>WHERE</span> timestamp_start <span>&lt;=</span> toStartOfFifteenMinute(point_in_time)</span>\n<span>\t<span>GROUP</span> <span>BY</span> device_id</span>\n<span>\t<span>UNION</span> <span>ALL</span></span>\n<span>\t<span>SELECT</span> <span>max</span>(<span>timestamp</span>) <span>as</span> timestamp_outer,</span>\n<span>\t\tdevice_id</span>\n<span>\t\targMax(temp, <span>timestamp</span>) <span>as</span> temp,</span>\n<span>\t\targMax(pressure, <span>timestamp</span>) <span>as</span> pressure,</span>\n<span>\t\targMax(flowRate, <span>timestamp</span>) <span>as</span> flowRate</span>\n<span>\t<span>FROM</span> readings</span>\n<span>\t<span>WHERE</span> <span>timestamp</span> <span>BETWEEN</span> toStartOfFifteenMinute(point_in_time) <span>AND</span> point_in_time</span>\n<span>\t<span>GROUP</span> <span>BY</span> device_id)</span>\n<span><span>GROUP</span> <span>BY</span> device_id</span></code></pre></div>\n<p>Notice the <code>UNION ALL</code> clause combining values from the two tables and the complementing <code>WHERE</code> conditions.</p>\n<p>In a recent test on a dataset of over 200 million rows this approach
