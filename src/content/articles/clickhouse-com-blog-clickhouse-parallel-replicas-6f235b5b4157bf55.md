Sub-second aggregation of 100B rows at TB/s throughput.</p>\n<p>So, how does ClickHouse do this? Let’s unpack what happens under the hood, starting with how ClickHouse makes GROUP BY so fast on a single node.</p>\n<h2 id=\"how-clickhouse-makes-group-by-fast\"></h2>\n<p>ClickHouse is fast because it parallelizes each query across all CPU cores, using <strong>parallel streams</strong> (<em>think highway lanes</em>) in the <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/developer/understanding-query-execution-with-the-analyzer#query-pipeline\">query pipeline</a> (physical query plan) to build <strong>partial aggregation states</strong>.</p>\n<h3 id=\"columnar-storage-sets-the-stage\"></h3>\n<p>ClickHouse uses <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">columnar storage</a>: queries read only the referenced columns, scan fewer bytes due to high per-column compression, and execute vectorized (SIMD) operations on contiguous data. The result is low I/O and high arithmetic intensity, the perfect setup for running one parallel query pipeline stream per CPU core.</p>\n<h3 id=\"one-stream-per-core\"></h3>\n<p>ClickHouse runs one <strong>parallel query pipeline stream per CPU core</strong>. Each stream scans rows, applies filters, and builds partial aggregate states in parallel.</p>\n<p>Here’s what happens inside the query engine:</p>\n<p><span><img alt=\"Parallel Replicas-animation-01.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FParallel_Replicas_animation_01_5c34c23bfa.gif&w=2048&q=75\"></span></p>\n<p><strong>① Many part ranges at once</strong></p>\n<p>ClickHouse simultaneously scans data from multiple <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">data part</a> ranges (consecutive row blocks selected by<a target=\"_blank\" href=\"https://clickhouse.com/docs/primary-indexes\"> index analysis</a>) into different streams.</p>\n<p><strong>② Parallel filtering + aggregation</strong></p>\n<p>Each stream works on its own (non-overlapping) ranges, filtering rows and updating partial states using <a target=\"_blank\" href=\"https://clickhouse.com/blog/cpu-dispatch-in-clickhouse\">vectorized execution</a> (SIMD).</p>\n<p><strong>③ Merge the partial states</strong></p>\n<p>Partial states from all streams are combined into the final result. This merge step generally <strong>runs in parallel across multiple merge threads</strong>. There are, however, specialized GROUP BY variants where this was not always the case; <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-11#parallel-merge-for-small-group-by\">we continue to extend these implementations to support fully parallelized merges</a>.</p>\n<p><em>(Separately, if the query computes <strong>multiple aggregates</strong>, such as COUNT, SUM, or MAX, each aggregate maintains its own partial states, and their <strong>merges run in parallel with each other</strong>.)</em></p>\n<p><strong>④ Sort + limit</strong></p>\n<p>The merged results are ordered, and the query’s LIMIT clause is applied (if present).</p>\n<p><strong>⑤ Return the answer</strong></p>\n<p>The final result is sent back to the client.</p>\n<p>This design works because pipeline streams don’t compute final values directly. They build <strong>mergeable partial states</strong> that combine into one correct result later.</p>\n<h3 id=\"why-partial-states-matter\"></h3>\n<blockquote>\n<p>Partial states make parallelism possible.</p>\n</blockquote>\n<p><em>Without them</em>, GROUP BY couldn’t be split efficiently across cores or across nodes later. Every core (or node) would need to see all rows for a specific group. <em>With them</em>, any core (or node) can process any subset of rows independently and emit mergeable states that combine into one correct result.</p>\n<p>This flexibility enables:</p>\n<ul>\n<li>\n<p><strong>Efficient and straightforward pipeline stream scheduling</strong>: Streams don’t need data pre-partitioned by key; they can scan arbitrary ranges.</p>\n</li>\n<li>\n<p><strong>Dynamic load balancing</strong>: If one stream hits skewed data, <a target=\"_blank\" href=\"https://clickhouse.com/docs/academic_overview#4-2-multi-core-parallelization\">rows can be rerouted</a> to others, keeping overall throughput high; all that matters is producing mergeable states.</p>\n</li>\n</ul>\n<p>ClickHouse parallelizes all <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query=U0VMRUNUICogCkZST00gc3lzdGVtLmZ1bmN0aW9ucwpXSEVSRSBpc19hZ2dyZWdhdGUKQU5EIGVtcHR5KGFsaWFzX3RvKQpPUkRFUiBCWSBuYW1l&chart=eyJ0eXBlIjoibGluZSIsImNvbmZpZyI6eyJ4YXhpcyI6InllYXIiLCJ5YXhpcyI6Ijk5dGhfYXZnX3RlbXAiLCJzZXJpZXMiOiJjb3VudHJ5IiwidGl0bGUiOiJUZW1wZXJhdHVyZSBieSBjb3VudHJ5IGFuZCB5ZWFyIn19&run_query=true&tab=results\">170+ aggregate functions</a> (and their <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=7ApwD0cfAFI\">combinators</a>) across cores and, as we’ll show, across nodes.</p>\n<p>Now let’s zoom in even further, into the internals of the query pipeline’s aggregation stage.</p>\n<h3 id=\"inside-the-group-by-execution-pipeline\"></h3>\n<p>GROUP BY queries are processed independently by each pipeline stream using a <em>hash aggregation algorithm</em>: each stream maintains an in-memory hash table where each key (e.g., town) points to a partial aggregation state.</p>\n<blockquote>\n<p><strong>The hash tables behind GROUP BY</strong><br>ClickHouse doesn’t use <em>one</em> hash table, but<a target=\"_blank\" href=\"https://clickhouse.com/blog/hash-tables-in-clickhouse-and-zero-cost-abstractions\"> 30+ specialized variants</a>, automatically chosen by grouping key type, cardinality, workload, and other factors.<br><br>As Andy Pavlo (CMU)<a target=\"_blank\" href=\"https://www.youtube.com/watch?v=Vy2t_wZx4Is&t=3579s\"> put</a> it: “ClickHouse is a freak system — you guys have 30 versions of a hash table!” That obsession with low-level detail is why GROUP BY runs so fast.</p>\n</blockquote>\n<p>The animation below shows this in action on a query averaging price per town, then sorting to return the top town:</p>\n<p><span><img alt=\"Parallel Replicas-animation-02.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FParallel_Replicas_animation_02_7c5d14f827.gif&w=2048&q=75\"></span></p>\n<p><strong>① Each stream builds its own hash table</strong></p>\n<ul>\n<li>\n<p><strong>Stream 1</strong>: London → (sum=500k, count=2); Oxford → (sum=600k, count=1)</p>\n</li>\n<li>\n<p><strong>Stream 2</strong>: Oxford → (sum=400k, count=1); London → (sum=400k, count=1)</p>\n</li>\n</ul>\n<p><em>(In reality, all streams run in parallel;  the animation shows them sequentially for clarity. We also simplified the hash tables: in practice, they store pointers into a shared memory arena where the aggregation states are allocated and updated.)</em></p>\n<p><strong>② Partial results are merged</strong></p>\n<p>The sums and counts combine into global results:</p>\n<ul>\n<li>\n<p><strong>Oxford</strong>: (600k+400k) / (1+1) = <strong>500k</strong></p>\n</li>\n<li>\n<p><strong>London</strong>: (500k+400k) / (2+1) = <strong>300k</strong></p>\n</li>\n</ul>\n<blockquote>\n<p><strong>Why not just average the averages?</strong><br>If stream 1 had 250k for London and stream 2 had 400k for London, a naïve average gives 325k, which is wrong. By merging sums + counts, ClickHouse gets the correct 300k for London.</p>\n</blockquote>\n<p><strong>③ Sorted + limited</strong></p>\n<p>The merged groups are sorted, LIMIT applied, and the final result returned.</p>\n<h3 id=\"elegant-parallelism\"></h3>\n<p>In short, partial states enable both <strong>independence</strong> and <strong>correctness</strong>:</p>\n<ul>\n<li>\n<p>Independence, because any query pipeline stream can aggregate any rows.</p>\n</li>\n<li>\n<p>Correctness, because merge produces the right final result every time.</p>\n</li>\n</ul>\n<p>It’s a beautifully simple idea: parallelism without compromise. That’s the essence of ClickHouse GROUP BY.</p>\n<h3 id=\"memory-for-group-by-partial-states\"></h3>\n<p>The <strong>cardinality of grouping keys</strong> (e.g., number of towns) drives peak memory usage: more distinct values → more hash table entries per query pipeline stream.</p>\n<p>ClickHouse offers optimizations:</p>\n<ul>\n<li>\n<p>If grouping keys form a <strong>prefix of the table’s sorting key</strong>, rows can be scanned and <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/select/group-by#group-by-optimization-depending-on-table-sorting-key\">aggregated in order</a>. Each stream then processes rows for a small set of groups at a time, and once a group is complete, its result is flushed forward in the pipeline. This keeps memory use low, but limits parallelism, so it’s off by default.</p>\n</li>\n<li>\n<p>If memory runs out, <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/select/group-by#group-by-in-external-memory\">ClickHouse spills partial states to disk</a>.</p>\n</li>\n</ul>\n<p>Memory usage also depends on the chosen <strong>aggregation functions</strong>:</p>\n<ul>\n<li>\n<p><strong>Tiny partial states</strong> → <code>sum</code>, <code>count</code>, <code>min</code>, <code>max</code>, <code>avg</code> (just one or two numbers)</p>\n</li>\n<li>\n<p><strong>Medium partial states</strong> → <code>groupArray</code> (bounded arrays)</p>\n</li>\n<li>\n<p><strong>Large partial states</strong> → <code>uniqExact</code> (stores either the raw distinct values or their hashes, depending on type; merged by union)</p>\n</li>\n</ul>\n<p>These differences affect both <strong>memory footprint</strong> and <strong>scalability across nodes</strong>, a theme we’ll revisit later.</p>\n<p>All of these optimizations stack together, so that GROUP BY performance scales with cores and with nodes. Let’s measure it.</p>\n<h2 id=\"how-we-measured\"></h2>\n<p>To keep the results clear and reproducible, here’s the setup we used for all benchmarks. We ran ClickHouse Cloud services of different sizes, from a single node to multi-node clusters with parallel replicas. Each test used the same datasets and queries so that scaling effects could be isolated and compared fairly.</p>\n<p>All benchmarks are <strong>fully reproducible</strong>. The code lives in a<a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/ParallelReplicasBench\"> public GitHub repository</a> and runs against any dataset/query set. The framework supports <strong>vertical scaling</strong> (more cores per node) and <strong>horizontal scaling</strong> (more nodes) and includes a generator for large-scale UK property prices datasets.</p>\n<p>The generator <strong>replicates existing rows</strong>. That may sound artificial, but our test query’s <strong>GROUP BY keys (county, town, district) stay the same</strong>, so results scale as they would naturally (Oxford doesn’t become a new town when more houses sell there).</p>\n<p>We used:</p>\n<ul>\n<li>\n<p>A <strong>ClickHouse Cloud service</strong> running ClickHouse <strong>v25.6</strong> with a <strong>varying number of compute nodes</strong> in <strong>AWS us-east-2</strong></p>\n</li>\n<li>\n<p>A dedicated <strong>EC2 m6i.8xlarge</strong> (32 vCPUs, 128 GB RAM, same region) instance to drive benchmarks via <code>clickhouse-client</code></p>\n</li>\n</ul>\n<p>Each configuration ran every query 10 times. We track:</p>\n<ul>\n<li>\n<p><strong>cold</strong> — first run (caches disabled)</p>\n</li>\n<li>\n<p><strong>hot</strong> — fastest warm run</p>\n</li>\n<li>\n<p><strong>hot_avg</strong> — average of warm runs</p>\n</li>\n</ul>\n<p>For clarity, we show only <strong>hot results</strong> here; the repo has the <strong>full dataset</strong> (cold, hot, hot_avg) plus extensive details on parallel replicas execution.</p>\n<p>Now that the setup is clear, we can look at the results, beginning with vertical scaling, where performance depends on how well GROUP BY uses additional cores on a single node.</p>\n<h2 id=\"scaling-group-by-vertically-with-more-cores-per-node\"></h2>\n<blockquote>\n<p><strong>Scaling up made simple</strong>: All benchmarks were run in <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a>, where <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates#clickhouse-cloud-enters-the-stage\">compute is decoupled from storage</a>. Ok speed, but not interactive, 14 seconds feels long in dashboards or ad-hoc analysis.</p>\n<blockquote>\n<p>About the time to tie your shoes, wait at a red light, or reheat a slice of pizza in the microwave (apologies to any Italian readers).</p>\n</blockquote>\n<p>For fixed cardinality workloads like this (the UK isn’t adding new counties or towns), an<a target=\"_blank\" href=\"https://clickhouse.com/docs/materialized-view/incremental-materialized-view\"> incremental materialized view</a> is the obvious answer. Pre-aggregating by geography cuts data volume dramatically and<a target=\"_blank\" href=\"https://clickhouse.com/blog/accelerating-clickhouse-json-queries-for-fast-bluesky-dashboards#final-takeaways-for-clickhouse-users\"> guarantees</a> millisecond response times.</p>\n<blockquote>\n<p><strong>Materialized views: storing partial states on disk</strong><br>ClickHouse incremental materialized views extend the partial aggregation states idea: instead of recomputing GROUP BY at query time, they capture the partial aggregation states during inserts, store them in data parts, and let background merges incrementally combine them. In<a target=\"_blank\" href=\"https://clickhouse.com/use-cases/observability\"> observability</a>, every log line counts, and ad-hoc queries may slice across any dimension. Same when grouping cardinality isn’t fixed. Then the alternative is brute force:\nWhen one big box, even with 89 cores, isn’t enough, the only option is to scale out. That’s where <strong>parallel replicas</strong> come in.</p>\n<h2 id=\"scaling-group-by-horizontally-with-parallel-replicas\"></h2>\n<blockquote>\n<p><strong>Scaling out made simple</strong>: In ClickHouse Cloud, compute is decoupled from storage, so new compute nodes come online instantly.</p>\n</blockquote>\n<p>Instead of physically <a target=\"_blank\" href=\"https://clickhouse.com/docs/shards\">sharding</a> data, all nodes in ClickHouse Cloud read from a single limitless shard in object storage, acting as <em>virtual replicas</em>. With the <strong>parallel replicas</strong> feature, those nodes become <strong>additional parallel processing streams for the same query</strong>. More nodes → faster queries. A single coordinator orchestrates, dynamically slicing the data across nodes at runtime (think of it as <strong>virtual sharding on demand</strong>):</p>\n<p><span><img alt=\"Parallel Replicas-animation-03.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FParallel_Replicas_animation_03_49f48777c7.gif&w=2048&q=75\"></span></p>\n<p><em>(The feature is currently in beta in ClickHouse Cloud; you can enable it today for some of your workloads, with GA coming soon.)</em></p>\n<p>Without parallel replicas, a GROUP BY query could only use the cores of a single node (89 in our setup). With parallel replicas, every node’s cores join the same query:</p>\n<ul>\n<li>\n<p>At the default <strong>3 nodes</strong>, you already scale from 89 → <strong>267 cores</strong>.</p>\n</li>\n<li>\n<p>At <strong>10 nodes</strong>, that’s <strong>890 cores</strong>.</p>\n</li>\n<li>\n<p>At <strong>20 nodes</strong>, <strong>1,780 cores</strong>.</p>\n</li>\n<li>\n<p>At <strong>100+ nodes</strong>, you’re fanning a single GROUP BY across <strong>8,900+ cores</strong> (and 35,600+ GiB RAM).</p>\n</li>\n</ul>\n<p>This is done <strong>without sharding or data movement</strong>, just by adding additional stateless compute nodes. It's <strong>one click</strong> (or API call).</p>\n<p><em><strong>In this post, we stop at 100 nodes</strong>; the “how far can it go?” exploration is something we’ll save for a dedicated follow-up once parallel replicas are GA.</em></p>\n<blockquote>\n<p>Parallel replicas also accelerate <strong>scalar aggregates</strong> and <strong>plain SELECTs</strong>: for scalar aggregates (e.g., SUM/AVG without GROUP BY), the compute nodes build, send, and merge the same partial states described above; for non-aggregate SELECTs, nodes process data in parallel and send sub-results, and the coordinator performs the final SORT/LIMIT.</p>\n</blockquote>\n<h3 id=\"how-work-is-split-across-replicas\"></h3>\n<p>The chart shows how our <strong>10B-row GROUP BY</strong> scales across nodes (each with 89 cores):</p>\n<p><span><img alt=\"Parallel Replicas.003.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FParallel_Replicas_003_15a267088a.png&w=2048&q=75\"></span></p>\n<p><em><a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/3b6da4b0d0607d4debe5783021ffd2019058637e/blog-examples/ParallelReplicasBench/results/2025-08-29_horiz_uk_b10_n1-3-10-20-40-80-100_c89_r10_nocachedrop/summary_matrix-nodes-1_3_10_20_40_80_100_cores-89_2025-08-29_101110.json\">Here</a> are the full results behind the chart above.</em></p>\n<p>With 1 node, the query finishes in <strong>14.2 s</strong> at ~703M rows/s (~5.9 GiB/s).</p>\n<p>Adding additional nodes cuts runtime (and boosts throughput):</p>\n<ul>\n<li><strong>3 nodes → 5.2 s</strong>,</li>\n<li><strong>10 nodes → 2.0 s</strong>,</li>\n<li><strong>20 nodes → 1.3 s</strong>,</li>\n<li><strong>40 nodes → 0.85 s</strong>,</li>\n<li><strong>80 nodes → 0.56 s</strong>,</li>\n<li><strong>100 nodes → 0.55 s</strong>.</li>\n</ul>\n<p>The chart also shows <strong>per-node workload participation</strong>, <strong>per-node data read (uncompressed)</strong>, and <strong>network traffic</strong> (each node sends partial states to the coordinator, which receives them from all nodes and merges them).</p>\n<blockquote>\n<p><strong>Peeking behind the numbers</strong>: Our benchmark driver tracks way more detail: <strong>rows processed per node</strong>, <strong>compressed/uncompressed bytes scanned</strong>, <strong>memory usage</strong>, <strong>scan vs. aggregation time</strong>, <strong>cold/warm/hot status</strong>. One node scans ~84 GiB; three nodes ~28 GiB; ten nodes ~8 GiB. At 80–100 nodes, each replica handles ~1 GiB or less, and coordination overhead (e.g., partial states sent over the network to the coordinator) starts to dominate, flattening the curve on smaller datasets.</p>\n<h3 id=\"scaling-at-1t-rows\"></h3>\n<p>That flattening appears when per-node work gets too small to justify parallel replicas’ coordination overhead. To prove it, we reran the same query on the same compute nodes (each with 89 cores) on a dataset <strong>100× larger: 1 trillion rows</strong>.</p>\n<p><span><img alt=\"Parallel Replicas.004.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FParallel_Replicas_004_2e1de3a30e.png&w=2048&q=75\"></span></p>\n<p><em>Full results are <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/3b6da4b0d0607d4debe5783021ffd2019058637e/blog-examples/ParallelReplicasBench/results/2025-08-30_horiz_uk_t1_n1-3-10-20-40-80-100_c89_r10/summary_matrix-nodes-1_3_10_20_40_80_100_cores-89_2025-08-30_165307.json\">here</a>.</em></p>\n<p>At small node counts, each node is overloaded: a single node must scan and aggregate <strong>8.2 TiB</strong>, and with 3 nodes it’s still nearly <strong>3 TiB</strong> each.</p>\n<p>With <strong>10 nodes</strong> the per-node read drops to <strong>~910 GiB</strong>, and scaling kicks in nicely. Then node doublings are linear or better:</p>\n<ul>\n<li>10 → 20 nodes: <strong>2.02× faster</strong></li>\n<li>20 → 40 nodes: <strong>2.28× faster</strong></li>\n<li>40 → 80 nodes: <strong>2.17× faster</strong></li>\n<li>80 → 100 nodes: <strong>1.39× faster</strong> (better than the linear 1.25× expectation)</li>\n</ul>\n<p>Even at <strong>100 nodes</strong>, each replica processes <strong>~90 GiB</strong>, which is enough work to justify the coordination overhead of parallel replicas, so scaling remains strong.</p>\n<p><em>And yes, scaling would continue beyond 100 nodes on the 1T-row dataset, but as noted earlier, we’re saving the “how far can it go?” deep dive for a dedicated follow-up once parallel replicas are GA.</em></p>\n<p>How well the parallel replicas feature works also depends on <strong>partial-state size</strong>; we’ll look at that next.</p>\n<h2 id=\"when-group-by-gets-heavy\"></h2>\n<p>Not all GROUP BYs are created equal. So far, we’ve shown light aggregates like SUM and AVG, where partial states are tiny. But what happens when GROUP BY gets heavier, like <strong>COUNT DISTINCT</strong>? That’s where scaling looks different, and partial state size starts to matter.</p>\n<p>To demonstrate this, we count distinct streets with sales in each county per quarter over the 10B rows dataset.</p>\n<div><pre><code><span>USE uk_b10; <span>-- 10B rows dataset</span></span>\n<span></span>\n<span><span>SELECT</span></span>\n<span>  county,</span>\n<span>  toStartOfQuarter(<span>date</span>) <span>AS</span> qtr,</span>\n<span>  uniq(street) <span>AS</span> distinct_streets_with_sales</span>\n<span><span>FROM</span></span>\n<span>  uk_price_paid</span>\n<span><span>GROUP</span> <span>BY</span></span>\n<span>  county, qtr</span>\n<span><span>ORDER</span> <span>BY</span></span>\n<span>  qtr, county;</span></code></pre></div>\n<!-- -->\n<p>The query is simple; the aggregate choice matters.</p>\n<p><em>Note: This benchmark focuses on how different aggregate functions produce different partial state sizes. Since it uses a fresh GROUP BY query (different from earlier benchmarks), <strong>we ran it on 16-core nodes instead of 89-core ones</strong>, showing at the same time that parallel replicas scale efficiently regardless of core count.</em></p>\n<h3 id=\"the-light-case-uniq\"></h3>\n<p>The uniq aggregation function is approximate but efficient. It uses adaptive sampling (up to 65,536 hashes), keeping states compact.</p>\n<p><span><img alt=\"Parallel Replicas.005.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FParallel_Replicas_005_3b0ca1a948.png&w=2048&q=75\"></span></p>\n<p><em>For full results, go <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/9884ee05fbd20223cd9c67ab736dfdbc1024c133/blog-examples/ParallelReplicasBench/results/2025-09-02_horiz_uniq_uk_b10_n1-3-10-20-40-80-100_c16_r10/summary_matrix-nodes-1_3_10_20_40_80_100_cores-16_2025-09-02_050856.json\">here</a>.</em></p>\n<ul>\n<li>\n<p><strong>Per-node sent states:</strong> <strong>~58 MiB</strong> per <em>sending node</em> (2 senders with 3 nodes) to <strong>~4.2 MiB</strong> per node with 100 nodes</p>\n</li>\n<li>\n<p><strong>Coordinator received total:</strong> <strong>~115 MiB</strong> (2×58 MiB) with 3 nodes to  <strong>~416 MiB</strong> (99x4.2 MiB) with 100 nodes</p>\n</li>\n</ul>\n<p>→ Coordinator fan-in stays small; per-node traffic shrinks as nodes increase.</p>\n<h3 id=\"the-heavy-case-uniqexact\"></h3>\n<p>The uniqExact aggregation function computes true COUNT DISTINCT. Partial states grow because each node must track all distinct values it sees, stored either as raw values or as hashes, depending on type, before the coordinator merges them.</p>\n<p><span><img alt=\"Parallel Replicas.006.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FParallel_Replicas_006_2bd7005e5d.png&w=2048&q=75\"></span></p>\n<p><em>You find the full results <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/9884ee05fbd20223cd9c67ab736dfdbc1024c133/blog-examples/ParallelReplicasBench/results/2025-09-02_horiz_uniqExact_uk_b10_n1-3-10-20-40-80-100_c16_r10/summary_matrix-nodes-1_3_10_20_40_80_100_cores-16_2025-09-02_055212.json\">here</a>.</em></p>\n<ul>\n<li>\n<p><strong>Per-node sent states:</strong> <strong>~225 MiB</strong> per <em>sending node</em> (2 senders with 3 nodes) to <strong>~16 MiB</strong> per node with 100 nodes</p>\n</li>\n<li>\n<p><strong>Coordinator received total:</strong> <strong>~450 MiB</strong> (2×225 MiB) with 3 nodes to <strong>~1.5 GiB</strong> (99x16 MiB) with 100 nodes</p>\n</li>\n</ul>\n<p>States are <strong>~4× larger</strong> than with uniq, so network fan-in and merge time are more noticeable, even though runtime still improves.</p>\n<p>But this isn’t universal: uniqExact state size scales with <strong>cardinality</strong>. In our data, unique streets per (county, quarter) max at ~17k and stay stable, making this example relatively mild.</p>\n<blockquote>\n<p><strong>Cardinality caveat:</strong> When distincts explode (e.g., <code>uniqExact(user_id)</code> for billions of users, or <code>uniqExact(url)</code> across the web), states can be <strong>orders of magnitude larger</strong> than <code>uniq</code>, and network overhead grows accordingly.</p>\n</blockquote>\n<h3 id=\"takeaways-on-distincts\"></h3>\n<p>Parallel replicas scale all 170+ aggregate functions, but the size of partial states determines efficiency:</p>\n<ul>\n<li>\n<p><strong>Light states</strong> (e.g. <em>sum</em>, <em>count</em>, <em>uniq</em>): scale well.</p>\n</li>\n<li>\n<p><strong>Heavy states</strong> (<em>uniqExact</em>): scale too, but with more network/merge cost.</p>\n</li>\n<li>\n<p><strong>Other options</strong> (<em>uniqHLL12</em>): fixed ~2.5 KB state with ~1–2% error for 10K–100M distincts; less accurate on tiny sets, degrades beyond 100M; a practical balance for some workloads.</p>\n</li>\n</ul>\n<p>Heavy aggregates still scale, but larger partial states increase network traffic and merge cost. Whether the trade-off pays off depends on how much data each node has to process. That brings us to the safeguards ClickHouse applies to keep parallel replicas efficient.</p>\n<h2 id=\"scaling-limits-and-safeguards\"></h2>\n<p>One query doesn’t always get faster by throwing more nodes at it.</p>\n<p>On <strong>smaller datasets (e.g., 10B rows)</strong>, parallel replicas scale well at low node counts, but at higher counts, nodes may run out of work, and coordination overhead dominates.</p>\n<p>On <strong>larger datasets (e.g., 1T rows)</strong>, the opposite happens: low node counts can be overwhelmed, while higher counts scale cleanly because each node still has plenty of rows to process, making the coordination cost worth it.</p>\n<p>ClickHouse uses two guardrails to keep parallel replicas efficient:</p>\n<ul>\n<li>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#parallel_replicas_min_number_of_rows_per_replica\">parallel_replicas_min_number_of_rows_per_replica</a> — only turns a node into a parallel replica if it gets enough rows to justify the overhead.</p>\n</li>\n<li>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#max_parallel_replicas\">max_parallel_replicas</a> — caps the maximum number of nodes that are used as parallel replicas for a query (default 1000).</p>\n</li>\n</ul>\n<p>Behind the scenes, the query planner estimates <strong>rows_to_read</strong> (e.g., via index analysis), the number of rows it expects the query will actually scan and process. The two settings from above then decide together whether parallel replicas are worth it and, if so, how many to use:</p>\n<ul>\n<li><strong>Enable rule</strong>: Parallel replicas are only enabled for a query if</li>\n</ul>\n<div><pre><code><span>rows_to_read &gt;= 2* parallel_replicas_min_number_of_rows_per_replica</span></code></pre></div>\n<p>Otherwise, they’re disabled, and the query runs on a single node.</p>\n<ul>\n<li><strong>Limit rule</strong>: If enabled via rule above, the number of nodes used as parallel replicas (number_of_replicas_to_use) is limited to</li>\n</ul>\n<div><pre><code><span>rows_to_read / parallel_replicas_min_number_of_rows_per_replica</span>\n<span></span>\n<span>(still capped by min(cluster size, max_parallel_replicas))</span></code></pre></div>\n<p>If this value is ≤ 1, parallel replicas are also disabled and the query falls back to normal single-node execution.</p>\n<p>In other words: small datasets skip parallel replicas entirely; large ones use them, but only up to the point where each node still gets meaningful work.</p>\n<p><strong>Example</strong>: Say a query has <strong>10B rows to read</strong>,  max_parallel_replicas = 100, and parallel_replicas_min_number_of_rows_per_replica = 1B.</p>\n<ul>\n<li>\n<p>Enable rule: 10B ≥ 2×1B → <strong>passes</strong> (parallel replicas enabled).</p>\n</li>\n<li>\n<p>Limit rule: 10B ÷ 1B = 10 → <strong>10 nodes used as parallel replicas for the query</strong> (not 100).</p>\n</li>\n</ul>\n<p>Each activated node then processes ~1B rows, enough work to justify the overhead.</p>\n<p><strong>Default behavior:</strong> By default, parallel_replicas_min_number_of_rows_per_replica is 0, which disables this safeguard. In that case, parallel replicas are always enabled, capped by max_parallel_replicas (default 1000) or by the cluster size, whichever is smaller. On small datasets, this can add unnecessary coordination overhead, so tuning the setting is recommended in production. You can also toggle parallel replicas per query with enable_parallel_replicas, and, if needed, override max_parallel_replicas for that query.</p>\n<p>Together, these safeguards try to ensure parallel replicas only kick in when they’ll cut query time, not add to it.</p>\n<p>Next, let’s look under the hood at how parallel replicas actually distribute work across nodes.</p>\n<h2 id=\"how-parallel-replicas-distribute-work\"></h2>\n<p><em>(We’ve already published a<a target=\"_blank\" href=\"https://clickhouse.com/docs/deployment-guides/parallel-replicas\"> detailed guide on how work is distributed with parallel replicas</a>; here we’ll just summarize the essentials.)</em></p>\n<p>The node that receives a query (in ClickHouse Cloud, the one picked by the load balancer) always becomes the <strong>coordinator</strong> for that query. Importantly, the coordinator is also a full parallel replica, executing its share of work just like the others, as shown in the earlier animation.</p>\n<p>Once a query arrives, the coordinator plans the work in ranges of <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes#data-is-organized-into-granules-for-parallel-data-processing\">granules</a> (the smallest unit of processing in ClickHouse, ~8,192 consecutive rows by default, selected via<a target=\"_blank\" href=\"https://clickhouse.com/docs/primary-indexes\"> index analysis</a>). It assigns granules across participating replicas, including itself.</p>\n<p>Each replica scans its assigned granules locally, computes <strong>partial aggregation states</strong>, and streams those states back. The coordinator then performs the <strong>final merge</strong> and returns the result.</p>\n<p>This granule-based model enables <strong>fine-grained load balancing</strong>:</p>\n<ul>\n<li>\n<p><strong>Dynamic coordination</strong>: replicas request new tasks as they finish previous ones, so faster replicas automatically pick up more work.</p>\n</li>\n<li>\n<p><strong>Task stealing</strong>: if one replica lags, others can grab its remaining granules.</p>\n</li>\n<li>\n<p><strong>Cache locality</strong>: Via consistent hashing, the same nodes process the same granules on repeated queries, reusing cached data. This works best when the full cluster is used (cluster size ≤ max_parallel_replicas); otherwise, node assignment is random.</p>\n</li>\n</ul>\n<p>That’s enough ground-level detail.
