This can be guaranteed by either using a single partition (Debezium source default) or by using <a target=\"_blank\" href=\"https://debezium.io/documentation/reference/stable/transformations/partition-routing.html\">hash-based partitioning</a> for cases where more than a single partition is required due to throughput requirements. This does <a target=\"_blank\" href=\"https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-delete-events\">require tombstone events</a> to be omitted in Debezium when a delete occurs. To simplify our pipeline, we disable these. Users should drop these in their <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-postgresql-change-data-capture-cdc-part-2#configure-kafka-connect-sink\">Kafka Sink</a> should they need this advanced feature.</p>\n<h3 id=\"configuring-postgresql\"></h3>\n<p>The PostgreSQL connector can be used with a standalone PostgreSQL server or with a cluster of PostgreSQL servers but is supported on primary servers only - the Debezium connector cannot connect to a replica instance.</p>\n<p>Note <a target=\"_blank\" href=\"https://debezium.io/documentation/reference/stable/connectors/postgresql.html\">the following</a> from the Debezium documentation:</p>\n<blockquote>\n<p>“If the primary server fails or is demoted, the connector stops. More specifically, this setting controls what (if any) information is available for the previous values of the table columns involved whenever an UPDATE or DELETE event occurs.</p>\n<p>While four different values are supported, we recommend the following based on whether you need support for deletes:</p>\n<ul>\n<li><code>DEFAULT</code> - The default behavior is that update and delete events contain the previous values for the primary key columns of a table if that table has a primary key. For an UPDATE event, only the primary key columns with changed values are present. If a table does not have a primary key, the connector does not emit UPDATE or DELETE events for that table. Only use this value if:\n<ul>\n<li>Your ClickHouse <code>ORDER BY</code> clause only contains the Postgres primary key columns. This is unlikely since typically users add columns to the <code>ORDER BY</code> to optimize aggregation queries that are unlikely to be primary keys in Postgres.</li>\n<li>You do not need support for deletes. Note: The configuration used below does not need the previous column values for updates. They are required for deletes as the new state is null.</li>\n</ul>\n</li>\n<li><code>FULL</code> - Emitted events for update and delete operations contain the previous values of all columns in the table. This is needed if you need to support delete operations.</li>\n</ul>\n<p>Set this setting using the <code>ALTER</code> command.</p>\n<div><pre><code><span><span>ALTER TABLE</span> uk_price_paid REPLICA <span>IDENTITY</span> <span>FULL</span>;</span></code></pre></div>\n<p>The rest of this post assumes the user needs to support deletes. This assumes the user is running the Kafka Connect framework. A <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/integrations/kafka#choosing-an-option\">number of Kafka Connect Sinks </a>can be used with ClickHouse, including the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/integrations/kafka#confluent-http-sink-connector\">Confluent HTTP Connector</a>. The insert of a batch is acknowledged prior to another batch being consumed.</li>\n</ul>\n<p>This allows the number of partitions for a topic to be scaled while still meeting our requirement of in-order delivery for any changes pertaining to a specific Postgres row, assuming we can guarantee that any events for a row are sent to the same <a target=\"_blank\" href=\"https://debezium.io/documentation/reference/stable/transformations/partition-routing.html\">partition via hashing</a> from the Debezium connector.</p>\n<p>We show configuring the ClickHouse Kafka Connect Sink in Confluent Cloud below. considerations when running a CDC pipeline using Debezium for ClickHouse and Postgres:</p>\n<ul>\n<li>\n<p>The Debezium connector will batch row changes where possible, up to a max size of the <code>max.batch.size</code>. These batches are formed every poll interval <code>poll.interval.ms</code> (500ms default). Users can increase these values for larger and more efficient batches at the expense of higher end-to-end latency. Remember that ClickHouse prefers batches of at <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/bestpractices/bulk-inserts\">least 1000</a> to avoid common issues such as <a target=\"_blank\" href=\"https://clickhouse.com/docs/knowledgebase/exception-too-many-parts\">too many parts</a>. For low throughput environments (&lt;100 rows per second), this batching is not as critical as ClickHouse will likely keep up with merges. However, users should avoid small batches at a high rate of insert.</p>\n<p>Batching can also be configured on the Sink side. This is currently not supported explicitly in the ClickHouse Connect Sink but can be configured through the Kafka connect framework - see the setting <a target=\"_blank\" href=\"https://docs.confluent.io/platform/current/installation/configuration/consumer-configs.html#max-poll-records\"><code>consumer.override.max.poll.records</code></a>. Alternatively, users can configure <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/asynchronous-inserts#enabling-asynchronous-inserts\">ClickHouse Async inserts </a>and allow ClickHouse to batch. In this mode, inserts can be sent as small batches to ClickHouse, which will batch rows before flushing. Note that while flushing, rows will not be searchable. This approach, therefore, **does not **help with end-to-end latency.</p>\n</li>\n<li>\n<p>Users should be cognizant of <a target=\"_blank\" href=\"https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-wal-disk-space\">WAL disk usage</a> and the importance of <a target=\"_blank\" href=\"https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-property-heartbeat-interval-ms\"><code>heartbeat.interval.ms</code></a> in cases where tables with few changes are being monitored in databases with many updates.</p>\n</li>\n<li>\n<p>The above approach <strong>does not currently support Postgres primary key changes</strong>. To implement this, users will need to detect <code>op=delete</code> messages from Debezium, which have no <code>before</code> or <code>after</code> fields. The <code>id</code> should then be used to delete these rows in ClickHouse - preferably using <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/lightweght-delete\">Lightweight deletes</a>. This requires custom code instead of using a Kafka sink for sending data to ClickHouse.</p>\n</li>\n<li>\n<p>If the Primary key of a table changes, users will likely need to create a new ClickHouse table with the new column as part of the <code>ORDER BY</code> clause. Note this also requires a <a target=\"_blank\" href=\"https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-streaming-changes\">process to be performed for the Debezium connector</a>.</p>\n</li>\n<li>\n<p>The logical decoding, on which the Debezium connector depends, does not support DDL changes. This means that the connector is unable to report DDL change events back to consumers.</p>\n</li>\n<li>\n<p>Logical decoding replication slots are supported only on primary servers. When there is a cluster of PostgreSQL servers, the connector can run on only the active primary server. It cannot run on hot or warm standby replicas. If the primary server fails or is demoted, the connector stops. After the primary server has recovered, you can restart the connector. If a different PostgreSQL server has been promoted to primary, adjust the connector configuration before restarting the connector.</p>\n</li>\n<li>\n<p>While Kafka Sinks can be safely scaled to use more workers (assuming events for the same Postgres row are hashed to the same partition), the Debezium connector allows only a <a target=\"_blank\" href=\"https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-property-tasks-max\">single task</a>. The solution proposed above uses a connector per table, allowing the solution to be scaled at a table level.</p>\n</li>\n<li>\n<p>The documented approach assumes a connector instance per table. We currently do not support a connector monitoring several tables - although this may be achievable with topic routing, i.e., messages are routed to a table-specific topic. This configuration has not yet been tested.</p>\n</li>\n</ul>\n<h2 id=\"conclusion\"></h2>\n<p>In this blog post, we have explored how a CDC pipeline can be constructed to replicate changes from Postgres to ClickHouse in near real-time. We discussed how the ReplacingMergeTree is fundamental to this design and how users can optimize the table design and use the FINAL operator for query time deduplication. As well as providing the instructions for building a pipeline, including how to configure Debezium, we have discussed other considerations for users wanting to build a production solution. While the details in this blog post are specific to Postgres, they can potentially be applied to all source databases supported by Debezium thanks to its DBMS-independent message format. We leave this as an exercise for the reader to explore other databases and let us know how you get on!</p></div></article>"
