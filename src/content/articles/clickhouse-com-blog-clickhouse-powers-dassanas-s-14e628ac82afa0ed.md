But then, even modern SIEMs are designed for immutable time series event data, e.g. logs. But security data is much more than just logs. For example, the state of an alert could be “open” or “closed”. Say you want to find out how many alerts are in an “open” state, how will you go about it? If the alert was in an “open” state an hour ago, and you sent that event to a SIEM but now the alert state has changed to “closed”, can you send an update request to your SIEM updating the alert state from “open” to “closed”? Of course, you can’t, it is called immutable for a reason. So the solution to this problem is re-inserting the updated data, and then just querying the most recent data. These are called last point queries and are quite notorious when run on append-only systems like SIEMs.</p>\n<p>Not only the fundamental “mutating” nature of security data makes SIEMs hard to operate, but SIEMs companies have also stopped innovating and investing in solving basic problems such as data normalization. What AWS calls an “account” id, GCP calls it a “project” id, and Azure calls it a “subscription” id. Wouldn’t it be beautiful if we can just normalize these things and call them something like “AssetContainerId”. This way, if the system supports SQL, you can just write queries like -</p>\n<div><pre><code><span><span><span>select</span> <span>count</span>(<span>*</span>) <span>as</span> count,assetContainerID <span>from</span> findings <span>where</span> status</span>=<span>'open'</span> <span>group</span> <span>by</span> assetContainerID</span></code></pre></div>\n<p><span><img alt=\"Dasana_Query.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDasana_Query_5637ad20fe.png&w=2048&q=75\"></span></p>\n<p><em>In the above example, we are showing the count of assets grouped by normalized asset type.</em></p>\n<p>That dream is what Dassana is. No system comes close to ClickHouse when it comes to the flexibility ClickHouse provides. Most big data systems force you to batch data which adds a lot of complexity on the application side.</li>\n<li>In-built accounting system to track query costs such as the number of rows read, etc.</li>\n<li>Ability to automatically move data to a different storage tier. This is an essential feature for data archival and having an in-built storage tier system has saved us precious development time. As icing on the cake, ClickHouse supports row level and column level TTLs (time to live) too.</li>\n<li>Advanced external dictionary options such as the ability to populate (and refresh) dictionaries from Postgres database and HTTP servers.</li>\n</ul>\n<p>As a seed-funded start-up, we also evaluated the cost savings at length and found that ClickHouse would cost us a fraction of what it would cost compared to other big data systems.</p>\n<h2 id=\"how-dassana-uses-clickhouse\"></h2>\n<p>When we first started, under the covers, Dassana heavily used the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/replacingmergetree/\">ReplacingMergeTree</a> table engine to store mutable data. When the state of a finding (alert) needed to be updated, we inserted a new row for the same alert with an updated state value and let the table engine handle deduplication logic. But this didn’t solve the problem when we wanted to provide near real-time deduplicated results back. This is where advanced features like <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/aggregatingmergetree/\">AggregatingMergeTree</a> with a materialized view came into play.</p>\n<p>In case you are wondering if the data was stored twice, once in ReplacingMergeTree and then again in <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/aggregatingmergetree/\">AggregatingMergeTree</a>, the answer is no, thanks to ClickHouse's <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter/ttl/\">TTL</a> feature.</p>\n<p>To query duplicated data, we used a “group by” aggregation query. While this approach worked for a while, as our data grew we started hitting performance issues. You can read more about this deduplication approach here <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/deduplication\">Row-level Deduplication Strategies for Upserts and Frequent Updates</a></p>\n<p>None of the suggested approaches worked for us at scale, and this is when we realized the magical power of the dictionary feature of ClickHouse.</p>\n<p>Let’s take an example. Consider the following schema:</p>\n<div><pre><code><span>CREATE TABLE default.foo (</span>\n<span>   tenant UUID,</span>\n<span>   record_id UInt64,</span>\n<span>   insert_ts UInt64,</span>\n<span>   data String,</span>\n<span>   insert_ts_dt DateTime MATERIALIZED toDateTime(divide(insert_ts,1000))</span>\n<span>)</span>\n<span>Engine = ReplacingMergeTree(insert_ts)</span>\n<span>ORDER BY (tenant, record_id);</span></code></pre></div>\n<p>Here, <code>record_id</code> is the unique “asset id” or the entity id for which we want to query deduplicated data. “data” is just an arbitrary value for the <code>record_id</code>.</p>\n<p>Now, let’s create a dictionary like this:</p>\n<div><pre><code><span>CREATE OR REPLACE DICTIONARY default.foo_last_point_dict</span>\n<span>(</span>\n<span>   `record_id_hash` UInt64,</span>\n<span>   `insert_ts` UInt64</span>\n<span>)</span>\n<span>PRIMARY KEY record_id_hash</span>\n<span>SOURCE(CLICKHOUSE(</span>\n<span>   QUERY '</span>\n<span>           SELECT cityHash64(tenant, record_id) as record_id_hash, max(insert_ts)</span>\n<span>           FROM table_x</span>\n<span>           WHERE {condition}</span>\n<span>           GROUP BY record_id_hash</span>\n<span>           ORDER BY record_id_hash</span>\n<span>       '</span>\n<span>   update_field 'insert_ts_dt'</span>\n<span>   update_lag 120</span>\n<span>))</span>\n<span>LIFETIME(5)</span>\n<span>LAYOUT(SPARSE_HASHED(PREALLOCATE 0));</span></code></pre></div>\n<p>The most important thing to note here is the query:</p>\n<div><pre><code><span>SELECT cityHash64(tenant, record_id) as record_id_hash, max(insert_ts)</span>\n<span>           FROM table_x</span>\n<span>           WHERE {condition}</span>\n<span>           GROUP BY record_id_hash</span>\n<span>           ORDER BY record_id_hash</span></code></pre></div>\n<p>This query is periodically run by ClickHouse according to the LIFETIME (5 seconds above). The value of <code>insert_ts_dt</code>, configured via <code>update_field</code>, is injected into the <code>WHERE</code> clause to determine the data that is returned. This query returns the max <code>insert_ts</code> for each <code>record_id_hash</code> used to populate the dictionary.\nTo query the data, we run a SQL query like this:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> foo</span>\n<span><span>WHERE</span> <span>equals</span>(insert_ts, dictGet(<span>'default.foo_last_point_dict, '</span>insert_ts<span>', cityHash64(tenant, record_id)))</span></span></code></pre></div>\n<p>This query selects the rows in the main table where the <code>insert_ts</code> is the same as that in the last-point (most recent) value in the dictionary.</p>\n<p>As with any system, the total complexity remains the same - you can just shuffle it around. In this case, we wanted great performance, but it comes with the following challenges that one must be aware of:</p>\n<ul>\n<li>If the cardinality of <code>record_id</code> is very high, there will be higher memory consumption. Fortunately, we found that we can store hundreds of millions of assets (distinct <code>record_id</code>) data on a 32GB RAM box.</li>\n<li>There is a short time window of 5 seconds (dictionary load frequency) during which the query will match stale data. This is within our accuracy budget as anyhow the data is loaded in a streaming fashion and most analytical queries for our use case are about trending and approximation.</li>\n</ul>\n<p>It is worth mentioning that we experimented with the “Join” table engine too but found the performance of our dictionary based approach to be far more performant.</p>\n<h2 id=\"lessons-learned\"></h2>\n<p>While this post has shown you some of the powerful features of ClickHouse, we want to highlight some of our learnings too. ClickHouse, in all its glory and power, is a force that needs to be handled with due care and attention to detail. Some of our learnings are:</p>\n<ol>\n<li>Production parity. Most likely, you are running ClickHouse on Intel CPUs. Don’t run tests on Apple Silicon and expect everything to work the same on Intel CPUs. Of all the ClickHouse builds, Intel builds are the most stable. Similarly, try allocating the same amount of resources to the test cluster as available to the production cluster. This might sound expensive, but you can turn off the test cluster when not in use. Certain issues only surface when the system is heavily used.</li>\n<li>Don’t manage ClickHouse manually. It is a crime if you are not using ClickHouse Cloud since this takes away a lot of the complexity of scaling and replicating data.</li>\n<li>Don’t use experimental features in production. This should be obvious learning, but it is sometimes tempting to use experimental features. For example, we started using projections when they were almost in production, but we should have waited. Wait for the training wheels to come off.</li>\n</ol>\n<h3 id=\"about-dassana\"></h3>\n<p>Founded by a team of successful serial entrepreneurs and cloud security veterans, we're building a security data lake to consolidate disparate data sources and provide contextualized data insights.
