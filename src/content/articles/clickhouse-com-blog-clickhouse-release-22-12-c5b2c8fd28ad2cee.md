The latter relies on sorting data and dumping it to disk, often overcoming memory at the expense of performance. While this at least allowed users to execute large joins, it often suffered from slow performance. With this release, we introduce an exciting non-memory bound addition to the join algorithms, which overcomes some of the performance challenges of partial merge: The Grace Hash.</p>\n<p>The <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Hash_join#Grace_hash_join\">Grace Hash algorithm </a>utilizes a two-phased approach to joining the data. Our implementation differs slightly from the <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=GRONctC_Uh0\">classic algorithmic description</a> in order to fit our query pipeline.</p>\n<p>Our first phase reads the right table and splits it into N buckets depending on the hash value of key columns (initially, N is <code>grace_hash_join_initial_buckets</code>). This is done in a way to ensure that each bucket can be processed independently. Rows from the first bucket are added to an in-memory hash table while the others are saved to disk. If the hash table grows beyond the memory limit (e.g., as set by <code>max_bytes_in_join</code>), we increase the number of buckets and recompute the assigned bucket for each row. Any rows which don’t belong to the current bucket are flushed and reassigned.</p>\n<p><span><img alt=\"right-side-grace.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fright_side_grace_8054638766.png&w=2048&q=75\"></span></p>\n<p>The left table is then read. Rows corresponding to the first bucket are joined (as the hash table is in memory), with others being flushed to their appropriate disk-based bucket. The key in both of these steps is that the hash function will consistently assign values to the same bucket, thereby effectively partitioning the data and solving the problem by decomposition.</p>\n<p><span><img alt=\"left-side-grace.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fleft_side_grace_c09fcd9258.png&w=2048&q=75\"></span></p>\n<p>After we finish reading the left table, we must process the remaining buckets on disk. These are processed sequentially. We build the hash table for each bucket from the right table data. Again, if we run out of memory, we must increase the number of buckets. Once a hash table has been built from a right bucket, we stream the left bucket and complete the join for this pair. Note that during this step, we may get some rows that belong to another bucket other than the current due to them being saved before the number of buckets was increased. In this case, we save them to the new actual buckets and process them further. This process is repeated for all of the remaining buckets.</p>\n<p><span><img alt=\"grace-final-step.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fgrace_final_step_8424107c1a.png&w=2048&q=75\"></span></p>\n<p>This approach of partitioning data ensures that we can both limit memory and the number of times we need to scan each table. Both sides of the table are scanned twice - once for partitioning the data and again for the join stage. While not as fast as a hash join, the performance benefits can be appreciable compared to the <code>partial_merge</code>.</p>\n<p><strong>Now let's take a practical example.</strong></p>\n<p>In our <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=GEFQJZTCMQPSB8ZMDCHJWK\">play.clickhouse.com</a>, we maintain an anonymized <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/metrica\">web analytics dataset </a>in the table <code>hits</code>.  Every row in this table represents a website click, recording details such as the browser agent and url. The dataset also includes a <code>Referer</code> column (also a URL), indicating the previous location from which the visitor arrived for each URL. Suppose we identify the previous two pages visited prior to a URL, not just the immediate referer. We could solve this with a sort by time, but let's make it deliberately more tricky and solve it with graph analysis. This requires us to effectively do graph navigation of depth 2, as shown below:</p>\n<p><span><img alt=\"url-self-join.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Furl_self_join_511e5fc0c9.png&w=2048&q=75\"></span></p>\n<p>This can be realized in SQL as a self-join, where we join the <code>hits</code> table to itself by looking for pairs of rows that share a common URL and Referer value.</p>\n<pre><p>\nSELECT\n\tUserID,\n\th1.Referer,\n\th1.URL,\n\th2.URL\nFROM hits AS h1\nINNER JOIN hits AS h2 ON h1.UserID = h2.UserID AND h1.URL = h2.Referer\nWHERE h1.URL != '' AND h2.URL != '' AND h1.Referer != '' AND h2.Referer != ''\nORDER BY UserID ASC\nLIMIT 10\n</p>\n</pre>\n<p>While the results to this query aren’t particularly interesting, we note the performance and memory overhead for the <code>hash</code>, <code>parallel_hash</code>, <code>partial_merge</code> and <code>grace_join</code> algorithms below.</p>\n<p><span><img alt=\"hash-algorithms.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fhash_algorithms_061cca0703.png&w=2048&q=75\"></span>\n<span><img alt=\"hash-join-results.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fhash_join_results_ee7184297b.png&w=2048&q=75\"></span></p>\n<p>Note: the <code>parallel_hash</code>  is a variation of a <code>hash</code> join that splits the data into buckets and builds several hash tables concurrently, instead of one, to speed up the join at the expense of higher memory overhead.</p>\n<p>The results here are quite clear. Grace offers improved performance over <code>partial_merge</code> at the expense of more memory overhead. While hash, and more so <code>parallel_hash</code>, are considerably faster, you pay an overhead and rely on having sufficient memory. The choice here is up to the user. Note that these results will vary depending on your data and query.</p>\n<p>Note the Grace Hash test here was run with the setting <code>grace_hash_join_initial_buckets=128</code>. The primary benefit of selecting a “correct” value for <code>grace_hash_join_initial_buckets</code> is it avoids the re-bucketing we described earlier - potentially speeding up the JOIN. For now, this is left to the user to tune manually.</p>\n<h2 id=\"enforce-password-complexity-rules-nikolay-degterinsky\"></h2>\n<p>ClickHouse considers security to be a first-class citizen. Prior to 22.12, users could create passwords with no enforcement of complexity. While we trust our users to be responsible, mistakes and oversights happen, and weak passwords could be created. We needed to close this for our own needs with ClickHouse Cloud, but also something our community needed.</p>\n<p>Password enforcement can be set by adding a <code>password_complexity</code> config key to your server configuration. An example of 4 rules enforcing a strong standard:</p>\n<pre><p>\n$ cat /etc/clickhouse-server/config.d/rules.yaml\npassword_complexity:\n  - rule:\n    pattern: '.{12}'\n    message: 'be at least 12 characters long'\n  - rule:\n    pattern: '\\p{N}'\n    message: contain at least 1 numeric character\n  - rule:\n    pattern: '\\p{Lu}'\n    message: contain at least 1 uppercase character\n  - rule:\n    pattern: '[^\\p{L}\\p{N}]'\n    message: contain at least 1 special character\n</p>\n</pre>\n<p>Attempts to violate this policy now result in an error e.g.,</p>\n<pre><p>\nclickhouse-cloud:) CREATE USER vasyan IDENTIFIED WITH sha256_password BY 'qwerty123'\nDB::Exception: Invalid password.
