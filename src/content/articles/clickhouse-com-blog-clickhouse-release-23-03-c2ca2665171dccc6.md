But don't miss out on compressed marks in memory, extended temporary tables, and the ability to see the results of a cancelled query (among many more).</p>\n<h2 id=\"parallel-replicas-for-utilizing-the-full-power-of-your-replicas-nikita-mikhailov\"></h2>\n<p>With <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/29279\">parallel replicas</a>, data can be processed in parallel by multiple replicas of the same shard.</p>\n<p>In ClickHouse clusters, <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=vBjCJtw_Ei0&t=1s\">sharding</a> can be used when the overall amount of data doesn’t fit onto a single host or when data processing is too slow with a single host: The data is split over multiple hosts in the form of shards (collections of <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#mergetree-data-storage\">data parts</a>).</p>\n<p>This allows query performance to be scaled as distinct subsets of data can be processed in parallel by multiple ClickHouse hosts. Usually, a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/distributed\">distributed table</a> is used for routing a query to all shards. We sketch this below:</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2F1Vp9tYw.png&w=2048&q=75\"></span></p>\n<p><span><img alt=\"0_23.3_release.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F0_23_3_release_b6fd3919a7.png&w=2048&q=75\"></span></p>\n<p>There are scenarios where having more than one shard is impractical or unnecessary, respectively. For example, when you run ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/integrations/s3#s3-backed-mergetree\">on top</a> of virtually limitless <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/storing-data#zero-copy\">shared</a> <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Object_storage\">object storage</a>, like in <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a>, all ClickHouse instances have access to the same physical data and are effectively multiple replicas of a single (limitless) shard. With the new ClickHouse parallel replicas feature, you can utilize such replicas for parallelizing data processing. We visualize this below:</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2F8bIeTyY.png&w=2048&q=75\"></span></p>\n<p><span><img alt=\"1_23.3_release.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F1_23_3_release_c2f39e748e.png&w=2048&q=75\"></span></p>\n<p>The above visualization shows that with the setting <code><a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/29279\">allow_experimental_parallel_reading_from_replicas</a> = true</code>, a query is sent to a (random) initiator replica node, which forwards the query to all participating replicas (the number is configured via <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-max_parallel_replicas\">max_parallel_replicas</a>). Each replica then processes a distinct subset of data <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=hP6G2Nlz_cA\">ranges</a> (dynamically assigned by the initiator node) of the overall shard data in parallel, sending its local results back to the initiator node, which merges the local results into the final result.</p>\n<p>In ClickHouse Cloud, this separation of storage and compute allows to dynamically increase (or decrease) the number of replica nodes in order to (ideally) linearly or even <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=ISaGUjvBNao&t=2035s\">superlinearly</a> tune query processing times. Without requiring any physical resharding or rebalancing of the actual data!</p>\n<p>The parallel replicas feature also works for self-managed ClickHouse clusters consisting of multiple shards with multiple replicas per shard. Then multiple replicas per shard will process distinct subsets of data ranges of the shard in parallel:</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2F0hQGfVQ.png&w=2048&q=75\"></span></p>\n<p><span><img alt=\"2_23.3_release.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F2_23_3_release_110a15bc75.png&w=2048&q=75\"></span></p>\n<p>Therefore data processing speed can be tuned by adding additional copies (replicas) of the data.</p>\n<h2 id=\"parallel-replicas-with-dynamic-shards-antonio-andelic\"></h2>\n<p>By processing distinct subsets of the data, every parallel replica can be imagined as a shard without physically sharding the data.</p>\n<p>Dynamic sharding now allows users to control how these virtual shards are formed and, thus, how the query is distributed. Parallel replicas can now be <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/45108\">configured</a> to split work by automatically adding a distinct filter based on the  <code><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-parallel_replicas_custom_key\">parallel_replicas_custom_key</a></code> expression to the query on the initiator node before forwarding the query to all participating replicas:</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2FPbRDCxX.png&w=2048&q=75\"></span></p>\n<p><span><img alt=\"3_23.3_release.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F3_23_3_release_247091c27f.png&w=2048&q=75\"></span></p>\n<p>This can be beneficial for specific queries. For example, for GROUP BY queries, if the group by column is used as the <code>parallel_replicas_custom_key</code> expression, then there is no need for the initiator node to merge the local results from the participating replicas, as there will be no group overlaps in the local results (therefore <code><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#distributed-group-by-no-merge\">distributed_group_by_no_merge</a></code> is set to 2 automatically if <code>parallel_replicas_custom_key</code> is set).</p>\n<p>Furthermore, you can now also configure, via the <code><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-parallel_replicas_custom_key_filter_type\">parallel_replicas_custom_key_filter_type</a></code> setting, how the <code>parallel_replicas_custom_key</code> expression is used for splitting work between the participating replica nodes. When set to <code>default</code>, then a “remainder of division” SQL predicate using a modulus of the NODE_COUNT will be added to the query on the initiator node (we assume that each of the <code>NODE_COUNT</code> participating nodes has a distinct identifier <code>NODE_NUM</code> in the range <code>0 to NODE_COUNT - 1</code>):</p>\n<div><pre><code><span><span>WHERE</span> parallel_replicas_custom_key <span>%</span> NODE_COUNT <span>=</span> NODE_NUM</span></code></pre></div>\n<p>When <code>parallel_replicas_custom_key_filter_type</code> is set to <code>range</code>, then the entire value space of  the <code>parallel_replicas_custom_key</code> expression is evenly split between the replica nodes by adding a “range” predicate to the query for each replica that, simplified, looks like this (the <code>parallel_replicas_custom_key</code> expression needs to be of unsigned integer type for the range filter):</p>\n<div><pre><code><span><span>WHERE</span> parallel_replicas_custom_key <span>&gt;=</span> NODE_NUM <span>*</span> (MAX_OF_VALUE_SPACE <span>/</span> NODE_COUNT)</span>\n<span>  <span>AND</span> parallel_replicas_custom_key <span>&lt;</span> (NODE_NUM <span>+</span> <span>1</span>) <span>*</span> (MAX_OF_VALUE_SPACE <span>/</span> NODE_COUNT)</span></code></pre></div>\n<p>This “range” work split configuration is an optimization for saving IO time if the data is locally distributed (<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">sorted</a>) according to the <code>parallel_replicas_custom_key</code> and if the values of the key are uniformly distributed across the entire domain of its data type (like it is the case when hash values are used).</p>\n<p>For those of you that would like to read more about parallel replicas and how to exploit the full power of object storage-based clusters, stay tuned for more in-depth blog posts coming soon.</p>\n<h2 id=\"lightweight-deletes-are-now-ga-jianmei-zhang-and-alexander-gololobov\"></h2>\n<p>In a <a target=\"_blank\" href=\"https://clickhouse.com/blog/handling-updates-and-deletes-in-clickhouse\">recent blog post</a>, we explored strategies for deleting and updating data in ClickHouse. As part of this, we discussed a recent feature that makes deleting data in ClickHouse a lighter weight operation - aptly named “Lightweight Deletes”. To much community demand and anticipation we can now announce that this feature is generally available and ready for use in production.</p>\n<p>This approach to removing data now represents the preferred and most efficient way to remove data from ClickHouse. While excluded from search results, the deleted rows will reside on disk until their parts are merged. The time taken for this to happen is not deterministic. This means:</p>\n<ul>\n<li>Space savings will not be as immediate as issuing a deletion <a target=\"_blank\" href=\"https://clickhouse.com/blog/handling-updates-and-deletes-in-clickhouse\">through regular mutations</a>.
