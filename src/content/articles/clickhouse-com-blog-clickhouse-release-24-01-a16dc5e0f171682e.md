id=\"contributed-by-prashantr36-and-robert-schulze\"></h3>\n<p>Users new to ClickHouse who experiment with the LIKE operator and match operator are often taken aback by its performance. Depending on the expression being matched this can either be mapped to a regular expression or perform a substring search using an efficient implementation of the rather unknown <a target=\"_blank\" href=\"https://clickhouse.com/codebrowser/ClickHouse/src/Common/Volnitsky.h.html\">Volnitsky's string search algorithm</a>. ClickHouse also utilizes the primary key and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/skipping-indexes\">skipping indexes</a> on a best-effort basis to accelerate LIKE / regex matching.</p>\n<p>While string matching has a number of applications, from data cleaning to searching logs in Observability use cases, it is hard to express a \"fuzzy\" relationship between two strings as a LIKE pattern or regular expression. Real-world datasets are often more “messy” and need more flexibility than substring searching offers, e.g., to find misspelled strings or mistakes made as the result of <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Optical_character_recognition\">Optical Character Recognition (OCR)</a>.</p>\n<p>To address these challenges, a number of well-known string similarity algorithms exist, including <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Levenshtein_distance\">Levenshtein</a>, <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Damerau%E2%80%93Levenshtein_distance\">Damerau Levenshtein</a>, <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Jaro%E2%80%93Winkler_distance#Jaro_similarity\">Jaro Similarity</a>, and <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Jaro%E2%80%93Winkler_distance#Jaro%E2%80%93Winkler_similarity\">Jaro Winkler</a>. These are widely used in applications such as spell checking, plagiarism detection, and more broadly in the field of natural language processing, computational linguistics and bioinformatics.</p>\n<p>All of these algorithms compute a string similarity (<a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Edit_distance\">edit distance</a>) between the search string and a target set of tokens. This metric aims to quantify how dissimilar two strings are to one another by counting the minimum number of operations required to transform one string into the other. Each algorithm differs in the operations it permits to compute this distance, with some also weighting specific operations more than others when computing a count.</p>\n<p>In 24.1, we extend our existing support for<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/string-functions#editdistance\"> Levenshtein distance</a> with new functions for <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Damerau%E2%80%93Levenshtein_distance\">Damerau Levenshtein</a>, <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Jaro%E2%80%93Winkler_distance#Jaro_similarity\">Jaro Similarity</a>, and <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Jaro%E2%80%93Winkler_distance#Jaro%E2%80%93Winkler_similarity\">Jaro Winkler</a>.</p>\n<p>Possibly the most well-known algorithm that implements this concept (so much so it's often used interchangeably with edit distance) is the Levenshtein distance. This metric computes the minimum number of single-character edit operations required to change one word into the other. Edit operations are limited to 3 types:</p>\n<ul>\n<li><strong>Insertions:</strong> Adding a single character to a string.</li>\n<li><strong>Deletions:</strong> Removing a single character from a string.</li>\n<li><strong>Substitutions:</strong> Replacing one character in a string with another character.</li>\n</ul>\n<p>The Levenshtein distance between two strings is the minimum number of these operations required to transform one string into the other. Damerau-Levenshtein builds upon this concept by adding <strong>transpositions,</strong> i.e., the swapping of adjacent characters.</p>\n<p>For example, consider the difference between Levenshtein and Damerau Levenshtein for “example” and “exmalpe”.</p>\n<p>Using Levenshtein distance, we need 3 operations:\n<span><img alt=\"string_similarity_01.png\" possible application, let's consider the problem of <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Typosquatting\">typosquatting</a> also known as URL hijacking. Our current release brings some additional optimization when FINAL is used with the ReplacingMergeTree table engine.</p>\n<p>As a reminder, FINAL can be used as a query modifier for tables created with the ReplacingMergeTree, AggregatingMergeTree, and CollapsingMergeTree engines in order to apply missing data transformations on the fly at query time. Since ClickHouse 23.12, the table data matching a query’s WHERE clause is divided into non-intersecting and intersecting ranges based on sorting key values. Non-intersecting ranges are data areas that exist only in a single part and thus need no transformation. Conversely, rows in intersecting ranges potentially exist (based on sorting key values) in multiple parts and require special handling. All non-intersecting data ranges are processed in parallel as if no FINAL modifier was used in the query. This leaves only the intersecting data ranges, for which the table engine’s merge logic is applied on the fly at query time.</p>\n<p>As a reminder, the following diagram shows how such data ranges are merged at query time by a <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-23-12#optimizations-for-final\">query pipeline</a>:<br>\n<span><img alt=\"final_01.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Ffinal_01_27361751d7.png&w=2048&q=75\"></span>\nData from the selected data ranges is streamed in physical order at the granularity of <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/development/architecture#block\">blocks</a> (that combine multiple neighboring rows of a data range) and merged using a <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/K-way_merge_algorithm#:~:text=In%20computer%20science%2C%20k%2Dway,sorted%20lists%20greater%20than%20two.\">k-way merge sort</a> algorithm.</p>\n<p>The <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/replacingmergetree\">ReplacingMergeTree</a> table engine retains only the most recently inserted version of a row (based on the creation timestamp of its containing part) during the merge, with older versions discarded. To merge rows from the streamed data blocks, the algorithm iterates row-wise over the block’s columns and copies the data to a new block. In order for the CPU to execute this logic efficiently, blocks need to reside in CPU caches, e.g. L1/L2/L3 caches. The more columns that are contained in a block, the higher the chance that blocks need to be repeatedly evicted from the CPU caches leading to <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Thrashing_(computer_science)\">cache trashing</a>. The next diagram illustrates this:\n<span><img alt=\"final_02.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Ffinal_02_fe27a5a464.png&w=2048&q=75\"></span>\nWe assume that a CPU cache can hold two blocks from our example data at the same time. When the aforementioned merge algorithm iterates in order over blocks from all three selected matching data ranges to merge their data row-wise, the runtime will be negatively impacted by the worst-case scenario of one cache eviction per iteration. This requires data to be copied from the main memory into the CPU cache over and over leading to slower overall performance due to unnecessary memory accesses.</p>\n<p>ClickHouse 24.1 tries to prevent this with a more cache-friendly query-time merge algorithm specifically for the ReplacingMergeTree, which works similarly to the <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#more-parts--more-background-part-merges\">vertical</a> background merge algorithm. The next diagram sketches how this algorithm works:\n<span><img alt=\"final_03.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Ffinal_03_e4e011278b.png&w=2048&q=75\"></span>\nInstead of copying all column values for each row during merge sort, the merge algorithm is split into two phases. In phase 1, the algorithm merges only data from the sorting key columns. We assume that column c<sub>1</sub> is a sorting key column in our example above. Additionally, based on the sorting key column merge, the algorithm creates a temporary row-level filter bitmap for the data ranges indicating which rows would survive a regular merge. In phase 2, these bitmaps are used to filter the data ranges accordingly and remove all old rows from further processing steps. This filtering happens column-by-column and only for all non-sorting-key-columns. Note that both phase 1 and phase 2 individually require less space in CPU caches than the previous 23.12 merge algorithm, resulting in fewer CPU cache evictions and, thus decreased memory latency.</p>\n<p>We demonstrate the new vertical query-time merge algorithm for FINAL with a concrete example.
