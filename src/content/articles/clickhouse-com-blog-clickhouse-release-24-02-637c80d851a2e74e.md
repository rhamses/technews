While ensuring this was as efficient as possible we noticed that the function also performed the necessary unpacking of any const arguments (the most common use case i.e. we pass a constant vector for comparison) which led to unnecessary memory copies. This meant the actual function runtime was dominated by memory operations - vectorization in this case was a comparatively small gain. Once <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/60928\">eliminated performance was improved a staggering 270x</a> on automated benchmarks!</p>\n<p>While it's not worth comparing performance to previous versions for this function (they are a little embarrassing :)), we thought we’d use the opportunity to note that the improvements allow us to demonstrate a nice performance optimization users can now exploit.</p>\n<p>Readers may recall that the cosine distance and dot product are closely related. More specifically, cosine distance measures the cosine of the angle between two vectors in a multi-dimensional space. It is derived from the cosine similarity, with cosine distance defined as 1 - cosine similarity. The cosine similarity is calculated as the dot product of the vectors divided by the product of their magnitudes i.e. <code>1- ((a.b)/||a||||b||)</code>. Conversely, the dot product measures the sum of the products of the corresponding entries of the two sequences of numbers i.e. vectors A and B with components <code>a<sub>i</sub></code> and <code>b<sub>i</sub></code>, the dot product is <code>A⋅B=∑a<sub>i​</sub>b<sub>i​</sub></code>.</p>\n<p>Cosine distance and dot product become particularly related when you normalize the vectors (i.e., when the magnitude of both vectors is 1). In this case, the cosine similarity is exactly the dot product because the denominators in the cosine similarity formula (the magnitudes of the vectors) are both 1, thus canceling out. Our cosine distance thus simply becomes <code>1-(a.b)</code>.</p>\n<p><strong>How can we exploit this?</strong></p>\n<p>We can normalize our vectors at insert time using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/distance-functions#l2norm\">L2Norm function</a> (vector magnitude) allowing us to use the <code>dotProduct</code> function at query time. The main motivation for this is that the <code>dotProduct</code> function is computationally simpler (we don’t have to compute the magnitude for each vector), thus potentially saving us a little query time.</p>\n<p>To perform normalization at query time:</p>\n<div><pre><code><span><span>INSERT INTO</span> glove</span>\n<span>SETTINGS schema_inference_make_columns_nullable <span>=</span> <span>0</span></span>\n<span><span>SELECT</span></span>\n<span>\tword,</span>\n<span>\tvector <span>/</span> L2Norm(vector) <span>AS</span> vector</span>\n<span><span>FROM</span> s3(<span>'https://datasets-documentation.s3.eu-west-3.amazonaws.com/glove/glove_840b_300d.parquet'</span>)</span>\n<span>SETTINGS schema_inference_make_columns_nullable <span>=</span> <span>0</span></span>\n<span></span>\n<span><span>0</span> <span>rows</span> <span>in</span> set. For optimal performance, <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#data-needs-to-be-batched-for-optimal-performance\">data needs to be batched</a>, and generally, we should avoid creating too many small inserts too frequently.</p>\n<p>Asynchronous inserts shift data batching from the client side to the server side: data from insert queries is inserted into a buffer first and then written to the database storage later or <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#asynchronous-inserts\">asynchronously</a> respectively. This is handy, especially for scenarios where many concurrent clients insert data frequently into a table, the data should be analyzed in real-time, and delays caused by client-side batching are unacceptable. For <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#example-application-and-benchmark-setup\">example</a>, observability use cases frequently involve thousands of monitoring agents continuously sending small amounts of event and metrics data. Such scenarios can utilize the asynchronous insert mode, illustrated by the following diagram:</p>\n<p><span><img alt=\"01.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F01_2fb5e510c3.png&w=2048&q=75\"></span></p>\n<p>In the example scenario in the diagram above, ClickHouse receives an asynchronous insert query 1 for a specific table after a period of no insert activity for this table. After receiving insert query 1, the query’s data is inserted into an in-memory buffer, and the default <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert-busy-timeout-ms\">buffer flush timeout</a> counter starts. Before the counter ends, and therefore the buffer gets flushed, the data of other asynchronous insert queries from the same or other clients can be collected in the buffer. Flushing the buffer will create a data part on disk containing the combined data from all insert queries received before the flush.</p>\n<p>Note that with the <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#default-return-behavior\">default return behavior</a>, all insert queries only return with an acknowledgment of the insert to the sender after the buffer flush occurs. In other words, the client-side call sending the insert query is <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#disadvantage\">blocked</a> until the next buffer flush occurs. As a consequence, infrequent inserts have a higher latency. We sketch this below:</p>\n<p><span><img alt=\"02.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F02_4cbac33f6b.png&w=2048&q=75\"></span></p>\n<p>The extreme case scenario above shows infrequent insert queries. ClickHouse receives an asynchronous insert query 1 after a period of no insert activity for a table. This triggers a new buffer flush cycle with the default <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert-busy-timeout-ms\">buffer flush timeout</a>, meaning that the sender of that query needs to wait for the complete default buffer flush time (200 ms for OSS or 1000 ms for ClickHouse Cloud) before receiving an acknowledgment of the insert. Similarly, the sender of insert query 2 experiences a high insert latency.</p>\n<p>The <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#allow-experimental-async-insert-adaptive-busy-timeout\">adaptive asynchronous insert buffer flush timeout</a> introduced in ClickHouse 24.2 solves this problem by using an adaptive algorithm for automatically adjusting the buffer flush timeout based on the frequency of inserts:</p>\n<p><span><img alt=\"03.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F03_0e6a6407e8.png&w=2048&q=75\"></span></p>\n<p>For the extreme case scenario shown before with some infrequent insert queries, the buffer flush timeout counter now starts with a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert-busy-timeout-min-ms\">minimal value</a> (50 ms). Therefore the data from these queries is written to disk much sooner.  It is ok to almost immediately write small data amounts to disk, as the frequency is low. Therefore there is no risk of the <code>Too many parts</code> <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/merge-tree-settings#parts-to-throw-insert\">safeguard</a> kicking in.</p>\n<p>Frequent inserts work as before. They will be delayed and combined:</p>\n<p><span><img alt=\"04.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F04_31798ba4da.png&w=2048&q=75\"></span></p>\n<p>When ClickHouse receives insert query 1 after a period of no insert activity for a table, the buffer flush timeout counter starts with a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert-busy-timeout-min-ms\">minimal value</a>, which is automatically adjusted <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert-busy-timeout-increase-rate\">up</a> to a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert-busy-timeout-max-ms\">maximum value</a> when additional inserts occur frequently (and gets also adjusted back <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert-busy-timeout-decrease-rate\">down</a> when the insert frequency decreases).</p>\n<p>In summary, frequent inserts work as before. They will be delayed and combined together. Infrequent inserts, however, will not be delayed much and behave like synchronous inserts.  \\\nYou can just enable async insert and stop worrying. 😀</p>\n<p>Let’s demonstrate this with an example.
