With our new query analysis and optimization infrastructure, now <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-24-03#analyzer-enabled-by-default\">enabled</a> by default, we finally have everything in place to introduce long-awaited and powerful features like recursive CTEs.</p>\n<p>ClickHouse recursive CTEs <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Hierarchical_and_recursive_queries_in_SQL\">have</a> the standard SQL:1999 syntax and <a target=\"_blank\" href=\"https://www.youtube.com/live/dtUqgcfOGmE?si=Dzg93iQE3a5XCutn&t=2813\">pass</a> all PostgreSQL tests for recursive CTEs. Furthermore, ClickHouse now has better support for recursive CTEs than PostgreSQL. Inside the CTE’s UNION ALL clause’s bottom part, multiple (arbitrarily complex) queries can be specified, the CTE base table can be referenced multiple times, etc.</p>\n<p>Recursive CTEs can solve hierarchical problems elegantly and simply. For example, they can easily answer reachability questions for <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Hierarchical_database_model\">hierarchical data models</a> (e.g. trees and graphs) .</p>\n<blockquote>\n<p>Specifically, recursive CTEs can calculate <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Transitive_closure\">transitive closures</a> of relations. With the <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/London_Underground\">London Underground</a>'s tube connections as a binary relation example, you can imagine the set of all directly connected tube stations: <code>Oxford Circus -&gt; Bond Street</code>, <code>Bond Street -&gt; Marble Arch</code>, <code>Marble Arch -&gt; Lancaster Gate</code>, and so on. The transitive closure of those connections includes all possible connections between these stations, e.g. <code>Oxford Circus -&gt; Lancaster Gate</code>, <code>Oxford Circus -&gt; Marble Arch</code>, and so on.</p>\n</blockquote>\n<p>To demonstrate this, we use an adapted version of a <a target=\"_blank\" href=\"https://github.com/nicola/tubemaps/blob/master/datasets/london.connections.csv\">data set</a> modeling all London Underground connections where each entry represents two directly connected stations. Then, we can use a recursive CTE to answer questions like this easily:</p>\n<p><strong>When starting at <a target=\"_blank\" href=\"https://tfl.gov.uk/tube/stop/940GZZLUOXC/oxford-circus-underground-station\">Oxford Circus station</a> on the <a target=\"_blank\" href=\"https://www.london-tube-map.info/central-line/\">Central Line</a>, which stations can we reach with a maximum of five stops?</strong></p>\n<p>We visualize this with a screenshot of the Central Line station map:</p>\n<p><span><img alt=\"unnamed2.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Funnamed2_16f66d4149.png&w=2048&q=75\"></span></p>\n<p>We create a ClickHouse table for storing the London Underground connections data set:</p>\n<div><pre><code><span><span>CREATE</span> <span>OR</span> REPLACE <span>TABLE</span> Connections (</span>\n<span>    Station_1 String,</span>\n<span>    Station_2 String,</span>\n<span>    Line String,</span>\n<span>    <span>PRIMARY KEY</span>(Line, Station_1, Station_2)</span>\n<span>);</span></code></pre></div>\n<blockquote>\n<p>An attentive reader will have recognized that we didn’t specify a table engine in the DDL statement above (this is possible since ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/whats-new/changelog#improvement-1\">24.3</a>) and used PRIMARY KEY syntax in the column definition (possible since ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/whats-new/changelog/2023#new-feature-5\">23.7</a>). that stops self-joining once no new join partners are found or an abort condition is met. For this, our CTE above starts with executing the <code>UNION ALL</code> clause’s top part, querying our <code>Connections</code> table for all stations directly connected to the <code>Oxford Circus</code> station on the <code>Central Line</code>. This will return a table that is bound to the <code>Reachable_Stations</code> identifier and looks like this:</p>\n<div><pre><code><span>Initial Reachable_Stations table content</span>\n<span> ┌─Station_1─────┬─Station_2────────────┐</span>\n<span> │ Oxford Circus │ Bond Street          │</span>\n<span> │ Oxford Circus │ Tottenham Court Road │</span>\n<span> └───────────────┴──────────────────────┘</span></code></pre></div>\n<p>From now on, only the CTE’s <code>UNION ALL</code> clause’s bottom part will be executed (recursively):</p>\n<p><code>Reachable_Stations</code> is joined with the <code>Connections</code> table to find the following join partners within the <code>Connections</code> table whose <code>Station_1</code> value matches the <code>Station_2</code> value of  <code>Reachable_Stations</code>:</p>\n<div><pre><code><span>Connections table join partners</span>\n<span></span>\n<span>┌─Station_1────────────┬─Station_2─────┐</span>\n<span>│ Bond Street          │ Marble Arch   │</span>\n<span>│ Bond Street          │ Oxford Circus │</span>\n<span>│ Tottenham Court Road │ Holborn       │</span>\n<span>│ Tottenham Court Road │ Oxford Circus │</span>\n<span>└──────────────────────┴───────────────┘</span></code></pre></div>\n<p>Via the <code>UNION ALL</code> clause, these join partners are added to the <code>Reachable_Stations</code> table (with the <code>Station_1</code> column replaced by <code>Oxford Circus</code>), and the first iteration of our recursive CTE is complete. In the next iteration, by executing the CTE’s <code>UNION ALL</code> clause’s bottom part, <code>Reachable_Stations</code> is again joined with the <code>Connections</code> table to identify (and add to <code>Reachable_Stations</code>) all NEW  join partners within the <code>Connections</code> table whose <code>Station_1</code> value matches the <code>Station_2</code> value of  <code>Reachable_Stations</code>. These iterations continue until no new join partners are found or a stop condition is met. In our query above, we use a <code>stops</code> counter to abort the CTE’s iteration cycle when our specified number of allowed stops from the start station is reached.</p>\n<p>Note that the result lists <code>Oxford Circus</code> as a reachable station from <code>Oxford Circus</code> with 2 and 4 stops. That is theoretically correct but not very practical, and caused by the fact that our query doesn’t mind any directions or cycles. We leave this as a fun exercise for the reader.</p>\n<p>As a bonus question, we are interested in how many stops it takes from the <code>Oxford Circus</code> station on the <code>Central Line</code> to reach the <code>Stratford</code> station.
