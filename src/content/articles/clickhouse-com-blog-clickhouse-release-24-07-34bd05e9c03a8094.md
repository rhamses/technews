One of these optimizations is <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/order-by#optimization-of-data-reading\">optimize_read_in_order</a>: If a query’s ORDER BY columns form a prefix of the table’s primary key, or if in a <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-24-07#merge-join-algorithm-for-asof-join\">full sorting merge join</a> the physical row order of one or both joined tables matches the join key sort order, the data can be read in disk order, and the sorting operation can be skipped. This is also generally beneficial for memory usage. Less memory is required as no full in-memory sort takes place. In addition, <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-faster-queries-with-projections-and-primary-indexes#utilize-indexes-for-preventing-resorting-and-enabling-short-circuiting\">short-circuiting</a> is possible when the query uses a LIMIT clause.</p>\n<p>The <code>optimize_read_in_order</code> optimization prevents data from being re-sorted but reduces the parallelism for reading the table data. <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#query-pipeline\">Normally</a>, the table data is split into non-overlapping ranges read (<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select#implementation-details\">streamed</a>) by <code>N</code> threads in parallel into the query engine for further processing (N is controlled by the  <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#max_threads\">max_threads</a> setting).</p>\n<p>The following diagram shows why this approach is not feasible for the <code>optimize_read_in_order</code> optimization:</p>\n<p><span><img alt=\"Blog-release-24.7.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_24_7_001_3974ac87bd.png&w=2048&q=75\"></span></p>\n<p>In the diagram above, we sketch some data parts belonging to a table whose rows on disk are sorted (per data part) by the <code>CounterID</code> column first. For this, the right-hand side table’s data can be split and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#description\">read in parallel by multiple threads</a>, but only a single thread can fill this data into the hash table, as hash tables are not <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Thread_safety\">thread-safe</a> for insertions. This can become a bottleneck for the JOIN runtime if the right-hand side table is large.</p>\n<p>The following diagram shows how the parallel hash join algorithm overcomes this bottleneck:</p>\n<p><span><img alt=\"Blog-release-24.7.003.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_24_7_003_05208133bc.png&w=2048&q=75\"></span></p>\n<p>In the algorithm’s ① build phase, the data from the right table is split and streamed in parallel by <code>N</code> streams (N is controlled by the  <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#max_threads\">max_threads</a> setting) to fill <code>N</code> hash tables in parallel. The rows from each stream are routed to one of the <code>N</code> hash tables by applying a hash function to the join keys of every row. The hash function for splitting the rows into hash tables differs from the one used internally in the hash tables.</p>\n<p>In the algorithm’s ② probe phase, data from the left table is split and streamed in parallel by <code>N</code> streams (again, <code>N</code> is controlled by the <code>max_threads</code> setting). The same ‘bucket hash function’ from step ① is applied to the join keys of each row to determine the corresponding hash table, and the rows are joined by doing lookups into the corresponding hash table.</p>\n<p>To avoid wasting memory, hash tables are pre-allocated with a limited initial size. If a table runs full, a new larger hash table is allocated, data from the previous table is copied over, and the old table is deallocated. The larger size of the new hash table is always chosen by increasing the size of the previous table with an internal multiplier.</p>\n<p>In ClickHouse 24.7, when a parallel hash join is finished, the final sizes of hash tables are now collected and cached (with the JOIN’s right table name and names of the join columns used as input for the lookup key). In subsequent query executions, hash tables are pre-allocated based on their remembered size from previous query runs. This saves time by avoiding redundant intermediate resize steps. median_size<span>=</span><span>149909</span></span>\n<span>...</span></code></pre></div>\n<h2 id=\"merge-join-algorithm-for-asof-join\"></h2>\n<h3 id=\"contributed-by-vladimir-cherkasov\"></h3>\n<p>ClickHouse was the first SQL DBMS to introduce the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part1#asof-join\">ASOF JOIN</a> in April 2019.</p>\n<p>As a reminder, ASOF JOIN provides non-exact matching capabilities. If a row from the left table doesn’t have an exact match in the right table, then the closest matching row from the right table is used as a match instead.</p>\n<p>This is particularly useful for time-series analytics and can drastically reduce query complexity.</p>\n<p>Also, when <a target=\"_blank\" href=\"https://clickhouse.com/blog/modeling-machine-learning-data-in-clickhouse\">ClickHouse is used as a feature store</a> for machine learning, the ASOF JOIN is handy. It allows to <a target=\"_blank\" href=\"https://clickhouse.com/blog/modeling-machine-learning-data-in-clickhouse#joining-and-aligning-features\">easily combine the features</a> appropriately to produce a set of feature vectors.</p>\n<p>So far, ASOF JOIN only supported the memory-bound <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2#hash-join\">hash</a> and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part2#parallel-hash-join\">parallel hash</a> join algorithms.</p>\n<p>Since ClickHouse 24.7 ASOF JOIN also works with the non-memory bound <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part3#full-sorting-merge-join\">full sorting merge</a> join algorithm. As a reminder, the join strategy of that algorithm requires the joined data to first be sorted in order of the join keys before join matches can be identified by interleaved linear scans and merges of the sorted streams of blocks of rows from both tables:</p>\n<p><span><img alt=\"Blog-release-24.7.005.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_24_7_005_ab9826afde.png&w=2048&q=75\"></span></p>\n<p>The full sorting merge join can take advantage of the physical row order of one or both tables, allowing sorting to be skipped (plus benefiting from the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-24-07#optimizations-for-reading-in-order\">new optimizations for reading in order</a>, described in a section further above). In such cases, the join performance can be competitive with the hash join algorithms, while generally requiring significantly less memory. Otherwise, the full sorting merge join needs to fully sort the rows of the tables before identifying join matches. The sorting can occur in memory, and the memory usage generally is <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3#description\">independent</a> of the size of the joined tables.</p>\n<p>Let’s look at a concrete example.</p>\n<p>Imagine that we are tracking internet user’s website click events in a <code>hits</code> table and user sessions in a <code>sessions</code> table. Then, we can use ASOF JOIN to concisely formulate a query for  finding the first user click event for each session:</p>\n<div><pre><code><span>SELECT ... </span>\n<span>FROM hits h ASOF JOIN sessions s</span>\n<span>ON h.UserID = s.UserID AND h.EventTime &gt; s.StartTime;</span></code></pre></div>\n<p>We are simulating the <code>sessions</code> table with the <code>hits</code> table and reformulate the query from above to a self ASOF JOIN:</p>\n<div><pre><code><span>SELECT ... </span>\n<span>FROM hits t1 ASOF JOIN hits t2 </span>\n<span>ON t1.UserID = t2.UserID AND t1.EventTime &lt; t2.EventTime;</span></code></pre></div>\n<p>To run this query, we create the <code>hits</code> table using the <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickBench/blob/main/clickhouse/create.sql\">DDL statement</a> provided by <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickBench/tree/main?tab=readme-ov-file#clickbench-a-benchmark-for-analytical-databases\">ClickBench</a>.</p>\n<p>Next, we insert the data (100 million rows):</p>\n<div><pre><code><span>INSERT INTO hits SELECT * FROM s3('s3://clickhouse-public-datasets/hits_compatible/hits.parquet');</span></code></pre></div>\n<p>Now we are ready to run the ASOF join query from above with the default hash join algorithm:</p>\n<div><pre><code><span><span>SELECT</span> <span>count</span>() </span>\n<span><span>FROM</span> hits t1 ASOF <span>JOIN</span> hits t2 </span>\n<span><span>ON</span> t1.UserID <span>=</span> t2.UserID <span>AND</span> t1.EventTime <span>&lt;</span> t2.EventTime;</span>\n<span></span>\n<span>   ┌──<span>count</span>()─┐</span>\n<span><span>1.</span> │ <span>81878322</span> │ <span>-- 81.88 million</span></span>\n<span>   └──────────┘</span>\n<span></span>\n<span><span>1</span> <span>row</span> <span>in</span> set.
