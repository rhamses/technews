A projection typically has a different primary key than the original table (and, therefore, a different row order). it is also possible to pre-compute aggregate values in projections incrementally.</p>\n<p>When a user executes a query, ClickHouse chooses between reading from the original table or one of its projections. This is shown in the following diagram:</p>\n<p><span><img alt=\"0_24.8blog.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F0_24_8blog_599e91ec01.png&w=2048&q=75\"></span></p>\n<p>The decision to read from the original table or one of its projections is made individually per every table part. ClickHouse generally aims to read as little data as possible and employs a couple of tricks to identify the best part to read from, for example, sampling the primary key of a part. In some cases, source table parts have no corresponding projection parts. This can happen, for example, because creating a projection for a table in SQL is “lazy” by default - it only affects newly inserted data but keeps existing parts unaltered.</p>\n<p>The following diagram shows a more concrete example of a query that computes the maximum price of <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/uk-price-paid\">properties sold in the U.K.</a> grouped by town and street:</p>\n<p><span><img alt=\"1_24.8blog.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F1_24_8blog_6af7037dcc.png&w=2048&q=75\"></span></p>\n<p>As one of the projections already contains the pre-computed aggregate values, ClickHouse tries to read from the corresponding projection parts to avoid aggregating at query runtime again. If a specific part lacks the corresponding projection part, query execution falls back to the original part.</p>\n<p>But what happens if the rows in the original table change in a non-trivial way by non-trivial data part background merges?</p>\n<p>For example, assume the table is stored using ClickHouse’s <code>ReplacingMergeTree</code> table engine. If the same row is detected in multiple input parts during merge, only the most recent row version (from the most recently inserted part) will be kept, while all older versions will be discarded.</p>\n<p>Similarly, if the table is stored using the <code>AggregatingMergeTree</code> table engine, the merge operation may fold the same rows in the input parts (based on the primary key values) into a single row to update partial aggregation states.</p>\n<p>Before ClickHouse v24.8, projection parts either silently got out of sync with the main data, or certain operations like updates and deletes could not be run at all as the database automatically threw an exception if the table had projections.</p>\n<p>Since v24.8, a new table-level setting <code>deduplicate_merge_projection_mode</code> controls the behavior if the aforementioned non-trivial background merge operations occur in parts of the original table.</p>\n<p>Delete mutations are another example of part merge operations that drop rows in the parts of the original table. Since v24.7, we also have a setting to control the behavior w.r.t. delete mutations triggered by lightweight deletes: <code>lightweight_mutation_projection_mode</code>.</p>\n<p>Below are the possible values for both <code>deduplicate_merge_projection_mode</code> and<code> lightweight_mutation_projection_mode</code>:</p>\n<ul>\n<li>\n<p><code>throw</code>: an exception is thrown, preventing projection parts from going out of sync.</p>\n</li>\n<li>\n<p><code>drop</code>: affected projection table parts are dropped. Queries will fall back to the original table part for affected projection parts.</p>\n</li>\n<li>\n<p><code>rebuild</code>: the affected projection part is rebuilt to stay consistent with data in the original table part.</p>\n</li>\n</ul>\n<p>We demonstrate the <code>drop</code> behavior with two diagrams. The first diagram shows a row in the original table data part is deleted (by running a mutation merge operation). To prevent projection parts from becoming out-of-sync, the associated projection table data part is deleted:</p>\n<p><span><img alt=\"2_24.8blog.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F2_24_8blog_ef0b7cbcb8.png&w=2048&q=75\"></span></p>\n<p>The example aggregation query would still be able to run (albeit slower) - it will simply fall back to the original table part for parts where it cannot find projection parts. However, when a projection part still exists, query execution would prefer these over the original table parts:</p>\n<p><span><img alt=\"3_24.8blog.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F3_24_8blog_16a95e59fe.png&w=2048&q=75\"></span></p>\n<p>If <code>deduplicate_merge_projection_mode</code> is set to <code>rebuild</code>, ClickHouse will rebuild the projection table data part associated with the modified original table data part:</p>\n<p><span><img alt=\"4_24.8blog.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F4_24_8blog_3715c468bc.png&w=2048&q=75\"></span></p>\n<p>Note that this behavior is a significant advantage over incremental materialized views, which are similar to projections.
