Yet, as <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-24-05#cross-join-improvements\">promised</a>, we keep pushing join performance further in every release with <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/concepts/why-clickhouse-is-so-fast#meticulous-attention-to-detail\">meticulous</a> low-level optimizations.</p>\n<p>In version 24.7, we improved the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-24-07#faster-parallel-hash-join\">hash table allocation</a> for the parallel hash join. Since version 24.12, ClickHouse can <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-24-12#automatic-join-reordering\">automatically determine</a> which table in the join query should be used for the parallel hash join’s <code>build phase</code>. In 25.1, we’ve also sped up the algorithm's <code>probe phase</code>.</p>\n<p>To understand this improvement, let’s first briefly explain how the <code>build phase</code> and <code>probe phase</code> previously worked. This diagram illustrates the previous mechanics of the parallel hash join in ClickHouse (click to enlarge):</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/25_01_01_8cfbd11186.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F25_01_01_8cfbd11186.png&w=2048&q=75\"></span></a></p>\n<p>In the algorithm’s ① <strong>build phase</strong>, the data from the right table is split and processed in parallel by <code>N</code> processing threads to fill <code>N</code> hash table instances in parallel. <code>N</code> is controlled by the <code>max_threads</code> setting, which is <code>4</code> in our example. Each processing thread runs a loop:</p>\n<ol>\n<li>Load the next unprocessed block of rows from the right table.</li>\n<li>Apply an <code>instance hash function</code> (blue in the diagram) to the join keys of each row, then take the result modulo the number of threads to determine the target hash table instance.</li>\n<li>Apply an <code>insert hash function</code> (yellow in the diagram) to the join keys and use the result as the key to ② insert the row data into the selected hash table instance.</li>\n<li>Repeat from Step 1.</li>\n</ol>\n<p>In the algorithm’s ③ <strong>probe phase</strong>, data from the left table is split and processed in parallel by <code>N</code> processing threads (again, <code>N</code> is controlled by the <code>max_threads</code> setting). Each processing thread runs a loop:</p>\n<ol>\n<li>Load the next unprocessed block of rows from the left table.</li>\n<li>Apply the same <code>instance hash function</code> used in the build phase (blue in the diagram) to the join keys of each row, then take the result modulo the number of threads to determine the lookup hash table instance.</li>\n<li>Apply the same <code>insert hash function</code> used in the build phase (yellow in the diagram) to the join keys and use the result to perform a ④ lookup in the selected hash table instance.</li>\n<li>If the lookup succeeds and the join key values match, ⑤ return the joined rows.</li>\n<li>Repeat from Step 1.</li>\n</ol>\n<p>The parallel hash join’s <code>build phase</code> described above speeds up processing by concurrently filling multiple hash tables, making it faster than the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#hash-join\">non-parallel hash join</a>, which <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#description\">relies</a> on a single hash table.</p>\n<p>Since hash tables are not <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Thread_safety\">thread-safe</a> for concurrent inserts, the non-parallel hash join <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#description\">performs</a> all insertions on a single thread, which can become a bottleneck for larger tables in join queries. However, hash tables are thread-safe for concurrent reads, allowing the <code>probe phase</code> in the non-parallel hash join to read from a single hash table in parallel efficiently.</p>\n<p>In contrast, the parallel hash join’s concurrent <code>build phase</code> introduces overhead in the above-described <code>probe phase</code>, as input blocks from the left table must first be split and routed to the appropriate hash table instances.</p>\n<p>To address this, the <code>probe phase</code> now uses a single shared hash table that all processing threads can access concurrently, just like in the non-parallel hash join. This eliminates the need for input block splitting, reduces overhead, and improves efficiency.</p>\n<p>The next diagram illustrates the improved mechanics of the parallel hash join in ClickHouse (click to enlarge):</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/25_01_02_cb04311596.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F25_01_02_cb04311596.png&w=2048&q=75\"></span></a></p>\n<p>The  ① <strong>build phase</strong> is still executed concurrently. However, when <code>max_threads</code> is set to <code>N</code>, instead of filling <code>N</code> separate hash table instances in parallel, the process now uses <code>N</code> <a target=\"_blank\" href=\"https://clickhouse.com/blog/hash-tables-in-clickhouse-and-zero-cost-abstractions\">two-level hash table</a> instances. Their 256 buckets are filled concurrently by <code>N</code> processing threads, but in a non-overlapping manner:</p>\n<ul>\n<li>for <strong>hash table instance #0</strong>, the threads only fill <strong>bucket #0</strong>, <strong>bucket #<code>N</code></strong>, <strong>bucket #(<code>N</code> * 2)</strong>, …</li>\n<li>for <strong>hash table instance #1</strong>, the threads only fill <strong>bucket #1</strong>, <strong>bucket #<code>N</code> + 1</strong>, <strong>bucket #(<code>N</code> * 2 + 1)</strong>, …</li>\n<li>for <strong>hash table instance #2</strong>, the threads only fill <strong>bucket #2</strong>, <strong>bucket #<code>N</code> + 2</strong>, <strong>bucket #(<code>N</code> * 2 + 2)</strong>, …</li>\n<li>for <strong>hash table instance #3</strong>, the threads only fill <strong>bucket #3</strong>, <strong>bucket #<code>N</code> + 3</strong>, <strong>bucket #(<code>N</code> * 2 + 3)</strong>, …</li>\n<li>and so on…</li>\n</ul>\n<p>To achieve this, each processing thread runs a loop:</p>\n<ol>\n<li>Load the next unprocessed block of rows from the right table.</li>\n<li>Apply an <code>insert hash function</code> (yellow in the diagram) to the join keys of each row, then take the result modulo <code>256</code> to determine the target bucket number.</li>\n<li>Take the target bucket number from step 2 modulo the number of threads to determine the target two-level hash table instance.</li>\n<li>Use the result of the <code>insert hash function</code>  from step 1 as the key to ② insert the row data into the selected bucket number of the selected two-level hash table instance.</li>\n<li>Repeat from Step 1.</li>\n</ol>\n<p>Filling the buckets of the <code>N</code> two-level hash table instances without overlap during the build phase enables efficient (constant-time) ③ merging of these <code>N</code> instances into a single shared two-level hash table. This is efficient because merging simply involves placing all filled buckets into a new two-level hash table container without the need to combine entries across buckets.</p>\n<p>In the ④ <strong>probe phase</strong>, all <code>N</code> processing threads can then read from this shared two-level hash table concurrently, just like in the non-parallel hash join. Each processing thread runs a loop:</p>\n<ol>\n<li>Load the next unprocessed block of rows from the left table.</li>\n<li>Apply the same <code>insert hash function</code> used in the build phase (yellow in the diagram)  to the join keys of each row, then take the result modulo 256 to determine the bucket number for the lookup in the shared two-level hash table.</li>\n<li>Perform a ⑤ lookup in the selected bucket.</li>\n<li>If the lookup succeeds and the join key values match, ⑥ return the joined rows.</li>\n<li>Repeat from Step 1.</li>\n</ol>\n<p>Note that compared to the previous implementation, only a single hash function is now used in both the build and probe phases instead of two. The indirection introduced by the two-level hash table requires only lightweight modulo operations.</p>\n<p>To showcase the new parallel hash join's speed improvements, we first run a synthetic test on an AWS EC2 m6i.8xlarge instance with 32 vCPUs and 128 GiB RAM.</p>\n<p>We run this query on ClickHouse version 24.12:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    <span>count</span>(c),</span>\n<span>    version()</span>\n<span><span>FROM</span> numbers_mt(<span>100000000</span>) <span>AS</span> a</span>\n<span><span>INNER</span> <span>JOIN</span></span>\n<span>(</span>\n<span>    <span>SELECT</span></span>\n<span>        number,</span>\n<span>        toString(number) <span>AS</span> c</span>\n<span>    <span>FROM</span> numbers(<span>2000000</span>)</span>\n<span>) <span>AS</span> b <span>ON</span> (a.number <span>%</span> <span>10000000</span>) <span>=</span> b.number</span>\n<span>SETTINGS join_algorithm <span>=</span> <span>'parallel_hash'</span>;</span></code></pre></div>\n<div><pre><code><span>┌─count(c)─┬─version()──┐</span>\n<span>1. │ 20000000 │ 24.12.1.27 │</span>\n<span>   └──────────┴────────────┘</span>\n<span></span>\n<span>1 row in set.
