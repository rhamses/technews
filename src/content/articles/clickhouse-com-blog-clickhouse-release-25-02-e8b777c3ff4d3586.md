In the previous release, we optimized the <strong>probe phase</strong> of parallel hash joins. In this release, we revisited the <strong>build phase</strong> once <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-24-12#automatic-join-reordering\">more</a>, eliminating unnecessary CPU thread contention for fully unthrottled performance.</p>\n<p>In our previous release post, we provided a <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-01#faster-parallel-hash-join\">detailed explanation</a> of how the build and probe phases of the parallel hash join algorithm. As a reminder, during the <strong>build phase</strong>, <code>N</code> threads concurrently insert data from the right table of the join into <code>N</code> hash tables in parallel, row-block by row-block. Once that phase is complete, the <strong>probe phase</strong> begins, where <code>N</code> concurrent threads process rows from the left table, performing lookups into the hash tables populated during the build phase.</p>\n<p>The value of <code>N</code> is determined by the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#max_threads\">max_threads</a> setting, which defaults to the number of available CPU cores on the ClickHouse server executing the join.</p>\n<p>Additionally, ClickHouse offers two settings to control the size of hash tables in hash-based joins: <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/query-complexity#settings-max_rows_in_join\">max_rows_in_join</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/query-complexity#settings-max_bytes_in_join\">max_bytes_in_join</a>. By default, both are set to <code>0</code>, allowing unlimited hash table size. These limits help manage memory usage during joins, preventing excessive allocation. If a limit is reached, users can <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/query-complexity#settings-join_overflow_mode\">configure</a> ClickHouse to either abort with an exception (the default behavior) or return partial results based on the processed data.</p>\n<p>The following diagram refers to the <a target=\"_blank\" href=\"https://clickhouse.com/uploads/25_01_02_cb04311596.png\">full diagram</a> from the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-01#faster-parallel-hash-join\">previous</a> post and illustrates the parallel hash join’s <strong>build phase</strong> (with <code>max_threads</code> set to <code>4</code>), highlighting where these size limits are enforced to control memory usage:</p>\n<p><span><img alt=\"Blog-release-25.02.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_02_001_e9b5fd2515.png&w=2048&q=75\"></span></p>\n<p>Each processing thread runs a loop:</p>\n<p>① Load the next block of rows from the input table, and ② insert its rows into the hash tables as <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-01#faster-parallel-hash-join\">previously explained</a>.</p>\n<p>If ③ <code>max_rows_in_join</code> or <code>max_bytes_in_join</code> is set, the processing thread ④ retrieves the total row count and byte size from all hash table instances. To prevent concurrent modifications, the current processing thread <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Lock_(computer_science)\">locks</a> the mutex of each hash table sequentially, making other threads wait until the count is complete. If the row count or byte size exceeds the thresholds, the join is aborted.</p>\n<p>Until this version, the hash table size check in step ④ was always executed, even when no limit was set, causing threads to wait for each other and utilize only about 50% of CPU time.</p>\n<p>With the new check in step ③, this contention is eliminated, allowing the parallel hash join to fully utilize all CPU cores and complete faster.</p>\n<p>To better illustrate the improvement, we use a synthetic join query, which makes it easier to simulate a very large right-hand side table, focusing primarily on the build phase rather than the probe phase. Elapsed: 12.275 sec.
