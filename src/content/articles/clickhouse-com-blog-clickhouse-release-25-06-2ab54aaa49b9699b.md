This means that for the entire duration of the query, it will see the same data, even if new rows are inserted or existing rows are updated or deleted in parallel.</p>\n<p>At the core of this is the immutability of <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">table data parts</a>:</p>\n<ul>\n<li>\n<p><strong>Inserts</strong> always create new parts; existing data is never modified in place.</p>\n</li>\n<li>\n<p><strong>Deletes</strong> and <strong>updates</strong> are eventually applied via <em>mutations</em> or <em>part merges</em>, which generate new parts with the changes applied.</p>\n</li>\n</ul>\n<p>Because of this immutability, <strong>SELECT queries</strong> can safely work with a consistent snapshot of the relevant data parts at the time the query starts.</p>\n<p>The animation below illustrates this snapshot mechanism:</p>\n<p><span><img alt=\"Blog-release-25.6 - animation 01.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_6_animation_01_d2faa106c6.gif&w=2048&q=75\"></span></p>\n<p>① When ClickHouse receives a SELECT query <code>Q1</code> on table <code>t</code>, it identifies the relevant data parts during query planning and index analysis.</p>\n<p>② These parts are <strong>marked as referenced</strong> by the query.</p>\n<p>While Q1 is running, these changes can safely occur <strong>without affecting the result</strong>:</p>\n<p>③ A part is deleted<br>\n④ A new part is inserted<br>\n⑤ A part is mutated</p>\n<p>Thanks to the reference system, Q1 continues to read from the original snapshot and sees a <strong>fully consistent view</strong> throughout execution.</p>\n<p>Crucially, <strong>referenced parts are not deleted</strong> until all queries using them have completed. Once Q1 finishes, its references are released and old parts can be safely cleaned up.</p>\n<h3 id=\"the-problem-multiple-snapshots-for-subqueries\"></h3>\n<p>Before version 25.6, ClickHouse always took separate snapshots for each subquery or table reference, leading to possible inconsistencies:</p>\n<p><span><img alt=\"Blog-release-25.6 - animation 02.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_6_animation_02_5184ff1d1f.gif&w=2048&q=75\"></span></p>\n<p>① When ClickHouse receives a SELECT query with subqueries SQ1 and SQ2,</p>\n<p>② it determines data parts for SQ1, then separately for SQ2 (④).</p>\n<p>③ If a data part is inserted, deleted, or mutated in between,</p>\n<p>④ the subqueries may see inconsistent versions of the data.</p>\n<h3 id=\"the-fix-a-single-snapshot-for-the-whole-query\"></h3>\n<p>Since <strong>version 25.6</strong>, ClickHouse takes a <strong>single consistent snapshot</strong> across the entire query, even when it involves multiple subqueries or <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/select/with\">CTEs</a>. This ensures correctness for even the most complex SELECTs.</p>\n<p>This behavior is controlled by the setting <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#enable_shared_storage_snapshot_in_query\">enable_shared_storage_snapshot_in_query</a>:<br>\n<code>SET enable_shared_storage_snapshot_in_query = 1;</code></p>\n<p>When enabled, <strong>all subqueries share the same snapshot</strong> for each table:</p>\n<p><span><img alt=\"Blog-release-25.6 - animation 03.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_6_animation_03_ca1ea18825.gif&w=2048&q=75\"></span></p>\n<p>You can see the previous and this new behavior in action in the release call, where Alexey walks through a concrete example (click to open the recording at the right timecode):</p>\n<p><a target=\"_blank\" href=\"https://www.youtube.com/live/_9IBOM3pR4U?si=p6a4c47FaqbLqZBO&t=779\">\n  <span><img alt=\"Watch example in release call\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_6_003_5d4fbf3264.png&w=2048&q=75\"></span>\n</a></p><h2 id=\"filtering-by-multiple-projections\"></h2>\n<h3 id=\"contributed-by-amos-bird\"></h3>\n<p>ClickHouse supports several mechanisms to accelerate real-time analytics at scale. One particularly powerful feature is <strong>projections</strong>, automatically maintained, hidden tables that optimize query performance.</p>\n<p>A projection can have a different sort order (and thus a different <a target=\"_blank\" href=\"https://clickhouse.com/docs/primary-indexes\">primary index</a>) than the base table, and can even pre-aggregate data. When a query runs, ClickHouse automatically chooses the most efficient data path, whether from the base table or a projection, to minimize the amount of data read.</p>\n<p>Let’s walk through a simple example with a base table and two projections:</p>\n<div><pre><code><span><span>CREATE TABLE</span> page_views</span>\n<span>(</span>\n<span>    id UInt64,</span>\n<span>    event_date <span>Date</span>,</span>\n<span>    user_id UInt32,</span>\n<span>    url String,</span>\n<span>    region String,</span>\n<span>    PROJECTION region_proj</span>\n<span>    (</span>\n<span>        <span>SELECT</span> <span>*</span> <span>ORDER</span> <span>BY</span> region</span>\n<span>    ),</span>\n<span>    PROJECTION user_id_proj</span>\n<span>    (</span>\n<span>        <span>SELECT</span> <span>*</span> <span>ORDER</span> <span>BY</span> user_id</span>\n<span>    )</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (event_date, id);</span></code></pre></div>\n<p>The diagram below sketches the base table and its two projections:</p>\n<p><span><img alt=\"Blog-release-25.6.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_6_001_e17a0ef47b.png&w=2048&q=75\"></span></p>\n<p>① The base table <code>page_views</code> tracks website visits and is sorted by <code>(event_date, id)</code>. This defines its primary index, making queries that filter by those columns fast and efficient.</p>\n<p>② The <code>region_proj</code> projection stores the same data sorted by region. Its primary index speeds up queries filtering on that column.</p>\n<p>③ Similarly, <code>user_id_proj</code> stores the data sorted by user_id, optimizing for queries on that field.</p>\n<h3 id=\"two-key-limitations-now-improved\"></h3>\n<p>Previously, projections had two main limitations:</p>\n<ol>\n<li>\n<p><strong>Each projection duplicated the full base table data</strong>, leading to storage overhead.</p>\n</li>\n<li>\n<p><strong>Only one projection could be used per query</strong>, limiting optimization when multiple filters were involved.</p>\n</li>\n</ol>\n<h3 id=\"smarter-storage-with-part-offset\"></h3>\n<p>Since version 25.5, ClickHouse <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/78429\">supports</a> the <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/mergetree-family/mergetree#virtual-columns\">virtual column</a> <code>_part_offset</code> in projections. This unlocks a more space-efficient way to store projections.</p>\n<p>There are now two ways to define a projection:</p>\n<ol>\n<li>\n<p><strong>Store full columns</strong> (the original behavior): The projection contains full data and can be read directly, offering faster performance when filters match the projection’s sort order.</p>\n</li>\n<li>\n<p><strong>Store only the sorting key + _part_offset</strong>: The projection works like an index. ClickHouse uses the projection’s primary index to locate matching rows, but reads the actual data from the base table. This reduces storage overhead at the cost of slightly more I/O at query time.</p>\n</li>\n</ol>\n<p>You can also mix these approaches, storing some columns in the projection and others indirectly via _part_offset.</p>\n<p>The diagram below illustrates the second (index-like) approach:</p>\n<p><span><img alt=\"Blog-release-25.6.002.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_6_002_c451512aa5.png&w=2048&q=75\"></span></p>\n<p>① The base table now shows the virtual <code>_part_offset</code> column.</p>\n<p>② The <code>region_proj</code> and ③ <code>user_id_proj</code> projections store only their sorting key and _part_offset, referencing rows in the base table and significantly reducing data duplication.</p>\n<h3 id=\"combining-projections-in-one-query\"></h3>\n<p>Starting in <strong>version 25.6</strong>, building on the _part_offset support introduced in the previous version, ClickHouse <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/80343\">can</a> now use <strong>multiple projections</strong> to accelerate a single query with multiple filters.</p>\n<p>Importantly, ClickHouse still reads data from only one projection (or the base table), but can use other projections' primary indexes to prune unnecessary parts before reading.</p>\n<p>This is especially useful for queries that filter on multiple columns, each potentially matching a different projection.</p>\n<blockquote>\n<p>Currently, this mechanism only prunes entire parts. Granule-level pruning is not yet supported.</p>\n</blockquote>\n<p>To demonstrate this, we define the table (with projections using _part_offset columns) and insert five example rows matching the diagrams above.</p>\n<div><pre><code><span><span>CREATE TABLE</span> page_views</span>\n<span>(</span>\n<span>    id UInt64,</span>\n<span>    event_date <span>Date</span>,</span>\n<span>    user_id UInt32,</span>\n<span>    url String,</span>\n<span>    region String,</span>\n<span>    PROJECTION region_proj</span>\n<span>    (</span>\n<span>        <span>SELECT</span> _part_offset <span>ORDER</span> <span>BY</span> region</span>\n<span>    ),</span>\n<span>    PROJECTION user_id_proj</span>\n<span>    (</span>\n<span>        <span>SELECT</span> _part_offset <span>ORDER</span> <span>BY</span> user_id</span>\n<span>    )</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (event_date, id);</span>\n<span>SETTINGS</span>\n<span>    index_granularity <span>=</span> <span>1</span>, <span>-- one row per granule</span></span>\n<span>    max_bytes_to_merge_at_max_space_in_pool <span>=</span> <span>1</span>;
