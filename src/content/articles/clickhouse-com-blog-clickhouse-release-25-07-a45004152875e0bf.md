This is where each CPU core accumulates partial results, like sums and counts, for its slice of the data, which are later merged into the final answer.</p>\n<h3 id=\"why-partial-states-are-needed\"></h3>\n<blockquote>\n<p>Partial aggregation states are what make this highly parallel processing model possible, they allow each CPU core to work independently while still contributing to a correct final result.</p>\n</blockquote>\n<p>To understand why partial states are used, consider this query calculating average <a target=\"_blank\" href=\"https://clickhouse.com/docs/getting-started/example-datasets/uk-price-paid\">property prices per town</a>:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    town,</span>\n<span>    <span>avg</span>(price) <span>AS</span> avg_price</span>\n<span><span>FROM</span> uk_price_paid</span>\n<span><span>GROUP</span> <span>BY</span> town;</span></code></pre></div>\n<!-- -->\n<p>Suppose we want the average price in London using two CPU cores:</p>\n<p><span><img alt=\"Blog-release-25.7.004.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_7_004_d5a6838a81.png&w=2048&q=75\"></span></p>\n<p><strong>① Parallel processing and ② partial aggregation states</strong></p>\n<p>Lane 1 sees two London rows → sum = 500,000, count = 2</p>\n<p>Lane 2 sees one London row → sum = 400,000, count = 1</p>\n<p><strong>③ Merge into the ④ final state</strong></p>\n<p>Final avg = (500,000 + 400,000) / (2 + 1) = 300,000</p>\n<blockquote>\n<p>You <strong>must</strong> merge sums and counts, <strong>not intermediate averages</strong>, to avoid errors like:<br><br>(250,000 + 400,000) / 2 = 325,000 ← incorrect</p>\n</blockquote>\n<h3 id=\"how-group-by-aggregation-works-under-the-hood\"></h3>\n<p>Now let’s zoom in even further, into the <strong>internals of the aggregation stage</strong>. We’ll see how each processing lane maintains its own hash table and builds aggregation states independently.</p>\n<p>GROUP BY queries are processed independently by each lane using a hash aggregation algorithm: each lane maintains a <a target=\"_blank\" href=\"https://clickhouse.com/blog/hash-tables-in-clickhouse-and-zero-cost-abstractions\">hash table</a> where each key (e.g. town) points to an aggregation state.</p>\n<p>For our example, when a processing lane sees LONDON in the input:</p>\n<ul>\n<li>\n<p>If the key doesn’t exist in the ① hash table, a new entry is created and an aggregation state is allocated in a ② global memory arena. A <strong>pointer</strong> to that state is stored in the hash table.</p>\n</li>\n<li>\n<p>If it does exist, the pointer is used to <strong>look up and update</strong> the existing aggregation state in the arena.</p>\n</li>\n</ul>\n<p><span><img alt=\"Blog-release-25.7.005.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_7_005_0cd6d4a724.png&w=2048&q=75\"></span></p>\n<h3 id=\"optimization-for-count\"></h3>\n<p>Now, here’s where this release improves things.</p>\n<p>For this query:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    town,</span>\n<span>    <span>count</span>() <span>AS</span> count</span>\n<span><span>FROM</span> uk_price_paid</span>\n<span><span>GROUP</span> <span>BY</span> town;</span></code></pre></div>\n<!-- -->\n<p>…ClickHouse skips the memory arena entirely.</p>\n<p>Since count() is an <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Additive_function\">additive function</a>, it doesn’t require a complex aggregation state to correctly merge partial results across lanes. Count() only needs to store a single 64-bit integer (the count itself), which is no larger than a pointer on 64-bit systems, ClickHouse can:</p>\n<ul>\n<li>Store the count <strong>directly</strong> in the hash table cell</li>\n<li>Skip allocating space in the memory arena</li>\n<li>Skip pointer indirection</li>\n</ul>\n<p><span><img alt=\"Blog-release-25.7.006.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_7_006_89cd529cab.png&w=2048&q=75\"></span></p>\n<p>This avoids memory allocation and pointer chasing altogether, reducing CPU and memory overhead.</p>\n<p>In our tests, count() aggregations are now <strong>20–30% faster</strong> than before, with lower memory usage and fewer CPU cycles.</p>\n<h3 id=\"why-this-matters\"></h3>\n<p><strong>Count aggregations are everywhere</strong>: from dashboards ranking the most active users or <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#count-aggregations-in-clickhouse-and-elasticsearch\">most downloaded packages</a>, to alerting systems tracking unusual event frequencies.
