Where most databases force you to load files into a native format first, ClickHouse skips that step and still gives you full SQL: joins, window functions, 170+ aggregate functions, and more.</p>\n<p>Among these formats, <strong>Parquet plays a special role</strong> as the storage layer behind modern Lakehouse table formats like <strong>Iceberg</strong> and <strong>Delta Lake</strong>. That’s why in recent years we’ve heavily optimized for Parquet, as part of our mission to make ClickHouse the fastest engine in the world for querying it at scale.</p>\n<p>This release introduces a new and faster <strong>native Parquet reader</strong> in ClickHouse (currently experimental). Until now, the previous non-native reader relied on the <a target=\"_blank\" href=\"https://github.com/apache/arrow/tree/main/cpp\">Apache Arrow library</a>: Parquet files were parsed into <a target=\"_blank\" href=\"https://arrow.apache.org/\">Arrow</a> format, and <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/775b7d30c814bf9f28614b472d4ae8c10b39fa92/src/Processors/Formats/Impl/ArrowColumnToCHColumn.cpp\">copied</a> (in a streaming fashion) into ClickHouse’s native in-memory format for execution. The new native reader removes that extra layer, reading Parquet files <strong>directly into ClickHouse’s in-memory format</strong>, with better <strong>parallelism</strong> and <strong>I/O efficiency</strong>.</p>\n<blockquote>\n<p>Internally, we called it Yet Another Parquet Reader, because it really is the third. The first attempt (<code>input_format_parquet_use_native_reader</code>) was started but never finished. The second (v2) reached a pull request but stalled. Now, with v3, we finally have a fully integrated, native Parquet reader.</p>\n</blockquote>\n<p>Now let’s look at what this new reader unlocks: improved parallelism and more efficient I/O.</p>\n<h3 id=\"improved-parallelism\"></h3>\n<p>The diagram below (from our <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-and-parquet-a-foundation-for-fast-lakehouse-analytics\">earlier deep dive</a>) shows the physical on-disk structure of a Parquet file:</p>\n<p><span><img alt=\"Blog-release-25.8.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_8_001_4d2fc7259a.png&w=2048&q=75\"></span></p>\n<p>We won't go into much detail here (you can read the deep dive for that), just briefly:</p>\n<p><strong>Parquet files are hierarchical:</strong></p>\n<p><strong>① Row groups</strong> — horizontal partitions, typically ~1M rows / ~500 MB.<br>\n<strong>② Column chunks</strong> — vertical slices, one per column in each row group.<br>\n<strong>③ Pages</strong> — smallest unit, ~1 MB blocks of encoded values.</p>\n<p>With this layout in mind, ClickHouse parallelizes Parquet queries across available CPU cores.</p>\n<p>The old reader already supported <strong>scanning multiple row groups in parallel</strong>, but the new reader goes further:  Instead of only processing entire row groups in parallel, <strong>the new reader can read different columns from the same row group concurrently</strong>, enabling better CPU utilization when fewer row groups are available.</p>\n<p>And because the ClickHouse engine parallelizes almost every stage of query execution (filtering, aggregating, sorting), the new reader plugs seamlessly into an execution model that’s parallel from end to end:</p>\n<p><span><img alt=\"1_25.8-release.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F1_25_8_release_88a03c5498.png&w=2048&q=75\"></span></p>\n<p>① Prefetch threads — fetch multiple columns in parallel.<br>\n② Parsing threads — decode columns in parallel.<br>\n③ File streams — process different Parquet files concurrently.<br>\n④ Processing lanes — filter, aggregate, and sort across CPU cores in parallel.</p>\n<p><strong>Note that with the new reader, ① prefetching is smarter:</strong> it runs in a separate thread pool and only pulls what’s actually needed. For example, non-PREWHERE columns are prefetched only after <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/prewhere\">PREWHERE</a> is done, and we know which pages we'll need to read, eliminating wasted reads. <em>(We’ll talk more about PREWHERE in the next section.)</em></p>\n<p>Parallel processing of Parquet data boosts query performance, but the volume of data scanned also plays a huge role in speed. On that front, too, the new Parquet reader is more efficient!</p>\n<h3 id=\"improved-i-o-efficiency\"></h3>\n<p>While parallelism speeds up processing, smarter filtering reduces how much needs to be processed in the first place.</p>\n<p>The diagram below shows the metadata Parquet stores for filtering:</p>\n<p><span><img alt=\"Blog-release-25.8.003.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_8_003_8c3178fd05.png&w=2048&q=75\"></span></p>\n<p>① <strong>Dictionaries</strong> — map unique values for low-cardinality columns.<br>\n② <strong>Page stats</strong> — min/max values per page.<br>\n③ <strong>Bloom filters</strong> — per-column hints to skip irrelevant data.<br>\n④ <strong>Row group stats</strong> — min/max values for entire row groups.</p>\n<p>The previous ClickHouse Parquet reader already used <strong>row-group-level</strong> min/max and Bloom filters to avoid scanning irrelevant data.</p>\n<p>The new native reader adds <strong>page-level min/max filtering</strong> and support for <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/prewhere\"><strong>PREWHERE</strong></a>, making it even more efficient. We’ll demo that next.</p>\n<h3 id=\"parquet-reader-performance\"></h3>\n<p>The new Parquet reader generally improved the performance of <a target=\"_blank\"
