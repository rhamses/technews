For example, avg() keeps a local sum and count per key. These partial states are then ② merged and ③ finalized:</p>\n<p><span><img alt=\"image1.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fimage1_22f08c4ca7.gif&w=2048&q=75\"></span></p>\n<p>In the <strong>general</strong> case, ClickHouse uses a two-level hash table, where keys point to aggregation states stored in a shared memory arena:</p>\n<p><span><img alt=\"image4.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fimage4_47dbc05bee.png&w=2048&q=75\"></span></p>\n<p>In the general case, the merge step itself (② in the animation above) is <strong>parallelized across multiple merge threads</strong>.</p>\n<p><em>(Separately, if the query computes <strong>multiple aggregates</strong>, such as COUNT, SUM, or MAX, each aggregate maintains its own partial states, and their <strong>merges run in parallel with each other</strong>.)</em></p>\n<h3 id=\"but-group-by-is-heavily-specialized\"></h3>\n<p>ClickHouse does not use a single hash table implementation. It uses <a target=\"_blank\" href=\"https://clickhouse.com/blog/hash-tables-in-clickhouse-and-zero-cost-abstractions\"><strong>30+ specialized variants</strong></a>, automatically selected depending on:</p>\n<ul>\n<li>key type,</li>\n<li>expected cardinality,</li>\n<li>aggregation functions used,</li>\n<li>and other query characteristics.</li>\n</ul>\n<p>For example:</p>\n<ul>\n<li>\n<p>For <code>GROUP BY … count()</code>, ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-07#optimization-for-count\">skips</a> the memory arena entirely and stores counts directly inside the hash table cells.</p>\n</li>\n<li>\n<p>For queries grouping by small integer keys (8-bit, 16-bit), ClickHouse uses a highly optimized <strong>FixedHashMap</strong>, essentially an array indexed directly by the key value.</p>\n</li>\n</ul>\n<p>And this specialization is what matters here.</p>\n<p>While the merge step is parallel for the general two-level hash table, until this release the merge step was single-threaded when the aggregation used FixedHashMap.</p>\n<p>This meant that queries grouping on small integers (common in dimensional and categorical analytics) did not benefit from multi-threaded merging.</p>\n<h3 id=\"new-in-25-11-parallel-merge-for-fixedhashmap\"></h3>\n<p>ClickHouse 25.11 parallelizes the merge step for GROUP BY queries using small 8-bit and 16-bit keys. Each processing stream still builds its own FixedHashMap, but now the final merge can be performed by multiple threads working on disjoint regions of these maps.</p>\n<h3 id=\"example-averaging-price-per-property-type\"></h3>\n<p>Here’s an example using 8-bit keys: a query computing the average price per property type in <a target=\"_blank\" href=\"https://clickhouse.com/docs/getting-started/example-datasets/uk-price-paid\">the UK property prices dataset</a>:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    type,</span>\n<span>    <span>avg</span>(price) <span>AS</span> price_avg</span>\n<span><span>FROM</span> uk_price_paid</span>\n<span><span>GROUP</span> <span>BY</span> type</span></code></pre></div>\n<p>The type column <a target=\"_blank\" href=\"https://clickhouse.com/docs/getting-started/example-datasets/uk-price-paid#create-table\">is</a> an Enum8 ('terraced' = 1, 'semi-detached' = 2, 'detached' = 3, 'flat' = 4, 'other' = 0) and is <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/enum\">stored</a> internally as an 8-bit integer.</p>\n<p>When running the query above, each processing stream stores partial states in a FixedHashMap, an array indexed directly by the key. This gives extremely fast inserts/lookups and, crucially, lets multiple merge threads operate safely on <strong>different key ranges</strong> without lock contention.</p>\n<p>The three maps below show the partial avg states produced independently by three parallel streams (on a machine with three CPU cores).</p>\n<p><span><img alt=\"image7.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fimage7_a16fd688b4.png&w=2048&q=75\"></span></p>\n<p>ClickHouse then uses three parallel merge threads to combine these partial states. Each merge thread is assigned an ID (0–2) and processes only the positions corresponding to that ID. For example, thread 0 handles positions 0, 3, 6…, thread 1 handles 1, 4, 7…, and thread 2 handles 2, 5, 8….</p>\n<p>The diagram illustrates how the three threads (sketched with three different colors) merge corresponding entries across maps:</p>\n<p><span><img alt=\"image5.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fimage5_ecd1e64ff3.png&w=2048&q=75\"></span></p>\n<p>In practice, all partial maps are merged into a single result FixedHashMap: the merge threads write the final averages for each key into that map, and the design allows them to work on different portions safely in parallel (ordinary hash tables cannot support this because they are not <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Thread_safety\">thread-safe</a> for insertions).</p>\n<h3 id=\"performance-gains\"></h3>\n<p>This optimization is most noticeable for aggregation functions that require non-trivial merge operations. But because this index depends on the physical sort order of the table, <strong>each table can have only one primary index</strong>.</p>\n<p>To accelerate queries whose filters don't align with that single index, ClickHouse offers <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/alter/projection\"><strong>projections</strong></a> - automatically maintained, hidden table copies stored in different sort orders. Since release <strong>25.6</strong>, ClickHouse can create lightweight <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-06#filtering-by-multiple-projections\">projections that behave like secondary indexes</a> by storing only their sorting key plus a <a target=\"_blank\" href=\"https://clickhouse.com/docs/data-modeling/projections#smarter_storage_with_part_offset\">_part_offset</a> pointer back to the base table, greatly reducing storage overhead.</p>\n<p>Until now, this mechanism could only prune entire parts. With this release, _part_offset-based projections now support <strong>granule-level pruning</strong>, enabling much finer filtering and dramatically faster queries.</p>\n<p><strong>Results:</strong> On the UK price paid dataset with two lightweight projections (by_time and by_town), a query filtering on both date and town showed a <strong>90% speedup</strong> (0.010s vs 0.077s), reading only ~16k rows instead of scanning all ~30 million rows. ClickHouse used the primary indexes of <em>both</em> projections as secondary indexes to prune base table granules.</p>\n<p>Two new settings control this optimization:</p>\n<ul>\n<li><code>max_projection_rows_to_use_projection_index</code>: Maximum estimated rows to read from projection before applying its index</li>\n<li><code>min_table_rows_to_use_projection_index</code>: Minimum estimated table rows before considering projection index</li>\n</ul>\n<p>ClickHouse tables once had only <em>one</em> primary index. Now they can have <strong>many</strong>, each behaving like a primary index, and ClickHouse will use <em>all of them</em> when your query has multiple filters.</p>\n<p><strong><a target=\"_blank\" href=\"https://clickhouse.com/blog/projections-secondary-indices\">Read the full deep-dive on projections as secondary indices →</a></strong></p>\n<h2 id=\"speed-up-distinct-with-projections\"></h2>\n<h3 id=\"contributed-by-nihal-z-miaji\"></h3>\n<p>This release includes a second projection-based optimization.</p>\n<p>As described in the previous section, projections are automatically maintained, hidden table copies stored in a different sort order, or even in a pre-aggregated layout, to speed up queries that benefit from that data organization.</p>\n<p>When a query runs, ClickHouse automatically chooses the cheapest data path, reading either from the base table or from a projection to minimize the amount of data scanned.</p>\n<p>With this release, the same logic now accelerates DISTINCT queries as well: if retrieving all distinct values requires reading fewer rows from a projection, ClickHouse will automatically use it.</p>\n<p>A common way to reduce the number of rows needed for a DISTINCT is to define a projection that pre-aggregates the data using a GROUP BY that includes the distinct key.
