For larger LIMIT values, the overhead of these per-row lookups could outweigh the benefits of deferred I/O.</p>\n<p>For that reason, the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-gets-lazier-and-faster-introducing-lazy-materialization\">original lazy materialization blog post</a> noted:</p>\n<blockquote>\n<p>Note: Lazy materialization is applied automatically for LIMIT N queries, but only up to a N threshold. id=\"contributed-by-alexander-gololobov\"></h3>\n<p>Top-N queries got faster. Lazy reading got faster. And, unsurprisingly for a ClickHouse release, joins got faster as well. ClickHouse 25.12 ships with a simple  (for now) but more powerful join reordering algorithm for INNER JOINs - DPsize - that explores more join orders than the existing greedy approach, often producing more efficient execution plans with less intermediate data.</p>\n<h3 id=\"join-reordering-primer\"></h3>\n<p>As a quick <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-09#join-reordering\">reminder</a>, when multiple tables are joined, the join order does not affect correctness, but it can dramatically affect performance. Different join orders can produce vastly different amounts of intermediate data. Since ClickHouse’s default hash-based join algorithms build in-memory structures from one side of each join, choosing a join order that keeps build inputs small is critical for fast and efficient execution.</p>\n<h3 id=\"dpsize-join-reordering-algorithm\"></h3>\n<p><a target=\"_blank\" href=\"https://www.vldb.org/conf/2006/p930-moerkotte.pdf\">DPsize</a> is one of the classic join reordering algorithms and is used, often with variations, in many database systems, including PostgreSQL and IBM DB2.</p>\n<p>It can be considered the classical <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Dynamic_programming\">dynamic programming</a> approach (hence the name DPsize) that constructs the optimal join order based on a given cost model in a bottom-up fashion:</p>\n<ul>\n<li>It starts with the simplest plans: single tables.</li>\n<li>It then builds optimal plans for pairs of tables.</li>\n<li>Then for three tables, four tables, and so on.</li>\n<li>At each step, it constructs larger join plans by combining two already-optimal smaller subplans.</li>\n</ul>\n<p>You can think of it as gradually assembling the final join tree, increasing its size step by step while always reusing the cheapest plans found so far.</p>\n<p>The trade-off is optimize-cost:</p>\n<ul>\n<li>DPsize explores many more possible join orders than greedy algorithms.</li>\n<li>In practice, this means DPsize is more powerful, but also more optimizer-time expensive, than greedy reordering.</li>\n</ul>\n<p>This is why many systems historically default to greedy join ordering and only use DP-based approaches selectively.</p>\n<h3 id=\"dpsize-in-clickhouse-25-12\"></h3>\n<p>In ClickHouse 25.12, DPsize is introduced as an additional option for INNER JOIN reordering: a simple but more expressive algorithm that explores a richer set of join orders and can produce better execution plans for more complex join graphs.</p>\n<p>A new experimental setting controls what algorithms are used in which order, e.g. <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#query_plan_optimize_join_order_algorithm\">query_plan_optimize_join_order_algorithm</a>='dpsize,greedy' means that DPsize is tried first with fallback to greedy.</p>\n<h3 id=\"demonstration\"></h3>\n<p>Let’s see DPsize in action using the classic <a target=\"_blank\"
