However, creating and merging too many small parts is expensive, so <strong>inserts must be batched for optimal performance</strong>.</p>\n<p>\n  As <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#data-needs-to-be-batched-for-optimal-performance\">mentioned in the blog post initially introducing async inserts</a>:\n  Using ClickHouse is like driving a Formula One car 🏎. The power is there, but you need to be in the right gear for top insert speed.\n  Batching can be handled <em>manually</em> by the client or <em>automatically</em> by ClickHouse using <strong>asynchronous inserts</strong>, which perform server-side batching transparently.\n</p>\n<h3 id=\"why-batching-alone-is-not-enough\"></h3>\n<p>As also <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#idempotent-inserts\">described</a> in the original blog post introducing asynchronous inserts, batching alone is not sufficient in real-world ingestion pipelines. Inserts must also be <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Idempotence\"><strong>idempotent</strong></a><strong>.</strong> Network failures, timeouts, or node crashes can make it unclear whether an insert actually reached durable storage, forcing clients to retry the same insert.</p>\n<h3 id=\"automatic-deduplication-for-idempotent-inserts\"></h3>\n<p>ClickHouse has long <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/developer/deduplicating-inserts-on-retries#enabling-insert-deduplication-on-retries\">supported</a> <strong>automatic deduplication for idempotent inserts</strong> into tables using *MergeTree family engines. When enabled, ClickHouse assigns a deduplication identifier to each insert, either derived from a hash of the inserted data or explicitly provided by the client via an insert deduplication token. These identifiers are tracked in <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-keeper-a-zookeeper-alternative-written-in-cpp\">Keeper</a> and used to detect and ignore duplicate inserts on retries. This mechanism makes client-side batched inserts safe to retry without risking duplicate data.</p>\n<h3 id=\"deduplication-for-asynchronous-inserts\"></h3>\n<p>Asynchronous inserts build on the same foundation, but apply deduplication at <strong>flush time</strong> rather than per client request. Individual INSERTs are first collected in an in-memory buffer. When the buffer is flushed, ClickHouse computes <strong>one deduplication hash (or token) per source insert</strong> contained in the batch.</p>\n<h3 id=\"the-problem-with-dependent-materialized-views-before-26-1\"></h3>\n<p>However, prior to ClickHouse 26.1, this mechanism did not work reliably when tables had dependent <a target=\"_blank\" href=\"https://clickhouse.com/docs/materialized-view/incremental-materialized-view\"><strong>incremental materialized views</strong></a>. While the source table could correctly deduplicate retried async inserts, the transformed data written by materialized views could still be duplicated, making async inserts unsafe in pipelines that relied on views.</p>\n<p><strong>This release fixes that.</strong> Deduplication now works end-to-end for asynchronous inserts <em>and</em> their dependent materialized views. Retries are handled consistently across all tables involved, allowing async inserts to be safely retried without producing duplicate data, even in complex ingestion pipelines.</p>\n<p>To make this concrete, the following example shows how asynchronous inserts and retries are deduplicated end-to-end in the presence of a dependent materialized view.</p>\n<h3 id=\"example-deduplicated-asynchronous-inserts-with-a-materialized-view\"></h3>\n<p>We start with a simple base table that stores raw values:</p>\n<div><pre><code><span><span>CREATE TABLE</span> events</span>\n<span>(</span>\n<span>    <span>value</span> UInt64</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> <span>value</span>;</span></code></pre></div>\n<p>The target table for our materialized view stores the sum of all raw values inserted into the base table:</p>\n<div><pre><code><span><span>CREATE TABLE</span> events_mv_target</span>\n<span>(</span>\n<span>    sum UInt64</span>\n<span>)</span>\n<span>ENGINE <span>=</span> SummingMergeTree</span>\n<span><span>ORDER</span> <span>BY</span> tuple();</span></code></pre></div>\n<p>Our materialized view reacts to all inserts into the base table and writes the sum of newly inserted values into the target table. Because the target table uses a SummingMergeTree engine, partial aggregates written by the materialized view are combined incrementally via <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges#what-are-part-merges-in-clickhouse\">background data part merges</a>:</p>\n<div><pre><code><span><span>CREATE</span> MATERIALIZED <span>VIEW</span> events_mv</span>\n<span><span>TO</span> events_mv_target</span>\n<span><span>AS</span></span>\n<span><span>SELECT</span></span>\n<span>    <span>sum</span>(<span>value</span>) <span>AS</span> sum</span>\n<span><span>FROM</span> events;</span></code></pre></div>\n<p>With this schema in place, the diagrams below illustrate how asynchronous INSERTs are buffered, deduplicated, and written to both the base table and the materialized view target table. First for an initial batch, and then for a retry.</p>\n<h3 id=\"diagram-1-initial-asynchronous-inserts-with-a-dependent-materialized-view\"></h3>\n<p><span><img alt=\"image1.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fimage1_016bbc96cf.png&w=2048&q=75\"></span></p>\n<p>① Three independent INSERTs are buffered and ② flushed together as a single batch. During the flush, the buffered inserts are concatenated into one (or more) in-memory <a target=\"_blank\" href=\"https://clickhouse.com/docs/development/architecture#block\">blocks</a>, bounded by <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#max_insert_block_size\">max_insert_block_size</a>. ClickHouse computes one deduplication hash per source INSERT and carries these hashes alongside the data during insert processing.</p>\n<p>The resulting in-memory block is first handed over to ③ base table processing, where each deduplication hash is checked independently against the base table’s deduplication state in Keeper. Any duplicate mini-blocks are filtered out, after which the remaining data is sorted by the primary key and written in compressed form as a new base table <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">data part</a>.</p>\n<p>The same in-memory block and deduplication hashes are also handed over to ④ materialized view processing. Deduplication is performed independently for the materialized view target table, after which the data is transformed using the view’s SELECT query and written in compressed form as a data part in the materialized view target table.</p>\n<h3 id=\"diagram-2-retry-with-a-dependent-materialized-view\"></h3>\n<p><span><img alt=\"image3.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fimage3_68db2d67e5.png&w=2048&q=75\"></span></p>\n<p>① A second batch of asynchronous INSERTs is buffered, consisting of one retried INSERT and one new INSERT. ② When the buffer is flushed, ClickHouse computes deduplication hashes for both and detects that the retried INSERT has already been processed.</p>\n<p>During ③ base table processing, the mini-block corresponding to the retried INSERT is filtered out using the stored deduplication state in Keeper. Only the new data is sorted and written as a new base table data part.</p>\n<p>The same filtering happens independently during ④ materialized view processing. The retried mini-block is dropped <strong>before</strong> the materialized view transformation is applied, ensuring that only the new data contributes to the aggregated result.</p>\n<p><strong>Background merges</strong> are shown for completeness only; they are independent of asynchronous inserts and deduplication and <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges\">are</a> part of normal MergeTree operation.</p>\n<p><strong>Key takeaway</strong>: Deduplication is scoped per table in ClickHouse. Base tables and materialized views track duplicates independently. As a result, retries are filtered consistently across all tables involved, and materialized views never skip or duplicate data just because the base table saw it first.</p>\n<h2 id=\"new-syntax-for-indexing-projections\"></h2>\n<h3 id=\"contributed-by-amos-bird\"></h3>\n<p>In the ClickHouse 25.6 and 25.11 releases, we made <a target=\"_blank\" href=\"https://clickhouse.com/blog/projections-secondary-indices\">projections behave like true secondary indexes</a>. Instead of storing complete data copies, a projection can store only the sorting key plus a <code>_part_offset</code> pointer back into the base table, greatly reducing storage overhead.</p>\n<p>In the following schema, we create <code>by_time</code> and <code>by_town</code> projections using this technique:</p>\n<div><pre><code><span><span>CREATE</span> <span>OR</span> REPLACE <span>TABLE</span> uk.uk_price_paid_with_proj</span>\n<span>(</span>\n<span>    price UInt32,</span>\n<span>    ...</span>\n<span>    PROJECTION by_time (</span>\n<span>        <span>SELECT</span> _part_offset <span>ORDER</span> <span>BY</span> <span>date</span></span>\n<span>    ),</span>\n<span>    PROJECTION by_town (</span>\n<span>        <span>SELECT</span> _part_offset <span>ORDER</span> <span>BY</span> town</span>\n<span>    )</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (postcode1, postcode2, addr1, addr2);</span></code></pre></div>\n<p>In ClickHouse 26.1, we have a new syntax for indexing projections. We can define the <code>by_time</code> and <code>by_town</code> and projections like this instead:</p>\n<div><pre><code><span><span>CREATE</span> <span>OR</span> REPLACE <span>TABLE</span> uk.uk_price_paid_with_proj</span>\n<span>(</span>\n<span>    price UInt32,</span>\n<span>    ...</span>\n<span>    PROJECTION by_time INDEX <span>date</span> TYPE basic,    </span>\n<span>    PROJECTION by_town INDEX town TYPE basic</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (postcode1, postcode2, addr1, addr2);</span></code></pre></div>\n<h2 id=\"faster-distinct-over-lowcardinality-columns\"></h2>\n<h3 id=\"contributed-by-nihal-z-miaji\"></h3>\n<p>ClickHouse already treats <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/lowcardinality\">LowCardinality columns</a> as a first-class optimization target. In a recent release, we significantly <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-11#parallel-merge-for-small-group-by\">improved</a> <strong>GROUP BY</strong> performance for LowCardinality keys by parallelizing the aggregation merge phase, removing a long-standing bottleneck for small, fixed-key aggregations. <em>(The engineer behind that optimization also <a target=\"_blank\" href=\"https://clickhouse.com/blog/parallelizing-fixed-hashmap-aggregation-merge-in-clickhouse\">blogged</a> about his journey)</em></p>\n<p>In ClickHouse 26.1, <strong>DISTINCT</strong> joins GROUP BY as another operator that benefits from dedicated LowCardinality optimizations.</p>\n<p>This optimization was originally introduced as a Christmas engineering gift and is <a target=\"_blank\" href=\"https://clickhouse.com/blog/christmas-gifts-2025#optimize-distinct-transform-for-lowcardinality-columns\">described in more detail in the accompanying post</a>.</p>\n<p>At a high level: When a DISTINCT query operates on a LowCardinality column, ClickHouse can now avoid unnecessary work by operating directly on the column’s dictionary representation instead of materializing full values. This reduces CPU work, improves cache locality, and significantly speeds up DISTINCT queries on columns with a small number of unique values.</p>\n<p>Together, these optimizations make both GROUP BY and DISTINCT much faster on LowCardinality data, a common pattern in analytical workloads with dimensions such as status codes, categories, regions, or enums.</p>\n<h2 id=\"introspection-and-diagnostics-for-mergetree-tables-and-keeper\"></h2>\n<p>ClickHouse is designed to be deeply observable, using <a target=\"_blank\" href=\"https://clickhouse.com/blog/the-state-of-sql-based-observability\">SQL to observe</a> itself.
