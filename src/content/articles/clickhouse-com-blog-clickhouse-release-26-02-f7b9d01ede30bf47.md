id=\"user-content-faster-right-and-full-join\"></h2>\n<h3 id=\"user-content-contributed-by-yarik-briukhovetskyi\"></h3>\n<p>This release improves the performance of <strong>RIGHT OUTER</strong> and <strong>FULL OUTER JOINs</strong>, two of the many <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part1#join-types-supported-in-clickhouse\">join types</a> supported by ClickHouse.</p>\n<p>As a reminder, when a left table and a right table are joined:</p>\n<div><pre><code><span>SELECT...</span>\n<span><span>FROM</span> left_table <span>JOIN</span> right_table <span>ON</span> ...</span></code></pre></div>\n<p>a <strong>RIGHT OUTER JOIN</strong> also returns rows from the right_table that have no match on the left side, filling the left-table columns with default values.</p>\n<p>A <strong>FULL OUTER JOIN</strong> returns unmatched rows from both tables, filling the missing columns with default values on the respective side.</p>\n<p>These join types require additional work compared to inner or left joins, so to understand the optimization in this release, we first need to look at how ClickHouse executes joins internally.</p>\n<h3 id=\"user-content-join-pipeline-in-clickhouse\"></h3>\n<p>ClickHouse executes joins using a <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#parallel-hash-join\">parallel hash-join algorithm</a> by default, whose physical query plan (“query pipeline”) is sketched below.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FScreenshot_2026_03_16_at_11_36_59_e99ac8e95c.png&w=2048&q=75\"></span></p>\n<p>① The right table is partitioned into N buckets, which are processed by N threads in parallel (N = max_threads, by default the number of CPU cores, 2 in the example), with one in-memory hash table built per bucket.</p>\n<p>② The left table is partitioned the same way and processed in parallel, so matching rows reach the corresponding hash table.</p>\n<p>③ Rows are joined by probing the matching hash table, producing the final result.</p>\n<p>With this execution model in mind, the behavior of different OUTER JOIN types becomes easier to understand.</p>\n<h3 id=\"user-content-why-left-outer-join-is-cheap\"></h3>\n<p>In a <strong>LEFT OUTER JOIN</strong>, unmatched rows are naturally available in the pipeline.</p>\n<p>All rows from the left table are streamed (②) and probed against the hash tables (③).<br>\nIf no match is found, the row can immediately be emitted with default values for the right table columns.</p>\n<h3 id=\"user-content-why-right-full-outer-join-is-harder\"></h3>\n<p>For <strong>RIGHT OUTER JOIN</strong> and <strong>FULL OUTER JOIN</strong>, the situation is different.</p>\n<p>These joins must also return rows from the right table that never matched any left-side row.</p>\n<p>But the right table is consumed earlier when building the hash tables (①), so those rows are no longer visible in the main pipeline flow.</p>\n<p>To produce the final result, ClickHouse must iterate over the right table data and generate the rows that were never matched.</p>\n<h3 id=\"user-content-parallel-generation-of-unmatched-rows-262\"></h3>\n<p>Previously, this post-processing step ran in a single thread.</p>\n<p>Since 26.2, unmatched rows from the right table are generated in parallel, with one thread per right table bucket.</p>\n<p>This is controlled by a new <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#parallel_non_joined_rows_processing\">parallel_non_joined_rows_processing</a> setting (enabled by default).</p>\n<h3 id=\"user-content-a-quick-reminder-pruning-in-clickhouse\"></h3>\n<p>The fastest analytical queries are the ones that read the least data.</p>\n<p>Analytical workloads typically filter contiguous
