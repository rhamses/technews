To keep inserts <a target=\"_blank\" href=\"https://clickhouse.com/docs/concepts/why-clickhouse-is-so-fast#storage-layer-concurrent-inserts-are-isolated-from-each-other\">fast</a>, additional data processing is <a target=\"_blank\" href=\"https://clickhouse.com/docs/concepts/why-clickhouse-is-so-fast#storage-layer-merge-time-computation\">deferred</a> to <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges\">background part merges</a>.</p>\n<p>These merges run continuously, combining smaller parts into larger ones. In the process, ClickHouse not only improves data layout for <a target=\"_blank\" href=\"https://clickhouse.com/docs/primary-indexes\">data skipping</a>, but also performs maintenance work such as <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-1-purpose-built-engines\">replacing rows</a>, <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/developer/ttl\">deleting rows</a>, <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-2-sql-style-updates\">updating rows</a>, or <a target=\"_blank\" href=\"https://clickhouse.com/docs/materialized-view/incremental-materialized-view\">pre-aggregating data</a>.</p>\n<p>To perform merges efficiently, ClickHouse automatically selects one of two merge algorithms based on factors such as table width, number of rows, and data size:</p>\n<h3 id=\"1-horizontal-merge\"></h3>\n<ul>\n<li>\n<p>Reads and merges <strong>all columns together</strong>, block by block</p>\n</li>\n<li>\n<p>Writes the merged data back to disk</p>\n</li>\n</ul>\n<h3 id=\"2-vertical-merge\"></h3>\n<ul>\n<li>\n<p>Reads and merges <strong>only the sorting key columns first</strong></p>\n</li>\n<li>\n<p>Temporarily records the final row order for the remaining columns</p>\n</li>\n<li>\n<p>Then processes and writes <strong>remaining columns one by one</strong></p>\n</li>\n</ul>\n<p>To see the difference more clearly, let’s look at how each merge strategy works in practice.</p>\n<h3 id=\"horizontal-merge-simple-and-cpu-efficient\"></h3>\n<p>Horizontal merging is straightforward. Since all parts are already sorted by the same key, ClickHouse performs a single linear merge pass, similar to <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Merge_sort\">merge sort</a>:</p>\n<ul>\n<li>\n<p>Parts are read sequentially</p>\n</li>\n<li>\n<p>Rows are compared on the fly</p>\n</li>\n<li>\n<p>A new merged part is written</p>\n</li>\n</ul>\n<p>The animation below illustrates this using example data parts from a table with a sorting key <code>(town, street)</code>:</p></div><div><p>The animation shows the horizontal merge process in three steps:</p>\n<p><strong>① Merge blocks</strong></p>\n<p>Data from multiple parts is read in blocks and merged in memory based on the sorting key in a single linear merge pass. For simplicity, the animation shows full parts instead of block-by-block processing.</p>\n<p><strong>② Write blocks into a new part</strong></p>\n<p>The merged data is written into a new data part. Again, the animation shows this as a single step for simplicity.</p>\n<p><strong>③ Deactivate old parts</strong></p>\n<p>Once the merge is complete, the original parts are marked as inactive and eventually removed.</p>\n<blockquote>\n<p>For wide tables (e.g. 100+ columns), this approach can be memory-intensive.</p>\n</blockquote>\n<p>Because merges operate on row blocks, ClickHouse must load entire blocks of wide rows into memory. The wider the table, the more expensive this becomes.</p>\n<p>To address this, ClickHouse uses an alternative merge strategy.</p>\n<h3 id=\"vertical-merge-memory-optimized-for-wide-tables\"></h3>\n<p>Vertical merging reduces memory usage by processing columns separately.</p>\n<p>The animation below shows this for a table with a sorting key <code>(town, street)</code>. For simplicity, only one additional column <code>price</code> is shown; other columns are processed the same way.</p></div><div><p>The animation shows the vertical merge process in five steps:</p>\n<p><strong>① Merge sorting key columns first</strong></p>\n<p>Data from multiple parts is read block by block and merged in memory using the sorting key in a single linear pass. For simplicity, the animation shows full columns instead of several column-blocks.</p>\n<p><strong>② Record row order and write key columns</strong></p>\n<p>The resulting final row order is temporarily stored, and the merged sorting key columns are written to the new data part.</p>\n<p><strong>③ Merge next column by recorded row order</strong></p>\n<p>The remaining columns are processed one by one. For each column, data is read block by block from all parts and merged according to the previously recorded final row order. The animation illustrates this as a single step and for one column only.</p>\n<p><strong>This combination of column-by-column and block-by-block processing is what makes vertical merges memory efficient.</strong></p>\n<p><strong>④ Add column data to the new part</strong></p>\n<p>The merged column data is appended to the new data part after each column is processed.</p>\n<p><strong>⑤ Deactivate old parts</strong></p>\n<p>Once all columns are processed, the original parts are marked as inactive and eventually removed.</p>\n<blockquote>\n<p>This merge strategy is more efficient for wide tables, where loading all columns at once would be memory-expensive.</p>\n</blockquote>\n<p>In practice, ClickHouse uses vertical merges only when it is expected to be beneficial.</p>\n<h3 id=\"when-does-clickhouse-use-vertical-merge\"></h3>\n<p>With default settings, vertical merge becomes eligible when the to be merged parts contain at least <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/merge-tree-settings#vertical_merge_algorithm_min_rows_to_activate\">131,072 rows</a> in total or at least <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/merge-tree-settings#vertical_merge_algorithm_min_columns_to_activate\">11 non-primary-key columns</a>.</p>\n<p>In other words, for merges where the memory savings are expected to outweigh the extra bookkeeping, ClickHouse automatically switches to the more memory-efficient vertical merge algorithm.</p>\n<p>This is often the case in TTL-driven workloads, where large volumes of data accumulate over time and are often stored in wide tables.</p>\n<h3 id=\"efficient-ttl-deletes-for-wide-tables\"></h3>\n<p>In ClickHouse, you can define <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/developer/ttl\">TTL rules</a> to <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/mergetree-family/mergetree#mergetree-removing-expired-data\">automatically delete table data</a> after a certain period.</p>\n<p>This is particularly useful for data that naturally ages out, such as logs, events, telemetry streams, or rolling analytics datasets.</p>\n<p>These workloads typically accumulate large volumes of data over time, and in modern observability use cases, that data is often stored as <a target=\"_blank\" href=\"https://clickhouse.com/blog/breaking-free-from-rising-observability-costs-with-open-cost-efficient-architectures\">wide events</a>,  with <a target=\"_blank\" href=\"https://clickhouse.com/blog/scaling-observability-beyond-100pb-wide-events-replacing-otel\">each row containing a large number of attributes</a>.</p>\n<p>As a result, TTL-based deletions href=\"https://clickhouse.com/docs/knowledgebase/when_is_ttl_applied\">TTL DELETE is executed during background merges</a>, even though it doesn’t combine parts, instead reading individual parts, The diagram below shows how two rows inserted into a table with a tags column of type Map are stored on disk.</p>\n<p><span><img alt=\"Screenshot 2026-04-13 at 17.41.17.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FScreenshot_2026_04_13_at_17_41_17_78c89f50f9.png&w=2048&q=75\"></span></p>\n<p>As the diagram shows, a Map column is stored on disk as two separate arrays: one containing all keys and one containing the corresponding values. These arrays are paired with an offsets file, which maps entries back to the table rows they belong to.</p>\n<h3 id=\"the-limitation\"></h3>\n<p>In practice, queries usually access only a small subset of keys within a map. Because keys and values are stored as plain arrays without indexing, every lookup requires scanning the arrays, leading to unnecessary data reads.</p>\n<h3 id=\"the-solution\"></h3>\n<p>To address this, the new storage format splits map data into multiple sub-arrays by grouping keys into hash-based buckets. As a result, accessing a single key, such as <code>tags['status']</code>, requires reading only the corresponding bucket instead of the entire column.</p>\n<blockquote>\n<p>This significantly reduces the amount of data processed for common lookup patterns.</p>\n</blockquote>\n<h3 id=\"no-insert-penalty\"></h3>\n<p>Importantly, this optimization does not impact insert performance. New data is written using the existing format, and the bucketed layout is applied later during background merges.</p>\n<p>The next diagram sketches this for two inserts into a table with a tags column of type Map.</p>\n<p><span><img alt=\"Screenshot 2026-04-13 at 17.41.46.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FScreenshot_2026_04_13_at_17_41_46_9a3d02007a.png&w=2048&q=75\"></span></p>\n<p>The diagram shows three steps:</p>\n<p><strong>① Insert → Level 0 parts (default format)</strong></p>\n<p>Each insert creates a new <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">data part</a> using the standard Map layout: keys and values are stored as two flat arrays, without any bucketing.</p>\n<p><strong>② Another insert → another Level 0 part</strong></p>\n<p>A second insert produces another part in the same format. At this stage, all map data is still stored as full key and value arrays.</p>\n<p>Accessing a single key would require scanning the entire arrays, but this is typically <strong>not an issue since Level 0 parts are small</strong>.</p>\n<p><strong>③ Background merge → bucketed Map storage</strong></p>\n<p>During the next <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges\">background merge</a>, ClickHouse reorganizes the Map data by splitting keys into hash-based buckets. Each bucket stores a subset of keys and their corresponding values in smaller arrays.</p>\n<p>When accessing a key such as <code>tags['status']</code>, ClickHouse uses the hash of the key to locate the corresponding bucket (e.g., <code>bucket 3</code>) and reads only those arrays, significantly reducing the amount of data that needs to be scanned.</p>\n<h3 id=\"performance-impact\"></h3>\n<p>In practice, this results in 2–49x faster single-key lookups depending on map size.</p>\n<h3 id=\"configuration\"></h3>\n<p>This behavior is controlled by the new <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/merge-tree-settings#map_serialization_version\">map_serialization_version</a> MergeTree setting set to <code>with_buckets</code>, and <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/merge-tree-settings#max_buckets_in_map\">max_buckets_in_map</a> specifies into how many buckets the data is split at a maximim (<code>32</code> by default).</p>\n<p>Additional settings further control the exact layout.
