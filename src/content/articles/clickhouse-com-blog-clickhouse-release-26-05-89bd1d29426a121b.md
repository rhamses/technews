As covered in our dedicated <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-top-n-queries-granule-level-data-skipping\">Top-N optimization post</a>, ClickHouse has accumulated several engine-level optimizations for queries with ORDER BY … LIMIT, including streaming execution, read-in-order, lazy reading, and data-skipping-based Top-N pruning.</p>\n<p>This release extends the same idea to another shape: GROUP BY … LIMIT queries without ORDER BY.</p>\n<p>Consider a query that groups by a key and then applies <code>LIMIT</code>, but has no <code>ORDER BY</code>, no <code>HAVING</code> clause, and no window function. In that case, the query does not ask for the smallest keys, the largest keys, the most frequent keys, or keys in any particular order. It only asks for <strong>any N distinct grouping keys</strong>.</p>\n<p>For example, because we already had the TPC-H dataset loaded for the previous section’s benchmark, we can reuse it here. This query asks for any 100 distinct order keys from the <code>lineitem</code> table:</p>\n<div><pre><code><span><span>SELECT</span> l_orderkey</span>\n<span><span>FROM</span> lineitem</span>\n<span><span>GROUP</span> <span>BY</span> l_orderkey</span>\n<span>LIMIT <span>100</span>;</span></code></pre></div>\n<h3 id=\"from-group-everything-then-limit-to-keep-only-n-groups\"></h3>\n<p>In TPC-H scale factor 100, <code>lineitem</code> contains 600 million rows and 150 million distinct <code>l_orderkey</code> values.</p>\n<p>Without the new optimization, ClickHouse treats the query like a regular <code>GROUP BY</code>: as it scans the input, every new <code>l_orderkey</code> creates a new entry in the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-parallel-replicas#how-clickhouse-makes-group-by-fast\">aggregation hash table</a>. Only after the aggregation result has been built does <code>LIMIT 100</code> reduce the output to 100 rows.</p>\n<p><span><img alt=\"Blog-release-26.05.003.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_26_05_003_03f393fa9d.png&w=2048&q=75\"></span></p>\n<p>With this release, ClickHouse recognizes this special pattern and avoids building groups that cannot affect the result. The optimization is controlled by the new <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#optimize_trivial_group_by_limit_query\"><code>optimize_trivial_group_by_limit_query</code></a> setting, which is enabled by default.</p>\n<p>For eligible queries, ClickHouse internally sets the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#max_rows_to_group_by\">aggregation limit</a> to <code>LIMIT + OFFSET</code> and uses <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#group_by_overflow_mode\"><code>group_by_overflow_mode</code></a> <code>= 'any'</code>. In practice, this means that once the aggregation hash table contains the first 100 distinct <code>l_orderkey</code> values, new keys are ignored instead of being added as new groups.</p>\n<p><span><img alt=\"Blog-release-26.05.004.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_26_05_004_0dabca7c6d.png&w=2048&q=75\"></span></p>\n<p>The scan still processes the input, but the aggregation state in main memory stays tiny: 100 groups instead of growing toward 150 million.</p>\n<h3 id=\"benchmark-11-9-faster-and-185-less-memory\"></h3>\n<p>To evaluate the impact, we ran the query again on an AWS EC2 m6i.8xlarge instance with 32 vCPUs and 128 GiB RAM.
