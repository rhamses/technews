The second makes the build-side hash tables themselves smaller.</p>\n<p>As shown above, ClickHouse inserts right-side rows into in-memory hash tables during the build phase. Each hash-table entry carries a reference to its corresponding row. In 26.7, ClickHouse stores that reference as a compact, <strong>8-byte index-based value for every key type</strong>.</p>\n<p>As a result, hash-table entries for <code>ALL</code> joins are now as compact as those for <code>ANY</code> joins, reducing memory consumption and improving cache efficiency.</p>\n<p>Across joins containing 100–300 million rows, the change produced a median <strong>12% speedup</strong> and <strong>15% lower peak memory usage</strong>. ClickHouse has also supported automatic reordering across larger join graphs for some time.</p>\n<p>As described in more detail <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fast-joins#statistics-based-join-reordering\">here</a>, ClickHouse uses column statistics to estimate the sizes of intermediate results and select a good join tree. Until now, it could use exhaustive <code>dpsize</code> search for smaller join graphs or the faster <code>greedy</code> algorithm for larger ones.</p>\n<p>26.7 adds a third option: <code>dpsub</code>, which uses dynamic programming over table subsets:</p>\n<div><pre><code><span>SET query_plan_optimize_join_order_algorithm = 'dpsub';</span></code></pre></div>\n<!-- -->\n<p><code>dpsub</code> considers all valid join orders and selects the lowest-cost plan, with lower optimization overhead than <code>dpsize</code>. It also supports non-inner joins.</p>\n<p>Algorithms can be chained to provide a fallback:</p>\n<div><pre><code><span>SET query_plan_optimize_join_order_algorithm = 'dpsub,greedy';</span></code></pre></div>\n<!-- -->\n<p>ClickHouse tries them in order and falls back when an algorithm cannot handle the query.</p>\n<h2 id=\"faster-vector-search-with-qbit\"></h2>\n<p>Vector search finds semantically similar items - such as related documents, products, or images - by comparing their embeddings: high-dimensional numerical representations of the underlying data.</p>\n<p>ClickHouse 26.7 introduces several improvements for searching these vectors more efficiently: <code>Int8</code> support for <code>QBit</code>, strided storage for reading fewer dimensions, randomized Hadamard rotations for better quantization, and quantization codecs for fast two-stage searches. We explore each of them below.</p>\n<p>The best way to understand these improvements is to see them in action. Alexey Milovidov built<a target=\"_blank\" href=\"https://embeddings.info/\"> embeddings.info</a>, an interactive, ClickHouse-powered explorer of millions of image embeddings.</p>\n<p><span><img alt=\"623612659-58de543d-aa71-41f5-872a-5d8202c5e420.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F623612659_58de543d_aa71_41f5_872a_5d8202c5e420_400b7737c7.png&w=2048&q=75\"></span></p>\n<p>Select an image to find its nearest neighbors, then change the embedding model, numerical representation, rotation, bit precision, or number of dimensions and observe the effect on search speed and quality. The complete implementation and data pipelines are available in the<a target=\"_blank\" href=\"https://github.com/ClickHouse/embeddings\"> ClickHouse/embeddings repository</a>.</p>\n<p>First, a quick <code>QBit</code> refresher. <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-10#qbit-data-type\">Introduced</a> in ClickHouse 25.10 and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-26-02#user-content-production-ready-text-index-and-qbit-data-type\">production-ready</a> since 26.2, <code>QBit</code> is a data type <a target=\"_blank\" href=\"https://clickhouse.com/blog/qbit-vector-search\">designed</a> for storing vector embeddings:</p>\n<div><pre><code><span><span>CREATE TABLE</span> vectors</span>\n<span>(</span>\n<span>    id UInt64,</span>\n<span>    name String,</span>\n<span>    vec QBit(BFloat16, <span>1536</span>),</span>\n<span>    ...</span>\n<span>)</span>\n<span><span>ORDER</span> <span>BY</span> (...);</span></code></pre></div>\n<!-- -->\n<p>Here, <code>QBit(BFloat16, 1536)</code> stores a 1,536-dimensional embedding whose coordinates use the <code>BFloat16</code> type.</p>\n<p>What makes <code>QBit</code> special is that a query can choose how precisely to read those vectors. <code>BFloat16</code> uses 16 bits per coordinate, and <code>QBit</code> organizes those bits into independently readable planes, from the most to the least significant. A distance query can therefore read only the first N planes:</p>\n<div><pre><code><span><span>SELECT</span> id, name</span>\n<span><span>FROM</span> vectors</span>\n<span><span>ORDER</span> <span>BY</span> L2DistanceTransposed(vec, target, <span>10</span>)</span>\n<span>LIMIT <span>10</span>;</span></code></pre></div>\n<!-- -->\n<p>The final argument instructs ClickHouse to use the 10 most significant bits out of 16. Reading fewer bits means less I/O and faster distance calculations; reading more provides greater precision and recall.</p>\n<p>This matters at scale. One billion 1,536-dimensional <code>BFloat16</code> vectors contain roughly 3 TB of uncompressed numerical data. Reading 10 rather than all 16 bit planes reduces the vector data read by 37.5%. A query can go further - down to eight or four bits - when speed matters more than perfect recall.</p>\n<p>Using fewer bits inevitably loses some information. So how can we preserve more search quality at lower precision?</p>\n<p>That brings us to the first QBit improvement in 26.7: <code>Int8</code> quantization.</p>\n<h2 id=\"qbit-flexible-int8-quantization\"></h2>\n<h3 id=\"contributed-by-alexey-milovidov\"></h3>\n<p>Reading fewer bit planes makes vector search faster, but it also discards information. ClickHouse 26.7 adds a more efficient starting point: embeddings can now be quantized to <code>Int8</code> and stored directly in <code>QBit</code>.</p>\n<p><strong>For non-mathematical readers</strong>: <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Quantization\">Quantization</a> represents embedding values with fewer bits, reducing storage and speeding up distance calculations while preserving as much search accuracy as possible.</p>\n<p><code>QBit(Int8, N)</code> preserves QBit’s runtime flexibility. The data is stored as eight bit planes, and each query can choose any precision from a binary representation using one bit to the full eight bits.</p>\n<p>ClickHouse’s Int8 quantizer uses 256 non-uniform buckets designed for Gaussian-distributed embedding coordinates. Their boundaries are tuned to minimize the mean-squared error of distance calculations over quantized data. This requires no data scan, distribution estimation, or per-dataset calibration. The specialized <code>quantizeBFloat16ToInt8</code> and <code>dequantizeInt8ToBFloat16</code> functions expose this functionality:</p>\n<div><pre><code><span><span>CREATE TABLE</span> images</span>\n<span>(</span>\n<span>    id UInt64,   </span>\n<span>    emb QBit(Int8, <span>2048</span>),</span>\n<span>    ...</span>\n<span>)</span>\n<span><span>ORDER</span> <span>BY</span> (...);</span>\n<span></span>\n<span><span>INSERT INTO</span> images</span>\n<span><span>SELECT</span></span>\n<span>    id,</span>\n<span>    quantizeBFloat16ToInt8(embedding <span>*</span> <span>sqrt</span>(<span>2048</span>)),</span>\n<span>    ...</span>\n<span><span>FROM</span> src;</span></code></pre></div>\n<!-- -->\n<p>For unit-normalized embeddings, multiplying by the square root of the dimensionality brings the coordinates to the scale expected by the quantizer.\nQueries can then select their precision at runtime:</p>\n<div><pre><code><span><span>SELECT</span> id</span>\n<span><span>FROM</span> images</span>\n<span><span>ORDER</span> <span>BY</span> cosineDistanceTransposedQuantized(emb, target, <span>4</span>)</span>\n<span>LIMIT <span>10</span>;</span></code></pre></div>\n<!-- -->\n<p>Here, ClickHouse reads only the four most significant bit planes, half the vector data required by the full eight-bit representation. The distance function interprets the quantized values directly, reconstructing them as part of the calculation.\nThe same stored vectors therefore support everything from 1-bit binary quantization to full 8-bit precision. On the tested datasets, using all eight bits achieved roughly 99–99.5% recall, while lower precisions provide progressively larger I/O savings.\nBit precision is only one way to reduce the work. The next improvement lets ClickHouse read fewer vector dimensions as well.</p>\n<h2 id=\"qbit-read-fewer-dimensions-with-strided-storage\"></h2>\n<h3 id=\"contributed-by-alexey-milovidov\"></h3>\n<p>Bit planes let a query control how many bits it reads from each vector coordinate. ClickHouse 26.7 adds a second control: how many dimensions it reads.</p>\n<p>An optional third <code>QBit</code> parameter - the stride - divides a vector’s dimensions into independently readable groups</p>\n<div><pre><code><span>emb QBit(Int8, <span>1024</span>, <span>256</span>)</span></code></pre></div>\n<!-- -->\n<p>This stores the 1,024 dimensions as four groups of 256. Within each group, the eight <code>Int8</code> bit planes are stored as separate on-disk streams:</p>\n<p><span><img alt=\"Screenshot 2026-08-05 at 12.21.14.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FScreenshot_2026_08_05_at_12_21_14_bbbf452a64.png&w=2048&q=75\"></span></p>\n<p>A query can therefore select both its bit precision and the number of dimensions:</p>\n<div><pre><code><span>...<span>ORDER</span> <span>BY</span> cosineDistanceTransposedQuantized(</span>\n<span>    emb,</span>\n<span>    target,</span>\n<span>    <span>4</span>,     <span>-- read four bit planes</span></span>\n<span>    <span>256</span>    <span>-- read the first 256 dimensions</span></span>\n<span>)</span></code></pre></div>\n<!-- -->\n<p>This query reads only four bits from the first quarter of the vector: four of the 32 available streams. That is approximately 3% of the equivalent Float32 vector payload.</p>\n<p>Strided storage is particularly useful for embeddings trained with<a target=\"_blank\" href=\"https://arxiv.org/abs/2205.13147\"> Matryoshka Representation Learning</a>. These models arrange information so that prefixes of the vector - such as the first 256 or 512 dimensions - remain useful representations on their own. Queries can therefore trade some recall for substantially less I/O and faster distance calculations without storing several versions of each embedding.</p>\n<p>QBit can now vary both the number of bits and the number of dimensions read.</p>\n<p>The next improvement focuses on preserving more search quality when those vectors are quantized.</p>\n<h2 id=\"better-quantization-with-randomized-hadamard-rotations\"></h2>\n<h3 id=\"contributed-by-alexey-milovidov\"></h3>\n<p>Quantization works best when information is distributed evenly across a vector’s dimensions. Real embeddings are not always so cooperative: some dimensions may carry much larger values or more variation than others, causing low-precision quantization to lose disproportionate amounts of information.</p>\n<p>A common solution is to rotate the vector space before quantization. Applying the same orthogonal rotation to every stored vector and query vector preserves their original distances, while spreading information more evenly across dimensions. Quantization can then represent the vectors with less error.</p>\n<p>A general random rotation requires an expensive matrix multiplication. Hadamard transforms provide the same kind of mixing much more efficiently. ClickHouse 26.7 introduces <code>randomHadamardTransform</code> as a building block for vector-quantization pipelines:</p>\n<div><pre><code><span><span>SELECT</span> randomHadamardTransform(</span>\n<span>    [<span>1.</span>, <span>2.</span>, <span>3.</span>, <span>4.</span>]::<span>Array</span>(Float32)</span>\n<span>);</span>\n<span></span>\n<span><span>-- [0, 2, 1, -5]</span></span>\n<span><span>-- an orthogonal, norm-preserving rotation</span></span></code></pre></div>\n<!-- -->\n<p>The transformation is deterministic: the same seed produces the same rotation, allowing it to be applied consistently during ingestion and search:</p>\n<div><pre><code><span><span>SELECT</span> randomHadamardTransform(v, seed);</span></code></pre></div>\n<!-- -->\n<p>An optional third argument truncates the transformed vector to a requested number of dimensions:</p>\n<div><pre><code><span><span>SELECT</span> randomHadamardTransform(v, seed, <span>256</span>);</span></code></pre></div>\n<!-- -->\n<p>This produces a Johnson–Lindenstrauss-style random projection: a smaller representation that approximately preserves distances.</p>\n<p>Randomized Hadamard rotations make it possible to build higher-quality quantization pipelines explicitly.</p>\n<p>The next improvement packages that work into a codec, so ClickHouse can manage the quantized representation automatically.</p>\n<h2 id=\"quantization-codecs-fast-two-stage-vector-search\"></h2>\n<h3 id=\"contributed-by-shankar-iyer\"></h3>\n<p>The previous improvements provide the building blocks for custom quantization pipelines: rotate the vectors, quantize them, store the resulting representation, and call the appropriate distance function.</p>\n<p>ClickHouse 26.7 can now manage this automatically through a quantization codec. The codec stores a compact quantized companion alongside the full-precision vectors:</p>\n<div><pre><code><span><span>CREATE TABLE</span> vecs</span>\n<span>(    </span>\n<span>    id UInt32,</span>\n<span>    v <span>Array</span>(BFloat16) CODEC(Quantized(<span>'rabitq'</span>, <span>384</span>)),</span>\n<span>    ...</span>\n<span>)</span>\n<span><span>ORDER</span> <span>BY</span> (...);</span></code></pre></div>\n<!-- -->\n<p>Supported methods include <code>int8</code>, one-bit <code>rabitq</code>, two-bit <code>turboquant</code>, <code>mrl</code>, and product quantization (<code>pq</code>). The codec handles the required transformations and maintains both representations.</p>\n<p>Quantized codes enable a fast two-stage brute-force search without requiring a vector index:</p>\n<div><pre><code><span><span>SET</span> vector_search_use_quantized_codes <span>=</span> <span>1</span>;</span>\n<span></span>\n<span><span>SELECT</span> id</span>\n<span><span>FROM</span> vecs</span>\n<span><span>ORDER</span> <span>BY</span> L2Distance(v, target)</span>\n<span>LIMIT <span>10</span>;</span></code></pre></div>\n<!-- -->\n<p>In the first stage, ClickHouse scans the much smaller quantized representation and uses approximate distances to select promising candidates. In the second, it reads the full-precision vectors for only those candidates and recalculates their exact distances.</p>\n<p>Every vector is still considered, but the expensive full-precision work is restricted to a small shortlist. The quantized first stage can require up to <strong>8× less I/O</strong>, while one-bit codes are <strong>16× smaller</strong> than the original <code>BFloat16</code> vectors.</p>\n<p>The query itself remains unchanged: enable quantized-code search, and ClickHouse automatically performs the approximate scan followed by full-precision rescoring.</p>\n<p>That covers the vector-search improvements in 26.7.</p>\n<p>Next, we turn to text search and faster phrase matching.</p>\n<h2 id=\"position-for-phrase-matching\"></h2>\n<h3 id=\"contributed-by-elmi-ahmadov\"></h3>\n<p>Text indexes now store token positions, a feature that’s needed for efficient phrase search.
