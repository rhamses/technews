contentHtml: "<article><div><p>We've released <a target=\"_blank\" href=\"https://www.npmjs.com/package/@clickhouse/rowbinary\">@clickhouse/rowbinary</a>, a Node.js reader and writer for ClickHouse's <a target=\"_blank\" href=\"https://clickhouse.com/docs/interfaces/formats/RowBinary\">RowBinary</a>, RowBinaryWithNames, and RowBinaryWithNamesAndTypes formats. You can import it and call its generic parser like any other library. But it also ships as an Agent Skill: point a coding agent at the bundled <code>SKILL.md</code> and, instead of calling the library, the agent reads it and writes a parser specialized to your query's exact column types. Those generated parsers run 1.5–3.4x faster than composing the library's functions in a loop, cost about $0.20 each to generate, and avoid the silent data-corruption bugs that models produce when they write binary decoders from memory.</p>\n<h2 id=\"why-we-built-it\"></h2>\n<p>RowBinary is one of the most efficient ways to get data out of ClickHouse, and one of the most annoying formats to consume from JavaScript. The wire format itself is simple: little-endian primitives, <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/LEB128\">LEB128</a> varints for variable widths, no per-row overhead. The pain is on the reader side. Every leaf type has its own read pattern. <code>Nullable</code>, <code>Array</code>, <code>Map</code>, <code>Tuple</code>, and <code>LowCardinality</code> nest arbitrarily. <code>DateTime64</code> needs precision-aware scaling and an optional timezone. The <code>Variant</code>, <code>Dynamic</code>, and <code>JSON</code> types are self-describing and recursive: each value carries its own type tag and dispatches back into the same parsing machinery.</p>\n<p>So most applications fall back to JSON formats, which cost real CPU time and, worse, silently round <code>UInt64</code> values past <code>Number.MAX_SAFE_INTEGER</code> to <code>float64</code> unless you take the slow stringify-then-reparse path. Teams that do adopt RowBinary end up with a generic, type-dispatched parser: one function per type, dispatched per cell at runtime. It's easy to maintain and hard to make fast, because every cell pays a dispatch and V8's inliner gives up on the <a target=\"_blank\" href=\"https://people.dsv.su.se/~beatrice/python/dls15_large_images.pdf\">megamorphic</a> call sites. What you actually want at high QPS is a parser <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Monomorphization\">monomorphized</a> to your query: the right read operations inlined in the right order for your exact columns, with no dispatch at all. Nobody writes these by hand, per query, for every query they ship.</p>\n<p>That's the gap this package closes. The library gives you correct, tested reading primitives for the whole ClickHouse type system. The skill teaches a coding agent to assemble those primitives into the hand-tuned, query-specific parser you'd never write yourself.</p>\n<h2 id=\"what-it-is-and-how-to-use-it\"></h2>\n<p>The package has two layers.</p>\n<p>The first is a library of type-specific reading primitives: one small function per leaf type, plus composable wrappers for <code>Nullable</code>, <code>Array</code>, <code>Map</code>, <code>Tuple</code>, and the rest of the type algebra, in full-buffer and chunked-stream variants. Each primitive is written to be monomorphizable (small, single-purpose, free of megamorphic dispatch) so it can be inlined into a query-specific parser without defeating V8's optimizer. This layer is a perfectly usable library on its own: import it, call <code>parseRowBinary(...)</code>, get correct results. It also exports writers, streaming in both directions, and a dynamic RowBinaryWithNamesAndTypes pipeline built on <a target=\"_blank\" href=\"https://www.npmjs.com/package/@clickhouse/datatype-parser\">@clickhouse/datatype-parser</a>.</p>\n<p>The second layer is the <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhouse-js/blob/main/skills/clickhouse-js-node-rowbinary/SKILL.md\">SKILL.md</a>. Rather than describing how to call the API, it teaches a coding agent the policy for assembling the primitives into a bespoke parser for a given query's column types. The comments in the library source explain why each block looks the way it does and which axes are safe to change: buffer ownership, <code>BigInt</code> vs <code>number</code> for 64-bit integers, <code>Date</code> mapper hooks, <code>Decimal</code> scale handling, <code>Array</code> materialization strategy, fast paths for fixed-width columns. The library is the reference implementation, the comments are the design rationale, and the <code>SKILL.md</code> is the codegen policy.</p>\n<p>To install:</p>\n<div><pre><code><span>npm i @clickhouse/rowbinary</span></code></pre></div>\n<p>The skill is registered in the package's <code>agents.skills</code> field, so any agent that scans <code>node_modules</code> for skills finds it automatically. You can also add it directly:</p>\n<div><pre><code><span>npx skills add ClickHouse/clickhouse-js --skill clickhouse-js-node-rowbinary</span></code></pre></div>\n<h3 id=\"what-the-agent-generates\"></h3>\n<p>Take the orders schema from our benchmarks:</p>\n<div><pre><code><span>id     UInt8</span>\n<span>uid    UUID</span>\n<span>price  Decimal64(<span>2</span>)</span>\n<span>status Enum8(<span>'new'</span> <span>=</span> <span>1</span>, <span>'shipped'</span> <span>=</span> <span>2</span>, <span>'done'</span> <span>=</span> <span>3</span>)</span></code></pre></div>\n<p>Composing the library's public API gives you a correct parser, and it's the obvious thing to write:</p>\n<div><pre><code><span><span>export</span> <span>const</span> <span>readOrderRow</span>: <span>Reader</span>&lt;<span>OrderRow</span>&gt; = <span>(<span>s</span>) =&gt;</span> ({</span>\n<span>  <span>id</span>: <span>readUInt8</span>(s),</span>\n<span>  <span>uid</span>: <span>formatUUID</span>(<span>readUUID</span>(s)),</span>\n<span>  <span>price</span>: <span>readDecimal64</span>(<span>2</span>)(s),   <span>// closure rebuilt every row</span></span>\n<span>  <span>status</span>: <span>readInt8</span>(s),</span>\n<span>});</span></code></pre></div>\n<p>But every field does its own bounds check, <code>readDecimal64(2)</code> builds a fresh closure per row, and <code>formatUUID</code> goes through <code>BigInt</code>. With the skill loaded, the agent notices that every column is fixed-width and emits this instead:</p>\n<div><pre><code><span><span>export</span> <span>const</span> <span>readOrderRowFast</span>: <span>Reader</span>&lt;<span>OrderRow</span>&gt; = <span>(<span>s</span>) =&gt;</span> {</span>\n<span>  <span>const</span> { buf, view } = s;</span>\n<span>  <span>// Every column is fixed-width: 1 + 16 + 8 + 1 = 26 bytes.</span></span>\n<span>  <span>// One bounds check for the whole row, then read at constant offsets.</span></span>\n<span>  <span>const</span> o = <span>advance</span>(s, <span>26</span>);</span>\n<span>  <span>const</span> id = buf[o]!;</span>\n<span>  <span>const</span> uid = <span>formatUUIDTable</span>(buf.<span>subarray</span>(o + <span>1</span>, o + <span>17</span>)); <span>// table, not BigInt</span></span>\n<span>  <span>const</span> <span>price</span>: <span>DecimalValue</span> = [view.<span>getBigInt64</span>(o + <span>17</span>, <span>true</span>), <span>2</span>];</span>\n<span>  <span>const</span> status = view.<span>getInt8</span>(o + <span>25</span>);</span>\n<span>  <span>return</span> { id, uid, price, status };</span>\n<span>};</span></code></pre></div>\n<p>One bounds check for the whole 26-byte row, reads at constant offsets, the Decimal scale baked in, and a lookup-table UUID formatter. The output is byte-identical to the composed version and 3.41x faster.</p>\n<p>Because the parser is specialized anyway, <code>.map()</code>-style transformations are free: rename a column, derive a field, or drop one you never use, and the transformation moves into the read loop at zero extra cost, with zero extra options added to the library.</p>\n<p>A few properties worth knowing before you adopt it:</p>\n<ul>\n<li><strong>The generated parser is a regular piece of code.</strong> A human commits it, and it's reviewed, tested, and benchmarked like any other module. The skill produces source you read, not a binary you trust. The library ships a comprehensive test suite you can borrow to cover the now app-owned reader.</li>\n<li><strong>The skill is auditable.</strong> It's a markdown file plus densely commented, tested TypeScript, all in the npm tarball.</li>\n<li><strong>The generic reader still works.</strong> Skip the agent entirely and call <code>parseRowBinary(...)</code> for a known-good path. The skill is multiplicative, not a replacement.</li>\n<li><strong>It works best with a model that can read the whole library</strong> and follow multi-step reference instructions. Small models degrade, but with focused sub-agents they remain viable: Haiku's pass rate jumped from 52% to 86%.</li>\n</ul>\n<h2 id=\"how-we-got-here\"></h2>\n<h3 id=\"the-conventional-answer-is-a-compiler\"></h3>\n<p>Schema-driven binary formats have a standard playbook for producing monomorphized parsers: build a codegen compiler. That's the shape <code>protoc</code>, <code>flatc</code>, and Cap'n Proto all adopted: take a schema, run a compiler, emit specialized code per target language. It works, but a codegen compiler is a real piece of software, with a parser for the schema language, an IR, a backend per target language, an options matrix, a release cadence, and a maintainer queue. Every degree of customization a user wants (a different decimal library, a custom <code>Date</code> mapper, <code>BigInt</code> vs <code>number</code> for <code>Int64</code>, eager vs lazy <code>Array</code> materialization, a string-interning table for <code>LowCardinality</code>) has to be designed as a flag, named, documented, kept stable across versions, and tested against every other flag.</p>\n<p>We could have built one for RowBinary in JavaScript. Instead, we decomposed the compiler into artifacts an agent can read and recombine at inference time: densely commented primitives and a markdown file. The customization surface stops being a fixed list of flags and becomes a conversation with a model that has read your library. If you want <code>Decimal128</code> mapped to a custom big-decimal library, or <code>DateTime64(9)</code> as nanoseconds-in-<code>BigInt</code>, or <code>LowCardinality(String)</code> materialized through a string-interning table, those aren't flags we have to ship. The agent handles them in a few hundred tokens because it understands the comments in <code>decimal.ts</code>.</p>\n<h3 id=\"what-the-eval-told-us\"></h3>\n<p>We benchmarked three decode paths on 50k rows per schema: the correct JSON path (server-side stringification of wide integers, client-side re-parse to <code>BigInt</code>), the generic RowBinary reader composed from the library API, and the agent-generated monomorphic parser. Hardware and versions are listed at the end of the post.</p>\n<p>RowBinary beats JSON by 3.3x on a wide-integer financial ledger schema on an Apple M4 Max (<a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhouse-js/blob/8c51d9a12e67e82ef431e8158d5b77ce26e40e3a/skills/clickhouse-js-node-rowbinary/tests/ledger.bench.ts\">benchmark source</a>) and by 2.5x on a 4-core AMD EPYC 7763 in CI (<a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhouse-js/actions/runs/28439460847/job/84273435913#step:9:40\">run</a>). The gap widens with newer hardware because RowBinary's work is pointer arithmetic and contiguous memory reads, while JSON's is branchy tokenization and <code>BigInt</code> allocation. An IoT schema holds a steadier ~2.1x on both machines. Note that these numbers compare against the <em>correct</em> JSON path. Bare <code>JSONEachRow</code> looks closer at 1.8x, but it silently rounds every <code>UInt128</code>, <code>Int128</code>, and any <code>UInt64</code> past <code>Number.MAX_SAFE_INTEGER</code> to <code>float64</code>. The decode succeeds, the numbers are wrong, and nothing complains until you compare totals against the server.</p>\n<p>The agent-generated parser then beats the composed reader by another 1.5–3.4x:</p>\n<div><table><thead><tr><th>Schema</th><th>Shape</th><th>Speedup vs composed reader</th></tr></thead><tbody><tr><td>Financial ledger</td><td>Wide integers (<code>UInt128</code>, <code>Int128</code>)</td><td>1.55x</td></tr><tr><td>IoT telemetry</td><td><code>Float64</code> / integers</td><td>2.46x</td></tr><tr><td>Orders</td><td>Fixed-width, denormalized</td><td>3.41x</td></tr></tbody></table></div>\n<p>Every numeric-heavy schema we tested came in at 1.5x or better. RowBinary doesn't win everywhere, though. On a string-heavy log schema, <code>JSONCompactEachRow</code> beats even the optimized RowBinary reader, and the skill's own guidance says not to use RowBinary there. The skill knows its own boundaries.</p>\n<p>Generation cost, averaged across four numeric-heavy schemas with Claude Sonnet 4.6: ~230k tokens in (almost all served from the prompt cache across the agent loop; the unique skill footprint per call is ~28k), ~2.1k tokens out, <strong>$0.20 per parser</strong> with caching and $0.72 as an uncached upper bound. Regenerating per deploy is well within budget.</p>\n<p>The eval also showed why the skill matters beyond speed. RowBinary stores a UUID as two little-endian <code>UInt64</code> halves, each byte-reversed relative to the text form. Asked to write that decoder purely from memory, with no documentation, tools, or test-and-fix loop, Sonnet 4.6 got the byte order wrong in 3 of 5 runs, each time producing the same silently corrupt output: the 16 wire bytes hexed in order, formatted as a perfectly plausible UUID string. Opus 4.8 was reliable at 5 of 5. With the skill loaded, every run is correct by construction, because the reference primitive sits in the library two function calls away from where the agent is reading.</p>\n<p>That failure mode is why we care about this more than the speedup. ClickHouse users run these parsers against billions of rows. A JSON path that rounds <code>UInt128</code> to <code>float64</code> produces totals that are off by a little across millions of records, and someone notices six weeks later when a finance report doesn't balance. A UUID decoder that hexes the wire bytes in source order produces strings that pass schema validation and quietly break join predicates. These are the bugs that make teams refuse to put AI-generated code on the data path at all. The skill addresses them by making the generated parser a recombination of the official, tested, code-reviewed primitives we maintain. When you review the generated parser in a PR, you're reviewing code assembled from code we wrote.</p>\n<h3 id=\"what-the-skill-cost-to-produce\"></h3>\n<p>A fair objection is that a capable enough coding agent should be able to write this parser without any skill at all. It can, and that's how the skill got built. Claude Code with Opus, given the RowBinary spec and the ClickHouse source as reference, produced a working reader. It took a few million tokens, roughly a day of continuous prompting, several rounds of test-writing and benchmark-tweaking, and a human reviewing each iteration.</p>\n<p>The skill is the compiled artifact of that day. It bakes in the accumulated lessons (LEB128 reads, Decimal scale handling, which integer widths need <code>BigInt</code>, how V8 inlines and doesn't) that a model would otherwise rediscover from scratch every time. A compiler is amortized engineering in the same way: someone spent months teaching it the type system and the codegen rules so that every user downstream gets specialized output cheaply. Here the investment was a day of human-AI collaboration, frozen into markdown and commented code, and everyone downstream gets it for a $0.20 inference call.</p>\n<h3 id=\"where-this-fits\"></h3>\n<p>Agent Skills landed as a format in October 2025 and became an open standard in December 2025. The most common pattern so far is <em>ship a <code>SKILL.md</code> alongside your npm package so the agent calls your API correctly</em>: Vercel Labs's <code>skills</code> CLI, antfu's <code>skills-npm</code>, <code>npm-agentskills</code>, and similar. Those are useful, and we already ship one of that shape: <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhouse-js/tree/main/skills/clickhouse-js-node-troubleshooting\">clickhouse-js-node-troubleshooting</a>, a runbook the agent consults when something breaks.</p>\n<p><code>@clickhouse/rowbinary</code> is a different shape: library-as-reference rather than library-as-API. Instead of treating the library as a black box to call, the agent treats it as a transparent reference implementation to fork per query. That changes how you should write code if you're authoring a skill like this. Code meant to be called needs an honest description. Code meant to be read needs dense comments, internal consistency, and no cleverness that doesn't reproduce.</p>\n<p>We expect the pattern to generalize. Anywhere you'd have reached for a codegen compiler (narrow, schema-driven, performance-sensitive output), there's now an alternative that costs a markdown file and an inference call. If you find places where the skill produces bad output, the comments in the library are where fixes go; please <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhouse-js/issues\">file an issue</a>.</p>\n<h3 id=\"benchmark-environment\"></h3>\n<p>Local: Apple M4 Max, Node v24.6.0, macOS 26.5.1, ClickHouse 26.1.1.200.
