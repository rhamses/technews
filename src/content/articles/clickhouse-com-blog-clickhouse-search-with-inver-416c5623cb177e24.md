An inverted index is the central data structure that enables fast and powerful searching in vast collections of text documents. The idea underlying inverted indexes is to compile a database of terms with pointers to the documents which contain these terms.</p>\n<p>Let's look at a small example with four documents to better understand how inverted indexes work.</p>\n<div><pre><code><span><span>CREATE TABLE</span> docs</span>\n<span>(</span>\n<span>    `key` UInt64,</span>\n<span>    `doc` String</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree()</span>\n<span><span>ORDER</span> <span>BY</span> key;</span>\n<span></span>\n<span><span>INSERT INTO</span> docs <span>VALUES</span></span>\n<span>    (<span>0</span>, <span>'Sail against the wind'</span>),</span>\n<span>    (<span>1</span>, <span>'Wait and see'</span>),</span>\n<span>    (<span>2</span>, <span>'Sail the seven seas'</span>),</span>\n<span>    (<span>3</span>, <span>'See how the wind blows'</span>);</span></code></pre></div>\n<p>To find all documents which contain the term \"wind\" we could write the following SQL query:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> docs</span>\n<span><span>WHERE</span> doc <span>LIKE</span> <span>'%wind%'</span>;</span>\n<span></span>\n<span>┌─key─┬─doc────────────────────┐</span>\n<span>│   <span>0</span> │ Sail against the wind  │</span>\n<span>│   <span>3</span> │ See how the wind blows │</span>\n<span>└─────┴────────────────────────┘</span>\n<span></span>\n<span><span>2</span> <span>rows</span> <span>in</span> set. The simplest method to achieve that is to store the terms in alphabetical sort order and to use binary search for lookups. In contrast to that, ClickHouse stores dictionaries as finite state transducers (FSTs). We will discuss FSTs in more detail below. Their main advantage is that redundancies, e.g., shared prefixes between adjacent terms, can be easily removed. This reduces the memory footprint of the dictionary and improves the overall throughput.</p>\n<p>Further interesting extensions of dictionaries that are currently not supported but might be added in the future include the following:</p>\n<ul>\n<li>a removal of stop words that carry no semantic weight like \"a\", \"and\", \"the\" etc., and</li>\n<li>lemmatization and stemming as language-specific techniques to reduce words to their linguistic word root, e.g., \"walking\" becomes \"walk\", \"went\" becomes \"go\", \"driving\" becomes \"drive\" etc.</li>\n</ul>\n<p>ClickHouse also stores the posting lists in a compressed format (more specifically as \"roaring bitmap\") with the goal of reducing their memory consumption. We will dig a bit deeper into posting list compression below. In the initial inverted index version, posting lists refer to the row positions of the documents which contain the corresponding term. This might be extended in the future with additional metadata, for example:</p>\n<ul>\n<li>A document frequency count stored with each posting indicating how often the term occurs in the document. Such information will allow us to calculate the term frequency / inverse document frequency (TF-IDF), which is useful for <a target=\"_blank\" href=\"https://monkeylearn.com/blog/what-is-tf-idf/\">ranking search results</a>.</li>\n<li>Word-level postings, i.e., the exact positions of terms inside documents. Such data allows to answer phrase queries where the user does not search for a single term but for multiple consecutive terms (a \"phrase\").</li>\n</ul>\n<p>If we rerun our query, it will automatically use the index:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>from</span> docs <span>WHERE</span> doc <span>LIKE</span> <span>'%wind%'</span>;</span>\n<span></span>\n<span>┌─key─┬─doc────────────────────┐</span>\n<span>│   <span>0</span> │ Sail against the wind  │</span>\n<span>│   <span>3</span> │ See how the wind blows │</span>\n<span>└─────┴────────────────────────┘</span>\n<span></span>\n<span><span>2</span> <span>rows</span> <span>in</span> set. As you can see in the example above, the postings within a posting list are monotonically increasing. Furthermore, the terms in real-world data are typically distributed in a highly skewed manner. This means that most terms normally occur in only a few documents, whereas a few terms occur in many documents. Traditional implementations of inverted indexes exploit both properties by compressing their posting lists with a combination of <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Delta_encoding\">delta encoding</a> and <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Golomb_coding\">Golomb (or Golomb-Rice) encoding</a>. Such compression accomplishes a very high compression rate, but compression and decompression become <a target=\"_blank\" href=\"https://dl.acm.org/doi/10.5555/1012294.1012301\">rather slow</a>.</p>\n<p><a target=\"_blank\" href=\"https://dl.acm.org/doi/10.1145/3035918.3064007\">Modern posting list compression formats</a> are able to strike a better balance between compression/decompression performance and compression rate. Inverted indexes in ClickHouse utilize the state-of-the-art <a target=\"_blank\" href=\"https://roaringbitmap.org/\">roaring bitmaps</a> format to compress the posting lists. The main idea of this format is to represent the postings as a bitmap (e.g. [3, 4, 7] becomes [00011001]), which are then divided into chunks and stored in specialized containers.</p>\n<p><span><img alt=\"roaring_bitmaps.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Froaring_bitmaps_5f08ce3cd9.png&w=2048&q=75\"></span></p>\n<p>Roaring bitmaps store sorted lists of 32-bit integers, i.e., the maximum value is ca. 4.2 billion. The range of all possible integers is then split into equally large ranges of 2^16 integers. All integers in one chunk share their 16 most significant bits, whereas the 16 least significant bits are kept in a specialized container, depending on the distribution of the values in the range. The available container types include an array (for sparsely distributed values), bitmap (for densely distributed values), and run-length encoded (RLE, for data with long consecutive runs of values). An \"array of containers\" sorted on the upper 16 bits serves as an entry point into the list of containers. This structure is usually small enough to fit into the CPU cache.</p>\n<p>In the context of inverted indexes, it is also important to be able to merge and intersect two posting lists quickly. This becomes necessary when users search for a disjunction (OR) or conjunction (AND) of multiple terms, e.g., <code>SELECT * from docs WHERE doc IN ('wind', 'blows', 'sail')</code>. Roaring bitmaps are especially good at this as they come with optimized algorithms to union and intersect every combination of two container types. For more details on roaring bitmaps, we refer to <a target=\"_blank\" href=\"https://dl.acm.org/doi/10.1002/spe.2402\">this publication</a>.</p>\n<h2 id=\"dictionary-compression\"></h2>\n<p>Now that we have taken a closer look at the posting lists let's turn our attention to the compression of dictionaries. The inverted indexes in ClickHouse use Finite State Transducers (FSTs) to represent dictionaries. Most people are probably unfamiliar with FSTs, but many people know <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Finite-state_machine\">Finite State Machines</a>. This type of automata has a set of states and a set of transitions between the states, and depending on whether one ends up in an accepting or a non-accepting state, they accept or reject an input. FSTs work similarly, except that state transitions not only consume input, they also produce output. For this reason, FSTs are a popular tool in computer linguistics to translate between two languages.</p>\n<p><span><img alt=\"FST.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FFST_e320464f13.png&w=2048&q=75\"></span></p>\n<p>In ClickHouse's inverted indexes, FSTs \"translate\" terms to posting list offsets. The FST in the above example accepts the terms \"See, \"see\", \"seas\", \"seven\" and \"wind\". The posting list offset is computed by accumulating the outputs of each transition. For example, the term \"seas\" produces offset 4 + 5 = 9. The figure shows a compressed FST in which common substrings are removed using the techniques explained <a target=\"_blank\" href=\"https://link.springer.com/chapter/10.1007/3-540-44674-5_18\">here</a>.</p>\n<h2 id=\"disk-layout\"></h2>\n<p>Before demonstrating inverted indexes on a realistic dataset, we will quickly discuss their construction and on-disk layout.</p>\n<p>Inverted index construction, also known as \"inversion\", is a CPU and time-intensive operation. Inverted indexes in ClickHouse are implemented as secondary indices, and as such, they exist at the granularity of a part. With the current implementation, a merge of two parts re-creates the inverted index on the new part from scratch. This might be optimized in the future with more lightweight incremental index maintenance that is able to merge two existing indexes directly. For now, care was taken to limit the cost of index creation. Out of different possible <a target=\"_blank\" href=\"https://onlinelibrary.wiley.com/doi/10.1002/asi.10268\">index construction methods</a>, ClickHouse uses a strategy (\"single-pass in-memory inversion\") which</p>\n<ul>\n<li>iterates the underlying column data in a single pass (as opposed to requiring two passes),</li>\n<li>processes a configurable chunk of data (as opposed to allocating memory proportional to the size of the underlying column), and</li>\n<li>constructs the index directly (instead of writing intermediate files to disk, which are subsequently merged in a postprocessing step).</li>\n</ul>\n<p>The resulting inverted index is segmented, i.e., consists of multiple smaller sub-indexes. Each segment corresponds to a consecutive row range of the original column. Row ranges can be of different sizes but their approximate size can be controlled by the parameter <code>max_digestion_size_per_segment</code>.</p>\n<p><span><img alt=\"inverted_index_layout.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Finverted_index_layout_51921c5459.png&w=2048&q=75\"></span></p>\n<p>The index of a part is stored as three files.</p>\n<p>The metadata file is an array of segment descriptors, each containing a unique segment id, a start row id, a dictionary offset, and a posting list offset. The start row id represents the starting row of the segment, whereas the dictionary and posting list offsets point to the beginning of the current segment's sections in the posting list and the dictionary files.</p>\n<p>The posting list file contains the posting lists of all segments. A segment can have multiple posting lists because it can have multiple terms. Starting from the metadata file, we can use the posting list offset to jump to the first posting list of a segment. But since there can be multiple terms within the segment, we also need to find the correct posting list within the segment.</p>\n<p>That is what the dictionary file is for. It contains each segment's dictionary (+ the dictionary size) in the form of a minimized FST. During an index lookup, ClickHouse will use the dictionary and the posting list offset in the metadata file to jump to the right FST and the beginning of the segment's posting lists. It will then use the FST in the dictionary file to calculate the offset from the start of the segment's posting lists to the actual posting list and eventually decompress it. Because of this architecture, the inverted index is never fully read into memory; only pieces of the metadata file, the dictionary file, and the posting list file are read at a time.</p>\n<h2 id=\"a-real-world-example\"></h2>\n<p>Finally, it is time to demonstrate the inverted index. Inverted Indices to ClickHouse? Yes, you read it right. Read on to learn more about how they work and how you can use them to accelerate your string matching.
