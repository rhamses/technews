indexes to eliminate work before any data is read</strong>, further accelerating Top-N queries as data sizes grow.</p>\n<h2 id=\"how-clickhouse-already-optimizes-top-n-queries\"></h2>\n<p>ClickHouse already applies several optimizations to run Top-N queries efficiently and fast:</p>\n<ol>\n<li>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/select#implementation-details\">Streaming</a> Top-N (bounded memory):<br>\nClickHouse doesn’t sort all rows at once. Instead, it streams data and keeps only the current Top-N candidates, so memory usage stays proportional to N rather than to the table size.</p>\n</li>\n<li>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-faster-queries-with-projections-and-primary-indexes#utilize-indexes-for-preventing-resorting-and-enabling-short-circuiting\">Read in order</a> (avoid sorting completely):<br>\nIf the data on disk is already ordered by the ORDER BY column(s), or can be read in that order via a <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/alter/projection\">projection</a>, ClickHouse can avoid sorting and simply read the first rows in order.</p>\n</li>\n<li>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-gets-lazier-and-faster-introducing-lazy-materialization\">Lazy reading</a> (defer reading non-order columns):<br>\nEven when the query selects many columns, ClickHouse can first determine the Top-N rows using only the columns needed for ordering, and only then read the remaining columns for those rows. This reduces I/O dramatically.</p>\n</li>\n</ol>\n<p>These optimizations are <strong>orthogonal</strong> to each other: they address different aspects of Top-N query execution and can be applied independently or in combination within a single query.</p>\n<p>Despite these optimizations, Top-N queries still require scanning all relevant <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes#data-is-organized-into-granules-for-parallel-data-processing\">granules</a>, even when only a handful of rows are ultimately returned.</p>\n<h2 id=\"the-missing-piece-skipping-data-before-it-is-ever-read\"></h2>\n<p>ClickHouse applies additional, orthogonal optimizations for Top-N queries by using <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/skipping-indexes/examples\">data skipping indexes</a> for static or dynamic Top-N filtering, <strong>significantly reducing the number of rows that need to be processed</strong>.</p>\n<p>The rest of this post shows how this works in practice, starting with the simplest case.</p>\n<h2 id=\"static-top-n-filtering-no-predicates\"></h2>\n<p>Let’s start with the simplest case: a Top-N query without any predicates or filters.</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> T <span>ORDER</span> <span>BY</span> c <span>ASC</span> LIMIT <span>3</span>;</span></code></pre></div>\n<p>Even without a WHERE clause, ClickHouse can reduce the amount of data read if a <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/skipping-indexes/examples\">minmax data skipping index</a> exists on the ORDER BY column <code>c</code>.</p>\n<p>To illustrate this, assume table T consists of five <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes#data-is-organized-into-granules-for-parallel-data-processing\">granules</a> (the smallest processing units in ClickHouse, each covering 8,192 rows by default). As soon as a granule becomes eligible for reading (after <a target=\"_blank\" href=\"https://clickhouse.com/docs/primary-indexes\">primary index analysis</a> for the predicate evaluation), its corresponding minmax data skipping index entry is consulted.</p>\n<p>At that point, the current Top-N threshold is compared against the granule’s min/max metadata. If the granule cannot possibly contain values that would improve the Top-N result set, it is skipped immediately and never read.</p>\n<p>As execution progresses and better Top-N candidates are found, the threshold tightens further, allowing ClickHouse to prune an increasing number of granules dynamically during query execution. Each optimization addresses a different bottleneck, and together they allow ClickHouse to scale Top-N queries from millions to billions of rows efficiently.</p>\n<p>For users, this means a familiar query pattern <code>ORDER BY … LIMIT N</code> now benefits from increasingly aggressive pruning as data grows. By treating common query patterns as problems that can often be solved <em>before</em> touching the data at all.</p></div></article>"
