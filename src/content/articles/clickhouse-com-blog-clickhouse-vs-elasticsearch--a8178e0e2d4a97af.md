We will leave a comparison of ClickHouse and Elasticsearch for metric use cases for another blog.</p>\n</blockquote>\n<h2 id=\"count-aggregation-approaches\"></h2>\n<h3 id=\"parallelization\"></h3>\n<h4 id=\"clickhouse\"></h4>\n<p>ClickHouse was built from the <a target=\"_blank\" href=\"https://youtu.be/ZOZQCQEtrz8?si=XrQ-vMDiHEsgsrYq&t=103\">very beginning</a> to filter and <strong>aggregate</strong> internet-scale data as quickly and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/faq/general/why-clickhouse-is-so-fast\">efficiently</a> as possible. To do so, ClickHouse parallelizes SELECT queries, including aggregation functions like <code>count(*)</code> and all other <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/reference\">90+</a> aggregation functions at the level of ① column values, ② table chunks, and ③ table shards:\n<span><img alt=\"Elasticsearch_blog2_02.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FElasticsearch_blog2_02_fd9e5b0dd8.png&w=2048&q=75\"></span></p>\n<h5 id=\"simd-parallelization\"></h5>\n<p>ClickHouse utilizes the CPU's <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Single_instruction,_multiple_data\">SIMD units</a> (e.g. <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/AVX-512\">AVX512</a>) to apply the same operations to consecutive values in a column. <a target=\"_blank\" href=\"https://clickhouse.com/blog/cpu-dispatch-in-clickhouse\">This</a> blog post details how this works.</p>\n<h5 id=\"multi-core-parallelization\"></h5>\n<p>On a single machine with <code>n</code> CPU cores, ClickHouse runs an aggregation query with <code>n</code> <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/query-processing/README.md#clickhouse\">parallel execution lanes</a> (or fewer or more, if requested by the user via <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#max_threads\">max_threads</a> setting):\n<span><img alt=\"Elasticsearch_blog2_03.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FElasticsearch_blog2_03_2f10f45c58.png&w=2048&q=75\"></span></p>\n<p>The figure above shows how ClickHouse processes <code>n</code> non-overlapping data ranges in parallel. These data ranges can be arbitrary, e.g. they don’t need to be based on the grouping key. When the aggregation query contains a filter in the form of a <code>WHERE</code> clause, and the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes\">primary index</a> can be utilized to evaluate this filter, ClickHouse locates matching table data ranges and spreads these <a target=\"_blank\" href=\"https://youtu.be/hP6G2Nlz_cA?si=FeCadjUfzgiw-Qph&t=633\">dynamically</a> among the <code>n</code> execution lanes.</p>\n<p>This parallelization approach is enabled using <a target=\"_blank\" href=\"https://www.google.com/url?q=https://clickhouse.com/blog/aggregate-functions-combinators-in-clickhouse-for-arrays-maps-and-states%23working-with-aggregation-states&sa=D&source=docs&ust=1714996294648579&usg=AOvVaw3syvRuV3_D61ogmWRv-PDF\">partial aggregation states</a>: each of the <code>n</code> execution lanes produces partial aggregation states. These partial aggregation states are eventually merged into the final aggregation result.</p>\n<p>For the <code>count(*)</code> aggregation, the partial aggregation state is simply an incrementally updated count variable. In fact, <code>count(*)</code> aggregation is the simplest kind of aggregation and could be parallelized internally, even without the concept of partial aggregation states. To give a concrete example where partial aggregation states enable parallelization, we use this aggregation query to <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=EAI3T1FVZSGSRJFSSDCCQP\">calculate</a> average house prices per town based on the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/uk-price-paid\">UK property prices dataset</a>:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    town,</span>\n<span>    <span>avg</span>(price) <span>AS</span> avg_price</span>\n<span><span>FROM</span> uk_price_paid</span>\n<span><span>GROUP</span> <span>BY</span> town;</span></code></pre></div>\n<p>Assume the database wants to calculate the average house prices in <code>London</code> using two parallel execution lanes:\n<span><img alt=\"Elasticsearch_blog2_04.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FElasticsearch_blog2_04_cffa2ff47a.png&w=2048&q=75\"></span></p>\n<p>Execution lane 1 averages the house prices of all rows in its data range consisting of two records for London. The resulting <code>partial aggregation state</code> for <code>avg</code> generally consists of</p>\n<ul>\n<li>a <code>sum</code> (here for execution lane 1: <code>500,000</code> as the summarized house prices in <code>London</code>) and</li>\n<li>a <code>count</code> (here for execution lane 1: <code>2</code> as the number of processed records for <code>London</code>).</li>\n</ul>\n<p>Execution lane 2 calculates a similar partial aggregation state. These two partial aggregation states are merged, and with that, the final result can be produced: The average house price for the <code>London</code> records is <code>(500,000 + 400,000) / (2 + 1)</code> = <code>900,000 / 3</code> = <code>300,000</code>.</p>\n<p>Partial aggregation states are necessary to compute correct results. Simply averaging the averages of sub-ranges produces incorrect results. For example, if we average the average of the first sub-range (<code>250,000</code>) with the average of the second sub-range (<code>400,000</code>), we obtain <code>(650,000 / 2)</code> = <code>325,000</code>, which is incorrect.</p>\n<p>ClickHouse parallelizes all of its supported <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/reference\">90+ aggregation functions</a> plus their combinations with <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/combinators\">aggregate function combinators</a> across all available CPU cores.</p>\n<h5 id=\"multi-node-parallelization\"></h5>\n<p>If the source table of an aggregation query is <a target=\"_blank\" href=\"https://youtu.be/vBjCJtw_Ei0?si=lZYrLGN04R7l0Uhq\">sharded</a> and spread over multiple nodes, then ClickHouse parallelizes aggregation functions across all available CPU cores of all available nodes.</p>\n<p>Each node (in parallel) performs the aggregation locally using the aforementioned multi-core parallelization technique. The resulting partial aggregation states are streamed to and merged by the initiator node (the node that initially received the aggregation query):</p>\n<p><span><img alt=\"Elasticsearch_blog2_05.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FElasticsearch_blog2_05_8cba60d720.png&w=2048&q=75\"></span></p>\n<p>As an <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#distributed-group-by-no-merge\">optimization</a>, if the aggregation query’s GROUP BY key is a prefix of the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/architecture/horizontal-scaling#shard\">sharding key</a>, then the initiator node doesn’t need to merge partial aggregation states, and the merge happens as a last step on each node, and the final results are streamed back to the initiator node instead.</p>\n<h5 id=\"incremental-aggregation\"></h5>\n<p>All techniques discussed so far are applied at \"query time\", i.e. when the user runs <code>SELECT count(*) FROM ... GROUP BY ...</code> queries. If the same expensive aggregation query is run repeatedly, e.g. hourly, or if sub-second latencies are required, but the queried data set is too large for that, then ClickHouse provides an additional optimization that shifts the load from the query time to the insert time and (mostly) the background merge time. Specifically, the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#-multi-core-parallelization\">above-mentioned</a> partial aggregation technique (based on <code>partial aggregation states</code>) can also be used at the <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing/README.md#logical-and-physical-on-disk-data-structures-1\">data part</a> level during (<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/server-configuration-parameters/settings#background_pool_size\">parallel</a>) <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing/README.md#insert-processing-1\">background part merges</a>.</p>\n<p>This yields a powerful, highly scalable <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#approaches-for-continuous-data-summarization\">continuous data summarization technique</a>, with the result that aggregation queries will find the majority of the data already aggregated. The following diagram sketches this:\n<span><img alt=\"Elasticsearch_blog2_06.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FElasticsearch_blog2_06_8a694b0035.png&w=2048&q=75\"></span></p>\n<p>① The <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/combinators#-state\">-State</a> aggregate function combinator can be used to instruct the ClickHouse query engine to only combine the partial aggregation states (<a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#-multi-core-parallelization\">produced</a> by the parallel execution lanes) <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#-multi-core-parallelization\">instead</a> of combining and calculating the final result:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    town,</span>\n<span>    avgState(price) <span>AS</span> avg_price_state</span>\n<span><span>FROM</span> uk_price_paid</span>\n<span><span>GROUP</span> <span>BY</span> town;</span></code></pre></div>\n<blockquote>\n<p>When you <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=EAI3T1FVZSGSRJFSSDCCQP\">run</a> this query, the partial aggregation states in <code>avg_price_state</code> are not really meant to be printed on the screen.</p>\n</blockquote>\n<p>These combined partial aggregation states can then be written as <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing/README.md#logical-and-physical-on-disk-data-structures-1\">data parts</a> into a table with the <a target=\"_blank\" href=\"https://youtu.be/QDAJTKZT8y4\">AggregatingMergeTree</a> table engine:</p>\n<div><pre><code><span><span>INSERT INTO</span> <span>&lt;</span><span>table</span> <span>with</span> AggregatingMergeTree engine<span>&gt;</span></span>\n<span><span>SELECT</span></span>\n<span>    town,</span>\n<span>    avgState(price) <span>AS</span> avg_price_state</span>\n<span><span>FROM</span> uk_price_paid</span>\n<span><span>GROUP</span> <span>BY</span> town;</span></code></pre></div>\n<p>② This table engine <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/continuous-data-transformation/README.md#clickhouse\">continues</a> the partial aggregation <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/continuous-data-transformation/README.md#clickhouse\">incrementally</a> (and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/server-configuration-parameters/settings#background_pool_size\">parallelized</a>) during background part merges. The merged result is the equivalent of running the aggregation query over all of the original data.</p>\n<blockquote>\n<p>A <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#clickhouse-3\">materialized view</a> does the insert step above automatically. <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/continuous-data-transformation/README.md#clickhouse-materialized-views\">Here</a>'s a concrete example based on the <code>average house price per town</code> example we used above.</p>\n</blockquote>\n<p>③ At query time, the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/combinators#-merge\">-Merge</a> aggregate function combinator can be used to combine the partial aggregation states into the final result aggregation values:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    town,</span>\n<span>    avgMerge(avg_price_state) <span>AS</span> avg_price</span>\n<span><span>FROM</span> <span>&lt;</span><span>table</span> <span>with</span> AggregatingMergeTree engine<span>&gt;</span></span>\n<span><span>GROUP</span> <span>BY</span> town;</span></code></pre></div>\n<h4 id=\"elasticsearch\"></h4>\n<p>Compared with ClickHouse, Elasticsearch leverages a completely different parallelization approach for its <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html\">terms aggregation</a> (which is <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#count-aggregations-in-clickhouse-and-elasticsearch\">used</a> to calculate counts in Elasticsearch). This leads to less efficient hardware utilization than ClickHouse:\n<span><img alt=\"Elasticsearch_blog2_07.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FElasticsearch_blog2_07_fc1d7751f7.png&w=2048&q=75\"></span>\nThe <code>terms aggregation</code> always needs a size parameter (called <code>n</code> in the following), and Elasticsearch runs this aggregation with <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/8.12/size-your-shards.html#single-thread-per-shard\">one</a> CPU thread per <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing/README.md#elasticsearch\">shard</a>, independent of the number of CPU cores. Each thread calculates shard-local <code>top n</code> results (based on the largest <code>count</code> values per group by <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html#search-aggregations-bucket-terms-aggregation-order\">default</a>) from its processed shard. Shard-local results are eventually consolidated into a global <code>top n</code> final result.</p>\n<p>Elasticsearch’s multi-node parallelization of the <code>terms aggregation</code> works similarly. When the shards are spread over multiple nodes, each node produces (with the technique explained above) a node-local <code>top n</code> result, and these node-local results are consolidated into the final global result by the coordinating node (the node that initially received the aggregation query).</p>\n<p>Based on how the data is spread over shards, this parallelization approach potentially has a precision issue. We illustrate this with an example:\n<span><img alt=\"Elasticsearch_blog2_08.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FElasticsearch_blog2_08_3f35a3f165.png&w=2048&q=75\"></span>\nWe assume, based on the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/uk-price-paid\">UK property prices dataset</a>, that we want to calculate the top two towns with the most sold properties. The data is spread over two shards. The figure above shows abstractly ① the shard-local counts of property sale records per town. Each processing thread ② returns a shard-local <code>top 2</code> result, which is consolidated ③ into the final global <code>top 2</code> result. This result is incorrect, though. Based on the shard-global data, this is the correct count of records per town:</p>\n<ul>\n<li><code>Town 1</code>: <code>11</code></li>\n<li><code>Town 2</code>:  <code>8</code></li>\n<li><code>Town 3</code>:  <code>9</code></li>\n<li><code>Town 4</code>:  <code>9</code></li>\n</ul>\n<p>The ③ result calculated by Elasticsearch has both the count value and ranking for <code>Town 2</code> wrong. Precision can be increased by analyzing returned <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html#terms-agg-doc-count-error\">count errors</a> and adjusting the <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html#search-aggregations-bucket-terms-aggregation-shard-size\">shard size</a> parameter - this commands each processing thread to return a larger <code>top n</code> result from each shard than requested by the query, increasing memory requirements and runtimes.</p>\n<blockquote>\n<p>Elasticsearch also leverages SIMD hardware units <a target=\"_blank\" href=\"https://cr.openjdk.org/~vlivanov/talks/2019_CodeOne_MTE_Vectors.pdf\">based</a> on the JVM's auto-vectorization and the Java <a target=\"_blank\" href=\"https://github.com/apache/lucene/pull/12311\">Panama Vector API</a>. Additionally, <a target=\"_blank\" href=\"https://www.elastic.co/blog/whats-new-elasticsearch-platform-8-12-0\">since</a> Elasticsearch 8.12 <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing/README.md#elasticsearch\">segments</a> can be searched in parallel by query processing threads, with the <a target=\"_blank\" href=\"https://www.elastic.co/blog/whats-new-elasticsearch-platform-8-12-0\">exception</a> of the <code>terms aggregation</code>. Because applying the above-mentioned technique to segments instead of shards has the same issue with precision. As a shard consists of multiple segments, this would also multiply the work per processing thread with an increased <code>shard size parameter</code>.</p>\n</blockquote>\n<h3 id=\"precision\"></h3>\n<h4 id=\"elasticsearch\"></h4>\n<p>As described <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#elasticsearch\">above</a>, count values in Elasticsearch's <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html\">terms aggregation</a> are <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html#terms-agg-doc-count-error\">approximate</a> by default when the queried data is split over more than one <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing/README.md#elasticsearch\">shard</a>. The accuracy of results can be improved by analyzing returned <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html#terms-agg-doc-count-error\">count errors</a> and adjusting the <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html#search-aggregations-bucket-terms-aggregation-shard-size\">shard size</a> parameter, but that increases runtimes and memory requirements.</p>\n<h4 id=\"clickhouse\"></h4>\n<p>The <code>count(*)</code> aggregation function in ClickHouse calculates fully accurate results.</p>\n<p>ClickHouse <code>count(*)</code> aggregations are easy to use and don't require additional configuration like in Elasticsearch.</p>\n<h3 id=\"no-limit-clause\"></h3>\n<h4 id=\"elasticsearch\"></h4>\n<p>Because of its <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#elasticsearch\">execution model</a>, count aggregations without a limit clause are impossible in Elasticsearch — users must always specify a <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html#search-aggregations-bucket-terms-aggregation-size\">size</a> setting. Even with large size values, bucket aggregations over high-cardinality data sets are restricted by the <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-settings.html#search-settings-max-buckets\">max_buckets</a> setting or require paginating through results using an <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-composite-aggregation.html\">expensive</a> <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-composite-aggregation.html\">composite aggregation</a>.</p>\n<h4 id=\"clickhouse\"></h4>\n<p>ClickHouse <code>count(*)</code> aggregations are not limited by size restrictions. They additionally <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/group-by#group-by-in-external-memory\">support</a> spilling temporary results to disk if the query memory consumption exceeds an (optional) user-specified maximum memory <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/query-complexity#settings-max_bytes_before_external_group_by\">threshold</a>. In addition, independent of data set size, ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/group-by#group-by-optimization-depending-on-table-sorting-key\">can</a> run aggregations with minimal memory requirements if the grouping columns in an aggregation form a prefix of the primary key.</p>\n<p>Again, ClickHouse <code>count(*)</code> aggregations have a lower degree of complexity compared to Elasticsearch.</p>\n<h2 id=\"approaches-for-continuous-data-summarization\"></h2>\n<p>No matter how efficient the aggregation and query processing in a database is, aggregating <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-one-billion-row-challenge\">billions</a> or <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-1-trillion-row-challenge\">trillions</a> of rows (typical in <a target=\"_blank\" href=\"https://clickhouse.com/blog/the-unbundling-of-the-cloud-data-warehouse\">modern data analytics</a> use cases) will always be inherently costly due to the sheer amount of data that must be processed.</p>\n<p>Therefore, databases specializing in analytical workloads often provide data summarization as a building block for users to automatically transform incoming data to a summarized data set, representing the original data in a <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=QUigKP7iy7Y&t=1s\">pre-aggregated</a> and usually <a target=\"_blank\" href=\"https://youtu.be/QUigKP7iy7Y?si=1QyGJdYTdE7q16gH&t=179\">significantly small</a> format. Queries will utilize the precomputed data to provide sub-second latencies in interactive use cases, like the above-mentioned <a target=\"_blank\" href=\"https://clickpy.clickhouse.com/\">ClickPy application</a>.</p>\n<p>Both Elasticsearch and ClickHouse provide built-in techniques for automatic continuous data summarization. Their techniques have the same functional capabilities but drastically differ in implementation, efficiency, and with that, computing costs.</p>\n<h3 id=\"elasticsearch\"></h3>\n<p>Elasticsearch provides a mechanism called <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/transforms.html\">transforms</a> for batch-converting existing indices into summarized indices or continuously converting ingested data.</p>\n<p>Based on the Elasticsearch <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing/README.md#elasticsearch\">on-disk format</a>, we describe how transforms work <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/continuous-data-transformation/README.md#elasticsearch\">here</a> in detail.</p>\n<p>We note three downsides of the Elasticsearch approach, namely:</p>\n<ul>\n<li>\n<p><strong>The requirement to retain old raw data</strong>: otherwise, transforms can’t correctly recalculate aggregations.</p>\n</li>\n<li>\n<p><strong>Poor scalability and high computing costs</strong>: Whenever new raw data documents are detected for buckets after a <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/continuous-data-transformation/README.md#elasticsearch\">checkpoint</a>, all of the bucket data is queried from the ever-growing raw data source index and reaggregated. This doesn’t scale to billion, let alone trillion-scale document sets, and results in high computing costs.</p>\n</li>\n<li>\n<p><strong>Not real-time</strong>: The transforms pre-aggregation target index is only up to date with the raw data source index after the next <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/continuous-data-transformation/README.md#elasticsearch\">check interval</a>.</p>\n</li>\n</ul>\n<blockquote>\n<p>Exclusively for time series metric data, Elasticsearch also provides a <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/downsampling.html\">downsampling</a> technique for reducing the footprint of that data by storing it at reduced granularity. Downsampling is the successor of <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/8.13/xpack-rollup.html\">rollups</a> and equivalent to a transform that groups metrics data documents by their timestamp casted to a fixed time interval (e.g. hour, day, month, or year) and then applies a fixed set of aggregations ( <code>min</code>, <code>max</code>, <code>sum</code>, <code>value_count</code>, and <code>average</code>). A comparison with ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/blog/chaining-materialized-views\">chained materialized views</a> could be the topic of a future blog.</p>\n</blockquote>\n<h3 id=\"clickhouse\"></h3>\n<p>ClickHouse uses <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/cascading-materialized-views\">materialized views</a> in combination with the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/aggregatingmergetree#aggregatingmergetree\">AggregatingMergeTree</a> table engine and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#-multi-core-parallelization\">partial aggregation states</a> for automatic and (in contrast to Elasticsearch) <strong>incremental</strong> data transformation.</p>\n<p>Based on ClickHouse’s <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing/README.md#clickhouse\">on-disk format</a>, we explain the mechanics of incremental materialized views in detail <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/continuous-data-transformation/README.md#clickhouse\">here</a>.</p>\n<p>ClickHouse materialized views have three key advantages over Elasticsearch transforms:</p>\n<ul>\n<li>\n<p><strong>No raw data dependency</strong>: Raw data in source tables is never queried, not even when the user wants to perform an exact aggregation calculation. This allows different <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/ttl\">TTL</a> settings to be applied to the source and the pre-aggregated target table. Furthermore, in scenarios where only the same set of aggregation queries should be performed, users can choose to ditch the source data after pre-aggregation completely (using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/null\">Null table engine</a>).</p>\n</li>\n<li>\n<p><strong>High scalability and low computing costs</strong>: Incremental aggregation is engineered especially for scenarios where raw data source tables contain billions or trillions of rows. Instead of querying the ever-growing source table repeatedly and recalculating aggregate values from all existing rows belonging to the same group when new raw data rows for that group exist, ClickHouse simply calculates a <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#-multi-core-parallelization\">partial aggregation state</a> from (only) the values of the newly inserted raw data rows. This state is incrementally <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/continuous-data-transformation/README.md#clickhouse\">merged</a> with the previously calculated states in the background. In other words - each raw data value is aggregated with other raw data values exactly once. This results in dramatically lower computing costs compared to aggregation by brute force over the raw data.</p>\n</li>\n<li>\n<p><strong>Real-time</strong>: When an insert into the raw data source table is successfully acknowledged, the pre-aggregation target table is guaranteed to be up-to-date.</p>\n</li>\n</ul>\n<h3 id=\"backfilling-pre-aggregations\"></h3>\n<p>In our <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_the_billion_row_matchup\">accompanying benchmark blog post</a>, we use continuous transforms in Elasticsearch and equivalent materialized views in ClickHouse to pre-aggregate ingested data on the fly into separate data sets. Sometimes, this is not feasible. For example, when a large portion of the data is already ingested, re-ingesting is not possible or too expensive, and queries that would benefit from running over this data in a pre-aggregated format are introduced.</p>\n<h4 id=\"elasticsearch\"></h4>\n<p>We simulated this scenario in Elasticsearch by running a <code>batch</code> transform over the already ingested <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_the_billion_row_matchup#data\">10 billion rows data set</a>, pre-calculating counts into a separate data set to speed up an aggregation query that we use as part of our benchmark. Both <code>continuous</code> and <code>batch</code> transforms use the same checkpoints-based mechanism described above. Because of the downsides of this mechanism, where the same values are queried and aggregated repeatedly at checkpoints:</p>\n<p><strong>Backfilling via the batch transform took 5 full days</strong> (using significant computing costs). It is a long time to wait until queries can benefit from the pre-aggregated data.</p>\n<h4 id=\"clickhouse\"></h4>\n<p>In ClickHouse, backfilling pre-aggregations works by using an <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/insert-into#inserting-the-results-of-select\">INSERT INTO SELECT</a> statement to insert directly into the materialized view’s target table <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch#variant-1---directly-inserting-into-the-target-table-by-using-the-materialized-views-transformation-query\">using</a> the view's SELECT query (transformation) :</p>\n<p><strong>For the 10 billion rows data set, this takes <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch#variant-1---directly-inserting-into-the-target-table-by-using-the-materialized-views-transformation-query\">20 seconds</a> instead of 5 full days</strong>.</p>\n<p>These 20 seconds include aggregating the full 10 billion row data set and writing the result (as partial aggregation states) into the target table, which will be used subsequently for the materialized view to handle additional incoming data. Depending on the cardinality of the raw data set, this can be a memory-intensive approach, as the complete raw data set is ad-hoc aggregated. Alternatively, users can utilize a <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch#variant-2---table-to-table-copy-into-a-null-table-engine-table-with-a-connected-materialized-view\">variant</a> that requires minimal memory.</p>\n<p>Note that the <code>20 seconds ClickHouse approach</code> of manually aggregating the raw data set and directly inserting the result into the target table is not feasible in Elasticsearch. Theoretically, this could work with a <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/docs-reindex.html\">reindex</a> (index to index copy) operation. However, this would require keeping the <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing/README.md#elasticsearch\">_source</a> data in the raw data set (requiring drastically more storage space).
