Additionally, for the <code>inverted index</code> the <code>keyword</code> type implies that there is no <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/analysis-normalizers.html\">normalization</a> and <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/analysis-tokenizers.html\">tokenization</a> of the field values. This is possible by setting the <code>index</code> <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/keyword.html#keyword-params\">parameter</a> for the <code>keyword</code> type to <code>false</code> in the index mapping. However, because these fields (<code>project</code> and <code>url</code>) are also part of our ClickHouse table’s primary key (and therefore, the ClickHouse primary index <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing/README.md#logical-and-physical-on-disk-data-structures-1\">data structure</a> is populated with values from these fields), we also kept the Elasticsearch <code>inverted index</code> for these fields.</p>\n<p>The <code>date</code> type <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/date.html\">is</a> internally stored as a <code>long</code> number in both <code>doc_values</code> (to support aggregations and sorting) and <code>Bkd trees</code> (queries on dates <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/date.html\">are</a> internally converted to range queries <a target=\"_blank\" href=\"https://www.elastic.co/blog/numeric-and-date-ranges-in-elasticsearch-just-another-brick-in-the-wall\">utilizing</a> Bkd trees). Because we <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch#tables\">use</a> the date column also as a primary key column in ClickHouse, we didn’t switch off Bkd trees for the date field in Elasticsearch.</p>\n<blockquote>\n<p>**In this blog, we focus on comparing the aggregation performance of the column-oriented <code>doc_values</code> data structure with ClickHouse’s columnar storage format and leave comparisons of other data structures for future blogs.</p>\n</blockquote>\n<h5 id=\"source\"></h5>\n<p>To compare storage implications of <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/mapping-source-field.html\">_source</a>, we used two different <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch#mappings\">index mappings</a>:</p>\n<ol>\n<li>one that stores <code>_source</code> (see the <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing/README.md#elasticsearch\">segment data structure</a> internals)</li>\n<li>one that doesn’t store <code>_source</code></li>\n</ol>\n<p>Note that by disabling <code>_source</code>, we <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_the_billion_row_matchup#storage-size\">reduce</a> the data storage size. However, <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/docs-reindex.html\">reindex</a> (index to index copy) operations (e.g. for changing an index mapping in hindsight or to <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/setup-upgrade.html#upgrade-index-compatibility\">upgrade</a> an index to a new major version) and <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/docs-update.html\">update</a> operations are <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/mapping-source-field.html#disable-source-field\">no longer possible</a>. Some queries also suffer with respect to performance because <code>_source</code> is the fastest way to retrieve field values in scenarios where all or a large subset of the indexed document fields are requested. Despite its <a target=\"_blank\" href=\"https://staging.clickhouse.com/blog/clickhouse_vs_elasticsearch_the_billion_row_matchup#storage-size\">much lower</a> storage requirements, ClickHouse always allows <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/insert-into#inserting-the-results-of-select\">table-to-table copy</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/lightweight-update\">update</a> operations.</p>\n<h4 id=\"transforms\"></h4>\n<p>For <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#approaches-for-continuous-data-summarization\">continuous data transformation</a>, we <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch#elasticsearch---transforms\">created</a> transforms for pre-calculating aggregations.</p>\n<p>We <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch#mappings-for-by-country_code-project-transforms-destination-indexes\">optimized</a> the automatically deduced index mappings for the transformed destination indexes to eliminate <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/mapping-source-field.html\">_source</a>.</p>\n<h3 id=\"clickhouse-setup\"></h3>\n<p>Configuring ClickHouse is much simpler compared to Elasticsearch and requires less upfront planning and setup code.</p>\n<h4 id=\"clickhouse-configuration\"></h4>\n<p>ClickHouse is deployed as a native binary. We are interested in running aggregation queries with cold caches, where the query processing engine must load and scan the data and calculate the aggregation result from scratch.</p>\n<h3 id=\"query-runtimes\"></h3>\n<p>We run all <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_the_billion_row_matchup#benchmark-queries\">benchmark queries</a> over the data sets that:</p>\n<ul>\n<li>Are compressed with the Elasticsearch and ClickHouse standard <code>LZ4</code> codec</li>\n<li>Don’t store <code>_source</code> in Elasticsearch</li>\n</ul>\n<p>All queries are executed three times with cold caches. We execute one query at a time i.e., measure latency only. In our charts in this blog, we take the average execution time as the final result and link to the detailed benchmark run results.</p>\n<h4 id=\"elasticsearch\"></h4>\n<p>We run Elasticsearch queries (DSL) via the <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search.html\">Search REST API</a> and use the JSON response body’s <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-search.html#search-api-response-body\">took</a> time, representing the total server-side execution time.</p>\n<p>ESQL queries are executed with the <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/esql-query-api.html\">ESQL REST API</a>. Responses of Elasticsearch ESQL queries don’t include any runtime information. Server-side execution times for ESQL queries are logged in Elasticsearch’s <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/logging.html\">log file</a>, though.</p>\n<p>We know that query runtimes are also available in the <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/index-modules-slowlog.html#search-slow-log\">search slow log</a>, but only on a per-shard level and not in consolidated form for the complete query execution over all involved shards.</p>\n<h4 id=\"clickhouse\"></h4>\n<p>All ClickHouse SQL queries are executed via <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/cli\">ClickHouse client</a>, and the server-side execution time is taken from the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/query_log\">query_log</a> system table (from the <code>query_duration_ms</code> field).</p>\n<h3 id=\"disabling-caches\"></h3>\n<h4 id=\"elasticsearch\"></h4>\n<p>For query processing, Elasticsearch <a target=\"_blank\" href=\"https://www.elastic.co/blog/elasticsearch-caching-deep-dive-boosting-query-speed-one-cache-at-a-time\">leverages</a> the operating-system-level <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Page_cache\">filesystem cache</a>, the shard-level <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/shard-request-cache.html\">request cache</a>, and the segment-level <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/query-cache.html\">query cache</a>.</p>\n<p>For DSL queries, we disabled the <code>request cache</code> on a per-request basis with the request_cache-<a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/shard-request-cache.html#_enabling_and_disabling_caching_per_request\">query-string parameter</a>. For ESQL queries, this is not possible, though.</p>\n<p>The <code>query cache</code> can only be enabled or disabled <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/query-cache.html#query-cache-index-settings\">per</a> index, but not per request. Instead, we manually dropped the request and query caches via the <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/indices-clearcache.html\">clear cache API</a> before each query run.</p>\n<p>There is no Elasticsearch API or setting for dropping or ignoring the <code>filesystem cache</code>, so we drop it manually using a simple <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch#process-for-dropping-filesystem-cache-for-elasticsearch\">process</a>.</p>\n<h4 id=\"clickhouse\"></h4>\n<p>Like Elasticsearch, ClickHouse utilizes the OS <code>filesystem cache</code> and a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/query-cache\">query cache</a> for query processing.</p>\n<p>Both caches can be manually dropped with a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/system\">SYSTEM DROP CACHE statement</a>.</p>\n<p>We disabled both caches per query with the query’s <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select#settings-in-select-query\">SETTINGS clause</a>:</p>\n<p><code>… SETTINGS enable_filesystem_cache=0, use_query_cache=0;</code></p>\n<h3 id=\"query-peak-memory-usages\"></h3>\n<h4 id=\"clickhouse\"></h4>\n<p>We use the ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/query_log\">query_log</a> system table to track and report queries' peak memory consumption (<code>memory_usage</code> field). As a bonus, we also report the data processing throughput (<code>rows/s</code> and <code>GB/s</code>) for some queries, as reported by the ClickHouse client. This can also be calculated from <code>query_log</code> fields (e.g. <code>read_rows</code> and <code>read_bytes</code> divided by <code>query_duration_ms</code>).</p>\n<h4 id=\"elasticsearch\"></h4>\n<p>Elasticsearch runs all queries within the Java JVM, with half of the machine's available 64 GB RAM allocated at startup. Elasticsearch doesn’t directly track queries' peak memory consumptions within the JVM memory. The <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/search-profile.html\">search profiling API</a>, used under the hood of Kibana’s graphical <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/kibana/current/xpack-profiler.html\">search profiler</a>, only profiles queries' CPU usage. Likewise, the <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/index-modules-slowlog.html#search-slow-log\">search slow log</a> only tracks runtimes but not memory. The <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/cluster-stats.html\">Cluster stats API</a> returns cluster and node-level metrics and statistics like current peak JVM memory usage, e.g. returned by this call:\n<code>GET /_nodes/stats?filter_path=nodes.*.jvm.mem.pools.old</code>.
