contentHtml: "<article><div><div><p>In the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-vs-promethous-high-cardinality-p1-understanding-the-problem\">previous post</a>, we explored why high cardinality creates challenges for Prometheus and other series-oriented time-series databases. We looked at how the underlying storage model, where every unique combination of labels creates an independent time series, introduces memory overhead, write amplification, operational complexity, and query-time tradeoffs as dimensionality and churn increase.</p>\n<p>You’ll often hear us say that ClickHouse is not significantly affected by high cardinality when used for observability workloads. That’s true for the workloads we usually mean, but it needs qualification. ClickHouse still pays for cardinality, mostly at query time rather than during ingestion.</p>\n<p>In this post, we'll explore why ClickHouse, and more broadly column-oriented databases, handle high-cardinality observability data so differently from systems such as Prometheus.</p>\n<p>We'll also cover where this model is weaker than Prometheus. ClickHouse is not a drop-in Prometheus replacement, and this approach requires a different way of thinking about telemetry, instrumentation, and aggregation.</p>\n<h2 id=\"why-cardinality-is-different-in-clickhouse\"></h2>\n<p>To understand why high cardinality behaves differently in ClickHouse, we first need to rethink how observability data is modeled. Rather than treating telemetry as millions of independently maintained time series, ClickHouse encourages a shift toward representing metrics as rows in a table containing attributes and measurements that can later be aggregated at query time.</p>\n<p>This is often referred to as the \"wide events\" approach, <a target=\"_blank\" href=\"https://charity.wtf/2022/08/15/live-your-best-life-with-structured-events/\">popularized by practitioners such as Charity Majors</a>. If it helps, you can think of this simply as logs with metrics attached. Let’s first explore how this differs from a traditional Prometheus-style metric model.</p>\n<h3 id=\"metrics-as-wide-events\"></h3>\n<p>It’s important to emphasize that we are not attempting to directly model Prometheus metrics, metric types, or PromQL semantics inside ClickHouse, although work in this <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/102246\">area is underway</a> and the model certainly has benefits, which we’ll explore later. Instead, the wide events approach encourages a broader shift away from the traditional Prometheus metric model toward an event-style model for observability data.</p>\n<p>In this model, telemetry is represented as timestamped events containing dimensions, attributes, and numeric measurements, rather than as independently maintained time series. Instead of storing a metric as a separate series with its own identity and lifecycle, each event contains contextual attributes alongside one or more numeric measurements. Queries then dynamically aggregate these events into the desired views, rates, summaries, or time buckets at read time.</p>\n<p>Importantly, this is often a more relaxed and natural way to produce telemetry. Rather than defining strict metric schemas in advance, applications simply emit structured events with numeric values. A common pattern in ClickHouse observability deployments is to store metrics directly alongside logs using wide event schemas<a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/ingesting-data/schemas\"> such as otel_logs</a>.</p>\n<p>For example, rather than defining multiple separate metrics for response times, request counts, status codes, and hosts, a service might simply emit events like:</p></div><div><pre><code><span>logger.<span>Info</span>(<span>\"request completed\"</span>,</span>\n<span>    zap.<span>String</span>(<span>\"host\"</span>, <span>\"host-42\"</span>),</span>\n<span>    zap.<span>String</span>(<span>\"application\"</span>, <span>\"checkout-service\"</span>),</span>\n<span>    zap.<span>String</span>(<span>\"request_path\"</span>, <span>\"/api/payments\"</span>),</span>\n<span>    zap.<span>Uint16</span>(<span>\"status\"</span>, responseStatus),</span>\n<span>    zap.<span>Uint64</span>(<span>\"response_time\"</span>, responseTime),</span>\n<span>    zap.<span>Uint64</span>(<span>\"size\"</span>, responseSize),</span>\n<span>)</span></code></pre></div><p>With wide events, the request itself becomes the natural unit of telemetry. All contextual dimensions and measurements remain attached to the same event. In a Prometheus-style model, the same information would typically be decomposed across multiple metric definitions, counters, gauges, histograms, and label combinations. Once collapsed into aggregates this way, the individual signals are lost and unrecoverable. Its primary limitation is that all keys and values must share the same type, with the map defined as <code>Map&lt;String, type&gt;</code>. In practice, this usually means values are stored as strings. While this is flexible, it can require query-time casting if values need to be interpreted as numeric or other strongly typed data.</p>\n<p>Historically, Map also had an important disadvantage at read time. Reading a single label required reading the entire map structure and all labels associated with it, creating significant I/O overhead. However, recent support for <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-26-03#sharded-map\">sharded maps</a> largely mitigates this issue by allowing more selective access to map contents.</p>\n<p>For our earlier example, a table schema for wide events might look like:</p></div><div><pre><code><span><span>CREATE TABLE</span> events</span>\n<span>(</span>\n<span>    `<span>time</span>` DateTime CODEC(Delta(<span>4</span>), ZSTD(<span>3</span>)),</span>\n<span>    `labels` Map(LowCardinality(String), String),</span>\n<span>    `response_time` UInt16 MATERIALIZED toUInt16(labels[<span>'response_time'</span>]),</span>\n<span>    `host` LowCardinality(String) MATERIALIZED labels[<span>'host'</span>],</span>\n<span>    `status` LowCardinality(String) MATERIALIZED labels[<span>'status'</span>],</span>\n<span>    `application` LowCardinality(String) MATERIALIZED labels[<span>'application'</span>],</span>\n<span>    INDEX idx_labels_keys mapKeys(labels) TYPE text(tokenizer <span>=</span> <span>array</span>),</span>\n<span>    INDEX idx_labels_vals mapValues(labels) TYPE text(tokenizer <span>=</span> <span>array</span>)</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (host, toStartOfMinute(<span>time</span>), status, application)</span>\n<span>SETTINGS</span>\n<span>    map_serialization_version <span>=</span> <span>'with_buckets'</span>,</span>\n<span>    max_buckets_in_map <span>=</span> <span>32</span>,</span>\n<span>    map_buckets_strategy <span>=</span> <span>'sqrt'</span>;</span></code></pre></div><div><p><em>Note that the settings here force sharding of the map. So rather than thinking in terms of \"series objects\", ClickHouse simply stores rows of data containing a timestamp, a sharded map of labels, and regular numeric columns for metric values.</p>\n<p>We have also <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/performance_tuning#materialize-frequently-queried-attributes\">materialized keys from the labels map</a> that we expect to be filtered on or accessed frequently, so they can exist as dedicated columns on disk. This materialization occurs automatically at insert time and enables ClickHouse to filter, prune, and read these dimensions directly without accessing the labels map at query time, reducing I/O for common access patterns.</p>\n<p>The same approach can also be applied to frequently queried numeric values. In the example above, <code>response_time</code> is materialized from the map into a dedicated typed column because it is expected to be aggregated regularly. This avoids repeated map access and query-time casting when computing operations such as <code>avg(response_time)</code> or percentile calculations.</p>\n<p>Importantly, materialized columns can also be added after data has already been ingested. Newly inserted rows will physically store the materialized column on disk, while older rows can still resolve the value indirectly from the underlying map when queried. For example, if we later decide that <code>labels['region']</code> has become a common filter, we could add:</p></div><div><pre><code><span><span>ALTER TABLE</span> events</span>\n<span><span>ADD</span> <span>COLUMN</span> region LowCardinality(String)</span>\n<span>MATERIALIZED labels[<span>'region'</span>];</span></code></pre></div><div><p>New data will immediately benefit from direct column access, pruning, and improved compression, while historical rows still remain queryable via <code>region</code> without requiring a full table rewrite.</p>\n<p>Internally, a <code>Map</code> is represented as an array of key-value pairs, with bucketed serialization that distributes keys across multiple independent buckets based on a hash of the label name. This means that queries that read a specific label only need to access the bucket containing that key, rather than the full map structure. Metric columns themselves are stored independently and compressed separately from the labels.</p>\n<p><span><img alt=\"map_type_clickstack.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmap_type_clickstack_0ce07ceb2c.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p><em>① Each insert initially creates a Level 0 part using the default <code>Map</code> layout, where keys and values are stored as flat arrays without bucketing.  ② Additional inserts create more Level 0 parts in the same format. Since these parts are small, scanning the full key and value arrays is typically inexpensive.  ③ During background merges, ClickHouse rewrites the <code>Map</code> into bucketed storage by hashing keys into smaller independent buckets. In Prometheus, each new label combination creates a new series object with its own metadata, chunks, and indexing overhead. In ClickHouse, adding a new combination of label values does not create a new structural object or in-memory series representation. It simply adds another row containing a different set of label values.\nWhen rows are inserted, they are written to disk as a part, sorted by the target table’s primary key - in this case, the host, timestamp with a granularity of one minute, status, and application. Codecs can be applied to each column before ZSTD compression to minimize future I/O during reads.</p></div><div><p>To manage the number of parts per table, a background merge job periodically combines smaller parts into larger ones, while preserving the specified sort order, until they reach a configurable compressed size (typically ~150 GB). Over time, this process creates a hierarchical structure of merged parts.</p>\n<p><span><img alt=\"part_merging.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpart_merging_c7cdd2fb3d.png&w=2048&q=75\"></span></p>\n<p>At insert time, ClickHouse writes rows, not series objects.</p>\n<h3 id=\"benefits-of-columnar-storage\"></h3>\n<p>The column orientation and sorting of the table still provide several important benefits, even when the labels themselves are stored in a Map rather than as fully independent columns.</p>\n<ul>\n<li>\n<p><strong>Fast filtering with data pruning</strong> - A sparse index is built over the table’s sorting key, which in this case consists of commonly filtered dimensions materialized from the label map, followed by the timestamp.</p>\n<p>In the example above, labels such as host, status, and application are materialized into dedicated columns and included in the ordering key. Data is stored in parts, with each part divided into granules of roughly 8,000 rows. For each granule, ClickHouse records the first value of the sorting key columns rather than indexing every row, which is why the index is considered sparse.</p>\n<p>Because the data is physically ordered by frequently queried dimensions and then by time, rows with similar values are naturally grouped together on disk. This allows ClickHouse to efficiently prune granules when queries filter on common labels such as host, application, status, or a time range. Instead of scanning the entire dataset, it can skip large sections of irrelevant data and read only the granules likely to contain matching rows, significantly reducing I/O and improving query performance.</p>\n<p>Secondary indexes over <code>mapKeys(labels)</code> and <code>mapValues(labels)</code> further complement this. These inverted indexes allow ClickHouse to prune granules even when filtering on labels that are not materialized into dedicated columns, helping retain flexibility for highly dynamic dimensions.</p>\n</li>\n</ul></div><div><ul>\n<li>\n<p><strong>Compression</strong> - Even with labels stored inside a Map, ClickHouse still achieves excellent compression for observability workloads. Data is physically ordered by commonly filtered dimensions such as host, status, and application, followed by time. This naturally groups together rows with similar label sets, metric values, and repeated strings, creating strong locality that compression algorithms can exploit effectively.</p>\n<p>Materializing frequently queried labels into dedicated columns further improves compression. Since rows with the same values are stored contiguously on disk, dictionary encoding and compression codecs become significantly more effective.</p>\n<p>Metric columns that have been materialized, such as <code>response_time</code> in the above example, remain fully column-oriented and are compressed independently using both type-specific codecs and general-purpose compression algorithms such as ZSTD. Numeric columns can additionally benefit from <a target=\"_blank\" href=\"https://clickhouse.com/blog/optimize-clickhouse-codecs-compression-schema\">codecs such as Delta</a> or <a target=\"_blank\" href=\"https://www.vldb.org/pvldb/vol8/p1816-teller.pdf\">Gorilla</a>.</p>\n<p>The Map structure itself also compresses effectively. Label keys are highly repetitive across rows, while many label values exhibit strong temporal locality in real workloads - Use of materialized map labels in the primary key helps with this locality. Combined with sharded map serialization, this allows ClickHouse to maintain strong compression characteristics even with highly dynamic label sets.</p>\n</li>\n<li>\n<p><strong>Reduced I/O</strong> - Reduced I/O - Queries only need to read the granules, columns, and map buckets required to satisfy the query. Frequently filtered labels and metrics, such as <code>host</code>, <code>response_time</code>, and <code>status</code> are materialized into dedicated columns, allowing many common queries to avoid accessing the label map entirely. Because these materialized columns are part of the sorting key, ClickHouse can efficiently prune granules before reading metric data.</p>\n<p>For labels stored only inside the sharded <code>Map</code>, ClickHouse reads only the bucket containing the requested keys rather than the full label structure. This significantly reduces I/O compared to earlier map implementations while preserving the flexibility of dynamic labels.</p>\n<p>The schema also defines <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/mergetree-family/textindexes\">inverted indexes</a> over <code>mapKeys(labels)</code> and <code>mapValues(labels)</code>. These indexes allow ClickHouse to further prune granules when queries filter on non-materialized labels, avoiding reads of granules that cannot contain the requested label names or values. This provides efficient filtering even for highly dynamic dimensions such as <code>container_id</code> or <code>pod_id</code> without requiring every label to become a dedicated column.</p>\n<p>Because metric columns are stored independently and contiguously on disk, ClickHouse can also efficiently apply vectorized query execution, reading large batches of values continuously into memory for high analytical throughput.</p>\n</li>\n</ul>\n<p><span><img alt=\"text_indices.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Ftext_indices_e6cfb586de.png&w=2048&q=75\"></span></p>\n<p><em>At query time, the text index uses a layered lookup process to efficiently resolve matching rows without scanning the full dataset, using a sparse index, dictionary blocks and posting listings. For more details, see <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-full-text-search-object-storage\">our dedicated post</a>.</em></p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/skipping-indexes#bloom-filter-types\">Bloom filter indices</a> can also be used for this purpose and may be sufficient for many workloads. In practice, the best choice depends on the label distribution, query patterns, and the selectivity of the applied filters.</p>\n<ul>\n<li>\n<p><strong>Analytical aggregations</strong> - In this model, metrics are represented as numeric columns, such as <code>response_time</code>. Aggregations become straightforward and efficient. If we want to compute something like <code>avg(response_time)</code>, ClickHouse only needs to read the <code>response_time</code> column for the rows that match the query filters. Thanks to the sparse index and secondary filters, the engine can identify the specific granule ranges that satisfy the filters and only read those ranges from disk. Those ranges can be processed in parallel across all CPU cores and servers in a cluster. This gives us effective predicate pushdown at the storage level.</p>\n<p>As a result, aggregation performance is not directly tied to cardinality as in a series-based model. It is more closely related to the number of rows that match the query filters. Only the relevant metric column needs to be read for the matching rows. Filters on high-cardinality columns are often beneficial because they tend to reduce the number of rows scanned. In contrast, queries with no filters or filters on low-cardinality columns will typically require more data to be read, which requires parallelized reads for performance.</p>\n</li>\n</ul>\n<h3 id=\"example\"></h3>\n<p>Consider the earlier <code>metrics</code> table. Each type encodes assumptions about how the data should be interpreted. Counters handle rates and resets. Histograms and summaries support latency and distribution analysis. This is largely due to the complexity of fully reproducing Prometheus semantics, particularly around counters, histograms, range vectors, and the broader PromQL execution model.</p>\n<p>If you require mature, battle-tested PromQL support deeply integrated into dashboards, alerts, and operational workflows, Prometheus remains the obvious choice. By shifting from a series-oriented model to wide events stored in column-oriented tables, ClickHouse avoids the per-series write amplification, memory overhead, and operational fragility that make cardinality so challenging in systems such as Prometheus. Instead, the tradeoffs move primarily to query-time aggregation and data modeling decisions, areas where ClickHouse’s columnar execution model, compression, pruning, and parallelization are particularly strong.</p></div></div></article>"
