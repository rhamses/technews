contentHtml: "<article><div><p><a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhousectl\"><code>clickhousectl</code></a> is the CLI for ClickHouse, local and cloud, built to help both humans and AI agents develop with ClickHouse.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhousectl-v0-2-0-postgres-clickpipes-more\">v0.2.0</a> brought managed Postgres, ClickPipes for eight data sources, and SQL-over-HTTP. v0.3.0 brings a raft of improvements for the agentic experience, more ways to install, OAuth support for Query Endpoints, and custom configs.</p>\n<p>If you already have it installed, update in place:</p>\n<div><pre><code><span>clickhousectl update</span></code></pre></div>\n<p>If not, install it using your favorite method below:</p>\n<div><pre><code><span>curl https://clickhouse.com/cli | sh</span>\n<span>pip install clickhousectl</span>\n<span>uv tool install clickhousectl</span>\n<span>npm i -g clickhousectl</span>\n<span>cargo install clickhousectl</span></code></pre></div>\n<h2 id=\"a-global-clickhouse-on-your-path\"></h2>\n<p>When you select a default ClickHouse version with <code>clickhousectl local use latest</code>, this now puts ClickHouse on your path at <code>~/.local/bin/clickhouse</code>. It's similar to doing <code>./clickhouse install</code> with the binary itself, but allows you to manage the version globally with <code>clickhousectl</code>. This means you can shell directly to the <code>clickhouse</code> binary to use its myriad of subcommands (<code>local</code>, <code>benchmark</code>, <code>format</code>, etc,.)</p>\n<h2 id=\"improving-the-agent-experience\"></h2>\n<h3 id=\"structured-output-by-default-for-agents\"></h3>\n<p>In v0.3.0, <code>clickhousectl</code> can detect when it's running inside various coding agents, and optimise its behavior automatically. For example, it will now default to JSON output on stdout when running inside an agent.</p>\n<p>This detection depends on agents self-declaring via non-sensitive environment variables (<code>AGENT</code>, <code>AI_AGENT</code> and some agent-specific variables that have not standardised yet).</p>\n<h3 id=\"meaningful-error-codes\"></h3>\n<p>Alongside this, exit codes now follow <a target=\"_blank\" href=\"https://cli.github.com/\"><code>gh</code></a> conventions, so agents and scripts can branch on why a command failed.</p>\n<div><table><thead><tr><th>Code</th><th>Meaning</th></tr></thead><tbody><tr><td><code>0</code></td><td>Success</td></tr><tr><td><code>1</code></td><td>Error (anything not classified below)</td></tr><tr><td><code>2</code></td><td>Cancelled (user aborted)</td></tr><tr><td><code>4</code></td><td>Auth required (no credentials, 401/403, OAuth-only writes)</td></tr></tbody></table></div>\n<h2 id=\"env-support-for-cloud-credentials\"></h2>\n<p><code>clickhousectl</code> now reads a <code>.env</code> file in your working directory for <code>CLICKHOUSE_</code> environment variables. Add your Cloud API credentials in there and any <code>cloud</code> command will pick them up:</p>\n<div><pre><code><span>CLICKHOUSE_CLOUD_API_KEY=your-key</span>\n<span>CLICKHOUSE_CLOUD_API_SECRET=your-secret</span></code></pre></div>\n<h2 id=\"query-clickhouse-cloud-services-with-oauth\"></h2>\n<p><code>cloud service query</code> runs SQL against a Cloud service over HTTP. Previously, it only supported using API keys for auth and required provisioning a Query Endpoint. v0.3.0 adds support for querying services with OAuth. When using OAuth, you do not need to first provision a Query Endpoint.</p>\n<div><pre><code><span>clickhousectl cloud auth login</span>\n<span>clickhousectl cloud service query --name my-service --query <span>\"SELECT 1\"</span></span></code></pre></div>\n<p>Querying an idled service wakes it automatically. A stopped service is never woken and fails with a hint to run <code>clickhousectl cloud service start</code>.</p>\n<h2 id=\"custom-config-files-for-local-servers\"></h2>\n<p>Local servers start with sensible defaults, but sometimes you need to flip a setting. v0.3.0 lets you drop a config into <code>~/.clickhouse/configs/</code> and apply it by name:</p>\n<div><pre><code><span><span>mkdir</span> -p ~/.clickhouse/configs</span>\n<span><span>cat</span> &gt; ~/.clickhouse/configs/analytics.xml &lt;&lt;<span>'EOF'</span></span>\n<span>&lt;clickhouse&gt;</span>\n<span>    &lt;query_log&gt;</span>\n<span>        &lt;database&gt;system&lt;/database&gt;</span>\n<span>        &lt;table&gt;query_log&lt;/table&gt;</span>\n<span>    &lt;/query_log&gt;</span>\n<span>&lt;/clickhouse&gt;</span>\n<span>EOF</span>\n<span></span>\n<span><span># See which configs are available</span></span>\n<span>clickhousectl <span>local</span> server configs</span>\n<span></span>\n<span><span># Start a server with one applied</span></span>\n<span>clickhousectl <span>local</span> server start --config-file analytics</span></code></pre></div>\n<p>The named file is overlaid on top of ClickHouse's built-in defaults, so it only needs to contain the settings you want to change, no need to reproduce a full config. Files can be <code>.xml</code>, <code>.yaml</code>, or <code>.yml</code>, and you can reference them by name with or without the extension.</p>\n<h2 id=\"more-install-options\"></h2>\n<p><code>clickhousectl</code> already ships via the install script, <code>cargo binstall</code>, npm, and crates.io. v0.3.0 adds the Python packaging ecosystem:</p>\n<div><pre><code><span>pip install clickhousectl</span>\n<span><span># or</span></span>\n<span>pipx install clickhousectl</span>\n<span><span># or</span></span>\n<span>uv tool install clickhousectl</span></code></pre></div>\n<h2 id=\"postgres-in-local-init\"></h2>\n<p><code>local init</code> scaffolds a standard folder structure for your ClickHouse project files. With managed and local Postgres now part of <code>clickhousectl</code>, <code>init</code> also lays down a <code>postgres/</code> tree alongside the <code>clickhouse/</code> one:</p>\n<div><pre><code><span>clickhousectl <span>local</span> init</span></code></pre></div>\n<div><pre><code><span>clickhouse/</span>\n<span>├── tables/</span>\n<span>├── materialized_views/</span>\n<span>├── queries/</span>\n<span>└── seed/</span>\n<span>postgres/</span>\n<span>├── tables/</span>\n<span>├── views/</span>\n<span>├── functions/</span>\n<span>├── queries/</span>\n<span>└── seed/</span></code></pre></div>\n<h2 id=\"faster-offline-friendly-version-resolution\"></h2>\n<p>When you ask for a version spec like <code>stable</code> or <code>26.5</code>, <code>clickhousectl</code> now checks your already-installed versions <em>before</em> reaching out to the network. If you've got a match locally, commands like <code>clickhousectl local use 26.5</code> resolve instantly and work offline, only falling back to a remote lookup when there's nothing suitable installed.</p>\n<h2 id=\"deprecated-fields-removed\"></h2>\n<p>Deprecated API fields are now hidden from CLI output to prevent confusing agents.</p></div></article>"
