contentHtml: "<article><div><p><a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhousectl\"><code>clickhousectl</code></a> is the CLI for ClickHouse, local and cloud, built to help both humans and AI agents develop with ClickHouse.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhousectl-v0-3-0\">v0.3.0</a> brought agent-aware defaults, OAuth querying for Cloud, and custom local server configs. v0.4.0 adds horizontal autoscaling for Cloud services, ClickPipe schema discovery, finer control over ClickPipe ingestion, and opt-out anonymous usage telemetry.</p>\n<p>If you already have it installed, update in place:</p>\n<div><pre><code><span>clickhousectl update</span></code></pre></div>\n<p>If not, install it using your favorite method below:</p>\n<div><pre><code><span>curl https://clickhouse.com/cli | sh</span>\n<span>pip install clickhousectl</span>\n<span>uv tool install clickhousectl</span>\n<span>npm i -g clickhousectl</span>\n<span>cargo install clickhousectl</span></code></pre></div>\n<h2 id=\"horizontal-autoscaling-for-cloud-services\"></h2>\n<p>ClickHouse Cloud services have two autoscaling modes: vertical (a fixed replica count with variable memory per replica) and horizontal (fixed memory per replica with a variable replica count). v0.4.0 exposes horizontal autoscaling on <code>service create</code> and <code>service scale</code>:</p>\n<div><pre><code><span>clickhousectl cloud service create --name my-service \\</span>\n<span>  --min-replicas 2 --max-replicas 8 --autoscaling-mode horizontal</span>\n<span></span>\n<span>clickhousectl cloud service scale &lt;service-id&gt; \\</span>\n<span>  --min-replicas 2 --max-replicas 8 --autoscaling-mode horizontal</span></code></pre></div>\n<p>The horizontal flags are mutually exclusive with the vertical ones (<code>--num-replicas</code>, <code>--min-replica-memory-gb</code>/<code>--max-replica-memory-gb</code> as a variable range), and the CLI rejects <code>--min-replicas</code> without <code>--max-replicas</code> before making any network call. Horizontal autoscaling requires the org-level feature to be enabled.</p>\n<h2 id=\"clickpipe-schema-discovery-beta\"></h2>\n<p><code>clickpipe schema-discover</code> probes a Kafka or Kinesis source and returns the inferred fields and types without creating a pipe. Use it to preview the <code>--column</code> definitions before you create the pipe for real. It takes the same source connection flags as the corresponding <code>create</code> subcommand, minus the destination options:</p>\n<div><pre><code><span>clickhousectl cloud clickpipe schema-discover &lt;service-id&gt; kafka \\</span>\n<span>  --brokers <span>'broker:9092'</span> --topics events \\</span>\n<span>  --format JSONEachRow \\</span>\n<span>  --auth SCRAM-SHA-256 --username user --password pass</span></code></pre></div>\n<p>Note that <code>schema-discover</code> requires an API key and does not support a read-only OAuth login.</p>\n<h2 id=\"finer-control-over-clickpipe-ingestion\"></h2>\n<p>Object storage pipes with continuous ingestion get two new controls: <code>--skip-initial-load</code> skips the initial snapshot and only ingests new objects, and <code>--start-after</code> resumes ingestion after a specific object key:</p>\n<div><pre><code><span>clickhousectl cloud clickpipe create object-storage &lt;service-id&gt; \\</span>\n<span>  --name my-s3-continuous-pipe \\</span>\n<span>  --source-url <span>'https://bucket.s3.us-east-1.amazonaws.com/data/**'</span> \\</span>\n<span>  --format JSONEachRow \\</span>\n<span>  --continuous \\</span>\n<span>  --queue-url <span>'https://sqs.us-east-1.amazonaws.com/123/my-queue'</span> \\</span>\n<span>  --start-after obj-key-001 \\</span>\n<span>  --database default --table events \\</span>\n<span>  --column <span>\"event_id:Int64\"</span> --column <span>\"name:String\"</span></span></code></pre></div>\n<p><code>--skip-initial-load</code> only applies when <code>--queue-url</code> is set, and it's mutually exclusive with <code>--start-after</code>.</p>\n<p>MySQL CDC pipes can now set the replication server ID with <code>--server-id</code>, useful when multiple pipes read from the same MySQL instance or to avoid colliding with existing replicas:</p>\n<div><pre><code><span>clickhousectl cloud clickpipe create mysql &lt;service-id&gt; \\</span>\n<span>  --name my-mysql-pipe \\</span>\n<span>  --host mysql.example.com \\</span>\n<span>  --username root --password pass \\</span>\n<span>  --table-mapping <span>\"mydb.users:mydb_users\"</span> \\</span>\n<span>  --server-id 4242</span></code></pre></div>\n<h2 id=\"partial-updates-for-postgres-configs\"></h2>\n<p><code>cloud postgres config patch</code> now applies true partial updates. Pass only the settings you want to change and everything else in the config keeps its current value:</p>\n<div><pre><code><span>clickhousectl cloud postgres config patch &lt;pg-id&gt; --<span>set</span> max_connections=500</span></code></pre></div>\n<h2 id=\"global-oauth-tokens\"></h2>\n<p>OAuth tokens from <code>cloud auth login</code> now live globally at <code>~/.clickhouse/tokens.json</code>, alongside your versions and configs. Existing project-local token files are migrated automatically on first use. OAuth remains <strong>read-only</strong>.</p>\n<p>API key credentials (<code>credentials.json</code>) stay project-local. Use API keys for destructive permissions on a per-org / per-project level.</p>\n<h2 id=\"safer-local-server-lifecycle\"></h2>\n<p><code>local server stop &lt;name&gt;</code> is now idempotent, matching <code>docker stop</code> and <code>systemctl stop</code>. Stopping a server that exists but isn't running succeeds with exit code 0 instead of erroring. Unknown names still fail, so typos surface. <code>--json</code> output gains an <code>already_stopped</code> field so scripts can tell a real stop from a no-op.</p>\n<p><code>local remove &lt;version&gt;</code> now refuses to delete a version that a running server is using. Previously it deleted the binary out from under the server and reported success. It fails with the server names listed, and <code>--force</code> stops them first:</p>\n<div><pre><code><span>clickhousectl <span>local</span> remove 26.5</span>\n<span><span># Error: Version 26.5 is in use by running server(s): default.</span></span>\n<span><span># Stop them first, or pass --force.</span></span>\n<span></span>\n<span>clickhousectl <span>local</span> remove 26.5 --force</span>\n<span><span># Stopped server 'default'</span></span>\n<span><span># Removed 26.5</span></span></code></pre></div>\n<p><code>--config</code> is now the primary flag for <code>local server start</code> (<code>--config-file</code> still works as a hidden alias), and <code>stop-all</code> flushes its progress output immediately, so it no longer looks frozen during the graceful-kill wait.</p>\n<h2 id=\"anonymous-usage-telemetry\"></h2>\n<p>v0.4.0 adds anonymous usage telemetry to help us understand which commands matter. Each event contains: the command path, the <em>names</em> of flags passed (never values, never positional arguments), the exit code, the CLI version, OS and architecture, whether it ran in CI, and whether it ran under a detected coding agent. There is <strong>no install ID and no fingerprinting</strong>.</p>\n<p>The first run of <code>clickhousectl</code> prints a one-time telemetry notice and sends no telemetry, giving you the opportunity to opt-out before anything is sent. Opting out works any of these ways:</p>\n<div><pre><code><span><span># Persistently, per machine</span></span>\n<span>clickhousectl telemetry <span>disable</span></span>\n<span></span>\n<span><span># Check the current state</span></span>\n<span>clickhousectl telemetry status</span>\n<span></span>\n<span><span># Per environment/shell (https://consoledonottrack.com)</span></span>\n<span><span>export</span> DO_NOT_TRACK=1</span></code></pre></div>\n<p>To see exactly what would be sent without sending it, set <code>CHCTL_TELEMETRY_DEBUG=1</code>. You can compile telemetry out entirely with <code>cargo build --no-default-features</code>. Full details are in the <a target=\"_blank\" href=\"https://clickhouse.com/docs/interfaces/cli#telemetry\">telemetry docs</a>.</p>\n<h2 id=\"running-server-in-one-command\"></h2>\n<p>On a fresh install you can now start a server without setting a default or specifying a version and it will automatically install the latest master build of ClickHouse.</p>\n<div><pre><code><span>clickhousectl <span>local</span> server start</span></code></pre></div>\n<p><code>clickhousectl</code> also now records the etag of an installed master build. If the build hasn't moved, the installed binary is reused on successive installs:</p>\n<div><pre><code><span>clickhousectl <span>local</span> install latest</span>\n<span><span># first run: downloads master</span></span>\n<span>clickhousectl <span>local</span> install latest</span>\n<span><span># latest is up to date (master build unchanged); using 26.7.1.1</span></span></code></pre></div>\n<h2 id=\"better-update-visibility\"></h2>\n<p><code>clickhousectl</code> looks for an available update when you run a command, caches the result, and does not look again for 24 hours. The \"update available\" message is now more present on successive commands to encourage more frequent updating. Running <code>clickhousectl update</code> updates the binary, and clears the cache.</p></div></article>"
