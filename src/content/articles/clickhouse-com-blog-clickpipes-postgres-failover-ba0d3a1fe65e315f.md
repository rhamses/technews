contentHtml: "<div><h2 id=\"introduction\"></h2>\n<p>To continue providing maximum reliability and flexibility for all Postgres ClickPipes users, we have now added a toggle to allow creating a logical replication slot with failover enabled. This allows ClickPipes to work seamlessly with high-availability (HA) to preserve replication slots post-failover.</p>\n<h2 id=\"background\"></h2>\n<p>Postgres has a feature known as <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/hot-standby.html\">hot standbys</a> that allows \"read replicas\" of a Postgres instance to be spun up for querying. Hot standbys recently gained the ability to perform logical decoding (introduced in Postgres 16, released 2023), which allows users to move their CDC workloads off their primary instance. However, this was not enough to unlock high availability for CDC, as any slots created were only for that cluster and not replicated in any manner. In Postgres 17 (released 2024), this was addressed by enabling logical replication failover, which essentially selects slots on the primary instance to be periodically synchronized to one or more standbys in a way that allows logical decoding to resume cleanly after a standby is promoted.</p>\n<h2 id=\"why-would-you-want-this\"></h2>\n<p>Postgres is quintessentially a \"core\" database for transaction processing, and that has often necessitated high-availability via standbys (as Postgres is a single-writer design). However, as query workloads diversify, it is becoming increasingly common to replicate data from Postgres to other sources via CDC to leverage their strengths. Until very recently, while Postgres itself was HA, these pipelines were not. Logical replication failover now makes this a reality.</p>\n<h2 id=\"process\"></h2>\n<p>Although the ClickPipe itself only contains a toggle to enable failover, the entire process of preparing failover slots for use is more complex and has several prerequisites. If you are using Postgres on-premises, you can configure it using the steps below. If you are running Postgres through a managed provider (such as <a target=\"_blank\" href=\"https://aws.amazon.com/rds/\">AWS RDS</a> or <a target=\"_blank\" href=\"https://cloud.google.com/sql?hl=en\">Google CloudSQL</a>), you'll need to work with your provider to ensure that the Postgres configuration settings are correctly tuned. Some providers, such as <a target=\"_blank\" href=\"https://planetscale.com/postgres\">PlanetScale for Postgres</a>, already <a target=\"_blank\" href=\"https://planetscale.com/docs/postgres/integrations/logical-cdc#configure-planetscale-cluster-for-failover\">support</a> this feature as they perform failovers as part of their periodic maintenance.</p>\n<ol>\n<li>\n<p>Your primary and hot standby servers should both be running Postgres 17 or later. Your hot standby should use a physical replication slot to receive changes from the primary (as opposed to WAL archival and restore). Most managed services already set up read replicas in this manner.</p>\n</li>\n<li>\n<p>To ensure your standbys are set up to handle primary crashes, you should have both <a target=\"_blank\" href=\"https://postgresqlco.nf/doc/en/param/synchronous_standby_names/\">synchronous_standby_names</a> and <a target=\"_blank\" href=\"https://postgresqlco.nf/doc/en/param/synchronous_commit/\">synchronous_commit</a> set up so that the primary needs to confirm WAL receipt by a standby before acknowledging a commit, ensuring changes are persisted unless both the primary and standby go down. Again, most managed services already have this setup, but adjustments can be made based on the specific guarantees required.</p>\n</li>\n<li>\n<p>You need to enable the settings <a target=\"_blank\" href=\"https://postgresqlco.nf/doc/en/param/hot_standby_feedback/\">hot_standby_feedback</a> and <a target=\"_blank\" href=\"https://postgresqlco.nf/doc/en/param/sync_replication_slots/\">sync_replication_slots</a> on the standby. sync_replication_slots tells the standby to start a slotsync worker that synchronizes slots from the primary. This setting, in turn, requires hot_standby_feedback for doing this reliably.</p>\n</li>\n<li>\n<p>You need to add the physical replication slot being used by your hot standby to <a target=\"_blank\" href=\"https://postgresqlco.nf/doc/en/param/synchronized_standby_slots/\">synchronized_standby_slots</a> on the primary. This ensures that the standbys confirm receipt of WAL containing changes before they're sent on the logical replication slot being used by the ClickPipe. Without this, it's possible that the standby is \"behind\" the ClickPipe and is unable to resume properly after failover.</p>\n</li>\n<li>\n<p>When creating the ClickPipe, ensure that you select the option to <a target=\"_blank\" href=\"https://clickhouse.com/docs/integrations/clickpipes/postgres/faq#failover-slot\">create a replication slot with failover enabled</a>.</p>\n</li>\n</ol></div><div><ol>\n<li>After the ClickPipe is created and is in the Running state, query pg_replication_slots on the standby to see a slot starting with mirror_ (the UUID of the slot is the same as the UUID of the ClickPipe). This slot is synced from the primary and has synced and failover set to true. This slot is now ready to use when the standby is promoted.</li>\n</ol>\n<h2 id=\"conclusion\"></h2>\n<p>The ClickPipes team is hard at work improving our existing connectors while delivering more ways to replicate data to ClickHouse. With support for logical replication failover, users can now confidently rely on Postgres ClickPipes to replicate critical data and gain all the advantages of ClickHouse's query performance for real-time analytics use cases. We also continue to support replicating from hot standbys directly, which can help alleviate some load from the primary for other workloads.</p>\n<p>If you'd like to run queries on <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> with your data in Postgres, we recommend <a target=\"_blank\" href=\"https://clickhouse.com/docs/integrations/clickpipes/postgres\">ClickPipes for Postgres</a>, which provides reliable, real-time replication without requiring infrastructure management. Self-hosted ClickHouse users should consider <a target=\"_blank\" href=\"https://github.com/PeerDB-io/peerdb\">PeerDB</a>, the battle-hardened CDC tool that powers all Postgres ClickPipes.</p></div>"
