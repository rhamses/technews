Each row in this dataset represents a single Python package download, and the historical data traces back to 2011.</p>\n<div><pre><code><span><span>SELECT</span> <span>count</span>() <span>FROM</span> pypi.pypi</span>\n<span></span>\n<span>┌───────<span>count</span>()─┐</span>\n<span>│ <span>2214017475506</span> │ <span>-- 2.21 trillion</span></span>\n<span>└───────────────┘</span></code></pre></div>\n<p>ClickHouse is the analytical database powering ClickPy, making it possible for Python enthusiasts to check their favorite Python package popularity or understand new trends in the Python ecosystem.</p>\n<p>Reaching this scale with minimal ongoing maintenance highlights why ClickHouse works well as a long-term store for high-volume analytical data. Hitting the 2 trillion row mark gave us a reason to review the ingestion pipeline and make it more robust.</p>\n<p>Evolving a data ingestion pipeline at this scale is not a trivial task. The system needs to remain available, ingestion must continue uninterrupted, and changes have to be introduced carefully. As part of this work, we also looked closer at the historical data, which led us to uncover some discrepancies.</p>\n<p>The rest of this post explains how we redesigned the ingestion pipeline and, later on, how we fixed historical data while keeping ClickPy running throughout the process.</p>\n<h2 id=\"replacing-the-legacy-ingestion-pipeline\"></h2>\n<p>The initial pipeline was built at a time when <a target=\"_blank\" href=\"https://clickhouse.com/cloud/clickpipes\">ClickPipes</a> did not exist yet, therefore it required quite a bit of scripting. We described the original ingestion pipeline in this <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickpy-one-trillion-rows#ingesting-the-data\">blog post</a>.&#160;</p>\n<p>Pypi download statistics <a target=\"_blank\" href=\"https://packaging.python.org/en/latest/guides/analyzing-pypi-package-downloads/#public-dataset\">are publicly available</a> on a BigQuery table, and we have an automated BigQuery job that exports daily data to a Google Cloud Storage bucket. Finally, a custom script runs every day a ClickHouse insert statement to ingest data directly from the GCS bucket to ClickPy's main table, <code>pypi</code>.</p>\n<p><span><img alt=\"clickpy-2-trillion-rows-1.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickpy_2_trillion_rows_1_2167e28828.jpg&w=2048&q=75\"></span></p>\n<p>This approach worked, but at this scale, it left room for improvement. The main opportunity was to replace the custom ingestion script, shown as ClickLoad in the diagram, with ClickPipes.</p>\n<p>Moving to ClickPipes removes several operational constraints introduced by a cron-based script:</p>\n<ul>\n<li>Retries, backoff, and failure handling are built in instead of being hand-rolled</li>\n<li>Pipeline state and progress are visible, which makes it easier to detect stalled or partial ingestions</li>\n<li>Delegate ingestion pipeline maintenance to the ClickHouse team&#160;&#160;</li>\n<li>Changes to ingestion logic require fewer moving parts and less custom code</li>\n</ul>\n<p>With ClickPipes in place, ingestion becomes a first-class part of the system rather than a separate process that needs to be monitored and maintained alongside it.</p>\n<p><span><img alt=\"clickpy-2-trillion-rows-2.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickpy_2_trillion_rows_2_e9e6d6b383.jpg&w=2048&q=75\"></span></p>\n<p>The challenge of replacing the custom script with ClickPipes is the scale at which we're operating. We can't afford to corrupt the data. The main table <code>pypi</code> contains more than 2 trillion rows, and we also have several materialized views built from the <code>pypi</code> table, which makes re-ingesting the data from scratch not an option.</p>\n<h2 id=\"hot-swap-with-clickpipes-at-scale\"></h2>\n<p>We adopted a staged approach to replace the custom ingestion script with ClickPipes while keeping risk low.</p>\n<p>The first step was to isolate the new pipeline from production. pipeline, we also took the opportunity to extend the dataset with new fields to address recent community feature requests [<a target=\"_blank\" view were in place, configuring ClickPipes was straightforward. ClickPipes supports <a target=\"_blank\" href=\"https://clickhouse.com/docs/integrations/clickpipes/object-storage/gcs/overview#continuous-ingestion-lexicographical-order\">continuous ingestion</a> and keeps track of which files have already been processed, but it does not support starting ingestion from an arbitrary point in time. To avoid re-ingesting the full historical dataset, we updated the BigQuery export job to write new data to a fresh GCS bucket. ClickPipes was then configured to read from this new location, allowing the new pipeline to start from the migration point.</p>\n<p>We let the new ingestion pipeline run in parallel for several days and compared daily row counts between the production database pypi and the staging database pypi_clickpipes. Once the data matched, switching over was simple. We disabled the cron job that ran the custom script and updated the materialized view to write directly to <code>pypi.pypi</code>.</p>\n<p>After the switch, we removed the cloned tables from the <code>pypi_clickpipes</code> database and kept only <code>pypi_raw</code>, <code>pypi_mv</code>, and the tables created and managed by ClickPipes. This results in a clean separation of concerns: the <code>pypi</code> database continues to serve ClickPy, while <code>pypi_clickpipes</code> is dedicated to ingestion and transformation logic.</p>\n<h2 id=\"discovering-historical-ingestion-gaps\"></h2>\n<p>While validating the new ingestion pipeline, we noticed discrepancies between BigQuery (the source of data) and ClickHouse. When comparing daily row counts, some historical dates in ClickHouse were missing data.</p>\n<p>At this scale, issues like this are easy to miss. Queries continue to work, and dashboards still render, but the results are quietly incorrect. Once identified, the challenge was to correct the data without rebuilding the full dataset or interrupting ongoing ingestion.</p>\n<h2 id=\"fix-the-past\"></h2>\n<p>The most direct way to fix the past data is to delete the affected days and re-ingest them from the source. However, column-oriented databases are optimized for fast inserts and analytical queries, not for modifying existing data. ClickHouse is no exception. That said, ClickHouse recently introduced <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-1-purpose-built-engines\">lightweight delete and update operations</a>, which made it possible to safely delete large ranges of data even on a multi-trillion-row table.</p>\n<p>To fix a single day of data, we followed this sequence:</p>\n<ol>\n<li>Delete the affected day from all tables that aggregate data by day.</li>\n<li>Delete the affected day from the main pypi table.</li>\n<li>Temporarily drop materialized views that do not aggregate by day.</li>\n<li>Re-ingest the source data for the affected day into the pypi table.</li>\n<li>Recreate the materialized views that do not aggregate by day.</li>\n<li>Rebuild the tables populated by those materialized views.</li>\n</ol>\n<p>The distinction between daily and non-daily aggregations is important. For tables that group data by day, such as pypi_downloads_per_day, we can delete a specific date and rely on materialized views to repopulate it during re-ingestion.</p>\n<p>For tables that do not group by day, such as monthly aggregates, it is not possible to isolate rows belonging to a single day. In those cases, materialized views must be dropped before re-ingestion to avoid duplicate data, then recreated and rebuilt once the backfill is complete.</p>\n<p>The full script used for this process is available <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickpy/blob/main/scripts/day-fix.sh\">here</a>.</p>\n<h2 id=\"where-this-leaves-clickpy\"></h2>\n<p><a target=\"_blank\" href=\"https://clickpy.clickhouse.com/\">ClickPy</a> reaching 2 trillion rows is more than a numerical milestone. It reflects both the growing activity of the Python ecosystem and the ability of ClickHouse to support analytical workloads at this scale. We offer ClickPy as a free open source service because we enjoy building applications on top of large datasets, want to support the open source community, and, thanks to ClickHouse, can operate it <a target=\"_blank\" href=\"https://clickhouse.com/blog/cloud-data-warehouses-cost-performance-comparison\">cost-efficiently</a> even at multi-trillion-row scale.</p>\n<p>The work described in this post, migrating the ingestion pipeline to ClickPipes and correcting historical data, is part of our ongoing effort to keep the platform healthy and relevant as it grows. Community engagement plays an important role in shaping ClickPy, and we encourage <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickpy/issues\">feature requests and issue</a> reports as they directly drive improvements. A recent example is support for exporting charts through Metabase.</p>\n<p>With these changes in place, ClickPy is more accurate, easier to operate, and ready for continued growth.</p></div></article>"
