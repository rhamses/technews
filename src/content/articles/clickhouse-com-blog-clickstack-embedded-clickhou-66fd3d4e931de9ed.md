contentHtml: "<div><h2 id=\"user-content-tldr\"></h2>\n<p>With 26.2, we are introducing a new distribution method: ClickStack UI embedded in ClickHouse. The ClickStack UI is now distributed and embedded directly in the ClickHouse binary, making it easy to experiment with observability on your local instance, explore your own datasets, and even inspect ClickHouse itself.  Simply navigate to <a target=\"_blank\" href=\"https://localhost:8123/\">https://localhost:8123</a>, select \"ClickStack\", and start exploring.</p>\n<h2 id=\"user-content-introduction\"></h2>\n<p>Historically, ClickStack has been available through Docker-based distributions. You can run the <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/deployment/all-in-one\">full stack in a single container</a> for testing and experimentation, or deploy <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/deployment/hyperdx-only\">each component independently</a> when moving to production - running the UI, collector, and ClickHouse separately using <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/deployment/helm\">tools such as Helm</a>.</p>\n<p>More recently, <a target=\"_blank\" href=\"https://clickhouse.com/blog/introducing-managed-clickstack-beta\">we introduced a managed ClickStack offering</a> in ClickHouse Cloud, where we host both the UI and ClickHouse. Users benefit from integrated authentication along with ClickHouse Cloud's separation of storage and compute - enabling both long-term data retention in object storage while allowing independent scaling of compute to minimize the cost per GB.</p>\n<p><strong>From 26.2, we are adding a 3rd option.</strong></p>\n<p>The ClickStack UI now comes embedded in the ClickHouse binary itself. At first glance, embedding a web application into a high-performance C++ database might sound like it would significantly increase the binary size. In practice, we have kept the additional footprint under 4.1 MB, ensuring installation remains lightweight and fast.</p>\n<p>This means that installing ClickHouse now gives you ClickStack out of the box. Whether you use Docker, download the binary, or install via your favorite package manager, ClickStack is immediately available. Simply install ClickHouse, navigate to <a target=\"_blank\" href=\"http://localhost:8123/\">http://localhost:8123</a>, and select ClickStack from the menu. Within seconds, you can begin exploring your logs, traces, and metrics.</p>\n<h2 id=\"user-content-built-for-exploration-and-local-development\"></h2>\n<p>The embedded version of the ClickStack UI  is designed for local exploration, learning, and exploring your own ClickHouse data with an observability UI. It is not intended for production deployments.</p>\n<p>This distribution makes it easy to experiment with observability on your local ClickHouse instance, explore your own datasets, and even inspect ClickHouse itself. ClickHouse already exposes rich internal logs and metrics that are invaluable for diagnosing and optimizing performance. The ClickStack UI provides convenient ways to visualize this data and better understand how your instance behaves.</p></div><div><blockquote>\n<p>The ClickHouse preset dashboard can be useful for diagnosing local issues and performance problems. Users can also search their local logs and build visualizations over system metric tables.</p>\n</blockquote>\n<p>For larger or production deployments, we always recommend running ClickStack components separately.</p>\n<p>The embedded version also intentionally omits certain capabilities to keep the distribution size small and the experience simple. There is no persistent state storage so alerting is disabled, as well as dashboard and querying persistence. <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/event_patterns\">Event pattern</a> functionality is also not included to keep the size small as this requires <a target=\"_blank\" href=\"https://clickhouse.com/blog/event-patterns-clickstack#how-clickstack-implements-event-patterns\">a WASM Python runtime</a>.</p>\n<p>Some of these limitations may be addressed in the future using approaches such as browser based storage, but for now the focus is simplicity and approachability.</p>\n<p>If you plan to operate ClickStack at scale, or require alerting and persistence, the <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/getting-started/oss\">open source docker versions</a> or <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/getting-started/managed\">managed cloud</a> offering remain the recommended path.</p>\n<h2 id=\"user-content-the-technical-challenges\"></h2>\n<p>For the curious reader, embedding a full web application inside a C++ database binary involved some interesting engineering decisions.</p>\n<h3 id=\"user-content-assumptions\"></h3>\n<p>Embedding ClickStack inside ClickHouse meant working within a strict set of conditions defined by the core team, reflecting the engineering standards expected of the ClickHouse binary:</p>\n<ol>\n<li>Adding a <a target=\"_blank\" href=\"http://node.js/\">Node.js</a> dependency to ClickHouse is a non-starter</li>\n<li>Files must be embedded in the binary, not lingering somewhere in the file system</li>\n<li>ClickStack should not significantly inflate the binary size</li>\n</ol>\n<h3 id=\"user-content-the-nextjs-parts\"></h3>\n<p>The UI that powers ClickStack, HyperDX, is a Next.js application. For those familiar, Next.js is a full-stack framework that renders pages on the server before serving, meaning that both the frontend and the backend are bundled into an application. It allows you to serve both static pages and dynamic HTML. However, serving dynamic pages without introducing a Node.js dependency would mean rewriting a lot of the Next.js internals. This meant serving dynamic pages was off the table. Luckily, ClickStack heavily uses static pages. There is still React running in the browser, but very little dynamic server-side rendering ever occurs.</p>\n<p>ClickHouse has some existing HTML pages,  such as <code>play.html</code> for running queries in a WebUI, and <code>dashboards.html</code> for some extremely helpful dashboards to see the health of your ClickHouse instance. The <code>dashboards.html</code> page even loads some JavaScript!</p>\n<p>However, both are a far cry from the complexity of serving a webpack output from a modern full-featured website like ClickStack. I'll get to that complexity in the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickstack-embedded-clickhouse#bundling-into-clickhouse\">Bundling into ClickHouse</a> section, but the existing web pages meant we could add an additional handler with just a little custom functionality.</p>\n<h3 id=\"user-content-clickstack-existing-variations-and-connecting-to-clickhouse\"></h3>\n<p>ClickStack already has a few  dependencies on which it relies for core functionality. The standard application includes Next.js, Express, and MongoDB. Express and MongoDB are primarily used for the CRUD persistence layer for saved searches, dashboards, and sources. The Express server also serves as a proxy for ClickHouse,  while also handling authentication to ensure DB credentials are not leaked to the frontend. It was safe to assume that the Express backend, MongoDB, and a proxy layer would not be available when embedding ClickStack in ClickHouse.</p>\n<p>However, there already existed a <a target=\"_blank\" href=\"https://play-clickstack.clickhouse.com/\">demo site</a> with most capabilities we needed; connections stored in session storage, sources persisted in local storage, and ability to query ClickHouse directly without a proxy layer. The only modifications needed would be to adjust all links with the prefix \"/clickstack\". With this mechanism, we could attempt bundling into ClickHouse.</p>\n<blockquote>\n<p>We also decided to remove <code>pyodide</code>, a WASM Python runtime for the browser used for ClickStack's \"Event Patterns\" feature, purely because its size would inflate the ClickHouse binary size by more than we are comfortable with.</p>\n</blockquote>\n<h3 id=\"user-content-bundling-into-clickhouse\"></h3>\n<p>ClickHouse uses many 3rd-party libraries and manages them via git submodules. This means that updating a version of a dependency is as simple as checking out a specific commit and rerunning the ClickHouse build. This provides us with the basic foundation to ensure that upgrading to a newer ClickStack version is potentially easy if we can provide it as a usable sub-module.</p>\n<p>Building ClickHouse requires many dependent tools such as <code>cmake</code>, <code>ccache</code>, <code>ninja</code>, and many more. But NOT Node.js. For the purpose of reducing friction in local development as well as build times, this meant adding a new dependency with rather large implications like <a target=\"_blank\" href=\"http://node.js/\">node.js</a> was not an option. A good alternative is to generate a static bundle upon release and included directly in a git submodule. As we didn't want to clutter the ClickStack repo, this meant creating a new repo that can reproducibly check out a ClickStack version, build the static output, and update the bundle - ideally all automated upon the release of a new ClickStack version.</p>\n<p>But we still have an issue - the files are now present in a ClickHouse build, but how can they be embedded?</p>\n<p>C++ does have an #embed macro that allows embedding known files as raw bytes rather than as a file. Unfortunately, a feature of <a target=\"_blank\" href=\"http://next.js/\">Next.js</a> is that it outputs seemingly randomized file names, and lots of them. To handle this, we  generate a C++ file on the fly using some <code>cmake</code> magic. It does the following:</p>\n<ol>\n<li>Creates a new file with some static definitions, specifically a struct definition that includes the file name, bytes, and MIME type</li>\n<li>Find all files in contrib/clickstack/out</li>\n<li>Sort by name</li>\n<li>For each file\n<ol>\n<li>Gzip the file (to reduce binary size + bytes shipped to browser)</li>\n<li>Generate an entry in an array</li>\n</ol>\n</li>\n</ol>\n<p>The generated file is then simply #included. Then, when a request is made to the <code>/clickstack</code> HTTP handler, there is a binary search for the file. If it is found, the file is returned with the appropriate MIME type. In the browser, the user must supply some username and password credentials to authenticate against ClickHouse - these are then used to directly query  ClickHouse over HTTP.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_mar2026_image3_ab1eabc337.png&w=2048&q=75\"></span></p>\n<p>The result is a very lean addition, around 4.2mb embedded directly into the actual binary itself.</p>\n<h2 id=\"user-content-getting-started\"></h2>\n<p>To try ClickStack embedded in ClickHouse, install ClickHouse as you normally would. You can use the one-line installer:</p>\n<div><pre><code><span>curl https://clickhouse.com/ | sh</span></code></pre></div>\n<p>Or see the Open Source Quick Start <a target=\"_blank\" href=\"https://clickhouse.com/docs/getting-started/quick-start/oss\">guide</a> for alternatives.</p>\n<p>For this example, we will enable internal logs so you can explore your own ClickHouse instance, including executed queries and resource usage.</p>\n<p>After downloading the binary, move to the directory where you want ClickHouse to store its data. Then create a configuration snippet that enables the query and metric logs:</p>\n<div><pre><code><span><span>mkdir</span> -p config.d &amp;&amp; <span>echo</span> <span>\"&lt;clickhouse&gt;&lt;query_log&gt;&lt;database&gt;system&lt;/database&gt;&lt;table&gt;query_log&lt;/table&gt;&lt;/query_log&gt;&lt;query_thread_log&gt;&lt;database&gt;system&lt;/database&gt;&lt;table&gt;query_thread_log&lt;/table&gt;&lt;/query_thread_log&gt;&lt;query_views_log&gt;&lt;database&gt;system&lt;/database&gt;&lt;table&gt;query_views_log&lt;/table&gt;&lt;/query_views_log&gt;&lt;metric_log&gt;&lt;database&gt;system&lt;/database&gt;&lt;table&gt;metric_log&lt;/table&gt;&lt;/metric_log&gt;&lt;asynchronous_metric_log&gt;&lt;database&gt;system&lt;/database&gt;&lt;table&gt;asynchronous_metric_log&lt;/table&gt;&lt;/asynchronous_metric_log&gt;&lt;/clickhouse&gt;\"</span> | <span>sudo</span> <span>tee</span> ./config.d/query_logs.xml &gt; /dev/null</span></code></pre></div>\n<p>This appends to the default configuration and enables system log tables.</p>\n<p>Start the server and open your browser at <a target=\"_blank\" href=\"http://localhost:8123/clickstack\">http://localhost:8123/clickstack</a></p>\n<div><pre><code><span>./clickhouse server</span></code></pre></div>\n<p>A connection to the local instance is created automatically. If you already have OpenTelemetry data loaded, ClickStack will detect it and create sources automatically. On a fresh installation, you will be prompted to create a source. For this example, create a new <strong>Log Source</strong> that points to <code>system.query_log</code>.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_mar2026_image8_3e2b3fa28f.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p>Config: <code>Name: Query Logs</code></p>\n<p><code>Database: system</code></p>\n<p><code>Table: query_log</code></p>\n<p><code>Timestamp Column: event_time</code></p>\n<p><code>Default Select: event_time, query_kind, query, databases, tables, initial_user, projections, memory_usage, written_rows, read_rows, query_duration_ms</code>.*</p>\n</blockquote>\n<p>Save the source. You will be redirected to the search view, where query logs should immediately begin appearing.</p>\n<p>At this point, you are observing your own ClickHouse instance.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_mar2026_image5_4ac157885b.png&w=2048&q=75\"></span></p>\n<p>Feel free to open the play UI at <a target=\"_blank\" href=\"http://localhost:8213/play\">http://localhost:8213/play</a>, run a few queries and watch them appear in ClickStack. With the default selection you can view the execution time, the memory usage and other useful metadata such as the projections used.</p>\n<p>We also include a built-in ClickHouse preset dashboard, available from the left navigation menu. It provides insights into query latency and slow queries, highlights the most time consuming query patterns, shows query counts per table, and surfaces key system metrics such as CPU usage, memory consumption, S3 requests, and insert activity. Together, these views give you immediate observability into your ClickHouse instance, powered entirely by the embedded ClickStack UI.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_mar2026_image2_42373b1362.png&w=2048&q=75\"></span></p>\n<p>To continue exploring ClickStack and learning its features, we recommend trying it with one of our <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/sample-datasets\">sample datasets</a>. These include sample <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/getting-started/sample-data\">observability data</a> from the <a target=\"_blank\" href=\"https://github.com/ClickHouse/opentelemetry-demo\">OpenTelemetry demo</a>, along with examples for <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/example-datasets/session-replay-demo\">exploring session replay functionality</a> and monitoring your <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/getting-started/local-data\">local infrastructure and ClickHouse instance</a>.</p>\n<h2 id=\"user-content-conclusion\"></h2>\n<p>With ClickStack now embedded directly in ClickHouse, getting started with observability is as simple as installing the database itself. There is no additional setup, no separate services to run, and no external UI to deploy. Within seconds, you can begin exploring logs, traces, metrics, and even ClickHouse's own internal behavior.</p>\n<p>Our hope is that this distribution lowers the barrier to entry and makes it easier to discover the value of ClickStack using your own local datasets. It provides a practical environment for learning the product, running demos, training teams, experimenting with queries, and understanding how ClickHouse behaves during development.</p>\n<p>We look forward to seeing how the community uses it, and contributes to its evolution.</p></div>"
