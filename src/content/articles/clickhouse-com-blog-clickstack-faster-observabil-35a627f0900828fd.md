contentHtml: "<div><h2 id=\"user-content-introduction\"></h2>\n<p>ClickHouse has become the storage engine of choice for modern observability. Its columnar architecture and execution model make it exceptionally fast for logs, traces, and wide event data at massive scale. Companies such as <a target=\"_blank\" href=\"https://clickhouse.com/blog/netflix-petabyte-scale-logging\">Netflix</a>, <a target=\"_blank\" href=\"https://clickhouse.com/blog/how-tesla-built-quadrillion-scale-observability-platform-on-clickhouse\">Tesla</a>, <a target=\"_blank\" href=\"https://clickhouse.com/blog/how-anthropic-is-using-clickhouse-to-scale-observability-for-ai-era\">Anthropic</a>, and <a target=\"_blank\" href=\"https://clickhouse.com/blog/why-openai-uses-clickhouse-for-petabyte-scale-observability\">OpenAI</a> rely on it to power demanding telemetry workloads.</p>\n<p>But database speed alone does not guarantee observability performance. To consistently deliver low latency queries under heavy, high cardinality workloads, queries must be shaped to work with the internals of the engine. ClickStack bridges that gap by tightly integrating the UI with ClickHouse, embedding optimization best practices directly into how queries are generated and executed.</p>\n<p>In this post, we explore how that integration accelerates observability today and how we plan to extend those optimizations even further.</p>\n<h2 id=\"user-content-true-speed-requires-planning\"></h2>\n<p>ClickHouse is fast by design. Its performance comes from innovations across both the storage and query processing layers.</p>\n<p>However, these architectural advantages only translate into real world speed when queries are written to take advantage of them. Observability workloads are demanding and poorly shaped queries can bypass pruning, inflate intermediate state, and waste CPU and memory. Building an observability solution on top of ClickHouse requires more than simply exposing arbitrary SQL. Queries must align with how the engine stores, prunes, and processes data.</p>\n<p>Even with a <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/analyzer\">mature query analyzer</a>, optimization still matters. We are <em><strong>not yet</strong></em> at a point where every query is automatically rewritten into its most efficient form.</p>\n<p>ClickStack addresses this by tightly coupling the observability UI with ClickHouse itself. Rather than simply passing through user generated SQL, it carefully constructs and rewrites queries to ensure they are executed in the most efficient way possible. This includes techniques such as breaking complex queries into smaller stages, reshaping them to maximize pruning, and minimizing the amount of data read while remaining conscious of CPU and memory usage. The goal is to consistently align query patterns with the engine's strengths.</p>\n<p>We explore several of these optimizations below and how, over time, we plan to expose them as opinionated APIs, allowing others to benefit from the same query formulation strategies outside the ClickStack interface.</p>\n<h2 id=\"user-content-progressive-time-window-pagination-for-search\"></h2>\n<p>One of the most common access patterns in ClickStack is simple search. Users open the search dialog to browse logs or traces, typically over the last 15 minutes or the last hour. Occasionally, they expand that range to days or even weeks. The intent is rarely to retrieve everything. Instead, users are scanning, looking for signals, patterns, or specific events.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_mar2026_image4_c0ef3da65b.png&w=2048&q=75\"></span></p>\n<p>The key insight is that we do not need a complete result set before returning data. We only need enough rows to populate the first page. By delivering results incrementally, users see data almost immediately and can begin investigating. In practice, most users refine their query before paging deeply into historical data. That behavior allows us to optimize for fast time to first result rather than full range completeness. A naive implementation might issue a single query across the entire requested range:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> logs</span>\n<span><span>WHERE</span> <span>timestamp</span> <span>BETWEEN</span> now() <span>-</span> <span>INTERVAL</span> <span>30</span> <span>DAY</span> <span>AND</span> now()</span>\n<span><span>ORDER</span> <span>BY</span> <span>timestamp</span> <span>DESC</span></span>\n<span>LIMIT <span>500</span>;</span></code></pre></div>\n<p>This forces ClickHouse to scan and sort across the full 30 day range before applying the offset, potentially reading far more data than necessary.</p>\n<p>Instead, ClickStack searches progressively, starting with the most recent window:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> logs</span>\n<span><span>WHERE</span> <span>timestamp</span> <span>&gt;=</span> now() <span>-</span> <span>INTERVAL</span> <span>6</span> <span>HOUR</span></span>\n<span><span>ORDER</span> <span>BY</span> <span>timestamp</span> <span>DESC</span></span>\n<span>LIMIT <span>500</span>;</span></code></pre></div>\n<p>If insufficient rows are found, it expands to older windows, for example the previous 6 hours, then 12 hours, then 24 hours, applying pagination only within each bounded window. If sufficient results have been accumulated, we can terminate further scans.</p>\n<p>This approach pairs naturally with ClickHouse's <a target=\"_blank\" href=\"https://clickhouse.com/docs/knowledgebase/async_vs_optimize_read_in_order\">optimize_read_in_order</a> capability. When the ORDER BY clause aligns with the table's primary key, ClickHouse can read data in key order without a separate global sort. In ClickStack, OpenTelemetry tables can be ordered by a time based key such as <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/functions/date-time-functions#toStartOfMinute\"><code>toStartOfMinute(timestamp)</code></a>, so descending time queries align with the physical layout. Combined with bounded time windows, this allows ClickHouse to return the newest rows quickly with minimal extra sorting or scanning.</p>\n<h2 id=\"user-content-chunked-queries\"></h2>\n<p>A similar technique is used for charting, but with a different objective. In search, we optimize for fast time to the first result and may terminate early. For charts, users expect a complete visualization across the full time range. Instead of running one large aggregation query, we split the range into granularity aligned windows and execute them independently.</p>\n<p>For example, a 30 day chart at 5 minute resolution might otherwise require a single aggregation over billions of rows. Rather than executing this as one monolithic query, ClickStack divides the time range into bucket aligned windows. Each window becomes its own query, scanning a smaller slice of partitions.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_mar2026_image5_173d4da4d4.gif&w=2048&q=75\"></span></p>\n<p>These queries can run in parallel, and their results are concatenated client side in order. Windows are aligned to bucket boundaries to ensure aggregation buckets are never split. The result is a progressive loading effect.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_mar2026_image3_4b3edfa904.gif&w=2048&q=75\"></span></p>\n<p>This matters because a single large aggregation over billions of rows can monopolize cluster resources or even time out. Chunking constrains each scan lowering memory consumption, and allowing progressive rendering.</p>\n<h2 id=\"user-content-automatic-use-of-materialized-columns\"></h2>\n<p>Another early optimization in ClickStack was the automatic use of <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/performance_tuning#materialize-frequently-queried-attributes\">materialized columns for map attributes</a>.</p>\n<p>Observability data is inherently semi structured. Resource attributes such as Kubernetes labels and span attributes are commonly stored as arbitrary key value pairs using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/map\">Map type</a>. This allows flexible ingestion without requiring users to define every possible column in advance. However, querying map keys at runtime is expensive. ClickHouse must read the map structure processing all keys within it, increasing IO and CPU usage.</p>\n<blockquote>\n<p>Recently users have begun to use the JSON type which creates a dedicated typed subcolumn for each attribute. This mitigates the disadvantages of the map type but does come with its own insert overhead costs.</p>\n</blockquote>\n<p>Consider a simplified trace table schema:</p>\n<div><pre><code><span><span>CREATE TABLE</span> otel.otel_traces</span>\n<span>(</span>\n<span>    `<span>Timestamp</span>` DateTime64(<span>9</span>) CODEC(Delta(<span>8</span>), ZSTD(<span>1</span>)),</span>\n<span>    `TraceId` String CODEC(ZSTD(<span>1</span>)),</span>\n<span>    `SpanId` String CODEC(ZSTD(<span>1</span>)),</span>\n<span>    `ServiceName` LowCardinality(String) CODEC(ZSTD(<span>1</span>)),</span>\n<span>    `ResourceAttributes` Map(LowCardinality(String), String) CODEC(ZSTD(<span>1</span>)),</span>\n<span>    `SpanAttributes` Map(LowCardinality(String), String) CODEC(ZSTD(<span>1</span>)),</span>\n<span>    `Duration` UInt64 CODEC(ZSTD(<span>1</span>)),</span>\n<span>    <span>-- Materialized column extracted at ingest time</span></span>\n<span>    `PodName` String MATERIALIZED ResourceAttributes[<span>'k8s.pod.name'</span>],</span>\n<span>    INDEX idx_res_attr_key mapKeys(ResourceAttributes) TYPE bloom_filter(<span>0.01</span>) GRANULARITY <span>1</span>,</span>\n<span>    INDEX idx_res_attr_value mapValues(ResourceAttributes) TYPE bloom_filter(<span>0.01</span>) GRANULARITY <span>1</span>,</span>\n<span>    INDEX idx_duration Duration TYPE minmax GRANULARITY <span>1</span></span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>PARTITION</span> <span>BY</span> toDate(<span>Timestamp</span>)</span>\n<span><span>ORDER</span> <span>BY</span> (ServiceName, SpanName, toDateTime(<span>Timestamp</span>));</span></code></pre></div>\n<p>Without materialization, a filter would look like:</p>\n<div><pre><code><span>ResourceAttributes[<span>'k8s.pod.name'</span>] <span>=</span> <span>'payments-7f9d8c'</span></span></code></pre></div>\n<p>With materialization, the query becomes:</p>\n<div><pre><code><span>PodName <span>=</span> <span>'payments-7f9d8c'</span></span></code></pre></div>\n<p>By extracting the attribute at ingest time into a physical column, we avoid runtime map extraction. ClickHouse can read only the required column instead of scanning and decoding the entire map structure. Regular columns also benefit from better compression and more effective pruning.</p>\n<p>ClickStack automatically detects when a commonly used attribute has been materialized. If a user filters on <code>k8s.pod.name</code>, the generated query transparently targets the <code>PodName</code> column. Users get fast filters on common attributes and stable performance at high data volumes, without needing to manage schema optimizations themselves.</p>\n<h2 id=\"user-content-automatic-use-of-materialized-views-with-cost-selection\"></h2>\n<p>A more recent optimization in ClickStack is automatic use of materialized views. In ClickStack, users build dashboards, charts, search experiences, session replay, and service maps from sources, where each source maps to an underlying ClickHouse table. Since the start of this year, sources can also have one or more incremental materialized views attached, designed to pre-aggregate the most common, aggregation-heavy visualizations.</p>\n<p>In ClickHouse, an incremental materialized view is not a static snapshot. It is closer to an always-on trigger: as new data is inserted into the source table, the view runs an aggregation on each inserted block and writes the resulting aggregation states into a separate target table. Over time, those partial states are merged in the background, producing the same result you would get by aggregating the raw data at query time, but at a fraction of the cost.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_mar2026_image9_7c80bfa1f3.png&w=2048&q=75\"></span></p>\n<p>Effectively the user is shifting the cost of the query from query time to insert time, with the cost amortized across all of the inserts, such that the read time performance is lightweight and fast.</p>\n<p>Consider a concrete example. Suppose a common visualization needs \"request count and average duration per minute, grouped by service and status code\":</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    toStartOfMinute(<span>Timestamp</span>) <span>AS</span> <span>time</span>,</span>\n<span>    ServiceName,</span>\n<span>    StatusCode,</span>\n<span>    <span>count</span>() <span>AS</span> count,</span>\n<span>    <span>avg</span>(Duration) <span>AS</span> avg_duration</span>\n<span><span>FROM</span> otel.otel_traces</span>\n<span><span>WHERE</span> <span>Timestamp</span> <span>&gt;=</span> now() <span>-</span> <span>INTERVAL</span> <span>24</span> <span>HOUR</span></span>\n<span><span>GROUP</span> <span>BY</span> <span>time</span>, ServiceName, StatusCode</span>\n<span><span>ORDER</span> <span>BY</span> <span>time</span>;</span></code></pre></div>\n<div><pre><code><span>-- results omitted <span>for</span> brevity</span>\n<span>38210 rows <span>in</span> <span>set</span>. Elapsed: 0.790 sec. Processed 166.45 million rows, 2.99 GB (210.65 million rows/s., 3.79 GB/s.) Peak memory usage: 598.18 MiB.</span></code></pre></div>\n<p>Instead of recomputing this over raw traces every time a dashboard loads, we create a target table that stores aggregation states:</p>\n<div><pre><code><span><span>CREATE TABLE</span> otel.otel_traces_1m</span>\n<span>(</span>\n<span>    `<span>Timestamp</span>` DateTime,</span>\n<span>    `ServiceName` LowCardinality(String),</span>\n<span>    `StatusCode` LowCardinality(String),</span>\n<span>    `count` SimpleAggregateFunction(sum, UInt64),</span>\n<span>    `avg__Duration` AggregateFunction(avg, UInt64)</span>\n<span>)</span>\n<span>ENGINE <span>=</span> AggregatingMergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (<span>Timestamp</span>, ServiceName, StatusCode);</span></code></pre></div>\n<p>And then define the incremental materialized view that continuously maintains those states as data is inserted:</p>\n<div><pre><code><span><span>CREATE</span> MATERIALIZED <span>VIEW</span> otel_v2.otel_traces_1m_mv</span>\n<span><span>TO</span> otel.otel_traces_1m</span>\n<span><span>AS</span></span>\n<span><span>SELECT</span></span>\n<span>    toStartOfMinute(<span>Timestamp</span>) <span>AS</span> <span>Timestamp</span>,</span>\n<span>    ServiceName,</span>\n<span>    StatusCode,</span>\n<span>    <span>count</span>() <span>AS</span> count__,</span>\n<span>    avgState(Duration) <span>AS</span> avg__Duration</span>\n<span><span>FROM</span> otel.otel_traces</span>\n<span><span>GROUP</span> <span>BY</span> <span>Timestamp</span>, ServiceName, StatusCode;</span></code></pre></div>\n<p>Querying the pre-aggregated table is then lightweight, using less resources:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    toStartOfMinute(<span>Timestamp</span>) <span>AS</span> <span>time</span>,</span>\n<span>    ServiceName,</span>\n<span>    StatusCode,</span>\n<span>    <span>sum</span>(count) <span>AS</span> count,</span>\n<span>    avgMerge(avg__Duration) <span>AS</span> avg_duration</span>\n<span><span>FROM</span> otel_v2.otel_traces_1m</span>\n<span><span>WHERE</span> <span>Timestamp</span> <span>&gt;=</span> now() <span>-</span> <span>INTERVAL</span> <span>24</span> <span>HOUR</span></span>\n<span><span>GROUP</span> <span>BY</span> <span>time</span>, ServiceName, StatusCode</span>\n<span><span>ORDER</span> <span>BY</span> <span>time</span>;</span></code></pre></div>\n<div><pre><code><span>38246 rows <span>in</span> <span>set</span>. Elapsed: 0.027 sec. Processed 41.22 thousand rows, 1.57 MB (1.52 million rows/s., 57.80 MB/s.) Peak memory usage: 21.34 MiB.</span></code></pre></div>\n<p>In this example our query is 30x faster and uses 28x less memory.</p>\n<p>Once a materialized view is created, users simply register them with a source:</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_mar2026_image6_a5473bd3d5.png&w=2048&q=75\"></span></p>\n<p>When a visualization or alert runs, ClickStack evaluates the base table and any registered views, rewrites the query for each compatible candidate, and selects the best option using a cost model driven by ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/explain#explain-estimate\"><code>EXPLAIN ESTIMATE</code></a>. This indicates the number of rows the query will need to read:</p>\n<div><pre><code><span>EXPLAIN ESTIMATE</span>\n<span><span>SELECT</span></span>\n<span>    toStartOfMinute(<span>Timestamp</span>) <span>AS</span> <span>time</span>,</span>\n<span>    ServiceName,</span>\n<span>    StatusCode,</span>\n<span>    <span>sum</span>(count) <span>AS</span> count,</span>\n<span>    avgMerge(avg__Duration) <span>AS</span> avg_duration</span>\n<span><span>FROM</span> otel.otel_traces_1m</span>\n<span><span>WHERE</span> <span>Timestamp</span> <span>&gt;=</span> (now() <span>-</span> toIntervalHour(<span>24</span>))</span>\n<span><span>GROUP</span> <span>BY</span></span>\n<span>    <span>time</span>,</span>\n<span>    ServiceName,</span>\n<span>    StatusCode</span>\n<span><span>ORDER</span> <span>BY</span> <span>time</span> <span>ASC</span></span></code></pre></div>\n<div><pre><code><span>┌─database─┬─table──────────┬─parts─┬──rows─┬─marks─┐</span>\n<span>1. │ otel_v2  │ otel_traces_1m │     1 │ 41220 │     5 │</span>\n<span>   └──────────┴────────────────┴───────┴───────┴───────┘</span>\n<span>1 row <span>in</span> <span>set</span>. Elapsed: 0.006 sec.</span></code></pre></div>\n<p>If multiple materialized views could satisfy the query, ClickStack automatically chooses the view which minimizes the scanned rows and granules. If no view is compatible, it falls back to the source table, so dashboards keep working without changes while still benefiting from acceleration whenever possible.</p>\n<p>From the end user's perspective, this acceleration is completely automatic. They continue to build dashboards and explore data exactly as before. There is no need to rewrite queries, change chart definitions, or select a specific table. When a compatible materialized view exists, ClickStack transparently routes the query to it.</p></div><div><p>The only visible differences are improved performance and a subtle acceleration indicator in the UI. A lightning bolt icon signals that the visualization is being served from a materialized view. Users can click this icon to see which view was selected and confirm that the query was accelerated. Otherwise, the experience remains unchanged, just faster performance at scale.</p>\n<h2 id=\"user-content-query-rewriting-to-exploit-indices\"></h2>\n<p>ClickHouse provides several types of <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/performance_tuning#adding-skip-indices\">data skipping indices</a>, including MinMax, set, Text and Bloom filters. These indices store metadata at the granule level, typically around 8,192 rows per granule. Instead of indexing individual rows, they allow ClickHouse to determine whether an entire granule can be skipped before reading it. The fastest data to process is the data you never read.</p>\n<p>Users can attach MinMax indices to numeric columns, Bloom filters to string columns, or text indices for <a target=\"_blank\" href=\"https://clickhouse.com/blog/full-text-search-ga-release\">tokenized full text search</a>. However, for these indices to be used effectively, queries must be written in a way that matches the index expression. Not all functions can exploit all index types. This is a deliberate design choice in ClickHouse to ensure correctness and predictable behavior.</p>\n<p>ClickStack detects the skip indices defined on a table and rewrites queries to ensure the analyzer correctly infers their use. This guarantees that the correct index-aware functions are used, minimizing IO and avoiding unnecessary granule scans.</p>\n<p>Consider the common case where users search logs using a Lucene-style query string. They are not writing SQL.</p></div><div><p>Consider the full-text logs schema:</p>\n<div><pre><code><span><span>CREATE TABLE</span> otel_logs (</span>\n<span>    Body String,</span>\n<span>    ...</span>\n<span>    INDEX idx_body_text Body TYPE text(tokenizer <span>=</span> splitByNonAlpha)</span>\n<span>)</span></code></pre></div>\n<p>Suppose a user searches for the term \"error\" over a defined time period. A naive implementation might issue the following:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> otel_logs</span>\n<span><span>WHERE</span> (<span>Timestamp</span> <span>&gt;=</span> <span>'2026-01-01'</span>)</span>\n<span>  <span>AND</span> (<span>Timestamp</span> <span>&lt;</span> <span>'2026-03-14'</span>)</span>\n<span>  <span>AND</span> (Body ILIKE <span>'% error %'</span>);</span></code></pre></div>\n<div><pre><code><span>1 row <span>in</span> <span>set</span>. Elapsed: 0.708 sec. Processed 91.56 million rows, 14.91 GB (129.37 million rows/s., 21.06 GB/s.)</span></code></pre></div>\n<p>This works, but does not exploit the text index. ClickStack, however, detects the index is available and uses the <code>hasAllTokens()</code> function - specifically designed to leverage the text index:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> otel_logs</span>\n<span><span>WHERE</span> (<span>Timestamp</span> <span>&gt;=</span> <span>'2026-01-01'</span>)</span>\n<span>  <span>AND</span> (<span>Timestamp</span> <span>&lt;</span> <span>'2026-03-14'</span>)</span>\n<span>  <span>AND</span> hasAllTokens(Body, <span>'error'</span>);</span></code></pre></div>\n<div><pre><code><span>1 row <span>in</span> <span>set</span>. Elapsed: 0.029 sec. Processed 2.86 million rows, 22.92 MB (97.87 million rows/s., 784.96 MB/s.)</span></code></pre></div>\n<p>For multi-word phrases such as \"connection refused\", ClickStack combines index usage with a confirmation filter to preserve ordering semantics:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> otel_logs</span>\n<span><span>WHERE</span> (<span>Timestamp</span> <span>&gt;=</span> <span>'2026-01-01'</span>)</span>\n<span>  <span>AND</span> (<span>Timestamp</span> <span>&lt;</span> <span>'2026-03-14'</span>)</span>\n<span>  <span>AND</span> hasAllTokens(Body, <span>'connection refused'</span>)</span>\n<span>  <span>AND</span> (<span>lower</span>(Body) <span>LIKE</span> <span>lower</span>(<span>'%connection refused%'</span>));</span></code></pre></div>\n<p>The result is a single multi-token lookup against the text index, dramatically reducing scanned granules.</p>\n<p>Similar care is needed if exploiting bloom filters. In this case, ClickStack detects the expression used for the bloom filter index and ensures it combines this appropriately with the appropriate functions for matching. Consider the following (simplified) schema for logs:</p>\n<div><pre><code><span><span>CREATE TABLE</span> otel_logs (</span>\n<span>    Body String,</span>\n<span>    INDEX idx_body_bloom tokens(<span>lower</span>(Body))</span>\n<span>        TYPE bloom_filter(<span>0.001</span>)</span>\n<span>        GRANULARITY <span>8</span></span>\n<span>)</span></code></pre></div>\n<blockquote>\n<p>Note we lower the body to achieve case insensitive matching.</p>\n</blockquote>\n<p>Suppose a user searches for \"error\", this requires use of the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/functions/string-search-functions#hasToken\"><code>hasToken</code></a> function but also requires us to combine this with the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/functions/string-functions#lower\"><code>lower</code></a> function to ensure the index is used. ClickStack detects the expression, reflecting this in the final transpiled SQL:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> otel_logs</span>\n<span><span>WHERE</span> (<span>Timestamp</span> <span>&gt;=</span> <span>'2026-01-01'</span>)</span>\n<span>  <span>AND</span> (<span>Timestamp</span> <span>&lt;</span> <span>'2026-03-14'</span>)</span>\n<span>  <span>AND</span> hasAll(</span>\n<span>      tokens(<span>lower</span>(Body)),</span>\n<span>      tokens(<span>lower</span>(<span>'error'</span>))</span>\n<span>  );</span></code></pre></div>\n<p>The key is that the left side exactly matches the stored index expression. This allows ClickHouse to activate the Bloom filter and skip granules that definitely do not contain the token.</p>\n<p>The same principle applies to Map-based columns, such as LogAttributes and ResourceAttributes for default OTel tables. These often have Bloom filter indices on <code>mapKeys(...)</code> and <code>mapValues(...)</code> designed to allow granules to be skipped if an attribute key or value is not present.</p>\n<p>When a user searches for:</p>\n<div><pre><code><span>LogAttributes.error.message:\"Failed\"</span></code></pre></div>\n<p>ClickStack must do more than translate this to:</p>\n<div><pre><code><span>LogAttributes[<span>'error.message'</span>] ILIKE <span>'%Failed%'</span></span></code></pre></div>\n<p>To activate a Bloom filter on <code>mapKeys(LogAttributes)</code>, ClickStack appends an index hint that signals to the planner that the key is being accessed:</p>\n<div><pre><code><span><span>AND</span> indexHint(mapContains(LogAttributes, <span>'error.message'</span>))</span></code></pre></div>\n<p>This hint does not change query correctness - it simply tells ClickHouse to return the granules which match the filter but NOT read them (saving the Map I/O access). This allows ClickHouse to skip entire granules that do not contain that key at all. For high-cardinality semi structured data, this can eliminate vast portions of the dataset before any row-level evaluation occurs.</p>\n<p>Skip indices in ClickHouse are powerful, but they only work when queries precisely match the index definition. Small differences in function usage can mean the difference between skipping granules and scanning them and thus fast queries and slow.</p>\n<p>By inspecting the schema and rewriting queries to mirror index expressions exactly, ClicKStack ensures defined indices are actually used, delivering predictable performance without requiring users to hand-tune SQL.</p>\n<h2 id=\"user-content-primary-key-awareness\"></h2>\n<p>In ClickHouse, the <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes\">primary key plays a central role in data pruning</a>. Unlike traditional databases where primary keys enforce uniqueness, in ClickHouse the primary key defines the physical sort order of data. Queries that filter or order using expressions aligned with the primary key allow the engine to quickly eliminate large ranges of data without scanning them.</p>\n<p>In ClickStack, users are free to define their own schemas and primary keys - aligning these with their common access patterns. However, we provide sensible defaults for OpenTelemetry logs, traces, and metrics that are optimized for common observability workloads. These typically combine temporal components with Timestamp. For example, a common key might look like:</p>\n<div><pre><code><span><span>ORDER</span> <span>BY</span> (toStartOfMinute(<span>Timestamp</span>), ServiceName)</span></code></pre></div>\n<p>This structure allows queries to efficiently prune data both by time and by service.</p>\n<p>To ensure the primary key is fully exploited, ClickStack rewrites timestamp filters so they align with the expressions used in the key. For example, if a user filters on a time range, the naïve query might look like:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> otel_logs</span>\n<span><span>WHERE</span> <span>Timestamp</span> <span>&gt;=</span> <span>'2026-03-14 10:00:00'</span></span>\n<span>  <span>AND</span> <span>Timestamp</span> <span>&lt;</span> <span>'2026-03-14 11:00:00'</span></span>\n<span><span>ORDER</span> <span>BY</span> <span>Timestamp</span> <span>DESC</span>;</span></code></pre></div>\n<p>If the table is ordered by toStartOfMinute(Timestamp), ClickStack augments the filter to match the key expression:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> otel_logs</span>\n<span><span>WHERE</span> toStartOfMinute(<span>Timestamp</span>) <span>&gt;=</span> toStartOfMinute(<span>'2026-03-14 10:00:00'</span>)</span>\n<span>  <span>AND</span> toStartOfMinute(<span>Timestamp</span>) <span>&lt;</span> toStartOfMinute(<span>'2026-03-14 11:00:00'</span>)</span>\n<span>  <span>AND</span> <span>Timestamp</span> <span>&gt;=</span> <span>'2026-03-14 10:00:00'</span></span>\n<span>  <span>AND</span> <span>Timestamp</span> <span>&lt;</span> <span>'2026-03-14 11:00:00'</span></span>\n<span><span>ORDER</span> <span>BY</span> toStartOfMinute(<span>Timestamp</span>) <span>DESC</span>;</span></code></pre></div>\n<p>By including the primary key expression in the filter, ClickHouse can prune partitions and granules much more aggressively. In practice, this can significantly reduce the amount of data scanned.</p>\n<p>The same optimization applies when the primary key uses coarser expressions such as <code>toStartOfDay(Timestamp).</code> ClickStack automatically adds filters on both the derived expression and the raw timestamp, ensuring precise filtering across narrow time windows while still enabling efficient index pruning. In internal testing, this approach reduced query latency by roughly 25%, with larger gains possible for complex queries.</p>\n<h2 id=\"user-content-intelligent-sampling\"></h2>\n<p>Some ClickStack features require analyzing very large datasets to generate visual insights. Running these queries across billions of rows would be computationally expensive and could significantly increase latency and resource consumption. To keep the interface responsive while still providing accurate insights, ClickStack applies <strong>intelligent sampling techniques</strong> that reduce the amount of data read while preserving representative results.</p>\n<p>The goal of sampling is not simply to reduce the dataset size. It must also ensure that the sample is deterministic when necessary and statistically representative of the larger dataset. Depending on the feature, ClickStack applies different sampling strategies that balance accuracy and performance.</p>\n<p>Below are several examples of how sampling is used throughout ClickStack.</p>\n<h3 id=\"user-content-event-deltas-deterministic-part-offset-sampling\"></h3>\n<p>The <a target=\"_blank\" href=\"https://clickhouse.com/blog/%20faster-root-cause-for-slow-traces-with-clickstack-event-deltas\">Event Deltas feature</a> compares the attribute distribution of events inside a selected time-series region (\"outliers\") with those outside it (\"inliers\"). This requires retrieving full rows for a small set of representative events from each group.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_mar2026_image1_7659047573.png&w=2048&q=75\"></span></p>\n<p>For example, suppose a user selected the inliers as being the subset between a specific date range where the Duration was between 500 and 1000. A naive approach to sampling might attempt to fetch rows using:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> otel_traces</span>\n<span><span>WHERE</span> <span>Timestamp</span> <span>&gt;=</span> <span>1700000000</span></span>\n<span>  <span>AND</span> <span>Timestamp</span> <span>&lt;=</span> <span>1700003600</span></span>\n<span>  <span>AND</span> Duration <span>&gt;=</span> <span>500</span></span>\n<span>  <span>AND</span> Duration <span>&lt;=</span> <span>1000</span></span>\n<span><span>ORDER</span> <span>BY</span> rand()</span>\n<span>LIMIT <span>1000</span>;</span></code></pre></div>\n<p>However, in ClickHouse LIMIT is applied after rows are read and filtered. The result is a deterministic sample that avoids scanning the entire dataset.</p>\n<h3 id=\"user-content-value-distribution-sampling-for-facets\"></h3>\n<p>Another common workflow is showing top attribute values within a filtered dataset. When searching in ClickStack, facets appear alongside the results to show which fields are present and provide a representative sample of values for those fields. This helps users quickly understand the shape of the data and guides them in refining their filters.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_mar2026_image2_1036405e6d.png&w=2048&q=75\"></span></p>\n<p>Computing exact distributions over billions of rows would be expensive. Queries such as \"show the latest logs\", \"top error messages\", or \"slowest requests\" typically take the form ORDER BY … LIMIT N.
