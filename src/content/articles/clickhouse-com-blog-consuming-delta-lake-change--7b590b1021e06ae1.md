ClickHouse, on the other hand, is an open-source, columnar database optimised for high-performance analytical queries. Combining these technologies allows users to leverage the strengths of both: Delta Lake for <a target=\"_blank\" href=\"https://clickhouse.com/resources/engineering/data-lakehouse\">data lakehouse</a> concerns and ClickHouse for fast, real-time data access. ClickHouse can already be used as a read-only query engine on your Delta Lake parquet using the <strong>DeltaLake</strong> or <strong>deltaLakeCluster</strong> table engines, with <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/issues/79603\">write support</a> coming soon.</p>\n<div><pre><code><span><span>CREATE TABLE</span> my_delta_table</span>\n<span>ENGINE <span>=</span> DeltaLake(<span>'s3://path/to/deltalake/table'</span>, <span>'access-key'</span>, <span>'secret-key'</span>)</span></code></pre></div>\n<!-- -->\n<p>The schema is automatically inferred from Delta Lake metadata and can be queried like so:</p>\n<div><pre><code><span><span>SELECT</span> col1, col2, col3, _file, _time, …etc </span>\n<span><span>FROM</span> my_delta_table</span></code></pre></div>\n<!-- -->\n<p>For more ad-hoc queries, the table functions <strong>deltaLake</strong> and <strong>deltaLakeCluster</strong> can be used to query data in place:</p>\n<div><pre><code><span><span>SELECT</span> col1, col2, col3, _file, _time, …etc </span>\n<span><span>FROM</span> deltaLake(<span>'s3://path/to/deltalake/table'</span>, <span>'access-key'</span>, <span>'secret-key'</span>)</span></code></pre></div>\n<!-- -->\n<p>Using ClickHouse as the query layer for your Delta tables is an effective strategy if the data is mostly cold and not frequently queried, and you are willing to tolerate the performance of remote object storage reads, without a need for duplication across your lakehouse-warehouse. Some users could benefit from frequent, latency-sensitive reads, likely using ClickHouse for real-time data access used by other systems - such as APIs, dashboards, recommender systems or other user-facing applications. Furthermore, even with optimisation techniques such as caching, remote object storage scans can be slower and costly, making data residency in ClickHouse a compelling interface for such use cases.</p>\n<p>Change Data Capture (CDC) is a process for replicating incremental changes from a Delta Lake table, typically after a snapshot of the data. This reduces data transfer overhead and ensures that ClickHouse always reflects the latest state of the data in the delta table with minimal latency.</p>\n<h2 id=\"key-components-of-the-pipeline\"></h2>\n<p>A CDC pipeline from Delta Lake to ClickHouse would involve the following core components:</p>\n<ul>\n<li><strong>Delta Lake table(s):</strong> The source data lake where data is persisted.</li>\n<li><strong>Change Data Feed (CDF):</strong> Delta Lake's mechanism for capturing row-level changes.</li>\n<li><strong>ClickHouse:</strong> The destination database to enable real-time usage of the data.</li>\n</ul>\n<h3 id=\"data-modelling\"></h3>\n<p>Due to the eventually consistent reconciliation of the upstream state, we use the ClickHouse ReplacingMergeTree table engine, a variant of MergeTree that is helpful in CDC workflows to resolve duplication or out-of-order data ingest (such as insert, then delete, then update operations). These techniques more or less <a target=\"_blank\" href=\"https://clickhouse.com/blog/postgres-to-clickhouse-data-modeling-tips-v2\">align with Postgres data modelling guidance provided in the past</a>. A ClickHouse table can be created with the below DDL, with an <code>name</code> and <code>age</code> as our ordering key and the <code>_commit_version</code> from the Delta Table CDF as our version key. For append-only workflows with no update or delete operations, a MergeTree table would provide more optimal query conditions.</p>\n<div><pre><code><span><span>CREATE TABLE</span> default.new_cdc_table</span>\n<span>(</span>\n<span>    `id` String,</span>\n<span>    `name` String,</span>\n<span>    `age` Int64,</span>\n<span>    `created_at` DateTime,</span>\n<span>    `_change_type` String,</span>\n<span>    `_commit_version` Int64,</span>\n<span>    `_commit_timestamp` DateTime</span>\n<span>)</span>\n<span>ENGINE <span>=</span> ReplacingMergeTree(`_commit_version`)</span>\n<span><span>PARTITION</span> <span>BY</span> toYYYYMM(`created_at`)</span>\n<span><span>ORDER</span> <span>BY</span> (`name`, `age`)</span></code></pre></div>\n<!-- -->\n<p>This table definition configures deduplication based on the primary key. When duplicates are found during merges, ClickHouse keeps only one row per unique key combination. Adding a version column (in this case, <strong>_commit_version</strong>) signals to ClickHouse to retain the row with the highest commit version. If no version column is specified, ClickHouse defaults to the last inserted row, which is typically not optimal for eventually consistent use cases such as CDC. This pattern of data insertion is well established and is what we use in the internals of the <a target=\"_blank\" href=\"https://clickhouse.com/docs/integrations/clickpipes/postgres\">Postgres</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/integrations/clickpipes/mysql\">MySQL</a> CDC processes with ClickPipes and PeerDB.</p>\n<p>There are a few caveats to consider when using the ReplacingMergeTree to model CDC data. The first is merge timing - unlike UPSERT operations in traditional RDBMSs, duplications aren’t removed immediately upon insertion. Deduplication of data only happens during background merge operations, which ClickHouse controls automatically. This can be circumvented by making queries on the table FINAL. Another condition some users find is the presence of a deleted record - due to soft deleting the row, it continues to exist in the ClickHouse destination table with the last values or default ClickHouse values. The example script in our pipeline does not support deletion events at this time.</p>\n<h2 id=\"data-preparation-in-delta-lake\"></h2>\n<p><a target=\"_blank\" href=\"https://github.com/ClickHouse/deltalake-cdc?tab=readme-ov-file#1-generate-sample-data\">An example data loader script</a> is used to create an unpartitioned Delta Lake table (although partitioning the table is recommended for very large tables) and stream synthetically generated data. The DataFrame library Polars is used to create records at a batch size provided. A sample performance benchmark of the data generation is that it can generate and write 20,000 records at a time, which is approximately 10MB worth of data into the Delta Lake table that can be generated on a c5.large AWS EC2 instance with 2 vCPU and 4 GB RAM every 1 second in the same region as the S3 bucket; the batch size is configurable and can be run on commodity hardware such as a laptop. The data loader script will create the Delta Lake table if it doesn’t already exist, and enable the CDF on creation, which has an insignificant impact on insertion. Once there are enough commits in the Delta Lake table, the data is ready to start ingesting into ClickHouse.</p>\n<h2 id=\"change-data-capture\"></h2>\n<p>CDC can be a challenging process depending on the source and the protocols involved. Open Table Formats (OTF) like Delta Lake and Apache Iceberg introduce complexity for CDC compared to traditional transactional databases like Postgres. While Postgres maintains a built-in Write-Ahead log (WAL) that records every change in chronological order within transaction boundaries, open table formats must reconstruct change streams from file-level operations across distributed storage. These formats rely on metadata layers and commit version differencing to track changes, which creates challenges in maintaining ordering, handling concurrent writes, and ensuring that consumers can reliably identify what changed between table versions. Fortunately, Delta Lake provides the <a target=\"_blank\" href=\"https://docs.delta.io/latest/delta-change-data-feed.html\">Change Data Feed (CDF)</a>, which enables operations on row-level data and can be processed by downstream systems like ClickHouse and ClickPipes. The change data is committed as part of the transaction, and becomes available at the same time new data is committed to the table. This setting can be enabled on Delta Lake table creation:</p>\n<div><pre><code><span><span>CREATE TABLE</span> my_cdc_table (id STRING, name STRING, age <span>INT</span>, created_at <span>TIMESTAMP</span>) TBLPROPERTIES (delta.enableChangeDataFeed <span>=</span> <span>true</span>)</span></code></pre></div>\n<!-- -->\n<p>Or can be added to existing tables like so:</p>\n<div><pre><code><span><span>ALTER TABLE</span> my_cdc_table <span>SET</span> TBLPROPERTIES (delta.enableChangeDataFeed <span>=</span> <span>true</span>)</span></code></pre></div>\n<!-- -->\n<p>Unlike RDBMS CDC mechanisms, the CDF is a <strong>logical abstraction that is constructed from multiple components</strong> when querying for change data rather than explicit change records consumed from some physical storage. The general advice is to let the ReplacingMergeTree table engine resolve the state of the table in an eventually consistent way, rather than reconcile in program memory or at source, as this can be costly and slow.</p>\n<h2 id=\"python-prototype-for-cdc-from-delta-lake-to-clickhouse\"></h2>\n<p>Our <a target=\"_blank\" href=\"https://github.com/ClickHouse/deltalake-cdc\">reference implementation</a> uses the <a target=\"_blank\" href=\"https://pypi.org/project/deltalake/\">DeltaLake Python library</a>, which uses <a target=\"_blank\" href=\"https://github.com/delta-io/delta-rs\">delta-rs</a> bindings to read from Delta Lake. At a high level, the underlying algorithm iterates through each version in the specified range (starting version - continuous polling), reads through the transaction log for each version, and categorises the actions in CDC / add row / remove row operations. Separate DataFusion execution plans are created for each file type. It then combines all 3 operations and projects the final schema with the CDF metadata columns (_change_type, _commit_version, _commit_timestamp).</p>\n<p>The underlying library supports consuming the CDF from a version or timestamp, but for our example, we have opted to support only version. The number of records received can vary based on the size of changes made when that version was committed.
