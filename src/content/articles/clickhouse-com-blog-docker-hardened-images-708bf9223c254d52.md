contentHtml: "<div><h2 id=\"user-content-tldr\"></h2>\n<p><em>ClickHouse is now available on <a target=\"_blank\" href=\"https://hub.docker.com/hardened-images/catalog?search=clickhouse\">Docker Hardened Images</a>: stripped-down, security-hardened builds of the ClickHouse stack, including the server image, ClickHouse Keeper, the Kubernetes Operator and its Helm chart, and the metrics exporter, all built to pass enterprise security scans by shipping only what each component needs to run. Everything about how ClickHouse runs stays the same, only the packaging around it changes.</em></p>\n<h2 id=\"user-content-deploying-clickhouse-anywhere\"></h2>\n<p>For millions of developers, the fastest way to try ClickHouse is a single command:</p>\n<div><pre><code><span>docker run -d --name my-clickhouse-server \\</span>\n<span>  --<span>ulimit</span> nofile=262144:262144 \\</span>\n<span>  clickhouse/clickhouse-server</span></code></pre></div>\n<p>With that you have a running columnar database that can aggregate billions of rows in real time. That low barrier to entry is deliberate and the adoption of the <a target=\"_blank\" href=\"https://hub.docker.com/r/clickhouse/clickhouse-server\">clickhouse/clickhouse-server image</a> has passed 100M+ pulls on Docker Hub.</p>\n<p>For a large part of our community, that first <code>docker run</code> is their entry point to ClickHouse, and getting started is the easy part. The friction shows up later. Once you move past experimentation and small workloads, the command that runs on your laptop has to run at enterprise scale: inside a pipeline, behind a security team, with a vulnerability scanner monitoring everything.</p>\n<p>This post covers why the standard ClickHouse Docker image gets flagged in those scans (the findings come from unused packages in the Ubuntu base, not from ClickHouse), and how the Docker Hardened Image passes them while running exactly the same database.</p>\n<h2 id=\"user-content-from-first-query-to-production\"></h2>\n<p>Every container image is really two components stacked together: the application you want, and a base operating system layer it runs on. At the time of writing, the standard ClickHouse image is built on <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/master/docker/server/Dockerfile.ubuntu\">Ubuntu 22.04</a>. That base brings convenience, a familiar environment, a shell, debugging tools, but it also brings dozens of packages ClickHouse never uses: Perl, wget, apt itself, and a long tail of transitive dependencies that exist only because Ubuntu ships them by default.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fdhi_jul2026_image2_59f522a402.png&w=2048&q=75\"></span>\n<em>CVEs live in the base image, not in ClickHouse.</em></p>\n<p>This matters a lot in an enterprise pipeline, because security scanners such as Trivy, Grype, and the built-in AWS ECR scanner inventory every package in the image, whether the application loads it or not. Some of those Ubuntu packages carry known CVEs with no upstream fix. For example, wget has shipped with <a target=\"_blank\" href=\"https://ubuntu.com/security/CVE-2021-31879\">CVE-2021-31879</a> unpatched since 2021. The scanner reports the findings, the security team blocks the deployment, and they are right to do so: the vulnerabilities are real, even if the vulnerable tools never run.</p>\n<p>The result is a frustrating loop that many teams will recognize. The database works, but the deployment is blocked anyway. Days go into investigating findings and writing risk exceptions for packages ClickHouse never touches, and the exceptions often get rejected regardless.</p>\n<h2 id=\"user-content-a-smooth-developer-experience-in-enterprise-workloads\"></h2>\n<p>In April 2026, Docker added clickhouse-server to its <a target=\"_blank\" href=\"https://hub.docker.com/hardened-images/catalog?search=clickhouse\">Hardened Images catalog</a>. Docker Hardened Images (DHI) start from a different question: what does ClickHouse actually need to run?</p>\n<p>The DHI clickhouse-server image ships a minimal base with no package manager and no network tools like wget or curl, runs as a non-root user out of the box, and carries SLSA Level 3 provenance, cryptographic proof of what went into the build. Docker's security team maintains it and actively patches CVEs. Rather than patching the wget vulnerability, DHI removes wget entirely.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fdhi_jul2026_image3_4eb4b5deab.png&w=2048&q=75\"></span>\n<span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fdhi_jul2026_image4_ee8f0f180f.png&w=2048&q=75\"></span></p>\n<p>The difference shows up in the scan results. Docker's own <a target=\"_blank\" href=\"https://docs.docker.com/scout/\">Scout</a> comparison found the standard image carrying 8 medium and 11 low severity findings across 111 packages. The DHI image carried 0 medium and 14 low, with every remaining finding in core libraries like glibc and openssl where no fix exists on any distribution. The findings that block deployments, the ones in unnecessary utilities, are gone because the utilities are gone.</p>\n<p>From ClickHouse's perspective, nothing changes. Your volume mounts and config files carry over untouched. Moving to the hardened image takes one changed line:</p>\n<div><pre><code><span><span># standard image</span></span>\n<span>docker run -d --<span>ulimit</span> nofile=262144:262144 \\</span>\n<span>  clickhouse/clickhouse-server</span>\n<span></span>\n<span><span># hardened image</span></span>\n<span>docker run -d --<span>ulimit</span> nofile=262144:262144 \\</span>\n<span>  -e CLICKHOUSE_PASSWORD=mysecretpassword \\</span>\n<span>  dhi.io/clickhouse-server:26.2-debian13</span></code></pre></div>\n<p><em>Note: <code>CLICKHOUSE_PASSWORD</code> is what makes ClickHouse reachable over the network. Without it, the <code>default</code> user is restricted to localhost.</em></p>\n<p>With major security improvements come minor inconveniences: DHI images live in a separate registry, so you mirror the image to your organization's Docker Hub namespace once and authenticate to dhi.io.</p>\n<p>For the full walkthrough, including Kubernetes configuration, the metrics exporter, debugging without the usual tools, and a migration checklist, read Docker's companion post: <a target=\"_blank\" href=\"https://www.docker.com/blog/from-security-blocked-to-prod-ready-clickhouse-on-docker-hardened-images/\">From Security Blocked to Prod Ready: ClickHouse on Docker Hardened Images</a>.</p>\n<h2 id=\"user-content-developer-experience-and-security-are-not-a-tradeoff\"></h2>\n<p>At first this looks like a tradeoff: keep the shell, package manager, and network tools and the container is easy to debug but harder to secure, while stripping them out gives you the reverse. But that tension only exists if it all has to happen in one image, and it doesn't. For local development and debugging, Docker Hardened Images (DHI) ships a dev variant with the extra tooling, and <code>docker debug</code> attaches a full toolset to the hardened image temporarily without rebuilding it. Because you harden what ships to production rather than what runs on your laptop, you keep your debugging tools in development and the smaller attack surface in production.</p>\n<p>The payoff is a shorter conversation with your security team. Instead of spending days arguing that each flagged CVE sits in a package ClickHouse never loads, you deploy an image where those packages don't exist, with build provenance to back it up. Nothing about the database itself changes. The speed, scale, and cost efficiency that made you choose ClickHouse all carry over, and what gets simpler is the security approval.</p>\n<p>Docker Hardened Images (DHI) are a hardened build of the open-source clickhouse-server image, for teams that self-manage ClickHouse and secure the container themselves. If you run on Kubernetes, the <a target=\"_blank\" href=\"https://clickhouse.com/docs/products/kubernetes-operator/overview\">ClickHouse Kubernetes Operator</a> automates deployment and management, and it ships as a hardened image and Helm chart in the DHI catalog too, alongside ClickHouse Keeper and the metrics exporter.</p>\n<p>If you'd rather not run your own infrastructure, ClickHouse also offers <a target=\"_blank\" href=\"https://clickhouse.com/docs/products/cloud/features/infrastructure/deployment-options\">managed and self-deployed options</a>: ClickHouse Cloud runs everything for you, Bring Your Own Cloud puts that managed service inside your own cloud account, and ClickHouse Private and ClickHouse Government are self-deployed builds with FIPS 140-3 and further hardening for the strictest compliance environments. Whichever you pick, it's ClickHouse underneath. What differs is how much of the operational work you keep and how much you hand off.</p>\n<h2 id=\"user-content-try-it-out-yourself\"></h2>\n<p>Whether you are typing your first <code>docker run</code> or shipping into a locked-down enterprise pipeline, there is a ClickHouse image that fits.</p>\n<p>Find clickhouse-server in the <a target=\"_blank\" href=\"https://hub.docker.com/hardened-images/catalog?search=clickhouse\">Docker Hardened Images catalog</a>, and read <a target=\"_blank\" href=\"https://www.docker.com/blog/from-security-blocked-to-prod-ready-clickhouse-on-docker-hardened-images/\">Docker's full guide</a> for setup details. You can reproduce the scan comparison yourself in two minutes:</p>\n<div><pre><code><span>docker scout quickview clickhouse/clickhouse-server:latest</span>\n<span>docker scout quickview dhi.io/clickhouse-server:26.2-debian13</span></code></pre></div>\n<p>And if you'd rather skip image decisions entirely, <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> runs everything for you.</p></div>"
