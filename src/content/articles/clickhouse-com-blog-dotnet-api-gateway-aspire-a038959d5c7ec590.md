contentHtml: "<div><h2 id=\"user-content-why-clickhouse-and-aspire\"></h2>\n<p>If you spend most of your time in ASP.NET Core, two pieces of this demo may be new: ClickHouse and Aspire. A quick intro before we dive in:</p>\n<p><strong>Aspire</strong> is Microsoft's .NET stack for coordinating distributed services. You write an <code>AppHost</code> project, a small C# program that describes your services, databases, containers, and how they connect, and <code>dotnet run</code> brings the whole graph up locally. Aspire also includes a web UI that shows every resource, streams logs, and renders OpenTelemetry traces and metrics emitted by your services. Once you have used it, going back to juggling launch profiles and a <code>docker-compose.yml</code> feels archaic.</p>\n<p><strong>ClickHouse</strong> is an extremely fast, open-source, columnar database built for analytical queries over large volumes of data. It is the database you reach for when you want to ask questions like \"what was p95 latency by route over the last hour?\" across very large request histories and get an answer quickly. Unlike transactional databases like SQL Server or Postgres, ClickHouse is tuned for aggregates over append-mostly data. The mental model worth carrying into the rest of this post: ClickHouse is to analytical SQL what Redis is to caching: purpose-built for one job and very fast at it.</p>\n<p>We ship two ClickHouse integrations for Aspire which let you set up a database and a client that talks to it with just a few lines of code. That is the foundation the rest of this sample builds on.</p>\n<h3 id=\"user-content-the-demo\"></h3>\n<p>In this post we will build an application that uses Aspire to orchestrate:</p>\n<ul>\n<li>A ClickHouse container</li>\n<li>A YARP API gateway</li>\n<li>Two backend APIs for <code>Products</code> and <code>Orders</code></li>\n<li>A background load generator that calls our backend APIs</li>\n<li>An analytics API</li>\n<li>A Blazor dashboard</li>\n</ul>\n<p>The gateway is the center of the demo. It does two things:</p>\n<ol>\n<li>Routes traffic to backend services with YARP.</li>\n<li>Records each proxied request into ClickHouse.</li>\n</ol>\n<p>At the same time, the gateway emits custom OpenTelemetry metrics that show up in Aspire:</p>\n<ul>\n<li>Request count</li>\n<li>Duration histogram</li>\n<li>Backend failure count</li>\n</ul>\n<p>That gives us a useful split:</p>\n<ul>\n<li>Aspire shows live operational telemetry.</li>\n<li>ClickHouse stores the full request history for aggregate analytics.</li>\n</ul>\n<h3 id=\"user-content-try-it-yourself\"></h3>\n<p>The full source is in the <a target=\"_blank\" href=\"https://github.com/ClickHouse/aspire-clickhouse-gateway-analytics-demo\">companion repository</a>. At service startup the integration reads the injected connection string, registers an <code>IClickHouseClient</code> singleton in DI, and adds a health check and OpenTelemetry tracing for queries, all from this one line.</p>\n<h2 id=\"user-content-the-gateway-logging-layer\"></h2>\n<p>The core middleware pattern is straightforward:</p>\n<ul>\n<li>Start a stopwatch</li>\n<li>Call the next delegate</li>\n<li>Normalize the route</li>\n<li>Capture the current trace id</li>\n<li>Emit gateway metrics</li>\n<li>Enqueue a row for background ingestion</li>\n</ul>\n<p>That last step is worth dwelling on. The proxied request must not wait on ClickHouse; if the database is slow or briefly unavailable, we want the gateway to keep serving traffic. So the middleware does not insert anything itself, it simply hands off the row to a bounded in-memory queue:</p>\n<div><pre><code><span><span>if</span> (!requestLogQueue.TryEnqueue(logEntry))</span>\n<span>{</span>\n<span>    GatewayMetrics.LogDrops.Add(<span>1</span>, tags);</span>\n<span>}</span></code></pre></div>\n<p>The queue uses a bounded <code>System.Threading.Channels</code> channel with <code>FullMode = DropWrite</code>:</p>\n<div><pre><code><span>Channel.CreateBounded(<span>new</span> BoundedChannelOptions(Capacity)</span>\n<span>{</span>\n<span>    FullMode = BoundedChannelFullMode.DropWrite,</span>\n<span>    SingleReader = <span>true</span>,</span>\n<span>    SingleWriter = <span>false</span>,</span>\n<span>});</span></code></pre></div>\n<p><code>DropWrite</code> is the part that keeps the request path safe. If the queue fills up, <code>TryEnqueue</code> returns <code>false</code> immediately. The middleware increments a <code>gateway.log_drops</code> counter (tagged the same way as the rest of the gateway metrics) and moves on. The proxied request never waits on the database, and the dropped-row counter becomes a first-class signal you can alert on.</p>\n<p>A background <code>IHostedService</code> drains the channel. Its loop is small: wait for one row, drain whatever else is immediately available into a capped batch, bulk-insert, repeat:</p>\n<div><pre><code><span><span>while</span> (!stoppingToken.IsCancellationRequested)</span>\n<span>{</span>\n<span>    batch.Add(<span>await</span> queue.Reader.ReadAsync(stoppingToken));</span>\n<span></span>\n<span>    <span>while</span> (batch.Count &lt; MaxBatchSize &amp;&amp; queue.Reader.TryRead(<span>out</span> <span>var</span> more))</span>\n<span>    {</span>\n<span>        batch.Add(more);</span>\n<span>    }</span>\n<span></span>\n<span>    <span>try</span></span>\n<span>    {</span>\n<span>        <span>await</span> client.InsertBinaryAsync(<span>\"request_logs\"</span>, batch, InsertOptions, stoppingToken);</span>\n<span>    }</span>\n<span>    <span>catch</span> (Exception ex)</span>\n<span>    {</span>\n<span>        logger.LogError(ex, <span>\"Failed to write {Count} request log rows to ClickHouse.\"</span>, batch.Count);</span>\n<span>    }</span>\n<span>    <span>finally</span></span>\n<span>    {</span>\n<span>        batch.Clear();</span>\n<span>    }</span>\n<span>}</span></code></pre></div>\n<p>Each <code>InsertBinaryAsync</code> call takes a list of POCOs and the driver streams them in ClickHouse's native <code>RowBinary</code> format. Values like <code>Guid</code>, <code>DateTime</code>, and <code>uint</code> round-trip in their native binary representation with no string conversions.</p>\n<p>The mapping from .NET property names to snake_case column names is declared on the record itself:</p>\n<div><pre><code><span><span><span>internal</span> <span>sealed</span> <span>record</span> <span>RequestLogRow</span>(<span></span></span></span>\n<span><span><span>    [property: ClickHouseColumn(Name = <span>\"request_id\"</span></span>)] Guid RequestId,</span></span>\n<span><span>    [property: <span>ClickHouseColumn</span>(<span>Name = <span>\"trace_id\"</span></span>)] <span>string</span> TraceId,</span></span>\n<span><span>    [property: <span>ClickHouseColumn</span>(<span>Name = <span>\"timestamp\"</span></span>)] DateTime Timestamp,</span></span>\n<span><span>    <span>// ... remaining columns</span></span></span>\n<span><span>    [property: <span>ClickHouseColumn</span>(<span>Name = <span>\"error_message\"</span></span>)] <span>string</span>? ErrorMessage)</span>;</span></code></pre></div>\n<p>The POCO has to be registered with the client once so the driver can build its column writer for the type. The pump does it at startup, right after creating the schema:</p>\n<div><pre><code><span>client.RegisterBinaryInsertType();</span></code></pre></div>\n<p>The insert runs with two ClickHouse-side settings:</p>\n<div><pre><code><span><span>private</span> <span>static</span> <span>readonly</span> InsertOptions InsertOptions = <span>new</span>()</span>\n<span>{</span>\n<span>    CustomSettings = <span>new</span> Dictionary&lt;<span>string</span>, <span>object</span>&gt;</span>\n<span>    {</span>\n<span>        [<span>\"async_insert\"</span>] = <span>1</span>,</span>\n<span>        [<span>\"wait_for_async_insert\"</span>] = <span>1</span>,</span>\n<span>    },</span>\n<span>};</span></code></pre></div>\n<p><code>async_insert = 1</code> tells ClickHouse to batch incoming inserts instead of creating a part per insert call. ClickHouse works best with small numbers of large inserts; async inserts let the server batch incoming data to avoid creating too many new parts.</p>\n<p><code>wait_for_async_insert = 1</code> means the background writer waits until the insert has been flushed to disk. Without it, ClickHouse would acknowledge the insert before the data is durable, and any crash or restart between acknowledgement and flush could lose rows silently. In a production gateway you might flip <code>wait_for_async_insert</code> to <code>0</code> if you can tolerate that small data-loss window, but this sample keeps the safer default.</p>\n<h2 id=\"user-content-schema\"></h2>\n<p>The raw table is focused on request analytics:</p>\n<div><pre><code><span><span>CREATE TABLE</span> IF <span>NOT</span> <span>EXISTS</span> request_logs (</span>\n<span>    request_id UUID,</span>\n<span>    trace_id String,</span>\n<span>    <span>timestamp</span> DateTime64(<span>6</span>, <span>'UTC'</span>),</span>\n<span>    <span>method</span> LowCardinality(String),</span>\n<span>    route_pattern LowCardinality(String),</span>\n<span>    path String,</span>\n<span>    upstream_service LowCardinality(String),</span>\n<span>    status_code UInt16,</span>\n<span>    duration_ms Float64,</span>\n<span>    request_size UInt32,</span>\n<span>    response_size UInt32,</span>\n<span>    error_message Nullable(String)</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree()</span>\n<span><span>PARTITION</span> <span>BY</span> toYYYYMMDD(<span>timestamp</span>)</span>\n<span><span>ORDER</span> <span>BY</span> (upstream_service, route_pattern, <span>timestamp</span>)</span>\n<span>TTL <span>timestamp</span> <span>+</span> <span>INTERVAL</span> <span>30</span> <span>DAY</span>;</span></code></pre></div>\n<p>A few of the type choices are worth calling out because they have no direct equivalent in SQL Server or Postgres:</p>\n<ul>\n<li><code>LowCardinality(String)</code> on <code>method</code>, <code>route_pattern</code>, and <code>upstream_service</code> dictionary-encodes the column. ClickHouse stores a small dictionary of unique values plus integer indexes per row, which collapses storage and speeds up <code>GROUP BY</code> / <code>WHERE</code> filters dramatically for low-cardinality columns.</li>\n<li><code>DateTime64(6, 'UTC')</code> is microsecond-precision and bakes the timezone into the column metadata, eliminating the usual UTC-vs-local confusion at query time.</li>\n<li><code>UInt16</code> for <code>status_code</code> halves the column footprint vs. a 32-bit default. ClickHouse rewards picking the tightest integer type that fits.</li>\n<li><code>Nullable(String)</code> is opt-in: columns are NOT NULL by default and <code>Nullable</code> carries a per-row null bitmap, so it is reserved for fields where null is genuinely meaningful.</li>\n</ul>\n<p>The engine clauses carry most of the query performance and retention story:</p>\n<ul>\n<li><code>PARTITION BY toYYYYMMDD(timestamp)</code> splits the table into daily partitions. Time-range queries skip every partition outside the window.</li>\n<li><code>ORDER BY (upstream_service, route_pattern, timestamp)</code> is the sorting key. It controls on-disk layout and the sparse primary index. Filters on the leading key columns are fast; filters on <code>path</code> are not.</li>\n<li><code>TTL timestamp + INTERVAL 30 DAY</code> drops old partitions automatically during background merges. No cleanup job required.</li>\n</ul>\n<p>The sample also creates a materialized view called <code>request_stats_mv</code>. If you have not used ClickHouse materialized views before, this is where the schema gets interesting.</p>\n<p>A materialized view in ClickHouse is not a cached query. It is a separate table that ClickHouse populates automatically as rows land in the source table. Every insert into <code>request_logs</code> triggers the view's <code>SELECT</code> statement and the result is written into the view's own storage. The view uses <code>AggregatingMergeTree</code>, which means the stored rows are partial aggregation states, not final values.</p>\n<p>The key to reading the DDL is the <code>-State</code> / <code>-Merge</code> suffix convention. In the view definition:</p>\n<div><pre><code><span>countState() <span>AS</span> request_count,</span>\n<span>avgState(duration_ms) <span>AS</span> avg_duration,</span>\n<span>quantilesTDigestState(<span>0.5</span>, <span>0.95</span>, <span>0.99</span>)(duration_ms) <span>AS</span> duration_quantiles</span></code></pre></div>\n<p><code>countState()</code> does not store a finished count. It stores an intermediate aggregation state that ClickHouse can merge with other states later. When the dashboard queries the view, it uses the corresponding <code>-Merge</code> combinators:</p>\n<div><pre><code><span>countMerge(request_count) <span>AS</span> request_count,</span>\n<span>avgMerge(avg_duration) <span>AS</span> avg_latency_ms,</span>\n<span>quantilesTDigestMerge(<span>0.5</span>, <span>0.95</span>, <span>0.99</span>)(duration_quantiles) <span>AS</span> percentiles</span></code></pre></div>\n<p>This is what makes the pattern efficient. The raw <code>request_logs</code> table may have millions of rows, but the materialized view has already reduced them to one partial-aggregate row per service, route, status code, and minute. The dashboard query merges those small intermediate states instead of scanning the full log. The result is that percentile and error-rate panels stay fast regardless of how much traffic the gateway has handled.</p>\n<h2 id=\"user-content-the-observability-story\"></h2>\n<p>The Aspire dashboard renders traces, metrics, and structured logs from the OTLP feed that every service publishes. The logs, traces, and metrics in the dashboard's views are purely in-memory. When the AppHost stops, the history is gone. It's a system designed for the inner dev loop, but it is not a production observability stack.</p>\n<p>The good news is that the wiring above does not change when you move beyond development. The services emit standard OTLP, so swapping the dashboard endpoint for a production observability backend is a configuration change. <a target=\"_blank\" href=\"https://clickhouse.com/use-cases/observability\">ClickStack</a>, the ClickHouse- and OpenTelemetry-native stack for logs, metrics, and traces, is a natural place to store and query that data with strong performance and compression.</p>\n<h3 id=\"user-content-in-clickhouse\"></h3>\n<p>Finally, let's look at the dashboard backed by ClickHouse. This view is intentionally different from the Aspire dashboard. It is not trying to show every span or every live process.
