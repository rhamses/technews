methodology used to compare query performance fairly.</p>\n<h2 id=\"methodology\"></h2>\n<p>To reflect real observability workflows, we benchmarked both systems under cold and hot conditions.</p>\n<p><strong>Cold runs</strong> simulate first-touch queries over previously unseen time ranges, where the required log data must be loaded from disk.</p>\n<p><strong>Hot runs</strong> simulate repeated execution once the same data is already cached.</p>\n<h3 id=\"caches-considered-in-this-benchmark\"></h3>\n<p>Three cache layers can influence query latency:</p>\n<ol>\n<li>\n<p><strong>Linux page cache</strong><br>The operating system’s file cache, which avoids re-reading data from disk.</p>\n</li>\n<li>\n<p><strong>Filter-evaluation caches</strong><br>Engine-level caches that remember prior predicate/filter results to speed up repeated filtering work.</p>\n<ul>\n<li>ClickHouse: <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/query-condition-cache\">query condition cache</a></li>\n<li>Elasticsearch: <a target=\"_blank\" href=\"https://www.elastic.co/docs/reference/elasticsearch/configuration-reference/node-query-cache-settings\">node query cache</a></li>\n</ul>\n</li>\n<li>\n<p><strong>Full query-result caches</strong><br>Caches that store complete query responses for identical repeated queries.</p>\n<ul>\n<li>ClickHouse: <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/query-cache\">query cache</a></li>\n<li>Elasticsearch: <a target=\"_blank\" href=\"https://www.elastic.co/docs/reference/elasticsearch/rest-apis/shard-request-cache\">shard request cache</a></li>\n</ul>\n</li>\n</ol>\n<p>To focus on core execution performance, <strong>we disabled full query-result caches during benchmarking</strong>. Otherwise, we would mostly be measuring the speed of repeated in-memory result lookups, which is not very interesting here. We kept filter-evaluation caches enabled, however, because they are part of the engines’ normal execution path.</p>\n<h3 id=\"measuring-cold-runs\"></h3>\n<p>For a cold run, we fully shut down both systems, dropped the Linux page cache, restarted the servers, and only then executed a query.</p>\n<p>This means:</p>\n<ul>\n<li>no data pages were cached in memory</li>\n<li>the engine had to load required data from disk</li>\n<li>runtime reflects storage efficiency, pruning ability, and raw execution speed</li>\n</ul>\n<p>Each query in the OTel log query suite was executed under these cold-start conditions, and the reported cold totals are the sum of all per-query runtimes.</p>\n<h3 id=\"measuring-hot-runs\"></h3>\n<p>Hot runs kept both systems running between executions without dropping the Linux page cache.</p>\n<p>For each query:</p>\n<ul>\n<li>the same query was executed <strong>three times in a row</strong></li>\n<li>full query-result caches remained disabled</li>\n<li>filter-evaluation caches remained enabled</li>\n<li>the <strong>fastest</strong> of the three runs was recorded as the hot result</li>\n</ul>\n<p>This isolates repeated-query performance without allowing full result reuse.</p>\n<p>Each query in the OTel log query suite was measured under these conditions, and the reported hot totals are the sum of all per-query runtimes.</p>\n<h3 id=\"elasticsearch-query-dsl-vs-es-ql\"></h3>\n<p>Elasticsearch results shown in the main charts use <a target=\"_blank\" href=\"https://www.elastic.co/docs/explore-analyze/query-filter/languages/querydsl\">Query DSL</a>. We also implemented the full suite in <a target=\"_blank\" href=\"https://www.elastic.co/docs/explore-analyze/query-filter/languages/esql-kibana\">ES|QL</a>, but observed consistently slower runtimes in our tests, so Query DSL serves as the stronger Elasticsearch baseline throughout the main benchmark.</p>\n<p>The public benchmark repository <a target=\"_blank\" href=\"https://github.com/ClickHouse/TextBench/tree/main/elasticsearch/results/es_dsl_vs_esql\">includes</a> the corresponding cold and hot per-query comparison charts for Query DSL vs ES|QL.</p>\n<p>With the benchmark methodology established, we next examine how both systems store OTel logs on disk. That on-disk layout is essential context for the results that follow.</p>\n<h3 id=\"what-about-opensearch\"></h3>\n<p>This benchmark focuses on Elasticsearch, not OpenSearch. We chose Elasticsearch as the baseline because it remains the best-known reference point for full-text log search. OpenSearch is closely related and often chosen by teams looking for an Elasticsearch-compatible, AWS-native, or lower-cost option.</p>\n<p>We did not run the full benchmark suite against OpenSearch for this post, so the results below should be read strictly as ClickHouse vs. Elasticsearch. But for teams comparing OpenSearch vs. ClickHouse for log analytics, the core architectural question is the same: search is usually only the first step. Once matching log rows need to be filtered, counted, grouped by service, or aggregated over time, the workload becomes analytical, and that is where ClickHouse is designed to pull ahead.</p>\n<h2 id=\"how-otel-logs-are-stored-on-disk\"></h2>\n<p>To better understand the storage footprint results in the next section, we first look at how Elasticsearch and ClickHouse store and compress ingested OTel logs on disk. The following diagram provides a simplified sketch.</p>\n<p><span><img alt=\"Blog-FTS-vs-Elasticsearch.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_FTS_vs_Elasticsearch_001_19f2e37110.png&w=2048&q=75\"></span></p>\n<p>In both systems, ingested OTel log data is ultimately written into immutable on-disk units:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://lucene.apache.org/core/3_0_3/fileformats.html#Segments\">Lucene segments</a> in Elasticsearch and</li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">data parts</a> in ClickHouse</li>\n</ul>\n<p>These units logically belong to shards (not shown in the diagram) and are continuously merged in the background into larger ones. Segments typically grow to about 5 GB and parts to about 150 GB, though larger forced merges are possible in both systems.</p>\n<p>In Elasticsearch, shards in turn make up indexes, as described <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing#elasticsearch\">here</a>; ClickHouse shards are described <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing#clickhouse\">here</a>.</p>\n<p>Within those on-disk units, both systems organize data into specialized structures that serve four main purposes: fast aggregations, full-text search, returning original documents, and pruning irrelevant data during query execution.</p>\n<h3 id=\"columnar-storage-for-fast-aggregations\"></h3>\n<p>Both systems use <strong>① columnar storage</strong>: aggregation queries read only the referenced columns, scan fewer bytes due to per-column compression, and execute vectorized (SIMD) operations on contiguous data.</p>\n<p>In Elasticsearch <strong><a target=\"_blank\" href=\"https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/doc-values\">doc_values</a></strong> each column <a target=\"_blank\" href=\"https://lucene.apache.org/core/9_9_0/core/org/apache/lucene/codecs/lucene90/Lucene90DocValuesFormat.html\">is</a> automatically encoded individually with specialized codecs such as delta and gcd, depending on data type and cardinality. However, <a target=\"_blank\" href=\"https://github.com/elastic/elasticsearch/issues/78266\">no</a> general-purpose compression algorithm such as lz4 or zstd is applied.</p>\n<p>In ClickHouse, compression codec(s) are also applied per <strong><a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">column file</a></strong>. ClickHouse supports <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/table#general-purpose-codecs\">general-purpose</a> (e.g. lz4 and zstd), <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/table#specialized-codecs\">specialized</a> (e.g. delta and gcd), and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/table#encryption-codecs\">encryption</a> codecs (e.g. AES_128), which can also be <a target=\"_blank\" href=\"https://clickhouse.com/blog/optimize-clickhouse-codecs-compression-schema\">chained</a> per column.</p>\n<h3 id=\"inverted-indexes-for-full-text-search\"></h3>\n<p>Both systems use an <strong>② <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Inverted_index\">inverted index</a></strong> as the basic data structure for full-text search.</p>\n<h3 id=\"stored-fields-and-source\"></h3>\n<p>In Elasticsearch <strong>③ <a target=\"_blank\" href=\"https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/mapping-store\">stored fields </a></strong> serve as a document store for returning original field values in query responses. By default, they also store <a target=\"_blank\" href=\"https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/mapping-source-field\">_source</a>, which contains the original ingested JSON documents. Stored fields are compressed using the algorithm defined by the <a target=\"_blank\" href=\"https://www.elastic.co/docs/reference/elasticsearch/index-settings/index-modules\">index.codec</a> setting: lz4 by default, or zstd for higher compression ratios at the cost of slower performance.</p>\n<blockquote>\n<p><strong>Why _source matters for logs</strong><br>For log analytics, returning the original ingested document is often essential. In Elasticsearch OSS, that makes _source hard to avoid in practice; Enterprise tiers can instead use <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/mapping-source-field.html#synthetic-source\">synthetic _source</a>.</p>\n</blockquote>\n<p>In ClickHouse, there is no separate equivalent structure: original rows are reconstructed directly from the values stored in the column files.</p>\n<h3 id=\"sparse-indexing-for-pruning\"></h3>\n<p>ClickHouse uses sparse indexing: because OTel log records are stored on disk in sorted order, the engine can group them into blocks, record value ranges for each block in a <strong>③ <a target=\"_blank\" href=\"https://clickhouse.com/docs/primary-indexes\">sparse primary index</a></strong>, and skip blocks that fall entirely outside the requested range.</p>\n<p><a target=\"_blank\" href=\"https://www.elastic.co/search-labs/blog/apache-lucene-10-release-highlights\">Lucene has a related sparse-indexing capability for sorted data</a>, but Elasticsearch does not expose it as a separate storage category in the <a target=\"_blank\" href=\"https://www.elastic.co/docs/reference/elasticsearch/rest-apis/index-disk-usage\">_disk_usage</a> output used for this comparison.</p>\n<p>Also note that in Elasticsearch the inverted index is not used only for full-text search. For all string fields except <code>Body</code>, we used the <a target=\"_blank\" href=\"https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/keyword\">keyword</a> type, while <code>Timestamp</code> uses a <a target=\"_blank\" href=\"https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/date\">date</a> type and numeric fields use <a target=\"_blank\" href=\"https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/number\">numeric</a> types. All these types by default also populate the inverted index for exact-match filtering, with values indexed as-is and without analysis. This means filters on these fields can be resolved efficiently through the inverted index, making it the closest analogue to ClickHouse’s sparse primary index in this comparison.</p>\n<h3 id=\"points-and-norms-for-filtering-and-scoring\"></h3>\n<p>In Elasticsearch, <strong>④ <a target=\"_blank\" href=\"https://www.elastic.co/fr/blog/lucene-points-6-0\">points</a></strong> support efficient filtering and range queries on numeric and date fields, while <a target=\"_blank\" href=\"https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/norms\">norms</a> store per-document scoring factors for text relevance.</p>\n<p>ClickHouse does not use a separate points structure: numeric and date filtering is handled through columnar scans plus sparse primary and <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/skipping-indexes\">skipping indexes</a>. ClickHouse also does not currently score full-text search results, which is not relevant for our logging use case.</p>\n<p>Now that the storage building blocks are clear, we can turn to their combined effect on disk usage.</p>\n<h2 id=\"otel-log-storage-footprint\"></h2>\n<p>The storage structures above explain where bytes go.
