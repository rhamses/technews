This can be achieved by skipping the denormalization and storing the <code>station_id</code> in a separate table before modifying the query to use a simple subquery.</p>\n<p>Let's first recap this suggestion for the benefit of readers. Below we create a <code>stations</code> table and populate it directly by inserting the data over HTTP using a url function.</p>\n<pre><p>\nCREATE TABLE stations\n(\n    `station_id` LowCardinality(String),\n    `country_code` LowCardinality(String),\n    `state` LowCardinality(String),\n    `name` LowCardinality(String),\n    `lat` Float64,\n    `lon` Float64,\n    `elevation` Float32\n)\nENGINE = MergeTree\nORDER BY (country_code, station_id)\nINSERT INTO stations\nSELECT\n    station_id,\n    substring(station_id, 1, 2) AS country_code,\n    trimBoth(state) AS state,\n    name,\n    lat,\n    lon,\n    elevation\nFROM url('https://noaa-ghcn-pds.s3.amazonaws.com/ghcnd-stations.txt', Regexp, 'station_id String, lat Float64, lon Float64, elevation Float32, state String, name String')\nSETTINGS format_regexp = '^(.{11})\\\\s+(\\\\-?\\\\d{1,2}\\\\.\\\\d{4})\\\\s+(\\\\-?\\\\d{1,3}\\\\.\\\\d{1,4})\\\\s+(\\\\-?\\\\d*\\\\.\\\\d*)\\\\s+(.{2})\\\\s(.*?)\\\\s{2,}.*$'\n0 rows in set. Furthermore, the parent query can also utilize its primary key. The need to only read smaller ranges of these columns, and thus less data off the disk, offsets any join cost. As pointed out by members of our community, keeping the data denormalized is beneficial in this case.</p>\n<p>There is one issue here though - we are relying on the <code>location</code> and <code>name</code> being denormalized onto our weather data. The reason for this can be found in <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/join/#performance\">our documentation</a>.</p>\n<blockquote>\nWhen running a JOIN, there is no optimization of the order of execution in relation to other stages of the query. The join (a search in the right table) is run before filtering in WHERE and before aggregation.”\n</blockquote>\n<p>The documentation also suggests dictionaries as a possible solution. Let's now demonstrate how we can improve this query performance using a dictionary now that the data is normalized.</p>\n<h2 id=\"creating-a-dictionary\"></h2>\n<p>Dictionaries provide us with an in-memory key-value pair representation of our data, optimized for low latent lookup queries. We can utilize this structure to improve the performance of queries in general, with JOINs particularly benefiting where one side of the JOIN represents a look-up table that fits into memory.</p>\n<h3 id=\"choosing-a-source-and-key\"></h3>\n<p>In ClickHouse Cloud, the dictionary itself can currently be populated from two sources: local ClickHouse tables and HTTP URLs*. The dictionary's contents can then be configured to reload periodically to reflect any changes in the source data.</p>\n<blockquote>\n* We anticipate expanding this in the future to include support for other sources supported in OSS.\n</blockquote>\n<p>Below we create our dictionary using the <code>stations</code> table as the source.</p>\n<pre><p>\nCREATE DICTIONARY stations_dict\n(\n `station_id` String,\n `state` String,\n `country_code` String,\n `name` String,\n `lat` Float64,\n `lon` Float64,\n `elevation` Float32\n)\nPRIMARY KEY station_id\nSOURCE(CLICKHOUSE(TABLE 'stations'))\nLIFETIME(MIN 0 MAX 0)\nLAYOUT(complex_key_hashed_array())\n</p>\n</pre>\n<p>The <code>PRIMARY KEY</code> here is the <code>station_id</code> and intuitively represents the column on which lookups will be performed. Values must be unique, i.e., rows with the same primary key will be deduplicated. The other columns represent attributes. You may notice that we have separated our location into <code>lat</code> and <code>lon</code> as the <code>Point</code> type is not currently supported as an attribute type for dictionaries. The <code>LAYOUT</code> and <code>LIFETIME</code> are less obvious and need some explanation.\nNote: In ClickHouse Cloud, the dictionary will automatically be created on all nodes. For OSS, this behavior is possible if using a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/database-engines/replicated/\">Replicated</a> database. Other configurations will require the creation of the dictionary on all nodes manually or through the use of the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/distributed-ddl\">ON CLUSTER</a> clause.</p>\n<h3 id=\"choosing-a-layout\"></h3>\n<p>The layout of a dictionary controls how it is stored in memory and the indexing strategy for the primary key. Each of the layout options has different pros and cons.</p>\n<p>The <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-layout/#flat\"><code>flat</code></a> type allocates an array with as many entries as the largest key value, e.g., if the largest value is 100k, the array will also have 100k entries. This is well suited to cases where you have a monotonically increasing primary key in your source data. In this case, it is very memory-compact and provides access speeds 4-5x faster than the hash-based alternatives - a simple array offset lookup is required. However, it is limited in that the key size can also not exceed 500k - although this is configurable via the setting <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-layout/#flat\"><code>max_array_size</code></a>. It is also inherently less efficient on large sparse distributions, wasting memory in such cases.</p>\n<p>For cases where you have a very large number of entries, large key values, and/or a sparse distribution of values, then <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-layout/#flat\"><code>flat</code></a> layout becomes less optimal. At this point, we would typically recommend a hash-based dictionary - specifically the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-layout/#dicts-external_dicts_dict_layout-hashed-array\"><code>hashed_array</code></a> dictionary, which can efficiently support millions of entries. This layout is more memory efficient than the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-layout/#dicts-external_dicts_dict_layout-hashed\"><code>hashed</code></a> layout and almost as fast. For this type, a hash table structure is used to store the primary key, with values providing offset positions into the attribute-specific arrays. This is in contrast <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-layout/#dicts-external_dicts_dict_layout-hashed\"><code>hashed</code></a> layout, which, although a little faster, requires a hash table to be allocated for each attribute - thus consuming more memory. In most cases, we, therefore, recommend the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-layout/#dicts-external_dicts_dict_layout-hashed-array\"><code>hashed_array</code></a> layout - although users should experiment with <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-layout/#dicts-external_dicts_dict_layout-hashed\"><code>hashed</code></a> if they have only a few attributes.</p>\n<p>All of these types also require the keys to be castable to UInt64. If not, e.g., they are Strings, we can use the complex variants of the hashed dictionaries: <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-layout/#complex-key-hashed\"><code>complex_key_hashed</code></a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-layout/#complex-key-hashed-array\"><code>complex_key_hashed_array</code></a>, following the same rules above otherwise.</p>\n<p>We try to capture the above logic with a flow chart below to help you choose the right layout (most of the time):</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/choosing_layout_c187d7c55d.png\">\n         <span><img alt=\"choosing_layout.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fchoosing_layout_c187d7c55d.png&w=2048&q=75\"></span>\n</a></p><p>For our data, where our primary key is the String <code>country_code</code>, we choose the <code>complex_key_hashed_array</code> type since our dictionaries have at least three attributes in each case.</p>\n<p>Note: We also have sparse variants of the <code>hashed</code> and <code>complex_key_hashed</code> layouts. This layout aims to achieve constant time operations by splitting the primary key into groups and incrementing a range within them. We rarely recommend this layout, which is only efficient if you have only one attribute. Although operations are constant time, the actual constant is typically higher than the non-sparse variants. Finally, ClickHouse offers specialized layouts such as <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-polygon/\">polygon</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-layout#ip_trie\">ip_trie</a>. We explored the former in the <a target=\"_blank\" href=\"https://clickhouse.com/blog/real-world-data-noaa-climate-data\">original blog</a>, and will save others for future posts since they represent more advanced use cases.</p>\n<h3 id=\"choosing-a-lifetime\"></h3>\n<p>Our above dictionary DDL also highlights the need to specify a <code>LIFETIME</code> for our dictionary. This specifies how often the dictionary should be refreshed by re-reading the source. This is specified in either seconds or as a range, e.g., <code>LIFETIME(300)</code> or <code>LIFETIME(MIN 300 MAX 360)</code>. In the latter case, a value will choose a random time, uniformly distributed in the range. This ensures the load on the dictionary source is distributed over time when multiple servers are updating. The value <code>LIFETIME(MIN 0 MAX 0)</code>, used in our example, means the dictionary contents will never be updated - appropriate in our case as our data is static.</p>\n<p>If your data is changing and you need to reload the data periodically, this behavior can be controlled through an <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-lifetime\">invalidate_query</a> parameter which returns a row. If the value of this row changes between update cycles, ClickHouse knows the data must be re-fetched. This could, for example, return a timestamp or row count. Further options exist for ensuring only the data has changed since the previous update is loaded - see our <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts-dict-lifetime\">documentation</a> for examples of using the <code>update_field</code>.</p>\n<h2 id=\"using-a-dictionary\"></h2>\n<p>Although our dictionary has been created, it requires a query to load the data into memory. The easiest ways to do this are to issue a simple <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/ext-dict-functions/#dictget-dictgetordefault-dictgetornull\"><code>dictGet</code></a> query to retrieve a single value (loading the dataset into the dictionary as a by-product) or by issuing an explicit <code>SYSTEM RELOAD DICTIONARY</code> command.</p>\n<pre><p>\nSYSTEM RELOAD DICTIONARY stations_dict\n0 rows in set. Elapsed: 0.561 sec.\nSELECT dictGet(stations_dict, 'state', 'CA00116HFF6')\n┌─dictGet(stations_dict, 'state', 'CA00116HFF6')─┐\n│ BC                                             │\n└────────────────────────────────────────────────┘\n1 row in set. Elapsed: 0.001 sec.\n</p><a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=CSFKIYZ88AJGRHVNXRYYI3\">✎</a>\n</pre>\n<p>The <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/ext-dict-functions/#dictget-dictgetordefault-dictgetornull\"><code>dictGet</code></a> example above retrieves the <code>station_id</code> value for the country code <code>PO</code>.</p>\n<p>Returning to our original join query, we can restore our subquery and utilise the dictionary only for our location and name fields.</p>\n<pre><p>\nSELECT\n    tempMax / 10 AS maxTemp,\n    station_id,\n    date,\n    (dictGet(stations_dict, 'lat', station_id), dictGet(stations_dict, 'lon', station_id)) AS location,\n    dictGet(stations_dict, 'name', station_id) AS name\nFROM noaa\nWHERE station_id IN (\n    SELECT station_id\n    FROM stations\n    WHERE country_code = 'PO'\n)\nORDER BY tempMax DESC\nLIMIT 5\n┌─maxTemp─┬─station_id──┬───────date─┬─location──────────┬─name───────────┐\n│    45.8 │ PO000008549 │ 1944-07-30 │ (40.2,-8.4167)    │ COIMBRA        │\n│    45.4 │ PO000008562 │ 2003-08-01 │ (38.0167,-7.8667) │ BEJA           │\n│    45.2 │ PO000008562 │ 1995-07-23 │ (38.0167,-7.8667) │ BEJA           │\n│    44.5 │ POM00008558 │ 2003-08-01 │ (38.533,-7.9)     │ EVORA/C. COORD │\n│    44.2 │ POM00008558 │ 2022-07-13 │ (38.533,-7.9)     │ EVORA/C. COORD │\n└─────────┴─────────────┴────────────┴───────────────────┴────────────────┘\n5 rows in set. Elapsed: 0.012 sec. Processed 522.48 thousand rows, 6.64 MB (44.90 million rows/s., 570.83 MB/s.)\n</p> <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=2APN6W2QFMGF4EVYIMWCC3\">✎</a>\n</pre>\n<p>Now that's better! The key here is we are able to exploit the subquery optimization, benefiting from it utilizing its <code>country_code</code> primary key. The parent query is then able to restrict the <code>noaa</code> table read to only those returned station ids, again exploiting its primary key to minimize the data read. Finally, the <code>dictGet</code> is only needed for the final 5 rows to retrieve the <code>name</code> and <code>location</code>. We visualize this below:</p>\n<p><span><img alt=\"dictionary_lookup_speed.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fdictionary_lookup_speed_c145181747.png&w=2048&q=75\"></span></p>\n<p>An experienced dictionary user might be tempted to try other approaches here. We could, for example:</p>\n<ul>\n<li>Drop the sub-query and utilise a <code>dictGet(stations_dict, 'country_code', station_id) = 'PO'</code> filter. This <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=NJM1DPH69PXZYW6XA5TUKX\">isn't faster</a> (around 0.5s) as a dictionary look-up needs to be made for each station. We look at a similar example to this below.</li>\n<li>Exploit the fact that dictionaries can be used in JOIN clauses like tables (see below). Sorting this join by geoDistance and restricting the results to those where the distance is less than 20km, we select the top result per resort and sort this by total snow.
