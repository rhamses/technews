In our previous post, we showed the basics of loading a Hacker News dataset. As well as demonstrating the power of schema inference to a getting-started user, we also highlighted the need to define a schema for efficient query execution. Before delving into more complex topics such as schema optimization and primary key selection, we exploit the fact that the Hacker News dataset is distributed as JSON to take a small detour and explore the recently added JSON capabilities of ClickHouse.</p>\n<p>The JSON file format has become ubiquitous for encoding datasets, such as structured logs, due to its human-readable, self-describing format. ClickHouse has become an increasingly popular data store to analyze logs and events encoded in JSON. The JSON data type enhances existing JSON capabilities by allowing columns to be automatically inferred and created from the data, i.e. there is no requirement beyond declaring a column as “JSON”. This allows ClickHouse to deal with dynamic schemas where new columns are added and removed continuously. In this post, we demonstrate these capabilities through the Hacker News dataset.</p>\n<p>While the examples below are executed using <a target=\"_blank\" href=\"https://clickhouse.cloud/signUp\">ClickHouse Cloud</a>, all commands will also be compatible with self-managed ClickHouse clusters running on the average laptop with internet access. Our client is hosted on a <a target=\"_blank\" href=\"https://aws.amazon.com/ec2/instance-types/c5/\">c5ad.4xlarge</a> with 16 cores and 32GB of RAM.</p>\n<p>The JSON data type is still experimental within ClickHouse as of version 22.8. This feature is therefore not ready for production use. Users are encouraged to experiment and provide feedback as we move to a production-ready state.</p>\n<h2 id=\"download\"></h2>\n<p>Our examples all access the file via the url function and do not require the user to download the dataset explicitly. The JSON version of the dataset can, however, be downloaded from here for more curious readers. At 4.9GB, and 28m rows, this compressed file should take 5-10 minutes to download.</p>\n<h2 id=\"reading-json\"></h2>\n<p>Our Hacker News data is effectively ndjson, with one JSON row per line. This equates to the ClickHouse JSONEachRow format. Using the DESCRIBE command, we can inspect the types assigned by schema inference before sampling a row.</p>\n<pre><p>\nDESCRIBE TABLE url('https://datasets-documentation.s3.eu-west-3.amazonaws.com/hackernews/hacknernews.json.gz', 'JSONEachRow');\n┌─name────────┬─type─────────────────────|\n│ id          │ Nullable(Float64)        │\n│ deleted     │ Nullable(Float64)        │\n│ type        │ Nullable(String)         │\n│ by          │ Nullable(String)         │\n│ time        │ Nullable(String)         │\n│ text        │ Nullable(String)         │\n│ dead        │ Nullable(Float64)        │\n│ parent      │ Nullable(Float64)        │\n│ poll        │ Nullable(Float64)        │\n│ kids        │ Array(Nullable(Float64)) │\n│ url         │ Nullable(String)         │\n│ score       │ Nullable(Float64)        │\n│ title       │ Nullable(String)         │\n│ parts       │ Array(Nullable(Float64)) │\n│ descendants │ Nullable(Float64)        │\n└─────────────┴──────────────────────────|\n</p>\n</pre>\n<pre><p>\nSELECT *\nFROM url('https://datasets-documentation.s3.eu-west-3.amazonaws.com/hackernews/hacknernews.json.gz', JSONEachRow)\nLIMIT 1\nFORMAT Vertical;\nRow 1:\n──────\nid:          11132929\ndeleted:     0\ntype:        story\nby:          brakmic\ntime:        2016-02-19 11:40:55\ntext:\ndead:        1\nparent:      0\npoll:        0\nkids:        [11133170]\nurl:         https://www.washingtonpost.com/news/morning-mix/wp/2016/02/18/s-f-tech-bro-writes-open-letter-to-mayor-i-shouldnt-have-to-see-the-pain-struggle-and-despair-of-homeless-people/\nscore:       3\ntitle:       SF ‘tech bro’ writes to mayor: ‘I shouldn’t have to see the despair of homeless’\nparts:       []\ndescendants: 0\n</p>\n</pre>\n<p>Readers of our <a target=\"_blank\" href=\"https://clickhouse.com/blog/getting-data-into-clickhouse-part-1\">previous blog post in this series</a> will notice this isn’t significantly different from our CSV example - Note how we can also request our output to be returned in JSON by reusing the format JSONEachRow. The key observation is that the post column is assigned the new type <code>Object('json')</code>.</p>\n<h2 id=\"json-as-objects\"></h2>\n<p>Above, we introduced the <code>Object(‘json’)</code> type to represent a JSON row. Assuming we map our Hacker News rows to this type, our schema definition becomes trivial. This is the true power of this type. Our data is now treated as semi-structured, and any sub-columns will automatically be created and their types inferred from the data!</p>\n<pre><p>\nDROP TABLE IF EXISTS hackernews;\nSET allow_experimental_object_type = 1;\nCREATE TABLE hackernews\n(\n   `post` JSON\n)\nENGINE = MergeTree\nORDER BY tuple();\n</p>\n</pre>\n<p>A few important observations here. We use the JSON type as an abbreviation for <code>Object('JSON')</code> - in the future, we may add additional Object representations beyond JSON. Secondly, we are required to set <code>allow_experimental_object_type = 1</code> to use this type since it is experimental. Finally, note that we can’t utilize any sub-columns of post as primary keys and thus have defined our <code>ORDER BY as tuple()</code>, i.e., no primary key. We address this limitation later.</p>\n<p>With this table created, insertion becomes trivial.</p>\n<pre><p>\nINSERT INTO hackernews SELECT post\nFROM url('https://datasets-documentation.s3.eu-west-3.amazonaws.com/hackernews/hacknernews.json.gz', 'JSONAsObject', 'post JSON')\n0 rows in set. As of 22.8, type inference works for numeric and strings: with the former being assigned the minimal bit representation possible based on the observed data.</p>\n<h2 id=\"querying-json\"></h2>\n<p>Querying our columns within each row requires us to use dot representation to indicate field paths in the JSON. We can’t specify codecs for sub-columns for similar reasons. To overcome this restriction, we recommend users use the JSON type for the semi-structured parts of rows that are subject to change but explicitly specify columns for those for which a reliable structure and type can be declared. For example, below, we explicitly define the time and type columns but leave the others to be captured by the post column. This, in turn, allows us to define these as components of the primary key.</p>\n<pre><p>\nSET allow_experimental_object_type = 1;\nDROP TABLE IF EXISTS hackernews;\nCREATE TABLE hackernews\n(\n   `post` JSON,\n   `type` String,\n   `time` DateTime\n)\nENGINE = MergeTree ORDER BY (time, type);\n</p>\n</pre>\n<p>To insert data we need to use the format JSONAsString which interprets each row as a single JSON string. This allows the use of the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/json-functions/\">JSONExtract* </a>functions for extracting specific fields. Future releases of ClickHouse will support these functions with JSONAsObject. We include the optional <code>post String</code> component of the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/table-functions/url/\">url</a> function for clarity. If excluded, ClickHouse will infer a column <code>json</code>.</p>\n<pre><p>\nINSERT INTO hackernews SELECT\n   post::JSON,\n   JSONExtractString(post, 'type') AS type,\n   toDateTime(JSONExtractString(post, 'time')) AS time\nFROM url('https://datasets-documentation.s3.eu-west-3.amazonaws.com/hackernews/hacknernews.json.gz', 'JSONAsString', 'post String')\n0 rows in set. Elapsed: 335.605 sec. Processed 28.74 million rows, 16.24 GB (85.63 thousand rows/s., 48.38 MB/s.)\n</p>\n</pre>\n<p>Repeating the earlier query, and adjusting for our field names, demonstrates the performance benefit of managing our structured fields separately and using them in the primary key (notice the speed up!).</p>\n<pre><p>\nSELECT\n   toYYYYMM(time) AS monthYear,\n   bar(count(), 0, 120, 20)\nFROM hackernews\nWHERE (type IN ('story', 'comment')) AND ((post.title ILIKE '%ClickHouse%') OR (post.text ILIKE '%ClickHouse%')) AND (monthYear &gt; '201908')\nGROUP BY monthYear\nORDER BY monthYear ASC\n// omitted for brevity\n26 rows in set. For numeric types, we aim to minimize resource utilization (disk and memory) by assigning the lowest bit representation possible. However, should a new value arrive which requires this to be extended, the type will transparently change. For example, suppose we receive an update of our data, and a new column “likes” has been added to represent equivalent functionality added to Hacker News.</p>\n<p>If we insert a single comment with 2 likes, our new column will be initially represented as an Int8.</p>\n<pre><p>\nINSERT INTO hackernews(post, type, time) FORMAT JSONEachRow 11:48:08\"};\n</p>\n</pre>\n<pre><p>\nDESCRIBE TABLE hackernews\nFORMAT Vertical\nSETTINGS describe_extend_object_types = 1\nQuery id: c1a80073-b5c3-48c1-aa77-7cef5f3eb2d1\nRow 1:\n──────\nname:               post\ntype:               Tuple(by String, dead Int8, deleted Int8, descendants Int16, id Int32, kids Array(Int32), likes Int8, parent Int32, parts Array(Int32), poll Int32, score Int16, text String, time String, title String, type String, url String)\ndefault_type:\ndefault_expression:\ncomment:\ncodec_expression:\nttl_expression:\n</p>\n</pre>\n<p>However, suppose a 2nd comment receives impacts queries. However, if the value is sent as a string (e.g. due to a single “dirty” document), it will transparently convert the column to a String type.
