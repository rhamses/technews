contentHtml: "<article><div><p>If you work with ClickHouse regularly, you usually need two things: a clean local setup and a way to manage Cloud services from the terminal. clickhousectl gives you both in one place. It handles local version management, isolated servers, project scaffolding, and ClickHouse Cloud operations without sending you off to a pile of shell scripts.</p>\n<p>Install it:</p>\n<div><pre><code><span>curl https://clickhouse.com/cli | sh</span></code></pre></div>\n<p>The installer detects your OS and architecture, drops the binary at <code>~/.local/bin/clickhousectl</code>, and creates a <code>chctl</code> alias. Check it's on your path:</p>\n<div><pre><code><span>chctl --version</span></code></pre></div>\n<h2 id=\"bootstrap-a-project\"></h2>\n<p>Install a ClickHouse version and mark it active:</p>\n<div><pre><code><span>chctl <span>local</span> use stable</span></code></pre></div>\n<p>This grabs the latest stable release if you don't already have it and sets it as the active version. Binaries live in <code>~/.clickhouse/versions/</code> and are shared across every project on the machine, so you're not re-downloading ClickHouse each time. Check what you're on:</p>\n<div><pre><code><span>chctl <span>local</span> <span>which</span></span>\n<span></span>\n<span>26.2.8.7 (stable)</span></code></pre></div>\n<p>To list what's installed locally, or see everything available upstream:</p>\n<div><pre><code><span>chctl <span>local</span> list</span>\n<span>chctl <span>local</span> list --remote</span></code></pre></div>\n<p>Pin a specific release when you need to:</p>\n<div><pre><code><span>chctl <span>local</span> use 26.3</span></code></pre></div>\n<p>Now make a directory for the project and drop into it. The scaffolded layout, the named server's data directory, and the SQL files are all scoped to whichever directory you run <code>chctl</code> from, so pick a home for it up front:</p>\n<div><pre><code><span><span>mkdir</span> events-pipeline &amp;&amp; <span>cd</span> events-pipeline</span></code></pre></div>\n<p>Scaffold the layout:</p>\n<div><pre><code><span>chctl <span>local</span> init</span>\n<span></span>\n<span>clickhouse/</span>\n<span>├── tables/              <span># CREATE TABLE statements</span></span>\n<span>├── materialized_views/  <span># Materialized view definitions</span></span>\n<span>├── queries/             <span># Saved analytical queries</span></span>\n<span>└── seed/                <span># Test data (CSVs or INSERT scripts)</span></span></code></pre></div>\n<p>A sensible standard layout helps humans and agents alike keep track of what's going on. Keep <code>tables/</code> and <code>materialized_views/</code> as your schema source of truth, drop day-to-day queries into <code>queries/</code>, and use <code>seed/</code> for anything you need to load during development.</p>\n<p>Write a table to <code>clickhouse/tables/events.sql</code>:</p>\n<div><pre><code><span><span>CREATE TABLE</span> IF <span>NOT</span> <span>EXISTS</span> events</span>\n<span>(</span>\n<span>    <span>timestamp</span> DateTime,</span>\n<span>    user_id   UInt64,</span>\n<span>    event     LowCardinality(String),</span>\n<span>    properties String</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree()</span>\n<span><span>ORDER</span> <span>BY</span> (event, <span>timestamp</span>)</span></code></pre></div>\n<p>Start a named server and apply it:</p>\n<div><pre><code><span>chctl <span>local</span> server start --name dev</span>\n<span>chctl <span>local</span> client --name dev --queries-file clickhouse/tables/events.sql</span></code></pre></div>\n<p>This gives you an isolated instance with its own data directory at <code>.clickhouse/servers/dev/data/</code>. Run as many named servers as you want; they don't share state.</p>\n<p>Seed some rows. Write to <code>clickhouse/seed/events.sql</code>:</p>\n<div><pre><code><span><span>INSERT INTO</span> events <span>VALUES</span></span>\n<span>    (now(), <span>1</span>, <span>'page_view'</span>, <span>'{\"page\": \"/pricing\"}'</span>),</span>\n<span>    (now(), <span>2</span>, <span>'signup'</span>, <span>'{\"plan\": \"cloud\"}'</span>),</span>\n<span>    (now(), <span>1</span>, <span>'page_view'</span>, <span>'{\"page\": \"/docs\"}'</span>);</span></code></pre></div>\n<p>Apply it and query:</p>\n<div><pre><code><span>chctl <span>local</span> client --name dev --queries-file clickhouse/seed/events.sql</span>\n<span>chctl <span>local</span> client --name dev --query <span>\"SELECT event, count() FROM events GROUP BY event\"</span></span>\n<span></span>\n<span>┌─event─────┬─count()─┐</span>\n<span>│ page_view │       2 │</span>\n<span>│ signup    │       1 │</span>\n<span>└───────────┴─────────┘</span></code></pre></div>\n<h2 id=\"manage-local-dev-servers\"></h2>\n<p>Named servers get more useful once you run multiple versions side by side. Spin up a second server alongside <code>dev</code>, but on a different release:</p>\n<div><pre><code><span>chctl <span>local</span> server start --name staging --version latest</span></code></pre></div>\n<p><code>--version</code> overrides your pinned version for this server only. <code>dev</code> keeps running on whatever <code>chctl local use stable</code> resolved to; <code>staging</code> runs on whatever <code>latest</code> resolves to right now. If that version isn't installed, <code>chctl</code> fetches it first.</p>\n<p>List them:</p>\n<div><pre><code><span>chctl <span>local</span> server list</span>\n<span>+---------+---------+-------+------------+-----------+----------+</span>\n<span>| Name    | Status  | PID   | Version    | HTTP Port | TCP Port |</span>\n<span>+---------+---------+-------+------------+-----------+----------+</span>\n<span>| dev     | running | 99493 | 26.2.8.7   | 8126      | 9003     |</span>\n<span>| staging | running | 98060 | 26.4.1.997 | 8128      | 9007     |</span>\n<span>+---------+---------+-------+------------+-----------+----------+</span>\n<span></span>\n<span>2 servers, 2 running</span></code></pre></div>\n<p>This is the pattern for upgrade testing: keep <code>dev</code> on the version you run in production, point <code>staging</code> at the one you're evaluating, and apply the same schema files to both. If something breaks, you find out before the upgrade.</p>\n<p>Ports auto-assign when the defaults are taken, so you don't have to manage them yourself.</p>\n<p>Apply the same schema files to the new server:</p>\n<div><pre><code><span>chctl <span>local</span> client --name staging --queries-file clickhouse/tables/events.sql</span></code></pre></div>\n<p>And run any saved query against whichever server you pick:</p>\n<div><pre><code><span>chctl <span>local</span> client --name staging --queries-file clickhouse/queries/daily_events.sql</span></code></pre></div>\n<p>Stop a server when you're done:</p>\n<div><pre><code><span>chctl <span>local</span> server stop staging</span></code></pre></div>\n<p>Or delete it and its data directory entirely:</p>\n<div><pre><code><span>chctl <span>local</span> server remove staging</span></code></pre></div>\n<h2 id=\"connect-to-clickhouse-cloud\"></h2>\n<p>Every command you've seen so far has a Cloud equivalent.</p>\n<p>Cloud auth is split in two by design. Browser-based OAuth gets you read-only access. Anything that mutates state (creating services, scaling them, applying schema changes) requires explicit API key authentication.</p>\n<p>The split exists because <code>chctl</code> is a tool an agent can drive. Getting an API key requires a deliberate step in the Cloud console, which forces the question: do I actually want to give this CLI (and by extension, whatever's running it) write access to my Cloud account?</p>\n<p>Authenticate for read-only access:</p>\n<div><pre><code><span>chctl cloud auth login</span></code></pre></div>\n<p>OAuth opens in your browser; the token is cached locally after. If you belong to more than one Cloud organisation, list them and pick one:</p>\n<div><pre><code><span>chctl cloud org list</span>\n<span>+-------------------+--------------+</span>\n<span>| Name              | ID           |</span>\n<span>+-------------------+--------------+</span>\n<span>| CLICKHOUSECTL_CLI | 5fae43a3-... |</span>\n<span>+-------------------+--------------+</span></code></pre></div>\n<p>With a single org, <code>chctl</code> auto-selects it and you can skip this step. With multiple, pass <code>--org-id</code> to scope commands:</p>\n<div><pre><code><span>chctl cloud service list --org-id 5fae43a3-xxxx-xxxx-xxxx-6e139718b9a3</span>\n<span></span>\n<span>+------+----------+---------+----------+-----------+--------------+</span>\n<span>| Name | ID       | State   | Provider | Region    | Endpoint     |</span>\n<span>+------+----------+---------+----------+-----------+--------------+</span>\n<span>| blog | c04e...  | running | aws      | us-east-1 | xyz...cloud  |</span>\n<span>+------+----------+---------+----------+-----------+--------------+</span></code></pre></div>\n<p>For anything that writes, generate an API key in the <a target=\"_blank\" href=\"https://clickhouse.cloud/\">Cloud console</a> and authenticate with it:</p>\n<div><pre><code><span>chctl cloud auth login --api-key &lt;key&gt; --api-secret &lt;secret&gt;</span></code></pre></div>\n<p>Or set <code>CLICKHOUSE_API_KEY</code> and <code>CLICKHOUSE_API_SECRET</code> as environment variables and <code>chctl</code> will pick them up automatically. API keys are scoped to a single org at creation time, so <code>--org-id</code> isn't needed once you're authenticated this way. Stay tuned for improvements to the auth flow.</p>\n<p>With write access, create a service:</p>\n<div><pre><code><span>chctl cloud service create --provider aws --region us-east-1 --name getting_started</span>\n<span></span>\n<span>Service created successfully!</span>\n<span></span>\n<span>Service: getting_started</span>\n<span>  ID: c04e0b96-xxxx-xxxx-xxxx-a91717ae4906</span>\n<span>  State: provisioning</span>\n<span>  Provider: aws</span>\n<span>  Region: us-east-1</span>\n<span>  Replicas: 3</span>\n<span>  Min Memory/Replica: 16 GB</span>\n<span>  Max Memory/Replica: 120 GB</span>\n<span>  Host: xyz.us-east-1.aws.clickhouse.cloud</span>\n<span>  Port: 9440</span>\n<span></span>\n<span>Credentials (save these, password shown only once):</span>\n<span>  Username: default</span>\n<span>  Password: xyz</span></code></pre></div>\n<p>Save the password somewhere you can retrieve it. It's not shown again.</p>\n<p>Scaling works the same way. Pass only what you want to change. No need to restate every parameter:</p>\n<div><pre><code><span>chctl cloud service scale c04e0b96-xxxx-xxxx-xxxx-a91717ae4906 --num-replicas 4</span>\n<span></span>\n<span>Service getting_started scaling updated</span>\n<span>  Replicas: 4</span></code></pre></div>\n<p>Apply the schema files you developed locally:</p>\n<div><pre><code><span>chctl cloud service client --name getting_started --queries-file clickhouse/tables/events.sql --user default --password xyz</span></code></pre></div>\n<h2 id=\"develop-with-an-ai-agent\"></h2>\n<p><code>chctl</code> ships agent skills for coding assistants. To install the Claude Code set:</p>\n<div><pre><code><span>chctl skills --agent claude</span></code></pre></div>\n<p>Three skills land in <code>.claude/skills/</code>:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://github.com/ClickHouse/agent-skills/tree/main/skills/clickhouse-best-practices\"><code>clickhouse-best-practices</code></a>: 28 rules covering schema design, query optimisation, and inserts. Keeps the agent honest about primary keys, data types, JOINs, and partitioning.</li>\n<li><a target=\"_blank\" href=\"https://github.com/ClickHouse/agent-skills/tree/main/skills/clickhousectl-local-dev\"><code>clickhousectl-local-dev</code></a>: how to manage versions, scaffold projects, start servers, write schemas, and seed data with <code>chctl</code>.</li>\n<li><a target=\"_blank\" href=\"https://github.com/ClickHouse/agent-skills/tree/main/skills/clickhousectl-cloud-deploy\"><code>clickhousectl-cloud-deploy</code></a>: Cloud authentication, service creation, schema migration from local, and application connection config.</li>\n</ul>\n<p>With these loaded, a prompt like:</p>\n<blockquote>\n<p>Set up a ClickHouse project for tracking web analytics events. I want to store page views, sessions, and conversions.</p>\n</blockquote>\n<p>gets the agent to pick up <code>clickhousectl-local-dev</code>, where it will do something like:</p>\n<ul>\n<li>install a ClickHouse version</li>\n<li>scaffold the project</li>\n<li>start a dev server</li>\n<li>write out files like <code>clickhouse/tables/page_views.sql</code>, <code>sessions.sql</code>, and <code>conversions.sql</code></li>\n<li>seed data</li>\n<li>run verification</li>\n</ul>\n<p>Follow up with:</p>\n<blockquote>\n<p>Push this to ClickHouse Cloud. Create a service in AWS us-east-1.</p>\n</blockquote>\n<p>and it switches to <code>clickhousectl-cloud-deploy</code>: <code>cloud auth login</code>, <code>cloud service create</code>, then <code>cloud service client --queries-file</code> against the same SQL files it just wrote locally. The local project is the source of truth. Cloud is just another target.</p>\n<h2 id=\"use-clickhousectl-in-ci-cd\"></h2>\n<p><code>chctl</code> is a static binary with JSON output and env-var auth, so it drops into pipelines without a lot of wrapper scripting.</p>\n<p>Here's a GitHub Actions workflow that spins up ClickHouse, applies your schema, and runs test queries on every push:</p>\n<div><pre><code><span><span>name:</span> <span>Schema</span> <span>validation</span></span>\n<span><span>on:</span> [<span>push</span>]</span>\n<span></span>\n<span><span>env:</span></span>\n<span>  <span>CLICKHOUSE_VERSION:</span> <span>\"26.3\"</span></span>\n<span></span>\n<span><span>jobs:</span></span>\n<span>  <span>validate:</span></span>\n<span>    <span>runs-on:</span> <span>ubuntu-latest</span></span>\n<span>    <span>steps:</span></span>\n<span>      <span>-</span> <span>uses:</span> <span>actions/checkout@v4</span></span>\n<span></span>\n<span>      <span>-</span> <span>name:</span> <span>Install</span> <span>clickhousectl</span></span>\n<span>        <span>run:</span> <span>curl</span> <span>https://clickhouse.com/cli</span> <span>|</span> <span>sh</span></span>\n<span></span>\n<span>      <span>-</span> <span>name:</span> <span>Install</span> <span>ClickHouse</span></span>\n<span>        <span>run:</span> <span>chctl</span> <span>local</span> <span>install</span> <span>${{</span> <span>env.CLICKHOUSE_VERSION</span> <span>}}</span></span>\n<span></span>\n<span>      <span>-</span> <span>name:</span> <span>Start</span> <span>server</span></span>\n<span>        <span>run:</span> <span>chctl</span> <span>local</span> <span>server</span> <span>start</span> <span>--name</span> <span>ci</span></span>\n<span></span>\n<span>      <span>-</span> <span>name:</span> <span>Apply</span> <span>schema</span></span>\n<span>        <span>run:</span> <span>|</span></span>\n<span><span>          for f in clickhouse/tables/*.sql; do</span></span>\n<span><span>            chctl local client --name ci --queries-file \"$f\"</span></span>\n<span><span>          done</span></span>\n<span><span></span></span>\n<span>      <span>-</span> <span>name:</span> <span>Run</span> <span>test</span> <span>queries</span></span>\n<span>        <span>run:</span> <span>|</span></span>\n<span><span>          for f in clickhouse/queries/test_*.sql; do</span></span>\n<span><span>            chctl local client --name ci --queries-file \"$f\"</span></span>\n<span><span>          done</span></span>\n<span><span></span></span>\n<span>      <span>-</span> <span>name:</span> <span>Stop</span> <span>server</span></span>\n<span>        <span>run:</span> <span>chctl</span> <span>local</span> <span>server</span> <span>stop</span> <span>ci</span></span></code></pre></div>\n<p>Pin <code>CLICKHOUSE_VERSION</code> to match production. Upgrade it in one place and CI validates your whole schema against the new release on the next push, which is most of the confidence you need before an upgrade.</p>\n<p>For Cloud writes from CI, set <code>CLICKHOUSE_API_KEY</code> and <code>CLICKHOUSE_API_SECRET</code> as secrets in your workflow and <code>chctl</code> picks them up automatically. Or pass them explicitly:</p>\n<div><pre><code><span>chctl cloud auth login --api-key <span>$CLICKHOUSE_API_KEY</span> --api-secret <span>$CLICKHOUSE_API_SECRET</span></span></code></pre></div>\n<p><code>--json</code> gives you machine-readable output for anything scripted downstream:</p>\n<div><pre><code><span>chctl cloud service list --json | jq <span>'.[0].id'</span></span></code></pre></div>\n<h2 id=\"what-s-next\"></h2>\n<p>clickhousectl is open source at <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhousectl\">github.com/ClickHouse/clickhousectl</a>. For the design thinking behind it, see <a target=\"_blank\" href=\"https://clickhouse.com/blog/introducing-clickhousectl-official-cli-for-clickhouse-local-and-cloud\">Introducing clickhousectl</a>.</p>\n<p>If you don't have a ClickHouse Cloud account yet, <a target=\"_blank\" href=\"https://clickhouse.cloud/\">sign up</a> and run the last two sections against a real service.</p></div></article>"
