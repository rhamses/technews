contentHtml: "<article><div><p><span><img alt=\"ClickHouse Delete Statement.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FClick_House_Delete_Statement_6fd661d851.png&w=2048&q=75\"></span></p>\n<p>As the world’s fastest database for real-time analytics, many ClickHouse workloads involve large amounts of data that is written once and not frequently modified (for example, telemetry events generated by IOT devices or customer clicks generated by an e-commerce website). While these are typically immutable, additional data sets critical to providing context during analytics (e.g., lookup tables with information based on device or customer ID) may require modifications.</p>\n<p>Historically there have been multiple approaches to updating and deleting data in ClickHouse, depending on your goals and performance requirements. The rest of this article describes each approach and its trade-offs, as well as some recent developments with Lightweight Deletes that address some common challenges. We recommend best practices and highlight some important considerations when considering an approach.</p>\n<p>Before proceeding, determine whether updates are the best way to solve your problem. For example, for infrequently changed data, versioning the data may be a better option. ClickHouse is the number one analytics database in terms of storage efficiency and query performance, so just saving multiple versions of data instead of updating may work better in many cases.</p>\n<h2 id=\"lightweight-deletes\"></h2>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/lightweght-delete/#lightweight-delete-internals\">Lightweight Deletes</a> represent the preferred and most efficient way to remove data from ClickHouse. Exposed via the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/lightweght-delete/#lightweight-delete-internals\"><code>DELETE FROM</code></a>  table syntax, users can specify a condition to remove specific rows as shown below:</p>\n<div><pre><code><span><span>DELETE</span> <span>FROM</span> <span>table</span> <span>WHERE</span> col1 <span>=</span> <span>'Hi'</span> <span>AND</span> col2 <span>=</span> <span>2</span></span></code></pre></div>\n<p>This operation is asynchronous by default unless the setting <code>mutations_sync</code> is set to 1 (see below). When executing the delete, ClickHouse saves a mask for each row, indicating whether it is deleted in a <code>_row_exists</code> column. Subsequent queries, in turn, exclude those deleted rows as shown below.</p>\n<p><span><img alt=\"lightweight_deletes_v2.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Flightweight_deletes_v2_b891b54446.png&w=2048&q=75\"></span></p>\n<p>Internally, ClickHouse orders data into parts, each containing column data files and indices.\nRegular merge cycles are responsible for combining (merging) and rewriting these parts. This ensures the number of files does not continue to grow as more data is inserted, keeping queries fast. These merges consider lightweight deletes, excluding those rows marked for deletion in the newly formed parts.</p>\n<p><span><img alt=\"lightweight-delete-merge(1).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Flightweight_delete_merge_1_a2519ab507.png&w=2048&q=75\"></span></p>\n<p>Released in 22.8, and still experimental as of the time of writing, lightweight deletes are on track to become production ready in one of the next releases. Until this time, the use of lightweight deletes requires setting <code>allow_experimental_lightweight_delete=true</code>.</p>\n<p>Users should be aware that by relying on normal background merge cycles, rows will only be eventually removed from the disk. While excluded from search results, the rows will reside on disk until their part is merged. The time taken for this to happen is not deterministic. This has a few implications:</p>\n<ul>\n<li>Space savings will not be as immediate as issuing a deletion through mutations - see below. Consider using mutations if space savings are critical, e.g., insufficient disk space.</li>\n<li>With no guarantees for removal, users with compliance requirements may wish to use mutations to ensure data is deleted.</li>\n</ul>\n<p>The cost of a lightweight delete operation depends on the number of matching rows in the WHERE clause and the current number of data parts. This operation will be most efficient when matching a small number of rows. Users should also be aware that Lightweight Deletes perform best on Wide parts, where the column data files are stored separately, vs. Compact parts, where a single file is used for all column data. The former allows the mask <code>_row_exists</code> to be stored as a separate file, thereby allowing it to be written independently of the other columns. Generally, compact parts will be formed after inserts. Once parts exceed a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree/#mergetree-data-storage\">certain size</a> (e.g., due to merging), the wide format is used. For most workloads, this shouldn’t be a concern.</p>\n<p>Finally, note that Lightweight Delete uses the same mutation queue and background threads we describe below. We recommend the documentation <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/lightweght-delete/#lightweight-delete-internals\">here</a> for further details on the internal implementation.</p>\n<h2 id=\"mutations\"></h2>\n<h3 id=\"updating-data-using-mutations\"></h3>\n<p>The easiest way to update data in the ClickHouse table is to use <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter/update/\">ALTER…UPDATE</a> statement.</p>\n<div><pre><code><span><span>ALTER TABLE</span> <span>table</span></span>\n<span>    <span>UPDATE</span> col1 <span>=</span> <span>'Hi'</span> <span>WHERE</span> col2 <span>=</span> <span>2</span></span></code></pre></div>\n<p>This query will update <code>col1</code> on the <code>table</code> table using a given filter.</p>\n<p>Unlike some databases, ClickHouse’s <code>ALTER UPDATE</code> statement is asynchronous by default. This means that the update occurs in the background and you will not get an instant effect on the table. This process of updating tables is called <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter/#mutations\">mutations</a>.</p>\n<p><span><img alt=\"mutation_01.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmutation_01_24b8cb7f88.png&w=2048&q=75\"></span></p>\n<p><strong>An important note here</strong> is that updating data is a heavy query because ClickHouse has to do a lot of work to optimize storage and processing. A mutation operation forces all data parts containing those rows to be deleted to be re-written, with the target rows excluded when forming the new part. This can cause considerable I/O and cluster overhead, so use this with caution or consider the alternatives discussed below.</p>\n<h3 id=\"deleting-data-using-mutations\"></h3>\n<p>Like updates, deletes are also possible with mutations and offer an alternative to Lightweight Deletes. In most cases, Lightweight Deletes are more appropriate for data removal due to the mutation cost of rewriting all columns. More specifically, unlike Lightweight Deletes, all columns are rewritten vs. just a <code>_row_exists</code> mask column.</p>\n<p>However, given the “eventual deletion of data from disk” property of Lightweight Deletes, users may prefer this mutation-based approach to achieve guaranteed disk space savings. Furthermore, this approach can be appropriate when users need to guarantee data removal from the disk, e.g., due to compliance reasons.</p>\n<div><pre><code><span><span>ALTER TABLE</span> <span>table</span></span>\n<span>    <span>DELETE</span> <span>WHERE</span> col2 <span>=</span> <span>3</span></span></code></pre></div>\n<p>In this query, all rows with <code>col2</code> value of <code>3</code> are deleted. Similar to other mutations, deletes are also asynchronous by default. This can be made synchronous using the same <code>mutations_sync</code> setting described above.</p>\n<h3 id=\"checking-mutation-progress\"></h3>\n<p>Since mutations run asynchronously, monitoring can be performed via the <code>system.mutations</code> table. This allows users to need to check their progress for a specific mutation on a table.</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    command,</span>\n<span>    is_done</span>\n<span><span>FROM</span> system.mutations</span>\n<span><span>WHERE</span> <span>table</span> <span>=</span> <span>'tablename'</span></span>\n<span></span>\n<span>┌─command───────────────────────────────┬─is_done─┐</span>\n<span>│ <span>UPDATE</span> col1 <span>=</span> <span>'Hi'</span> <span>WHERE</span> col2 <span>=</span> <span>2</span>     │       <span>1</span> │</span>\n<span>│ <span>UPDATE</span> col1 <span>=</span> <span>'All hi'</span> <span>WHERE</span> col2 <span>&gt;</span> <span>0</span> │       <span>0</span> │</span>\n<span>└───────────────────────────────────────┴─────────┘</span></code></pre></div>\n<p>If the value of <code>is_done</code> is <code>0</code> for a specific mutation, it’s still being executed. Mutations are executed for each table part where mutated parts become available instantly:</p>\n<p><span><img alt=\"mutation_progress.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmutation_progress_6523b90d1c.png&w=2048&q=75\"></span></p>\n<h3 id=\"synchronous-updates\"></h3>\n<p>For users requiring synchronous updates, the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings/#mutations_sync\">mutations_sync</a> parameter can be set to a value of <code>1</code> (or <code>2</code> if we also want to wait till all replicas are also updated):</p>\n<div><pre><code><span><span>SET</span> mutations_sync <span>=</span> <span>1</span></span></code></pre></div>\n<p>Now our update query will wait for the mutation to complete:</p>\n<div><pre><code><span><span>ALTER TABLE</span> <span>table</span></span>\n<span>    <span>UPDATE</span> col1 <span>=</span> <span>'bye'</span> <span>WHERE</span> col2 <span>&gt;</span> <span>0</span></span>\n<span></span>\n<span><span>0</span> <span>rows</span> <span>in</span> set. Elapsed: <span>1.182</span> sec.</span></code></pre></div>\n<p>Note how it took 1 second for this query to finish while ClickHouse waited for the background mutation to complete. Note this parameter also applies to Lightweight Deletes.</p>\n<h2 id=\"updating-an-entire-table\"></h2>\n<p>In some cases, users need to update the values of an entire column. Initially, users may try to achieve this by using the <code>ALTER TABLE</code> query without a <code>WHERE</code> clause. This, however, fails, as shown below:</p>\n<div><pre><code><span><span>ALTER TABLE</span> <span>table</span> <span>UPDATE</span> col1 <span>=</span> <span>'bye'</span>;</span>\n<span></span>\n<span>Syntax error: failed <span>at</span> position <span>38</span> (<span>end</span> <span>of</span> query):</span>\n<span><span>ALTER TABLE</span> <span>table</span> <span>UPDATE</span> col1 <span>=</span> <span>'bye'</span>;</span></code></pre></div>\n<p>ClickHouse won't let you update an entire table because updates are heavy. One way to force ClickHouse to accept this operation is with an always-true filter:</p>\n<div><pre><code><span><span>ALTER TABLE</span> <span>table</span></span>\n<span>    <span>UPDATE</span> col1 <span>=</span> <span>'bye'</span> <span>WHERE</span> <span>true</span></span></code></pre></div>\n<p>However, a more optimal approach is to create a new column with the new value as the default and then switch the old and new columns. For example:</p>\n<div><pre><code><span><span>ALTER TABLE</span> <span>table</span> <span>ADD</span> <span>COLUMN</span> col1_new String <span>DEFAULT</span> <span>'global hi'</span>;</span>\n<span></span>\n<span><span>ALTER TABLE</span> <span>table</span></span>\n<span>    RENAME <span>COLUMN</span> col1 <span>TO</span> col1_old,</span>\n<span>    RENAME <span>COLUMN</span> col1_new <span>TO</span> col1,</span>\n<span>    <span>DROP</span> <span>COLUMN</span> col1_old;</span></code></pre></div>\n<p>We use the default value of the <code>col1_new</code> column to specify what we want to use as the updated value. This is safe and much more efficient since we skip the heavy mutation operation here.</p>\n<h2 id=\"updating-and-deleting-using-joins\"></h2>\n<p>Sometimes, we need to delete or update rows based on relations; thus, we have to join tables. This is best achieved in ClickHouse using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/join/\">Join table engine</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/other-functions/#joinget\">joinGet</a> function. Suppose we have two tables - one with all pageviews and the other with all logins tracked:</p>\n<div><pre><code><span><span>CREATE TABLE</span> pageviews</span>\n<span>(</span>\n<span>    `user_id` UInt64,</span>\n<span>    `<span>time</span>` DateTime,</span>\n<span>    `session_id` UInt64</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> <span>time</span>;</span>\n<span></span>\n<span><span>CREATE TABLE</span> logins</span>\n<span>(</span>\n<span>    `user_id` UInt64,</span>\n<span>    `<span>time</span>` DateTime</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> <span>time</span>;</span></code></pre></div>\n<p>The difference between the tables is that the <code>logins</code> table only stores a single event per session. Suppose at some point in time, we decided to add the <code>session_id</code> column to the <code>logins</code> table:</p>\n<div><pre><code><span><span>ALTER TABLE</span> logins</span>\n<span>    <span>ADD</span> <span>COLUMN</span> `session_id` UInt64</span></code></pre></div>\n<p>We now need to update the <code>logins.session_id</code> column with corresponding values from the <code>pageviews</code> table using a JOIN on <code>user_id</code> and <code>time</code>:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> logins l.time)</span>\n<span></span>\n<span>┌─user_id─┬────────────────<span>time</span>─┬─p.user_id─┬──────────────p.time─┬─session_id─┐</span>\n<span>│       <span>2</span> │ <span>12</span>:<span>23</span>:<span>16</span> │ <span>2752888102</span> │</span>\n<span>│       <span>1</span> │ <span>2023</span><span>-01</span><span>-09</span> <span>13</span>:<span>23</span>:<span>16</span> │         <span>1</span> │ <span>2023</span><span>-01</span><span>-09</span> <span>13</span>:<span>23</span>:<span>16</span> │ <span>4135462640</span> │</span>\n<span>└─────────┴─────────────────────┴───────────┴─────────────────────┴────────────┘</span></code></pre></div>\n<p>First, we need to create and populate a special  <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/join/\"><code>Join</code></a> table:</p>\n<div><pre><code><span><span>CREATE TABLE</span> pageviews_join</span>\n<span>ENGINE <span>=</span> <span>Join</span>(<span>ANY</span>, <span>LEFT</span>, user_id, <span>time</span>) <span>AS</span></span>\n<span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> pageviews</span></code></pre></div>\n<p>This table will allow us to use the <code>joinGet</code> function to fetch values based on JOIN while executing an update query:</p>\n<div><pre><code><span><span>ALTER TABLE</span> logins</span>\n<span>    <span>UPDATE</span> session_id <span>=</span> joinGet(<span>'pageviews_join'</span>, <span>'session_id'</span>, user_id, <span>time</span>) <span>WHERE</span> session_id <span>=</span> <span>0</span></span></code></pre></div>\n<p>And we can see, the <code>logins</code> table was updated accordingly with the JOIN:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> logins</span>\n<span></span>\n<span>┌─user_id─┬────────────────<span>time</span>─┬─session_id─┐</span>\n<span>│ <span>TABLE</span> pageviews_join</span></code></pre></div>\n<p>The same approach can be used to delete data with lightweight or mutation based deletes.</p>\n<h2 id=\"deleting-large-blocks-efficiently\"></h2>\n<p>If we have to delete big blocks of data, users can partition a table so that partitions can be dropped as required. This is a lightweight operation. Suppose we have the following table:</p>\n<div><pre><code><span><span>CREATE TABLE</span> hits</span>\n<span>(</span>\n<span>    `project` String,</span>\n<span>    `url` String,</span>\n<span>    `<span>time</span>` DateTime,</span>\n<span>    `hits` UInt32</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>PARTITION</span> <span>BY</span> project</span>\n<span><span>ORDER</span> <span>BY</span> (project, path, <span>time</span>)</span></code></pre></div>\n<p>Having this table partitioned by the <code>project</code> column allows us to delete rows with a specific <code>project</code> value by dropping an entire partition. Let’s delete everything with <code>project</code> = <code>c</code>:</p>\n<div><pre><code><span><span>ALTER TABLE</span> hits</span>\n<span>    <span>DROP</span> <span>PARTITION</span> <span>'c'</span></span></code></pre></div>\n<p>Here, <code>c</code> is the <code>project</code> column value we want to delete:</p>\n<p><span><img alt=\"partition_delete.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpartition_delete_3ee4669374.png&w=2048&q=75\"></span></p>\n<p>The list of available partitions can be found in the <code>system.parts</code> table:</p>\n<div><pre><code><span><span>SELECT</span> <span>partition</span></span>\n<span><span>FROM</span> system.parts</span>\n<span><span>WHERE</span> <span>table</span> <span>=</span> <span>'hits'</span></span>\n<span></span>\n<span>┌─<span>partition</span>─┐</span>\n<span>│ c         │</span>\n<span>│ a         │</span>\n<span>│ b         │</span>\n<span>└───────────┘</span></code></pre></div>\n<p>We can also move partitions between tables (e.g., if we want to move data to a <code>trash</code> table instead of deleting it) using the DETACH and ATTACH statements.</p>\n<p>When setting up partitioning in your DDL, be aware of the common pitfall of partitioning by a column or expression with high cardinality. This can cause many parts to be created, leading to performance issues.</p>\n<h2 id=\"deleting-old-data-regularly\"></h2>\n<p>In cases of <a target=\"_blank\" href=\"https://docs.google.com/document/d/1CAmuBror9fGLZwFCiBUH5rt89LKq-ylA1Lpa6-FrJns/edit\">time-series data</a>, we might want to delete outdated data regularly. ClickHouse has the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-ttl\">TTL</a> feature for this exact use case. This requires configuring a table and specifying which data we want to be dropped and when. Suppose we want to delete data older than one month from our <code>hits</code> table:</p>\n<div><pre><code><span><span>ALTER TABLE</span> hits</span>\n<span>    MODIFY TTL <span>time</span> <span>+</span> <span>INTERVAL</span> <span>1</span> <span>MONTH</span></span></code></pre></div>\n<p>Here we ask ClickHouse to delete all rows that have a <code>time</code> column value more than one month ago from the current time. TTL can also be <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#mergetree-column-ttl\">set on columns</a> to reset their values to defaults after a period of time. This operation can be made more efficient by partitioning by date, rounded to an appropriate unit of time, e.g., days. ClickHouse will, in turn, automatically drop data in the most efficient way when executing a TTL rule. Again, tables should <strong>not</strong> be partitioned by time columns of high cardinality (e.g. millisecond granularity) to avoid high part counts. Typically partitioning by day or month is sufficient for most TTL operations.</p>\n<h2 id=\"deleting-and-updating-using-collapsingmergetree\"></h2>\n<p>If we have to update individual rows frequently, we can use the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/collapsingmergetree/\">CollapsingMergeTree</a> engine to efficiently manage data updates.</p>\n<p>Suppose we have a table with article stats to track each article's reading depth. We want a single row that shows how deeply each user has read each article. The challenge here is that we have to update the actual reading progress while the user reads an article. Let's create a table for our data:</p>\n<div><pre><code><span><span>CREATE TABLE</span> article_reads</span>\n<span>(</span>\n<span>    `user_id` UInt32,</span>\n<span>    `article_id` UInt32,</span>\n<span>    `read_to` UInt8,</span>\n<span>    `read_start` DateTime,</span>\n<span>    `read_end` DateTime,</span>\n<span>    `sign` Int8</span>\n<span>)</span>\n<span>ENGINE <span>=</span> CollapsingMergeTree(sign)</span>\n<span><span>ORDER</span> <span>BY</span> (read_start, article_id, user_id)</span></code></pre></div>\n<p>The special <code>sign</code> column is used for CollapsingMergeTree as a way to tell ClickHouse we want to update the specific row. If we insert <code>-1</code> for the <code>sign</code> column, the whole row is going to be deleted. If we insert a row with <code>sign = 1</code>, ClickHouse will keep the row. Rows to update are identified based on the sorting key used in the <code>ORDER BY ()</code> DDL statement when creating the table:</p>\n<p><span><img alt=\"collapsing_merge_tree.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fcollapsing_merge_tree_ceb2d258bb.png&w=2048&q=75\"></span></p>\n<p>To satisfy the deduplication condition on the sorting key, we have to insert the same value for the <code>read_start, article_id, user_id</code> columns to update a row. For example, when a user starts reading an article, we insert the following row:</p>\n<div><pre><code><span><span>INSERT INTO</span> article_reads</span>\n<span>            <span>VALUES</span>(<span>1</span>, <span>12</span>, <span>0</span>, now(), now(), <span>1</span>);</span></code></pre></div>\n<p>We now have a single row in the table:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> article_reads</span>\n<span></span>\n<span>┌─user_id─┬─article_id─┬─read_to─┬──────────read_start─┬────────────read_end─┬─sign─┐</span>\n<span>│       <span>1</span> │         <span>12</span> │       <span>0</span> │ <span>2023</span><span>-01</span><span>-06</span> <span>15</span>:<span>20</span>:<span>32</span> │ <span>2023</span><span>-01</span><span>-06</span> <span>15</span>:<span>20</span>:<span>32</span> │    <span>1</span> │</span>\n<span>└─────────┴────────────┴─────────┴─────────────────────┴─────────────────────┴──────┘</span></code></pre></div>\n<p>A minute later, when the user reaches 70% of our article, we insert the following 2 rows:</p>\n<div><pre><code><span><span>INSERT INTO</span> article_reads</span>\n<span>            <span>VALUES</span>(<span>1</span>, <span>12</span>, <span>0</span>, <span>'2023-01-06 15:20:32'</span>, now(), <span>-1</span>),</span>\n<span>                  (<span>1</span>, <span>12</span>, <span>70</span>, <span>'2023-01-06 15:20:32'</span>, now(), <span>1</span>);</span></code></pre></div>\n<p>The first row with <code>sign=-1</code> is used to tell ClickHouse it should delete the existing row (based on values in the ORDER BY tuple - <code>read_start</code>, <code>article_id</code> and <code>user_id</code> columns). The second inserted row (with <code>sign=1</code>) is the new row with the <code>read_to</code> column set to the new value of <code>70</code>.</p>\n<p>Since data updates are <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/collapsingmergetree/#table_engine-collapsingmergetree-collapsing-algorithm\">happening in the background</a>, with eventual consistency of results, we should filter on the <code>sign</code> column to get correct results:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    article_id,</span>\n<span>    user_id,</span>\n<span>    <span>max</span>(read_end),</span>\n<span>    <span>max</span>(read_to)</span>\n<span><span>FROM</span> article_reads</span>\n<span><span>WHERE</span> sign <span>=</span> <span>1</span></span>\n<span><span>GROUP</span> <span>BY</span></span>\n<span>    user_id,</span>\n<span>    article_id</span>\n<span></span>\n<span>┌─article_id─┬─user_id─┬───────<span>max</span>(read_end)─┬─<span>max</span>(read_to)─┐</span>\n<span>│         <span>12</span> │       <span>1</span> │ <span>2023</span><span>-01</span><span>-06</span> <span>15</span>:<span>21</span>:<span>59</span> │           <span>70</span> │</span>\n<span>└────────────┴─────────┴─────────────────────┴──────────────┘</span>\n<span></span>\n<span><span>1</span> <span>row</span> <span>in</span> set. Elapsed: <span>0.004</span> sec.</span></code></pre></div>\n<p>The <code>CollapsingMergreTree</code> engine will now take care of removing canceled rows from storage efficiently in the background, so we don’t have to delete them manually. You can find further examples of using the CollapsingMergeTree engine <a target=\"_blank\" href=\"https://www.google.com/url?q=https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/collapsingmergetree/%23example-of-use&sa=D&source=docs&ust=1678440218544759&usg=AOvVaw3vOSZ1Rbl24kvzHT48kuyp\">here</a>.</p>\n<h2 id=\"upserts-using-versioning-and-replacingmergetree\"></h2>\n<p>For more sophisticated cases, we might want to use versioning based on the  <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/replacingmergetree/\">ReplacingMergeTree</a> engine. This engine implements an efficient way of doing what’s known as <code>UPSERT</code> in other DBMSs, by using a special version column to track which rows should be removed. If multiple rows with the same sorting key are present, only the one with the largest version is kept in storage while others are removed:</p>\n<p><span><img alt=\"replacing_merge_tree.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Freplacing_merge_tree_a2a573138a.png&w=2048&q=75\"></span></p>\n<p>For our previous example with articles reading, we can use the following structure:</p>\n<div><pre><code><span><span>CREATE TABLE</span> article_reads</span>\n<span>(</span>\n<span>    `user_id` UInt32,</span>\n<span>    `article_id` UInt32,</span>\n<span>    `read_to` UInt8,</span>\n<span>    `read_time` DateTime,</span>\n<span>    `version` Int32</span>\n<span>)</span>\n<span>ENGINE <span>=</span> ReplacingMergeTree(version)</span>\n<span><span>ORDER</span> <span>BY</span> (article_id, user_id)</span></code></pre></div>\n<p>Note the special <code>version</code> numeric column, which will be used by the ReplacingMergeTree engine to mark rows for removal. Let’s simulate a user reading an article over time from 0 to 80%:</p>\n<div><pre><code><span><span>INSERT INTO</span> article_reads</span>\n<span>           <span>VALUES</span>(<span>1</span>, <span>12</span>, <span>0</span>, <span>'2023-01-06 15:20:32'</span>, <span>1</span>),</span>\n<span>                 (<span>1</span>, <span>12</span>, <span>30</span>, <span>'2023-01-06 15:21:42'</span>, <span>2</span>),</span>\n<span>                 (<span>1</span>, <span>12</span>, <span>45</span>, <span>'2023-01-06 15:22:13'</span>, <span>3</span>),</span>\n<span>                 (<span>1</span>, <span>12</span>, <span>80</span>, <span>'2023-01-06 15:23:10'</span>, <span>4</span>);</span></code></pre></div>\n<p>Here we increase the <code>version</code> column value as reading progress is tracked. The process of row removal is also executed in the background through normal merge cycles, so we need to filter based on the latest version at query time:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> article_reads</span>\n<span><span>WHERE</span> (user_id <span>=</span> <span>1</span>) <span>AND</span> (article_id <span>=</span> <span>12</span>)</span>\n<span><span>ORDER</span> <span>BY</span> version <span>DESC</span></span>\n<span>LIMIT <span>1</span></span>\n<span></span>\n<span>┌─user_id─┬─article_id─┬─read_to─┬───────────read_time─┬─version─┐</span>\n<span>│       <span>1</span> │         <span>12</span> │      <span>80</span> │ <span>2023</span><span>-01</span><span>-06</span> <span>15</span>:<span>23</span>:<span>10</span> │       <span>5</span> │</span>\n<span>└─────────┴────────────┴─────────┴─────────────────────┴─────────┘</span></code></pre></div>\n<p>Or we can use LIMIT 1 BY to get the list of rows with the latest version:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    user_id,</span>\n<span>    article_id,</span>\n<span>    read_to</span>\n<span><span>FROM</span> article_reads</span>\n<span><span>ORDER</span> <span>BY</span> version <span>DESC</span></span>\n<span>LIMIT <span>1</span> <span>BY</span></span>\n<span>    user_id,</span>\n<span>    article_id</span>\n<span></span>\n<span>┌─user_id─┬─article_id─┬─read_to─┐</span>\n<span>│       <span>1</span> │         <span>12</span> │      <span>80</span> │</span>\n<span>└─────────┴────────────┴─────────┘</span></code></pre></div>\n<p>And again, we do not have to care about removal of old versions - this is done automatically by ClickHouse in the background.</p>\n<h2 id=\"summary\"></h2>\n<p>Updating and deleting data in analytical environments can be challenging and impact database performance dramatically. To address this ClickHouse provides multiple powerful ways to update and delete data efficiently for different cases:</p>\n<ul>\n<li>Lightweight Deletes via the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/delete/#lightweight-delete-internals\"><code>DELETE FROM</code></a> syntax for removing data from ClickHouse. This is the most efficient way to delete data, provided that immediate disk space savings are not required, and users can tolerate deleted data “existing” on disk.</li>\n<li>Mutation-based deletes via <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter/delete/\"><code>ALTER…DELETE</code></a> in cases where immediate disk space savings are required. For example, compliance requirements require guarantees around removing data from disk.</li>\n<li>Mutation-based updates using <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter/update/\"><code>ALTER…UPDATE</code></a> in case of irregular and non-frequent changes</li>\n<li>Using <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#mergetree-table-ttl\">TTLs</a> for regular removal of (outdated) data based on date/time,</li>\n<li>Using <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/collapsingmergetree/\">CollapsingMergeTree</a> to update or remove individual rows frequently.</li>\n<li>Using <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/replacingmergetree/\">ReplacingMergeTree</a> to implement upsert (insert/update) based on versioning.</li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter/partition/#drop-partitionpart\">Dropping partitions</a> when removing large blocks of data regularly.</li>\n<li>Creating new columns (and dropping old ones) might also be a more efficient way to update entire tables.</li>\n</ul></div></article>"
