contentHtml: "<div><p>In financial services, market data systems typically split into two tiers: real-time and historical.</p>\n<p>The real-time tier handles the live feed and the current trading day, serving queries that need answers in microseconds. And then, there's the historical tier, a durable archive of every prior day, that serves queries for research, backtesting, transaction-cost analysis, and regulatory reconstruction.</p>\n<p>The historical tier is also the lowest-risk place to try a new database - it doesn't touch the live trading path, doesn't need microsecond latency, and the workload is well-understood (which makes it easy to test).</p>\n<p>In this post, we load real tick data from Binance's public archive and show that ClickHouse stores it cheaply, queries it quickly, and handles the operations that matter to a trading desk: VWAP, OHLC candles, and as-of joins.</p>\n<h2 id=\"user-content-why-clickhouse-for-historical-ticker-data\"></h2>\n<p>Before the worked example, a brief word on why ClickHouse is well-suited to this workload. It comes down to two things: how it stores data, and how you query it.</p>\n<h3 id=\"user-content-cost-efficiency\"></h3>\n<p>Unlike row-oriented databases, which store each record separately, ClickHouse stores data as columns, with values stored together on disk. For analytical workloads, this has a significant consequence for storage efficiency.</p>\n<p>Storing similar data next to each other allows us to apply compression techniques to reduce the space they occupy. For example:</p>\n<ul>\n<li>Dictionary encoding saves space when a column has low cardinality. Instead of storing the same string thousands of times, we store a dictionary of distinct values and an integer reference per row.</li>\n<li>Delta encoding works well for timestamps or any column where adjacent values are monotonically increasing and differ by small amounts. Rather than storing the full value each time, we store only the difference from the previous value.</li>\n<li>Run-length encoding replaces a sequence of identical adjacent values with a single value and a count.</li>\n</ul>\n<p>Tick data tends to compress particularly well because it has exactly these properties: timestamps that increment in small regular steps, prices that drift slowly, symbols that repeat millions of times, and trade IDs that increase monotonically.</p>\n<p><span><img alt=\"Replacing HDB ClickHouse Diagram (1).jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FReplacing_HDB_Click_House_Diagram_1_4f1038d953.jpg&w=2048&q=75\"></span></p>\n<p>Beyond these specialized encodings, storing similar values together creates highly repetitive byte patterns that general-purpose compression algorithms such as ZSTD and LZ4 can exploit. These are applied to every column to reduce the amount of data stored.</p>\n<h3 id=\"user-content-query-accessibility\"></h3>\n<p>The second reason to consider ClickHouse for historical tick data is its ease of querying. ClickHouse uses SQL - the common language across data engineering, analytics, and business intelligence. According to the 2025 Stack Overflow Developer survey, <a target=\"_blank\" href=\"https://survey.stackoverflow.co/2025/technology#most-popular-technologies\">58.6% of developers</a> use it.</p>\n<p>There's no specialist language to learn, no small talent pool to hire from, and no bottleneck of having to route every question through the people who can write the queries. We'll see this in action in the worked examples below.</p>\n<h2 id=\"user-content-a-worked-example-using-clickhouse-for-historical-ticker-data\"></h2>\n<p>Now we're going to have a look at a worked example showing how to use ClickHouse to query historical ticker data.\nWe'll use <a target=\"_blank\" href=\"https://data.binance.vision/\">Binance's public market-data archive</a>, a free, openly redistributable dataset containing billions of records.</p>\n<h3 id=\"user-content-one-month-of-data-on-clickhouse-local\"></h3>\n<p>We'll start with an example that you can run on your own computer - one month of USD-M perpetual futures (from January 2024) across five of the most active symbols - BTC, ETH, SOL, BNB, and XRP.</p>\n<p>That gives us hundreds of millions of trades and nearly 2 billion quotes. You can use this script to download the data, which consists of 155 ZIP files totaling 21 GB.</p>\n<h4 id=\"user-content-trades\"></h4>\n<p>Let's start with trades. <code>update_id</code> is a monotonically increasing integer.</p>\n<p>Every time the best bid or best ask changes (e.g., when an order is placed, canceled, or filled), Binance adds a new record to the <code>quotes</code> table.</p>\n<p>The schema for the <code>quotes</code> table is shown below:</p>\n<div><pre><code><span><span>CREATE TABLE</span> quotes</span>\n<span>(</span>\n<span>    symbol     LowCardinality(String),</span>\n<span>    ts         DateTime64(<span>3</span>) CODEC(DoubleDelta, ZSTD(<span>1</span>)),</span>\n<span>    bid_price  <span>Decimal</span>(<span>12</span>, <span>4</span>)   CODEC(ZSTD(<span>1</span>)),</span>\n<span>    bid_qty    <span>Decimal</span>(<span>16</span>, <span>3</span>)   CODEC(ZSTD(<span>1</span>)),</span>\n<span>    ask_price  <span>Decimal</span>(<span>12</span>, <span>4</span>)   CODEC(ZSTD(<span>1</span>)),</span>\n<span>    ask_qty    <span>Decimal</span>(<span>16</span>, <span>3</span>)   CODEC(ZSTD(<span>1</span>)),</span>\n<span>    update_id  UInt64 CODEC(DoubleDelta, ZSTD(<span>1</span>))</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (symbol, ts);</span></code></pre></div>\n<p>And we can ingest the data using the following query:</p>\n<div><pre><code><span><span>INSERT INTO</span> quotes <span>SELECT</span></span>\n<span>    splitByChar(<span>'-'</span>, _file)[<span>1</span>] <span>AS</span> symbol,</span>\n<span>    fromUnixTimestamp64Milli(transaction_time),</span>\n<span>    best_bid_price, best_bid_qty, best_ask_price, best_ask_qty, update_id</span>\n<span><span>FROM</span> file(<span>'data/*-bookTicker-*.zip :: *.csv'</span>, CSVWithNames);</span></code></pre></div>\n<p>To ingest just under 2 billion records takes around 8 minutes:</p>\n<div><pre><code><span>1997061823 rows <span>in</span> <span>set</span>.
