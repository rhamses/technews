contentHtml: "<div><h3 id=\"introduction\"></h3>\n<p>Our mission for ClickHouse Cloud, since its early days, has been to equip our users to develop analytics applications at scale, without having to worry about the operational overhead of infrastructure planning, sizing, and managing complex scaling operations. For this reason, the service has supported vertical autoscaling since its inception, so users never have to overprovision or monitor their usage. Based on memory and CPU usage, the service scales to accommodate the workload within the bounds specified by the user.</p>\n<p>Now, we are excited to bring <strong>horizontal scaling</strong> to ClickHouse Cloud in Private Preview. This feature is available for Production instances in ClickHouse Cloud. Horizontal scaling will allow customers to control the number of replicas in their service to match their workload demands.</p>\n<p>As part of Private Preview, this feature is available via ClickHouse Cloud APIs. We will also be enabling horizontal scaling via the cloud console very soon. To access horizontal scaling for your service, please contact the ClickHouse Support Team at <a target=\"_blank\" href=\"mailto:support@clickhouse.com\">support@clickhouse.com</a>.</p>\n<h3 id=\"why-horizontal-scaling\"></h3>\n<p>Before we get into the details of horizontal scaling in ClickHouse Cloud, let’s first take a look at how horizontal and vertical scaling are different.</p>\n<p>Vertical scaling usually involves increasing the resources available - adding more memory or CPU - to a single machine, or a set of machines, in a cluster. Larger machines can handle greater loads, especially ones where you might want all resources to fit in the memory of a single machine - for instance supporting large joins across tables. There are physical limits to vertical scaling though - the machines have an upper limit to how large they can get.</p>\n<p>Horizontal scaling, on the other hand, involves adding more machines. Usually, these are all of the same size in order to scale out a cluster of homogenous machines (or replicas). The workload is then distributed among a large number of smaller machines (as opposed to a few large machines in case of vertical scaling).</p>\n<p>Horizontal scaling provides better fault tolerance as the load is spread over a larger set of replicas. It is usually faster to scale out a service horizontally, by adding smaller machines, than it is to scale vertically by increasing the size of existing replicas. Because of the mechanics of how horizontal scaling works, it can also be less disruptive than vertical scaling, as new replicas are being added (rather than existing replicas being resized, or replaced).</p>\n<p>Horizontal and vertical scaling help with different kinds of workloads. Workloads that need lots of resources from a single machine benefit from vertical scaling. For workloads with high concurrency, horizontal scaling can be a great alternative. For instance, you might have the need to ingest a large amount of data into ClickHouse. Adding additional replicas will allow the ingestion to proceed much faster. Horizontal scaling also works much better than vertical scaling in scenarios where the request rate is increasing, and you need to quickly add capacity to the cluster without impacting the existing capacity.</p>\n<h3 id=\"horizontal-scaling-in-action\"></h3>\n<p>Once horizontal scaling is enabled on the service, you can use ClickHouse Cloud <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/manage/api/swagger#/paths/~1v1~1organizations~1:organizationId~1services~1:serviceId~1scaling/patch\">public APIs</a> to scale your service by updating the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/manage/api/swagger#/paths/~1v1~1organizations~1%7BorganizationId%7D~1services~1%7BserviceId%7D~1scaling/patch\">scaling settings</a> for the service.</p>\n<p>Let’s see how horizontal scaling works.</p>\n<ol>\n<li>\n<p>First, inspect the memory allocated to your cluster as well as the number of replicas. You can do this by looking at the cloud console dashboard as well as the number of replicas from your service settings. Here we have a 3 replica cluster with 16 GiB of memory allocated to each, resulting in a total of 48 GiB memory allocated to the cluster.</p>\n<p><span><img alt=\"unnamed (3).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Funnamed_3_8227247d97.png&w=2048&q=75\"></span></p>\n<p><span><img alt=\"unnamed (4).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Funnamed_4_fe1f1310f3.png&w=2048&q=75\"></span>\n<em>Service scaling settings from ClickHouse Cloud console</em></p>\n</li>\n<li>\n<p>Let’s say we now want to horizontally scale the cluster to 6 replicas of 16 GiB each. This means that once scaling is complete, we should end up with a total memory of 96 GiB across six replicas.</p>\n</li>\n</ol>\n<blockquote>\n<p><strong>Note</strong>: The API currently assumes that the min and max. total memory is based on 3 replicas, which is the number of replicas in a default production ClickHouse cluster. This means that the <code>minTotalMemoryGb </code>and <code>maxTotalMemoryGb</code> have values equal to 24 and 96 respectively, which comes out to a per-node memory minimum of <code>8GiB</code> and <code>32GiB</code> respectively, as reflected by the UI. If we want to horizontally scale out from 3 to 6 replicas, we need to only change the <code>numReplicas</code> in the API, or the <code>Number of Nodes</code> in the UI, without changing the min and max memory size. Thus, for an <code>16GiB</code> replica size, our total memory will come out to be <code>96GiB</code>across 6 replicas</p>\n</blockquote>\n<p>To do so, we issue a patch request, to adjust the number of replicas in a cluster as shown below (screenshots from postman client).</p>\n<p><span><img alt=\"unnamed (5).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Funnamed_5_24d9c7cab6.png&w=2048&q=75\"></span>\n<em>PATCH request to update numReplicas</em></p>\n<p><span><img alt=\"unnamed (6).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Funnamed_6_9a4ad59745.png&w=2048&q=75\"></span>\n<em>Response from PATCH request</em></p>\n<ol>\n<li>\n<p>Once you issue the PATCH request, you’ll see that the scaling settings screen now displays “6” as the setting for the number of replicas in the cluster. It is important to note that this is not the current number of replicas in the cluster, it is the desired number of replicas.</p>\n<p><span><img alt=\"unnamed (7).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Funnamed_7_d528dc717c.png&w=2048&q=75\"></span></p>\n</li>\n<li>\n<p>Looking back at the monitoring screen for this cluster, we can now see that the cluster has indeed been scaled to a total of 96 GiB memory.</p>\n<p><span><img alt=\"unnamed (8).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Funnamed_8_7700054f43.png&w=2048&q=75\"></span></p>\n</li>\n</ol>\n<h3 id=\"looking-to-the-future\"></h3>\n<p>As mentioned earlier, we will soon make horizontal scaling available via the cloud console directly. During Private Preview, we will improve the UI and API experience of horizontally scaling a ClickHouse Cloud service based on customer feedback, before making the capability generally available (GA).</p>\n<p>Making horizontal scaling self-service and GA is just the first step. In the near future, we will also enable horizontal autoscaling, whereby a ClickHouse Cloud user is able to set minimum and maximum replica counts on their service as bounds within which their service should autoscale. Based on the load on the cluster, we will automatically horizontally scale the cluster as needed to closely match the actual utilization. Our end goal is to provide a mix of horizontal and vertical autoscaling to achieve the optimal performance for a service based on the workload.</p></div><p><a target=\"_blank\" href=\"https://clickhouse.cloud/signUp?loc=blog-cta-footer&utm_source=clickhouse&utm_medium=web&utm_campaign=blog\">Get started</a> with ClickHouse Cloud today and receive $300 in credits.
