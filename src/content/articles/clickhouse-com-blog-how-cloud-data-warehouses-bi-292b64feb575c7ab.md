service has two independent dimensions:</p>\n<p><strong>1. You only pay for <strong>what each query actually consumes</strong>, not for the size or uptime of a cluster.</p>\n<p>What follows is a concise breakdown of how BigQuery’s compute model works, how it scales, and how billing is derived from that model.</p>\n<p>BigQuery executes each query using its engine, running on a shared pool of pre-provisioned compute (engine paper: <a target=\"_blank\" href=\"https://storage.googleapis.com/gweb-research2023-media/pubtools/3293.pdf\">Dremel: Interactive Analysis of Web-Scale Datasets</a>). <strong>dynamic</strong> and depends on the query plan:</p>\n<ul>\n<li><strong>Scan &amp; filter</strong> stages can be highly parallel (many slots) if there are lots of partitions or column chunks to read.</li>\n<li><strong>Aggregation</strong> stages often use fewer slots, shaped by grouping cardinality and data distribution.</li>\n<li><strong>Final merge</strong> stages usually need only a handful of slots to combine partial results.</li>\n</ul>\n<p>In other words, BigQuery tries to give each stage <strong>as much parallelism as it can actually use</strong>, and that slot allocation can slot-seconds</strong></li>\n</ul>\n<p>Stage 3 — Final merge</p>\n<ul>\n<li><strong>Duration:</strong> 2 seconds</li>\n<li><strong>Slots used:</strong> 4</li>\n<li><strong>Slot-time:</strong> 2 seconds × 4 slots = <strong>8 slot-seconds</strong></li>\n</ul>\n<p>Now sum up the slot-time:</p>\n<ul>\n<li><strong>Total slot-seconds:</strong> 12,000 + 3,600 + 8 = <strong>15,608 slot-seconds</strong></li>\n<li><strong>Wall-clock runtime:</strong> <strong>20 seconds</strong></li>\n<li><strong>Billed compute:</strong> <strong>15,608 slot-seconds</strong></li>\n</ul>\n<p>So even
