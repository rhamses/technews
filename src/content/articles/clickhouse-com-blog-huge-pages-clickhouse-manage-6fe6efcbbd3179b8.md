contentHtml: "<div><p>What are huge pages, and why do they matter for Postgres? The OS hands out memory in 4KB pages, and the CPU keeps a small cache of virtual-to-physical translations, the TLB. A huge page is the same memory in much bigger units, 2MB or 1GB, so one page-table entry covers up to 262,144x more ground.</p>\n<p>Postgres is unusually sensitive to page size. Its cache, shared_buffers, is one big shared-memory segment, and every backend process maps it through its own page tables. At 4KB pages, a 100GB cache costs each backend about 200MB of page-table entries, so 100 connections burns 20GB of RAM on page tables alone; with 2MB huge pages, tens of MB. And a TLB holds a few thousand translations, which covers just a few MB of that cache at 4KB, so each 2MB page gives a slot 512x the reach, the hot working set stays in the TLB, and reads stop stalling on page-table walks.</p>\n<p>In ClickHouse Managed Postgres every server runs its buffer cache on huge pages. Getting that to hold reliably takes three pieces: reserving the pages early, refusing to run without them, and sizing shared_buffers so the whole shared memory segment lands on the reserved pool exactly.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fhugepages_postgres_jul2026_image1_e990803005.png&w=2048&q=75\"></span></p>\n<h2 id=\"user-content-reserving_the_pages\"></h2>\n<p>A quarter of the machine's memory is reserved as huge pages, mirroring the <code>shared_buffers</code> = 25% of RAM rule in the base configuration. The reservation runs before Postgres ever starts, and it flushes caches and compacts memory first so the kernel can still find contiguous 2MB blocks:</p>\n<div><pre><code><span><span>echo</span> <span>'vm.nr_hugepages = '</span> &gt; /etc/sysctl.d/10-hugepages.conf</span>\n<span><span>sync</span></span>\n<span><span>echo</span> 3 &gt; /proc/sys/vm/drop_caches</span>\n<span><span>echo</span> 1 &gt; /proc/sys/vm/compact_memory</span>\n<span>sysctl --system</span></code></pre></div>\n<p>The allocation is then verified against <code>HugePages_Total</code> in <code>/proc/meminfo</code>, and provisioning fails if the kernel comes up short. Huge pages can only be reserved reliably while memory is unfragmented; on a machine that has been under load, the same request routinely fails.</p>\n<h2 id=\"user-content-refusing_to_run_without_them\"></h2>\n<p>Postgres is pinned to <code>huge_pages = 'on'</code>, so it either gets its pages or refuses to start. The default, <code>'try'</code>, silently falls back to 4KB pages with nothing in the logs, and every property described above quietly disappears. A refusal at startup is diagnosable; a silent fallback is discovered months later, usually by a profiler.</p>\n<p>There is a runtime check, too. The postmaster's <code>/proc/&lt;pid&gt;/status</code> records how much of its address space sits on hugetlb pages; on the demo box below it reads:</p>\n<div><pre><code><span>$ grep HugetlbPages /proc//status</span>\n<span>HugetlbPages:   700416 kB</span></code></pre></div>\n<p><code>HugetlbPages: 0</code> on a server that should be using huge pages means the fallback happened.</p>\n<h2 id=\"user-content-sizing_shared_buffers_to_the_page\"></h2>\n<p>Postgres's shared memory segment is bigger than shared_buffers: it also carries buffer descriptors, WAL buffers, and lock tables. On the demo box below, <code>shared_buffers = 32GB</code> produces a 32.75GB segment, about 750MB of overhead. If shared_buffers alone filled the reserved pool, the full segment would not fit, and <code>'on'</code> would refuse to boot. The sizing works in two passes. First point shared_buffers at the entire pool, then ask the binary what the full segment would actually cost, without starting the server:</p>\n<div><pre><code><span>postgres -D  -C shared_memory_size</span></code></pre></div>\n<p>Subtract the difference back out of shared_buffers, round down to whole 8KB blocks, and write the result:</p>\n<div><pre><code><span><span># conf.d/002-hugepages.conf</span></span>\n<span>huge_pages = <span>'on'</span></span>\n<span>huge_page_size = 0        <span># use the system default, 2MB</span></span>\n<span>shared_buffers = kB</span></code></pre></div>\n<p>The overhead is measured rather than assumed because it shifts with version and settings, and measuring at the larger size errs a few pages under the reservation. The reserved pool and the rest of memory are then accounted separately: huge pages do not count toward the kernel's commit limit, so memory overcommit is tuned against the remaining 75% of RAM.</p>\n<h2 id=\"user-content-seeing_it_on_real_hardware\"></h2>\n<p>We put the claim about page tables on a single EC2 box: an <code>r7i.4xlarge</code> (16 vCPU, 128GB), Postgres 16 with <code>shared_buffers = 32GB</code>, and a pgbench dataset whose 15.6GB accounts table is loaded fully into the cache with <code>pg_prewarm</code>. Each test connection then runs one full sequential scan of that table, which makes its backend touch every cached page and build its complete page-table mapping, and holds the connection open. We sampled the kernel's <code>PageTables</code> counter from <code>/proc/meminfo</code> at 25, 50, 100, and 200 connections, once with 4KB pages and once with 2MB huge pages. Same box, same data, same access pattern; the only variable is the page size.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fhugepages_postgres_jul2026_image2_d02cfccbc0.png&w=2048&q=75\"></span></p>\n<p>With 4KB pages, page tables grow by 31.1MB per connection, matching the arithmetic (15.6GB of touched cache / 4KB pages x 8 bytes per entry = 31.2MB), and reach 6.1GB at 200 connections, kernel memory spent on bookkeeping for 15.6GB of data. With 2MB huge pages the same 200 connections cost 111MB, about 0.5MB per connection.</p>\n<div><table><thead><tr><th>Connections</th><th>PageTables, 4KB</th><th>PageTables, 2MB huge pages</th></tr></thead><tbody><tr><td>0</td><td>48 MB</td><td>5 MB</td></tr><tr><td>25</td><td>789 MB</td><td>18 MB</td></tr><tr><td>50</td><td>1.53 GB</td><td>31 MB</td></tr><tr><td>100</td><td>3.06 GB</td><td>58 MB</td></tr><tr><td>200</td><td>6.12 GB</td><td>111 MB</td></tr></tbody></table></div>\n<p>The <code>huge_pages = 'on'</code> behavior is equally visible. With no pool reserved, Postgres refuses to start and says why:</p>\n<div><pre><code><span>FATAL:  could not map anonymous shared memory: Cannot allocate memory</span>\n<span>HINT:  This error usually means that PostgreSQL<span>'s request for a shared</span></span>\n<span><span>memory segment exceeded available memory, swap space, or huge pages.</span></span></code></pre></div>\n<p>Throughput moves too, though less dramatically than the memory: select-only pgbench at 100 clients ran 373,083 TPS on 4KB pages and 418,087 TPS on 2MB huge pages, a 12% difference on an otherwise identical box. The structural change is in the memory: page tables that scale linearly with connections versus page tables that stay flat.</p>\n<h2 id=\"user-content-the_takeaway\"></h2>\n<p>Huge pages turn shared_buffers from a per-connection page-table tax into a flat, translation-friendly cache. Reserving the pool before fragmentation, running <code>huge_pages = 'on'</code> so a broken setup fails at boot instead of degrading silently, and sizing the segment to the reservation with the numbers the postgres binary itself reports are what make the configuration hold in production rather than only on a fresh box.</p></div>"
