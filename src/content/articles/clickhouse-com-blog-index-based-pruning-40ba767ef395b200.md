contentHtml: "<div><p>The fastest analytical queries are the ones that read the least data. We know we say that a lot, but that’s only because it’s true!</p>\n<p>ClickHouse has several ways to make this happen. In this blog post, we'll use a dataset of UK property sales to walk through three index-based pruning techniques - so you know exactly what to reach for and when.</p>\n<h2 id=\"user-content-pruning_technique_1_primary_index\"></h2>\n<p>The first pruning technique, the primary key, is one of the first things that you learn when creating a table. A table’s primary key determines the sort order of the data within a data part.</p>\n<p>Table parts are comprised of granules, each containing 8,192 rows by default. ClickHouse’s primary index stores the <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes#the-primary-index-has-one-entry-per-granule\">primary key column values for the first row in every granule</a>.</p>\n<p>In the diagram below, data is sorted by the primary key, <code>C1</code>, and rows are organized into granules (<code>g1</code> to <code>g4</code>). We use 3 rows per granule in this diagram for clarity. The primary index stores the first value for each granule, i.e., 10 for <code>g1</code>, 20 for <code>g2</code>, and so on.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpruning_001_767cab4175.png&w=2048&q=75\"></span></p>\n<p>The primary index allows entire granules to be skipped before reading them, based on the filter condition on the primary key. For example, for a query that contains <code>WHERE C1 &gt; 60</code>, granules <code>g1</code> and <code>g2</code> are pruned using the index, so only the remaining data is read.</p>\n<h2 id=\"user-content-pruning_technique_2_lightweight_projections\"></h2>\n<p>Our next pruning technique is <a target=\"_blank\" href=\"https://clickhouse.com/blog/projections-secondary-indices\">lightweight projections</a>, which was first introduced in <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-06#filtering-by-multiple-projections\">ClickHouse 25.6</a> and received a more user-friendly syntax in <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-26-01#new-syntax-for-indexing-projections\">ClickHouse 26.1</a>.</p>\n<p>Projections in ClickHouse are automatically maintained, hidden table copies stored in a different sort order, and therefore with a different primary index. These alternative layouts can speed up queries that benefit from those orderings. The downside is that projections duplicated the base table’s data on disk.</p>\n<p>Lightweight projections behave like a secondary index without duplicating full rows. Instead of storing complete data copies, they store only their sorting key plus a <code>_part_offset</code> pointer back into the base table. This greatly reduces storage overhead but means that any other returned columns must be read from the base table.</p>\n<p>We can see how this works by updating our diagram to add a lightweight projection on <code>C2</code>:</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpruning_002_5dd07dd9ad.png&w=2048&q=75\"></span></p>\n<p>For filters on a column that is not part of the primary key, such as <code>WHERE C2 &gt; 900</code>, ClickHouse can use a lightweight projection, which stores the sorted projection key (<code>C2</code>) values plus <code>_part_offset</code> values and provides its own primary index (②) that allows granules to be pruned for filters on the projection key.</p>\n<h2 id=\"user-content-pruning_technique_3_skip_indexes\"></h2>\n<p>Our final technique is <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/skipping-indexes\">skip indexes</a>. One such skip index is the minmax index, which records the minimum and maximum values for a column for each granule.</p>\n<p>Minmax indexes have been supported in ClickHouse for more than five years, but we’ve recently added support for automatically creating these indexes for every column of a specific type in a table.</p>\n<p>The advantage of a minmax index over a lightweight projection is that it doesn’t duplicate the column values on disk. However, something to keep in mind is that the column on which we apply a minmax index needs to be somewhat correlated with the primary-key, otherwise the index won’t effectively prune data.</p>\n<p>In the diagram below, the minmax index (③) records the minimum and maximum values of <code>C3</code> for each granule.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpruning_003_9950c00fa2.png&w=2048&q=75\"></span></p>\n<p>For a filter like <code>WHERE C3 &gt; 600</code>, granules <code>g1</code> to <code>g3</code> can be skipped because their maximum value is below 600, so only g4 needs to be read.</p>\n<h2 id=\"user-content-pruning_in_action\"></h2>\n<p>Now that we’ve got a high-level understanding of each of the pruning techniques, let’s learn how to put them into action on a real-life dataset.
