contentHtml: "<div>\n<blockquote>\n<p><strong>TL;DR</strong><br>Index sharding distributes the analysis of primary and secondary indexes across replicas, freeing working memory for query execution and accelerating index analysis by up to 7.7×  in our tests on a 50 billion row table.</p>\n</blockquote>\n<br>\n<h2 id=\"the-next-bottleneck-to-scale\"></h2>\n<p>ClickHouse was built to be fast at scale.</p>\n<p>But \"scale\" means a lot of different things to a lot of different people. For the ClickHouse engineering team, it is a cycle: focus on a number perceived to be large, make an effort to change its perception to be normal, find another number. The numbers we've focused on recently have been <strong>index sizes</strong> and <strong>index analysis time</strong>.</p>\n<p><strong><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-23-03#parallel-replicas-for-utilizing-the-full-power-of-your-replicas-nikita-mikhailov\">Parallel replicas</a></strong>, introduced in ClickHouse 23.3, made query execution scale horizontally by distributing data reading across the fleet.</p></div><div><p>Index sharding extends that same principle one step earlier: the index analysis phase that happens before any data is read at all.</p>\n<p>Until now, ClickHouse has been operating under an assumption: every replica loads the entire index from object storage into working memory.</p></div><div><p>For most workloads, this is a non-issue. Indexes are small, working memory is plentiful, and ClickHouse's sparse index design keeps things lean by design.</p>\n<p>But at a truly massive scale, hundreds of billions of rows, petabytes of data, dozens of replicas, the primary key index alone can reach 100GB or more per replica. Add vector search indexes, bloom filters, and full-text search indexes on top of that, and you're looking at a very expensive proposition: the same enormous index loaded redundantly across every single replica.</p>\n<p>Index Sharding changes the contract. Instead of every replica loading everything, indexes are partitioned across the fleet. Each replica owns a slice, and together they cover it all.</p></div><div><p>The result is three compounding wins:</p>\n<ol>\n<li>Dedicating less working memory for indexes per replica as you scale out</li>\n<li>Horizontally scalable index analysis due to the work being spread across more machines in parallel</li>\n<li>Faster individual processing because of a dramatic increase in<a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Locality_of_reference\"> locality of reference</a>.</li>\n</ol>\n<h2 id=\"how-index-analysis-works\"></h2>\n<p>When data is written to a ClickHouse MergeTree table, it is organized into <em><a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">parts</a></em>: immutable, self-contained units of column data. As each part is written, ClickHouse builds its indexes inline and stores them alongside the column data in object storage.</p>\n<p><span><img alt=\"Blog-Index_Sharding.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Index_Sharding_001_be93967e06.png&w=2048&q=75\"></span></p>\n<p>In ClickHouse Cloud, this means the <a target=\"_blank\" href=\"https://clickhouse.com/docs/primary-indexes\">primary key index</a>, the <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes#mark-files-are-used-for-locating-granules\">mark files</a>, and any <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/skipping-indexes\">secondary indexes</a> all live in the same location as the part data itself.</p>\n<p>When a query arrives that touches an indexed column, ClickHouse must load those index files from object storage into working memory before it can determine which granules are worth reading.</p>\n<p><span><img alt=\"Blog-Index_Sharding.002.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Index_Sharding_002_52ae76e4b0.png&w=2048&q=75\"></span></p>\n<p>The index cannot be consulted on disk or directly in object storage; it must be resident in memory for the analysis to work.</p>\n<p>This is what makes index memory a fixed cost per replica: every replica that participates in query analysis must have the relevant indexes loaded before it can do any analyzing.\nClickHouse's primary index is intentionally sparse. Rather than tracking every row, it stores one entry (called a mark) per granule: a block of 8,192 rows by default.</p>\n<p><span><img alt=\"Blog-Index_Sharding.003.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Index_Sharding_003_10c91d8985.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p>This makes the index small enough to fit entirely in memory while still providing the <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes#the-primary-index-is-used-for-selecting-granules\">fast binary search</a> used to skip over data that the index identifies as irrelevant.</p>\n</blockquote>\n<p>When you run a query with a <strong><code>WHERE</code></strong> clause that reads indexed columns, ClickHouse performs <em>index analysis</em>: a two-step process that first removes any irrelevant partitions from the query when a table has been configured with a <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/mergetree-family/custom-partitioning-key\">partitioning key</a>. It then scans the marks for each data part to find which granules <em>might</em> contain matching rows, skips the rest entirely, then streams only the selected granules off disk. This is what gives ClickHouse its characteristic speed. On a well-indexed table, it reads a tiny fraction of the data.</p>\n<p>The same mechanism applies to secondary indexes: bloom filters for set membership tests, <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-full-text-search-object-storage\">text indexes</a> for full-text search, and vector indexes for approximate nearest neighbor, all of which are loaded from their respective index files into working memory to drive granule skipping.</p>\n<p>For a typical table with billions of rows, this is perfectly manageable. The bottleneck emerges at the high end of the scale curve.</p>\n<h2 id=\"the-bottleneck-indexes-don-t-scale-horizontally-alongside-replicas\"></h2>\n<p>In ClickHouse Cloud, all replicas share storage. A table with five petabytes of data living in object storage doesn't need that data duplicated across replicas; only the compute is replicated. The data stays in one place, and replicas stream what they need when they need it.</p>\n<p><span><img alt=\"Blog-Index_Sharding.004.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Index_Sharding_004_f538eee94f.png&w=2048&q=75\"></span></p>\n<p>But until now, indexes did not share the same fate. While every index is stored alongside the data in object storage, every replica that serves queries must load the active primary key index from object storage into its own working memory.</p>\n<p><span><img alt=\"Blog-Index_Sharding.005.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Index_Sharding_005_1d181fd80c.png&w=2048&q=75\"></span></p>\n<p>Every replica that evaluates a bloom filter or a text index loads that index too, or pushes the skip index evaluation from index analysis down to data read via <code>use_skip_indexes_on_data_read</code>. If you add replicas to handle more query concurrency or more throughput, each new replica brings its own copy of the full index.</p>\n<p>At petabyte scale, the primary key alone can reach 100-400 GiB per replica in memory. With secondary index marks on top, and a growing popularity for vector search and full-text search, the memory cost of adding replicas becomes a significant portion of working memory; memory that could be used to process queries instead.</p>\n<p>The bottleneck is that the more replicas you add, precisely to get more horizontally scaled performance, the worse the situation gets. For a 100 GB index, the cumulative working memory consumed across the fleet scales directly with replica count:</p>\n<div><table><thead><tr><th>Replicas</th><th>Index memory per replica</th><th>Cumulative index memory</th></tr></thead><tbody><tr><td>1</td><td>100 GB</td><td>100 GB</td></tr><tr><td>3</td><td>100 GB</td><td>300 GB</td></tr><tr><td>6</td><td>100 GB</td><td>600 GB</td></tr><tr><td>9</td><td>100 GB</td><td>900 GB</td></tr><tr><td>12</td><td>100 GB</td><td>1.2 TB</td></tr></tbody></table></div>\n<p>Every replica holds the same identical index. Every byte of that index is replicated in full across the fleet, and the bill grows with every node you add.</p>\n<p><span><img alt=\"Blog-Index_Sharding.006.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Index_Sharding_006_1fb52ec0f5.png&w=2048&q=75\"></span></p>\n<h2 id=\"index-sharding-and-the-core-concepts\"></h2>\n<p>The core insight behind Index Sharding is simple:</p>\n<blockquote>\n<p>If you have N replicas, each one only needs to be responsible for 1/N of the entire index.</p>\n</blockquote>\n<p><span><img alt=\"Blog-Index_Sharding.007.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Index_Sharding_007_94537217c1.png&w=2048&q=75\"></span></p>\n<p>Here's how it works: When a query arrives, instead of the query initiator loading and analyzing the full index locally, it distributes the work out across all available replicas. Each replica receives a subset of the data parts to analyze via a virtual hash ring; a technique referred to as consistent hashing. Each replica loads its assigned portion of the index from object storage, performs the analysis, and returns the ranges of granules that matched. The initiator merges these results into a complete picture of what needs to be read, without any single node ever touching the whole thing.</p>\n<p>The actual data reading then proceeds using parallel replicas in the normal way, with each replica responsible for reading the data it analyzed.</p>\n<p>You can see this distribution in action with <code>EXPLAIN indexes=1</code>:</p>\n<div><pre><code><span>EXPLAIN indexes<span>=</span><span>1</span></span>\n<span><span>SELECT</span> UserID <span>FROM</span> hits</span>\n<span><span>WHERE</span> UserID <span>=</span> <span>1</span></span>\n<span>SETTINGS distributed_index_analysis <span>=</span> <span>1</span></span>\n<span>FORMAT LineAsString;</span></code></pre></div>\n<!-- -->\n<div><pre><code><span>Indexes:</span>\n<span>PrimaryKey</span>\n<span>  Keys: UserID</span>\n<span>  Condition: (UserID in [...])</span>\n<span>  Parts: 208/208</span>\n<span>  Granules: 247702/143169495</span>\n<span>  Distributed:</span>\n<span>    Address: replica-1:9000  Parts received: 35  Granules received: 45094</span>\n<span>    Address: replica-2:9000  Parts received: 47  Granules received: 53988</span>\n<span>    Address: replica-3:9000  Parts received: 43  Granules received: 47387</span>\n<span>    Address: replica-4:9000  Parts received: 43  Granules received: 56130</span>\n<span>    Address: replica-5:9000  Parts received: 40  Granules received: 45103</span></code></pre></div>\n<p>The same distribution sketched as a diagram:</p>\n<p><span><img alt=\"Blog-Index_Sharding.008.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Index_Sharding_008_ccf9ec9042.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p>The distribution covers all index types.</p>\n</blockquote>\n<p>Primary key indexes, bloom filters, full-text search indexes, and vector search indexes are all included. This matters especially for secondary indexes, which can be an even larger size relative to the table. A table with multiple text or vector indexes can easily accumulate hundreds of gigabytes of index data that previously had to be replicated across every node.</p>\n<h2 id=\"what-happens-when-a-replica-is-added-to-the-service\"></h2>\n<p>When a replica is added to the service, part assignments are rebalanced across the new replica count. As a new replica brings itself into the service, it can optionally arrive with its primary key cache and its mark cache pre-populated with both <code>prewarm_primary_key_cache</code> and <code>prewarm_mark_cache</code> enabled. If not enabled, the new replica starts with less memory initially consumed and loads its assigned indexes from object storage on demand as analysis requests arrive. When <code>use_primary_key_cache</code> is enabled, existing replicas detect that certain parts are no longer their responsibility and unload them in the background, reclaiming working memory automatically.</p>\n<p>This is where ClickHouse Cloud's compute-storage separation pays a particular dividend.</p>\n<p>In a traditional shared-nothing architecture, adding a replica means moving or copying data to the new node before it can participate in query execution. In ClickHouse Cloud, the data never moves. All replicas read from the same shared object storage, so a new replica is available to serve index analysis requests as soon as it has loaded its assigned index slice. The cost of scaling out is bounded entirely by index loading time, not data transfer.</p>\n<p>The result is that the memory benefits of Index Sharding compound at exactly the moment you want them to: as you scale out, each replica's index footprint shrinks, and adding that next replica costs only the time it takes to warm up a fraction of the total index.</p>\n<p><span><img alt=\"Blog-Index_Sharding.009.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Index_Sharding_009_3f8d705b6b.png&w=2048&q=75\"></span></p>\n<h2 id=\"how-does-clickhouse-protect-itself-from-failure-to-analyze\"></h2>\n<p>Transient failure handling is a crucial component to account for in distributed systems. There are a handful of reasons that a request for index analysis on a specific part will fail transiently. Common cases include network failures during a request between the initiator and the responsible replica, and the responsible replica not yet having the requested part loaded, but the list of how things can go wrong in a distributed system receives new and exciting entries every day; so let’s talk about how we handle known cases.</p>\n<p>When the initiator distributes an index analysis across all replicas, replicas respond with analysis for each part they are asked to analyze. In the event of a failure for a specific part, our solution is simple: fall back to analyzing the part locally. Instead of retrying the replica that produced an initial failure, the initiator will load the part’s index into local memory and run the analysis. Future requests will continue to reach out to the responsible node, and any failures will result in the fallback to the initiator’s memory.</p>\n<h2 id=\"how-does-index-sharding-reduce-memory-usage-on-replicas\"></h2>\n<p>Before index sharding, the relationship between replicas and index memory was linear and unavoidable. A 100GB index across three replicas consumed 300GB of working memory in aggregate. Scale to nine replicas and that number became 900GB, with every replica carrying the full weight regardless of how many others were doing the same job.</p>\n<p>With the introduction of index sharding, the cumulative working memory consumed by indexes across your entire fleet is now statically bounded to the size of the index itself, regardless of how many replicas you run. Add more replicas, and the cumulative total stays flat while each individual replica's share shrinks proportionally.</p>\n<p><span><img alt=\"Blog-Index_Sharding.010.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Index_Sharding_010_3eca2acf20.png&w=2048&q=75\"></span></p>\n<p>Let's visualize an example of how index analysis might get assigned across a ClickHouse cluster. On a table with a 16GB primary key across 25 parts, with Distributed Index Analysis enabled on 10 replicas, the memory distribution looked like this:</p>\n<div><table><thead><tr><th>Replica</th><th>Primary Key Memory</th><th>Parts Assigned</th></tr></thead><tbody><tr><td>replica-1</td><td>3.57 MB</td><td>193</td></tr><tr><td>replica-2</td><td>3.41 MB</td><td>210</td></tr><tr><td>replica-3</td><td>3.69 MB</td><td>219</td></tr><tr><td>replica-4</td><td>3.72 MB</td><td>226</td></tr><tr><td>replica-5</td><td>3.84 MB</td><td>226</td></tr></tbody></table></div>\n<p>Each replica holds only what it needs. The 16GB index lives once in aggregate across the fleet, not once per node within it. This changes the economics of scaling out. You can increase replica count for concurrency and throughput without being forced to provision ever-larger instances just to absorb index memory overhead.</p>\n<blockquote>\n<p>The working memory freed on each replica is available for what it was always meant for: processing queries.</p>\n</blockquote>\n<h2 id=\"how-does-index-sharding-increase-analysis-performance\"></h2>\n<p>There is a second benefit that compounds with the first: when index analysis is distributed, it is also <em>faster</em>.</p>\n<p>Without index sharding, index analysis is fundamentally bound to a single node from the perspective of a single query. One node does all the work, scanning through marks for potentially hundreds of millions of granules, before any data reading can begin. For tables with heavy and highly-selective secondary indexes like vector search and full-text search, this analysis phase is often the dominant cost of a query.</p>\n<p>Distributing the analysis across replicas turns that single bottleneck into a distributed one. Each replica works on its slice simultaneously, and the initiator merges compact range results rather than doing the full evaluation itself. More replicas means more parallelism, and more parallelism means faster analysis.</p>\n<p>On a 50 billion row table (17,000 parts, 6 million marks), benchmarked at 10 replicas:</p>\n<div><table><thead><tr><th>Query type</th><th>Without distributed index analysis</th><th>With distributed index analysis</th><th>Speedup</th></tr></thead><tbody><tr><td>Primary key range query</td><td>1.0s</td><td>0.23s</td><td>4.3x</td></tr><tr><td>Bloom filter lookup</td><td>8.5s</td><td>1.1s</td><td>7.7x</td></tr><tr><td>Vector search</td><td>6.5s</td><td>0.9s</td><td>7.2x</td></tr><tr><td>Full-text index search</td><td>3.1s</td><td>0.53s</td><td>5.8x</td></tr></tbody></table></div>\n<p>The gains compound further as you add replicas. Scaling from 10 to 20 replicas with Index Sharding enabled:</p>\n<div><table><thead><tr><th>Query type</th><th>10 replicas</th><th>20 replicas</th><th>Additional speedup</th></tr></thead><tbody><tr><td>Primary key range query</td><td>0.23s</td><td>0.16s</td><td>1.4x</td></tr><tr><td>Bloom filter lookup</td><td>1.1s</td><td>0.65s</td><td>1.7x</td></tr><tr><td>Vector search</td><td>0.9s</td><td>0.52s</td><td>1.7x</td></tr><tr><td>Full-text index search</td><td>0.53s</td><td>0.37s</td><td>1.4x</td></tr></tbody></table></div>\n<p>Without index sharding, adding replicas increases data read throughput, but doesn't help index analysis at all. It remains single-node work. With it, every replica you add contributes to both analysis throughput and memory distribution. For queries where index analysis is the bottleneck, which is common on large tables with secondary indexes, especially full-text and vector search, this is the difference between index analysis being a tax you pay on every query versus a force multiplier you gain from your investment in replicas.</p>\n<h2 id=\"what-kind-of-workloads-will-this-benefit-the-most\"></h2>\n<p>Index sharding works best where index analysis is already a meaningful part of query cost: large tables with multiple secondary indexes, high replica counts, and selective filters that lean heavily on those indexes to eliminate granules before data reading begins. Full-text search, vector similarity, and bloom filter indexes are the clearest examples. Each can occupy gigabytes of working memory per replica on large tables, and once a table crosses into that territory, both the memory savings and the analysis parallelism compound with every replica added.</p>\n<p>To ensure the coordination overhead of distributing analysis is always justified, index sharding activates automatically once two table-level thresholds are met. The first is <code>distributed_index_analysis_min_parts_to_activate</code> (default: <code>10</code>), which requires a minimum part count before distribution is attempted. The second, and more important, is <code>distributed_index_analysis_min_indexes_bytes_to_activate</code> (default: <code>1073741824</code>, i.e. 1GB), which requires the combined uncompressed size of all indexes on disk to exceed 1GB. Below that threshold, loading indexes locally is fast and cheap. Above it, the cost of analysis starts to shape query latency and per-replica working memory in ways that distribution meaningfully addresses.</p>\n<p>Both thresholds are table-level settings and can be adjusted to match your workload:</p>\n<div><pre><code><span><span>ALTER TABLE</span> my_favorite_table MODIFY SETTING</span>\n<span>    distributed_index_analysis_min_parts_to_activate <span>=</span> <span>20</span>,</span>\n<span>    distributed_index_analysis_min_indexes_bytes_to_activate <span>=</span> <span>21474836480</span>; <span>-- 20 GB</span></span></code></pre></div>\n<!-- -->\n<p>Both conditions need to be met when <code>distributed_index_analysis</code> is enabled for the analysis to upgrade from local to distributed, ensuring that smaller analyses remain performant.</p></div><div><h2 id=\"can-i-see-a-demo\"></h2>\n<p>On an internal database of ours with a merge table over eight sub-tables, we can produce a query of <code>SELECT * ...
