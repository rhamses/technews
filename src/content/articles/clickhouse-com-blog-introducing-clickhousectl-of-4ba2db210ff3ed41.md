contentHtml: "<article><div><p><code>clickhousectl</code> is the official CLI for ClickHouse. It manages local installations, runs local servers, and operates ClickHouse Cloud. It's designed to work for humans and AI agents alike. It's in beta starting today.</p>\n<div><pre><code><span>curl https://clickhouse.com/cli | sh</span></code></pre></div>\n<blockquote>\n<p><strong>Beta:</strong> clickhousectl is currently in beta. Features and behavior may change.</p>\n</blockquote>\n<h2 id=\"why-a-cli-and-why-now\"></h2>\n<p>Agentic development is the biggest shift in how software gets built in decades, and is fundamentally changing how platforms like ClickHouse will be used. High quality, powerful infrastructure matters more than ever, but it needs to adapt to a new way of working: agents interacting on behalf of the user.</p>\n<p>Agentic Experience is now an integral part of Developer Experience.</p>\n<p>ClickHouse is open source, it's a single binary, and it runs great on a laptop. The local developer experience has long been one of ClickHouse's many strengths. But the experience was designed for humans. There’s more we can do to help LLMs develop with ClickHouse.</p>\n<p>Whether an agent is building a local prototype or deploying to production on ClickHouse Cloud, <code>clickhousectl</code> gives it a streamlined, predictable interface that supports agentic development.</p>\n<h2 id=\"local-development\"></h2>\n<h3 id=\"version-management\"></h3>\n<p><code>clickhousectl</code> works as a version manager for ClickHouse, inspired by tools like <code>uv</code> and <code>pnpm</code>. The CLI helps to discover and download available ClickHouse versions. Installed binaries are stored in a global repository at <code>~/.clickhouse/versions/</code>, so they can be reused across projects without duplicating storage.</p>\n<div><pre><code><span><span># See what's available</span></span>\n<span>clickhousectl <span>local</span> list --remote</span>\n<span></span>\n<span><span># Install the latest stable release</span></span>\n<span>clickhousectl <span>local</span> install stable</span>\n<span></span>\n<span><span># Set the active version (installs it if needed)</span></span>\n<span>clickhousectl <span>local</span> use stable</span></code></pre></div>\n<h3 id=\"project-scaffolding\"></h3>\n<p><code>clickhousectl</code> can scaffold a standard project structure for your ClickHouse SQL files. This is optional (use your own structure if you prefer), but for agents, having a consistent convention means less ambiguity when writing and organizing SQL.</p>\n<div><pre><code><span>clickhousectl <span>local</span> init</span></code></pre></div>\n<p>This creates:</p>\n<div><pre><code><span>clickhouse/</span>\n<span>├── tables/                 <span># CREATE TABLE statements</span></span>\n<span>├── materialized_views/     <span># Materialized view definitions</span></span>\n<span>├── queries/                <span># Saved queries</span></span>\n<span>└── seed/                   <span># Seed data and INSERT statements</span></span></code></pre></div>\n<h3 id=\"running-local-servers\"></h3>\n<p><code>clickhousectl</code> can create, manage and query local ClickHouse server instances. Each server gets its own isolated, persistent data directory, so you can run multiple servers side by side for different projects. If default ports are already in use, free ports are detected and assigned automatically.</p>\n<div><pre><code><span><span># Start a server with the system default version (configured by `clickhousectl local use`)</span></span>\n<span>clickhousectl <span>local</span> server start --name dev</span>\n<span></span>\n<span><span># Connect and run a query</span></span>\n<span>clickhousectl <span>local</span> client --name dev --query <span>\"CREATE DATABASE product\"</span></span>\n<span></span>\n<span><span># Run SQL from a file</span></span>\n<span>clickhousectl <span>local</span> client --name dev --queries-file clickhouse/tables/events.sql</span>\n<span></span>\n<span><span># Start a second server with a specific version</span></span>\n<span>clickhousectl <span>local</span> server start --name dev-new --version 26.3</span></code></pre></div>\n<h2 id=\"clickhouse-cloud\"></h2>\n<p>When it's time to go to production, the same CLI that managed your local development now manages your cloud infrastructure. The cloud commands cover organizations, services, backups, API keys, team members, invitations, and activity logs. Every command supports <code>--json</code> output for easy parsing by agents and scripts.</p>\n<div><pre><code><span><span># Create with specific infrastructure</span></span>\n<span>clickhousectl cloud service create --name my-service \\</span>\n<span>  --provider aws \\</span>\n<span>  --region us-east-1 \\</span>\n<span>  --min-replica-memory-gb 8 \\</span>\n<span>  --max-replica-memory-gb 32 \\</span>\n<span>  --num-replicas 2</span>\n<span></span>\n<span><span># List services</span></span>\n<span>clickhousectl cloud service list</span>\n<span></span>\n<span><span># Scale a running service</span></span>\n<span>clickhousectl cloud service scale &lt;service-id&gt; \\</span>\n<span>  --min-replica-memory-gb 24 \\</span>\n<span>  --max-replica-memory-gb 48 \\</span>\n<span>  --num-replicas 3</span></code></pre></div>\n<h2 id=\"destructive-operations-and-permissions\"></h2>\n<p>clickhousectl supports destructive operations — removing servers, dropping data, deleting Cloud services — as you'd expect from a CLI.</p>\n<p>Using the CLI with AI agents means those agents inherit the ability to perform destructive operations. We're still investigating what good looks like for agent guardrails here, so we'd encourage you to be cautious when pairing agents with clickhousectl around production resources.</p>\n<p>For ClickHouse Cloud, clickhousectl supports two authentication methods: OAuth and API keys. OAuth uses a device flow that opens your browser. Credentials obtained through OAuth are read-only, meaning you can list services, run queries, and inspect resources, but you cannot perform destructive operations. To create, scale, delete, or otherwise modify Cloud resources, you must authenticate with an API key.</p>\n<p>API keys are created at the organization level, so an agent authenticated with a key is scoped to that organization and can't escape to another. You're responsible for creating the key and selecting its permissions — read-write across all services, read-only on some and read-write on others, or whatever granularity fits your setup.</p>\n<h2 id=\"agent-skills\"></h2>\n<p><code>clickhousectl</code> can also install the official <a target=\"_blank\" href=\"https://github.com/ClickHouse/agent-skills\">ClickHouse Agent Skills</a> directly into your coding agents. In addition to the existing best practices skill, we’ve added 2 new skills that help your agent work with ClickHouse locally and in the cloud using the CLI.</p>\n<div><pre><code><span><span># Interactive: choose your agents</span></span>\n<span>clickhousectl skills</span>\n<span></span>\n<span><span># Non-interactive: install into all detected agents automatically</span></span>\n<span>clickhousectl skills --detected-only</span></code></pre></div>\n<h2 id=\"get-started\"></h2>\n<p><code>clickhousectl</code> is in beta for macOS and Linux.</p>\n<div><pre><code><span>curl https://clickhouse.com/cli | sh</span></code></pre></div>\n<p>Tip: A <code>chctl</code> alias is created automatically for convenience.</p>\n<p>We'd love feedback. If you hit issues or have ideas for what the CLI should do next, <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhousectl\">let us know on GitHub</a>.</p></div></article>"
