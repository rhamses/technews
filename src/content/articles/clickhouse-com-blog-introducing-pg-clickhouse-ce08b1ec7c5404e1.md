contentHtml: "<div><p>Over the last year, we’ve noticed a strong pattern in customers who’ve migrated their analytics workloads to ClickHouse Cloud: <a target=\"_blank\" href=\"https://www.postgresql.org/\">After self-hosted ClickHouse, PostgreSQL</a> is the most common source of migrations. <a target=\"_blank\" href=\"https://clickhouse.com/cloud/clickpipes\">ClickPipes</a> made data replication and migrations easy for these use-cases. However, we found that users still face significant challenges migrating queries and application code from PostgreSQL to ClickHouse. To address this, a few months ago we started looking into ways to simplify and reduce the time required to migrate analytical queries from PostgreSQL to ClickHouse.</p>\n<p>Today, we’re pleased to release <a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_clickhouse/\">pg_clickhouse</a> v0.1.0, an Apache 2-licensed PostgreSQL <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/sql-createextension.html\">extension</a> to transparently execute analytics queries on ClickHouse directly from PostgreSQL.</p>\n<p>Download pg_clickhouse from:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://pgxn.org/dist/pg_clickhouse\">PGXN</a></li>\n<li><a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_clickhouse/releases\">GitHub</a></li>\n</ul>\n<p>Or kick the tires by spinning up a Docker instance:</p>\n<div><pre><code><span>docker run --name pg_clickhouse -e POSTGRES_PASSWORD=my_pass </span>\n<span>       -d ghcr.io/clickhouse/pg_clickhouse:18</span></code></pre></div>\n<p>Consider starting with the <a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_clickhouse/blob/main/doc/tutorial.md\">tutorial</a>, or watch Sai run through the tutorial in the video below.</p>\n<h2 id=\"goals\"></h2>\n<p>Consider the common case where an organization builds an application backed by Postgres, including not only business data and transaction processing, but logging and metrics, as well. As the product grows, user traffic and data volume exponentially increase. As a result, the analytical queries powering both real-time customer-facing features and observability systems begin to slow down.</p>\n<p>Developers frequently mitigate these issues by using PostgreSQL read replicas, a provisional solution, at best. Eventually, they look to move the workload to a specialized analytics database such as ClickHouse. <a target=\"_blank\" href=\"https://clickhouse.com/cloud/clickpipes\">ClickPipes</a> powers rapid data migration, but what to do with the existing PostgreSQL queries against that data, often created by SQL libraries or <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Object%E2%80%93relational_mapping\">ORM</a>s?</p>\n<blockquote>\n<p>The time-consuming part isn’t moving data; ClickPipes has that bit nailed. It’s rewriting months or years of analytics SQL baked into dashboards, ORMs, and cron jobs.</p>\n</blockquote>\n<p>We imagined a PostgreSQL extension to reduce the need to migrate those queries at all, where one could follow the data migration with the workload migration simply by pointing those queries at a new Postgres database or schema.</p>\n<p>Thus we set forth to build pg_clickhouse with a number of goals in mind:</p>\n<ol>\n<li>Provide ClickHouse query execution from PostgreSQL</li>\n<li>Allow existing PostgreSQL queries to run unmodified</li>\n<li>Push down query execution to ClickHouse</li>\n<li>Create a foundation for continual query and <a target=\"_blank\" href=\"https://www.postgresql.org/about/featurematrix/detail/postgres_fdw-pushdown/\">pushdown</a> evolution</li>\n</ol>\n<p>What if ClickHouse tables looked just like regular PostgreSQL tables? Say they live in a separate schema from the existing Postgres analytics tables, but provide the identical structure? This pattern would allow existing queries to work as before, with just a change to <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/ddl-schemas.html#DDL-SCHEMAS-PATH\">search_path</a>.</p>\n<h2 id=\"history\"></h2>\n<p>The <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/SQL/MED\">SQL/MED</a> addresses exactly this use case by providing database extensions, called <em>foreign data wrappers,</em> to allow external data management via SQL. PostgreSQL has supported <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/ddl-foreign-data.html\">foreign data wrappers</a> since version 9.3 back in 2011, and a <a target=\"_blank\" href=\"https://wiki.postgresql.org/wiki/Foreign_data_wrappers\">robust array of “FDW” extensions</a>, as they’re commonly<br>\ncalled, has grown in the ensuing years.</p>\n<p>We cast about for existing solutions, and quickly found and validated <a target=\"_blank\" href=\"https://github.com/ildus/clickhouse_fdw\">clickhouse_fdw</a>, developed by <a target=\"_blank\" href=\"https://github.com/ildus\">Ildus Kurbangaliev</a> for <a target=\"_blank\" href=\"https://www.adjust.com/\">Adjust</a> based on <a target=\"_blank\" href=\"https://github.com/Percona-Lab/clickhousedb_fdw\">initial work</a> by <a target=\"_blank\" href=\"https://github.com/ibrarahmad\">Ibrar Ahmed</a> at <a target=\"_blank\" href=\"https://www.percona.com/\">Percona</a>. It supports not only raw data access, but query <a target=\"_blank\" href=\"https://www.postgresql.org/about/featurematrix/detail/postgres_fdw-pushdown/\">pushdown</a>, including for some <code>JOIN</code>s and aggregate functions.</p>\n<p>The project originated in 2019 from a fork of <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/postgres-fdw.html\">postgres_fdw</a>, the canonical reference implementation for PostgreSQL FDWs, as well as a fork of the <a target=\"_blank\" href=\"https://github.com/clickHouse/clickhouse-cpp/\">ClickHouse C++ library</a>. Sadly, it has seen only basic maintenance work since late 2020, mostly patches to ensure it works with newer versions of PostgreSQL. clickhouse_fdw was a great start, but hasn’t benefited from recent pushdown improvements in the PostgreSQL FDW API, including support for advanced aggregations, SEMI-JOINs, subqueries and more. It also lacked testing and support for platforms beyond Linux and lagged updates for new major PostgreSQL releases. After chatting about it with Ildus, we imported much of the functionality into a new project, <a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_clickhouse/\">pg_clickhouse</a>, keeping the <a target=\"_blank\" href=\"https://github.com/clickHouse/pg_clickhouse?tab=Apache-2.0-1-ov-file#readme\">Apache 2 license</a> for consistency of distribution.</p></div><div><h2 id=\"improvements\"></h2>\n<p>While <a target=\"_blank\" href=\"https://github.com/ildus/clickhouse_fdw\">clickhouse_fdw</a> and its predecessor, <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/postgres-fdw.html\">postgres_fdw</a>, provided the foundation for our FDW, we set out to modernize the code &amp; build process, to fix bugs &amp; address shortcomings, and to engineer into a complete product featuring near universal <a target=\"_blank\" href=\"https://www.postgresql.org/about/featurematrix/detail/postgres_fdw-pushdown/\">pushdown</a> for analytics queries and aggregations.</p>\n<p>Such advances include:</p>\n<ul>\n<li>Adopting standard <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/extend-pgxs.html\">PGXS</a> build pipeline for PostgreSQL extensions</li>\n<li>Adding prepared <code>INSERT</code> support to and adopting the latest supported<br>\nrelease of the <a target=\"_blank\" href=\"https://github.com/clickHouse/clickhouse-cpp/\">ClickHouse C++ library</a></li>\n<li>Creating test cases and CI <a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_clickhouse/actions\">workflows</a> to ensure it works on PostgreSQL versions 13-18 and ClickHouse versions 22-25</li>\n<li>Support for TLS-based connections for both the <a target=\"_blank\" href=\"https://clickhouse.com/docs/native-protocol/basics\">binary protocol</a> and the <a target=\"_blank\" href=\"https://clickhouse.com/docs/interfaces/http\">HTTP API</a>, required for <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a></li>\n<li>Bool, Decimal, and JSON support</li>\n<li>Transparent aggregate function pushdown, including for <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/functions-aggregate.html#FUNCTIONS-ORDEREDSET-TABLE\">ordered-set aggregates</a>: like <code>percentile_cont()</code></li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-part1#left--right-semi-join\">SEMI JOIN</a> pushdown</li>\n</ul>\n<p>These last two features significantly advance the fitness of a foreign data wrapper for an analytics database. After all, the entire point is to benefit from the execution speed of running analytics workload on a specialized and efficient engine. It wouldn’t be much use if it just returned millions of rows for PostgreSQL to aggregate.</p>\n<h2 id=\"aggregate-pushdown\"></h2>\n<p>Ordered-set aggregates are some of the hardest functions to map between engines because the syntax does not translate directly. Ideally, an aggregate function fully pushes down to ClickHouse for efficient execution. Consider this query adapted from our <a target=\"_blank\" href=\"https://github.com/ClickHouse/HouseClick\">HouseClick</a> project:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    type,</span>\n<span>    round(<span>min</span>(price)) <span>+</span> <span>100</span> <span>AS</span> min,</span>\n<span>    round(<span>max</span>(price)) <span>AS</span> max,</span>\n<span>    round(<span>percentile_cont</span>(<span>0.5</span>) <span>WITHIN</span> <span>GROUP</span> (<span>ORDER</span> <span>BY</span> price)) <span>AS</span> median,</span>\n<span>    round(<span>percentile_cont</span>(<span>0.25</span>) <span>WITHIN</span> <span>GROUP</span> (<span>ORDER</span> <span>BY</span> price)) <span>AS</span> \"25th\",</span>\n<span>    round(<span>percentile_cont</span>(<span>0.75</span>) <span>WITHIN</span> <span>GROUP</span> (<span>ORDER</span> <span>BY</span> price)) <span>AS</span> \"75th\"</span>\n<span><span>FROM</span></span>\n<span>    uk.uk_price_paid</span>\n<span><span>GROUP</span> <span>BY</span></span>\n<span>    type</span></code></pre></div>\n<p>This query uses 3 aggregate functions. <code>min()</code> and <code>max()</code> pushdown automatically, as they have the same names in both ClickHouse and PostgreSQL. But not <code>percentile_cont()</code>, which computes or averages the highest value within the percentage of all values. No such function exists in ClickHouse; nor does ClickHouse support the <code>WITHIN GROUP (ORDER BY x)</code> ordered set aggregate syntax.</p>\n<p>It does, however, provide <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/aggregate-functions/parametric-functions\">parametric aggregate functions</a>, including <code>quantile</code>, which implement a subset of the ordered set aggregate syntax. Thus, pg_clickhouse rewrites this query for ClickHouse as:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    type,</span>\n<span>    (round(<span>min</span>(price)) <span>+</span> <span>100</span>),</span>\n<span>    round(<span>max</span>(price)),</span>\n<span>    round(quantile(<span>0.5</span>)(price)),</span>\n<span>    round(quantile(<span>0.25</span>)(price)),</span>\n<span>    round(quantile(<span>0.75</span>)(price))</span>\n<span><span>FROM</span></span>\n<span>    uk.uk_price_paid</span>\n<span><span>GROUP</span> <span>BY</span></span>\n<span>    type</span></code></pre></div>\n<p>Note the transparent conversion of <code>percentile_cont()</code>s <em>direct arguments</em> (<code>0.5</code>, <code>0.25</code>, <code>0.75</code>) to <code>quantile()</code>’s <em>parametric constants,</em> and then the <code>ORDER BY</code> arguments to <em>function arguments</em>:</p>\n<div><pre><code><span>percentile_cont(0.5) WITHIN GROUP (ORDER BY price) =&gt; quantile(0.5)(price)</span></code></pre></div>\n<p>More than that, pg_clickhouse, like clickhouse_fdw before it, translates <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/sql-expressions.html#SYNTAX-AGGREGATES\">PostgreSQL aggregate</a> <code>FILTER (WHERE)</code> expressions to ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/aggregate-functions/combinators#-if\">-If combinators</a>.
