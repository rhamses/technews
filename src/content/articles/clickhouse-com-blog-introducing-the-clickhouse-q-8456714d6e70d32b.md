contentHtml: "<article><div><p>Real-world workloads, like dashboards, alerts, or interactive analytics, often run the same filters (WHERE conditions) over and over against the same data or against continuously growing data, as in observability scenarios. While ClickHouse is fast, these repeated scans can add up, especially when the filter is selective but doesn’t align well with the table’s primary index.</p>\n<p>To address this, ClickHouse 25.3 introduces the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/query-condition-cache\">query condition cache</a>: a lightweight, memory-efficient way to cache which ranges of data matched (or didn’t match) a given filter. The cache operates at the granule level, allowing ClickHouse to skip large portions of data during repeated query execution, even if the overall query shape changes.</p>\n<p>To celebrate the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-03#json-data-type-is-production-ready\">GA</a> of our new JSON type, we’ll demonstrate how the query condition cache works using a real-world JSON dataset: a stream of JSON events <a target=\"_blank\" href=\"https://clickhouse.com/blog/building-a-medallion-architecture-for-bluesky-json-data-with-clickhouse#reading-bluesky-data\">scraped</a> from <a target=\"_blank\" href=\"https://bsky.social/about\">Bluesky</a>, a popular social media platform. Along the way, we’ll take a look under the hood at how ClickHouse processes data and how the query condition cache fits into that flow. Spoiler: it’s fast, compact, and surprisingly effective, even for something as niche as spotting pretzel emojis in posts.</p>\n<p>Let’s dive in.</p>\n<h2 id=\"setting-the-stage-loading-100-million-json-events\"></h2>\n<p>We start by creating a simplified table on a test machine with 32 CPU cores:</p>\n<div><pre><code><span><span>CREATE TABLE</span> We’re still hardening its behavior, especially for edge cases like FINAL queries on ReplacingMergeTree and AggregatingMergeTree, before turning it on globally.</p>\n<p>We run the same query with the query condition cache enabled:</p>\n<div><pre><code><span><span>SELECT</span> <span>count</span>()</span>\n<span><span>FROM</span> bluesky</span>\n<span><span>WHERE</span></span>\n<span>    data.kind <span>=</span> <span>'commit'</span></span>\n<span>    <span>AND</span> data.commit.operation <span>=</span> <span>'create'</span></span>\n<span>    <span>AND</span> data.commit.collection <span>=</span> <span>'app.bsky.feed.post'</span></span>\n<span>    <span>AND</span> data.commit.record.text <span>LIKE</span> <span>'%🥨%'</span></span>\n<span>SETTINGS use_query_condition_cache <span>=</span> <span>true</span>;</span></code></pre></div>\n<!-- -->\n<div><pre><code><span>┌─count()─┐</span>\n<span>│      69 │</span>\n<span>└─────────┘</span>\n<span></span>\n<span>1 row in set. Elapsed: 0.481 sec. Processed 99.43 million rows, 7.96 GB (206.78 million rows/s., 16.54 GB/s.)</span>\n<span>Peak memory usage: 258.10 MiB.</span></code></pre></div>\n<p>The query behaves the same, nearly a full table scan with similar runtime and memory usage. However, with the query condition cache enabled, ClickHouse now stores information about each examined granule in the cache. We illustrate this with a diagram:</p>\n<p><span><img alt=\"Blog-query condition cache.002.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_query_condition_cache_002_e474c9cd4d.png&w=2048&q=75\"></span></p>\n<p>As shown in the trace log entries <a target=\"_blank\" href=\"https://clickhouse.com/blog/introducing-the-clickhouse-query-condition-cache#initial-trace-log-analysis\">above</a>, the selected granules are ① streamed by 32 parallel processing streams (blue dashed lines in the diagram) into the query engine to run ② a query counting Bluesky events using ③ a predicate that filters for posts with a pretzel emoji. Each stream ④ handles specific granule ranges, ⑤ filters all rows in each granule using the query predicate, ⑥ counts matching rows, and all partial results are ⑦ merged into the final output.</p>\n<p>During step ⑤, for every processed granule, ⑧ an entry is written to the ⑨ query condition cache: the cache key is formed from the table ID, the data part name the granule belongs to, and a hash of the query predicate. This maps to an array where each position corresponds to a granule’s index within the data part, and the value indicates whether none (<code>0</code>) or at least one (<code>1</code>) row matched the predicate. For selective filters (filters that let only a few rows pass), the array will contain lots of zeros.</p>\n<p>⊛ We note that writing to and reading from the cache can become a performance issue itself if not done carefully. To avoid that the cache turns into a bottleneck, ClickHouse batches multiple granules and writes their matches into the cache at once.</p>\n<h2 id=\"inspecting-the-query-condition-cache\"></h2>\n<p>We can query that cache via the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/system-tables/query_condition_cache\">query_condition_cache</a> system table:</p>\n<div><pre><code><span><span>SELECT</span> table_uuid, part_name, key_hash, matching_marks</span>\n<span><span>FROM</span> system.query_condition_cache LIMIT <span>1</span> FORMAT Vertical;</span></code></pre></div>\n<!-- -->\n<div><pre><code><span>table_uuid:     6f0f1c9d-3e98-4982-8874-27a18e8b0c2b</span>\n<span>part_name:      all_9_9_0</span>\n<span>key_hash:       10479296885953282043</span>\n<span>matching_marks: [1,1,1,0,0,0, ...]</span></code></pre></div>\n<h2 id=\"comparing-with-and-without-the-cache\"></h2>\n<p>Now that the query condition cache is filled for the predicate of our first example query, we can run the query a second time with the query condition cache enabled:</p>\n<div><pre><code><span><span>SELECT</span> <span>count</span>()</span>\n<span><span>FROM</span> bluesky</span>\n<span><span>WHERE</span></span>\n<span>    data.kind <span>=</span> <span>'commit'</span></span>\n<span>    <span>AND</span> data.commit.operation <span>=</span> <span>'create'</span></span>\n<span>    <span>AND</span> data.commit.collection <span>=</span> <span>'app.bsky.feed.post'</span></span>\n<span>    <span>AND</span> data.commit.record.text <span>LIKE</span> <span>'%🥨%'</span></span>\n<span>SETTINGS use_query_condition_cache <span>=</span> <span>true</span>;</span></code></pre></div>\n<!-- -->\n<div><pre><code><span>┌─count()─┐</span>\n<span>│      69 │</span>\n<span>└─────────┘</span>\n<span></span>\n<span>1 row in set. Its size is configurable via <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/server-configuration-parameters/settings#query_condition_cache_size\">query_condition_cache_size</a> (default: 100 MB). At that 100 MB size, it can hold ~839 million (100 * 1024 * 1024 * 8) granule entries—each granule covering 8,192 rows—allowing up to 6.8 trillion rows with one column. In practice, this total is divided by the number of columns used in the filter. This stands in contrast to the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/query-cache\">query result cache</a>, which maps queries to their complete result sets, typically consuming significantly more memory per cached entry.</p>\n<h2 id=\"reusing-the-predicate-top-pretzel-post-languages\"></h2>\n<p>The best part of the new query condition cache is that it operates at the level of the query predicate, not the full query. This means any query using the same predicate can benefit in the same way, regardless of what else the query is doing. In contrast, the <code>query result cache</code> stores complete results for entire queries, so it can’t (<a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/issues/57490\">currently</a>) be reused across different queries, even if they share the same filter logic.</p>\n<p>We demonstrate the advantage with another pretzel post analysis query that returns the top post languages:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    arrayJoin(<span>CAST</span>(data.commit.record.langs, <span>'Array(String)'</span>)) <span>AS</span> <span>language</span>,</span>\n<span>    <span>count</span>() <span>AS</span> count</span>\n<span><span>FROM</span> bluesky</span>\n<span><span>WHERE</span></span>\n<span>    data.kind <span>=</span> <span>'commit'</span></span>\n<span>    <span>AND</span> data.commit.operation <span>=</span> <span>'create'</span></span>\n<span>    <span>AND</span> data.commit.collection <span>=</span> <span>'app.bsky.feed.post'</span></span>\n<span>    <span>AND</span> data.commit.record.text <span>LIKE</span> <span>'%🥨%'</span></span>\n<span><span>GROUP</span> <span>BY</span> <span>language</span></span>\n<span><span>ORDER</span> <span>BY</span> count <span>DESC</span></span>\n<span>SETTINGS use_query_condition_cache <span>=</span> <span>true</span>;</span></code></pre></div>\n<!-- -->\n<div><pre><code><span>┌─language─┬─count─┐</span>\n<span>│ en       │    38 │</span>\n<span>│ de       │    10 │</span>\n<span>│ ja       │     8 │</span>\n<span>│ es       │     5 │</span>\n<span>│ pt       │     2 │</span>\n<span>│ nl       │     1 │</span>\n<span>│ zh       │     1 │</span>\n<span>│ el       │     1 │</span>\n<span>│ fr       │     1 │</span>\n<span>└──────────┴───────┘</span>\n<span></span>\n<span>9 rows in set.
