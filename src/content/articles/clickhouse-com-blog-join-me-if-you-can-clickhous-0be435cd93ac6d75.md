In <a target=\"_blank\" href=\"https://clickhouse.com/blog/join-me-if-you-can-clickhouse-vs-databricks-snowflake-join-performance\">Part 1</a>, we ran 17 join-heavy queries with no tweaks, and ClickHouse still came out ahead: faster and cheaper than Databricks and Snowflake.</p>\n<p>This post is about going one step further. The join queries ran unmodified, fast and cheap, right out of the gate.</p>\n<p>But why stop there? Let’s see how far we can push performance with a little ClickHouse-native tuning.</p>\n<p>In this post, we’ll show how turning your dimension tables into in-memory dictionaries can supercharge your queries. It’s one of the easiest ways to turbocharge join lookups, and it’s a drop-in change that can unlock serious performance gains.</p>\n<p>Let’s dive in.</p>\n<h2 id=\"supercharge-your-joins-with-dictionaries\"></h2>\n<p>Let’s introduce the star of this tuning technique: <a target=\"_blank\" href=\"https://clickhouse.com/blog/faster-queries-dictionaries-clickhouse\">dictionaries</a>.</p>\n<p>If you’re running queries with joins, especially foreign key joins on small dimension tables in <a target=\"_blank\" href=\"https://clickhouse.com/resources/engineering/real-time-analytics-star-schema-joins\">star or snowflake schemas</a>, dictionaries can make a big difference.</p>\n<h3 id=\"why-dictionaries\"></h3>\n<p>Dictionaries let you load a table into memory as a fast, key-value structure, optimized for ultra-low-latency lookups. When one side of a join fits into memory (like a dimension table), you can replace a traditional join with a dictionary lookup and get a speed boost in return.</p>\n<p>Let’s revisit the benchmark setup.</p>\n<p>The original dataset simulates orders at a national coffee chain and consists of:</p>\n<ul>\n<li>Sales: the main fact table (orders)</li>\n<li>Products: a product dimension table</li>\n<li>Locations: a store/location dimension table</li>\n</ul>\n<p>These were the same tables we used in Part 1, and most of the queries rely on foreign key joins, typically between the large fact table and smaller dimension tables, making them ideal for in-memory dictionaries.</p>\n<p>Instead of joining against tables on disk, we’ll load the Products and Locations tables into dictionaries, and show how this simple tuning step unlocks even faster performance.</p>\n<h3 id=\"from-tables-to-dictionaries-how-to-migrate-dimension-tables\"></h3>\n<p>Let’s walk through how to turn your existing dimension tables into dictionaries.</p>\n<p>ClickHouse dictionaries are incredibly flexible; you can build them from virtually any source ClickHouse can query. You can load them from any format or location that ClickHouse can read from, which includes a wide range of file formats (like Parquet, Arrow, JSON) and integration points (like S3, HDFS, Kafka, and tables in open formats like Iceberg or Delta Lake). If ClickHouse can query it, you can likely build a dictionary from it.</p>\n<h4 id=\"migrating-the-locations-dimension-table-key-lookups-with-a-hashed-key-dictionary\"></h4>\n<p>We’re migrating the Locations dimension table from an existing Iceberg table in S3:</p>\n<div><pre><code><span><span>CREATE</span> DICTIONARY dicts.dict_locations</span>\n<span>(</span>\n<span>    location_id String,</span>\n<span>    record_id   String,</span>\n<span>    city        String,</span>\n<span>    state       String,</span>\n<span>    country     String,</span>\n<span>    region      String</span>\n<span>)</span>\n<span><span>PRIMARY KEY</span> location_id</span>\n<span>SOURCE(CLICKHOUSE(</span>\n<span>         QUERY \"</span>\n<span>            SELECT</span>\n<span>                COALESCE(location_id, '') AS location_id,</span>\n<span>                COALESCE(record_id, '') AS record_id,</span>\n<span>                COALESCE(city, '') AS city,</span>\n<span>                COALESCE(state, '') AS state,</span>\n<span>                COALESCE(country, '') AS country,</span>\n<span>                COALESCE(region, '') AS region</span>\n<span>            FROM icebergS3('s3://clickhouse-datasets/coffeeshop/dim_locations/')\"))</span>\n<span>LIFETIME(<span>0</span>)</span>\n<span>LAYOUT(complex_key_hashed());</span></code></pre></div>\n<p>This <code>dict_locations</code> dictionary loads from an external Iceberg table and will be automatically available on all ClickHouse Cloud compute nodes. We set the LIFETIME to 0 to indicate that the content is static and won’t be automatically refreshed.</p>\n<p>All lookups into the Locations dimension table in the <a target=\"_blank\" href=\"https://github.com/sdairs/coffeeshop-benchmark/blob/main/clickhouse-cloud/queries.sql\">benchmark queries</a> are <strong>simple key lookups</strong> by <code>location_id</code> (e.g. 'AUSTX156' or 'HOUTX133'). We use the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/dictionaries#complex_key_hashed\">complex_key_hashed</a> dictionary layout to support fast in-memory access with String keys, since layouts like <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/dictionaries#flat\">flat</a> and <a target=\"_blank\" href=\"http://reference/\">hashed</a> only support UInt64 keys.</p>\n<blockquote>\n<p>The dictionary layout defines how content is stored in memory, optimized for specific lookup patterns.</p>\n</blockquote>\n<h4 id=\"migrating-the-products-dimension-table-time-aware-lookups-with-a-range-dictionary\"></h4>\n<p>To give a second source data example, we’re migrating the Products dimension table directly from its native MergeTree table used in Part 1:</p>\n<div><pre><code><span><span>CREATE</span> <span>OR</span> REPLACE DICTIONARY dicts.dict_products (</span>\n<span>    record_id String,</span>\n<span>    product_id String,</span>\n<span>    name String,</span>\n<span>    category String,</span>\n<span>    subcategory String,</span>\n<span>    standard_cost Float64,</span>\n<span>    standard_price Float64,</span>\n<span>    from_date <span>Date</span>,</span>\n<span>    to_date <span>Date</span></span>\n<span>)</span>\n<span><span>PRIMARY KEY</span> name</span>\n<span>SOURCE(CLICKHOUSE(db <span>'coffeeshop'</span> <span>table</span> <span>'dim_products'</span>))</span>\n<span>LIFETIME(<span>0</span>)</span>\n<span>LAYOUT(COMPLEX_KEY_RANGE_HASHED())</span>\n<span><span>RANGE</span>(MIN from_date MAX to_date);</span></code></pre></div>\n<p>All lookups into the Products dimension table in the benchmark queries are <strong>range-based</strong> using <code>from_date</code> and <code>to_date</code> to find which product version was active at a given time (e.g. as <a target=\"_blank\" href=\"https://github.com/sdairs/coffeeshop-benchmark/blob/dd63a6c60f61d5ff0b145d4ee2cb0ea3406d38c8/clickhouse-cloud/queries.sql#L83\">seen</a> in Q4).</p>\n<p>To handle this efficiently, we use a <strong><a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/dictionaries#range_hashed\">Range Dictionary</a></strong>. It’s optimized for exactly this use case: matching a given key and a time to the correct product version. In memory, ClickHouse builds a hash map on the primary key and performs a fast binary search across sorted date ranges.</p>\n<p><strong>Just one catch</strong>: make sure the source data has no overlapping ranges for the same key, otherwise, the dictionary will only return the first match, which may not be correct. We <a target=\"_blank\" href=\"https://pastila.nl/?01c0241e/fc6223d0aa17106f21f85d1bf84671e6#ROElgbNXajmPEZCgL3xrkQ==\">checked</a> that there are no overlapping ranges in the original Products dimension table.</p>\n<blockquote>\n<p>ClickHouse supports more dictionary layouts for advanced use cases. Like <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=ESlAhUJMoz8&index=51\">regex matching</a>, <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=4dxMAqltygk&index=32\">CIDR range lookup</a>, or <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=FyRsriQp46E&index=19\">point-in-polygon geospatial queries</a>. We won’t use them here, but if you’re classifying user agents, geolocating IPs, or mapping GPS points, they’re worth checking out.</p>\n</blockquote>\n<h3 id=\"updating-your-queries-to-use-dictionaries\"></h3>\n<p>Once the dictionaries are set up, updating the queries is straightforward. Each join becomes a lightning-fast in-memory lookup. Here’s how we transformed the joins:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>     f.order_date,</span>\n<span>     l.city,</span>\n<span>     p.subcategory</span>\n<span>   <span>FROM</span> fact_sales f</span>\n<span>① <span>JOIN</span> dim_locations l</span>\n<span>     <span>ON</span> f.location_id <span>=</span> l.location_id</span>\n<span>② <span>JOIN</span> dim_products p</span>\n<span>     <span>ON</span> f.product_name <span>=</span> p.name</span>\n<span>    <span>AND</span> f.order_date <span>BETWEEN</span> p.from_date <span>AND</span> p.to_date</span>\n<span>   <span>WHERE</span> …</span>\n<span>   <span>GROUP</span> <span>BY</span> …</span>\n<span>   <span>ORDER</span> <span>BY</span> …</span></code></pre></div>\n<p>The Sales fact table is joined with:</p>\n<p>① <strong>The Locations dimension table</strong> using <code>location_id</code> as join key</p>\n<p>② <strong>The Products dimension table</strong> using a join key combination of <code>product_name</code> and a date range filter (<code>order_date</code> BETWEEN <code>from_date</code> AND <code>to_date</code>)</p>\n<p>We swap the two JOINs from above with two dictionary lookups:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>     f.order_date,</span>\n<span>①   dictGet(</span>\n<span>       <span>'dicts.dict_locations'</span>, <span>'city'</span>,</span>\n<span>       f.location_id) <span>AS</span> city,</span>\n<span>②   dictGet(</span>\n<span>       <span>'dicts.dict_products'</span>,<span>'subcategory'</span>,</span>\n<span>       f.product_name, f.order_date) <span>AS</span> subcategory,</span>\n<span>   <span>FROM</span> fact_sales f</span>\n<span>   <span>WHERE</span> …</span>\n<span>   <span>GROUP</span> <span>BY</span> …</span>\n<span>   <span>ORDER</span> <span>BY</span> …</span></code></pre></div>\n<p>① A straightforward <strong>one-to-one lookup in the dict_locations dictionary</strong> using <code>location_id</code> as the key.\n<br>→ This replaces a simple equality join with an in-memory dictionary lookup.</p>\n<p>② A <strong>range-based lookup in the dict_products dictionary</strong> using a compound key of <code>product_name</code> and <code>order_date</code>.\n<br>→ This replaces a join with a range predicate (<code>order_date</code> BETWEEN <code>from_date</code> AND <code>to_date</code>) and ensures the correct product version is returned based on time.</p>\n<p>These small changes remove full joins from the query plan, replacing them with ultra-fast lookups in memory. The pattern is repeatable and easy to apply across <a target=\"_blank\" href=\"https://github.com/sdairs/coffeeshop-benchmark/blob/main/clickhouse-cloud-tuned/queries.sql\">all</a> 17 benchmark queries.</p>\n<h2 id=\"results-how-much-faster\"></h2>\n<p>With all the dimension lookups swapped to dictionaries, and the queries adapted, we re-ran the benchmark queries.
