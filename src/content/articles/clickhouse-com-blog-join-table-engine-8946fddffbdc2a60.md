contentHtml: "<div><h2 id=\"user-content-dictionaries-in-clickhouse\"></h2>\n<p>When you move data from your transactional or event-based data sources to an analytical database like ClickHouse, you will likely consider modeling a dimensional schema according to the <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Dimensional_modeling\">Kimball methodology</a>.</p>\n<blockquote>\n<p><a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Dimensional_modeling\">Dimensional modeling</a> always uses the concepts of facts (measures), and dimensions (context). Facts are typically (but not always) numeric values that can be aggregated, and dimensions are groups of hierarchies and descriptors that define the facts.</p>\n</blockquote>\n<p>It follows that fact tables are typically immutable, and data are appended to them; whereas dimension tables are smaller, and subject to (infrequent) updates (<a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Slowly_changing_dimension\">slowly changing dimensions</a>). When you run an analytical query, you have to join those dimensions against the fact table.</p>\n<p>One common approach to do this in ClickHouse is to have a copy of the dimension data in memory in a <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/special/dictionary\">Dictionary</a>. This approach enables <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-direct-join-part4#direct-join\">Direct Joins</a> and is <a target=\"_blank\" href=\"https://clickhouse.com/blog/postgres-to-clickhouse-data-modeling-tips-v2#optimizing-joins\">recommended for optimizing join performance</a>.</p>\n<p>A Dictionary is set up by specifying, among others, the <code>SOURCE</code> and <code>LIFETIME</code> attributes. ClickHouse pulls fresh data from the source and uses <code>LIFETIME</code> to determine how often it should refresh the Dictionary. But some customers asked me: Isn't there a way to update a Dictionary like a regular table? And indeed, there is a way to achieve this, using another special table engine.</p>\n<h2 id=\"user-content-the-join-table-engine\"></h2>\n<p>The <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/special/join\"><code>Join</code> table engine</a> is just what we need here. It is an in-memory structure, laying out data for a <em>specific</em> type of join that has to be stated in the table definition, and it is backed by a persistence layer. Setting up the <code>Join</code> table, you need to configure</p>\n<ul>\n<li><em>join strictness</em></li>\n<li><em>join type</em></li>\n<li>the <em>key column(s)</em> you want to use in the join.</li>\n</ul>\n<h3 id=\"user-content-join-strictness\"></h3>\n<p>This can be <code>ANY</code> or <code>ALL</code>. With <code>ALL</code>, all matching rows are taken from the <code>Join</code> table; <code>ANY</code> takes only the latest one.</p>\n<p>This means with <code>ANY</code> type <em>an <strong><code>INSERT</code></strong> becomes an <strong><code>UPSERT</code></strong> by key:</em> you update a dimension row by inserting another row with the same key.</p>\n<h3 id=\"user-content-join-type\"></h3>\n<p>One of ClickHouse's <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/select/join#supported-types-of-join\">join types</a>, like <code>INNER</code> or <code>LEFT</code> or <code>RIGHT</code>. For dimensional modeling, you will mostly use <code>LEFT</code>.</p>\n<h2 id=\"user-content-querying-a-join-table\"></h2>\n<p>While a <code>Join</code> table can be queried like any regular table using <code>SELECT</code>, there are two more ways of using it:</p>\n<ol>\n<li>If you place the <code>Join</code> table in a <code>JOIN</code> query where the join parameters match the ones in the definition of the table, ClickHouse will automatically know to use the Direct Join algorithm.</li>\n<li>You can look up values for a given key using <code>joinGet</code>. This works just like <code>dictGet</code> for Dictionaries.</li>\n</ol>\n<h2 id=\"user-content-drawbacks-in-the-open-source-implementation\"></h2>\n<p>So a <code>Join</code> table with <code>ANY LEFT</code> join condition would be just the thing to implement a <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Slowly_changing_dimension#Type_1:_overwrite\">Type 1 slowly changing dimension</a>, right? You can update values for a given key and have a high performing join. Why don't we use it all the time, then?</p>\n<p>It turns out that the implementation of the <code>Join</code> table engine in open source ClickHouse has a couple of drawbacks that make it less suitable for this use case:</p>\n<ol>\n<li><strong><code>Join</code> tables are not distributed</strong>; each cluster node would have to maintain its own copy/version of the table.</li>\n<li><strong>The persistence layer is not built for frequent inserts/updates</strong>. The Join table engine persists data as compressed Native-format .bin files in the table's data directory on disk (one file per INSERT batch). On server startup, these files are read back sequentially and the in-memory HashJoin hash table is reconstructed from them. This means each update will create a new numbered .bin file. There is no background compaction process — files are never merged automatically. Over time, this leads to performance degradation.</li>\n</ol>\n<h2 id=\"user-content-implementation-in-clickhouse-cloud\"></h2>\n<p><strong>These issues have been solved very elegantly in ClickHouse Cloud.</strong> In ClickHouse Cloud, a <code>Join</code> table is actually transparently implemented as a <code>SharedJoin</code> table with a MergeTree family backing table:</p>\n<ul>\n<li>for <code>ALL</code> join, this is a <code>MergeTree</code> table</li>\n<li>for <code>ANY</code> join, a <code>ReplacingMergeTree</code> table.</li>\n</ul>\n<p>You can find these tables in <code>system.tables</code>. The naming convention for the underlying table is <code>.inner_id.SharedJoin.&lt;uuid of Join table&gt;</code>.</p>\n<blockquote>\n<p><strong>Note:</strong> there is a setting <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#join_any_take_last_row\"><code>join_any_take_last_row</code></a> that is <strong>not</strong> honored</p>\n</blockquote>\n<p>The in-memory table is populated from the persistent (underlying) table using a query (which includes <code>FINAL</code> in the case of <code>ANY</code> join) on insert to Join table (with filter to select only newest data) and on table load on startup.</p>\n<h2 id=\"user-content-example-data-enrichment\"></h2>\n<p>Probably the most meaningful use case is enrichment / dimensional modeling with an <code>ANY LEFT</code> join. To illustrate this specific case, let's take the example from the ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/special/join#example\">docs</a> and modify it a bit:</p>\n<div><pre><code><span><span>-- Create the fact table and insert some data</span></span>\n<span><span>CREATE</span> <span>OR</span> REPLACE <span>TABLE</span> id_val (</span>\n<span>    `id` UInt32,</span>\n<span>    `val` UInt32</span>\n<span>) ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (id);</span>\n<span></span>\n<span><span>INSERT INTO</span> id_val <span>VALUES</span></span>\n<span>    (<span>1</span>, <span>11</span>), (<span>2</span>, <span>12</span>), (<span>3</span>, <span>13</span>);</span>\n<span></span>\n<span><span>-- Creating the right-side Join table:</span></span>\n<span><span>CREATE</span> <span>OR</span> REPLACE <span>TABLE</span> id_val_join (</span>\n<span>    `id` UInt32,</span>\n<span>    `val` UInt8</span>\n<span>) ENGINE <span>=</span> <span>Join</span>(<span>ANY</span>, <span>LEFT</span>, id);</span>\n<span></span>\n<span><span>-- Insert some values</span></span>\n<span><span>INSERT INTO</span> id_val_join <span>VALUES</span></span>\n<span>    (<span>1</span>, <span>21</span>), (<span>1</span>, <span>22</span>), (<span>3</span>, <span>23</span>);</span>\n<span></span>\n<span><span>-- Enrichment query</span></span>\n<span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> id_val</span>\n<span><span>ANY</span> <span>LEFT</span> <span>JOIN</span> id_val_join <span>USING</span> (id);</span></code></pre></div>\n<div><pre><code><span>┌─<span>id</span>─┬─val─┬─id_val_join.val─┐</span>\n<span>1. │  1 │  11 │              22 │</span>\n<span>2. │  2 │  12 │               0 │</span>\n<span>3. │  3 │  13 │              23 │</span>\n<span>   └────┴─────┴─────────────────┘</span></code></pre></div>\n<p>Now, let's find out what happens in the <code>Join</code> table and in the underlying table when we upsert an entry for key <code>1</code>.</p>\n<div><pre><code><span><span>-- And another insert</span></span>\n<span><span>INSERT INTO</span> id_val_join <span>VALUES</span> (<span>1</span>,<span>42</span>);</span></code></pre></div>\n<p>Look up the underlying table:</p>\n<div><pre><code><span><span>SELECT</span> database, name, uuid, engine</span>\n<span><span>FROM</span> system.tables</span>\n<span><span>WHERE</span> name <span>=</span> <span>'id_val_join'</span></span>\n<span>FORMAT Vertical;</span></code></pre></div>\n<div><pre><code><span>database:                         default</span>\n<span>name:                             id_val_join</span>\n<span>uuid:                             64f169ee-977d-46c2-b067-580fdf8c1d4b</span>\n<span>engine:                           SharedJoin</span></code></pre></div>\n<p>The <code>Join</code> table deduplicates and keeps the latest entry only:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> id_val_join;</span></code></pre></div>\n<div><pre><code><span>┌─<span>id</span>─┬─val─┐</span>\n<span>1. │  3 │  23 │</span>\n<span>2. │  1 │  42 │</span>\n<span>   └────┴─────┘</span></code></pre></div>\n<p>Constructing the underlying <code>ReplacingMergeTree</code> table from the UUID, we see this one retains the duplicates until they are merged out:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> default.`.inner_id.SharedJoin<span>.64</span>f169ee<span>-977</span>d<span>-46</span>c2<span>-</span>b067<span>-580</span>fdf8c1d4b`;</span></code></pre></div>\n<div><pre><code><span>┌─<span>id</span>─┬─val─┐</span>\n<span>1. │  1 │  22 │</span>\n<span>2. │  3 │  23 │</span>\n<span>3. │  1 │  42 │</span>\n<span>   └────┴─────┘</span></code></pre></div>\n<p>Finally, running the enrichment query again, we see how the updated dimension entry reflects in the result:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> id_val</span>\n<span><span>ANY</span> <span>LEFT</span> <span>JOIN</span> id_val_join <span>USING</span> (id);</span></code></pre></div>\n<div><pre><code><span>┌─<span>id</span>─┬─val─┬─id_val_join.val─┐</span>\n<span>1. │  1 │  11 │              42 │</span>\n<span>2. │  2 │  12 │               0 │</span>\n<span>3. │  3 │  13 │              23 │</span>\n<span>   └────┴─────┴─────────────────┘</span></code></pre></div>\n<p>Every time you insert a new row or a set of rows:</p>\n<ul>\n<li>The data is inserted into the underlying <code>ReplacingMergeTree</code> table.</li>\n<li>The in-memory representation is updated on insert to the Join table (with a filter on block ID to select only newest data) and on table load on startup.</li>\n<li>This query also applies <code>FINAL</code>, so the in-memory <code>Join</code> table will never have duplicates.</li>\n<li>The <code>join_any_take_last_row</code> is ignored. You always get the latest entry.</li>\n</ul>\n<h2 id=\"user-content-conclusion\"></h2>\n<ul>\n<li>The <code>Join</code> table engine in ClickHouse provides a precomputed hash map that can be used to speed up JOINs.</li>\n<li>Like a dictionary, a <code>Join</code> table is kept in memory. But it is backed by a persistence layer (saved in files).</li>\n<li>In ClickHouse Cloud, <code>Join</code> tables are automatically clustered and backed by full <code>MergeTree</code> tables, making them suitable for frequent updates.</li>\n<li>In particular, for dimensional modeling in ClickHouse Cloud, use <code>Join(ANY, LEFT, id)</code> — upserting, deduplication, and data compaction is automatically handled by the underlying <code>ReplacingMergeTree</code>!</li>\n</ul></div>"
