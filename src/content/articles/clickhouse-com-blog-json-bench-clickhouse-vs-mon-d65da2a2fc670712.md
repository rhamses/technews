In this post, we’re benchmarking it against other candidates to highlight its outstanding capabilities in handling JSON data.</p>\n<h4 id=\"json-support\"></h4>\n<p>We recently <a target=\"_blank\" href=\"https://clickhouse.com/blog/a-new-powerful-json-data-type-for-clickhouse\">built</a> a new powerful JSON data type for ClickHouse with true column-oriented storage, support for dynamically changing data structures <a target=\"_blank\" href=\"https://clickhouse.com/blog/a-new-powerful-json-data-type-for-clickhouse#challenge-2-dynamically-changing-data-without-type-unification\">without</a> type unification and the ability to query individual JSON paths really fast.</p>\n<h4 id=\"json-storage\"></h4>\n<p>ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/blog/a-new-powerful-json-data-type-for-clickhouse\">stores</a> the values of each unique JSON path as <a target=\"_blank\" href=\"https://clickhouse.com/blog/a-new-powerful-json-data-type-for-clickhouse#traditional-data-storage-in-clickhouse\">native columns</a>, allowing high data compression and, as we are demonstrating in this blog, maintaining the same <a target=\"_blank\" href=\"https://benchmark.clickhouse.com/\">high query performance</a> seen on classic types:</p>\n<p><span><img alt=\"JSON-Benchmarks.007.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FJSON_Benchmarks_007_6ec81b11c0.png&w=2048&q=75\"></span></p>\n<p>The diagram above sketches how the values from each unique JSON path are stored on disk in separate (highly compressed) column files (inside a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/parts#what-are-table-parts-in-clickhouse\">data part</a>). This ensures that ingested JSON documents are stored on disk, within each table part, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/best-practices/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">ordered</a> by the values of these paths. Additionally, ClickHouse generates a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/best-practices/sparse-primary-indexes#introduction\">sparse primary index</a> to automatically <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/best-practices/sparse-primary-indexes#the-primary-index-is-used-for-selecting-granules\">accelerate</a> queries that filter on these primary key columns:</p>\n<p><span><img alt=\"JSON-Benchmarks.008.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FJSON_Benchmarks_008_3e7fba21fe.png&w=2048&q=75\"></span></p>\n<p>Using JSON subcolumns as primary key columns enables better colocation of similar data within each column file, which can <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/best-practices/sparse-primary-indexes#optimal-compression-ratio-of-data-files\">increase</a> compression ratios for these column files, provided the primary key columns <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/best-practices/sparse-primary-indexes#optimal-compression-ratio-of-data-files\">are</a> arranged in ascending order of cardinality. The on-disk data ordering <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-faster-queries-with-projections-and-primary-indexes#utilize-indexes-for-preventing-resorting-and-enabling-short-circuiting\">also</a> prevents resorting and allows short-circuiting when a query's search sort order matches the physical data order.</p>\n<h4 id=\"flexible-compression-options\"></h4>\n<p>By default, ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/table#column_compression_codec\">applies</a> <code>lz4</code> compression in the self-managed version and <code>zstd</code> in <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> to each data column file individually, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/data-compression/compression-modes#block\">block-wise</a>.</p>\n<p>It is also <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/table#column_compression_codec\">possible</a> to define the compression codec(s) per individual column in the <code>CREATE TABLE</code> query. ClickHouse supports <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/table#general-purpose-codecs\">general-purpose</a>, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/table#specialized-codecs\">specialized</a>, and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/table#encryption-codecs\">encryption</a> codecs, which can also be <a target=\"_blank\" href=\"https://clickhouse.com/blog/optimize-clickhouse-codecs-compression-schema\">chained</a>.</p>\n<p>For its JSON type, ClickHouse currently supports defining codecs for the whole JSON field (e.g. <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/clickhouse/ddl_zstd.sql#L8\">here</a>, we change the codec from the default <code>lz4</code> to <code>zstd</code>).  We are <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/issues/68428\">planning</a> to support specifying codecs also per JSON path.</p>\n<h4 id=\"flexible-json-format-options\"></h4>\n<p>ClickHouse supports <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/formats\">over 20 different JSON formats</a> for ingesting data and returning query results.</p>\n<h4 id=\"query-processing\"></h4>\n<p>Due to ClickHouse’s outstanding performance in our <a target=\"_blank\" href=\"https://clickhouse.com/blog/json-bench-clickhouse-vs-mongodb-elasticsearch-duckdb-postgresql#benchmark-results\">benchmark results</a>, we’ve included a brief explanation of how it handles queries over JSON data.</p>\n<p>As mentioned earlier, ClickHouse stores the values of each unique JSON path similarly to traditional data types (e.g. integers), enabling <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#high-performance-aggregations-in-clickhouse\">high-performance aggregations</a> over JSON data.</p>\n<p>Built for internet-scale analytics, ClickHouse is <a target=\"_blank\" href=\"https://youtu.be/ZOZQCQEtrz8?si=XrQ-vMDiHEsgsrYq&t=103\">designed</a> to efficiently filter and aggregate data using the full resources available by fully parallelizing its <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/reference\">90+</a> built-in aggregation functions. This approach can be illustrated with the <code>avg</code> aggregation function:</p>\n<p><span><img alt=\"JSON-Benchmarks.009.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FJSON_Benchmarks_009_d2d2163ae6.png&w=2048&q=75\"></span></p>\n<p>The diagram above shows how ClickHouse ① processes an <code>avg</code> aggregation query referencing two JSON paths <code>c.a</code> and <code>c.b</code>. Using (only) the corresponding data columns <code>a.bin</code> and <code>b.bin</code>, ClickHouse processes <code>N</code> non-overlapping data ranges in parallel across <code>N</code> CPU cores on a single server. These data ranges are independent of the grouping key and are <a target=\"_blank\" href=\"https://www.vldb.org/pvldb/vol17/p3731-schulze.pdf\">dynamically balanced</a> to optimize workload distribution. This parallelization is made possible through the use of <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#-multi-core-parallelization\">partial aggregation states</a>.</p>\n<p>In our benchmark for ClickHouse, we also <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/clickhouse/physical_query_plans.sh\">track</a> the <a target=\"_blank\" href=\"https://youtu.be/hP6G2Nlz_cA\">physical execution plans</a>, introspecting this parallelization approach. For example, although <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#use_query_cache\">disabled by default</a>, ClickHouse provides a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/query-cache\">query result cache</a>.</p>\n<h3 id=\"mongodb\"></h3>\n<p><a target=\"_blank\" href=\"https://www.mongodb.com/\">MongoDB</a> is one of the most renowned <a target=\"_blank\" href=\"https://clickhouse.com/engineering-resources/json-database\">JSON databases</a>.</p>\n<h4 id=\"json-support\"></h4>\n<p>MongoDB stores all data natively as collections of <a target=\"_blank\" href=\"https://www.mongodb.com/resources/basics/json-and-bson\">BSON</a> documents, where BSON <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/BSON\">is</a> the binary representation of a JSON document.</p>\n<h4 id=\"json-storage\"></h4>\n<p>MongoDB’s default storage engine, <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/core/wiredtiger/#wiredtiger-storage-engine\">WiredTiger</a>, organizes data on disk as blocks that <a target=\"_blank\" href=\"https://source.wiredtiger.com/11.0.0/arch-data-file.html\">represent</a> pages of a <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/B-tree\">B-Tree</a>. The root and internal nodes store keys and references to other nodes, while the leaf nodes hold the data blocks for stored BSON documents:</p>\n<p><span><img alt=\"JSON-Benchmarks.011.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FJSON_Benchmarks_011_1c3970b491.png&w=2048&q=75\"></span></p>\n<p>MongoDB allows users to create secondary <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/indexes/#details\">indexes</a> on JSON paths to accelerate queries that filter on those paths. These indexes <a target=\"_blank\" href=\"https://www.slideshare.net/slideshow/mongodb-days-uk-indexing-and-performance-tuning/54794973#2\">are</a> structured as B-Trees, with each entry corresponding to an ingested JSON document and storing the values of the indexed JSON paths. These indexes are loaded into memory, enabling the query planner to <a target=\"_blank\" href=\"https://www.slideshare.net/slideshow/mongodb-days-uk-indexing-and-performance-tuning/54794973#2\">quickly</a> traverse the tree to locate matching documents, which are then loaded from disk for processing.</p>\n<h4 id=\"covered-index-scans\"></h4>\n<p>If a query references only indexed JSON paths, MongoDB can satisfy it entirely using the in-memory B-Tree index, without loading documents from disk. This optimization, known as a <a target=\"_blank\" href=\"https://www.slideshare.net/slideshow/mongodb-days-uk-indexing-and-performance-tuning/54794973#2\">covered index scan</a>, is triggered by <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/core/query-optimization/#covered-query\">covered queries</a>:</p>\n<p><span><img alt=\"JSON-Benchmarks.012.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FJSON_Benchmarks_012_ac6786dc13.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p>All five of our benchmark queries in MongoDB are covered queries. This is because the <a target=\"_blank\" href=\"https://clickhouse.com/blog/json-bench-clickhouse-vs-mongodb-elasticsearch-duckdb-postgresql#some-json-paths-can-be-used-for-indexes-and-data-sorting\">default compound index</a> we <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/mongodb/ddl_zstd.js#L6\">created</a> for all collections includes every field required by the queries. To follow <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/core/query-optimization/#performance\">best practices</a>, we also explicitly <a target=\"_blank\" href=\"https://clickhouse.com/blog/json-bench-clickhouse-vs-mongodb-elasticsearch-duckdb-postgresql#no-tuning\">enabled</a> covered index scans.</p>\n</blockquote>\n<p>You can confirm this by examining the <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/tree/c7afa7078aed72c55ff4441a2da635424fde7724/mongodb/results/_index_usage\">query execution plans</a>. For example, queries on the 1 billion documents collection <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/mongodb/results/_index_usage/_m6i.8xlarge_bluesky_1000m_zstd.index_usage\">show</a> only <code>IXSCAN</code> stages, with no <code>COLLSCAN</code> or <code>FETCH</code> <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/reference/explain-results/#explain-output-structure\">stages</a>. In contrast, <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/tree/c7afa7078aed72c55ff4441a2da635424fde7724/mongodb/results_without_covered_index_scans/_index_usage\">older plans</a>—before enabling covered index scans—<a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/mongodb/results_without_covered_index_scans/_index_usage/_m6i.8xlarge_bluesky_1000m_zstd.index_usage\">include</a> <code>COLLSCAN</code> or <code>FETCH</code>, indicating that documents were being loaded from disk.</p>\n<p>This method depends on the index fitting into memory. On our <a target=\"_blank\" href=\"https://clickhouse.com/blog/json-bench-clickhouse-vs-mongodb-elasticsearch-duckdb-postgresql#hardware-and-operating-system\">test machine</a> with 128 GB of RAM, the <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/mongodb/results/m6i.8xlarge_bluesky_1000m_zstd.json#L20\">27 GB index</a> for the largest dataset fits easily. In <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/sharding/\">sharded setups</a>, however, covered index scans require the index to <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/core/query-optimization/#restrictions-on-sharded-collection\">include</a> the shard key.</p>\n<h4 id=\"data-compression\"></h4>\n<p>WiredTiger <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/core/wiredtiger/#compression\">defaults</a> to block compression with the <a target=\"_blank\" href=\"https://google.github.io/snappy/\">snappy</a> library for collections and <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/reference/glossary/#std-term-prefix-compression\">prefix compression</a> for B-Tree indexes. Alternatively, <code>zstd</code> compression can be enabled for collections to achieve higher compression rates.</p>\n<h4 id=\"data-sorting\"></h4>\n<p>MongoDB supports <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/core/clustered-collections/\">clustered collections</a>, which store documents in the order of a specified <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/reference/method/db.createCollection/#std-label-db.createCollection.clusteredIndex\">clustered index</a>, helping to colocate similar data and improve compression. However, since clustered index keys <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/core/clustered-collections/#set-your-own-clustered-index-key-values\">must</a> be unique and are limited to a maximum size of 8 MB, we couldn’t use them for our test data.</p>\n<h4 id=\"caches\"></h4>\n<p>MongoDB relies on both the <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/core/wiredtiger/#memory-use\">WiredTiger internal cache</a> and the operating system’s page cache but does not have a query results cache. The WiredTiger cache, which stores recently accessed data and indexes, operates independently of the OS page cache. By default, its size is <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/core/wiredtiger/#memory-use\">set</a> to 50% of the available RAM minus 1 GB. This cache can only be cleared by restarting the MongoDB server.</p>\n<h4 id=\"limitations\"></h4>\n<p>The <code>time_us</code> JSON path in our <a target=\"_blank\" href=\"https://clickhouse.com/json-bench-clickhouse-vs-mongodb-elasticsearch-duckdb-postgresql#the-json-dataset---a-billion-bluesky-events\">Bluesky test data</a> contains microsecond-precision dates. Currently, MongoDB only supports <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/reference/method/Date/#behavior\">millisecond</a> precision, whereas ClickHouse handles <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/data-types/datetime64\">nanoseconds</a>.</p>\n<p>Additionally, MongoDB’s aggregation framework lacks a built-in <code>COUNT DISTINCT</code> operator. As a workaround, we use the less efficient <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/reference/operator/aggregation/addToSet/\">$addToSet</a> for benchmark <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/mongodb/queries_formatted.js#L31\">query ②</a>.</p>\n<h3 id=\"elasticsearch\"></h3>\n<p><a target=\"_blank\" href=\"https://www.elastic.co/elasticsearch\">Elasticsearch</a> is a JSON-based search and analytics engine.</p>\n<h4 id=\"json-support\"></h4>\n<p>Elasticsearch <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/docs-index_.html\">receives</a> all ingested data natively as JSON documents.</p>\n<h4 id=\"json-storage-and-data-compression\"></h4>\n<p>Ingested JSON data in Elasticsearch is indexed and stored in <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing#logical-and-physical-on-disk-data-structures\">various</a> data structures optimized for specific access patterns. These structures reside within a <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing#logical-and-physical-on-disk-data-structures\">segment</a>, the core indexing unit of <a target=\"_blank\" href=\"https://lucene.apache.org/\">Lucene</a>, the Java library that powers Elasticsearch’s search and analytics capabilities:</p>\n<p><span><img alt=\"JSON-Benchmarks.013.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FJSON_Benchmarks_013_0c4a7cf1a0.png&w=2048&q=75\"></span></p>\n<p>① <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/mapping-store.html\">Stored fields</a> serve as a document store for returning the original values of fields in query responses. By default, they also store ② <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/mapping-source-field.html\">_source</a>, which contains the original JSON documents ingested. Stored fields are compressed using the algorithm defined by the <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/index-modules.html\">index.codec</a> setting—<code>lz4</code> by default or <code>zstd</code> for higher compression ratios, albeit with slower performance.</p>\n<p>③ <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/doc-values.html\">Doc_values</a> store values from ingested JSON documents in a column-oriented on-disk structure optimized for analytical queries that aggregate and sort the data. Note that <code>doc_values</code> are not compressed with <code>lz4</code> or <code>zstd</code>. Instead, each column <a target=\"_blank\" href=\"https://lucene.apache.org/core/9_9_0/core/org/apache/lucene/codecs/lucene90/Lucene90DocValuesFormat.html\">is</a> encoded individually with specialized codecs based on the column values‘ data type, cardinality, etc.</p>\n<p><a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing#logical-and-physical-on-disk-data-structures\">Here</a>, we describe the other Lucene segment data structures, such as the ④ <code>inverted index</code>,  ⑤ <code>Bkd-trees</code>, and ⑥ <code>HNSW graphs</code> in more detail.</p>\n<h4 id=\"the-role-of-source\"></h4>\n<p>The <code>_source</code> field is essential in Elasticsearch OSS for operations like <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/docs-reindex.html\">reindexing</a> or <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/setup-upgrade.html#upgrade-index-compatibility\">upgrading</a> an index to a new major version and is also useful for queries that return original documents. Disabling <code>_source</code> significantly reduces disk usage but removes these capabilities.</p>\n<p>In Elasticsearch enterprise tiers, the <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/mapping-source-field.html#synthetic-source\">synthetic _source</a> feature allows <code>_source</code> to be reconstructed on demand from other Lucene data structures.</p>\n<p>Our <a target=\"_blank\" href=\"https://clickhouse.com/blog/json-bench-clickhouse-vs-mongodb-elasticsearch-duckdb-postgresql#benchmark-queries\">benchmark queries</a> utilize <code>doc_values</code> and don’t require <code>_source</code>, as they return aggregated values rather than original documents. Therefore, we simulate the storage savings of <code>synthetic _source</code> by running benchmarks with <code>_source</code> disabled. For comparison, we also tested with <code>_source</code> enabled at various compression levels.</p>\n<h4 id=\"configuring-elasticsearch-for-fair-storage-comparison\"></h4>\n<p>As noted earlier, Elasticsearch indexes and stores data in various structures optimized for specific access patterns. Since our benchmark focuses on data aggregations, we configured Elasticsearch to best align with this use case:</p>\n<ul>\n<li>\n<p><strong>Minimized inverted index size</strong>: We disabled full-text search by <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/elasticsearch/config/index_template_no_source_best_compression.json#L53\">mapping</a> all strings as <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/keyword.html\">keyword</a> types. This still supports effective filtering for our benchmark queries while also populating <code>doc_values</code> for efficient aggregations.</p>\n</li>\n<li>\n<p><strong>Date field mapping</strong>: The ingested documents’ date field was <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/elasticsearch/config/index_template_no_source_best_compression.json#L79\">mapped</a> to Elasticsearch’s date type, which <a target=\"_blank\" href=\"https://www.elastic.co/blog/numeric-and-date-ranges-in-elasticsearch-just-another-brick-in-the-wall\">leverages</a> Lucene’s <a target=\"_blank\" href=\"https://users.cs.duke.edu/~pankaj/publications/papers/bkd-sstd.pdf\">Bkd</a> trees for range queries on dates.</p>\n</li>\n<li>\n<p><strong>Reduced storage overhead</strong>: We <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/elasticsearch/config/filebeat.yml#L82\">disabled</a> all meta-fields, ensuring only fields from the ingested JSON data are stored. Storage sizes were tested with _source disabled to simulate synthetic _source.</p>\n</li>\n<li>\n<p><strong>Index sorting</strong>: We <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/elasticsearch/config/index_template_source_best_compression.json#L28\">enabled</a> index sorting using the same fields as <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/clickhouse/ddl_zstd.sql#L10\">ClickHouse’s sorting key</a>, optimizing data compression and query performance.</p>\n</li>\n<li>\n<p><strong>Single-node optimization</strong>: Replicas were <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/elasticsearch/config/index_template_no_source_best_compression.json#L44\">disabled</a> since we ran Elasticsearch on a single node.</p>\n</li>\n<li>\n<p><strong>Optimized rollovers and merges</strong>: We <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/elasticsearch/config/ilm.json#L7\">applied</a> <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/size-your-shards.html#shard-size-recommendation\">best practices</a> for index rollovers and merges.</p>\n</li>\n</ul>\n<p>The next diagram summarises our benchmark configuration of Elasticsearch’s data structures:</p>\n<p><span><img alt=\"JSON-Benchmarks.014.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FJSON_Benchmarks_014_16218543f4.png&w=2048&q=75\"></span></p>\n<p>Note that disabling <code>_source</code> essentially makes the <code>index.codec</code> setting ineffective. It doesn’t matter if <code>lz4</code> or <code>zstd</code> is selected, as there is no data that can be compressed with these algorithms.</p>\n<h4 id=\"data-sorting\"></h4>\n<p>To <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/tune-for-disk-usage.html#_use_index_sorting_to_colocate_similar_documents\">improve</a> compression ratios for <code>stored fields</code> and <code>doc_values</code>, Elasticsearch allows optional configuration of <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/index-modules-index-sorting.html\">data sorting</a> on disk before compression. Similar to ClickHouse, this sorting also enhances query performance by <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing#on-disk-data-ordering\">enabling</a> early termination.</p>\n<h4 id=\"caches\"></h4>\n<p>Elasticsearch processes queries <a target=\"_blank\" href=\"https://www.elastic.co/blog/elasticsearch-caching-deep-dive-boosting-query-speed-one-cache-at-a-time\">using</a> the operating system’s page cache along with two query-result caches: the shard-level <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/shard-request-cache.html\">request cache</a> and the segment-level <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/query-cache.html\">query cache</a>.</p>\n<p>Additionally, Elasticsearch executes all queries within the Java JVM, typically allocating half of the available physical RAM at startup, <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/guide/current/heap-sizing.html#compressed_oops\">up</a> to a 32 GB heap size limit. This limit allows for memory-efficient <a target=\"_blank\" href=\"https://docs.oracle.com/javase/7/docs/technotes/guides/vm/performance-enhancements-7.html#compressedOop\">object pointers</a>. Any remaining physical RAM beyond this limit is used indirectly for caching disk-loaded data in the operating system’s page cache.</p>\n<h4 id=\"limitations\"></h4>\n<p>Query workloads <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#count-aggregations-in-clickhouse-and-elasticsearch\">commonly</a> present in large-scale data analytics and observability use cases almost always use <code>count(*)</code> and <code>count_distinct(...)</code> aggregations over billions of table rows</p>\n<p>To reflect real-world scenarios, most of our <a target=\"_blank\" href=\"https://clickhouse.com/blog/json-bench-clickhouse-vs-mongodb-elasticsearch-duckdb-postgresql#benchmark-queries\">benchmark queries</a> include <code>count(*)</code> aggregations, with <code>query ②</code> also incorporating a <code>count_distinct(...)</code> aggregation.</p>\n<p>In Elasticsearch, <code>count(*)</code> aggregations are <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#elasticsearch\">approximate</a> when the data spans multiple <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch/on-disk-format-and-insert-processing#elasticsearch\">shards</a>. Similarly, the ES|QL <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/esql-functions-operators.html#esql-count_distinct\">COUNT_DISTINCT</a> aggregate function is also approximate, relying on the <a target=\"_blank\" href=\"https://static.googleusercontent.com/media/research.google.com/fr//pubs/archive/40671.pdf\">HyperLogLog++</a> algorithm.</p>\n<p>In contrast, ClickHouse calculates fully accurate results for <code>count(*) aggregations</code>. Additionally, ClickHouse offers both <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/reference/uniq#agg_function-uniq\">approximate</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/reference/uniqexact\">exact</a> versions of the <code>count_distinct(...)</code> function. For <code>query ②</code>, we opted for the exact version to ensure precision.</p>\n<p>The <code>time_us</code> JSON path in our <a target=\"_blank\" href=\"https://clickhouse.com/blog/json-bench-clickhouse-vs-mongodb-elasticsearch-duckdb-postgresql#the-json-dataset---a-billion-bluesky-events\">Bluesky test datasets</a> contains timestamps with microsecond precision. While Elasticsearch supports storing these timestamps in the <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/date_nanos.html\">date_nanos</a> type, its ES|QL <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/esql-functions-operators.html\">date and time functions</a> only work with the <a target=\"_blank\" href=\"https://www.elastic.co/guide/en/elasticsearch/reference/current/date.html\">date</a> type, which has millisecond precision. As a workaround, we <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/elasticsearch/config/filebeat.yml#L88\">store</a> <code>time_us</code> in Elasticsearch as a <code>date</code> type with reduced precision.</p>\n<p>ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/date-time-functions\">functions for working with dates and times</a> can handle dates with nanosecond precision.</p>\n<h3 id=\"duckdb\"></h3>\n<p><a target=\"_blank\" href=\"https://duckdb.org/\">DuckDB</a> is a columnar analytical database designed for single-node environments.</p>\n<h4 id=\"json-support\"></h4>\n<p>DuckDB introduced its JSON support in 2022 through the <a target=\"_blank\" href=\"https://duckdb.org/docs/data/json/json_type.html\">JSON logical type</a>.</p>\n<h4 id=\"json-storage\"></h4>\n<p>DuckDB <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=bZOvAKGkzpQ\">is</a> a <a target=\"_blank\" href=\"https://clickhouse.com/engineering-resources/what-is-columnar-database\">columnar database</a>. However, unlike ClickHouse, DuckDB stores JSON data differently. In a DuckDB table with a JSON column, the ingested JSON documents are stored as plain strings rather than being decomposed or optimized for columnar storage:</p>\n<p><span><img alt=\"JSON-Benchmarks.015.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FJSON_Benchmarks_015_08bf8f39b1.png&w=2048&q=75\"></span></p>\n<p>DuckDB automatically <a target=\"_blank\" href=\"https://duckdb.org/docs/guides/performance/indexing.html\">creates</a> <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Block_Range_Index\">min-max indexes</a> for general-purpose data type columns, storing the minimum and maximum values for each <a target=\"_blank\" href=\"https://duckdb.org/docs/guides/performance/how_to_tune_workloads.html#the-effect-of-row-groups-on-parallelism\">row group</a> to accelerate filtering and aggregation queries.</p>\n<p>It <a target=\"_blank\" href=\"https://duckdb.org/docs/guides/performance/indexing.html#art-indexes\">also</a> generates <a target=\"_blank\" href=\"https://db.in.tum.de/~leis/papers/ART.pdf\">Adaptive Radix Tree (ART)</a> indexes for columns with <code>PRIMARY KEY</code>, <code>FOREIGN KEY</code>, or <code>UNIQUE</code> constraints. ART indexes can be explicitly added to other columns but come with <a target=\"_blank\" href=\"https://duckdb.org/docs/guides/performance/indexing.html#art-indexes\">limitations</a>: they store a secondary data copy, and their effectiveness is limited to point queries or highly selective filters that target roughly 0.1% or fewer of the rows.</p>\n<h4 id=\"data-compression\"></h4>\n<p>DuckDB automatically <a target=\"_blank\" href=\"https://duckdb.org/docs/internals/storage.html#compression\">applies</a> <a target=\"_blank\" href=\"https://duckdb.org/2022/10/28/lightweight-compression.html\">lightweight compression algorithms</a> to column data <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=bZOvAKGkzpQ\">based</a> on types, cardinality, and other factors.</p>\n<h4 id=\"data-sorting\"></h4>\n<p>DuckDB documentation <a target=\"_blank\" href=\"https://duckdb.org/docs/guides/performance/indexing.html#the-effect-of-ordering-on-zonemaps\">recommends</a> pre-ordering data during insertion to group similar values, improving compression ratios and enhancing the <a target=\"_blank\" href=\"https://duckdb.org/docs/guides/performance/indexing.html#the-effect-of-ordering-on-zonemaps\">effectiveness</a> of min-max indexes. However, DuckDB does not provide automatic data ordering.</p>\n<h4 id=\"caches\"></h4>\n<p>DuckDB relies on the operating system’s page cache and its <a target=\"_blank\" href=\"https://duckdb.org/2024/07/09/memory-management.html\">buffer manager</a> to cache pages from its persistent storage.</p>\n<h3 id=\"postgresql\"></h3>\n<p><a target=\"_blank\" href=\"https://www.postgresql.org/\">PostgreSQL</a> is a well-established <a target=\"_blank\" href=\"https://clickhouse.com/engineering-resources/what-is-columnar-database#row-based-vs-column-based\">row-oriented</a> relational database with first-class JSON support. We chose it as a representative of row-based systems to compare its performance and storage capabilities with modern column-oriented databases like ClickHouse and DuckDB. That said, PostgreSQL is not designed for large-scale analytical workloads like those tested in JSONBench and is not directly competitive with the other systems in this context.</p>\n<h4 id=\"json-support\"></h4>\n<p>PostgreSQL natively supports JSON data through its JSON and JSONB data types.</p>\n<p>Introduced in PostgreSQL 9.2 (2012), the <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/datatype-json.html\">JSON type</a> stores JSON documents as text, requiring processing functions to reparse the document on each execution, <a target=\"_blank\" href=\"https://clickhouse.com/blog/json-bench-clickhouse-vs-mongodb-elasticsearch-duckdb-postgresql#duckdb\">similar</a> to DuckDB’s current logical JSON type.</p>\n<p>In 2014, PostgreSQL 9.4 introduced the <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/datatype-json.html\">JSONB type</a>, which uses a decomposed binary format similar to MongoDB’s BSON. Due to its improved performance and functionality, JSONB is now the <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/datatype-json.html\">recommended</a> option for working with JSON data in PostgreSQL.</p>\n<h4 id=\"json-storage\"></h4>\n<p>PostgreSQL <a target=\"_blank\" href=\"https://www.postgresql.org/docs/8.1/storage.html\">is</a> a <a target=\"_blank\" href=\"https://clickhouse.com/engineering-resources/what-is-columnar-database#row-based-vs-column-based\">row-based</a> data store and, therefore, stores ingested JSON documents as JSONB tuples sequentially on disk:</p>\n<p><span><img alt=\"JSON-Benchmarks.016.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FJSON_Benchmarks_016_3b37162b4d.png&w=2048&q=75\"></span></p>\n<p>Users can <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/sql-createindex.html\">create</a> secondary indexes on specific JSON paths to speed up queries filtering on these paths. By <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/sql-createindex.html\">default</a>, PostgreSQL creates B-Tree index data structures containing one entry for each ingested JSON document, where each B-Tree entry stores the values of the indexed JSON paths within the corresponding document.</p>\n<h4 id=\"index-only-scans\"></h4>\n<p>PostgreSQL supports <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/indexes-index-only-scans.html\">index-only scans</a> with B-tree indexes, <a target=\"_blank\" href=\"https://clickhouse.com/blog/json-bench-clickhouse-vs-mongodb-elasticsearch-duckdb-postgresql#covered-index-scans\">similar</a> to MongoDB, for queries referencing only JSON paths stored in the index. However, this optimization is not automatic and <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/indexes-index-only-scans.html\">depends</a> on the table’s data being stable, with rows marked as visible in the table’s <code>visibility map</code>. This allows the data to be read directly from the index without needing additional checks in the main table.</p>\n<p>To verify if PostgreSQL’s query planner used index-only scans for specific benchmark queries, you can examine the <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/tree/c7afa7078aed72c55ff4441a2da635424fde7724/postgresql/results/_index_usage\">query execution plans</a> that our benchmark tracks for PostgreSQL.</p>\n<h4 id=\"data-compression\"></h4>\n<p>PostgreSQL stores data row-wise in 8-kilobyte <a target=\"_blank\" href=\"https://en.m.wikipedia.org/wiki/Page_(computer_memory)\">pages</a> on disk, aiming to fill each page with tuples. For optimal storage, tuples are ideally kept under 2 KB. Any tuple larger than 2 KB is processed using <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/storage-toast.html\">TOAST</a>, which <a target=\"_blank\" href=\"https://www.postgresql.org/docs/17/sql-createtable.html#SQL-CREATETABLE-PARMS-COMPRESSION\">compresses</a> and splits the data into smaller chunks. Supported compression methods for TOASTed tuples <a target=\"_blank\" href=\"https://www.postgresql.org/docs/17/sql-createtable.html#SQL-CREATETABLE-PARMS-COMPRESSION\">include</a> <code>pglz</code> and <code>lz4</code>, while tuples under 2 KB remain uncompressed.</p>\n<h4 id=\"data-sorting\"></h4>\n<p>PostgreSQL supports <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/sql-cluster.html\">clustered tables</a>, where data is physically reordered based on the tuples of an index. However, unlike ClickHouse and Elasticsearch, PostgreSQL’s compression ratio does not improve with sorted table data. This is because, as explained above, compression is applied per tuple (only for tuples larger than 2 KB), regardless of data order. Additionally, PostgreSQL’s row-based storage prevents colocating similar data within columns, which could otherwise enhance compression by grouping similar values together.</p>\n<h4 id=\"caches\"></h4>\n<p>PostgreSQL uses internal caches to speed up data access, including caching <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/plpgsql-implementation.html#PLPGSQL-PLAN-CACHING\">query execution plans</a> and <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/pgbuffercache.html\">frequently accessed table and index data blocks</a>. Like other benchmark candidates, it also leverages the operating system’s page cache. However, PostgreSQL does not provide a dedicated cache for query results.</p>\n<h2 id=\"benchmark-setup\"></h2>\n<p>Inspired by <a target=\"_blank\" href=\"https://benchmark.clickhouse.com/\">ClickBench</a>, we created <a target=\"_blank\" href=\"https://jsonbench.com/\">JSONBench</a>—a fully reproducible benchmark you can set up and run on your own machine in minutes. Detailed instructions are available <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/?tab=readme-ov-file#usage\">here</a>.</p>\n<h3 id=\"hardware-and-operating-system\"></h3>\n<p>As a test machine per benchmark candidate, we used a dedicated AWS EC2 <strong>m6i.8xlarge</strong> instance with <strong>32 CPU cores</strong>, <strong>128 GB RAM</strong>, and a <strong>10 TB gp3 id=\"measurements\"></h3>\n<p>Our benchmark evaluates both <strong>storage size</strong> and <strong>query performance</strong>, testing each system with its <strong>default data compression</strong> id=\"benchmark-methodology\"></h2>\n<p>In this blog post, we analyzed and compared the storage size of <strong>up to 1 billion ingested Bluesky JSON documents</strong> and the query performance of <strong>five typical analytical queries executed sequentially</strong> on the ingested data.</p>\n<p>The evaluation was performed on <strong>five different open-source data stores</strong>, each operating on a <strong>single node</strong>, following a well-defined methodology, which we describe below.</p>\n<h3 id=\"no-tuning\"></h3>\n<p>Similar to <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickBench?tab=readme-ov-file#installation-and-fine-tuning\">ClickBench</a>, we use all systems in standard configuration without applying any fine-tuning measures.</p>\n<p>An exception was MongoDB, where we initially got an exception for running <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/mongodb/queries_formatted.js#L17\">query ②</a>:</p>\n<div><pre><code><span>MongoServerError[ExceededMemoryLimit]: PlanExecutor error during aggregation :: caused by :: Used too much memory <span>for</span> a single array. Memory <span>limit</span>: 104857600. Current <span>set</span> has 2279516 elements and is 104857601 bytes.</span></code></pre></div>\n<p>The issue arose due to the <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/reference/operator/aggregation/addToSet/\">$addToSet</a> operator, used as a <a target=\"_blank\" href=\"https://clickhouse.com/blog/json-bench-clickhouse-vs-mongodb-elasticsearch-duckdb-postgresql#limitations\">workaround</a> for the missing <code>COUNT DISTINCT</code> operator in MongoDB. By default, this operator has a 100 MB limit for the size of in-memory sets (implemented as arrays), which was exceeded during query execution. To address this, we <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/mongodb/run_queries.sh#L24\">increased</a> the <code>internalQueryMaxAddToSetBytes</code> value.</p>\n<p>Additionally, to follow <a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/core/query-optimization/#performance\">best practices</a>—similar to the <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickBench/blob/96994da9b0cd61b04e543224dd89c9de32486415/mongodb/benchmark.sh#L14\">MongoDB setup in ClickBench</a>—we <a target=\"_blank\" href=\"https://github.com/ClickHouse/JSONBench/blob/c7afa7078aed72c55ff4441a2da635424fde7724/mongodb/run_queries.sh#L36\">enabled</a> the <a target=\"_blank\" href=\"https://github.com/mongodb/mongo/blob/8a2f52590d92482624723086b88151c93ee56f1c/src/mongo/db/query/query_knobs.idl?utm_source=chatgpt.com#L285\">internalQueryPlannerGenerateCoveredWholeIndexScans</a> setting. This allows the query planner to generate <a target=\"_blank\" href=\"https://staging.clickhouse.com/blog/json-bench-clickhouse-vs-mongodb-elasticsearch-duckdb-postgresql#covered-index-scans\">covered index scans</a>, ensuring that all five benchmark queries in MongoDB are covered queries. Consequently, the reported query runtimes represent lower bounds, as runtimes without this optimization were significantly slower.</p>\n<h3 id=\"no-query-results-cache\"></h3>\n<p>When query result caches are enabled, systems like Elasticsearch and ClickHouse can instantly serve results by fetching them directly from the cache. While this is efficient, it doesn’t provide meaningful performance insights for our benchmark. To ensure consistency, we disable or clear query result caches after each execution.</p>\n<p>Our goal is to focus solely on testing the performance of JSON data types across different systems.
