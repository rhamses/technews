contentHtml: "<article><div><p>In August 2024, ClickHouse v24.8 introduced a <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/newjson\">powerful <strong>JSON data type</strong> to ClickHouse</a>. Since then, we’ve continuously improved it with new features and optimizations.</p>\n<p>In this post, we’ll show how <strong>we’ve just made it even better</strong> in ClickHouse v25.8.</p>\n<p>ClickHouse is already the industry leader in analytical performance, and <strong>the latest changes in v25.8 make ClickHouse the leader in analytics over JSON data</strong>, too.</p>\n<h2 id=\"how-the-json-type-worked-in-v24-8\"></h2>\n<p>Let’s start with a quick recap of <a target=\"_blank\" href=\"https://clickhouse.com/blog/a-new-powerful-json-data-type-for-clickhouse\">how JSON data is stored in MergeTree parts</a> as designed in ClickHouse v24.8.</p>\n<p>In the illustration below, we have JSON data with K unique paths with string values. The first <strong>N paths</strong> are stored as subcolumns in <em>dynamic paths</em>. All remaining <strong>K – N paths</strong> are stored in a <em>shared data</em> structure, which is represented as a <code>Map(String, String)</code> column containing both paths and values.</p>\n<p><span><img alt=\"json_type_update_image1.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fjson_type_update_image1_min_e5ac49a759.png&w=2048&q=75\"></span></p>\n<p>For example, if we query the data of the path <code>key1</code>, ClickHouse first checks metadata to see whether <code>key1</code> is in <em>dynamic paths</em> or <em>shared data</em>. In this example path <code>key1</code> is in <em>dynamic paths</em>, so its values are stored in dedicated data files, which can be read directly and efficiently.</p>\n<p><span><img alt=\"json_type_update_image2.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fjson_type_update_image2_min_5b0c0617cb.png&w=2048&q=75\"></span></p>\n<p>Now, if we query <code>key_n+1</code>, the metadata shows that it’s <em>not</em> part of <em>dynamic paths</em>. Instead, it resides in <em>shared data</em>. To extract its values, ClickHouse must read the <strong>entire</strong> <code>Map(String, String)</code> column and filter it in memory. This is much less efficient.</p>\n<p><span><img alt=\"json_type_update_image3.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fjson_type_update_image3_min_820f9daa60.png&w=2048&q=75\"></span></p>\n<p>By default, the limit on dynamic paths is <strong>1024</strong>. Raising this limit to handle more paths is usually a bad idea, especially when using remote storage like S3, because creating thousands of files per part increases memory usage during merges and complicates reads.</p>\n<p>As a result, workloads with thousands or tens of thousands of unique JSON paths suffer from poor performance.</p>\n<p>This is the challenge we set out to solve.</p>\n<p><strong>ClickHouse v25.8</strong> introduces <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/83777\">two new serialization formats for <em>shared data</em></a> that dramatically improve the efficiency of reading specific paths.</p>\n<ol>\n<li>\n<h3 id=\"bucketed-shared-data\"></h3>\n</li>\n</ol>\n<p>The first new serialization splits <em>shared data</em> into <strong>N buckets</strong>. Each bucket contains its own <code>Map(String, String)</code> column, with a deterministic assignment of paths to buckets.</p>\n<p><span><img alt=\"json_type_update_image4.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fjson_type_update_image4_min_7b81db8ed5.png&w=2048&q=75\"></span></p>\n<p>When querying a path like <code>key_m1</code>, ClickHouse can immediately determine which bucket contains the requested path. Only that bucket is read, while the rest are skipped.</p>\n<p><span><img alt=\"json_type_update_image5.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fjson_type_update_image5_min_ce58cd599c.png&w=2048&q=75\"></span></p>\n<p>This <strong>reduces the amount of data scanned and improves performance</strong> compared to reading the entire <em>shared data</em>. However, increasing the number of buckets too far creates too many files and reintroduces file-system overhead.</p>\n<ol>\n<li>\n<h3 id=\"advanced-shared-data\"></h3>\n</li>\n</ol>\n<p>The second and more powerful approach is the <strong>advanced serialization format</strong>.</p>\n<p>Here, each bucket contains 3 files:</p>\n<ul>\n<li><strong><code>.structure</code></strong> – metadata for each granule: number of rows, list of paths in the granule, and offset in the <code>.paths_marks</code> file.</li>\n<li><strong><code>.data</code></strong> – the actual path data stored in columnar format per granule.</li>\n<li><strong><code>.paths_marks</code></strong> – offsets pointing to the start of each path’s data in the <code>.data</code> file.</li>\n</ul>\n<p><span><img alt=\"json_type_update_image6.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fjson_type_update_image6_min_aba69b1ac7.png&w=2048&q=75\"></span></p>\n<p>When querying the path <code>key_m1</code> ,ClickHouse first checks the <code>.structure</code> file to see if the granule contains <code>key_m1</code>. If not, the granule is skipped entirely. If it does, ClickHouse looks up the offset in the <code>.paths_marks</code> file and jumps directly to the <code>key_m1</code> path’s data in the <code>.data</code> file and reads it.</p>\n<p><span><img alt=\"json_type_update_image7.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fjson_type_update_image7_min_9ec2b127d6.png&w=2048&q=75\"></span></p>\n<p>This <strong>avoids reading the data of unrelated paths into memory and significantly improves query performance</strong>.</p>\n<h3 id=\"supporting-nested-paths\"></h3>\n<p>Many JSON documents contain nested structures like arrays of objects. Extracting a nested path from such structures using the above approach still requires reading the entire array, which is inefficient for large payloads.</p>\n<p>To address this, <strong>the advanced format was extended with additional files for subcolumn handling</strong>.</p>\n<p>Here each bucket has 6 files:</p>\n<ul>\n<li><strong><code>.structure</code></strong> – metadata for each granule: number of rows, list of paths in the granule and offsets in files <code> .paths_marks</code> and <code> .substreams_metadata</code>.</li>\n<li><strong><code>.data</code></strong> – the actual path data stored in columnar format per granule, but split into substreams. A single path may have multiple substreams. This structure allows ClickHouse to read only the substreams needed to reconstruct the requested subcolumn, rather than scanning the entire path value.</li>\n<li><strong><code>.paths_marks</code></strong> – offsets pointing to the start of each path’s data in the <code> .data</code> file.</li>\n<li><strong><code>.substreams_marks</code></strong> – offsets pointing to the start of each path’s substream in the <code>.data</code> file.</li>\n<li><strong><code>.substreams</code></strong> – list of substreams present for each path in a granule. This may differ across granules (e.g., some arrays may contain objects with different nested fields).</li>\n<li><strong><code>.substreams_metadata</code></strong> – for each path, stores offsets in the <code> .substreams</code> and <code> .substreams_marks</code> files, effectively linking a path to its subcolumns and their data locations.</li>\n</ul>\n<p><span><img alt=\"json_type_update_image8.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fjson_type_update_image8_min_bad57854bf.png&w=2048&q=75\"></span></p>\n<p>When querying the subcolumn of path <code>key_m1</code>, ClickHouse first reads data from the <code>.structure</code> file and checks if this granule contains the requested path <code>key_m1</code>. If not, the granule is skipped entirely. If it does, ClickHouse uses the offset stored in the <code> .structure</code> file to read the corresponding entry in <code>.substreams_metadata</code> and obtain the offsets for <code>key_m1</code>.</p>\n<p>Using the first offset, ClickHouse then reads the list of substreams for this path in the granule. If this list does not include the substreams required for the requested subcolumn, the granule is skipped. If the required substreams are present, ClickHouse uses the second offset to read their positions from <code>.substreams_marks</code> and then reads only the data of those substreams from the <code>.data</code> file.</p>\n<p>After reconstructing the requested subcolumn, ClickHouse proceeds to the next granule.</p>\n<p><span><img alt=\"json_type_update_image9.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fjson_type_update_image9_min_11de95296c.png&w=2048&q=75\"></span></p>\n<p>This avoids reading the data of unrelated paths and unrelated substreams of the requested path in the granule in memory. This <strong>significantly improves the performance of nested subcolumn reading</strong>.</p>\n<h2 id=\"balancing-efficiency-and-compatibility\"></h2>\n<p>The <strong>advanced format is</strong> <strong>excellent for selective reads</strong>, but it doesn’t come for free: <strong>reading the entire JSON column or performing merges becomes slower</strong>, because the in-memory representation of the shared data (<code>Map(String, String)</code>) is very different from its storage layout, resulting in expensive conversions during entire JSON column reading.</p>\n<p>To address this, ClickHouse v25.8 makes a trade-off by <strong>storing a copy of the data in the original format alongside the advanced one</strong>. This effectively doubles the storage requirement, but you get all the benefits of the new format without the sacrifices noted above.</p>\n<p>In the below illustration, you can see the copy is stored in three extra files:</p>\n<ul>\n<li><strong><code>.copy.offsets</code></strong> – offsets of the original <code>Map(String, String)</code> column.</li>\n<li><strong><code>.copy.indexes</code></strong> –  indexes into the combined list of paths across buckets (avoids storing all paths again).</li>\n<li><strong><code>.copy.values</code></strong> - values of the original <code>Map(String, String)</code> column.</li>\n</ul>\n<p><span><img alt=\"json_type_update_image10.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fjson_type_update_image10_min_67dddd93b4.png&w=2048&q=75\"></span></p>\n<p>This makes <strong>reading full JSON columns and performing merges as fast as before</strong>, while still <strong>keeping the benefits of the advanced format for selective reads</strong>.</p>\n<h2 id=\"performance\"></h2>\n<p><a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/83777#issuecomment-3073272839\">We benchmarked the new serialization formats with JSON data containing <strong>10, 100, 1000, and 10,000 unique paths</strong></a>.</p>\n<p>The new advanced shared data serialization delivers <strong>performance close to storing all paths as dynamic subcolumns</strong> both in query speed and memory usage,
