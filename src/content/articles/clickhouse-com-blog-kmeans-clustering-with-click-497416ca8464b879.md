They wanted to solve this at scale across potentially billions of data points while ensuring memory could be tightly managed. In this post, we give implementing K-means clustering using just SQL a try and show that it scales to billions of rows.</p>\n<blockquote>\n<p>In the writing of this blog, we became aware of the work performed by Boris Tyshkevich. While we use a different approach in this blog, we would like to recognize Boris for his work and for having this idea well before we did!</p>\n</blockquote>\n<p>As part of implementing K-Means with ClickHouse SQL, we cluster 170M NYC taxi rides in under 3 minutes. The equivalent scikit-learn operation with the same resources takes over 100 minutes and requires 90GB of RAM. With no memory limitations and ClickHouse automatically distributing the computation, we show that ClickHouse can accelerate machine learning workloads and reduce iteration time.</p>\n<p><span><img alt=\"kmeans_cluster_1.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fkmeans_cluster_1_b68b16e5d0.png&w=2048&q=75\"></span></p>\n<p>All of the code for this blog post can be found in a notebook <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/kmeans/kmeans.ipynb\">here</a>.</p>\n<h2 id=\"why-k-means-in-clickhouse-sql\"></h2>\n<p>The key motivation for using ClickHouse SQL to do K-Means is that training is not memory-bound, making it possible to cluster PB datasets thanks to the incremental computation of centroids (with settings to limit memory overhead). In contrast, distributing this workload across servers using Python-based approaches would require an additional framework and complexity.</p>\n<p>Additionally, we can easily increase the <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part2\">level of parallelism in our clustering</a> to use the full resources of a Clickhouse instance. Should we need to handle larger datasets, we simply scale the database service - a simple operation in ClickHouse Cloud.</p>\n<p>Transforming the data for K-Means is a simple SQL query that can process billions of rows per second. With centroids and points held in ClickHouse, we can compute statistics such as model errors with just SQL and potentially use our clusters for other operations e.g. product quantization for vector search.</p>\n<h2 id=\"k-means-recap\"></h2>\n<p>K-Means is an <a target=\"_blank\" href=\"https://cloud.google.com/discover/what-is-unsupervised-learning\">unsupervised machine learning algorithm</a> for partitioning a dataset into K distinct, non-overlapping subgroups (clusters) where each data point belongs to the cluster with the nearest mean (the cluster's centroid). The process begins by initializing K centroids randomly or based on some heuristic. These centroids serve as the initial representatives of the clusters. The algorithm then iterates through two main steps until convergence: assignment and update.</p>\n<p>In the assignment step, each data point is assigned to the nearest cluster based on the Euclidean distance (or another distance metric) between it and the centroids. In the update step, the centroids are recalculated as the mean of all points assigned to their respective clusters, potentially shifting their positions.</p>\n<p>This process is guaranteed to converge, with the assignments of points to clusters eventually stabilizing and not changing between iterations. The number of clusters, K, needs to be specified beforehand and heavily influences the algorithm's effectiveness with the optimal value depending on the dataset and the goal of the clustering. For more details, we recommend this <a target=\"_blank\" href=\"https://medium.com/@dilekamadushan/introduction-to-k-means-clustering-7c0ebc997e00\">excellent overview</a>.</p>\n<h2 id=\"points-and-centroids\"></h2>\n<p>The key problem our user posed was the ability to efficiently compute centroids. Suppose we have a simple data schema for a <code>transactions</code> table, where each row represents a bank transaction for a specific customer. Vectors in ClickHouse are represented as an <code>Array</code> type.</p>\n<div><pre><code><span><span>CREATE TABLE</span> transactions</span>\n<span>(</span>\n<span>  id UInt32,</span>\n<span>  vector <span>Array</span>(Float32), </span>\n<span>  <span>-- e.g.[0.6860357,-1.0086979,0.83166444,-1.0089169,0.22888935]</span></span>\n<span>  customer UInt32,</span>\n<span>  ...other columns omitted <span>for</span> brevity</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree <span>ORDER</span> <span>BY</span> id</span></code></pre></div>\n<p>Our user wanted to find the centroid for each customer, effectively the positional average of all the transaction vectors associated with each customer. To find the set of average vectors, we can use the <code>avgForEach</code><sub><a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/reference/avg\">[1][2]</a></sub> function. For instance, consider the example of computing the average of 3 vectors, each with 4 elements:</p>\n<div><pre><code><span><span>WITH</span> vectors <span>AS</span></span>\n<span>   (</span>\n<span>       <span>SELECT</span> c1 <span>AS</span> vector</span>\n<span>       <span>FROM</span> <span>VALUES</span>([<span>1</span>, <span>2</span>, <span>3</span>, <span>4</span>], [<span>5</span>, <span>6</span>, <span>7</span>, <span>8</span>], [<span>9</span>, <span>10</span>, <span>11</span>, <span>12</span>])</span>\n<span>   )</span>\n<span><span>SELECT</span> avgForEach(vector) <span>AS</span> centroid</span>\n<span><span>FROM</span> vectors</span>\n<span></span>\n<span>┌─centroid──┐</span>\n<span>│ [<span>5</span>,<span>6</span>,<span>7</span>,<span>8</span>] │</span>\n<span>└───────────┘</span></code></pre></div>\n<p>In our original <code>transactions</code> table, computing the average per customer thus becomes:</p>\n<div><pre><code><span><span>SELECT</span> customer, avgForEach(vector) <span>AS</span> centroid <span>FROM</span> transactions <span>GROUP</span> <span>BY</span> customer</span></code></pre></div>\n<p>While simple, this approach has a few limitations. Firstly, for very large datasets, when the <code>vector</code> contains many <code>Float32</code> points and the <code>customer</code> column has many unique elements (high cardinality), this query can be very memory intensive. Secondly, and maybe more relevant to K-Means, this approach requires us to rerun the query if new rows are inserted, which is inefficient. We can address these problems through Materialized Views and the AggregatingMergeTree engine.</p>\n<h3 id=\"incrementally-computing-centroids-with-materialized-views\"></h3>\n<p>Materialized Views allow us to shift the cost of computing our centroids to insert time. Unlike in other databases, a ClickHouse Materialized View is just a trigger that runs a query on blocks of data as they are inserted into a table. The results of this query are inserted into a second \"target\" table. In our case, the Materialized View query will compute our centroids, inserting the results to a table <code>centroids</code>.</p>\n<p><span><img alt=\"Incremental computing centroids with MV.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FIncremental_computing_centroids_with_MV_ca482bcd3f.png&w=2048&q=75\"></span></p>\n<p>There are some important details here:</p>\n<ul>\n<li>Our query, which computes our centroids, must produce the result set in a format that can be merged with subsequent result sets - since every block inserted will produce a result set. Rather than just sending averages to our <code>centroids</code> table (<a target=\"_blank\" href=\"https://www.stevefenton.co.uk/blog/2020/02/can-you-average-averages-in-your-analytics/\">the average of an average would be incorrect</a>), we send the <a target=\"_blank\" href=\"https://clickhouse.com/blog/aggregate-functions-combinators-in-clickhouse-for-arrays-maps-and-states#working-with-aggregation-states\">“average state”</a>. The average state representation contains the sum of each vector position, along with a count. This is achieved using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/combinators#-state\"><code>avgForEachState</code></a> function - notice how we’ve just appended <code>State</code> to our function name! The AggregatingMergeTree table engine is required to store these aggregation states. We explore this more below.</li>\n<li>The entire process is incremental with the <code>centroids</code> table containing the final state i.e. a row per centroid. Readers will notice that the table which receives inserts has a Null table engine. This causes the inserted rows to be thrown away, saving the IO associated with writing the full dataset on each iteration.</li>\n<li>The query of our Materialized View is only executed on the blocks as they are inserted. The number of rows in each block can vary depending on the method of insertion. We recommend at least 1000 rows per block if formulating blocks on the client side, e.g., using the Go client. If the server is left to form blocks (e.g. when inserting by HTTP), the size can also <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#max_insert_block_size\">be specified</a>.</li>\n<li>If using an <code>INSERT INTO SELECT</code> where ClickHouse reads rows from another table or external source, e.g. S3, the block size can be controlled by several key parameters discussed in detail in <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part2#shifting-gears\">previous blogs</a>. These settings (along with the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#max-insert-threads\">number of insert threads</a>) can have a dramatic effect on both the memory used (larger blocks = more memory) and the speed of ingestion (larger blocks = faster). These settings mean the amount of memory used <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part2#formula-one\">can be finely controlled</a> in exchange for performance.</li>\n</ul>\n<h3 id=\"aggregatingmergetree\"></h3>\n<p>Our target table <code>centroids</code> uses the engine <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/aggregatingmergetree\">AggregatingMergeTree</a>:</p>\n<div><pre><code><span><span>CREATE TABLE</span> centroids</span>\n<span>(</span>\n<span>   customer UInt32,</span>\n<span>   vector AggregateFunction(avgForEach, <span>Array</span>(Float32))</span>\n<span>)</span>\n<span>ENGINE <span>=</span> AggregatingMergeTree  <span>ORDER</span> <span>BY</span> customer</span></code></pre></div>\n<p>Our <code>vector</code> column here contains the aggregate states produced by the <a target=\"_blank\" href=\"https://clickhouse.com/blog/aggregate-functions-combinators-in-clickhouse-for-arrays-maps-and-states\"><code>avgForEachState</code></a> function above. These are intermediate centroids that must be merged to produce a final answer. This column needs to be of the appropriate type <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/data-types/aggregatefunction\"><code>AggregateFunction(avgForEach, Array(Float32))</code></a>.</p>\n<p>Like all ClickHouse MergeTree tables, the AggregatingMergeTree <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#mergetree-data-storage\">stores data as parts that must be merged</a> transparently to allow more efficient querying. When merging parts containing our aggregate states, this must be done so that only states pertaining to the same customer are merged. This is effectively achieved by ordering the table by the <code>customer</code> column with the <code>ORDER BY</code> clause. At query time, we must also ensure intermediate states are grouped and merged. This can be achieved by ensuring we <code>GROUP BY</code> by the column <code>customer</code> and use the Merge equivalent of the <code>avgForEach</code> function: <code>avgForEachMerge.</code></p>\n<div><pre><code><span><span>SELECT</span> customer, avgForEachMerge(vector) <span>AS</span> centroid</span>\n<span><span>FROM</span> centroids <span>GROUP</span> <span>BY</span> customer</span></code></pre></div>\n<blockquote>\n<p>All aggregation functions have an equivalent state function, obtained by appending <code>State</code> to their name, which produces an intermediate representation that can be stored and then retrieved and merged with a <code>Merge</code> equivalent. For more details, we recommend <a target=\"_blank\" href=\"https://clickhouse.com/blog/aggregate-functions-combinators-in-clickhouse-for-arrays-maps-and-states\">this blog</a> and the video from our <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=7ApwD0cfAFI\">very own Mark</a>.</p>\n</blockquote>\n<p>This query will be very fast compared to our earlier <code>GROUP BY</code>. Most of the work for computing averages has been moved to insert time, with a small number of rows left for query time merging. Let's assume we're trying to cluster a table <code>points</code> where each row has a vector representation. Here, we will cluster on similarity rather than just basing our centroids on the customer as we did with transactions.</p>\n<h3 id=\"a-single-iteration\"></h3>\n<p>We need to be able to store the current centroids after each iteration of the algorithm. <strong>For now, let's assume we have identified an optimal value of K.</strong> Our target table for our centroids might look like this:</p>\n<div><pre><code><span><span>CREATE TABLE</span> centroids</span>\n<span>(</span>\n<span>  k UInt32,</span>\n<span>  iteration UInt32,</span>\n<span>  centroid UInt32,</span>\n<span>  vector AggregateFunction(avgForEach, <span>Array</span>(Float32))</span>\n<span>)</span>\n<span>ENGINE <span>=</span> AggregatingMergeTree </span>\n<span><span>ORDER</span> <span>BY</span> (k, iteration, centroid)</span></code></pre></div>\n<p>The value of the <code>k</code> column is set to our chosen value of K. Our <code>centroid</code> column here denotes the centroid number itself, with a value between 0 and <code>K-1</code>. Rather than use a separate table for each iteration of the algorithm, we simply include an <code>iteration</code> column and ensure our ordering key is <code>(k, iteration, centroid)</code>. ClickHouse will ensure the intermediate state is only merged for each unique K, centroid, and iteration. This means our final row count will be small, ensuring fast querying of these centroids.</p>\n<p>Our Materialized View for computing our centroids should be familiar with only a small adjustment to also <code>GROUP BY k, centroid, and iteration</code>:</p>\n<div><pre><code><span><span>CREATE TABLE</span> temp</span>\n<span>(</span>\n<span>   k UInt32,</span>\n<span>   iteration UInt32,</span>\n<span>   centroid UInt32,</span>\n<span>   vector <span>Array</span>(Float32)</span>\n<span>)</span>\n<span>ENGINE <span>=</span> <span>Null</span></span>\n<span></span>\n<span><span>CREATE</span> MATERIALIZED <span>VIEW</span> centroids_mv <span>TO</span> centroids</span>\n<span><span>AS</span> <span>SELECT</span> k, iteration, centroid, avgForEachState(vector) <span>AS</span> vector</span>\n<span><span>FROM</span> temp <span>GROUP</span> <span>BY</span> k, centroid, iteration</span></code></pre></div>\n<p>Notice that our query executes over blocks inserted into a <code>temp</code> table, not our data source table transactions, which does not have an <code>iteration</code> or <code>centroid</code> column. This temp table will receive our inserts and uses the Null table engine again to avoid writing data. With these building blocks in place, we can visualize a single iteration of the algorithm assuming <code>K = 5</code>:</p>\n<p><span><img alt=\"kmeans_clickhouse.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fkmeans_clickhouse_59999c3dc2.png&w=2048&q=75\"></span></p>\n<p>The above shows how we insert into our temp table and thus compute our centroids by performing an <code>INSERT INTO SELECT</code> with a <code>points</code> table as our source data. <strong>This insertion effectively represents an iteration of the algorithm.</strong> The <code>SELECT</code> query here is critical as it needs to specify the transaction vector and its current centroid and iteration (and fixed value of K). This requires us to initialize the system. We can do this by simply selecting and inserting K random points with the following query (k=5):</p>\n<div><pre><code><span><span>INSERT INTO</span> temp <span>WITH</span> </span>\n<span>  <span>5</span> <span>as</span> k_val,</span>\n<span>  vectors <span>AS</span></span>\n<span>  (</span>\n<span>      <span>SELECT</span> vector</span>\n<span>      <span>FROM</span> points</span>\n<span>      <span>-- select random points, use k to make pseudo-random</span></span>\n<span>      <span>ORDER</span> <span>BY</span> cityHash64(concat(toString(id), toString(k_val))) <span>ASC</span></span>\n<span>      LIMIT k_val <span>-- k</span></span>\n<span>  )</span>\n<span><span>SELECT</span></span>\n<span>  k_val <span>as</span> k,</span>\n<span>  <span>1</span> <span>AS</span> iteration,</span>\n<span>  rowNumberInAllBlocks() <span>AS</span> centroid,</span>\n<span>  vector</span>\n<span><span>FROM</span> vectors</span></code></pre></div>\n<blockquote>\n<p>Successful clustering is very sensitive to the initial placement of centroids;  poor assignment leads to slow convergence or suboptimal clustering. We will discuss this a little later.</p>\n</blockquote>\n<h3 id=\"centroid-assignment-and-when-to-stop-iterating\"></h3>\n<p>All of the above represents a single iteration (and initialization step). The simplest way to do this is to simply stop when points no longer change centroids (and thus clusters) between iterations.</p>\n<blockquote>\n<p>To identify which points belong to which centroids, we can use the above SELECT from our earlier <code>INSERT INTO SELECT</code> at any time.</p>\n</blockquote>\n<p>To compute the number of points that moved clusters in the last iteration, we first compute the centroids for the previous two iterations (1) and (2). Using these, we identify the centroids for each point for each iteration (3) and (4). If these are the same (5), we return 0 and 1 otherwise. A total of these (6) values provides us with the number of points that moved clusters.</p>\n<div><pre><code><span><span>WITH</span> <span>5</span> <span>as</span> k_val,</span>\n<span>(</span>\n<span> This gives us a cost metric that we aim to minimize. The method <code>compute_d2_error</code> computes this using the following SQL query (assuming a value of 5 for K):</p>\n<div><pre><code><span><span>WITH</span> <span>5</span> <span>as</span> k_val,</span>\n<span>(</span>\n<span>       <span>SELECT</span> <span>max</span>(iteration)</span>\n<span>       <span>FROM</span> centroids <span>WHERE</span> k<span>=</span>{k}</span>\n<span>) <span>AS</span> c_iteration,</span>\n<span>(</span>\n<span>   <span>SELECT</span> groupArray((centroid, position))</span>\n<span>   <span>FROM</span></span>\n<span>   (</span>\n<span>       <span>SELECT</span></span>\n<span>           centroid,</span>\n<span>           avgForEachMerge(vector) <span>AS</span> position</span>\n<span>       <span>FROM</span> centroids</span>\n<span>       <span>WHERE</span> iteration <span>=</span> c_iteration <span>AND</span> k<span>=</span>k_val</span>\n<span>       <span>GROUP</span> <span>BY</span> centroid</span>\n<span>   )</span>\n<span>) <span>AS</span> c_centroids</span>\n<span><span>SELECT</span></span>\n<span>   <span>sum</span>(pow((arraySort(c <span>-</span><span>&gt;</span> (c<span>.2</span>), arrayMap(x <span>-</span><span>&gt;</span> (x<span>.1</span>, L2Distance(x<span>.2</span>, vector)), c_centroids))[<span>1</span>])<span>.2</span>, <span>2</span>)) <span>AS</span> distance</span>\n<span><span>FROM</span> points</span></code></pre></div>\n<blockquote>\n<p>This value is guaranteed to decrease as we increase K e.g. if we set K to the number of points, each cluster will have 1 point thus giving us an error of 0. The goal is to find the \"elbow point\" where the rate of decrease in SSE sharply changes. This point indicates a diminishing return on the benefit of increasing K. Choosing K at the elbow point provides a model that captures the inherent grouping in the data without overfitting. A simple way to identify this elbow point is to plot K vs SEE and identify the value visually. For our NYC taxis data, we measure and plot SSE for the K values 2 to 20:</p>\n<p><span><img alt=\"k_vs_d_2.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fk_vs_d_2_db70f33f8d.png&w=2048&q=75\"></span></p>\n<p>The elbow point here isn’t as clear as we’d like, but a value of 5 seems a reasonable candidate.</p>\n<blockquote>\n<p>The above results are based on a single end-to-end run for each value of K.
