contentHtml: "<article><div><blockquote>\n<p>This blog was originally posted in 2019. We are re-posting in tribute to the authors of the LZ family of algorithms: <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Abraham_Lempel\">Abraham Lempel</a> and <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Jacob_Ziv\">Jacob Ziv</a>, who recently passed away.</p>\n</blockquote>\n<blockquote>\n<p>It can be tempting to think that every new feature is novel. That every new release is set to change the market. However, we -- as an industry -- stand on the shoulder of giants. Jacob's contributions to information theory (beyond compression algorithms) are, and remain, an inspiration to generations of practitioners and researchers.</p>\n</blockquote>\n<h2 id=\"introduction\"></h2>\n<p>When you run queries in ClickHouse, you might notice that the profiler often shows the LZ_decompress_fast function near the top. What is going on? This question had us wondering how to choose the best compression algorithm.</p>\n<p>ClickHouse stores data in compressed form. When running queries, ClickHouse tries to do as little as possible in order to conserve CPU resources. In many cases, all the potentially time-consuming computations are already well optimized, plus the user wrote a well-thought-out query. Then all that's left to do is to perform decompression.</p>\n<p><span><img alt=\"lz4_resources.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Flz4_resources_95ea1ddc5c.png&w=2048&q=75\"></span></p>\n<p>So why does LZ4 decompression becomes a bottleneck? LZ4 seems like an <a target=\"_blank\" href=\"https://github.com/lz4/lz4/\">extremely light algorithm</a>: the data decompression rate is usually from 1 to 3 GB/s per processor core, depending on the data. This is much faster than the typical disk subsystem. Moreover, we use all available CPU cores, and decompression scales linearly across all physical cores.</p>\n<p>However, there are two points to keep in mind. First, compressed data is read from disk, but the decompression speed is given in terms of the amount of uncompressed data. If the compression ratio is large enough, there is almost nothing to read from the disks. But there will be a lot of decompressed data, and this naturally affects CPU utilization: in the case of LZ4, the amount of work necessary to decompress data is almost proportional to the volume of the decompressed data itself.</p>\n<p>Second, if data is cached, you might not need to read data from disks at all. You can rely on page cache or use your own cache. Caching is more efficient in column-oriented databases, since only frequently used columns stay in the cache. This is why LZ4 often appears to be a bottleneck in terms of CPU load.</p>\n<p>This brings up two more questions. First, if decompression is slowing us down, is it worth compressing data to begin with? But this speculation is irrelevant in practice. ClickHouse offers several compression options, principally — LZ4 and <a target=\"_blank\" href=\"https://github.com/facebook/zstd/\">Zstandard</a>. LZ4 is used by default. Switching to Zstandard makes compression stronger and slower. But there wasn't an option to completely disable compression, since LZ4 is assumed to provide a reasonable minimal compression that can always be used. (Which is exactly why I love LZ4.)</p>\n<p>But then a mysterious stranger appeared in the <a target=\"_blank\" href=\"https://t.me/clickhouse_en\">ClickHouse telegram support group</a> who said that he has a very fast disk subsystem (with NVMe SSD) and decompression is the only thing slowing his queries down, so it would be nice to be able to store data without compression. I replied that we don't have this option, but it would be easy to add. A few days later, we got a pull request implementing the compression method none. I asked the contributor to report back on how much this option helped to accelerate queries. The response was that this new feature turned out to be useless in practice, since the uncompressed data started to take up too much disk space and didn't fit into those NVMe drives.</p>\n<p>The second question that arises is that if there is a cache, why not use it to store data that is already decompressed? This is a viable possibility that will eliminate the need for decompression in many cases. ClickHouse also has a cache like this: the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#setting-use_uncompressed_cache\">cache of decompressed blocks</a>. But it's a pity to waste a lot of RAM on this. So usually it only makes sense to use on small, sequential queries that use nearly identical data.</p>\n<p>Our conclusion is thus that it's always preferable to store data in a compressed format. Always write data to disk in compressed format. Transmit data over the network with compression, as well. In my opinion, default compression is justifiable even when transferring data within a single data center in a 10 GB network without oversubscription, while transferring uncompressed data between data centers is just unacceptable.</p>\n<h2 id=\"why-lz4\"></h2>\n<p>Why choose LZ4? Couldn't we choose something even lighter? Theoretically, we could, and this is a good thought. But let's look at the class of algorithms that LZ4 belongs to.</p>\n<p>First of all, it's generic and doesn't adapt to the data type. For example, if you know in advance that you will have an array of integers, you can use one of the VarInt algorithms, and this will use the CPU more effectively. Second, LZ4 is not overly dependent on data model assumptions. Let's say you have an ordered time series of sensor values and an array of floating-point numbers. If you consider this, you can calculate deltas between these numbers and then compress them with a generic algorithm, which will result in a higher compression ratio.</p>\n<p>You won't have any problems using LZ4 with any byte arrays or files. Of course, it does have a specialization (more on that later), and in some cases, its use is pointless. But if we call it a general-purpose algorithm, we'll be fairly close to the truth. We should note that thanks to its internal design, LZ4 automatically implements the <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Run-length_encoding\">RLE</a> algorithm as a special case.</p>\n<p>However, the more important question is whether LZ4 is the most optimal algorithm of this class in terms of overall speed and strength of compression. Optimal algorithms are called the Pareto frontier, which means that no other algorithm is definitively better in one way and not worse in other ways (and on a wide variety of datasets, as well). Some algorithms are faster but result in a smaller compression ratio, while others have stronger compression but are slower to compress or decompress.</p>\n<p>To be honest, LZ4 is not really the Pareto frontier — there are some options available that are just a tiny bit better. For instance, look at <a target=\"_blank\" href=\"https://sites.google.com/site/powturbo/\">LZTURBO</a> from a developer nicknamed <a target=\"_blank\" href=\"https://github.com/powturbo\">powturbo</a>. There is no doubt about the reliability of the results, thanks to the <a target=\"_blank\" href=\"https://encode.su/\">encode.su</a> community (the largest and possibly the only forum on data compression). Unfortunately, the developer does not distribute the source code or binaries; they are only available to a limited number of people for testing or for a lot of money. Also, take a look at <a target=\"_blank\" href=\"https://github.com/inikep/lizard/\">Lizard</a> (previously LZ5) and <a target=\"_blank\" href=\"https://github.com/centaurean/density\">Density</a>. They might work slightly better than LZ4 when you select a certain compression level. Another really interesting option is <a target=\"_blank\" href=\"https://github.com/ConorStokes/LZSSE/\">LZSSE</a>. But finish reading this article before you check it out.</p>\n<h2 id=\"how-lz4-works\"></h2>\n<p>Let's look at how LZ4 works in general. This is one of the implementations of the LZ77 algorithm. L and Z represent the developers' names (Lempel and Ziv), and 77 is for 1977, when the algorithm was published. It has many other implementations: QuickLZ, FastLZ, BriefLZ, LZF, LZO, and gzip and zip if low compression levels are used.</p>\n<p>A data block compressed using LZ4 contains a sequence of entries (commands or instructions) of two types:</p>\n<ol>\n<li>Literals: \"Take the following N bytes as-is and copy them to the result\".</li>\n<li>Match: \"Take N bytes from the decompressed result starting at the offset value relative to the current position\".</li>\n</ol>\n<p>Example. Before compression:</p>\n<div><pre><code><span>Hello world Hello</span></code></pre></div>\n<p>After compression:</p>\n<div><pre><code><span>literals 12 \"Hello world \" match 5 12</span></code></pre></div>\n<p>If we take a compressed block and iterate the cursor through it while running these commands, we will get the original uncompressed data as the result.</p>\n<p>So that's basically how data is decompressed. The basic idea is clear: to perform compression, the algorithm encodes a repeated sequence of bytes using matches.</p>\n<p>Some characteristics are also clear. This byte-oriented algorithm does not dissect individual bytes; it only copies them in their entirety. This is how it differs from entropy encoding. For instance,<a target=\"_blank\" href=\"https://github.com/facebook/zstd/\"> zstd</a> is a combination of LZ77 and entropy encoding.</p>\n<p>Note that the size of the compressed block shouldn't be too large. The size is chosen to avoid wasting a lot of RAM during decompression, to avoid slowing down random access too much in the compressed file (which consists of a large number of compressed blocks), and sometimes so the block will fit in a CPU cache. For example, you can choose 64 KB so that the buffers for compressed and uncompressed data will fit in the L2 cache with half still free.</p>\n<p>If we need to compress a larger file, we can concatenate the compressed blocks. This is also convenient for storing additional data (like a checksum) with each compressed block.</p>\n<p>The maximum offset for the match is limited. In LZ4, the limit is 64 kilobytes. This amount is called the sliding window. This means that matches can be found in a window of 64 kilobytes preceding the cursor, which slides with the cursor as it moves forward.</p>\n<p>Now let's look at how to compress data, or, in other words, how to find matching sequences in a file. You can always use a suffix trie (it's great if you've actually heard of this). There are methods that guarantee that the longest match is located in the preceding bytes after compression. This is called optimal parsing, and it provides nearly the best compression ratio for a fixed-format compressed block. But there are better approaches, such as finding a good-enough match that is not necessarily the longest. The most efficient way to find it is using a hash table.</p>\n<p>To do this, we iterate the cursor through the original block of data and take a few bytes after the cursor (let's say 4 bytes). We hash them and put the offset from the beginning of the block (where the 4 bytes were taken from) into the hash table. The value 4 is called \"min-match\" — using this hash table, we can find matches of at least 4 bytes.</p>\n<p>If we look at the hash table and it already has a matching record, and the offset doesn't exceed the sliding window, we check to see how many more bytes match after those 4 bytes. Maybe there are a lot more matches. It is also possible that there is a collision in the hash table, and nothing matches, but this is not a big deal. You can just replace the value in the hash table with a new one. Collisions in the hash table will simply lead to a lower compression ratio since there will be fewer matches. By the way, this type of hash table (with a fixed size and no resolution of collisions) is called a \"cache table\". This name makes sense because, in the event of a collision, the cache table simply forgets about the old entry.</p>\n<blockquote>\n<p>A challenge for the careful reader. Let's assume that the data is an array of UInt32 numbers in little endian format that represents a part of a sequence of natural numbers: 0, 1, 2… Explain why this data isn't compressed when using LZ4 (the size of the compressed data isn't any smaller compared to the uncompressed data).</p>\n</blockquote>\n<h2 id=\"how-to-speed-everything-up\"></h2>\n<p>So I want to speed up LZ4 decompression. Let's see how the decompression loop looks like. Here it is in pseudocode:</p>\n<div><pre><code><span>while (...)</span>\n<span>{</span>\n<span>   read(input_pos, literal_length, match_length);</span>\n<span></span>\n<span>   copy(output_pos, input_pos, literal_length);</span>\n<span>   output_pos += literal_length;</span>\n<span></span>\n<span>   read(input_pos, match_offset);</span>\n<span></span>\n<span>   copy(output_pos, output_pos - match_offset,</span>\n<span>       match_length);</span>\n<span>   output_pos += match_length;</span>\n<span>}</span></code></pre></div>\n<p>LZ4 format is designed so that literals and matches alternate in a compressed file. Obviously, the literal always comes first (because there's nowhere to take a match from at the very beginning). Therefore, their lengths are encoded together.</p>\n<p>It's actually a little more complicated than this. One byte is read from the file, and then it's split into two nibbles (half-bytes) which contain the encoded numbers 0 to 15. If the corresponding number is not 15, it is assumed to be the length of the literal and match, respectively. And if it is 15, the length is longer, and it is encoded in the following bytes. Then the next byte is read, and its value is added to the length. If it is equal to 255, the same thing is done with the next byte.</p>\n<p>Note that the maximum compression ratio for LZ4 format does not reach 255. And another useless observation is that if your data is very redundant, using LZ4 twice will improve the compression ratio.</p>\n<p>When we read the length of a literal (and then the match length and the match offset), just copying two blocks of memory is enough to decompress it.</p>\n<h3 id=\"how-to-copy-a-memory-block\"></h3>\n<p>It would seem that you could just use the <code>memcpy</code> function, which is designed to copy memory blocks. But this is not the optimal approach and not really appropriate.</p>\n<p>Using memcpy isn't optimal because:</p>\n<ol>\n<li>It is usually located in the libc library (and the libc library is usually dynamically linked, so the memcpy call will be made indirectly via PLT).</li>\n<li>It is not inlined by compiler if the size argument is unknown at compile time.</li>\n<li>It puts out a lot of effort to correctly process the leftovers of a memory block that are not multiples of the machine word length or register.</li>\n</ol>\n<p>The last point is the most important. Let's say we asked the <code>memcpy</code> function to copy exactly 5 bytes. It would be great to copy 8 bytes right away, using two movq instructions.</p>\n<p><code>Hello world <span>Hello </span><span>wo</span>...<br>\n^^^^^<span>^^^</span> - src<br>\n&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;^^^^^<span>^^^</span> - dst</code></p>\n<p>But then we'll be copying three extra bytes, so we'll be writing outside of buffer bounds. The <code>memcpy</code> function doesn't have permission to do this, because it could overwrite some data in our program and lead to a memory stomping bug. And if we wrote to an unaligned address, these extra bytes could land on an unallocated page of virtual memory or on a page without write access. That would give us a segmentation fault (this is good).</p>\n<p>But in our case, we can almost always write extra bytes. We can read extra bytes in the input buffer as long as the extra bytes are located entirely inside it. Under the same conditions, we can write the extra bytes to the output buffer, because we will still overwrite them on the next iteration.</p>\n<p>This optimization is already in the original implementation of LZ4:</p>\n<div><pre><code><span><span><span>inline</span> <span>void</span> <span>copy8</span><span>(UInt8 * dst, <span>const</span> UInt8 * src)</span></span></span>\n<span><span></span>{</span>\n<span>   <span>memcpy</span>(dst, src, <span>8</span>);    <span>/// Note that memcpy isn't actually called here.</span></span>\n<span>}</span>\n<span></span>\n<span><span><span>inline</span> <span>void</span> <span>wildCopy8</span><span>(UInt8 * dst, <span>const</span> UInt8 * src, UInt8 * dst_end)</span></span></span>\n<span><span></span>{</span>\n<span>   <span>do</span></span>\n<span>   {</span>\n<span>       <span>copy8</span>(dst, src);</span>\n<span>       dst += <span>8</span>;</span>\n<span>       src += <span>8</span>;</span>\n<span>   } <span>while</span> (dst &lt; dst_end);</span>\n<span>}</span></code></pre></div>\n<p>To take advantage of this optimization, we just need to make sure that we are far enough away from the buffer bounds. This shouldn't cost anything, because we are already checking for buffer overflow. And processing the last few bytes, the \"leftover\" data, can be done after the main loop.</p>\n<p>However, there are still a few nuances. Copying occurs twice in the loop: with a literal and a match. However, when using the <code>LZ4_decompress_fast</code> function (instead of <code>LZ4_decompress_safe</code>), the check is performed only once, when we need to copy the literal. The check is not performed when copying the match, but the <a target=\"_blank\" href=\"https://github.com/lz4/lz4/blob/master/doc/lz4_Block_format.md\">specification for the LZ4 format</a> has conditions that allow you to avoid it:</p>\n<ul>\n<li>The last 5 bytes are always literals.</li>\n<li>The last match must start at least 12 bytes before the end of block.</li>\n<li>Consequently, a block with less than 13 bytes cannot be compressed.</li>\n</ul>\n<p>Specially selected input data may lead to memory corruption. If you use the <code>LZ4_decompress_fast</code> function, you need protection from bad data. At the very least, you should calculate checksums for the compressed data. If you need protection from hackers, use the <code>LZ4_decompress_safe</code> function. Other options: take a cryptographic hash function as the checksum (although this is likely to destroy performance); allocate more memory for buffers; allocate memory for buffers with a separate <code>mmap</code> call and create a guard page.</p>\n<p>When I see code that copies 8 bytes of data, I immediately wonder why exactly 8 bytes. You can copy 16 bytes using SSE registers:</p>\n<div><pre><code><span><span><span>inline</span> <span>void</span> <span>copy16</span><span>(UInt8 * dst, <span>const</span> UInt8 * src)</span></span></span>\n<span><span></span>{</span>\n<span><span>#<span>if</span> __SSE2__</span></span>\n<span>    _mm_storeu_si128(<span>reinterpret_cast</span>&lt;__m128i *&gt;(dst),</span>\n<span>        _mm_loadu_si128(<span>reinterpret_cast</span>&lt;<span>const</span> __m128i *&gt;(src)));</span>\n<span><span>#<span>else</span></span></span>\n<span>    <span>memcpy</span>(dst, src, <span>16</span>);</span>\n<span><span>#<span>endif</span></span></span>\n<span>}</span>\n<span></span>\n<span><span><span>inline</span> <span>void</span> <span>wildCopy16</span><span>(UInt8 * dst, <span>const</span> UInt8 * src, UInt8 * dst_end)</span></span></span>\n<span><span></span>{</span>\n<span>    <span>do</span></span>\n<span>    {</span>\n<span>        <span>copy16</span>(dst, src);</span>\n<span>        dst += <span>16</span>;</span>\n<span>        src += <span>16</span>;</span>\n<span>    } <span>while</span> (dst &lt; dst_end);</span>\n<span>}</span></code></pre></div>\n<p>The same thing works for copying 32 bytes for AVX and 64 bytes for AVX-512. In addition, you can unroll the loop several times. If you have ever looked at how <code>memcpy</code> is implemented, this is exactly the approach that is used. (By the way, the compiler won't unroll or vectorize the loop in this case, because this will require inserting bulky checks.)</p>\n<p>Why didn't the original LZ4 implementation do this? First, it isn't clear whether this is better or worse. The resulting gain depends on the size of the blocks to copy, so if they are all short, it would be creating extra work for nothing. And secondly, it ruins the provisions in the LZ4 format that help avoid an unnecessary branch in the internal loop.</p>\n<p>However, we will keep this option in mind for the time being.</p>\n<h3 id=\"tricky-copying\"></h3>\n<p>Let's go back to the question of whether it's always possible to copy data this way. Let's say we need to copy a match, that is, take a piece of memory from the output buffer that is located at some offset behind the cursor and copy it to the cursor position.</p>\n<p>Imagine a simple case when you need to copy 5 bytes at an offset of 12:</p>\n<p><code><span>Hello</span> world ...........<br>\n^^^^^ - src<br>\n&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;^^^^^ - dst<br>\n<br>\nHello world <span>Hello</span> <span>wo</span>...<br>\n^^^^^ - src<br>\n&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;^^^^^ - dst</code></p>\n<p>But there is a more difficult case, when we need to copy a block of memory that is longer than the offset. In other words, it includes some data that has not yet been written to the output buffer.</p>\n<p>Copy 10 bytes at an offset of 3:</p>\n<p><code><span>abc</span>.............<br>\n^^^^^^^^^^ - src<br>\n&#160;&#160;&#160;^^^^^^^^^^ - dst<br>\n<br>\nabc<span>abcabcabca</span>...<br>\n^^^^^^^^^^ - src<br>\n&#160;&#160;&#160;^^^^^^^^^^ - dst</code></p>\n<p>We have all the data during the compression process, and such a match may well be found. The <code>memcpy</code> function is not suitable for copying it, because it doesn't support the case when ranges of memory blocks overlap. The <code>memmove</code> function won't work either, because the block of memory that the data should be taken from has not been fully initialized yet. We need to copy the same way as if we were copying byte by byte.</p>\n<div><pre><code><span>op[0] = match[0];</span>\n<span>op[1] = match[1];</span>\n<span>op[2] = match[2];</span>\n<span>op[3] = match[3];</span>\n<span>...</span></code></pre></div>\n<p>Here's how it works:</p>\n<p><code><span>a</span>bc<span>a</span>............<br>\n^ - src<br>\n&#160;&#160;&#160;^ - dst<br>\n<br>\na<span>b</span>ca<span>b</span>...........<br>\n&#160;^ - src<br>\n&#160;&#160;&#160;&#160;^ - dst<br>\n<br>\nab<span>c</span>ab<span>c</span>..........<br>\n&#160;&#160;^ - src<br>\n&#160;&#160;&#160;&#160; ^ - dst<br>\n<br>\nabc<span>a</span>bc<span>a</span>.........<br>\n&#160;&#160;&#160;^ - src<br>\n&#160;&#160;&#160;&#160; ^ - dst<br>\n<br>\nabca<span>b</span>ca<span>b</span>........<br>\n&#160;&#160;&#160;&#160;^ - src<br>\n&#160;&#160;&#160;&#160;&#160;&#160;&#160;^ - dst</code></p>\n<p>In other words, we must create a repeating sequence. The original implementation of LZ4 used some surprisingly strange code to do this:</p>\n<div><pre><code><span><span>const</span> <span>unsigned</span> dec32table[] = {<span>0</span>, <span>1</span>, <span>2</span>, <span>1</span>, <span>4</span>, <span>4</span>, <span>4</span>, <span>4</span>};</span>\n<span><span>const</span> <span>int</span> dec64table[] = {<span>0</span>, <span>0</span>, <span>0</span>, <span>-1</span>, <span>0</span>, <span>1</span>, <span>2</span>, <span>3</span>};</span>\n<span></span>\n<span><span>const</span> <span>int</span> dec64 = dec64table[offset];</span>\n<span>op[<span>0</span>] = match[<span>0</span>];</span>\n<span>op[<span>1</span>] = match[<span>1</span>];</span>\n<span>op[<span>2</span>] = match[<span>2</span>];</span>\n<span>op[<span>3</span>] = match[<span>3</span>];</span>\n<span>match += dec32table[offset];</span>\n<span><span>memcpy</span>(op<span>+4</span>, match, <span>4</span>);</span>\n<span>match -= dec64;</span></code></pre></div>\n<p>It copies the first 4 bytes one by one, skips ahead by some magic number, copies the next 4 bytes entirely, and moves the cursor to a match using another magic number. The author of the code (<a target=\"_blank\" href=\"http://fastcompression.blogspot.com/\">Yan Collet</a>) somehow forgot to leave a comment about what this means. In addition, the variable names are confusing. They are both named dec...table, but one is added and the other is subtracted. In addition, one of them is unsigned, and the other is int. However, the author recently improved this place in the code.</p>\n<p>Here's how it actually works. We copy the first 4 bytes one at a time:</p>\n<p><code>abc<span>abca</span>.........<br>\n^^^^ - src<br>\n&#160;&#160;&#160;^^^^ - dst</code></p>\n<p>Now we can copy 4 bytes at once:</p>\n<p><code>abcabca<span>bcab</span>.....<br>\n&#160;^^^^ - src<br>\n&#160;&#160;&#160;&#160;&#160;&#160;&#160;^^^^ - dst</code></p>\n<p>We can continue as usual, copying 8 bytes at once:</p>\n<p><code>abcabcabcab<span>cabcabca</span>.....<br>\n&#160;&#160;^^^^^^^^ - src<br>\n&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;&#160;^^^^^^^^ - dst</code></p>\n<p>As we all know from experience, sometimes the best way to understand code is to rewrite it. We could create a representative set of data and hardware, then perform serious load testing and choose the method that is best on average. But we don't have a representative dataset. For testing, I used a sample of <a target=\"_blank\" href=\"http://getting/\">Web Analytics Data</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/ontime\">flights in the United States</a>. But this isn't sufficient because ClickHouse is used by hundreds of companies around the world. By over-optimizing one dataset, we might cause a drop in performance with other data and not even realize it. And if the results depend on the processor model, we'll have to explicitly write the conditions in the code and test it on each model (or consult the reference manual on timing instructions, what do you think?). In either case, this is too time-consuming.</p>\n<p>So I decided to use another method, which is obvious to colleagues who studied at our School of Data Analysis: <a target=\"_blank\" href=\"https://learnforeverlearn.com/bandits/\">\"multi-armed bandits\"</a>. The point is that the variant of the algorithm is chosen randomly, and then we use statistics to progressively choose the variants that perform better.</p>\n<p>Many blocks of data need to be decompressed, so we need independent function calls for decompressing data. We could choose one of the four algorithms for each block and measure its execution time. An operation like this usually costs nothing in comparison with processing a block of data, and in ClickHouse, a block of uncompressed data is at least 64 KB. (Read this <a target=\"_blank\" href=\"http://btorpey.github.io/blog/2014/02/18/clock-sources-in-linux/\">article</a> about measuring time).</p>\n<p>To get a better understanding of how the \"multi-armed bandits\" algorithm works, let's look at where the name comes from. This is an analogy with slot machines in a casino which have several levers that a player can pull to get some random amount of money. The player can pull the levers multiple times in any order. Each lever has a fixed probability for the corresponding amount of money given out, but the player does not know how it works and can only learn it from experience playing the game. Once they figure it out, they can maximize their winnings.</p>\n<p>One approach to maximizing the reward is to evaluate the probability distribution for each lever at each step based on the game statistics from previous steps. Then we mentally \"win\" a random reward for each lever based on the distributions received. Finally, we pull the lever that had the best outcome in our mental game. This approach is called Thompson Sampling.</p>\n<p>But we are choosing a decompression algorithm. The result is the execution time in picoseconds per byte: the fewer, the better. We will consider the execution time to be a random variable and evaluate its distribution using mathematical statistics. The Bayesian approach is often used for tasks like this, but it would be cumbersome to insert complex formulas into C++ code. We can use a parametric approach and say that a random variable belongs to a parametric family of random variables and then evaluate its parameters.</p>\n<p>How do we select the family of random variables? As an example, we could assume that the code execution time has a normal distribution. But this is absolutely wrong. First, the execution time can't be negative, and normal distribution takes values everywhere on the number line. Second, I assume that the execution time will have a heavy \"tail\" on the right end.</p>\n<p>However, there are factors that could make it a good idea to estimate normal distribution only for the purposes of Thompson Sampling (despite the fact that the distribution of the target variable is not necessarily normal). The reason for this is that it is very easy to calculate the mathematical expectation and the variance, and after a sufficient number of iterations, a normal distribution becomes fairly narrow, similar to the distributions that we would have obtained using other methods. If we aren't too concerned with the convergence rate at the first steps, these details can be ignored.</p>\n<p>This may seem like a somewhat ignorant approach. Experience has shown us that the average time for query execution, website page loading, and so on is \"garbage\" that isn't worth calculating. It would be better to calculate the median, which is a <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Robust_statistics\">robust statistic</a>. But this is a little more difficult, and as I will show later, the described method justifies itself for practical purposes.</p>\n<p>At first, I implemented the calculation of the mathematical expectation and variance, but then I decided that this was too good, and I needed to simplify the code to make it \"worse\":</p>\n<div><pre><code><span><span>/// For better convergence, we don't use proper estimate of stddev.</span></span>\n<span><span>/// We want to eventually separate the two algorithms even in cases</span></span>\n<span><span>///  when there is no statistical significant difference between them.</span></span>\n<span><span><span>double</span> <span>sigma</span><span>()</span> <span>const</span></span></span>\n<span><span></span>{</span>\n<span>    <span>return</span> <span>mean</span>() / <span>sqrt</span>(<span>adjustedCount</span>());</span>\n<span>}</span>\n<span></span>\n<span><span><span>double</span> <span>sample</span><span>(pcg64 &amp; There might be an exceptionally large difference on certain CPUs.</p>\n<p>I prepared a set of datasets from different tables in ClickHouse with real data, for a total of 256 different files each with 100 MB of uncompressed data (the number 256 was coincidental). Then I looked at the CPUs of the servers where I can run benchmarks. I found servers with the following CPUs:</p>\n<ul>\n<li>Intel® Xeon® CPU E5-2650 v2 @ 2.60GHz</li>\n<li>Intel® Xeon® CPU E5-2660 v4 @ 2.00GHz</li>\n<li>Intel® Xeon® CPU E5-2660 0 @ 2.20GHz</li>\n<li>Intel® Xeon® CPU E5645 @ 2.40GHz</li>\n<li>Intel Xeon E312xx (Sandy Bridge)</li>\n<li>AMD Opteron(TM) Processor 6274</li>\n<li>AMD Opteron(tm) Processor 6380</li>\n<li>Intel® Xeon® CPU E5-2683 v4 @ 2.10GHz</li>\n<li>Intel® Xeon® CPU E5530 @ 2.40GHz</li>\n<li>Intel® Xeon® CPU E5440 @ 2.83GHz</li>\n<li>Intel® Xeon® CPU E5-2667 v2 @ 3.30GHz</li>\n</ul>\n<p>The most interesting part comes next — the following processors were also made available:</p>\n<ul>\n<li>AMD EPYC 7351 16-Core Processor, a new AMD server processor at the time.</li>\n<li>Cavium ThunderX2, which is AArch64, not x86. Yes, LZ4 decompression was accelerated on average by 12-20%, and on some datasets, the performance more than doubled. But in general, this doesn't have much effect on query execution time. It's difficult to find real queries that gain more than a couple of percents in speed.</p>\n<p>At the time, we decided to use ZStandard level 1 instead of LZ4 on several clusters intended for executing long queries; because it is more important to save IO and disk space on cold data. Keep this in mind if you have a similar workload.</p>\n<p>We observed the greatest benefits from optimizing decompression in highly compressible data, such as columns with mostly duplicate string values. However, we have developed a separate solution specifically for this scenario that allows us to significantly speed up queries over this kind of data.</p>\n<p>Another point to remember is that optimization of decompression speed is often limited by the format of the compressed data. LZ4 uses a very good format, but Lizard, Density, and LZSSE have other formats that can work faster. Perhaps instead of trying to accelerate LZ4, it would be better to just integrate LZSSE into ClickHouse.</p>\n<p>It's unlikely that these optimizations will be implemented in the mainstream LZ4 library: in order to use them, the library interface would have to be modified. In fact, this is often the case with improving algorithms — optimizations don't fit into old abstractions, and they have to be revised. However, variable names have already been corrected in the original implementation. For instance, <code>inc</code> and <code>dec</code> tables have been <a target=\"_blank\" href=\"https://github.com/lz4/lz4/blob/dev/lib/lz4.c#L313\">corrected</a>. In addition, the original implementation accelerated decompression by the same 12-15% by copying 32 bytes instead of 16, as discussed above. We tried the 32-byte option ourselves, and the results were not that great, but they were still <a target=\"_blank\" href=\"https://habrastorage.org/webt/d0/jn/ia/d0jniaidtjaqnnu2ek3fbznv8ji.png\">faster</a>.</p>\n<p>If you look at the profile at the beginning of the article, you may notice that we could have removed one extra copying operation from the page cache to userspace (either using mmap, or using O_DIRECT and userspace page cache, but both options are problematic). We also could have slightly improved the checksum calculation (CityHash128 is currently used without CRC32-C, but we could use HighwayHash, FARSH, or XXH3). Acceleration of these two operations is useful for weakly compressed data since they are performed on compressed data.</p>\n<p>In any case, the changes were incorporated into master, and the ideas that resulted from this research have been applied in other tasks.</p></div></article>"
