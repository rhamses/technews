While individual deployments may benefit from further tuning based on their specific requirements, the resulting optimizations would be effective across a broad range of observability workloads we saw within our user base.</p>\n</blockquote>\n<p>Focusing initially on the logs schema, we decided to use a dataset that was derived from the same OpenTelemetry corpus used in our <a target=\"_blank\" href=\"https://clickhouse.com/blog/building-clickcannon-a-tool-for-benchmark-clickhouse#intro\">ClickCannon benchmarking work</a>. We continue to evolve this dataset over time, using insights from anonymized platform telemetry to ensure it remains representative of production workloads and the query patterns our customers rely on most.</p>\n<h2 id=\"user-content-evaluating_improvements\"></h2>\n<p>Measuring the success of a schema change is more nuanced than simply looking at query latency. Every optimization introduces trade-offs, and an improvement in one area can create regressions elsewhere. Our goal was not to produce the fastest possible benchmark result for a single query, but to improve ClickStack's overall efficiency, i.e., improving query performance while preserving a balanced operational profile. To achieve this, every schema iteration was evaluated against a consistent set of metrics and qualifying criteria before being considered for adoption.</p>\n<blockquote>\n<p>All benchmarks were performed using <a target=\"_blank\" href=\"https://clickhouse.com/docs/cloud/reference/warehouses\">ClickHouse Cloud warehouses</a>. Again, if these are appreciably impacted, they must be evaluated against the gains made in query performance.</p>\n<p>Assuming any additional costs are acceptable, we evaluate the performance of individual queries. While most optimizations targeted a specific query pattern, every benchmark run also includes the broader workload to ensure improvements are not achieved at the expense of regressions elsewhere in the product.</p>\n<h2 id=\"user-content-schema_optimizations\"></h2>\n<p>We explored a wide range of potential optimizations, but the most impactful changes fell into five categories: primary key noteworthy design decisions. OpenTelemetry's dynamic attributes e.g. <code>ResourceAttributes</code> are stored using ClickHouse's <code>Map</code> type, allowing arbitrary resource, scope, and log attributes to be ingested without requiring schema changes. To accelerate filtering on commonly queried attributes, a small set of Kubernetes and deployment-related fields are materialized into dedicated columns. This avoids repeatedly extracting values from maps at query time and improves performance for common searches and aggregations. The UI automatically identifies that these columns have been extracted and uses them where possible.</p>\n<p>The schema also makes extensive use of data-skipping indexes. Bloom filters are applied to both map keys and map values, allowing ClickHouse to quickly eliminate granules that cannot possibly contain a requested attribute or value. Similarly, the log body is indexed using a <code>tokenbf_v1</code> index, enabling more efficient token-based searches over unstructured log content.</p>\n<p>The ordering strategy is equally important. Data is sorted by <code>(ServiceName, TimestampTime, Timestamp)</code>, with the primary key containing only <code>(ServiceName, TimestampTime)</code>. Placing <code>ServiceName</code> first ensures telemetry from the same service is co-located on disk, making service-specific filtering highly efficient. <code>TimestampTime</code>, a minute-level representation of the nanosecond-precision <code>Timestamp</code> column, was included to improve locality and create more contiguous ranges for time-based queries. Notably, the sparse primary key index (controlled by the <code>PRIMARY KEY</code> clause) does not include the full <code>Timestamp</code> column itself. Since most filtering benefits are already captured by <code>TimestampTime</code>, including the higher-cardinality timestamp would provide little additional pruning while increasing memory consumption for the primary key index.</p>\n<h3 id=\"user-content-time_bucketing_the_primary_key\"></h3>\n<p>Defining a primary key in ClickHouse defines how your data is sorted at rest, as well as the contents of the sparse index. The previous primary key was <code>(ServiceName, TimestampTime)</code>. <code>ServiceName</code> is the name of the service emitting telemetry, and <code>TimestampTime</code> is the <code>Timestamp</code> rounded down to seconds.</p>\n<p>If structured appropriately, the primary key can be exploited by the <a target=\"_blank\" href=\"https://clickhouse.com/docs/knowledgebase/async_vs_optimize_read_in_order#what-about-optimize_read_in_order\">read_in_order</a> optimization, which short-circuits Top N queries after a <code>LIMIT</code> has been reached — used in the ClickStack UI when searching logs. However, this requires the primary key to align with the query time sorting, typically <code>Timestamp</code>, in ClickStack. This optimization was the main influence for modifying the primary key.</p>\n<p>The challenge was choosing the right level of time bucketing. Using a high-cardinality value, such as the raw timestamp, would fragment the data into too many small ranges, reducing compression efficiency and making scans less efficient. This was one of the primary reasons the original schema led with <code>ServiceName</code>, which groups similar data together on disk and improves locality.</p>\n<p>Our initial experiments used <code>toStartOfMinute(Timestamp)</code>. While this successfully activated the <code>read_in_order</code> optimization, benchmarks showed that both search and aggregation queries suffered because the finer granularity created too many granule ranges to read from disk. As the time range over which the search grew, this effect became increasingly pronounced.</p>\n<div><pre><code><span><span>-- Before</span></span>\n<span><span>PRIMARY KEY</span> (ServiceName, TimestampTime)</span>\n<span><span>ORDER</span> <span>BY</span> (ServiceName, TimestampTime, <span>Timestamp</span>)</span>\n<span></span>\n<span><span>-- After</span></span>\n<span><span>PRIMARY KEY</span> (toStartOfFiveMinutes(TimestampTime), ServiceName, TimestampTime)</span></code></pre></div>\n<p>After extensive testing, we settled on <code>toStartOfFiveMinutes(Timestamp)</code>. The five-minute bucket preserved the benefits of <code>read_in_order</code> while maintaining larger, more contiguous data ranges on disk. It showed no measurable degradation for timestamp-driven queries, improved compression characteristics, and avoided the regressions seen with one-minute bucketing. It also proved beneficial for queries that relied on other predicates, such as <code>ServiceName</code>, which were negatively impacted by the higher cardinality of the one-minute approach.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_perf_jul2026_image11_fc3daccaeb.png&w=2048&q=75\"></span>\n<em>The green bars here represent the previous schema, the yellow the proposed changes. This means it's 32 bytes instead of 64, with second-level precision. This reduced the size of the sparse primary key index and the amount of data read during pruning, while still providing effective time-based pruning using a lower-cardinality timestamp.</p>\n<div><pre><code><span><span>-- Before</span></span>\n<span>`TimestampTime` DateTime <span>DEFAULT</span> toDateTime(<span>Timestamp</span>),</span>\n<span><span>PARTITION</span> <span>BY</span> toDate(TimestampTime)</span>\n<span><span>PRIMARY KEY</span> (toStartOfFiveMinutes(TimestampTime), ServiceName, TimestampTime)</span>\n<span></span>\n<span><span>-- After</span></span>\n<span><span>PARTITION</span> <span>BY</span> toDate(<span>Timestamp</span>)</span>\n<span><span>PRIMARY KEY</span> (toStartOfFiveMinutes(<span>Timestamp</span>), ServiceName, <span>Timestamp</span>)</span></code></pre></div>\n<p>Once the primary key was reorganized around <code>toStartOfFiveMinutes(Timestamp)</code>, that benefit largely disappeared. The five-minute bucket already established the desired temporal locality, and <code>Timestamp</code> naturally orders rows within each bucket. Benchmarking showed that retaining the intermediate <code>TimestampTime</code> column provided no measurable improvement, so we removed it. This simplified the schema, slightly reduced primary key memory usage, eliminated an unnecessary timestamp predicate in many queries, and avoided maintaining two timestamp representations.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_perf_jul2026_image6_eedc8c391d.png&w=2048&q=75\"></span>\n<em>The green bars represent the previous schema with TimestampTime; the yellow bars show the schema after removing it. Only the affected queries are shown.</em></p>\n<h3 id=\"user-content-using_text_index_for_the_body\"></h3>\n<p>The log <code>Body</code> column was previously using a <code>tokenbf</code>, which applies a bloom filter to the tokens of the string. Bloom filters are probabilistic data structures that can definitively eliminate granules that do not contain a match, but have an associated false positive rate (1% in the previous schema). This allows many granules to be skipped entirely, but any remaining granules still need to be read and the matching rows verified. Because Bloom filters can produce false positives, some of those granules may ultimately contain no matching rows at all.</p>\n<p>Earlier this year, we announced <a target=\"_blank\" href=\"https://clickhouse.com/blog/full-text-search-ga-release\">text indexes as GA in ClickHouse</a>. This uses an inverted index to provide superior granule pruning that is also deterministic (no false positivity).</p>\n<div><pre><code><span><span>-- Before</span></span>\n<span>INDEX idx_lower_body <span>lower</span>(Body) TYPE tokenbf_v1(<span>32768</span>, <span>3</span>, <span>0</span>) GRANULARITY <span>8</span></span>\n<span></span>\n<span><span>-- After</span></span>\n<span>INDEX idx_lower_body <span>lower</span>(Body) TYPE text(tokenizer <span>=</span> <span>'splitByNonAlpha'</span>)</span></code></pre></div>\n<p>We apply this new text index with the <code>splitByNonAlpha</code> tokenizer — similar to <code>tokenbf</code>. Our testing revealed that while incurring an insert time overhead and some additional storage footprint for indices, read performance was maintained or improved.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_perf_jul2026_image7_19a2aa5571.png&w=2048&q=75\"></span>\n<em>The green bars here represent bloom filters; the yellow bars represent full-text search. The regression demonstrates how tricky schema changes are and why representative queries are so important for optimizing. This appears as a regression now, but will be addressed by the block offset and block number optimization mentioned later.</p>\n<p>Furthermore, if the text index determines that a term exists in a row, ClickHouse can often satisfy part of the query directly from the index through the <code>direct_read</code> optimization. For highly selective searches, this avoids reading and decompressing large portions of the underlying column data, reducing both I/O and CPU overhead. This differs from the Bloom filter-based approach, which can only indicate that a granule might contain a match and still requires the data to be read and verified. As a result, text indexes are particularly effective for \"needle-in-a-haystack\" searches, where only a small fraction of rows contain the requested term, or any search filters on the Body that also request an aggregation e.g., count for the search histogram page.</p>\n<h3 id=\"user-content-traceid_as_text_index\"></h3>\n<p>As mentioned earlier, Bloom filters have an associated false positive rate. Text indexes do not, which makes them especially effective for highly selective searches. A <code>TraceId</code> lookup is a good example: the query is usually looking for one exact identifier across a very large volume of data. We thus decided to evaluate removing the Bloom filter from the <code>TraceId</code> column and using a text index instead.</p>\n<div><pre><code><span><span>-- Before</span></span>\n<span>INDEX idx_trace_id TraceId TYPE bloom_filter(<span>0.001</span>) GRANULARITY <span>1</span>,</span>\n<span></span>\n<span><span>-- After</span></span>\n<span>INDEX idx_trace_id TraceId TYPE text(tokenizer<span>=</span><span>'array'</span>),</span></code></pre></div>\n<p>As shown in the benchmark results below, replacing the Bloom filter with a text index improved <code>TraceId</code> searches by up to 22% in benchmarking, and scales well with increased volume.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_perf_jul2026_image5_2c3676b63e.png&w=2048&q=75\"></span></p>\n<p>This does increase index storage, but because indexes reside in object storage, the additional cost is typically outweighed by the resulting improvements in query performance.</p>\n<h3 id=\"user-content-block_offset_and_block_number_settings\"></h3>\n<p>Many workflows in ClickStack ultimately require loading a single row. Viewing an individual log line is a common example. Search results typically return only a subset of columns to minimize data transfer and query cost, so when a user drills into a result, we need to fetch the complete row and all of its associated column values.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_perf_jul2026_image3_ca65b2b40f.png&w=2048&q=75\"></span></p>\n<p>Identifying that row efficiently is not as straightforward as it might seem. ClickHouse's primary key is designed for data locality and pruning rather than uniqueness, meaning there may be multiple rows that share the same values for the columns returned by the initial search. Historically, ClickStack would use all returned column values as predicates when reloading the row. For example, if a search returned <code>Timestamp</code>, <code>ServiceName</code>, <code>SeverityText</code>, and <code>Body</code>, those values would all be included in the subsequent lookup query. This works, but requires filtering on additional columns and can result in more data being read than necessary.</p>\n<blockquote>\n<p>The performance of this query also regressed after introducing text indexes due to their evaluation overhead. This motivated us to eliminate that overhead where possible.</p>\n</blockquote>\n<p>ClickHouse provides a better mechanism through the <code>_block_number</code> and <code>_block_offset</code> virtual columns. Every inserted row belongs to a block, identified by <code>_block_number</code>, and has a unique position within that block, identified by <code>_block_offset</code>.</p>\n<div><pre><code><span><span>-- Before</span></span>\n<span>SETTINGS index_granularity <span>=</span> <span>8192</span>, ttl_only_drop_parts <span>=</span> <span>1</span>;</span>\n<span></span>\n<span><span>-- After</span></span>\n<span>SETTINGS index_granularity <span>=</span> <span>8192</span>, ttl_only_drop_parts <span>=</span> <span>1</span>, enable_block_number_column <span>=</span> <span>1</span>, enable_block_offset_column <span>=</span> <span>1</span>;</span></code></pre></div>\n<p>By enabling the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/merge-tree-settings#enable_block_number_column\">table settings</a> required to persist these values, ClickStack can return them alongside search results and use them when fetching the full row.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickstack_perf_jul2026_image9_cf879ccc59.png&w=2048&q=75\"></span></p>\n<p>This significantly simplifies the lookup query. Instead of filtering on many potentially large columns, ClickStack only needs the primary key columns together with <code>_block_number</code> and <code>_block_offset</code> to uniquely identify the row. Users could create materialized views tailored to their workload, register them with a source, and ClickStack would automatically use them whenever a query could be satisfied by the view instead of the underlying telemetry tables. This allowed users to shift work from query time to insert time, often resulting in substantial performance improvements.</p>\n<p>As we gained more experience with the feature, we began looking for opportunities to apply the same approach elsewhere in the product. One area stood out immediately: autocomplete and filter value suggestions. Historically, this required querying the live <code>otel_logs</code> and <code>otel_traces</code> tables directly. While simple, the approach scaled poorly as datasets grew. Users were often forced to choose between slow introspection queries or sampled results that failed to surface enough values to be useful.</p></div><div><p>To address this, we started shipping materialized views as part of the default ClickStack schema. Rather than scanning telemetry tables at query time, ClickStack now maintains compact rollup tables dedicated to metadata discovery.
