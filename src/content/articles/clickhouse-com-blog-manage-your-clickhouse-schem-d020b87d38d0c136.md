Rotem dives into the details and shows the value of the recent support for ClickHouse.</p>\n</blockquote>\n<h2 id=\"the-rise-and-fall-of-schema-less-technologies\"></h2>\n<p>In the early 2010s, dynamically typed languages like Python and Javascript, and NoSQL databases like MongoDB and Elasticsearch marked the trend of departing from rigid, upfront schema planning.  All of these technologies, with less verbose syntax and greater flexibility, promised quicker development cycles and easier prototyping, making them the languages of choice for startups and new projects aiming for rapid market entry.</p>\n<p>However, as projects and organizations grew larger in size and complexity, the initial advantages of these technologies began to reveal significant trade-offs. The lack of schema enforcement led to inconsistencies in data, making it harder to ensure data quality and integrity as applications evolved. The absence of strict type systems and the flexible nature of schema-less databases made debugging and maintaining large codebases increasingly difficult.</p>\n<p>The increasing interest in relational storage technology such as ClickHouse signifies a nuanced shift in our industry’s approach to data management. While modern data systems need to process diverse datasets that sometimes require an unstructured approach, there is a growing appreciation for the efficiency and organization that comes with strongly typed, structured data processing methods.</p>\n<h2 id=\"managing-schemas-is-still-a-pain\"></h2>\n<p>One of the drivers of the NoSQL movement was that many developers wanted to avoid the pains of managing database schemas at all costs. Schema changes, also called migrations, require technical expertise to be done safely and efficiently. Modern databases provide a limited, <em>imperative</em>, way of changing schemas called DDL statements.</p>\n<p>What if instead of giving up on schemas and their benefits entirely, we could make managing them a seamless process that does not require any special effort? Administering database schemas undoubtedly requires technical expertise, but it's not an infinitely complex problem. Thus, automated tools can be created to simplify the task for non-experts.</p>\n<h2 id=\"database-schema-as-code\"></h2>\n<p><span><img alt=\"atlas_declarative_vs_imperative.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fatlas_declarative_vs_imperative_ffff9cd809.png&w=2048&q=75\"></span></p>\n<p>In recent years, in the wake of huge advancements made in cloud resource management with an approach called <a target=\"_blank\" href=\"https://developer.hashicorp.com/terraform/tutorials/aws-get-started/infrastructure-as-code\">Infrastructure-as-Code</a>, a new approach for managing database schemas is emerging. This approach, coined <a target=\"_blank\" href=\"https://atlasgo.io/blog/2024/01/24/why-schema-as-code\">\"Database Schema-as-Code\"</a> and embodied by projects such as <a target=\"_blank\" href=\"https://atlasgo.io/\">Atlas</a> and <a target=\"_blank\" href=\"https://www.skeema.io/\">Skeema</a>, aims to greatly simplify schema management by arming engineers with a tool that offers a _declarative _API for interacting with databases.</p>\n<p>A declarative API works by providing the tool with the <em>desired state</em> of the system and letting the tool figure out the operations needed to reconcile it with the <em>current state</em>. In the context of database schema management, users provide the tool with the schema they would like their database to have, let the tool inspect the current database information schema, and generate a migration plan for them automatically.</p>\n<p>Automatic migration planning isn’t a new concept, of course. Application development frameworks and ORMs such as Django, have offered similar capabilities for many years. The issue with automating migration planning at the ORM level is that they are only usable in their specific context and cannot be applied generically for every stack. In addition, ORMs tend to focus on a small subset of database features such as tables, columns, foreign keys, and indexes and do not provide a way to manage more advanced objects such as views, materialized views, stored procedures, etc.</p>\n<h2 id=\"how-it-works\"></h2>\n<p>Let’s see how Database Schema-as-Code and declarative migrations work in practice. To demonstrate it we will use <a target=\"_blank\" href=\"https://atlasgo.io/\">Atlas</a>, an open-core database schema-as-code tool (F.D: I am one of the creators). For getting started and installation instructions, visit the <a target=\"_blank\" href=\"https://atlasgo.io/getting-started\">Atlas docs</a>.</p>\n<p>As a prerequisite to this demo, let’s run a local, empty ClickHouse instance using Docker:</p>\n<div><pre><code><span>docker run --<span>rm</span> -d --name atlas-demo -e CLICKHOUSE_DB=demo -p 9000:9000 clickhouse/clickhouse-server:latest</span></code></pre></div>\n<p>Contrary to more traditional approaches, with declarative migrations, we always start with the desired state of the database. Let’s create a file named <code>schema.sql</code> with the following contents:</p>\n<div><pre><code><span><span>CREATE TABLE</span> `users` (</span>\n<span>   `id` UInt64,</span>\n<span>   `name` String)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>PRIMARY KEY</span> (`id`)</span>\n<span><span>ORDER</span> <span>BY</span> `id`;</span></code></pre></div>\n<p>Now, we can apply this schema to the target database using the <code>atlas schema apply</code> command:</p>\n<div><pre><code><span>atlas schema apply \\</span>\n<span>-u <span>\"clickhouse://localhost:9000/demo\"</span> \\</span>\n<span>--to file://schema.sql \\</span>\n<span>--dev-url <span>\"docker://clickhouse/23.11/demo\"</span></span></code></pre></div>\n<p>This will tell Atlas that we want to apply the schema defined in the file named <code>schema.sql</code> to the ClickHouse database at <code>localhost:9000/demo</code> (which we just used Docker to spin up locally).</p>\n<p>Atlas connects to the target database, inspects its information schema, calculates the diff between the current and desired state, and prompts us to approve the migration plan:</p>\n<div><pre><code><span>-- Planned Changes:</span>\n<span>-- Create <span>\"users\"</span> table</span>\n<span>CREATE TABLE `<span>users</span>` (</span>\n<span>  `<span>id</span>` UInt64,</span>\n<span>  `name` String</span>\n<span>) ENGINE = MergeTree</span>\n<span> PRIMARY KEY (`<span>id</span>`) SETTINGS index_granularity = 8192;</span>\n<span>? Are you sure?:</span>\n<span>  ▸ Apply</span>\n<span>    Lint and edit</span>\n<span>    Abort</span></code></pre></div>\n<p>The plan looks good, and so we hit \"Apply\" to apply the changes to the database.</p>\n<p>After successfully running the migration Atlas planned for us, we can re-run the <code>schema apply</code> command to ensure that the database is at its desired state:</p>\n<div><pre><code><span>atlas schema apply \\</span>\n<span>-u <span>\"clickhouse://localhost:9000/demo\"</span> \\</span>\n<span>--to file://schema.sql \\</span>\n<span>--dev-url <span>\"docker://clickhouse/23.11/demo\"</span></span></code></pre></div>\n<p>Once again, Atlas connects to our ClickHouse instance, inspects it, and calculates the diff, this time telling us:</p>\n<div><pre><code><span>Schema is synced, no changes to be made</span></code></pre></div>\n<p>Next, let’s make a small change to our desired state to show that declarative migrations work on a live database with an existing schema. Let’s add a new column to our <code>users</code> table, <code>email_address</code>. Edit <code>schema.sql</code> adding the following column:</p>\n<div><pre><code><span><span>CREATE TABLE</span> `users` (</span>\n<span>    `id` UInt64,</span>\n<span>    `name` String,</span>\n<span><span>+</span>    `email_address` String</span>\n<span>)</span>\n<span> ENGINE <span>=</span> MergeTree</span>\n<span> <span>PRIMARY KEY</span> (`id`)</span>\n<span><span>ORDER</span> <span>BY</span> `id`;</span></code></pre></div>\n<p>Next, let’s re-run the <code>schema apply</code>command and see how Atlas plans the migration for us:</p>\n<div><pre><code><span>-- Planned Changes:</span>\n<span>ALTER TABLE `<span>users</span>` ADD COLUMN `email_address` String;</span>\n<span>? Are you sure?:</span>\n<span>  ▸ Apply</span>\n<span>    Lint and edit</span>\n<span>    Abort</span></code></pre></div>\n<p>Great! Atlas detected the existing table and planned migration to add the missing column to the target database.  Let’s hit <code>Apply</code> to bring our database to the desired state.</p>\n<h2 id=\"wrapping-up\"></h2>\n<p>The 2010s trended towards schema-less databases as developers sought to avoid the complexities of schema management, but this shift led to challenges in data consistency and maintenance as systems scaled. Learning from the challenges of the past, the tech industry is now showing a renewed interest in relational technologies.</p>\n<p>However, developers still face the same challenges with schema management as they did in the past. Database Schema-as-Code tools such as <a target=\"_blank\" href=\"https://atlasgo.io/\">Atlas</a> emerge as a solution, offering to simplify and streamline schema operations, bridging the gap between the desire for development efficiency and the need for structured data integrity.</p>\n<p>In this article, we have shown a glimpse of the capabilities of Atlas which in what is by no means a comprehensive guide.
