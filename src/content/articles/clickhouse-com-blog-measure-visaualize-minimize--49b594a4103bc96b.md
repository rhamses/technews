contentHtml: "<div><h2 id=\"introduction\"></h2>\n<p>Many of the blog topics at ClickHouse are initiated by community engagement through mediums such as our <a target=\"_blank\" href=\"https://clickhouse.com/slack\">public Slack channel</a>. With the recent announcement of our <a target=\"_blank\" href=\"https://clickhouse.com/blog/kafka-connect-connector-clickhouse-with-exactly-once\">official Kafka Connector</a> and its <a target=\"_blank\" href=\"https://clickhouse.com/blog/real-time-event-streaming-with-kafka-connect-confluent-cloud-clickhouse\">support in Confluent Cloud</a>, we’ve had folks reaching out to ask about how to measure and mitigate latency when dealing with Kafka and transferring data to ClickHouse Cloud. That’s a good conversation to have and formulated our response in a blog post - let’s discuss!</p>\n<h2 id=\"how-does-the-kafka-connector-work\"></h2>\n<p>First things first, let’s remind everyone about how the connection between Kafka and ClickHouse works (and where our connector fits in). An example data flow might look like this:</p>\n<p><span><img alt=\"kafka_clickhouse_flow.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fkafka_clickhouse_flow_0cfec94deb.png&w=2048&q=75\"></span></p>\n<p>In essence, producers submit data to topics (A), which are fetched and then sent by “Kafka Connect” to the connector through polling (B), which pushes the records to ClickHouse (C). In the above diagram, A is separate from B, and B is separate from C - all three are distinct systems, with network connections between them.</p>\n<p>Implementations can vary of course, but we’ll work with the broadest setup for now so that it covers the most cases - if your setup doesn’t have a component mentioned, feel free to ignore that part.</p>\n<h2 id=\"what-is-latency\"></h2>\n<p>This all may be obvious but it bears repeating: latency (in this context) is the time data takes to travel from Point A to Point B. It’s caused by several factors, the most common being: hardware, software, and the network.</p>\n<p>Hardware factors are usually physical limitations that contribute to latency - VM sizing, processor speeds, etc. We defer these to the reader to resolve and focus on variables controllable by the Connector itself.</p>\n<p>Software factors are usually more design limitations than physical issues - number of threads, data structure, configuration settings, etc. They’re also especially common and what most of this guide will be focusing on.</p>\n<p>Network factors are usually the physical network between nodes, virtual connections between virtual machines, distance from client to server, etc.</p>\n<h2 id=\"when-is-latency-an-issue\"></h2>\n<p>Before we get into the <strong>how</strong> of latency, it’s important to briefly talk about <strong>when</strong> and <strong>why</strong>: “Why should I care about latency? When is latency an issue?”</p>\n<p>You’re the expert on your use case, but we would caution you about setting unrealistic expectations around latency - it’s easy to be overly fixated on small differences in latency, which are unlikely to have a significant business impact, such that even a second or two deviation results in alarms. Please keep in mind that in a network distributed environment there will be some amount of latency - the task is more about mitigating/stabilizing it where and when possible, rather than eliminating it entirely. Ideally, you are able to establish what is an acceptable latency and ensure this is maintained within defined bounds - possibly with an SLA.</p>\n<p>Similarly, one use case may tolerate far more latency than another use case - if you’re doing analysis on data once a week, that may allow for far more latency than real-time analytics. Even for real-time analytics, what “real-time” means is something you have to decide - again, you’re the expert on your use case; just keep in mind there are going to be hardware/software/network limitations.</p>\n<h2 id=\"how-do-i-measure-latency\"></h2>\n<p>In order to identify whether you have a latency problem in your Kafka pipeline, you need to be able to measure it.</p>\n<p>The simplest approach is to append timestamp values to messages at various points of the Kafka pipeline. These can later be compared, and visualized, to indicate possible steps causing latency.</p>\n<p>One really effective way we’ve seen to achieve this<sup>1</sup> is by using <a target=\"_blank\" href=\"https://docs.confluent.io/platform/current/connect/transforms/overview.html\">single message transformers</a>:</p>\n<p><span><img alt=\"message_transform.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmessage_transform_98ad734849.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p><sup>1</sup> There’s multiple options available, for example JMX, but we found SMT to be good enough - YMMV</p>\n</blockquote>\n<p>This transform takes several out-of-the-box fields (Offset, Partition, Timestamp, and Topic) and adds them into the object for the connector to pass on to ClickHouse, without having to change the message producers. This transformer can be configured to run at various steps, allowing users to attribute latency to specific parts of a processing pipeline.</p>\n<p><span><img alt=\"kafka_data_transformed.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fkafka_data_transformed_5674bc6163.png&w=2048&q=75\"></span></p>\n<p>The above transform allows us to identify timings at different stages of the Kafka pipeline. We can also record the exact point at which a message was inserted into ClickHouse as a row. This can be achieved using an insert timestamp via a DEFAULT expression, which can then be compared with earlier timings added by transforms:</p>\n<div><pre><code><span><span>CREATE TABLE</span> data_testing</span>\n<span>(</span>\n<span>  `raw` String,</span>\n<span>  `generationTimestamp` DateTime64(<span>3</span>),</span>\n<span>  `insertTime` DateTime64(<span>3</span>) <span>DEFAULT</span> now()</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> insertTime</span></code></pre></div>\n<p>Notice that we’re using “DEFAULT now()” so that the time is generated by ClickHouse and not present in the message itself - this will give us the insert time.</p>\n<p>If your messages have a generation timestamp, you could also track the time between: Message Generation &lt;-&gt; Kafka Insert &lt;-&gt; ClickHouse Insert.</p>\n<h2 id=\"how-do-i-visualize-latency\"></h2>\n<p>One common way to visualize latency is to use the built-in tables ClickHouse SQL Console (on ClickHouse Cloud) provides:</p>\n<p><span><img alt=\"sql-ui-kafka_increasing_latency.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsql_ui_kafka_increasing_latency_08fc385a2b.png&w=2048&q=75\"></span></p>\n<p>The data for this chart was created using a fairly simple query to calculate median, 75th percentile, and 99th percentile:</p>\n<div><pre><code><span><span>SELECT</span> formatDateTime(insertTime, <span>'%F %k:%i'</span>) <span>as</span> byMinutes,</span>\n<span>    median(dateDiff(<span>'second'</span>, generationTimestamp, insertTime)) <span>AS</span> median,</span>\n<span>    median(<span>.75</span>)(dateDiff(<span>'second'</span>, generationTimestamp, insertTime)) <span>AS</span> p_75,</span>\n<span>    median(<span>.95</span>)(dateDiff(<span>'second'</span>, generationTimestamp, insertTime)) <span>AS</span> p_95</span>\n<span><span>FROM</span> default.kafka_data</span>\n<span><span>WHERE</span> insertTime <span>&gt;</span> now() <span>-</span> <span>interval</span> <span>60</span> <span>MINUTE</span></span>\n<span><span>GROUP</span> <span>BY</span> byMinutes</span>\n<span><span>ORDER</span> <span>BY</span> byMinutes ASCENDING</span></code></pre></div>\n<p>InsertTime is provided by a default column (mentioned earlier using “now()”) while <code>generationTimestamp</code> is a column we set when generating the data - you could just as easily use something like <code>kafkaField</code> (mentioned earlier that was created by a transform).</p>\n<p>Note: The data in the example chart shows a slowly increasing latency time and just seeing this would be enough to indicate a possible issue - the power of a visual!</p>\n<h2 id=\"how-do-i-deal-with-latency\"></h2>\n<p>We’re going to cover a few ways to address latency, but keep in mind that this list isn’t exhaustive - you may find other methods work better. If you do, please let us know - the more information, the better we can help others!</p>\n<p>Latency can occur in multiple parts of the system. We address potential causes at each stage below.</p>\n<h3 id=\"latency-between-kafka-and-kafka-connect\"></h3>\n<h4 id=\"fetch-and-batch-size\"></h4>\n<p>Records are fetched by Kafka Connect independently of the connector, and you can tweak this by setting <strong>consumer.fetch.min.bytes</strong> and <strong>consumer.fetch.max.bytes</strong>. As you can imagine, there’s a balancing act here - ideally, you’re fetching more records than the batch size so that you always have enough to fill a batch. You can even tweak how often fetching happens by setting <strong>consumer.fetch.max.wait.ms</strong> - it might take longer, but the fetch is more likely to hit the maximum size (and so optimize how many connections need to be made) if you find you’re not generating messages all that often.</p>\n<p>Similarly, on the other side, the batches the connector receives are controlled by polling (the default is 500):</p>\n<div><pre><code><span>consumer.max.poll.records=[NUMBER OF RECORDS]</span>\n<span>consumer.max.partition.fetch.bytes=[NUMBER OF RECORDS * RECORD SIZE IN BYTES]</span></code></pre></div>\n<p>Different Kafka Connect hosts are going to have different ways to handle adjusting - see <a target=\"_blank\" href=\"https://docs.confluent.io/cloud/current/connectors/bring-your-connector/custom-connector-manage.html#override-configuration-properties\">Confluent’s documentation</a> for their preferred method, for example.</p>\n<h4 id=\"number-of-partitions\"></h4>\n<p>The number of topic partitions can affect the volume of inserts and batch sizes (which can increase network chattiness, as you might imagine). One hundred messages spread out across one hundred partitions is going to have more of an impact than a single partition, especially based on the numbers of tasks/workers running. Since the above poll and fetch process is performed per task (see below), more partitions may increase the time to fill a batch (if following recommendations below of one task per partition) - potentially increasing latency. We generally thus recommend leaning towards fewer partitions (within reason) rather than more, but there’s not a set rule for sizing this.</p>\n<p>We generally recommend inserting data in fairly large batches of at least 1,000 rows at a time, and ideally between 10,000 to 100,000 rows (See our <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/bestpractices/bulk-inserts\">best practices</a> for more information).</p>\n<h4 id=\"number-of-tasks\"></h4>\n<p>In Kafka Connect, tasks are the workers that actually copy the data - we’ve seen recommendations that you have at least as many tasks as partitions, to ensure each “channel” flows properly.</p>\n<p>If you’d like to dig deeper into Tasks, check out the <a target=\"_blank\" href=\"https://docs.confluent.io/platform/current/connect/index.html#tasks\">Confluent doc on the topic</a>.</p>\n<h4 id=\"too-many-parts\"></h4>\n<p>Something that we’ve run into are “Too Many Parts” errors - ClickHouse is optimized for large volumes of data (properly batched) rather than frequent smaller inserts (the classic “chatty” vs “batchy” network debate). Inserts are handled on a per task basis - each task is responsible for inserting that task’s data into ClickHouse - so more partitions/tasks isn’t always better.</p>\n<h3 id=\"latency-between-kafka-connect-and-clickhouse-cloud\"></h3>\n<h4 id=\"instance-sleeping\"></h4>\n<p>ClickHouse Cloud will put instances to sleep (to save you credits) when the service is not subject to queries. This means that when there are gaps in insert and query activity, the instance may be paused. If there is, in turn, an influx of new data, it will likely create a delay as the instance is spun back up.</p>\n<p>If this latency is unacceptable, users can <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/manage/scaling\">tune the idling timeout</a> for a service to the workload - increasing it so that shorter periods of inactivity do not result in idling.</p>\n<h4 id=\"instance-sizing\"></h4>\n<p>More data is going to require more capacity - though ClickHouse is very efficient, this general adage still applies. ClickHouse Cloud will generally handle scaling for you - see <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/about-us/cloud#clickhouse-cloud-benefits\">our documentation</a> for more details.</p>\n<h4 id=\"asynchronous-vs-synchronous-inserts\"></h4>\n<p>By default, our connector sends data through synchronous inserts - waiting for a confirmation before continuing. This is generally safer from a data-loss perspective, but it does introduce some level of latency as each insert requires confirmation of success.</p>\n<p>Asynchronous inserts, on the other hand, can be configured to just submit data and move on without waiting - <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#fire-and-forget-return-behavior\">potentially improving throughput</a>. If potential lost messages aren't a concern (for instance, you’re doing consumer analytics and need a more general amount of data rather than specific entries) this may be a faster method. Note that this method means <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#default-return-behavior\">lower durability guarantees</a>, delivering at best at least once semantics.</p>\n<p>See our <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/asynchronous-inserts\">documentation</a> for more details on configuring this.</p>\n<h2 id=\"conclusion\"></h2>\n<p>In this post, we have described latency, which can be an issue in Kafka and ClickHouse architectures.  As well as identifying causes of latency and approaches to minimize it, we have first suggested a simple means to measure and visualize it.</p>\n<p>We hope this helps you on your ClickHouse journey - more to come!</p></div><p><a target=\"_blank\" href=\"https://clickhouse.cloud/signUp?loc=blog-cta-footer&utm_source=clickhouse&utm_medium=web&utm_campaign=blog\">Get started</a> with ClickHouse Cloud today and receive $300 in credits.
