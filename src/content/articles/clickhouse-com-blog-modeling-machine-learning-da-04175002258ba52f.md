contentHtml: "<div><p>In this article, we explore the world of MLOps and how data in OLAP databases can be modeled and transformed to allow it to act as an efficient feature store for training ML models. While the lessons shared are applicable to a range of OLAP systems, we will use ClickHouse as an example to demonstrate these techniques - for no reason other than we know it well!</p>\n<p>The approaches discussed in this blog are used by <a target=\"_blank\" href=\"https://clickhouse.com/blog/transforming-ad-tech-how-cognitiv-uses-clickhouse-to-build-better-machine-learning-models\">existing ClickHouse users</a>, who we thank for sharing their techniques, as well as out of the box feature stores.</p>\n<p>We focus on using an ClickHouse as a data source, offline store, and transformation engine. These components of a feature store are fundamental to delivering data efficiently and correctly to model training. While most out-of-the-box feature stores provide abstractions, we peel back the layers and describe how data can be modeled efficiently to build and serve features. For users looking to build their own feature store, or just curious as to the techniques existing stores use, read on.</p>\n<h2 id=\"why-clickhouse\"></h2>\n<p>We have explored what a feature store is <a target=\"_blank\" href=\"https://clickhouse.com/blog/powering-featurestores-with-clickhouse\">in previous blog posts</a> and recommend users are familiar with the concept before diving into this one. In its simplest form, a feature store is a centralized repository for storing and managing data that will be used to train ML models, aiming to improve collaboration and reusability and reduce model iteration time.</p>\n<p>As a real-time data warehouse, ClickHouse can fulfill two primary components of a feature store beyond simply providing a datasource.</p>\n<p><span><img alt=\"feature_store_clickhouse.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Ffeature_store_clickhouse_baabeb2e00.png&w=2048&q=75\"></span></p>\n<ol>\n<li><strong>Transformation Engine</strong>: ClickHouse utilizes SQL for declaring data transformations, optimized by its analytical and statistical functions. It supports querying data from various sources, such as Parquet, Postgres, and MySQL, and performs aggregations over petabytes of data. Materialized views allow data transformations at insert time. Additionally, ClickHouse can be used in Python via chDB for transforming large data frames.</li>\n<li><strong>Offline Store</strong>: ClickHouse can persist query results through <code>INSERT INTO SELECT</code> statements, automatically generating table schemas. It supports efficient data iteration and scaling, with features often represented in tables with timestamps for point-in-time queries. ClickHouse’s sparse indices and <code>ASOF LEFT JOIN</code> clause facilitate fast filtering and feature selection, optimizing data preparation for training pipelines. This work is parallelized and executed across a cluster, enabling the offline store to scale to petabytes while keeping the feature store lightweight.</li>\n</ol>\n<p>In this post, we show how data can be modeled and managed in ClickHouse to perform these roles.</p>\n<h2 id=\"high-level-steps\"></h2>\n<p>When using ClickHouse as the basis for your offline feature store, we think of the steps to train a model as consisting of the following:</p>\n<ol>\n<li>\n<p><strong>Exploration</strong> - Familiarize yourself with source data in ClickHouse with SQL queries.</p>\n</li>\n<li>\n<p><strong>Identify the data subset and features</strong> - Identify the possible features, their respective entities, and the subset of data needed to produce them. We refer to the subset from this step as the \"feature subset.\"</p>\n</li>\n<li>\n<p><strong>Creating Features</strong> - Create the SQL queries required to generate the features.</p>\n</li>\n<li>\n<p><strong>Generating model data</strong> - Combine the features appropriately to produce a set of feature vectors, usually achieved using an ASOF JOIN on a common key and timestamp proximity.</p>\n</li>\n<li>\n<p><strong>Generating test and training sets</strong> - Split the \"feature subset\" into a test and training set (and possibly validation).</p>\n</li>\n<li>\n<p><strong>Train model</strong> - Train model(s) using the training data, possibly with different algorithms.</p>\n</li>\n<li>\n<p><strong>Model selection &amp; tuning</strong> - Evaluate models against the validation set, choose the best model, and fine-tune hyperparameters.</p>\n</li>\n<li>\n<p><strong>Model evaluation</strong> - Evaluate the final model against the test set. If performance is sufficient, stop; otherwise, return to 2.</p>\n</li>\n</ol>\n<p>We concern ourselves with steps (1) to (5) as these are ClickHouse-specific. One of the key properties of the above process is that it is highly iterative. Steps (3) and (4) could be loosely referred to as \"Feature engineering\" and something that typically consumes more time than choosing the model and refining the hyperparameters. Optimizing this process and ensuring ClickHouse is used as efficiently as possible can, therefore, deliver significant time and cost savings.</p>\n<p>We explore each of these steps below and propose a flexible approach that optimally leverages ClickHouse features, allowing users to iterate efficiently.</p>\n<h2 id=\"dataset-and-example\"></h2>\n<p>For our example, we use the following web analytics dataset, described <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/metrica\">here</a>. If we consider the above source data, this is denoted by the column <code>IsNotBounce.</code> This represents our target class or label.</p>\n<blockquote>\n<p>We aren't going to actually build this model and provide the Python code, rather focusing on the data modeling process. For this reason, our choice of features is illustrative only.</p>\n</blockquote>\n<h2 id=\"step-1---exploration\"></h2>\n<p>Exploring and understanding the source data requires users to become familiar with ClickHouse SQL. We recommend users familiarize themselves with ClickHouse's wide range of <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions\">analytical functions</a> during this step. Once familiar with the data, we can begin identifying the features for our model and the subset of the data required to produce them.</p>\n<h2 id=\"step-2---features-and-subsets\"></h2>\n<p>To predict whether a visit will bounce, our model will require a training set where each data point contains appropriate features assembled into a feature vector. Typically, these features will be based on a subset of the data.</p>\n<p>We've explored the concept of features and feature vectors in other blogs and how they loosely correlate to a column and row of a <strong>result set</strong>, respectively. Importantly, they need to be available at training and request time.</p>\n<p><span><img alt=\"features.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Ffeatures_7d40dbf1cd.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p>Note we emphasized \"result set\" above. A feature vector is rarely just a row from a table with the features of a subset of the columns. Often, a complex query must be issued to compute the feature from an aggregation or transformation.</p>\n</blockquote>\n<h3 id=\"identifying-features\"></h3>\n<p>Before identifying features, we should be aware of two of the key properties that will influence our modeling process:</p>\n<ul>\n<li>\n<p><strong>Association with entities</strong> - Features are typically associated with an <code>entity</code> with which they are associated or \"keyed\". For our problem, the features we think might be useful in making a prediction might be a mixture of user or domain-based. A user-based feature would be request-specific, e.g., the user's age, client IP, or user agent. A domain feature would be associated with the page visited e.g. <code>number of visits per year</code>.</p>\n<p>Associating features with an instance of an entity requires the entity to have a key or identifier. In our case we need an identifier for the user and a domain value. These are available from the <code>UserID</code> and <code>URL</code> columns, respectively. The domain can be extracted from the URL using the domain function in ClickHouse, i.e., <code>domain(URL)</code>.</p>\n</li>\n<li>\n<p><strong>Dynamic &amp; complex</strong> - While certain features remain relatively static, e.g., the user's age, others, such as the client IP, will exhibit changes over time. In such cases, we need to access the feature’s value as it existed at a specific timestamp. This is key for creating point-in-time correct training sets.</p>\n<p>While some features will likely be simple, e.g., whether the device is mobile or the client IP, other more complicated features require aggregate statistics, which change over time - and this is where ClickHouse excels!</p>\n</li>\n</ul>\n<h3 id=\"example-features\"></h3>\n<p>For example, suppose we consider the following features to be useful in predicting whether a website visit will bounce. All of our features are associated with a timestamp as they are dynamic and change over time.</p>\n<ul>\n<li><strong>User-agent of the visit</strong> -  Associated with the user entity and available in the column <code>UserAgent</code>.</li>\n<li><strong>Category of the referrer</strong> - (e.g., search engine, social media, direct). A user feature available through the column <code>RefererCategoryID</code>.</li>\n<li><strong>Number of domains visited per hour</strong> - at the time the user made the request. Requires a <code>GROUP BY</code> to compute this user feature.</li>\n<li><strong>Number of unique IPs visiting the domain per hour</strong> - Domain feature requiring a <code>GROUP BY</code>.</li>\n<li><strong>Category of the page</strong> - User feature available through the column <code>URLCategoryID</code>.</li>\n<li><strong>Average request time for the domain per hour</strong> - Requires a <code>GROUP BY</code> to compute this from the <code>FetchTiming</code> column.</li>\n</ul>\n<blockquote>\n<p>These features might not be ideal and illustrative only. Linking many of these features to the user entity is somewhat simplistic. For instance, some features would be more accurately associated with the request or session entity.</p>\n</blockquote>\n<h3 id=\"feature-subsets\"></h3>\n<p>Once we have an idea of the features we will use, we can identify the required subset of the data needed to build them. This step is optional as sometimes users wish to use the whole data, or the data isn't large and complex enough to warrant this step.</p>\n<p>When applied, we often see users creating tables for their model data - we refer to these as the \"feature subset\". These consist of:</p>\n<ul>\n<li>The entity values for each feature vector.</li>\n<li>A timestamp of the event if it exists.</li>\n<li>Class label.</li>\n<li>The columns needed to produce the planned features. Users may wish to add other columns that they consider useful in future iterations.</li>\n</ul>\n<p>This approach provides several advantages:</p>\n<ul>\n<li>\n<p>Allows the data to be ordered and optimized for future accesses. Typically, the model data will be read and filtered differently than the source data. These tables can also generate features faster than the source data when producing a final training set.</p>\n</li>\n<li>\n<p>A subset or transformed set of data may be required for the model. Identifying, filtering, and transforming this subset may be an expensive query. By inserting the data into an intermediate model table, this query only has to be executed once. Subsequent feature generation and model training runs can thus obtain the data efficiently from this table.</p>\n<p>We can use this step to de-duplicate any data. While the raw data might not contain duplicates, the resulting subset may if we extract a subset of the columns for features.</p>\n</li>\n</ul>\n<p>Suppose for our model we create an intermediate table <code>predict_bounce_subset</code>. This table needs the <code>EventTime</code>, the label <code>IsNotBounce</code>, and the entity keys <code>Domain</code> and <code>UserID</code>. Additionally, we include the simple feature columns <code>UserAgent</code>, <code>RefererCategoryID</code> , and <code>URLCategoryID</code>, as well as those needed to produce our aggregate features - <code>FetchTiming</code> and <code>ClientIP</code>.</p>\n<div><pre><code><span><span>CREATE TABLE</span> predict_bounce_subset</span>\n<span>(</span>\n<span>  EventTime DateTime64,</span>\n<span>  UserID UInt64,</span>\n<span>  Domain String,</span>\n<span>  UserAgent UInt8,</span>\n<span>  RefererCategoryID UInt16,</span>\n<span>  URLCategoryID UInt16,</span>\n<span>  FetchTiming UInt32,</span>\n<span>  ClientIP UInt32,</span>\n<span>  IsNotBounce UInt8</span>\n<span>)</span>\n<span>ENGINE <span>=</span> ReplacingMergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (EventTime, Domain, UserID, UserAgent, RefererCategoryID, URLCategoryID, FetchTiming, ClientIP, IsNotBounce)</span>\n<span><span>PRIMARY KEY</span> (EventTime, Domain, UserID)</span></code></pre></div>\n<p>We use a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/replacingmergetree\">ReplacingMergeTree</a> as our table engine. This engine de-duplicates rows that have the same values in the ordering key columns. This is performed <a href=\"\">asynchronously in the background at merge tree</a>, although we can ensure we don't receive duplicates at query time using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/from#final-modifier\"><code>FINAL</code> modifier</a>. This approach to deduplication tends to be more resource efficient than the alternative in this scenario - using a <code>GROUP BY</code> of the columns we wish to de-duplicate data by at insert time below. Above, we assume all columns should be used to identify unique rows. It is possible to have events with the same <code>EventTime</code>, <code>UserID</code>, <code>Domain</code>, e.g. multiple requests made when visiting a domain with different <code>FetchTiming</code> values.</p>\n<p>Further details on the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/replacingmergetree\">ReplacingMergeTree</a> can be found here.</p>\n<blockquote>\n<p>As an optimization, we only load a subset of the ordering keys into the primary key (held in memory) via the <code>PRIMARY KEY</code> clause. By default, all columns in the <code>ORDER BY</code> are loaded. In this case, we will likely only want to query by the <code>EventTime</code>, <code>Domain</code>, and <code>UserID</code>.</p>\n</blockquote>\n<p>Suppose we wish to only train our bounce prediction model on events not associated with bots - identified by <code>Robotness=0</code>. We also will require a <code>Domain</code> and <code>UserID</code> value.</p>\n<p>We can populate our <code>predict_bounce_subset</code> table using an <code>INSERT INTO SELECT</code>, reading the rows from <code>web_events</code> and applying filters that reduce our data size to 42m rows.</p>\n<div><pre><code><span><span>INSERT INTO</span> predict_bounce_subset <span>SELECT</span></span>\n<span>\tEventTime,</span>\n<span>\tUserID,</span>\n<span>\tdomain(URL) <span>AS</span> Domain,</span>\n<span>\tUserAgent,</span>\n<span>\tRefererCategoryID,</span>\n<span>\tURLCategoryID,</span>\n<span>\tFetchTiming,</span>\n<span>\tClientIP,</span>\n<span>\tIsNotBounce</span>\n<span><span>FROM</span> web_events</span>\n<span><span>WHERE</span> Robotness <span>=</span> <span>0</span> <span>AND</span> Domain <span>!=</span> <span>''</span> <span>AND</span> UserID <span>!=</span> <span>0</span></span>\n<span></span>\n<span><span>0</span> <span>rows</span> <span>in</span> set. Elapsed: <span>7.886</span> sec. Processed <span>99.98</span> million <span>rows</span>, <span>12.62</span> GB (<span>12.68</span> million <span>rows</span><span>/</span>s., <span>1.60</span> GB<span>/</span>s.)</span>\n<span></span>\n<span><span>SELECT</span> formatReadableQuantity(<span>count</span>()) <span>AS</span> count</span>\n<span><span>FROM</span> predict_bounce_subset <span>FINAL</span></span>\n<span></span>\n<span>┌─count─────────┐</span>\n<span>│ <span>42.89</span> million │</span>\n<span>└───────────────┘</span>\n<span></span>\n<span><span>1</span> <span>row</span> <span>in</span> set. Elapsed: <span>0.003</span> sec.</span></code></pre></div>\n<blockquote>\n<p>Note the use of the <code>FINAL</code> clause above to ensure we only count unique rows.</p>\n</blockquote>\n<h3 id=\"updating-feature-subsets\"></h3>\n<p>While some subsets of data are static, others will be subject to change as new events arrive in the source table. Often, users, therefore, need to keep subsets up-to-date. While this can be achieved with scheduled queries that rebuild the tables (e.g., using dbt), ClickHouse (incremental) Materialized views can be used to maintain these.</p>\n<p>Materialized views allow users to shift the cost of computation from query time to insert time. A ClickHouse materialized view is just a trigger that runs a query on blocks of data as they are inserted into a table e.g., the <code>web_events</code> table. The results of this query are then inserted into a second \"target\" table - the subset table in our case. Should more rows be inserted, results will again be sent to the target table. This merged result is the equivalent of running the query over all of the original data.</p>\n<p><span><img alt=\"feature_store_mv.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Ffeature_store_mv_7b51b97cf9.png&w=2048&q=75\"></span></p>\n<p>A materialized which maintains our <code>predict_bounce_subset</code> is shown below:</p>\n<div><pre><code><span><span>CREATE</span> MATERIALIZED <span>VIEW</span> predict_bounce_subset_mv <span>TO</span> predict_bounce_subset <span>AS</span></span>\n<span><span>SELECT</span></span>\n<span>   EventTime,</span>\n<span>   UserID,</span>\n<span>   domain(URL) <span>AS</span> Domain,</span>\n<span>   UserAgent,</span>\n<span>   RefererCategoryID,</span>\n<span>   URLCategoryID,</span>\n<span>   FetchTiming,</span>\n<span>   ClientIP,</span>\n<span>   IsNotBounce</span>\n<span><span>FROM</span> web_events</span>\n<span><span>WHERE</span> Robotness <span>=</span> <span>0</span> <span>AND</span> Domain <span>!=</span> <span>''</span> <span>AND</span> UserID <span>!=</span> <span>0</span></span></code></pre></div>\n<p>This is a simple example, and we recommend that users learn more about the power of materialized views <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/materialized-view\">here</a>. For the subsequent steps, we assume we will use the model table <code>predict_bounce_subset</code>.</p>\n<h2 id=\"step-3---creating-features\"></h2>\n<p>For model training, we'll need to assemble our planned features into a set of feature vectors with the label <code>IsNotBounce</code> i.e.</p>\n<p><span><img alt=\"feature.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Ffeature_9c3c5fe592.png&w=2048&q=75\"></span></p>\n<p>Note how we assemble our feature vector from features from multiple entities. In many cases we are looking for the feature value at the closest point in time from another entity.</p>\n<p>An experienced SQL developer familiar with ClickHouse could probably formulate a query that produced the above feature vector. While possible, this will invariably not only be a complex and computationally expensive query - especially over larger datasets of billions of rows.</p>\n<p>Furthermore as noted, our feature vectors are dynamic and potentially consist of any number of combinations of different features during different training iterations. Additionally, ideally different engineers and data scientists would be using the same definition of a feature as well as writing the queries as optimally as possible.</p>\n<p>Given the above demands, it makes sense to materialize our features into tables writing the results of the query into a table using <code>INSERT INTO SELECT</code>. This effectively means we perform the feature generation once, writing the results to a table from which they can be efficiently read and reused when iterating. This also allows us to declare the feature query once, optimally, and share the results with other engineers and scientists.</p>\n<blockquote>\n<p>For now, we omit how users might wish to declare, version control, and share their feature definitions. SQL is, after all, code. There are several solutions to this problem, some of which solve different challenges - see \"Build or Adopt\".</p>\n</blockquote>\n<h3 id=\"feature-tables\"></h3>\n<p>A feature table contains instances of a feature associated with an entity and, optionally, a timestamp. We have seen our users employ two table models for features - either creating a table <strong>per feature</strong> or <strong>per entity</strong>. Each approach has its respective pros and cons we explore below. Both of these allow re-usability of the features though, with the advantage they ensure the data is compressed well.</p>\n<blockquote>\n<p>You don't need to create a feature table for every feature. Some can be consumed from the model table as-is, in cases where they are represented by a column value.</p>\n</blockquote>\n<h3 id=\"feature-tables-per-feature\"></h3>\n<p>With a table per feature, the table name denotes the feature itself. The primary advantage of this approach is it potentially simplifies later joins. Additionally, it means users can use materialized views to maintain these tables as the source data changes - see \"Updating\".</p>\n<p>The disadvantage of this approach is it doesn't scale as well as the \"per event\". Users with thousands of features will have thousands of tables. While possibly manageable, creating materialized views to maintain each of these is not viable.</p>\n<p>As an example, consider the table responsible for storing the domain feature \"number of unique IPs for each domain\".</p>\n<div><pre><code><span><span>CREATE TABLE</span> number_unique_ips_per_hour</span>\n<span>(</span>\n<span>  Domain String,</span>\n<span>  EventTime DateTime64,</span>\n<span>  <span>Value</span> Int64</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (Domain, EventTime)</span></code></pre></div>\n<p>We have chosen the <code>ORDER BY</code> key to optimize both <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/data-modeling/schema-design#choosing-an-ordering-key\">compression and future reads</a>. We can populate our feature table using a simple <code>INSERT INTO SELECT</code> with an aggregation to compute our feature.</p>\n<div><pre><code><span><span>INSERT INTO</span> number_unique_ips_per_hour <span>SELECT</span></span>\n<span>   Domain,</span>\n<span>   toStartOfHour(EventTime) <span>AS</span> EventTime,</span>\n<span>   uniqExact(ClientIP) <span>AS</span> <span>Value</span></span>\n<span><span>FROM</span> predict_bounce_subset <span>FINAL</span></span>\n<span><span>GROUP</span> <span>BY</span></span>\n<span>   Domain,</span>\n<span>   EventTime</span>\n<span></span>\n<span><span>0</span> <span>rows</span> <span>in</span> set. Elapsed: <span>0.777</span> sec. Processed <span>43.80</span> million <span>rows</span>, <span>1.49</span> GB (<span>56.39</span> million <span>rows</span><span>/</span>s., <span>1.92</span> GB<span>/</span>s.)</span>\n<span></span>\n<span><span>SELECT</span> <span>count</span>()</span>\n<span><span>FROM</span> number_unique_ips_per_hour</span>\n<span></span>\n<span>┌─<span>count</span>()─┐</span>\n<span>│  <span>613382</span> │</span>\n<span>└─────────┘</span></code></pre></div>\n<p>We choose to use <code>Domain</code> and <code>Value</code> as the column name for entity and feature value. This makes our future queries a little simpler. Users may wish to use a generic table structure for all features, with an <code>Entity</code> and <code>Value</code> column.</p>\n<div><pre><code><span><span>CREATE TABLE</span> <span>&lt;</span>feature_name<span>&gt;</span></span>\n<span>(</span>\n<span>  Entity Variant(UInt64, Int64, String),</span>\n<span>  EventTime DateTime64,</span>\n<span>  <span>Value</span> Variant(UInt64, Int64, Float64)</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (Entity, EventTime)</span></code></pre></div>\n<p>This requires the use of the <code>Variant</code> type. This type allows a column to support a union of other data types e.g. <code>Variant(String, Float64, Int64)</code> means that each row of this type has a value of either type <code>String</code>, <code>Float64</code> <code>Int64</code> or none of them (NULL value).</p>\n<p>This feature is currently experimental and optional for the above approach but required for the \"Per entity\" approach described below.</p>\n<h3 id=\"feature-tables-per-entity\"></h3>\n<p>In a per entity approach we use the same table for all features which are associated with the same entity.
