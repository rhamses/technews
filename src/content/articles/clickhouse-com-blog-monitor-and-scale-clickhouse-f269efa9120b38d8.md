contentHtml: "<article><div><p>ClickHouse Cloud makes it trivial to automatically scale your infrastructure up and down, horizontally or vertically, in response to resource pressure. But sometimes you want to go further and monitor SLAs on specific queries. Perhaps they're the queries fired off by your frontend app, and it degrades your user-experience when latency exceeds &gt;200ms.</p>\n<p>This guide shows you how to tag queries so you can calculate SLAs, then use <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhousectl\"><code>clickhousectl</code></a> to query and scale ClickHouse Cloud to investigate and fix breaches. You'll also see how you can pass this workflow off to an agent to investigate and remediate for you.</p>\n<p>Try out the <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/ai/clickhousectl/agentic-sla-scaling\">runnable example</a>.</p>\n<h2 id=\"setup\"></h2>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/interfaces/cli\">Install <code>clickhousectl</code></a> and use an API key to auth:</p>\n<div><pre><code><span>curl https://clickhouse.com/cli | sh</span>\n<span></span>\n<span>clickhousectl cloud auth login --api-key <span>\"<span>$CLICKHOUSE_CLOUD_API_KEY</span>\"</span> --api-secret <span>\"<span>$CLICKHOUSE_CLOUD_API_SECRET</span>\"</span></span></code></pre></div>\n<p>Confirm you can see your services. The first column is the service ID you'll use everywhere else:</p>\n<div><pre><code><span>clickhousectl cloud service list</span></code></pre></div>\n<h2 id=\"defining-and-measuring-your-sla\"></h2>\n<p>First, you need to define your SLA and know how to measure it. An SLA is only useful if it's specific: a percentile, a latency target, and the queries it applies to. For a frontend dashboard, that might be <em>\"p99 under 200 ms for the queries behind the main view\"</em>. That's what we'll use for the example here.</p>\n<p>The <code>system.query_log</code> records every query a ClickHouse service runs. The trick is to tag your queries so you can easily filter to them. Set <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#log_comment\"><code>log_comment</code></a> on the queries you want to track, and they become trivial to isolate later:</p>\n<div><pre><code><span><span>SELECT</span> event_type, <span>count</span>(), <span>avg</span>(<span>value</span>), quantile(<span>0.9</span>)(<span>value</span>)</span>\n<span><span>FROM</span> events</span>\n<span><span>WHERE</span> event_type <span>=</span> <span>'purchase'</span></span>\n<span>  <span>AND</span> event_time <span>&gt;</span> now() <span>-</span> <span>INTERVAL</span> <span>1</span> <span>DAY</span></span>\n<span><span>GROUP</span> <span>BY</span> event_type</span>\n<span>SETTINGS log_comment <span>=</span> <span>'frontend-dashboard'</span>;</span></code></pre></div>\n<p>With the queries tagged, you can read them back from the log:</p>\n<div><pre><code><span>clickhousectl cloud service query --<span>id</span> <span>\"<span>$SERVICE_ID</span>\"</span> --query <span>\"</span></span>\n<span><span>  SELECT event_time, query_duration_ms</span></span>\n<span><span>  FROM clusterAllReplicas(default, system.query_log)</span></span>\n<span><span>  WHERE type = 'QueryFinish'</span></span>\n<span><span>    AND log_comment = 'frontend-dashboard'</span></span>\n<span><span>  ORDER BY event_time DESC</span></span>\n<span><span>  LIMIT 10\"</span></span></code></pre></div>\n<p>Once you can see them, measuring the SLA is just an aggregation. Compute the p99 latency for exactly that workload over the last five minutes:</p>\n<div><pre><code><span>clickhousectl cloud service query --<span>id</span> <span>\"<span>$SERVICE_ID</span>\"</span> --query <span>\"</span></span>\n<span><span>  SELECT</span></span>\n<span><span>      toUInt64(quantile(0.99)(query_duration_ms)) AS p99_ms,</span></span>\n<span><span>      count() AS queries</span></span>\n<span><span>  FROM clusterAllReplicas(default, system.query_log)</span></span>\n<span><span>  WHERE event_time &gt; now() - INTERVAL 5 MINUTE</span></span>\n<span><span>    AND type = 'QueryFinish'</span></span>\n<span><span>    AND log_comment = 'frontend-dashboard'\"</span></span></code></pre></div>\n<h2 id=\"investigating-a-breach\"></h2>\n<p>A breached SLA tells you that latency went up, but not why. There are two places to look, and they answer different questions. Sometimes it's a simple case of CPU/Memory being over-utilised. Other times the hardware stats look fine, and you need to dig a little deeper into whats going on inside the database.</p>\n<h3 id=\"inside-the-database\"></h3>\n<p>The first signal lives in ClickHouse itself. <code>system.query_log</code> doesn't just help you with the SLA query, you can ask questions about everything else that ran alongside it, too. That helps you to understand if something about the workload is changing.</p>\n<p>Bucketing volume and latency by minute is a good place to start:</p>\n<div><pre><code><span>clickhousectl cloud service query --<span>id</span> <span>\"<span>$SERVICE_ID</span>\"</span> --query <span>\"</span></span>\n<span><span>  SELECT</span></span>\n<span><span>      toStartOfMinute(event_time) AS minute,</span></span>\n<span><span>      count() AS queries,</span></span>\n<span><span>      toUInt64(quantile(0.99)(query_duration_ms)) AS p99_ms</span></span>\n<span><span>  FROM clusterAllReplicas(default, system.query_log)</span></span>\n<span><span>  WHERE event_time &gt; now() - INTERVAL 30 MINUTE</span></span>\n<span><span>    AND type = 'QueryFinish'</span></span>\n<span><span>    AND log_comment = 'frontend-dashboard'</span></span>\n<span><span>  GROUP BY minute</span></span>\n<span><span>  ORDER BY minute\"</span></span></code></pre></div>\n<p>A common case can be an increase in query volume/concurrency. As your application grows, more users are actively viewing their dashboard, firing off more queries at the same.</p>\n<p>If query volume climbed in lockstep with p99, you probably have a concurrency problem. If p99 rose while volume stayed flat, something <em>else</em> is competing for resources, and you can widen the same query (drop the <code>log_comment</code> filter, group by <code>log_comment</code> or <code>query_kind</code>) to find the heavy queries, ingestion, or merges crowding out your dashboard.</p>\n<h3 id=\"system-metrics\"></h3>\n<p>The second signal is resource pressure. To see whether the service is actually saturated, look at its metrics. ClickHouse Cloud exposes a <a target=\"_blank\" href=\"https://clickhouse.com/docs/integrations/prometheus\">Prometheus-compatible endpoint</a> per service. <code>clickhousectl</code> can help you take a quick peek:</p>\n<div><pre><code><span>clickhousectl cloud service prometheus <span>\"<span>$SERVICE_ID</span>\"</span> --filtered-metrics <span>true</span></span></code></pre></div>\n<p>The snapshot is enough to get an idea of current state. For trends over time, point a standing Prometheus scraper at the same endpoint.</p>\n<p>Pay particular attention to these metrics:</p>\n<div><table><thead><tr><th>Resource</th><th>Metric(s)</th><th>How to read it</th></tr></thead><tbody><tr><td><strong>CPU</strong></td><td><code>ClickHouseAsyncMetrics_CGroupUserTimeNormalized</code> + <code>ClickHouseAsyncMetrics_CGroupSystemTimeNormalized</code>, vs. <code>ClickHouseAsyncMetrics_CGroupMaxCPU</code></td><td>Sum the two normalized values to get cores in use. ~1.0 = one core saturated; approaching <code>CGroupMaxCPU</code> = CPU maxed out.</td></tr><tr><td><strong>Memory</strong></td><td><code>ClickHouseAsyncMetrics_CGroupMemoryUsed</code> ÷ <code>ClickHouseAsyncMetrics_CGroupMemoryTotal</code></td><td>Fraction of the memory limit in use. Approaching 1.0 = memory pressure.</td></tr><tr><td><strong>Concurrency</strong></td><td><code>ClickHouseMetrics_Query</code></td><td>Queries executing right now, a quick proxy for how busy the service is.</td></tr></tbody></table></div>\n<p>The state of the service helps you determine the right action to take. High concurrency with low memory suggests that you add replicas, we just need more cores to spread query concurrency over. Memory pinned near the limit on every replica suggests you need bigger replicas.</p>\n<h2 id=\"scaling-with-clickhousectl\"></h2>\n<p><code>cloud service scale</code> allows you to scale a ClickHouse Cloud service horizontally and vertically:</p>\n<div><pre><code><span>clickhousectl cloud service scale <span>\"<span>$SERVICE_ID</span>\"</span> \\</span>\n<span>  --min-replica-memory-gb 8 \\</span>\n<span>  --max-replica-memory-gb 16 \\</span>\n<span>  --num-replicas 3</span></code></pre></div>\n<p><code>--num-replicas</code> is the horizontal dimension (how many replicas run in parallel). The <code>--min-replica-memory-gb</code> and <code>--max-replica-memory-gb</code> flags control vertical scaling. ClickHouse Cloud has native auto-scaling that can vertically scale replicas when it sees resource pressure. Set them apart to let Cloud scale replicas up and down automatically; set them equal to fix the replica size. The example above runs 3 replicas, each free to scale between 8 and 16 GB.</p>\n<h2 id=\"a-simple-cron\"></h2>\n<p>You could put this inside a simple cron:</p>\n<div><pre><code><span><span>#!/usr/bin/env bash</span></span>\n<span><span>set</span> -euo pipefail</span>\n<span>SERVICE_ID=<span>\"&lt;your-service-id&gt;\"</span></span>\n<span>SLA_MS=200</span>\n<span></span>\n<span>p99=$(clickhousectl cloud service query --<span>id</span> <span>\"<span>$SERVICE_ID</span>\"</span> --format TSV --query <span>\"</span></span>\n<span><span>  SELECT toUInt64(quantile(0.99)(query_duration_ms))</span></span>\n<span><span>  FROM clusterAllReplicas(default, system.query_log)</span></span>\n<span><span>  WHERE event_time &gt; now() - INTERVAL 1 MINUTE</span></span>\n<span><span>    AND type = 'QueryFinish'</span></span>\n<span><span>    AND log_comment = 'frontend-dashboard'\"</span>)</span>\n<span></span>\n<span><span>if</span> (( p99 &gt; SLA_MS )); <span>then</span></span>\n<span>  <span>echo</span> <span>\"SLA breached: p99=<span>${p99}</span>ms &gt; <span>${SLA_MS}</span>ms. Scaling out\"</span></span>\n<span>  clickhousectl cloud service scale <span>\"<span>$SERVICE_ID</span>\"</span> --num-replicas 4</span>\n<span><span>else</span></span>\n<span>  <span>echo</span> <span>\"OK: p99=<span>${p99}</span>ms\"</span></span>\n<span><span>fi</span></span></code></pre></div>\n<p>Run it once a minute, and it can give you a super simple way to give your application some breathing room. But you'll have to think about the rest of the flow, too. Scaling back down if pressure eases, scaling further when needed, deciding between horizontal or vertical scaling, and so on.</p>\n<p>If you want to go beyond hard-coded heuristics, it's an interesting use case for agents.</p>\n<p>A cron might still be the right way to run the SLA-check every minute. But if the SLA is breached, an agent can help to reason about what action to take.</p>\n<p>The ClickHouse agent skills can help your agent to better use ClickHouse and <code>clickhousectl</code>. You can install them easily using <code>clickhousectl</code> itself:</p>\n<div><pre><code><span>clickhousectl skills --agent claude</span></code></pre></div>\n<p>The check itself can stay a cron, it's cheap and predictable. But instead of a hard-coded <code>scale --num-replicas 4</code>, you can pass the failure to an LLM, giving it context about the failure, how to investigate, and what remediation options it should consider:</p>\n<div><pre><code><span><span>if</span> (( p99 &gt; SLA_MS )); <span>then</span></span>\n<span>  <span>read</span> -r -d <span>''</span> PROMPT &lt;&lt;<span>EOF || true</span></span>\n<span><span>The 'frontend-dashboard' query latency SLA on ClickHouse Cloud service $SERVICE_ID</span></span>\n<span><span>has just breached: p99 over the last minute is ${p99}ms against a ${SLA_MS}ms target.</span></span>\n<span><span></span></span>\n<span><span>You're the on-call agent. Work out WHY the SLA is breaching, then remediate it by</span></span>\n<span><span>applying exactly one scaling action to the service. Let the evidence drive the choice.</span></span>\n<span><span></span></span>\n<span><span>What you have to work with (clickhousectl only):</span></span>\n<span><span>  - SQL against the service's system tables. system.query_log is the richest source:</span></span>\n<span><span>    one row per query, with its timing and memory use, each tagged with the workload</span></span>\n<span><span>    it belongs to in the log_comment column ('frontend-dashboard' is the SLA workload):</span></span>\n<span><span>      clickhousectl cloud service query --id $SERVICE_ID --format TSV --query \"&lt;SQL&gt;\"</span></span>\n<span><span>  - Live resource pressure from Prometheus (CPU, memory, query concurrency, merges):</span></span>\n<span><span>      clickhousectl cloud service prometheus $SERVICE_ID --filtered-metrics true</span></span>\n<span><span></span></span>\n<span><span>Your two scaling levers. Apply only ONE, whichever the root cause calls for:</span></span>\n<span><span>  - Replica count:  clickhousectl cloud service scale $SERVICE_ID --num-replicas N</span></span>\n<span><span>  - Replica size:   clickhousectl cloud service scale $SERVICE_ID --min-replica-memory-gb M --max-replica-memory-gb M</span></span>\n<span><span></span></span>\n<span><span>General advice on which scaling pattern to use:</span></span>\n<span><span>- Prefer scaling vertically if cause is unclear.</span></span>\n<span><span>- Scale vertically if latency is likely caused by resource contention from other queries.</span></span>\n<span><span>- Scale horizontally if latency is caused by an increase in query concurrency or write throughput.</span></span>\n<span><span></span></span>\n<span><span>Apply one action, then explain the evidence you relied on and why that lever fits.</span></span>\n<span><span>EOF</span></span>\n<span></span>\n<span>  <span>printf</span> <span>'%s'</span> <span>\"<span>$PROMPT</span>\"</span> | claude -p --model sonnet --allowedTools <span>\"Bash(clickhousectl:*)\"</span></span>\n<span><span>fi</span></span></code></pre></div>\n<h3 id=\"use-your-own-scaling-policy\"></h3>\n<p>You can take this further with your own rules and guidelines for scaling. Perhaps you want to guide the model not to scale beyond X replicas, or give it additional guidance on exactly what to look for (and how).</p>\n<p>Creating a context file in Markdown, or encoding it inside a custom agent skill, is a great way to guide the agent towards more desirable behaviour.</p>\n<h3 id=\"auditing\"></h3>\n<p>Every action performed via <code>clickhousectl</code> lands in the ClickHouse Cloud activity log, so you get an audit trail for free:</p>\n<div><pre><code><span>clickhousectl cloud activity list</span></code></pre></div>\n<h2 id=\"get-clickhousectl\"></h2>\n<p>Everything in this guide uses <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhousectl\"><code>clickhousectl</code></a>, the ClickHouse CLI for local and cloud. It's the single tool for taking a project from your laptop to production: spinning up ClickHouse locally, building against it, and managing the Cloud service it eventually runs on.</p>\n<p>Install with:\n<code>curl https://clickhouse.com/cli | sh</code></p></div></article>"
