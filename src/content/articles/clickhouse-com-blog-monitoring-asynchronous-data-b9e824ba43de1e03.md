contentHtml: "<div><h2 id=\"introduction\"></h2>\n<p>In this follow-up post about <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse\">asynchronous inserts</a>, we give guidance and queries for monitoring asynchronous inserts. This can be helpful for validating that everything is working correctly according to your settings. And, especially identifying insert errors that <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#insert-errors-can-occur-during-buffer-flush\">occurred</a> during buffer flushes for asynchronous inserts performed in <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#fire-and-forget-return-behavior\">fire and forget mode</a>.</p>\n<h2 id=\"asynchronous-insert-mechanics-primer\"></h2>\n<p>As a reminder, asynchronous inserts keep the frequency of part creations automatically under control by buffering several (potentially small) inserts server side before a new part gets created. The following diagram visualizes this:\n<span><img alt=\"monitoring_async_inserts_02.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmonitoring_async_inserts_02_9956927ad0.png&w=2048&q=75\"></span>\nWhen ClickHouse ① receives an asynchronous insert query, then the query’s data is ② immediately written into an in-memory buffer first. Asynchronously to ①, and only when ③ the next buffer flush takes place, the buffer’s data is <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns\">sorted</a> and written as a part to the database storage. Before the buffer gets flushed, the data of other asynchronous insert queries from the same or other clients can be collected in the buffer. The part created from the buffer flush will, therefore, potentially contain the data from several asynchronous insert queries. Note that there <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#there-can-be-multiple-parts\">can be</a> multiple parts being created from a single buffer flush, and there <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#there-can-be-multiple-buffers\">can be</a> multiple buffers in operation at any time.</p>\n<h2 id=\"relevant-system-tables\"></h2>\n<p>ClickHouse provides <a target=\"_blank\" href=\"https://clickhouse.com/blog/the-state-of-sql-based-observability\">SQL-based observability</a> of itself. Each ClickHouse node is constantly monitoring itself and continuously writing metrics, logs, traces, and other observability data into <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-debugging-issues-with-system-tables\">system tables</a>. This allows us to simply use SQL and ClickHouse itself to look deeply under the hood of ClickHouse data processing mechanisms, like asynchronous inserts. In general, system tables are the number one troubleshooting tool for both our core and support engineers.</p>\n<p>This diagram lists the system tables containing observability data collected when ClickHouse receives and executes asynchronous inserts:\n<span><img alt=\"monitoring_async_inserts_03.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmonitoring_async_inserts_03_53edd98f35.png&w=2048&q=75\"></span>\n① When ClickHouse receives and executes an insert query, then this is <a target=\"_blank\" href=\"https://clickhouse.com/blog/monitoring-troubleshooting-insert-queries-clickhouse\">logged</a> together with execution statistics into the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/query_log\">system.query_log</a> table.</p>\n<p>② In the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/metrics\">system.metrics</a> table, you can check the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/metrics#pendingasyncinsert\">PendingAsyncInsert</a> metric to get the number of asynchronous insert queries whose data is currently buffered and waiting to be flushed.</p>\n<p>③ The <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/asynchronous_insert_log\">system.asynchronous_insert_log</a> table logs all buffer flush events.</p>\n<p>④ Whenever a table part is created, then this event is logged in the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/part_log\">system.part_log</a> table.</p>\n<p>⑤ The <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/parts\">system.parts</a> table contains meta information about all currently existing table parts.</p>\n<p>In the following sections, we present and describe a few handy queries over these aforementioned system tables for introspecting the execution stages of asynchronous inserts.</p>\n<p>Note that these queries are assumed to be executed on a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/distributed#distributed-clusters\">cluster with a specific name</a> by utilizing the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/table-functions/cluster\">clusterAllReplicas</a> table function. If you are not using a clustered version of ClickHouse, you can query the tables directly from your single node.</p>\n<h2 id=\"queries-for-introspecting-async-inserts\"></h2>\n<p>To help with debugging, we provide a simple <a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/2363ddd25ee96700ebcd66dcca8a8ba9\">script</a> that creates all of the following queries as handy <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/view#parameterized-view\">parameterized views</a>.</p>\n<h3 id=\"part-creations\"></h3>\n<p>Remember that the main purpose of asynchronous inserts is to keep the frequency of part creations under control by buffering several (potentially small) inserts ClickHouse-server side, before a new part gets created.</p>\n<p><a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/7596e3586b545506851635694ba4ad06\">Here</a> is a query over the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/part_log\">system.part_log</a> table (joined with <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/parts\">system.parts</a> for additional info) that you can use for double-checking the frequency of part creations. <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#there-can-be-multiple-parts\">Remember</a> that the table rows buffered in the asynchronous insert buffer can potentially contain several different <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/custom-partitioning-key\">partitioning key</a> values, and therefore, during buffer flush, ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse#poorly-chosen-partitioning-key\">will</a> create (at <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#settings-max_insert_block_size\">least</a>) one new part per table partition.</p>\n<p>The query is configured with 4 CTE identifiers (<code>db_name</code>, <code>table_name</code>, <code>last_x_minutes</code>, and <code>last_m_parts_per_node_per_partition</code>). The parameterized view <code>monitor_parts</code> has the same identifiers as parameters.</p>\n<p>The query lists, for a specific database and table, the latest m newly created parts during the last x minutes per cluster node (<code>n</code>) and per table partition (<code>ptn</code>)  the creation times (<code>write</code>), contained <code>rows</code> and compressed size <code>on disk</code>.</p>\n<p>For convenience, we also show (<code>prev</code>) for each part how much time has passed since a previous part was created on the same cluster node for the same table partition.</p>\n<p>This is an example result for a <code>SELECT * FROM monitor_parts(db_name='default', table_name='upclick_metrics’, last_x_minutes=10, last_m_parts_per_node_per_partition=4)</code> view query:\n<span><img alt=\"monitoring_async_inserts_04.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmonitoring_async_inserts_04_b3c16c0fc3.png&w=2048&q=75\"></span>\nThe result shows the latest 4 created parts per cluster node (on a three-node ClickHouse Cloud service) and per table partition within the last 10 minutes. As our <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/main/blog-examples/async_inserts/upclick-gcp/commands/CREATE_TABLE.sql\">example target table</a> doesn’t use a partitioning key, the <code>ptn</code> column is empty. We can see that on each of the three cluster nodes, a new part was created every 30 seconds. That was exactly how we configured asynchronous inserts in one of our benchmark <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#benchmark-1\">runs</a> with a 30 seconds buffer flush time. Remember that the buffer exists <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#there-can-be-multiple-buffers\">per</a> node.</p>\n<h3 id=\"buffer-flushes\"></h3>\n<p>In case the result of the previous query doesn’t show the expected part creation frequency for asynchronous inserts, a first debugging step would be to check the frequency of buffer flushes.</p>\n<p>A query can be found <a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/0135b7f125c96bb42a798105653fc8aa\">here</a>, which joins the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/asynchronous_insert_log\">system.asynchronous_insert_log</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/query_log\">system.query_log</a> tables. <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#there-can-be-multiple-buffers\">Remember</a> that there is one separate buffer per cluster node and per insert query shape (the syntax of the insert query excluding the values clause / the data) and per <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/query-level\">settings</a>.</p>\n<p>The query is configured with 4 CTE identifiers (<code>db_name</code>, <code>table_name</code>, <code>last_x_minutes</code>, and <code>last_m_flushes_per_node_per_shape_per_settings</code>). The parameterized view <code>monitor_flushes</code> has the same identifiers as parameters.</p>\n<p>The query lists, for a specific  database and table, information about the latest <code>m</code> buffer flushes during the last <code>x</code> minutes per cluster node (<code>n</code>) per query shape (<code>q</code>) id per query settings (<code>s</code>) id. For each buffer flush, we list the <code>flush</code> time, the number of <code>rows</code>, and the amount of uncompressed <code>data</code> flushed to disk. For convenience, we also show (<code>prev</code>) for each buffer flush how much time has passed since a previous flush took place on the same node for the same query shape and settings. Plus, we show one concrete <code>sample_query</code> per insert query shape id and the <code>sample_settings</code> corresponding to a settings id.</p>\n<p>This is an example result for a <code>SELECT * FROM monitor_flushes(db_name='default', table_name='upclick_metrics’, last_x_minutes=10, last_m_flushes_per_node_per_shape_per_settings=4)</code> view query:\n<span><img alt=\"monitoring_async_inserts_05.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmonitoring_async_inserts_05_2c1063e0dd.png&w=2048&q=75\"></span>\nThe result shows the latest 4 buffer flushes per cluster node (on a three-node ClickHouse Cloud service) and per query shape and settings within the last 10 minutes. We can see that on each of the three cluster nodes, a buffer flush took place every 30 seconds. That matches one of our benchmark <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#benchmark-1\">runs</a> with a 30-second buffer flush <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#async-insert-busy-timeout-ms\">timeout</a>. The flush times correlate with the part creation times returned from the <a target=\"_blank\" href=\"https://clickhouse.com/blog/blog/monitoring-asynchronous-data-inserts-in-clickhouse#part-creations\">previous</a> query. Note that all insert queries have the same shape and settings as indicated in the example result above.</p>\n<h3 id=\"insert-errors-during-buffer-flushes\"></h3>\n<p>Insert errors can <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#insert-errors-can-occur-during-buffer-flush\">occur</a> during buffer flushes. With the <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#default-return-behavior\">default</a> asynchronous insert return behavior, the sender of the query gets a detailed error message returned instead of an acknowledgment. With the <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#fire-and-forget-return-behavior\">fire and forget mode</a>, however, the original insert into the buffer for that query gets successfully acknowledged to the sender, regardless of whether the insert into the target table during a later buffer flush actually succeeds or not.</p>\n<p><a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/9fa07e8a54acde9dfaa0a296f001ab93\">Here</a> is a query for finding out about insert errors during buffer flushes in hindsight. The query runs over the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/asynchronous_insert_log\">system.asynchronous_insert_log</a> table and is configured with 3 CTE identifiers (<code>db_name</code>, <code>table_name</code>, and <code>last_x_minutes</code>). The parameterized view <code>monitor_flush_errors</code> has the same identifiers as parameters.</p>\n<p>The query lists per cluster node (<code>n</code>) and error <code>status</code> and <code>exception</code> message the latest buffer <code>flush</code> times within the last x minutes during which the exception took place. Together with the <code>query_id</code> of one of the queries whose buffered data caused the insert error during the buffer flush. You can use this id for querying (or joining) the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/query_log\">system.query_log</a> table for getting more information about the specific query.</p>\n<p>This is an example result for a <code>SELECT * FROM monitor_flush_errors(db_name='default', table_name='upclick_metrics’, last_x_minutes=10)</code> view query:\n<span><img alt=\"monitoring_async_inserts_06.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmonitoring_async_inserts_06_7e1fc33d80.png&w=2048&q=75\"></span>\nThe result shows that some parsing errors happened during two buffer flushes per cluster node (on a three-node ClickHouse Cloud service) within the last 10 minutes.</p>\n<h3 id=\"pending-flushes\"></h3>\n<p>Lastly, <a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/65e2fb5510c6b3f63221c79ba5f0d045\">here</a> is a query that checks the current value of the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/metrics#pendingasyncinsert\">PendingAsyncInsert</a> metric in the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/metrics\">system.metrics</a> table for getting the number of asynchronous insert queries whose data is currently buffered and waiting to be flushed per cluster node.</p>\n<p>This is an example query result:\n<span><img alt=\"monitoring_async_inserts_07.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmonitoring_async_inserts_07_d8a874e7ae.png&w=2048&q=75\"></span></p>\n<h2 id=\"scenarios\"></h2>\n<p>In this section, we are going to use some of the queries from the previous section to identify the root cause of buffer flush and part write frequencies.</p>\n<h3 id=\"simple-and-straightforward\"></h3>\n<p>When no partitioning key is used in the target table, and each insert query has the same shape and settings, we will see that the buffer gets flushed according to the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#asynchronous-insert-settings\">configured</a> flush threshold settings, and there is a 1:1 relationship between buffer flushes and parts written to disk. This occurs <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#there-can-be-multiple-buffers\">per</a> node. The following two example query results for the <a target=\"_blank\" href=\"https://clickhouse.com/blog/monitoring-asynchronous-data-inserts-in-clickhouse#buffer-flushes\">buffer flushes</a> and <a target=\"_blank\" href=\"https://clickhouse.com/blog/blog/monitoring-asynchronous-data-inserts-in-clickhouse#part-creations\">part creations</a> queries demonstrate this:\n<span><img alt=\"monitoring_async_inserts_08.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmonitoring_async_inserts_08_330f3facff.png&w=2048&q=75\"></span>\nOn a three-node ClickHouse Cloud service, we configured asynchronous inserts in one of our benchmark <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#benchmark-1\">runs</a> with a 30-second buffer flush time. We see that there is a buffer flush every 30 seconds on each node, resulting in a part being written to disk every 30 seconds per node. See the highlighted rows in the two query results above, where the same color is used for corresponding buffer flushes and part creations.</p>\n<h3 id=\"multiple-partitioning-keys\"></h3>\n<p>When a partitioning key is <a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/2362a0279f2159cc162e0105bc745952\">used</a> in the target table, then there is generally no longer a (per node) 1:1 relationship between buffer flushes and parts written to disk. Instead, more than one part can be created per buffer flush. The next two example query results show this:\n<span><img alt=\"monitoring_async_inserts_09.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmonitoring_async_inserts_09_de264230e3.png&w=2048&q=75\"></span>\nThe highlighted rows in the two query results above indicate that a single buffer flush on one node resulted in three parts being written to disk on the same node at the same time. Because the rows in the buffer contained three different partitioning key values when the buffer was flushed.</p>\n<h3 id=\"multiple-query-shapes\"></h3>\n<p>Because there <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#there-can-be-multiple-buffers\">is</a> one separate buffer per insert query shape (and per node), more than one buffer flush can potentially occur per <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#asynchronous-insert-settings\">configured</a> buffer flush threshold on a single node. These two example query results sketch this:\n<span><img alt=\"monitoring_async_inserts_10.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmonitoring_async_inserts_10_3171ae2deb.png&w=2048&q=75\"></span>\nWe configured asynchronous inserts with a 30-second buffer flush time. As indicated by the two highlighted rows in the <code>Buffer flushes</code> query result above, two buffer flushes took place on the same node on the next buffer flush timeout. Because the node received insert queries for the same target table but with two different syntactic shapes, there are two separate buffers on the node. As indicated by the two highlighted rows in the <code>Parts written do disk</code> query result, there is still a 1:1 relationship between buffer flushes and parts written to disk as there is no partitioning key is used in the target table.</p>\n<h3 id=\"multiple-settings\"></h3>\n<p>Similarly to different query shapes, there <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#there-can-be-multiple-buffers\">is</a> a separate buffer per set of unique insert query <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/query-level\">settings</a>. This can be useful for enabling different flush thresholds for data for the same table,  and to control resource usage of specific data. We can observe these mixed buffer flush cycles below:\n<span><img alt=\"monitoring_async_inserts_11.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmonitoring_async_inserts_11_84c65f38ec.png&w=2048&q=75\"></span>\nThe two highlighted rows in the <code>Buffer flushes</code> query result above show that there are two separate and different flush cycles on the same node for the same target table. Because the node received insert queries for the same target table but with two different settings, specifically buffer flush <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#asynchronous-insert-settings\">threshold settings</a>, there are two buffers with separate flush cycles on the node. The two highlighted rows in the <code>Parts written do disk</code> query result show that there is still a 1:1 relationship between buffer flushes and parts written to disk, as there is no partitioning key is used in the target table.</p>\n<h3 id=\"combinations\"></h3>\n<p>There can be scenarios with a combination of a partitioned target table and async inserts for this table with different query shapes and settings. This results in each cluster node operating a buffer per different query shape per setting set. This creates (<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings#max_insert_block_size\">at least</a>) one part per different partitioning key value stored in the rows contained in the buffer when one of these buffers gets flushed. Our provided <code>Buffer flushes</code> and <code>Parts written do disk</code> introspection queries will indicate this properly.</p>\n<h2 id=\"summary\"></h2>\n<p>In this blog post, we provided guidance and queries for introspecting asynchronous inserts.
