In our first post, we focus on monitoring data concerning INSERT statements to address early misconfiguration or misuse. In a later post, we’ll look at monitoring SELECT queries and how we can detect problems your users are experiencing early, allowing you to deliver a better ClickHouse experience.</p>\n<p>All of the examples in this post were created in ClickHouse Cloud where you can <a target=\"_blank\" href=\"https://clickhouse.cloud/signUp\">spin up a cluster on a free trial in minutes</a>, let us deal with the infrastructure, and get querying! This includes access to SQL Console, which we have used here for visualizing the results of queries.</p>\n<h2 id=\"monitoring-insert-queries\"></h2>\n<p>In this blog post, you will find a list of useful SQL queries for monitoring the results of INSERT statements. These queries fall into two main categories:</p>\n<ol>\n<li><strong>Monitoring</strong> - Used for understanding the clickhouse cluster setup and usage</li>\n<li><strong>Troubleshooting</strong> - Required when identifying the root cause of an issue</li>\n</ol>\n<p>Let's run through a quick overview of the queries you will see on this blog post.</p>\n<div><table><tbody><tr><th>Topic</th><th>Summary</th></tr><tr><td>Monitoring Insert Metrics</td><td><strong>Monitoring</strong>. And how many times?</td></tr></tbody></table></div>\n<h3 id=\"monitoring-asynchronous-inserts\"></h3>\n<p>Asynchronous inserts are the recommended way to insert data into ClickHouse Cloud via the <code>async_insert</code> setting. For further details on how they work and the accompanying best practices, see <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/asynchronous-inserts/\">here</a>.</p>\n<p>When using <code>async_insert</code>, new parts are not created after each INSERT SQL query, but when either the setting <code>async_insert_busy_timeout_ms</code> or <code>async_insert_max_data_size</code> is exceeded - these settings control the flushing of a buffer.</p>\n<p>This process writes to a number of useful log tables with the system database. The insert process is visualized below, with an indication of the relevant log file at each stage.</p>\n<p><span><img alt=\"insert_logs.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Finsert_logs_c3f274c6c6.png&w=2048&q=75\"></span></p>\n<p>We can use the query below to review how many (and how often) new parts are created during the last two hours.</p>\n<pre><p>\nSELECT\n    count() AS new_parts,\n    toStartOfMinute(event_time) AS modification_time_m,\n    table,\n    sum(rows) AS total_written_rows,\n    formatReadableSize(sum(size_in_bytes)) AS total_bytes_on_disk\nFROM clusterAllReplicas(default, system.part_log)\nWHERE (event_type = 'NewPart') AND (event_time &gt; (now() - toIntervalHour(2)))\nGROUP BY\n    modification_time_m,\n    table\nORDER BY\n    modification_time_m ASC,\n    table DESC\n</p>\n</pre>\n<p><span><img alt=\"part_log.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpart_log_3121218d57.png&w=2048&q=75\"></span></p>\n<p><strong>This first query also applies to synchronous inserts.</strong></p>\n<p>We can also use the <code>system.asynchronous_insert_log</code> table to review each async insert's status. The result of the following query is ordered by <code>flush_time</code> with the results allowing us to determine when the data was inserted (multiple lines can belong to the same flush, you can group by flush_query_id in order to have one line per flush).</p>\n<pre><p>\nSELECT\n    event_time,\n    query,\n    database,\n    table,\n    bytes,\n    status,\n    flush_time\nFROM clusterAllReplicas(default, system.asynchronous_insert_log)\nORDER BY flush_time DESC\n</p>\n</pre>\n<p><span><img alt=\"async_query_log.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fasync_query_log_f39c1dc4eb.png&w=2048&q=75\"></span></p>\n<h3 id=\"monitoring-synchronous-inserts\"></h3>\n<p>While in most cases, asynchronous inserts are the most practical means of inserting data, users may not be using this approach if they can batch their insert requests client-side or are performing a bulk load.</p>\n<p>For synchronous inserts, in addition to watching the number of new parts created, users should monitor the <strong>number of insert <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/bestpractices/bulk-inserts/\">bulk requests</a></strong> that have been processed and the <strong>total written rows</strong>. There should be a big difference between these metrics. If not, this means you are inserting a small number of rows on each INSERT SQL request which can produce errors such as <a target=\"_blank\" href=\"https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse\"><code>DB::Exception: Too many parts</code></a>.</p>\n<p>We will use two different system tables to collect these two metrics.</p>\n<ol>\n<li>The table <code>system.query_logs</code> will provide us with the metric about how many Insert <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/bestpractices/bulk-inserts/\">bulk requests</a> have been processed by the ClickHouse service - specifically, for the query below, see the value of <code>nb_bulk_inserts</code>.</li>\n</ol>\n<pre><p>\nSELECT\n    toStartOfMinute(event_time) AS event_time_m,\n    count(*) AS nb_bulk_inserts\nFROM clusterAllReplicas(default, system.query_log)\nWHERE (query ILIKE '%insert%') AND (query_kind = 'Insert') AND (type = 'QueryFinish') AND (NOT (Settings['async_insert']) = '1') AND (event_time &gt; (now() - toIntervalDay(3)))\nGROUP BY event_time_m\nORDER BY event_time_m ASC\n</p>\n</pre>\n<p><span><img alt=\"bulk_inserts.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fbulk_inserts_a5f675e69a.png&w=2048&q=75\"></span></p>\n<ol>\n<li>The <code>system.part_log</code> table provides the important statistic regarding the amount of data written. With this query we will be able to calculate the <code>total_written_rows</code>, and <code>total_bytes_on_disk</code>. This query will be mainly used for troubleshooting or tuning ingestion strategies.</li>\n</ol>\n<pre><p>\nSELECT\n    toStartOfMinute(event_time) AS modification_time_m,\n    table,\n    sum(rows) AS total_written_rows,\n    formatReadableSize(sum(size_in_bytes)) AS total_bytes_on_disk\nFROM clusterAllReplicas(default, system.part_log)\nWHERE (event_type = 'NewPart') AND (event_time &gt; (now() - toIntervalDay(3)))\nGROUP BY\n    modification_time_m,\n    table\nORDER BY\n    modification_time_m ASC,\n    table DESC\n</p>\n</pre>\n<p><span><img alt=\"number_parts.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fnumber_parts_b7f73008be.png&w=2048&q=75\"></span></p>\n<p>The previous queries will show you data for the last 3 days.  Modify this to suit your ingestion rate e.g. a few hours from now (<code>event_time &gt; now() - toIntervalHour(2)</code>).</p>\n<h4 id=\"average-insert-query-duration-over-time\"></h4>\n<p>With this query, we aim to measure the performance of insert operations using the number of insert batches and the average duration that it took to complete them. By plotting this data, we can see how a ClickHouse service is performing for these operations. The relation between these two lines allows you to see bottlenecks in your system during periods of heavy load. These will be easier to correlate if all your batches have a consistent size.</p>\n<p>This is again only applicable to synchronous inserts since the timing doesn’t capture the entire event for an asynchronous operation - rather just the buffering stage.</p>\n<pre><p>\nSELECT\n    toStartOfMinute(event_time) AS event_time_m,\n    count() AS count_batches,\n    avg(query_duration_ms) AS avg_duration\nFROM clusterAllReplicas(default, system.query_log)\nWHERE (query_kind = 'Insert') AND (type != 'QueryStart') AND (event_time &gt; (now() - toIntervalDay(2)))\nGROUP BY event_time_m\nORDER BY event_time_m ASC\n</p>\n</pre>\n<p><span><img alt=\"insert_query_duration.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Finsert_query_duration_151d34aa62.png&w=2048&q=75\"></span></p>\n<p>As an alternative to computing the mean, ClickHouse offers the ability to calculate medians via the function <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/reference/quantile/\">quantiles</a>. The new query thus becomes:</p>\n<pre><p>\nSELECT\n    toStartOfHour(event_time) AS event_time_h,\n    count() AS count_batches,\n    quantile(0.25)(query_duration_ms),\n    quantile(0.5)(query_duration_ms),\n    quantile(0.75)(query_duration_ms),\n    quantile(0.95)(query_duration_ms),\n    quantile(0.99)(query_duration_ms)\nFROM clusterAllReplicas(default, system.query_log)\nWHERE (query_kind = 'Insert') AND (type != 'QueryStart') AND (event_time &gt; (now() - toIntervalDay(2)))\nGROUP BY event_time_h\nORDER BY event_time_h ASC\n</p>\n</pre>\n<p><strong>Limitation:</strong> This information does not reflect the accurate data for <code>async_insert</code> or the Buffer engine.</p>\n<h4 id=\"memory-and-cpu-usage-for-inserts\"></h4>\n<p>To understand the resource consumption of our inserts, we need to go a little deeper. The following query returns the memory and CPU usage for each insert operation. These results allow you to see, for each batch, the amount of resources needed. This can be used to adjust either your service size or throughput.</p>\n<p>Again note that this only applies to synchronous inserts.</p>\n<pre><p>\nSELECT\n    event_time,\n    formatReadableSize(memory_usage) AS memory,\n    ProfileEvents['UserTimeMicroseconds'] AS userCPU,\n    ProfileEvents['SystemTimeMicroseconds'] AS systemCPU,\n    replaceRegexpAll(query, CHAR(10), ''),\n    initial_query_id\nFROM clusterAllReplicas(default, system.query_log)\nWHERE (query_kind = 'Insert') AND (type = 'QueryFinish')\nORDER BY memory_usage DESC\nLIMIT 10\n</p>\n</pre>\n<p><span><img alt=\"insert_memory_usage.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Finsert_memory_usage_e4875e69c6.png&w=2048&q=75\"></span></p>\n<p><strong>Limitation:</strong> This information does not reflect the accurate data for async_insert or the Buffer engine.</p>\n<h3 id=\"parts-and-partitions\"></h3>\n<p>Now that we have a high-level idea about how much data we are ingesting, we can go behind the scenes and learn more about partitions and parts to understand the behavior of our insert operations more deeply.</p>\n<p>Let’s start with a definition for both of these terms:</p>\n<p>A <strong>partition</strong> in ClickHouse is an internal split of your data by a field value. Each partition is stored separately to simplify the manipulations of this data. A great example of this is partitioning by month. This will cause the data for each month to be stored in the same partition. This partition information will be captured in the folder name, allowing parts associated with a partition to be identified quickly on disk. This simplifies implementing TTL rules and accelerates SELECT queries when reading a specific month (note it can also slow queries down if querying multiple months).</p>\n<p>Here we will extract the month for the <strong>VisitDate</strong> column and partition our table by the resulting values.</p>\n<pre><p>\nCREATE TABLE visits\n(\n   VisitDate Date,\n   Hour UInt8,\n   ClientID UUID\n)\nENGINE = MergeTree()\nPARTITION BY toYYYYMM(VisitDate)\nORDER BY Hour;\n</p>\n</pre>\n<p>You can read more about Partitions <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/custom-partitioning-key/\">here</a>.</p>\n<p><strong>Parts</strong> are the chunks associated with each partition. When data is inserted into a table, separate data parts are created, and each of them is lexicographically sorted by the primary key. The primary key allows the part to be efficiently scanned. However, if you have too many parts, then SELECT queries will be slow due to the need to evaluate more indices and read more files.</p>\n<p>The common <code>Too many parts</code> issue can be the result of several causes, including:</p>\n<ul>\n<li>Partition key with excessive cardinality,</li>\n<li>Many small inserts,</li>\n<li>Excessive materialized views.</li>\n</ul>\n<p>If you are interested to know more about this issue, please review the blog post <a target=\"_blank\" href=\"https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse\">Getting started with ClickHouse? Here are 13 Deadly Sins and how to avoid them</a>.</p>\n<p>Now let’s imagine you are a DevOps engineer. You want to first have a global perspective before digging into specific databases or tables. In this case, you need one query to tell you if you have any hot spots in your partitions and parts.</p>\n<p>The following query produces a  <code>MaxPartCountForPartition</code> value showing your current highest number of parts per partition. If this key metric begins to exceed your normal trend line, you will need to identify the responsible table to reduce its number of parts.</p>\n<pre><p>\nSELECT\n    toStartOfMinute(event_time) AS event_time_m,\n    avg(value) AS avg_MaxPartCountForPartition\nFROM clusterAllReplicas(default, system.asynchronous_metric_log)\nWHERE (event_time &gt; (now() - toIntervalDay(1))) AND (metric = 'MaxPartCountForPartition')\nGROUP BY event_time_m\nORDER BY event_time_m ASC\n</p>\n</pre>\n<p><span><img alt=\"max_part_count_per_partition.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmax_part_count_per_partition_5d07533759.png&w=2048&q=75\"></span></p>\n<h3 id=\"parts-per-partition\"></h3>\n<p>Suppose the previous query has identified a potential issue. In that case, the following allows you to dig deeper and determine the number of partitions per database table and the number of parts in each partition. Remember that while Clickhouse internally merges parts, too many parts will result in more merge pressure in an attempt to keep the number of parts low. This consumes resources and potentially results in the error highlighted above.</p>\n<pre><p>\nSELECT\n    concat(database, '.', table) AS table,\n    count() AS parts_per_partition,\n    partition_id\nFROM clusterAllReplicas(default, system.parts)\nWHERE active AND (database != 'system')\nGROUP BY\n    database,\n    table,\n    partition_id\nHAVING parts_per_partition &gt; 1\nORDER BY parts_per_partition DESC\n</p>\n</pre>\n<p><span><img alt=\"parts_per_partition.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fparts_per_partition_25638e4e8a.png&w=2048&q=75\"></span></p>\n<p>Now that we know which parts and partitions have issues, it is useful to review the peak usage of memory this part has consumed.</p>\n<pre><p>\nSELECT\n   event_date,\n   argMax(table, peak_memory_usage) AS table,\n   argMax(event_time, peak_memory_usage) AS event_time,\n   formatReadableSize(MAX(peak_memory_usage)) AS max_peak_memory_usage\nFROM \n   clusterAllReplicas(default, system.part_log)\nWHERE\n   peak_memory_usage &gt; 0\nGROUP BY\n   event_date\nORDER BY\n   event_date DESC\n</p>\n</pre>\n<p><span><img alt=\"memory_per_part.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmemory_per_part_6999e55be1.png&w=2048&q=75\"></span></p>\n<h3 id=\"errors-in-data-parts\"></h3>\n<p>The <code>system.part_log</code> table contains all information on the life of a part as a series of events. The <code>event_type</code> column can categorize these events:</p>\n<ul>\n<li><code>NEW_PART</code> - Inserting of a new data part.</li>\n<li><code>MERGE_PARTS</code> - Merging of data parts.</li>\n<li><code>DOWNLOAD_PART</code> - Downloading a data part.</li>\n<li><code>REMOVE_PART</code> - Removing or detaching a data part using DETACH PARTITION.</li>\n<li><code>MUTATE_PART</code> - Mutating of a data part.</li>\n<li><code>MOVE_PART</code> - Moving the data part from one disk to another one.</li>\n</ul>\n<p>The <code>error</code> column captures the success of the execution of each event. The query below will filter and collect only the part events with errors. Using the response, we can see the attempted action, the table's name, and the error's cause.</p>\n<pre><p>\nSELECT\n    event_date,\n    event_type,\n    table,\n    error,\n    errorCodeToName(error) AS error_code,\n    COUNT()\nFROM clusterAllReplicas(default, system.part_log)\nWHERE (database = 'default') AND (error &gt; 0)\nGROUP BY\n    event_date,\n    event_type,\n    error,\n    error_code,\n    table\n</p>\n</pre>\n<p>In the specific example below, we can see that when a <code>NewPart</code> was created on the tables <code>visits</code> and <code>visits_o</code>, we had deduplicated inserts, prompting us to review our ingest code for why are we sending the same data multiple times.</p>\n<p>You could have different errors and different <code>event_types</code>. Feel free to create a case in the ClickHouse Cloud portal if you have any questions about these errors.</p>\n<p><span><img alt=\"insert_errors.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Finsert_errors_38419fbb15.png&w=2048&q=75\"></span></p>\n<h2 id=\"conclusion\"></h2>\n<p>In this blog post we have shown some of the most important queries for monitoring your INSERT operations. We recommend proactively monitoring the results of these queries and alerting if the behavior is usual, potentially using tools such as <a target=\"_blank\" href=\"https://grafana.com/grafana/plugins/grafana-clickhouse-datasource/\">Grafana which has a mature ClickHouse integration</a> and supports alerting. In next post in this series, we will examine how to monitor your SELECT queries and identify issues early before they are escalated by your users.</p></div></article>"
