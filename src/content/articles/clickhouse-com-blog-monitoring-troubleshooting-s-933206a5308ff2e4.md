Specifically, what are the biggest tables in terms of rows, data and primary key size. We can also see when each table was last modified:</p>\n<pre><p>\nSELECT\n    table,\n    sum(rows) AS rows,\n    max(modification_time) AS latest_modification,\n    formatReadableSize(sum(bytes)) AS data_size,\n    formatReadableSize(sum(primary_key_bytes_in_memory)) AS primary_keys_size,\n    any(engine) AS engine,\n    sum(bytes) AS bytes_size\nFROM clusterAllReplicas(default, system.parts)\nWHERE active\nGROUP BY\n    database,\n    table\nORDER BY bytes_size DESC\n</p>\n</pre>\n<p><span><img alt=\"cluster-overview.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fcluster_overview_c04845cf4a.png&w=2048&q=75\"></span></p>\n<h2 id=\"most-expensive-select-queries\"></h2>\n<p>We next want to identify the most expensive queries in our ClickHouse service. The query below returns historical queries ordered by their duration, allowing us to see which ones need our attention.</p>\n<p>We have a large number of columns that will allow us to better understand the reasons why each query was slow. This includes:</p>\n<ol>\n<li>Columns allowing us to understand the query type and its timing.</li>\n<li>The size and the amount of rows that have been read by the service to provide the result.</li>\n<li>The number of rows returned in the result.</li>\n<li>Any exceptions which have occurred including the stack trace.</li>\n<li>The requesting user.</li>\n<li>The format, functions, dictionaries and settings used.</li>\n</ol>\n<pre><p>\nSELECT\n    type,\n    query_start_time,\n    formatReadableTimeDelta(query_duration_ms) AS query_duration,\n    query_id,\n    query_kind,\n    is_initial_query,\n    query,\n    concat(toString(read_rows), ' rows / ', formatReadableSize(read_bytes)) AS read,\n    concat(toString(result_rows), ' rows / ', formatReadableSize(result_bytes)) AS result,\n    formatReadableSize(memory_usage) AS `memory usage`,\n    exception,\n    concat('\\n', stack_trace) AS stack_trace,\n    user,\n    initial_user,\n    multiIf(empty(client_name), http_user_agent, concat(client_name, ' ', toString(client_version_major), '.', toString(client_version_minor), '.', toString(client_version_patch))) AS client,\n    client_hostname,\n    databases,\n    tables,\n    columns,\n    used_aggregate_functions,\n    used_dictionaries,\n    used_formats,\n    used_functions,\n    used_table_functions,\n    ProfileEvents.Names,\n    ProfileEvents.Values,\n    Settings.Names,\n    Settings.Values\nFROM system.query_log\nWHERE (type != 'QueryStart') AND (query_kind = 'Select') AND (event_date &gt;= (today() - 1)) AND (event_time &gt;= (now() - toIntervalDay(1)))\nORDER BY query_duration_ms DESC\nLIMIT 10\n</p>\n</pre>\n<p><span><img alt=\"most-expensive-selects.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmost_expensive_selects_f5141df105.png&w=2048&q=75\"></span></p>\n<h2 id=\"compare-metrics-between-two-queries\"></h2>\n<p>Let's imagine that you have identified an expensive SELECT that you wish to improve from the previous query results. For this, you can compare metrics between versions of the query using their respective ids. This information is returned if you are using the <code>clickhouse-client</code>.</p>\n<pre><p>\nclickhouse-client --host play.clickhouse.com --user play --secure\nClickHouse client version 22.13.1.160 (official build).\nConnecting to play.clickhouse.com:9440 as user play.\nConnected to ClickHouse server version 22.13.1 revision 54461.\nplay-eu :) SELECT 1\nSELECT 1\nQuery id: 13f75255-edec-44b2-b63b-affa9d345f0f\n┌─1─┐\n│ 1 │\n└───┘\n1 row in set. Elapsed: 0.002 sec.\n</p>\n</pre>\n<p>However, we appreciate this information might not always be available through other clients or applications. Assuming the response to the earlier section has provided you with your baseline id, execute the next iteration of your query and collect the id with the following:</p>\n<pre><p>\nSELECT\n    query_id,\n    query,\n    formatReadableTimeDelta(query_duration_ms) AS query_duration\nFROM clusterAllReplicas(default, system.query_log)\nWHERE (type != 'QueryStart') AND (query_kind = 'Select') AND (event_time &gt;= (now() - toIntervalHour(1)))\nORDER BY event_time DESC\nLIMIT 10\n</p>\n</pre>\n<p>If you are unable to identify the query e.g. due to high load, add a filter for the table or query  column using the <code>ILIKE</code> function.</p>\n<p>Once you have the two <code>query_id</code> values, you can run the following query to compare both executions.</p>\n<pre><p>\nWITH\n    query_id = '...query_id_old_version...' AS first,\n    query_id = '...query_id_new_version...' AS second\nSELECT\n    PE.Names AS metric,\n    anyIf(PE.Values, first) AS v1,\n    anyIf(PE.Values, second) AS v2\nFROM clusterAllReplicas(default, system.query_log)\nARRAY JOIN ProfileEvents AS PE\nWHERE (first OR second) AND (event_date = today()) AND (type = 2)\nGROUP BY metric\nHAVING v1 != v2\nORDER BY\n    (v2 - v1) / (v1 + v2) ASC,\n    v2 ASC,\n    metric ASC\n</p>\n</pre>\n<p><span><img alt=\"compare-metrics.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fcompare_metrics_e6a45b5f2f.png&w=2048&q=75\"></span></p>\n<p>In general you should be looking for large differences in any metric. id=\"average-query-duration-and-number-of-requests\"></h2>\n<p>It’s important to understand how many concurrent select queries a ClickHouse service is handling and for how long on average these requests are taking to be processed. This data is also great for troubleshooting, as you can see if the number of requests has had a negative impact on the response time. While for our example we count the requests across all databases and tables, this query could easily be modified to filter for one or more specific tables or databases.</p>\n<p>The following query is also great as a time-series visualization in SQL console.</p>\n<pre><p>\nSELECT\n    toStartOfHour(event_time) AS event_time_h,\n    count() AS count_m,\n    avg(query_duration_ms) AS avg_duration\nFROM clusterAllReplicas(default, system.query_log)\nWHERE (query_kind = 'Select') AND (type != 'QueryStart') AND (event_time &gt; (now() - toIntervalDay(3)))\nGROUP BY event_time_h\nORDER BY event_time_h ASC\n</p>\n</pre>\n<p><span><img alt=\"average_select_query_duration.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Faverage_select_query_duration_d67fe5ffae.png&w=2048&q=75\"></span></p>\n<p>Note: <code>avg_duration</code> is in milliseconds</p>\n<h2 id=\"number-of-sql-queries-by-client-or-user\"></h2>\n<p>While we have seen how the total number of queries, and their duration, can be visualized across all clients, you will often need to identify hot spots from a specific user or client. In this case, performing a similar query with grouping by the client name is useful. The query below aggregates the last 10 minutes and groups by <code>client_name</code>. Feel free to adapt it if you need a larger overview of the same data.</p>\n<pre><p>\nSELECT\n    toStartOfMinute(event_time) AS event_time_m,\n    if(empty(client_name), 'unknow_or_http', client_name) AS client_name,\n    count(),\n    query_kind\nFROM clusterAllReplicas(default, system.query_log)\nWHERE (type = 'QueryStart') AND (event_time &gt; (now() - toIntervalMinute(10))) AND (query_kind = 'Select')\nGROUP BY\n    event_time_m,\n    client_name,\n    query_kind\nORDER BY\n    event_time_m DESC,\n    count() ASC\nLIMIT 100\n</p>\n</pre>\n<p><span><img alt=\"queries-by-client.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fqueries_by_client_8b3113d890.png&w=2048&q=75\"></span></p>\n<p>This query can also be adapted to show the top queries by user, by modifying the GROUP BY to use the <code>user</code> column instead of the <code>client_name</code>.</p>\n<h2 id=\"troubleshooting-too-many-simultaneous-queries\"></h2>\n<p>This error can happen when you are handling a very large number of concurrent SELECT queries. The settings <code>max_concurrent_queries</code> and the more specific <code>max_concurrent_select_queries</code> can help you to fine-tune when this error is triggered. If this error does occur, it is important to establish that no queries are “stuck”. The results of the query below show an <code>elapsed</code> column formatted with the <code>formatReadableTimeDelta</code> function, which can be easily used to see if any of the queries are stuck.</p>\n<pre><p>\nSELECT\n    formatReadableTimeDelta(elapsed) AS time_delta,\n    *\nFROM clusterAllReplicas(default, system.processes)\nWHERE query ILIKE 'SELECT%'\nORDER BY time_delta DESC\n</p>\n</pre>\n<p><span><img alt=\"TOO_MANY_SIMULTANEOUS_QUERIES.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FTOO_MANY_SIMULTANEOUS_QUERIES_ea790eddd2.png&w=2048&q=75\"></span></p>\n<p>While all of the queries in my cluster have completed in less than a second, this should be reviewed carefully if your ClickHouse service has a large and heavy number of SELECT queries.</p>\n<p>If you identified queries that are stuck or failed in the previous query, you can review the <code>system.stack_trace</code> table to get more details on the cause with a full stack trace. This information is useful for troubleshooting.</p>\n<pre><p>\nSELECT\n    thread_id,\n    query_id,\n    arrayStringConcat(arrayMap((x, y) -&gt; concat(x, ': ', y), arrayMap(x -&gt; addressToLine(x), trace), arrayMap(x -&gt; demangle(addressToSymbol(x)), trace)), '\\n') AS n_trace\nFROM clusterAllReplicas(default, system.stack_trace)\nWHERE query_id IS NOT NULL\nSETTINGS allow_introspection_functions = 1\n</p>\n</pre>\n<p><span><img alt=\"query_stack_trace.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fquery_stack_trace_d34db7cc9b.png&w=2048&q=75\"></span></p>\n<p>When using the ClickHouse SQL-console, you can double click on each cell to get the full context via an inspector.</p>\n<h2 id=\"conclusion\"></h2>\n<p>In this blog post, we have reviewed different ways to troubleshoot and understand how SELECT queries are behaving in ClickHouse as well as providing the methods to help you to review your improvements and changes.
