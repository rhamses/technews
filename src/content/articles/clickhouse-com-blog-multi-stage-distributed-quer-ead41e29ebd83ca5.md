contentHtml: "<div><blockquote>\n<p><strong>TL;DR</strong><br>Multi-stage distributed execution gives ClickHouse Cloud a new way to scale one query across many nodes. It repartitions intermediate data between stages, removing key bottlenecks in large joins and high-cardinality aggregations.<br><br>Early TPC-H results show up to 3.4× speedups for join-heavy queries while retaining near-linear aggregation scaling: 7.4× faster on 8 nodes than on 1 node.</p>\n</blockquote>\n<br>\n<h2 id=\"scaling-one-query-across-many-nodes\"></h2>\n<p>ClickHouse has always been able to scale a single query across multiple nodes. In shared-nothing deployments, users do this with physical sharding and the <code>Distributed</code> table engine. In ClickHouse Cloud, parallel replicas brought intra-query scaling to shared storage.</p>\n<p>These mechanisms work well for many analytical queries, but they were not the final answer for modern PB-scale workloads. They could fan out work across nodes, but they could not freely repartition intermediate results between execution stages. That limited how far ClickHouse could scale high-cardinality aggregations, and especially large joins.</p>\n<p>Multi-stage distributed query execution is the next step. It gives ClickHouse Cloud a new way to parallelize a single query across the CPU and memory of all available nodes, without the bottlenecks of the previous execution models.</p>\n<p>In this post, we introduce the new extension of ClickHouse’s query execution model and walk through how it works. We use a multi-table join as the running example because joins are among the hardest analytical workloads to scale, but the mechanism is much broader: it is a new foundation for distributed query execution in ClickHouse Cloud.</p>\n<p>Before we look at the new mechanics, let’s review what came before and why those approaches weren’t enough for modern PB-scale workloads.</p>\n<h2 id=\"why-existing-distributed-execution-was-not-enough\"></h2>\n<p>The existing distributed execution was useful but not elastic enough for PB-scale workloads.</p>\n<p>In shared-nothing open source deployments, ClickHouse scales a query by physically <a target=\"_blank\" href=\"https://clickhouse.com/docs/shards\">sharding</a> data across nodes and querying those shards through a <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/special/distributed\">Distributed table</a>. Each node processes its local slice, and the requester merges the results.</p>\n<p><span><img alt=\"Blog-Distributed_JOINS-introduction.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Distributed_JOINS_introduction_001_bf34c79f03.png&w=2048&q=75\"></span></p>\n<p>That works, but capacity is tied to the shard layout.</p>\n<blockquote>\n<p><strong>Bottleneck: capacity is tied to shard layout</strong><br>Adding compute does not automatically make one query faster. Large tables must first be redistributed across more shards.</p>\n</blockquote>\n<p>Large joins across physically sharded tables expose a second limitation. A join only works when matching rows meet on the same machine. With a distributed JOIN, each node keeps its local left side, fetches the missing right-side shards from the other nodes, builds a full right-side hash table, and returns its local join result to the requester.</p>\n<p><span><img alt=\"Blog-Distributed_JOINS-introduction.002.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Distributed_JOINS_introduction_002_68e4f2362c.png&w=2048&q=75\"></span></p>\n<p>GLOBAL JOIN reduces the many-to-many network round-trip by computing the right side once and broadcasting it to every node.</p>\n<p><span><img alt=\"Blog-Distributed_JOINS-introduction.003.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Distributed_JOINS_introduction_003_69a7171fae.png&w=2048&q=75\"></span></p>\n<p>But the core problem remains: large right sides still have to be copied across the cluster.</p>\n<blockquote>\n<p><strong>Bottleneck: large right sides are copied everywhere</strong><br>Distributed JOIN and GLOBAL JOIN handle network traffic in different ways, but both still make every shard join against a full right side.</p>\n</blockquote>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> removed the physical sharding problem by moving to <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates\">shared storage</a>. Any node can access the same table data, and <a target=\"_blank\" href=\"https://clickhouse.com/docs/deployment-guides/parallel-replicas\">parallel replicas</a> allow multiple nodes to participate in a single query. Nodes can be added or removed instantly, with no data copying or reshuffling.</p>\n<p><span><img alt=\"Blog-Distributed_JOINS-introduction.004.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Distributed_JOINS_introduction_004_1af1e0a189.png&w=2048&q=75\"></span></p>\n<p>That made <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-parallel-replicas\">intra-query scaling</a> in ClickHouse Cloud much more elastic. But parallel replicas still had a structural limitation: they could split work across replicas, but they could not freely repartition intermediate data between execution stages.</p>\n<p>This shows up in two places.</p>\n<p>First, joins. On a single node, ClickHouse can <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#parallel-hash-join\">parallelize both sides of its default hash join strategy</a>: it partitions rows by the join key into multiple hash tables, so both build and probe work can run across CPU cores. The same remains true inside each node when parallel replicas are used.</p>\n<p>The limitation is one level higher. Across multiple nodes, dividing the build side itself would require a shuffle stage that repartitions both inputs by join key between nodes. Parallel replicas do not have that mechanism. The next best option is to distribute the left-side read ranges after <a target=\"_blank\" href=\"https://clickhouse.com/docs/primary-indexes\">primary-index pruning</a>. That parallelizes probe-side work across nodes, but those ranges are not partitioned by the join key. A row in one left-side range can match rows anywhere in the right-side table, so each node still needs the full right side to build its local hash table(s) before probing its local slice.</p>\n<p><span><img alt=\"Blog-Distributed_JOINS-introduction.005.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Distributed_JOINS_introduction_005_8a9fda944e.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p><strong>Bottleneck: the build side does not scale out</strong><br>The left-side probe is divided across nodes, but the build side is not. Every node still builds the same hash table from the full right side, so the build step is repeated instead of divided across the cluster.</p>\n</blockquote>\n<p>Second, aggregations. Nodes can scan and aggregate locally in parallel. But without a shuffle by the GROUP BY key, ClickHouse cannot guarantee that all rows for the same GROUP BY key end up on the same node.</p>\n<p><span><img alt=\"Blog-Distributed_JOINS-introduction.006.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Distributed_JOINS_introduction_006_72425a40cd.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p><strong>Bottleneck: final aggregation is still single-node</strong><br>Partial groups must be merged by one coordinator. For high-cardinality GROUP BY, that final merge is bounded by one node’s CPU and memory, not the cluster.</p>\n</blockquote>\n<p>Both problems have the same root cause: there is no general way to repartition intermediate data between execution stages. That is what multi-stage distributed execution adds.</p>\n<h2 id=\"introducing-multi-stage-distributed-execution\"></h2>\n<p>Multi-stage distributed execution adds the missing primitive: it lets ClickHouse Cloud move intermediate data between nodes while a query is running.</p>\n<p>Instead of executing a query as one distributed fan-out plus a final merge, ClickHouse splits the query plan into stages running in parallel across worker nodes. Between stages, exchange operators move the intermediate results into the shape required by the next stage.</p>\n<p><span><img alt=\"Blog-Distributed_JOINS-introduction.007.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Distributed_JOINS_introduction_007_f6cb8aa8b8.png&w=2048&q=75\"></span></p>\n<p>For example, data can be shuffled by a join key so each worker receives the matching slice of both join inputs. It can be shuffled by a GROUP BY key so each worker owns complete groups. Small inputs can be broadcast to all workers. Final results can be gathered by the coordinator.</p>\n<blockquote>\n<p><strong>Prior bottlenecks removed: data can move between stages</strong><br>Large joins no longer need every node to build the full right-side hash table. High-cardinality aggregations no longer need one coordinator to merge all partial groups.</p>\n</blockquote>\n<p>The core abstraction is the exchange operator, a well-known building block in parallel query execution, <a target=\"_blank\" href=\"https://scholar.colorado.edu/concern/reports/sj139272m\">introduced</a> for the Volcano system and used by MPP databases like Teradata and Greenplum, as well as in SQL Server.</p>\n<p>The exchange operator redistributes data between plan stages. Multi-stage distributed execution uses three main exchange types:</p>\n<ol>\n<li>\n<p><strong>GatherExchange</strong> (N-to-1):  sends worker output to the coordinator, usually at the top of the plan to produce the final result.</p>\n</li>\n<li>\n<p><strong>ShuffleExchange</strong> (M-to-N): repartitions rows by a key, such as a join key or GROUP BY key. This is what lets each worker own a complete, disjoint slice of the next operation.</p>\n</li>\n<li>\n<p><strong>BroadcastExchange</strong> (1-to-N):  copies a small input to every worker, useful when one side of a join is small enough to replicate cheaply.</p>\n</li>\n</ol>\n<p>There is also <strong>ScatterExchange</strong>, which spreads rows randomly amongst workers.</p>\n<p>Those are the mechanics in the abstract. The easiest way to see why they matter is to follow one query through the stages.</p>\n<h3 id=\"how-one-analytical-join-query-avoids-the-old-bottlenecks\"></h3>\n<p>Let’s make this concrete with a <a target=\"_blank\" href=\"https://clickhouse.com/docs/getting-started/example-datasets/tpch\">TPC-H</a>-like query that hits both bottlenecks from the previous section: a large join side that should not be copied to every worker node, and an aggregation that should not collapse into a single-node final merge.</p>\n<p>The query computes total shipment revenue per nation: it joins lineitem to supplier, joins the result to the small nation table, groups by n_name, and sorts by revenue.</p>\n<div><pre><code><span><span>SELECT</span> n_name, <span>sum</span>(l_extendedprice) <span>AS</span> No worker needs the full build side, and no additional network exchange is needed for this join.</p>\n<p><span><img alt=\"Blog-Distributed_JOINS-introduction.013.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Distributed_JOINS_introduction_013_65c74d64b3.png&w=2048&q=75\"></span></p>\n<h4 id=\"step-4-shuffle-by-group-by-key-for-final-aggregation\"></h4>\n<p>The join output is still partitioned by supplier key, not by <code>n_name</code>. The GatherExchange (line 3) combines the sorted results from all workers at the coordinator to produce the final output.</p>\n<p><span><img alt=\"Blog-Distributed_JOINS-introduction.015.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_Distributed_JOINS_introduction_015_227587d6be.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p><strong>Prior bottleneck avoided: the coordinator only gathers final rows</strong><br>The coordinator still receives the query result, but the expensive work has already happened across the workers. It gathers sorted, already-aggregated rows; it does not merge large partial groups or build a large join hash table.</p>\n</blockquote>\n<p>The example above shows the logical data movement: shuffle here, broadcast there, gather at the end. Under the hood, ClickHouse Cloud needs a transport layer that can move those intermediate blocks efficiently between workers.</p>\n<h3 id=\"how-does-data-move-between-stages\"></h3>\n<p>Exchanges can move data in two ways.</p>\n<p>The default is <strong>streaming exchange</strong>. Workers send blocks directly to other workers over TCP using a custom binary protocol. Data starts moving as soon as it is produced: a worker reading lineitem can begin sending blocks into a ShuffleExchange immediately, while the receiving workers start consuming them without waiting for the full input. In other words, exchanges are pipelined rather than “write everything, then read everything.”</p>\n<p>The second mode is <strong>persisted exchange</strong>. Instead of sending intermediate blocks directly between workers, ClickHouse writes them to shared object storage. This is useful for future fault recovery and for spilling intermediate results when a query exceeds cluster memory.</p>\n<p>Streaming exchange is optimized for fast interactive queries and is the default. If a worker fails, the query fails and the client retries it. For these workloads, rerunning the query is usually cheaper than checkpointing every exchange.</p>\n<h3 id=\"why-clickhouse-cloud-makes-this-possible\"></h3>\n<p>Multi-stage distributed execution depends on workers being interchangeable. A stage can run on any worker only if that worker can access the data and metadata it needs.</p>\n<h4 id=\"shared-storage-makes-workers-interchangeable\"></h4>\n<p>ClickHouse Cloud already has that foundation. Table data lives in shared object storage, and every node has access to the metadata needed to read it. The coordinator can therefore assign stages dynamically across the cluster: any worker can scan table data, receive shuffled rows, build its share of a hash table, aggregate its assigned groups, or sort its local result.</p>\n<h4 id=\"shuffle-improves-memory-utilization\"></h4>\n<p>This also improves memory utilization. When a ShuffleExchange partitions a large join across 8 workers, each worker receives roughly 1/8 of the rows and builds roughly 1/8 of the hash table. A join that would require 16 GiB of memory on one node can instead use about 2 GiB per worker across 8 nodes.</p>\n<h4 id=\"shared-storage-can-avoid-some-broadcasts\"></h4>\n<p>Shared storage also opens up future optimizations. For small tables, a worker may not need to receive a broadcast over the network at all; it can read the table directly from object storage and keep it in the local SSD cache for future reads. That is useful for dimension tables like nation or supplier, where local cached reads may be cheaper than broadcasting the table through the exchange layer.</p>\n<h4 id=\"toward-stateless-workers\"></h4>\n<p>The longer-term direction is fully stateless workers: nodes that can appear on demand, pick up work for a query, read the data they need from shared storage, and disappear again when the work is done. Without fixed ownership or manual data placement. Multi-stage distributed execution is a step toward that model.</p>\n<h3 id=\"what-about-single-node-queries\"></h3>\n<p>ClickHouse’s single-node execution path is unchanged. Columnar MergeTree storage, vectorized execution, and aggressive pipeline parallelism are still the foundation of query performance.</p>\n<p>Multi-stage distributed execution is an additional, opt-in path for queries that benefit from scaling across multiple nodes. It extends ClickHouse’s execution model and does not replace the single-node engine.</p>\n<h2 id=\"tpc-h-benchmark-results-for-multi-stage-distributed-query-execution\"></h2>\n<p>TPC-H is an industry-standard benchmark for analytical query processing.
