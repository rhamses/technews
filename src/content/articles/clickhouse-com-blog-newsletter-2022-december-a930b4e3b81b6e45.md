Materialized view queries can contain subqueries or dictionary lookups so the destination table will contain data from multiple sources. Like a materialized view, a projection is defined as a query, but the result of this query is saved in the same table (but hidden).</p>\n<p>When ClickHouse receives a query for data in a table with a projection, it will first analyze whether it should use the original data or the projection data to answer the query. Whichever requires less data to be read and processed will be chosen.</p>\n<p>As an example, consider a simple table containing metric names and values:</p>\n<div><pre><code><span>CREATE TABLE metrics</span>\n<span>(</span>\n<span>\ttimestamp DateTime64 CODEC(Delta, Default),</span>\n<span>\tname LowCardinality(String),</span>\n<span>\tvalue Float64</span>\n<span>) ENGINE = MergeTree()</span>\n<span>ORDER BY (name, timestamp)</span></code></pre></div>\n<p>Take a note of two optimizations to the data types:</p>\n<ol>\n<li>Instead of storing the <code>timestamp</code> as is we use delta encoding where only the difference between one value and the next are stored. We expect most values to be quite similar (same year, month, day, hour, etc.) so this will reduce the storage required for this column by a lot.</li>\n<li>Similarly, instead of storing the names of our metrics as they are, we use the <code>LowCardinality</code> dictionary encoding to store a map of names and pointers to where they occur in the data. We only expect a limited number of unique metrics so this will also reduce storage by a lot.</li>\n</ol>\n<p>Notice also how we order the data by metric name first and then by timestamp. This will make queries that look for individual metrics very fast. The following query finds the latest temperature reading:</p>\n<div><pre><code><span><span>SELECT</span> name, argMax(<span>value</span>, <span>timestamp</span>) val_max <span>FROM</span> metrics</span>\n<span><span>WHERE</span> symbol <span>=</span> <span>'TEMP'</span> <span>GROUP</span> <span>BY</span> symbol</span>\n<span> </span>\n<span>┌─name───┬─val_max─┐</span>\n<span>│ TEMP   │     <span>179</span> │</span>\n<span>└────────┴─────────┘</span>\n<span> </span>\n<span><span>1</span> <span>row</span> <span>in</span> set. Elapsed: <span>0.009</span> sec. Processed <span>73.73</span> thousand <span>rows</span>, <span>1.38</span> MB (<span>8.01</span> million <span>rows</span><span>/</span>s., <span>150.32</span> MB<span>/</span>s.)</span></code></pre></div>\n<p>Requesting the latest values for all metrics is 100x slower:</p>\n<div><pre><code><span><span>SELECT</span> name, argMax(<span>value</span>, <span>timestamp</span>) val_max</span>\n<span><span>FROM</span> metrics <span>GROUP</span> <span>BY</span> symbol</span>\n<span><span>255</span> <span>rows</span> <span>in</span> set. Elapsed: <span>0.902</span> sec. Processed <span>220.01</span> million <span>rows</span>, <span>6.08</span> GB (<span>259.38</span> million <span>rows</span><span>/</span>s., <span>6.74</span> GB<span>/</span>s.)</span></code></pre></div>\n<p>To speed up this query we can add a projection that always stores the latest value for a metric</p>\n<div><pre><code><span>ALTER TABLE metrics ADD PROJECTION latest_values</span>\n<span>(SELECT argMax(value, timestamp) GROUP BY name)</span></code></pre></div>\n<p>And to make the data available immediately we can materialize the projection like this:</p>\n<div><pre><code><span>ALTER TABLE metrics MATERIALIZE PROJECTION latest_values</span>\n<span>SETTINGS mutations_sync = 1</span></code></pre></div>\n<p>Now let’s run the same query again:</p>\n<div><pre><code><span><span>SELECT</span> name, argMax(<span>value</span>, <span>timestamp</span>) val_max</span>\n<span><span>FROM</span> metrics <span>GROUP</span> <span>BY</span> symbol</span>\n<span><span>255</span> <span>rows</span> <span>in</span> set. Elapsed: <span>0.007</span> sec. Processed <span>255</span> <span>rows</span>, <span>156.13</span> KB (<span>1.42</span> million <span>rows</span><span>/</span>s., <span>84.33</span> MB<span>/</span>s.)</span></code></pre></div>\n<p>Getting the latest value for all metrics is faster than getting the latest value for a single metric was! All we had to do was add a projection. No need to change our query or our table structure even one bit.</p>\n<p>Give projections a try!
