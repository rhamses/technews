And when you have some, you typically lock them in a secure space - in a vault or in a database. Unfortunately, the best datasets often contain sensitive information about customers, proprietary data, or trade secrets. And so they only ever live in production databases, and even for internal development and testing purposes, other data has to be used, often synthetically generated test data.</p>\n<p>However, synthetic data is often flawed. It usually does not accurately represent what the real data is like. Characteristics like the cardinality of dimensions, the range and distribution of numeric values, and the proportion of empty values will often differ significantly from the actual data. This is a major problem for developing and testing queries that scan a large amount of data to arrive at a result - exactly what ClickHouse is good at.</p>\n<p>For example, for a query that contains <code>GROUP BY dimension</code>, there is a big difference in memory usage and performance between <code>dimension</code> having a cardinality in the hundreds or billions. A <code>GROUP BY</code> will be calculated using a hash map with one key for each distinct value. A few hundred key-value pairs will easily fit into memory, and the query will be lightning fast - whereas for billions of values, the hash map will have to be offloaded to disk resulting in a much slower query, or the query might even fail.</p>\n<p>So how do we develop and test with data that is close to the actual data in characteristics (such as the cardinality of values in columns) - but is not the actual data?</p>\n<p>One answer is obfuscation. And ClickHouse actually ships with a built-in obfuscator, either <code>clickhouse-obfuscator</code> (on Linux) or <code>clickhouse obfuscator</code> (on Mac). Docs are <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/utilities/clickhouse-obfuscator/\">here</a>.</p>\n<p>The ClickHouse Obfuscator will read a dataset as its input and produce as its output a dataset that is very similar in characteristics but won’t contain the same actual values. Let’s look at how it works using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/uk-price-paid/\">UK Property Price Paid</a> dataset.</p>\n<p>First, a look at some high-level characteristics:</p>\n<pre><p>\nSELECT count(), avg(price), max(price) FROM uk_price_paid\n┌──count()─┬──────avg(price)─┬─max(price)─┐\n│ 26763022 │ 208231.24594106 │  932540400 │\n└──────────┴─────────────────┴────────────┘\n</p>\n</pre>\n<p>As we can see, the total number of real estate transactions in the dataset is 26.7 million, with an average price of about £208,000 and a maximum price ever paid of £932 million.\nLet’s obfuscate this:</p>\n<div><pre><code><span>clickhouse obfuscator --structure <span>\"price Int64, date UInt16, postcode1 String, postcode2 String, type String, is_new UInt8, duration String, addr1 String, addr2 String, street String, locality String, town String, district String, county String, category String\"</span> --input-format Parquet --output-format Parquet --seed <span>\"<span>${RANDOM}</span><span>${RANDOM}</span><span>${RANDOM}</span><span>${RANDOM}</span>\"</span> &lt; uk_price_paid.parquet &gt; obfuscated.parquet</span></code></pre></div>\n<p>Notice how we convert one Parquet file into another - the obfuscator works on non-ClickHouse data!\nLet’s check what the same characteristics of the obfuscated dataset look like:</p>\n<pre><p>\nSELECT count(), avg(price), max(price) FROM file('obfuscated.parquet')\n┌──count()─┬─────────avg(price)─┬─max(price)─┐\n│ 26763022 │ 223585.90603467726 │  994963827 │\n└──────────┴────────────────────┴────────────┘\n</p>\n</pre>\n<p>The number of rows is the same - but the average and maximum prices have changed slightly.\nEven the distribution of prices has stayed about the same. For example, the distribution of prices below £1M:</p>\n<pre><p>\nSELECT band, q1.count AS real, q2.count AS obfuscated FROM\n(SELECT floor(price, -5) band, count() count FROM file('uk_price_paid.parquet') GROUP BY band) q1\nLEFT JOIN\n(SELECT floor(price, -5) band, count() count FROM file('obfuscated.parquet') GROUP BY band) q2\nUSING band WHERE band &lt; 1e6 ORDER BY band\n┌───band─┬────real─┬─obfuscated─┐\n│      0 │ 8728237 │    8803178 │\n│ 100000 │ 9277684 │    7936176 │\n│ 200000 │ 4422328 │    5148196 │\n│ 300000 │ 1944389 │    1906225 │\n│ 400000 │  975584 │    1493438 │\n│ 500000 │  465029 │     361164 │\n│ 600000 │  291360 │     221633 │\n│ 700000 │  178879 │     249621 │\n│ 800000 │  117307 │     113644 │\n│ 900000 │   77406 │     166402 │\n└────────┴─────────┴────────────┘\n</p>\n</pre>\n<p>It’s worth noting that the obfuscator does not encrypt or hash the data - so not all information is lost (on purpose, to preserve the characteristics). Therefore it is not automatically safe to share an obfuscated dataset with just anybody. But it should go a long way toward making sharing easier and should be especially useful for internal use, for example, for development and testing of an application.</p>\n<p>Have fun with the ClickHouse Obfuscator - and maybe you can free up a useful dataset or two.</p>\n<h2 id=\"reading-corner\"></h2>\n<p>What we’ve been reading:</p>\n<ol>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/blog/100x-faster-graphql-hive-migration-from-elasticsearch-to-clickhouse\"><strong>100x Faster: GraphQL Hive migration from Elasticsearch to ClickHouse</strong></a> The Guild tested InfluxDB, TimescaleDB and ClickHouse to replace their existing Elasticsearch setup.
