This allows query performance to be scaled as distinct subsets of data can be processed in parallel by multiple ClickHouse hosts.</p>\n<h2 id=\"query-of-the-month---lightweight-deletes\"></h2>\n<p>Lightweight deletes have the potential to impact how users fundamentally approach handling uses in ClickHouse, where the data is not immutable. For this month's query, we explore how Lightweight deletes can be used when incrementally updating materialized tables.</p>\n<p>We regularly see users with complex schemas needing to materialize multiple tables into a new table via a JOIN operation to accelerate subsequent queries. In data warehousing use cases, this table would typically represent a model. This \"de-normalization\" process is typically achieved in ClickHouse by using an <code>INSERT INTO SELECT</code> query <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/insert-into#inserting-the-results-of-select\">link</a>, where the results of the join are inserted into a target table. We visualize this below:</p>\n<p><span><img alt=\"materialized-target.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmaterialized_target_d864e66596.png&w=2048&q=75\"></span></p>\n<p>As well as simplifying subsequent queries, this approach has the potential to improve query performance dramatically. While this solves cases where the data is static, more thought is required if the source tables are subject to changes. In cases where the source tables are append-only, the denormalized table can easily be updated with a simple condition that identifies any changes. For example, this could be a timestamp column on the source tables that identifies new rows. With this condition, we can stream new rows into the target table by re-executing the <code>INSERT INTO SELECT</code>.</p>\n<p><span><img alt=\"Update-materializedsimple.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FUpdate_materializedsimple_125e068d05.png&w=2048&q=75\"></span></p>\n<p>Things get a little more complex if the source tables are subject to updates and duplicates. In this case, users might stream new rows into a temporary table (1). The target table could then be streamed into a new table, with a check to omit results in the temporary table (2) - this assumes the presence of a unique row identifier (<code>id</code> below). Rows from the temporary table are then inserted into the new table (3). This new table could subsequently be exposed as the latest version of the model, e.g., with an <code>EXCHANGE</code> statement <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/exchange#exchange-tables\">link</a>. This rather complex process is shown below:</p>\n<p><span><img alt=\"old-incremental.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fold_incremental_10d5efe4be.png&w=2048&q=75\"></span></p>\n<p>This process requires a complete copy of the data to be made in order to update the target table. This was historically preferred in ClickHouse to <a target=\"_blank\" href=\"https://clickhouse.com/blog/handling-updates-and-deletes-in-clickhouse\">delete Mutations</a>, which incur a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/bestpractices/avoid-mutations\">higher resource cost</a> than simple appends. However, the arrival of lighter-weight deletes opens the potential to simplify this process. Below we show how new rows are still streamed into a temporary table (1). However, this temporary table can now be used to remove rows from the existing target table (using the new DELETE syntax) before inserting the new rows. This avoids copying data and provides a faster means of updating a materialized model.</p>\n<p><span><img alt=\"delete-incremental.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fdelete_incremental_7c3f2d8576.png&w=2048&q=75\"></span></p>\n<p>Note: the temporary table here can potentially just be a subquery. The use of a table ensures the process isn’t memory bound.</p>\n<p>The above logic is still quite complex: surely there is a way to encapsulate this process and make it simpler? Readers of this newsletter, who are also dbt users, will immediately recognize the above use case as \"<a target=\"_blank\" href=\"https://docs.getdbt.com/docs/build/materializations#incremental\">Incremental Materializations</a>\" - a simple model type in dbt. Hence, the <a target=\"_blank\" href=\"https://github.com/ClickHouse/dbt-clickhouse\">dbt-clickhouse plugin</a> utilizes the exact processes above, with the lightweight deletes approach now recommended.</p>\n<p>The use cases for Lightweight deletes go beyond incremental models...support for processing <a target=\"_blank\" href=\"https://medium.com/@damienthomlutz/deleting-records-in-kafka-aka-tombstones-651114655a16\">Kafka tombstone messages</a> anyone?
