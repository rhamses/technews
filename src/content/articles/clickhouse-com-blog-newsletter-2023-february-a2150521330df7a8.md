So what are your options once you’ve overcome the shock of a query response time where you had time to blink!?!?? Well, this is when we turn to the ClickHouse toolbox and pull out <strong>SAMPLE BY</strong>.</p>\n<p>Often we don’t need precise answers, especially if your source data isn’t precise and approximate answers are sufficient. At PB or even TB scale, some businesses can accept some imprecision in exchange for a significant reduction in cost. Alternatively, strict latency requirements may be more important than complete accuracy. This is the spirit of SAMPLE BY.</p>\n<p>Consider the Wikistat dataset. This provides us with a row for every page on Wikipedia per hour, with a count of the number of visits, from May 2015 to April 2022. This is a decent-sized dataset of around 425 billion rows and 15TB uncompressed. For those of you with some spare time, you can download and load it into ClickHouse by following the instructions <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/wikistat\">here</a>.</p>\n<p>Suppose we wanted to compute the average number of page hits per month since 2015. This needs a full table scan to compute the answer. On a 60-core machine with no tuning, ClickHouse runs this query in under 5 minutes (limited by I/O):</p>\n<pre><p>\nSELECT\n\tmonth,\n\tavg(hits)\nFROM wikistat\nGROUP BY toStartOfMonth(time) AS month\nORDER BY month ASC\n┌──────month─┬──────────avg(hits)─┐\n│ 2015-05-01 │  3.617108988953329 │\n│ 2015-06-01 │ 3.4978754072915894 │\n│ 2015-07-01 │ 3.3329051255889595 │\n│ 2015-08-01 │ 3.3877185707856237 │\n│ 2015-09-01 │ 3.4814217901734508 │\n…\n│ 2022-11-01 │ 3.5633514296196567 │\n│ 2022-12-01 │ 3.5317530490738696 │\n│ 2023-01-01 │ 3.5829006605488463 │\n│ 2023-02-01 │ 3.4581641236938476 │\n└────────────┴────────────────────┘\n94 rows in set. Elapsed: 278.166 sec. Processed 425.11 billion rows, 5.10 TB (1.53 billion rows/s., 18.34 GB/s.)\n</p>\n</pre>\n<p>Even if we could speed this up with some tuning, it's unlikely we’d achieve performance gains sufficient to make this a sub-minute query (without a projection e.g. <code>ORDER BY (cityHash64(path), time)</code>). But suppose we were content with an approximation for these values. We could naively try manual sampling by limiting to the first 1m rows.</p>\n<pre><p>\n SELECT\n   month,\n   avg(hits)\n   FROM ( SELECT time, hits FROM wikistat LIMIT 1000000 )\nGROUP BY toStartOfMonth(time) AS month\nORDER BY month ASC\n┌──────month─┬──────────avg(hits)─┐\n│ 2015-05-01 │  2.359986873769416 │\n│ 2015-06-01 │  2.292891439278604 │\n│ 2015-07-01 │ 2.3796534376746785 │\n│ 2015-08-01 │  2.229300091491308 │\n...\n│ 2022-01-01 │  2.395112662646779 │\n│ 2022-02-01 │ 2.5044186449488826 │\n│ 2022-03-01 │  2.168976377952756 │\n│ 2022-04-01 │  2.182795698924731 │\n└────────────┴────────────────────┘\n84 rows in set. Elapsed: 0.290 sec. Processed 4.91 million rows, 58.87 MB (16.91 million rows/s., 202.88 MB/s.)\n</p>\n</pre>\n<p>300s to 0.2s is quite some speedup, but the results are clearly imprecise - it's unlikely your manager would accept this for a degree of inaccuracy no matter the cost and latency saving! This can be attributed to the lack of randomness here, i.e., we simply use the first 1m rows.</p>\n<p>To address this, ClickHouse offers native random sampling. This allows the user to only execute the query on a random fraction of data (a sample). This requires us to define a sampling key at table creation time, which is ideally a prefix of the primary key for optimal performance.</p>\n<pre><p>\nCREATE TABLE default.wikistat_sampled (\n   `time` DateTime CODEC(Delta(4), ZSTD(3)),\n   `project` LowCardinality(String),\n   `subproject` LowCardinality(String),\n   `path` String CODEC(ZSTD(3)),\n   `hits` UInt64 CODEC(ZSTD(3))\n) ENGINE = MergeTree ORDER BY (cityHash64(path), time) SAMPLE BY cityHash64(path)\n</p>\n</pre>\n<p>\nA few key points here:\n</p><ul>\n<li>The SAMPLE BY expression must be part of the primary key and return an integer - hence we use the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/hash-functions/#cityhash64\">cityHash64 function</a>. Ensure this is not an ascending numeric and randomly distributed in the space for random sampling - tip: use a hash to randomize an auto incrementing integer.</li>\n<li>It should be uniformly distributed in the domain if its datatype. In this case, path is actually imperfect as it doesnt fully satisfy this property but is sufficient for our example. A better distributed value will result in better sampling and more accurate estimations.</li>\n<li>If optimal sampling performance is required, as in our case, the SAMPLE BY column should be the first element in the ORDER BY key. If you needed to optimize for matching on Path, you might place it 2nd or just use <code>cityHash64(path)=cityHash64(“value”)</code>. However you include it, ensure the low cardinality columns come first to allow the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/improving-query-performance/sparse-primary-indexes/sparse-primary-indexes-cardinality\">use of the generic exclusion algorithm</a>.</li>\n</ul>\n<p>We can now query, using only a fraction of our data - expressing the sample as either an <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/sample/#sample-n\">absolute number of rows</a> or as <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/sample/#sample-k\">a ratio from 0 to 1</a>. Below, we utilize 1% of the data with a value of 0.01.</p>\n<pre><p>\nSELECT\n\tmonth,\n\tavg(hits)\nFROM wikistat_sampled SAMPLE 0.01\nGROUP BY toStartOfMonth(time) AS month\nORDER BY month ASC\n┌──────month─┬──────────avg(hits)─┐\n│ 2015-05-01 │ 3.2243997815421004 │\n│ 2015-06-01 │ 3.1547988082990828 │\n│ 2015-07-01 │ 2.9813449766968887 │\n│ 2015-08-01 │ 3.0210786179578397 │\n│ 2015-09-01 │ 3.1277045971550463 │\n│ 2022-11-01 │ 3.4243634422663884 │\n│ 2022-12-01 │  3.415336905631455 │\n│ 2023-01-01 │ 3.4066985347564027 │\n│ 2023-02-01 │  3.254118466286919 │\n└────────────┴────────────────────┘\n94 rows in set. Elapsed: 6.272 sec. Processed 4.26 billion rows, 179.40 GB (679.64 million rows/s., 28.60 GB/s.)\n</p>\n</pre>\n<p>Notice the accuracy of the results is reasonable, as well as the dramatic performance improvements. This sampling is entirely deterministic and consistent across tables for the same values. As a final note, the above is fine for an average, but for other calculations, such as a sum, we’d need to factor in the fact we’re only using a sample in any calculations. Consider the above query but computing hits per month:</p>\n<pre><p>\nSELECT\n\tmonth,\n\tsum(hits)\nFROM wikistat\nGROUP BY toStartOfMonth(time) AS month\nORDER BY month ASC\n┌──────month─┬───sum(hits)─┐\n│ 2015-05-01 │ 18505958911 │\n│ 2015-06-01 │ 16325574540 │\n│ 2015-07-01 │ 15541045668 │\n│ 2015-08-01 │ 15763416762 │\n│ 2022-10-01 │ 16041055714 │\n│ 2022-11-01 │ 16195366347 │\n│ 2022-12-01 │ 15383779088 │\n│ 2023-01-01 │ 16631174276 │\n│ 2023-02-01 │  5061601075 │\n└────────────┴─────────────┘\n94 rows in set. Elapsed: 289.147 sec. Processed 425.11 billion rows, 5.10 TB (1.47 billion rows/s., 17.64 GB/s.)\n</p>\n</pre>\n<br>\n<pre><p>\nSELECT\n\tmonth,\n\tsum(hits) * 100\nFROM wikistat_sampled\nSAMPLE 1 / 100\nGROUP BY toStartOfMonth(time) AS month\nORDER BY month ASC\n┌──────month─┬─multiply(sum(hits), 100)─┐\n│ 2015-05-01 │          \t16546351200 │\n│ 2015-06-01 │          \t14769222800 │\n│ 2015-07-01 │          \t13938421600 │\n│ 2015-08-01 │          \t14087318900 │\n│ 2022-10-01 │          \t15483441000 │\n│ 2022-11-01 │          \t15595982500 │\n│ 2022-12-01 │          \t14908441500 │\n│ 2023-01-01 │          \t15842792600 │\n│ 2023-02-01 │           \t4772219400 │\n└────────────┴──────────────────────────┘\n94 rows in set.
