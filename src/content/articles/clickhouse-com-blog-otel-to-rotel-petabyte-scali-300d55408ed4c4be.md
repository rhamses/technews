The goal was to represent a system where a larger number of edge collectors publish data to a stream consumed by a smaller number of collectors that write batch data efficiently to ClickHouse. In the pipeline both Rotel and the OTel Collector support the same Kafka Protobuf encoding, so they are interchangeable</p></div><div><p><span><img alt=\"rotel-pipeline-1.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frotel_pipeline_1_04c5704b11.jpg&w=2048&q=75\"></span></p>\n<h3 id=\"evaluation-approach\"></h3>\n<p>Our goal was to determine the <strong>maximum throughput a single collector could sustain</strong> on fixed hardware, focusing on efficiency rather than scaling up or out. We wanted to see how far one node could be pushed before degrading, while staying within our evaluation budget. We centered the test on the gateway collector because it exports directly to ClickHouse, which performs best with large batch inserts. Maximizing batching efficiency favors running fewer, larger gateway collectors, so this was the component we optimized and measured.</p>\n<p><strong>Detecting Saturation</strong></p>\n<p>We identified two signals that would indicate we had hit the maximum capacity a collector could handle:</p>\n<ol>\n<li><strong>Memory growth</strong> - Collectors internally buffer payloads in the face of back pressure from downstream components, which shows up as a rapid increase in memory usage.</li>\n<li><strong>Kafka consumer lag</strong> - When a collector can’t keep up with incoming messages, its Kafka consumer lag grows - the time gap between the last read message and current wall time.</li>\n</ol>\n<p><strong>Test Setup</strong></p>\n<p>For each test we ran the pipeline at a point just below saturation for a total of 15 minutes, recording two metrics:</p>\n<ul>\n<li><strong>Trace spans/sec</strong>, as recorded by the load generator</li>\n<li><strong>MB/sec ingest into ClickHouse</strong>, as measured by AWS Cloudwatch</li>\n</ul>\n<p>Aggregate bandwidth helps provide a normalized throughput metric, given trace spans can have large variations in size between environments. In our pipeline configuration the single edge collector would emit optimized batches to Kafka, reducing overall message count while increasing individual message size.</p>\n<p>For each test we capture the average CPU for Rotel and ClickHouse.</p>\n<h3 id=\"opentelemetry-clickhouse-schema\"></h3>\n<p>For our benchmark we used a single ClickHouse data schema that is compatible with both the OpenTelemetry collector and Rotel. This <a target=\"_blank\" href=\"https://clickhouse.com/docs/use-cases/observability/clickstack/ingesting-data/schemas\">schema</a> is recommended for use with ClickHouse and the ClickStack observability solution, for OTel metrics, logs, and traces.</p>\n<p>The OTel data model relies heavily on key/value attributes to represent the unique properties of infrastructure and application environments that are important for analysis. The <code>clickhouse-rs</code> crate uses RowBinary, a row-oriented, binary serialization format transmitted over HTTP, to write and read data from ClickHouse. In contrast, the OTel Collector’s Go driver and ClickHouse’s internal server communication use the column-oriented native protocol.</p>\n<p>When working with JSON column types, the clickhouse-rs crate <a target=\"_blank\" href=\"https://github.com/ClickHouse/clickhouse-rs/blob/main/examples/data_types_new_json.rs\">recommends</a> serializing values to a JSON string before sending them over the wire. ClickHouse does not store JSON columns as raw strings, so this stringification step is only for transport, but it still adds overhead. The client must serialize the JSON, and the server must parse it again. This requires scanning JSON keys and string values to escape characters such as quotes and backslashes, which becomes expensive on large strings at high throughput.</p>\n<p>With help from the ClickHouse Slack community, we discovered that JSON columns can be encoded in the native RowBinary format instead. A JSON column is encoded as a sequence of key and value pairs. You write the string key, followed by a type tag for the value, followed by the raw value itself. This avoids JSON serialization costs and lets us stream structured data directly to ClickHouse.</p>\n<p>For example, take the simple JSON object:</p></div><div><pre><code><span><span>{</span></span>\n<span>  <span>\"a\"</span><span>:</span> <span>42</span><span>,</span></span>\n<span>  <span>\"b\"</span><span>:</span> <span>\"dog\"</span><span>,</span></span>\n<span>  <span>\"c\"</span><span>:</span> <span>98</span></span>\n<span><span>}</span></span></code></pre></div><div><p>The RowBinary encoding for that looks like:</p>\n<p><span><img alt=\"row-binary-clickhouse.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frow_binary_clickhouse_60704c5612.png&w=2048&q=75\"></span></p>\n<p>JSON RowBinary first encodes the number of key/value pairs as a variable-length integer (<code>varint</code>), so <code>03</code> pairs, followed by the encoding for each key/value pair. For a given key/value pair the encoding uses a <code>varint</code> for the key length, <code>01 </code>here, followed by the string bytes, finally followed by the value encoding. If the type of the value is known in the JSON type declaration, like <code>a</code> is in the example above, then it encodes that type directly, <code>2a 00 00 00 00 00 00 00</code> for the value 42. If the type is not declared, it uses the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/data-types-binary-encoding\">Dynamic Type encoding</a>. For example, the key <code>c</code> uses the encoding <code>0a</code> to indicate an Int64, followed by the value 98 (<code>62 00 00 00 00 00 00 00</code>). Finally, the key <code>b</code> is followed by <code>15</code> to indicate that the value is of string type, followed by the length of the string <code>03</code>, then the string “dog”.</p>\n<p>This is much more efficient, reducing any serialization/deserialization time for both client and server. While this JSON encoding is not supported in the <code>clickhouse-rs</code> crate yet, we plan to help contribute support soon.</p>\n<h3 id=\"rerunning-the-test\"></h3>\n<p>After updating Rotel to use this improved <a target=\"_blank\" href=\"https://github.com/streamfold/rotel/pull/200\">encoding approach</a>, we reran our tests to measure the impact. The results showed that we were not able to exceed the previous peak of 1.45M spans per second, but we did observe roughly a <strong>10% reduction in CPU usage</strong> on the ClickHouse server and a small reduction in CPU on the gateway collector. This reduction appeared consistently across multiple runs, which suggests that the lower server-side deserialization cost provided a real benefit.</p>\n<p>The synthetic load used in this evaluation does not contain large string values, and the number of attributes per span may differ from production workloads. Although we did not see a significant improvement on the client side, we believe the faster JSON serialization and deserialization path will be more noticeable for spans that contain larger attribute sets.</p>\n<div><table><thead><tr><th></th><th>Rotel</th><th>ClickHouse</th></tr></thead><tbody><tr><td>CPU</td><td>88.5%</td><td>50.7%</td></tr></tbody></table></div>\n<p><span><img alt=\"rotel-results-2.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frotel_results_2_cafed54f6b.png&w=2048&q=75\"></span></p>\n<h2 id=\"doubling-throughput-with-one-weird-trick-finding-and-resolving-allocator-lock-contention\"></h2>\n<p>At this point in our testing we required two instances of Rotel on the gateway collector to saturate the host’s 8 vCPUs and achieve 1.45m events/sec into ClickHouse. The Rotel Kafka receiver ran in a single Tokio task, that when simplified, looked something like this.</p>\n<p><span><img alt=\"rotel-process-pipe.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frotel_process_pipe_0d20719952.jpg&w=2048&q=75\"></span></p>\n<p>There are two problems with this approach:</p>\n<ol>\n<li>Each step must be done sequentially, i.e. no parallelism.</li>\n<li>Unmarshaling is an expensive CPU-bound computation that has the potential to block Tokio executor threads.</li>\n</ol>\n<p>Tokio is an asynchronous runtime for the Rust programming language that relies on cooperative scheduling. That means that tasks are expected to voluntarily yield control back to the runtime at<code>.await</code> points or other yield points. There are <a target=\"_blank\" href=\"https://ryhl.io/blog/async-what-is-blocking/\">numerous articles</a> on the internet that explain the importance of this contract and the potentially disastrous implications of ignoring it. However, suffice it to say, a tokio task \"should never be too far away from an .await point\" and a good rule of thumb is to never spend more than 10 to 100 microseconds between each <code>.await</code>.</p>\n<p>Throughout Rotel's exporters we use a separate thread pool for the CPU intensive work of marshaling and compressing outgoing request payloads. With our Kafka receiver, payloads are decompressed in a background thread of the <a target=\"_blank\" href=\"https://github.com/fede1024/rust-rdkafka\">rust-rdkafka library</a> before they reach the <code>recv()</code> call. In our initial Kafka receiver implementation we had kept the work of unmarshaling the incoming payloads in the Tokio async task. After determining this unmarshaling was CPU intensive, we updated the Kafka receiver to use the same thread pool as the exporters for running blocking tasks.</p>\n<p>After refactoring, the receiver's main processing loop looked something like:</p></div><div><pre><code><span><span>loop</span> {</span>\n<span>  <span>select!</span> {</span>\n<span>    message = <span>recv</span>() =&gt; {</span>\n<span>        unmarshaling_futures.<span>push</span>(<span>spawn_blocking</span>(<span>unmarshal</span>(message)))     </span>\n<span>    },</span>\n<span>    unmarshaled_res = unmarshaling_futures.<span>next</span>() =&gt; {</span>\n<span>        <span>send_to_pipeline</span>(unmarshaled_res)</span>\n<span>    }</span>\n<span>  }</span>\n<span>}</span></code></pre></div><div><p>We then reran the tests with a single Rotel process on the gateway collector. We restarted our load generator at the previous maximum of 1.45M trace spans/s and were able to process the same throughput as before. However, we were shocked to find that the <strong>CPU load had dropped 40%</strong>!</p>\n<p>Previously it took two Rotel instances to saturate the vCPUs, which suggested that the Kafka receiver was hitting a serial bottleneck. Adding parallelism by moving marshaling work into separate threads should have removed that limitation. We expected that a single Rotel instance, with the bottleneck resolved, would reach the same throughput as two instances and show similar CPU usage.</p>\n<p>With CPU load now significantly lower than before, we continued to increase the throughput. <strong>We were able to increase throughput by 2x from 1.45M to 3.6M trace spans/s!</strong></p>\n<div><table><thead><tr><th>Rotel</th><th>Trace Spans</th><th>Trace Spans / Core</th><th>ClickHouse Network In (compressed)</th></tr></thead><tbody><tr><td>Single Rotel process</td><td>3.6 M/sec</td><td>450 K/sec</td><td>204 MB/sec</td></tr></tbody></table></div>\n<p>At 3.6M trace spans/s we again reached CPU saturation around 93%.</p>\n<div><table><thead><tr><th></th><th>Rotel</th><th>ClickHouse</th></tr></thead><tbody><tr><td>CPU</td><td>93.7%</td><td>55.7%</td></tr></tbody></table></div>\n<p><span><img alt=\"rotel-results-3.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frotel_results_3_6f12650fb4.png&w=2048&q=75\"></span></p>\n<p>With the performance gains confirmed, our next step was to understand what drove the improvement in CPU efficiency. On first inspection, nothing immediately jumped right out to us. Can you spot it? The workload generates a lot of short lived objects, so we spend a lot of time allocating and freeing memory.</p>\n<p><strong>Old:</strong></p>\n<p><span><img alt=\"rotel-flame-old.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frotel_flame_old_ab73c122fe.png&w=2048&q=75\"></span></p>\n<p><strong>New:</strong></p>\n<p><span><img alt=\"rotel-flame-new.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frotel_flame_new_b96de94460.png&w=2048&q=75\"></span></p>\n<h3 id=\"profiling-kafka-receiver-changes-with-linux-perf\"></h3>\n<p>Running Linux perf stat showed some striking differences between the builds.</p></div><div><pre><code><span>perf stat -c cycles,instructions,cache-misses,cache-references,context-switches,cpu-migrations</span></code></pre></div><p><strong>Old:</strong></p><div><pre><code><span>295612663445 cycles </span>\n<span>264853636815 instructions # 0.90 insn per cycle </span>\n<span>615670230 cache-misses # 32.963 % of all cache refs </span>\n<span>1867733351 cache-references </span>\n<span>1224819 context-switches </span>\n<span>1230 cpu-migrations </span>\n<span>50.296446757 seconds time elapsed</span></code></pre></div><p><strong>New:</strong></p><div><pre><code><span>150590256805 cycles </span>\n<span>287007890213 instructions # 1.91 insn per cycle </span>\n<span>598469068 cache-misses # 51.429 % of all cache refs </span>\n<span>1163669589 cache-references </span>\n<span>37675 context-switches </span>\n<span>43 cpu-migrations </span>\n<span>43.716966122 seconds time elapsed</span></code></pre></div><div><p>The new build is averaging 1.9 instructions per cycle with only 862 context switches/sec - not amazing for instruction-level parallelism (ILP), but not terrible. The old version was averaging .9 instructions per cycle and an astounding 24,350 context switches/sec, <strong>that’s a 32.5x decrease in context switches in the new build!</strong> Essentially we were getting no ILP and we were constantly parking and unparking threads. Further, the new version averages 1 cpu migration/sec, showing excellent cache affinity while the old version averaged 24.5 migrations/sec - that’s a <strong>24.5x decrease in the new build</strong> indicating the scheduler couldn’t keep threads on the same cores in the old build.</p>\n<p>The new version shows much better parallelization characteristics, allowing us to ramp our throughput even further than before. However, all we did was just move some work to different threads.</p>\n<p>We could assume the poor performance in the old version was likely due to blocking Tokio executor threads, thereby creating additional overhead in polling, spinning, and attempted work stealing. However digging into the results of a <code>perf report</code> led to our actual more nuanced answer.</p>\n<h3 id=\"digging-into-profiles-with-linux-perf-report\"></h3>\n<p>After running the tests again with a perf record we had a much more detailed view of the old new and old builds. The new version looks pretty healthy. We’re spending most of our time in compressing data for exporting, transforming OTLP into rows for ClickHouse, and allocating and deallocating memory.</p>\n<p><span><img alt=\"rotel-perf.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frotel_perf_7c027ee07e.png&w=2048&q=75\"></span></p>\n<p>However the old version has quite a different story. It spent 15% of the time freeing memory and only 9.75% of its time compressing and preparing data for ClickHouse, as opposed to ~20% in the new version. We were also spending a lot of time in <code>_raw_spin_unlock_irqrestore</code>, <code>finish_task_switch.isra.0</code>,  <code>__lll_lock_wait_private</code> and <code>__lll_lock_wake_private</code>.</p>\n<p><span><img alt=\"rotel-perf-2.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frotel_perf_2_85c829c9d1.png&w=2048&q=75\"></span></p>\n<p>If we view the report with children, we can see the time spent waiting on locks was happening when we were attempting to free memory.</p>\n<p><span><img alt=\"rotel-perf-3.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frotel_perf_3_9f387c611c.png&w=2048&q=75\"></span></p>\n<p><strong>So what do these functions do?</strong></p>\n<p><code>_raw_spin_unlock_irqrestore</code> is a Linux kernel function that re-enables interrupts and releases a spinlock, restoring the interrupt context to what it was before a corresponding <code>_raw_spin_lock_irqsave</code> call. More importantly <code>_raw_spin_unlock_irqrestore</code> is called when a task is about to be preempted, allowing the scheduler to perform a context switch. <code>finish_task_switch.isra.0</code> on the other hand is the compiler optimized version of <code>finish_task_switch</code> which performs cleanup and post context-switch actions.These functions correspond to the massive increase in context switches we observed in the older version.</p>\n<p><code>__lll_lock_wait_private</code> and <code>__lll_lock_wake_private</code> are internal, low-level functions within <code>glibc</code> and are related to the implementation of mutexes and other synchronization primitives. <strong>What’s interesting here is that we see the locking showing up when attempting to free memory.</strong></p>\n<p>In retrospect, looking back at our old version’s flamegraph, the problem is obvious. Ideally we’d have used a tool like <a target=\"_blank\" href=\"https://www.brendangregg.com/blog/2014-11-09/differential-flame-graphs.html\">differential flame graphs</a> to compare the two flame graphs side by side making it easier to spot the difference (my kingdom for more, easy to use, flame graph tooling). Fortunately we quickly uncovered the root cause with perf stat and perf record. <strong>The contention is in the ClickHouse exporter marshaling functions (TransformPayload) rather than the Kafka receiver.</strong></p>\n<p><span><img alt=\"rotel-flamegraph-3.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frotel_flamegraph_3_ee3ea81bf4.png&w=2048&q=75\"></span></p>\n<h3 id=\"glibc-multi-threaded-allocation\"></h3>\n<p>So now it’s clear why our changes caused CPU utilization to drop while throughput improved. The old version was doing a lot of work, just not the type of work we wanted to be doing! Essentially the old version was spin locking attempting to free memory.</p>\n<p>To understand what was going on requires a brief understanding of how the <code>glibc</code> allocator works. Memory is separated into regions called “arenas”, each of these arenas has a mutex lock protecting both allocation and deallocation. Where possible threads will attempt to create separate arenas to avoid lock contention, with the number of allocated arenas growing as a thread pool increases. However, if deallocation occurs on a different thread to the one on which allocation was performed, then the de-allocating thread will have to lock the owning arena - causing other threads to wait and thus contention.\nIn our older version, we allocated our memory for processing trace data during the Kafka receiver’s unmarshaling routine on a Tokio executor I/O task. This work was scheduled on the reduced set of Tokio async executor threads, for which there were only eight, one per core, on the gateway collector node. Later in the pipeline that memory was deallocated as part of the ClickHouse exporter request marashaling, which executed as a blocking task on a much larger thread pool - 10s to 100s of threads.</p>\n<p>Here’s an illustration of the data flow and locking pattern running on a two-core box with just two Tokio async executor threads:</p>\n<p><span><img alt=\"rotel-threading-old.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frotel_threading_old_208db15f08.png&w=2048&q=75\"></span></p>\n<p>In the new version, the allocations occurring during the CPU bound Kafka receiver unmarshaling routine executes on the same, much larger, thread pool as the deallocation was occurring. As the pipeline volume grows, increasing the amount of unmarshaling/marshaling, the blocking thread pool grows. This increases the number of arenas, reducing the chance of lock contention.</p>\n<p>The pipeline now appears more like this:</p>\n<p><span><img alt=\"rotel-threading-new.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frotel_threading_new_8936c04ae2.jpg&w=2048&q=75\"></span></p>\n<h3 id=\"confirming-arena-lock-contention-with-jemalloc\"></h3>\n<p>A helpful early reviewer of this post posed the question “I’m curious if this phenomenon reproduces on jemalloc?”. <a target=\"_blank\" href=\"https://jemalloc.net/\">Jemalloc</a> is a general purpose malloc implementation that is specifically designed to reduce lock contention for threaded programs on multi-processor systems. We had tested Rotel with jemalloc in the past and found no significant performance wins. However, our ClickHouse exporter workload combined with the recent Kafka receiver, clearly puts pressure on allocation so we were keen to try running both the old and new versions with jemalloc.</p>\n<p>After modifying the previous version with an older task scheduling model to use jemalloc, <strong>we saw a reduction in CPU utilization from 93% to 40%. This reduction matched what we saw moving the unmarshaling to the shared thread pool, confirming our findings</strong>.</p>\n<p>Although jemalloc lowered CPU usage in the previous version, it introduced higher Kafka lag at full throughput. Combined with the fact that jemalloc is <a target=\"_blank\" href=\"https://jasone.github.io/2025/06/12/jemalloc-postmortem/\">no longer actively maintained</a>, we do not plan to adopt it as the default allocator. We may add feature flags so users can opt in to custom allocators such as jemalloc or mimalloc when needed.</p>\n<h2 id=\"fast-lz4-compression-for-an-additional-push\"></h2>\n<p>Rotel uses the recommended LZ4 compression setting for ClickHouse payloads to reduce over-the-wire data transfer. It leverages the same <code>lz4_flex</code> crate that <code>clickhouse-rs</code> uses, but we had imported it directly. When we pulled over the compression support that relied on the <a target=\"_blank\" href=\"https://github.com/PSeitz/lz4_flex\"><code>lz4-flex</code></a> crate, we failed to notice the feature settings in the <code>Cargo.toml</code> import.</p>\n<p>The <code>lz4-flex</code> crate has both unsafe and safe implementations, with the unsafe versions providing slightly improved performance (read about Rust unsafe <a target=\"_blank\" href=\"https://doc.rust-lang.org/book/ch20-01-unsafe-rust.html\">here</a>). With <code>lz4-flex</code>, you must opt-in to the unsafe, faster, variant of the library.</p>\n<p>The clickhouse-rs crate opts into the unsafe variant of <code>lz4-flex</code>, but we had missed that. Enabling that provided a slight additional boost, taking our gateway collector throughput from <strong>3.6M to 3.7M trace spans/sec and 209 MB/sec.</strong></p>\n<div><table><thead><tr><th>Rotel</th><th>Trace Spans</th><th>Trace Spans / Core</th><th>ClickHouse Network In (compressed)</th></tr></thead><tbody><tr><td>Single Rotel process</td><td>3.7 M/sec</td><td>462.5 K/sec</td><td>209 MB/sec</td></tr></tbody></table></div>\n<p>CPU also decreased just slightly on the gateway collector.</p>\n<div><table><thead><tr><th></th><th>Rotel</th><th>ClickHouse</th></tr></thead><tbody><tr><td>CPU</td><td>90.8%</td><td>57.8%</td></tr></tbody></table></div>\n<p><span><img alt=\"rotel-results-4.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frotel_results_4_045ede7829.png&w=2048&q=75\"></span></p>\n<h2 id=\"complete-end-to-end-evaluation\"></h2>\n<p>After working through multiple optimizations of Rotel and evaluating it against the Null table engine of ClickHouse, we were able to scale the single instance throughput of Rotel from an initial 1.1M trace spans/sec to a total of <strong>3.7M trace spans/sec</strong> or <strong>462.5 K trace spans/sec per-core</strong>. This is nearly over 4x the original 1.1 M/sec throughput we saw when testing the OTel collector.</p>\n<p>We now turned our attention to the final piece which was getting the data permanently into ClickHouse and committed fully to disk. They improved their pipeline throughput 20x, while retaining just 10% of the capacity footprint they required before. If they were to continue on their previous trajectory, it would have been prohibitively expensive to operate. Other organizations like <a target=\"_blank\" href=\"https://clickhouse.com/blog/netflix-petabyte-scale-logging\">Netflix</a> and <a target=\"_blank\" href=\"https://kccncna2025.sched.com/event/29Kgb\">OpenAI</a>, have also reached similar conclusions: that once you reach this level of volume, efficiency is critically important to the business. This is the context in which we have sought to improve the efficiency of OpenTelemetry collection and have developed Rotel.</p>\n<h3 id=\"near-4x-efficiency-improvement\"></h3>\n<p>This work pushed us to optimize Rotel into a high-throughput pipeline for streaming OpenTelemetry tracing data into ClickHouse. In our tests, Rotel reached nearly <strong>four times the throughput</strong> of the OpenTelemetry Collector on the same hardware, which can translate into meaningful resource savings at large scale. Rotel has first-class support for OpenTelemetry traces, metrics, and logs, and while this post focused on tracing, we plan to evaluate log and metric workloads as part of future benchmarking.</p>\n<p>We are also interested in learning which capabilities matter most when operating at this level of volume. If you have ideas or want to share your own scaling challenges, you can join the community on <a target=\"_blank\" href=\"https://rotel.dev/discord\">Discord</a> or contribute on <a target=\"_blank\" href=\"https://github.com/streamfold/rotel\">GitHub</a>.</p>\n<h3 id=\"further-work\"></h3>\n<p>Here are some topics we would like to explore more after working on this post:</p>\n<h4 id=\"deep-dive-on-kafka-reliability\"></h4>\n<p>We only briefly touched on it in this post, but Rotel supports reliable delivery guarantees via end-to-end message acknowledgement, to ensure at-least-once delivery when streaming data from Kafka rather than relying on auto-commit which can easily result in data-loss . This support required a number of changes to the pipeline and rigorous testing to ensure Rotel does not drop data while also reducing duplicate deliveries. We would like to deep-dive into what reliable delivery means, how we built it, and the verification tools we built to test it. Look for a follow up post on this.</p>\n<h4 id=\"explore-clickhouse-native-protocol\"></h4>\n<p>Rotel’s ClickHouse integration is built on the <code>clickhouse-rs</code> Rust crate, which uses the RowBinary protocol over HTTP. The OpenTelemetry Collector uses the Go ClickHouse driver, which communicates using the native ClickHouse protocol. The native protocol is the same one used for internal ClickHouse to ClickHouse transfers, and benchmarks have shown it to be more than <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-input-format-matchup-which-is-fastest-most-efficient#insert-performance-of-common-input-formats\">20 percent faster than RowBinary</a>. ClickHouse has also added support for Apache Arrow Flight, which uses the Arrow in-memory format for efficient transport. We intend to evaluate moving from the row-oriented RowBinary format to one of the column-oriented formats, since they may provide another increase in throughput for Rotel. We plan to share our testing results in a future update.</p>\n<h4 id=\"further-exploring-blocking-tasks-on-tokio\"></h4>\n<p>Blocking tasks like deserializing payloads, can have large impacts on Tokio performance. It wasn’t until we worked through this benchmark that we discovered how much, so we want to find other potential impacts of this. We already know that Rotel’s OTLP receiver performs expensive Protobuf deserialization inline during the async task processing of the connection. This is built into the <code>tonic</code> crate, so we would like to explore how best to split this out. From some early analysis with the perf tools we think there may be big wins here.</p>\n<h4 id=\"reducing-memory-allocation-impacts\"></h4>\n<p>While Rust does not have a garbage collector, at high volumes memory allocation and deallocation still have a significant performance impact. In Rotel we are regularly cycling through memory allocations for short-lived objects as they move through the pipeline. Adopting a memory free list approach that allows us to skip the allocator for common reused buffers should cut performance overheads significantly. Of course, implementing it can be tricky and runs the risk of ballooning your memory usage if you’re not careful. This is another area where we may need to dive into the <code>tonic</code> crate to make necessary changes.</p>\n<p><em>We’d like to thank Sujay Jayakar, Ben Sigelman, Rick Branson, Vlad Seliverstov, Rory Crispin and Achille Roussel for reviewing early drafts of this post.</em></p></div><div><h2 id=\"addendum\"></h2>\n<h3 id=\"considered-projects\"></h3>\n<p>While compiling these benchmarks we wanted to include other data planes that offered OpenTelemetry support, but found them incompatible with the benchmark.
