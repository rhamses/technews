contentHtml: "<div><p>We’re open sourcing <a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_stat_ch\"><strong>pg_stat_ch</strong></a>: a PostgreSQL extension that turns every query execution into a fixed-size ~4.6KB event and streams them into ClickHouse.</p>\n<p>Once events are in ClickHouse, you can slice and drill into query behavior like an APM: p50 to p99 latency over time, top queries by runtime, errors by app, and “what changed between 2pm and 3pm” across days or months of history.</p>\n<p>It’s open-source, Apache 2.0, and supports PostgreSQL 16 to 18. If you want to try it, <a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_stat_ch?tab=readme-ov-file#quickstart\">give the quickstart a go.</a></p>\n<p>In this post, I’ll walk through how it works under the hood, the tradeoffs we made, and how it compares with existing extensions.</p>\n<h2 id=\"why-build-pg-stat-ch\"></h2>\n<p>In January, we launched <a target=\"_blank\" href=\"https://clickhouse.com/cloud/postgres\">Postgres managed by ClickHouse</a>. We need to understand how the clusters we manage are running, and we want to provide the same level of insight to our customers.</p>\n<p>ClickHouse, the analytical database we’re best known for, comes with its own internal system tables that collect everything happening within the server. It’s also built for analytics, so you can just analyse your ClickHouse usage within ClickHouse itself. We rely on this for the managed ClickHouse service in ClickHouse Cloud, as do our customers.</p>\n<p>Postgres doesn’t have that level of introspection capability out of the box, and isn’t built for analytics. So, we wanted a way to match that level of detail about what's happening inside Postgres, and the same level of analytical capability to work with it. <a target=\"_blank\" href=\"https://clickhouse.com/blog/pg_stat_ch-postgres-extension-stats-to-clickhouse#what-you-can-actually-do-with-raw-events\">See below for examples of the kind of insights you can get with pg_stat_ch.</a></p>\n<p>We frequently use extensions like <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/pgstatstatements.html\">pg_stat_statements</a>, <a target=\"_blank\" href=\"https://github.com/percona/pg_stat_monitor\">pg_stat_monitor</a> and <a target=\"_blank\" href=\"https://github.com/DataDog/pg_tracing\">pg_tracing</a>, and while they cover some parts of the problem, we had 3 primary goals that they didn’t cover:</p>\n<ul>\n<li>\n<p>Capture everything a PostgreSQL cluster does: every SELECT, INSERT, DDL, and even the queries that fail.</p>\n</li>\n<li>\n<p>Ship events off to an external system to handle analyses</p>\n</li>\n<li>\n<p>Incur minimal overhead to PostgreSQL</p>\n</li>\n</ul>\n<p>We haven’t shipped pg_stat_ch to production yet, but we’re actively driving it there as part of ClickHouse’s managed Postgres effort. Today it streams per-query events into ClickHouse with a 2KB query text cap and no plan capture yet.</p>\n<p>If you operate PostgreSQL at scale, we’d love feedback, and we’ll keep sharing what we learn as it hardens.</p></div><div><h2 id=\"the-architecture-in-30-seconds\"></h2>\n<p>Under the hood, pg_stat_ch does the minimum work possible: on the hot path it’s just a <a target=\"_blank\" href=\"https://en.cppreference.com/w/cpp/string/byte/memcpy.html\">memcpy</a> into a shared-memory ring buffer. A background worker wakes up once a second, batches what’s in the buffer, and flushes it using ClickHouse’s native binary protocol with LZ4 compression.</p>\n<p><span><img alt=\"pg_stat_ch architecture diagram\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FLogo_Architecture_Diagrams_for_pg_stat_ch_Release_Blog_1365_Open_e095fb2920.png&w=2048&q=75\"></span></p>\n<p>Every time PostgreSQL executes a statement, whether it’s a SELECT, an INSERT, DDL, or even a query that fails with a syntax error, <code>pg_stat_ch</code> records it as a fixed size event. Each event includes 45 fields, covering timing, buffer I/O, WAL, CPU and JIT stats, error details, and basic client context.</p>\n<p>From there, the backend does one quick copy into a shared-memory ring buffer and moves on. Once a second, a background worker drains up to 10,000 events, packs them into a columnar block, compresses it with LZ4, and sends it to ClickHouse over the native binary protocol.</p>\n<p>On the ClickHouse side, raw events land in <a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_stat_ch/blob/main/docker/init/00-schema.sql\">the <code>events_raw</code> table</a>, and four materialized views pre-aggregate them into dashboards you can query immediately:</p>\n<div><table><thead><tr><th>View</th><th>What it does</th></tr></thead><tbody><tr><td>events_recent_1h</td><td>Rolling 1-hour copy for “what’s happening right now”</td></tr><tr><td>query_stats_5m</td><td>5-minute buckets with p95/p99 via quantilesTDigest</td></tr><tr><td>db_app_user_1m</td><td>Per-database/app/user load attribution, 1-minute granularity</td></tr><tr><td>errors_recent</td><td>7-day rolling window of every error with full context</td></tr></tbody></table></div>\n<p>The important bit here is that <strong>all aggregation happens in ClickHouse, not in PostgreSQL.</strong> Postgres captures events and pushes them out. ClickHouse compresses, stores, and answers analytical queries.</p>\n<h2 id=\"engineering-decisions\"></h2>\n<h3 id=\"decision-1-fixed-size-events\"></h3>\n<p>We had two options for event data: variable-length (allocate per event based on query text size, like pg_stat_monitor does with <a target=\"_blank\" href=\"https://tselai.com/pg-dsm-registry-allocations\">PostgreSQL’s DSA allocator</a>) or fixed-size.</p>\n<p>We chose fixed-size. The memcpy is fast, but the real cost is LWLock acquisition, name resolution (get_database_name, GetUserNameFromId, GetClientAddress), and getrusage() for CPU timing. <a target=\"_blank\" href=\"https://clickhouse.com/blog/pg_stat_ch-postgres-extension-stats-to-clickhouse#overhead-on-postgresql\">We’ll get to the measured overhead below.</a></p>\n<p>The bigger advantage of fixed-size is a predictable memory footprint you can reason about at startup:</p>\n<div><pre><code><span>queue_capacity = 65,536 events (default)</span>\n<span>event_size     = ~4.6 KB</span>\n<span>total memory   = 65,536 × 4.6 KB = 294.4 MB</span></code></pre></div>\n<p>You know exactly how much shared memory you need at shared_preload_libraries time. The queue capacity and event size are configurable settings, so you can tune based on your workload.</p>\n<p>There is a tradeoff: query texts longer than 2KB (or the configured event size) get truncated. You still get the fingerprint (query_id) and all 45 metrics. If it’s running, you can look up the full text by the query_id in pg_stat_statements.</p>\n<h3 id=\"decision-2-ensure-negligible-impact-on-postgres\"></h3>\n<p>The ring buffer is the hottest data structure in the extension. Every backend process writes to it (producers), and one background worker reads from it (consumer). On a busy 32-core system, that’s potentially dozens of concurrent writers.</p>\n<p>Here’s the layout:</p>\n<div><pre><code><span>┌───────────────────────────────────────────┐</span>\n<span>│ [Rarely changed]                          │</span>\n<span>│   LWLock* lock                            │</span>\n<span>│   uint32  capacity                        │</span>\n<span>│                                           │</span>\n<span>│ ─── CACHE LINE BOUNDARY (64 bytes) ───────│</span>\n<span>│                                           │</span>\n<span>│ [Producer-hot: many backends write]       │</span>\n<span>│   atomic_uint64 head                      │</span>\n<span>│   atomic_uint64 enqueued                  │</span>\n<span>│   atomic_uint64 dropped                   │</span>\n<span>│   atomic_flag   overflow_logged           │</span>\n<span>│                                           │</span>\n<span>│ ─── CACHE LINE BOUNDARY ──────────────────│</span>\n<span>│                                           │</span>\n<span>│ [Consumer-hot: bgworker reads/writes]     │</span>\n<span>│   atomic_uint64 tail                      │</span>\n<span>│   atomic_uint64 exported                  │</span>\n<span>│                                           │</span>\n<span>│ ─── CACHE LINE BOUNDARY ──────────────────│</span>\n<span>│                                           │</span>\n<span>│ [Stats: bgworker writes, anyone reads]    │</span>\n<span>│   atomic_uint64 send_failures             │</span>\n<span>│   TimestampTz   last_success_ts           │</span>\n<span>│   TimestampTz   last_error_ts             |</span>\n<span>│   char          last_error_text[256]      │</span>\n<span>│   atomic_uint32 bgworker_pid              │</span>\n<span>└───────────────────────────────────────────┘</span></code></pre></div>\n<p>The PG_CACHE_LINE_SIZE padding between sections is the critical detail. Without it, every time the background worker updates tail, it invalidates the cache line containing head on every producer’s CPU core. That’s <strong>false sharing</strong> — and on multi-socket systems it can cost 50–100ns per access. With the separation, producer cores and the consumer core work on independent cache lines and never interfere.</p>\n<p>The capacity is always a power of 2 (1,024 to 65,536), so slot addressing uses a bitmask (index &amp; (capacity - 1)) instead of modulo. One fewer division instruction in the hot path.</p>\n<h3 id=\"decision-3-no-back-pressure\"></h3>\n<p>There are exactly two ways events can be lost, and both are deliberate:</p>\n<ol>\n<li>\n<p><strong>Queue overflow.</strong> The ring buffer fills up faster than the background worker drains it. New events are dropped — the producer atomically increments a dropped counter and returns in nanoseconds.</p>\n</li>\n<li>\n<p><strong>Export failure.</strong> The background worker dequeues a batch, then the ClickHouse insert fails. Those events are gone. We don’t re-enqueue them.</p>\n</li>\n</ol>\n<p>The alternative is back-pressure. That would mean if ClickHouse slows down or goes offline, PostgreSQL starts feeling it too, and your queries get slower. <strong>For us, that’s a non-starter.</strong></p>\n<p>For an OLTP system doing 50,000 queries/second, if back-pressure adds a 10ms stall per query during a ClickHouse blip, p99 latency goes from 5ms to 15ms. This would have a material impact on SLOs and users will notice. This is not an acceptable tradeoff for monitoring.</p>\n<p>This is the same philosophy behind UDP-based metrics systems (<a target=\"_blank\" href=\"https://www.etsy.com/codeascraft/measure-anything-measure-everything#:~:text=brag%20about%20them.-,Why%20UDP%3F,-So%2C%20why%20do\">StatsD</a>, <a target=\"_blank\" href=\"https://pkg.go.dev/github.com/DataDog/datadog-agent/cmd/dogstatsd?utm_source=chatgpt.com#section-readme:~:text=datadog/dogstatsd%3Alatest-,Why%20UDP%3F,-Like%20StatsD%2C%20DogStatsD\">DogStatsD</a>): a few lost data points are infinitely preferable to affecting the system you’re observing.</p>\n<p><strong>Observability should observe, not obstruct.</strong></p>\n<p>The dropped counter is visible via the included pg_stat_ch_stats() function so you can monitor overflow and tune queue_capacity. In practice, with a 1-second flush interval and 10K batch size, you need sustained 65K QPS with a completely stalled ClickHouse to start dropping.</p>\n<h3 id=\"decision-4-minimize-lock-contention\"></h3>\n<p>The enqueue path uses three tiers to minimize lock contention:</p>\n<p><span><img alt=\"pg_stat_ch enqueue path\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDark_Mode_New_Diagram_0807f482fc.png&w=2048&q=75\"></span></p>\n<ol>\n<li>\n<p><strong>Step 1</strong> is the safety valve. We check for overflow using atomics only. If the ring is full, we drop the event and return immediately. Overflow handling never takes a lock.</p>\n</li>\n<li>\n<p><strong>Step 2</strong> is the normal case. We try to grab the <a target=\"_blank\" href=\"https://doxygen.postgresql.org/lwlock_8h_source.html\">LWLock</a> without blocking. When there is no contention, enqueue looks just like the simple design: take the lock, memcpy into the slot, bump head, release.</p>\n</li>\n<li>\n<p><strong>Step 3</strong> allows it to scale when you have lots of backends running at once (say 32+). Instead of every backend vying for the same exclusive lock for every query, each backend stashes events in a small process-local buffer and flushes them once per transaction. On TPC-B, with about 5 queries per transaction, this design cuts lock acquisitions from roughly 150K per second to about 30K per second, around a 5x reduction.</p>\n</li>\n</ol>\n<p>That process-local buffer lives in static <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/.bss\">BSS</a>, about 37KB per backend (8 events × ~4.6KB each). pg_stat_ch also registers an <a target=\"_blank\" href=\"https://doxygen.postgresql.org/ipc_8h.html\"><code>on_shmem_exit</code></a> handler to flush anything left at backend shutdown, exporting buffered events even when a backend exits mid-transaction.</p>\n<h3 id=\"decision-5-native-protocol-with-lz4\"></h3>\n<p>We use ClickHouse’s native binary protocol via clickhouse-cpp (statically linked into the extension .so) rather than HTTP. Three reasons:</p>\n<ol>\n<li>\n<p><strong>LZ4 block compression</strong> — critical for reducing bandwidth when shipping thousands of events/second over the network</p>\n</li>\n<li>\n<p><strong>Columnar encoding</strong> — data is sent column-major, which ClickHouse can ingest directly without row-to-column transposition</p>\n</li>\n<li>\n<p><strong>Type-safe binary encoding</strong> — no JSON parsing overhead</p>\n</li>\n</ol>\n<p>We compile the clickhouse-cpp client into the extension as a static library. That keeps deployment simple: no extra runtime dependencies beyond PostgreSQL (and optionally OpenSSL). The downside is size. Static linking pushes the extension over 20 MB, but we’re fine with that tradeoff if it means fewer “it works on my box” surprises.</p>\n<p>We intentionally set socket timeouts to 30 seconds. The background worker still needs to respond to PostgreSQL signals, especially during operations like DROP DATABASE (via <code>procsignal_sigusr1_handler</code>). If we used infinite timeouts and the network to ClickHouse stalled, we could end up hanging DROP DATABASE until the socket unwedged, which is not acceptable.</p>\n<h2 id=\"how-we-hook-into-postgresql\"></h2>\n<p>PostgreSQL offers extensions a handful of hooks. pg_stat_ch wires into those hooks to capture the right data at the right moment, before Postgres tears down the state we need. Here are the hooks we use, what we do in each one, and why each matters.</p>\n<div><table><thead><tr><th>Hook</th><th>What pg_stat_ch Does</th><th>Why Here?</th></tr></thead><tbody><tr><td>ExecutorStart</td><td>Record query_start_ts, CPU baseline via getrusage(), enable INSTRUMENT_ALL</td><td>Need a time-zero reference <em>before</em> any work. If we don’t enable instrumentation here, Postgres won’t collect buffer/WAL/timing stats at all.</td></tr><tr><td>ExecutorRun</td><td>Increment/decrement nesting level (with PG_FINALLY for exception safety)</td><td>Tracks query nesting for CTEs, subqueries, function calls. Otherwise, a nested query’s metrics bleed into the parent.</td></tr><tr><td>ExecutorFinish</td><td>Same nesting-level tracking</td><td>AFTER triggers fire here and can execute nested queries — would corrupt the nesting count without tracking.</td></tr><tr><td>ExecutorEnd</td><td><strong>Main collection point.</strong> Finalize timing, compute CPU delta, extract all 45 fields, enqueue event.</td><td>Must happen <em>before</em> standard_ExecutorEnd() because it nulls out estate, planstate, totaltime.</td></tr><tr><td>ProcessUtility</td><td>Snapshot buffer/WAL/CPU counters, execute, compute delta</td><td>DDL/COPY/VACUUM bypass the executor entirely — no QueryDesc, no instrumentation. We manually compute the delta.</td></tr><tr><td>emit_log_hook</td><td>Capture SQLSTATE, severity, message text for errors</td><td>Error tracking is impossible from executor hooks alone. Syntax errors, permission denials, constraint violations — none of them reach ExecutorEnd.</td></tr></tbody></table></div>\n<p>All hooks chain to previous hook values, so pg_stat_ch coexists with pg_stat_statements, auto_explain, pg_tracing, and anything else. The chaining order follows shared_preload_libraries load order.</p>\n<p><span><img alt=\"pg_stat_ch postgres hooks\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FLogo_Architecture_Diagrams_for_pg_stat_ch_Release_Blog_1365_Open_1_8cdff66547.png&w=2048&q=75\"></span></p>\n<h2 id=\"overhead-on-postgresql\"></h2>\n<p>We ran pgbench (TPC-B, scale factor 10, 32 clients, 8 threads, 30 seconds) on an <a target=\"_blank\" href=\"https://frame.work/desktop\">AMD Ryzen AI MAX+ 395 (16c/32t, 64MB L3, 128GB RAM)</a> against PostgreSQL 18 with and without pg_stat_ch.&#160;ClickHouse was running locally in Docker.</p>\n<div><table><thead><tr><th></th><th>TPS</th><th>latency avg</th></tr></thead><tbody><tr><td>without pg_stat_ch</td><td>41,309</td><td>0.775 ms</td></tr><tr><td>with pg_stat_ch</td><td>36,656</td><td>0.873 ms</td></tr><tr><td>overhead</td><td>~11%</td><td>~11%</td></tr></tbody></table></div>\n<p>At 36.6K TPS, pg_stat_ch captured <strong>7.7 million events</strong> over 30 seconds with <strong>zero drops</strong> (queue_capacity=4M, flush_interval=100ms, batch_max=100K). Each number is the average of two consecutive runs.</p>\n<p>Here’s the flamegraph:</p>\n<p><span><img alt=\"Flamegraph of pgbench with pg_stat_ch\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fimage2_c36d949269.png&w=2048&q=75\"></span></p>\n<p>We also profiled 8 backends for 10 seconds using perf record with DWARF call graphs:</p>\n<div><pre><code><span>Overhead Component                    % of CPU</span>\n<span>──────────────────────────────────────────────────</span>\n<span>Enqueue (<span>try</span>-<span>lock</span> fast path)            <span>0.94</span>%    ← was <span>2.32</span>% <span>before batching</span></span>\n<span><span>  Batch <span>flush</span> (<span>XactCallback → batch</span>)    0.54%    ← <span>new</span>: amortized <span>lock</span> path</span></span>\n<span><span><span>BuildEvent</span> (<span>QueryDesc → <span>struct</span></span>)         0.33%</span></span>\n<span><span>ProcessUtility overhead                 0.08%</span></span>\n<span><span><span>InstrAlloc</span> (<span>enable instrumentation</span>)     0.05%</span></span>\n<span><span>Nesting <span>tracking</span> (<span>Run + Finish</span>)         0.05%</span></span>\n<span><span>──────────────────────────────────────────────────</span></span>\n<span><span>TOTAL pg_stat_ch CPU overhead          ~2.0%</span></span></code></pre></div>\n<p>So, the observed CPU overhead of pg_stat_ch is ~2%. The ~11% overhead to TPS/latency we see in the benchmark is due to contention amplification on the enqueue lock. This pgbench TPC-B setup has very short, sub-millisecond transactions at high concurrency, so even a small serialized section can translate to a noticeable TPS drop.</p>\n<p>Before <a target=\"_blank\" href=\"https://clickhouse.com/blog/pg_stat_ch-postgres-extension-stats-to-clickhouse#decision-4-minimize-lock-contention\">the try-lock + local batching change</a>, pg_stat_ch acquired the enqueue LWLock on every query. Under this workload that lock became a hot spot and the TPS drop was about 24%. The try-lock + local batching optimization brought this down to about 11%: backends now attempt a non-blocking enqueue and, if the lock is contended, buffer events locally and flush them once per transaction. With roughly 5 queries per TPC-B transaction, this reduces lock acquisitions from ~150K/s to ~30K/s (a 5x reduction), which materially reduces contention.</p>\n<p>This also explains the apparent mismatch between ~2% CPU overhead and ~11% TPS overhead. The ~2% figure is the time spent in pg_stat_ch code itself (building events, enqueue fast path, batched flush) and it excludes the knock-on effects of lock contention. The remaining gap is time lost to lock contention and scheduling effects around the shared enqueue path, which shows up as reduced throughput rather than CPU time spent in the extension.</p>\n<p>TPC-B at 32 clients is probably close to the worst case for this effect, we expect that most real workloads will see less impact. We’ll publish additional numbers on more representative workloads shortly after launch to quantify overhead when lock pressure is lower.</p>\n<h2 id=\"storage-and-compression-in-clickhouse\"></h2>\n<p>Each PschEvent is fixed size in PostgreSQL shared memory. We shipped 7.7M pgbench events to ClickHouse and measured the actual on-disk size:</p>\n<div><pre><code><span>7.7M events × ~4.6KB ≈ 35 GB as raw structs</span>\n<span>ClickHouse compressed:     426 MB</span>\n<span>compression ratio:         ~83:1 (from raw event size)</span>\n<span>bytes per row:             ~36 bytes compressed</span></code></pre></div>\n<p>The per-column breakdown shows where the compression wins:</p>\n<div><table><thead><tr><th>Column</th><th>Compressed</th><th>Ratio</th><th>Bytes/row</th></tr></thead><tbody><tr><td>query (text)</td><td>119 MB</td><td>5.6:1</td><td>10.0</td></tr><tr><td>ts_start</td><td>44 MB</td><td>2.2:1</td><td>3.7</td></tr><tr><td>cpu_user_time_us</td><td>33 MB</td><td>2.9:1</td><td>2.8</td></tr><tr><td>duration_us</td><td>32 MB</td><td>3.0:1</td><td>2.7</td></tr><tr><td>query_id</td><td>30 MB</td><td>3.2:1</td><td>2.5</td></tr><tr><td>db</td><td>317 KB</td><td>230:1</td><td>~0</td></tr><tr><td>username</td><td>440 KB</td><td>221:1</td><td>~0</td></tr><tr><td>app</td><td>440 KB</td><td>221:1</td><td>~0</td></tr></tbody></table></div>\n<p>Low-cardinality strings (db, username, app) compress to almost nothing — dictionary encoding reduces them to a few bits per row. The query column dominates at 119MB, but pgbench has only a handful of distinct query texts that repeat millions of times, so even that compresses 5.6:1.</p>\n<p>A real workload with more diverse queries would compress differently — the query column would be larger, but the low-cardinality columns would still be near-zero. The point stands: months of query telemetry fits in surprisingly little space.</p>\n<p>For a real workload at 10K QPS, we’d expect this to work out at under $100/month in storage costs:</p>\n<div><pre><code><span>events per day:       10,000 × 86,400 = 864M</span>\n<span>raw event size:       864M × 4.6KB ≈ 4 TB/day</span>\n<span>at 36 bytes/row:      864M × 36 = ~31 GB/day</span>\n<span>monthly storage:      31 × 30 = ~930 GB/month</span>\n<span></span>\n<span>cloud block storage:  ~<span>$0</span>.08/GB/month = ~<span>$74</span>/month</span>\n<span>S3-backed cold tiers: ~<span>$0</span>.02/GB/month = ~<span>$19</span>/month</span></code></pre></div>\n<p>We think that’s pretty reasonable for a 10K QPS workload, for the level of insight it allows over the events.</p></div><div><h2 id=\"what-you-can-actually-do-with-raw-events\"></h2>\n<p>With raw events per query in ClickHouse, you can ask questions that are impossible with aggregate-only systems.
