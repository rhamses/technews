contentHtml: "<div><p>We <a target=\"_blank\" href=\"https://clickhouse.com/blog/postgres-managed-by-clickhouse\">recently launched a managed service that brings PostgreSQL and ClickHouse</a> together as a single, unified data stack. The goal is simple: let teams run transactional and analytical workloads side by side without stitching together multiple systems or maintaining complex pipelines. This launch reflects a pattern we have seen repeatedly in production. PostgreSQL remains the system of record, while ClickHouse handles analytics at scale.</p>\n<blockquote>\n<p>Start with PostgreSQL, scale with ClickHouse.</p>\n</blockquote>\n<p>In this post, we step back from the managed service and focus on its open source foundations. We show how to build the same unified data stack using open source components, how the integration works in practice, and how to offload analytics to ClickHouse without rewriting applications or rebuilding pipelines.</p>\n<h2 id=\"introducing-an-open-source-data-stack\"></h2>\n<p>The Open Source unified data stack, <a target=\"_blank\" href=\"https://github.com/ClickHouse/postgres-clickhouse-stack\">available on Github</a>, is simple and built on top of four open source components:</p>\n<ul>\n<li>\n<p><a target=\"_blank\" href=\"https://github.com/postgres/postgres\">Postgres</a> is the primary database of the data stack acting as the system of records and handling all transactional workload.</p>\n</li>\n<li>\n<p><a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse\">ClickHouse</a> is a purpose-built open source analytical database of the data stack. As data volume grows, this is the preferred database to handle analytical workload.</p>\n</li>\n<li>\n<p><a target=\"_blank\" href=\"https://github.com/PeerDB-io/peerdb\">PeerDB</a> is an open source tool to stream data from PostgreSQL to Data warehouse, including ClickHouse. It uses change data capture (CDC) to replicate inserts, updates, and deletes into ClickHouse in near real-time.</p>\n</li>\n<li>\n<p><a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_clickhouse\">pg_clickhouse</a> is an open source postgres extension that runs analytics queries on ClickHouse directly from PostgreSQL without rewriting any SQL.</p>\n</li>\n</ul>\n<p>These four components come together to form the open source unified data stack. Below is a high-level overview of the stack.</p>\n<p><span><img alt=\"postgres-oss-diagram-1.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpostgres_oss_diagram_1_e72845a9a9.jpg&w=2048&q=75\"></span></p>\n<h3 id=\"implementing-the-stack\"></h3>\n<p>Running PostgreSQL and ClickHouse side by side is a well established pattern. Many teams use this architecture in production, and GitLab <a target=\"_blank\" href=\"https://about.gitlab.com/blog/two-sizes-fit-most-postgresql-and-clickhouse/\">described it publicly</a> as early as 2022. Depending on the workload, the implementation falls into two main patterns, Change data capture or split-writes.</p>\n<h4 id=\"change-data-capture-cdc\"></h4>\n<p><strong>Components</strong>: Postgres, ClickHouse, PeerDB and pg_clickhouse (optional).</p>\n<p>This approach is well suited for operational, real-time analytical workloads where analytics run directly on application data. Common use cases include retail platforms, financial systems, and CSM or CRM applications.</p>\n<p>PostgreSQL remains the system of record. All writes go to PostgreSQL, while PeerDB streams inserts, updates, and deletes into ClickHouse using CDC. ClickHouse maintains a near real-time copy of the data, allowing analytical queries to run on the latest state without adding additional load to the transactional database.</p>\n<p>Applications can continue to send both transactional and analytical queries to PostgreSQL thanks to pg_clickhouse which transparently offloads analytical queries to ClickHouse. This keeps application changes minimal. Alternatively, applications can query ClickHouse directly if needed.</p>\n<p><strong>Customer examples</strong>:  <a target=\"_blank\" href=\"https://clickhouse.com/blog/seemplicity-scaled-real-time-security-analytics-with-postgres-cdc-and-clickhouse\">Seemplicity</a>, <a target=\"_blank\" href=\"https://clickhouse.com/blog/sewerai-sewer-management-at-scale\">Sewer AI</a></p>\n<p><span><img alt=\"postgres-oss-diagram-2.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpostgres_oss_diagram_2_9a4ab8724a.jpg&w=2048&q=75\"></span></p>\n<h3 id=\"split-writes\"></h3>\n<p><strong>Components</strong>: PostgreSQL, ClickHouse, and pg_clickhouse (optional).</p>\n<p>This pattern is commonly used for observability or event-based workloads, where analytical data consists of logs, metrics, or events. These datasets do not require transaction support and are written at high volume.</p>\n<p>In this case, analytical data can be written directly to ClickHouse, or routed through PostgreSQL using pg_clickhouse when minimal application change is preferred. PostgreSQL is not the system of record for this data and does not need to store the full analytical dataset.</p>\n<p>Querying follows the same model as the CDC approach. Analytical queries run on ClickHouse, either transparently offloaded from PostgreSQL via pg_clickhouse or issued directly to ClickHouse.</p>\n<p><strong>Customer examples</strong>: <a target=\"_blank\" href=\"https://clickhouse.com/blog/langfuse-and-clickhouse-a-new-data-stack-for-modern-llm-applications\">Langfuse</a>, <a target=\"_blank\" href=\"https://clickhouse.com/blog/langchain-why-we-choose-clickhouse-to-power-langchain\">Langchain</a></p>\n<p><span><img alt=\"postgre-oss-diagram-3.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpostgre_oss_diagram_3_4452977ed6.jpg&w=2048&q=75\"></span></p>\n<h2 id=\"get-started-locally\"></h2>\n<p>Whether you're implementing a new application or extending an existing PostgreSQL application, getting started locally is straightforward. The <a target=\"_blank\" href=\"https://github.com/ClickHouse/postgres-clickhouse-stack?tab=readme-ov-file#getting-started\">Getting started guide</a> explains how to run the stack locally. Once you have it running locally, you can simply connect your application to the <a target=\"_blank\" href=\"https://github.com/ClickHouse/postgres-clickhouse-stack?tab=readme-ov-file#connect-to-postgresql\">exposed PostgreSQL database instance</a>.</p>\n<p>At that point, it is no different than running it with your own PostgreSQL instance. You might stop here while your application is running just fine on PostgreSQL only. Then once you need to improve the analytical workload performance, it is very simple to do:</p>\n<ol>\n<li><a target=\"_blank\" href=\"https://github.com/ClickHouse/postgres-clickhouse-stack?tab=readme-ov-file#create-the-clickhouse-database\">Create a database in ClickHouse</a> for replicated tables.</li>\n<li><a target=\"_blank\" href=\"https://github.com/ClickHouse/postgres-clickhouse-stack?tab=readme-ov-file#replicate-data-from-postgresql-to-clickhouse\">Replicate data</a> from PostgreSQL using PeerDB.</li>\n<li><a target=\"_blank\" href=\"https://github.com/ClickHouse/postgres-clickhouse-stack?tab=readme-ov-file#configure-clickhouse-foreign-data-wrapper\">Configure</a> the pg_clickhouse extension.</li>\n<li>Direct queries to the pg_clickhouse tables via&#160; your <a target=\"_blank\" href=\"https://github.com/ClickHouse/postgres-clickhouse-stack?tab=readme-ov-file#configure-application-to-use-clickhouse-for-analytical-queries\">PostgreSQL connection string</a>.</li>\n</ol>\n<p>The application still relies on PostgreSQL as the primary database, making the required changes to the application code very minimal, just a new connection option. Note that you can also connect your application <a target=\"_blank\" href=\"https://github.com/ClickHouse/postgres-clickhouse-stack?tab=readme-ov-file#connect-directly-to-clickhouse\">directly to ClickHouse</a> if that works better for you.</p>\n<p>The project provides an <a target=\"_blank\" href=\"https://github.com/ClickHouse/postgres-clickhouse-stack?tab=readme-ov-file#sample-application\">end to end example</a> with a sample application that initially runs the entire workload in PostgreSQL. A script migrates the analytical workload in just a few steps.</p>\n<h2 id=\"when-to-start-with-the-stack\"></h2>\n<p>Starting with this setup makes sense when:</p>\n<ul>\n<li>PostgreSQL is your primary database</li>\n<li>Analytical queries are part of the product, not just offline reporting</li>\n<li>You expect data volume or query complexity to grow&#160;</li>\n</ul>\n<p>As growth timelines shrink, waiting to \"outgrow\" PostgreSQL often means reacting under pressure. Starting with PostgreSQL and ClickHouse together avoids a disruptive transition. But even if you adopt the stack later, PostgreSQL remains the main interface, keeping changes contained.</p>\n<h2 id=\"from-open-source-to-production-ready\"></h2>\n<p>The open source data stack provides a strong foundation, but many production environments require managed services with clear operational boundaries and predictable behavior. Running and upgrading databases, operating replication pipelines, and handling failures often become the limiting factors rather than the architecture itself.</p>\n<p>We recently <a target=\"_blank\" href=\"https://clickhouse.com/blog/postgres-managed-by-clickhouse\">launched a managed version of the unified data stack</a> that delivers the same architecture as a single, integrated experience under one ClickHouse Cloud account.</p>\n<p>Deployment, scaling, upgrades, and reliability are handled by the platform, removing the need to operate clusters or data pipelines manually. PostgreSQL by ClickHouse connects directly to ClickHouse through <a target=\"_blank\" href=\"https://clickhouse.com/cloud/clickpipes\">ClickPipes</a>, the managed alternative to PeerDB. Managed PostgreSQL also comes with the pg_clickhouse extension preinstalled and configured, allowing analytical queries to be offloaded to ClickHouse without rewriting applications.</p></div><div><h2 id=\"a-new-baseline\"></h2>\n<p>PostgreSQL and ClickHouse are not competing databases. They are complementary systems designed for different workloads.</p>\n<p>With mature CDC and query offload tooling, using both from the start no longer requires complex pipelines or duplicated application logic. PostgreSQL remains the system of record for transactions, while ClickHouse handles analytical queries efficiently as data volume and query complexity grow.</p>\n<p><strong>The default open data stack is no longer a single database. It is PostgreSQL for transactions, ClickHouse for analytics, and a clean, well-defined bridge between the two.</strong></p></div>"
