contentHtml: "<div><p>Postgres <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/extend-extensions.html\">extensions</a> add functionality that Postgres itself does not include. Examples include <a target=\"_blank\" href=\"https://postgis.net/\">PostGIS</a> for geospatial data, <a target=\"_blank\" href=\"https://github.com/pgvector/pgvector\">pgvector</a> for embeddings, and <a target=\"_blank\" href=\"https://github.com/timescale/timescaledb\">TimescaleDB</a> for time-series. Via extensions the Postgres ecosystem distributes new functionality; just <code>CREATE EXTENSION</code> to hook into Postgres internals, and thereafter the user mostly forgets about it.</p>\n<p><a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/ddl-foreign-data.html\">Foreign Data Wrapper</a> extensions, also known as “FDW”s, teach Postgres how to read (and sometimes write) data outside of Postgres. Simply declare a foreign table:</p>\n<div><pre><code><span><span>CREATE</span> <span>FOREIGN</span> <span>TABLE</span> events (...)</span>\n<span>SERVER my_clickhouse OPTIONS (<span>table</span> <span>'events'</span>);</span></code></pre></div>\n<p>Then <code>SELECT * FROM events</code> resembles a query against any other table. Internally, Postgres asks the FDW to fetch the data from elsewhere.</p>\n<p><a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_clickhouse\">pg_clickhouse</a>, the FDW we maintain, fetches data from <a target=\"_blank\" href=\"https://clickhouse.com/\">ClickHouse</a>. While people often rely on the <a target=\"_blank\" href=\"https://clickhouse.com/blog/postgres-clickhouse-oss\">unified data stack</a> — Postgres for transactional data and ClickHouse for analytics — pg_clickhouse executes SQL queries on both systems. As we worked on it for the past 6 months, we found that a single question drives most of the engineering work: how much of a query do we send across the wire as SQL versus how many rows do we drag back as data?</p>\n<p>That question encompasses the meaning of <a target=\"_blank\" href=\"https://whatisdatabase.com/optimizing-database-performance-with-pushdown-techniques\">pushdown</a>: how much work can we “push down” to the remote service? The answer seems simple: “send everything!” — the <code>WHERE</code> clause, the <code>GROUP BY</code>, the <code>LIMIT</code>. But a closer examination reveals the complexity: Some clauses we can send. Some we can almost send — if we rewrite them. Some we used to send but stopped, because they returned the wrong results. And some clauses can never be sent by any FDW, regardless of the engineering one throws at them.</p>\n<p>We’ve found the process of making these determinations highly iterative.</p>\n<p>To demonstrate, let’s examine the impact of that iteration on a single query: what gets pushed down, what doesn't, and how we continuously modified the code in response to the question.</p>\n<p>The goal is to illuminate the inner workings of an FDW for people who’ve heard of FDWs but don’t know how they work in detail. Whether you're a Postgres user curious about ClickHouse, a ClickHouse user curious about Postgres, or someone thinking about writing an FDW yourself, we hope you find this exercise edifying.</p>\n<h2 id=\"user-content-the-query-that-takes-80-ms-or-4-minutes\"></h2>\n<p>This query ranks the busiest web events in the last week for the US, UK, and DE, by country and event name. It reports volume, unique users, premium share, p95 latency, and each event’s rank by country, returning the top 100 rows overall to provide a small snapshot and avoid streaming raw events.</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>  u.country,</span>\n<span>  e.event_name,</span>\n<span>  <span>count</span>(<span>*</span>) <span>AS</span> n,</span>\n<span>  <span>count</span>(<span>DISTINCT</span> e.user_id) <span>AS</span> unique_users,</span>\n<span>  <span>count</span>(<span>*</span>) <span>FILTER</span> (<span>WHERE</span> e.properties<span>-</span><span>&gt;&gt;</span><span>'tier'</span> <span>=</span> <span>'premium'</span>) <span>AS</span> premium_count,</span>\n<span>  <span>percentile_cont</span>(<span>0.95</span>) <span>WITHIN</span> <span>GROUP</span> (<span>ORDER</span> <span>BY</span> e.duration_ms) <span>AS</span> p95_ms,</span>\n<span>  <span>ROW_NUMBER</span>() <span>OVER</span> (<span>PARTITION</span> <span>BY</span> u.country <span>ORDER</span> <span>BY</span> <span>count</span>(<span>*</span>) <span>DESC</span>) <span>AS</span> rank_in_country</span>\n<span><span>FROM</span> events_ch e <span>JOIN</span> users_ch u <span>USING</span> (user_id)</span>\n<span><span>WHERE</span> e.ts <span>&gt;=</span> now() <span>-</span> <span>interval</span> <span>'7 days'</span></span>\n<span>  <span>AND</span> u.country <span>IN</span> (<span>'US'</span>, <span>'UK'</span>, <span>'DE'</span>)</span>\n<span>  <span>AND</span> e.properties<span>-</span><span>&gt;&gt;</span><span>'platform'</span> <span>=</span> <span>'web'</span></span>\n<span><span>GROUP</span> <span>BY</span> u.country, e.event_name</span>\n<span><span>ORDER</span> <span>BY</span> n <span>DESC</span></span>\n<span>LIMIT <span>100</span>;</span></code></pre></div>\n<p><code>events_ch</code> and <code>users_ch</code> are foreign tables backed by ClickHouse. With every clause in this query pushed down, it returns 100 rows in roughly 80 ms.</p>\n<p>If a single clause fails to push down, the query takes minutes. We built support for pushing down the window function, the percentile, the JSON access, and the FILTER aggregate; but each was, at some earlier point, not yet pushed down. When an operation cannot be pushed down, the rest of the query can't push down either; rows that should have been aggregated remotely must stream back to Postgres so it can aggregate them locally. The wire ends up carrying tens to hundreds of millions of rows instead of 100.</p>\n<p>Pushdown looks like a feature, but it’s really an agreement between two SQL grammars, revised for every Postgres release. This explains why the pg_clickhouse release notes often look like corrections: revoking incorrect array-function pushdown, adding safer functions like <code>levenshtein</code> and <code>soundex</code>, and respecting planner invariants like <a target=\"_blank\" href=\"https://github.com/postgres/postgres/blob/901ed9b/src/backend/executor/execMain.c#L2649-L2676\">EvalPlanQual</a> even when the remote could move faster.</p>\n<h2 id=\"user-content-2-what-the-fdw-actually-negotiates\"></h2>\n<p>An FDW does not send the original Postgres query to the remote database; doing so causes errors where the SQL dialects differ. But ideally, It also does not pull every row back unless it has to (as simple FDWs like <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/file-fdw.html\">file_fdw</a> do), because although the results would be correct, execution would be slow.</p>\n<p><span><img alt=\"Diagram showing how a Foreign Data Wrapper sits between an application and a remote database, forwarding SQL queries and returning data rows\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F2026_05_14_12_09_23_7401c62d71.png&w=2048&q=75\"></span></p>\n<p>Postgres does not directly decide that a scan, join, aggregate, sort, or limit can be executed in ClickHouse. Instead, it asks the FDW to contribute foreign paths to the planner via the FDW planning callbacks. pg_clickhouse registers these planning callbacks:</p>\n<div><pre><code><span>routine-&gt;GetForeignRelSize    = clickhouseGetForeignRelSize;</span>\n<span>routine-&gt;GetForeignPaths      = clickhouseGetForeignPaths;</span>\n<span>routine-&gt;GetForeignPlan       = clickhouseGetForeignPlan;</span>\n<span>routine-&gt;GetForeignJoinPaths  = clickhouseGetForeignJoinPaths;</span>\n<span>routine-&gt;GetForeignUpperPaths = clickhouseGetForeignUpperPaths;</span></code></pre></div>\n<p><code>GetForeignPaths</code>, <code>GetForeignJoinPaths</code>, and <code>GetForeignUpperPaths</code> tell the planner what can be pushed down. If the planner selects one of those paths, <code>GetForeignPlan</code> builds the plan and generates the ClickHouse SQL.</p>\n<p>These callbacks are just entry points; pg_clickhouse’s callback functions verify that each clause or expression can be translated without changing the result. Of course it started out quite simple: just a few clauses and expressions inherited from the original fork from <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/postgres-fdw.html\">postgres_fdw</a>. Thus pg_clickhouse initially pushed down <code>count(*)</code> but not <code>count(*) FILTER (...)</code>, couldn’t push down <code>percentile_cont</code> or JSON predicates like <code>properties-&gt;&gt;'platform'</code>: because it did not know how.</p>\n<p>Thus, pushdown is not a yes/no decision for a whole query, but constitutes a series of smaller decisions: does Postgres expose the hook, can pg_clickhouse translate the expression, and can ClickHouse execute it with the same meaning?</p>\n<h2 id=\"user-content-3-the-progression-one-query-every-step-weve-shipped\"></h2>\n<p>To answer the question, \"why doesn’t X push down?\" let’s look at one realistic query and walk it through everything pg_clickhouse has shipped. Same query, seven steps. Each step pushes down more to ClickHouse; Postgres must evaluate what remains after pulling back the rows it needs to do so.</p>\n<p>Each step examines the same query. Lines marked ✓ push down at that step; lines marked ✗ remain local. Each step also marks a real date in our history, when the relevant pushdown landed in the codebase, or when we expect to ship it. Each step demonstrates what the query plan looked like as of that date.</p>\n<h3 id=\"user-content-step-1-scan-simple-where\"></h3>\n<p>Inherited from the original clickhouse_fdw via initial port <a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_clickhouse/commit/e5035bc\"><code>e5035bc</code></a> (October 2, 2025). Available in pg_clickhouse since v0.1.0 (December 9, 2025).</p>\n<p>The starting point is deliberately small: pg_clickhouse only pushes down predicates it can translate with confidence. Comparisons like <code>&gt;=</code>, membership checks like <code>IN</code>, and simple timestamp arithmetic are safe to push down because Postgres and ClickHouse have clear equivalents for them. In other words, those filters run in ClickHouse rather than collecting all the rows to evaluate in Postgres.</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>  u.country, The SQL translator (internally called a “deparser”) emits one remote scan for <code>events</code> with the timestamp predicate, and one remote scan for <code>users</code> with the country predicate. It sends these two separate queries to ClickHouse and collects the results. Everything that combines rows or changes their shape, including the join, grouping, aggregates, window function, sort, and limit, runs inside Postgres against those retrieved rows. Thus the wire must carry every matching <code>events</code> row from the last seven days, plus every matching <code>users</code> row, before Postgres can reduce the result to 100 rows.</p>\n<p>The point is that even the simplest pushdown is already a translation problem: <code>now()</code> can be pushed down as <code>now()</code>, while <code>interval '7 days'</code> is translated as <code>7 * 86400</code>. Those mappings live in <a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_clickhouse/blob/main/src/custom_types.c\">src/custom_types.c</a>, where pg_clickhouse records the expressions it knows how to translate safely for ClickHouse. The steps outlined below expand that vocabulary from base filters to joins, aggregates, windows, and limits.</p>\n<h3 id=\"user-content-step-2-join-pushdown\"></h3>\n<p>Inner-JOIN deparse came from the original clickhouse_fdw, but the inherited cost estimates were placeholders, and the Postgres planner often pulled rows back to join locally rather than push. Commit <a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_clickhouse/commit/b345682\"><code>b345682</code></a> (December 1, 2025) replaced them with row-count-based estimates and cost-based scans higher than join paths, so the planner reliably picks the pushed plan. Plus <a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_clickhouse/commit/6a297ec\"><code>6a297ec</code></a> (Nov 13, 2025) for <code>join_use_nulls</code> outer-join semantics. All shipped in v0.1.0 (December 9, 2025).</p>\n<p>At this step pg_clickhouse stops treating <code>events_ch</code> and <code>users_ch</code> as two independent remote scans. Since both tables live on the same ClickHouse server and the join condition has a ClickHouse equivalent, the FDW can ask ClickHouse to make the join before any joined rows cross the wire.</p>\n<div><pre><code><span><span>SELECT</span> ...                                                         <span>-- ✗ (still)</span></span>\n<span><span>FROM</span> events_ch e                                                   <span>-- ✓</span></span>\n<span>  <span>JOIN</span> users_ch u <span>USING</span> (user_id)                                  <span>-- ✓ joins push</span></span>\n<span><span>WHERE</span> e.ts <span>&gt;=</span> now() <span>-</span> <span>interval</span> <span>'7 days'</span>                            <span>-- ✓</span></span>\n<span>  <span>AND</span> u.country <span>IN</span> (<span>'US'</span>,<span>'UK'</span>,<span>'DE'</span>)                                <span>-- ✓</span></span>\n<span>  <span>AND</span> e.properties<span>-</span><span>&gt;&gt;</span><span>'platform'</span> <span>=</span> <span>'web'</span>                            <span>-- ✗ stays local</span></span>\n<span><span>GROUP</span> <span>BY</span> u.country, e.event_name                                   <span>-- ✗</span></span>\n<span><span>ORDER</span> <span>BY</span> n <span>DESC</span>                                                    <span>-- ✗</span></span>\n<span>LIMIT <span>100</span>                                                          <span>-- ✗</span></span></code></pre></div>\n<p>The remote SQL is now roughly <code>SELECT * FROM events ALL INNER JOIN users USING (user_id) WHERE …</code>. The <code>ALL</code> keyword is deliberate: ClickHouse's default join can return only one matching row, while a Postgres inner join returns all matches. Emitting <code>ALL INNER JOIN</code> preserves Postgres semantics. The JSON predicate still cannot be translated at this point, so it is left out of the remote <code>WHERE</code> and applied locally to the returned rows.</p>\n<p>Postgres enabled this kind of join pushdown in 9.6 (commit <a target=\"_blank\" href=\"https://github.com/postgres/postgres/commit/e4106b25287\"><code>e4106b25287</code></a>, 2016, Etsuro Fujita). Previously, FDWs had to hook deeper into the planner to accomplish join pushdown.</p>\n<p>For our query, this single step reduces query time from roughly 30 minutes to 30 seconds, because the join filters rows before they leave the remote.</p>\n<h3 id=\"user-content-step-3-group-by-simple-aggregates-order-by-limit\"></h3>\n<p>Also inherited via <a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_clickhouse/commit/e5035bc\"><code>e5035bc</code></a>. GROUP BY, basic aggregates (<code>count</code>, <code>sum</code>, <code>min</code>, <code>max</code>, <code>avg</code>), ORDER BY, and LIMIT all pushdown since v0.1.0 (December 9, 2025).</p>\n<p>This step emphasizes result-shaping work: grouping rows, computing basic aggregates, sorting the grouped result, and applying the final limit. Postgres exposes these operations as “upper” planning stages, and the FDW can offer a remote version of each stage when the whole stage can be represented in ClickHouse. Aggregate pushdown arrived in Postgres 10 (commit <a target=\"_blank\" href=\"https://github.com/postgres/postgres/commit/7012b132d07\"><code>7012b132d07</code></a>); ORDER BY and LIMIT pushdown followed in Postgres 12.</p>\n<p>Still, at this point pg_clickhouse cannot push down all of the operations: The grouping stage must encompass the entire SELECT list, and it hasn’t been wired to push down three expressions:</p>\n<ul>\n<li><code>count(*) FILTER (WHERE e.properties-&gt;&gt;'tier' = 'premium')</code>: the FILTER body contains a JSON op without a pushdown mapping</li>\n<li><code>percentile_cont(...) WITHIN GROUP (ORDER BY ...)</code>: ClickHouse has an equivalent function, but pg_clickhouse hasn’t mapped it</li>\n<li><code>ROW_NUMBER() OVER (...)</code>: window functions have not been mapped to ClickHouse equivalents at all</li>\n</ul>\n<p>Note that grouped pushdown is all-or-nothing for a given grouped result. So even though <code>count(*)</code>, <code>count(DISTINCT)</code>, <code>GROUP BY</code>, <code>ORDER BY</code>, and <code>LIMIT</code> are individually fine, the grouped part of this particular The full, richer query needs three more steps to fully land.</p>\n<h3 id=\"user-content-step-4-ordered-set-aggregates\"></h3>\n<p>Commit <a target=\"_blank\" href=\"https://github.com/ClickHouse/pg_clickhouse/commit/087cfdc\"><code>087cfdc</code></a> (November 10, 2025), in v0.1.0. Previously, <code>percentile_cont</code> blocked the upper rel for any query that used it.</p>\n<p>This step teaches pg_clickhouse one more aggregate translation: Postgres <code>percentile_cont(p) WITHIN GROUP (ORDER BY x)</code> can be expressed as ClickHouse <code>quantile(p)(x)</code>. This change removes the percentile from the list of blockers. The allow list remains narrow: for example, pg_clickhouse still refuses <code>string_agg(... ORDER BY ...)</code> because ClickHouse's closest equivalent does not preserve the same within-group ordering semantics.</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>  ...                                             <span>-- ✗ still blocked</span></span>\n<span>  <span>percentile_cont</span>(...) <span>AS</span> p95_ms,                 <span>-- ✓ now shippable</span></span>\n<span>  <span>ROW_NUMBER</span>() <span>OVER</span> (...) <span>AS</span> rank_in_country      <span>-- ✗ window not remote yet</span></span>\n<span><span>FROM</span> ...                                          <span>-- (everything else unchanged from Step 2-3)</span></span></code></pre></div>\n<p>The <code>percentile_cont</code> function becoming individually shippable is necessary but not sufficient. Walking the query through that history surfaces a few facts that a simple list of changes does not, to whit:</p>\n<ul>\n<li>Pushdown is granular.&#160;Each clause must be independently negotiated. A clause that looks \"obvious\" can fail to push down because of a single sub-expression: <code>count(*) FILTER (WHERE json_op)</code>&#160;waits on the JSON op even though count and FILTER are individually fine.</li>\n<li>Pushdown is all-or-nothing at the upper-rel level. A grouped query can only be pushed down if the whole grouped relation can be represented safely in ClickHouse SQL. One unsupported aggregate or sub-expression can block the entire grouped plan. Put another way, adding support for a small missing translation can unlock pushdown for the full query.</li>\n<li>Most \"improvements\" are translations, not new features.&#160;<code>percentile_cont</code>, <code>ROW_NUMBER</code>, <code>-&gt;&gt;</code>. Postgres has them, ClickHouse has them. What was missing was the deparser code connecting the two grammars. In our v0.2.0 we revoked pushdown for <code>array_dims</code>, <code>array_lower</code>&#160;and friends. Inside an FDW, it’s a contract. Postgres has to expose the right planner hook, pg_clickhouse has to translate the expression without changing its meaning, and ClickHouse has to support the same semantics. If any part of that chain is missing, the safe answer is to keep the work local or to fail loudly.</p>\n<p>Hence FDW work often looks incremental from the outside. JSON sub-columns, percentile_cont, filtered aggregates, window functions, join semantics, DML support: each represents a small agreement between two SQL systems. But once the last blocker to pushdown lifts, the effect is not small. A query that used to stream millions of rows into Postgres can collapse into a single ClickHouse SELECT that returns 100 rows.</p>\n<p>Pushdown is not a race to ship every clause remotely. Some translations are added. Some are revoked. Some wait on Postgres planner support. Some wait on ClickHouse engine behavior. And some should never be pushed at all, because the remote system cannot honestly promise the same answer Postgres would produce.</p>\n<p>The work is not to make ClickHouse pretend to be Postgres. The work is to decide, clause by clause, where the two systems can agree.</p>\n<p>Every byte kept off the wire is a byte that all three parties have agreed to omit.</p></div>"
