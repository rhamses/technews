No drilling down, no cross-referencing, no holding multiple tabs in your head at once.</p>\n<h3 id=\"user-content-slow-patterns\"></h3>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpg_query_insights_may2026_image2_b916e3ce03.png&w=2048&q=75\"></span></p>\n<p>When the overview points at trouble, the patterns table is where the investigation starts. One row per query pattern your database has run, sorted by whatever you suspect:</p>\n<ul>\n<li>total runtime</li>\n<li>total CPU</li>\n<li>error count</li>\n<li>max latency</li>\n<li>P95</li>\n</ul>\n<p>When you sort by <strong>total duration</strong>, the top pattern is usually the answer to \"what is costing me the most?\" It may not be the slowest pattern individually. A query that runs eight million times a day at twelve milliseconds can matter more than one that ran once at three seconds.</p>\n<p>Each sort gives you a different lens. <strong>Total CPU</strong> shows compute-heavy patterns. <strong>Error count</strong> surfaces repeated failures. <strong>P95</strong> catches the worst outliers. Together, they turn a broad sign of trouble into a specific place to start.</p>\n<p>Narrow the table to whichever slice of your workload you're investigating, by:</p>\n<ul>\n<li>database</li>\n<li>application name</li>\n<li>operation type</li>\n<li>user</li>\n</ul>\n<p><em>\"Show me only what the orders service is doing on the sales db.\"</em></p>\n<h3 id=\"user-content-detail\"></h3>\n<p><span><img alt=\"2026-05-07_11-52-56.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2F2026_05_07_11_52_56_f30d449327.png&w=2048&q=75\"></span></p>\n<p>Click into a pattern's row and the flyout opens. This is where investigations <em>land</em>.</p>\n<p>The flyout takes every execution of the pattern over your time range and aggregates the counters that explain why it's slow:</p>\n<ul>\n<li>percentile latencies (p95/p99)</li>\n<li>where the time went, by CPU</li>\n<li>what got read from cache versus disk</li>\n<li>what spilled to temp (blocks read)</li>\n<li>where parallel workers should have launched and didn't</li>\n<li>where the WAL volume came from</li>\n</ul>\n<p>Everything you need to diagnose a slow pattern is in one place, in one glance.</p>\n<h2 id=\"user-content-a-latency-regression-end-to-end\"></h2>\n<p>Here's a concrete walkthrough. You run a managed Postgres instance backing a sales orders dashboard. Over the past week, p99 latency on the dashboard's main endpoint has been creeping up. p50 is fine. Users are occasionally reporting slow queries and query timeouts. You open Query Insights to find out which query is responsible.</p>\n<p><strong>1. Open the tab.</strong></p>\n<p>You land on the instance, click <strong>Query insights</strong>. The stats grid: query volume flat, error rate flat, cache hit ratio at 99.4%. Nothing alarming at first glance.</p>\n<p><strong>2. Switch the chart metric.</strong></p>\n<p>The default chart is <code>query_count</code>. You switch it to <code>p99_duration</code>. The line slopes up over the week. p50 stays flat. The regression is real and it's on the tail.</p>\n<p><strong>3. Find the slow pattern.</strong></p>\n<p>You sort the patterns table by <strong>Total Duration</strong> or <strong>P99</strong> or <strong>Avg Duration</strong> descending. The top row:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> </span>\n<span><span>FROM</span> orders </span>\n<span><span>JOIN</span> customers <span>ON</span> orders.customer_id <span>=</span> customers.id</span>\n<span><span>WHERE</span> orders.status <span>=</span> $<span>1</span> </span>\n<span><span>ORDER</span> <span>BY</span> orders.created_at <span>DESC</span> </span>\n<span>LIMIT $<span>2</span>;</span></code></pre></div>\n<p><strong>4. Open the pattern flyout.</strong></p>\n<ul>\n<li>Average latency is healthy, in the single-digit milliseconds</li>\n<li>p99 is in the hundreds of milliseconds (the tail is the actual problem)</li>\n<li>cache hit ratio is near 100%, so the bottleneck isn't shared buffer I/O</li>\n<li>WAL bytes are zero, as expected for a read-only query</li>\n</ul>\n<p>Drilling into recent executions in the flyout:</p>\n<ul>\n<li><code>Temp block ops</code> is non-zero (the sort is spilling to disk)</li>\n<li><code>Parallel workers launched</code> is well below <code>parallel workers planned</code></li>\n</ul>\n<p>That combination matters. It is not a write problem. It is not a buffer-pool problem. The query is spilling while sorting, and the spill is what's pushing the tail.</p>\n<p><strong>5. Fix.</strong></p>\n<p>Once the spill is identified, the next step is to confirm it with <code>EXPLAIN (ANALYZE, BUFFERS)</code>. The plan will show the Sort node marked as spilling to disk, along with how much memory the sort actually consumed during execution. You'll see <code>Sort Method: external merge  Disk: NkB</code> where a healthy plan would have shown <code>Sort Method: quicksort  Memory: NkB</code>. The Disk figure tells you how much temp file the sort wrote. Compare it to your configured <code>work_mem</code>: a small overshoot is a tuning problem, a large multiple is a plan-shape problem.</p>\n<p>From there the fix is clear: add an index that supports the filter and ordering so Postgres can avoid the sort entirely, increase <code>work_mem</code> for the right role or session so the sort has enough room to run in memory, or both. Query Insights points you at the pattern; EXPLAIN ANALYZE tells you what to do about it.</p>\n<h2 id=\"user-content-healthy-instance\"></h2>\n<p>After applying the fix, the difference shows up immediately in Query Insights. The spill disappears from the pattern's detail, parallel workers launch as planned, and the p99 comes back down to match the p50. The overview confirms it: cache hit ratio steady, no new errors, latency flat across the board. The instance is healthy again.</p>\n<p>A healthy instance has a familiar shape. Cache hit ratio sits in the high nineties. Query volume moves with your application traffic, not against it. Error rate stays flat or zero. The patterns table has no single dominant offender: total duration is spread across many patterns, none of them pulling far ahead of the rest. Latency percentiles track each other closely, with p99 staying within a reasonable multiple of p50. When everything looks like this, Query Insights is quiet in the best possible way.</p>\n<h2 id=\"user-content-how-its-built\"></h2>\n<p>A few design choices behind the product:</p>\n<p><strong>We use the same engine our customers do.</strong> The Insights backend is ClickHouse Cloud — the fastest way we know to store and query data at this shape and volume. Per-query telemetry from a busy Postgres instance is millions of rows a day. ClickHouse ingests from many producers, columnar compression that keeps months of per-execution detail cheap to retain, and sub-second aggregations over billions of rows. The UI stays interactive when you're slicing across a week or a month of every executed statement on a busy database: percentile recomputes, ranking resorts, filter changes are very fast.</p>\n<p><strong>Normalized in Postgres, before the wire.</strong> We hook the parse-analyze phase, the moment after Postgres parses a statement and identifies the location of every literal in the query text. We swap each literal for a placeholder (<code>$1</code>, <code>$2</code>, …) and cache the resulting pattern in a per-backend LRU keyed by queryid. When the executor finishes the statement, that cached pattern is what gets attached to the event before it's enqueued. The exact statement with values never leaves the database. <strong>PII and PHI are not in the telemetry stream by design.</strong></p>\n<p><strong>Out of the way of the database.</strong> ~3% producer overhead per statement: enqueue path uses a non-blocking try-lock on a shared-memory ring buffer. If the lock is contended, the producer queues locally and flushes at transaction end rather than spinning or blocking. Under pressure, the extension drops events with a counter rather than back-pressuring Postgres. The first rule of telemetry: never become the bottleneck you were trying to measure.</p>\n<p><strong>Open source.</strong> <a target=\"_blank\" href=\"https://github.com/clickhouse/pg_stat_ch\">pg_stat_ch</a> is Apache 2.0 License. Run it against any Postgres, ship to any ClickHouse.</p>\n<p><strong>Raw events, not aggregates.</strong> pg_stat_ch emits one raw event per executed statement (top-level and nested), subject to sampling. Every percentile, ranking, and breakdown in the UI is a ClickHouse query against the same event stream.</p>\n<h2 id=\"user-content-whats-next\"></h2>\n<p>Some of what we're working on next: an <strong>Open API</strong> exposing the same data the UI runs which is purpose-built for the agentic era. The goal is to keep this configurable to manage load on the database, for example, enabling <code>ANALYZE</code> without <code>BUFFERS</code>, or setting query latency thresholds for plan collection.</p>\n<p>On top of this data, we plan to provide actionable recommendations such as index hints, <code>work_mem</code> tuning suggestions, and autovacuum guidance to reduce the cognitive load of figuring out \"what to do next.\" We also want to add regression alerts for cases like p99 latency doubling, new top offenders emerging, or error counts crossing defined thresholds.</p>\n<h2 id=\"user-content-try-it\"></h2>\n<p>Try Query Insights by signing up for ClickHouse Cloud and provisioning a Postgres service.
