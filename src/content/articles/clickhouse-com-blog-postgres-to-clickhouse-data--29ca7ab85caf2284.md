CDC continuously tracks inserts, updates, and deletes in Postgres and replicates them to ClickHouse, enabling real-time analytics.</p>\n<p>You can implement Postgres CDC to ClickHouse using <a target=\"_blank\" href=\"https://github.com/PeerDB-io/peerdb\">PeerDB</a>, an open-source replication tool, or leverage a fully integrated experience in ClickHouse Cloud with <a target=\"_blank\" href=\"https://clickhouse.com/docs/integrations/clickpipes/postgres\">ClickPipes</a>. <strong>Since Postgres and ClickHouse are different databases, an important aspect alongside replication is effectively modeling tables and queries in ClickHouse to maximize performance.</strong></p>\n<p>This blog takes a deep dive into how Postgres CDC to ClickHouse works internally and delves into best practices for data modeling and query tuning. <strong>We will cover topics such as data deduplication strategies, handling custom ordering keys, optimizing JOINs, materialized views (MVs) including refreshable MVs, denormalization, and more.</strong> You can also apply these learnings to one-time migrations (not CDC) from Postgres, so we expect this to help any Postgres users looking to use ClickHouse for analytics. We published a <a target=\"_blank\" href=\"https://clickhouse.com/blog/postgres-to-clickhouse-data-modeling-tips\">v1</a> of this blog late last year; this one will be an advanced version of that blog.</p>\n<h4 id=\"dataset\"></h4>\n<p>Throughout this blog post, we will illustrate the strategies using a real-world dataset, specifically a subset of the well-known StackOverflow dataset, which we will load into PostgreSQL. This dataset is used across ClickHouse documentation, and you can find more information about it <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/stackoverflow\">here</a>. We also implemented a Python script that simulates user activity on StackOverflow. Instructions on how to reproduce the experiments can be found on <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/postgresql-clickhouse-data-modeling\">GitHub</a>.</p>\n<h2 id=\"how-does-data-get-replicated\"></h2>\n<h3 id=\"postgresql-logical-decoding\"></h3>\n<p>ClickPipes and PeerDB use <a target=\"_blank\" href=\"https://www.pgedge.com/blog/logical-replication-evolution-in-chronological-order-clustering-solution-built-around-logical-replication\">Postgres Logical Decoding</a> to consume changes as they happen in Postgres. The Logical Decoding process in Postgres enables clients like ClickPipes to receive changes in a human-readable format, i.e., a series of INSERTs, UPDATEs, and DELETEs. To learn more about how Logical Decoding works, you can read one of our <a target=\"_blank\" href=\"https://www.pgedge.com/blog/logical-replication-evolution-in-chronological-order-clustering-solution-built-around-logical-replication\">blogs</a> that goes into full detail.</p>\n<p>As part of the replication process, ClickPipes automatically creates corresponding tables with the most <a target=\"_blank\" href=\"https://docs.peerdb.io/datatypes/datatype-matrix\">native data-type mapping</a> in ClickHouse and performs initial snapshots/backfills super <a target=\"_blank\" href=\"https://blog.peerdb.io/parallelized-initial-load-for-cdc-based-streaming-from-postgres#heading-parallelized-initial-snapshot-for-cdc-based-streaming\">efficiently</a>.</p>\n<h3 id=\"replacingmergetree\"></h3>\n<p>ClickPipes maps Postgres tables to ClickHouse using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/mergetree-family/replacingmergetree\">ReplacingMergeTree</a> engine. ClickHouse performs best with append-only workloads and <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/developer/mutations\">does not recommend</a> frequent UPDATEs. This is where ReplacingMergeTree is particularly powerful.</p>\n<p>With ReplacingMergeTree, updates are modeled as inserts with a newer version (<code>_peerdb_version</code>) of the row, while deletes are inserts with a newer version and <code>_peerdb_is_deleted</code> marked as true. The ReplacingMergeTree engine in background deduplicates/merges data and retains the latest version of the row for a given primary key (id), enabling efficient handling of UPDATEs and DELETEs as versioned inserts.</p>\n<p>Below is an example of a CREATE Table statement executed by ClickPipes to create the table in ClickHouse.</p>\n<div><pre><code><span><span>CREATE TABLE</span> users</span>\n<span>(</span>\n<span>    `id` Int32,</span>\n<span>    `reputation` String,</span>\n<span>    `creationdate` DateTime64(<span>6</span>),</span>\n<span>    `displayname` String,</span>\n<span>    `lastaccessdate` DateTime64(<span>6</span>),</span>\n<span>    `aboutme` String,</span>\n<span>    `views` Int32,</span>\n<span>    `upvotes` Int32,</span>\n<span>    `downvotes` Int32,</span>\n<span>    `websiteurl` String,</span>\n<span>    `location` String,</span>\n<span>    `accountid` Int32,</span>\n<span>    `_peerdb_synced_at` DateTime64(<span>9</span>) <span>DEFAULT</span> now64(),</span>\n<span>    `_peerdb_is_deleted` Int8,</span>\n<span>    `_peerdb_version` Int64</span>\n<span>)</span>\n<span>ENGINE <span>=</span> ReplacingMergeTree(_peerdb_version)</span>\n<span><span>PRIMARY KEY</span> id</span>\n<span><span>ORDER</span> <span>BY</span> id;</span></code></pre></div>\n<h3 id=\"illustrative-example\"></h3>\n<p>The illustration below walks through a basic example of synchronization of a table <code>users</code> between PostgreSQL and ClickHouse using ClickPipes.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpostgres_cdc_data_modelling_004_d06ef24091.png&w=2048&q=75\"></span></p><p><strong>Step 1</strong> shows the initial snapshot of the 2 rows in PostgreSQL and ClickPipes performing the initial load of those 2 rows to ClickHouse. If you observe, both rows are copied as-is to ClickHouse.</p>\n<p><strong>Step 2</strong> shows three operations on the users table: inserting a new row, updating an existing row, and deleting another row.</p>\n<p><strong>Step 3</strong> shows how ClickPipes replicates the INSERT, UPDATE, and DELETE operations to ClickHouse as versioned inserts. The UPDATE appears as a new version of the row with ID 2, while the DELETE appears as a new version of ID 1 with is _deleted marked as true. Because of this, ClickHouse has three additional rows compared to PostgreSQL.</p>\n<p>As a result, running a simple query like <code>SELECT count(*) FROM users;</code> may produce different results in ClickHouse and PostgreSQL. According to the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/merges#replacing-merges\">ClickHouse merge documentation</a>, outdated row versions are eventually discarded during the merge process. However, the timing of this merge is unpredictable, meaning queries in ClickHouse may return inconsistent results until it occurs.</p>\n<p>How can we ensure identical query results in both ClickHouse and PostgreSQL?</p>\n<h2 id=\"deduplication-strategy\"></h2>\n<p>This section discusses various approaches to ensuring your queries in ClickHouse produce results consistent with PostgreSQL.</p>\n<h3 id=\"default-approach-use-final-keyword\"></h3>\n<p>The recommended way to deduplicate data in ClickHouse queries is to use the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/select/from#final-modifier\">FINAL modifier.</a> This ensures only the deduplicated rows are returned, which is ideal for ClickHouse tables synced via Postgres CDC. Add FINAL to your query.</p>\n<p>FINAL adds some overhead to your queries. However, ClickHouse remains fast. FINAL performance has been significantly improved over multiple releases (<a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/73132\">#73132</a>, <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/73682\">#73682</a>, <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/58120\">#58120</a>, <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/47915\">#47915</a>).&#160;</p>\n<p>Let's look at how to apply it to three different queries.</p>\n<p><em>Note in the following queries the WHERE clause to filter out deleted rows.</em></p>\n<ul>\n<li><strong>Simple count query</strong>: Count the number of posts.</li>\n</ul>\n<p>This is the simplest query you can run to check if the synchronization went fine. The two queries should return the same count.</p>\n<div><pre><code><span><span>-- PostgreSQL </span></span>\n<span><span>SELECT</span> <span>count</span>(<span>*</span>) <span>FROM</span> posts;</span>\n<span></span>\n<span><span>-- ClickHouse </span></span>\n<span><span>SELECT</span> <span>count</span>(<span>*</span>) <span>FROM</span> posts <span>FINAL</span> <span>where</span> _peerdb_is_deleted<span>=</span><span>0</span>;</span></code></pre></div>\n<ul>\n<li><strong>Simple aggregation with JOIN</strong>: Top 10 users who cumulate the most number of views.</li>\n</ul>\n<p>An example of an aggregation on a single table. Having duplicates here would greatly affect the result of the sum function.</p>\n<div><pre><code><span><span>-- PostgreSQL </span></span>\n<span><span>SELECT</span></span>\n<span>    <span>sum</span>(p.viewcount) <span>AS</span> viewcount,</span>\n<span>    p.owneruserid <span>as</span> user_id,</span>\n<span>    u.displayname <span>as</span> display_name</span>\n<span><span>FROM</span> posts p</span>\n<span><span>LEFT</span> <span>JOIN</span> users u <span>ON</span> u.id <span>=</span> p.owneruserid</span>\n<span><span>WHERE</span> p.owneruserid <span>&gt;</span> <span>0</span></span>\n<span><span>GROUP</span> <span>BY</span> user_id, display_name</span>\n<span><span>ORDER</span> <span>BY</span> viewcount <span>DESC</span></span>\n<span>LIMIT <span>10</span>;</span>\n<span></span>\n<span><span>-- ClickHouse </span></span>\n<span><span>SELECT</span></span>\n<span>    <span>sum</span>(p.viewcount) <span>AS</span> viewcount,</span>\n<span>    p.owneruserid <span>AS</span> user_id,</span>\n<span>    u.displayname <span>AS</span> display_name</span>\n<span><span>FROM</span> posts <span>AS</span> p</span>\n<span><span>FINAL</span></span>\n<span><span>LEFT</span> <span>JOIN</span> users <span>AS</span> u</span>\n<span><span>FINAL</span> <span>ON</span> (u.id <span>=</span> p.owneruserid) <span>AND</span> (u._peerdb_is_deleted <span>=</span> <span>0</span>)</span>\n<span><span>WHERE</span> (p.owneruserid <span>&gt;</span> <span>0</span>) <span>AND</span> (p._peerdb_is_deleted <span>=</span> <span>0</span>)</span>\n<span><span>GROUP</span> <span>BY</span></span>\n<span>    user_id,</span>\n<span>    display_name</span>\n<span><span>ORDER</span> <span>BY</span> viewcount <span>DESC</span></span>\n<span>LIMIT <span>10</span></span></code></pre></div>\n<h4 id=\"final-setting\"></h4>\n<p>Rather than adding the FINAL modifier to each table name in the query, you can use the <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#final\">FINAL setting</a> to apply it automatically to all tables in the query.</p>\n<p>This setting can be applied either per query or for an entire session.</p>\n<div><pre><code><span><span>-- Per query FINAL setting</span></span>\n<span><span>SELECT</span> <span>count</span>(<span>*</span>) <span>FROM</span> posts SETTINGS <span>final</span> <span>=</span> <span>1</span>;</span>\n<span></span>\n<span><span>-- Set FINAL for the session</span></span>\n<span><span>SET</span> <span>final</span> <span>=</span> <span>1</span>;</span>\n<span><span>SELECT</span> <span>count</span>(<span>*</span>) <span>FROM</span> posts;</span></code></pre></div>\n<h4 id=\"row-policy\"></h4>\n<p>An easy way to hide the redundant <code>_peerdb_is_deleted = 0</code> filter is to use <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/access-rights#row-policy-management\">ROW policy.</a> Below is an example that creates a row policy to exclude the deleted rows from all queries on the table votes.</p>\n<div><pre><code><span><span>-- Apply row policy to all users</span></span>\n<span><span>CREATE</span> <span>ROW</span> POLICY cdc_policy <span>ON</span> votes <span>FOR</span> <span>SELECT</span> <span>USING</span> _peerdb_is_deleted <span>=</span> <span>0</span> <span>TO</span> <span>ALL</span>;</span></code></pre></div>\n<blockquote>\n<p>Row policies are applied to a list of users and roles. We apply it to all users and roles, but depending on your environment, you should apply it only to specific users or roles.</p>\n</blockquote>\n<h3 id=\"query-like-postgres----minimize-migration-effort\"></h3>\n<p>Migrating an analytical dataset from PostgreSQL to ClickHouse often requires modifying application queries to account for differences in data handling and query execution. As mentioned in the previous section, PostgreSQL queries may need adjustments to ensure proper data deduplication in ClickHouse.</p>\n<p>This section will explore techniques for deduplicating data while keeping the original queries unchanged.</p>\n<h4 id=\"views\"></h4>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/create/view#normal-view\">Views</a> are a great way to hide the FINAL keyword from the query, as they do not store any data and simply perform a read from another table on each access.</p>\n<p>Below is an example of creating views for each table of our database in ClickHouse with the FINAL keyword and filter for the deleted rows.</p>\n<div><pre><code><span><span>CREATE</span> <span>VIEW</span> posts_view <span>AS</span> <span>SELECT</span> <span>*</span> <span>FROM</span> posts <span>FINAL</span> <span>where</span> _peerdb_is_deleted<span>=</span><span>0</span>;</span>\n<span><span>CREATE</span> <span>VIEW</span> users_view <span>AS</span> <span>SELECT</span> <span>*</span> <span>FROM</span> users <span>FINAL</span> <span>where</span> _peerdb_is_deleted<span>=</span><span>0</span>;</span>\n<span><span>CREATE</span> <span>VIEW</span> votes_view <span>AS</span> <span>SELECT</span> <span>*</span> <span>FROM</span> votes <span>FINAL</span> <span>where</span> _peerdb_is_deleted<span>=</span><span>0</span>;</span>\n<span><span>CREATE</span> <span>VIEW</span> comments_view <span>AS</span> <span>SELECT</span> <span>*</span> <span>FROM</span> comments <span>FINAL</span> <span>where</span> _peerdb_is_deleted<span>=</span><span>0</span>;</span></code></pre></div>\n<p>Then, we can query the views using the same query we would use in PostgreSQL.</p>\n<div><pre><code><span><span>-- Most viewed posts</span></span>\n<span><span>SELECT</span></span>\n<span>    <span>sum</span>(viewcount) <span>AS</span> viewcount,</span>\n<span>    owneruserid</span>\n<span><span>FROM</span> posts_view</span>\n<span><span>WHERE</span> owneruserid <span>&gt;</span> <span>0</span></span>\n<span><span>GROUP</span> <span>BY</span> owneruserid</span>\n<span><span>ORDER</span> <span>BY</span> viewcount <span>DESC</span></span>\n<span>LIMIT <span>10</span></span></code></pre></div>\n<h4 id=\"refreshable-material-view\"></h4>\n<p>Another approach is to use a <a target=\"_blank\" href=\"https://clickhouse.com/docs/materialized-view/refreshable-materialized-view\">Refreshable Materialized View</a>, which enables you to schedule query execution for deduplicating rows and storing the results in a destination table. With each scheduled refresh, the destination table is replaced with the latest query results.</p>\n<p>The key advantage of this method is that the query using the FINAL keyword runs only once during the refresh, eliminating the need for subsequent queries on the destination table to use FINAL.</p>\n<p>However, a drawback is that the data in the destination table is only as up-to-date as the most recent refresh. That said, for many use cases, refresh intervals ranging from several minutes to a few hours may be sufficient.</p>\n<div><pre><code><span><span>-- Create deduplicated posts table </span></span>\n<span><span>CREATE table</span> deduplicated_posts <span>AS</span> posts;</span>\n<span></span>\n<span><span>-- Create the Materialized view and schedule to run every hour</span></span>\n<span><span>CREATE</span> MATERIALIZED <span>VIEW</span> deduplicated_posts_mv REFRESH <span>EVERY</span> <span>1</span> <span>HOUR</span> <span>TO</span> deduplicated_posts <span>AS</span> </span>\n<span><span>SELECT</span> <span>*</span> <span>FROM</span> posts <span>FINAL</span> <span>where</span> _peerdb_is_deleted<span>=</span><span>0</span></span></code></pre></div>\n<p>Then, you can query the table <code>deduplicated_posts</code> normally.</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    <span>sum</span>(viewcount) <span>AS</span> viewcount,</span>\n<span>    owneruserid</span>\n<span><span>FROM</span> deduplicated_posts</span>\n<span><span>WHERE</span> owneruserid <span>&gt;</span> <span>0</span></span>\n<span><span>GROUP</span> <span>BY</span> owneruserid</span>\n<span><span>ORDER</span> <span>BY</span> viewcount <span>DESC</span></span>\n<span>LIMIT <span>10</span>;</span></code></pre></div>\n<h3 id=\"advanced-tuning-merge-settings\"></h3>\n<p>ReplicatingMergeTree engine table removes duplicates periodically, at merge time, to be precise, as documented <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/replacing-merge-tree#tuning-merges-for-better-query-performance\">here</a>.&#160;</p>\n<p>By default, merging occurs infrequently and is not frequent enough to serve as a reliable deduplication method. However, you can adjust the merge timing by modifying the table configuration.</p>\n<p>The ReplacingMergeTree documentation <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/replacing-merge-tree#tuning-merges-for-better-query-performance\">here</a> describes the three settings that can be adjusted to merge the data more frequently:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/merge-tree-settings#min_age_to_force_merge_seconds\">min_age_to_force_merge_seconds </a>: ClickHouse will consider merging parts that are older than this value. Default to 0 - Disabled.&#160;</li>\n<li><a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/merge-tree-settings#min_age_to_force_merge_on_partition_only\">min_age_to_force_merge_on_partition_only</a>: Whether min_age_to_force_merge_seconds should be applied only on the entire partition and not on a subset. Default to false.</li>\n</ul>\n<p>We can set these values to existing tables using the ALTER TABLE statement. For example, I could set <code>min_age_to_force_merge_seconds</code> to <code>10 seconds</code>, <code>min_age_to_force_merge_on_partition_only</code> to <code>true</code> for the table posts with the following command.</p>\n<div><pre><code><span><span>-- Tune merge settings</span></span>\n<span><span>ALTER TABLE</span> posts MODIFY SETTING min_age_to_force_merge_seconds<span>=</span><span>10</span>;</span>\n<span><span>ALTER TABLE</span> posts MODIFY SETTING min_age_to_force_merge_on_partition_only<span>=</span><span>true</span>;</span></code></pre></div>\n<blockquote>\n<p>Tweaking these settings increases merge frequency and can drastically reduce duplicates, but it doesn’t guarantee that there will be no duplicates. This may be acceptable for some analytical workloads.</p>\n</blockquote>\n<h2 id=\"ordering-keys\"></h2>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/migrations/postgresql/designing-schemas#primary-ordering-keys-in-clickhouse\">Ordering Keys</a> (a.k.a. sorting keys) define how data is sorted on disk and indexed for a table in ClickHouse. When replicating from Postgres, ClickPipes sets the Postgres primary key of a table as the ordering key for the corresponding table in ClickHouse. In most cases, the Postgres primary key serves as a sufficient ordering key, as ClickHouse is already optimized for fast scans, and custom ordering keys are often not required.</p>\n<p>For larger use cases, you should include additional columns beyond the Postgres primary key in the ClickHouse ordering key to optimize queries. By default, choosing an ordering key different from the Postgres primary key can cause data deduplication issues in ClickHouse. This happens because the ordering key in ClickHouse serves a dual role: it controls data indexing and sorting while acting as the deduplication key. You can learn more about this caveat <a target=\"_blank\" href=\"https://docs.peerdb.io/mirror/ordering-key-different\">here</a>. The easiest way to address this issue is by defining refreshable materialized views.</p>\n<h3 id=\"use-refreshable-materialized-views\"></h3>\n<p>A simple way to define custom ordering keys (ORDER BY) is using refreshable materialized views (MVs). These allow you to periodically (e.g., every 5 or 10 minutes) copy the entire table with the desired ordering key. For more details and caveats, refer to the section <a target=\"_blank\" href=\"https://clickhouse.com/blog/postgres-to-clickhouse-data-modeling-tips-v2#refreshable-material-view\">above</a>.</p>\n<p>Below is an example of a Refreshable MV with a custom ORDER BY and required deduplication:</p>\n<div><pre><code><span><span>CREATE</span> MATERIALIZED <span>VIEW</span> posts_final</span>\n<span>REFRESH <span>EVERY</span> <span>10</span> <span>second</span> ENGINE <span>=</span> ReplacingMergeTree(_peerdb_version)</span>\n<span><span>ORDER</span> <span>BY</span> (owneruserid,id) <span>-- different ordering key but with suffixed postgres pkey</span></span>\n<span><span>AS</span></span>\n<span><span>SELECT</span> <span>*</span> <span>FROM</span> posts <span>FINAL</span> </span>\n<span><span>WHERE</span> _peerdb_is_deleted <span>=</span> <span>0</span>; <span>-- this does the deduplication</span></span></code></pre></div>\n<h3 id=\"custom-ordering-keys-without-refreshable-materialized-views\"></h3>\n<p>If refreshable materialized views don't work due to the scale of data, here are a few recommendations you can follow to define custom ordering keys on larger tables and overcome deduplication-related <a target=\"_blank\" href=\"https://docs.peerdb.io/mirror/ordering-key-different\">issues</a>.</p>\n<p><strong>Choose ordering key columns that don't change for a given row</strong></p>\n<p>When including additional columns in the ordering key for ClickHouse (besides the primary key from Postgres), we recommend selecting columns that don't change for each row. This helps prevent data consistency and deduplication issues with ReplacingMergeTree.</p>\n<p>For example, in a multi-tenant SaaS application, using (<code>tenant_id</code>, <code>id</code>) as the ordering key is a good choice. These columns uniquely identify each row, and <code>tenant_id</code> remains constant for an <code>id</code> even if other columns change. Since deduplication by id aligns with deduplication by (tenant_id, id), it helps avoid data <a target=\"_blank\" href=\"https://docs.peerdb.io/mirror/ordering-key-different\">deduplication issues</a> that could arise if tenant_id were to change.</p>\n<p><strong>Note</strong>: If you have scenarios where ordering keys need to include columns that change, please reach out to us at <a target=\"_blank\" href=\"mailto:support@clickhouse.com\">support@clickhouse.com</a>. There are advanced methods to handle this, and we will work with you to find a solution.</p>\n<p><strong>Set Replica Identity on Postgres Tables to Custom Ordering Key</strong></p>\n<p>For Postgres CDC to function as expected, it is important to modify the <code>REPLICA IDENTITY</code> on tables to include the ordering key columns. This is essential for handling DELETEs accurately.</p>\n<p>If the <code>REPLICA IDENTITY</code> does not include the ordering key columns, Postgres CDC will not capture the values of columns other than the primary key - this is a limitation of Postgres logical decoding. All ordering key columns besides the primary key in Postgres will have nulls. This affects deduplication, meaning the previous version of the row may not be deduplicated with the latest deleted version (where <code>_peerdb_is_deleted</code> is set to 1).</p>\n<p>In the above example with <code>owneruserid</code> and <code>id</code>, if the primary key does not already include <code>owneruserid</code>, you need to have a <code>UNIQUE INDEX</code> on (<code>owneruserid</code>, <code>id</code>) and set it as the <code>REPLICA IDENTITY</code> for the table. This ensures that Postgres CDC captures the necessary column values for accurate replication and deduplication.</p>\n<p>Below is an example of how to do this on the events table. Make sure to apply this to all tables with modified ordering keys.</p>\n<div><pre><code><span><span>-- Create a UNIQUE INDEX on (owneruserid, id)</span></span>\n<span><span>CREATE</span> <span>UNIQUE</span> INDEX posts_unique_owneruserid_idx <span>ON</span> posts(owneruserid, id);</span>\n<span><span>-- Set REPLICA IDENTITY to use this index</span></span>\n<span><span>ALTER TABLE</span> posts REPLICA <span>IDENTITY</span> <span>USING</span> INDEX posts_unique_owneruserid_idx;</span></code></pre></div>\n<h3 id=\"another-option-projections\"></h3>\n<p>As described in ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter/projection\">documentation</a>, Projections are useful for running queries on a column that is not a part of the primary key.</p>\n<blockquote>\n<p>The biggest caveat with Projections is that they get skipped when querying the table with the FINAL keyword and do not account for deduplication. This could work for a few use cases where duplicates (updates, deletes) are not present or are less common.</p>\n</blockquote>\n<p>Projections are defined on the table we want to add a custom ordering key for. Then, each time a query is executed on this table, ClickHouse determines if the query execution can benefit from using one of the existing Projections.</p>\n<p>Let's take an example where we want to order the table posts by the field <code>creationdate</code> instead of the current one id. This would benefit query that filter using a date range.</p>\n<p>Consider the following query that finds the most viewed posts mentioning \"clickhouse\" in 2024.</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    id,</span>\n<span>    title,</span>\n<span>    viewcount</span>\n<span><span>FROM</span> stackoverflow.posts</span>\n<span><span>WHERE</span> (toYear(creationdate) <span>=</span> <span>2024</span>) <span>AND</span> (body <span>LIKE</span> <span>'%clickhouse%'</span>)</span>\n<span><span>ORDER</span> <span>BY</span> viewcount <span>DESC</span></span>\n<span>LIMIT <span>5</span></span>\n<span></span>\n<span><span>5</span> <span>rows</span> <span>in</span> set. Elapsed: <span>0.617</span> sec. Processed <span>4.69</span> million <span>rows</span>, <span>714.67</span> MB (<span>7.60</span> million <span>rows</span><span>/</span>s., <span>1.16</span> GB<span>/</span>s.)</span>\n<span>Peak memory usage: <span>147.04</span> MiB.</span></code></pre></div>\n<p>By default, ClickHouse needs to do a full scan of the table as the order by is <code>id</code>, we can note in the last query processed 4.69 million rows.\nNow, let's add a Projection to order by <code>creationdate</code>.</p>\n<div><pre><code><span><span>-- Create the Projection</span></span>\n<span><span>ALTER TABLE</span> posts <span>ADD</span> PROJECTION creation_date_projection (</span>\n<span><span>SELECT</span></span>\n<span><span>*</span></span>\n<span><span>ORDER</span> <span>BY</span> creationdate</span>\n<span>);</span>\n<span></span>\n<span><span>-- Materialize the Projection</span></span>\n<span><span>ALTER TABLE</span> posts MATERIALIZE PROJECTION creation_date_projection;</span></code></pre></div>\n<p>Then, we run again the same query.</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    id,</span>\n<span>    title,</span>\n<span>    viewcount</span>\n<span><span>FROM</span> stackoverflow.posts</span>\n<span><span>WHERE</span> (toYear(creationdate) <span>=</span> <span>2024</span>) <span>AND</span> (body <span>LIKE</span> <span>'%clickhouse%'</span>)</span>\n<span><span>ORDER</span> <span>BY</span> viewcount <span>DESC</span></span>\n<span>LIMIT <span>5</span></span>\n<span></span>\n<span><span>5</span> <span>rows</span> <span>in</span> set. Elapsed: <span>0.438</span> sec. Processed <span>386.80</span> thousand <span>rows</span>, <span>680.42</span> MB (<span>882.29</span> thousand <span>rows</span><span>/</span>s., <span>1.55</span> GB<span>/</span>s.)</span>\n<span>Peak memory usage: <span>79.37</span> MiB.</span></code></pre></div>\n<p>ClickHouse utilized the Projection to execute the query, reducing rows scanned to just 386,000 compared to 4.69 million previously, while also lowering memory usage.</p>\n<h2 id=\"joins-and-denormalization\"></h2>\n<p>Since Postgres is a relational database, its data model is heavily <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Database_normalization\">normalized</a>, often involving hundreds of tables. In our StackOverflow dataset, the votes table could be a good candidate for conversion into a dictionary. This <a target=\"_blank\" href=\"https://clickhouse.com/docs/dictionary#speeding-up-joins-using-a-dictionary\">documentation</a> provides an example of how to use dictionaries to optimize JOIN queries with the StackOverflow dataset.</p>\n</li>\n<li>\n<p><strong>JOIN algorithms</strong>: ClickHouse offers various algorithms for joining tables, and selecting the right one depends on the specific use case. This <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-fully-supports-joins-how-to-choose-the-right-algorithm-part5\">blog</a> explains how to choose the most suitable algorithm. Elapsed: <span>7.202</span> sec. Processed <span>60.42</span> million <span>rows</span>, <span>1.83</span> GB (<span>8.39</span> million <span>rows</span><span>/</span>s., <span>254.19</span> MB<span>/</span>s.)</span>\n<span>Peak memory usage: <span>1.99</span> GiB.</span>\n<span></span>\n<span><span>-- Use parallel hash algorithm</span></span>\n<span><span>SELECT</span></span>\n<span>    <span>sum</span>(p.viewcount) <span>AS</span> viewcount,</span>\n<span>    p.owneruserid <span>AS</span> user_id,</span>\n<span>    u.displayname <span>AS</span> display_name</span>\n<span><span>FROM</span> posts <span>AS</span> p</span>\n<span><span>FINAL</span></span>\n<span><span>LEFT</span> <span>JOIN</span> users <span>AS</span> u</span>\n<span><span>FINAL</span> <span>ON</span> (u.id <span>=</span> p.owneruserid) <span>AND</span> (u._peerdb_is_deleted <span>=</span> <span>0</span>)</span>\n<span><span>WHERE</span> (p.owneruserid <span>&gt;</span> <span>0</span>) <span>AND</span> (p._peerdb_is_deleted <span>=</span> <span>0</span>)</span>\n<span><span>GROUP</span> <span>BY</span></span>\n<span>    user_id,</span>\n<span>    display_name</span>\n<span><span>ORDER</span> <span>BY</span> viewcount <span>DESC</span></span>\n<span>LIMIT <span>10</span></span>\n<span>FORMAT `<span>NULL</span>`</span>\n<span>SETTINGS join_algorithm <span>=</span> <span>'parallel_hash'</span></span>\n<span></span>\n<span><span>10</span> <span>rows</span> <span>in</span> set. Elapsed: <span>2.160</span> sec. Processed <span>60.42</span> million <span>rows</span>, <span>1.83</span> GB (<span>27.97</span> million <span>rows</span><span>/</span>s., <span>847.53</span> MB<span>/</span>s.)</span>\n<span>Peak memory usage: <span>5.44</span> GiB.</span></code></pre></div>\n<h3 id=\"denormalization\"></h3>\n<p>Another approach users follow to speed up queries is denormalizing data in ClickHouse to create a more flattened table. <span>BY</span> (upvotes) </span>\n<span><span>AS</span> </span>\n<span><span>SELECT</span></span>\n<span>    u.id <span>AS</span> UserId,</span>\n<span>    u.displayname,</span>\n<span> In this case, there is no need to use a Common Table Expression, as we want to process the entire dataset.</p>\n<p>To return the same result as the JOIN query, we run a simple query on the materialized view.</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> top_upvoted_users_activity_mv</span>\n<span><span>ORDER</span> <span>BY</span> upvotes <span>DESC</span></span>\n<span>LIMIT <span>10</span>;</span></code></pre></div>\n<h4 id=\"raw-denormalization-using-incremental-materialized-view\"></h4>\n<p>Incremental Materialized Views can also be used for raw denormalization, offering two key advantages over Refreshable Materialized Views (RMVs):</p>\n<ul>\n<li>The query runs only on newly inserted rows rather than scanning the entire source table, making it a suitable choice for massive datasets, including those in the petabyte range.</li>\n<li>The materialized view is updated in real-time as new rows are inserted into the source table, whereas RMVs refresh periodically.</li>\n</ul>\n<p>However, a limitation is that deduplication cannot occur at insert time. eliminate duplicates.</p>\n<div><pre><code><span><span>INSERT INTO</span> daily_posts_activity</span>\n<span><span>SELECT</span> toStartOfDay(creationdate)::<span>Date</span> <span>AS</span> <span>Day</span>,</span>\n<span>       uniqState(<span>CASE</span> <span>WHEN</span> posttypeid<span>=</span><span>1</span> <span>THEN</span> id <span>END</span>) <span>as</span> Questions,</span>\n<span>       uniqState(<span>CASE</span> <span>WHEN</span> posttypeid<span>=</span><span>2</span> <span>THEN</span> id <span>END</span>) <span>as</span> Answers</span>\n<span><span>FROM</span> posts <span>FINAL</span></span>\n<span><span>GROUP</span> <span>BY</span> <span>Day</span></span></code></pre></div>\n<p>Then, we can create the Materialized view to keep running the query on each new incoming block of rows.</p>\n<div><pre><code><span><span>CREATE</span> MATERIALIZED <span>VIEW</span> daily_posts_activity_mv <span>TO</span> daily_posts_activity <span>AS</span></span>\n<span><span>SELECT</span> toStartOfDay(creationdate)::<span>Date</span> <span>AS</span> <span>Day</span>,</span>\n<span>       uniqState(<span>CASE</span> <span>WHEN</span> posttypeid<span>=</span><span>1</span> <span>THEN</span> id <span>END</span>) <span>as</span> Questions,</span>\n<span>       uniqState(<span>CASE</span> <span>WHEN</span> posttypeid<span>=</span><span>2</span> <span>THEN</span> id <span>END</span>) <span>as</span> Answers</span>\n<span><span>FROM</span> posts</span>\n<span><span>GROUP</span> <span>BY</span>
