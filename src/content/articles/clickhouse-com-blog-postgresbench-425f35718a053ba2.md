ClickHouse is an example of that focus. Performance is not a feature we add later. It is a core design goal from the start.</p>\n<p>We applied a similar approach when building <a target=\"_blank\" href=\"https://clickhouse.com/cloud/postgres\">our managed Postgres service</a>. The result is offering one of the fastest managed Postgres services to our customers. Postgres handles transactional workloads, while ClickHouse handles analytical workloads. Together they form a unified data stack enabling a \"<a target=\"_blank\" href=\"https://clickhouse.com/blog/ai-redrawing-database-market#real-time_analytics\">best-of-breed</a>\" foundation SaaS and AI applications.&#160;</p>\n<p>With that in mind, it felt natural to evaluate it the same way we evaluate ClickHouse: with a public, reproducible benchmark.</p>\n<p>That is why we built <a target=\"_blank\" href=\"https://postgresbench.clickhouse.com/\">PostgresBench</a>, a benchmark to compare managed Postgres services.</p>\n<p><span><img alt=\"CleanShot 2026-04-02 at 12.04.50.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FClean_Shot_2026_04_02_at_12_04_50_54c3552a58.png&w=2048&q=75\"></span></p>\n<h2 id=\"from-clickbench-to-postgresbench\"></h2>\n<p><a target=\"_blank\" href=\"https://benchmark.clickhouse.com/\">ClickBench is a widely referenced OLAP benchmark</a>. It benchmarks more than 40 databases using a transparent and reproducible methodology. All queries, datasets, and results are public and anyone can validate the numbers or submit improvements.</p>\n<p>PostgresBench applies the same methodology to transactional Postgres workloads. The rules are straightforward:</p>\n<ul>\n<li>Use a well-understood, standard workload</li>\n<li>Keep infrastructure consistent across all services tested</li>\n<li>Publish all configuration so results can be reproduced</li>\n<li>Allow anyone to submit results or flag issues</li>\n</ul>\n<p>If a number looks wrong, it can be checked. If a configuration is unfair, it can be fixed. That is the point.</p>\n<h2 id=\"benchmark-design\"></h2>\n<h3 id=\"workload\"></h3>\n<p>PostgresBench is built on <code>pgbench</code>, the <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/pgbench.html\">standard Postgres benchmarking tool</a>. We use the TPC-B-like workload it includes out of the box, which simulates short concurrent transactions with frequent writes and updates. It is a reasonable proxy for common transactional patterns: payments, order processing, inventory updates, and similar workloads that hit the database hard with small, frequent writes.</p>\n<p>We chose <code>pgbench</code> deliberately. Tools like <code>sysbench</code> and <code>Percona TPCC</code> are designed originally for MySQL workloads. For a Postgres benchmark, <code>pgbench</code> feels more natural, and it ships with Postgres, which makes it easy for anyone to reproduce results without additional tooling.</p>\n<h3 id=\"running-parameters\"></h3>\n<p>Each benchmark run uses the following parameters:</p>\n<div><pre><code><span>pgbench -c 256 -j 16 -T 600 -M prepared -P 30 \\</span>\n<span>  -s <span>$SCALE_FACTOR</span> \\</span>\n<span>  -h <span>$PGHOST</span> -p <span>$PGPORT</span> -U <span>$PGUSER</span> -d <span>$PGDATABASE</span></span></code></pre></div>\n<p>We ran each benchmark with 256 clients and 16 threads, which reflects realistic concurrency for a production transactional workload. Each run lasts 10 minutes, long enough to move past warmup and capture stable throughput.</p>\n<p>We tested two scale factors: 6849 (~100 GB) and 34247 (~500 GB). These correspond to dataset sizes typical of real Postgres deployments: one where the app is getting started, growing quickly and working set reasonably fits in cache and the other that has achieved reasonable scale, is growing and working set starts spilling to disk The gap between results at these two sizes tells you something useful about how a service handles storage pressure as data grows.</p>\n<h3 id=\"metrics-captured\"></h3>\n<p>We report average TPS, average latency, P95 latency, and P99 latency across all three runs per configuration. We publish the ranking for the best and worst run, and the details of each individual run are available in the repository.</p></div><div><h3>Get started with our native Postgres Service</h3><p>To try ClickHouse's native Postgres service, sign up for Private Preview using this link.</p><p><a target=\"_blank\" href=\"https://clickhouse.com/cloud/postgres?loc=blog-cta-1278-get-started-with-our-native-postgres-service-sign-up&utm_blogctaid=1278\">Sign up</a></p></div><div><h2 id=\"fairness\"></h2>\n<p>No benchmark is perfectly neutral. Every choice, from instance type to Postgres configuration, can favor one system over another. We explain our thinking behind each decision below, and document the exact settings used for each system in the benchmark repository alongside the results.</p>\n<h3 id=\"client-machine-setup\"></h3>\n<p>We provisioned a 16 vCPU, 64 GB instance in the us-east-2 region to run the benchmark client, sized to ensure the client is never the bottleneck. All services were tested in the same region, so results reflect only database performance, not cross-region network latency. We also do not colocate client and database by availability zone, since not all services offer this capability. However, to ensure fairness for those that do, this is something we may consider adding in the future. <a target=\"_blank\" href=\"https://github.com/ClickHouse/PostgresBench/issues\">Contributions are welcome</a>.</p>\n<h3 id=\"instance-selection\"></h3>\n<p>For most services, we targeted a 1:4 CPU-to-RAM ratio and tested two sizes: 4 vCPUs/16GB RAM and 16 vCPUS/64GB RAM. Aurora does not offer an instance class that provides this ratio so we used a 1:8 ratio at two sizes as well: 4 vCPUs/32 GB RAM and 16 vCPUS/128 GB RAM.</p>\n<p>We used <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/AWS_Graviton\">Graviton instances</a> with NVMe caching for all services that support them, including AWS RDS and Aurora. This gives competitors the same hardware advantage, even though NVMe in those cases is used for caching rather than primary storage.</p>\n<h3 id=\"single-node\"></h3>\n<p>While all services offer high availability, the underlying architectures differ. Some use standby replication, others use shared or distributed storage layers. Since we are focused on single-node compute and storage performance, we tested without HA enabled to isolate that. We may add HA configurations as a separate dimension in the future.</p>\n<h3 id=\"default-postgres-configuration\"></h3>\n<p>We do not modify default PostgreSQL configurations across services; each system is tested using its out-of-the-box settings. This reflects typical user behavior, where most expect performance without tuning. We may incorporate Postgres configs as an additional dimension in the future.</p>\n<h3 id=\"a-note-on-pricing\"></h3>\n<p>We did not compare pricing. Postgres managed by ClickHouse had not yet been released at the time of testing. We expect pricing to be competitive for similar hardware profiles and you'll be able to extrapolate price-performance from the results here once it is available.</p>\n<h2 id=\"the-first-cohort\"></h2>\n<h3 id=\"systems-included\"></h3>\n<p>The first release of PostgresBench covers five services, each tested in two instance configurations: a smaller 4 vCPU / 16 GB setup and a larger 16 vCPU / 64 GB setup, or equivalent. This lets us observe how each service scales with more resources, not just how it performs at a single point.</p>\n<p>All services were tested in us-east-2 with HA disabled, using Postgres 17 or 18 depending on what each provider supports. id=\"why-postgres-managed-by-clickhouse-leads-this-benchmark\"></h2>\n<p>The TPC-B workload blends both read and write operations and can become I/O-intensive due to continuous DML (UPDATE) activity generating WAL records. This pattern is typical of fast-growing OLTP workloads, where sustained write activity drives WAL generation and makes disk performance a critical dimension for Postgres performance.</p>\n<p>Postgres managed by ClickHouse is backed by NVMe storage that is physically co-located with compute. This enables microsecond-scale disk access latency, rather than milliseconds, along with consistently high IOPS that are neither shared across tenants nor constrained by network bandwidth. As a result, it can deliver significantly better performance than architectures built on shared storage, such as EBS or object storage, without compromising <a target=\"_blank\" href=\"https://clickhouse.com/blog/enterprise-postgres-service-in-clickhouse-cloud?loc=postgresWeek5#cross-az-ha\">availability</a> or <a target=\"_blank\" href=\"https://clickhouse.com/blog/enterprise-postgres-service-in-clickhouse-cloud?loc=postgresWeek5#backups-pitr-and-forks\">durability</a></p>\n<p>In contrast, alternatives like EBS-backed volumes introduce network latency into the I/O path. While reads may benefit from the kernel page cache, every <code>fsync</code>, including transaction commits, must still be acknowledged by the remote storage layer. For write-heavy workloads like the one used in this benchmark, that per-commit overhead accumulates quickly and directly impacts performance.</p>\n<blockquote>\n<p>TL;DR: Most of the time, Postgres isn’t slow, your storage is. Stay tuned for a deeper technical dive on this topic coming soon.</p>\n</blockquote>\n<p>The image below shows the reduction in P99 latency for disk-bound workloads when moving from traditional Postgres to NVMe-backed Postgres.</p>\n<p><span><img alt=\"postgres-launch-1.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpostgres_launch_1_5e02d22e1a.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p>For Postgres workloads that are primarily throttled by disk IOPS and latency, this architectural difference is a decisive factor. The benchmark results reflect that directly.</p>\n</blockquote>\n<h2 id=\"built-to-be-verified\"></h2>\n<p>The full benchmark repository is open source.</p>\n<p>Publishing structured JSON for every run means results can be compared programmatically, not just visually. The repository includes, script to run the benchmark and all raw results. If a configuration is incorrect or gives an unfair advantage to any service, it can be reviewed and corrected in the open.</p>\n<p>The repository is available at <a target=\"_blank\" href=\"http://github.com/ClickHouse/PostgresBench\">github.com/ClickHouse/PostgresBench</a>.</p>\n<h3 id=\"submit-results\"></h3>\n<p>To run the benchmark against your own instance, simply execute this command. It takes between 30 and 40 minutes to run.</p>\n<div><pre><code><span><span># Set connection parameters</span></span>\n<span><span>export</span> PGHOST=<span>\"your-database-host\"</span></span>\n<span><span>export</span> PGPORT=5432</span>\n<span><span>export</span> PGUSER=<span>\"postgres\"</span></span>\n<span><span>export</span> PGPASSWORD=<span>\"your-password\"</span></span>\n<span><span>export</span> PGDATABASE=<span>\"postgres\"</span></span>\n<span></span>\n<span><span># Required: instance hardware details</span></span>\n<span><span>export</span> VCPUS=16</span>\n<span><span>export</span> RAM_GB=64</span>\n<span></span>\n<span><span># Required: instance metadata</span></span>\n<span><span>export</span> SYSTEM_NAME=<span>\"Postgres by ClickHouse\"</span></span>\n<span><span>export</span> INSTANCE_TYPE=<span>\"m8gd.4xlarge\"</span>       </span>\n<span><span>export</span> INSTANCE_STORAGE=<span>\"950 GB - NVMe\"</span>  </span>\n<span><span>export</span> PRIMARY_STORAGE=<span>\"NVMe\"</span>  </span>\n<span>          </span>\n<span><span># Optional: output</span></span>\n<span><span>export</span> OUT_JSON=<span>\"results.json\"</span>   <span># Output file name (default: oltpbench_result.json)</span></span>\n<span></span>\n<span><span># Run the benchmark</span></span>\n<span>./run.sh</span></code></pre></div>\n<p>The script handles the data initialization, runs the benchmark three times and writes the result in a JSON file.</p>\n<p>To add your system:</p>\n<ol>\n<li>Clone the benchmark repository</li>\n<li>Follow the documented infrastructure setup to match the tested instance specs</li>\n<li>Run <code>run.sh</code> with the published parameters</li>\n<li>Create a Pull-Request to submit your results</li>\n<li>We will review the configuration and publish the results</li>\n</ol>\n<h2 id=\"postgresbench-is-live\"></h2>\n<p><a target=\"_blank\" href=\"https://postgresbench.clickhouse.com/\">PostgresBench</a> is now live, with all benchmark results publicly available to explore and compare.</p>\n<p>Interested in adding your system to the board?
