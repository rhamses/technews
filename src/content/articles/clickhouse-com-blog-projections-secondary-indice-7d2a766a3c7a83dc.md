contentHtml: "<article><div><blockquote>\n<p><strong>TL;DR</strong><br><br>ClickHouse tables once had only <em>one</em> primary index.<br>Now they can have <strong>many</strong>, implemented as lightweight projections that behave like primary indexes, without duplicating data.</p>\n</blockquote>\n<p><strong>Prefer a quick walkthrough?</strong><br>\nWatch Mark explain how projections act as secondary indexes in ClickHouse:</p>\n<br>\n<h2 id=\"why-projections-matter\"></h2>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/primary-indexes\">Primary indexes</a> are the most important mechanism ClickHouse uses to speed up filtered queries. By storing rows on disk in the order of the table’s sorting key, the engine maintains a sparse index that can quickly locate the relevant ranges of data. But because this index depends on the physical sort order of the table, <strong>each table can have only one primary index</strong>.</p>\n<p>To accelerate queries whose filters do not align with that single index, ClickHouse offers <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/alter/projection\"><strong>projections</strong></a> - automatically maintained, hidden table copies stored in a different sort order, and therefore with a different primary index. These alternative layouts can speed up queries that benefit from those orderings. The downside, historically, was storage cost: <strong>projections duplicated the base table’s data on disk</strong>.</p>\n<h2 id=\"lightweight-projections-as-secondary-indexes\"></h2>\n<p>Since release <strong>25.6</strong>, however, ClickHouse can create much more lightweight <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-06#filtering-by-multiple-projections\">projections that behave like a <strong>secondary index</strong></a> without duplicating full rows. Instead of storing complete data copies, they store only their sorting key plus a <a target=\"_blank\" href=\"https://clickhouse.com/docs/data-modeling/projections#smarter_storage_with_part_offset\">_part_offset</a> pointer back into the base table, greatly reducing storage overhead.</p>\n<p>When applicable, <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-06#smarter-storage-with-_part_offset\">ClickHouse uses such a projection’s primary index like a secondary index to locate matching rows</a>, while still reading the actual row data from the base table. Multiple lightweight projections can work together, so a query with several filters can take advantage of every applicable projection, and if one of the filters also matches the base table’s primary index, <strong>that index participates as well</strong>.</p>\n<h2 id=\"from-part-level-to-granule-level-pruning\"></h2>\n<p>Until now, this mechanism could only prune entire parts; <strong>granule-level pruning</strong> was not supported.</p>\n<p>With this release, _part_offset-based projections now behave like true secondary indexes with <strong>granule-level pruning</strong>, enabling much finer filtering and dramatically faster queries.</p>\n<h2 id=\"example-combining-multiple-projection-indexes\"></h2>\n<p>To demonstrate this, we’ll again use <a target=\"_blank\" ClickHouse now supports granule-level pruning for lightweight projections, enabling them to act as true secondary indexes that work together to dramatically speed up multi-filter queries without duplicating full table data.
