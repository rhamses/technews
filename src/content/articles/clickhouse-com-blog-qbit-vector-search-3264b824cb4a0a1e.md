It powers <a target=\"_blank\" href=\"https://engineering.atspotify.com/2023/10/introducing-voyager-spotifys-new-nearest-neighbor-search-library\">music recommendations</a>, <a target=\"_blank\" href=\"https://help.openai.com/en/articles/8868588-retrieval-augmented-generation-rag-and-semantic-search-for-gpts\">retrieval-augmented generation (RAG) for large language models</a> where external knowledge is fetched to improve answers, and even googling is <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/RankBrain\">powered by vector search</a> to some extent. Many specialised databases are built to handle vector search very well. Nevertheless, these systems are rarely ideal for storing and querying structured data. As a result, we often see <a target=\"_blank\" href=\"https://youtu.be/jmVxfGEN0QQ?si=utgs-siTTUjAhYoV&t=1069\">users preferring regular databases</a> with ad-hoc vector capabilities over fully specialised vector stores.</p>\n<p>In ClickHouse, brute-force vector search has been supported for <a target=\"_blank\" href=\"https://clickhouse.com/blog/vector-search-clickhouse-p1\">several years</a> already. More recently, we added methods for approximate nearest neighbour (ANN) search, including <strong>HNSW</strong> – the current standard for fast vector retrieval. We also revisited quantisation and built a new data type: <strong>QBit</strong>.</p>\n<p>Each vector search method has its own parameters that decide trade-offs for recall, accuracy, and performance. Normally, these have to be chosen up-front. If you get them wrong, a lot of time and resources are wasted, and changing direction later becomes painful.</p>\n<p>With QBit, no early decisions are needed. You can adjust precision and speed trade-off directly at query time, exploring the right balance as you go.</p>\n<h2 id=\"vector-search-primer\"></h2>\n<p>Let’s start with the basics. Vector search is used to find the most similar document (text, image, song, and so on) in a dataset. First, all items are converted into high-dimensional vectors (arrays of floats) using embedding models. These embeddings capture <strong>the meaning</strong> of the data. By comparing distances between vectors, we can see how close two items are in meaning.</p>\n<p>Here’s a small example. Imagine we have embeddings for fruits and animals. Which one do you think sits closest to <i>lemon</i>? 🍋</p>\n<p><span><img alt=\"Diagram 4.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_4_285d6bf2af.jpg&w=2048&q=75\"></span></p>\n<p>An apple! results. But hopefully, we can all agree that <em>horse</em> and <em>dog</em> being at the bottom of the list feels about right.</p>\n<h2 id=\"approximate-nearest-neighbours-ann\"></h2>\n<p>Exact vector search is powerful but slow, and therefore costly. Many applications can tolerate a bit of flexibility. For example, it’s fine if, after listening to Eminem, you’re recommended Snoop Dogg or Tupac. But something has gone very wrong if the next suggestion is <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=dQw4w9WgXcQ\">this</a>.</p>\n<p>That’s why Approximate Nearest Neighbour (ANN) techniques exist. They provide faster and cheaper retrievals at the expense of perfect accuracy. The two most common approaches are <strong>quantisation</strong> and <strong>HNSW</strong>.</p>\n<p>We’ll look briefly at both, and then see how QBit fits into this picture.</p>\n<h3 id=\"quantisation\"></h3>\n<p>Suppose our stored vectors are of type <code>Float64</code>, and we’re not happy with the performance. The natural question is: <em>what if we downcast the data to a smaller type?</em></p>\n<p>Smaller numbers mean smaller data, and smaller data means faster distance calculations. ClickHouse’s vectorized query execution engine can fit more values into processor registers per operation, increasing throughput directly. On top of that, reading fewer bytes from disk reduces I/O load. This idea is known as <strong>quantisation</strong>.</p>\n<p>When quantising, we have to decide how to store the data. We can either:</p>\n<ol>\n<li>Keep the quantised copy alongside the original column, or</li>\n<li>Replace the original values entirely (by downcasting on insertion).</li>\n</ol>\n<p>The first option doubles storage, but it’s safe as we can always fall back to full precision. The second option saves space and I/O, but it’s a one-way door. If later we realise the quantisation was too aggressive and results are inaccurate, there’s no way back.</p>\n<h3 id=\"hierarchical-navigable-small-world-hnsw\"></h3>\n<p>There are many data structures designed to find the nearest neighbour without scanning all candidates. We call them <em>indexes</em>. Among them, <strong>HNSW</strong> is often seen as the monarch.</p>\n<p><span><img alt=\"Diagram 1.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_1_69207f0b0f.jpg&w=2048&q=75\"></span></p>\n<p>HNSW is built from multiple layers of nodes (vectors). Each node is randomly assigned to one or more layers, with the chance of appearing in higher layers decreasing exponentially.</p>\n<p>When performing a search, we start from a node at the top layer and move greedily towards the closest neighbours. Once no closer node can be found, we descend to the next, denser layer, and continue the process. The higher layers provide long-range connections to avoid getting trapped in local minima, while the lower layers ensure precision.</p>\n<p>Because of this layered design, HNSW achieves logarithmic search complexity with respect to the number of nodes. Far faster than the linear scans used in brute-force search or quantisation-based methods.</p>\n<p>The main bottleneck is memory. ClickHouse uses the <a target=\"_blank\" href=\"https://github.com/unum-cloud/usearch\">usearch</a> implementation of HNSW, which is an in-memory data structure that doesn’t support splitting. As a result, larger datasets require proportionally more RAM. Quantising the data before building the index can help reduce this footprint, but many HNSW parameters still have to be chosen in advance, including the quantisation level itself. And this is exactly the rigidity that QBit set out to address.</p>\n<h3 id=\"quantised-bit-qbit\"></h3>\n<p>QBit is a new data structure that can store <code>BFloat16</code>, <code>Float32</code>, and <code>Float64</code> values by taking advantage of how floating-point numbers are represented – as bits. Instead of storing each number as a whole, QBit splits the values into <em>bit planes</em>: every first bit, every second bit, every third bit, and so on.</p>\n<p>When running a search, ClickHouse can read just the required subcolumns to reconstruct the data up to the user-specified precision.</p>\n<p><span><img alt=\"Updated Diagram 2.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FUpdated_Diagram_2_980e31551a.jpg&w=2048&q=75\"></span></p>\n<p>This approach solves the main limitation of traditional quantisation. There’s no need to store duplicated data or risk making values meaningless. It also avoids the RAM bottlenecks of HNSW, since QBit works directly with the stored data rather than maintaining an in-memory index.</p>\n<p>Most importantly, <strong>no upfront decisions are required</strong>. Precision and performance can be adjusted dynamically at query time, allowing users to explore the balance between accuracy and speed with minimal friction.</p>\n<p>Although QBit speeds up vector search, its computational complexity remains <em>O(n)</em>. In other words: <em>if your dataset is small enough for an HNSW index to fit comfortably in RAM, that is still the fastest choice</em>.</p>\n<div><table><thead><tr><th>Category</th><th>Brute-force</th><th>HNSW</th><th>QBit</th></tr></thead><tbody><tr><td><strong>Precision</strong></td><td>Perfect</td><td>Great</td><td>Flexible</td></tr><tr><td><strong>Speed</strong></td><td>Slow</td><td>Fast</td><td>Flexible</td></tr><tr><td><strong>Others</strong></td><td>Quantized: creation and data ingestion.</li>\n<li>Distance calculations.</li>\n</ol>\n<p>Let’s look into both.</p>\n<h3 id=\"the-data-type\"></h3>\n<p><span><img alt=\"Diagram 5.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_5_7dc7fd77d8.jpg&w=2048&q=75\"></span></p>\n<p>When data is inserted into a QBit column, it is transposed so that all first bits line up together, all second bits line up together, and so on. We call these <em>groups</em>.</p>\n<p>Each group is stored in a separate <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/fixedstring\"><code>FixedString(N)</code></a> column: fixed-length strings of <code>N</code> bytes stored consecutively in memory with no separators between them. All such groups are then bundled together into a single <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/data-types/tuple\">Tuple</a>, which forms the underlying structure of QBit.</p>\n<p>If we start with a vector of 8×<code>Float64</code> elements, each group will contain 8 bits. Because a <code>Float64</code> has 64 bits, we end up with 64 groups (one for each bit). Therefore, the internal layout of <code>QBit(Float64, 8)</code> looks like a Tuple of 64×<code>FixedString(1)</code> columns.</p>\n<p>If the original vector length doesn’t divide evenly by 8, the structure is padded with invisible elements to make it align to 8. This ensures compatibility with <code>FixedString</code>, which operates strictly on full bytes. For example, in the picture above, the vector contains 5 <code>Float64</code> values. It would be padded by three zeroes producing 8×<code>Float64</code>, which is then transposed into a Tuple of 64×<code>FixedString(1)</code>. Or, if we started with 76×<code>BFloat16</code> elements, we would pad it to 80×<code>BFloat16</code> and transpose it into a Tuple of 16×<code>FixedString(10)</code>.</p>\n<h3 id=\"the-distance-calculation\"></h3>\n<div><pre><code><span><span>SELECT</span> </span>\n<span>  word, </span>\n<span>  L2DistanceTransposed(vec, [...], <span>16</span>) <span>AS</span> distance </span>\n<span><span>FROM</span> fruit_animal </span>\n<span><span>ORDER</span> <span>BY</span> distance;</span></code></pre></div>\n<h4 id=\"i-o-optimisation\"></h4>\n<p>Before we can calculate distances, the required data must be read from disk and then <strong>untransposed</strong> (converted back from the grouped bit representation into full vectors). Because QBit stores values bit-transposed by precision level, ClickHouse can <strong>read only the top bit planes</strong> needed to reconstruct numbers up to the desired precision.</p>\n<p>In the query above, we use a precision level of 16. Since a <code>Float64</code> has 64 bits, we only read the first 16 bit planes, skipping 75% of the data.</p>\n<p><span><img alt=\"Diagram 3.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_3_211329e344.jpg&w=2048&q=75\"></span></p>\n<p>After reading, we reconstruct only the top portion of each number from the loaded bit planes, leaving the unread bits zeroed out.</p>\n<p><span><img alt=\"Diagram 6.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_6_ec1c4364a9.jpg&w=2048&q=75\"></span></p>\n<h4 id=\"calculation-optimisation\"></h4>\n<p>One might ask whether casting to a smaller type, such as <code>Float32</code> or <code>BFloat16</code>, could eliminate this unused portion. It does work, but explicit casts are expensive when applied to every row. Instead, we can downcast only the reference vector and treat the QBit data as if it contained narrower values (“forgetting” the existence of some columns), since its layout often corresponds to a truncated version of those types. But not always!</p>\n<p><span><img alt=\"Diagram 7.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_7_d2613e3963.jpg&w=2048&q=75\"></span></p>\n<p>Let’s start with the simple case where the original data is <code>Float32</code>, and the chosen precision is 16 bits or fewer. <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Bfloat16_floating-point_format\"><code>BFloat16</code></a> is a <code>Float32</code> truncated by half. It keeps the same sign bit and 8-bit exponent, but only the upper 7 bits of the 23-bit mantissa. Because of this, reading the first 16 bit planes from a QBit column effectively reproduces the layout of <code>BFloat16</code> values. So in this case, we can (<a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/88243\">and do</a>) safely convert the reference vector (the one all the data in QBit is compared against) to <code>BFloat16</code> and treat the QBit data as if it were stored that way from the start.</p>\n<p><code>Float64</code>, however, is a different story. It uses an 11-bit exponent and a 52-bit mantissa, meaning it’s not simply a <code>Float32</code> with twice the bits. Its structure and exponent bias are completely different. Downcasting a <code>Float64</code> to a smaller format like <code>Float32</code> requires an actual IEEE-754 conversion, where each value is <strong>rounded</strong> to the nearest representable <code>Float32</code>. This rounding step is computationally expensive and cannot be replaced with simple bit slicing or permutation.</p>\n<p>The same holds when the precision is 16 or smaller. Converting from <code>Float64</code> to <code>BFloat16</code> is effectively the same as first converting to <code>Float32</code> and then truncating that to <code>BFloat16</code>. So here too, bit-level tricks won’t help.</p>\n<h4 id=\"let-s-vectorise\"></h4>\n<h5 id=\"what-s-vectorisation\"></h5>\n<p>The main performance difference between regular quantised columns and QBit columns is the need to untranspose the bit-grouped data back into vector form during search. Doing this efficiently is critical. ClickHouse has a vectorized query execution engine, so it makes sense to use it to our advantage. You can read more about vectorisation in <a target=\"_blank\" href=\"https://clickhouse.com/blog/cpu-dispatch-in-clickhouse\">this</a> ClickHouse blog post.</p>\n<p>In short, <strong>vectorisation</strong> allows the CPU to process multiple values in a single instruction using <strong>SIMD</strong> (Single-Instruction-Multiple-Data) registers. The term originates from the fact that SIMD instructions operate on small batches (vectors) of data. Individual elements within these vectors are of fixed length and are typically referred to as <em>lanes</em>.</p>\n<p>There are two common approaches to vectorising algorithms:</p>\n<ol>\n<li>\n<p><strong>Auto-vectorisation</strong>. Write an algorithm in such a way that the compiler will figure out the concrete SIMD instructions itself. As compilers can only do this with very simple straight-forward functions, usually <em>such a way</em> is only achievable if the architecture of your system is carefully designed around an auto-vectorising algorithm, like <a target=\"_blank\" href=\"https://dl.acm.org/doi/10.1145/3725333\">here</a>.</p>\n</li>\n<li>\n<p><strong>Intrinsics</strong>. Write the algorithm using explicit <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Intrinsic_function\">intrinsics</a>: special functions that compilers map directly into CPU instructions. These are platform dependent, but offer full control.</p>\n</li>\n</ol>\n<h5 id=\"general-algorithm\"></h5>\n<p>SIMD untransposition is too complex for the compiler to auto-vectorise, so we’ve taken the second route and will walk you through it. Let’s first look at the idea behind the algorithm, and then see how it fits into the vectorized world.</p>\n<p><span><img alt=\"Diagram 8.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_8_fa2abe95fa.jpg&w=2048&q=75\"></span></p>\n<p><span><img alt=\"Diagram 9.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_9_544ae9ea68.jpg&w=2048&q=75\"></span></p>\n<p><span><img alt=\"Diagram 10.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_10_874d6bf97d.jpg&w=2048&q=75\"></span></p>\n<p><span><img alt=\"Diagram 11.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_11_e0fcfb28e9.jpg&w=2048&q=75\"></span></p>\n<p>We loop through all <code>FixedString</code> columns of the QBit (64 of them for <code>Float64</code>). Within each column, we iterate over every byte of the <code>FixedString</code>, and within each byte, over every bit.</p>\n<p>If a bit is <strong>0</strong>, we apply a zero mask to the destination at the corresponding position. If a bit is <strong>1</strong>, we apply a mask that depends on its position within the byte. For example, if we are processing the first bit, the mask is <code>10000000</code>;  for the second bit, it becomes <code>01000000</code>, and so on. The operation we apply is a <strong>logical OR</strong>, merging the bit from the source into the destination byte.</p>\n<h5 id=\"vectorized-algorithm\"></h5>\n<p>Let’s now look at the second iteration (steps 3 and 4 from above) using <strong>AVX-512</strong>, an instruction set that’s common across modern CPUs. In this example, we’re unpacking the second <code>FixedString(1)</code> group and each bit here contributes to the <em>second</em> <em>bit</em> of eight resulting <code>Float64</code> values.</p>\n<p><span><img alt=\"Diagram 12.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_12_80c9d0b961.jpg&w=2048&q=75\"></span></p>\n<p>When dealing with SIMD, it’s easier to think in <em>lanes</em>. AVX-512 operates on 512-bit registers, which correspond to eight 64-bit lanes. Let’s map our fixed strings across those lanes to visualise the data layout.</p>\n<p><span><img alt=\"Diagram 13.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_13_b2583d8ae5.jpg&w=2048&q=75\"></span></p>\n<p>Since we’re unpacking the <strong>second</strong> bit of each <code>Float64</code>, the bitmask now has its second bit set.<br>\nWe apply that mask across the lanes.</p>\n<p><span><img alt=\"Diagram 14.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_14_1e9ddccd54.jpg&w=2048&q=75\"></span></p>\n<p>The destination (<code>dst</code>) already contains results from the previous iteration. We are working on merging in the second bit as well.</p>\n<p><span><img alt=\"Diagram 15.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_15_1ce1ce3211.jpg&w=2048&q=75\"></span></p>\n<p>Now comes the interesting part. If our mask were all ones, we’d simply OR the new bits into the destination (this case is what we call <code>upd</code>). If the mask were all zeros, the destination would stay unchanged. In practice, each bit of the mask decides which lane to update: where the mask is <code>1</code>, take the value from <code>upd</code>; where it’s <code>0</code>, keep the old one. Luckily, AVX-512 provides an intrinsic that does exactly this: it merges elements conditionally within the lanes, choosing between <code>upd</code> and the <code>dst</code> based on the mask bits.</p>\n<p><span><img alt=\"Diagram 16.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_16_9486d1cabb.jpg&w=2048&q=75\"></span></p>\n<p>Congratulations, we’ve just unpacked <strong>eight values in a single iteration</strong>!</p>\n<p>Now that the data is ready, we can compute distances. For that, we use <a target=\"_blank\" href=\"https://github.com/ashvardanian/SimSIMD\">SimSimd</a>, an amazing library that performs vectorized distance calculations on almost any hardware.</p>\n<h2 id=\"benchmarks\"></h2>\n<p>We ran benchmarks on the <a target=\"_blank\" href=\"https://clickhouse.com/docs/getting-started/example-datasets/hackernews-vector-search-dataset\">HackerNews dataset</a>, which contains around <strong>29 million comments</strong> represented as <code>Float32</code> embeddings. We measured the speed of searching for a single new comment (using its embedding) and computed the recall based on 10 new comments.</p>\n<p><em>Recall</em> here is the fraction of true nearest neighbours that appear among the top-k retrieved results (in our case, <em>k = 20</em>). <em>Granularity</em> is how many bit groups we read.</p>\n<p><span><img alt=\"Diagram 17.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FDiagram_17_56c83fcb80.jpg&w=2048&q=75\"></span></p>\n<p>We achieved nearly <strong>2× speed-up</strong> with a good recall.
