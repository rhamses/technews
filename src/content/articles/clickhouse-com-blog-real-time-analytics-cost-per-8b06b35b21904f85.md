contentHtml: "<div><h2 id=\"tl-dr\"></h2>\n<p>A benchmark for real-time analytics needs to measure the system end-to-end: fresh data in, query-ready data maintained, fast answers out, and the cost of keeping that full path running.</p>\n<p>That is what CostBench measures. It captures the cost and latency of continuous ingest, data maintenance, and query execution together, because different systems spend work in different places.</p>\n<p>A read-only benchmark on a static dataset can show how fast queries return once the data is already prepared. It does not show the cost of making that data query-ready, or whether queries stay fast while fresh data is continuously arriving and being maintained in parallel.</p>\n<p>In this post, we use CostBench to compare Snowflake and ClickHouse Cloud across that full real-time analytics path.</p>\n<p><strong>Prefer a video walkthrough?</strong></p>\n<p>This webinar covers the same benchmark story in video form, with a deeper look at the mechanics behind the results: full-path cost-performance, continuously changing data, and why ClickHouse is query-ready on ingest and materialized views stay in sync with the base table.</p>\n<h2 id=\"user-content-realtime_analytics_does_not_start_when_a_query_runs\"></h2>\n<blockquote>\n<p>Real-time analytics starts when fresh data arrives.</p>\n</blockquote>\n<p>Before a dashboard, user, or AI agent can get a fast answer, the system has already done a lot of work: ingesting new rows, organizing them for pruning, maintaining derived tables, preserving freshness, and keeping read capacity available for low-latency queries.</p>\n<p>That full path is what <a target=\"_blank\" href=\"https://clickhouse.com/blog/costbench-data-warehouse-cost-performance\">CostBench</a> is designed to measure: not just the final read query, but the full running system that turns fresh data into fast answers.</p>\n<p>That was also the core idea behind our <a target=\"_blank\" href=\"https://clickhouse.com/blog/write-side-cost-performance-snowflake-clickhouse\">earlier benchmark on query-ready data</a>. We measured one important aspect of this path: the cost-performance of continuously ingesting data <strong>and</strong> keeping raw data physically organized for fast analytical reads.</p>\n<p>Snowflake <a target=\"_blank\" href=\"https://www.snowflake.com/en/blog/engineering/efficient-snowflake-ingestion-query-ready/\">responded</a> to that benchmark with a set of recommendations: use different ingestion methods, use larger warehouses for loading, and use Snowflake’s newer real-time features where available.</p>\n<p>Some of those recommendations improve a Snowflake setup. Others answer a different question, such as how quickly Snowflake can batch-load data, when the objective is maximum throughput rather than sustained query-readiness. But all of them point back to the same principle we started with:</p>\n<blockquote>\n<p>A real-time analytics system should be benchmarked as a full path, not as isolated ingest, maintenance, or read tests.</p>\n</blockquote>\n<p>That is what this post does. We use CostBench to rerun the comparison as an end-to-end benchmark: continuous ingest, raw-data organization, pre-aggregation freshness, and continuous query serving. We test two Snowflake paths: the broadly available standard-table setup and the newer Interactive Tables setup.</p>\n<p>All benchmark code and results are available in the <a target=\"_blank\" href=\"https://github.com/ClickHouse/CostBench/tree/main/full-path-realtime/quotes\">CostBench repository</a>. The stock-quotes dataset requires a <a target=\"_blank\" href=\"https://github.com/ClickHouse/CostBench/tree/main/full-path-realtime/quotes#data-source--licensing\">separate data license</a>, so the data itself cannot be redistributed.</p>\n<br>\n<h2 id=\"costbench-measures-the-complete-analytics-path\"></h2>\n<blockquote>\n<p>Loading a static dataset, running each query multiple times, and reporting the fastest hot-cache result does not reflect the performance or cost of a real-time analytics system.</p>\n</blockquote>\n<p>Most database benchmarks load a static dataset once, let the system fully prepare it, then run each query multiple times and report the fastest hot-cache result. That measures repeated reads over stable, already-prepared data. It does not show the time and cost of making fresh data query-ready, or how queries behave when they run continuously over data that keeps changing, while ingest, maintenance, and refresh work keep running in parallel and caches never settle on a single static view.</p>\n<p>That was our motivation for creating CostBench.</p>\n<p>CostBench measures cost-performance across the complete analytics path:</p>\n<p><span><img alt=\"super_cool_01.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsuper_cool_01_8e3ad63faf.gif&w=2048&q=75\"></span></p>\n<p>① Fresh data arrives continuously.</p>\n<p>② The system writes that data and makes it <a target=\"_blank\" href=\"https://clickhouse.com/blog/write-side-cost-performance-snowflake-clickhouse#what-does-query-ready-mean\">query-ready</a>.</p>\n<p>③ Raw data is kept in an ordered layout, so later queries can skip most of the table instead of scanning everything.</p>\n<p>④ The system maintains pre-aggregated data, so the lowest-latency queries read even less at query time.</p>\n<p>⑤ Finally, the system has to serve fast answers continuously over constantly changing data, while ingest, maintenance, and refresh work keep running in the background.</p>\n<blockquote>\n<p><strong>CostBench is not a bulk-load or backfill benchmark</strong><br>\nCostBench simulates a <a target=\"_blank\" href=\"https://clickhouse.com/blog/selecting-a-real-time-analytical-database\">real-time analytics system</a> in which fresh data is continuously generated at the source and must become query-ready as it arrives. It is not a bulk-load or backfill benchmark that asks how quickly a system can load data that already exists.</p>\n</blockquote>\n<p>In this post, we apply that methodology to Snowflake and ClickHouse.</p></div><div><h2 id=\"user-content-what_our_first_benchmark_measured_queryready_raw_data\"></h2>\n<p>Our <a target=\"_blank\" href=\"https://clickhouse.com/blog/write-side-cost-performance-snowflake-clickhouse\">original benchmark</a> measured one important part of the full <a target=\"_blank\" href=\"https://clickhouse.com/blog/selecting-a-real-time-analytical-database\">real-time analytics</a> path: the cost of continuously turning newly written raw data into query-ready raw data.</p>\n<p>Below is the original setup, along with Snowflake's main comments that it helps clarify.</p>\n<p><span><img alt=\"super_cool_02.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsuper_cool_02_cfb22bda80.gif&w=2048&q=75\"></span></p>\n<h3 id=\"user-content-dataset_and_ordering_key\"></h3>\n<p>We used the <a target=\"_blank\" href=\"https://benchmark.clickhouse.com/\">ClickBench</a> web analytics dataset, with <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickBench/blob/main/clickhouse-cloud/create.sql\">more than 100 columns and the original multi-column sorting key</a> used by the ClickBench <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickBench/blob/main/clickhouse-cloud/queries.sql\">workload</a>.</p>\n<p>That choice was deliberate. Many ClickBench queries benefit from this ordering in ClickHouse, so to keep later query performance measurements fair, we used the equivalent clustering key in Snowflake.</p>\n<blockquote>\n<p><strong>Snowflake’s comment:</strong> use a simpler clustering key, and avoid the artificial arrival pattern created by repeating the original ClickBench dataset to reach 100 billion rows.</p>\n</blockquote>\n<p>That is fair, and we address both in the expanded benchmark below. But they actually answer different questions: how data arrives, and what physical layout the system has to maintain for the workload.</p>\n<h3 id=\"user-content-continuous_ingest_at_a_fixed_rate\"></h3>\n<p>We ingested data continuously at roughly 1 million rows per second, or about 1 GB of uncompressed data per second.</p>\n<p>This was not a maximum-throughput loading test. The ingest rate was intentionally fixed to simulate a real-time workload where new data arrives continuously, and the goal was to use the smallest, lowest-cost Snowflake setup that could sustain that rate while keeping the table query-ready.</p>\n<blockquote>\n<p><strong>Snowflake’s comment:</strong> use COPY INTO, Snowpipe Streaming, larger warehouses, and Gen2 warehouses.</p>\n</blockquote>\n<p>Those are reasonable choices for other ingest tests. But in this benchmark, the loading mechanism was secondary. The question was not how quickly Snowflake could finish loading 100 billion rows, but what it would cost to keep up with a fixed real-time ingest rate as common in real-time analytics use cases.</p>\n<h3 id=\"user-content-queryready_raw_data_not_preaggregation\"></h3>\n<p>The first benchmark focused on the base table: newly written raw data in, query-ready raw data out. It did not measure materialized views.</p>\n<blockquote>\n<p><strong>Snowflake’s comment:</strong> broader production setups should include more of the data pipeline.</p>\n</blockquote>\n<p>Agreed. That is exactly what CostBench adds next: derived-data maintenance, freshness, and reads alongside ingest and raw-data organization.</p>\n<h3 id=\"user-content-reads_measured_after_loading\"></h3>\n<p>After the table reached 100 billion rows, we ran the ClickBench query workload once to validate query performance.</p>\n<p>So the first benchmark did not measure continuous serving while ingest, clustering, refresh, or other maintenance work continued in the background.</p>\n<blockquote>\n<p><strong>Snowflake’s comment:</strong> use Interactive Tables and Interactive Warehouses for high-concurrency, low-latency serving.</p>\n</blockquote>\n<p>Fair enough. Interactive Tables were not part of the first benchmark because that benchmark used the Snowflake path most customers could actually use: standard tables with clustering. Interactive Tables are a newer feature and are currently available only in selected regions.</p>\n<p>For the expanded benchmark, we therefore test both paths: the broadly available Snowflake setup using standard tables and materialized views, and an Interactive Tables setup in a supported region.</p>\n<h2 id=\"user-content-the_expanded_benchmark_addresses_the_broader_question\"></h2>\n<p>Before Snowflake published its response, we had already started applying the new CostBench methodology to <a target=\"_blank\" href=\"https://github.com/ClickHouse/CostBench/tree/main/full-path-realtime/quotes\">a broader full-path benchmark</a>.</p>\n<p>This time, we intentionally started at the easier end of the spectrum: a much simpler dataset and ordering key, a cleaner arrival pattern, and continuous reads while data keeps moving, a setup that removes several of the factors Snowflake objected to in the original ClickBench test.</p>\n<p>We will repeat this with heavier datasets later. But first, we wanted to measure the full path in the cleanest possible case.</p>\n<p><span><img alt=\"super_cool_03.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsuper_cool_03_511670f5b9.gif&w=2048&q=75\"></span></p>\n<h3 id=\"user-content-simpler_dataset_timestampordered_ingest\"></h3>\n<p>We use <a target=\"_blank\" href=\"https://github.com/ClickHouse/CostBench/tree/main/full-path-realtime/quotes#dataset\">a real stock market quotes dataset</a> licensed from a <a target=\"_blank\" href=\"https://github.com/ClickHouse/CostBench/tree/main/full-path-realtime/quotes#data-source--licensing\">data provider</a>, with access to hundreds of billions of rows.</p>\n<p>Compared with ClickBench, it has a much simpler shape: <a target=\"_blank\" href=\"https://github.com/ClickHouse/CostBench/tree/main/full-path-realtime/quotes#schema-vendor-agnostic\">12 columns</a>, a simple two-column sorting key, and a natural timestamp order.</p>\n<p>We ingest the data in strict timestamp order at steady rate of 1 million rows per second. At that rate, the system receives 100 billion fresh rows every 28 hours.</p>\n<h3 id=\"user-content-simple_clustering_key\"></h3>\n<p>This time, the sorting/clustering key are just two columns: <code>(sym, t)</code> - the stock symbol and the timestamp. This is as natural and simple as it can get.</p>\n<p>ClickHouse <a target=\"_blank\" href=\"https://github.com/ClickHouse/CostBench/blob/6fb94fd628b100db69bc2bf9f8d6f149eec54601/full-path-realtime/quotes/clickhouse-cloud/create.sql#L22\">sorts</a> the raw table by those columns, and Snowflake <a target=\"_blank\" href=\"https://github.com/ClickHouse/CostBench/blob/6fb94fd628b100db69bc2bf9f8d6f149eec54601/full-path-realtime/quotes/snowflake/create.sql#L58\">clusters</a> the raw table by those columns.</p>\n<h3 id=\"user-content-preaggregations_included\"></h3>\n<p>Unlike the original benchmark, this run includes continuously maintained pre-aggregations.</p>\n<p>That means we also measure the cost of keeping derived data fresh while new rows keep arriving.</p>\n<h3 id=\"user-content-continuous_queries_on_the_matching_layouts\"></h3>\n<p>This time, queries run continuously while fresh data continues to arrive.</p>\n<p>The workload includes two query types: <strong>dashboard queries against the pre-aggregated data</strong>, and <strong>drill-down queries against the raw data</strong> with filters matching the raw table’s ordering/clustering key.</p>\n<p><strong>We keep the systems’ caches enabled</strong>. In benchmarks with static data, we usually disable query-result caches to avoid measuring memory lookups instead of pure engine performance. Here, the data is constantly changing, so caches are much less useful, and leaving them enabled better reflects real-world usage.</p>\n<p><strong>We run each query once per round</strong>. That mirrors how these queries are used in practice: a dashboard refresh, a user drill-down, or an exploratory ad-hoc query happens once against the latest state of the data.</p>\n<p>That simulates the real-time scenario more directly: ingest, maintenance, freshness, and reads all happen at the same time.</p>\n<h2 id=\"user-content-clickhouse_cloud_setup\"></h2>\n<p>For ClickHouse Cloud, we used separate services for ingest and reads, so the write path and query path were <a target=\"_blank\" href=\"https://clickhouse.com/blog/introducing-warehouses-compute-compute-separation-in-clickhouse-cloud\">isolated</a> from each other.</p>\n<p><span><img alt=\"super_cool_04.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fsuper_cool_04_ed5d57168d.gif&w=2048&q=75\"></span></p>\n<h3 id=\"user-content-client_setup\"></h3>\n<p>The <a target=\"_blank\" href=\"https://github.com/ClickHouse/CostBench/blob/main/full-path-realtime/quotes/clickhouse-cloud/ingest_parquet_dir.py\">client</a> (benchmark driver) is kept intentionally simple and it performs the the same work for ClickHouse and Snowflake.</p>\n<p>It reads Parquet row groups directly from existing Parquet files in binary form, combines them into batches of roughly 1 million rows, and sends those batches to the target system.
