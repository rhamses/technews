It was designed to handle analytical workloads on big data sets using column-oriented database principles similar to ClickHouse. As part of the AWS offering, it is often the default solution AWS users turn to for their analytical data needs.</p>\n<p>While attractive to existing AWS users due to its tight integration with the Amazon ecosystem, Redshift users that adopt it to power real-time analytics applications find themselves in need of a more optimized solution for this purpose. As a result, they increasingly turn to ClickHouse to benefit from superior query performance and data compression, either as a replacement or a “speed layer” deployed alongside existing Redshift workloads.</p>\n<p>In this blog, we explore why users move workloads from Redshift to ClickHouse, providing evidence of increased compression and query performance and describe options for migrating data – in bulk, as well as continuously appending new data using AWS EventBridge, AWS Lambda and AWS Glue.</p>\n<h2 id=\"clickhouse-vs-redshift\"></h2>\n<p>For users heavily invested in the AWS ecosystem, Redshift represents a natural choice when faced with data warehousing needs. Redshift differs from ClickHouse in this important aspect – it optimizes its engine for data warehousing workloads requiring complex reporting and analytical queries. Across all deployment modes, the following two limitations make it difficult to use Redshift for real-time analytical workloads:</p>\n<ul>\n<li>Redshift <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/dg/c-query-performance.html\">compiles code for each query execution plan</a>, which adds significant overhead to first-time query execution (up to 2s in our testing). This overhead can be justified when query patterns are predictable and compiled execution plans can be stored in a <a target=\"_blank\" href=\"https://medium.com/@success.gritfeat/amazon-redshift-query-code-compilation-cache-153319fabef6\">query cache</a>. However, this introduces challenges for interactive applications with variable queries. Even when Redshift is able to exploit this code compilation cache, ClickHouse is faster on most queries - see \"Benchmarks\" and  \"ClickHouse vs Redshift Query Comparison\" below.</li>\n<li>Redshift <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/dg/c_workload_mngmt_classification.html\">limits concurrency to 50 across all queues</a>, which (while adequate for BI) makes it inappropriate for highly concurrent analytical applications.</li>\n</ul>\n<p>Conversely, while ClickHouse can also be utilized for complex analytical queries it is optimized for real-time analytical workloads, either powering applications or acting as a <a target=\"_blank\" href=\"https://clickhouse.com/resources/engineering/how-to-choose-a-database-for-real-time-analytics-in-2026\">warehouse acceleration layer</a>. As a result, Redshift users typically replace or augment Redshift with ClickHouse for the following reasons:</p>\n<ul>\n<li><strong>ClickHouse achieves lower query latencies</strong>, including for varied query patterns, under high concurrency and while subjected to streaming inserts. Even when your query misses a cache, which is inevitable in interactive user-facing analytics, ClickHouse can still process it fast.</li>\n<li><strong>ClickHouse places much higher limits on concurrent queries</strong>, which is vital for real-time application experiences. In ClickHouse, self-managed as well as cloud, you can scale up your compute allocation to achieve the concurrency your application needs for each service. The level of permitted query concurrency is <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/server-configuration-parameters/settings#max-concurrent-queries\">configurable in ClickHouse</a>, with ClickHouse Cloud defaulting to a value of 1000.</li>\n<li><strong>ClickHouse offers superior data compression</strong>, which allows users to reduce their total storage (and thus cost) or persist more data at the same cost and derive more real-time insights from their data. See \"ClickHouse vs Redshift Storage Efficiency\" below.</li>\n</ul>\n<p>Users additionally appreciate ClickHouse for its wide-ranging support of real-time analytical capabilities, such as:</p>\n<ul>\n<li><strong>Large range of specialized analytical functions</strong> designed to shorten and simplify query syntax, e.g., <a target=\"_blank\" href=\"https://clickhouse.com/blog/aggregate-functions-combinators-in-clickhouse-for-arrays-maps-and-states\">aggregate combinators</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/array-functions/\">array functions</a></li>\n<li><strong>SQL query syntax designed to make analytical queries easier,</strong> e.g., ClickHouse does not enforce aliases in the SELECT</li>\n<li><strong>Superior <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/data-types\">data types</a> support</strong>, including <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/dg/r_Character_types.html#r_Character_types-varchar-or-character-varying\">Strings longer than 65k characters</a>, <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/dg/c_unsupported-postgresql-datatypes.html\">Enums, and Arrays</a>, which are commonly needed for analytical query schema</li>\n<li><strong>Superior <a target=\"_blank\" href=\"https://clickhouse.com/blog/data-formats-clickhouse-csv-tsv-parquet-native\">file and data formats</a> support</strong>, compared to a more <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/dg/r_COPY.html\">limited selection in Redshift</a>, simplifying the import and export of analytical data,</li>\n<li><strong>Superior <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/integrations\">federated querying capabilities</a></strong>, enabling ad-hoc queries against a wide range of data lakes and data stores, including <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/table-functions/s3\">S3</a>, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/integrations/mysql\">MySQL</a>, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/table-functions/postgresql\">Postgres</a>, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/table-functions/mongodb\">MongoDB</a>, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/integrations/deltalake\">Delta Lake</a>, and more</li>\n<li><strong>Secondary Indexes &amp; Projections</strong> - ClickHouse supports <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/skipping-indexes\">secondary indices</a>, including <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/invertedindexes#usage\">inverted indices for text matching</a>, as well <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#projections\">Projections</a> to allow users to target specific queries for optimization.</li>\n</ul>\n<h3 id=\"redshift-deployment-options\"></h3>\n<p>When deploying Redshift, users are presented with several options, each with respective strengths and weaknesses for different workloads:</p>\n<p><strong><a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/working-with-serverless.html\">Redshift Serverless</a></strong> - A recent addition to the Redshift product lineup (<a target=\"_blank\" href=\"https://aws.amazon.com/about-aws/whats-new/2022/07/amazon-redshift-serverless-generally-available/\">GA in July 2022</a>), this offering separates storage and compute and automatically provisions and scales the warehouse capacity based on query load. Similar to <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a>, this is a fully managed offering where instances are automatically upgraded. Available compute capacity is measured through a <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/serverless-capacity.html\">custom Redshift Processing Units (RPU) unit</a> (approximately two virtual CPUs and 16 GB of RAM), for which the user sets a limit (defaulting to 128). Users are charged for the data stored, and the compute capacity consumed while the warehouse is active with 1-second granularity and a minimum charging period of 1 minute. While <a target=\"_blank\" href=\"https://chariotsolutions.com/blog/post/first-look-at-amazon-redshift-serverless/\">changing RPU limits requires notable downtime</a>, this offering is suitable for ad-hoc analytics where performance is not critical, and workloads are variable with potential idle time. However, it is less appropriate for high or potentially unbounded and unpredictable query workloads, e.g., for applications where the load is based on the number of users. Furthermore, if latency is critical, users typically lean to the provisioned choices below.</p>\n<p><strong><a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/overview.html\">Redshift Provisioned</a></strong> - The original Redshift offering, with recent additions and improvements, offers users several choices:</p>\n<ul>\n<li><strong><a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/working-with-clusters.html\">DC2 nodes</a></strong> - Designed for compute-intensive data warehouses based on local SSD storage, where query latency is critical. Redshift recommends <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/working-with-clusters.html\">these for datasets that are less than 1TB compressed</a>. Users can select specific <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/working-with-clusters.html#rs-upgrading-to-ra3\">node sizes and the number of nodes</a> to increase total capacity.</li>\n<li><strong><a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/working-with-clusters.html\">RA3 nodes</a></strong> - These nodes offer higher storage to compute ratios and offload data to S3 once the local disk is full, using a feature known as <a target=\"_blank\" href=\"https://aws.amazon.com/blogs/big-data/use-amazon-redshift-ra3-with-managed-storage-in-your-modern-data-architecture/\">Managed Storage</a>. This ability is comparable to ClickHouse Cloud's shared-nothing architecture, where the local disk acts as a cache with s3 offering unbounded storage capacity. Note, however, that, unlike ClickHouse Cloud, data In Redshift is still associated with a specific node, preventing storage and compute from being scaled and paid for completely independently. Storage costs are priced independently of where the data resides (i.e., local disk or s3), with users <a target=\"_blank\" href=\"https://aws.amazon.com/redshift/pricing/\">paying only for managed storage used.</a></li>\n</ul>\n<p>In the rest of this post, we show how Redshift users can migrate data in bulk to ClickHouse, as well as keep data synchronized between the new systems in side-by-side deployments.</p>\n<h2 id=\"setup-and-dataset\"></h2>\n<p>Examples in this blog post utilize <a target=\"_blank\" href=\"https://clickhouse.cloud/signUp?loc=blog-redshift\">ClickHouse Cloud</a>, which has a free trial that allows the completion of the scenarios we cover. We apply these recommendations to all of our table schemas.</p>\n<p>Currently, codecs in ClickHouse must be specified when creating tables. These can, however, be combined (e.g., <code>CODEC(Delta, ZSTD)</code>). Furthermore, ClickHouse allows these compression algorithms to be tuned, usually sacrificing compression or decompression speed for increased space savings (e.g. <code>ZSTD(9)</code> offers higher reduction rates than <code>ZSTD(3)</code> at the cost of slower compression, but largely consistent decompression performance at query time). This increased tunability helps ClickHouse achieve higher compression rates.</p>\n<h3 id=\"sorting-keys\"></h3>\n<p>Both ClickHouse and Redshift have the concept of a “sorting key”, which defines how data is sorted when being stored. Redshift defines the sorting key using the <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/dg/r_CREATE_TABLE_NEW.html\">SORTKEY</a> clause:</p>\n<div><pre><code><span><span>CREATE TABLE</span> some_table(...) SORTKEY (column1, column2)</span></code></pre></div>\n<p>Comparatively, ClickHouse uses an ORDER BY clause to specify the sort order:</p>\n<div><pre><code><span><span>CREATE TABLE</span> some_table(...) ENGINE <span>=</span> MergeTree <span>ORDER</span> <span>BY</span> (column1, column2)</span></code></pre></div>\n<p>In most cases, users can use the same sorting key columns and order in ClickHouse as Redshift, assuming you are using the default <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/dg/t_Sorting_data.html\">COMPOUND type</a>. When data is added to Redshift, you should run a <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/dg/r_VACUUM_command.html\">VACUUM</a> and <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/dg/r_ANALYZE.html\">ANALYZE</a> commands to re-sort newly added data and update the statistics for the query planner - otherwise, the unsorted space grows. No such process is required for ClickHouse.</p>\n<p>Redshift supports a couple of convenience features for sorting keys. One is automatic sorting keys (using SORTKEY AUTO), which may be appropriate for getting started, but explicit sorting keys ensure the best performance and storage efficiency when the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/improving-query-performance/sparse-primary-indexes/sparse-primary-indexes-cardinality/\">sorting key is optimal</a>. The other is the <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/dg/r_CREATE_TABLE_NEW.html\"><code>INTERLEAVED</code></a> sort key, which gives equal weight to a subset of columns in the sort key to improve performance when a query uses one or more secondary sort columns. ClickHouse supports explicit <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter/projection/\">projections</a>, which achieve the same end result with a slightly different setup.</p>\n<p>Users should be aware that the “primary key” concept represents different things in ClickHouse and Redshift. In Redshift, the primary key resembles the traditional RDMS <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Primary_key\">concept</a> intended to enforce constraints. However, they are not strictly enforced in Redshift and instead act as hints for the<a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/dg/c_best-practices-defining-constraints.html\"> query planner</a> and <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/dg/c_choosing_dist_sort.html\">data distribution among nodes</a>. In ClickHouse, the primary key denotes columns used to construct the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes\">sparse primary index</a>, used to ensure the data is ordered on disk, maximizing compression while avoiding pollution of the primary index and wasting memory.</p>\n<h3 id=\"example-table\"></h3>\n<p>In this example, we assume our data is only present in Redshift, and we are unfamiliar with the equivalent ClickHouse Ethereum schemas. This approach is easy to implement and maintain. It assumes our data is immutable, with only rows added, and having a property (usually a timestamp) that can be used to identify new data. For our example, suppose we schedule an export every hour of the last 60 minutes of data. This further assumes new rows will be inserted in real time with no delays. In most cases, this is unlikely, with new rows having some delay and offset from the current time. Every time we run an export, we need to export rows from a window offset from the current time. For example, suppose we were confident our data would be available within 15 minutes. We would in turn export all rows from <code>&lt;scheduled_time&gt;-75mins</code> to <code>&lt;scheduled_time&gt;-15mins</code>.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Scheduling_Exports_5186906f3e.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FScheduling_Exports_5186906f3e.png&w=2048&q=75\"></span></a></p>\n<p>This approach relies on data being reliably inserted to Redshift within 15 minutes.</p>\n<h4 id=\"redshift-native\"></h4>\n<p>Redshift supports native <a target=\"_blank\" href=\"https://aws.amazon.com/premiumsupport/knowledge-center/redshift-schedule-query/\">scheduled query functionality</a>, but it is not a viable choice for our purposes. First, it does not support the ability to reference scheduled time needed for our offset calculation. Second, this functionality is only <a target=\"_blank\" href=\"https://docs.aws.amazon.com/redshift/latest/mgmt/query-editor-schedule-query.html\">provided for provisioned and not serverless clusters.</a> Using Redshift native scheduling may be sufficient for users who want to perform periodic table export independent of the scheduled time.
