contentHtml: "<div><p><a target=\"_blank\" href=\"https://www.respan.ai/\">Respan</a> (formerly Keywords AI) is building an AI gateway with built-in observability. Designed for LLM applications running in production, the platform routes requests across models and providers while giving teams visibility into performance, evaluations, and prompt management.</p>\n<p>Part of YC’s W24 cohort, the company quickly gained traction with thousands of developers, and traffic grew from a few hundred requests per day to roughly 30 million requests per day, or close to one billion requests per month. Alongside live LLM calls, cached requests also generate observability data, pushing overall event volume even higher.</p>\n<p>Today, Respan processes around 50 million events per day. At that scale, activity is constant. \"There are thousands of events going through our pipeline as we speak,\" said co-founder and CTO Raymond Huang at a <a target=\"_blank\" href=\"https://clickhouse.com/videos/meetupsf_dec_20251\">December 2025 meetup in San Francisco</a>.</p>\n<p>At the meetup, Raymond walked through a live demo showing how Respan’s backend evolved from a simple Postgres-based setup to <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a>, which now powers high-throughput ingestion, fast analytics, and production-grade LLM observability.</p>\n<h2 id=\"from-postgres-to-clickhouse\"></h2>\n<p>Respan is a lean team with a true startup mentality. \"We move fast and we build fast,\" Raymond says. Early on, the platform’s backend reflected that scrappy mindset: a Django app backed by Postgres, logging each request as it arrived. \"One request comes in, it goes into Postgres, and we store it,\" Raymond explains. \"It’s that simple.\"</p>\n<p>At low volumes, the approach worked. The system handled tens of events per second without trouble, and the mental model was easy to reason about. But as workloads climbed into the 50 to 100 requests per second range, transactions started to contend with one another.</p>\n<p>Postgres was behaving exactly as it should, serializing work to preserve correctness, but under steady write pressure, each insert had to complete its transaction and be recorded in the write-ahead log before subsequent writes could proceed. As Raymond puts it, “Things start to pile up, and from there they escalate quickly.”</p>\n<p>There was a clear mismatch between Postgres’s transactional model and the demands of real-time observability at scale. Squeezing more out of their current setup wasn’t an option, so the team decided to look for a better solution. They found it in ClickHouse Cloud.</p>\n<p>\"We decided to move to ClickHouse,\" Raymond says. \"That helped significantly. We can now easily handle the scale that we couldn’t before.\"</p>\n<h2 id=\"designing-logs-for-sustained-ingestion\"></h2>\n<p>As they began migrating to ClickHouse, the team focused on getting the schema right. They knew it could handle the write volume, but only if the data model supported it.</p>\n<p>Logs were designed to be compact and structured, storing only the fields that would actually be queried or aggregated. Metrics and metadata—latency, throughput, routing time, cost—are written as typed columns optimized for analytical workloads.</p>\n<p>Larger text fields, like prompt inputs and model outputs, are deliberately truncated before ingestion. The goal isn’t to capture full transcripts, but to preserve enough context for debugging and analysis without letting row size grow unchecked.</p>\n<p>\"We don’t store big data in ClickHouse because memory efficiency is important,\" Raymond says. \"We store minimal information so we can keep each message small and the ingestion rate as high as possible.\"</p></div><div><h2 id=\"building-fast-analytics-with-materialized-views\"></h2>\n<p>Ingesting data at scale is only useful if the analytics layer can keep up. Respan's customers expect dashboards that load quickly and support common slices of data without delay. To make that happen, the team relies heavily on <a target=\"_blank\" href=\"https://clickhouse.com/docs/materialized-view/incremental-materialized-view\">incremental materialized views</a>.</p>\n<p>Raw logs are first aggregated into minute-level windows, partitioned by organization, then cascaded into hourly rollups. Each materialized view targets a specific dimension—organization and API key, customer identifier, environment, deployment or model—so dashboards query pre-aggregated data instead of scanning raw logs.</p>\n<p>\"This way, we don’t have to recompute all the aggregations,\" Raymond says. \"That saves us a lot of query power.\"</p>\n<p>By aggregating early and limiting recomputation, the team keeps query costs predictable and avoids full-table scans as the dataset grows. “With this breakdown, we can easily grab data and have optimal performance,” Raymond adds.</p>\n<p>Not every query needs to be real-time. Some dashboards require sorting and joining against user-level metadata—customer IDs, names, email addresses—alongside aggregated metrics. Grouping by every metadata column would make queries heavier and more expensive, especially as row counts grow.</p>\n<p>Instead, the team uses <a target=\"_blank\" href=\"https://clickhouse.com/docs/materialized-view/refreshable-materialized-view\">refreshable materialized views</a> for this layer of analytics. These views aggregate the necessary fields and refresh on a fixed cadence—every 10 minutes in Raymond’s demo—rather than updating on every insert.</p>\n<p>\"The user data doesn’t have to be real-time,\" Raymond explains. By separating high-frequency metrics from slightly delayed metadata, the system avoids wide <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/select/group-by\">GROUP BY</a> clauses and keeps joins efficient.</p>\n<p>Everything is written into <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/mergetree-family/mergetree\">MergeTree</a> tables, partitioned by time, so queries can filter aggressively before joining. The result is dashboards that remain fast and sortable, even when combining behavioral metrics with user attributes.</p>\n<h2 id=\"traces-without-expensive-reconciliation\"></h2>\n<p>Understanding complex LLM workflows doesn’t end with logs. Respan also supports tracing to show how individual requests move through the system. Each trace is composed of spans, which may arrive out of order in distributed environments.</p>\n<p>Rather than enforcing strict ingestion order, the system encodes relationships directly in the data. Spans reference their parents, and those relationships are resolved analytically at query time. \"Everything can be asynchronous as long as eventually they meet each other in the database,\" Raymond says. By avoiding coordination at write time, the pipeline remains fully asynchronous.</p>\n<p>When building trace aggregations, the team is equally deliberate. They avoid using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/select/from#final-modifier\">FINAL</a> modifier, which can force ClickHouse to recompute and merge large portions of a table at query time. Instead, trace metrics such as span counts, token usage, cost, and error rates are computed using aggregate functions. Functions like <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/aggregate-functions/reference/argmax\">argMax</a> allow the system to select the latest point-in-time values without triggering expensive full-table processing. The result is trace analytics that remain predictable and memory-efficient as span volume grows.</p>\n<h2 id=\"a-system-that-s-easier-to-operate-at-scale\"></h2>\n<p>As Respan’s system scaled, operational simplicity became increasingly important. One of ClickHouse’s biggest strengths, Raymond says, is the simplicity of its <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes\">indexing model</a>, which reduces what engineers have to manage day to day.</p>\n<p>\"This enables me to sort really quickly without having to worry about index-tree structure,\" he says. \"I only have to worry about if the partition is right and whether the querying data fits into the memory. If it doesn’t, I just scale the instance—it’s that simple.\"</p>\n<p>That predictability extends to everyday workflows like log search. Even without relying on advanced full-text search features, straightforward string queries can scan tens of millions of rows in sub-second time. As Raymond says, \"That’s pretty impressive.\"</p>\n<p>Today, ClickHouse underpins Respan’s observability stack from ingestion through customer-facing analytics. Most importantly, it provides a solid foundation that scales with the product, without forcing constant architectural revisions as usage grows.</p>\n<p>\"Big shoutout to the ClickHouse team,\" Raymond says. \"We built one of the best products in the LLM observability space—this wouldn’t have been possible without ClickHouse’s support.\"</p></div>"
