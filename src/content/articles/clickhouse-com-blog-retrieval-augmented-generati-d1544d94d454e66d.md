These services have proven useful for a wide range of applications, including technical users needing to write code snippets. SQL generation performs remarkably well when a schema and question is provided. At ClickHouse, we actually already exploit these capabilities, exposing the ability to query with natural language in our <a target=\"_blank\" href=\"https://clickhouse.com/blog/announcing-genai-powered-query-suggestions-clickhouse-cloud\">ClickHouse Cloud SQL console</a>.</p>\n<p>While ChatGPT is often sufficient to get started, when we want to build something at scale or integrate these capabilities into a production app, it invariably makes sense to explore equivalent services in a cloud provider. For AWS, the Bedrock service provides these capabilities by exposing foundational machine learning models (including LLMs) as a fully managed service. These models are contributed by companies such as Anthropic and Cohere and are made available through a simple API. This represented the simplest way to get started for my app.</p>\n<h2 id=\"retrieval-augmented-generation-rag\"></h2>\n<p>The term RAG also seems to be currently very widespread, with some companies gambling on its need being so pervasive that an entire class of databases has arisen to service this. <strong>Retrieval-augmented generation (RAG) is a technique that aims to combine the power of pre-trained language models with the benefits of information retrieval systems</strong>. The objective here is typically simple: to enhance the quality and relevance of generated text by providing the model with additional information. This falls into the field of prompt engineering, where we modify our question or prompt to include more useful information to help the LLM formulate a more accurate answer.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Click_House_RAG_Flow_31846db18a.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FClick_House_RAG_Flow_31846db18a.png&w=2048&q=75\"></span></a></p>\n<p>By providing additional information to the LLM, RAG aims to overcome a few problems users often experience when relying on models to generate text, most of which are the result of the LLM's internal knowledge being based on a fixed training corpus from a point in time. Without access to domain-specific or up-to-date information, the model can struggle in scenarios where the question goes beyond this foundational knowledge, resulting in either no answer or \"hallucinations\" where responses are not grounded in reality and are factually incorrect.</p>\n<p>To provide additional supporting information to the model for our Google Analytics use case, we need a means of finding content that is contextually relevant to the question at hand. In <a target=\"_blank\" href=\"https://clickhouse.com/blog/vector-search-clickhouse-p2#searching-vectors-in-clickhouse\">an earlier blog post</a>, we explored how this can be done with vector embeddings. To do this, we could use another model to generate embeddings for documents we will use as context, (e.g., internal documentation) and store these in a database. We can then use the same model to convert our user’s natural language question to an embedding and retrieve the most relevant content (e.g., top 10 documents) to use as context when making the request to our LLM model/service.</p>\n<p>While dedicated vector databases were specifically designed for only this function, databases like ClickHouse have native support for vector functionality as well. This means that ClickHouse can serve as <strong><em>both</em></strong> a vector and an analytics database, which simplifies overall architectures by removing the need for multiple bespoke data stores in RAG pipelines.</p>\n<p>This 2 step process of retrieval and generation is admittedly a simplistic overview of RAG (not least glossing over the biggest challenge of relevancy for the retrieved documents) but sufficient for our needs.</p>\n<p>As we’ll discover below, for our use case, RAG is also relevant as we needed to provide not only the table schema but also likely example queries for problems such as how to identify returning users or how the LLM should deal with less structured questions such as “Posts about Materialized views”.</p>\n<h2 id=\"a-little-bit-of-research\"></h2>\n<p>The foundation of our app is text to SQL. This is an active domain of research and thanks to the <a target=\"_blank\" href=\"https://yale-lily.github.io/spider\">Spider: Yale Semantic Parsing and Text-to-SQL Challenge</a> it is relatively easy to see which approaches are leading in providing the best accuracy.</p>\n<p><em>“The goal of the Spider challenge is to develop natural language interfaces to cross-domain databases. It consists of 10,181 questions and 5,693 unique complex SQL queries on 200 databases with multiple tables covering 138 different domains. To do well on it, systems must generalize well to not only new SQL queries but also new database schemas.”</em></p>\n<p>This specific challenge is more general than that of our Google Analytics question-to-text problem - ours is domain-specific, whereas Spider aims to measure the performance of cross-domain zero-shot performance. Despite this, the leader papers seemed worth exploring for inspiration. Reassuringly, the current leaders including <a target=\"_blank\" href=\"https://github.com/BeachWang/DAIL-SQL\">DAIL-SQL</a> rely on the principle of using prompt engineering and a RAG-based approach.</p>\n<p>The principle innovation with  <a target=\"_blank\" href=\"https://github.com/BeachWang/DAIL-SQL\">DAIL-SQL</a> is to mask keywords (e.g. columns and values) in a set of possible useful prompt questions (the “candidate set”), with an embedding generated for the question. A “skeleton” query is then generated (and masked) using a specialist pre-trained transformer model. Example questions for the prompt are in turn identified by comparing the question and its skeleton SQL against the candidate questions and their SQL. See <a target=\"_blank\" href=\"https://github.com/ClickHouse/bedrock_rag/blob/main/DAIL-SQL.md\">here</a> for a more detailed overview. This is surprisingly simple and effective and offers some useful pointers on achieving decent results.</p>\n<p>While I did not need the flexibility of the cross-domain features of the above process, it did provide some hints on the need to achieve good results. Providing SQL examples for similar questions seemed essential to good performance - especially in our domain where concepts such as “returning users” cannot easily be deduced from the schema. However, the masking of questions and comparison of SQL queries seemed unnecessary, given the domain-specific nature of my problem.</p>\n<p>Most importantly, it's clear the problem should be decomposed into multiple steps.</p>\n<h2 id=\"udf-s-to-generate-embeddings\"></h2>\n<p>Given the above research, our RAG flow would invariably require us to be able to generate embeddings for text (e.g., to find similar questions). The components of the RAG flow were largely assembled independently with testing to ensure each delivered accurate results.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/Click_House_App_RAG_Flow_3b178d282e.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FClick_House_App_RAG_Flow_3b178d282e.png&w=2048&q=75\"></span></a></p>\n<p>In summary, our flow consists of two main stages to assist with prompt generation: Handling Concepts and Metric Extraction.</p>\n<p>Extraction of concepts attempts to identify if the question contains a conceptual filter and takes steps (1) to (5):</p>\n<ol>\n<li>We first identify if the question contains a concept using the <a target=\"_blank\" href=\"https://www.anthropic.com/index/claude-2\"><code>anthropic.claude-v2</code></a> model and <a target=\"_blank\" href=\"https://github.com/ClickHouse/bedrock_rag/blob/d7727bf25c5a3650b0875dab4228a21096b911b0/question_to_sql.py#L210\">a simple prompt</a>. If not, go to Metric Extraction and step (6).</li>\n<li>Convert the concept into an embedding using the <code>amazon.titan-embed-text-v1</code> model.</li>\n<li>Search ClickHouse for the top 3 most relevant pages using the embedding from step (2).</li>\n<li><a target=\"_blank\" href=\"https://github.com/ClickHouse/bedrock_rag/blob/d7727bf25c5a3650b0875dab4228a21096b911b0/question_to_sql.py#L89\">Prompt the</a> <code>anthropic.claude-v2</code> model to extract they key words and phrases from the pages returned in step (3)</li>\n<li>Modify the original question to associate the concept with the above words.</li>\n</ol>\n<p>Metric extraction aims to identify the main metrics which the question needs to compute, in order to ensure relevant examples are added to the prompt. This takes steps (6) to (9):</p>\n<ol>\n<li>Extract GA metrics <a target=\"_blank\" href=\"https://github.com/ClickHouse/bedrock_rag/blob/d7727bf25c5a3650b0875dab4228a21096b911b0/question_to_sql.py#L257\">by prompting</a> the <code>anthropic.claude-v2</code> model.</li>\n<li>Convert metrics into embeddings using the <code>amazon.titan-embed-text-v1</code> model.</li>\n<li>Query for the top matching question for each metric using the embeddings from step (7). Add these to the set of examples.</li>\n<li>Use a simple regex to establish if an area of the site is being targeted and add examples.</li>\n</ol>\n<p>Finally, we generate the prompt:</p>\n<ol>\n<li>Generate the final SQL prompt for the <code>anthropic.claude-v2</code> model to produce the SQL. Execute this against the site pages and <code>ga_daily</code> table.</li>\n</ol>\n<h2 id=\"handling-concepts-steps-1-to-5\"></h2>\n<p>As described above, we also wanted to have the flexibility to handle conceptual questions such as \"pages about X\". For this, we need the text content for the contextual information, which for our use case, are pages on our website. While writing a generic crawler can be challenging, a simple <a target=\"_blank\" href=\"https://scrapy.org/\">Scrapy-based</a> crawler for our limited site that exploited our sitemaps[<a target=\"_blank\" href=\"https://clickhouse.com/sitemap.xml\">1</a>]<a target=\"_blank\" href=\"https://clickhouse.com/docs/sitemap.xml\">[2]</a> and page structure should be more than sufficient. <a target=\"_blank\" href=\"https://github.com/ClickHouse/bedrock_rag/tree/main/spider\">The code</a> should be reusable as a basis for those looking to implement a similar service on their own site.</p>\n<p>To compare pages with a concept we need a means of:</p>\n<ol>\n<li>Extracting concepts from questions.</li>\n<li>Representing the concepts such that relevant pages can be identified.</li>\n</ol>\n<p>For (1), we experimented with a number of techniques but found the <a target=\"_blank\" href=\"https://www.anthropic.com/index/claude-2\"><code>anthropic.claude-v2 model</code></a>, available in Bedrock, to be highly effective. With an <a target=\"_blank\" href=\"https://github.com/ClickHouse/bedrock_rag/blob/d7727bf25c5a3650b0875dab4228a21096b911b0/question_to_sql.py#L210\">appropriate prompt</a> containing examples, this proved accurate at extracting the target concept.</p>\n<p>For (2), we first identify pages relevant to the concept extracted from step (1). For this, we create and store embeddings for each of our site pages based on their textual content as well as the concept itself. Given a source table <code>source_pages</code> with <code>url</code>, <code>raw_title</code>, and <code>raw_content</code> columns as shown below, we can insert rows to a target table <code>site_pages</code> invoking the <code>embed</code> function at insert time. These phrases and keywords are added to the prompt as an example question and answer. This is our domain-specific context that will help the LLM perform more accurately for our use case. For example, the concept “dictionaries” might result in the following being added to the prompt:</p>\n<div><pre><code><span><span>/* Answer the following: To filter by pages containing words: */</span></span>\n<span> <span>SELECT</span> page_location <span>FROM</span> ga_daily <span>WHERE</span> page_location <span>IN</span> (<span>SELECT</span> url <span>FROM</span> site_pages <span>WHERE</span> content ILIKE <span>'dictionary engine'</span> <span>OR</span> content ILIKE <span>'dictionary functions'</span> <span>OR</span> content ILIKE <span>'dictionary'</span> <span>OR</span> content ILIKE <span>'dictionary configuration'</span> <span>OR</span> content ILIKE <span>'cache'</span> <span>OR</span> content ILIKE <span>'dictionary updates'</span> <span>OR</span> content ILIKE <span>'dictionaries'</span>)</span></code></pre></div>\n<p>In addition, we rewrite the original question to indicate that the concept involves filtering on words.</p>\n<div><pre><code><span>What <span>are</span> the number <span>of</span> <span>new</span> users <span>for</span> blogs about dictionaries <span>over</span> <span>time</span>? </span>\n<span></span>\n<span>becomes…</span>\n<span></span>\n<span>What <span>are</span> the number <span>of</span> <span>new</span> users <span>for</span> blogs about dictionaries <span>over</span> <span>time</span>? <span>For</span> the topic <span>of</span> dictionaries, <span>filter</span> <span>by</span> dictionary configuration,dictionaries,dictionary functions,cache,dictionary engine,dictionary,dictionary updates</span></code></pre></div>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/uploads/RAG_extracting_concepts_82f7e5c9a7.png\"><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FRAG_extracting_concepts_82f7e5c9a7.png&w=2048&q=75\"></span></a></p>\n<p>The principle idea here is we would present these phrases to the user as those most representing the target concept, possibly with the matching pages. They could in turn choose to add or remove phases and words based on the results. While this is not necessarily the only way to represent a concept, it has the advantage of turning a loose idea such as a concept into something concrete. This approach is also simpler than the other obvious alternative: simply adding a filter to the main query, which filters pages based on as a distance function to the concept’s embedding. This latter approach requires us to either define a minimum score, which would need to be established, or only using the top K. Neither of these seemed realistic and explainable to the end user.</p>\n<p>Based on the research, it appeared that adding questions to the prompt would be essential in obtaining good results. This seemed even more important given that for many of the Google Analytics metrics such as “Returning users” or “Total sessions,” there is no easy way to deduce them from the schema. For example, as <a target=\"_blank\" href=\"https://clickhouse.com/blog/enhancing-google-analytics-data-with-clickhouse\">shown in our earlier blog</a>, we estimate the metric of “Returning users” as the following query:</p>\n<div><pre><code><span><span>SELECT</span> event_date, uniqExact(user_pseudo_id) <span>AS</span> returning_users</span>\n<span><span>FROM</span> ga_daily</span>\n<span><span>WHERE</span> (event_name <span>=</span> <span>'session_start'</span>) <span>AND</span> is_active_user <span>AND</span> (ga_session_number <span>&gt;</span> <span>1</span> <span>OR</span> user_first_touch_timestamp <span>&lt;</span> event_date)</span>\n<span><span>GROUP</span> <span>BY</span> event_date</span>\n<span><span>ORDER</span> <span>BY</span> event_date <span>ASC</span></span></code></pre></div>\n<p>This particular query would be challenging for the LLM to infer from just a schema. We therefore aim to provide this as context, when required, in our prompt. For example:</p>\n<div><pre><code><span><span>/*Answer the following: find returning users:*/</span></span>\n<span><span>SELECT</span> uniqExact(user_pseudo_id) <span>AS</span> returning_users <span>FROM</span> ga_daily <span>WHERE</span> (event_name <span>=</span> <span>'session_start'</span>) <span>AND</span> is_active_user <span>AND</span> (ga_session_number <span>&gt;</span> <span>1</span> <span>OR</span> user_first_touch_timestamp <span>&lt;</span> event_date)</span></code></pre></div>\n<p>Based on some initial experimentations, it also became apparent that providing all of the possible metrics as questions, with their SQL examples, in the prompt would degrade the prediction quality of the generated text. Longer prompts result in critical details being ignored and are also slower, consuming more tokens. We therefore opted for a simple supplementary table containing the question, its SQL response, and an embedding of the question itself:</p>\n<div><pre><code><span><span>CREATE TABLE</span> default.questions</span>\n<span>(</span>\n<span>  `question` String,</span>\n<span>  `query` String,</span>\n<span>  `embedding` <span>Array</span>(Float32)</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> question</span></code></pre></div>\n<p>We can populate this using the same UDF embed function as before.</p>\n<p>Initial experiments used the following query to identify the top 3 most relevant example questions:</p>\n<div><pre><code><span><span>SELECT</span> question, query <span>FROM</span> questions <span>ORDER</span> <span>BY</span> cosineDistance(embedding, embed(\"Show me returning users over the last 30 days for blog posts\")) <span>ASC</span> LIMIT <span>3</span></span></code></pre></div>\n<p>While simple, this delivered unsatisfactory results with the results not always including the GA metric that was required. We needed a means to extract:</p>\n<ul>\n<li>The specific Google Analytics metrics that the question included e.g. “returning users”.</li>\n<li>Whether an area of the site was being targeted by the question e.g. blogs or docs. This was likely common for our use case and translates to a specific filter on the url. This “domain knowledge” is also not inferable from the schema.</li>\n</ul>\n<p>For this task, we reuse the Claude model to extract the key metrics from the query <a target=\"_blank\" href=\"https://github.com/ClickHouse/bedrock_rag/blob/d7727bf25c5a3650b0875dab4228a21096b911b0/question_to_sql.py#L257\">using a prompt with examples</a>. This returns the key metrics which in turn is embedded and used to identify appropriate questions.</p>\n<p>For example, for the question “What are the number of returning users per day for the month of October for doc pages?” we extract the metric “returning users” leading to the following query:</p>\n<div><pre><code><span><span>SELECT</span> question, query <span>FROM</span> questions <span>ORDER</span> <span>BY</span> cosineDistance(embedding, embed(\"returning users\")) <span>ASC</span> LIMIT <span>1</span></span></code></pre></div>\n<p>The matching questions and their accompanying SQL are in turn added to our final prompt.
