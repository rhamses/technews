The slot was also now beginning to retain WAL for the decoding process, <strong>which is dangerous, as without a way to read from or drop the slot, it can continue retaining WAL indefinitely, risking storage exhaustion</strong>. A few months earlier, another customer using a different managed Postgres service saw the same symptoms while creating a few pipes on a read replica. While we were not able to deterministically solve it, tuning some settings (like turning on <a target=\"_blank\" href=\"https://postgresqlco.nf/doc/en/param/hot_standby_feedback/\"><code>hot_standby_feedback</code></a>) seemed to make it go away, so we attributed it to some idiosyncrasy in their managed service (we now know that this was not the case). This was when I set aside time to investigate this further.</p>\n<h2 id=\"waiting-for-a-commit-that-never-comes\"></h2>\n<p>I got my first clue from support for the customer's Postgres provider, which was a <code>strace</code> output on the backend process running the broken query:</p>\n<div><pre><code><span>strace: Process <span>117778</span> <span>attached</span></span>\n<span><span><span>restart_syscall</span><span>(&lt;... resuming interrupted nanosleep ...&gt;)</span> </span>= <span>0</span></span>\n<span><span>nanosleep</span>({tv_sec=<span>0</span>, tv_nsec=<span>1000000</span>}, <span>NULL</span>) = <span>0</span></span>\n<span><span>nanosleep</span>({tv_sec=<span>0</span>, tv_nsec=<span>1000000</span>}, <span>NULL</span>) = <span>0</span></span>\n<span><span>nanosleep</span>({tv_sec=<span>0</span>, tv_nsec=<span>1000000</span>}, <span>NULL</span>) = <span>0</span></span>\n<span><span>nanosleep</span>({tv_sec=<span>0</span>, tv_nsec=<span>1000000</span>}, <span>NULL</span>) = <span>0</span></span>\n<span><span>nanosleep</span>({tv_sec=<span>0</span>, tv_nsec=<span>1000000</span>}, <span>NULL</span>) = <span>0</span></span>\n<span><span>nanosleep</span>({tv_sec=<span>0</span>, tv_nsec=<span>1000000</span>}, <span>NULL</span>) = <span>0</span></span>\n<span>...</span></code></pre></div>\n<p>Seeing only <code>nanosleep</code> here and no IO or other syscalls would suggest that the backend is in a loop of <code>sleep()</code> calls with a constant duration of 1ms each. This was already a good clue since there are only a few places where such a loop exists in Postgres code. After finding a function in the control flow of creating replication slots that could sleep in this manner under certain conditions, I worked backwards to figure out what this function does and what can get it into this state. And while this bug is not that common in production databases, the \"reproduction\" of this issue is relatively trivial:</p>\n<ol>\n<li>Either set up or nicely ask a managed service to give you a Postgres cluster (v16+ since that's when standbys started supporting creation of logical replication slots) with a primary instance and a read replica.</li>\n<li>On the <em>primary</em>, start a transaction and perform any DML operation. As an optimization, Postgres only assigns transactions a transactionid/XID once they have written data, so this is to make the transaction \"real\". Don't COMMIT or ROLLBACK just yet; just leave the session open.</li>\n<li>On the <em>read replica</em>, create a logical replication slot (the most straightforward method would be to use the SQL function <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-REPLICATION\"><code>pg_create_logical_replication_slot</code></a>). Once you issue the command, Ctrl-C becomes useless. Trying to cancel or terminate the backend from another session doesn't work either. If you read syscalls from the backend process via <code>strace</code> or similar, you'd see a lot of <code>nanosleep</code> syscalls like the one above.</li>\n<li>COMMIT/ROLLBACK the transaction from step 2. Doing this will eventually cause the slot creation to return successfully (if you tried to cancel it earlier, it will notice the attempt now and cancel itself).</li>\n</ol>\n<p>Internally, creating a replication slot requires waiting for transactions before the slot creation query is issued to COMMIT/ROLLBACK, to reach a \"consistent point\" where the slot can decode all future transactions. While it is not ideal to have long-running transactions on Postgres for various reasons, the reality is that certain transactions (think reporting queries or large data backfills) can take a while. If we create a slot under these conditions, it will have to wait for transactions to complete and therefore take longer than usual.</p>\n<div><pre><code><span><span>2025-05-22 10:44:53.868 </span><span>UTC</span> [<span>1195</span>] <span>LOG:  00000:</span> <span>logical</span> <span>decoding</span> <span>found</span> <span>initial</span> <span>starting</span> <span>point</span> <span>at</span> <span>0</span><span>/356B148</span></span>\n<span><span>2025-05-22 10:44:53.868 </span><span>UTC</span> [<span>1195</span>] <span>DETAIL:</span>  <span>Waiting</span> <span>for</span> <span>transactions</span> <span>(approximately</span> <span>1</span><span>)</span> <span>older</span> <span>than</span> <span>6068 </span><span>to</span> <span>end.</span></span></code></pre></div>\n<p>Since waiting on these older transactions can take an arbitrary amount of time, it is crucial to implement this wait as efficiently as possible. Postgres already handles various locks for different operations, and we can reuse this infrastructure to take a lock on older transactions. Since transactions only release their <code>transactionid</code> lock after completing, acquiring this lock confirms that the transaction is done. This approach provides visibility—system tables display active waits, allowing administrators to monitor progress.</p>\n<div><pre><code><span><span>SELECT</span> pid,wait_event_type,wait_event,state,query </span>\n<span><span>FROM</span> pg_stat_activity</span>\n<span><span>WHERE</span> pid<span>=</span><span>804</span>;</span></code></pre></div>\n<div><pre><code><span>pid <span>|</span> wait_event_type <span>|</span>  wait_event   <span>|</span> state  <span>|</span>                             query</span>\n<span><span>-----+-----------------+---------------+--------+----------------------------------------------------------------</span></span>\n<span> <span>804</span> <span>|</span> Lock            <span>|</span> transactionid <span>|</span> active <span>|</span> <span>SELECT</span> pg_create_logical_replication_slot(<span>'demo_slot'</span>, <span>'pgoutput'</span>);</span>\n<span>(<span>1</span> <span>row</span>)</span></code></pre></div>\n<div><pre><code><span><span>SELECT</span> locktype,transactionid,pid,mode </span>\n<span><span>FROM</span> pg_locks</span>\n<span><span>WHERE</span> pid<span>=</span><span>804</span> <span>AND</span> granted<span>=</span><span>'f'</span>;</span></code></pre></div>\n<div><pre><code><span>locktype    | transactionid | pid |   mode</span>\n<span>---------------+---------------+-----+-----------</span>\n<span> transactionid |          6077 | 804 | ShareLock</span></code></pre></div>\n<p>If needed, one can cancel the problematic transactions or the slot creation process that’s still waiting. However, this holds only for a “typical” Postgres instance. As it turns out, being a Postgres read replica breaks some invariants, which leads to different behaviour in the same case.</p>\n<h2 id=\"read-replicas-aren-t-magic-actually\"></h2>\n<p>While \"read replica\" is the colloquial term for a Postgres instance serving read-only traffic (a term that makes it seem more straightforward than it actually is), Postgres refers to these as \"hot standbys\". A hot standby is a Postgres instance in \"recovery mode\" that constantly receives WAL records from a primary Postgres instance and uses these to maintain an exact copy of all data on the primary. The relevant detail here is that the standby can only indirectly observe what transactions running on the primary are doing via the write-ahead log. Specifically, the standby continuously maintains a list of transactions running on the primary known as <code>KnownAssignedXids</code> based on information from incoming WAL records.</p>\n<p>The function that implements the \"wait for a transaction to complete\" operation described earlier is named <a target=\"_blank\" href=\"https://github.com/postgres/postgres/blob/483f7246f39b3af250fed1e613d962b85b568861/src/backend/storage/lmgr/lmgr.c#L663\"><code>XactLockTableWait</code></a>, and the crucial part for us is this loop (code simplified for brevity):</p>\n<div><pre><code><span><span><span>void</span></span></span>\n<span><span><span>XactLockTableWait</span><span>(TransactionId xid, Relation rel, ItemPointer ctid,</span></span></span>\n<span><span><span>\t\t\t\t  XLTW_Oper oper)</span></span></span>\n<span><span>    &lt;...&gt;</span></span>\n<span><span>\t<span>for</span> <span>(;;)</span></span></span>\n<span><span>\t</span>{</span>\n<span>\t\t<span>Assert</span>(<span>TransactionIdIsValid</span>(xid));</span>\n<span>\t\t<span>SET_LOCKTAG_TRANSACTION</span>(tag, xid);</span>\n<span></span>\n<span>\t\t(<span>void</span>) <span>LockAcquire</span>(&amp;tag, ShareLock, <span>false</span>, <span>false</span>);</span>\n<span>\t\t<span>LockRelease</span>(&amp;tag, ShareLock, <span>false</span>);</span>\n<span></span>\n<span>\t\t<span>if</span> (!<span>TransactionIdIsInProgress</span>(xid))</span>\n<span>\t\t\t<span>break</span>;</span>\n<span></span>\n<span>        \t<span>pg_usleep</span>(<span>1000L</span>);</span>\n<span>\t}</span>\n<span>    &lt;...&gt;</span></code></pre></div>\n<p>Postgres acquires a lock on the transaction ID provided as input via <code>LockAcquire</code>, which hangs until the transaction completes and releases its lock. After obtaining the lock, we release it immediately and check if the transaction is still in progress via <a target=\"_blank\" href=\"https://github.com/postgres/postgres/blob/7c319f54917faf564b660fe9027c4835a422bad6/src/backend/storage/ipc/procarray.c#L1402\"><code>TransactionIdIsInProgress</code></a>. If it isn't, we exit. However, there is a 1ms sleep before the loop repeats, which we hit if we find the transaction is still running. If we only reach the check after we acquire a lock, how can this happen? As mentioned in a comment within this function, there is a window where the transaction has registered itself as running but hasn't yet acquired its lock on the transactionid. While the code handles this case regardless, the sleep is good for avoiding repeated locking until the transaction reaches a consistent state. Under regular operation, this case should rarely be hit and not for very long.</p>\n<p><span><img alt=\"User Image (5).png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FUser_Image_5_f945b563ad.png&w=2048&q=75\"></span></p>\n<p>Let's now consider the case of a hot standby. A standby still needs to find a consistent point while creating a logical replication slot, and older transactions need to end for that. It isn't the one running the transaction; therefore, the <code>LockAcquire</code> will always return immediately on standby. But <code>TransactionIdIsInProgress</code> does take <code>KnownAssignedXids</code> into account, so we know that the transaction is still running. Thus, we hit the 1ms sleep and then another loop iteration. But unlike earlier, this is not a transient situation; we can be stuck here for hours.</p>\n<ol>\n<li>The optimized <code>LockAcquire</code> wait on the primary is replaced by a fixed 1ms polling loop that wastes cycles if we need to wait a long time.</li>\n<li>If <code>LockAcquire</code> needs to wait, it also handles interrupts. Since the function was designed around waiting in <code>LockAcquire</code> and the sleep case is for transient cases, there is no code for handling interrupts within the loop. This is what made the backend process \"unkillable\".</li>\n<li>We don't report that we're waiting on an external operation, as <code>LockAcquire</code> handled this. The only way a regular user can tell that their slot creation is stuck on this is to look at logs, which still mention the need to wait for older transactions to complete. On a primary, this same wait would be visible in system tables.</li>\n</ol>\n<p>This issue is a good example of well-written code causing problems because it was unwittingly roped into handling something it was not designed for. This tends to happen in any codebase of sizable complexity.</p>\n<h2 id=\"resolution---allowing-an-intervention\"></h2>\n<p>Our immediate concern was that it was currently impossible to stop a slot creation waiting for a consistent point on a standby. To this effect, I submitted a <a target=\"_blank\" href=\"https://www.postgresql.org/message-id/flat/CAM45KeELdjhS-rGuvN%3DZLJ_asvZACucZ9LZWVzH7bGcD12DDwg%40mail.gmail.com\">patch</a> to the Postgres mailing list, which just added an interrupt check before each sleep call:</p>\n<div><pre><code><span>+\t\t\tCHECK_FOR_INTERRUPTS();</span>\n<span> \t\t\tpg_usleep(1000L);</span></code></pre></div>\n<p>Postgres maintainers quickly <a target=\"_blank\" href=\"https://github.com/postgres/postgres/commit/961553daf5d6087b175aa98f3031a46a8666cecf\">accepted</a> this patch (thanks, Fujii Masao, for reviewing it!) and backported it to all supported major versions of Postgres. After a minor version upgrade, this problem should be mitigated for all users running hot standbys.</p>\n<p>Another community member graciously addressed the issues around the lack of a <code>wait_event</code> here and the inefficient loop. A <a target=\"_blank\" href=\"https://www.postgresql.org/message-id/flat/CABPTF7WZODAVPFxtn9ygA9d6zckkJbFG%3DSUtHdvk7ca%3DUTzSFg%40mail.gmail.com\">patch</a> is out to add a new wait event that highlights this case, and there is also an ongoing discussion about improving the way standbys wait for transactions to complete on the primary. Both these changes are still in flight and should hopefully make it to Postgres 19 next year.</p>\n<h2 id=\"lessons-learned-and-a-debt-repaid\"></h2>\n<p>Once the ClickPipes team understood that this issue was not a one-off case, it took me a day or two to determine the RCA and develop the patch that addresses it. Being familiar with the Postgres codebase, its well-structured nature allowed me to hone in on XactLockTableWait() and work backwards. While the Postgres community has an older and sometimes daunting contribution process of submitting patches to a mailing list, they were also instrumental in reviewing the patch soon and getting it backported, continuing to ensure a high-quality user experience.</p>\n<p>This investigation into a seemingly simple bug reveals the incredible depth and complexity that lie beneath the surface of modern database systems. Postgres, with decades of development and its battle-tested architecture, still harbors edge cases where different subsystems can interact with each other in unexpected ways. Similarly, ClickHouse, with its columnar storage engine and rich feature set, also presents fascinating challenges in pushing the boundaries of analytical performance. As both databases are open source, it’s easier to identify issues like this, fix them, and submit your patches upstream, repaying your debt to a system that has served you well.</p>\n<p>Replicating data from PostgreSQL to ClickHouse unlocks columnar storage performance, parallel query execution, and advanced time-series analytics, enabling workloads that would be impractical or impossible on row-based transactional systems.
