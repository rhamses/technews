contentHtml: "<div><h2 id=\"user-content-introduction\"></h2>\n<p>Auto-scaling database resources requires careful balance: scale up too slowly and you risk performance degradation; scale down too aggressively and you trigger constant oscillations. Our auto-scaling system used a single 30-hour lookback window to make scaling decisions. This made scale-ups fast and stable, but it meant scale-downs were conservative by design. After traffic dropped, a cluster could take up to 30 hours to right-size.</p>\n<p>This post explores how we solved this problem with a <strong>two-window recommender</strong>: a dual-window approach that scales up aggressively and scales down faster. We paired this two-window framework with a new target-tracking CPU recommendation system, replacing our previous CPU recommendation algorithm that didn't work well with multiple windows.</p>\n<p>The result: significantly faster scale-downs, minimized scaling oscillations, and substantial infrastructure cost reduction for variable workloads, all while maintaining the stability needed for production databases.</p>\n<p><strong>Note</strong>: This post focuses on vertical auto-scaling, adjusting CPU and memory per replica. For horizontal scaling options and user-facing configuration, see the <a target=\"_blank\" href=\"https://clickhouse.com/docs/manage/scaling\">ClickHouse Cloud scaling documentation</a>.</p>\n<h2 id=\"user-content-the-problem-long-lookback-windows\"></h2>\n<p>Our original auto-scaling system used a 30-hour lookback window to determine resource recommendations. This approach had clear benefits:</p>\n<ul>\n<li><strong>Fast scale-up</strong>: When usage spiked, we'd see it immediately and scale up</li>\n<li><strong>Stability</strong>: The long window prevented reacting to transient fluctuations</li>\n</ul>\n<p>However, it created a critical problem for scale-downs:</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FSmarter_Auto_Scaling_Click_House_1_584cbb2499.jpg&w=2048&q=75\"></span></p>\n<p><strong>Result</strong>: 30 hours of over-provisioned resources after traffic dropped, increasing infrastructure spend more than necessary.</p>\n<p><strong>Key metric</strong>: The system tracks <strong>peak (maximum) usage</strong> within the lookback period rather than average usage. Provisioning based on averages would leave insufficient capacity during peak moments, leading to query failures or degraded performance.</p>\n<p>We needed a way to keep the fast, stable scale-ups while making scale-downs significantly faster.</p>\n<h2 id=\"user-content-the-two-window-solution\"></h2>\n<p>Instead of using a single window, we use two lookback windows with different time ranges:</p>\n<ul>\n<li><strong>Small Window</strong> (3 hours): Captures recent usage patterns, enables faster scale-down</li>\n<li><strong>Large Window</strong> (30 hours): Ensures we scale up in a single step to the maximum usage seen in the longer lookback window, rather than multiple gradual scale-ups. This is critical because scaling takes time and invalidates local caches; so it is safer to scale up in a single step.</li>\n</ul>\n<p>We explored various short window durations before settling on 3 hours. A 1-hour window was too reactive; it scaled down too aggressively and caused oscillations. A 6-hour window didn't improve scale-down latency enough. Three hours struck the right balance between responsiveness and stability.</p>\n<p>Each window independently generates a recommendation using both memory and CPU analysis. The system then merges these recommendations based on the scaling direction each window suggests.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FSmarter_Auto_Scaling_Click_House_2_92568fa5da.jpg&w=2048&q=75\"></span></p>\n<h3 id=\"user-content-generating-recommendations-per-window\"></h3>\n<p>The system generates recommendations for both windows in parallel:</p>\n<ol>\n<li><strong>Small window</strong> (3 hours): Analyzes recent <strong>maximum</strong> usage patterns</li>\n<li><strong>Large window</strong> (30 hours): Analyzes historical <strong>maximum</strong> usage patterns</li>\n<li><strong>Previous small window</strong>: Fetches the last small window recommendation for trend detection</li>\n</ol>\n<p>For each window, the system runs <strong>both memory-based and CPU-based analysis in parallel</strong>, then selects whichever recommends more resources (since CPU and memory scale in a fixed 1:4 ratio, this covers both dimensions). Each window's recommendation is then compared to the current allocation to determine the scaling direction: scale-up if it recommends more, scale-down if it recommends less, or no change.</p>\n<h3 id=\"user-content-merging-the-recommendations\"></h3>\n<p>Since each window looks at a different time range, they can reach different conclusions. The small window might see that traffic has been calm for the past 3 hours and recommend scaling down, while the large window still remembers yesterday's spike and wants to hold steady, or even scale up. The question becomes: when they disagree, which one do we pick?</p>\n<div><table><thead><tr><th>Large Window</th><th>Small Window</th><th>Picked Recommendation</th><th>Reasoning</th></tr></thead><tbody><tr><td>Scale-up</td><td>Scale-up</td><td><strong>Large window</strong></td><td>Single-step scale to longer-term peak</td></tr><tr><td>Scale-up</td><td>No change</td><td><strong>Small window</strong></td><td>Recent usage is stable, don't scale yet</td></tr><tr><td>Scale-up</td><td>Scale-down</td><td><strong>Hunting check</strong></td><td>If small window trending up, use large to avoid hunting; else use small</td></tr><tr><td>No change</td><td>Scale-up</td><td>—</td><td>Not possible (large window contains small window data)</td></tr><tr><td>No change</td><td>No change</td><td><strong>Small window</strong></td><td>No change</td></tr><tr><td>No change</td><td>Scale-down</td><td><strong>Hunting check</strong></td><td>If small window trending up, use large to avoid hunting; else use small</td></tr><tr><td>Scale-down</td><td>Scale-up</td><td>—</td><td>Not possible (large window contains small window data)</td></tr><tr><td>Scale-down</td><td>No change</td><td><strong>Large window</strong></td><td>Service likely idling/stopped</td></tr><tr><td>Scale-down</td><td>Scale-down</td><td><strong>Small window</strong></td><td>Faster scale-down</td></tr></tbody></table></div>\n<p>When both windows agree on direction, we pick the small window for scale-downs (faster) and the large window for scale-ups (single-step to peak). When they disagree, we run a hunting check. Some cases are simply not possible because the large window completely overlaps the small window.</p>\n<h3 id=\"user-content-preventing-hunting\"></h3>\n<p>To prevent hunting, the system uses the previous small window recommendation. When windows disagree (large wants scale-up but small wants scale-down), the system checks if the small window recommendation is trending upward.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FSmarter_Auto_Scaling_Click_House_3_271d0c3c1d.jpg&w=2048&q=75\"></span></p>\n<p><em>Illustrative example: After high CPU usage subsides, actual utilization (blue dots) drops then starts rising slowly. The large window (yellow) holds its recommendation steady. The small window (green) drops fast after the spike. Without the hunting check, the two-window merge logic would alternate between trusting each window, producing the red line, hunting between scale-down and scale-up. The hunting check prevents this by trusting the large window whenever the small window is trending upward.</em></p>\n<p><strong>Hunting check</strong>: <code>current_small_window &gt; previous_small_window</code></p>\n<ul>\n<li><strong>If trending up</strong>: Trust large window (usage is rising, prevents hunting and scale in single step rather than gradually)</li>\n<li><strong>If stable/down</strong>: Trust small window (safe to scale down)</li>\n</ul>\n<p>With the two-window framework in place, we needed CPU and memory recommenders to generate proposals for each window. But our existing CPU recommender, which used fixed scaling factors, had problems that the two-window approach made significantly worse.</p>\n<h2 id=\"user-content-the-fixed-factor-cpu-scaling-problem\"></h2>\n<p>Our original CPU recommender used a threshold-based approach:</p>\n<div><pre><code><span><span>if</span> utilization &gt; 75%:  scale to 2× current recommendation</span>\n<span><span>if</span> utilization &lt; 37.5%: scale to 0.5× current recommendation</span>\n<span>otherwise: no change</span></code></pre></div>\n<p>This created two major issues when used with the two-window approach:</p>\n<h3 id=\"user-content-cascading-scale-ups-across-windows\"></h3>\n<p>The fixed-factor algorithm could only double or halve the <em>last recommendation;</em> it couldn't calculate directly from the actual peak usage data. With two windows running in parallel, this meant even when the 30-hour window could <em>see</em> a large peak, it couldn't jump to the right size in one step.</p>\n<p>For example, imagine a service that peaked at 48 cores yesterday but has since dropped to 12 cores:</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FSmarter_Auto_Scaling_Click_House_4_b6cb0eeee1.jpg&w=2048&q=75\"></span></p>\n<h3 id=\"user-content-oscillations-with-shorter-windows\"></h3>\n<p>With shorter windows, the 2x scaling factor created severe oscillations:</p>\n<div><pre><code><span>Hour 0: 50 cores allocated, 40 cores used (80%) → Scale to 100 cores</span>\n<span>Hour 3: 40 cores used / 100 allocated (40%) → Scale to 50 cores</span>\n<span>Hour 6: 40 cores used / 50 allocated (80%) → Scale to 100 cores</span>\n<span>Hour 9: Repeat...</span></code></pre></div>\n<p>Result: Constant scaling disruptions every few hours, with minor usage changes.</p>\n<p>We needed an approach that scales based on actual usage, not previous recommendations.</p>\n<h2 id=\"user-content-target-tracking-cpu-recommendation\"></h2>\n<p>To solve these problems, we replaced the fixed-factor algorithm with <strong>target-tracking</strong>. Target-tracking scales capacity based on a <strong>target utilization metric</strong>. Instead of doubling or halving allocations, it calculates the exact resources needed to maintain the target utilization level.</p>\n<h3 id=\"user-content-how-target-tracking-works\"></h3>\n<p>The algorithm calculates a threshold band based on current allocation and watermarks. Scaling only occurs when peak usage falls outside this band:</p>\n<div><pre><code><span>min_threshold = current_allocation × low_watermark</span>\n<span>max_threshold = current_allocation × high_watermark</span>\n<span></span>\n<span><span>if</span> peak_usage outside [min_threshold, max_threshold]:</span>\n<span>    new_allocation = peak_usage ÷ target_utilization</span>\n<span><span>else</span>:</span>\n<span>    maintain current_allocation</span></code></pre></div>\n<p><span><img alt=\"Smarter Auto-Scaling ClickHouse.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FSmarter_Auto_Scaling_Click_House_c22e54a36c.jpg&w=2048&q=75\"></span></p>\n<p>The algorithm scales to achieve target utilization, creating a stable band where usage can fluctuate around the target without triggering another scaling event. In our current implementation, target utilization is the geometric mean of the watermarks.</p>\n<h3 id=\"user-content-why-geometric-mean-ensuring-reversible-scaling\"></h3>\n<p>The target utilization is set to the geometric mean of the watermarks:</p>\n<div><pre><code><span>target_utilization = √(high_watermark × low_watermark)</span>\n<span><span># Example: √(0.75 × 0.375) = √0.28125 = 0.53</span></span></code></pre></div>\n<p>This ensures <strong>reversible scaling</strong>: if usage returns to the same value, allocation returns to the same value.</p>\n<div><pre><code><span>Start: 100 cores, 80 cores usage</span>\n<span>Scale up to: 80 / 0.53 = 151 cores</span>\n<span></span>\n<span>Later, usage drops back to 80 cores:</span>\n<span>With 151 cores: 80 / 151 = 53% (within thresholds, no change)</span>\n<span></span>\n<span>If usage later spikes to 120 cores:</span>\n<span>Calculate: 120 / 0.53 = 226 cores</span>\n<span></span>\n<span>If usage returns to 80 cores again:</span>\n<span>With 226 cores: 80 / 226 = 35.4% (below 37.5% low watermark)</span>\n<span>Scale to: 80 / 0.53 = 151 cores (same as before!)</span></code></pre></div>\n<p>Using the geometric mean for target utilization provides important mathematical guarantees:</p>\n<ul>\n<li>reversible scaling (same usage returns to same allocation)</li>\n<li>balanced headroom in both directions</li>\n<li>prevention of allocation drift over time.</li>\n</ul>\n<h3 id=\"user-content-smoothing-out-transient-spikes\"></h3>\n<p>To avoid reacting to transient spikes, the system smooths CPU usage using a <strong>10-minute rolling window of median values</strong> calculated per replica. This filters out short-lived spikes while preserving genuine sustained increases. The system then takes the maximum of these smoothed values across all replicas as the peak usage.</p>\n<p>Target-tracking solved the CPU side. But CPU is only half the picture, each window also needs a memory-based recommendation.</p>\n<h2 id=\"user-content-memory-based-recommendation\"></h2>\n<p>Like the CPU recommender, each window also generates a memory-based recommendation. The memory recommender tracks multiple signals like query memory, resident memory, and OOM events (both ClickHouse-managed and container-level) and applies usage-based multipliers to ensure sufficient headroom.</p>\n<p>For each window, both CPU and memory recommendations are generated independently, and the system selects whichever recommends more resources. Since ClickHouse Cloud maintains a fixed 1 CPU core to 4 GB memory ratio, CPU and memory scale together in lockstep.</p>\n<p>For details on memory signals, skew-based multipliers, and the recommendation formula, see the <a target=\"_blank\" href=\"https://clickhouse.com/docs/manage/scaling\">scaling documentation</a>.</p>\n<p>The two-window recommender with target-tracking optimizes resource allocation during active usage. But what about services that go completely quiet?</p>\n<h2 id=\"user-content-automatic-idling\"></h2>\n<p>While the two-window recommender optimizes resource allocation during <strong>active usage</strong>, ClickHouse Cloud also provides <strong>automatic idling</strong> as a separate cost-optimization feature for periods of <strong>complete inactivity</strong>.</p>\n<p><strong>Key distinction</strong>: Auto-scaling adjusts resources based on usage patterns during active periods, while automatic idling completely pauses services when they receive no queries for a configured duration.</p>\n<p>When a service idles, compute resources are suspended (no billing for CPU/memory) while data remains intact in storage. The service automatically resumes when a new query arrives. ClickHouse Cloud also implements adaptive idling: smart logic that prevents idling when background merges are needed or service initialization times warrant longer timeouts.</p>\n<p>For complete details on automatic idling, configuration options, use cases, and adaptive behavior, see the <a target=\"_blank\" href=\"https://clickhouse.com/docs/manage/scaling#automatic-idling\">Automatic Idling documentation</a>.</p>\n<h2 id=\"user-content-conclusion\"></h2>\n<p>The two-window recommender with target-tracking CPU scaling has delivered significant improvements: scale-down latency reduced from 30 hours to 3 hours, oscillation issues minimized, cascading over-provisioning resolved, and substantial infrastructure cost reduction for variable workloads.</p>\n<p>The key insight is that <strong>different time windows excel at different tasks</strong>: short windows for responsive scale-down, long windows for stable scale-up decisions. By merging recommendations from both windows, we get the best of both worlds.</p>\n<p>Together with memory-based recommendations and idling, these changes have made our ClickHouse auto-scaling system faster, more stable, and more cost-efficient, enabling our customers to run production workloads with confidence. The two-window recommender and target-tracking algorithm provide a strong foundation, and we're continuing to refine our scaling algorithms to match allocation even more closely to actual utilization.</p></div>"
