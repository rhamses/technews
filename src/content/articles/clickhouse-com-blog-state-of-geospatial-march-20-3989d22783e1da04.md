contentHtml: "<div><p>ClickHouse is best known as an analytics engine built for speed at scale, but over the past several years it has grown a surprisingly complete set of geospatial capabilities.</p>\n<p>In this post we're going to take a tour of where things stand today: the type system, the functions, the sharp edges, a look at where ClickHouse fits and where it does not.</p>\n<h2 id=\"user-content-a-brief-history\"></h2>\n<p>Geospatial support in ClickHouse has grown steadily over time rather than arriving all at once.</p>\n<p>ClickHouse uses a YY.MM versioning scheme - version 20.1 shipped in January 2020, 21.9 in September 2021, and so on. The earliest geospatial functions predate this scheme and appear under version 1.x in the function catalog.</p>\n<p>Those early functions were a handful of coordinate-distance functions: <code>greatCircleDistance</code> and eventually <code>geoDistance</code>. There were no geometry types - functions just took raw coordinate values as parameters.</p>\n<p>In 2020 (version 20.1), the grid-based indexing systems arrived: <code>geohashEncode</code>/<code>geohashDecode</code> and <a target=\"_blank\" href=\"https://h3geo.org/\">H3</a> (Uber's hexagonal hierarchical grid) both landed in that release. <a target=\"_blank\" href=\"https://s2geometry.io/\">S2</a> (Google's spherical geometry library) followed in 2021 (version 21.9). These cover a huge share of real-world spatial analytics use cases - binning observations into cells, aggregating by region at a chosen resolution, proximity lookups - and ClickHouse handles them extremely fast.</p>\n<p><code>Point</code>, <code>Ring</code>, <code>Polygon</code>, and <code>MultiPolygon</code> arrived in v20.5 (May 2020), initially behind an experimental flag. They are custom names layered over ClickHouse's existing primitives - <code>Tuple</code> and <code>Array</code> - rather than a separate storage format. The experimental flag was removed in v23.5, making them production-ready. WKT parsing functions like <code>readWKTPolygon</code> and <code>svg</code> followed in v21.4. <code>LineString</code> came later still, added in v24.6.</p>\n<p>The most significant recent additions both landed in 2025. The <code>Geometry</code> type, introduced in v25.11, uses the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/data-types/variant\"><code>Variant</code></a> type and can hold any geometry subtype in a single column - points alongside polygons alongside linestrings - without splitting into separate columns or tables. WKB (Well-Known Binary) support arrived around the same time (v25.7–v25.12), enabling direct import from <a target=\"_blank\" href=\"https://postgis.net/\">PostGIS</a> and other GIS tools without a text parsing round-trip.</p>\n<p>If you want to trace this history yourself, you can use the <code>system.functions</code> table, which records which version each function was introduced in:</p>\n<div><pre><code><span><span>SELECT</span></span>\n<span>    splitByChar(<span>'.'</span>, introduced_in)[<span>1</span>] <span>AS</span> major_version,</span>\n<span> functions, S2 support, and additional H3 functions all within that release year.</p>\n<p>To see the full list with exact versions, <a target=\"_blank\" It makes the type system genuinely composable - you can write functions that accept any geometry type, store mixed data naturally, and ingest from external sources without knowing the geometry type in advance. The recent work to make all geometry functions accept both <code>Geometry</code> and the individual sub-types continues to smooth out the rough edges.</p>\n<p>For analytics at scale on location data, ClickHouse is already an excellent choice. The tooling is mature, the performance is hard to beat, and the 2025 type system improvements mean the ergonomics are considerably better than they were.</p></div>"
