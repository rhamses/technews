id=\"introduction\"></h2>\n<p>As a high-performance OLAP database, ClickHouse is used for many use cases, including real-time analytics for <a target=\"_blank\" href=\"https://clickhouse.com/blog/working-with-time-series-data-and-functions-ClickHouse\">time series</a> data. Its diversity of use cases has helped drive a huge range of <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/\">analytical functions</a>, which assist in querying most data types. These query features and high compression rates have increasingly led users to utilize ClickHouse to store Observability data. This data takes three common forms: logs, metrics, and traces. In this series of blog posts, we will explore how these “pillars” can be collected, optimally stored, queried, and visualized.</p>\n<p>For this post, we start with logs and possibilities for collection and querying. We have attempted to ensure examples can be reproduced. We also note that agent support for specific data types with ClickHouse is constantly evolving, with this post representing the current state of play of the ecosystem as of January 2023. We thus always encourage our users to review documentation and linked issues.</p>\n<p>While our examples assume a modern architecture where a user must collect logs from a Kubernetes cluster, the recommendations and advice are not Kubernetes-dependent and apply equally to self-managed servers or other container orchestration systems. We used our development cloud environment for testing, producing around 100GB of logs daily from about 20 nodes. Note that we have made no effort to tune agents or measure their resource overhead - something we recommend users research or do before production deployment. This post also focuses on data collection, proposing a schema and data model but leaving optimizations to a later post.</p>\n<p>For our examples, we store data in a <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> service where you can spin up a cluster on a free trial in minutes, let us deal with the infrastructure and get you querying!</p>\n<p><strong>Note:</strong> All the reproducible configuration examples used in this article are available to consult in this <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/building-an-o11y-solution\">repository</a></p>\n<h2 id=\"observability-architectures\"></h2>\n<p>Most agents use a common architecture pattern for collecting Observability data at scale, promoting an agent and aggregator concept. The latter can be ignored for small deployments, with agents deployed close to their data source and responsible for processing and sending data directly to ClickHouse over either HTTP or the native protocol. In a Kubernetes environment, this means deploying the agent as a <a target=\"_blank\" href=\"https://kubernetes.io/docs/concepts/workloads/controllers/daemonset/\">Daemonset</a>. This deploys an <a target=\"_blank\" href=\"https://kubernetes.io/docs/concepts/workloads/pods/\">agent pod</a> to each K8s node, responsible for collecting the logs of other containers (typically read from disk).</p>\n<p><span><img alt=\"agent_architecture.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fagent_architecture_bd0e3a1af7.png&w=2048&q=75\"></span></p>\n<p>This architecture is sufficient for users not requiring high durability or availability and for a small number of agents with low friction to make configuration changes. However, users should be aware that this may result in many small inserts, especially if agents are configured to flush data frequently, e.g., because of a need for data to be available promptly for analysis and issue identification. In this case, the users should consider configuring agents to use <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/bestpractices/asynchronous-inserts/\">asynchronous inserts</a> to avoid common problems resulting <a target=\"_blank\" href=\"https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse\">from too many parts</a>.</p>\n<p>Larger deployments introduce an aggregator or gateway concept. This aims to configure lighter-weight agents close to their data source, only responsible for forwarding data to an aggregator. This reduces the possibility of disrupting existing services. The aggregator is responsible for processing steps such as enrichment, filtering, and ensuring a schema is applied, as well as batching and reliable delivery to ClickHouse. This aggregator is usually deployed as a <a target=\"_blank\" href=\"https://kubernetes.io/docs/concepts/workloads/controllers/deployment/\">Deployment</a> or <a target=\"_blank\" href=\"https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/\">Statefulset</a> and can be replicated for high availability if required.</p>\n<p><span><img alt=\"aggregator_architecture.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Faggregator_architecture_8485f75130.png&w=2048&q=75\"></span></p>\n<p>As well as minimizing load at the data source on potentially critical services, this architecture allows data to be batched and inserted as larger blocks into ClickHouse. This property is significant since it aligns with ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/bestpractices/bulk-inserts/#:~:text=Generally%2C%20we%20recommend%20inserting%20data,between%2010%2C000%20to%20100%2C000%20rows.\">insert best practices</a>.</p>\n<p>The above architecture simplifies an enterprise architecture which, in reality, also needs to consider where data should be buffered, load-balancing, high availability, complex routing, and the need to separate your record (archive) and analysis systems. These concepts are covered in detail well by the Vector documentation <a target=\"_blank\" href=\"https://vector.dev/docs/setup/going-to-prod/\">here</a>. While Vector-specific, the principles here apply to other agents discussed. An important quality of these architectures is that the agent and aggregator can also be heterogeneous with mixes of <a target=\"_blank\" href=\"https://vector.dev/docs/setup/going-to-prod/architecting/#choosing-agents\">technology common</a>, especially when collecting data of different types since some agents excel at different Observability pillars.</p>\n<h2 id=\"agents\"></h2>\n<p>At ClickHouse, our users gravitate toward four principal agent technologies: Open Telemetry Collector, Vector, FluentBit, and Fluentd. The latter of these two share the same origin and many of the same concepts. For brevity, we explore FluentBit, which is more lightweight and sufficient for log collection in Kubernetes, but Fluentd would represent a valid approach. These agents can assume an aggregator or collector role and can be <a target=\"_blank\" href=\"https://clickhouse.com/blog/storing-log-data-in-clickhouse-fluent-bit-vector-open-telemetry#interoperabilityandchoosingastack\">used together (with some limitations)</a>. Although they use different terminology, they all utilize a common architecture with pluggable inputs, filters/processors, and outputs. ClickHouse is either supported as official output or integration is achieved via generic HTTP support.</p>\n<p>In the initial examples below, however, we deploy each agent in both the aggregator and collector roles. We utilize each agent's official Helm chart for a simple getting-started experience, note the important configuration changes, and share the <code>values.yaml</code> file.</p>\n<p>Our examples use a single replica for our aggregator, although these can be easily deployed with multiple replicas and load-balanced for performance and fault tolerance. All of the agents support the enrichment of the logs with Kubernetes metadata, critical for future analysis, such as the pod name, container id, and node from which the log originated. <a target=\"_blank\" href=\"https://kubernetes.io/docs/concepts/overview/working-with-objects/annotations/\">Annotations</a> and <a target=\"_blank\" href=\"https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/\">labels</a> can also be included on log entries (enabled by default for FluentBit and Vector). These are typically sparse but potentially numerous (hundreds); a production architecture should assess their value and filter them. We recommend using a Map type for these to avoid column explosion, which has <a target=\"_blank\" href=\"https://clickhouse.com/blog/storing-log-data-in-clickhouse-fluent-bit-vector-open-telemetry#querying-the-map-type\">query implications</a>.</p>\n<p>All agents required tuning (via the <a target=\"_blank\" href=\"https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/\">resources</a> YAML key) in the aggregator role to avoid OOM issues and to keep up with our throughput (around 100GB a day). Your mileage may vary here depending on the number of aggregators and log throughput, but tuning resources will almost always be required in large environments.</p>\n<h3 id=\"open-telemetry-otel-collector-alpha\"></h3>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/engineering-resources/opentelemetry-otel\">OpenTelemetry</a> is a collection of tools, APIs, and SDKs for instrumenting, generating, collecting, and exporting Observability data. As well as offering agents in most of the popular languages, a <a target=\"_blank\" href=\"https://opentelemetry.io/docs/collector/\">Collector component</a> written in Golang provides a vendor-agnostic implementation of how to receive, process, and export Observability data. By supporting several input formats, such as Prometheus and OTLP, as well as a wide range of export targets, including ClickHouse, the OTEL Collector can provide a centralized processing gateway. The Collector uses the terms <a target=\"_blank\" href=\"https://opentelemetry.io/docs/collector/configuration/#receivers\">receiver</a>, <a target=\"_blank\" href=\"https://opentelemetry.io/docs/collector/configuration/#processors\">processor</a>, and <a target=\"_blank\" href=\"https://opentelemetry.io/docs/collector/configuration/#exporters\">exporter</a> for its three stages and <a target=\"_blank\" href=\"https://opentelemetry.io/docs/collector/deployment/\">gateway</a> for an aggregator instance.</p>\n<p>While more commonly used as a gateway/aggregator, handling tasks such as batching and retries, the Collector can also be deployed as an <a target=\"_blank\" href=\"https://opentelemetry.io/docs/collector/deployment/\">agent itself</a>. <a target=\"_blank\" href=\"https://opentelemetry.io/docs/reference/specification/protocol/\">OTLP</a> represents the <a target=\"_blank\" href=\"https://opentelemetry.io/docs/reference/specification/protocol/design-goals/\">Open Telemetry data standard</a> for communication between gateway and agent instances, which can occur over gRPC or HTTP. As we will see below, this protocol is also supported by Vector and FluentBit.</p>\n<h4 id=\"clickhouse-support\"></h4>\n<p>ClickHouse is supported in the OTEL exporter through a <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter\">community contribution</a>, with support for logs and traces (a <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-collector-contrib/pull/16477\">PR is under review</a> for metrics). Communication with ClickHouse occurs over the optimized native format and protocol via the official Go client.</p>\n<p>Before using the Open Telemetry Collector, users should consider the following points:</p>\n<ul>\n<li>The ClickHouse data model and schema used by the agent are hard coded. As of the time of writing, there is no ability to change the types or codecs used. Mitigate this by creating the table before deploying the connector, thus enforcing your schema.</li>\n<li>The exporter is not distributed with the core OTEL distribution but rather as an extension through the <code>contrib</code> image. Practically this means using the correct docker image in the Helm chart.</li>\n<li>The exporter is in alpha, and although we have had no issues collecting over a TB of logs, users should adhere to the <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-collector#alpha\">advice provided by Open Telemetry</a>. The logs use case for OTEL is still relatively new and less mature than the Fluent Bit or Vector offerings.</li>\n</ul>\n<h4 id=\"kubernetes-deployment\"></h4>\n<p><span><img alt=\"otel_architecture.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fotel_architecture_e50c0a8c3d.png&w=2048&q=75\"></span></p>\n<p>The <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-helm-charts/tree/main/charts/opentelemetry-collector\">official Helm chart</a> represents the simplest deployment means if only collecting logs. In future posts, when we instrument applications, <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-operator\">the operator</a> offers auto-instrumentation features and other deployment modes, e.g., as a sidecar. For logs, however, the basic chart is sufficient. The full details on installing and configuring the chart can be found <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/tree/main/blog-examples/building-an-o11y-solution/otel_to_otel\">here</a>, including the steps for deploying a gateway and agent as well as sample configurations.</p>\n<p>Note that the exporter also supports ClickHouse’s native <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/faq/operations/delete-old-data/#ttl\">TTL features</a> for data management and relies on partitioning by date (enforced by the schema). We set <a target=\"_blank\" href=\"https://github.com/ClickHouse/examples/blob/d4d703633636c9282eb3589f52e64e34f1ab148f/observability/logs/kubernetes/otel_to_otel/gateway.yml#L81\">TTL to 0 in our example</a>, disabling data expiration, but this represents a useful feature and a common requirement in logs that could easily be used in the schema of other agents.</p>\n<h4 id=\"data-and-schema\"></h4>\n<p>Our earlier example has configured the aggregator to send data to an <code>otel.otel_logs</code> table. It aims to be vendor agnostic and support multiple <a target=\"_blank\" href=\"https://vector.dev/docs/reference/configuration/sources/\">inputs</a> and <a target=\"_blank\" href=\"https://vector.dev/docs/reference/configuration/sinks/\">outputs</a>, including the OTLP protocol allowing it to operate as an aggregator for Open Telemetry agents. Written in Rust, Vector uses the terminology <a target=\"_blank\" href=\"https://vector.dev/docs/reference/configuration/sources/\">sources</a>, <a target=\"_blank\" href=\"https://vector.dev/docs/reference/configuration/transforms/\">transforms</a>, and <a target=\"_blank\" href=\"https://vector.dev/docs/reference/configuration/sinks/\">sinks</a> for its 3-stage pipeline. It represents a feature-rich log collection solution and is increasingly popular within the ClickHouse community.</p>\n<h4 id=\"clickhouse-support\"></h4>\n<p>ClickHouse is supported in Vector through a <a target=\"_blank\" href=\"https://vector.dev/docs/reference/configuration/sinks/clickhouse/\">dedicated sink</a> (currently in Beta), with communication occurring over the <a target=\"_blank\" href=\"https://github.com/vectordotdev/vector/blob/21d39317fb3268e5e26c81fdac41d9664e729251/src/sinks/clickhouse/http_sink.rs#L129-L155\">HTTP protocol using JSON format</a> and <a target=\"_blank\" href=\"https://vector.dev/docs/reference/configuration/sinks/clickhouse/#buffers-and-batches\">requests batched on insert</a>. While not as performant as other protocols, this offloads data processing to ClickHouse and simplifies debugging network traffic. While a data model is enforced, the user must create the target table and choose their types and encodings. A <a target=\"_blank\" href=\"https://vector.dev/docs/reference/configuration/sinks/clickhouse/#skip_unknown_fields\"><code>skip_unknown_fields</code></a> option allows the user to create a table with a subset of the available columns. This causes any columns not in the target table to be ignored. Below we create a target table in the <code>vector</code> database covering all post columns, including those added from Kubernetes enrichment. For now, we utilize a table ordering key optimized for filtering by container name. Future posts will discuss optimizing this schema.</p>\n<pre><p>\nCREATE database vector\nCREATE TABLE vector.vector_logs\n(\n   `file` String,\n   `timestamp` DateTime64(3),\n   `kubernetes_container_id` LowCardinality(String),\n   `kubernetes_container_image` LowCardinality(String),\n   `kubernetes_container_name` LowCardinality(String),\n   `kubernetes_namespace_labels`  Map(LowCardinality(String), String),\n   `kubernetes_pod_annotations`  Map(LowCardinality(String), String),\n   `kubernetes_pod_ip` IPv4,\n   `kubernetes_pod_ips` Array(IPv4),\n   `kubernetes_pod_labels` Map(LowCardinality(String), String),\n   `kubernetes_pod_name` LowCardinality(String),\n   `kubernetes_pod_namespace` LowCardinality(String),\n   `kubernetes_pod_node_name` LowCardinality(String),\n   `kubernetes_pod_owner` LowCardinality(String),\n   `kubernetes_pod_uid` LowCardinality(String),\n   `message` String,\n   `source_type` LowCardinality(String),\n   `stream` Enum('stdout', 'stderr')\n)\nENGINE = MergeTree\nORDER BY (`kubernetes_container_name`, timestamp)\n</p>\n</pre>\n<p>By default, the <a target=\"_blank\" href=\"https://vector.dev/docs/reference/configuration/sources/kubernetes_logs/\">Kubernetes log input</a> for Vector creates columns with <code>.</code> in the column name, e.g., <code>kubernetes.pod_labels</code>. With a historical focus on logs and written in C to minimize any overheads, FluentBit aims to be lightweight and fast. The code was initially developed by TreasureData but has long been open-sourced as a Cloud Native Computing Foundation project under an Apache 2.0 license. Adopted as a first-class citizen by <a target=\"_blank\" href=\"https://github.com/fluent/fluent-bit#fluent-bit-in-production\">multiple cloud providers</a>, it offers comparable <a target=\"_blank\" href=\"https://github.com/fluent/fluent-bit#plugins-inputs-filters-and-outputs\">input, processing, and output</a> features to the above tools.</p>\n<p>FluentBit uses <a target=\"_blank\" href=\"https://docs.fluentbit.io/manual/concepts/data-pipeline/input\">inputs</a>, <a target=\"_blank\" href=\"https://docs.fluentbit.io/manual/concepts/data-pipeline/parser\">parsers</a>/<a target=\"_blank\" href=\"https://docs.fluentbit.io/manual/concepts/data-pipeline/filter\">filters</a>, and <a target=\"_blank\" href=\"https://docs.fluentbit.io/manual/concepts/data-pipeline/output\">outputs</a> for its pipeline (and <a target=\"_blank\" href=\"https://docs.fluentbit.io/manual/concepts/data-pipeline/buffer\">buffer</a> and <a target=\"_blank\" href=\"https://docs.fluentbit.io/manual/concepts/data-pipeline/router\">router</a> concepts beyond scope of this post). An aggregator instance is referred to as an <a target=\"_blank\" href=\"https://fluentbit.io/blog/2020/12/03/common-architecture-patterns-with-fluentd-and-fluent-bit/\">aggregator</a>.</p>\n<h4 id=\"clickhouse-support\"></h4>\n<p>luentBit does not have a ClickHouse-specific output, relying on generic <a target=\"_blank\" href=\"https://docs.fluentbit.io/manual/pipeline/outputs/http\">HTTP support</a>. This works well and relies on inserting data in JSONEachRow format. However, users need to be cautious with this approach as the output does not perform any batching. FluentBit thus needs to be configured appropriately to avoid lots of small inserts and <a target=\"_blank\" href=\"https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse\">“too many part” issues</a>. Users should be aware that Fluent bit stores everything in chunks. These <a target=\"_blank\" href=\"https://docs.fluentbit.io/manual/administration/buffering-and-storage#chunks\">chunks</a> have a data structure of a tag and a payload size of up to 2MB. When using Kubernetes, each container outputs to a separate file identified by a dynamic tag.  The tag is also used to read individual chunks.. These chunks are flushed independently by tag, by the agent, to the aggregator per the <a target=\"_blank\" href=\"https://docs.fluentbit.io/manual/v/1.3/configuration/file#config_section\">flush interval</a>. The aggregator retains tag information for any downstream routing needs. It will use its own flush interval setting for each tag to determine writes to ClickHouse. Users thus have two options:</p>\n<ul>\n<li>Configure a large flush interval, i.e., at least 10s, on the agent and aggregator. This can be effective but can also result in a thundering-herd effect, causing spikes in inserts to ClickHouse. However, internal merges should keep up if the interval is large enough.</li>\n<li>Configure the output to use ClickHouse’s asynchronous inserts - this is especially recommended if you don’t deploy an aggregator instance. This causes ClickHouse to buffer inserts and is the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/asynchronous-inserts/\">recommended approach</a> to dealing with this write pattern. The behavior of <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/bestpractices/asynchronous-inserts/\">async inserts can be tuned</a> with implications on delivery guarantees to Fluent Bit. Specifically, the setting <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings/#wait-for-async-insert\"><code>wait_for_async_insert</code></a> controls if the write is acknowledged when it is written to the buffer (0) or when it has been written as an actual data part (and available for read queries). A value of 1, provides greater delivery guarantees at the expense of a possible reduction in throughput. Note that the Fluent Bit offset management and advancing is based on the acknowledgment from the output. A value of 0 for <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings/#wait-for-async-insert\"><code>wait_for_async_insert</code></a> maybe mean data is acknowledged prior to it being fully processed, i.e., subsequent failure could occur, causing data loss. This may be acceptable in some cases. Note also the settings <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings/#async-insert-max-data-size\"><code>async_insert_max_data_size</code></a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings/#async-insert-max-data-size\"><code>async_insert_busy_timeout_ms</code></a>, which control the exact flushing behavior of the buffer.</li>\n</ul>\n<p>Without an explicit understanding of ClickHouse, users must pre-create their tables before deployment. Similar to Vector, this leaves the schema decisions to the user. FluentBit creates a nested JSON Schema with a depth greater than 1. This can potentially contain hundreds of fields as a unique column is created for each unique label or annotation. Our previous post proposed using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/working-with-json/json-semi-structured\">JSON type</a> for this <code>kubernetes</code> column. This defers column creation to ClickHouse and allows dynamic sub-columns to be created based on the data. This offers a great starting experience but is sub-optimal as users can’t use codecs or use specific sub-columns in the table's ordering key (unless using <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/json-functions/\">JSONExtract</a>), leading to poorer compression and slower queries. It can also lead to column explosion in environments without controls over label and annotation use. Furthermore, this feature is currently experimental. A more optimized approach for this schema is moving labels and annotations to a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/integrations/data-formats/json#other-approaches\">Map type</a> - this conveniently reduces the <code>kubernetes</code> column to a depth of 1. This requires us to modify the data structure slightly in our processor pipeline and results in the following schema.</p>\n<pre><p>\nCREATE TABLE fluent.fluent_logs\n(\n    `timestamp` DateTime64(9),\n    `log` String,\n    `kubernetes` Map(LowCardinality(String), String),\n    `host` LowCardinality(String),\n    `pod_name` LowCardinality(String),\n    `stream` LowCardinality(String),\n    `labels` Map(LowCardinality(String), String),\n    `annotations` Map(LowCardinality(String), String)\n)\nENGINE = MergeTree\nORDER BY (host, pod_name, timestamp)\n</p>\n</pre>\n<h4 id=\"kubernetes-deployment\"></h4>\n<p><span><img alt=\"fluent_bit_architecture.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Farchitecture_c294fb9252.png&w=2048&q=75\"></span></p>\n<p>A <a target=\"_blank\" href=\"https://clickhouse.com/blog/kubernetes-logs-to-clickhouse-fluent-bit\">previous blog post</a> discussed the deployment of Fluent Bit to collect Kubernetes logs to ClickHouse in detail. These should match your typical workflows and access patterns. Ensure that the columns you typically filter by in your workflows are present in the ORDER BY table declaration. The ordering of these columns should also consider their respective cardinalities to ensure the optimal filtering algorithms can be used in ClickHouse. In most cases, order your columns in <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/improving-query-performance/sparse-primary-indexes/sparse-primary-indexes-multiple/#generic-exclusion-search-algorithm\">order of increasing cardinality</a>. For logs, this typically means placing the server or pod name first, followed by the timestamp: but again, this depends on how you plan to filter. Beyond 3-4, columns within a key are typically not recommended and provide little value. Instead, consider alternatives for accelerating queries as discussed in the post <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-faster-queries-with-projections-and-primary-indexes\">Supercharging your ClickHouse queries</a> and <a target=\"_blank\" href=\"https://clickhouse.com/blog/working-with-time-series-data-and-functions-ClickHouse\">Working with time series data in Clickhouse</a>.</p>\n<p>The Map type is prevalent in many of the schemas in this post. This type requires the values and keys to have the same type - sufficient for Kubernetes labels. Be aware that when querying a subkey of a Map type, the entire parent column is loaded. If the map has many keys, this can incur a significant query penalty. If you need to query a specific key frequently, consider moving it into its own dedicated column at the root.</p>\n<p>Note that we currently find the OTEL collector's default table schema and ordering key can make some queries expensive once datasets get larger, especially if your access patterns do not match the key. This is especially relevant to log data, where retention is typically only required for days before deletion can occur. Note that partitions can either positively or negatively impact query performance: If most queries hit a single partition, query performance improvement can improve. Conversely, if queries usually hit multiple partitions, it can result in degraded performance.</p>\n<p>Finally, even if your access patterns deviate from your ordering keys, linear scans are extremely fast in ClickHouse, making most queries still practical.
