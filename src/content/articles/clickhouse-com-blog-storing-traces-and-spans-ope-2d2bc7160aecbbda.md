As a high-performance real-time analytics database, ClickHouse is used for many use cases, including real-time analytics for <a target=\"_blank\" href=\"https://clickhouse.com/blog/working-with-time-series-data-and-functions-ClickHouse\">time series</a> data. Its diversity of use cases has helped drive a huge range of <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/functions/\">analytical functions</a>, which assist in querying most data types. These query features and high compression rates have increasingly led users to utilize ClickHouse to store Observability data. This data takes three common forms: logs, metrics, and traces. In this blog, the <a target=\"_blank\" href=\"https://clickhouse.com/blog/storing-log-data-in-clickhouse-fluent-bit-vector-open-telemetry\">second in an Observability series</a>, we explore how trace data can be collected, stored, and queried in ClickHouse.</p>\n<p>We have focused this post on using <a target=\"_blank\" href=\"https://clickhouse.com/engineering-resources/opentelemetry-otel\">OpenTelemetry</a> to collect trace data for storage in ClickHouse. When combined with Grafana, and recent developments in the <a target=\"_blank\" href=\"https://github.com/grafana/clickhouse-datasource/pull/329\">ClickHouse plugin</a>, traces are easily visualized and can be combined with logs and metrics to obtain a deep understanding of your system behavior and performance when detecting and diagnosing issues.</p>\n<p>We have attempted to ensure that any examples can be reproduced, and while this post focuses on data collection and visualization basics, we have included some tips on schema optimization. For example purposes, we have forked the <a target=\"_blank\" href=\"https://opentelemetry.io/ecosystem/demo/\">official OpenTelemetry Demo</a>, adding support for ClickHouse and including an OOTB Grafana dashboard for visualizing traces.</p>\n<h2 id=\"what-are-traces\"></h2>\n<p>Telemetry is data emitted from a system about its behavior. This data can take the form of logs, metrics, and traces. A trace records the paths taken by requests (made by an application or end-user) as they propagate through multi-service architectures such as microservice and serverless applications. A single trace consists of multiple spans, each a unit of work or operation. The span provides details of an operation, principally the time it took, in addition to <a target=\"_blank\" href=\"https://opentelemetry.io/docs/concepts/signals/traces/#attributes\">other metadata</a> and related log messages. These spans are hierarchy related as a tree, with the first span relating the root and covering the entire trace from start to finish. Beneath this root and each subsequent span, child operations are captured. As we navigate the tree, we can see the child operations and steps that make up the above level. This gives us ever-increasing context as to the work performed by the original request. This is visualized below:</p>\n<p><span><img alt=\"traces_concept.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Ftraces_concept_4908965e1c.png&w=2048&q=75\"></span></p>\n<p>These traces, when combined with metrics and logs, can be critical in obtaining insights into the behavior of a system for the detection and resolution of issues.</p>\n<h2 id=\"what-is-opentelemetry\"></h2>\n<p>The OpenTelemetry project is a vendor-neutral open-source framework consisting of SDKs, APIs, and components that allow the ingesting, transforming, and sending of Observability data to a backend. More specifically, this consists of several main components:</p>\n<ul>\n<li>A set of <strong>specifications and conventions</strong> of how metrics, logs, and traces should be collected and stored. This includes recommendations for language-specific agents and a full specification for the OpenTelemetry Line Protocol (OTLP) based on <a target=\"_blank\" href=\"https://protobuf.dev/\">protobuf</a>. This allows data to be transmitted between services by providing a full description of the client-server interface and the message format.</li>\n<li><strong>Language-specific libraries and SDKs</strong> for instrumenting, generating, collecting, and exporting observability data. This is particularly relevant to the collection of trace data.</li>\n<li>An <strong>OTEL Collector</strong> written in Golang provides a vendor-agnostic implementation of receiving, processing and exporting Observability data. The OTEL Collector provides a centralized processing gateway by supporting several input formats, such as Prometheus and OTLP, and a wide range of export targets, including ClickHouse.</li>\n</ul>\n<p>In summary, OpenTelemetry standardizes the collection of logs, metrics, and traces. Importantly, it is not responsible for storing this data in an <a target=\"_blank\" href=\"https://clickhouse.com/engineering-resources/top-opentelemetry-compatible-platforms/\">Observability backend</a> - this is where ClickHouse comes in!</p>\n<h2 id=\"why-clickhouse\"></h2>\n<p>Trace data is typically represented as a single table, with each span a row, and thus can be considered just another real-time analytics problem. As well as providing high compression for this data type, ClickHouse provides a rich SQL interface with additional <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/reference\">analytical functions</a> that trivialize querying traces. When combined with Grafana, users have a <a target=\"_blank\" href=\"https://clickhouse.com/blog/breaking-free-from-rising-observability-costs-with-open-cost-efficient-architectures\">highly cost-efficient way of storing and visualizing traces</a>. While other stores may offer similar compression levels, ClickHouse is unique in combining this low latency querying as the world's fastest analytical database. In fact, these characteristics led to ClickHouse becoming a preferred backend for many commercial observability solutions like: <a target=\"_blank\" href=\"https://signoz.io/\">Signoz.io</a>, <a target=\"_blank\" href=\"https://www.highlight.io/\">Highlight.io</a>, <a target=\"_blank\" href=\"https://qryn.metrico.in/\">qryn</a>, <a target=\"_blank\" href=\"https://betterstack.com/press/series-a/\">BetterStack</a>, or homegrown large-scale observability platforms like <a target=\"_blank\" href=\"https://www.uber.com/en-ES/blog/logging/\">Uber</a>, <a target=\"_blank\" href=\"https://blog.cloudflare.com/http-analytics-for-6m-requests-per-second-using-clickhouse/\">Cloudflare</a>, or <a target=\"_blank\" href=\"https://about.gitlab.com/handbook/engineering/development/ops/monitor/observability/#how-are-we-currently-using-clickhouse\">Gitlab</a>.</p>\n<h2 id=\"instrumentation-libraries\"></h2>\n<p>Instrumentation libraries are provided for the most popular languages. These provide both automatic instrumentation of code, where an application/services framework is exploited to capture the most common metric and trace data, and manual instrumentation techniques. While automatic instrumentation is typically sufficient, the latter allows users to instrument-specific parts of their code, potentially in more detail - capturing application-specific metrics and trace information.</p>\n<p>For the purposes of this blog, we are only interested in the capture of trace information. The <a target=\"_blank\" href=\"https://opentelemetry.io/docs/demo/architecture/\">OpenTelemetry demo application consists of a microservices architecture</a> with many dependent services, each in a different language, to provide a reference for implementors. The OTEL Collector can also provide a centralized processing gateway by supporting several input formats, such as Prometheus and OTLP, and a wide range of export targets, including ClickHouse.</p>\n<p>The Collector uses the concept of pipelines. These can be of type logs, metrics, or traces and consist of a receiver, processor, and exporter.</p>\n<p><span><img alt=\"otel_collector.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fotel_collector_fef083663e.png&w=2048&q=75\"></span></p>\n<p>The <a target=\"_blank\" href=\"https://opentelemetry.io/docs/collector/configuration/#receivers\">receiver</a> in this architecture acts as the input for OTEL data. This can be either via a pull or push model. While this can occur over a number of protocols, trace data from instrumentation libraries will be pushed via <a target=\"_blank\" href=\"https://opentelemetry.io/docs/reference/specification/protocol/\">OTLP</a> using either gRPC or HTTP. <a target=\"_blank\" href=\"https://opentelemetry.io/docs/collector/configuration/#processors\">Processors</a> subsequently run on this data providing filtering, batching, and enrichment capabilities. Finally, an exporter sends the data to a backend destination via either push or pull. In our case, we will push the data to ClickHouse.</p>\n<p>Note that while more commonly used as a gateway/aggregator, handling tasks such as batching and retries, the collector can also be deployed as an agent itself - this is useful for log collection, as described in our previous post. OTLP represents the OpenTelemetry data standard for communication between gateway and agent instances, which can occur over gRPC or HTTP. For the purposes of trace collection, the collector is simply deployed as a gateway, however, as shown below:</p>\n<p><span><img alt=\"otel_architecture.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fotel_architecture_248c22ed3a.png&w=2048&q=75\"></span></p>\n<p>Note that more advanced architectures are possible for higher load environments. We recommend this <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=WhRrwSHDBFs\">excellent video discussing possible options</a>.</p>\n<h3 id=\"clickhouse-support\"></h3>\n<p>ClickHouse is supported in the OTEL exporter through <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter\">a community contribution</a>, with support for logs, traces, and metrics. Communication with ClickHouse occurs over the optimized native format and protocol via the official Go client. Before using the OpenTelemetry Collector, users should consider the following points:</p>\n<ul>\n<li>\n<p>The ClickHouse data model and schema that the agent uses are hard coded. For leaner deployments, users can <a target=\"_blank\" href=\"https://opentelemetry.io/docs/collector/custom-collector/\">build a custom collector image</a> with only the required components.</p>\n</li>\n<li>\n<p>As of version 0.74, users should pre-create the database in ClickHouse before deployment if not set to the value of <code>default</code> (as used in the demo fork).</p>\n<div><pre><code><span><span>CREATE</span> DATABASE otel</span></code></pre></div>\n</li>\n<li>\n<p>The exporter is in alpha, and users should adhere to the advice <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-collector#alpha\">provided by OpenTelemetry</a>.</p>\n</li>\n</ul>\n<h2 id=\"example-application\"></h2>\n<p><span><img alt=\"otel_demo.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fotel_demo_ab40c40d7f.png&w=2048&q=75\"></span></p>\n<p><a target=\"_blank\" href=\"https://opentelemetry.io/ecosystem/demo/\">OpenTelemetry provides a demo application</a> giving a practical example of the implementation of OpenTelemetry. Based on the partition expression <code>toDate(Timestamp)</code>, which creates a partition by day, queries that target the most recent data, e.g., the last 24 hours, will benefit. Queries over many partitions/days (only likely if you expand your retention beyond the default of 3 days) will conversely potentially be negatively impacted. If you expand your data retention period to months or years or have access patterns that need to target a wider time range, consider using a different expression, e.g., partition by week, if you have a TTL of a year.</p>\n</li>\n<li>\n<p><strong>Map</strong> - the Map type is used extensively in the above schema for attributes. These are designed to speed up queries that either filter by trace id or the maps or keys of our attributes. Generally, secondary indices are effective when a strong correlation between the primary key and the targeted column/expression exists, or a value is very sparse in the data. This ensures that when applying a filter matching this expression, <a target=\"_blank\" href=\"https://clickhose.com/docs/en/optimize/skipping-indexes\">granules on disk </a>that have a reasonable chance of not containing the target value can be skipped. Likewise, our attribute keys and values will be correlated with the ServiceName and SpanName columns of the primary key. Generally, we consider these to be good candidates for bloom filters. This seems to negate most of the benefit of the materialized view, which adds questionable value for the additional query and maintenance complexity. However, it provides an excellent example of how materialized views can potentially be applied to accelerate queries. We have insufficient evidence to testify to the value of other bloom filters and would recommend users experiment.</p>\n</li>\n<li>\n<p><strong>High memory</strong> - We have found the OTEL collector to be very memory intensive. In the earlier configuration, we use the <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-collector/blob/main/processor/batchprocessor/README.md\">batch processor</a> to send data to ClickHouse after 5s or when the batch reaches 100,000 rows. While this optimizes for ClickHouse inserts and adheres to <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/bestpractices/bulk-inserts\">best practices</a>, it can be very memory intensive under high load - especially when <a target=\"_blank\" href=\"https://clickhouse.com/blog/storing-log-data-in-clickhouse-fluent-bit-vector-open-telemetry\">collecting logs</a>. This can be mitigated by reducing the flush time and/or batch size. Be aware that this requires tuning as it may cause e<a target=\"_blank\" href=\"https://clickhouse.com/docs/knowledgebase/exception-too-many-parts\">xcessive parts to accumulate in ClickHouse</a>. Alternatively, users may wish to use <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/bestpractices/asynchronous-inserts\">asynchronous inserts </a>to send data. This will reduce the batch size but is only supported over HTTP in the exporter. To activate, use the <code>connection_params</code> in the exporter config, e.g.,</p>\n<div><pre><code><span><span>connection_params:</span></span>\n<span> \t<span>async_insert:</span> <span>1</span></span>\n<span> \t<span>wait_for_async_insert:</span> <span>0</span></span></code></pre></div>\n<p>Note that this will not be as efficient for inserts to ClickHouse.</p>\n</li>\n<li>\n<p><strong>End-to-end delivery</strong> - We currently see no support for end-to-end delivery guarantees. i.e., the application SDKs will consider a trace sent once the Collector receives it. If the OTEL Collector crashes, batches currently in memory will be lost. This can be mitigated by reducing the batch size (see above). However, users may also wish to consider alternative architectures involving Kafka (see <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/kafkareceiver\">receiver</a> and <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/kafkaexporter\">exporter</a>) or equivalent persistent queues if higher delivery guarantees are required. We have not explored the <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-collector/tree/main/exporter/exporterhelper#persistent-queue\">recent persistent queues feature</a>, which is in alpha but promises to improve resilience.</p>\n</li>\n<li>\n<p><strong>Scaling</strong> - The above deployment only utilizes a single collector. In a high-volume production environment, it is likely users would need to deploy multiple collectors behind a load balancer. The OTEL collector supports this using a <a target=\"_blank\" href=\"https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/exporter/loadbalancingexporter/README.md\">Trace Id/Service Name load-balancing exporter</a>. This ensures spans from the same trace are forwarded to the same collector. Note that we have also made no effort to tune agents or measure their resource overhead - something we recommend users research or do before production deployment. We plan to explore these topics in later posts.</p>\n</li>\n<li>\n<p><strong>Sampling</strong> - Our current implementation results in all data being stored in ClickHouse. While ClickHouse offers fantastic compression, we appreciate that users will wish to employ <a target=\"_blank\" href=\"https://opentelemetry.io/blog/2022/tail-sampling/\">sampling techniques</a>. This allows only a subset of traces to be stored, thus reducing hardware requirements. Be aware this<a target=\"_blank\" href=\"https://opentelemetry.io/blog/2022/tail-sampling/#limitations-of-opentelemetry\"> complicates scaling</a>. We will address this in a later post.</p>\n</li>\n</ul>\n<h2 id=\"conclusion\"></h2>\n<p>This blog post shows how traces can easily be collected and stored in ClickHouse using OpenTelemetry. We have forked the OpenTelemetry demo to support ClickHouse, touched on queries and visualization techniques using Grafana, and highlighted some approaches to reducing query complexity and some of the future work for the project. For further reading, we encourage users to explore topics beyond this post, such as how the OTEL collector can be deployed at scale, handling backpressure, and delivery guarantees.
