contentHtml: "<article><div><blockquote>\n<p><strong>TL;DR</strong><br><br>ClickHouse used to fully scan secondary indexes before query execution.<br>Streaming secondary indices make index evaluation incremental and demand-driven, eliminating unnecessary upfront work and improving latency and memory usage.</p>\n</blockquote>\n<h2 id=\"before-sequential-index-scans\"></h2>\n<p>Before ClickHouse 25.9, <strong>secondary indices</strong> (e.g., minmax, set, bloom filter, vector, text) were evaluated <em>before</em> reading the underlying table data.</p>\n<p>The index entries are scanned <em>upfront</em> to decide which <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes#data-is-organized-into-granules-for-parallel-data-processing\">granules</a> (the smallest processing units in ClickHouse, typically covering 8,192 rows each) may contain matching rows for a query’s WHERE filter.</p>\n<p>The following animation illustrates this process:</p>\n<p><span><img alt=\"Blog-release-25.9-animation-01.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_9_animation_01_5495b32bde.gif&w=2048&q=75\"></span></p>\n<p>① <strong>Index scan and granule selection</strong> - ClickHouse checks each index entry to determine which granules to read. Only matching granules are chosen; the others are skipped.</p>\n<p>② <strong>Query execution</strong> - The selected granules are <a target=\"_blank\" href=\"https://clickhouse.com/docs/optimize/query-parallelism\">streamed</a> into the query engine and processed into the final result.</p>\n<p>This upfront index evaluation has several drawbacks:</p>\n<ul>\n<li>\n<p><strong>Startup delay:</strong> Index analysis happens before the actual query execution begins.</p>\n</li>\n<li>\n<p><strong>Heavy index scans:</strong> In some cases (e.g., queries with highly selective WHERE filters over huge tables), scanning the index can cost more than scanning and processing the selected data itself.</p>\n</li>\n<li>\n<p><strong>Inefficient with LIMIT:</strong> Even if a query stops early due to a LIMIT, ClickHouse still has to scan the entire index upfront (and may select more data than necessary).</p>\n</li>\n</ul>\n<h2 id=\"how-streaming-secondary-indices-work\"></h2>\n<p>ClickHouse 25.9 eliminates these drawbacks by interleaving data reads with index checks, as shown in the animation below:</p>\n<p><span><img alt=\"Blog-release-25.9-animation-02.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_release_25_9_animation_02_1e370aca28.gif&w=2048&q=75\"></span></p>\n<p>① <strong>Index scan, granule selection, and</strong> ② <strong>query execution (concurrent)</strong> – When ClickHouse is about to read a table data granule (e.g. because it was selected by the <a target=\"_blank\" href=\"https://clickhouse.com/docs/primary-indexes\">primary index analysis</a>), it first checks the corresponding secondary index entry (if one exists). If the secondary index indicates the table granule can be skipped, it’s never read. Otherwise, the granule is read and processed by the query engine, while scanning continues on subsequent granules.</p>\n<p>This incremental, two-stream process—reading table granules alongside checking their secondary index entries—is why we call the feature <em>streaming secondary indices</em> (controlled by the setting <a target=\"_blank\" href=\"https://clickhouse.com/docs/operations/settings/settings#use_skip_indexes_on_data_read\">use_skip_indexes_on_data_read</a>) .</p>\n<p><em>(Note: For simplicity, the animation shows a single-threaded query engine, but in reality multiple threads process many granules concurrently.)</em></p>\n<p><strong>This concurrent execution eliminates the startup delay and avoids wasted work.</strong> For example, with queries that stop early due to a LIMIT, ClickHouse halts index checks and granule reads as soon as the result is complete.</p>\n<h2 id=\"demo-faster-results-with-streaming-secondary-indices\"></h2>\n<p>In the release webinar, Alexey <a target=\"_blank\" href=\"https://www.youtube.com/live/LCHEPNXo8kQ?si=uyYeTXZpDioXHbHN&t=1081\">demonstrated</a> <em>streaming secondary indices</em> on massive ClickHouse tables containing trillions of log records from test runs applied to pull requests and commits. On these datasets, some individual secondary indices alone exceed <strong>6 TB compressed</strong>.</p>\n<p>Since reproducing that scale isn’t practical, we’ll use a simplified artificial example that
