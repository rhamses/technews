We outline a formula that you can use to determine the best block size / parallelism ratio for your ingestion use case. And lastly, we will break the speed limit by utilizing ClickHouse Cloud’s new SharedMergeTree table engine combined with easy horizontal cluster scaling.</p>\n<p>Note that we only demonstrate a tuning scenario here, where data is pulled by the ClickHouse servers themselves. You can read about a setting where clients push the data to ClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse\">here</a>.</p>\n<h2 id=\"the-challenge\"></h2>\n<p>\nUsing ClickHouse for <a target=\"_blank\" href=\"https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#data-needs-to-be-batched-for-optimal-performance\">large data loads</a> is like driving a high-performance Formula One car 🏎 .\nA copious amount of raw horsepower is available, and you can reach top speed for your large data load. But, to achieve maximum ingestion performance, you must choose (1) a high enough gear (<a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#insert-block-size\">insert block size</a>) and (2) an appropriate acceleration level (<a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#insert-parallelism\">insert parallelism</a>) based on (3) the concrete amount of available horsepower (<a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#hardware-size\">CPU cores and RAM</a>).\n</p>\n<p>Ideally, we would like to drive our race car in the <strong>highest gear</strong> with <strong>full acceleration</strong>:</p>\n<ul>\n<li>Highest gear: The larger we <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#configuration-when-data-is-pulled-by-clickhouse-servers\">configure the insert block size</a>, the fewer parts ClickHouse has to create, and the fewer <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Category:Disk_file_systems\">disk file</a> <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Input/output\">i/o</a> and <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#more-parts--more-background-part-merges\">background merges</a> are required.</li>\n<li>Full acceleration: The higher we <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#configuration-when-data-is-pulled-by-clickhouse-servers-1\">configure the number of parallel insert threads</a>, the faster the data will be processed.</li>\n</ul>\n<p>However, there is a conflicting tradeoff between these two performance factors (plus a tradeoff with background part merges). The amount of available main memory of ClickHouse servers is limited. Larger blocks use <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#impact-on-performance-and-resource-usage\">more</a> main memory, which limits the number of parallel insert threads we can utilize. Conversely, a higher number of parallel insert threads requires <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#impact-on-performance-and-resource-usage-1\">more</a> main memory, as the number of insert threads determines the number of insert blocks created in memory concurrently. This limits the possible size of insert blocks. Additionally, there can be resource contention between insert threads and <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#more-parts--more-background-part-merges\">background merge threads</a>. A high number of configured insert threads (1) creates more parts that need to be merged and (2) takes away CPU cores and memory space from background merge threads.</p>\n<p>Our challenge is to find a sweet spot with a large enough block size and a large enough number of parallel insert threads to reach the best possible insert speed.</p>\n<h2 id=\"the-experiment\"></h2>\n<p>In the following sections, we put these block size / parallelism settings to the test and evaluate their effect on ingest speed.</p>\n<h3 id=\"test-data\"></h3>\n<p>The data we experiment with is from the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-vs-snowflake-for-real-time-analytics-benchmarks-cost-analysis#pypi-dataset\">PyPi dataset</a> (hosted in a GCS bucket). It consists of <strong>65.33 billion rows</strong> and has a raw, uncompressed size of ~<strong>14 TiB</strong>. The compressed data size on disk (when stored in a ClickHouse table) is ~<strong>1.2 TiB</strong>.</p>\n<h3 id=\"test-table-and-insert-query\"></h3>\n<p>For these tests, we will ingest this data as fast as possible into a <a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/50ec22c9cf6a5569c45d1aea958a09d4\">table</a> in a ClickHouse Cloud <a target=\"_blank\" href=\"https://clickhouse.com/pricing\">service that c</a>onsists of 3 ClickHouse servers with 59 CPU cores and 236 GiB of RAM per server. We’ll use an <a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/808dd03d7bc4cf061bf98b7bbb77c3a6\">INSERT INTO SELECT query</a> in combination with the <a target=\"_blank\" Our goal here is to tune a dedicated service only used by us for one purpose: Achieving top speed for inserting our dataset.</p>\n<p>If we match the amount of utilized parallel insert threads with the number of 59 available CPU cores, the time to 3k active parts is increased compared to lower thread settings.</p>\n<p>The lowest time is achieved with 16 insert threads, leaving plenty of the 59 CPU cores available for <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#more-parts--more-background-part-merges\">background part merge threads</a> that run concurrently with the data insertion.</p>\n<p>Note that the blue horizontal bar on top in the chart above denotes the available memory per server (236 GiB RAM). The following chart visualizes the results of these ingest test runs, where we doubled the insert block size a few times (from <a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/6c2bd2b6bd18aca4a1cce665d0c806fe\">1 million</a> to <a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/bfd88290a696144de9b5f6d4d07f0c08\">5 million</a> to <a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/4cff7a19f89faac96f53f2e3963403b3\">10 million</a> to <a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/174b81144169ae02dcec1c4518839f53\">20 million</a> to <a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/8955d5a57ad4babf84690a10f90da97a\">40 million</a>, until <a target=\"_blank\" href=\"https://gist.github.com/tom-clickhouse/3570f02b38e8b5f11351cd2d446f7d8c\">80 million</a>):</p>\n<p><span><img alt=\"large_data_loads-p2-07.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Flarge_data_loads_p2_07_357c63e939.png&w=2048&q=75\"></span></p>\n<p>For each block size, we doubled the number of insert threads (starting at 4) until the peak memory usage (blue vertical bars) almost reached the available memory per server (blue horizontal bar). This is the sweet spot for our server size of 59 CPU cores and 236 GiB RAM. This causes a moderate amount of <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part2#shifting-gears\">6.5 thousand initial parts</a>, that can be quickly merged to less than 3000 parts in the background by the free 27 CPU cores (32 cores are used for reading and ingesting the data in parallel). With 16 insert threads and less, the insert parallelism is too low. With 59 insert threads, a 10 million rows block size doesn’t fit into the RAM.</p>\n<p>A 5 million row block size works with 59 insert threads. Still, it creates <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part2#shifting-gears\">13 thousand initial parts</a> without leaving any dedicated CPU cores for an efficient background merging, resulting in resource contention and a long time to reach 3 thousand active parts. With 32 and 16 insert threads, the data is processed slower but merged faster as more dedicated CPU cores are available for background merges. 4 and 8 insert threads don’t create enough insert parallelism with a 5 million row block size.</p>\n<p>Insert block sizes of 20 million rows and more cause <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part2#shifting-gears\">low numbers of initial parts</a>, but the high memory overhead restricts insertion to a low number of insert threads creating insufficient insert parallelism.</p>\n<p><strong>With our identified sweet spot settings, we sped up the ingest by a factor of almost 3.</strong> We used exactly the same underlying hardware, but we utilized it more effectively for our data ingestion, without creating too many initial parts by pressing the accelerator pedal in half force (32 insert threads) with the highest possible gear (10 million rows block size).</p>\n<h2 id=\"formula-one\"></h2>\n<p>We are aware that identifying perfect settings for large multi-billion row inserts via several test runs is impractical. Therefore we give you this handy formula for calculating approximately the settings for top speed of your large data loads:</p>\n<p><code>• <code>max_insert_threads</code>: choose ~ half of the available CPU cores for insert threads (to leave enough dedicated cores for background merges)\n<br><br>• <code>peak_memory_usage_in_bytes</code>: choose an intended peak memory usage; either all available RAM (if it is an isolated ingest) or half or less (to leave room for other concurrent tasks) <br><br>Then:<br><code>min_insert_block_size_bytes</code> = <code>peak_memory_usage_in_bytes</code> / (~3 * <code>max_insert_threads</code>)\n</code></p>\n<p>With this formula, you can set <code>min_insert_block_size_rows</code> to 0 (to disable the row based threshold) while setting <code>max_insert_threads</code> to the chosen value and <code>min_insert_block_size_bytes</code> to the calculated result from the above formula.</p>\n<h2 id=\"breaking-the-speed-limit-with-clickhouse-cloud\"></h2>\n<p><span><img alt=\"large_data_loads-p2-08.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Flarge_data_loads_p2_08_ac7345f2e0.png&w=2048&q=75\"></span></p>\n<p>The next measure to make the ingestion even faster is to put more horsepower into our engine and increase the number of available CPU cores, respectively, by adding additional servers.</p>\n<p>Combined with its <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates\">SharedMergeTree table engine</a>, ClickHouse Cloud <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates#automatic-cluster-scaling\">allows</a> you to freely (and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates#seamless-cluster-scaling\">quickly</a>!) either change the size (CPU and RAM) of existing servers or add additional servers.
