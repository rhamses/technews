For example, assuming an (arbitrarily) basic transfer throughput of 10 million rows per second, 36 billion rows can be loaded per hour and 864 billion rows per day. Loading a few trillion rows would require multiple days.</p>\n<p>This is enough time for things to go temporarily wrong - for example, there could be a transient network connection issue, causing the data load to be interrupted and fail. Without a managed solution using a stateful orchestration of the data transfer with built-in resiliency and automatic retries, users often resort to truncating the ClickHouse target table and starting the whole data load from scratch again. This further increases the overall time it takes to load the data and, most importantly, could also fail again, leaving you unhappy. Alternatively, you can try to identify which data was successfully ingested into the ClickHouse target table and then try to load just the missing subset. This can be tricky without a unique sequence in your data and requires manual intervention and extra time.</p>\n<h2 id=\"clickpipes\"></h2>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/cloud/clickpipes\">ClickPipes</a> is a fully managed integration solution in <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> providing built-in support for continuous, fast, resilient, and scalable data ingestion from an external system:</p>\n<p><span><img alt=\"clickpipes.gif\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickpipes_552fe0630e.gif&w=2048&q=75\"></span></p>\n<p>Having only <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickpipes-is-generally-available\">GA’d</a> this September, ClickPipes currently supports Apache Kafka in a number of flavors: OSS <a target=\"_blank\" href=\"https://kafka.apache.org/\">Apache Kafka</a>, <a target=\"_blank\" href=\"https://www.confluent.io/lp/confluent-cloud/\">Confluent Cloud</a>, and <a target=\"_blank\" href=\"https://aws.amazon.com/msk/\">AWS MSK</a>. This recommendation is made for several reasons:</p>\n<ol>\n<li>\n<p>Most current database systems and external data sources support an efficient and reliable export of very large data volumes into (relatively cheap) object storage.</p>\n</li>\n<li>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/blog/apache-parquet-clickhouse-local-querying-writing\">Parquet</a> has become almost ubiquitous as a file interchange format that offers highly efficient <a target=\"_blank\" href=\"https://clickhouse.com/blog/apache-parquet-clickhouse-local-querying-writing-internals-row-groups#compression\">storage</a> and <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-23-05#parquet-reading-even-faster-michael-kolupaev\">retrieval</a>. ClickHouse has blazingly <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-23-08#reading-files-faster-michael-kolupaevpavel-kruglov\">fast</a> built-in Parquet support.</p>\n</li>\n<li>\n<p>A ClickHouse server can process and insert the data from files stored in object storage with a <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#configuration-when-data-is-pulled-by-clickhouse-servers-1\">high level of parallelism</a> utilizing all available CPU cores.</p>\n</li>\n</ol>\n<p>② You can then use our <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad#clickload\">ClickLoad script</a>, described in more detail below, that orchestrates a reliable and resilient data transfer into your ClickHouse target table by utilizing one of our object storage integration table functions (e.g. <a target=\"_blank\" provide a step-by-step example of using ClickLoad <a target=\"_blank\" for ClickLoad originated from our<a target=\"_blank\" href=\"https://clickhouse.com/support/program\"> support</a> team guiding some of our ClickHouse Cloud customers in successfully migrating their data with trillions of rows.</p>\n<p>In a classical <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Divide-and-conquer_algorithm\">divide-and-conquer</a> fashion, ClickLoad splits the overall to-be-loaded file data into repeatable and retry-able tasks. These tasks are used to load the data from object storage incrementally into ClickHouse tables, with automatic retries in case of failures.</p>\n<p>For <strong>easy scalability</strong>, we adapt the queue-worker approach <a target=\"_blank\" href=\"https://clickhouse.com/blog/building-real-time-applications-with-clickhouse-and-hex-notebook-keeper-engine\">introduced</a> in another blog. Stateless ClickLoad <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py\">workers</a> orchestrate the data loading by reliably claiming file load tasks from a <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad#table-schemas-for-job-task-table\">task table</a> backed by the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/keeper-map\">KeeperMap table engine</a>. Each task potentially contains multiple files to process, with the KeeperMap table <a target=\"_blank\" href=\"https://clickhouse.com/blog/building-real-time-applications-with-clickhouse-and-hex-notebook-keeper-engine#using-the-keepermap-table-engine\">guaranteeing</a> each task (and thus file) can only be assigned to one worker. This allows us to parallelize the file load process by <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/examples/pypi/README.md#step--spinning-up-100-workers\">spinning up</a> additional workers, <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part3#insert-throughput-can-be-easily-scaled\">increasing</a> the overall ingest throughput.</p>\n<p>As a prerequisite, the task table is populated with file load tasks for the ClickLoad workers:</p>\n<p><span><img alt=\"large_data_loads-p3-03.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Flarge_data_loads_p3_03_e36d9f3100.png&w=2048&q=75\"></span></p>\n<p>① Users can utilize a corresponding object storage command line interface tool (e.g. Amazon <a target=\"_blank\" href=\"https://aws.amazon.com/cli/\">aws-cli</a>, Microsoft <a target=\"_blank\" href=\"https://learn.microsoft.com/en-us/cli/azure/\">azure-cli</a>, or Google <a target=\"_blank\" href=\"https://cloud.google.com/storage/docs/gsutil\">gsutil</a>) for <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/examples/pypi/README.md#step--create-a-file-containing-the-bucket-urls-for-all-to-be-loaded-files\">creating</a> a local file containing the object storage urls of the to-be-loaded files.</p>\n<p>② We provide <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad#scheduling-files-for-clickhouse-import\">instructions</a> plus a separate script <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/queue_files.py\">queue_files.py</a> that <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/queue_files.py#L123\">splits</a> the entries from the file from step ① into <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/queue_files.py#L128\">chunks</a> of file urls and <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/queue_files.py#L105\">loads</a> these chunks as file load tasks into the task table.</p>\n<p>The following diagram shows how these file load tasks from the task table are used by a ClickLoad worker orchestrating the data load:</p>\n<p><span><img alt=\"large_data_loads-p3-04.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Flarge_data_loads_p3_04_db22d9a507.png&w=2048&q=75\"></span></p>\n<p>For <strong>easy retry-able file loads</strong> in case <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part3#resilient-data-loading\">something goes wrong</a>, each ClickLoad worker first loads all file data into a (<a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L617\">different</a> per worker) <code>staging table</code>: after ① <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L209\">claiming</a> its next task, a worker <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L279\">iterates</a> over the task’s list of file urls and ② (sequentially) instructs the ClickHouse server to load each file from the task into a <code>staging table</code> by using <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L297\">INSERT INTO SELECT FROM queries</a> (where the ClickHouse server by itself <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#configuration-when-data-is-pulled-by-clickhouse-servers-1\">pulls</a> the file data from object storage). This inserts the file data with a <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#configuration-when-data-is-pulled-by-clickhouse-servers-1\">high level of parallelism</a> and creates <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#mergetree-data-storage\">data parts</a> in the staging table.</p>\n<p>Suppose one of the insert queries for the current task is interrupted and fails in between a state where the staging table already contains some data in the form of parts. In this case, the worker first ③ instructs the ClickHouse server to <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L263C17-L263C17\">truncate</a> the staging table (drop all parts), and then ② <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L256\">retries</a> its current file load task from scratch. On successfully completing the task, the worker ③ uses specific <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L591\">queries</a> and <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L606\">commands</a>, causing the ClickHouse server to <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L269\">move</a> all parts (from all partitions) from the staging table to the target table. The worker then ① claims and processes the next task from the task table.</p>\n<p>In <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a>, all data is stored <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates#clickhouse-cloud-enters-the-stage\">separately</a> from the ClickHouse servers in <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates#shared-object-storage-for-data-availability\">shared object storage</a>. Consequently, moving parts is a lightweight operation that only changes parts' <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates#sharedmergetree-for-cloud-native-data-processing\">metadata</a> but doesn’t physically move parts.</p>\n<p>Note that each worker <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L173\">creates</a> its <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L406\">own</a> staging tables on startup and then executes an <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L191\">endless loop</a> checking for unprocessed tasks, with <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L203C16-L203C16\">sleep breaks</a> in case no new task is found. We use a <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L124\">signal handler</a> <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L143\">registered</a> for <code>SIGINT</code> (<code>Ctrl+C</code>) and <code>SIGTERM</code> (Unix process <code>kill signal</code>) signals for cleaning up (deleting) the worker’s staging tables when a worker is shut down.</p>\n<p>Also, note that a worker processes atomic <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L194\">chunks of files</a> instead of single files to reduce <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-keeper-a-zookeeper-alternative-written-in-cpp#linearizability-vs-multi-core-processing\">contention on Keeper</a> when replicated tables are used. The latter creates a (much) larger number of <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter/partition#move-partition-to-table\">MOVE PARTITION</a> calls that are coordinated by Keeper in a replicated cluster. Furthermore, we <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/queue_files.py#L127\">randomize</a> the file chunk size to prevent Keeper contention when multiple parallel workers run.</p>\n<h3 id=\"staging-tables-ensure-that-loaded-data-will-be-stored-exactly-once\"></h3>\n<p>The <code>INSERT INTO SELECT FROM</code> queries used by the ClickLoad workers could insert the file data directly into the target table. But when an insert query invariably fails, so as not to cause data duplication when we retried the task, we would need to delete all data from the previously failed task. This deletion is much more difficult than when data is inserted into a staging table, which can simply be truncated.</p>\n<p>For example, just dropping parts in the target table is impossible as the initially inserted parts get automatically <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#more-parts--more-background-part-merges\">merged</a> (potentially with parts from prior successful inserts) in the background.</p>\n<p>Relying on <a target=\"_blank\" href=\"https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse#5-deduplication-at-insert-time\">automatic insert deduplication</a> is also not generally possible because (1) it is highly unlikely that <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#configuration-when-data-is-pulled-by-clickhouse-servers-1\">insert threads</a> recreate exactly the same insert blocks, and (2) with a high number of running workers, the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/merge-tree-settings#replicated-deduplication-window\">default</a> per-table deduplication window in ClickHouse could be insufficient.</p>\n<p>Lastly, explicitly deduplicating all rows with an <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/optimize\">OPTIMIZE DEDUPLICATE</a> statement would be (1) a very heavy and slow operation the larger the target table gets and (2) could potentially accidentally deduplicate rows that are intentionally identical in the source data files.</p>\n<p>The only way to reliably delete the data from a failed insert from the target table before retrying the insert would be to use an ​​<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter/delete\">ALTER TABLE DELETE</a>, a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/lightweight-delete\">lightweight delete</a>, or a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/lightweight-update\">lightweight update</a> statement. All of these are eventually materialized with a heavy <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter#mutations\">mutation</a> operation, which becomes more expensive as the table increases in size.</p>\n<p>Conversely, the detour via a staging table allows our workers to guarantee that each row from the loaded files is stored exactly once in the target table by efficiently dropping or moving parts, depending on whether the task failed or succeeded.</p>\n<h3 id=\"workers-are-lightweight\"></h3>\n<p>ClickLoad’s worker <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py\">script</a> only orchestrates data loading but doesn’t actually load any data by itself. Instead, the ClickHouse server and its hardware resources are utilized for <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#configuration-when-data-is-pulled-by-clickhouse-servers-1\">pulling</a> the data from object storage and writing it into ClickHouse tables.</p>\n<p>Note that running ClickLoad requires a separate machine with network access to both the source object storage bucket and the target ClickHouse instance. Because of the workers’ lightweight working fashion, a moderately sized machine <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/examples/pypi/README.md#example-for-resiliently-loading-a-large-data-set\">can</a> run 100s of parallel worker instances.</p>\n<h3 id=\"insert-throughput-can-be-easily-scaled\"></h3>\n<p>Multiple workers and <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part1#clickhouse-cloud\">multiple ClickHouse servers</a> (with a <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/cloud/reference/architecture\">load balancer</a> in front in ClickHouse Cloud) can be utilized for <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/examples/pypi/README.md#result\">scaling</a> the ingest throughput:</p>\n<p><span><img alt=\"large_data_loads-p3-05.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Flarge_data_loads_p3_05_adf15d96ff.png&w=2048&q=75\"></span></p>\n<p>The <code>INSERT INTO SELECT FROM</code> queries from all workers are evenly distributed to, and then executed in parallel, by the number of available ClickHouse servers. Note that each worker has its <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L617\">own</a> staging table.</p>\n<p>Doubling the number of workers can double the ingest throughput, provided the ClickHouse servers executing the insert queries have enough resources.</p>\n<p>Similarly, doubling the number of ClickHouse servers can double the ingest throughput.  In our tests, when loading a 600+ billion row <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-vs-snowflake-for-real-time-analytics-benchmarks-cost-analysis#pypi-dataset\">dataset</a> (with 100 parallel workers), increasing the number of ClickHouse servers in a ClickHouse Cloud service from 3 to 6 exactly doubled the ingest throughput (from 4 million rows/second to 8 million rows/second).</p>\n<h3 id=\"continuous-data-ingestion-is-possible\"></h3>\n<p>As mentioned above, each worker executes an <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L191\">endless loop</a> checking for unprocessed tasks in the task table with <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L203C16-L203C16\">sleep breaks</a> in case no new task is found. This allows the easy implementation of a continuous data ingestion process by adding new file load tasks into the task table in case new files are detected in the object storage bucket. The running workers will then automatically claim these new scheduled tasks. We describe a concrete example <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/examples/pypi/README.md#setting-up-a-continuous-data-load\">here</a> but leave this implementation to the reader</p>\n<h3 id=\"any-partitioning-key-is-supported\"></h3>\n<p>The ClickLoad worker's file load mechanism is independent of any <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/custom-partitioning-key\">partitioning</a> scheme of the target table. The workers don’t create any partitions by themselves. We also don’t require that each loaded file belong to a specific partition. Instead, the target table can have any (or no) <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/custom-partitioning-key\">custom partition key</a>, which we duplicate in the staging table (which is a DDL-level <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L399\">clone</a> of the target table).</p>\n<p>After each successful <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L261\">files chunk transfer</a>, we just <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/tree/main/blog-examples/large-data_loads/src/worker.py#L269\">move</a> over all (parts belonging to) partitions that were naturally created for the staging table during the ingest of data from the currently processed files. This means that overall, exactly the same number of partitions <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/internals#support-for-arbitrary-partitioning-keys\">are</a> created for the target table as if we inserted all data (without using our ClickLoad script) directly into the target table.</p>\n<p>You can find a more detailed explanation <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/internals#support-for-arbitrary-partitioning-keys\">here</a>.</p>\n<h3 id=\"projections-and-materialized-views-are-fully-supported\"></h3>\n<p>Loading trillions of rows reliably into the target table is a good first step. However, <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter/projection\">projections</a> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/cascading-materialized-views\">materialized views</a> can <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-faster-queries-with-projections-and-primary-indexes\">supercharge your queries</a> by allowing a table to have <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=QDAJTKZT8y4&t=414s\">automatic incremental aggregations</a> and multiple-row orders with <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#using-multiple-primary-indexes\">additional primary indexes</a>.</p>\n<p>Creating projections or materialized views on the target table <strong>after</strong> the trillions of rows are initially loaded would require expensive projection <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/alter/projection#materialize-projection\">materializations</a> or a ClickHouse-side table-to-table reload of the data for <a target=\"_blank\" href=\"https://www.youtube.com/watch?v=QDAJTKZT8y4\">triggering</a> materialized views. Both of these would again take a long period of time, including the risk that something goes wrong. Therefore, the most efficient option is to create projections and materialized views <strong>before</strong> the initial data load. ClickLoad fully (and transparently) supports this.</p>\n<h4 id=\"projections-support\"></h4>\n<p>The staging table <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L165\">created</a> by our ClickLoad worker script is a full DDL-level clone of the target table, including all defined projections. Because the data parts of projections <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/optimize/sparse-primary-indexes#option-3-projections\">are</a> stored as subdirectories within the <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/internals#support-for-arbitrary-partitioning-keys\">part directories</a> of the projection's host table, they are automatically moved over from the staging table to the target table after each file load task.</p>\n<h4 id=\"materialized-views-support\"></h4>\n<p>The following diagram shows the basic logic for ClickLoad’s materialized views support:</p>\n<p><span><img alt=\"large_data_loads-p3-06.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Flarge_data_loads_p3_06_55dc349ce4.png&w=2048&q=75\"></span></p>\n<p>In the diagram above, the target table has two connected materialized views (<code>MV-1</code> and <code>MV-2</code>) that would trigger on new direct inserts into the target table and store the data (in a <a target=\"_blank\" href=\"https://youtu.be/QDAJTKZT8y4?si=a6isJuHsYCG-dTDA\">transformed</a> form) in their own target tables.</p>\n<p>Our ClickLoad worker script replicates this behavior by automatically creating a staging table not <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L399\">just</a> for the main target table but <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L419\">also</a> for all materialized view (mv) target tables. Together with the additional staging tables, we automatically <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L422\">create</a> clones of the materialized view triggers but configure them to react to inserts on the staging table and then target their corresponding target staging tables.</p>\n<p>When ① data gets inserted into the target table’s staging table (and ② stored in the form of parts), this insert ③ automatically triggers the mv copies, ④ causing corresponding inserts into the target tables of the staging mvs. If the whole insert succeeds, we ⑤ <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L269\">move</a> all parts (partitions) from the staging tables into their counterparts. If something goes wrong, e.g., one of the materialized views has a problem with the current data, we just <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L263\">drop</a> all parts from all staging tables and <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L256\">retry</a> the insert. If the <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L23\">maximum number of retries</a> is exceeded, we skip (and log) the current file and continue with the next one. With this mechanism, we ensure that the insert is atomic and the data is always consistent between the main target table and all connected materialized views.</p>\n<p>Note that moving parts into the target table in step ⑤ does not trigger any of the connected original materialized views.</p>\n<p>Detailed error information about failed materialized views is in the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/system-tables/query_views_log\">query_views_log</a> system table.</p>\n<p>Also, as explained <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part3#any-partitioning-key-is-supported\">above</a>, the target tables for the materialized views can have any (or no) <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/custom-partitioning-key\">custom partition key</a>. Our orchestration logic is independent of this.</p>\n<p>Our ClickLoad worker script currently only supports materialized views created with the <code>TO target_table</code> <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/view#materialized-view\">clause</a> and doesn’t support <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/cascading-materialized-views#yearly-aggregated-table-and-materialized-view\">chained</a> (<code>cascaded</code>) materialized views.</p>\n<h3 id=\"clickload-works-best-with-moderate-file-sizes\"></h3>\n<p>The worker’s processing unit is a whole file. If something goes wrong while a file is loaded, we reload the whole file. Therefore, we recommend using moderately sized files with millions but not trillions of rows per file and approximately 100 to 150 MB in compressed size. This ensures an efficient retry mechanism.</p>\n<h3 id=\"prs-are-welcome\"></h3>\n<p>As mentioned above, the origin of our ClickLoad script was helping some of our ClickHouse Cloud customers migrate their large data amounts during support interactions. Therefore, the script currently relies on cloud-specific features like <code>MOVE PARTITION</code> <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part3#the-core-approach\">being</a> a lightweight operation for the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates\">SharedMergeTree</a> engine. This engine also allows the <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-cloud-boosts-performance-with-sharedmergetree-and-lightweight-updates#seamless-cluster-scaling\">easy</a> scaling up of the number of ClickHouse servers for <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part3#insert-throughput-can-be-easily-scaled\">increasing</a> the ingest throughput. We haven’t had a chance to test the script on alternative setups yet, but we welcome <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main\">contributions</a>. In principle, it should work on alternative setups with minimal tweaks. The <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/src/worker.py#L592\">MOVE PARTITION operations</a> must run on all shards in a sharded cluster, e.g., by utilizing the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/distributed-ddl\">ON CLUSTER</a> clause. Also, note that MOVE PARTITION currently cannot be run concurrently when <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/storing-data#zero-copy\">zero-copy replication</a> is used. We hope the script serves as a helpful starting point, and we welcome its use in more use cases and scenarios and collaborating on improvements!</p>\n<p>In the future, we expect the mechanics of this script to be considered as we build out support in <a target=\"_blank\" href=\"https://clickhouse.com/blog/supercharge-your-clickhouse-data-loads-part3#clickpipes\">ClickPipes</a> for ingesting files from object storage. Stay tuned for updates!</p>\n<h2 id=\"summary\"></h2>\n<p>Loading large datasets with trillions of rows can be a challenge. To overcome this, ClickHouse Cloud has <a target=\"_blank\" href=\"https://clickhouse.com/cloud/clickpipes\">ClickPipes</a> - a built-in managed integration solution featuring support for resiliently loading large data volumes robust to interruptions with automatic retries. If your external data source is not supported yet, we explored the mechanics of <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickLoad/blob/main/README.md\">ClickLoad</a> - a script for loading large datasets incrementally and reliably over a long period of time.</p>\n<p>This finishes our three-part blog series about supercharging large data loads.</p></div></article>"
