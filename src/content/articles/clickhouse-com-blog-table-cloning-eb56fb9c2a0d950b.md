Without touching the production data at all. And <strong>without copying a single byte</strong>.</p>\n<p>In ClickHouse, you can.</p>\n<p>This is one of those features that feels like magic. But it’s actually a very clean consequence of how ClickHouse stores data.</p>\n<p>And although this feature is <a target=\"_blank\" run tests on a <a target=\"_blank\" href=\"https://clickhouse.com/blog/introducing-warehouses-compute-compute-separation-in-clickhouse-cloud\">separate service with isolated compute resources</a>.</p>\n</blockquote>\n<p>In this post, we’ll take a closer look at how table cloning works under the hood, and why immutable data parts make it possible.</p>\n<p><strong>Prefer a quick walkthrough?</strong></p>\n<p>Mark recorded a short explanation of table cloning:</p>\n<h2 id=\"user-content-reminder_the_immutable_data_part_model\"></h2>\n<p>Every insert into a ClickHouse table produces a new, self-contained, immutable <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">data part</a> on disk.</p>\n<p>To sketch this, we use the following orders table tracking the total revenue per customer:</p>\n<div><pre><code><span><span>CREATE TABLE</span> orders</span>\n<span>(</span>\n<span>    order_id UInt32,</span>\n<span>    customer String,</span>\n<span>    total UInt32</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> order_id;</span></code></pre></div>\n<p>For this insert into the orders table:</p>\n<div><pre><code><span><span>INSERT INTO</span> orders <span>VALUES</span></span>\n<span>    (<span>1001</span>, <span>'Liam'</span>, <span>31000</span>),</span>\n<span>    (<span>1002</span>, <span>'Ben'</span>,   <span>7500</span>),</span>\n<span>    (<span>1003</span>, <span>'Anna'</span>, <span>12000</span>);</span></code></pre></div>\n<p>ClickHouse creates a new part on disk:</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclone_tables_feb2026_image2_521b2b8d25.png&w=2048&q=75\"></span>\n<br></p>\n<p>Under the hood, this part is a <strong>directory</strong> on disk that contains compressed <strong>column files</strong>, one per column in the table: order_id, customer, and total. Rows inside a part are physically sorted by the table’s sorting key, in this case, order_id.</p>\n<p>Data parts are fully self-contained. They include all metadata required to interpret their contents, without relying on a central catalog. Not shown in the diagram above, but parts contain additional metadata files, such as the sparse primary index, secondary data skipping indexes, column statistics, checksums, min-max indexes (if partitioning is used), and more.</p>\n<p>As new data arrives, ClickHouse never modifies existing parts in place. It always writes <strong>new parts</strong>.</p>\n<p>In the background, parts are <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges\">merged</a> into larger parts to control part counts and consolidate data, but even merges produce entirely <strong>new parts</strong>.</p>\n<p><em>(This design also enables ClickHouse to achieve <a target=\"_blank\" href=\"https://clickhouse.com/docs/concepts/why-clickhouse-is-so-fast#storage-layer-concurrent-inserts-are-isolated-from-each-other\">very high insert throughput</a>: data can be written as independent parts without global synchronization, and <a target=\"_blank\" href=\"https://clickhouse.com/docs/concepts/why-clickhouse-is-so-fast#storage-layer-merge-time-computation\">consolidated</a> later during background merges.)</em></p>\n<p>Similarly, deleting rows…</p>\n<div><pre><code><span><span>DELETE</span> <span>FROM</span> orders <span>WHERE</span> order_id <span>=</span> <span>1001</span>;</span></code></pre></div>\n<p>…or updating rows…</p>\n<div><pre><code><span><span>UPDATE</span> orders</span>\n<span><span>SET</span> total <span>=</span> <span>3600</span></span>\n<span><span>WHERE</span> order_id <span>=</span> <span>36043</span>;</span></code></pre></div>\n<p>…is <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-2-sql-style-updates\">implemented</a> by identifying the part containing the affected rows, writing a <strong>new part</strong> (or <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-2-sql-style-updates#stage-3-patch-parts--updates-the-clickhouse-way\">part fragment</a>) with the changes applied, and then eventually removing the old part.</p>\n<p>This <strong>strict immutability</strong> is the architectural property that makes instant, zero-copy table cloning possible.</p>\n<h2 id=\"user-content-from_immutable_parts_to_instant_clones\"></h2>\n<p>When you execute…</p>\n<div><pre><code><span><span>CREATE TABLE</span> staging CLONE <span>AS</span> production;</span></code></pre></div>\n<p>…ClickHouse does <strong>not</strong> copy the production table’s data.</p>\n<h3 id=\"no-data-is-copied\"></h3>\n<p>Because data parts are immutable and never modified in place, their content can be safely shared.</p>\n<p>Instead of copying data, ClickHouse creates a corresponding part directory for the cloned table for each existing part of the source table. If the source table has 142 parts, the clone will also have 142 parts.</p>\n<p>The files inside the cloned table’s part directories are <strong>hard-linked</strong> to the corresponding files in the source table’s part directories (via <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Hard_link\">POSIX hard links</a> on local filesystems or via metadata indirection on object storage such as S3).</p>\n<p>This applies to all files inside the part directory, including column data files as well as metadata files such as the sparse primary index, secondary data skipping indexes, column statistics, checksums, and min-max indexes.</p>\n<p><em>For clarity, the discussion below focuses on column files to explain the mechanics. In reality, the same hard-linking behavior applies to every file inside the part directory.</em></p>\n<h3 id=\"the-clone-behaves-exactly-like-the-source\"></h3>\n<p>At the moment of cloning, the new table has exactly the same number of data parts and the same column files and indexes per data part as the source table.</p>\n<p>The clone, therefore, behaves exactly like the original: queries, mutations, background merges, and storage layout all work in the same way. There is no “lightweight” or degraded mode. The clone is a full-fledged table from the very beginning.</p>\n<blockquote>\n<p>If you’re familiar with Git, this is essentially a fork: the cloned table starts identical to the original and diverges only when you modify it.</p>\n</blockquote>\n<h3 id=\"safe-sharing-through-immutability\"></h3>\n<p>Sharing column files between the production table and the cloned table is safe because any modification (inserts, deletes, or updates) always produces new data parts containing new column files.</p>\n<p><strong>If you modify the cloned table</strong>:<br>\nClickHouse writes new parts for the clone only. The original production table continues referencing the unchanged parts.</p>\n<p>Conversely, <strong>if the production table is modified</strong>:<br>\nIt also produces new parts containing new column files, while the previously referenced column files remain in place as long as data parts of the cloned table still reference them (as explained below, column files are only removed when no table references them anymore).</p>\n<h3 id=\"copy-on-write-and-storage-efficiency\"></h3>\n<p>As a consequence, as long as neither table modifies the shared data, <strong>the clone consumes virtually no additional disk space for the data itself</strong>. The referenced corresponding data part directories of both tables simply share the same underlying column files.</p>\n<p>Only when data of one of the tables is modified are new parts written, and even then, only for the affected data.</p>\n<blockquote>\n<p><strong>Part-level copy-on-write</strong><br>\nEven in a petabyte-scale table, updating a single row rewrites only the data part that contains it, <strong>not the entire dataset</strong>. All other parts remain shared and untouched.</p>\n</blockquote>\n<p>This is a fundamental property of the storage design: modifications are isolated at the part level, not the table level.</p>\n<p>Note that this <strong>part-level copy-on-write is not something special that only the clone does</strong>. It is the fundamental mechanism used for all data modifications in ClickHouse, including for the source table itself.</p>\n<p>As explained earlier, data modifications are implemented by identifying the part containing the affected rows, writing a new part with the changes applied, and eventually removing the old part.</p>\n<p>This <em>is</em> part-level copy-on-write. Cloning doesn’t introduce a new write path. It reuses the exact same storage mechanics that power all data modifications.</p>\n<h3 id=\"the-source-table-is-no-longer-special\"></h3>\n<p>Because parts are shared independently, <strong>the source table is no longer special after cloning</strong>.  it is simply another table referencing the same column files. You can drop the source table, and the column files will remain on disk as long as the data parts of the cloned table still reference them. Underlying column files are only removed once no table (and no running query) references them anymore.</p>\n<h3 id=\"instant-cloning-independent-of-table-size\"></h3>\n<p>The cloning time is effectively independent of table size.</p>\n<p>Whether the source table contains millions of rows or trillions, even petabytes of data, <strong>cloning is near-instantaneous</strong>.</p>\n<p>Technically, cloning time is proportional to the number of data parts (not the number of rows or bytes), since ClickHouse only creates corresponding part directories and hard links to existing files. Because these are lightweight filesystem operations, cloning remains extremely fast in practice, even for very large tables.</p>\n<p>To see how this works in practice, let’s walk through it visually.</p>\n<h2 id=\"user-content-copy_on_write_in_action\"></h2>\n<p>The diagrams below illustrate the part-level copy-on-write behavior described above.</p>\n<p>The first diagram sketches how the column files inside the data parts of a cloned table are hard-linked to the column files of the source table data parts.</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclone_tables_feb2026_image3_d323c0323d.png&w=2048&q=75\"></span>\n<br></p>\n<p><em>For simplicity, the diagram highlights only the column files. In reality, a data part also contains metadata files such as the sparse primary index, secondary data skipping indexes, column statistics, checksums, and min-max indexes. The entire set of files inside the part directory is hard-linked.</em></p>\n<p>And when the cloned table is updated…</p>\n<div><pre><code><span><span>UPDATE</span> cloned_orders</span>\n<span><span>SET</span> total <span>=</span> <span>3600</span></span>\n<span><span>WHERE</span> order_id <span>=</span> <span>36043</span>;</span></code></pre></div>\n<p>…a copy-on-write operation occurs:</p>\n<p><span><img alt=\"\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclone_tables_feb2026_image4_0b8375336b.png&w=2048&q=75\"></span>\n<br></p>\n<p>As explained earlier, this rewrite happens at the <strong>part level</strong>: only the data part containing the affected row is replaced. All other parts remain shared and untouched.</p>\n<p>The affected data part in the cloned table is rewritten as a new physical part containing the updated rows. The cloned table now references this newly written part directory instead of its previous directory, whose column files were hard-linked to the source.</p>\n<p>The cloned table’s original part directory, containing hard links to the source part’s column files, is removed (because it is replaced with the newly written part).</p>\n<p>The original production table continues to reference its unchanged part directory.</p>\n<p>Since the original table still references its unchanged part directory (whose column files were hard-linked from the clone’s previous part directory), the underlying files remain on disk.</p>\n<p>Column files are only removed once no table depends on them anymore.</p>\n<p>This is the core mechanism behind table cloning in ClickHouse.</p>\n<p>Immutability makes sharing safe. Part-level copy-on-write guarantees isolation <strong>without rewriting entire tables</strong>.</p>\n<p>Now that we’ve seen how it works under the hood, let’s step back and look at what this enables in practice.</p>\n<h2 id=\"user-content-putting_it_all_together\"></h2>\n<p>Table cloning in ClickHouse is a surprisingly powerful and practical feature.</p>\n<p>Whenever you need an <strong>exact copy</strong> of a table</p>\n<ul>\n<li>for staging environments</li>\n<li>schema or index experiments</li>\n<li>backfills</li>\n<li>migrations</li>\n<li>testing destructive changes</li>\n</ul>\n<p>You can create it <strong>instantly</strong>, without risking production data.</p>\n<p>The clone starts as an exact copy. It evolves independently. And as long as no data is modified, it consumes virtually <strong>no additional storage</strong>.</p>\n<p>Cloning feels like magic.</p>\n<p>It’s a natural consequence of how ClickHouse stores data: immutable parts that can be safely shared, combined with part-level copy-on-write semantics.</p>\n<p>Because parts are never modified in place, they can be reused. Because modifications always create new parts, isolation is guaranteed.</p>\n<p>The result is a feature that is simple, safe, storage-efficient, and effectively independent of table size.</p>\n<p>And in ClickHouse Cloud, cloned tables can optionally be queried from isolated compute services, so both your production data <em>and</em> compute remain untouched.</p></div>"
