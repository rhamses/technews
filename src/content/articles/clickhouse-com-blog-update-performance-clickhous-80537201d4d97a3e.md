contentHtml: "<article><div><blockquote>\n<p><strong>TL;DR</strong><br><br>· On identical hardware and data, ClickHouse is <strong>up to 4,000× faster</strong> on bulk UPDATEs, reaches <strong>parity on single-row updates</strong>, and stays <strong>competitive on cached point updates</strong>. <br><br>· Why it matters: Bulk updates are common in OLTP workloads, and ClickHouse’s columnar design + parallelism make them far faster. <br><br>· Caveat: PostgreSQL is fully transactional by default; ClickHouse isn’t. Results reflect native execution models, not identical guarantees.</p>\n</blockquote>\n<p>PostgreSQL is the most popular open-source <a target=\"_blank\" href=\"https://clickhouse.com/resources/engineering/oltp-vs-olap\">OLTP database</a> in the world.</p>\n<p>It’s a fair assumption that, when a developer thinks about UPDATE performance, they probably think of the baseline that PostgreSQL sets.</p>\n<p>In contrast, ClickHouse is the most popular open-source OLAP database in the world.</p>\n<p>While ClickHouse sets the expectation of OLAP performance, its OLTP potential is often underrated.</p>\n<p>In July 2025, <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-2-sql-style-updates\">ClickHouse v25.7 brought high-performance SQL-standard UPDATEs to ClickHouse</a>.</p>\n<p>Naturally, we want to know how ClickHouse stacks up against the best. <strong>Are UPDATEs in ClickHouse competitive with UPDATEs in Postgres?</strong></p>\n<p>In this post we first look at cold runs, the stress-test scenario where no data is cached, and then complement them with hot runs, which better reflect everyday workloads where indexes and cache hit rates are high.</p>\n<h2 id=\"comparing-postgresql-and-clickhouse-isn-t-apples-to-apples\"></h2>\n<p>In our previous post, <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-3-benchmarks\">we benchmarked the new high-performance SQL-standard UPDATEs against other ClickHouse update methods</a>. Here, out of curiosity, we’re running the same benchmarks against PostgreSQL on identical hardware and data.</p>\n<p>We focus on two OLTP staples: single-row updates and bulk changes on a classic orders dataset. These tests reveal how much update speed depends on finding rows efficiently, a strength ClickHouse inherits from its analytical roots.</p>\n<p>Before diving into the numbers, we want to acknowledge something: a PostgreSQL vs. ClickHouse comparison isn’t apples-to-apples.</p>\n<p>Both can run UPDATEs, but their execution models differ in ways that matter when interpreting results.</p>\n<blockquote>\n<p><strong>TL;DR:</strong> PostgreSQL wraps every statement in a fully transactional context and flushes WAL at commit by default; ClickHouse doesn’t. That means these results aren’t a perfect measure of transaction or durability performance. However, they’re still an interesting and relevant look at how each system handles update workloads under its native execution model.</p>\n</blockquote>\n<p>PostgreSQL and ClickHouse may both run UPDATE statements, but they don’t do it the same way. They share a similar approach to isolation, both use <strong>Multi-Version Concurrency Control (MVCC)</strong>, but differ in how they handle transactions, commit semantics, and durability guarantees.</p>\n<p>This difference matters when interpreting benchmark results.</p>\n<h3 id=\"multi-version-concurrency-control-mvcc\"></h3>\n<p>Both PostgreSQL and ClickHouse use <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Multiversion_concurrency_control\">MVCC</a> to let readers and writers work in parallel without blocking each other. Every query sees a <strong>consistent snapshot</strong> of the data as it existed when it started, which means:</p>\n<ul>\n<li>\n<p>Readers never see partial changes from concurrent updates.</p>\n</li>\n<li>\n<p>Readers and writers don’t block each other.</p>\n</li>\n<li>\n<p>Data is never overwritten in place; new versions are created, and old ones are kept until no query needs them.</p>\n</li>\n</ul>\n<p>How this looks in practice:</p>\n<p><strong>PostgreSQL</strong></p>\n<ol>\n<li>\n<p>Creates a <strong>new row version</strong> with the updated data.</p>\n</li>\n<li>\n<p>Keeps the old version until all readers of the old one finish.</p>\n</li>\n<li>\n<p>Removes old versions later via <strong><a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/sql-vacuum.html\">VACUUM</a></strong>.</p>\n</li>\n</ol>\n<p><strong>ClickHouse</strong></p>\n<ol>\n<li>\n<p>Creates a <strong>new <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">data part</a> (<a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-2-sql-style-updates#how-patch-parts-work\">patch</a>)</strong> with updated values.</p>\n</li>\n<li>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-25-06#single-snapshot-for-select\">Keeps old data parts until all readers of the old one finish</a>.</p>\n</li>\n<li>\n<p>Merges updates into the source data part during a <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges\">background merge</a> and discards old versions.</p>\n<blockquote>\n<p>On isolation alone, PostgreSQL and ClickHouse behave very similarly; both ensure readers always see a consistent snapshot while updates are in flight.</p>\n</blockquote>\n</li>\n</ol>\n<h3 id=\"transactions-commit-and-rollback\"></h3>\n<p>Here’s where the paths diverge:</p>\n<p><strong>PostgreSQL</strong></p>\n<ul>\n<li>\n<p>Runs <em>every</em> statement, even a single UPDATE, inside a <strong><a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/tutorial-transactions.html\">transaction context</a></strong>.</p>\n</li>\n<li>\n<p>If you don’t start one, it still wraps the statement in an <strong>implicit transaction</strong> (BEGIN → execute → COMMIT).</p>\n</li>\n<li>\n<p>Writes all changes to the <strong>Write-Ahead Log (<a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/wal-intro.html\">WAL</a>)</strong> before touching the table for durability and crash recovery.</p>\n</li>\n<li>\n<p><strong>COMMIT</strong> makes changes visible; <strong>ROLLBACK</strong> discards them before commit, marking old row versions invalid for later cleanup.</p>\n</li>\n</ul>\n<p><strong>ClickHouse</strong></p>\n<ul>\n<li>\n<p>Single inserts and updates on a MergeTree table <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/developer/transactional#case-1-insert-into-one-partition-of-one-table-of-the-mergetree-family\">are</a> <strong>atomic, consistent, isolated, and durable</strong>, applied as a whole, if they are packed and inserted as a single block.</p>\n</li>\n<li>\n<p>By default, it doesn’t wrap every statement in a transaction.</p>\n</li>\n<li>\n<p>Supports <strong>experimental</strong> <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/developer/transactional#transactions-commit-and-rollback\">multi-statement transactions</a> with explicit BEGIN, COMMIT, and ROLLBACK (not yet in ClickHouse Cloud).</p>\n</li>\n</ul>\n<blockquote>\n<p>PostgreSQL is fully transactional by default, adding <strong>per-update-statement overhead</strong>. ClickHouse avoids extra bookkeeping unless you explicitly start a transaction (experimental feature, not yet in ClickHouse Cloud).</p>\n</blockquote>\n<h3 id=\"durability-and-flush-policy\"></h3>\n<p>Here’s where the systems differ again, this time in how they guarantee durability and handle flushes to disk.</p>\n<p>PostgreSQL:</p>\n<ul>\n<li>\n<p><code>fsync</code> = <code>on</code>, <code>synchronous_commit</code> = <code>on</code> by default → WAL is flushed to disk at every commit.</p>\n</li>\n<li>\n<p>Adds latency but guarantees durability even if the OS crashes.</p>\n</li>\n</ul>\n<p>ClickHouse:</p>\n<ul>\n<li>\n<p><code>fsync_after_insert</code> = <code>false</code> by default → relies on OS page cache, parts are atomic but not immediately flushed.</p>\n</li>\n<li>\n<p>Faster inserts/updates, weaker immediate durability; you can enable <code>fsync_after_insert = 1</code> for stronger guarantees.</p>\n</li>\n</ul>\n<blockquote>\n<p>Implication for benchmarks: Results reflect the default durability/flush settings. You can shift absolute times by changing these knobs, but the relative patterns (row vs. column update costs) dominate.</p>\n</blockquote>\n<p>With the key execution model differences in mind, let’s look at how we put both systems to the test.</p>\n<h2 id=\"dataset-and-benchmark-setup\"></h2>\n<p>In our <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-3-benchmarks\">previous blog</a> on fast updates in ClickHouse, we walked through the dataset, schema, and setup in detail.
