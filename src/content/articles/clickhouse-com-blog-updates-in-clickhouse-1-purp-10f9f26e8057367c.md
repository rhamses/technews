Rather than force slow UPDATE operations into a system designed for big reads, we took a different path:</p>\n<blockquote>\n<p><strong>We sidestepped the update problem by treating updates as inserts.</strong></p>\n</blockquote>\n<p>This isn’t a workaround; it’s a deliberate design choice. Engines such as <strong>ReplacingMergeTree</strong>, <strong>CoalescingMergeTree</strong>, and <strong>CollapsingMergeTree</strong> let ClickHouse handle updates and deletes by writing new rows instead of modifying existing ones. They exploit ClickHouse’s high insert throughput and background merge process, avoiding the performance penalties of in-place updates.</p>\n<p>These engines <strong>still solve real problems at scale and are often the best fit for high-ingest, rapidly mutating workloads</strong>. They also inspired the next generation of update mechanics, so understanding how they work helps explain how ClickHouse makes SQL-style updates fast, too.</p>\n<p><strong>What this series covers</strong></p>\n<ul>\n<li>\n<p><strong>In this post (Part 1)</strong>, we’ll explore how purpose-built engines work, and why they’re still so effective.</p>\n</li>\n<li>\n<p><strong>In <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-2-sql-style-updates\">Part 2</a></strong>, we’ll turn to declarative, standard SQL-style UPDATE, powered by a new mechanism called <strong>patch parts</strong>.</p>\n</li>\n<li>\n<p><strong>And in <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-3-benchmarks\">Part 3</a></strong>,  we’ll benchmark all approaches to see how they stack up.</p>\n</li>\n</ul>\n<p>To understand how ClickHouse makes updates fast, it helps to start with why updates are hard in column stores to begin with.</p>\n<h2 id=\"why-updates-are-hard-in-column-stores\"></h2>\n<p>In database systems, updates and analytics pull in opposite directions; what’s fast for one tends to be slow for the other.</p>\n<p><strong>In row stores</strong> (like PostgreSQL or MySQL):</p>\n<ul>\n<li>\n<p>Each row is stored contiguously on disk.</p>\n</li>\n<li>\n<p>This makes <strong>updates easy</strong>, you can overwrite a row in place.</p>\n</li>\n<li>\n<p>But <strong>analytical queries suffer</strong>: even if you need just two columns, the entire row must be <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Page_(computer_memory)\">loaded</a> into memory.</p>\n</li>\n</ul>\n<p><strong>In column stores</strong> (like ClickHouse):</p>\n<ul>\n<li>\n<p>Each column is stored in a separate file.</p>\n</li>\n<li>\n<p>This makes <strong>analytics blazing fast</strong>, only the columns you query are read.</p>\n</li>\n<li>\n<p>But <strong>updates are harder</strong> because each column is stored separately, modifying a row means touching multiple files and rewriting fragments.</p>\n</li>\n</ul>\n<p>This tradeoff has long made efficient row-level updates a challenge for columnar systems.</p>\n<p>Let’s look at the first ClickHouse solution: purpose-built engines that tackle updates differently, by avoiding them entirely.</p>\n<h2 id=\"inserts-are-so-fast-we-turned-updates-into-inserts\"></h2>\n<p>The core idea is simple: ClickHouse is especially optimized for insert workloads. <strong>Because there are no global structures to lock or update</strong> (e.g., a global B++ index), <a target=\"_blank\" href=\"https://clickhouse.com/docs/concepts/why-clickhouse-is-so-fast#storage-layer-concurrent-inserts-are-isolated-from-each-other\">inserts are fully isolated</a>, run in parallel without interfering with each other, and hit disk at full speed (in one production setup, over <a target=\"_blank\" href=\"https://clickhouse.com/blog/how-tesla-built-quadrillion-scale-observability-platform-on-clickhouse#proving-the-system-at-scale\">1 billion rows per second</a>). This also means <strong>insert performance stays constant, no matter how large the table grows</strong>. Additionally, inserts stay <strong>lightweight</strong>: all the extra work, like resolving record updates, is <strong>decoupled</strong> and <a target=\"_blank\" href=\"https://clickhouse.com/docs/concepts/why-clickhouse-is-so-fast#storage-layer-merge-time-computation\">deferred to background merges</a>.</p>\n<blockquote>\n<p><strong>The trick:</strong> because inserts are so fast and efficient, ClickHouse can treat updates (and even deletes) as just more inserts.</p>\n</blockquote>\n<p>In high-throughput scenarios like IoT, the classic SQL-style UPDATE can be inefficient: even in a typical RDBMS, an UPDATE requires locating the row with the previous state, rewriting it, and often locking or rewriting more data than necessary.</p>\n<p>With purpose-built engines like <code>ReplacingMergeTree</code>, <code>CoalescingMergeTree</code>, and <code>CollapsingMergeTree</code>, ClickHouse uses a more efficient inserts-only model that skips locating the row with the previous state entirely. <strong>Even updates and deletes are expressed as fast, lightweight inserts</strong>, while the actual data modifications happen later via background merges.</p>\n<blockquote>\n<p><strong>Why this works so well</strong>: ClickHouse is already continuously <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges\">merging</a> smaller <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">data parts</a> into larger ones in the background; it’s right there in the name, <em>MergeTree</em>. These merges load the relevant data into memory, consolidate it, and write out a new part. Since the engine is already doing this work, handling updates or deletes during a merge adds minimal overhead. Keeping only the latest version of a row or removing a canceled one is practically free.</p>\n</blockquote>\n<p>This lightweight, <em>insert-and-merge</em> flow is only possible because of how ClickHouse organizes data on disk: into sorted and immutable data parts that are constantly merged in the background.</p>\n<h2 id=\"understanding-parts-and-merges\"></h2>\n<p>To understand how ClickHouse makes updates fast, and to follow the diagrams and mechanics in this (and the next) post, it helps to know what everything is built on: <strong>parts</strong>.</p>\n<h3 id=\"inserts-create-sorted-and-immutable-parts\"></h3>\n<p>Every time you insert data into a ClickHouse table, it’s written as a self-contained, <strong>immutable</strong> <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">data part</a> on disk.</p>\n<p>Each part contains rows (stored by column) and is named to reflect where it fits in the insert and merge history. For example, after this insert into an initially empty <code>orders</code> table with columns <code>order_id</code>, <code>item_id</code>, <code>quantity</code>, <code>price</code>, and <code>discount</code>:</p>\n<div><pre><code><span><span>INSERT INTO</span> orders <span>VALUES</span></span>\n<span>    (<span>1001</span>, <span>'kbd'</span>,   <span>10</span>, <span>45.00</span>, <span>0.00</span>),</span>\n<span>    (<span>1001</span>, <span>'mouse'</span>,  <span>6</span>, <span>25.00</span>, <span>0.00</span>);</span></code></pre></div>\n<!-- -->\n<p>ClickHouse creates a new part named <code>all_1_1_0</code>:</p>\n<p><span><img alt=\"Blog-updates Part 1.001.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_updates_Part_1_001_89d48bf1d2.png&w=2048&q=75\"></span></p>\n<p>Inside the part, <strong>rows are physically sorted on disk by the table’s sorting key</strong>, in this case, <code>(order_id, item_id)</code>. That’s true for every part in a MergeTree table and is critical for how ClickHouse can merge parts efficiently without random I/O or re-sorting.</p>\n<h3 id=\"how-to-read-a-part-name\"></h3>\n<p>Each part name follows the format <code>partition_minBlock_maxBlock_mergeLevel</code>. In this case:</p>\n<ul>\n<li>\n<p>all – <a target=\"_blank\" href=\"https://clickhouse.com/docs/partitions\">partition</a> ID (default in this case)</p>\n</li>\n<li>\n<p>1 – <strong>minimum block number</strong> in the part (explained below)</p>\n</li>\n<li>\n<p>1 – <strong>maximum block number</strong> in the part (also explained below)</p>\n</li>\n<li>\n<p>0 – <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges#what-are-part-merges-in-clickhouse\">merge level</a> (0 = initial insert, higher = merged)</p>\n</li>\n</ul>\n<h3 id=\"what-s-inside-a-part\"></h3>\n<p>Under the hood, this part is a folder on disk named <code>all_1_1_0</code>. It contains one file per column in the table: <code>order_id</code>, <code>item_id</code>, <code>quantity</code>, <code>price</code>, and <code>discount</code>. Each of these files is compressed and stores the column’s values for the rows in that part.</p>\n<p><em>We’ve sketched these column files in the diagram above to show how the data is laid out inside the part.</em></p>\n<h3 id=\"how-blocks-make-up-a-part\"></h3>\n<p>ClickHouse inserts data in <strong>blocks of rows</strong>, and each block is assigned a <strong>monotonically increasing block number</strong>. A part contains one or more of these blocks, either from a single insert or from merging multiple parts. The <code>minBlock</code> and <code>maxBlock</code> in the part name reflect the range of blocks in that part.</p>\n<h3 id=\"merges-happen-in-the-background\"></h3>\n<p>As new inserts arrive, ClickHouse doesn’t modify existing parts, it simply writes more. In the background, it <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges\">merges</a> them into larger parts to control part counts and consolidate data.</p>\n<h3 id=\"merges-are-fast-thanks-to-sorted-parts\"></h3>\n<p>ClickHouse can merge parts with remarkable efficiency because <strong>all parts are already sorted by the same columns</strong>. When two parts are merged, the engine simply interleaves their data in a single linear scan of both parts, <strong>no re-sorting, no random access, no temporary buffers</strong> are required.</p>\n<blockquote>\n<p>This is known as a <strong>single merge pass</strong>: ClickHouse reads both parts in order, compares rows on the fly, and writes out a new, merged part. It’s one of the core reasons merges are so fast and lightweight.</p>\n</blockquote>\n<p>That efficiency makes it possible to handle updates and deletes during merges with minimal overhead, they just become part of the same scan-and-write process.</p>\n<p>Now that we understand the foundation, let’s see it in action, starting with the most straightforward engine: ReplacingMergeTree.</p>\n<h2 id=\"replacingmergetree-replace-rows-by-inserting-new-ones\"></h2>\n<p>To demonstrate <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/mergetree-family/replacingmergetree\">ReplacingMergeTree</a>, we’ll use a simple orders table from a hardware store scenario:</p>\n<div><pre><code><span><span>CREATE TABLE</span> orders (</span>\n<span>    order_id   Int32,</span>\n<span>    item_id    String,</span>\n<span>    quantity   UInt32,</span>\n<span>    price      <span>Decimal</span>(<span>10</span>,<span>2</span>),</span>\n<span>    discount   <span>Decimal</span>(<span>5</span>,<span>2</span>)</span>\n<span>)</span>\n<span>ENGINE <span>=</span> ReplacingMergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (order_id, item_id);</span></code></pre></div>\n<!-- -->\n<p>To update a row, simply insert a new version with the same sorting key <code>(order_id, item_id)</code>. During background merges, ClickHouse will retain the most recent version (the one inserted last).\nFor example, imagine a customer ① initially ordered 10 keyboards and 6 mice at full price:</p>\n<div><pre><code><span><span>INSERT INTO</span> orders <span>VALUES</span></span>\n<span>    (<span>1001</span>, <span>'kbd'</span>,   <span>10</span>, <span>45.00</span>, <span>0.00</span>),</span>\n<span>    (<span>1001</span>, <span>'mouse'</span>,  <span>6</span>, <span>25.00</span>, <span>0.00</span>);</span></code></pre></div>\n<!-- -->\n<p>Later, they increased their mice order to 60 units, qualifying for a 20% bulk discount. Instead of modifying the old row, we ② insert a new one with the updated quantity and discount:</p>\n<div><pre><code><span><span>INSERT INTO</span> orders <span>VALUES</span></span>\n<span>    (<span>1001</span>, <span>'mouse'</span>, <span>60</span>, <span>25.00</span>, <span>0.20</span>);</span></code></pre></div>\n<!-- -->\n<p>The diagram below shows the <a target=\"_blank\" href=\"https://clickhouse.com/docs/parts\">data parts</a> created by the initial insert (①) and the update insert (②). During the next <a target=\"_blank\" href=\"https://clickhouse.com/docs/merges\">background merge</a> ③, ClickHouse automatically keeps the latest version and discards the outdated one:</p>\n<p><span><img alt=\"Blog-updates Part 1.002.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_updates_Part_1_002_47c8be6dff.png&w=2048&q=75\"></span></p>\n<p>After the merge, <strong>parts ① and ② are discarded</strong>, and part ③ becomes the <strong>active data part</strong> for the table.</p>\n<p>What if you only want to change a few columns? That’s where CoalescingMergeTree comes in.</p>\n<h2 id=\"coalescingmergetree-consolidate-partial-updates-automatically\"></h2>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/mergetree-family/coalescingmergetree\">CoalescingMergeTree</a> works just like ReplacingMergeTree, but with one key difference: it supports <strong>partial updates</strong>. Instead of providing the full row, you can insert only the changed columns.</p>\n<p>We are using the same orders table:</p>\n<div><pre><code><span><span>CREATE TABLE</span> orders (</span>\n<span>    order_id   Int32,</span>\n<span>    item_id    String,</span>\n<span>    quantity   Nullable(UInt32),</span>\n<span>    price      Nullable(<span>Decimal</span>(<span>10</span>,<span>2</span>)),</span>\n<span>    discount   Nullable(<span>Decimal</span>(<span>5</span>,<span>2</span>))</span>\n<span>)</span>\n<span>ENGINE <span>=</span> CoalescingMergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (order_id, item_id);</span></code></pre></div>\n<!-- -->\n<p><em>Note: The non-key columns are marked as Nullable so we can skip them during partial updates. This lets us insert only the fields that have changed, and leave the rest as NULL.</em></p>\n<p>Again, a customer ① initially ordered 10 keyboards and 6 mice at full price:</p>\n<div><pre><code><span><span>INSERT INTO</span> orders <span>VALUES</span></span>\n<span>    (<span>1001</span>, <span>'kbd'</span>,   <span>0</span>, <span>45.00</span>, <span>0.00</span>),</span>\n<span>    (<span>1001</span>, <span>'mouse'</span>, <span>6</span>, <span>25.00</span>, <span>0.00</span>);</span></code></pre></div>\n<!-- -->\n<p>② We insert a new row with partial updates (quantity and discount):</p>\n<div><pre><code><span><span>INSERT INTO</span> orders <span>VALUES</span></span>\n<span>    (<span>1001</span>, <span>'mouse'</span>, <span>60</span>, <span>NULL</span>, <span>0.20</span>);</span></code></pre></div>\n<!-- -->\n<p>A background merge of ① the initial insert and ② the update insert produces ③ a new active data part where <strong>ClickHouse keeps the latest non-null value for each column</strong>, consolidating sparse updates into a complete row. After the merge, parts ① and ② are discarded, just like in ReplacingMergeTree:</p>\n<p><span><img alt=\"Blog-updates Part 1.003.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_updates_Part_1_003_28e32ad9b9.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p>Learn about typical use cases and <strong><a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-25-6-coalescingmergetree\">what’s happening under the hood in CoalescingMergeTree</a></strong>.</p>\n</blockquote>\n<p>And what about deletes? CollapsingMergeTree handles them with a clever twist.</p>\n<h2 id=\"collapsingmergetree-delete-a-row-by-inserting-a-row\"></h2>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/mergetree-family/collapsingmergetree\">CollapsingMergeTree</a> lets you delete data without ever issuing a DELETE. Instead, you insert a special “cancelling” row that marks the original as invalid.</p>\n<p>Here’s the same simple orders table again, this time with an additional <code>is_valid</code> column used as the engine’s <a target=\"_blank\" href=\"https://clickhouse.com/docs/engines/table-engines/mergetree-family/collapsingmergetree#parameters\">sign parameter</a>:</p>\n<div><pre><code><span><span>CREATE TABLE</span> orders (</span>\n<span>    order_id   Int32,</span>\n<span>    item_id    String,</span>\n<span>    quantity   UInt32,</span>\n<span>    price      <span>Decimal</span>(<span>10</span>,<span>2</span>),</span>\n<span>    discount   <span>Decimal</span>(<span>5</span>,<span>2</span>),</span>\n<span>    is_valid   UInt8 <span>-- only required for CollapsingMergeTree</span></span>\n<span>)</span>\n<span>ENGINE <span>=</span> CollapsingMergeTree(is_valid)</span>\n<span><span>ORDER</span> <span>BY</span> (order_id, item_id);</span></code></pre></div>\n<!-- -->\n<p>① The initial order:</p>\n<div><pre><code><span><span>INSERT INTO</span> orders <span>VALUES</span></span>\n<span>    (<span>1001</span>, <span>'kbd'</span>,  <span>10</span>, <span>45.00</span>, <span>0.00</span>, <span>1</span>),</span>\n<span>    (<span>1001</span>, <span>'mouse'</span>, <span>6</span>, <span>25.00</span>, <span>0.00</span>, <span>1</span>);</span></code></pre></div>\n<!-- -->\n<p>② We remove an item by inserting a matching row (only the sorting key columns matter, rest can be NULL) with <code>is_valid</code> = <code>-1</code>:</p>\n<div><pre><code><span><span>INSERT INTO</span> orders <span>VALUES</span></span>\n<span>    (<span>1001</span>, <span>'mouse'</span>, <span>NULL</span>, <span>NULL</span>, <span>NULL</span>, <span>-1</span>);</span></code></pre></div>\n<!-- -->\n<p>During the ③ next merge, ClickHouse finds both the <code>+1</code> and <code>-1</code> rows for the same sorting key <code>(order_id, item_id)</code> and collapses them, removing both rows and discarding parts ① and ② in the process:</p>\n<p><span><img alt=\"Blog-updates Part 1.004.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FBlog_updates_Part_1_004_e809409678.png&w=2048&q=75\"></span></p>\n<blockquote>\n<p>This same mechanism also supports <strong>updates</strong>: to update a row, you insert a cancelling row followed by a new one with the updated values. During the next background merge, ClickHouse collapses the old and cancelling rows and retains only the new version.\n<br><br>\n<strong>This even allows you to update sorting key values</strong>, a unique capability of CollapsingMergeTree that’s not possible with ReplacingMergeTree or CoalescingMergeTree.</p>\n</blockquote>\n<p>And it’s not just upades and deletes, all three engines also support UPSERTs.</p>\n<h2 id=\"bonus-built-in-upsert-behavior\"></h2>\n<p>All three engines, ReplacingMergeTree, CoalescingMergeTree, and CollapsingMergeTree, support what is effectively an <strong>UPSERT</strong> (insert-or-update) operation: insert a new row, and if a match exists (by sorting key), the engine will apply the right logic to update.</p>\n<p>This kind of insert-or-update pattern is a powerful capability, something standard UPDATE doesn’t support directly.</p>\n<p>SQL does define a <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Merge_(SQL)\">MERGE</a> command for this, but it’s verbose and less efficient in practice. In ClickHouse, it’s just a fast insert.</p>\n<p>This insert-based model gives us efficient updates, deletes, and upserts. But what if you need the query side to catch up before merges do?</p>\n<h2 id=\"getting-up-to-date-results-with-final\"></h2>\n<p>All three engines described above use merges to consolidate data in the background. That makes insert-based updates and deletes highly efficient, but also eventually consistent: <strong>merges may lag behind</strong> when ingest is heavy (i.e., merges run continuously, but inserts may outpace them, think of it as a lagging consolidation window).</p>\n<p>To ensure query accuracy despite this, ClickHouse lets you <strong>apply the table engine’s merge logic on the fly</strong> using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/select/from#final-modifier\">FINAL</a> modifier:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> orders <span>FINAL</span>;</span></code></pre></div>\n<!-- -->\n<p>This doesn’t trigger a real merge on disk; instead, it performs an in-memory consolidation of all relevant data parts as they existed when the query began, returning fully merged rows.</p>\n<p>It works consistently across all three engines:</p>\n<ul>\n<li>With ReplacingMergeTree, it keeps the latest version of each row.</li>\n<li>With CoalescingMergeTree, it coalesces sparse updates into full rows.</li>\n<li>With CollapsingMergeTree, it applies the cancelation logic to collapse deletes and provide updates.</li>\n</ul>\n<p>FINAL gives you predictable, up-to-date results when you need them, while preserving the raw speed of insert-based processing.</p>\n<blockquote>\n<p><strong>No need to fear FINAL</strong><br>\nClickHouse <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-23-12#optimizations-for-final\">optimizes</a> FINAL with intelligent in-memory algorithms, selective part processing (skipping unnecessary merges), and vectorized execution, making on-the-fly consolidation fast, even on large datasets. ClickHouse avoids merging part ranges that don’t contain conflicting rows, skipping unnecessary work. Columns <a target=\"_blank\" href=\"https://clickhouse.com/blog/clickhouse-release-24-01#vertical-algorithm-for-final-with-replacingmergetree\">are</a> processed independently and in parallel, reducing memory usage and boosting performance, especially on wide tables.</p>\n</blockquote>\n<p>So you get the right answer. But is it really an UPDATE? Let’s take a step back.</p>\n<h2 id=\"how-different-is-this-from-a-real-update\"></h2>\n<p>If you zoom out, you’ll notice something familiar. ClickHouse updates follow the same rhythm as a traditional row-store: <strong>write a new version</strong>, then <strong>read the new version</strong>:</p>\n<div><table><thead><tr><th><strong>Traditional row store</strong></th><th><strong>ClickHouse</strong></th></tr></thead><tbody><tr><td>Overwrites the old row in place</td><td>Appends a new version next to the old one</td></tr><tr><td>Queries read the new version immediately</td><td>Queries read the new version immediately</td></tr><tr><td>Old version is gone once the write commits</td><td>Old version is removed later during background merges</td></tr></tbody></table></div>\n<p>So while the mechanics are different, especially in how cleanup is deferred, the update semantics are strikingly similar.</p>\n<p>However: to get that familiar result, you have to think like a ClickHouse engineer. That means understanding background merges, knowing when to use FINAL, and choosing the right engine. You also have to model each update as a new row insert, and often shape your schema around engine-specific behaviors. For example, ReplacingMergeTree only lets you update rows by their sorting key, and if that key changes, you’ll need to recreate the table.</p>\n<p>That’s not how users coming from traditional SQL databases expect updates to work.</p>\n<h2 id=\"from-engine-semantics-to-sql-simplicity\"></h2>\n<p>These purpose-built engines are incredibly efficient, but they come with tradeoffs. They offer speed and flexibility, but not the simplicity of standard SQL.
