href=\"https://clickhouse.com/blog/updates-in-clickhouse-1-purpose-built-engines\">1</a> and <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-2-sql-style-updates\">2</a> comparing these methods side by side to reveal why the benchmark charts look the way they do, and what’s really happening inside ClickHouse.</p>\n<h3 id=\"why-lightweight-updates-feel-like-inserts\"></h3>\n<blockquote>\n<p>Despite the name, these are ordinary <a target=\"_blank\" href=\"https://www.w3schools.com/sql/sql_update.asp\">SQL UPDATE statements</a>, ClickHouse just optimizes them by writing patch parts instead of rewriting full columns.</p>\n</blockquote>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-2-sql-style-updates#how-patch-parts-work\">Lightweight updates write tiny patch parts</a> instead of rewriting full columns.</p>\n<p><a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-2-sql-style-updates#how-patch-on-read-work\">Queries simply overlay these patches in memory (patch‑on‑read)</a>, so applying a small change feels almost as fast as inserting new rows.</p>\n<p>Specifically, a lightweight update writes a patch part that only contains:</p>\n<ul>\n<li>The <strong>updated values</strong></li>\n<li>A tiny bit of <strong><a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-2-sql-style-updates#patch-parts-at-scale-tracking-targeting-merging\">targeting metadata</a></strong>: _part, _part_offset, _block_number, _block_offset, and _data_version</li>\n</ul>\n<p>This metadata points <strong>exactly</strong> to the rows that need updating, so ClickHouse avoids scanning or rewriting any unrelated data.</p>\n<p>Update performance is roughly comparable to an <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/insert-into#inserting-the-results-of-select\">INSERT INTO … SELECT</a> that writes only the changed values plus their row’s metadata:</p>\n<div><pre><code><span><span>-- Lightweight update statement:</span></span>\n<span></span>\n<span><span>UPDATE</span> lineitem</span>\n<span><span>SET</span> l_discount <span>=</span> <span>0.045</span>, l_tax <span>=</span> <span>0.11</span>, ...</span>\n<span><span>WHERE</span> l_commitdate <span>=</span> <span>'1996-02-01'</span> <span>AND</span> l_quantity <span>=</span> <span>1</span>;</span></code></pre></div>\n<!-- -->\n<p>≈</p>\n<div><pre><code><span><span>-- Roughly equivalent:</span></span>\n<span></span>\n<span><span>INSERT INTO</span> patch</span>\n<span><span>SELECT</span> <span>0.045</span> <span>as</span> l_discount, <span>0.11</span> <span>as</span> l_tax, ...,</span>\n<span>       _part, _part_offset, _block_number, _block_offset </span>\n<span><span>FROM</span> lineitem</span>\n<span><span>WHERE</span> l_commitdate <span>=</span> <span>'1996-02-01'</span> <span>AND</span> l_quantity <span>=</span> <span>1</span>;</span></code></pre></div>\n<!-- -->\n<p>This is why lightweight updates feel as fast as small inserts, they avoid scanning or rewriting unrelated data.</p>\n<blockquote>\n<p>Because their mechanics are intentionally based on ClickHouse’s fast and efficient insert mechanics, <strong>you can make lightweight updates as frequently as you can do inserts</strong>.</p>\n</blockquote>\n<h3 id=\"when-to-use-lightweight-updates-and-when-not-to\"></h3>\n<blockquote>\n<p><strong>Lightweight updates are designed for frequent, small changes (≈ ≤ 10% of a table)</strong>.<br>Use them when you want updates to appear almost instantly with almost no <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-3-benchmarks#worst-case-post-update-query-time--bulk-updates\">worst-case post-update</a> query slow-down.</p>\n</blockquote>\n<p>Lightweight updates shine for <strong>small, frequent corrections</strong>, like updating a few percent of a table at a time.</p>\n<p>Large updates, however, create <strong>big patch parts</strong> which:</p>\n<ul>\n<li>\n<p>Must be <strong>applied in memory on every query</strong> (<a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-2-sql-style-updates#how-patch-on-read-works\">patch‑on‑read</a>) until they merge,</p>\n</li>\n<li>\n<p>add <strong>CPU and RAM overhead</strong> before materialization, and</p>\n</li>\n<li>\n<p>will <strong>merge into the source part eventually</strong>.</p>\n</li>\n</ul>\n<p>For <strong>large changes</strong>, this means queries can become much slower until the patches are materialized with the next regular background merge.\nIt is often <strong>better to run a <a target=\"_blank\" href=\"https://clickhouse.com/blog/updates-in-clickhouse-2-sql-style-updates#stage-1-classic-mutations-and-column-rewrites\">classic mutation</a></strong>, wait longer <strong>once</strong> (for the update to rewrite the part),\nand then enjoy <strong>baseline query performance</strong>  afterward.</p>\n<blockquote>\n<p>Think of lightweight updates as <strong>sticky notes</strong>, perfect for quick, precise edits.\n<strong>But if you’re re-papering the whole wall, new wallpaper (a mutation) is faster and cleaner.</strong></p>\n</blockquote>\n<p>We use two schematic charts to visualize the trade-off.</p>\n<h4 id=\"chart-1-update-latency\"></h4>\n<p>Chart 1 shows how update latency changes as the percentage of modified rows grows.</p>\n<p><span><img alt=\"Blog-updates Part 3.007.png\"
