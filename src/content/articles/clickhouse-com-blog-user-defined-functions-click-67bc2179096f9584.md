These functions can then be used like any in-built function in a query.</p>\n<p>To create our UDF, we use the <code>CREATE FUNCTION &lt;name&gt;</code> syntax and specify our method signature as a lambda expression. In it its simplest form, this might look like the following, which returns the string <code>odd</code> or <code>even</code> depending on the parity of the number:</p>\n<pre><p>\nCREATE FUNCTION parity_str AS (n) -&gt; if(n % 2, 'odd', 'even');\nSELECT\n    number,\n    parity_str(number)\nFROM numbers(5)\n<span>\n┌─number─┬─if(modulo(number, 2), 'odd', 'even')─┐\n│      0 │ even                                 │\n│      1 │ odd                                  │\n│      2 │ even                                 │\n│      3 │ odd                                  │\n│      4 │ even                                 │\n└────────┴──────────────────────────────────────┘\n</span></p> <a target=\"_blank\" href=\"https://sql.clickhouse.com/?query_id=3ZBX6XXPDY7TNOP7QOWHAB\">✎</a>\n</pre>\n<p>This is deliberately simple. As we’ll demonstrate, these can get considerably more complex.</p>\n<h2 id=\"the-problem\"></h2>\n<p>Our <code>git-import</code> generates data for several tables from the git commit history of a repository. One of these, <code>file_changes</code>, contains a row for every file changed in a commit. A commit that modifies more than one file will therefore generate multiple rows, allowing us to construct the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/github/#history-of-a-single-file\">history of a file </a>with a simple SELECT statement. For example, below, we look at the recent commits to our ReplicatedMergeTree:</p>\n<pre><p>\nSELECT\n    time,\n    substring(commit_hash, 1, 11) AS commit,\n    change_type,\n    author,\n    lines_added AS added,\n    lines_deleted AS deleted\nFROM git.file_changes\nWHERE path = 'src/Storages/StorageReplicatedMergeTree.cpp'\nORDER BY time DESC\nLIMIT 5\n<span>\n┌────────────────time─┬─commit──────┬─change_type─┬─author─────────────┬─added─┬─deleted─┐\n│ 2022-10-30 16:30:51 │ c68ab231f91 │ Modify      │ Alexander Tokmakov │    13 │      10 │\n│ 2022-10-23 16:24:20 │ b40d9200d20 │ Modify      │ Anton Popov        │    28 │      30 │\n│ 2022-10-23 01:23:15 │ 56e5daba0c9 │ Modify      │ Anton Popov        │    28 │      44 │\n│ 2022-10-21 13:35:37 │ 851f556d65a │ Modify      │ Igor Nikonov       │     3 │       2 │\n│ 2022-10-21 13:02:52 │ 13d31eefbc3 │ Modify      │ Igor Nikonov       │     4 │       4 │\n└─────────────────────┴─────────────┴─────────────┴────────────────────┴───────┴─────────┘\n</span>\n5 rows in set. A rename is denoted by the <code>change_type</code> having the value <code>Rename</code>. This problem might typically be solved by recursive CTEs, which are not supported in ClickHouse.</p>\n<div><pre><code><span>path = 'src/Storages/StorageReplicatedMergeTree.cpp' OR old_path = 'src/Storages/StorageReplicatedMergeTree.cpp`</span></code></pre></div>\n<p>Ideally, we want to recurse through the complete rename hierarchy and collect the full list of files. We could then simply modify our restriction to be <code>path IN (set of filenames)</code>. For this we will use a UDF.</p>\n<p>Note: this problem could also be solved at data insertion time. We could modify the original <code>git-import</code> tool to add an authoritative file id on all commits, giving us a consistent field value across all commits. Humor us and assume we can’t do this :)</p>\n<h2 id=\"creating-the-udf\"></h2>\n<p>In our case, we need a recursive behavior where the function calls itself - each time passing the previous path name and finding the next rename event.</p>\n<p><span><img alt=\"udf.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fudf_d5b6bbf4ac.png&w=2048&q=75\"></span></p>\n<p>Unfortunately, recursion is not currently supported in ClickHouse UDFs. We can work around this limitation by specifying the function N times, where each function calls another. While this limits us to a rename depth of N, it should be sufficient for our use case. Below we create our first function to show the general structure:</p>\n<pre><p>\nCREATE FUNCTION file_path_history AS n -&gt; if(empty(n), [], arrayConcat([n], file_path_history_01((\n    SELECT if(empty(old_path), NULL, old_path)\n    FROM git.file_changes\n    WHERE (path = n) AND ((change_type = 'Rename') OR (change_type = 'Add'))\n    LIMIT 1\n))))\n</p>\n</pre>\n<p>Our function <code>file_path_history</code> accepts the file's name of interest as a parameter <code>n</code> - likely the current known path on the first call. This path is then concatenated to the current result using the arrayConcat function, in addition to the result of a UDF call to the next level via <code>file_path_history_01</code> (we haven’t defined this yet). To this function, we pass the previous filename via the query:</p>\n<pre><p>\nSELECT if(empty(old_path), Null, old_path) FROM git.file_changes WHERE path = n AND (change_type = 'Rename' OR change_type = 'Add') LIMIT 1\n))))\n</p>\n</pre>\n<p>The following function, <code>file_path_history_01</code>, is very similar, except it will receive the old path of the original file specified by the user. It, in turn, finds the previous path for this file, invoking <code>file_path_history_02</code>. This artificial recursion continues until either we reach the maximum depth (i.e., the file has been renamed more than five times) or no result is returned from a SELECT (effectively a Null).</p>\n<p><span><img alt=\"recursive_udf.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frecursive_udf_e4ea7d0146.png&w=2048&q=75\"></span></p>\n<p>Our complete function definitions look like this. Note our final function is different and provides a base case:</p>\n<pre><p>\nCREATE FUNCTION file_path_history AS (n) -&gt; if(empty(n),  [], arrayConcat([n], file_path_history_01((SELECT if(empty(old_path), Null, old_path) FROM git.file_changes WHERE path = n AND (change_type = 'Rename' OR change_type = 'Add') LIMIT 1))));\nCREATE FUNCTION file_path_history_01 AS (n) -&gt; if(isNull(n), [], arrayConcat([n], file_path_history_02((SELECT if(empty(old_path), Null, old_path) FROM git.file_changes WHERE path = n AND (change_type = 'Rename' OR change_type = 'Add') LIMIT 1))));\nCREATE FUNCTION file_path_history_02 AS (n) -&gt; if(isNull(n), [], arrayConcat([n], file_path_history_03((SELECT if(empty(old_path), Null, old_path) FROM git.file_changes WHERE path = n AND (change_type = 'Rename' OR change_type = 'Add') LIMIT 1))));\nCREATE FUNCTION file_path_history_03 AS (n) -&gt; if(isNull(n), [], arrayConcat([n], file_path_history_04((SELECT if(empty(old_path), Null, old_path) FROM git.file_changes WHERE path = n AND (change_type = 'Rename' OR change_type = 'Add') LIMIT 1))));\nCREATE FUNCTION file_path_history_04 AS (n) -&gt; if(isNull(n), [], arrayConcat([n], file_path_history_05((SELECT if(empty(old_path), Null, old_path) FROM git.file_changes WHERE path = n AND (change_type = 'Rename' OR change_type = 'Add') LIMIT 1))));\nCREATE FUNCTION file_path_history_05 AS (n) -&gt; if(isNull(n), [], [n]);\n</p>\n</pre>\n<h2 id=\"using-our-function\"></h2>\n<p>We can now use our function <code>file_path_history</code> like any other.
