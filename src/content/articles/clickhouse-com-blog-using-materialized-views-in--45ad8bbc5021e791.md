Processing is usually done on an application side using one<a target=\"_blank\" href=\"https://clickhouse.com/docs/en/interfaces/third-party/client-libraries/\"> of the available libraries</a> for ClickHouse. Still, there are some critical processing points that can be moved to ClickHouse to increase the performance and manageability of the data. One of the most powerful tools for that in ClickHouse is <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/view/#materialized-view\">Materialized Views</a>. In this blog post, we explore materialized views and how they can be used in ClickHouse for accelerating queries as well as data transformation, filtering and routing tasks.</p>\n<p>If you want to learn more about Materialized Views, we offer a free, on-demand training course <a target=\"_blank\" href=\"https://learn.clickhouse.com/visitor_catalog_class/show/1043451/\">here</a>.</p>\n<h2 id=\"what-is-a-materialized-view\"></h2>\n<p>A materialized view is a special trigger that stores the result of a <code>SELECT</code> query on data, as it is inserted, into a target table:</p>\n<p><span><img alt=\"materialized_view.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmaterialized_view_5a321dc56d.png&w=2048&q=75\"></span></p>\n<p>This can be useful in many cases, but let’s take the most popular - making certain queries work faster.</p>\n<h2 id=\"quick-example\"></h2>\n<p>Let’s take 1b rows from the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/getting-started/example-datasets/wikistat/\">Wikistat dataset</a> as an example:</p>\n<pre><p>\nCREATE TABLE wikistat\n(\n    `time` DateTime CODEC(Delta(4), ZSTD(1)),\n    `project` LowCardinality(String),\n    `subproject` LowCardinality(String),\n    `path` String,\n    `hits` UInt64\n)\nENGINE = MergeTree\nORDER BY (path, time);\nOk.\nINSERT INTO wikistat SELECT *\nFROM s3('https://ClickHouse-public-datasets.s3.amazonaws.com/wikistat/partitioned/wikistat*.native.zst') LIMIT 1e9\n</p>\n</pre>\n<p>Suppose we frequently query for the most popular projects for a certain date:</p>\n<pre><p>\nSELECT\n    project,\n    sum(hits) AS h\nFROM wikistat\nWHERE date(time) = '2015-05-01'\nGROUP BY project\nORDER BY h DESC\nLIMIT 10\n</p>\n</pre>\n<p>This query takes a <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> development service 15 seconds to complete:</p>\n<pre><p>\n┌─project─┬────────h─┐\n│ en      │ 34521803 │\n│ es      │  4491590 │\n│ de      │  4490097 │\n│ fr      │  3390573 │\n│ it      │  2015989 │\n│ ja      │  1379148 │\n│ pt      │  1259443 │\n│ tr      │  1254182 │\n│ zh      │   988780 │\n│ pl      │   985607 │\n└─────────┴──────────┘\n10 rows in set. Elapsed: 14.869 sec. Processed 972.80 million rows, 10.53 GB (65.43 million rows/s., 708.05 MB/s.)\n</p>\n</pre>\n<p>If we have plenty of those queries and we need subsecond performance from ClickHouse, we can create a materialized view for this query:</p>\n<pre><p>\nCREATE TABLE wikistat_top_projects\n(\n    `date` Date,\n    `project` LowCardinality(String),\n    `hits` UInt32\n)\nENGINE = SummingMergeTree\nORDER BY (date, project);\nOk.\nCREATE MATERIALIZED VIEW wikistat_top_projects_mv TO wikistat_top_projects AS\nSELECT\n    date(time) AS date,\n    project,\n    sum(hits) AS hits\nFROM wikistat\nGROUP BY\n    date,\n    project;\n</p>\n</pre>\n<p>In these two queries:</p>\n<ul>\n<li><code>wikistat_top_projects</code> is the name of the table that we’re going to use to save a materialized view,</li>\n<li><code>wikistat_top_projects_mv</code> is the name of the materialized view itself (the trigger),</li>\n<li>we’ve used <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/summingmergetree/\">SummingMergeTree</a> because we would like to have our hits value summarized for each date/project pair,</li>\n<li>everything that comes after <code>AS</code> is the query that the materialized view will be built from.</li>\n</ul>\n<p>We can create any number of materialized views, but each new materialized view is an additional storage load, so keep the overall number sensible i.e. aim for under 10 per table.</p>\n<p>Now let’s populate the materialized view’s target table with the data from <code>wikistat</code> table using the same query:</p>\n<pre><p>\nINSERT INTO wikistat_top_projects SELECT\n    date(time) AS date,\n    project,\n    sum(hits) AS hits\nFROM wikistat\nGROUP BY\n    date,\n    project\n</p>\n</pre>\n<h2 id=\"query-materialized-view-table\"></h2>\n<p>Since <code>wikistat_top_projects</code> is a table, we have all of the power of ClickHouse SQL to query it:</p>\n<pre><p>\nSELECT\n    project,\n    sum(hits) hits\nFROM wikistat_top_projects\nWHERE date = '2015-05-01'\nGROUP BY project\nORDER BY hits DESC\nLIMIT 10\n┌─project─┬─────hits─┐\n│ en      │ 34521803 │\n│ es      │  4491590 │\n│ de      │  4490097 │\n│ fr      │  3390573 │\n│ it      │  2015989 │\n│ ja      │  1379148 │\n│ pt      │  1259443 │\n│ tr      │  1254182 │\n│ zh      │   988780 │\n│ pl      │   985607 │\n└─────────┴──────────┘\n10 rows in set. Elapsed: 0.003 sec. Processed 8.19 thousand rows, 101.81 KB (2.83 million rows/s., 35.20 MB/s.)\n</p>\n</pre>\n<p>Notice this took ClickHouse 3ms to generate the same result, as opposed to 15 seconds with the original query. Also note, that we still need to use <code>GROUP BY</code> here as the SummingMergeTree engine is asynchronous (this saves resources and reduces impact on query processing) and some values can be uncalculated.</p>\n<h2 id=\"managing-materialized-views\"></h2>\n<p>Materialized views can be listed using a <code>SHOW TABLES</code> query:</p>\n<pre><p>\nSHOW TABLES LIKE 'wikistat_top_projects_mv'\n┌─name─────────────────────┐\n│ wikistat_top_projects_mv │\n└──────────────────────────┘\n</p>\n</pre>\n<p>We can drop materialized views using <code>DROP TABLE</code> but this will only delete the trigger itself:</p>\n<pre><p>\nDROP TABLE wikistat_top_projects_mv\n</p>\n</pre>\n<p>Remember to drop the target table as well if it’s not needed anymore:</p>\n<pre><p>\nDROP TABLE wikistat_top_projects\n</p>\n</pre>\n<h2 id=\"getting-materialized-view-size-on-disk\"></h2>\n<p>All metadata on materialized view tables is available in the system database like any other table. E.g., to get its size on disk, we can do the following:</p>\n<pre><p>\nSELECT\n    rows,\n    formatReadableSize(total_bytes) AS total_bytes_on_disk\nFROM system.tables\nWHERE table = 'wikistat_top_projects'\n┌──rows─┬─total_bytes_on_disk─┐\n│ 15336 │ 37.42 KiB           │\n└───────┴─────────────────────┘\n</p>\n</pre>\n<h2 id=\"updating-data-in-materialized-views\"></h2>\n<p>The most powerful feature of materialized views is that the data is updated automatically in the target table, when it is inserted into the source tables using the <code>SELECT</code> statement:</p>\n<p><span><img alt=\"updating_materialized_view.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fupdating_materialized_view_b90a9ac7cb.png&w=2048&q=75\"></span></p>\n<p>So we don’t have to additionally refresh data in the materialized view - everything is done automatically by ClickHouse. Suppose we insert new data into the <code>wikistat</code> table:</p>\n<pre><p>\nINSERT INTO wikistat\nVALUES(now(), 'test', '', '', 10),\n      (now(), 'test', '', '', 10),\n      (now(), 'test', '', '', 20),\n      (now(), 'test', '', '', 30);\n</p>\n</pre>\n<p>Now let’s query the materialized view’s target table to verify the <code>hits</code> column is summed properly. We use <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/select/from/#final-modifier\">FINAL</a> modifier to make sure the summing engine returns summarized hits instead of individual, unmerged rows:</p>\n<pre><p>\nSELECT hits\nFROM wikistat_top_projects\nFINAL\nWHERE (project = 'test') AND (date = date(now()))\n┌─hits─┐\n│   70 │\n└──────┘\n1 row in set. Elapsed: 0.005 sec. Processed 7.15 thousand rows, 89.37 KB (1.37 million rows/s., 17.13 MB/s.)\n</p>\n</pre>\n<p>In production environments avoid <code>FINAL</code> for big tables and always prefer <code>sum(hits)</code> instead. Also check <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/operations/settings/settings/#optimize-on-insert\">optimize_on_insert</a> settings option which controls how data is merged in insert.</p>\n<h2 id=\"speed-up-aggregations-using-materialized-views\"></h2>\n<p>As shown in the previous section, materialized views are a way to improve query performance. All kinds of aggregations are common for analytical queries, not only <code>sum()</code> as shown in the previous example. The SummingMergeTree is useful for keeping a total of values, but there are more advanced aggregations that can be computed using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/aggregatingmergetree/\">AggregatingMergeTree</a> engine.</p>\n<p>Suppose we have the following type of query being executed frequently:</p>\n<pre><p>\nSELECT\n    toDate(time) AS date,\n    min(hits) AS min_hits_per_hour,\n    max(hits) AS max_hits_per_hour,\n    avg(hits) AS avg_hits_per_hour\nFROM wikistat\nWHERE project = 'en'\nGROUP BY date\n</p>\n</pre>\n<p>This gives us the monthly min, max and average of hits per day for the given project:</p>\n<pre><p>\n┌───────date─┬─min_hits_per_hour─┬─max_hits_per_hour─┬──avg_hits_per_hour─┐\n│ 2015-05-01 │                 1 │             36802 │  4.586310181621408 │\n│ 2015-05-02 │                 1 │             23331 │  4.241388590780171 │\n│ 2015-05-03 │                 1 │             24678 │  4.317835245126423 │\n...\n└────────────┴───────────────────┴───────────────────┴────────────────────┘\n38 rows in set. Elapsed: 8.970 sec. Processed 994.11 million rows\n</p>\n</pre>\n<p><strong>Note here that our raw data is already aggregated by the hour.</strong></p>\n<p>Let's store these aggregated results using a materialized view for faster retrieval. Aggregated results are defined using <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/combinators/#-state\">state combinators</a>. State combinators ask ClickHouse to save the internal aggregated state instead of the final aggregation result. This allows using aggregations without having to save all records with original values. The approach is quite simple - we use *State() functions when creating materialized views and then their corresponding *Merge() functions at query time to get the correct aggregate results:</p>\n<p><span><img alt=\"aggregations_materialized_views.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Faggregations_materialized_views_eeca26badf.png&w=2048&q=75\"></span></p>\n<p>We’ll use <code>min</code>, <code>max</code>, and <code>avg</code> states in our example. In the target table for a new materialized view we’re going to use <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/data-types/aggregatefunction/\"><code>AggregateFunction</code></a> type to store aggregation states instead of values:</p>\n<pre><p>\nCREATE TABLE wikistat_daily_summary\n(\n    `project` String,\n    `date` Date,\n    `min_hits_per_hour` AggregateFunction(min, UInt64),\n    `max_hits_per_hour` AggregateFunction(max, UInt64),\n    `avg_hits_per_hour` AggregateFunction(avg, UInt64)\n)\nENGINE = AggregatingMergeTree\nORDER BY (project, date);\nOk.\nCREATE MATERIALIZED VIEW wikistat_daily_summary_mv\nTO wikistat_daily_summary AS\nSELECT\n    project,\n    toDate(time) AS date,\n    minState(hits) AS min_hits_per_hour,\n    maxState(hits) AS max_hits_per_hour,\n    avgState(hits) AS avg_hits_per_hour\nFROM wikistat\nGROUP BY project, date\n</p>\n</pre>\n<p>Let’s also populate it with data:</p>\n<pre><p>\nINSERT INTO wikistat_daily_summary SELECT\n    project,\n    toDate(time) AS date,\n    minState(hits) AS min_hits_per_hour,\n    maxState(hits) AS max_hits_per_hour,\n    avgState(hits) AS avg_hits_per_hour\nFROM wikistat\nGROUP BY project, date\n0 rows in set. Elapsed: 33.685 sec. Processed 994.11 million rows\n</p>\n</pre>\n<p>At the query time, we use the corresponding <code>Merge</code> combinator to retrieve values:</p>\n<pre><p>\nSELECT\n    date,\n    minMerge(min_hits_per_hour) min_hits_per_hour,\n    maxMerge(max_hits_per_hour) max_hits_per_hour,\n    avgMerge(avg_hits_per_hour) avg_hits_per_hour\nFROM wikistat_daily_summary\nWHERE project = 'en'\nGROUP BY date\n</p>\n</pre>\n<p>Notice we get exactly the same results but thousands of times faster:</p>\n<pre><p>\n┌───────date─┬─min_hits_per_hour─┬─max_hits_per_hour─┬──avg_hits_per_hour─┐\n│ 2015-05-01 │                 1 │             36802 │  4.586310181621408 │\n│ 2015-05-02 │                 1 │             23331 │  4.241388590780171 │\n│ 2015-05-03 │                 1 │             24678 │  4.317835245126423 │\n...\n└────────────┴───────────────────┴───────────────────┴────────────────────┘\n32 rows in set. Elapsed: 0.005 sec. Processed 9.54 thousand rows, 1.14 MB (1.76 million rows/s., 209.01 MB/s.)\n</p>\n</pre>\n<p>Any <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/\">aggregate function</a> can be used with State/Merge combinator as a part of an aggregating materialized view.</p>\n<h2 id=\"compacting-data-to-optimize-storage\"></h2>\n<p>In some cases we only need to store aggregated data but ingesting is done in an event-based manner. If we still need raw data for the latest couple of days and it’s fine to save aggregated history, we can combine a materialized view and <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-ttl\">TTL</a> for the source table.</p>\n<p>To optimize storage space, we can also declare column types explicitly to make sure the <a target=\"_blank\" href=\"https://clickhouse.com/blog/optimize-clickhouse-codecs-compression-schema\">schema is optimal</a>. Suppose we want to store monthly aggregated data only for each <code>path</code> from <code>wikistat</code> table:</p>\n<pre><p>\nCREATE MATERIALIZED VIEW wikistat_monthly_mv TO\nwikistat_monthly AS\nSELECT\n    toDate(toStartOfMonth(time)) AS month,\n    path,\n    sum(hits) AS hits\nFROM wikistat\nGROUP BY\n    path,\n    month\n</p>\n</pre>\n<p>The original table (data stored hourly) takes 3x more disk space than the aggregated materialized view:</p>\n<div><table><tbody><tr><th><strong>wikistat (original table)</strong></th><th><strong>wikistat_daily (materialized view)</strong></th></tr><tr><td>1.78GiB</td><td>565.68 MiB</td></tr><tr><td>1b rows</td><td>~ 27m rows</td></tr></tbody></table></div>\n<p><strong>An important note here</strong> is that compacting only makes sense when the resulting number of rows will reduce by at least 10 times. In other cases, ClickHouse's powerful compression and encoding algorithms will show comparable storage efficiency without any aggregations.</p>\n<p>Now that we have monthly aggregations, we can add a TTL expression to the original table so that the data is deleted after 1 week:</p>\n<pre><p>\nALTER TABLE wikistat MODIFY TTL time + INTERVAL 1 WEEK\n</p>\n</pre>\n<h2 id=\"validating-and-filtering-data\"></h2>\n<p>Another popular example when materialized views are used is processing data right after insertion. Data validation is a good example.</p>\n<p><span><img alt=\"materialized_view_filter.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fmaterialized_view_filter_385e36a77d.png&w=2048&q=75\"></span></p>\n<p>Let’s say we want to filter out all <code>path</code> values that contain unwanted symbols before saving them into the resulting table with clean data. We have around 1% of such values in our table:</p>\n<pre><p>\nSELECT count(*)\nFROM wikistat\nWHERE NOT match(path, '[a-z0-9\\\\-]')\nLIMIT 5\n┌──count()─┐\n│ 12168918 │\n└──────────┘\n1 row in set. Elapsed: 46.324 sec. Processed 994.11 million rows, 28.01 GB (21.46 million rows/s., 604.62 MB/s.)\n</p>\n</pre>\n<p>To implement validation filtering we’ll need 2 tables - a table with all data and a table with clean data only. The materialized view’s target table will play the role of a final table with clean data, and the source table will be transitory. We can remove data from the source table either based on TTL, as we did in the previous section, or change the engine of this table to <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/special/null/\">Null</a>, which does not store any data (the data will only be stored in the materialized view):</p>\n<pre><p>\nCREATE TABLE wikistat_src\n(\n    `time` DateTime,\n    `project` LowCardinality(String),\n    `subproject` LowCardinality(String),\n    `path` String,\n    `hits` UInt64\n)\nENGINE = Null\n</p>\n</pre>\n<p>Now let’s create a materialized view using a data validation query:</p>\n<pre><p>\nCREATE TABLE wikistat_clean AS wikistat;\nOk.\nCREATE MATERIALIZED VIEW wikistat_clean_mv TO wikistat_clean\nAS SELECT *\nFROM wikistat_src\nWHERE match(path, '[a-z0-9\\\\-]')\n</p>\n</pre>\n<p>When we insert data, <code>wikistat_src</code> will remain empty:</p>\n<pre><p>\nINSERT INTO wikistat_src SELECT * FROM s3('https://ClickHouse-public-datasets.s3.amazonaws.com/wikistat/partitioned/wikistat*.native.zst') LIMIT 1000\n</p>\n</pre>\n<p>Let’s make sure source table is empty:</p>\n<pre><p>\nSELECT count(*)\nFROM wikistat_src\n┌─count()─┐\n│       0 │\n└─────────┘</p>\n</pre>\n<p>But our <code>wikistat_clean</code> materialized table now has only valid rows:</p>\n<pre><p>\nSELECT count(*)\nFROM wikistat_clean\n┌─count()─┐\n│      58 │\n└─────────┘\n</p>\n</pre>\n<p>The other 942 rows (1000 - 58) were excluded by our validation statement at insert time.</p>\n<h2 id=\"routing-data-to-tables\"></h2>\n<p>Another example materialized views can be used for is to route data to different tables based on certain conditions:</p>\n<p><span><img alt=\"routing_materialized_views.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Frouting_materialized_views_d9c9303103.png&w=2048&q=75\"></span></p>\n<p>For example, we might want to route invalid data into another table instead of dropping it. In that case, we create another materialized view but with a different query:</p>\n<pre><p>\nCREATE TABLE wikistat_invalid AS wikistat;\nOk.\nCREATE MATERIALIZED VIEW wikistat_invalid_mv TO wikistat_invalid\nAS SELECT *\nFROM wikistat_src\nWHERE NOT match(path, '[a-z0-9\\\\-]')\n</p>\n</pre>\n<p>When we have single materialized views for the same source table, they will be processed in the alphabetical order. Remember not to create more than the order of tens of materialized views per source table as insert performance can degrade.</p>\n<p>If we insert the same data again, we will find 942 invalid rows in <code>wikistat_invalid</code> materialized view:</p>\n<pre><p>\nSELECT count(*)\nFROM wikistat_invalid\n┌─count()─┐\n│     942 │\n└─────────┘\n</p>\n</pre>\n<h2 id=\"transforming-data\"></h2>\n<p>Since materialized views are based on the result of a query, we can use all the power of ClickHouse functions in our SQL to transform source values to enrich and improve data clarity. As a quick example, let’s merge <code>project</code>, <code>subproject</code> and <code>path</code> columns into a single <code>page</code> column and split time into <code>date</code> and <code>hour</code> columns:</p>\n<pre><p>\nCREATE TABLE wikistat_human\n(\n    `date` Date,\n    `hour` UInt8,\n    `page` String\n)\nENGINE = MergeTree\nORDER BY (page, date);\nOk.\nCREATE MATERIALIZED VIEW wikistat_human_mv TO wikistat_human\nAS SELECT\n    date(time) AS date,\n    toHour(time) AS hour,\n    concat(project, if(subproject != '', '/', ''), subproject, '/', path) AS page,\n    hits\nFROM wikistat\n</p>\n</pre>\n<p>Now <code>wikistat_human</code> will be populated with the transformed data on the fly:</p>\n<pre><p>\n┌───────date─┬─hour─┬─page──────────────────────────┬─hits─┐\n│ 2015-11-08 │    8 │ en/m/Angel_Muñoz_(politician) │    1 │\n│ 2015-11-09 │    3 │ en/m/Angel_Muñoz_(politician) │    1 │\n└────────────┴──────┴───────────────────────────────┴──────┘\n</p>\n</pre>\n<h2 id=\"creating-materialized-views-in-production\"></h2>\n<p>New data is automatically added to a materialized view’s target table when source data arrives. But in order to populate materialized view with existing data on production environments we have to follow some simple steps:</p>\n<ol>\n<li>Pause write to the source table.</li>\n<li>Create materialized view.</li>\n<li>Populate the target table with data from the source table.</li>\n<li>Restart writes to the source table.</li>\n</ol>\n<p>Alternatively, we can use a certain time point in the future while creating materialized view:</p>\n<pre><p>\nCREATE MATERIALIZED VIEW mv TO target_table\nAS SELECT …\nFROM soruce_table WHERE date &gt; `$todays_date`\n</p>\n</pre>\n<p>Where <code>$todays_date</code> should be replaced with an absolute date. Thus our materialized view will begin triggering tomorrow, so we have to wait until tomorrow and populate historical data with the following query:</p>\n<pre><p>\nINSERT INTO target_table\nSELECT ...\nFROM soruce_table WHERE date &lt;= `$todays_date`\n</p>\n</pre>\n<h2 id=\"materialized-views-and-joins\"></h2>\n<p>Since materialized views work with a result of an SQL query, we can use JOINs as well as any other SQL feature. But JOINs should be used with caution.</p>\n<p>Suppose we have a table with page titles for our <code>wikistat</code> dataset:</p>\n<pre><p>\nCREATE TABLE wikistat_titles\n(\n    `path` String,\n    `title` String\n)\nENGINE = MergeTree\nORDER BY path\n</p>\n</pre>\n<p>This table has page titles associated with path:</p>\n<pre><p>\nSELECT *\nFROM wikistat_titles\n┌─path─────────┬─title────────────────┐\n│ Ana_Sayfa    │ Ana Sayfa - artist   │\n│ Bruce_Jenner │ William Bruce Jenner │\n└──────────────┴──────────────────────┘\n</p>\n</pre>\n<p>We can now create a materialized view that joins <code>title</code> from the <code>wikistat_titles</code> table on the <code>path</code> value:</p>\n<pre><p>\nCREATE TABLE wikistat_with_titles\n(\n    `time` DateTime,\n    `path` String,\n    `title` String,\n    `hits` UInt64\n)\nENGINE = MergeTree\nORDER BY (path, time);\nOk.\nCREATE MATERIALIZED VIEW wikistat_with_titles_mv TO wikistat_with_titles\nAS SELECT time, path, title, hits\nFROM wikistat AS w\nINNER JOIN wikistat_titles AS wt ON w.path = wt.path\n</p>\n</pre>\n<p>Note that we use <code>INNER JOIN</code>, so we’ll have only records that have corresponding values in the <code>wikistat_titles</code> table after populating:</p>\n<pre><p>\nSELECT * FROM wikistat_with_titles LIMIT 5\n┌────────────────time─┬─path──────┬─title──────────────┬─hits─┐\n│ 2015-05-01 01:00:00 │ Ana_Sayfa │ Ana Sayfa - artist │    5 │\n│ 2015-05-01 01:00:00 │ Ana_Sayfa │ Ana Sayfa - artist │    7 │\n│ 2015-05-01 01:00:00 │ Ana_Sayfa │ Ana Sayfa - artist │    1 │\n│ 2015-05-01 01:00:00 │ Ana_Sayfa │ Ana Sayfa - artist │    3 │\n│ 2015-05-01 01:00:00 │ Ana_Sayfa │ Ana Sayfa - artist │  653 │\n└─────────────────────┴───────────┴────────────────────┴──────┘\n</p>\n</pre>\n<p>Let’s insert a new record into the <code>wikistat</code> table to see how our new materialized view works:</p>\n<pre><p>\nINSERT INTO wikistat VALUES(now(), 'en', '', 'Ana_Sayfa', 123);\n1 row in set. Elapsed: 1.538 sec.\n</p>\n</pre>\n<p>Note the high insert time here - <strong>1.538 sec</strong>. We can see our new row in <code>wikistat_with_titles</code>:</p>\n<pre><p>\nSELECT *\nFROM wikistat_with_titles\nORDER BY time DESC\nLIMIT 3\n┌────────────────time─┬─path─────────┬─title────────────────┬─hits─┐\n│ 2023-01-03 08:43:14 │ Ana_Sayfa    │ Ana Sayfa - artist   │  123 │\n│ 2015-06-30 23:00:00 │ Bruce_Jenner │ William Bruce Jenner │  115 │\n│ 2015-06-30 23:00:00 │ Bruce_Jenner │ William Bruce Jenner │   55 │\n└─────────────────────┴──────────────┴──────────────────────┴──────┘\n</p>\n</pre>\n<p>But what happens if we add data to the <code>wikistat_titles</code> table? Let’s check:</p>\n<pre><p>\nINSERT INTO wikistat_titles\nVALUES('Academy_Awards', 'Oscar academy awards');\n</p>\n</pre>\n<p>Nothing will appear in the materialized view even though we have corresponding values in the <code>wikistat</code> table:</p>\n<pre><p>\nSELECT *\nFROM wikistat_with_titles\nWHERE path = 'Academy_Awards'\n0 rows in set. Elapsed: 0.003 sec.\n</p>\n</pre>\n<p>This is because a materialized view only triggers when its source table receives inserts. It's just a trigger on the source table and knows nothing about the join table. Note that this doesn't only apply to join queries, and is relevant when introducing any table external in the materialized view's SELECT statement e.g. using a <code>IN SELECT</code>.</p>\n<p>In our case, <code>wikistat</code> is the source table for the materialized view, and <code>wikistat_titles</code> is a table we join to:</p>\n<p><span><img alt=\"updates_materialized_view.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fupdates_materialized_view_7f44013d64.png&w=2048&q=75\"></span></p>\n<p>This is why nothing appeared in our materialized view - nothing was inserted into <code>wikistat</code> table. But let’s insert something to it:</p>\n<pre><p>\nINSERT INTO wikistat VALUES(now(), 'en', '', 'Academy_Awards', 456);\n</p>\n</pre>\n<p>We can see new records in materialized view:</p>\n<pre><p>\nSELECT *\nFROM wikistat_with_titles\nWHERE path = 'Academy_Awards'\n┌────────────────time─┬─path───────────┬─title────────────────┬─hits─┐\n│ 2023-01-03 08:56:50 │ Academy_Awards │ Oscar academy awards │  456 │\n└─────────────────────┴────────────────┴──────────────────────┴──────┘\n</p>\n</pre>\n<p><strong>Be careful</strong>, since JOINs can dramatically downgrade insert performance when joining on large tables as shown above. Consider using <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/dictionaries/external-dictionaries/external-dicts/\">dictionaries</a> as a more efficient alternative.</p>\n<h2 id=\"summary\"></h2>\n<p>In this blog post, we’ve explored how materialized views are a powerful tool in ClickHouse to improve query performance and extend data management capabilities. You can even use JOINs with materialized views. Consider materialized columns as a quick alternative when no aggregation or filtering is required.</p></div></article>"
