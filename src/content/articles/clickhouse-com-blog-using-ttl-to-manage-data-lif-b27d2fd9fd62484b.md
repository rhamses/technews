contentHtml: "<article><div><p>If the data that you are analyzing in ClickHouse grows over time you may want to plan to move, remove, or summarize older data on a schedule. Typically, your options here will depend on your data retention requirements and whether query SLAs vary depending on the data age. For example, while storing all dimensions at the highest available granularity on the latest data is usually required, it might be optional to store historical data with a lower level of detail.</p>\n<p>Managing the data lifecycle can help optimize storage as well as <a target=\"_blank\" href=\"https://clickhouse.com/resources/engineering/clickhouse-query-optimisation-definitive-guide\">improve query performance</a>. ClickHouse has a simple but powerful data lifecycle management tool configured with the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-ttl\"><code>TTL</code></a> clause of DDL statements.</p>\n<p>In this blog post, we explore the <code>TTL</code> clause and how this can be used to solve a number of data management tasks.</p>\n<h2 id=\"user-content-automatically-delete-expired-data\"></h2>\n<p>Sometimes, it no longer makes sense to store older data and it can be removed from ClickHouse. This is usually called a retention policy. Data removal is done automatically in the background based on conditions in a <code>TTL</code> statement.</p>\n<p>Suppose we have the <code>events</code> table, and we would like to delete all records older than one month:</p>\n<div><pre><code><span><span>CREATE TABLE</span> events</span>\n<span>(</span>\n<span>    `event` String,</span>\n<span>    `<span>time</span>` DateTime,</span>\n<span>    `<span>value</span>` UInt64</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (event, <span>time</span>)</span>\n<span>TTL <span>time</span> <span>+</span> <span>INTERVAL</span> <span>1</span> <span>MONTH</span> <span>DELETE</span>;</span></code></pre></div>\n<p>We add the <code>TTL</code> statement and use the <code>DELETE</code> operation with <code>time + INTERVAL 1 MONTH</code>. This will remove a record when its <code>time</code> column value is more than one month in the past.</p>\n<p><strong>Note</strong> that records removal is an asynchronous background process, and outdated records can still be available for some time.</p>\n<p>Let's try to insert a couple of records, including an outdated one, into the table:</p>\n<div><pre><code><span><span>INSERT INTO</span> events <span>VALUES</span>(<span>'error'</span>, now() <span>-</span> <span>interval</span> <span>2</span> <span>month</span>, <span>123</span>), (<span>'error'</span>, now(), <span>123</span>);</span></code></pre></div>\n<p>We'll find both records available in the table right after insert:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> events;</span></code></pre></div>\n<div><pre><code><span>┌─event─┬────────────────<span>time</span>─┬─value─┐</span>\n<span>│ error │ 2022-11-24 09:34:44 │   123 │</span>\n<span>│ error │ 2023-01-24 09:34:44 │   123 │</span>\n<span>└───────┴─────────────────────┴───────┘</span></code></pre></div>\n<p>The outdated record will be removed in the background by an \"off-schedule\" merge which is scheduled periodically. Sometime later:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> events;</span></code></pre></div>\n<div><pre><code><span>┌─event─┬────────────────<span>time</span>─┬─value─┐</span>\n<span>│ error │ 2023-01-24 09:34:44 │   123 │</span>\n<span>└───────┴─────────────────────┴───────┘</span></code></pre></div>\n<h3 id=\"user-content-managing-background-removal\"></h3>\n<p>Background removal happens every 4 hours by default and can be controlled using the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree/#merge_with_ttl_timeout\"><code>merge_with_ttl_timeout</code></a> table settings option:</p>\n<div><pre><code><span><span>CREATE TABLE</span> events</span>\n<span>...</span>\n<span>TTL <span>time</span> <span>+</span> <span>INTERVAL</span> <span>1</span> <span>MONTH</span> <span>DELETE</span></span>\n<span>SETTINGS merge_with_ttl_timeout <span>=</span> <span>1200</span>;</span></code></pre></div>\n<p>Do not use values smaller than 300 seconds for this setting, as this can create I/O overhead and impact cluster performance. After some time, we can find that the outdated record no longer exists in our table:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> events;</span></code></pre></div>\n<div><pre><code><span>┌─event─┬────────────────<span>time</span>─┬─value─┐</span>\n<span>│ error │ 2023-01-24 09:34:44 │   123 │</span>\n<span>└───────┴─────────────────────┴───────┘</span></code></pre></div>\n<h3 id=\"user-content-filter-which-rows-to-delete\"></h3>\n<p>Let's assume we would like to delete only a specific type of record (e.g., where an <code>event</code> column value is <code>error</code>). We can additionally specify this in the <code>WHERE</code> clause of the <code>TTL</code> statement:</p>\n<div><pre><code><span><span>CREATE TABLE</span> events</span>\n<span>(</span>\n<span>    `event` String,</span>\n<span>    `<span>time</span>` DateTime,</span>\n<span>    `<span>value</span>` UInt64</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (event, <span>time</span>)</span>\n<span>TTL <span>time</span> <span>+</span> <span>INTERVAL</span> <span>1</span> <span>MONTH</span> <span>DELETE</span> <span>WHERE</span> event <span>=</span> <span>'error'</span>;</span></code></pre></div>\n<p>Now, only outdated rows with the <code>event='error'</code> value will be removed:</p>\n<div><pre><code><span><span>INSERT INTO</span> events <span>VALUES</span>(<span>'not_error'</span>, now() <span>-</span> <span>interval</span> <span>2</span> <span>month</span>, <span>123</span>), (<span>'error'</span>, now(), <span>123</span>);</span></code></pre></div>\n<p>We can be sure the <code>not_error</code> record will not be removed (though it's older than one month):</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> events;</span></code></pre></div>\n<div><pre><code><span>┌─event─────┬────────────────<span>time</span>─┬─value─┐</span>\n<span>│ error     │ 2023-01-24 09:48:05 │   123 │</span>\n<span>│ not_error │ 2022-11-24 09:48:05 │   123 │</span>\n<span>└───────────┴─────────────────────┴───────┘</span></code></pre></div>\n<h3 id=\"user-content-multiple-delete-conditions\"></h3>\n<p>ClickHouse allows specifying multiple TTL statements. This allows us to be more flexible and specific about what to remove and when. Let's say we want to remove all non <code>error</code> events in 1 month and all errors after 6 months:</p>\n<div><pre><code><span><span>CREATE TABLE</span> events</span>\n<span>(</span>\n<span>    `event` String,</span>\n<span>    `<span>time</span>` DateTime,</span>\n<span>    `<span>value</span>` UInt64</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (event, <span>time</span>)</span>\n<span>TTL <span>time</span> <span>+</span> <span>INTERVAL</span> <span>1</span> <span>MONTH</span> <span>DELETE</span> <span>WHERE</span> event <span>!=</span> <span>'error'</span>,</span>\n<span>    <span>time</span> <span>+</span> <span>INTERVAL</span> <span>6</span> <span>MONTH</span> <span>DELETE</span> <span>WHERE</span> event <span>=</span> <span>'error'</span>;</span></code></pre></div>\n<p>We can have any number of rules configured for the <code>TTL</code> statement.</p>\n<h3 id=\"user-content-move-data-to-historical-tables\"></h3>\n<p>We can use <a target=\"_blank\" href=\"https://clickhouse.com/blog/using-materialized-views-in-clickhouse\">Materialized Views</a> in combination with a <code>TTL</code> statement to address cases where we might want to move outdated data to another table before being removed from the main table.</p>\n<p>Suppose we want to move <code>error</code> events to the table <code>errors_history</code> before removing them from the <code>events</code> table. First, we create a target table for a materialized view, which is of the same structure as the <code>events</code> table:</p>\n<div><pre><code><span><span>CREATE TABLE</span> errors_history (</span>\n<span>    `event` String,</span>\n<span>    `<span>time</span>` DateTime,</span>\n<span>    `<span>value</span>` UInt64</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (event, <span>time</span>);</span></code></pre></div>\n<p><strong>Note</strong> that we can't use <code>CREATE TABLE errors_history AS events</code> as this will also copy the TTL expression, which we don't want to happen. Then we create the materialized view trigger to ingest data automatically into the <code>errors_history</code> table:</p>\n<div><pre><code><span><span>CREATE</span> MATERIALIZED <span>VIEW</span> errors_history_mv <span>TO</span> errors_history <span>AS</span></span>\n<span><span>SELECT</span> <span>*</span> <span>FROM</span> events <span>WHERE</span> event <span>=</span> <span>'error'</span>;</span></code></pre></div>\n<p>Now, when we insert data into the <code>events</code> table, <code>error</code> events are automatically inserted into the <code>errors_history</code> table as well. On the other hand, when the <code>TTL</code> procedure removes records from the <code>events</code> table, they remain in the <code>errors_history</code> table.</p>\n<h2 id=\"user-content-compacting-historical-data-using-aggregations\"></h2>\n<p>In many cases, we don't want to delete the data, but we can afford to reduce its level of detail in order to save resources. For example, let's consider a situation when we don't want to remove <code>error</code> events from our table. At the same time, we might not need the per-second details after one month, so we can leave daily aggregated numbers.</p>\n<p>This can be implemented using a <code>GROUP BY ... SET</code> clause of the <code>TTL</code> statement:</p>\n<div><pre><code><span><span>CREATE TABLE</span> events</span>\n<span>(</span>\n<span>    `event` String,</span>\n<span>    `<span>time</span>` DateTime,</span>\n<span>    `<span>value</span>` UInt64</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (toDate(<span>time</span>), event)</span>\n<span>TTL <span>time</span> <span>+</span> <span>INTERVAL</span> <span>1</span> <span>MONTH</span> <span>GROUP</span> <span>BY</span> toDate(<span>time</span>), event <span>SET</span> <span>value</span> <span>=</span> <span>SUM</span>(<span>value</span>);</span></code></pre></div>\n<p>Several important points here:</p>\n<ul>\n<li>The <code>GROUP BY toDate(time), event</code> expression should be a prefix of the <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/improving-query-performance/sparse-primary-indexes/sparse-primary-indexes-design\">primary key</a>, so we also changed <code>ORDER BY (toDate(time), event)</code>.</li>\n<li>The <code>SET value = SUM(value)</code> clause will set the <code>value</code> column to the sum of all values in each group (usual behavior for the <code>GROUP BY</code> clauses in queries).</li>\n<li>The <code>time</code> column value will be chosen randomly during grouping (as in the case of using <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/aggregate-functions/reference/any/\"><code>any()</code> aggregate function</a>).</li>\n</ul>\n<p>Let's ensure the following data is inserted:</p>\n<div><pre><code><span><span>INSERT INTO</span> events <span>VALUES</span>(<span>'error'</span>, now() <span>-</span> <span>interval</span> <span>2</span> <span>month</span>, <span>123</span>),</span>\n<span>                         (<span>'error'</span>, now() <span>-</span> <span>interval</span> <span>2</span> <span>month</span>, <span>321</span>);</span></code></pre></div>\n<p>After some time, when background merge happens, we can see our data is aggregated:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> events;</span></code></pre></div>\n<div><pre><code><span>┌─event─┬────────────────<span>time</span>─┬─value─┐</span>\n<span>│ error │ 2022-11-24 12:36:23 │   444 │</span>\n<span>└───────┴─────────────────────┴───────┘</span></code></pre></div>\n<h2 id=\"user-content-changing-compression\"></h2>\n<p>While it may not be feasible to remove or aggregate data, you may have more relaxed query SLAs for your historical data. To address this, we can consider using higher <a target=\"_blank\" href=\"https://clickhouse.com/resources/engineering/database-compression\">compression</a> levels for older data to save more space. For example, we can ask ClickHouse to use <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/sql-reference/statements/create/table/#lz4hc\"><code>LZ4HC</code></a> compression of the higher level for the data older than one month. We need to use the <code>RECOMPRESS</code> clause for this:</p>\n<div><pre><code><span><span>CREATE TABLE</span> events</span>\n<span>(</span>\n<span>    `event` String,</span>\n<span>    `<span>time</span>` DateTime,</span>\n<span>    `<span>value</span>` UInt64</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (toDate(<span>time</span>), event)</span>\n<span>TTL <span>time</span> <span>+</span> <span>INTERVAL</span> <span>1</span> <span>MONTH</span> RECOMPRESS CODEC(LZ4HC(<span>10</span>));</span></code></pre></div>\n<p>Note that recompressed data will take less space but will also take more time to compress, thus impacting insertion times.</p>\n<h2 id=\"user-content-column-level-ttl\"></h2>\n<p>We can also manage the lifecycle of a single column using <code>TTL</code>. Suppose we have a <code>debug</code> column in our table that stores additional debug information (e.g., errors backtrace). This column is only useful for one week, during which it consumes a lot of space. We can ask ClickHouse to reset it to the default value after a week:</p>\n<div><pre><code><span><span>CREATE TABLE</span> events</span>\n<span>(</span>\n<span>    `event` String,</span>\n<span>    `<span>time</span>` DateTime,</span>\n<span>    `<span>value</span>` UInt64,</span>\n<span>    `debug` String TTL <span>time</span> <span>+</span> <span>INTERVAL</span> <span>1</span> WEEK</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (event, <span>time</span>);</span></code></pre></div>\n<p>Now let's insert an outdated record with a <code>debug</code> column value:</p>\n<div><pre><code><span><span>INSERT INTO</span> events <span>VALUES</span>(<span>'error'</span>, now() <span>-</span> <span>interval</span> <span>1</span> <span>month</span>, <span>45</span>, <span>'a lot of details'</span>);</span></code></pre></div>\n<p>ClickHouse will reset this <code>debug</code> column value to an empty string once the TTL processing is completed:</p>\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>FROM</span> events;</span></code></pre></div>\n<div><pre><code><span>┌─event─┬────────────────<span>time</span>─┬─value─┬─debug─┐</span>\n<span>│ error │ 2022-12-24 15:13:54 │    45 │       │</span>\n<span>└───────┴─────────────────────┴───────┴───────┘</span></code></pre></div>\n<p>Note that ClickHouse will use the default value for the column <code>TTL</code>. So in case the <code>DEFAULT</code> expression is present, outdated columns will have this value assigned.</p>\n<h2 id=\"user-content-moving-data-between-hot-and-cold-storage\"></h2>\n<p>For local setups, consider using storage management for your data. Typically users need faster but smaller disks (called hot, e.g., SSD) and larger but slower ones (called cold, e.g., HDD or S3). ClickHouse allows setting data policy so that data is moved to a slower device once the faster device usage reaches a specific threshold. This storage policy is <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-multiple-volumes_configure\">configured</a> in two steps - declaring a storage list and a policy.</p>\n<p>Alternatively, consider using ClickHouse Cloud, which avoids this complexity by separating storage and compute using object storage. When coupled with intelligent caching for data queried more often, typically your newer \"hot\" data, tiered architectures are no longer required.</p>\n<h2 id=\"user-content-summary\"></h2>\n<p>ClickHouse provides powerful data lifecycles management tools to enable automatic removal, compaction, or movement between different storage types. Compacting and retention can be configured using the <code>TTL</code> statement at a table level. Use <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-multiple-volumes\">disk policies</a> to manage storage or consider using <a target=\"_blank\" href=\"https://clickhouse.com/cloud\">ClickHouse Cloud</a> as a reliable solution to scaling.</p>\n<p>For more details on TTL, see our <a target=\"_blank\" href=\"https://clickhouse.com/docs/en/guides/developer/ttl/\">recently published guide</a>.</p></div></article>"
