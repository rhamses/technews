This feature is contributed by <strong>JackyWoo</strong> and reviewed by <strong>Alexander Sapin</strong> (the author of ClickHouse Keeper).</p>\n<p>It was the only missing feature to implement. In this release, clickhouse-keeper is still considered in pre-production stage, but many companies already started to evaluate and use it as a replacement of ZooKeeper. You can also start using clickhouse-keeper in your testing environments and we will appreciate your feedback.</p>\n<p>ClickHouse Keeper development started in Sep 2020, more than a year ago. It was a long road, and most of the efforts were to ensure correctness and stability in unusual and exceptional scenarios. It is covered by <a target=\"_blank\" href=\"https://jepsen.io/\">Jepsen</a> tests (including ZooKeeper tests and <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/tree/master/tests/jepsen.clickhouse-keeper\">new introduced tests</a>), continuous randomized stress testing with ClickHouse functional and integration tests. It is started to be tested in Yandex Cloud and among our best friends. If you’re pretending to be our best friend, you can also do it.</p>\n<p><strong>How does this help you?</strong></p>\n<p>ClickHouse Keeper is a drop-in replacement for ZooKeeper. It implements the ZooKeeper wire protocol and data model, but does it better.</p>\n<p>In contrast to ZooKeeper, there are no issues with zxid overflow or packet sizes. It has better memory usage and it does not require JVM tuning (because it does not use the JVM). Logs and snapshots are compressed (by about 10x typically) and checksummed. It can run as a separate process or directly inside clickhouse-server. You can use it with ClickHouse or with your Kafkas and Hadoops as well.</p>\n<p><a target=\"_blank\" href=\"http://presentations.clickhouse.tech/meetup54/keeper.pdf\">More info</a>.</p>\n<h2 id=\"partitions-for-insert-into-file-url-and-hdfs-storages\"></h2>\n<p>When using the table engines <code>File</code>, <code>URL</code>, and <code>HDFS</code> ClickHouse now supports partitions. When creating a table you can specify the partition key using the <code>PARTITION BY</code> clause e.g. <code>CREATE TABLE hits_files (...) ENGINE = File(TabSeparated) PARTITION BY toYYYYMM(EventDate)</code>.</p>\n<p>Similarly, when exporting data from ClickHouse using the <code>file</code>, <code>url</code>, and <code>hdfs</code> table functions you can now specify that the data is to be partitioned into multiple files using a <code>PARTITION BY</code> clause. For example, <code>INSERT INTO TABLE FUNCTION file('path/hits_{_partition_id}', 'TSV', 'columns...') PARTITION BY toYYYYMM(EventDate) VALUES ...</code> will create as many files as there are unique months in the dataset.</p>\n<p>The <code>s3</code> table function has already supported partitioned writes since ClickHouse 21.10.</p>\n<p><strong>How does this help you?</strong></p>\n<p>If data is split into multiple files, <code>SELECT</code> queries will be automatically parallelized. For example:</p>\n<div><pre><code><span><span>SELECT</span> user_id, <span>count</span>() <span>FROM</span> s3(</span>\n<span>    <span>'https://s3.us-east-2.amazonaws.com/.../*.csv.zstd'</span>,</span>\n<span>    <span>'...'</span>, <span>'...'</span>,</span>\n<span>    CSV,</span>\n<span>    <span>'user_id UInt64, ...'</span>)</span></code></pre></div>\n<p>You can even parallelize data processing across a distributed compute cluster if you use the <code>s3Cluster</code> table function:</p>\n<div><pre><code><span><span>SELECT</span> user_id, <span>count</span>() <span>FROM</span> s3Cluster(</span>\n<span>    my_cluster,</span>\n<span>    <span>'https://s3.us-east-2.amazonaws.com/.../*.csv.zstd'</span>,</span>\n<span>    <span>'...'</span>,</span>\n<span>    <span>'...'</span>, CSV,</span>\n<span>    <span>'user_id UInt64, ...'</span>)</span></code></pre></div>\n<p>It can also be used for integration with external data processing tools that consume data from <code>s3</code>.</p>\n<h2 id=\"from-infile-in-clickhouse-client-now-supports-glob-patterns-and-parallel-reading\"></h2>\n<p>Just write:</p>\n<div><pre><code><span>INSERT INTO my_table FROM INFILE '*.csv.gz' FORMAT CSV</span></code></pre></div>\n<p>Glob patterns support <code>*</code>, <code>?</code> and <code>{n..m}</code> with <code>{1..10}</code> or (aligned) <code>{01..10}</code> forms.</p>\n<p>This query will be automatically parallelized and it will also automatically detect the compression format from the file extension and decompress transparently.</p>\n<p>This improvement is done by <strong>Arthur Filatenkov</strong>.</p>\n<p><strong>How does this help you?</strong></p>\n<p>Now you don’t have to recall how to write a parallel for loop in your command line shell. clickhouse-client will do everything for you, it works intuitively and fast.</p>\n<h2 id=\"support-for-interval-operator-inside-with-fill-modifier-for-order-by-clause\"></h2>\n<p>What’s the… <code>WITH FILL</code> modifier in the <code>ORDER BY</code> clause? Take a look at the example:</p>\n<div><pre><code><span>:) <span>SELECT</span> EventDate, <span>count</span>() <span>FROM</span> test.hits <span>WHERE</span> CounterID <span>=</span> <span>2841673</span> <span>GROUP</span> <span>BY</span> EventDate <span>ORDER</span> <span>BY</span> EventDate</span>\n<span></span>\n<span>┌──EventDate─┬─<span>count</span>()─┐</span>\n<span>│ <span>2014</span><span>-03</span><span>-17</span> │       <span>3</span> │</span>\n<span>│ <span>2014</span><span>-03</span><span>-19</span> │       <span>6</span> │</span>\n<span>│ <span>2014</span><span>-03</span><span>-21</span> │       <span>7</span> │</span>\n<span>│ <span>2014</span><span>-03</span><span>-22</span> │       <span>6</span> │</span>\n<span>└────────────┴─────────┘</span></code></pre></div>\n<p>We have the report with Mar 17th, 19th, 21st, and 22nd. But Mar 18th and 20th are missing, because there is no data for these dates.</p>\n<p>And this is how it works in all SQL databases.</p>\n<p>But ClickHouse also has a quite unique and neat <code>WITH FILL</code> modifier for the <code>ORDER BY</code> clause.</p>\n<p>You just write:</p>\n<div><pre><code><span><span>SELECT</span> EventDate, <span>count</span>() <span>FROM</span> test.hits <span>WHERE</span> CounterID <span>=</span> <span>2841673</span> <span>GROUP</span> <span>BY</span> EventDate</span>\n<span><span>ORDER</span> <span>BY</span> EventDate <span>WITH</span> FILL STEP <span>1</span></span>\n<span></span>\n<span>┌──EventDate─┬─<span>count</span>()─┐</span>\n<span>│ <span>2014</span><span>-03</span><span>-17</span> │       <span>3</span> │</span>\n<span>│ <span>2014</span><span>-03</span><span>-18</span> │       <span>0</span> │</span>\n<span>│ <span>2014</span><span>-03</span><span>-19</span> │       <span>6</span> │</span>\n<span>│ <span>2014</span><span>-03</span><span>-20</span> │       <span>0</span> │</span>\n<span>│ <span>2014</span><span>-03</span><span>-21</span> │       <span>7</span> │</span>\n<span>│ <span>2014</span><span>-03</span><span>-22</span> │       <span>6</span> │</span>\n<span>└────────────┴─────────┘</span></code></pre></div>\n<p>And missing data is automatically filled.</p>\n<p>You can also add <code>FROM</code> and <code>TO</code>:</p>\n<div><pre><code><span><span>ORDER</span> <span>BY</span> EventDate <span>WITH</span> FILL <span>FROM</span> <span>'2014-03-01'</span>::<span>Date</span> <span>TO</span> <span>'2014-03-31'</span>::<span>Date</span> STEP <span>1</span>;</span></code></pre></div>\n<p>And it will automatically fill missing rows in the report.</p>\n<p>The <code>STEP</code> can be an arbitrary number. But what can you do if you want to fill missing dates for a report by months? You cannot just write <code>STEP 30</code> or <code>STEP 31</code> because different months contain different number of days…</p>\n<p>Since ClickHouse version 21.12 you can do it like this:</p>\n<div><pre><code><span>ORDER BY EventDate WITH FILL STEP INTERVAL 1 MONTH</span></code></pre></div>\n<p><code>INTERVAL</code> is a standard SQL operator, you can use SECOND, MINUTE, HOUR, DAY, WEEK, MONTH, QUARTER and YEAR.</p>\n<p>This is implemented by <strong>Anton Popov</strong> who is the author of the “WITH FILL” feature.</p>\n<p><strong>How does this help you?</strong></p>\n<p>It allows you to avoid a postprocessing step for your reports.</p>\n<h2 id=\"add-support-for-identifier-table-and-database-query-parameters\"></h2>\n<p>ClickHouse has support for parameterized queries. For example:</p>\n<div><pre><code><span>SELECT uniq(user_id) FROM table WHERE website = {name:String}</span></code></pre></div>\n<p>It allows to safely substitute parameters without the risk of SQL injections:</p>\n<div><pre><code><span>curl https://clickhouse-server:8443/?param_name=upyachka -d 'SELECT uniq(user_id) FROM table WHERE website = {name:String}'</span></code></pre></div>\n<p>You can even create customized API handlers for clickhouse-server based on prepared queries.</p>\n<p>In version 21.12 we introduce support for using parameters for tables and databases in your queries. This is implemented with the <code>Identifier</code> table parameter:</p>\n<div><pre><code><span>SELECT uniq(user_id) FROM {tbl:Identifier}</span></code></pre></div>\n<p>Identifier parameters also work for CREATE, DROP and all DDL queries. This is implemented by <strong>Nikolai Degterinskiy</strong>.</p>\n<p><strong>How does this help you?</strong></p>\n<p>Let ClickHouse do the heavy lifting and keep your scripts safe and secure.</p>\n<h2 id=\"bool-data-type\"></h2>\n<p>This feature is experimental in version 21.12. It is implemented by <strong>Kevin Wan (MaxWk)</strong> on top of initial work by <strong>hczhcz</strong> and reviewed by <strong>Pavel Kruglov</strong>.</p>\n<p>ClickHouse now natively supports a <code>Bool</code> data type. It allows to represent values as “true”/”false” during data import and export in text formats. It can also be adjusted to anything else using the settings <code>bool_true_representation</code> and <code>bool_false_representation</code> (for example, “yes” and “no”).</p>\n<p><strong>How does this help you?</strong></p>\n<p>Native boolean data types exist today in other databases that are often integrated with ClickHouse, such as PostgreSQL. The <code>Bool</code> data type in ClickHouse will make it more compatible with existing code and ease migration from other databases.</p>\n<p>Also it simplifies data ingestion from various text sources.</p>\n<h2 id=\"query-optimizations-with-table-constraints\"></h2>\n<p>This feature is <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/18787\">contributed</a> by <strong>Nikita Vasilev</strong>. Nikita is one of the most notable ClickHouse contributors. He started in 2019 by introducing data skipping indices into ClickHouse, then continued in 2020 with SSD-optimized key-value dictionaries and now contributed the new advancements in the query optimizer. This feature is reviewed by <strong>Anton Popov</strong>.</p>\n<p>So, what optimizations? ClickHouse already allows to specify constraints for tables:</p>\n<div><pre><code><span><span>CREATE TABLE</span></span>\n<span>(</span>\n<span>    URL String,</span>\n<span>    Domain String,</span>\n<span>    <span>CONSTRAINT</span> validate <span>CHECK</span> isValidUTF8(URL) <span>AND</span> length(URL) <span>BETWEEN</span> <span>10</span> <span>AND</span> <span>10000</span>,</span>\n<span>    <span>CONSTRAINT</span> my_constraint <span>CHECK</span> Domain <span>=</span> domainWithoutWWW(URL)</span>\n<span>) ...</span></code></pre></div>\n<p>Constraints are checked on <code>INSERT</code>. In this example we validate the URL and check that the <code>Domain</code> column actually contains the domain of the URL.</p>\n<p>Since version 21.12 constraints can also automatically optimize your queries! For example, if you write:</p>\n<div><pre><code><span><span>SELECT</span> <span>count</span>() <span>FROM</span> hits <span>WHERE</span> domainWithoutWWW(URL) <span>=</span> <span>'ghe.clickhouse.tech'</span></span></code></pre></div>\n<p>The query can be automatically rewritten to:</p>\n<div><pre><code><span><span>SELECT</span> <span>count</span>() <span>FROM</span> hits <span>WHERE</span> Domain <span>=</span> <span>'ghe.clickhouse.tech'</span></span></code></pre></div>\n<p>Because the <code>Domain</code> column is smaller and more compressable it will be faster to read and does not require calculation of the domain from the URL.</p>\n<p>The only thing you need to do is to enable the <code>optimize_using_constraints</code> and <code>optimize_substitute_columns</code> settings.</p>\n<p>As a bonus, we introduced a new type of constraint: <code>ASSUME</code>.</p>\n<div><pre><code><span>CONSTRAINT my_constraint ASSUME Domain = domainWithoutWWW(URL)</span></code></pre></div>\n<p>This type of constraint will not check anything on <code>INSERT</code> but still use the assumption to optimize the queries.</p>\n<p>It can also do logical inference, simplify the conditions and remove the conditions that are proved to be satisfied by constraints.</p>\n<p>It is controlled by the <code>convert_query_to_cnf</code> setting. You can also enable <code>optimize_append_index</code>. With this setting ClickHouse will derive more conditions on the table primary key.</p>\n<p>The idea is so powerful that we cannot resist adding one more feature: <em>indices for hypothesis</em>.</p>\n<div><pre><code><span>INDEX my_index (a &lt; b) TYPE hypothesis GRANULARITY 1</span></code></pre></div>\n<p>The expression is checked and the result (true/false) is written as an index for query optimization.</p>\n<p><strong>How does this help you?</strong></p>\n<p>Especially in large ClickHouse deployments with many complex tables it can be hard for users to always be up to date on the best way to query a given dataset. Constraints can help optimize queries without having to change the query structure itself. They can also make it easier to make changes to tables.</p>\n<p>For example, let’s say you have a table containing web requests and it includes a URL column that contains the full URL of each request. Many times, users will want to know the top level domain (.com, .co.uk, etc.), something ClickHouse provides the <code>topLevelDomain</code> function to calculate. If you discover that many people are using this function you might decide to create a new materialized column that pre-calculates the top level domain for each record.</p>\n<p>Rather than tell all your users to change their queries you can use a table constraint to tell ClickHouse that each time a user tries to call the <code>topLevelDomain</code> function the request should be rewritten to use the new materialized column.</p>\n<h2 id=\"read-large-remote-files-in-chunks\"></h2>\n<p>ClickHouse combines a fast query engine and efficient data storage. It also allows to integrate external data sources for data import and export or even to process external datasets on the fly without the need for data import or preprocessing.</p>\n<p>When reading large files in <code>Parquet</code>, <code>ORC</code>, and <code>Arrow</code> format using the <code>s3</code>, <code>url</code>, and <code>hdfs</code> table functions, ClickHouse will now automatically choose whether to read the entire file at once or read parts of it incrementally. This is now enabled by default and the setting <code>remote_read_min_bytes_for_seek</code> controls when to switch from reading it all to reading in chunks. The default is 1MiB.</p>\n<p><code>Parquet</code>, <code>ORC</code>, and <code>Arrow</code> are column-oriented formats (quite similar to the ClickHouse Native format) and now we can read only requested columns even if they are being read from a remote HTTP server with the <code>url</code> table function (range requests will be performed to skip unneeded data).</p>\n<p>This feature is implemented by <strong>Kseniia Sumarokova</strong>.</p>\n<p><strong>How does this help our ClickHouse Users?</strong></p>\n<p>In previous versions, when reading files in Arrow-based formats from remote locations with the <code>s3</code>, <code>url</code>, and <code>hdfs</code> table functions, ClickHouse would always read the entire file into memory. This works well when the files are small but will cause excessive memory usage or not work at all when the files are large. With this change, ClickHouse will read large files in chunks to keep memory usage in check and is now able to read even very large files.</p>\n<h2 id=\"and-many-more\"></h2>\n<p>Read the <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/master/CHANGELOG.md\">full changelog</a> for the 21.12 “Christmas” release for the full list of gifts from the <a target=\"_blank\" href=\"https://clickhouse.com/company/\">ClickHouse Team</a>.</p></div></article>"
