table function. Data is posted on an HTTP server in a <code>.native.xz</code> file. The most annoying part of this query is that we have to specify the data structure and the format of this file.</p>\n<p>In the new ClickHouse release 22.1 it becomes much easier:</p>\n<div><pre><code><span>SELECT * FROM url('https://datasets.clickhouse.com/github_events_v2.native.xz')</span></code></pre></div>\n<p>Cannot be more easy! How is that possible?</p>\n<p>Firstly, we detect the data format automatically from the file extension. Here it is <code>.native.xz</code>, so we know that the data is compressed by <code>xz</code> (LZMA2) compression and is represented in <code>Native</code> format. The <code>Native</code> format already contains all information about the types and names of the columns, and we just read and use it.</p>\n<p>It works for every format that contains information about the data types: <code>Native</code>, <code>Avro</code>, <code>Parquet</code>, <code>ORC</code>, <code>Arrow</code> as well as <code>CSVWithNamesAndTypes</code>, <code>TSVWithNamesAndTypes</code>.</p>\n<p>And it works for every table function that reads files: <code>s3</code>, <code>file</code>, <code>hdfs</code>, <code>url</code>, <code>s3Cluster</code>, <code>hdfsCluster</code>.</p>\n<p>A lot of magic happens under the hood. It does not require reading the whole file in memory. For example, Parquet format has metadata at the end of file. So, we read the header first to find where the metadata is located, then do a range request to read the metadata about columns and their types, then continue to read the requested columns. And if the file is small, it will be read with a single request.</p>\n<p>If you want to extract the structure from the file without data processing, the DESCRIBE query is available:</p>\n<div><pre><code><span>DESCRIBE url('https://datasets.clickhouse.com/github_events_v2.native.xz')</span></code></pre></div>\n<p>Data structure can be also automatically inferred from <code>JSONEachRow</code>, <code>CSV</code>, <code>TSV</code>, <code>CSVWithNames</code>, <code>TSVWithNames</code>, <code>MsgPack</code>, <code>Values</code> and <code>Regexp</code> formats.</p>\n<p>For <code>CSV</code>, either Float64 or String is inferred. For <code>JSONEachRow</code> the inference of array types is supported, including multidimensional arrays. Arrays of non-uniform types are mapped to Tuples. And objects are mapped to the <code>Map</code> data type.</p>\n<p>If a format does not have column names (like <code>CSV</code> without a header), the names <code>c1</code>, <code>c2</code>, … are used.</p>\n<p>File format is detected from the file extension: <code>csv</code>, <code>tsv</code>, <code>native</code>, <code>parquet</code>, <code>pb</code>, <code>ndjson</code>, <code>orc</code>… For example, <code>.ndjson</code> file is recognized as <code>JSONEachRow</code> format and <code>.csv</code> is recognized as header-less <code>CSV</code> format in ClickHouse, and if you want <code>CSVWithNames</code> you can specify the format explicitly.</p>\n<p>We support “schema on demand” queries. For example, the autodetected data types for <code>TSV</code> format are Strings, but you can refine the types in your query with the <code>::</code> operator:</p>\n<div><pre><code><span><span>SELECT</span> c1 <span>AS</span> domain, uniq(c2::UInt64), <span>count</span>() <span>AS</span> cnt</span>\n<span>  <span>FROM</span> file(<span>'hits.tsv'</span>)</span>\n<span>  <span>GROUP</span> <span>BY</span> domain <span>ORDER</span> <span>BY</span> cnt <span>DESC</span> LIMIT <span>10</span></span></code></pre></div>\n<p>As a bonus, <code>LineAsString</code> and <code>RawBLOB</code> formats also get type inference. Try this query to see how I prefer to read my favorite website</p>\n<div><pre><code><span>SELECT extractTextFromHTML(*)</span>\n<span>  FROM url('https://news.ycombinator.com/', LineAsString);</span></code></pre></div>\n<p>Schema autodetection also works while creating <code>Merge</code>, <code>Distributed</code> and <code>ReplicatedMegreTree</code> tables. When you create the first replica, you have to specify the table structure. But when creating all the subsequent replicas, you only need <code>CREATE TABLE hits ENGINE = ReplicatedMegreTree(…)</code> without listing the columns – the definition will be copied from another replica.</p>\n<p>This feature is implemented by <strong>Pavel Kruglov</strong> with the inspiration of initial work by <strong>Igor Baliuk</strong> and with additions by <strong>ZhongYuanKai</strong>.</p>\n<h2 id=\"realtime-resource-usage-in-clickhouse-client\"></h2>\n<p><code>clickhouse-client</code> is my favorite user interface for ClickHouse. It is an example of how friendly every command line application should be.</p>\n<p>Now it shows realtime CPU and memory usage for the query directly in the progress bar:</p>\n<p>Image1<span><img alt=\"clickhouse-22.webp\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fclickhouse_22_f9c7a230d2.webp&w=2048&q=75\"></span></p>\n<p>For distributed queries, we show both total memory usage and max memory usage per host.</p>\n<p>This feature was made possible by implementation of distributed metrics forwarding by <strong>Dmitry Novik</strong>. I have added this small visualization to clickhouse-client, and now it is possible to add similar info in every client using native ClickHouse protocol.</p>\n<h2 id=\"parallel-query-processing-on-replicas\"></h2>\n<p>ClickHouse is a distributed MPP DBMS. It can scale up to use all CPU cores on one server and scale out to use computation resources of multiple shards in a cluster.</p>\n<p>But each shard usually contains more than one replica. And by default ClickHouse is using the resources of only one replica on every shard. E.g. if you have a cluster of 6 servers with 3 shards and two replicas on each, a query will use just three servers instead of all six.</p>\n<p>There was an option to enable <code>max_parallel_replicas</code>, but that option required specifying a “sampling key”, it was inconvenient to use and did not scale well.</p>\n<p>Now we have a setting to enable the new parallel processing algorithm: <code>allow_experimental_parallel_reading_from_replicas</code>. If it is enabled, replicas will dynamically select and distribute the work across them.</p>\n<p>It works perfectly even if replicas have lower or higher amounts of computation resources. And it gives a complete result even if some replicas are stale.</p>\n<p>This feature was implemented by <strong>Nikita Mikhaylov</strong></p>\n<h2 id=\"service-discovery\"></h2>\n<p>When adding or removing nodes in a cluster, now you don’t have to edit the config on every server. encode it in sparse format and automatically optimize calculations!</p>\n<p>It is a special column encoding, similar to <code>LowCardinality</code>, but it’s completely transparent and works automatically.</p>\n<div><pre><code><span>CREATE TABLE test.hits …</span>\n<span>ENGINE = MergeTree ORDER BY …</span>\n<span>SETTINGS ratio_of_defaults_for_sparse_serialization = 0.9</span></code></pre></div>\n<p>It allows compressing data better and optimizes computations, because data in sparse columns will be processed directly in sparse format in memory.</p>\n<p>Sparse or full format is selected based on column statistics that is calculated on insert and updated on background merges.</p>\n<p>Developed by <strong>Anton Popov</strong>.</p>\n<p>We also want to make
