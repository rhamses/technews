Root-cause analysis usually means keeping a close eye on a handful of key fields and watching how their values change as filters are applied.</p>\n<p>The new <strong>Pinned Fields</strong> feature makes this much easier: fields of interest can now be pinned to the top of the left panel, reducing scrolling and keeping critical context always in view. A small change, but a big boost to workflow efficiency.</p>\n<p><span><img alt=\"pinned_fields.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fpinned_fields_6f4ee0aea8.png&w=2048&q=75\"></span></p>\n<h2 id=\"support-for-any-aggregation\"></h2>\n<p>Users familiar with ClickHouse SQL will appreciate the addition of the <code>any</code> aggregate function to HyperDX. This function is handy when you need to return the value of a column in an aggregation where a metric isn’t appropriate and any value will do.</p>\n<p>It’s typically used alongside other aggregate functions, like <code>min</code> or <code>max</code>, to return a string label or non-numeric column.</p>\n<p>For example, consider the following SQL query, which calculates the average, 90th percentile, maximum, and minimum performance for each service running in a Kubernetes cluster:</p>\n<!-- -->\n<div><pre><code><span><span>SELECT</span></span>\n<span>    ServiceName,</span>\n<span>    <span>avg</span>(Duration) <span>AS</span> avg_duration,</span>\n<span>    <span>max</span>(Duration) <span>AS</span> max_duration,</span>\n<span>    quantiles(<span>0.9</span>)(Duration) <span>AS</span> `<span>90</span>_duration`</span>\n<span><span>FROM</span> otel_v2.otel_traces</span>\n<span><span>GROUP</span> <span>BY</span> ServiceName</span>\n<span>LIMIT <span>10</span></span></code></pre></div>\n<!-- -->\n<p>Suppose we also want to return the Kubernetes node name for each service in the aggregated results. In many cases, this is acceptable - either because there’s only one possible value (e.g. grouping by a unique key) or because any value provides enough context. We can modify the query as follows:</p>\n<!-- -->\n<div><pre><code><span><span>SELECT</span></span>\n<span>    ServiceName,</span>\n<span>    <span>any</span>(ResourceAttributes[<span>'k8s.node.name'</span>]) <span>AS</span> node_name,</span>\n<span>    <span>avg</span>(Duration) <span>AS</span> avg_duration,</span>\n<span>    <span>max</span>(Duration) <span>AS</span> max_duration,</span>\n<span>    quantiles(<span>0.9</span>)(Duration) <span>AS</span> `<span>90</span>_duration`</span>\n<span><span>FROM</span> otel_v2.otel_traces</span>\n<span><span>GROUP</span> <span>BY</span> ServiceName</span>\n<span>LIMIT <span>10</span></span></code></pre></div>\n<!-- -->\n<blockquote>\n<p>Effectively, the <code>any</code> function avoids the need to add the column to the <code>GROUP BY</code> - in turn avoiding the increase in the cardinality of the aggregation and associated memory overhead.</p>\n</blockquote>\n<p>Now, ClickStack users will rarely write raw SQL like the example above when exploring data. However, the <code>any</code> aggregate makes it possible to build richer tables more efficiently - without having to aggregate by every single field just to return a value.</p>\n<p>For example, we can create a table using the <code>any</code> function that reproduces the results of the above query:</p>\n<p><span><img alt=\"any_function.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fany_function_326df031bd.png&w=2048&q=75\"></span></p>\n<p>Sources in HyperDX represent a database and table from a specific ClickHouse instance - the foundation on which all searches and charts are built.</p>\n<p>When you create a source, it can be <strong>connected with another source of a different type</strong>. This tells HyperDX that the two datasets belong to the same observability context and can be correlated visually in the UI.</p>\n<p>This concept is key to delivering the “<strong>single pane of glass</strong>” experience: unifying logs, metrics, and traces so they can be explored together. For example, this enables you to view logs in the context of a trace and vice versa.</p>\n<p><span><img alt=\"correlated_sources.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fcorrelated_sources_ab65ef2352.png&w=2048&q=75\"></span></p>\n<p>Importantly, these connections had to be declared in <strong>both directions</strong>.</p>\n<p>When using the default OTEL schemas, sources for Logs, Traces, and Metrics are created automatically, and these bi-directional connections are set up for you.</p>\n<p>However, many users deviate from the defaults - often to work with their own <strong>wide events</strong>. In these cases, creating a data source is a manual exercise, and correlating two sources has traditionally required a multi-step process. More specifically:</p>\n<ol>\n<li>Create the first data source (e.g. <code>Logs</code>)</li>\n<li>Create the second data source (e.g. <code>Traces</code>) and specify that it’s correlated with the <code>Logs</code> source</li>\n<li>Go back and modify the Logs source to declare the correlation with <code>Traces</code></li>\n</ol>\n<p>In the latest version of ClickStack, this workflow is much simpler thanks to <strong>auto-correlated sources</strong>. Step 3 is now handled automatically - when a user declares a connection from one source to another in step (2), the reverse connection is created for you.</p>\n<p>For users managing a large number of sources, often across multiple data versions, this change greatly simplifies setup and reduces the chance of errors, ensuring more consistent data across the application.</p>\n<h2 id=\"improved-query-efficiency-for-time-based-primary-keys\"></h2>\n<p>In large-scale ClickStack deployments, it’s common to tune the primary key by making <code>toStartOf[Minute|Hour|etc)(Timestamp)</code> the first column, followed by fields like <code>ServiceName</code> and the high-granularity timestamp. This <a target=\"_blank\" href=\"https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes#ordering-key-columns-efficiently\">design aligns with ClickHouse best practices</a> and makes time-based filtering far more efficient.</p>\n<p>Previously, the HyperDX UI didn’t fully exploit this when returning the \"latest\" results. Queries ordered by the raw <code>Timestamp</code> alone did not align with the sorting key, forcing ClickHouse to scan more granules than necessary. Effectively, this prevented ClickHouse from using <a target=\"_blank\" href=\"https://clickhouse.com/docs/sql-reference/statements/select/order-by#optimization-of-data-reading\">optimize_read_in_order</a>, where the server leverages the table index to read rows in primary key order. With this optimization, queries on large datasets with a small <code>LIMIT</code> (like in HyperDX) can be executed much faster.</p>\n<p>The latest release fixes this with added intelligence in the search layer of HyperDX. When a <code>toStartOfMinute</code> (or equivalent) expression is detected in the primary key, HyperDX now automatically orders results beginning with this column (e.g. <code>ORDER BY toStartOfMinute(Timestamp) DESC, Timestamp DESC</code>).</p>\n<p>This allows ClickHouse to use the sorting key directly and read data in order, avoiding unnecessary scans. Queries that once required reading millions of rows can now return the same results after touching only a fraction of the data.</p>\n<p>For example, consider the following table of 100 million random integers populated with the <code>INSERT INTO SELECT</code>:</p>\n<div><pre><code><span><span>CREATE TABLE</span> random_integers</span>\n<span>(</span>\n<span>    `<span>value</span>` DateTime,</span>\n<span>    `name` String</span>\n<span>)</span>\n<span>ENGINE <span>=</span> MergeTree</span>\n<span><span>ORDER</span> <span>BY</span> (toStartOfMinute(<span>value</span>), name, <span>value</span>)</span>\n<span></span>\n<span><span>INSERT INTO</span> random_integers <span>SELECT</span></span>\n<span>    <span>value</span>,</span>\n<span>    <span>'asdf'</span> <span>AS</span> name</span>\n<span><span>FROM</span> generateRandom(<span>'value Int32'</span>)</span>\n<span>LIMIT <span>100000000</span></span></code></pre></div>\n<!-- -->\n<p>If we select the top 10 rows and order by <code>value</code>, note how all 100 million rows are read:</p>\n<!-- -->\n<div><pre><code><span><span>SELECT</span> <span>*</span> <span>from</span> random.random_integers</span>\n<span>  <span>ORDER</span> <span>BY</span> <span>value</span> <span>DESC</span></span>\n<span>  LIMIT <span>10</span></span></code></pre></div>\n<!-- -->\n<p>Conversely, if we order by <code>(toStartOfMinute(value), name, value)</code> we read a fraction of the number of rows - improving the response time:</p>\n<!-- -->\n<div><pre><code><span><span>SELECT</span> <span>*</span></span>\n<span><span>FROM</span> random.random_integers</span>\n<span><span>ORDER</span> <span>BY</span> (toStartOfMinute(<span>value</span>), <span>value</span>) <span>DESC</span></span>\n<span>LIMIT <span>10</span></span></code></pre></div>\n<!-- -->\n<h2 id=\"chart-display-switcher\"></h2>\n<p>Picking the right visualization isn’t always straightforward -
