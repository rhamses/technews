contentHtml: "<article><div><h2 id=\"the-problem-you-already-know\"></h2>\n<p>You have a lot of data sitting in your analytical database. Millions of customers, billions of transactions. And now someone asks: “Which customers are connected through shared purchases? What fraud rings exist in our transaction network?”</p>\n<p>If you’ve tried answering relationship questions with SQL, you know what happens. You write a recursive CTE. It times out at 3 hops. You try self-joins. The query plan explodes. So you think: maybe I need a graph database.</p>\n<p>And that’s where things get complicated.</p>\n<p>To use a graph database, you need to copy your data there. That means building an ETL pipeline. Maintaining it. Watching it break when schemas change upstream. Organizations report that data engineers spend <a target=\"_blank\" href=\"https://www.integrate.io/blog/etl-market-size-statistics/\">12 hours per week</a> just “chasing data” across disconnected systems. The ETL tools market is projected to grow from <a target=\"_blank\" href=\"https://www.integrate.io/blog/etl-market-size-statistics/\">$8.5 billion to $24.7 billion by 2033</a> - that’s a lot of money spent moving data around instead of using it.</p>\n<p>Here’s the thing: <strong>every time you copy data, you create a sync problem.</strong> Now you have two systems, two schemas, and queries running on data that’s already stale.</p>\n<p>What if you didn’t have to copy the data at all?</p>\n<h2 id=\"how-it-usually-works-and-why-it-breaks-down\"></h2>\n<p>The traditional approach treats your OLAP database and your graph database as separate systems:</p>\n<p><span><img alt=\"Zero-Copy Graph Analytics Blog Banner (2).jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FZero_Copy_Graph_Analytics_Blog_Banner_2_8486c7b04b.jpg&w=2048&q=75\"></span></p>\n<p>You get SQL analytics from your warehouse. You get graph queries from your graph database. But connecting them requires that ETL pipeline in the middle.</p>\n<p>The pain points add up:</p>\n<ul>\n<li><strong>Dual storage costs</strong> - You’re paying to store the same data twice</li>\n<li><strong>Sync lag</strong> - Your graph queries run on data that’s minutes to hours old</li>\n<li><strong>Schema evolution</strong> - Change a column in the warehouse, now you’re debugging two systems</li>\n<li><strong>Pipeline ownership</strong> - Someone has to maintain that sync job forever</li>\n</ul>\n<p>One <a target=\"_blank\" href=\"https://www.isaca.org/resources/news-and-trends/industry-news/2025/the-zero-etl-paradigm-transforming-enterprise-data-integration-in-real-time\">case study</a> showed that migrating away from traditional ETL reduced latency by 98% (from 30 minutes to under 30 seconds) and cut operational costs by 66%. That’s not a marginal improvement - that’s a different way of working.</p>\n<h2 id=\"the-zero-copy-alternative\"></h2>\n<p>So what if you could query relationships directly on your existing data?</p>\n<p>That’s the idea behind zero-copy graph analytics. Instead of copying data into a separate graph database, you add a graph query layer on top of your analytical database.</p>\n<p><span><img alt=\"Zero-Copy Graph Analytics Blog Banner.jpg\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2FZero_Copy_Graph_Analytics_Blog_Banner_bc8b067a03.jpg&w=2048&q=75\"></span></p>\n<p>PuppyGraph connects to ClickHouse via JDBC and provides a graph query interface (Cypher/Gremlin). No data movement. The same tables that power your SQL dashboards also serve graph traversals.</p>\n<p>What you get:</p>\n<ul>\n<li><strong>Real-time data</strong> - Query data as it exists now, not as of last sync</li>\n<li><strong>Single source of truth</strong> - One schema, one storage layer</li>\n<li><strong>No sync pipeline</strong> - Nothing to maintain, nothing to break</li>\n<li><strong>Lower costs</strong> - No duplicate storage</li>\n</ul>\n<p>The key insight is simple: your data already has relationships. Customers buy products. Accounts make transactions. Devices connect to accounts. You don’t need to move data to query those relationships - you just need the right query interface.</p>\n<h2 id=\"the-bigger-picture-lakehouse-graph\"></h2>\n<p>Zero-copy isn’t just a technique - it’s part of a broader shift in how we think about data architecture.</p>\n<p>Think of it like this: you have a library. For years, if you wanted to study books (SQL analytics), you went to the main reading room. If you wanted to understand how books cite each other (graph queries), you had to photocopy everything and take it to a separate research annex across town. Every time the library got new books, someone had to update the annex. It worked, but it was slow and expensive.</p>\n<p>The data lakehouse changed the first part of this equation. Open table formats like <a target=\"_blank\" href=\"https://www.puppygraph.com/blog/iceberg-vs--delta-lake\">Delta Lake and Iceberg</a> turned that reading room into a proper research library - warehouse-grade reliability on low-cost object storage. SQL engines, ML pipelines, and streaming workloads all started converging on the same data. One library, many ways to use it.</p>\n<p>But graph remained the outlier. If you wanted to trace relationships, you still had to make copies and maintain that research annex.</p>\n<p>The <a target=\"_blank\" href=\"https://www.bigdatawire.com/2025/01/24/puppygraph-brings-graph-analytics-to-the-lakehouse/\">Lakehouse Graph</a> approach finally closes this gap. Instead of copying data to a separate graph database, you add a graph query layer directly to your lakehouse. The same tables that serve your SQL dashboards also serve graph traversals. One library. All the tools you need. No photocopies.</p>\n<p>Here’s what this means in practice: your data team isn’t maintaining two systems anymore. When new data lands in ClickHouse, it’s immediately available for both aggregation queries and relationship traversals. Schema changes happen once. There’s no “graph is 2 hours behind” conversation.</p>\n<p>ClickHouse handles what it’s good at - the heavy aggregations, time-series analysis, and analytical queries that need to scan billions of rows fast. PuppyGraph adds the graph layer on top, giving you multi-hop relationship queries without moving data elsewhere. You’re not replacing one system with another - you’re extending what your existing system can do.</p>\n<p>This is the direction modern data architecture is heading: fewer specialized systems, more capabilities on the same data. The question isn’t “SQL or graph?” anymore. It’s “what question do you have?” and the same data answers both.</p>\n<h2 id=\"why-graph-queries-matter\"></h2>\n<p>Not all questions fit naturally into SQL.</p>\n<p>SQL works well for set-based operations: filter these rows, aggregate that column, join these tables. But some questions are fundamentally about traversing relationships:</p>\n<ul>\n<li>Which customers bought similar products to this customer?</li>\n<li>What accounts share devices with flagged accounts?</li>\n<li>How does money flow through a network of transfers?</li>\n</ul>\n<p>If you’ve written a 5-hop query in SQL (find accounts connected to accounts connected to accounts…), you’ve seen the query plan explode. Each hop adds another join. Performance degrades exponentially.</p>\n<p>Graph databases handle this differently. They use index-free adjacency - each node stores direct pointers to its neighbors. Traversing a relationship is a constant-time operation, not a table scan. Studies show graph databases can be <a target=\"_blank\" href=\"https://www.puppygraph.com/blog/graph-database-vs-relational-database\">50% faster for multi-hop relationship queries</a> compared to relational systems.</p>\n<p>The trade-off was always: do I copy my data into another system? Zero-copy removes that trade-off.</p>\n<h2 id=\"what-this-looks-like-in-practice\"></h2>\n<p>I built a reference implementation with two use cases to demonstrate how this works. The full code is in the <a target=\"_blank\" href=\"https://github.com/maruthiprithivi/zero_copy_graph_analytics\">GitHub repository</a>.</p>\n<h3 id=\"customer-360-product-recommendations\"></h3>\n<p>The dataset has 35.4 million records: 1 million customers, 7.3 million transactions, 27 million interactions.</p>\n<p>For aggregations, you use SQL:</p>\n<div><pre><code><span><span>-- Customer lifetime value by segment</span></span>\n<span><span>SELECT</span> segment, <span>AVG</span>(ltv) <span>as</span> avg_ltv, <span>COUNT</span>(<span>*</span>) <span>as</span> customers</span>\n<span><span>FROM</span> customers</span>\n<span><span>GROUP</span> <span>BY</span> segment</span>\n<span><span>ORDER</span> <span>BY</span> avg_ltv <span>DESC</span>;</span></code></pre></div>\n<p>For relationship queries, you use Cypher:</p>\n<div><pre><code><span>// Find products frequently bought together</span>\n<span>MATCH (c:Customer)-[:PURCHASED]-&gt;(p1:Product)</span>\n<span>MATCH (c)-[:PURCHASED]-&gt;(p2:Product)</span>\n<span>WHERE p1.category = 'Electronics'</span>\n<span>  AND p2.category = 'Electronics'</span>\n<span>  AND p1 &lt;&gt; p2</span>\n<span>RETURN p1.name, p2.name, COUNT(DISTINCT c) as co_purchases</span>\n<span>ORDER BY co_purchases DESC</span>\n<span>LIMIT 10;</span></code></pre></div>\n<p>Both queries run on the same underlying tables. No sync. No lag.</p>\n<h3 id=\"fraud-detection-finding-hidden-networks\"></h3>\n<p>The fraud dataset has 1.29 million records with 5 embedded fraud patterns: account takeover rings, money laundering networks, card fraud, synthetic identity, and merchant collusion.</p>\n<p>Individual transactions look normal. It’s only when you see the network that fraud patterns emerge.</p>\n<div><pre><code><span>// Detect accounts sharing devices (account takeover pattern)</span>\n<span>MATCH (a1:FraudAccount)-[:USED_DEVICE]-&gt;(d:FraudDevice)&lt;-[:USED_DEVICE]-(a2:FraudAccount)</span>\n<span>WHERE a1 &lt;&gt; a2 AND d.is_suspicious = 1</span>\n<span>RETURN d.device_id, d.location,</span>\n<span>       COLLECT(DISTINCT a1.account_id) as connected_accounts</span>\n<span>ORDER BY SIZE(connected_accounts) DESC</span>\n<span>LIMIT 10;</span></code></pre></div>\n<p>This query finds accounts that share a suspicious device - a classic account takeover pattern. In SQL, this would require self-joins that get slow at scale. As a graph traversal, it runs in milliseconds.</p>\n<h2 id=\"what-about-query-performance\"></h2>\n<p>There is always this question “what is the impact on query performance?” when we talk about running Graph Queries without having a native Graph Storage.
