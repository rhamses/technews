contentHtml: "<article><div><p>In our CI/CD system at ClickHouse we use <a target=\"_blank\" href=\"https://docs.aws.amazon.com/lambda/\">lambda functions</a> a lot. AWS provides two ways to deploy a lambda function: Docker images and ZIP archives.</p>\n<p>The latter is much lighter, so we have used it exclusively since <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/pull/43769\">November 2022</a>. Besides the artifact size, it was easier to automate it in a simple <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/1443e490ea5287175f031eaee567fe5024cd7306/tests/ci/team_keys_lambda/build_and_deploy_archive.sh\">script</a>.</p>\n<p>In late 2023, we started using Terraform/OpenTofu to manage the CI/CD infrastructure. This raised the question of \"how should we manage artifacts to deploy?\"</p>\n<p>The question contains two different points:</p>\n<ul>\n<li>\n<p>The artifact should not change the content after each rebuild; otherwise, it would be redeployed on each execution of the <code>tofu apply</code> command.</p>\n</li>\n<li>\n<p>Ideally, it should be built on the fly, without any additional infrastructure on top, like pushing it to S3 or so</p>\n</li>\n</ul>\n<p><span><img alt=\"zip-archive-blog-1.png\" src=\"https://clickhouse.com/_next/image?url=%2Fuploads%2Fzip_archive_blog_1_7a0fb214e9.png&w=2048&q=75\"></span></p>\n<h3 id=\"challenge-one-the-order-matters\"></h3>\n<p>There are many factors affecting the ZIP archive content. One of the unexpected (for me) things is the order of archived files. Here's the example:</p>\n<div><pre><code><span><span># create files 1 2 3 4 5</span></span>\n<span>$ touch {<span>1.</span><span>.5</span>}</span>\n<span></span>\n<span><span># archive them in sorted and reserved order</span></span>\n<span>$ ls [<span>1</span>-<span>5</span>] | sort    | <span>zip</span> -q -<span>0</span> --names-stdin <span>sorted</span>.<span>zip</span></span>\n<span>$ ls [<span>1</span>-<span>5</span>] | sort -r | <span>zip</span> -q -<span>0</span> --names-stdin <span>reversed</span>.<span>zip</span></span>\n<span></span>\n<span><span># compare two files byte-by-byte</span></span>\n<span>$ cmp -l sort.<span>zip</span> rev.<span>zip</span></span>\n<span> <span>31</span>  <span>61</span>  <span>65</span></span>\n<span> <span>62</span>  <span>62</span>  <span>64</span></span>\n<span><span>124</span>  <span>64</span>  <span>62</span></span>\n<span><span>155</span>  <span>65</span>  <span>61</span></span>\n<span><span>202</span>  <span>61</span>  <span>65</span></span>\n<span><span>249</span>  <span>62</span>  <span>64</span></span>\n<span><span>343</span>  <span>64</span>  <span>62</span></span>\n<span><span>390</span>  <span>65</span>  <span>61</span></span></code></pre></div>\n<p>And here's the very first issue to solve. The order of files must be the same.</p>\n<p>Besides that, we should omit passing the directories to the zip command. Otherwise, it could cause inconsistency. The argument <code>-D</code> helps here.</p>\n<p>So, here's the very first solved issue.</p>\n<div><pre><code><span><span>export</span> LC_ALL=c</span>\n<span><span># zip uses random files order by default, so we sort the files alphabetically</span></span>\n<span>find . ! -<span>type</span> d -print0 | <span>sort</span> -z | <span>tr</span> <span>'\\0'</span> <span>'\\n'</span> | zip -XD -0 ../<span>\"<span>$PACKAGE</span>\"</span>.zip --names-stdin</span></code></pre></div>\n<p>The found files are null-divided and sorted, and then null is replaced by a new line and passed to the ZIP.</p>\n<h3 id=\"challenge-two-age-matters\"></h3>\n<p>This is the part of the man zip about one of the arguments above:</p>\n<div><pre><code><span><span>-</span>X</span>\n<span>   <span>--no-extra</span></span>\n<span>           Do <span>not</span> save extra file attributes (Extended Attributes <span>on</span> OS<span>/</span><span>2</span>,</span>\n<span>           uid<span>/</span>gid <span>and</span> file times <span>on</span> Unix).  The  zip  format  uses  extra</span>\n<span>           fields  <span>to</span> include additional information <span>for</span> <span>each</span> entry.  <span>Some</span></span>\n<span>           extra fields <span>are</span> <span>specific</span> <span>to</span> particular  systems  while  others</span>\n<span>           <span>are</span> applicable <span>to</span> <span>all</span> systems.  Normally <span>when</span> zip <span>reads</span> entries</span>\n<span>           <span>from</span>  an  existing archive, it <span>reads</span> the extra fields it knows,</span>\n<span>           strips the rest, <span>and</span> adds the extra fields applicable  <span>to</span>  that</span>\n<span>           system.   <span>With</span>  <span>-</span>X, zip strips <span>all</span> <span>old</span> fields <span>and</span> <span>only</span> includes</span>\n<span>           the Unicode <span>and</span> Zip64 extra fields (currently these  two  extra</span>\n<span>           fields cannot be disabled).</span></code></pre></div>\n<p>So, it should ignore timestamps.. But!</p>\n<div><pre><code><span><span>$ </span><span><span>touch</span> -t 201212121212 {1..5}</span></span>\n<span><span>$ </span><span>zip -XD0q older.zip {1..5}</span></span>\n<span><span>$ </span><span><span>touch</span> -t 201212121213 {1..5}</span></span>\n<span><span>$ </span><span>zip -XD0q newer.zip {1..5}</span></span>\n<span><span>$ </span><span>cmp -l older.zip newer.zip</span></span>\n<span> 11 200 240</span>\n<span> 42 200 240</span>\n<span> 73 200 240</span>\n<span>104 200 240</span>\n<span>135 200 240</span>\n<span>168 200 240</span>\n<span>215 200 240</span>\n<span>262 200 240</span>\n<span>309 200 240</span>\n<span>356 200 240</span></code></pre></div>\n<p>Somebody lies. So, before archiving the files, we need to change the last modification time.</p>\n<p><code>find \"$PACKAGE\" ! -type d -exec touch -t 201212121212 {} +</code></p>\n<h3 id=\"challenge-three-python-byte-code\"></h3>\n<p>According to the <a target=\"_blank\" href=\"https://docs.aws.amazon.com/lambda/latest/dg/python-package.html#python-package-pycache\">recommendations</a>, including <code>.pyc</code> files in the lambda archive speeds-up the cold start of the lambdas, but can cause issues with the byte-code version. The byte-code version depends on the Python version and the system architecture.</p>\n<p>After some experiments, we found that the best way to skip the <code>.pyc</code> files is to use the <code>-x,--exclude</code> option of the zip command.</p>\n<h3 id=\"final-challenge-the-os-matters\"></h3>\n<p>The last challenge is the OS. The ZIP archive format depends on the OS on which it was created. MacOS and Linux produce different ZIP archives, even if the content is the same. At this point we were already too tired of finding out what was going on. It was clear that any difference in <code>zip</code> binary could cause a bit-difference in the archives.&#160;</p>\n<p>The best way we came up with is using Python to create the ZIP archive. Python's <code>zipfile</code> module creates a consistent ZIP archive, regardless of the OS. But to be completely sure, we use Python from the <code>public.ecr.aws/lambda/python</code> image, which is the same as the one used by AWS Lambda.</p>\n<div><pre><code><span>docker_cmd=(</span>\n<span>  docker <span>run</span><span> -i --net=host --<span>rm</span> --user=<span>\"<span>${UID}</span>\"</span> -e HOME=/tmp --entrypoint=/bin/bash</span></span>\n<span>  --<span>volume</span><span>=<span>\"<span>${WORKDIR}</span>/..:/ci\"</span> --workdir=<span>\"/ci/<span>${DIR_NAME}</span>\"</span> <span>\"<span>${DOCKER_IMAGE}</span>\"</span></span></span>\n<span>)</span>\n<span></span>\n<span><span>\"${docker_cmd[@]}\"</span> -ex &lt;&lt;EOF</span>\n<span>cd <span>'$PACKAGE'</span></span>\n<span>find ! -type d -exec touch -t <span>201212121212</span> {} +</span>\n<span></span>\n<span>python &lt;&lt;<span>'EOP'</span></span>\n<span>import zipfile</span>\n<span>import os</span>\n<span>files_path = []</span>\n<span>for root, _, files in os.walk(<span>'.'</span>):</span>\n<span>    files_path.extend(os.path.join(root, file) for file in files)</span>\n<span><span># persistent file order</span></span>\n<span>files_path.sort()</span>\n<span>with zipfile.ZipFile(<span>'../$PACKAGE.zip'</span>, <span>'w'</span>) as zf:</span>\n<span>    for file in files_path:</span>\n<span>        zf.write(file)</span>\n<span>EOP</span>\n<span>EOF</span></code></pre></div>\n<h2 id=\"building-the-virtual-environment-for-the-lambda\"></h2>\n<p>The code to address this challenge is quite simple. The only thing to remember is that the virtual environment should be created with the same Python version as the one used by AWS Lambda.</p>\n<div><pre><code><span>docker_cmd=(</span>\n<span>  docker run <span>-i</span> <span>--net</span>=host <span>--rm</span> <span>--user</span>=<span>\"<span>$</span>{UID}\"</span> <span>-e</span> HOME=/tmp <span>--entrypoint</span>=/bin/bash</span>\n<span>  <span>--volume</span>=<span>\"<span>$</span>{WORKDIR}/..:/ci\"</span> <span>--workdir</span>=<span>\"/ci/<span>$</span>{DIR_NAME}\"</span> <span>\"<span>$</span>{DOCKER_IMAGE}\"</span></span>\n<span>)</span>\n<span><span>rm</span> <span>-rf</span> <span>\"<span>$PACKAGE</span>\"</span> <span>\"<span>$PACKAGE</span>\"</span>.zip</span>\n<span>mkdir <span>\"<span>$PACKAGE</span>\"</span></span>\n<span><span>cp</span> app.py <span>\"<span>$PACKAGE</span>\"</span></span>\n<span><span>if</span> [ -<span>f</span> <span>requirements.txt</span> ]; then</span>\n<span>  VENV=lambda<span>-venv</span></span>\n<span>  <span>rm</span> <span>-rf</span> <span>\"<span>$VENV</span>\"</span></span>\n<span>  <span>\"<span>$</span>{docker_cmd[@]}\"</span> <span>-ex</span> &lt;&lt;EOF</span>\n<span>    <span>'$PY_EXEC'</span> <span>-m</span> venv <span>'$VENV'</span> &amp;&amp;</span>\n<span>    source <span>'$VENV/bin/activate'</span> &amp;&amp;</span>\n<span>    pip install <span>-r</span> requirements.txt &amp;&amp;</span>\n<span>    <span># To have consistent pyc files</span></span>\n<span>    find <span>'$VENV/lib'</span> <span>-name</span> <span>'*.pyc'</span> <span>-delete</span></span>\n<span>    <span>cp</span> <span>-rT</span> <span>'$VENV/lib/$PY_EXEC/site-packages/'</span> <span>'$PACKAGE'</span></span>\n<span>    <span>rm</span> <span>-r</span> <span>'$PACKAGE'</span>/{pip,pip-*,setuptools,setuptools-*}</span>\n<span>    chmod <span>0777</span> <span>-R</span> <span>'$PACKAGE'</span></span>\n<span>EOF</span>\n<span>fi</span></code></pre></div>\n<p>Here we check if the lambda function has a <code>requirements.txt</code> file. If it does, we create a virtual environment with the same Python version as the one used by AWS Lambda, install the dependencies, and copy the site-packages to the lambda package directory. To remove the unnecessary files, we delete the <code>pip</code> and <code>setuptools</code> directories as well as Python byte-code files.</p>\n<h2 id=\"conclusion\"></h2>\n<p>The full script doing the job is available <a target=\"_blank\" href=\"https://github.com/ClickHouse/ClickHouse/blob/1443e490ea5287175f031eaee567fe5024cd7306/tests/ci/team_keys_lambda/build_and_deploy_archive.sh\">here</a>. Later it was moved into the private repository, but it is still used in Terraform/OpenTofu configuration to deploy the lambda functions.</p></div></article>"
