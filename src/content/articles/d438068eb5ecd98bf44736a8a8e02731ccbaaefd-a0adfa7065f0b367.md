contentHtml: "<p>With <a href=\"https://aws.amazon.com/emr/serverless/\" target=\"_blank\" rel=\"noopener\">Amazon EMR Serverless</a>, you can run open source big data frameworks such as <a href=\"https://spark.apache.org/\" target=\"_blank\" rel=\"noopener\">Apache Spark</a> and <a href=\"https://hive.apache.org/\" target=\"_blank\" rel=\"noopener\">Apache Hive</a> without managing clusters or infrastructure. Customers are increasingly choosing EMR Serverless for their analytics workloads because of the simplicity of a fully managed, serverless experience. As adoption grows, teams want to bring their most demanding jobs to Serverless too. These jobs include large-scale joins, shuffle-heavy ETL, and memory-intensive analytics that previously required carefully sized clusters. Customers migrating these heavyweight workloads from their Spark clusters often need the same compute shapes on EMR Serverless to achieve the same price-performance and make migration easier.</p> \n<p>Today, we’re excited to announce a new 32 vCPU / 244 GB worker configuration on Amazon EMR Serverless, giving you the headroom to run your most intensive workloads without leaving the serverless experience.</p> \n<h2 id=\"overview-of-larger-workers\">Overview of larger workers</h2> \n<p>An EMR Serverless application uses workers to run your Spark tasks, and you can choose a worker size that matches your workload. The new 32 vCPU worker offers a large compute and memory footprint (32 vCPUs and 244 GB of memory) that supports attaching up to 2,000 GB of shuffle-optimized disk. This combination benefits three common workload patterns:</p> \n<ul> \n <li>Shuffle-intensive workloads – Wide transformations such as <code>join</code>, <code>groupBy</code>, <code>sortBy</code>, and <code>repartition</code> redistribute large amounts of data across the cluster. Larger workers keep more shuffle data local to each executor and read and write shuffle blocks on higher-throughput disk, reducing remote fetches and shuffle wait time.</li> \n <li>I/O-heavy workloads – Queries that scan large datasets or spill intermediate data to disk are limited by disk throughput and IOPS. The shuffle-optimized disk raises the ceiling on both sides. Large workers also improve network bandwidth.</li> \n <li>Memory-intensive workloads – Higher per-executor memory (244 GB versus 30 GB) lets more data be cached and processed in memory without spilling, which helps with data skew and caching.</li> \n</ul> \n<h2 id=\"benchmark-setup\">Benchmark setup</h2> \n<p>We compared the recommended large-worker configuration against common small-worker defaults at identical total compute (192 vCPUs).</p> \n<ul> \n <li>Large workers – 6 executors × (32 vCPU / 244 GB / 2,000 GB shuffle-optimized disk).</li> \n <li>Small workers – 48 executors × (4 vCPU / 30 GB / 200 GB standard disk).</li> \n</ul> \n<p>The two configurations differ in both worker shape and disk class. We compare them as paired configurations, since shuffle-optimized disk is the intended disk type for the 32 vCPU worker. The reported gains reflect this combined effect.</p> \n<p>Both configurations set <code>spark.dynamicAllocation.enabled=false</code> and <code>spark.scheduler.minRegisteredResourcesRatio=1</code> to reduce variance from worker launch times. Requiring full registration ensures each query starts only after the cluster is ready. We ran every query with 3 iterations and reported the median. Both benchmarks ran on EMR release <code>emr-7.13.0</code> in a virtual private cloud (VPC) with an Amazon Simple Storage Service (Amazon S3) gateway endpoint attached to the private subnets.</p> \n<h2 id=\"benchmark-results\">Benchmark results</h2> \n<p>This post presents benchmark results comparing the new 32 vCPU workers against the existing 4 vCPU standard workers using the industry-standard TPC-DS and TPC-H benchmarks. Across 126 queries (104 TPC-DS and 22 TPC-H), <strong>large workers delivered an average of 29% faster query execution and 29% lower query-attributed cost, with zero regressions and improvements peaking at 45–55% on shuffle-heavy, multi-table join queries</strong>. Both the larger executor shape and the shuffle-optimized disk contribute to these gains. The disk advantage is most pronounced on the shuffle and I/O-heavy queries where the largest improvements appear.</p> \n<p>The following table summarizes the results across both benchmarks. Large workers won every query on both performance and cost.</p> \n<p><strong>Note</strong>: The benchmark results in this post are derived from the TPC-DS and TPC-H benchmark specifications. We ran 104 queries from the TPC-DS v2.4 suite against a 3 TB partitioned Parquet dataset, with 3 iterations per query for statistical confidence.</p> \n<p>The test environment was as follows:</p> \n<ul> \n <li>Dataset: 3 TB partitioned Parquet (24 TPC-DS tables).</li> \n <li>Queries: 104 (full suite minus 4 incompatible with the dataset schema).</li> \n <li>Iterations: 3 per query (one query per <code>start-job-run</code>, a fresh Spark application each time).</li> \n <li>Networking: VPC with an Amazon S3 gateway endpoint.</li> \n <li>EMR release: <code>emr-7.13.0</code>.</li> \n</ul> \n<p>The following chart shows the top 10 and bottom 5 queries by performance improvement. With 6 large executors instead of 48 small ones, the shuffle-optimized disk provides significantly higher random I/O throughput for reading and writing shuffle blocks. In addition, fewer executors mean less network coordination during shuffle. Each executor fetches shuffle data from only 5 remote sources instead of 47. This increases the share of shuffle data read locally, which improves performance.</p> \n<h2 id=\"tpc-h-1-tb-benchmark\">TPC-H 1 TB benchmark</h2> \n<p>TPC-H is a decision support benchmark that focuses on ad hoc analytical queries. We ran all 22 TPC-H queries against a 1 TB dataset, with 3 iterations per query. Each query was submitted as a separate <code>start-job-run</code> (a fresh Spark application) to simulate the realistic pattern of independent ad hoc queries arriving without session warmup.</p> \n<p>The test environment was as follows:</p> \n<ul> \n <li>Dataset: 1 TB partitioned Parquet.</li> \n <li>Queries: 22.</li> \n <li>Iterations: 3 per query (one query per <code>start-job-run</code>, a fresh Spark application each time).</li> \n <li>Networking: VPC with an Amazon S3 gateway endpoint.</li> \n <li>EMR release: <code>emr-7.13.0</code>.</li> \n</ul> \n<div style=\"width: 810px\" class=\"wp-caption alignnone\">\n <img loading=\"lazy\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/07/28/BDB-6032-2.png\" alt=\"Bar chart of per-query performance improvement across the 22 TPC-H queries\" width=\"800\" height=\"1034\">\n <p class=\"wp-caption-text\">Performance improvement for TPC-H queries, 32 vCPU compared to 4 vCPU standard workers</p>\n</div> \n<h2 id=\"why-large-workers-are-faster-for-tpc-h\">Why large workers are faster for TPC-H</h2> \n<p>The shuffle-optimized disk accelerates this initial table-scan phase. The larger the shuffle volume relative to the number of executors, the more a job benefits from keeping shuffle data local on high-throughput disk. Jobs that shuffle tens of gigabytes or more per executor are strong candidates.</li> \n <li>Check the Stages tab for the Spill (memory) and Spill (disk) columns and the Executors tab for peak JVM memory. If data is spilling to disk or peak memory is close to the configured executor memory, the higher memory of the large worker can remove the spill and improve performance.</li> \n</ul> \n<h2 id=\"when-not-to-use-large-workers\">When not to use large workers</h2> \n<p>Large workers are not the best fit for every workload:</p> \n<ul> \n <li>I/O-bound jobs – For workloads whose runtime is dominated by reading and writing data (rather than shuffle or memory pressure), a larger number of smaller workers (for example, 8 or 16 vCPU) with the same disk sizes can deliver better aggregate throughput. Spreading the work across more executors increases read/write parallelism, although a few large workers can leave disk and network bandwidth underused.</li> \n</ul> \n<h2 id=\"conclusion\">Conclusion</h2> \n<p>In this post, we demonstrated that EMR Serverless 32 vCPU workers deliver performance and cost benefits for shuffle-intensive Spark workloads. Across 126 TPC-DS and TPC-H queries, larger workers achieved an average 29% faster execution and 29% lower cost.</p> \n<p>We recommend evaluating the 32 vCPU worker with shuffle-optimized disk for your shuffle-intensive and I/O-heavy EMR Serverless Spark workloads. Amazon EMR Serverless now supports a 32 vCPU / 244 GB worker configuration for the most demanding Spark jobs. Across 126 TPC-DS and TPC-H queries, larger workers delivered an average 29% faster query execution and 29% lower cost, with the biggest gains on shuffle-heavy, multi-table join queries.
