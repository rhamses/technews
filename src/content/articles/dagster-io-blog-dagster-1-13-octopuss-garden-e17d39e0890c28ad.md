But the bigger story is how we think about CLI tooling in an AI-native world.</p><p>We increasingly see command-line utilities as a strong abstraction layer for AI systems: they are explicit, composable, scriptable, and much easier for agents to call reliably than ad hoc product surfaces. We continued leaning into that idea by expanding <strong>dg api</strong> so that more of Dagster's interaction surface is available through structured commands.</p><p>That means agents (or humans!) can more cleanly inspect and work with assets, runs, schedules, sensors, deployments, secrets, and other parts of the Dagster platform through a stable interface built for programmatic use.</p><p>For example, an agent can discover and inspect jobs through a straightforward CLI interface like this:</p><pre><code><span><span>$ dg api job list\n</span></span><span>NAME      DESCRIPTION  SCHEDULES SENSORS ASSET JOB\n</span><span>my_daily_job  Daily snapshot 1     2    Yes\n</span><span>my_sensor_job Sensor-driven 0     1    No\n</span><span>$ dg api job get my_daily_job\n</span><span>Name:    my_daily_job\n</span><span>Description: Daily snapshot\n</span><span>Asset Job: Yes\n</span><span>Tags:    env=prod, team=data\n</span><span>Schedule:  daily (0 0 * * *) [RUNNING]\n</span><span>Sensor:   file_watcher [RUNNING]</span></code></pre><p>For human users, that same investment pays off as clearer tooling and a more consistent operational surface. For teams using AI assistants, it means Dagster becomes much easier to inspect, operate, and troubleshoot from within the tools where they already work.</p><h2>State-backed components are enabled by default</h2><p>State-backed components are the framework Dagster uses for integrations whose definitions depend on external metadata. Instead of re-querying external systems every time a code location loads, Dagster can fetch that state at controlled times, persist it, and then build definitions from the cached result.</p><p>For data teams, that means a more predictable experience when working with integrations like dbt, Fivetran, Airbyte, Tableau, Looker, Sigma, Power BI, and others. </p><p>Starting in Dagster 1.13, persisted local state becomes the default for state-backed components. For these components, teams should refresh definition state as part of CI/CD so each deploy is built against fresh external metadata, or on some defined schedule. If you use the GitHub Actions workflow generated by <strong>dg plus deploy configure</strong>, that refresh step is included by default. queried.</p><p>However, because Dagster had no way of distinguishing between this type of asset and a more typical one, you'd experience challenges with other parts of the system, such as Declarative Automation and stale status calculation, that assumed that the only way for the contents of an asset to update would be for a materialization event to occur.</p><p>Now, when you define an asset you can pass <strong>is_virtual=True</strong> to indicate that the asset's contents update automatically when its parents ancestors:</p><pre><code><span><span>dg.AutomationCondition.eager().resolve_through_virtual()</span></span></code></pre><p>We’re also shipping with opt-in support for automatically treating all views currently in preview, which means we do not recommend it for production use cases as we gather feedback and potentially make changes to the API and functionality. We’re excited to see how you use this!</p><h2>Easier adoption with 20+ additional components</h2><p>Dagster 1.13 continues the push toward declarative, integration-friendly pipeline building.</p><p>Across the 1.12.x line, we added 20+ additional components, making it easier to connect Dagster to the tools, warehouses, cloud services, and operational systems teams already rely on.</p><p>On the Components front, this cycle added or expanded support for:</p><ul><li><strong>DbtCloudComponent</strong> for loading dbt Cloud projects as Dagster assets.</li><li>Declarative pipeline support for Spark in feature preview.</li><li>Azure resource components for Blob Storage and ADLS2.</li><li>GCP resource components for BigQuery, GCS, GCS File Manager, and Dataproc.</li><li>New component and asset-loading capabilities across Databricks, Tableau, Looker, Census, Polytomic, and more.</li></ul><p>Several integrations also got deeper operational support:</p><ul><li><strong>dbt_cloud_assets</strong> now supports partitioned assets.</li><li><strong>DatabricksAssetBundleComponent</strong> became more flexible, including job-level subsetting and better asset mapping.</li><li><strong>DatabricksWorkspaceComponent</strong> can automatically cancel Databricks jobs when a Dagster run is terminated.</li><li>Fivetran gained a polling sensor for observability, richer connector metadata, retry-on-reschedule behavior, and resync support.</li><li>BI integrations now enrich assets with more table and storage metadata automatically.</li></ul><p>There is also a clear pattern across these changes: integrations are not just being added, they are becoming more observable, more configurable, and easier to fit into a consistent Dagster model.
