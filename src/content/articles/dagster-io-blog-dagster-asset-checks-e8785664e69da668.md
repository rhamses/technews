contentHtml: "<div><p>Data orchestrators help data engineers deliver data, and they help organizations understand that data: where it comes from, where it’s used, and whether it’s up-to-date.</p><p>But delivering garbage data on time is often worse than delivering no data at all.</p><p>To truly support the job of data engineering, data orchestrators need to help deliver <em>high-quality</em> data and help organizations understand the quality of that data. &#160;To do this, data orchestrators need to understand data quality checks.</p><p>Dagster’s recent <a target=\"_blank\" href=\"https://dagster.io/blog/dagster-1-5-how-will-i-know\">1.5 release</a> includes “Asset Checks”, a new feature that offers the ability to <strong>define data quality checks that target Dagster assets</strong>. Asset Checks answer a theme of feature requests that we’ve been receiving for years, and they represent the culmination of a multi-month <a target=\"_blank\" href=\"https://github.com/dagster-io/dagster/discussions/16266\">open design process</a>, with dozens of comments from members of the Dagster community.</p><p>In this post, we’ll summarize why we believe data quality checks should be tightly integrated with orchestration, then survey Dagster Asset Checks and how they help data engineers deliver high-quality data.</p><figure><p></p><figcaption>&gt; &#160; &#160;Watch our Launch Week presentation on Asset Checks. &#160;</figcaption></figure><h2>Data quality checks and orchestration</h2><p>In most data platforms, data quality checks don’t exist, or they’re managed in tools siloed from the orchestrator. &#160;We believe that this makes operating data pipelines and the data platform at large significantly more difficult than it needs to be. Data quality must be a first-class orchestration feature, for a few reasons:</p><ul><li><strong>Data pipeline health all in one place -</strong> Orchestrators are already the source of truth on what succeeded, what failed, and where data comes from and goes to. If the orchestrator also understands when data fails its quality checks, it’s uniquely able to provide a full picture of the health of each data asset, and the pipeline as a whole.</li><li><strong>Data quality checks are work, and work needs to be orchestrated</strong> - Without an orchestrator, it’s difficult to know when checks are executed, to make sure work happens in the right order, and to pick up where you left off when there’s a failure. It’s easy to execute checks too often or not often enough.</li><li><strong>Orchestrate based on check results: stop bad data from spreading</strong> - When data doesn’t meet your quality bar, often you don’t want to let it spread to downstream assets in your pipeline. An orchestrator that understands data quality checks can skip downstream computations when upstream checks don’t pass.</li><li><strong>Declarative data quality checks as part of an asset’s contract</strong> - With the <a target=\"_blank\" href=\"https://dagster.io/blog/software-defined-assets\">software-defined asset</a> approach, the orchestrator is a source of truth on what data assets make up the pipeline. It’s natural to extend this so that the orchestrator understands what data quality checks are defined for each asset. &#160;It can then present a reliable, unified view of what the data in the pipeline <em>intended</em> to look like, which acts as a shared point of reference for data pipeline developers and stakeholders.</li></ul><p>In short, when data orchestration is siloed from data quality, it’s difficult to get a grip on the health of your data pipeline, painful to track all the activity happening inside your data platform, and nearly impossible to coordinate data quality checks with data updates.</p><h4>Introducing Dagster Asset Checks</h4><p>As a data orchestrator, Dagster’s fundamental abstraction is the Software-defined Asset: a description, in code, of an asset that should exist and how to produce and update it. &#160;Dagster enables building data pipelines by defining graphs of assets.</p><p><strong>In Dagster 1.5, we introduced a new abstraction that goes hand-in-hand with software-defined assets: the Asset Check.</strong> &#160;Each Asset Check verifies some property of a Dagster data asset, for example, that it has no null values in a particular column. &#160;Here’s sample Python code that demonstrates how to define a Dagster asset and corresponding Asset Check:</p><div><pre><code>from dagster import asset, asset_check, AssetCheckResult\n@asset\ndef events():\n    ...\n@asset_check(asset=events)\ndef no_null_event_ids():\n    events_df = ...\n    return AssetCheckResult(passed=count_nulls(events_df, \"event_id\") == 0)\n@asset_check(asset=events)\ndef dates_formatted_yyyy_mm_dd():\n    events_df = ...\n    return AssetCheckResult(passed=check_date_format(events_df, \"YYYY-MM-DD\"))</code></pre></div><p>Note that writing data quality logic from scratch in Python is just one way to use Dagster’s data quality APIs. &#160;In many data platforms, these APIs will instead wrap tools like dbt tests, Great Expectations, or organization-specific DSLs for specifying data quality constraints.</p><h5>A unified view of pipeline health</h5><p>Asset Checks enable Dagster to expose a unified view of pipeline health. Dagster’s <a target=\"_blank\" href=\"https://docs.dagster.io/etl-pipeline-tutorial/building-an-asset-graph\">asset graph</a> UI can tell you both whether assets have been <a target=\"_blank\" href=\"https://dagster.io/glossary/data-materialization\">materialized</a> successfully and whether their checks have passed.</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686e7e527aa6632520008322_Screenshot%202025-07-09%20at%2010.35.24%E2%80%AFAM.png\"></p></figure><p>When viewing an asset in Dagster’s UI, you can see all of its checks, and whether they’ve passed, failed, or haven’t run. This means a single place to go to discover and learn about issues in your data pipeline, whether it’s data quality checks that aren’t passing, errors that are causing materializations to fail, or data that’s more outdated than expected.</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686e7e6e37fc843a7ebc0640_Screenshot%202025-07-09%20at%2010.36.20%E2%80%AFAM.png\"></p></figure><h5>Asset Checks and alerting</h5><p>When an asset check fails, often you want to receive an email or Slack message, so you can investigate. &#160;Dagster Cloud’s alerting system now allows you to subscribe to alerts that inform you about failed checks.</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686e7e98e473384f677fe4cd_Screenshot%202025-07-09%20at%2010.36.53%E2%80%AFAM.png\"></p></figure><p>In open source deployments, you can write a sensor that checks for failed asset checks in the Dagster event log and invokes code to alert on them.</p><h5>Flexible execution: inline with the pipeline or on their own</h5><p>Checks can be executed from Dagster, either inline with the data pipeline that includes the assets they’re checking, or on their own. Executing inline with assets makes it easy to execute checks whenever data changes, as well as to stopping data that fails checks from spreading downstream. &#160;Executing them on their own allows finer-grained control: for example, if you update data frequently, but your check is expensive, you might want to run the check independently from the data updates.</p><p>Data quality checks can run in their own steps, or they can run in the same step that generates the asset that they’re checking.</p><div><pre><code>### Example of a data quality check that runs in its own step. When you instruct\n### Dagster to evaluate this check, it will execute the code in the decorated\n### function.\n@asset_check(asset=events)\ndef no_null_event_ids():\n    events_df = ...\n    return AssetCheckResult(passed=count_nulls(events_df, \"event_id\") == 0)\n### Example of a data quality check that runs in the same step as the asset\n### it's checking.\n@asset(check_specs=[AssetCheckSpec(\"dates_formatted_correctly\", asset=\"logins\")])\ndef logins():\n    logins_df = ...\n    ...\n    return MaterializeResult(\n        check_results=[AssetCheckResult(passed=check_date_format(logins_df, \"YYYY-MM-DD\"))]\n    )</code></pre></div><h5>Asset Checks vs. software-defined assets</h5><p>In many ways, Asset Checks function like software-defined assets themselves: they can be flexibly scheduled, they operate on assets, and they’re declared in code. The core difference is that they affect the status of the assets they check, rather than acting as their own nodes in the lineage graph.</p><h5>Asset Checks as data contracts</h5><p>The fact that Dagster can display checks as soon as they’re defined, even if they haven’t run yet, makes them a way of communicating data contracts. &#160;You can navigate to the page for a Dagster asset to understand what properties its owners expected it to satisfy.</p><p>What this all amounts to is that you end up with a single system that can:</p><ul><li>Understand and communicate what data is expected to exist, how it’s partitioned, how fresh it’s expected to be, under what circumstances it should be updated, and which team owns it (asset definitions)</li><li>Execute and track updates to that data (asset materializations)</li><li>Understand and communicate what that data should look like (Asset Check definitions)</li><li>Execute and track computations that verify that it looks like that (Asset Check executions)</li></ul><p>When you encounter an asset in the wild, you can refer to this system to get a reliable picture of what to expect from it: what its author intends it to look like, compared with the reality of what it actually looks like.</p><h5>Asset Checks and dbt tests</h5><p>Just as any dbt model can be understood as a software-defined asset, any dbt test can be understood as an Asset Check.</p><p>When loading a dbt project into the asset graph, Dagster’s dbt integration can now load all dbt tests as Asset Checks. &#160;This makes it much easier to visualize the success and failure of those tests, as they now show up on the Dagster asset that corresponds to the dbt models that they’re checking.</p><p>It also allows you to kick off individual dbt tests from Dagster’s UI.</p><h5>Asset Checks and <a target=\"_blank\" href=\"https://dagster.io/glossary/anomaly-detection\">anomaly detection</a></h5><p>It’s often difficult to come up with a hard threshold for bad data that merits a check failure and subsequent alert. Because of this, many practitioners prefer to instead write data quality checks that fail when the numbers are significantly different than what’s been observed in the recent past.</p><p>Dagster facilitates this pattern with its asset materialization metadata system. Each time you materialize an asset, you can attach a dictionary of arbitrary metadata to it. For example, you can include a count of the number of records that have a null value in a particular column.</p><p>You can write Asset Checks that access the metadata for historical materializations from Dagster’s event log. This allows you to compare the current number of null records to the number of null records in recent materializations, and fail if the current value appears anomalous.</p><div><pre><code>@asset\ndef asset1():\n    num_rows = ...\n    return MaterializeResult(metadata={\"num_rows\": num_rows})\n@asset_check(asset=asset1)\ndef num_rows_is_within_two_standard_deviations(context):\n    records = context.instance.get_event_records(\n        EventRecordsFilter(DagsterEventType.ASSET_MATERIALIZATION, asset_key=AssetKey(\"asset1\")),\n        limit=11,\n    )\n    num_rows_values = [\n        record.asset_materialization.metadata[\"num_rows\"].value for record in records\n    ]\n    mean = statistics.mean(num_rows_values[:-1])\n    stdev = statistics.stdev(num_rows_values[:-1])\n    return AssetCheckResult(passed=abs(num_rows_values[-1] - mean) - 2 * stdev)</code></pre></div><p>‍</p><h4>Data quality checks vs. other data quality patterns</h4><p>Data quality checks are an important pattern for ensuring that data is high quality. However, they’re not the only pattern. &#160;Dagster has functionality that’s helpful for handling some of the other patterns as well.</p><p>In some cases, it’s useful to just track data quality metrics, without setting any particular threshold for alerting. &#160;For example, you might want to record the number of null rows in your dataset every time you materialize it, and have access to a chart that indicates how that number has changed over time. &#160;Dagster’s asset materialization metadata functionality enables implementing this: you can attach arbitrary metadata to each asset materialization, and, if that metadata is numeric, Dagster will plot it on the asset page:</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686e7ef04c5cd13cb641c887_Screenshot%202025-07-09%20at%2010.38.23%E2%80%AFAM.png\"></p></figure><p>In other cases, you might want to generate a full data quality report at the end of your pipeline. For example, a PDF or spreadsheet or HTML or Great Expectations <a href=\"https://docs.greatexpectations.io/docs/terms/data_docs/\" target=\"_blank\">Data Doc</a> that reports on the quality of multiple assets in your pipeline. &#160;The best way to implement this in Dagster is to model this report as its own data asset, which depends on the assets that it’s reporting on.</p><h4>Try it out!</h4><p>Asset Checks are part of Dagster’s latest big release – <a target=\"_blank\" href=\"https://dagster.io/blog/dagster-1-5-how-will-i-know\">Dagster 1.5</a>. To learn how to take them for a spin, check out the <a href=\"https://docs.dagster.io/guides/test/asset-checks\" target=\"_blank\">docs</a>. Or if you’re using dbt, a better place to start is <a href=\"https://docs.dagster.io/integrations/libraries/dbt/reference#loading-dbt-tests-as-asset-checks-\" target=\"_blank\">the reference section on how to load your dbt tests as Asset Checks</a>.</p><p>Note that Asset Checks are currently an experimental feature, and the API may change in future releases. During this period, checks do not consume <a target=\"_blank\" href=\"https://dagster.io/lp/dagster-plus-trial\">Dagster Cloud</a> credits.</p><p>As always, we’d love to hear your use cases and your feedback: in the #data-quality-asset-checks channel in our Slack, or as discussions or issues in Github.</p><p>Learn more about Asset Checks in <a href=\"https://docs.dagster.io/guides/test/asset-checks\" target=\"_blank\">the Dagster Docs</a>.</p></div>"
