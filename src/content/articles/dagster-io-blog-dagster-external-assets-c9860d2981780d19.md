contentHtml: "<div><figure><p></p><figcaption>&gt; &#160; &#160;Nick Schrock (CTO and founder of Dagster Labs) explains the goals of Dagster Pipes and shares a demo during Dagster Launch Week - Fall 2023. &#160;</figcaption></figure><p>‍</p><p>Today we’re announcing <strong>External Assets</strong>, available in <a target=\"_blank\" href=\"https://github.com/dagster-io/dagster\">open-source</a> and in <a target=\"_blank\" href=\"https://dagster.io/lp/dagster-plus-trial\">Cloud</a>. External Assets enable Dagster to model data assets that are not scheduled and orchestrated by Dagster. The primary goal of External Assets is to enable the adoption of Dagster as a “single pane of glass” for a data platform without requiring a wholesale migration of all scheduling and orchestration infrastructure in that platform.</p><h2>Context</h2><p>Dagster is traditionally categorized as an orchestrator. However, in our previous post announcing Pipes, we described how Dagster is actually three layered systems:</p><ol><li>A metadata platform for lineage, observability, and data quality;</li><li>An orchestrator; and</li><li>A Python framework for business logic and data transformations.</li></ol><p>Pipes integrations provide a clean separation between the orchestration and data transform layers. External assets, in a similar fashion, provide a clean separation between orchestration and the metadata layer.</p><p>Taken together, these two features make Dagster a the most flexible, composable, and powerful solution for building an organization’s data platform control plane.</p><h3>Metadata</h3><p>The data structure that drives Dagster’s metadata layer is the event log: an immutable log of events that serves as a ledger of all activity on the data platform. When Dagster orchestrates a computation, it automatically adds structured events to this log out of the box. This structured event log is the system of record of the data platform, and drives Dagster’s operational, cataloging, alerting, and data quality tools.</p><p>We've received consistent feedback from users that they wish they could leverage the power of the event log and its associated tooling without using Dagster as the orchestrator. The reason is not because Dagster is not valuable as an orchestrator. Far from it. Those users have typically already adopted Dagster for greenfield use cases because they love its orchestration capabilities.</p><p>What happens is that they soon rely on Dagster for not just scheduling, but observability and operations as well, getting enormous value out of the system. Based on the experience and the quality of the tools, they want to get the rest of their existing platform and stakeholders into that system as quickly as possible.</p><p>However, the rest of their platform already uses a wide range of formal and informal orchestration solutions. The idea of synchronously migrating all of that infrastructure is untenable. Without the migration, they are still left with a siloed control plane. It’s just that one of the silos is much better than the others.</p><p>External assets provide a solution for exactly this situation. Teams can migrate to Dagster for lineage, observability, and data quality without migrating any scheduling or orchestration infrastructure.</p><h3>How does it work?</h3><p>It works by allowing users to:</p><ol><li>First define their asset specifications––structure, lineage, and metadata––in a declarative fashion within Dagster.</li><li>Then use an API to inject events into the event log attached to those assets.</li></ol><h4>Declaring your Assets</h4><p>You can declare an asset graph with specifications, which are just metadata with no associated materialization function.</p><div><pre><code>from dagster import AssetSpec, Definitions, external_assets_from_specs\nraw_csv_asset = AssetSpec(\n    key=\"raw_csv_asset\",\n    description=\"A raw csv file generated daily by a 3rd party.\",\n    metadata={\"owner\": \"Alice\"},\n)\nparquet_asset = AssetSpec(\n    key=\"parquet_asset\",\n    deps=[raw_csv_asset],\n    description=\"Raw csv asset immediately transformed to parquet.\",\n    metadata={\"owner\": \"Bob\"},\n)\ndefs = Definitions(\n    assets=external_assets_from_specs([raw_csv_asset, parquet_asset])\n)</code></pre></div><p>These assets are viewable within Dagster, but cannot be materialized.</p><h4>Attaching Events to Those Assets</h4><p>You can attach events to these using APIs. There are three primary ways to do this: a REST API, a Dagster Sensor, or our Python API.</p><h5>REST API</h5><p>The primary tool for attaching events to External Assets is the REST API. A user can, with just a couple lines of code, call these from their existing code and systems in order to start using Dagster’s metadata capabilities.</p><div><pre><code>import requests\n### .. later on\nrequests.post(\n    url=f\"{DAGSTER_URL}/report_asset_materialization/\",\n    json={\"asset_key\": key_from_path(s3_path)},\n).raise_for_status()</code></pre></div><p>‍</p><h5>Using Dagster Sensors</h5><p>Sometimes, as a user, you want to track the metadata based on activity in another system, but you cannot or do not want to modify that system directly to push metadata to you. In those cases, you want instead pull metadata via a polling mechanism</p><p>Dagster already has a construct, sensors, designed to periodically run lightweight computations. Traditionally these have been used to monitor external state changes and kick off runs based on those changes (e.g. kick off a run whenever a new file appears in a specified s3 bucket). Now these can be repurposed for another end: to poll an external system and insert events into the event log based on that external system’s state.</p><h5>Using a Python API</h5><p>Lastly we have a Python API, so that users can insert metadata events into Dagster directly from Python scripts. This is useful for backfilling data, ad hoc operations, and other use cases.</p><h4>What is the value?</h4><p>A fair question is why do this at all? Here are a few example of the value of using external assets:</p><ul><li><strong>System of record for metadata</strong>: You can use Dagster for your system of record for both definition-level and runtime metadata.</li><li><strong>Alerting</strong>: Dagster has built-in alerting that responds to event log events. External assets can leverage this.</li><li><strong>Cross-cutting data lineage</strong>: You can track the <a target=\"_blank\" href=\"https://dagster.io/glossary/data-lineage\">lineage</a> of data assets as they cut across orchestrators and schedulers.</li><li><strong>Data Quality</strong>: You can track the results of data quality checks for external assets. </li><li><strong>Scheduling</strong>. You can schedule downstream computations based on events in the event, either with auto-materialize policies or vanilla sensors.</li></ul><p> &#160;Learn more about External Assets in <a target=\"_blank\" href=\"https://docs.dagster.io/guides/build/assets/external-assets\">the Dagster Docs</a>.</p><h3>Conclusion</h3><p>External assets allow for adoption of Dagster’s metadata capabilities independently from its orchestrator. You can use Dagster for lineage, observability, data quality, alerting and other capabilities without migrating scheduling and orchestration infrastructure.</p><p>We still believe that over time, organizations that adopt External Assets will eventually also migrate the scheduling and orchestration infrastructure to Dagster. However external assets provide an incremental pathway for getting there, with intermediate milestones that deliver tangible benefits to users at every step in the journey. It relieves pressure on the data platform, allowing them to do infrastructure migrations at a time and pace of their choosing, while still enabling them to deploy Dagster’s active metadata universally across the organization.</p></div>"
