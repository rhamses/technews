contentHtml: "<div><h2>The modern data stack has democratized big data bills</h2><p>Ah, the dreaded “let’s talk about your increased usage” email. Time to round up your technical stakeholders and finance team to figure out what budget is appropriate for the coming year.</p><p>The euphoria of powerful on-demand compute in data warehouses has given way to the hangover of pay-as-you-go pricing. Whether it's an ML engineer running a $30,000 backfill or a data analyst setting an operational dashboard to materialize 96 times a day, it's never been easier to set up data operations today that will cost you a ton of money later.</p><p>And this problem has only been compounded by the assortment of convenient point solutions that have become the foundation of the modern data stack.</p><p>Our tech stacks have become a black box where data operations go in and cloud bills come out.</p><figure><p></p><figcaption>&gt; &#160; &#160;As part of Launch Week, Jarred Colli shares the details on Dagster Insights, and Beb Pankow provides a quick demo. &#160;</figcaption></figure><h4>Getting operational visibility is possible</h4><p>If this sounds familiar, you’re not alone. We spent the last couple of months talking with our users to explore cost management best practices. We learned that nearly 70% of our customers felt that their cost management strategies were ineffective.</p><p>But some customers have dedicated the time and resources to improving their operational visibility, and here are the steps that were common their solutions:</p><ol><li><strong>Build a data attribution system:</strong> Passing and retrieving metadata to attribute compute activity in the data warehouse to specific data activities at the business level. I.e..</li><li><strong>Compile the data set for analysis</strong>: collect and normalize this data for analysis. A common strategy would be to pipe it into the data warehouse.</li><li><strong>Create a feedback loop:</strong> this information has to be shared back to stakeholders on some regular cadence to find opportunities for optimization</li></ol><p>Teams that take these steps can build at least some visibility into the cost of their operations. But they take a lot of effort and expertise to design, build and maintain, often at the expense of other important tasks.</p><h4>Why metadata attribution is hard to do</h4><p>Identifying the metadata you need, figuring out where it should go, and coming up with a plan to ensure that the metadata gets there is challenging. There will be different teams, different infrastructure combinations, recurring and adhoc data processes to consider, potentially multiple data warehouses, navigating this can be a real maze.</p><p>The technical strategy we typically see is for teams to try to <strong>pass their operational data from their data processes into the data warehouse</strong>. The data engineer defines the specific metadata that is passed to the compute layer by data pipelines at run time, and that operational data is later <a target=\"_blank\" href=\"https://dagster.io/glossary/data-normalization\">normalized</a> and <a target=\"_blank\" href=\"https://dagster.io/glossary/data-export\">exported</a> back from the compute layer to be analyzed on some fixed cadence.</p><p>This approach has some major drawbacks:</p><ul><li>Operational data is <a target=\"_blank\" href=\"https://dagster.io/glossary/dataset-splitting\">split</a> between the orchestrator and the data warehouse, losing valuable context about the pipeline’s execution.</li><li>It sometimes requires the creation of a technical governance layer</li><li>It does not work well for teams with multiple data warehouses</li></ul><p>We think teams should instead <strong>retrieve operational metadata from the data warehouse and attribute it to data processes inside the orchestrator</strong>.</p><h4>We think you should aggregate operational metadata in the orchestrator</h4><p>We believe that teams should use their data orchestrator as the starting point to solve these problems for the following reasons:</p><ul><li><strong>The orchestrator sits at the intersection of all of your recurring data processes</strong>: Dagster sees the data flowing through multiple tools— from ingestion to processing, transformation, and visualization. By making it the gathering point for your operational metadata, you can avoid creating new data silos.</li><li><strong>It provides the essential building blocks for attribution</strong>: Dagster’s framework already gives you the tools you need to create, write and retrieve metadata both at run time and asynchronously</li><li><strong>It preserves operational context</strong>: Dagster already has first-class knowledge of the objects creating the metadata - it will know that snowflake cost is associated with a particular asset, it knows the definition of the asset, when it was materialized, who owns it etc. Keeping all of this data in one place speeds up the feedback/optimization process.</li><li><strong>It speeds up the feedback loop</strong>: by aggregating and attributing your operational metadata at the orchestration layer, teams can respond more quickly to trend changes in these kpis.</li></ul><h4>Introducing: Dagster Insights</h4><p>Until recently, capturing metadata from your downstream systems and storing it in Dagster was challenging. Dagster didn’t make it easy to capture data that wasn’t available at runtime, and there were limited options for exploring Dagster information in aggregate.</p><p>Today we’re announcing the launch of Dagster Insights, a collection of a metrics store and API, tooling for capturing operational metadata, and a new set of visualizations within the UI all of which help shine a light on the performance of your data platform.</p><p>Dagster Insights will make it easier to capture operational data from pipelines and downstream systems and explore that data within the UI, or export it to other tools. These features are being released on request to Cloud customers who are interested in trying the features and giving us feedback.</p><h5>Platform-level <strong>visualization for operational metrics</strong></h5><p>Sometimes, you’re not sure where you need to focus your attention between your data pipelines. Maybe it's not obvious which assets or jobs are the most compute intensive, or which things are being run the most regularly.</p><p>Dagster can now provide <a target=\"_blank\" href=\"https://dagster.io/glossary/data-aggregation\">aggregated data</a> to give data teams a birds-eye view about the performance of pipelines, starting with the basic KPIs generated by Dagster such as compute duration, failures, retries, and materializations and more, helping to answer such questions as:</p><ul><li>where are my resources being used?</li><li>what are my most compute-intensive assets and data operations?</li><li>what pipelines are wasting the most compute time on retries?</li></ul><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686706536cff32d6ff1d6e34_681399f654933b29e12fbe37_67eaca6b54ea8b6b3a469e30_dagster-insights-2-min.png\"></p><figcaption> &#160; &#160; &#160;The new insights functionality provides granular analysis of your data pipeline execution. &#160;Shown here: Step retries. &#160; &#160;</figcaption></figure><h5><strong>Definition-level visualization for troubleshooting</strong></h5><p>A birds' eye view is useful for finding areas for investigation, but sometimes you need to dive into the pipeline or the asset for troubleshooting. &#160;Dagster Insights will make it possible to drill down into key metrics for specific data objects and answer questions like:</p><ul><li>why is my compute duration increasing so quickly?</li><li>when did the increase in step failures begin?</li></ul><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686706536cff32d6ff1d6e2c_681399f654933b29e12fbe36_67eaca6b54ea8b6b3a469e4c_dagster-insights-3-min.png\"></p><figcaption> &#160; &#160; &#160;Deep dive into specific assets to better understand execution and credit consumption patterns. &#160; &#160;</figcaption></figure><h5>Mechanisms for capturing and storing additional metadata</h5><p>While visualization of basic metrics can be helpful, we know that Dagster’s metadata by itself isn’t enough to get at the operational insight that teams want. So we’ve also added some capabilities for capturing and storing metadata that make it easier to:</p><p><strong>A Metrics Store + API</strong></p><p>Historically, Dagster’s metadata capabilities were limited to the data that could be captured and written into the event history log at run time. With the addition of a new API and data processing back end, important operational information about the characteristics of a data process can be written anytime.</p><div><pre><code>from dagster_cloud.dagster_insights import dbt_with_snowflake_insights\n@dbt_assets(...)\ndef my_asset(context: AssetExecutionContext):\n   dbt_cli_invocation = dbt_resource.cli([\"build\"], context=context)\n   yield from dbt_with_snowflake_insights(context, dbt_cli_invocation)</code></pre></div><p><strong>Tooling to capture real-time operational data</strong></p><p>We’ve added methods and capabilities to the dagster-cloud package that make retrieving this information from pipelines at runtime as simple as adding a few new lines of code. Out of the box, we’re providing tooling for easily capturing a defined set of metadata coming from dbt+snowflake, but we’ll soon open this up for capturing both predefined and arbitrary metadata from any downstream system.</p><div><pre><code>from dagster_cloud.dagster_insights import (\n    create_snowflake_insights_asset_and_schedule,\n)\nsnowflake_insights_definitions = create_snowflake_insights_asset_and_schedule(\n    start_date=\"2023-10-5\",\n    snowflake_resource_key=\"snowflake_insights\",\n)</code></pre></div><p><strong>Retrieve and submit latent operational data</strong></p><p>Capturing all of the metadata you need for operational visibility is a challenge because some kinds of data just aren’t available until after the computation is over. For example… credits in Snowflake. So, we’ve built an easily configurable data pipeline for retrieving data from those data sources and writing it back to Dagster’s metrics store. For now, this tooling is specific to Snowflake, which generates latent cost data, but it will be easily adjusted to other tools.</p><h4>The release plan</h4><p><strong>Available to Cloud customers only</strong></p><p>While visualizing and exploring Dagster-generated metrics within the UI will be available to all cloud users, capturing external metadata in our metrics store will be an Enterprise-only feature.</p><p><strong>Coming Improvements</strong></p><p>As part of the experimental release, out-of-the-box utilities for capturing external metadata are limited to dbt+Snowflake pipelines creating software-defined assets.</p><p>We plan to quickly follow up with additional data sources and capabilities for capturing arbitrary metadata, as well as native tooling for enabling these capabilities on pipelines using the ops / jobs framework in the coming weeks.</p><p><strong>Enabled on request</strong></p><p>Dagster Insights is an experimental feature, which means that it can only be enabled on request from our team. To get access to it, please reach out to us directly through your company slack channel or by joining #dagster-insights to request it, and read more about the status of <a href=\"https://docs.dagster.io/dagster-cloud/insights\" target=\"_blank\">the experimental release here</a>.</p></div>"
