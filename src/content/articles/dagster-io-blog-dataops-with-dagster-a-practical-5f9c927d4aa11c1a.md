contentHtml: "<div><p>DevOps gave us CI/CD. DataOps gives us data we can actually trust.</p><p>If you haven't heard of so-called “DataOps” before, you are probably already doing pieces of it. You've got schedules, you've got tests, maybe you've got some alerting. But DataOps is about bringing all of these together into a cohesive system that provides <em>visibility</em> into what's happening and <em>control</em> over how it behaves.</p><p>Think of it in two phases. <strong>Day 1</strong> is the developer experience or how you build, test, and ship pipeline code. <strong>Day 2</strong> is the operational layer or how your pipelines behave in production once they're running. Most orchestrators focus on one or the other. Dagster covers both.</p><figure><p></p></figure><h2><strong>Day 1: Developer Experience</strong></h2><p>Before you can have reliable data in production, you need a reliable way to build and ship pipeline code. This is where Dagster's developer experience really shines. It brings the same development workflow application engineers have had for years to data teams.</p><p>The<a target=\"_blank\" href=\"https://docs.dagster.io/guides/labs/dg/dagster-dg-cli\"> dg CLI</a> is your starting point. It greatly simplifies the ergonomics of building with Dagster. For example, dg dev launches a full local Dagster instance with UI in one command, dg scaffold generates assets with zero boilerplate, dg check validates your definitions before you push, and dg list lets you introspect everything without spinning up the UI. Having this functionality is useful for LLM coding agents. When you pair Claude code or Codex with our <a target=\"_blank\" href=\"https://github.com/dagster-io/skills\">official Dagster plugin and skills</a>, you can ship more confidently without having to be a Dagster expert since we have encoded that knowledge for you.&#160;</p><p>Once your code is ready,<a target=\"_blank\" href=\"https://docs.dagster.io/deployment/dagster-plus/ci-cd/branch-deployments\"> branch deployments</a> in Dagster+ close the gap between local dev and production. Every pull request automatically spins up a fully functional Branch Deployment, an ephemeral copy of your data platform. Open a PR, get an isolated environment, validate under production-like conditions, and merge with confidence. Branch deployments include change tracking that highlights which assets were modified, making code review far more meaningful. You can even configure them to clone production databases and run materializations against real data schemas.&#160;</p><p>‍</p><h2><strong>Day 2: DataOps in Production</strong></h2><p>DataOps is the practice of applying DevOps principles to data: automation, monitoring, reliability, and collaboration. Ultimately its about predictability and minimizing the amount of negative surprises.</p><p>The core principles:</p><ul><li><strong>Reliability</strong>: Can your pipelines recover from failure gracefully?</li><li><strong>Quality</strong>: Is the data that lands actually correct?</li><li><strong>Visibility</strong>: Can you and your stakeholders see what's going on without digging through logs?</li></ul><p>These are tangible engineering problems with specific solutions.</p><h2><strong>Reliability</strong></h2><p>Pipelines fail. APIs time out, databases go down, and rate limits get hit. A reliable data platform doesn't prevent every failure; it recovers automatically and gives you controls to manage how work gets processed.</p><h3><strong>Automatic Retries</strong></h3><p>The simplest reliability improvement is enabling automatic retries in your dagster.yaml:</p><pre><code><span><span>run_retries:</span><span>\n</span></span><span><span>  </span><span>enabled:</span><span> </span><span>true</span><span>\n</span></span><span><span>  </span><span>max_retries:</span><span> </span><span>3</span><span>\n</span></span><span><span>  </span><span>retry_on_asset_or_op_failure:</span><span> </span><span>true</span></span></code></pre><p>Any run that fails is picked up and retried without manual intervention. This covers a huge class of transient failures: network blips, rate limits, and brief connection issues. By default, retries use a FROM_FAILURE strategy that skips successful steps and re-executes only from the point of failure, so you're not wasting compute re-running work that already succeeded.</p><p>You can override retry settings per job with tags like dagster/max_retries and dagster/retry_strategy, and Dagster also supports op-level retries with exponential backoff for step-level transient failures. One tip: if you enable both, set retry_on_asset_or_op_failure: false at the instance level so run retries handle only infrastructure failures (like crashed workers) while op retries handle step-level issues. For the full breakdown, see<a target=\"_blank\" href=\"https://docs.dagster.io/deployment/execution/run-retries\"> configuring run retries</a>.</p><h3><strong>Concurrency Controls</strong></h3><p>Concurrency controls prevent failures before they happen. If your Redshift cluster can only handle a few concurrent connections, a burst of runs can overwhelm it. Without guardrails, you're essentially DDoS-ing your own warehouse.</p><pre><code><span><span>run_queue:</span><span>\n</span></span><span><span>  </span><span>max_concurrent_runs:</span><span> </span><span>15</span><span>\n</span></span><span><span>  </span><span>tag_concurrency_limits:</span><span>\n</span></span><span><span>    </span><span>-</span><span> </span><span>key:</span><span> </span><span>'database'</span><span>\n</span></span><span><span>      </span><span>value:</span><span> </span><span>'redshift'</span><span>\n</span></span><span><span>      </span><span>limit:</span><span> </span><span>4</span><span>\n</span></span><span><span>    </span><span>-</span><span> </span><span>key:</span><span> </span><span>'dagster/backfill'</span><span>\n</span></span><span><span>      </span><span>limit:</span><span> </span><span>10</span><span>\n</span></span><span></span></code></pre><p>This says: run at most 15 concurrent runs total, but only 4 can target Redshift at once, and backfills are capped at 10. Runs that exceed a tag limit wait in the queue instead of failing. On Dagster+, you configure this in your deployment settings. For more, see<a target=\"_blank\" href=\"https://docs.dagster.io/guides/operate/managing-concurrency\"> managing concurrency</a>.</p><h3><strong>Run Priority</strong></h3><p>If you've ever had to worry about launching a big backfill because it would bottleneck production jobs, this is for you.&#160;</p><p>Dagster processes runs first-in-first-out by default, but you can override that with the dagster/priority tag (higher numbers run first, negative numbers de-prioritize):</p><pre><code><span><span>@dg.job(</span><span>tags={</span><span>\"dagster/priority\"</span><span>: </span><span>\"5\"</span><span>}</span><span>)</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>critical_production_job</span><span>():</span><span> ...\n</span></span><span>\n</span><span><span></span><span>@dg.schedule(</span><span>\n</span></span><span><span>    cron_schedule=</span><span>\"0 * * * *\"</span><span>,\n</span></span><span><span>    job_name=</span><span>\"backfill_job\"</span><span>,\n</span></span><span><span>    tags={</span><span>\"dagster/priority\"</span><span>: </span><span>\"-1\"</span><span>},\n</span></span><span><span></span><span>)</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>low_priority_backfill</span><span>(</span><span>_</span><span>):</span><span> ...</span></span></code></pre><p>Combine priority with tag concurrency limits and production always runs first while backfills take only a couple of queue slots. No more weekend backfills blocking Monday morning dashboards. One important detail: a run blocked by tag concurrency limits won't block unrelated lower-priority runs. For details, see<a target=\"_blank\" href=\"https://docs.dagster.io/deployment/execution/customizing-run-queue-priority\"> customizing run queue priority</a>.</p><h3><strong>Run Timeouts</strong></h3><p>Sometimes, runs that start but never finish silently consume resources until you manually intervene. Run monitoring catches them:</p><pre><code><span><span>run_monitoring:</span><span>\n</span></span><span><span>  </span><span>enabled:</span><span> </span><span>true</span><span>\n</span></span><span><span>  </span><span>max_runtime_seconds:</span><span> </span><span>7200</span><span>  </span><span># 2 hours</span><span>\n</span></span><span><span>  </span><span>start_timeout_seconds:</span><span> </span><span>180</span><span>\n</span></span><span><span>  </span><span>max_resume_run_attempts:</span><span> </span><span>3</span><span>\n</span></span><span></span></code></pre><p>Any run exceeding the max runtime gets marked as failed. You can override per job with the dagster/max_runtime tag, maybe your warehouse refresh gets 4 hours while API ingestion gets 10 minutes:</p><pre><code><span><span>@dg.job(</span><span>tags={</span><span>\"dagster/max_runtime\"</span><span>: </span><span>14400</span><span>}</span><span>)  </span><span># 4 hours</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>nightly_warehouse_refresh</span><span>():</span><span> ...\n</span></span><span>\n</span><span>asset_job = dg.define_asset_job(\n</span><span><span>    name=</span><span>\"api_ingestion\"</span><span>,\n</span></span><span><span>    selection=</span><span>\"*\"</span><span>,\n</span></span><span><span>    tags={</span><span>\"dagster/max_runtime\"</span><span>: </span><span>600</span><span>},  </span><span># 10 minutes</span><span>\n</span></span><span>)\n</span><span></span></code></pre><p>Dagster Insights helps you find the right limits by showing 99th percentile runtimes, so you can set tight but realistic guardrails based on actual performance data.</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/69b80d6bfb2c8c89445c153a_a8a668b7.png\"></p></figure><p>‍</p><p>The monitoring daemon can also detect crashed run workers (like evicted K8s pods) and automatically resume them. See<a target=\"_blank\" href=\"https://docs.dagster.io/deployment/execution/run-monitoring\"> run monitoring</a> for more.</p><h3><strong>Backfill Strategies</strong></h3><p>When you need to reprocess 100 days of data, Dagster gives you three strategies via BackfillPolicy:</p><div><table>\n  <thead>\n    <tr>\n      <th>Factor</th>\n      <th>One per partition</th>\n      <th>Batched</th>\n      <th>Single run</th>\n    </tr>\n  </thead>\n  <tbody>\n    <tr>\n      <td>Run overhead</td>\n      <td>High (N runs)</td>\n      <td>Medium (N/batch)</td>\n      <td>Low (1 run)</td>\n    </tr>\n    <tr>\n      <td>Fault isolation</td>\n      <td><span>Best</span></td>\n      <td><span>Moderate</span></td>\n      <td><span>None</span></td>\n    </tr>\n    <tr>\n      <td>Retry cost</td>\n      <td>1 partition</td>\n      <td>1 batch</td>\n      <td>All partitions</td>\n    </tr>\n    <tr>\n      <td>Best for</td>\n      <td>Unreliable sources, APIs</td>\n      <td>Initial backfills</td>\n      <td>Spark, warehouse queries</td>\n    </tr>\n  </tbody>\n</table></div><p>One line of config takes you from 100 runs to 10, and on Dagster+, that also means reduced credit usage since credits are counted per run:</p><pre><code><span><span>@dg.asset(</span><span>\n</span></span><span>    partitions_def=daily_partitions,\n</span><span><span>    backfill_policy=dg.BackfillPolicy.multi_run(</span><span>max_partitions_per_run=</span><span>10</span><span>),\n</span></span><span><span></span><span>)</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>daily_events</span><span>(</span><span>context: dg.AssetExecutionContext</span><span>):</span><span>\n</span></span><span>    ...\n</span><span></span></code></pre><p>See<a target=\"_blank\" href=\"https://docs.dagster.io/examples/mini-examples/partition-backfill-strategies\"> backfill strategies</a> for the full comparison.</p><p>Reliability gets your pipelines running. But the data has to be right, too. A pipeline that consistently delivers wrong data is arguably worse than one that fails loudly, because stakeholders lose trust without understanding why. It's much easier to tell someone \"the data is stale because we caught an issue\" than \"the data has been wrong for three days and we just noticed.\" Trust is easy to lose and hard to win back.</p><h3><strong>Asset Checks</strong></h3><p>Asset checks are data quality tests tied directly to your assets. They run after materialization and show up in the UI next to the asset they're checking:</p><pre><code><span><span>@dg.asset_check(</span><span>asset=orders, blocking=</span><span>True</span><span>)</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>orders_id_has_no_nulls</span><span>():</span><span>\n</span></span><span><span>    orders_df = pd.read_csv(</span><span>\"orders.csv\"</span><span>)\n</span></span><span><span>    num_null_order_ids = orders_df[</span><span>\"order_id\"</span><span>].isna().</span><span>sum</span><span>()\n</span></span><span><span>    </span><span>return</span><span> dg.AssetCheckResult(\n</span></span><span><span>        passed=</span><span>bool</span><span>(num_null_order_ids == </span><span>0</span><span>),\n</span></span><span>        severity=dg.AssetCheckSeverity.ERROR,\n</span><span><span>        metadata={</span><span>\"null_count\"</span><span>: </span><span>int</span><span>(num_null_order_ids)},\n</span></span><span>    )\n</span><span></span></code></pre><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/69b80d6bfb2c8c89445c1534_ab26c8b5.png\"></p></figure><p>Just a Python function that returns pass or fail. No new DSL, no separate framework. If you use dbt, your dbt tests automatically surface as asset checks with no extra code.</p><h3><strong>Severity Levels and Blocking</strong></h3><p>Not all quality issues are equal. Dagster handles this with <strong>severity</strong> and <strong>blocking</strong>:</p><ul><li><strong>WARN</strong> severity: The check fails but downstream assets still run. Something to investigate, not a showstopper.</li><li><strong>ERROR</strong> severity + blocking=True: Downstream assets are blocked from materializing. Bad data stops at the source.</li></ul><p>This is critical for trust. Instead of bad data flowing through your pipeline and surfacing in a dashboard days later, you catch it at the source. Stakeholders never see it.</p><p>When you have many checks use @multi_asset_check to define multiple checks in a single function:</p><pre><code><span><span>@dg.multi_asset_check(</span><span>\n</span></span><span>    specs=[\n</span><span><span>        dg.AssetCheckSpec(</span><span>name=</span><span>\"no_null_ids\"</span><span>, asset=</span><span>\"orders\"</span><span>),\n</span></span><span><span>        dg.AssetCheckSpec(</span><span>name=</span><span>\"no_null_items\"</span><span>, asset=</span><span>\"orders\"</span><span>),\n</span></span><span>    ]\n</span><span><span></span><span>)</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>orders_checks</span><span>() -&gt; Iterable[dg.AssetCheckResult]:</span><span>\n</span></span><span><span>    orders_df = pd.read_csv(</span><span>\"orders.csv\"</span><span>)\n</span></span><span><span>    </span><span>yield</span><span> dg.AssetCheckResult(\n</span></span><span><span>        check_name=</span><span>\"no_null_ids\"</span><span>,\n</span></span><span><span>        passed=</span><span>bool</span><span>(orders_df[</span><span>\"order_id\"</span><span>].isna().</span><span>sum</span><span>() == </span><span>0</span><span>),\n</span></span><span><span>        asset_key=</span><span>\"orders\"</span><span>,\n</span></span><span>    )\n</span><span><span>    </span><span>yield</span><span> dg.AssetCheckResult(\n</span></span><span><span>        check_name=</span><span>\"no_null_items\"</span><span>,\n</span></span><span><span>        passed=</span><span>bool</span><span>(orders_df[</span><span>\"item_id\"</span><span>].isna().</span><span>sum</span><span>() == </span><span>0</span><span>),\n</span></span><span><span>        asset_key=</span><span>\"orders\"</span><span>,\n</span></span><span>    )\n</span><span></span></code></pre><p>You can also use factory patterns to generate checks from configuration and attach metadata to track values over time to catch gradual data drift. See<a target=\"_blank\" href=\"https://docs.dagster.io/guides/test/asset-checks\"> asset checks</a> for the full API.</p><h2><strong>Visibility</strong></h2><p>Your pipelines are reliable, and your data quality is enforced. But if your team can't <em>see</em> any of this, it doesn't matter much. Visibility is what turns infrastructure into confidence — it's the difference between stakeholders trusting your data platform and Slacking you every morning to ask if the dashboard is fresh.</p><h3><strong>Saved Selections</strong></h3><p>When you've got hundreds of assets across multiple teams and code locations, trying to comprehend everything at once is overwhelming. Saved selections in Dagster+ let you filter your asset graph, save the view, and share it with your team.</p><pre><code><span><span>key:\"RAW_DATA/orders\"+ and not group:MARKETING\n</span></span><span></span></code></pre><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/69b80d6bfb2c8c89445c1537_0c2dc684.png\"></p></figure><p>Save a selection with a name and icon, make it public or private, and you get: a filtered asset list, a scoped lineage graph, real-time insights scoped to that selection, and configurable alert policies. You can set alerts to fire when any asset in the selection degrades, changes schema, or violates a freshness policy, and route them to Slack, email, or PagerDuty. The Insights metrics we'll cover next are also scoped to your selections, so if you're a pipeline owner, you see success rates and MTTR for <em>your</em> pipeline, not the entire platform.</p><p>Pin selections to your home page and every morning you see at a glance whether your core KPIs are healthy, degraded, or in a warning state. No digging through a global asset graph. No asking around on Slack.</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/69b80d6bfb2c8c89445c153d_2bf7a3cc.png\"></p></figure><p>So now you have tailored views for everyone who depends on data. Your analytics engineer sees their dbt models, your ML engineer sees their feature pipelines, your VP sees the KPIs.</p><h3><strong>Insights: The Metrics App Developers Have Had for Years</strong></h3><p>Application developers have had dashboards for uptime, latency, error rates, and MTTR for decades. Data teams? We've been flying blind, judging platform health by whether anyone complained on Slack.</p><p>Dagster+ Insights surfaces real-time operational metrics for your data platform:</p><ul><li><strong>Success rate</strong>: Percentage of materializations succeeding, with week-over-week trending.</li><li><strong>Freshness pass rate</strong>: Are assets meeting their freshness policies? The data equivalent of an uptime SLA.</li><li><strong>Time to resolution</strong>: Your MTTR — how long it takes to recover from failures. The metric that proves your reliability investments are working.</li><li><strong>Cost metrics</strong>: Snowflake and BigQuery spend attributed to specific assets and jobs.</li></ul><p>Insights also includes comparison tools that let you benchmark up to five saved selections side by side, useful for identifying which teams or pipelines need the most investment. Custom metrics let you surface any numeric metadata you emit on materializations (row counts, file sizes, processing durations) for historical aggregation, so you're not limited to built-in KPIs. And for teams with existing observability stacks, Insights data can be exported via GraphQL to Datadog, Grafana, or wherever your organization already tracks operational health. You can also integrate Snowflake and BigQuery cost data directly into Insights for cost attribution at the asset level.</p><p>For more, see the<a target=\"_blank\" href=\"https://docs.dagster.io/guides/observe/insights\"> Insights guide</a>.</p><h2><strong>Putting It All Together</strong></h2><p>DataOps is a practice. Start with the highest-impact change for your team:</p><ul><li><strong>Flaky pipelines?</strong> Retries and concurrency controls.</li><li><strong>Bad data reaching stakeholders?</strong> Blocking asset checks on critical assets.</li><li><strong>Backfills disrupting production?</strong> Run priority and tag concurrency limits.</li><li><strong>Team lacks visibility?</strong> Saved selections for pipeline owners.</li><li><strong>Need to prove platform health?</strong> Insights for success rate, freshness, and MTTR.</li></ul><p>Stakeholder trust is the most important currency a data team has, and it's asymmetric: it takes months to build and minutes to destroy. Every feature in this post either prevents trust from eroding (retries, checks, timeouts) or makes the current state of trust measurable (Insights, saved selections, alerts).</p><p>Dagster gives you the building blocks to adopt DataOps incrementally. The goal is making the reliable path the easy path.</p><p>‍</p></div>"
