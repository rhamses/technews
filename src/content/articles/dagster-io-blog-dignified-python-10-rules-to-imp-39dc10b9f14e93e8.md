contentHtml: "<div><h2>Dignified Python</h2><p>Modern LLMs are trained on an enormous and unruly mix of code: questionable StackOverflow snippets, half-finished projects, and hobbyist repositories. When agents generate code from that background, the results can be fast but unfocused. Even when you don’t fully defer to them, the constant cycle of nudging, correcting, and rewriting can make development feel fragmented rather than cohesive.</p><p>At Dagster, intent has always mattered. The platform was built so engineers never have to guess what a system is doing or why it behaves the way it does. As we’ve adopted agent-assisted development, we’ve seen the same need emerge in code generation. LLMs are excellent at reproducing patterns, but they rarely understand the principles that make a codebase feel deliberate and unified.</p><p>Python’s flexibility amplifies this problem. There are often many valid ways to solve the same problem, and without guidance an LLM will default to whichever pattern it has seen most often. The result is code that technically works, but feels inconsistent. And can lead to a codebase that feels like it is authors with very different philosophies.</p><p>To address this, we codified our opinions about how Python should be written into a set of rules we call Dignified Python. Rather than relying on post-hoc cleanup through reviews or rewrites, we load these rules directly into the model’s context from the start. This gives agents a clear sense of our standards, conventions, and design philosophy.</p><p>By encoding intent upfront, we get the speed benefits of LLMs without sacrificing the clarity and consistency that make a shared codebase feel like a single system.</p><h2>Why Intent Matters</h2><p>At Dagster we have strong opinions about how Python should be written. Historically we enforced these through linting and code reviews, but as agents have become more ingrained in our workflows we have codified a set of rules that we can supply directly as context when working with an agent. We refer to these rules as \"Dignified Python.\"</p><p>Python's flexibility is one of its greatest strengths, but that flexibility becomes a liability when agents are involved. There are often many valid ways to accomplish the same task, and without guidance an LLM will pick whichever pattern it has seen most frequently. The result is inconsistent code that feels like it was written by a dozen different people with a dozen different philosophies.</p><p>Being opinionated cuts through this. By defining clear guidelines and loading them into Claude's context, we have drastically accelerated our engineering velocity while maintaining the quality and consistency of our codebase. The key insight is that you must impart your expertise to the model. An LLM has no understanding of your team's conventions, your architectural decisions, or the hard-won lessons that shaped your codebase. By encoding that expertise into rules, you ensure the AI produces code that reflects your standards rather than generic patterns.</p><p>The goal of Dignified Python is not just to generate code that works, it is to generate code that communicates intent. That is where LLMs often fall short. Models are excellent at reproducing patterns, but far less adept at expressing the design principles behind them. Intent is not about choosing the right snippet; it is about applying a coherent philosophy for how Python should be used. Our rules ensure that the code produced by agents reflects that philosophy.</p><h2>Ten Rules from Our Claude Prompt</h2><p>Below are ten rules extracted from the prompt we supply to Claude Code. They reflect Dagster's engineering judgment about how Python should be written, and they are battle-tested against a large, actively maintained codebase. We share them here so you can adopt or adapt them for your own workflows. The goal is simple: impart your expertise to the model so its output reflects your team's standards, not generic patterns from its training data.</p><h3>1. Look Before You Leap</h3><p>The single most important rule in Dignified Python is to check conditions proactively rather than relying on exceptions for control flow. We call this Look Before You Leap (LBYL), in contrast to the Easier to Ask for Forgiveness than Permission (EAFP) pattern that many LLMs default to.</p><pre><code><span><span># WRONG: Exception as control flow</span><span>\n</span></span><span><span></span><span>try</span><span>:\n</span></span><span>    value = mapping[key]\n</span><span>    process(value)\n</span><span><span></span><span>except</span><span> KeyError:\n</span></span><span><span>    </span><span>pass</span><span>\n</span></span><span>\n</span><span><span></span><span># CORRECT: Check first</span><span>\n</span></span><span><span></span><span>if</span><span> key </span><span>in</span><span> mapping:\n</span></span><span>    value = mapping[key]\n</span><span>    process(value)</span></code></pre><p>LBYL makes intent explicit. The reader can see immediately what conditions are being checked and what happens in each case. EAFP obscures this by burying the logic inside exception handlers.</p><p>Exceptions are still acceptable at error boundaries, when interacting with third-party APIs that provide no alternative, or when adding context before re-raising. A good example is interacting with external services where we lack control over the underlying behavior:</p><pre><code><span><span># ACCEPTABLE: Third-party API forces exception handling</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>_get_bigquery_sample</span><span>(</span><span>sql_client, table_name</span><span>):</span><span>\n</span></span><span><span>    </span><span>\"\"\"\n</span></span><span>    BigQuery's TABLESAMPLE doesn't work on views.\n</span><span>    There's no reliable way to determine a priori whether\n</span><span>    a table supports TABLESAMPLE.\n</span><span><span>    \"\"\"</span><span>\n</span></span><span><span>    </span><span>try</span><span>:\n</span></span><span><span>        </span><span>return</span><span> sql_client.run_query(</span><span>f\"SELECT * FROM </span><span>{table_name}</span><span> TABLESAMPLE...\"</span><span>)\n</span></span><span><span>    </span><span>except</span><span> Exception:\n</span></span><span><span>        </span><span>return</span><span> sql_client.run_query(</span><span>f\"SELECT * FROM </span><span>{table_name}</span><span> ORDER BY RAND()...\"</span><span>)</span></span></code></pre><h3>2. Never Swallow Exceptions</h3><p>A common issue that arises from LLM pattern matching is silent error swallowing. Many models overuse broad try and except blocks, and one of the most problematic variants is catching every exception and ignoring it entirely.</p><pre><code><span><span># WRONG: Silent exception swallowing</span><span>\n</span></span><span><span></span><span>try</span><span>:\n</span></span><span>    risky_operation()\n</span><span><span></span><span>except</span><span>:\n</span></span><span><span>    </span><span>pass</span><span>\n</span></span><span>\n</span><span><span></span><span># CORRECT: Let exceptions bubble up</span><span>\n</span></span><span>risky_operation()</span></code></pre><p><code>‍<br></code>Although the first version will run, it hides failures that may be critical to the correctness of your system. Debugging issues introduced by swallowed exceptions can be extremely difficult since the original error is lost and the failure often surfaces far away from the root cause. The Python community has long discussed restricting or discouraging bare except clauses, as seen in proposals like <a target=\"_blank\" href=\"https://peps.python.org/pep-0760/\">PEP 760</a>.</p><p>Dignified Python encourages code that is explicit. If an operation can fail in a meaningful way, that failure should be visible and actionable. That means allowing exceptions to propagate naturally unless there is a compelling and clearly defined reason to handle them.</p><h3>3. Magic Methods Must Be O(1)</h3><p>Performance is an area where agents often fall short. LLMs tend to focus on producing code that works, not code that is efficient. Without explicit guidance, they may introduce subtle performance issues that only become visible once the code is used at scale.</p><p>Magic methods <strong>like__l</strong>en__, <strong>__bool__</strong>, and <strong>__contains__</strong> are called frequently and implicitly. They must run in constant time.</p><pre><code><span><span># WRONG: __len__ doing iteration</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>__len__</span><span>(</span><span>self</span><span>) -&gt; </span><span>int</span><span>:</span><span>\n</span></span><span><span>    </span><span>return</span><span> </span><span>sum</span><span>(</span><span>1</span><span> </span><span>for</span><span> _ </span><span>in</span><span> self._items)\n</span></span><span>\n</span><span><span></span><span># CORRECT: O(1) __len__</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>__len__</span><span>(</span><span>self</span><span>) -&gt; </span><span>int</span><span>:</span><span>\n</span></span><span><span>    </span><span>return</span><span> self._count</span></span></code></pre><p><code>‍<br></code>The first implementation is correct but inefficient. Each call requires iterating over the entire collection, which can introduce significant overhead when used in loops, conditionals, or membership checks. The same rule applies to properties, which should never perform I/O or expensive computation.</p><h3>4. Check Existence Before Resolution</h3><p>When working with pathlib, LLMs often forget that certain methods can fail on non-existent paths. The rule is simple: always check <strong>.exists()</strong> before calling <strong>.resolve()</strong> or <strong>.is_relative_to()</strong>.</p><pre><code><span><span>from</span><span> pathlib </span><span>import</span><span> Path\n</span></span><span>\n</span><span><span></span><span># WRONG: resolve() can raise OSError on non-existent paths</span><span>\n</span></span><span>wt_path_resolved = wt_path.resolve()\n</span><span><span></span><span>if</span><span> current_dir.is_relative_to(wt_path_resolved):\n</span></span><span>    current_worktree = wt_path_resolved\n</span><span>\n</span><span><span></span><span># CORRECT: Check exists() first</span><span>\n</span></span><span><span></span><span>if</span><span> wt_path.exists():\n</span></span><span>    wt_path_resolved = wt_path.resolve()\n</span><span><span>    </span><span>if</span><span> current_dir.is_relative_to(wt_path_resolved):\n</span></span><span>        current_worktree = wt_path_resolved</span></code></pre><p><code>‍</code>This follows directly from the LBYL principle. Instead of catching exceptions after the fact, we verify preconditions before calling methods that might fail.</p><h3>5. Defer Import-Time Computation</h3><p>Module-level code runs when the module is imported. Side effects at import time cause slower startup, test brittleness, circular import issues, and unpredictable behavior based on import order.</p><pre><code><span><span>from</span><span> pathlib </span><span>import</span><span> Path\n</span></span><span><span></span><span>from</span><span> functools </span><span>import</span><span> cache\n</span></span><span>\n</span><span><span></span><span># WRONG: Path computed at import time</span><span>\n</span></span><span><span>SESSION_FILE = Path(</span><span>\"scratch/current-session-id\"</span><span>)\n</span></span><span>\n</span><span><span></span><span># CORRECT: Defer with @cache</span><span>\n</span></span><span><span></span><span>@cache</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>_session_file_path</span><span>() -&gt; Path:</span><span>\n</span></span><span><span>    </span><span>\"\"\"Return path to session ID file (cached after first call).\"\"\"</span><span>\n</span></span><span><span>    </span><span>return</span><span> Path(</span><span>\"scratch/current-session-id\"</span><span>)</span></span></code></pre><p><code>‍<br></code>The <strong>@cache</strong> decorator ensures the computation happens only once, but not until the function is first called. This pattern works for any resource initialization: configuration loading, database connections, or path construction.</p><h3>6. Verify Your Casts at Runtime</h3><p><strong>typing.cast()</strong> is a compile-time only construct. It tells the type checker to trust you but performs no runtime verification. If your assumption is wrong, you will get silent misbehavior instead of a clear error.</p><pre><code><span><span>from</span><span> typing </span><span>import</span><span> Any, cast\n</span></span><span><span></span><span>from</span><span> collections.abc </span><span>import</span><span> MutableMapping\n</span></span><span>\n</span><span># WRONG: Blind cast\n</span><span><span>cast(dict[str, Any], doc)[</span><span>\"key\"</span><span>] = value\n</span></span><span>\n</span><span># CORRECT: Assert before cast\n</span><span><span>assert isinstance(doc, MutableMapping), f</span><span>\"Expected MutableMapping, got {type(doc)}\"</span><span>\n</span></span><span><span>cast(dict[str, Any], doc)[</span><span>\"key\"</span><span>] = value</span></span></code></pre><p><code>‍<br></code>When the cost of the assertion is trivial (O(1) checks like <strong>isinstance</strong>), always add it. Skip the assertion only when you have just performed a type guard, or in measured performance-critical hot paths with documented justification.</p><h3>7. Use Literal Types for Fixed Values</h3><p>When strings represent a fixed set of valid values, such as error codes, status values, or command types, model them in the type system using <strong>Literal</strong>. This catches typos at type-check time, enables IDE autocomplete, and documents valid values directly in the code.</p><pre><code><span><span>from</span><span> typing </span><span>import</span><span> </span><span>Literal</span><span>\n</span></span><span><span></span><span>from</span><span> dataclasses </span><span>import</span><span> dataclass\n</span></span><span>\n</span><span><span></span><span># WRONG: Bare strings</span><span>\n</span></span><span><span>issues.append((</span><span>\"orphen-state\"</span><span>, </span><span>\"desc\"</span><span>))  </span><span># Typo goes unnoticed!</span><span>\n</span></span><span>\n</span><span><span></span><span># CORRECT: Literal type</span><span>\n</span></span><span><span>IssueCode = </span><span>Literal</span><span>[</span><span>\"orphan-state\"</span><span>, </span><span>\"orphan-dir\"</span><span>, </span><span>\"missing-branch\"</span><span>]\n</span></span><span>\n</span><span><span></span><span>@dataclass(</span><span>frozen=</span><span>True</span><span>)</span><span>\n</span></span><span><span></span><span>class</span><span> </span><span>Issue</span><span>:</span><span>\n</span></span><span>    code: IssueCode\n</span><span><span>    message: </span><span>str</span><span>\n</span></span><span>\n</span><span><span>issues.append(Issue(code=</span><span>\"orphan-state\"</span><span>, message=</span><span>\"desc\"</span><span>))  </span><span># Type-checked!</span></span></code></pre><p><code>‍<br></code>Before using a bare <strong>str</strong> type, ask: Is this string compared with <strong>==</strong> or <strong>in</strong> anywhere? Is there a fixed set of valid values? Would a typo cause a bug? If any answer is yes, use <strong>Literal</strong> instead.</p><h3>8. Declare Variables Close to Use</h3><p>Variables should be declared as close as possible to where they are used. Avoid early declarations that pollute scope and obscure data flow.</p><pre><code><span><span># WRONG: Variable declared 20 lines before use</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>process_data</span><span>(</span><span>ctx, items</span><span>):</span><span>\n</span></span><span>    result_path = compute_result_path(ctx)\n</span><span><span>    </span><span># ... 20 lines of other logic ...</span><span>\n</span></span><span>    save_to_path(transformed, result_path)\n</span><span>\n</span><span><span></span><span># CORRECT: Inline at call site</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>process_data</span><span>(</span><span>ctx, items</span><span>):</span><span>\n</span></span><span><span>    </span><span># ... other logic ...</span><span>\n</span></span><span>    save_to_path(transformed, compute_result_path(ctx))</span></code></pre><p><code>‍<br></code>This reduces cognitive load because readers do not need to scroll back to understand where a value came from. It also makes data flow visible at a glance. The exception is when a value is used multiple times or when inlining would hurt readability.</p><h3>9. Keyword Arguments for Complex Functions</h3><p>Functions with five or more parameters must use keyword-only arguments. Use the <strong>*</strong> separator after the first positional parameter to enforce this at the language level.</p><pre><code><span><span># WRONG: Positional chaos - what do these values mean?</span><span>\n</span></span><span><span>response = fetch_data(api_url, </span><span>30.0</span><span>, </span><span>3</span><span>, {</span><span>\"Accept\"</span><span>: </span><span>\"application/json\"</span><span>}, token)\n</span></span><span>\n</span><span><span></span><span># CORRECT: Keyword-only after first param</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>fetch_data</span><span>(</span><span>\n</span></span><span>    url,\n</span><span>    *,\n</span><span><span>    timeout: </span><span>float</span><span>,\n</span></span><span><span>    retries: </span><span>int</span><span>,\n</span></span><span><span>    headers: </span><span>dict</span><span>[</span><span>str</span><span>, </span><span>str</span><span>],\n</span></span><span><span>    auth_token: </span><span>str</span><span>,\n</span></span><span><span></span><span>) -&gt; Response:</span><span>\n</span></span><span>    ...\n</span><span>\n</span><span><span></span><span># Call site is self-documenting</span><span>\n</span></span><span>response = fetch_data(\n</span><span>    api_url,\n</span><span><span>    timeout=</span><span>30.0</span><span>,\n</span></span><span><span>    retries=</span><span>3</span><span>,\n</span></span><span><span>    headers={</span><span>\"Accept\"</span><span>: </span><span>\"application/json\"</span><span>},\n</span></span><span>    auth_token=token,\n</span><span>)</span></code></pre><p><code>‍<br></code>This improves call-site readability by forcing explicit parameter names. The first parameter (often <strong>self</strong>, <strong>ctx</strong>, or the primary subject of the function) can remain positional.</p><h3>10. Default Values Are Dangerous</h3><p>Avoid default parameter values unless absolutely necessary. They are a significant source of bugs because callers forget to pass a parameter and get unexpected results.</p><pre><code><span><span># DANGEROUS: Caller forgets encoding, gets wrong behavior</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>process_file</span><span>(</span><span>path: Path, encoding: </span><span>str</span><span> = </span><span>\"utf-8\"</span><span>) -&gt; </span><span>str</span><span>:</span><span>\n</span></span><span><span>    </span><span>return</span><span> path.read_text(encoding=encoding)\n</span></span><span>\n</span><span><span>content = process_file(legacy_latin1_file)  </span><span># Bug: should be encoding=\"latin-1\"</span><span>\n</span></span><span>\n</span><span><span></span><span># SAFER: Require explicit choice</span><span>\n</span></span><span><span></span><span>def</span><span> </span><span>process_file</span><span>(</span><span>path: Path, encoding: </span><span>str</span><span>) -&gt; </span><span>str</span><span>:</span><span>\n</span></span><span><span>    </span><span>return</span><span> path.read_text(encoding=encoding)\n</span></span><span>\n</span><span><span>content = process_file(legacy_latin1_file, encoding=</span><span>\"latin-1\"</span><span>)</span></span></code></pre><p><code>‍<br></code>When a default value is never overridden anywhere in your codebase, eliminate the parameter entirely or hardcode the value. Acceptable uses of defaults include truly optional behavior where the default is correct for 95%+ of callers, or temporary backwards compatibility when adding parameters to existing APIs.</p><h2>Build with Us</h2><p>Want to copy and paste the full set of rules?
