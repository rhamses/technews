contentHtml: "<div><p>Modern data pipelines are often responsible for applying consistent computations to diverse batches of data. For example, every time a file arrives in a directory, you might need to <a target=\"_blank\" href=\"https://dagster.io/glossary/data-parsing\">parse</a> it and build a dataset of statistics derived from it.</p><p>When working with small numbers of data assets, you can understand their <a target=\"_blank\" href=\"https://dagster.io/glossary/data-lineage\">lineage</a> and discern which are up to date. But what happens when you need to process thousands of data entries from different sources? If a single data entry is corrupted, you don’t want to have to regenerate all of your data outputs. Or if you receive new data entries, how do you recognize which ones are duplicates you’ve already processed?</p><p>In this post, we will explore Dynamic Partitioning in data pipelines, a strategy for enabling a single pipeline to process items selectively from a data collection, rather than managing a different parallel pipeline for each data asset in the collection. We developed this feature in response to feedback that users liked our declarative asset model, but found it restrictive in common situations. We believe this solution offers the best of both worlds, with both flexibility and declarative data management capabilities.</p><p>If you were looking for a broader explanation and examples of partitioning, we recommend Sandy Ryza’s recent blog post “<a target=\"_blank\" href=\"https://dagster.io/blog/partitioned-data-pipelines\">Partitions in Data Pipelines</a>” and his article \"<a target=\"_blank\" href=\"https://dagster.io/blog/backfills-in-ml\">Backfills in Data &amp; Machine Learning: A Primer</a>.\"</p><h2>Declaratively Defining Partitions: Unlocking Granular Control</h2><p>The idea behind partitioning is that a data asset can correspond to a collection of partitions that are tracked and computed independently. Typically, each partition corresponds to a separate file, or a slice of a table in a database.</p><p>Building your data pipeline with partitions enables your pipeline to (a) track the full set of partitions and (b) operate on subsets of your data. In doing so, you unlock granular control over your pipeline.</p><h3>Declaratively define a new partition</h3><p>Say you have a data pipeline responsible for processing a collection of files in a directory. If you declaratively define a new partition in your data pipeline for each file in your folder:</p><ul><li>You can detect when new files exist and kick off processing for just these files without re-processing past files.</li><li>If certain files contained corrupted data, you can reprocess just the affected files.</li><li>If there was an error in your processing logic, you can run a backfill that re-processes all your files.</li></ul><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686706596cff32d6ff1d703c_684849809a1580256d38241e_image.png\"></p></figure><p>Prior to <a target=\"_blank\" href=\"https://dagster.io/blog/dagster-1-2-formation\">Dagster 1.2</a>, Dagster had support for partitioned data pipelines where the set of partitions was known up-front. In code, you could either say something like “create a partition for every hour” or “here’s a list of partitions”.</p><p>However, you don’t always know the set of partitions up-front. Consider the following situations:</p><ul><li>Unknown arrivals: you want to process each file in a bucket, but you don’t know what files will arrive or when they will arrive.</li><li>Ad-hoc parameters: you have an <a target=\"_blank\" href=\"https://dagster.io/blog/dagster-ml-pipelines\">ML pipeline</a>, but you don’t know which hyper-parameters will be used in the future to generate ad-hoc models.</li></ul><p>In the next sections we’ll explore how Dagster can represent these unknown partition spaces while still providing the observability and control that declarative data management offers.</p><h2>Dagster's Solution: Dynamic Partitions</h2><p>In Dagster, a data collection where each element is produced by the same computation can be <a target=\"_blank\" href=\"https://dagster.io/glossary/data-modeling\">modeled</a> as a <strong>partitioned asset</strong>. When the partition space is unknown at definition time, you can represent this as a <strong>dynamically</strong> partitioned asset. For these assets, partitions can be added and removed dynamically, via code or the UI.</p><p>Modeling each data output as a partition, as opposed to its own data asset, ensures that even with thousands of items in your data collection, the data lineage remains clear and digestible.</p><p>If you were to represent each of these partitions as its own asset, then the <a href=\"https://docs.dagster.io/etl-pipeline-tutorial/building-an-asset-graph\" target=\"_blank\">asset graph</a> would get overwhelmingly (and unnecessarily) complex, and it would be difficult to operate on many partitions at once.</p><h3>A birds eye view of your data pipeline</h3><p>Using the asset graph view, you can observe the status of each object in your data pipeline at a high level. Because each element in your data collection is represented as a partition, you can easily identify which new partitions exist and require processing.</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686706596cff32d6ff1d7045_6848499a9a1580256d382e6f_image.png\"></p></figure><h3>Troubleshoot bugs</h3><p>You can easily spot corrupted partitions that might be causing an error. And for those specific partitions, you can deep-dive and see logs for the run that errored, or what data was generated in the past:</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686706596cff32d6ff1d703f_684849a465d34ccdc89323dd_image.png\"></p></figure><h3>Backfills</h3><p>If you update the logic in your shared computation, you’ll want to ensure that all partitions are re-processed with the updated logic. With just one action, you can backfill across all partitions:</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686706596cff32d6ff1d7042_684849c3e738b824f11a4762_image.png\"></p></figure><h2>Track execution progress</h2><p>Then, you can view a condensed view of which partitions have succeeded, failed, or are still in-progress:</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686706596cff32d6ff1d7039_684849c3e738b824f11a475f_image.png\"></p></figure><h3>How can you use a dynamic partition?</h3><p>A common pattern in data pipelines is detecting new files as they land in a bucket, processing them, and producing output files. Here’s an example of how you can implement this incremental update approach in Dagster through a sensor:</p><div><pre><code>from dagster import (\n   DynamicPartitionsDefinition,\n   asset,\n   sensor,\n   SensorResult,\n   RunRequest,\n   AssetSelection,\n)\nfiles_partitions_def = DynamicPartitionsDefinition(name=\"files\")\n@asset(partitions_def=files_partitions_def)\ndef files_metadata():\n   ...\n@asset(partitions_def=files_partitions_def)\ndef processed_files(files_metadata):\n   ...\n@asset(partitions_def=files_partitions_def)\ndef compressed_files(processed_files):\n   ...\n@sensor(\n   asset_selection=AssetSelection.keys(\n       files_metadata.key, processed_files.key, compressed_files.key\n   )\n)\ndef file_sensor(context):\n    new_files = [\n        filename\n        for filename in os.listdir(os.getenv(\"MY_DIRECTORY\"))\n        if not context.instance.has_dynamic_partition(\n            files_partitions_def.name, filename\n        )\n    ]\n    return SensorResult(\n        run_requests=[\n            RunRequest(partition_key=filename) for filename in new_files\n        ],\n        dynamic_partitions_requests=[\n            files_partitions_def.build_add_request(new_files)\n        ],\n    )</code></pre></div><p>‍</p><p>With this <code>file_sensor()</code> sensor, you can detect when new files are added to the folder and kick off runs to process just those new files. Scoping the execution of each run to just one partition via Dagster’s system ensures you can incrementally load new partitions instead of reading the entire bucket.</p><p>Then, in the UI, you can observe which new partitions were added (as a result of the new file being added), as well as any runs that were kicked off to process these partitions. This gives you a condensed view of the history of your data collection, and the actions taken to process new elements.</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686706596cff32d6ff1d7048_684849c3e738b824f11a475c_image.png\"></p></figure><h3>Conclusion</h3><p>Data engineers are challenged to manage diverse data collections with thousands of files or tables. Declaratively defining these collections as partitioned assets in Dagster offers granular control, high-level observability, efficient backfilling, and simplified incremental updates. Dynamically partitioned assets enable you to leverage these benefits even for an unknown partition space.</p><p>Even if your data pipeline processes a data collection containing thousands of items, dynamic partitioning will allow you to &#160;say goodbye to the complexity of a sprawling data lineage, and hello to a single pane of glass for managing and observing your assets.</p><p>For the reference documentation on dynamic partitioning, please see <a href=\"https://docs.dagster.io/guides/build/partitions-and-backfills#dynamically-partitioned-assets\" target=\"_blank\">Partitioned assets and jobs</a>.</p></div>"
