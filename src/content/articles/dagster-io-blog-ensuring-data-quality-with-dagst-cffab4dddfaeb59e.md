contentHtml: "<div><p>One of the most important considerations when building a data pipeline is ensuring that the data assets it produces are reliable, up-to-date, and trustworthy.</p><p>To that end, we strongly believe that <a target=\"_blank\" href=\"https://dagster.io/blog/ensuring-reliable-data-dagster-plus\">data quality should be natively integrated into the data orchestrator</a>, which not only ensures that the data orchestrator is the single pane of glass for your data assets but also allows the orchestrator to stop erroneous data from being propagated downstream to stakeholder-facing products, such as dashboards and reports.</p><p>While <a target=\"_blank\" href=\"https://dagster.io/blog/ensuring-reliable-data-dagster-plus\">Asset Checks</a> enable exactly this, you may often find yourself having to write a lot of custom logic and boilerplate code to codify the expectations you have of your data.</p><p>In this piece, we'll demonstrate &#160;how you can combine Great Expectations' extensive suite of data quality tests with Dagster's Asset Checks to improve the reliability of your data pipelines without having to write custom logic for testing your data.</p><p>The full code for this walkthrough can be found <a href=\"https://github.com/mjkanji/dagster-ge-demo.git\" target=\"_blank\">here</a>.</p><h2>Setup</h2><p>To start off, we recommend cloning the <a href=\"https://github.com/mjkanji/dagster-ge-demo\" target=\"_blank\">demo repo</a> to your computer and then install it as a package using pip. This will install Dagster, Great Expectations, and all the other dependencies you’ll need to follow along. We’d also recommend <a target=\"_blank\" href=\"https://dagster.io/blog/python-packages-primer-2#virtual-environments-aka-venvs\">creating a new virtual environment</a> before doing so.</p><div><pre><code>### Clone the repo and cd into the directory\ngit clone https://github.com/mjkanji/dagster-ge-demo.git\ncd dagster-ge-demo\n### Install the package\npip install -e \".[dev]\"</code></pre></div><pre></pre><p>Next, we’ll define a simple asset that fetches the infamous Titanic dataset from the internet, reads it using Pandas, and then writes it to disk as a CSV file.</p><div><pre><code>@asset\ndef titanic():\n    titanic_df = pd.read_csv(\n        \"https://github.com/datasciencedojo/datasets/raw/master/titanic.csv\"\n    )\n    titanic_df.to_csv(\"titanic.csv\", index=False)</code></pre></div><pre></pre><p>Since we’re fetching this data from the internet, it’s possible that the source file may change without our knowledge. To ensure that the materialized asset aligns with our expectations, we may want to codify some expectations about the data.</p><p>For example, we may expect that the Survived column (which indicates if a passenger survived):</p><ul><li>has no null values; and</li><li>that all of its values are either 0 or 1.</li></ul><p>We can use Dagster’s Asset Checks feature to codify these expectations. An example implementation for the first test is shown below. Since we want to ensure that <a href=\"https://docs.dagster.io/guides/test/asset-checksdefine-execute-asset-checks#blocking-downstream-assets\" target=\"_blank\">downstream assets are not materialized if our source contains potentially erroneous data</a>, we’ll also set blocking=True.</p><div><pre><code>@asset_check(asset=titanic, blocking=True)\ndef target_has_no_nulls(context: AssetCheckExecutionContext):\n    titanic_df = pd.read_csv(\"titanic.csv\")\n    num_null_survivednull_count = titanic_df[\"Survived\"].isna().sum()\n    return AssetCheckResult(\n        passed=bool(num_null_survived == 0),\n        severity=AssetCheckSeverity.ERROR,\n        metadata={\n            \"null_count\": int(num_null_survived),\n        },\n    )</code></pre></div><pre></pre><p>Please see <a href=\"https://docs.dagster.io/guides/test/asset-checks\" target=\"_blank\">the docs on Asset Checks</a> for a detailed breakdown of the Asset Checks API.</p><p>In this case, we’re defining the logic for the check by ourselves and also using <a href=\"https://docs.dagster.io/guides/build/assets/metadata-and-tags\" target=\"_blank\">Dagster’s robust metadata logging capabilities</a> to keep track of how the number of null values changes over time.</p><p>While this is a simple test, defining custom logic for every single expectation we have for every asset we create can easily get tedious and substantially increase the amount of code we may have to write and maintain. For large data pipelines, it may even require building utility functions and abstractions to reduce the duplication of code for similar patterns and types of tests, adding even more work to the data team’s docket.</p><h3>Great Expectations to the Rescue</h3><p>Thankfully, the team at <a href=\"https://greatexpectations.io/\" target=\"_blank\">Great Expectations</a> (GX) have already built an extensive suite of expectations for data quality checks (with a large number of additional checks implemented by the community) that we can build on top of, allowing us to focus on simply defining our expectations, without having to build the underlying implementation.</p><p>Before we rewrite the above test to use Great Expectations, let’s go over the GreatExpectationsResource, a simple resource that allows us to avoid having to duplicate some GX-related boilerplate in our asset checks:</p><div><pre><code>class GreatExpectationsResource(ConfigurableResource):\n    def get_validator(self, asset_df: pd.DataFrame):\n        project_config = DataContextConfig(\n            store_backend_defaults=InMemoryStoreBackendDefaults()\n        )\n        data_context = EphemeralDataContext(project_config=project_config)\n        data_source = data_context.sources.add_pandas(name=\"my_pandas_datasource\")\n        asset_name = \"asset_check_df\"\n        suite_name = \"asset_check_expectation_suite\"\n        data_asset = data_source.add_dataframe_asset(name=asset_name)\n        batch_request = data_asset.build_batch_request(dataframe=asset_df)\n        data_context.add_or_update_expectation_suite(suite_name)\n        validator = data_context.get_validator(\n            batch_request=batch_request, expectation_suite_name=suite_name\n        )\n        return validator</code></pre></div><pre></pre><p>Of note here is the fact that while GX has a rich ecosystem of abstractions for reading data from multiple sources, defining a re-usable set of expectations, and persisting GX-related configuration and validation results, we are opting to forego many of these features in favor of a simpler setup.</p><p>As such, we’re using an <a href=\"https://docs.greatexpectations.io/docs/oss/guides/setup/configuring_data_contexts/instantiating_data_contexts/instantiate_data_context#ephemeral\" target=\"_blank\">Ephemeral Data Context</a> and <a href=\"https://docs.greatexpectations.io/docs/oss/guides/connecting_to_your_data/fluent/in_memory/connect_in_memory_data\" target=\"_blank\">reading the data from memory</a> as a Pandas data frame (instead of using a GX data source). This is very similar to <a href=\"https://docs.greatexpectations.io/docs/oss/guides/expectations/how_to_create_and_edit_expectations_with_instant_feedback_from_a_sample_batch_of_data\" target=\"_blank\">using Great Expectations interactively</a>, while we rely on Dagster’s metadata logging to persist any important information (such as the validation results and related metadata).</p><p>Users with a deeper investment in GX or those wishing to use GX Cloud alongside Dagster may need to customize the setup to make use of GX’s more advanced features.</p><div><pre><code>@asset_check(asset=titanic, blocking=True)\ndef ge_target_has_no_nulls(\n    context: AssetCheckExecutionContext, ge_resource: GreatExpectationsResource\n):\n    titanic_df = pd.read_csv(\"titanic.csv\")\n    validator = ge_resource.get_validator(titanic_df)\n    validation_result = validator.expect_column_values_to_not_be_null(column=\"Survived\")\n    return AssetCheckResult(\n        passed=validation_result.success,\n        severity=AssetCheckSeverity.ERROR,\n        metadata=validation_result.result,\n    )</code></pre></div><p>Next, let’s look at how we can rewrite the Asset Check from before using a GX expectation:</p><pre></pre><p>Note that instead of defining the implementation for the null check ourselves, we’re using the expect_column_values_to_not_be_null method from Great Expectations.</p><p>We additionally use the ExpectationValidationResult.success attribute to determine if the check passed and pass this along to the AssetCheckResult. We also use the ExpectationValidationResult.result variable to log metadata, such as the number of rows that failed the test. This is a dictionary with metadata about the expectation; for example:</p><div><pre><code>{\n    'element_count': 891,\n    'unexpected_count': 0,\n    'unexpected_percent': 0.0,\n    'partial_unexpected_list': []\n}</code></pre></div><pre></pre><p>In this case, GX has tested 891 rows and none of the rows failed the test.</p><p>By capturing this information using Dagster, we can have a log of any changes over time. And Dagster will also automatically visualize this metadata for you in the Plots section of the Asset Check’s details (or Dagster Insights, if you’re using Dagster+).</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686619d1dc6482e76ceafd1e_6839c6d46d311c23c3029018_image.png\"></p></figure><p>For example, in the screenshot above, we can see that the last materialization had 112 rows which did not meet our expectations, allowing us to quickly identify anomalous events and debug them accordingly.</p><h3>Defining Multiple Expectations</h3><p>Recall that we had other expectations that we wanted to test. While we could simply replicate the above example and replace the validation_result definition to use a different expectation, this would be a rather verbose solution with a lot of code duplication.</p><p>Below, we’ll show two patterns you can use to quickly and succinctly define asset checks for multiple GX expectations.</p><h4>Using the multi_asset_check</h4><p>The first option is to use the multi_asset_check decorator; this allows you to define multiple checks using a single op/function. An example of this, with checks for both of our expectations, is shown below:</p><div><pre><code>@multi_asset_check(\n    specs=[\n        AssetCheckSpec(name=\"multicheck_target_has_no_nulls\", asset=titanic),\n        AssetCheckSpec(name=\"multicheck_target_has_valid_values\", asset=titanic),\n    ]\n)\ndef ge_multiple_checks(\n    context: AssetCheckExecutionContext, ge_resource: GreatExpectationsResource\n):\n    titanic_df = pd.read_csv(\"titanic.csv\")\n    validator = ge_resource.get_validator(titanic_df)\n    validation_result = validator.expect_column_values_to_not_be_null(column=\"Survived\")\n    yield AssetCheckResult(\n        passed=validation_result.success,\n        severity=AssetCheckSeverity.ERROR,\n        metadata=validation_result.result,\n        check_name=\"multicheck_target_has_no_nulls\",\n    )\n    validation_result = validator.expect_column_values_to_be_in_set(\n        column=\"Survived\", value_set={0, 1}\n    )\n    yield AssetCheckResult(\n        passed=validation_result.success,\n        severity=AssetCheckSeverity.ERROR,\n        metadata=validation_result.result,\n        check_name=\"multicheck_target_has_valid_values\",\n    )</code></pre></div><pre></pre><p>In this way, you can create a single op for each asset and then define and yield each of the expectations sequentially.</p><h4>Using the Factory Pattern to Generate Asset Checks with GX Expectations</h4><p>Alternatively, you can use the <a target=\"_blank\" href=\"https://dagster.io/blog/python-factory-patterns\">factory pattern</a> to further reduce the boilerplate for yielding individual AssetCheckResult objects by automatically generating the asset checks from a common specification. Thankfully, Great Expectations <a href=\"https://docs.greatexpectations.io/docs/reference/api/core/expectationconfiguration_class/\" target=\"_blank\">already has a ExpectationConfiguration class</a> that’s perfect for this job.</p><p>Our common format for the specs will be a dictionary that maps the names of the asset checks (i.e., what’s passed to the name argument of the @asset_check decorator) to their corresponding ExpectationConfiguration. For our two tests from earlier, the specs would be as follows:</p><div><pre><code>specs = {\n    \"factory_target_has_no_nulls\": ExpectationConfiguration(\n        expectation_type=\"expect_column_values_to_not_be_null\",\n        kwargs={\"column\": \"Survived\"},\n    ),\n    \"factory_target_has_valid_values\": ExpectationConfiguration(\n        expectation_type=\"expect_column_values_to_be_in_set\",\n        kwargs={\"column\": \"Survived\", \"value_set\": {0, 1}},\n    ),\n}\n</code></pre></div><pre></pre><p>You can find a wider array of tests in the <a href=\"https://greatexpectations.io/expectations/\" target=\"_blank\">Expectations Gallery</a> on the GX website, alongside the arguments each test requires.</p><p>Next, we define a factory for generating the asset checks from these specs as follows:</p><div><pre><code>def make_ge_asset_check(\n    expectation_name: str,\n    expectation_config: ExpectationConfiguration,\n    asset: CoercibleToAssetKey | AssetsDefinition | SourceAsset,\n):\n    @asset_check(\n        asset=asset,\n        name=expectation_name,\n        blocking=True,\n        compute_kind=\"great_expectations\",\n    )\n    def _asset_check(\n        context: AssetCheckExecutionContext, ge_resource: GreatExpectationsResource\n    ):\n        titanic_df = pd.read_csv(\"titanic.csv\")\n        validator = ge_resource.get_validator(titanic_df)\n        validation_result = expectation_config.validate(validator)\n        return AssetCheckResult(\n            passed=validation_result.success,  # type: ignore\n            severity=AssetCheckSeverity.ERROR,\n            metadata=validation_result.result,\n        )\n    return _asset_check</code></pre></div><pre></pre><p>And defining our asset checks is then reduced to a simple list comprehension:</p><div><pre><code>titanic_checks = [*make_ge_asset_check*(k, v, *titanic*) for k, v in specs.*items*()]\n</code></pre></div><pre></pre><p>Adding new expectations to our asset is now as simple as adding a new ExpectationConfiguration to the specs dictionary, making the code significantly less verbose.</p><p>We can also define checks for other assets by creating a new specs dictionary for each asset.</p><h3>Conclusion</h3><p>Dagster’s Asset Checks are a great tool for ensuring the reliability of your data and stopping malformed or erroneous data from flowing downstream.</p><p>Using them alongside Great Expectations’ expansive library of expectations works incredibly well and can help you significantly speed up the adoption of data quality checks in your data pipelines.</p></div>"
