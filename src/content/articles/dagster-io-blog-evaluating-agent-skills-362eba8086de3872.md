contentHtml: "<div><p>So you've written a <a target=\"_blank\" href=\"https://agentskills.io/home\">skill</a>. How do you know if the agent is actually using it? Is the correct context being referenced when you ask a question? Is it doing anything at all…?</p><p>We recently published our <a target=\"_blank\" href=\"https://github.com/dagster-io/skills\">own collection of skills</a> for working with the Dagster framework and the vast library of integrations that we support, and we had a similar question. We wanted to better understand what was going on under-the-hood when we asked Claude, \"Put my dbt models on a schedule to run every 15 minutes\". So we set out to create a light-weight evaluation framework to ensure users of our skills get the result they need.</p><p>Before we dig in to how we evaluated our skills, let's talk about the skills that we provide.</p><p>First, we have <strong>dagster-expert</strong> which is the cornerstone of context for ensuring your project adheres to the patterns and architectural decisions for working with the Dagster framework. This includes information like whether or not an asset should be partitioned, which automation strategy is best to use (declarative automation, schedules, sensors), the patterns for defining a resource, design patterns in data engineering, and how to organize your project(s). Additionally, this skill makes heavy use of the <strong>dg</strong> command-line utility which is how we provide deterministic actions to the agent. This means you can do things like scaffold a new project, launch assets to be materialized, view logs, and troubleshoot failures in both your local and deployed instances of Dagster.</p><p>Next up, we have the <strong>dagster-integrations</strong> skill, which has the largest surface area by far. These skills are broken down by category: AI &amp; ML, ETL tools, storage options, validation frameworks, etc. As an example, if you are trying to solve a specific data engineering problem, this skill will be able to provide you with suggested tools, how to initialize the integration, and how you would configure it within you Dagster project. It's worth pointing out that an additional complexity of creating a skill for integrations is that many of these tools have their own context, or documentation, that is required to ensure the tool is being used correctly. For that reason, we are trying &#160;to encode as many of the “quirks” and “gotchas” that an engineer might run into while working with these tools.</p><p>And finally, we have <strong>dignified-python</strong>. While not specifically designed for data engineering, this skills was created to promote what we consider to be production-ready Python. It is the skill we use internally while building with Python, and it includes many of the important concepts we promote, such as: modern type annotations, exception handling patterns, API design principles, and more.</p><h2>Evaluating Skills</h2><p>So now that you have an idea of what we're trying to validate, let's talk about how we've built a light weight evaluation framework for ensuring that our skills are providing the correct context, being invoked when we would expect, and are most importantly, producing correct outputs. Additionally, by having a light weight testing framework, it has enabled us to get quick and repeatable feedback on workflows with context on what does and doesn’t work. This allowed us to iterate quickly and drastically improve the Dagster skills</p><blockquote>All of the source code discussed in this post can be found in the <a target=\"_blank\" href=\"https://github.com/dagster-io/skills\">dagster-io/skills</a> repository in the <a target=\"_blank\" href=\"https://github.com/dagster-io/skills/blob/cd463cc29b5eecff55d75d3e3cedcd57240dda42/dagster-skills-evals/src/dagster_skills_evals/execution.py\">dagster-skills-evals</a> directory.</blockquote><p>The basic architecture of this framework is a simple utility that allows us to run Claude headlessly with prompts covering common use-cases, and a selection of plugins (skills) to use. It enables us to create a self-optimizing feedback loop. We can take the summary produced, provide that to an agent, and have it optimize the context while validating that the correct actions are being taken, token usage is reduced, and operations are simplified.</p><h2>Lessons learned</h2><p>While iterating on our skills, and validating the evaluation results, we've had a few insights.</p><h3>Less is more!</h3><p>This is the biggest takeaway in my mind. The initial creation of our skills was done by taking our existing documentation, pointing Claude at it, and asking it to extract the important information and re-structure it to be in the format of a skill.</p><p>There were a few issues with this automated translation, one is it still hallucinated and the parity of the translated docuements were not perfect. The second is that the resulting skills were extremely verbose, and our evaluations have revealed that terse skills seem to perform much more efficiently.</p><h3>Decision trees</h3><p>Another revelation is the importance of decision trees. At the top-level of each of our skills we define a decision tree of which files to reference. This maps key words or phrases to a sub-set of documentation within a <strong>references/</strong> directory, and has helped ensure the agent retrieves only the information required for a given foundational command-line utilities</h3><p>There is no replacement for purpose-built command-line utilities. We've found the composition of tools to work extraordinarily well from within our skills, and when interfacing with Dagster, we've opted to create specific <strong>dg</strong> commands to support it.</p><p>Instead of relying on the agent to determine which file to create, we have <strong>scaffold</strong> commands to make deterministic. To validate whether or not the Dagster definitions were created correctly, we have a <strong>dg check</strong> command. To interface with a Dagster instance, we've wrapped our API in a <strong>dg api</strong> command.</p><p>These commands have given our skills a structure to be based upon, and also a more predictable structure to parse.</p><h3>Feedback loops</h3><p>And finally, by creating this evaluation framework we have enabled ourselves (and agents) to iterate quickly and improve our skills in a quantitative way. By having a summary of all actions taken place during the agent’s session, we are able to quickly review if the expected behavior is taking place, and if not, modify our skills to ensure that it does.</p><h2>On evaluation documentation</h2><p>To close out this piece, I want to re-emphasize the importance of evaluations, a topic that feels surprisingly controversial, with many arguing online that they’re unnecessary. Before adopting this framework, we were primarily operating on faith: hoping that the context embedded in our skills would yield the desired outcomes. With evaluations in place, that guesswork disappeared. We gained clear, measurable confidence in system behavior, established tight feedback loops for iteration, and saw concrete improvements in both token utilization and tool usage.</p><p>And finally, it feel like we might be entering a new era for technical writing and education enabled by large-language models. Technical writing might be more important now than it has ever been—and it can be measured! We are now able to validate information architecture, documentation accuracy and topic coverage, and ensure that we are supporting both our human and agent readers in a qualitative way. Working on the Dagster skills and the evaluation framework has made it clear the immense importance of accurate, well thought-out documentation, and information architecture.</p><p>As always, contributions and feedback are always welcome, feel free to create discussions, pull requests, or issues on the <a target=\"_blank\" href=\"https://github.com/dagster-io/skills\">dagster-io/skills</a> repository.</p><p>‍</p></div>"
