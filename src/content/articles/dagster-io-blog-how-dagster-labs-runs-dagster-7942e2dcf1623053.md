contentHtml: "<div><p><a href=\"https://github.com/dagster-io/dagster-open-platform\" target=\"_blank\"><strong>Dagster Open Platform (DOP)</strong></a> is a complex and at-scale Dagster project, available as an open-source, public repository for others to reference and use as inspiration. It applies best practices in data engineering and Dagster to build complex asset-based pipelines. Dagster Open Platform was first announced at last month's <a target=\"_blank\" href=\"https://dagster.io/events/dagster-launch-week-oct-2023\">jam-packaged launch week</a>, but merits a highlight of its own.</p><p><em>This project is what runs the Dagster Labs business</em>. Dagster Open Platform contains parts of our data platform, so you can see how the Dagster Labs team uses Dagster itself. We use Dagster's most up-to-date best practices and APIs to practice what we preach. DOP is a valuable resource for Dagster users, growing data teams, and SaaS startups looking to build a reliable data platform of their own.</p><p>In this post, we'll take a technical deep dive into the patterns and implementations of our own Dagster project. All of the code snippets seen in this post are from the <a href=\"https://github.com/dagster-io/dagster-open-platform\" target=\"_blank\">Dagster Open Platform repository</a>.</p><h2>Guidance for after Day 1</h2><p>Dagster is an open-source Python framework for orchestrating data pipelines. By definition, a <em>framework</em> is a reusable set of classes and functions that provide generic functionality and allow developers to insert their code into specific places to customize the framework for their specific use case.</p><p>Being composable, there are lots of ways to do things in Dagster. Sometimes, our users have questions about the \"right\" thing to do. Throughout 2023, we've focused on defining the recommended way to use Dagster and what's essential to take Dagster to production for the first time. For example, we've released <a href=\"https://courses.dagster.io/courses/dagster-essentials\" target=\"_blank\">Dagster University</a>(which had over a thousand students in its first month!) and have been more intentional and user-focused than ever about our documentation.</p><p>But there is still a gap left once you've deployed Dagster into production. This is why we open-sourced Dagster Open Platform: to serve as a reference in the next steps of your Dagster journey. DOP contains the decisions we made for our data platform, providing your context and guidance on using Dagster not only on Day 1 but also on Day 180 and Day 365.</p><h4>Diving deep</h4><figure><p><img alt=\"Dagster Open orchestrates five core technologies: Snowflake, Slack, BigQuery, dbt, and Stich.\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/6867065036cc5c403c8a98f2_681399f654933b29e12fbe18_67eaca62ee9b55d17ac74217_dagster-open-technologies-min.jpeg\"></p><figcaption> &#160; &#160; &#160;Dagster Open orchestrates five core technologies: Snowflake, Slack, BigQuery, dbt, and Stich. &#160; &#160;</figcaption></figure><p>We recently open-sourced the code and dbt models we use to transform and analyze our open-source project's telemetry data. This blog will cover some of this, the utilities, and patterns that make up the DOP repository.</p><p>These are the patterns that we implemented and that work for our use cases. However, what works for us may not work for you. There will be decisions we'll revisit as we scale, but you'll still get value as I explain why we decided to implement the way we did and the tradeoffs involved.</p><h4>Working across environments</h4><p>Dagster can be run in multiple ways. For example, many users develop pipelines locally with the <code>dagster dev</code> CLI command. Some teams may run unit tests and programmatically build their assets with the <code>materialize</code> function. Afterward, they'll raise a PR with their changes and test pipelines in a close-to-production setting with <a href=\"https://docs.dagster.io/dagster-cloud/managing-deployments/branch-deployments\" target=\"_blank\">Dagster Cloud's branch deployments</a>. Finally, the PR gets merged, and the pipeline is running in production.</p><figure><p><img alt=\"Dagster runs in multiple environments to support a full developer lifecycle.\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/6867065036cc5c403c8a98ee_683d9292f8f29c757ae80c20_image.jpeg\"></p></figure><p>In each of these scenarios, Dagster is running in a different <strong>environment,</strong> and each environment has its nuances.</p><ul><li>When developing locally, a developer is working on their own copy or subset of the data</li><li>In the PR process, they want to materialize their assets to a temporary destination that gets deleted after the PR gets merged.</li><li>In production, the pipelines should run with all historical data and react to new data coming in</li></ul><p>In addition, unit tests can be run locally or in CI.</p><p>At Dagster Labs, we've found ourselves constantly writing logic to decide what database or S3 bucket to read and write from. This is why we have a set of helpers that not only figure out which environment Dagster is currently running in, but also what to do if in a specific environment.</p><p>In the Dagster Open Platform repository, a module called <code>utils</code> contains a few files, notably one called <code>environment_helpers.py</code>. We'll start this deep dive by looking at the heart of our utility:</p><div><pre><code>def get_environment() -&gt; str:\n    if os.getenv(\"DAGSTER_CLOUD_IS_BRANCH_DEPLOYMENT\", \"\") == \"1\":\n        return \"BRANCH\"\n    if os.getenv(\"DAGSTER_CLOUD_DEPLOYMENT_NAME\", \"\") == \"prod\":\n        return \"PROD\"\n    return \"LOCAL\"</code></pre></div><p>This leverages a few environment variables <a href=\"https://docs.dagster.io/dagster-cloud/managing-deployments/environment-variables-and-secrets#built-in-environment-variables\" target=\"_blank\">that Dagster Cloud sets</a>:</p><ul><li>When <code>DAGSTER_CLOUD_IS_BRANCH_DEPLOYMENT</code> is set, our Dagster deployment can safely assume that it's running within a Branch Deployment. We'll talk about how we optimize our pipelines and development process with this knowledge later.</li><li><code>DAGSTER_CLOUD_DEPLOYMENT_NAME</code> maps to the name of the environment you've defined for your Dagster Cloud deployment. Dagster Cloud users can have multiple deployments, so this can vary depending on how many you have. However, the Dagster Labs data team only has one we depend on, called <code>prod</code>, and we check for that.</li></ul><p>Otherwise, we assume you're running locally or running unit tests.</p><p>Using this method as the foundation for all of our environment helpers, we use those constants to define other helper methods that allow us to resolve what database to write to, what schema to write to, or what context the dbt project is running in.</p><p>During development, every engineer at Dagster Labs gets their own schema within a database called <code>SANDBOX</code>. Each schema is named after the person working within the schema. In my case, my dedicated schema is named <code>TIM</code>.</p><p>Where things get interesting is when a PR is raised. For each new PR, <a href=\"https://docs.dagster.io/guides/dagster/branch_deployments#testing-against-production-with-dagster-cloud-branch-deployments\" target=\"_blank\">we automatically make a zero-copy clone of our production databases</a> and name that clone based on the PR number, such as PR #1523 would have its own database called <code>PURINA_CLONE_1523</code>. When running pipelines within a Branch Deployment, the assets materialized will pull data from the zero-copy clones and write new data into that <code>PURINA_CLONE_1523</code> database. When the PR gets merged, the database is deleted.</p><p>You may catch some references to a certain pet treat company in our repository. That's because we believe in <a href=\"https://en.wikipedia.org/wiki/Eating_your_own_dog_food\" target=\"_blank\">dogfooding</a>, and we use our internal analytics platform to dogfood our product.</p><h4>Dissecting dbt</h4><p>dbt is the most popular tool that people use Dagster with. We've invested heavily into our <a target=\"_blank\" href=\"https://dagster.io/integrations/dagster-dbt\">dbt integration</a>, and can confidently say that Dagster is the best way to run dbt in production.</p><p>Recently, we open-sourced the dbt models related to our open-source telemetry models. We've also published the staging models for our cloud telemetry.</p><h5>Matching dbt sources to their asset keys</h5><p>If you're familiar with our dbt integration, you may use the <code>@dbt_assets</code> decorator and its companion <code>DagsterDbtTranslator</code> class. We configure our <code>DagsterDbtTranslator</code> to define the asset keys and map our dbt sources to upstream models. Asset keys typically convey the physical location of where the asset is stored. In the code snippet below, we set the asset key based on the namespace of the source.</p><div><pre><code>def get_asset_key(cls, dbt_resource_props: Mapping[str, Any]) -&gt; AssetKey:\n\tresource_type = dbt_resource_props[\"resource_type\"]\n\tresource_name = dbt_resource_props[\"name\"]\n\t... # Other logic\n\tif resource_type == \"source\":\n\t\tdatabase_name = dbt_resource_props[\"database\"].lower()\n\t\tschema_name = dbt_resource_props[\"schema\"].lower()\n\t\treturn AssetKey([database_name, schema_name, resource_name])</code></pre></div><p>With this method, the source table of <code>purina.prod_telemetry.oss_telemetry_events_raw</code> would resolve to an asset key of <code>[\"purina\", \"prod_telemetry\", \"oss_telemetry_events_raw\"]</code>:</p><div><pre><code>sources:\n  - name: prod_telemetry\n    database: purina\n    schema: prod_telemetry\n    tables:\n      - name: oss_telemetry_events_raw</code></pre></div><p>By following the convention that the asset key should match where the asset is stored, our dbt sources will always match up with their respective assets.</p><h5>Enriching dbt's metadata</h5><p>In the translator, we also define metadata for each model. In Dagster, there are two points where metadata can be added to an asset: static data can be added when an asset is defined and dynamic data is computed at every materialization. When each dbt model is defined in DOP, we attach a link to the table made in the Snowflake UI. By making the link readily available, developers and stakeholders can quickly navigate to the table in the Snowflake UI. Below is the override for <code>get_metadata</code> we use to create this link.</p><div><pre><code>def get_metadata(cls, dbt_node_info: Mapping[str, Any]) -&gt; Mapping[str, Any]:\n\tif dbt_node_info[\"resource_type\"] != \"model\":\n\t\treturn {}\n\treturn {\n\t\t\"url\": MetadataValue.url(\n\t\t\tf\"{SNOWFLAKE_URL}/{dbt_node_info['schema'].upper()}/table/{dbt_node_info['name'].upper()}\"\n\t\t)\n\t}</code></pre></div><p>You can find the complete code for our <code>DagsterDbtTranslator</code> implementation at <code>dagster_open_platform/utils/dbt.py</code>.</p><h5>Defining our dbt related objects</h5><p>We define our dbt-related objects in a few different places. We construct our translator in the utils directory because it's commonly used, and we instantiate our <code>DbtCliResource</code> with the rest of our resources. We define a separate set of <code>@dbt_assets</code> for each pipeline we have and leverage dbt's <code>source:&lt;source_name&gt;+</code> selector to decide which dbt models should be grouped together. This isn't necessary in some ways, as Dagster can dynamically resolve what dbt models to run. However, this tradeoff allows us to group our dbt assets semantically and partition dbt models with the same partition definitions as their ingestion and reporting.</p><h5>Bridging dbt across environments</h5><p>We can combine our understanding of working across environments (as described earlier) and pass it to our dbt project. One of our environment helper methods is <code>get_dbt_target</code>, which we use when building and running the dbt project. When in local development or a Branch Deployment, we limit the amount of data used in development to a short window of data, such as the past 90 days.</p><h3>Conclusion</h3><p>Dagster Open Platform is still in its early stages. We will continue sharing our more complex pipelines and end-to-end solutions with the open-source data community. If you're interested in keeping up-to-date and learning more about how we build out our own analytics, give the <a href=\"https://github.com/dagster-io/dagster-open-platform\" target=\"_blank\">Dagster Open Platform repository a star</a> ⭐!</p></div>"
