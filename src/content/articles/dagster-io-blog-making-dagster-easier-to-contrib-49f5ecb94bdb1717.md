contentHtml: "<div><p>Dagster started as an open source project, and community contributions remain an important part of how the project evolves.</p><p>At the same time, open-source contributions have changed rapidly. AI tools have made it much easier to generate pull requests, but reviewing a PR still takes context, judgment, and coordination. Across OSS, many maintainers are dealing with a new imbalance: proposed changes are becoming easier to produce than to review thoroughly.</p><p>We have felt some of those shifts ourselves. Over the past year, we have been <a target=\"_blank\" href=\"https://dagster.io/blog/monorepos-the-hub-and-spoke-model-and-copybara\">migrating Dagster to a monorepo</a> to better support both the open-source project and Dagster+ under a single development model.</p><p>Now that the migration is settling down, we are focused on making contributions to Dagster smoother, clearer, and more predictable again. Our goal is to make the process easier to navigate, easier to review, and more approachable for everyone who wants to help improve Dagster.&#160;</p><h2>Reducing review friction</h2><p>Like most large repositories, our repo runs a broad set of automated checks on every pull request. We lint with ruff, run tests, type-check Python, build documentation, and verify that site changes can be deployed successfully. Those checks are important, but they only answer part of the question. Passing CI tells us that a change does not obviously break the repository. It does not always tell us whether a PR matches the conventions and quality bar of the codebase.</p><p>That gap often creates the most frustrating part of contributing: the review loop. A pull request may be functionally correct but still needs several rounds of feedback to better align with repository conventions or improve clarity. To make that process smoother, we have been adding more automated review tools directly into our pull request workflow.</p><p>An example of a tool you may see on a Dagster pull request is <strong>Greptile</strong> for repository-aware suggestions based on the patterns already in use.</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/69cd17106e2110634f0086c4_fae11429.png\"></p></figure><p>These tools help surface repository-specific expectations earlier and reduce avoidable review churn, so human reviewers can focus on the substance of a change: whether it solves a real problem, fits the product, and is easy to maintain.</p><h2>What’s next for contributors</h2><p>Improving review tooling is only one part of making Dagster easier to contribute to. We also want to make it clearer how to contribute effectively in the first place: how the repository is organized, what good changes look like, and which kinds of contributions are especially valuable.</p><p>We already have contributor guidance for both code and docs, including our<a target=\"_blank\" href=\"https://docs.dagster.io/about/contributing\"> code contribution guidelines</a> and<a target=\"_blank\" href=\"https://docs.dagster.io/about/contributing-docs\"> documentation contribution guidelines</a>. We want to keep building on that foundation so contributors can spend less time guessing about conventions and more time making useful changes.</p><p>We also think tools can help here. For example, contributors using AI-assisted workflows can use resources like the Dignified Python skill to produce changes that are more consistent, readable, and reviewable. Over time, we want contributing to Dagster to feel more guided, more predictable, and more approachable for both human contributors and AI-assisted ones.</p><h2>Setting a PR up for success</h2><p>A reality of OSS in an AI-assisted world is that pull requests are becoming easier to generate than they are to review. The contributions that move most smoothly tend to share a few common traits.</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/69cd17106e2110634f0086c7_a5483c82.png\"></p></figure><h3>Keep the scope tight</h3><p>The strongest PRs usually solve one clear problem. A well-scoped contribution makes its goal obvious, keeps the change set focused, and makes it easy for a reviewer to understand what they are being asked to evaluate. AI tools can be very helpful once you know what you want to change, but they are much less effective when pointed at a broad prompt like “improve the documentation,” which often produces large, low-context diffs that are difficult to review and hard to merge.</p><h3>Limit the files you touch</h3><p>A focused PR is not just about intent. It is also about surface area. As the number of files in a change increases, the effort required to review it usually increases too. This is especially true when a PR spans multiple parts of the stack. Small, contained changes are easier to reason about, test, and merge with confidence than PRs that require multiple people from different Dagster teams to review.</p><h3>Choose the right part of the codebase</h3><p>The part of Dagster you are changing can also affect how easily a contribution lands. Changes to the core framework often require broader design context and more coordination, which can make them take longer to evaluate. For many contributors, docs, examples, <a target=\"_blank\" href=\"https://github.com/dagster-io/community-integrations\">community-integrations</a>, and other focused user-facing improvements are the fastest path to impact. These contributions are extremely valuable and often much easier for us to review and ship.</p><h2>Your contributions make Dagster</h2><p>Dagster has been shaped by community contributions from the beginning, and that has not changed. Even as the mechanics of contributing evolve, we still believe that thoughtful contributions from users and community members improve the project.</p><p>Our goal is not to make contributing more restrictive. It is to make the process clearer, smoother, and more predictable for everyone involved. That means better tooling, better guidance, and better signals about what kinds of contributions are easiest to review and merge.</p><p>We are grateful to everyone who has contributed to Dagster over the years, whether through code, documentation, integrations, bug reports, or feedback. That participation still matters deeply to us.</p><p>In the next post, we will go deeper into the technical side of our monorepo migration using <a target=\"_blank\" href=\"https://github.com/google/copybara\">Copybara</a>, including the <a target=\"_blank\" href=\"https://dagster.io/blog/monorepos-the-hub-and-spoke-model-and-copybara\">hub-and-spoke model we adopted</a> and how it has helped us build a more unified development workflow.</p></div>"
