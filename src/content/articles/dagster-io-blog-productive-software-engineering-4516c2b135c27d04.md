contentHtml: "<div><p>So you want to get stuff done. You want to be a <strong>productive</strong> software engineer. What does that mean?</p><p><strong>\"pro·duc·tive\"</strong> &#160;adjective:<em> producing or able to produce large amounts of goods, crops, or other commodities.</em></p><p>In the realm of software, the engineer’s commodity is a code change. These changes increase the utility delivered to users via the software we work on. A change may be a bug fix, an improvement to documentation, a new feature, or even the removal of code.</p><p>Version control systems are used to manage these changes, and many organizations require these changes to be peer-reviewed before they affect users. Using the lens of Git and GitHub, the unit of change is a <em>commit</em> and the unit of review is a <em>pull request</em> (PR). An accepted change can be <em>merged</em> into the next version to be released to users.</p><p>Developing changes to a piece of software is an iterative process. A variety of tools are used to create feedback loops that ensure changes are functional and high quality. Getting the most out of these feedback loops is key to becoming more productive. While computers drive the tools providing the tightest feedback loops—like static analysis and testing—the code review process is driven by people. This makes code reviews a much more challenging and rewarding feedback loop to optimize.</p><h2>Human in the Loop</h2><p>Code review involves other participants. Reviewers are often engineering stakeholders who have context on the change and can provide guidance. If they are thorough in the process, the change can immensely benefit from the feedback: it can be simplified, further contextualized, or armed with more wondrous insight. Once feedback is incorporated, the change can be signed off to be merged.</p><p>In inspecting this feedback loop, the point to note is that both the author of the change and the reviewers have levers to dictate the iteration process. For example, the author determines the scope and granularity of the change in review. The reviewers determine whether to give small nitpicks or critical comments regarding the structure or approach of the change.</p><p>By optimizing this process, the review feedback loop gives the author higher quality changes and reduced latency in getting them merged.</p><p>Here, we will focus on what steps the author can take to improve the review feedback loop. To further analyze this perspective, let us follow the journey of making a change.</p><h4>Making Changes</h4><p>Roughly speaking, the journey of a change is</p><ol><li>🤔 Have an idea</li><li>💻 Make the changes</li><li>👀 Have it reviewed</li><li>GOTO 2 (0-N times)</li><li>✅ Merge it</li></ol><p>…which might look something like this:</p><figure><p><img src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686619dd953fda88e2e1abfe_681399f654933b29e12fbe26_67eaca6604e25de455d7e733_getting-stuff-done-5.png\" alt=\"\"></p></figure><p>One way to increase our output is to reduce how long this process takes. The first thing that jumps out here is that the time writing code (in blue) is much smaller than the time spent waiting for review. We can spend some extra time reviewing our own code to make sure that we are not repeating things that surfaced in past reviews or making any trivial mistakes. We can also make sure changes are well tested to reduce the burden on the reviewer to validate correctness.</p><figure><p><img src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686619dd953fda88e2e1ac04_681399f654933b29e12fbe21_67eaca6604e25de455d7e72a_getting-stuff-done-4.png\" alt=\"\"></p></figure><p>Past optimizing one change at a time, our next step in improving output is to juggle multiple changes. Having different changes in flight is a fundamental skill for a productive engineer to utilize their time. Maximizing output through this approach has its limits, though. This works best when the time to change contexts from between changes is low, like fixing several bugs in the same area.</p><figure><p><img src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686619dd953fda88e2e1ac0d_681399f654933b29e12fbe29_67eaca6604e25de455d7e736_getting-stuff-done-3.png\" alt=\"\"></p></figure><p>As our skills grow as an engineer, our ideas become more ambitious, and we seek to make greater changes. A journey most engineers go through at some point is working hard to create a large change and putting it up for review in one grand PR, only to experience a long wait and a lack of thoughtful feedback.</p><figure><p><img src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686619dd953fda88e2e1ac07_681399f654933b29e12fbe24_67eaca6604e25de455d7e730_getting-stuff-done-2.png\" alt=\"\"></p></figure><h4>A Better Way</h4><p>How do we optimize for the code review feedback loop when working on significant changes? By breaking down the large change into smaller dependent changes. This practice has been called “Stacked Diffs” or “Stacked PRs”:</p><ul><li><a href=\"https://kurtisnusbaum.medium.com/stacked-diffs-keeping-phabricator-diffs-small-d9964f4dcfa6\" target=\"_blank\">Stacked Diffs: Keeping Phabricator Diffs Small</a> - Kurtis Nusbaum</li><li><a href=\"https://jg.gg/2018/09/29/stacked-diffs-versus-pull-requests/\" target=\"_blank\">Stacked Diffs Versus Pull Requests</a> - Jackson Gabbard</li><li><a href=\"https://benjamincongdon.me/blog/2022/07/17/In-Praise-of-Stacked-PRs/\" target=\"_blank\">In Praise of Stacked PRs</a> - Ben Congdon</li></ul><p>Doing this practice natively in Git &amp; Github is cumbersome, so several tools have sprung up that make this flow <strong>much</strong> easier:</p><figure><p><img src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686619dd953fda88e2e1ac01_681399f654933b29e12fbe23_67eaca6604e25de455d7e739_tools_logos.png\" alt=\"\"></p></figure><ul><li><a href=\"https://graphite.dev/\" target=\"_blank\">Graphite</a> - open-source CLI and a code review dashboard</li><li>Super Pull Requests [SPR] - a command line tool</li><li><a href=\"https://sapling-scm.com/docs/overview/stacks\" target=\"_blank\">Sapling</a> - first-class support for editing and manipulating stacks of commits.</li></ul><p>Even with these tools, creating stacked changes can be a novel way of working, so let us consider a few ways to think about producing these stacked changes.</p><h4>Prototype then Split</h4><p>One approach is to build first and deal with stacking later. This workflow is best if you are new to stacking diffs or are working on something that is speculative and might get thrown away. You can think about this workflow as a two-phase process, <strong>prototype,</strong> then <strong>split</strong>.</p><h5>1) Prototype</h5><ul><li>Focus on getting the idea working end to end; build it knowing you may throw it all or large portions away.</li><li>Good local commit organization is helpful but not critical.</li><li>Pay attention to the systemic challenges, local implementation details are easy to improve later. Being quick and dirty in this phase means you should be amenable to seeing how a different approach might work.</li><li>The number of corners cut should match your level of uncertainty</li><li>Keeping a draft PR in sync with your prototype can be useful as a remote <a target=\"_blank\" href=\"https://dagster.io/glossary/data-backup\">backup</a> as well as a means to get peer feedback on the overall approach.</li><li>Try to break out any changes you make along the way that makes sense to merge absent the overall feature.</li></ul><h5>2) Split</h5><p>The prototype works well enough to move forward, do a self-review, and clean things up.</p><ul><li>If you didn't manage your local commits well, rewriting things here is not a total loss. Things are usually better the second time you write them anyway.</li><li>Work to break things out into as many small single thesis PRs as possible.</li><li>Most of the review time should be spent on PRs that focus on any controversial changes.</li></ul><h4>Stacking as you Go</h4><p>As you become more comfortable with stacked diffs, you will start to be able to manage the decomposition as you go. This workflow is best when you have confidence in your approach, as rearranging the stack can be taxing.</p><ul><li>‘In progress’ commit(s) make up the \"working edge\" of the stack.</li><li>As a reviewable unit of change is identified - it is extracted from the working edge, rebased below, and sent out for review.</li><li>The working edge progresses forward as diffs lower in the stack are out for review.</li><li>Interactive rebase is used heavily and is critical for updating mid-stack changes.</li><li>Unless strictly dependent, accepted changes are rebased to the bottom and merged.</li></ul><figure><p><img src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686619dd953fda88e2e1ac0a_681399f654933b29e12fbe2b_67eaca6604e25de455d7e72d_getting-stuff-done-1.png\" alt=\"\"></p></figure><h4>Break it Down</h4><p>No matter how you go about it, breaking down a large change into smaller dependent changes is a powerful tool. Not only do you increase your output, but the care put into making changes easier to understand benefits every person to ever interact with it.</p><p>Most of our focus is on how a change affects the program, but considering how the change affects the other people working on the software is important for the sustainability of both the software and the people working on it. Much of programming can be an isolated exercise of man versus machine, but code review is our chance to cooperate with other people in the pursuit of bettering ourselves and our software.</p></div>"
