contentHtml: "<div><p>In a <a target=\"_blank\" href=\"https://dagster.io/blog/dignified-python-10-rules-to-improve-your-llm-agents\">previous post</a>, we discussed some of the stylistic choices we use internally to ensure that Python code generated by our agents remains “dignified.” These rules, covering style, structure, and idiomatic Python, help us maintain a consistently high-quality codebase even when much of the code is machine-assisted.</p><p>However, when we write code with assistance, our agents must also be held to the same standard for tests. In practice, this means being explicit about how we instruct our agents to design and write tests without introducing subtle errors or long-term maintenance issues.</p><p>This requires repository-wide testing strategies that define not just what “good tests” look like, but also when tests should be written, what kinds of tests are appropriate in different situations, and which patterns are disallowed.</p><p>In other words, we need to supply the rules and logic that define how tests should be written, not leave those decisions up to inference.</p><h2>How to Run Agentic Tests</h2><p>Our testing strategy is designed around <a target=\"_blank\" href=\"https://code.claude.com/docs/en/skills\">skills</a>. Most of the details for these skills can apply to any repo (with some slight changes). But before getting into our actual testing strategy, it is good to discuss how these tests run within our workflows.</p><p>Test-writing agents do not use the same authority or context as agents that produce application code. Test generation runs as sub-agents with a deliberately constrained role within an isolated context window. Constraining test work to a sub-agent prevents the common failure mode where an agent “fixes” a failing test by subtly adjusting the code under test.</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/697776498c7983bb5bc39117_0f1517a1.png\"></p></figure><p>Within that sub-agent, each skill represents a narrow task, adding coverage for a specific function, reproducing a reported bug, or refactoring an existing test for clarity. If a request can’t be expressed as a bounded skill, it usually doesn’t belong in an automated test pass.</p><p>Finally, we manage context very intentionally. Test sub-agents run with task-specific context and do not accumulate history across runs. This avoids speculative tests, accidental dependency on prior failures, and assertions based on deprecated behavior. Each invocation should be able to stand alone, producing tests that are readable, intentional, and deterministic.</p><h2>When Agents Write Tests</h2><p>We start with simple <a target=\"_blank\" href=\"https://github.com/dagster-io/erk/blob/master/.claude/skills/fake-driven-testing/references/workflows.md\">workflows</a>. Tests should be written for any new logic introduced under the src directory. We are explicit that agents should only write tests for the code actively being implemented in the current work session.</p><p>By narrowing the scope of what an agent is allowed to test, we reduce noise and ensure that tests track real, intentional changes to the codebase.</p><p>After limiting the scope of what qualifies as new testable code, we begin to distinguish between code for new feature development vs bug fixes.</p><p>Bug fixes, follow a more routine order of operations:</p><ol><li>Write a failing test that reproduces the bug.</li><li>Fix the bug.</li><li>Run the test and confirm that it now passes.</li><li>Leave the test in place as a regression test.</li></ol><p>For new features, Test Driven Development is encouraged. We expect appropriate tests to be included alongside the feature, though the specifics of which tests to write, and at what level are slightly more sophisticated.</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/697776498c7983bb5bc3911a_d3bf6d13.png\"></p></figure><h2>Choosing the Right Test Level</h2><p>As part of our repository context, we define a number of <a target=\"_blank\" href=\"https://github.com/dagster-io/erk/blob/master/.claude/skills/fake-driven-testing/references/testing-strategy.md\">explicit testing levels</a>. For each level, we describe its purpose and the rough proportion of the overall test suite it should represent. This gives agents a strong prior for where most tests should live.</p><p>For example, in one of our codebase, the majority of tests are written against a fake implementation of infrastructure, built specifically for testing. We prefer this approach over heavy use of mocks because they tend to be brittle upon refactoring and can introduce performance and safety issues.</p><p>The table for our testing levels reflects this preference by instructing the agent that business logic tests (level 4) should represent the majority of our testing codebase.</p><div><table> &#160;<thead> &#160; Without these constraints, agents tend to make small local decisions that feel reasonable but can slowly degrade the quality of the test suite over time.</p><p>One of the most common failure modes is performance erosion. As tests accumulate, unit tests that were originally lightweight and fast can become bulky and slow, eventually turning into a bottleneck for development and CI.</p><p>To counter this, we define both micro-level and macro-level anti-patterns that agents should actively watch for.</p><p><strong>Micro-level anti-patterns</strong></p><p>At the micro level, we call out specific implementation choices that are inappropriate for unit and business-logic tests. For example:</p><ul><li>Unit tests should avoid invoking <code>subprocess</code>, which is significantly slower than using the fake infrastructure we include as part of our testing codebase.</li><li>Tests should avoid unnecessary filesystem or network interactions when a fake or in-memory alternative exists.</li></ul><p>These rules help ensure that individual tests remain cheap to execute and resilient to change.</p><p><strong>Macro-level anti-patterns</strong></p><p>At the macro level, we define constraints that apply to the test suite as a whole. For example:</p><ul><li>The total runtime of unit tests should not exceed a few seconds.</li></ul><pre><code><span><span>Performance\n</span></span><span><span>Tests over fakes run </span><span>in</span><span> milliseconds. A typical test suite </span><span>of</span><span> </span><span>100</span><span>+ tests runs </span><span>in</span><span> seconds, enabling rapid iteration.</span></span></code></pre><p>This kind of global constraint prevents gradual performance regressions that can be difficult to notice in day-to-day development but are especially damaging at scale.</p><p>There are many additional micro-level anti-patterns defined in our repository context, all of which roll up into broader testing objectives defined elsewhere in our repo. By aligning individual rules with higher-level goals, we ensure that our testing strategy remains consistent, non-contradictory, and sustainable as the codebase grows.</p><h2>Putting the Strategy into Practice</h2><p>The best way to understand how this strategy works is to look at the tests generated by a <a target=\"_blank\" href=\"https://github.com/dagster-io/erk/pull/4793\">real pull request</a>. In this case, the PR adds support for removing installed capabilities from repositories and user settings. Because this is new feature work, new tests are expected and included.</p><p>In total, seven tests are added by our subagent, all of which are classified as level 4 business logic tests. This aligns with our expectation that the majority of new tests should validate behavior using fake infrastructure rather than relying on heavy mocking or fully real integrations.</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/697776498c7983bb5bc39111_5a611573.png\"></p></figure><p>Looking at one of the tests in detail, we can see how these principles show up in practice. Notably, the test does not use @patch decorators or Mock() objects. Instead, it relies on a fake implementation that behaves like the real system while preserving type safety and refactor resilience.</p><pre><code><span><span>def test_capability_remove_not_installed() -&gt; None:\n</span></span><span><span>    </span><span>\"\"</span><span>\"Test that removing a not-installed capability shows warning.\"</span><span>\"\"</span><span>\n</span></span><span>    runner = CliRunner()\n</span><span><span>    </span><span>with</span><span> erk_isolated_fs_env(runner) </span><span>as</span><span> env:\n</span></span><span>        git_ops = FakeGit(git_common_dirs={env.cwd: env.git_dir})\n</span><span>        global_config = GlobalConfig.test(\n</span><span><span>            env.cwd / </span><span>\"fake-erks\"</span><span>, use_graphite=False, shell_setup_complete=False\n</span></span><span>        )\n</span><span>\n</span><span>        erk_installation = FakeErkInstallation(config=global_config)\n</span><span>\n</span><span>        test_ctx = env.build_context(\n</span><span>            git=git_ops,\n</span><span>            erk_installation=erk_installation,\n</span><span>            global_config=global_config,\n</span><span>        )\n</span><span>\n</span><span><span>        result = runner.invoke(cli, [</span><span>\"init\"</span><span>, </span><span>\"capability\"</span><span>, </span><span>\"remove\"</span><span>, </span><span>\"learned-docs\"</span><span>], obj=test_ctx)\n</span></span><span>\n</span><span><span>        assert result.exit_code == </span><span>0</span><span>, result.output\n</span></span><span><span>        assert </span><span>\"Not installed\"</span><span> </span><span>in</span><span> result.output\n</span></span><span></span></code></pre><p>This test validates observable behavior rather than internal implementation details. The important outcomes are that the command exits successfully and that the user receives a clear warning when attempting to remove a capability that is not installed.</p><pre><code><span><span>    assert result.exit_code == </span><span>0</span><span>, result.output\n</span></span><span><span>    assert </span><span>\"Not installed\"</span><span> </span><span>in</span><span> result.output</span></span></code></pre><p>The test also respects our defined anti-patterns. It uses <code>CliRunner()</code> rather than spawning a subprocess, avoids hardcoded paths, and relies entirely on the fake infrastructure provided by the test environment. As a result, the test is fast, deterministic, and resilient to refactoring.</p><h2>Why a Testing Strategy is Still Foundational</h2><p>Agents remove friction from writing code, but they also remove many of the informal checks humans rely on. Without explicit guidance, tests can become slow, brittle, speculative, or focused on the wrong level of abstraction.</p><p>By defining when tests should be written, how workflows differ for features and bug fixes, and which testing levels are preferred, we turn testing into a set of guardrails that scale with automation. Clear anti-patterns further protect the test suite from gradual performance and maintenance regressions.</p><p>A well-defined testing strategy makes it possible to move quickly with agents while preserving correctness, confidence, and long-term maintainability. If you want the concrete skill, including our testing guidelines and our \"Dignified Python\" standards, <a target=\"_blank\" href=\"https://github.com/dagster-io/skills/tree/master\">check out our skills repo</a>.</p></div>"
