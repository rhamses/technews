contentHtml: "<div><p>We shipped <a target=\"_blank\" href=\"https://dagster.io/events/dagster-day\">Dagster Cloud 1.0</a> in August. It’s been pretty successful so far, and this is the first in a series of blog posts talking about how we built it.</p><p>Today I’m going to talk about why we made the unconventional decision to build our logging system on top of Postgres instead of Kafka, what worked well, what didn’t work well, and how we did it.</p><p>🔬 <a target=\"_blank\" href=\"https://dagster.io/blog/skip-kafka-use-postgres-message-queue#framing-the-problem\"><strong>Framing the problem<br>‍</strong></a>🔨 <a target=\"_blank\" href=\"https://dagster.io/blog/skip-kafka-use-postgres-message-queue#dont-choose-the-right-tool-for-the-job\"><strong>Don’t choose the right tool for the job<br>‍</strong></a>🚌 <a target=\"_blank\" href=\"https://dagster.io/blog/skip-kafka-use-postgres-message-queue#postgres-as-a-message-queue\"><strong>Postgres as a message queue<br>‍</strong></a>📏 <a target=\"_blank\" href=\"https://dagster.io/blog/skip-kafka-use-postgres-message-queue#how-we-measured\"><strong>How we measured<br>‍</strong></a>📈 <a target=\"_blank\" href=\"https://dagster.io/blog/skip-kafka-use-postgres-message-queue#scaling-the-database-archiving-and-rate-limiting\"><strong>Scaling the database: archiving and rate limiting<br>‍</strong></a>💥 <a target=\"_blank\" href=\"https://dagster.io/blog/skip-kafka-use-postgres-message-queue#dealing-with-failure\"><strong>Dealing with failure<br>‍</strong></a>🙈 <a target=\"_blank\" href=\"https://dagster.io/blog/skip-kafka-use-postgres-message-queue#things-that-didnt-go-well\"><strong>Things that didn’t go well<br>‍</strong></a>🧬 <a target=\"_blank\" href=\"https://dagster.io/blog/skip-kafka-use-postgres-message-queue#future-work\"><strong>Future work</strong></a></p><h2>🔬 Framing the problem</h2><p><a target=\"_blank\" href=\"https://dagster.io/lp/dagster-plus-trial\">Dagster Cloud</a> is a system for orchestrating data pipelines. At its core, there are two main components:</p><ul><li>A scheduler that kicks off runs of data pipelines</li><li>A logging system that aggregates structured and unstructured information about the pipelines and reports it to the user via a UI.</li></ul><p>In this post, we’re focused on that second component.</p><p>As the data pipeline executes, it spits out lots of event logs that we must store and <a target=\"_blank\" href=\"https://dagster.io/glossary/data-indexing\">index</a> to render our UI.</p><figure><p><img alt=\"A screenshot of Dagster's UI with logging\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686706643d612bf6cb90f378_681399f654933b29e12fbe04_67eac25a7c6c8c7a7e02a436_dagster-logs.webp\"></p><figcaption> &#160; &#160; &#160;Imagine the logs rapidly scrolling by in the bottom pane &#160; &#160;</figcaption></figure><p>At first glance, ingesting these logs looks like a classic Kafka-shaped problem. It’s an append-only, ordered queue of messages organized by topic that we want to consume in near-real-time. Furthermore, we have a <em>lot</em> of data coming from our customers, so it’s critical that we process this data in a scalable, cost-effective way. Kafka is the obvious solution.</p><p>Or is it?</p><h2>🔨 Don’t choose the right tool for the job</h2><p>I am a big fan of Dan McKinley’s essay on <a target=\"_blank\" href=\"https://boringtechnology.club/\">Choosing Boring Technology</a>.</p><p>The tl;dr is that adding infrastructure incurs significant costs. If you’re going to add new infrastructure, it better be really important and useful infrastructure. Especially when you’re a small startup.</p><p>When I say costs, I mean stuff like this:</p><ul><li>Time to evaluate the new technology</li><li>Time to learn best practices</li><li>Monitoring it</li><li>Debugging it in production</li><li>Following the ecosystem</li><li>Evangelizing it internally and driving the right level of adoption</li></ul><p>It’s just a lot of work to add a new piece of infra. And it’s often sustained work over a long period of time.</p><p>So here’s my philosophy when faced with a new problem:</p><ol><li><strong>Never choose the <em>wrong</em> tool for the job.</strong> If existing infrastructure can’t solve the problem, or it will be too slow, expensive, or insecure/noncompliant, don’t use it.</li><li><strong>It’s better to use a tool that you’re already using</strong>, even if it’s not the <em>perfect</em> tool for the job</li></ol><p>When we built the first features in the open-source project, we reached for Postgres. This was a technology our team already knew how to use, and from prior experience, we knew it could serve our initial use cases well.</p><h2>🚌 Postgres as a message queue</h2><p>As we were already running Postgres, if we could prove to ourselves that Postgres wasn’t the <em>wrong</em> tool for the job, it might be worth using instead of a new piece of infra like a dedicated message queue.</p><p>However, using a relational database - such as a Postgesql database - as a message queue is a <a target=\"_blank\" href=\"http://mikehadlow.blogspot.com/2012/04/database-as-queue-anti-pattern.html\">well-known anti-pattern.</a> The haters dial in on three main points:</p><ol><li>RDBMS’s are too slow to act as a message queue</li><li>Sharing direct RDBMS access across a fleet of services is bad practice</li><li>Many haters want you to buy their message queue product</li></ol><p>We don’t have any issues with #2, as <a target=\"_blank\" href=\"https://twitter.com/floydophone/status/1481743636043743233\">we are proud of our majestic, well-factored monolith</a> (but that’s another blog post… someday). In environments where this <em>is</em> an issue, it does not need to be a deal breaker; it can be wrapped in a service API just like any other piece of state.</p><p>Really, I’d like to focus on the first point: <strong>performance.</strong></p><h2>🚅 Computers Are Fast™ (and so is your RDBMS)</h2><p>I can’t tell you how many times I’ve heard this exact conversation in my career.</p><p>Engineer 1: “We need to adopt new technology X because boring technology Y is too slow.”<br>Engineer 2: “How slow is it, and how fast does it need to be?”<br>Engineer 1: “No idea, I never measured it.”</p><p>It’s important to actually measure this stuff by running a stress test. Most of the time, you’ll discover that the boring old technology is fast enough because Computers Are Fast™.</p><p>Computers are also Big, too. You can rent a <a target=\"_blank\" href=\"https://aws.amazon.com/ec2/instance-types/x1e/\">128-core, 3 TB of RAM instance from AWS</a>. That <a target=\"_blank\" href=\"https://www.computerworld.com/article/2534312/the--640k--quote-won-t-go-away----but-did-gates-really-say-it-.html\">ought to be enough for anybody.</a></p><p>Even if your old, boring technology is having trouble scaling today, you might be able to scale up if put on a New, Big Box™ with very little effort.</p><p>Obviously, this is not a silver bullet. Some workloads can’t take advantage of all those resources, or it otherwise won’t be cost-effective. <strong>But you should measure it and be sure.</strong></p><h2>📏 How we measured</h2><figure><p><img alt=\"When implementing new architecture like Postgres it is important to measure performance.\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686706643d612bf6cb90f366_684897704fae05c1eba0a611_image.jpeg\"></p></figure><p>‍</p><p>We originally chose Postgres simply because it was a technology that the team already knew. And it just kept chugging along as we gradually rolled our product out to a few early access customers.</p><p>However, before we launched Dagster Cloud to the public, we did revisit this decision to ensure that we made the right call. This time, we measured. This is actually a pretty straightforward, objective process that comes in three steps.</p><ol><li><strong>Define your service level objectives (SLOs) and measure them</strong> via an observability system like Datadog. You usually want, at a minimum, an availability SLO (i.e., 99.9% of requests succeed) and a latency SLO (p99 latency is &lt; 1s).</li><li><strong>Define your load objective.</strong> This is just the number of users you want to be able to support at a given time. If you’re launching a new product, ask marketing how much traffic they expect on launch day and double it. If there isn’t going to be a splashy launch, try to project out where you’ll be in, say, one year, and add a 10-20% buffer.</li><li><strong>Run a load test</strong> by spinning up a test cluster and writing some scripts to simulate real usage. Keep fixing bottlenecks and re-running load tests until you hit your objective.</li></ol><p>What we found was Postgres did not hit our objective out of the box. However, we were able to get there within 1-2 weeks of work. The specific changes we had to make were:</p><ul><li>Our DB instance size was too small. We had to move up to the next AWS instance size. For extra headroom, we picked an even larger instance size.</li><li>We had three problematic queries that we addressed one by one. We were able to completely eliminate one of them (it was unnecessary), and the other two were fixed by reducing a polling interval and by adding additional columns to the index.</li></ul><p>Once we had done this work, we were confident that we would be able to survive launch day and go well into 2023 without this system falling over.</p><h2>📈 Scaling the Postgresql database: archiving and rate limiting</h2><p>We did a number of tricks to scale the database beyond simply “buying a bigger box.”</p><p>The first thing we did was proactively address the issue of unbounded growth. When building a process that writes to a database, it’s critical to design your application in a way that does not cause unbounded growth. Said another way, we need a way to ensure that we’re regularly <a target=\"_blank\" href=\"https://dagster.io/glossary/data-purging\">purging</a> the database of old data, so it doesn’t continue to grow forever.</p><p>We solved this by building a log archiving system that consisted of two components:</p><ul><li><strong>The write path.</strong> We built a daemon that would select log entries that were older than two weeks, copy them into a file in S3, and delete the rows from the database.</li><li><strong>The read path.</strong> Our web application would look at the time period of the logs being queried and dynamically decide to query either the database or S3.</li></ul><p>This log archiving system substantially reduced the total size of the database, massively slowed its growth, and had a negligible impact on the user experience.</p><p>The second thing we were worried about were spikes in customer log volume. We are a developer tool, and from time to time developers make mistakes and create large volumes of log spew. We needed a way to protect the database from the impact of an incident like this.</p><p>We did this by introducing a rate limiter. When a customer would log too many events of a specific type during too short of a time window, our API servers would start processing and returning a <code>429: Too Many Requests</code> HTTP response code, causing our customers to throttle their requests.</p><p>Our rate limiter has a few important characteristics:</p><ul><li><strong>It does not depend on Postgres.</strong> The rate limiter is designed first and foremost to protect Postgres, so it’s one of the only stateful pieces of our infrastructure that cannot depend on it. We store its configuration in the Kubernetes ConfigMap, and we store counts in Redis.</li><li><strong>It supports different rate limits based on the - </strong>It supports rate limiting by DB cost.** We can give individual customer deployments a certain quota of “DB-seconds” - basically, time that they can spend querying the database. If they exceed this threshold we rate limit the misbehaving deployment.</li></ul><h2>💥 Dealing with failure</h2><p>One of the big advantages of using replicated, distributed message queue systems like Kafka is the strong availability guarantees and ability to recover from failure.</p><p>What we have found so far is that, because there are fewer moving parts than a large Kafka deployment, we likely have similar uptime with our single, rock-solid Postgres DB. Additionally, modern environments like AWS RDS allow for hot standbys and quick failovers to replicas, which means failures will often result in just a few seconds of downtime.</p><p>Regardless of whether you use Postgres or a message queue, it’s very important to actually test a failover. You’ll often find misbehaving clients that do not gracefully fail.</p><h2>🙈 Things that didn’t go well</h2><figure><p><img alt=\"When using Postgres where most people would use Kafka does present some issues.\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/686706643d612bf6cb90f37e_681399f654933b29e12fbe03_67eac25a7c6c8c7a7e02a432_kafka-queue-as-dumpster-fire.png\"></p><figcaption> &#160; &#160; &#160;Monet’s famous “Dumpster Fire in Paris” (1880, probably)(1)</figcaption></figure><p>Like any big launch, things weren’t perfect.</p><ul><li><strong>ID overflows.</strong> A long time ago, we built a prototype that used 32 bit autoincrement integers as the primary key for a few - <strong>Determining rate limiting thresholds.</strong> After we built our rate limiting infrastructure, it was challenging to determine which thresholds we should set. During development, we accidentally rate limited a few customers that had bursty traffic, leading to slightly degraded service for those customers.</li><li><strong>Upsizing our DB instance.</strong> Before launch we decided to upsize our DB instance. This required us to take a brief (20 minutes or so) downtime before the launch. While there are ways to do this sort of migration with no downtime, it would require more engineering time to implement, and add more risk to the migration due to the increased complexity of the migration. After examining our customer SLAs and determining that we had plenty of headroom, we decided to give our customers two weeks notice and take this brief downtime during our scheduled maintenance window.</li><li><strong>Redis-related downtime.</strong> We weren’t able to use Postgres for everything. Specifically, we had introduced Redis for some of our less important, transient event streams because the Python queue library we used at the time did not support Postgres. Redis ended up causing a number of incidents, so we are likely going to migrate this transient queue to Postgres.</li></ul><h2>🧬 Future work</h2><p>Our current architecture is not perfect, and we will have to make improvements in the future. Here are some of the things that are bad about it:</p><ul><li>We don’t support multiple regions, which is important for some non-US customers.</li><li>While short, failovers still require taking some downtime.</li><li>It is possible for a misbehaving internal service to take down the DB for everyone.</li><li>We are wasting money by having Postgres provisioned for peak load at all times.</li></ul><p>Today these are not major problems for us, and frankly, I’m not sure how we’ll tackle these problems. Maybe we’ll grow multi-region support and buy really big Postgres boxes. Maybe we’ll move to sharded Postgres. Maybe we’ll switch to Kafka or some other distributed queue. Maybe we’ll use <a target=\"_blank\" href=\"https://www.percona.com/blog/2019/05/24/an-overview-of-sharding-in-postgresql-and-how-it-relates-to-mongodbs/\">cool Postgres features</a>. Or maybe <a target=\"_blank\" href=\"https://neon.tech/\">Neon</a>, <a target=\"_blank\" href=\"https://www.cockroachlabs.com/\">CockroachDB</a> or DynamoDB will save us.</p><p>While I don’t know what the future will hold, I do know that we will try to choose the most boring technology possible, and ground our decisions to add new technology in objective measurement.</p><p>With that said: we’d love for you to help us solve these problems! <a target=\"_blank\" href=\"https://twitter.com/floydophone\">Hit me up on Twitter</a> if you’re interested in jamming on this stuff as a full-time engineer at Dagster Labs. &#160;And if you enjoyed this blog post, don't forget to <a target=\"_blank\" href=\"https://github.com/dagster-io/dagster\">star us on github!</a>.</p><p><em>(1) Image courtesy of </em><a target=\"_blank\" href=\"https://openai.com/dall-e-2/\"><em>DALL-E 2</em></a></p><figure><p><img alt=\"The Dagster Labs logo\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/68660d11f2d00b3dcf3a6be7_681399f654933b29e12fc506_image.png\"></p></figure><p>We're always happy to hear your feedback, so please reach out to us!
