However, assets that materialize this way create an orchestration puzzle. If Dagster never executes them, how does a downstream asset know when to re-run?</p><p>The answer is creating virtual assets within your Dagster asset graph using <code>is_virtual=True</code>:</p><pre><code><span><span>customer_lifetime_value = dg.AssetSpec(\n</span></span><span><span>    key=</span><span>\"customer_lifetime_value\"</span><span>,\n</span></span><span><span>    deps=[</span><span>\"raw_orders\"</span><span>, </span><span>\"raw_customers\"</span><span>],\n</span></span><span><span>    is_virtual=</span><span>True</span><span>,\n</span></span><span><span>    metadata={</span><span>\"target_lag\"</span><span>: </span><span>\"1 minute\"</span><span>, </span><span>\"refresh_mode\"</span><span>: </span><span>\"INCREMENTAL\"</span><span>},\n</span></span><span>)\n</span><span></span></code></pre><p>This tells Dagster that an asset should be maintained alongside the rest of the asset graph, but Dagster is not responsible for the actual materialization. Declaring virtual assets works hand in hand with Dynamic Tables, where Snowflake is responsible for maintaining the data.</p><p>The important part when combining Dagster and Dynamic Tables is when downstream work should run. A Dynamic Table isn't a view that's instantly consistent with its source. It's an asynchronous cache that Snowflake refreshes on a target lag, anywhere from a minute to an hour behind the source. So the right trigger isn't \"the source changed,\" it's \"the table actually refreshed.\" A Dagster sensor watches each table's <code>last_completed_refresh</code> and fires the downstream run only once new data has landed so your feature pipeline or dashboard re-runs on fresh data every time, and never reads a table mid-lag.</p><figure><p><img alt=\"\" src=\"https://cdn.prod.website-files.com/681399f654933b29e12fb8e4/6a1854e4a31fe17648bf0f66_2753ffe8.png\"></p></figure><p>The pattern applies beyond Dynamic Tables.
