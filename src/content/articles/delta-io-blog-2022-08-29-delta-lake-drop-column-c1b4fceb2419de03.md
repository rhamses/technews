than simply removing the column via a metadata operation. Suppose you have a Delta Lake with 10 terabytes of data in 100 columns and you’d like to drop one of the columns that contains 100 GB of data.</p>\n<p>With column mapping enabled, you can drop this column by adding a metadata entry to the transaction log, which will execute in a fraction of a second.</p>\n<p>If you read in all 10 TB of data to a DataFrame, drop a column with the DataFrame API, and then rewrite all the data, the operation will take a lot longer. Simply dropping a column can be a big data processing operation.</p>\n<p>Let’s dig into the implementation detail tradeoffs in more detail because they matter in certain regulatory and cost situations.</p>\n<h2 id=\"delta-lake-drop-column-additional-considerations\">Delta Lake drop column additional considerations</h2>\n<p>Some users need to drop columns physically from disk for regulatory purposes. They can’t simply perform a metadata operation and ignore the column. The data needs to be physically deleted.</p>\n<p>If you need to wipe the column from your systems completely, then you should overwrite the existing data and then perform a vacuum operation. That’s how to physically remove the column from disk.</p>\n<p>Delta Lake stores data in Parquet files, which are columnar, so having an extra column on disk doesn’t adversely impact the performance of your queries. The dropped columns are simply ignored when queries are run. Parquet’s columnar nature allows for column pruning, which is one of the main reasons Parquet is faster than a row-based file format, like CSV.</p>\n<p>You’ll need to pay extra to store columns that are “dropped” with a metadata operation because you don’t technically remove the column from the Parquet files. When the columns are physically deleted, you don’t have to pay to store them. As we discussed before, physically dropping columns requires compute, which costs money. Compute is generally more expensive than storage. The compute vs storage tradeoffs are outside the scope of this post, but will be covered in more detail in future posts. You don’t normally need to consider these costs because they’re so minimal, but worth keeping in mind when you’re brainstorming overall cost management at a high level.</p>\n<h2 id=\"next-steps\">Next steps</h2>\n<p>This blog post has shown you how to drop columns from Delta Lake tables with <code>DROP COLUMN</code> syntax and by overwriting the existing data lake.</p>\n<p>You’ve learned about the tradeoffs between the two approaches for dropping tables. <code>DROP COLUMN</code> is a lot quicker, but it doesn’t actually physically delete the data on disk, so it may not be sufficient for certain regulatory requirements. In general, <code>DROP COLUMN</code> is preferable, but use other methods if you need to physically remove the column for GDPR compliance.</p>\n<p>Delta Lake is continuously improving and improved support for <code>DROP COLUMN</code> is just one example.
