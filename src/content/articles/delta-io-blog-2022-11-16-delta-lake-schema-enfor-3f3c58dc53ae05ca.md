contentHtml: "<div>  <p>This post teaches you about Delta Lake schema enforcement and demonstrates how it protects you from adding files with incompatible schemas to your Delta table.</p>\n<p>Parquet tables don’t support built-in schema enforcement, so they accept data with any schema, which isn’t necessarily desirable. Accidentally writing Parquet files to your data lake can be surprisingly difficult to undo.</p>\n<p>Data lakes (e.g. Parquet tables) are schema-on-read, which means execution engines need to determine the schema when running queries. Data warehouses are schema-on-write, which means they check the schema when data is written. Delta Lake offers the flexibility of data lakes, and is also schema-on-write, offering the safety and guarantees of data warehouses. Delta Lake schema enforcement is a great schema-on-write benefit provided to users.</p>\n<p>Let’s start by looking at how Parquet tables without an associated Hive metastore entry don’t prevent you from appending data with a different schema which is potentially dangerous. We will visit Parquet tables stored in the Hive metastore later.</p>\n<h2 id=\"parquet-tables-dont-have-schema-enforcement\">Parquet tables don’t have schema enforcement</h2>\n<p>This section demonstrates how Parquet tables don’t have any built-in schema enforcement, so you can mistakenly append data with a different schema to a Parquet table.</p>\n<p>Start by creating a DataFrame with <code>first_name</code> and <code>age</code> columns and write it out to a Parquet table.</p>\n<pre><code><span><span>columns </span><span>=</span><span> [</span><span>\"first_name\"</span><span>, </span><span>\"age\"</span><span>]</span></span>\n<span><span>data </span><span>=</span><span> [(</span><span>\"bob\"</span><span>, </span><span>47</span><span>), (</span><span>\"li\"</span><span>, </span><span>23</span><span>), (</span><span>\"leonard\"</span><span>, </span><span>51</span><span>)]</span></span>\n<span><span>rdd </span><span>=</span><span> spark.sparkContext.parallelize(data)</span></span>\n<span><span>df </span><span>=</span><span> rdd.toDF(columns)</span></span>\n<span></span>\n<span><span>df.write.format(</span><span>\"parquet\"</span><span>).save(</span><span>\"tmp/parquet_table1\"</span><span>)</span></span></code></pre>\n<p>Now let’s append a DataFrame with a different schema to the Parquet table. Create a DataFrame with <code>first_name</code> and <code>favorite_color</code> columns, a different schema from before, and append it to the existing Parquet table.</p>\n<pre><code><span><span>columns = [\"first_name\", \"favorite_color\"]</span></span>\n<span><span>data = [(\"sal\", \"red\"), (\"cat\", \"pink\")]</span></span>\n<span><span>rdd = spark.sparkContext.parallelize(data)</span></span>\n<span><span>df = rdd.toDF(columns)</span></span>\n<span><span></span></span>\n<span><span>df.write.mode(\"append\").format(\"parquet\").save(\"tmp/parquet_table1\")</span></span></code></pre>\n<p>PySpark lets you append a DataFrame with a different schema to your Parquet table. Different schemas in a single Parquet table will conflict, and readers will have to resolve that conflict in the future. It’s better for the query engine to throw an error if you write data with a mismatched schema by default.</p>\n<p>PySpark, unfortunately, can’t run this pre-write check when working with Parquet tables because finding the schema of the underlying Parquet table would involve checking all the files individually, which would be slow for a large Parquet table.</p>\n<p>Read in the Parquet table to a DataFrame and inspect the contents.</p>\n<pre><code><span><span>spark.read.format(\"parquet\").load(\"tmp/parquet_table1\").show()</span></span>\n<span><span></span></span>\n<span><span>+----------+----+</span></span>\n<span><span>|first_name| age|</span></span>\n<span><span>+----------+----+</span></span>\n<span><span>|   leonard|  51|</span></span>\n<span><span>|       cat|null|</span></span>\n<span><span>|       sal|null|</span></span>\n<span><span>|       bob|  47|</span></span>\n<span><span>|        li|  23|</span></span>\n<span><span>+----------+----+</span></span></code></pre>\n<p>This isn’t a great result. PySpark has encountered two different schemas when reading the Parquet files and is only showing one of them. You’d need to manually set <code>mergeSchema</code> to <code>true</code> when reading the data to see all of the data.</p>\n<pre><code><span><span>spark.read.option(\"mergeSchema\", \"true\").format(\"parquet\").load(</span></span>\n<span><span>    \"tmp/parquet_table1\"</span></span>\n<span><span>).show()</span></span>\n<span><span></span></span>\n<span><span>+----------+----+--------------+</span></span>\n<span><span>|first_name| age|favorite_color|</span></span>\n<span><span>+----------+----+--------------+</span></span>\n<span><span>|   leonard|  51|          null|</span></span>\n<span><span>|       cat|null|          pink|</span></span>\n<span><span>|       sal|null|           red|</span></span>\n<span><span>|       bob|  47|          null|</span></span>\n<span><span>|        li|  23|          null|</span></span>\n<span><span>+----------+----+--------------+</span></span></code></pre>\n<p>Again, this isn’t PySpark’s fault. PySpark is providing the best default behavior possible given the schema-on-read limitations of Parquet tables.</p>\n<p>Let’s look at how Delta Lake supports schema enforcement and provides better default behavior out of the box.</p>\n<h2 id=\"delta-lake-schema-enforcement-is-built-in\">Delta Lake schema enforcement is built-in</h2>\n<p>Let’s perform the same operations, but on a Delta Lake, and see how the default operations differ from Parquet. Start by creating a DataFrame and writing it out to a Delta table.</p>\n<pre><code><span><span>columns = [\"first_name\", \"age\"]</span></span>\n<span><span>data = [(\"bob\", 47), (\"li\", 23), (\"leonard\", 51)]</span></span>\n<span><span>rdd = spark.sparkContext.parallelize(data)</span></span>\n<span><span>df = rdd.toDF(columns)</span></span>\n<span><span></span></span>\n<span><span>df.write.format(\"delta\").save(\"tmp/delta_table1\")</span></span></code></pre>\n<p>Create another DataFrame with a different schema and attempt to append it to the existing Delta Table.</p>\n<pre><code><span><span>columns = [\"first_name\", \"favorite_color\"]</span></span>\n<span><span>data = [(\"sal\", \"red\"), (\"cat\", \"pink\")]</span></span>\n<span><span>rdd = spark.sparkContext.parallelize(data)</span></span>\n<span><span>df = rdd.toDF(columns)</span></span>\n<span><span></span></span>\n<span><span>df.write.mode(\"append\").format(\"delta\").save(\"tmp/delta_table1\")</span></span></code></pre>\n<p>Here’s the error you’ll get:</p>\n<pre><code><span><span>AnalysisException: A schema mismatch detected when writing to the Delta table (Table ID: 1f0df7a5-dda6-494f-99bc-4732d455db0b).</span></span>\n<span><span>To enable schema migration using DataFrameWriter or DataStreamWriter, please set:</span></span>\n<span><span>'.option(\"mergeSchema\", \"true\")'.</span></span>\n<span><span>For other operations, set the session configuration</span></span>\n<span><span>spark.databricks.delta.schema.autoMerge.enabled to \"true\". See the documentation</span></span>\n<span><span>specific to the operation for details.</span></span>\n<span><span></span></span>\n<span><span>Table schema:</span></span>\n<span><span>root</span></span>\n<span><span>-- first_name: string (nullable = true)</span></span>\n<span><span>-- age: long (nullable = true)</span></span>\n<span><span></span></span>\n<span><span>Data schema:</span></span>\n<span><span>root</span></span>\n<span><span>-- first_name: string (nullable = true)</span></span>\n<span><span>-- favorite_color: string (nullable = true)</span></span></code></pre>\n<p>The error message gives you a descriptive explanation of why the operation failed and two different ways to enable writing data with mismatched schemas.</p>\n<p>The default Delta Lake schema enforcement behavior is desirable. You don’t want to allow data with an unmatched schema to be added to a Delta table by default. You only want to allow for schema mismatches when the user explicitly states that’s what they want.</p>\n<h2 id=\"delta-lake-write-with-mergeschema-set-to-true\">Delta Lake write with mergeSchema set to true</h2>\n<p>You can append a DataFrame with a different schema to the Delta table by explicitly setting <code>mergeSchema</code> equal to true.</p>\n<pre><code><span><span>df.write.option(\"mergeSchema\", \"true\").mode(\"append\").format(\"delta\").save(</span></span>\n<span><span>    \"tmp/delta_table1\"</span></span>\n<span><span>)</span></span></code></pre>\n<p>Read the Delta table and inspect the contents:</p>\n<pre><code><span><span>spark.read.format(\"delta\").load(\"tmp/delta_table1\").show()</span></span>\n<span><span></span></span>\n<span><span>+----------+----+--------------+</span></span>\n<span><span>|first_name| age|favorite_color|</span></span>\n<span><span>+----------+----+--------------+</span></span>\n<span><span>|   leonard|  51|          null|</span></span>\n<span><span>|       cat|null|          pink|</span></span>\n<span><span>|       sal|null|           red|</span></span>\n<span><span>|       bob|  47|          null|</span></span>\n<span><span>|        li|  23|          null|</span></span>\n<span><span>+----------+----+--------------+</span></span></code></pre>\n<p>Note that when reading the Delta table, you don’t need to set <code>mergeSchema</code> to <code>true</code> as you did when reading the Parquet table. When reading a Parquet table with files of different schemas, you need to manually set <code>mergeSchema</code> to <code>true</code>.</p>\n<p>The Delta Lake default behavior is much better. Readers of the Parquet table need to somehow know they need to set <code>mergeSchema</code> to <code>true</code> when they read the Parquet table that contains files with different schemas, which is an unreasonable demand. Data professionals may be reading tens or hundreds of Parquet tables. They can’t be expected to keep track of when they need to set <code>mergeSchema</code> to <code>true</code> and when it’s not necessary.</p>\n<h2 id=\"delta-lake-enable-automerge-to-merge-schemas-by-default\">Delta Lake enable autoMerge to merge schemas by default</h2>\n<p>You can also set a Spark property that will enable <code>autoMerge</code> by default. Once this property is set, you don’t need to manually set <code>mergeSchema</code> to <code>true</code> when writing data with a different schema to a Delta table.</p>\n<p>Here’s how to enable <code>autoMerge</code>:</p>\n<pre><code><span><span>spark.conf.set(\"spark.databricks.delta.schema.autoMerge.enabled\", \"true\")</span></span></code></pre>\n<p>Create a DataFrame with another schema and write it to the existing Delta table.</p>\n<pre><code><span><span>columns = [\"first_name\", \"country\"]</span></span>\n<span><span>data = [(\"bill\", \"usa\"), (\"xi\", \"china\")]</span></span>\n<span><span>rdd = spark.sparkContext.parallelize(data)</span></span>\n<span><span>df = rdd.toDF(columns)</span></span>\n<span><span></span></span>\n<span><span>df.write.mode(\"append\").format(\"delta\").save(\"tmp/delta_table1\")</span></span></code></pre>\n<p>Examine the contents of the Delta table and verify that the new data was properly appended.</p>\n<pre><code><span><span>spark.read.format(\"delta\").load(\"tmp/delta_table1\").show()</span></span>\n<span><span></span></span>\n<span><span>+----------+----+--------------+-------+</span></span>\n<span><span>|first_name| age|favorite_color|country|</span></span>\n<span><span>+----------+----+--------------+-------+</span></span>\n<span><span>|   leonard|  51|          null|   null|</span></span>\n<span><span>|       cat|null|          pink|   null|</span></span>\n<span><span>|       sal|null|           red|   null|</span></span>\n<span><span>|       bob|  47|          null|   null|</span></span>\n<span><span>|      bill|null|          null|    usa|</span></span>\n<span><span>|        xi|null|          null|  china|</span></span>\n<span><span>|        li|  23|          null|   null|</span></span>\n<span><span>+----------+----+--------------+-------+</span></span></code></pre>\n<p>We can see that the data was appended and we didn’t need to set <code>mergeSchema</code> to <code>true</code> when performing the write to the Delta table.</p>\n<p><strong>But watch out!</strong></p>\n<p>Take a close look at the property that enables <code>autoMerge</code> and notice that it’s specific to Delta Lake: <code>spark.databricks.<strong>delta</strong>.schema.autoMerge.enabled</code>.</p>\n<p>This configuration property does not impact the Parquet reads. You still need to manually set <code>mergeSchema</code> to <code>true</code> when reading a Parquet table, as before, even after setting this property.</p>\n<pre><code><span><span>spark.read.option(\"mergeSchema\", \"true\").format(\"parquet\").load(</span></span>\n<span><span>    \"tmp/parquet_table1\"</span></span>\n<span><span>).show()</span></span></code></pre>\n<p>This example has demonstrated two important concepts. Let’s discuss them separately.</p>\n<h2 id=\"delta-lake-schema-enforcement-vs-schema-evolution\">Delta Lake schema enforcement vs schema evolution</h2>\n<p>Schema enforcement is a Delta Lake feature that prevents you from appending data with a different schema to a table unless you explicitly specify that the table should allow data with different schemas to be written. Parquet tables don’t support schema enforcement. Parquet users need to manually implement schema enforcement business logic as a pre-write check if they want to make sure data with a different schema doesn’t get written.</p>\n<p>Schema evolution refers to the ability of a table to adapt to different schemas over time, typically by allowing for additional columns to be added. Our example has demonstrated schema evolution, but it’s an important topic, so we’ll cover it in more depth in a separate blog post.</p>\n<h2 id=\"delta-lake-schema-enforcement-vs-constraints\">Delta Lake schema enforcement vs constraints</h2>\n<p>Schema enforcement refers to schema-level checks when data is appended to an existing table. It refers to the presence of certain columns and data types.</p>\n<p>Delta Lake also supports <a target=\"_blank\" href=\"https://docs.delta.io/latest/delta-constraints.html\">constraints</a>, which are value-level checks when data is appended. You can add a constraint that will prevent you from adding <code>null</code> values to a given column for example.</p>\n<p>Schema enforcement and constraints are related because they both check the quality of your data before writing, but they’re separate concepts. You’ll often want to apply both schema enforcement and constraints.</p>\n<h2 id=\"schema-enforcement-edge-cases\">Schema enforcement edge cases</h2>\n<p>This post covers the most common schema enforcement situation, but there are some edge cases that aren’t discussed. See <a target=\"_blank\" href=\"https://www.databricks.com/blog/2019/09/24/diving-into-delta-lake-schema-enforcement-evolution.html\">this blog post</a> for more information about schema enforcement edge cases.</p>\n<h2 id=\"why-bad-writes-can-be-hard-to-fix-in-parquet-tables\">Why bad writes can be hard to fix in Parquet tables</h2>\n<p>Bad writes are surprisingly hard to undo in Parquet tables. Suppose you perform a write operation with a mismatched schema to a partitioned Parquet table that’s stored in the cloud. The write operation outputs 500 files to different partitions.</p>\n<p>It’s not easy to identify the 500 files that were written to the Parquet table. As a matter of fact, you won’t even know how many files were written when you’re trying to debug this.</p>\n<p>Once you identify the 500 files to be deleted, you need to make sure your script to delete the bad data will not accidentally delete good data as well! Manually removing data is dangerous. A single misplaced glob string character could cause you to accidentally wipe out all your data.</p>\n<p>Manually deleting data can also break downstream ETL pipeline automation too. It’s a dangerous operation that can create a change of ETL breakages.</p>\n<p>Delta Lake provides versioned data and ACID transactions, so you don’t need to perform any Parquet table hotfixes. You can easily <a target=\"_blank\" href=\"https://delta.io/blog/2022-10-03-rollback-delta-lake-restore/\">rollback a Delta table to a prior version</a> if you ever make a mistake.</p>\n<p>Up until now, we’ve just discussed Parquet files without associated Hive metastore entries. Parquet tables stored in Hive Metastore have completely different schema enforcement default behavior.</p>\n<p>Let’s create a Parquet table in Hive Metastore and observe the schema enforcement defaults.</p>\n<pre><code><span><span>columns = [\"first_name\", \"age\"]</span></span>\n<span><span>data = [(\"bob\", 47), (\"li\", 23), (\"leonard\", 51)]</span></span>\n<span><span>rdd = spark.sparkContext.parallelize(data)</span></span>\n<span><span>df = rdd.toDF(columns)</span></span>\n<span><span></span></span>\n<span><span>df.write.format(\"parquet\").saveAsTable(\"mystery_table\")</span></span></code></pre>\n<p>Try to append some data with a different schema to the table.</p>\n<pre><code><span><span>columns = [\"first_name\", \"favorite_color\"]</span></span>\n<span><span>data = [(\"sal\", \"red\"), (\"cat\", \"pink\")]</span></span>\n<span><span>rdd = spark.sparkContext.parallelize(data)</span></span>\n<span><span>df = rdd.toDF(columns)</span></span>\n<span><span></span></span>\n<span><span>df.write.mode(\"append\").format(\"parquet\").saveAsTable(\"mystery_table\")</span></span></code></pre>\n<p>The Parquet table does not allow for data with a different schema to be appended and throws this exception:</p>\n<pre><code><span><span>AnalysisException: cannot resolve 'age' given input columns: [first_name, favorite_color]</span></span></code></pre>\n<p>Parquet tables stored in Hive Metastore have schema enforcement built-in only if you are accessing it using the table name. If you forget to use the table name and use the path directly, you can bypass schema enforcement and mess up your table. It’s impossible to bypass the Delta Lake schema enforcement. In addition, you can’t set a config property or use <code>mergeSchema</code> to use a safe schema evolution for Parquet tables. <code>mergeSchema</code> is ignored when writing to a Parquet table:</p>\n<pre><code><span><span>df.write.option(\"mergeSchema\", \"true\").mode(\"append\").format(\"parquet\").saveAsTable(</span></span>\n<span><span>    \"mystery_table\"</span></span>\n<span><span>)</span></span></code></pre>\n<p>Here’s the error that’s thrown:</p>\n<pre><code><span><span>AnalysisException: cannot resolve 'age' given input columns: [first_name, favorite_color]</span></span></code></pre>\n<p>The customizable schema enforcement offered by Delta Lake is better than the rigid schema enforcement of managed Parquet tables.</p>\n<h2 id=\"conclusion\">Conclusion</h2>\n<p>Delta Lake is built with schema enforcement out of the box, which is a great way to protect the quality of your data table.</p>\n<p>Parquet tables without Hive metastore information don’t have built-in schema enforcement, don’t allow for good merge schema defaults, and are hard to fix if a write operation goes wrong. Parquet tables stored in Hive metastore allow for schema enforcement, but it’s rigid and not as flexible as the schema enforcement offered by Delta Lake.</p>\n<p>Schema enforcement is one of the many advantages Delta Lake offers compared to Parquet tables. You can easily <a target=\"_blank\" href=\"https://delta.io/blog/2022-09-23-convert-parquet-to-delta/\">convert from Parquet to Delta Lake</a> and take advantage of these features for your workloads.</p>  </div>"
