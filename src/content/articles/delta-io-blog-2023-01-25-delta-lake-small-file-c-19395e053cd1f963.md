contentHtml: "<div>  <p>This blog post shows you how to compact small files into larger files with the Delta Lake <code>OPTIMIZE</code> command. You will learn why small file compaction is important and why it’s easier to compact small files with Delta Lake compared to regular data lakes.</p>\n<p>Small files are problematic because they cause data queries to run slowly. They require a lot of I/O overhead, which is computationally expensive. They also create large metadata transaction logs which cause planning time slowness. Delta Lake provides an <code>OPTIMIZE</code> command that lets users compact the small files into larger files, so their queries are not burdened by the small file overhead.</p>\n<p>The following diagram shows how Delta Lake can make bin packing your small files into right sized files easy:</p>\n<p><img src=\"https://delta.io/_astro/image1.Cjq8K5tu_ev2TH.webp\"></p>\n<p>Let’s see how the command works with an example.</p>\n<h2 id=\"delta-lake-small-file-compaction-with-optimize-example\">Delta Lake small file compaction with OPTIMIZE example</h2>\n<p>Create a DataFrame with 5 rows of data.</p>\n<pre><code><span><span>df = spark.range(0, 5)</span></span></code></pre>\n<p>Write this DataFrame to a Delta table in multiple files.</p>\n<pre><code><span><span>df.repartition(5).write.format(\"delta\").save(\"tmp/table1\")</span></span></code></pre>\n<p>Note: we’re using <code>repartition(5)</code>, so multiple files are output. You will normally not want to use <code>repartition(5)</code> when writing data.</p>\n<p>Take a look at the files that are persisted in storage.</p>\n<pre><code><span><span>tmp/table1</span></span>\n<span><span>├── _delta_log</span></span>\n<span><span>│   └── 00000000000000000000.json</span></span>\n<span><span>├── part-00000-4dc9742a-7c76-4527-a2c6-d7904f56d05d-c000.snappy.parquet</span></span>\n<span><span>├── part-00001-18179b66-48f0-4d47-8f21-762678a7df66-c000.snappy.parquet</span></span>\n<span><span>├── part-00002-03f9116e-189e-4e55-bfe7-d501fffe4ced-c000.snappy.parquet</span></span>\n<span><span>└── part-00003-81cad732-eeaf-4708-9111-aa2e8136e304-c000.snappy.parquet</span></span></code></pre>\n<p>One row of data per file is obviously way too small. Let’s use the <code>OPTIMIZE</code> command to compact these tiny files into fewer, larger files.</p>\n<pre><code><span><span>from delta.tables import DeltaTable</span></span>\n<span><span></span></span>\n<span><span>delta_table = DeltaTable.forPath(spark, \"tmp/table1\")</span></span>\n<span><span></span></span>\n<span><span>delta_table.optimize().executeCompaction()</span></span></code></pre>\n<p>We can see that these tiny files have been compacted into a single file. A single file with only 5 rows is still way too small of course - we’re just using this micro example to demonstrate the functionality of <code>OPTIMIZE</code>.</p>\n<p>Let’s vacuum the Delta table and list the files to demonstrate that all the data is now in a single file:</p>\n<pre><code><span><span>spark.conf.set(\"spark.databricks.delta.retentionDurationCheck.enabled\", \"false\")</span></span>\n<span><span>delta_table.vacuum(0)</span></span></code></pre>\n<p>Note: setting the retention period to zero will prevent you from being able to rollback and time travel to previous versions. We’re only doing it to demonstrate the <code>OPTIMIZE</code> command functionality.</p>\n<p>Here are the files in the Delta table post-vacuum:</p>\n<pre><code><span><span>tmp/table1</span></span>\n<span><span>├── _delta_log</span></span>\n<span><span>│   ├── 00000000000000000000.json</span></span>\n<span><span>│   └── 00000000000000000001.json</span></span>\n<span><span>└── part-00000-2b164d47-0f85-47e1-99dc-d136c784baaa-c000.snappy.parquet</span></span></code></pre>\n<p>The transaction log contains two entries. The first entry is for when the Delta table was initially created and the second entry is for the <code>OPTIMIZE</code> command. Let’s look at the contents of the <code>00000000000000000001.json</code> file.</p>\n<pre><code><span><span>{</span></span>\n<span><span>  \"add\": {</span></span>\n<span><span>    \"path\": \"part-00000-2b164d47-0f85-47e1-99dc-d136c784baaa-c000.snappy.parquet\",</span></span>\n<span><span>    \"partitionValues\": {},</span></span>\n<span><span>    \"size\": 504,</span></span>\n<span><span>    \"modificationTime\": 1671468211798,</span></span>\n<span><span>    \"dataChange\": false,</span></span>\n<span><span>    \"stats\": \"{\\\"numRecords\\\":5,\\\"minValues\\\":{\\\"id\\\":0},\\\"maxValues\\\":{\\\"id\\\":4},\\\"nullCount\\\":{\\\"id\\\":0}}\"</span></span>\n<span><span>  }</span></span>\n<span><span>}</span></span>\n<span><span>{</span></span>\n<span><span>  \"remove\": {</span></span>\n<span><span>    \"path\": \"part-00003-81cad732-eeaf-4708-9111-aa2e8136e304-c000.snappy.parquet\",</span></span>\n<span><span>    \"deletionTimestamp\": 1671468210066,</span></span>\n<span><span>    \"dataChange\": false,</span></span>\n<span><span>    \"extendedFileMetadata\": true,</span></span>\n<span><span>    \"partitionValues\": {},</span></span>\n<span><span>    \"size\": 478</span></span>\n<span><span>  }</span></span>\n<span><span>}</span></span>\n<span><span>The other small files are also removed…</span></span></code></pre>\n<p>The <code>OPTIMIZE</code> command tombstoned all of the small data files and added a larger file with all the compacted data. Notice that <code>dataChange</code> is set to <code>false</code> for all the files that are added and removed.</p>\n<p>A compaction operation does not add any new data to the Delta table. It just rearranges existing data from small files into larger files. This is useful when you have downstream jobs that watch your Delta table and incrementally update when new files arrive. The <code>dataChange</code> flag differentiates between data that’s been rearranged into larger files for compaction purposes and brand new data that’s been ingested into your Delta table.</p>\n<p>Let’s take a look at the file size that Delta Lake targets when <code>OPTIMIZE</code> is run.</p>\n<h2 id=\"delta-lake-target-file-size\">Delta Lake target file size</h2>\n<p>Delta Lake targets 1 GB files when <code>OPTIMIZE</code> is run. The 1 GB default file size was selected from years of customer usage showing that this file size works well on common computational instances.</p>\n<p>You can configure this property by setting the <code>spark.databricks.delta.optimize.maxFileSize</code> property. This enables you to set a target file size that’s different from the default.</p>\n<p>The default file size of 1 GB has proven robust after years of testing on lots of Spark workloads. You should stick with the default unless you have a compelling reason to use a different file size.</p>\n<h2 id=\"delta-lake-optimize-with-predicate-filtering\">Delta Lake OPTIMIZE with predicate filtering</h2>\n<p>You can specify predicates to only compact a subset of your data. This is a good idea especially if you’re running a compaction job on the same dataset every day. You don’t need to waste computational resources analyzing data files that have already been compacted.</p>\n<p>Suppose you have a Delta table that’s partitioned by day and you have a daily job that compacts the small files. Here’s how to only compact newly added files that were added the previous day, in this case on November 18, 2021.</p>\n<pre><code><span><span>deltaTable.optimize().where(\"date='2021-11-18'\").executeCompaction()</span></span></code></pre>\n<p>This is a good way to structure a compaction job on a Delta table that’s updated incrementally because it saves you from having to scan files that have already been compacted. You should compact the minimal dataset whenever possible.</p>\n<h2 id=\"delta-lake-small-file-compaction-pre-delta-12\">Delta Lake small file compaction pre-Delta 1.2</h2>\n<p><code>OPTIMIZE</code> was added to Delta Lake as of version 1.2 (the Python bindings were added in version 2.0). Here’s how you can manually compact small files in Delta Lake versions prior to version 1.2. Let’s create some files to demonstrate with an example.</p>\n<p>Create a separate Delta table with a bunch of small files:</p>\n<pre><code><span><span>df = spark.range(0, 5)</span></span>\n<span><span>df.repartition(5).write.format(\"delta\").save(\"tmp/table2\")</span></span></code></pre>\n<p>Here’s how to compact the small files without using the <code>OPTIMIZE</code> command:</p>\n<pre><code><span><span>path = \"tmp/table2\"</span></span>\n<span><span>numFiles = 1</span></span>\n<span><span></span></span>\n<span><span>(</span></span>\n<span><span>    spark.read.format(\"delta\")</span></span>\n<span><span>    .load(path)</span></span>\n<span><span>    .repartition(numFiles)</span></span>\n<span><span>    .write.option(\"dataChange\", \"false\")</span></span>\n<span><span>    .format(\"delta\")</span></span>\n<span><span>    .mode(\"overwrite\")</span></span>\n<span><span>    .save(path)</span></span>\n<span><span>)</span></span></code></pre>\n<p>Let’s vacuum the table to demonstrate that the data has been compacted in a single file:</p>\n<pre><code><span><span>delta_table = delta.DeltaTable.forPath(spark, \"tmp/table2\")</span></span>\n<span><span>delta_table.vacuum(0)</span></span></code></pre>\n<p>There is only one remaining data file:</p>\n<pre><code><span><span>tmp/table2</span></span>\n<span><span>├── _delta_log</span></span>\n<span><span>│   ├── 00000000000000000000.json</span></span>\n<span><span>│   └── 00000000000000000001.json</span></span>\n<span><span>└── part-00000-2f60eca6-07ba-4f66-a89c-eab5caa94d25-c000.snappy.parquet</span></span></code></pre>\n<p>Manually compacting the files is inefficient and error prone.</p>\n<ul>\n<li>The user needs to correctly set the number of files. Figuring out the optimal number of files you should use when compacting your Delta table isn’t easy.</li>\n<li>The user needs to rewrite the entire dataset, including the small files and the large files. This can be really inefficient, especially if most data is in right-sized files and there are only some small files.</li>\n</ul>\n<p>The <code>OPTIMIZE</code> command provides a much better user experience.</p>\n<h2 id=\"what-causes-small-files\">What causes small files?</h2>\n<p>There are three principle causes of small data files:</p>\n<ul>\n<li><strong>User error</strong>: Users can repartition datasets and write out data with any number of files. Suppose you have a 500 GB dataset. A user could write out that dataset into 100,000 files by using <code>repartition(100000)</code>. That would create a small file problem.</li>\n<li><strong>Hive-partitioned or over-partitioned datasets</strong>: Disk partitioning requires splitting data by partition keys into different files. If the dataset is partitioned on a high-cardinality column or if there are deeply nested partitions, then more small files will be created. Suppose you have a 1 GB dataset. If that’s being written to a non-partitioned table, then the data can be written as a single file. If the data is being written to a Hive partitioned table with a partition key that has 5,000 unique values, then up to 5,000 files will be created when making the write.</li>\n<li><strong>Tables that are incrementally updated frequently</strong>: The more frequently a table gets updated, the more small files that will be created. A job that updates a table every 2 minutes will create more small files than a job that runs every 8 hours. Remember that some tables are updated frequently to provide freshness to queries.</li>\n</ul>\n<p>The ideal way to “solve” the small file problem is by architecting systems that don’t create small files in the first place. Sometimes small files are inevitable given business and query latency requirements, but other times they can be avoided. For example, you may be able to avoid a small file problem caused by Hive-style partitioning by instead using Z ORDER which can provide similar file skipping capabilities.</p>\n<p>Let’s dig into the tradeoffs between end-to-end query latency and small files.</p>\n<h2 id=\"etl-latency-vs-small-files-tradeoff\">ETL latency vs small files tradeoff</h2>\n<p>Suppose you have an ETL pipeline to ingest 5GB of data a day. The streaming data is ingested into a Delta table and queried by end users via a BI application.</p>\n<p>If the incremental update job is set up to run every 5 minutes, then the pipeline will create at least 288 small files per day.</p>\n<p>If the incremental update job is set up to run on a daily basis, then it can be configured to append five 1GB files. This setup won’t create any small files.</p>\n<p>The optimal solution depends on the requirements of the BI user:</p>\n<ul>\n<li>If the BI user needs to refresh their dashboard throughout the day and make decisions based on recent data, then frequent updates are required.</li>\n<li>If the BI user only loads the dashboard once a day to generate a report, then updates every 5 minutes aren’t needed.</li>\n</ul>\n<p>ETL pipelines with longer update latencies have fewer small files. In general, you should architect ETL pipelines with the highest latency that’s acceptable for the business requirements to minimize the number of small files created.</p>\n<h2 id=\"when-to-run-optimize-on-delta-lake\">When to run OPTIMIZE on Delta Lake</h2>\n<p>The <code>OPTIMIZE</code> command is used to solve the small file problem and should be run whenever there are enough small files to justify running the compaction operation.</p>\n<p>If there are only a few small files, then you don’t need to run <code>OPTIMIZE</code>. The small file overhead only starts to become a performance issue where there are lots of small files.</p>\n<p>You also don’t need to run <code>OPTIMIZE</code> on data that’s already been compacted. If you have an incremental update job, make sure to specify predicates to only compact the newly added data.</p>\n<h2 id=\"why-delta-lake-optimize-is-better-than-data-lake-compaction\">Why Delta Lake OPTIMIZE is better than data lake compaction</h2>\n<p>Compacting small files is a surprisingly hard challenge for data lakes.</p>\n<ul>\n<li>While you’re running the compaction operation, your data lake will be in an unusable state for readers. Data lakes don’t support ACID transactions.</li>\n<li>Running the compaction operation is risky on a data lake. You need to manually delete the small files after they’ve been compacted which is error-prone.</li>\n<li>Data lakes don’t have a <code>dataChange=false</code> flag to differentiate files that contain new data from files that contain existing data that was just compacted into new files. Downstream ETL processes that watch for new data files will reprocess compacted data files just as they would with new data for data lakes.</li>\n</ul>\n<p>Like most data operations, the <code>OPTIMIZE</code> command benefits greatly from the ACID transactions supported by Delta Lake. With Delta Lake you get a safe way to compact small files with a single command. With data lakes, you have to code custom logic and compact small files in a dangerous manner.</p>\n<h2 id=\"delta-lake-bin-packing\">Delta Lake bin packing</h2>\n<p>Compacting small files is an example of the bin packing problem: figuring out how to gather items of unequal sizes into a finite number of containers.</p>\n<p>Bin packing is the general computer science challenge of building an algorithm that efficiently organizes the files into equal size containers. The Delta Lake <code>OPTIMIZE</code> command uses a bin packing algorithm to compact small files into right-sized files. Here’s how the bin packing algorithm works at a high level:</p>\n<ul>\n<li>filter all files for only files &lt; maxFileSize (default 1GB)</li>\n<li>sequentially add them to “bins” until the bin is ~1GB</li>\n<li>everytime you overflow a bin it starts a new bin</li>\n<li>this happens per partition</li>\n</ul>\n<h2 id=\"delta-lake-optimize-vs-z-order\">Delta Lake OPTIMIZE vs Z ORDER</h2>\n<p>Delta Lake’s OPTIMIZE and Z ORDER commands serve completely different purposes, but they’re often used in conjuction.</p>\n<p>Optimize is used to compact the small files in a Delta table. Z ORDER is used to intelligently sort the data so it’s more likely that files are skipped when common queries are run.</p>\n<p>See <a target=\"_blank\" href=\"https://docs.delta.io/latest/optimizations-oss.html#z-ordering-multi-dimensional-clustering\">the documentation on Z ORDER for more information</a>.</p>\n<h2 id=\"conclusion\">Conclusion</h2>\n<p>This post taught you how to compact your small data files, why this will improve your query times, and how Delta Lake makes this operation easy with the <code>OPTIMIZE</code> command.</p>\n<p>You learned about common causes of small data files and how to architect ETL pipelines that are less likely to create small data files.</p>\n<p>You also learned about why Delta Lake is a great technology for small file compaction. Delta Lake’s ACID transactions make the <code>OPTIMIZE</code> command safe. The Delta Lake <code>dataChange</code> flag also lets you architect pipelines to distinguish between data that’s recently been ingested and “new” data files that actually just contains old data you already processed.</p>\n<p><code>OPTIMIZE</code> is an important performance optimization and you’re now equipped to harness the full power of the command.</p>  </div>"
