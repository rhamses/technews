contentHtml: "<div>  <p>This post shows how to time travel between different versions of a Delta table with Delta Lake. You can time travel by table version or by timestamp. You’ll learn about the benefits of time travel and why it’s an essential feature for production data workloads.</p>\n<p>You’ll also learn how the vacuum command can limit your ability to time travel. You must develop an optimal vacuum strategy that caters to your time travel needs.</p>\n<p>Let’s dive into an example. If you’d like to follow along, all <a target=\"_blank\" href=\"https://github.com/MrPowers/delta-examples/blob/master/notebooks/pyspark/time-travel.ipynb\">code snippets are in this notebook</a>.</p>\n<h2 id=\"delta-lake-time-travel-by-version-with-python-example\">Delta Lake time travel by version with Python example</h2>\n<p>Let’s make a Delta table with the following three versions:</p>\n<p><img src=\"https://delta.io/_astro/image1.MTwhZ2LH_Z1ni0S2.webp\"></p>\n<p>We’ll build this Delta table with these three versions by creating the Delta table, appending some data, and then performing an overwrite operation.</p>\n<p>Let’s start by creating the Delta table to create Version 0:</p>\n<pre><code><span><span>df = spark.range(0, 3)</span></span>\n<span><span>df.repartition(1).write.format(\"delta\").save(\"tmp/some_nums\")</span></span></code></pre>\n<p>Note: We’re using <code>repartition(1)</code> to output a single file to simplify this demonstration. You usually shouldn’t output a single file.</p>\n<p>Now append some data to the Delta table, which will create Version 1:</p>\n<pre><code><span><span>df = spark.range(8, 11)</span></span>\n<span><span>df.repartition(1).write.mode(\"append\").format(\"delta\").save(\"tmp/some_nums\")</span></span></code></pre>\n<p>Finally, overwrite the Delta table which will create Version 2 of the Delta table:</p>\n<pre><code><span><span>df = spark.createDataFrame([(55,), (66,), (77,)]).toDF(\"id\")</span></span>\n<span><span>df.repartition(1).write.mode(\"overwrite\").format(\"delta\").save(\"tmp/some_nums\")</span></span></code></pre>\n<p>Let’s read in the latest version of the Delta table to confirm it only contains the Version 2 data:</p>\n<pre><code><span><span>spark.read.format(\"delta\").load(\"tmp/some_nums\").show()</span></span>\n<span><span></span></span>\n<span><span>+---+</span></span>\n<span><span>| id|</span></span>\n<span><span>+---+</span></span>\n<span><span>| 55|</span></span>\n<span><span>| 66|</span></span>\n<span><span>| 77|</span></span>\n<span><span>+---+</span></span></code></pre>\n<p>Let’s look at some examples where we’re time traveling to different versions of the data. Here’s how to time travel back to Version 0 and read an earlier version of the Delta table:</p>\n<pre><code><span><span>spark.read.format(\"delta\").option(\"versionAsOf\", \"0\").load(\"tmp/some_nums\").show()</span></span>\n<span><span></span></span>\n<span><span>+---+</span></span>\n<span><span>| id|</span></span>\n<span><span>+---+</span></span>\n<span><span>|  0|</span></span>\n<span><span>|  1|</span></span>\n<span><span>|  2|</span></span>\n<span><span>+---+</span></span></code></pre>\n<p>Now read Version 1 of the Delta table:</p>\n<pre><code><span><span>spark.read.format(\"delta\").option(\"versionAsOf\", \"1\").load(\"tmp/some_nums\").show()</span></span>\n<span><span></span></span>\n<span><span>+---+</span></span>\n<span><span>| id|</span></span>\n<span><span>+---+</span></span>\n<span><span>|  8|</span></span>\n<span><span>|  9|</span></span>\n<span><span>| 10|</span></span>\n<span><span>|  0|</span></span>\n<span><span>|  1|</span></span>\n<span><span>|  2|</span></span>\n<span><span>+---+</span></span></code></pre>\n<p>We’ve already seen how Delta Lake will read in the latest version of the table by default when <code>versionAsOf</code> is not explicitly set. You can also explicitly read the latest version of the Delta table (Version 2 in this case):</p>\n<pre><code><span><span>spark.read.format(\"delta\").option(\"versionAsOf\", \"2\").load(\"tmp/some_nums\").show()</span></span>\n<span><span></span></span>\n<span><span>+---+</span></span>\n<span><span>| id|</span></span>\n<span><span>+---+</span></span>\n<span><span>| 55|</span></span>\n<span><span>| 66|</span></span>\n<span><span>| 77|</span></span>\n<span><span>+---+</span></span></code></pre>\n<p>Delta Lake makes it easy to time travel and read different versions of your Delta table. You can use the <code>history</code> command to show all versions of the Delta table and the associated timestamps.</p>\n<pre><code><span><span>from delta.tables import DeltaTable</span></span>\n<span><span></span></span>\n<span><span>delta_table = DeltaTable.forPath(spark, \"tmp/some_nums\")</span></span>\n<span><span>delta_table.history().select(\"version\", \"timestamp\", \"operation\").show(truncate=False)</span></span></code></pre>\n<p>Here’s the table that’s displayed:</p>\n<pre><code><span><span>+-------+-----------------------+---------+</span></span>\n<span><span>|version|timestamp              |operation|</span></span>\n<span><span>+-------+-----------------------+---------+</span></span>\n<span><span>|2      |2023-01-31 06:27:08.508|WRITE    |</span></span>\n<span><span>|1      |2023-01-31 06:26:56.895|WRITE    |</span></span>\n<span><span>|0      |2023-01-31 06:26:35.825|WRITE    |</span></span>\n<span><span>+-------+-----------------------+---------+</span></span></code></pre>\n<p>Let’s learn more about how Delta Lake is architected to allow for this feature.</p>\n<h2 id=\"delta-lake-time-travel-intuition\">Delta Lake time travel intuition</h2>\n<p>Delta Lake stores data in Parquet files and information about transactions in the <code>_delta_log</code> metadata folder.</p>\n<p>The <code>_delta_log</code> metadata folder tracks the Parquet data files that are added and removed from the Delta table for each transaction.</p>\n<p>The following diagram shows the files added and removed for each transaction in our example.</p>\n<p><img src=\"https://delta.io/_astro/image2.BT4nGTzG_Zh8vsP.webp\"></p>\n<p>Let’s look at how Delta Lake will inspect the transaction log and figure out which files should be read for each version:</p>\n<ul>\n<li>For Version 0, Delta Lake just needs to read File A</li>\n<li>Delta Lake will see both File A and File B should be read for Version 1</li>\n<li>For Version 2, Delta Lake will see that File A, File B, and File C were added, but File A and File B were removed, so only File C should be read. Delta Lake will only read File C and skip the other files when reading Version 2.</li>\n</ul>\n<p>Delta Lake is intelligent about reading files by consulting the transaction log. Query engines need to perform expensive file listing operations when reading files stored in data lakes. It’s much more efficient to intelligently query the transaction log to fetch the relevant files for a given version.</p>\n<h2 id=\"delta-lake-time-travel-by-timestamp\">Delta Lake time travel by timestamp</h2>\n<p>Delta Lake also lets you time travel based on timestamp.</p>\n<pre><code><span><span>spark.read.format(\"delta\").option(\"timestampAsOf\", \"2019-01-01\").load(\"tmp/some_nums\")</span></span></code></pre>\n<p>Time travel by timestamp is a great way to visit your data at an earlier state without having to figure out the exact version.</p>\n<p>Here’s an important detail worth knowing if you’re time-traveling based on timestamps and copying Delta tables to new locations. Delta Lake time-based time travel relies on file timestamps. When you copy a Delta Lake table to another location, it’s possible that the file timestamps will change, which will change the behavior of your time-based time travel code. So when copying Delta tables to another location, it’s crucial to retain the existing file timestamps.</p>\n<p>Changing timestamps when you copy files isn’t a factor you need to consider if you’re time-traveling by version number of course.</p>\n<h2 id=\"delta-lake-time-travel-sql-example\">Delta Lake time travel SQL example</h2>\n<p>Here’s the SQL syntax to time travel to a specific version:</p>\n<pre><code><span><span>SELECT count(*) FROM my_table VERSION AS OF 5238</span></span></code></pre>\n<p>And here’s the SQL syntax to time travel to a specific timestamp:</p>\n<pre><code><span><span>SELECT count(*) FROM my_table TIMESTAMP AS OF \"2019-01-01\"</span></span></code></pre>\n<p>Time travel works the same whether you’re using the SQL or Python APIs. The only difference is the syntax.</p>\n<h2 id=\"delta-lake-time-travel-after-vacuum\">Delta Lake time travel after vacuum</h2>\n<p>Delta Lake supports a <code>VACUUM</code> command that removes files from storage that are older than the retention period and have been marked for removal in the transaction log.</p>\n<p>If the <code>VACUUM</code> command removes a file from storage that a given Delta table version depends on you will no longer be able to time travel to that version of the Delta table.</p>\n<p>You need to set the retention period of your Delta tables to suit your time travel needs for a given table. Some tables should never be vacuumed because you want to retain access to every version. Other tables should be vacuumed frequently to save on storage costs. See <a target=\"_blank\" href=\"https://delta.io/blog/2023-01-03-delta-lake-vacuum-command/\">this blog post on the vacuum command</a> for more details.</p>\n<p>You should make sure to set a vacuum strategy for your tables that’s optimized for your time travel needs.</p>\n<h2 id=\"delta-lake-restore-vs-time-travel\">Delta Lake restore vs. time travel</h2>\n<p>Delta Lake supports a restore command that makes it easy to bring back a prior version of the Delta table to be considered the “current version”. See <a target=\"_blank\" href=\"https://delta.io/blog/2022-10-03-rollback-delta-lake-restore/\">this blog post on the RESTORE command</a> for more information.</p>\n<p>You have to specify the version every time you time travel because it doesn’t change the current version of the Delta table like RESTORE. Suppose a Delta table has three versions, and you time-travel back to Version 0. When you read the latest version of the Delta table again, it will still default back to the current version, even after you’ve time traveled</p>\n<p>RESTORE is better when you want to reset the current version of the table. For example, restore is great for when you ingest bad data and would like to undo the append for other readers.</p>\n<h2 id=\"delta-lake-time-travel-vs-data-lake-support\">Delta Lake time travel vs. data lake support</h2>\n<p>Delta Lake makes it easy to time travel between different versions of a Delta table. It’s a straightforward operation that’s a natural extension of the Delta Lake transaction log.</p>\n<p>Data lakes do not support time travel. When you’re reading a data lake, you always have to read the latest version. Build-in time travel is an important feature Delta Lake offers compared to data lakes.</p>\n<h2 id=\"conclusion\">Conclusion</h2>\n<p>This post taught you how to time travel between different versions of a Delta table by version number and by timestamp.</p>\n<p>You learned how the Delta transaction log makes it easy to implement time travel and how deleting historical files in your Delta table can limit your ability to time travel to specific versions.</p>\n<p>You need to be careful to set the retention period for your Delta tables so that you can time travel, but also with the right amount of flexibility to vacuum files and save on storage costs (if that’s important). See <a target=\"_blank\" href=\"https://delta.io/blog/2023-01-03-delta-lake-vacuum-command/\">the vacuum blog post</a> for more details.</p>\n<p>See <a target=\"_blank\" href=\"https://www.databricks.com/blog/2019/02/04/introducing-delta-time-travel-for-large-scale-data-lakes.html\">here for another blog on time travel</a> that describes real-world use cases for this functionality.</p>  </div>"
