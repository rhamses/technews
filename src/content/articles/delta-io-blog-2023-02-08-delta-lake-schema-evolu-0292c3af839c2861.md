Delta Lake does not allow you to append data with mismatched schema by default. This feature is called schema enforcement. It previously only had two columns.</p>\n<p>The “missing” data in the <code>country</code> column for the existing data is simply marked as <code>null</code> when new columns are added.</p>\n<p>Setting <code>mergeSchema</code> to <code>true</code> every time you’d like to write with a mismatched schema can be tedious. Let’s look at how to enable schema evolution by default.</p>\n<h2 id=\"delta-lake-schema-evolution-with-automerge\">Delta Lake schema evolution with autoMerge</h2>\n<p>You can enable schema evolution by default by setting <code>autoMerge</code> to <code>true</code>:</p>\n<pre><code><span><span>spark.conf.set(\"spark.databricks.delta.schema.autoMerge.enabled\", \"true\")</span></span></code></pre>\n<p>With <code>autoMerge</code> set to <code>true</code>, you can append DataFrames with different schemas without setting <code>mergeSchema</code>.   leonard|  51|   null|</span></span>\n<span><span>|       bob|  47|   null|</span></span>\n<span><span>|        li|  23|   null|</span></span>\n<span><span>|   sabrina|null|   null| # concepts:</p>\n<ul>\n<li><code>autoMerge</code> allows you to avoid explicitly setting <code>mergeSchema</code> every time you append data</li>\n<li>Schema evolution also lets you append DataFrames age|country|  id|</span></span>\n<span><span>+----------+----+-------+----+</span></span>\n<span><span>|   jordana|  26| brasil|null|</span></span>\n<span><span>|     frank|  68|    usa|null|</span></span>\n<span><span>|   leonard|  51|   null|null|</span></span>\n<span><span>|       bob|  47|   null|null|</span></span>\n<span><span>|        li|  23| overlap at all. As you can see, schema evolution is very permissive.</p>\n<p>If you don’t want to allow for appends with zero schema overlap, you may want to add some “pre-append checks”.</p>\n<h2 id=\"why-use-delta-lake-schema-evolution\">Why use Delta Lake schema evolution</h2>\n<p>You should enable Delta Lake schema evolution to allow for the schema of your table to change without doing a full data rewrite.</p>\n<p>As the preceding examples have shown, schema evolution is quite permissive and will allow you to append DataFrames with any schema to your existing Delta table. The DataFrames can contain extra columns, missing columns, or any combination thereof.</p>\n<p>Schema evolution is typically best used when you want to add a couple of rows or write data without a couple of rows, not for wholesale schema changes. This feature offers a lot of flexibility, so you must use it carefully.</p>\n<h2 id=\"when-to-avoid-delta-lake-schema-evolution\">When to avoid Delta Lake schema evolution</h2>\n<p>Schema enforcement is a powerful Delta Lake feature and is generally a smart default. When appending data to your Delta table, you generally want the schema of the new data to match the existing table.</p>\n<p>You should not enable schema evolution if you want the schema enforcement guarantee checks. Schema enforcement checks are disabled when schema evolution is enabled. So only enable these checks when you want them.</p>\n<p>Schema evolution can break downstream processes. You should ensure all downstream readers will still work before evolving the schema in your production pipelines.</p>\n<h2 id=\"delta-lake-mergeschema-vs-automerge\">Delta Lake mergeSchema vs autoMerge</h2>\n<p>Delta Lake <code>mergeSchema</code> only applies for a single write to a single table. It’s a good option if you only want to enable schema evolution for a single table.</p>\n<p>Delta Lake’s <code>autoMerge</code> option activates schema evolution for writes to any table. This can be quite convenient but also dangerous. Remember that schema evolution is rather permissive - it allows you to append data with any schema to any table without restrictions.</p>\n<p>Only enable <code>autoMerge</code> if you truly need that amount of flexibility. If you only want to enable schema evolution for a single job or a single table, <code>mergeSchema</code> is safer.</p>\n<h2 id=\"schema-evolution-for-parquet-tables\">“Schema evolution” for Parquet tables</h2>\n<p>Parquet tables don’t support schema evolution. Let’s see how they behave by default.</p>\n<p>Create a DataFrame with <code>city</code> and <code>country</code> columns and write it to a Parquet table.</p>\n<pre><code><span><span>df = spark.createDataFrame([(\"delhi\", \"india\"), (\"baltimore\", \"usa\")]).toDF(</span></span>\n<span><span>    \"city\", \"country\"</span></span>\n<span><span>)</span></span>\n<span><span></span></span>\n<span><span>df.write.format(\"parquet\").mode(\"append\").save(\"tmp/some_cities\")</span></span></code></pre>\n<p>Read the Parquet table and view the contents.</p>\n<pre><code><span><span>spark.read.format(\"parquet\").load(\"tmp/some_cities\").show()</span></span>\n<span><span></span></span>\n<span><span>+---------+-------+</span></span>\n<span><span>|     city|country|</span></span>\n<span><span>+---------+-------+</span></span>\n<span><span>|baltimore|    usa|</span></span>\n<span><span>|    delhi|  india|</span></span>\n<span><span>+---------+-------+</span></span></code></pre>\n<p>Now create another DataFrame with just an <code>id</code> column and append it to the Parquet table.</p>\n<pre><code><span><span>df = spark.range(0, 3)</span></span>\n<span><span>df.write.format(\"parquet\").mode(\"append\").save(\"tmp/some_cities\")</span></span></code></pre>\n<p>Note that the Parquet table simply accepts the appended data with a mismatched schema. Parquet has no notion of schema enforcement. Any data can get appended to a Parquet table.</p>\n<p>Now read in the Parquet table:</p>\n<pre><code><span><span>spark.read.format(\"parquet\").load(\"tmp/some_cities\").show()</span></span>\n<span><span></span></span>\n<span><span>+----+</span></span>\n<span><span>|  id|</span></span>\n<span><span>+----+</span></span>\n<span><span>|null|</span></span>\n<span><span>|null|</span></span>\n<span><span>|   0|</span></span>\n<span><span>|   1|</span></span>\n<span><span>|   2|</span></span>\n<span><span>+----+</span></span></code></pre>\n<p>That doesn’t look right!</p>\n<p>It’s also not the result you’ll always get. You may run the code again and get this result:</p>\n<pre><code><span><span>spark.read.format(\"parquet\").load(\"tmp/some_cities\").show()</span></span>\n<span><span></span></span>\n<span><span>+---------+-----------+</span></span>\n<span><span>|     city|    country|</span></span>\n<span><span>+---------+-----------+</span></span>\n<span><span>|  toronto|     canada|</span></span>\n<span><span>|   manila|philippines|</span></span>\n<span><span>|baltimore|        usa|</span></span>\n<span><span>|    delhi|      india|</span></span>\n<span><span>|     null|       null|</span></span>\n<span><span>|     null|       null|</span></span>\n<span><span>|     null|       null|</span></span>\n<span><span>+---------+-----------+</span></span></code></pre>\n<p>Spark is just grabbing the schema from the first file it encounters and assumes that it’s the schema for all the other files. It grabs the schema from the file with the <code>id</code> column in this example. It’s simply ignoring the <code>city</code> and <code>country</code> columns from the other files because it thinks they don’t exist.</p>\n<p>Spark intentionally grabs the schema from a single Parquet file when figuring out the schema. Reading the schema from all the files would be an expensive computation and slow down all reads.</p>\n<p>You can force Spark to read the schemas of all the Parquet files by setting the <code>mergeSchema</code> option when performing the read.</p>\n<pre><code><span><span>spark.read.format(\"parquet\").option(\"mergeSchema\", \"true\").load(</span></span>\n<span><span>    \"tmp/some_cities\"</span></span>\n<span><span>).show()</span></span>\n<span><span></span></span>\n<span><span>+----+---------+-------+</span></span>\n<span><span>|  id|     city|country|</span></span>\n<span><span>+----+---------+-------+</span></span>\n<span><span>|null|baltimore|    usa|</span></span>\n<span><span>|null|    delhi|  india|</span></span>\n<span><span>|   0|     null|   null|</span></span>\n<span><span>|   1|     null|   null|</span></span>\n<span><span>|   2|     null|   null|</span></span>\n<span><span>+----+---------+-------+</span></span></code></pre>\n<p>Note: The <code>mergeSchema</code> option when reading Parquet files is completely different than the <code>mergeSchema</code> option when writing Delta tables!</p>\n<p>When Spark reads the Parquet files with <code>mergeSchema</code> set to <code>true</code>, you get a similar result as when reading the Delta table, but it’s a lot more annoying.</p>\n<p>Data professionals usually read multiple Parquet tables and they shouldn’t be expected to figure out when <code>mergeSchema</code> is necessary. You don’t want to enable it by default because that’ll slow down all reads, even when it’s not necessary. The individuals that write mismatched schemas to Parquet lakes might forget to inform all the readers. It’s a dangerous design pattern to implement.</p>\n<p><strong>Reiterating an important note</strong>: The the <code>mergeSchema</code> in <code>spark.read.format(\"parquet\").option(\"mergeSchema\", \"true\")</code> is completely different from the <code>mergeSchema</code> in <code>df.write.format(\"delta\").option(\"mergeSchema\", \"true\").</code> One is for enabling schema resolution when reading Parquet lakes with different schemas. Another is to allow for schema evolution when writing to Delta tables. Don’t get them confused.</p>\n<h2 id=\"delta-lake-schema-evolution-vs-data-lakes\">Delta Lake schema evolution vs. data lakes</h2>\n<p>Data lakes are schema on read, which means the schema is inferred when reading data. As we can see, schema on read is a disadvantage when supporting data with changing schema. You either need to manually track which data tables have changing schemas or always set <code>mergeSchema</code> to <code>true</code> when reading data lakes, which will slow down all reads.</p>\n<p>Delta Lake tables are schema on write, which means that the schema is already defined when the data is read. Delta Lakes are aware when data with other schemas have been appended. Delta Lake works out the final schema for the table by querying the transaction log, not by opening all the individual Parquet files. This makes schema evolution with Delta tables fast and more convenient for the user.</p>\n<p>Delta Lake tables have several advantages over data lakes, and schema evolution is just one of the many benefits.</p>\n<h2 id=\"conclusion\">Conclusion</h2>\n<p>This post taught you how to enable schema evolution with Delta Lake and the benefits of managing Delta tables with flexible schemas.</p>\n<p>You learned about two ways to allow for schema evolution and the tradeoffs. It’s generally best to use <code>mergeSchema</code> for schema evolution unless you want to enable it globally for all tables.</p>\n<p>You also saw how Delta Lake offers real schema evolution. Parquet tables offer something similar to schema evolution, but it requires a read-time setting, which is inconvenient for the user. It’s also inefficient because it requires inspecting all the Parquet files before the read can even take place. This is one of the many examples where Delta Lake is more powerful than data lakes.</p>  </div>"
