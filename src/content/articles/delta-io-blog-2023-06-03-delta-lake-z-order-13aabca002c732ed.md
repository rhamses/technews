contentHtml: "<div>  <p>This blog post explains how to Z ORDER Delta tables and how this design pattern can significantly speed up your queries.</p>\n<p>Z Ordering your data reorganizes the data in storage and allows certain queries to read less data, so they run faster. When your data is appropriately ordered, more files can be skipped.</p>\n<p>Z Order is particularly important for the ordering of multiple columns. If you only need to order by a single column, then simple sorting suffices. If there are multiple columns, but we always/only query a common prefix of those columns, then hierarchical sorting suffices. Z Ordering is good when querying on one or multiple columns. You’ll see a concrete example later to further illustrate when Z Ordering fits well.</p>\n<p>Let’s start with a simple example and then explore how to develop an optimal Z ORDER strategy for your data. See <a target=\"_blank\" href=\"https://github.com/delta-io/delta-examples/blob/master/notebooks/pyspark/delta-z-order.ipynb\">this notebook</a> if you would like to follow along with the computations.</p>\n<h2 id=\"delta-lake-z-order-example\">Delta Lake Z Order Example</h2>\n<p>Let’s use a data set from the h2o benchmarks and demonstrate how Z Ordering the data can make a query faster.</p>\n<p>Suppose you have a one billion-row data set with nine columns as follows:</p>\n<pre><code><span><span>+-----+-----+------------+---+---+------+---+---+---------+</span></span>\n<span><span>|  id1|  id2|         id3|id4|id5|   id6| v1| v2|       v3|</span></span>\n<span><span>+-----+-----+------------+---+---+------+---+---+---------+</span></span>\n<span><span>|id016|id046|id0000109363| 88| 13|146094|  4|  6|18.837686|</span></span>\n<span><span>|id039|id087|id0000466766| 14| 30|111330|  4| 14|46.797328|</span></span>\n<span><span>|id095|id078|id0000584803| 56| 92|213320|  1|  9|63.464315|</span></span>\n<span><span>+-----+-----+------------+---+---+------+---+---+---------+</span></span></code></pre>\n<p>You’d like to run the following query: <code>select id1, sum(v1) as v1 from the_table where id1 = 'id016' group by id1</code>.</p>\n<p>The Delta table is initially stored in 395 files, and the rows with <code>id1 = 'id016'</code> are dispersed throughout all the files, so none of the files can be skipped when the query is run.</p>\n<p>It takes 4.51 seconds to run the query on the Delta table when it’s initially created:</p>\n<pre><code><span><span>(</span></span>\n<span><span>    spark.read.format(\"delta\")</span></span>\n<span><span>    .option(\"versionAsOf\", \"0\")</span></span>\n<span><span>    .load(delta_path)</span></span>\n<span><span>    .createOrReplaceTempView(\"x0\")</span></span>\n<span><span>)</span></span>\n<span><span></span></span>\n<span><span>spark.sql(</span></span>\n<span><span>    \"select id1, sum(v1) as v1 from x0 where id1 = 'id016' group by id1\"</span></span>\n<span><span>).collect()</span></span></code></pre>\n<p>Now let’s compact the Delta table so it does not contain unnecessarily small files.</p>\n<pre><code><span><span>delta_table = DeltaTable.forPath(spark, delta_path)</span></span>\n<span><span>delta_table.optimize().executeCompaction()</span></span></code></pre>\n<p>The compacted Delta table contains 27 files. The query now only takes 4.33 seconds to run.</p>\n<pre><code><span><span>(</span></span>\n<span><span>    spark.read.format(\"delta\")</span></span>\n<span><span>    .option(\"versionAsOf\", \"1\")</span></span>\n<span><span>    .load(delta_path)</span></span>\n<span><span>    .createOrReplaceTempView(\"x1\")</span></span>\n<span><span>)</span></span>\n<span><span></span></span>\n<span><span>spark.sql(</span></span>\n<span><span>    \"select id1, sum(v1) as v1 from x1 where id1 = 'id016' group by id1\"</span></span>\n<span><span>).collect()</span></span></code></pre>\n<p>On such a small dataset, compacting the 395 small files into 27 larger files doesn’t help the query runtime much. On a larger dataset with more small files, the compaction can materially speed up the query runtime.</p>\n<p>Let’s now Z Order the data by <code>id1</code>, so the rows with <code>id1 = 'id016'</code> are grouped together and not spread across all the files.</p>\n<pre><code><span><span>(</span></span>\n<span><span>    delta.DeltaTable.forPath(spark, table_path)</span></span>\n<span><span>    .optimize()</span></span>\n<span><span>    .executeZOrderBy(\"id1\")</span></span>\n<span><span>)</span></span></code></pre>\n<p>Now we only have rows with <code>id1 = 'id016'</code> in 1 of the 25 files. The query now takes 0.6 seconds to execute.</p>\n<pre><code><span><span>(</span></span>\n<span><span>    spark.read.format(\"delta\")</span></span>\n<span><span>    .option(\"versionAsOf\", \"2\")</span></span>\n<span><span>    .load(delta_path)</span></span>\n<span><span>    .createOrReplaceTempView(\"x2\")</span></span>\n<span><span>)</span></span>\n<span><span></span></span>\n<span><span>spark.sql(</span></span>\n<span><span>    \"select id1, sum(v1) as v1 from x2 where id1 = 'id016' group by id1\"</span></span>\n<span><span>).collect()</span></span></code></pre>\n<p>Z Ordering data can significantly improve query performance. This graph shows the query time by Delta table version:</p>\n<p><img src=\"https://delta.io/_astro/image1.CM9-3R6A_1m0v86.webp\"></p>\n<h2 id=\"why-file-skipping-improves-query-performance\">Why file skipping improves query performance</h2>\n<p>Transferring data from storage to memory is expensive, so minimizing the data sent over the wire speeds up your queries.</p>\n<p>Delta tables store per-file metadata in the transaction log that engines can consult when running queries, and that they can use to skip over files that do not contain data that is needed for the query.</p>\n<p>To make this possible, Delta tables store min/max values for columns in each file. Let’s visualize how the min/max statistics stored for the <code>id1</code> column can be used to perform file skipping.</p>\n<p><img src=\"https://delta.io/_astro/image2.C_HZyv3U_2qstWP.webp\"></p>\n<p>When reading data with <code>id1=id016</code>, we only need to grab files that contain rows <code>'id016'</code> between the <code>min_id1</code> and <code>max_id1</code> values. We know that a file with a <code>min_id1=id034</code> value has no rows of data relevant to our query.</p>\n<p>Z Ordering helps your queries run faster because it makes it more likely that data can be skipped.</p>\n<h2 id=\"delta-lake-z-order-by-multiple-columns\">Delta Lake Z ORDER by multiple columns</h2>\n<p>You can also Z Order a Delta table on multiple columns. Let’s look at a collection of query patterns and the tradeoffs associated with Z Ordering on various columns.</p>\n<p>Suppose you’re running the following types of queries frequently:</p>\n<ul>\n<li>query_a: <code>select id1, sum(v1) as v1 from x1 where id1 = 'id016' group by id1</code></li>\n<li>query_b: <code>select id2, sum(v1) as v1 from x1 where id2 = 'id047' group by id2</code></li>\n<li>query_c: <code>select id1, id2, sum(v1) where id1 = 'id016' and id2 = 'id047' group by id1, id2</code></li>\n</ul>\n<p>With this query pattern, Z Ordering on <code>id1</code> and <code>id2</code> could be good. Here’s how to run the Z Order command:</p>\n<pre><code><span><span>(</span></span>\n<span><span>    delta.DeltaTable.forPath(spark, table_path)</span></span>\n<span><span>    .optimize()</span></span>\n<span><span>    .executeZOrderBy(\"id1\", \"id2\")</span></span>\n<span><span>)</span></span></code></pre>\n<p>Let’s observe the query runtime on the four versions of our Delta table.</p>\n<ul>\n<li>x0: Delta table that was initially created</li>\n<li>x1: Delta table that has been compacted</li>\n<li>x2: Delta table Z Ordered by <code>id1</code></li>\n<li>x3: Delta table Z Ordered by <code>id1</code> and <code>id2</code></li>\n</ul>\n<p><img src=\"https://delta.io/_astro/image3.BwJyycLM_1r1qVD.webp\"></p>\n<p>As previously mentioned, small file compaction doesn’t help much in this example because the dataset is relatively small. Compaction can materially speed up queries when there are a lot of small files.</p>\n<p>Z Ordering the Delta table by <code>id1</code> improves queries that filter based on <code>id1</code>, but not for query_b, which only filters on <code>id2</code>. Z Ordering the table by <code>id1</code> and <code>id2</code> helps queries that filter on <code>id1</code>, <code>id2</code>, and both <code>id1</code> and <code>id2</code>.</p>\n<p>For this query pattern, Z Ordering by <code>id1</code> and <code>id2</code> provides a nice performance boost for all the queries. Z Ordering by <code>id1</code> only doesn’t help speed up <code>query_b</code>.</p>\n<p>It’s important to note that for a larger dataset, <code>query_a</code> will run faster for the Delta table that’s only Z Ordered by <code>id1</code> and slower for the Delta table that’s Z Ordered by <code>id1</code> and <code>id2</code>. Z Ordering by multiple columns limits the ability for the <code>id1</code> data to be colocated. Z Ordering has tradeoffs, so it’s important to analyze query patterns and select the right columns when Z Ordering your data.</p>\n<h2 id=\"delta-lake-z-ordering-vs-hive-style-partitioning\">Delta Lake Z Ordering vs. Hive-style partitioning</h2>\n<p>Delta Lake Z Ordering and Hive-style partitioning are techniques for grouping similar data in the same files, so only a subset of files are read when executing specific queries.</p>\n<p>Hive-style partitioning groups similar data in the same directory in storage. Z Ordering groups similar data in the same files without creating directories.</p>\n<p>Suppose you’d like to rearrange a Delta table so the following query executes better: <code>select id2, sum(v1) as v1 from x1 where id2 = 'id047' group by id2</code>.</p>\n<p>You can either Z Order by <code>id2</code> or partition by <code>id2</code>.</p>\n<p>Partitioning by <code>id2</code> guarantees complete data separation. There will be a separate directory for each value in <code>id2</code>, so the <code>id2=id07</code> directory will only contain rows with that exact data.</p>\n<p>Complete data separation can sometimes be great, but it can also be a liability. When you partition by a column with too many distinct values (aka a high cardinality column), lots of small files may be created depending on the size of the dataset and the skew.</p>\n<p>Updating a data set partitioned on a high cardinality column can rapidly exacerbate the small file problem.</p>\n<p>Deciding on the optimal data layout depends on the query pattern, data volume, column cardinality, and data skew. You should not be partitioning tables under one terabyte in general. You also shouldn’t partition by a column that will have partitions with less than 1 GB of data. If you’re partitioning a table that’s updated frequently, measure the number of new files created to assess the potential impact of the small file problem.</p>\n<p>Hive-style partitioning doesn’t necessarily cause a proliferation of small files. Suppose you write data into a table partitioned by the <code>ingestion_date</code> column every 8 hours. This write won’t necessarily cause more small files than writing to an unpartitioned lake. If you’re writing data to a table partitioned by a <code>medical_code</code> column with 10,000 distinct values, then every write operation can create up to 10,000 files, and the small file problem can snowball.</p>\n<p>You can always Z ORDER and incrementally append to avoid some small file issues created by Hive-style partitioning.</p>\n<p>Hive-style partitioning and Z Ordering aren’t mutually exclusive because you can also do both.</p>\n<h2 id=\"delta-lake-z-ordering-with-hive-style-partitioning\">Delta Lake Z Ordering with Hive-style partitioning</h2>\n<p>You can partition a Delta table in storage and Z Order the data within a given partition.</p>\n<p>For example, you can partition by <code>ingestion_date</code> and Z Order by <code>user_id</code>. This design would be a great way to run queries on user activity over time.</p>\n<p>This post does not cover the intricacies of Z Ordering vs. partitioning data. We will discuss this topic in detail in a future post.</p>\n<h2 id=\"when-z-ordering-does-not-improve-query-performance\">When Z Ordering does not improve query performance</h2>\n<p>Z Ordering only helps improve query performance if it can help you skip files.</p>\n<p>Let’s take a look at the following query that won’t benefit from our Delta table that’s Z Ordered by <code>id1</code>: <code>select id3, sum(v1) as v1 from x1 group by id3</code></p>\n<p>Z Ordering on <code>id1</code> would not improve the runtime for this particular query.</p>\n<p>It’s crucial to Z Order on the right columns to get performance gains for your most common query patterns.</p>\n<h2 id=\"conclusion\">Conclusion</h2>\n<p>Z Ordering is a powerful way to sort data that’s persisted in storage so that the engine can skip more files when running queries, so they execute faster.</p>\n<p>Z Ordering is an amazing Delta Lake feature unavailable in data lakes.</p>\n<p>This blog post showed you how to Z Order data by one or multiple columns. You learned about the best columns to use when Z Ordering data and the tradeoffs when you Z Order on multiple columns.</p>\n<p>You also learned how to use Z Ordering with or instead of Hive-style partitioning. The tradeoffs between Z Ordering and Hive-style partitioning are complex and will be covered in detail in a future post. Delta tables’ architecture fundamentally differs from data lakes, changing the cost/benefit equation of partitioning for practitioners.</p>  </div>"
