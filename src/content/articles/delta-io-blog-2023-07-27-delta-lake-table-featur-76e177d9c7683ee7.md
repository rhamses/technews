contentHtml: "<div>  <p>The original design of the Delta Lake Transaction Protocol specified two integers called “protocol versions” to keep track of both reader and writer features. Protocol versions allowed Delta Lake clients to safely handle tables by detecting incompatible protocol versions, and therefore helped manage the evolution of features in the Delta Lake protocol.</p>\n<p>This design has served Delta Lake well since inception, but has not come without complexities and constraints. In the integer based protocol versioning scheme, each version number bundles multiple features, and features across version numbers are cumulative. So, in order to get a new feature in a particular protocol version, users and developers would have to not only enable or implement all the features in a given version, but all features in all versions prior too!</p>\n<p>Versioning is a particularly difficult problem for a project like Delta Lake, which must consider users, administrators, and developers, across multiple stacks with their own sets of constraints - all at once in a single open protocol. This is why we’re super excited to introduce a new table compatibility management approach for Delta Lake, Table Features, which replaces integer based protocol reader and writer versions as the primary versioning scheme for Delta Lake tables.</p>\n<h2 id=\"what-are-delta-lake-table-features\">What are Delta Lake Table Features?</h2>\n<p>Delta Lake Table Features are a discrete feature-based compatibility scheme that replaces the traditional continuous integer-based protocol versioning scheme as the primary feature management mechanism for Delta Lake tables and clients.</p>\n<p><img src=\"https://delta.io/_astro/image1.D6KzWWc8_Z1b8jIN.webp\"></p>\n<p>With Table Features, users define their tables in terms of the features they use, instead of version numbers, which greatly simplifies table usability, maintenance, and upgrades. Developers can also now pick and choose to develop only the features necessary for their use case, instead of having to implement all features bundled in all the preceding version numbers.</p>\n<h2 id=\"how-do-delta-lake-table-features-work\">How do Delta Lake Table Features work?</h2>\n<p>To link Delta Lake Table features to the legacy protocol versioning scheme, support for Table Features semantics is itself considered a feature as a part of the final protocol versions: reader version 3 and writer version 7. These are the last protocol versions to be introduced by the Delta Lake protocol, and all subsequent features are now explicitly enabled through their respective features flag.</p>\n<h3 id=\"as-a-user-of-delta-spark\">As a user of Delta Spark</h3>\n<p>The move from protocol versions to table features is designed to be transparent to the user. Existing tables do not need to be explicitly upgraded to benefit, as the logic to match and handle legacy protocol versioning with table features is done by the client. You can still choose to <a target=\"_blank\" href=\"https://docs.delta.io/latest/versioning.html#upgrading-protocol-versions\">upgrade protocol versions manually</a>.</p>\n<p>To highlight how Table Features work in practice, let’s take a look at the evolution of a table using the latest release of Delta Spark connector, v2.4.0. The earliest Delta Spark version to support Table Features is v2.3.0.</p>\n<p>Creating a new table results in the following protocol action added to the Delta log:</p>\n<pre><code><span><span>CREATE TABLE t1 (id INT) USING delta</span></span>\n<span><span></span></span>\n<span><span>...</span></span>\n<span><span></span></span>\n<span><span>{\"protocol\":{\"minReaderVersion\":1,\"minWriterVersion\":2}}</span></span></code></pre>\n<p>Because there was no use or explicit enabling of a table feature like Change Data Feed or Deletion Vectors during creation, the current table state assumes the lowest possible reader and writer version.</p>\n<p>Let’s enable Change Data Feed and observe the changes to the log.</p>\n<pre><code><span><span>ALTER TABLE t1 SET TBLPROPERTIES (delta.enableChangeDataFeed = true)</span></span>\n<span><span></span></span>\n<span><span>...</span></span>\n<span><span></span></span>\n<span><span>{\"protocol\":{\"minReaderVersion\":1,\"minWriterVersion\":4}}</span></span></code></pre>\n<p>We can see that enabling Change Data Feed caused Delta Spark to upgrade the table to the protocol version (minWriterVersion 4) that contains the Change Data Feed feature. The mapping of legacy protocol versions to features is available in the <a target=\"_blank\" href=\"https://docs.delta.io/latest/versioning.html#features-by-protocol-version\">documentation</a>.</p>\n<p>Now let’s see the protocol action added to the Delta log by the client when we enable one of the latest features available in Delta Lake, Deletion Vectors.</p>\n<pre><code><span><span>ALTER TABLE t1 SET TBLPROPERTIES (delta.enableDeletionVectors = true)</span></span>\n<span><span></span></span>\n<span><span>...</span></span>\n<span><span></span></span>\n<span><span>{</span></span>\n<span><span>    \"protocol\": {</span></span>\n<span><span>        \"minReaderVersion\": 3,</span></span>\n<span><span>        \"minWriterVersion\": 7,</span></span>\n<span><span>        \"readerFeatures\": [</span></span>\n<span><span>            \"deletionVectors\"</span></span>\n<span><span>        ],</span></span>\n<span><span>        \"writerFeatures\": [</span></span>\n<span><span>            \"deletionVectors\",</span></span>\n<span><span>            \"checkConstraints\",</span></span>\n<span><span>            \"generatedColumns\",</span></span>\n<span><span>            \"invariants\",</span></span>\n<span><span>            \"changeDataFeed\",</span></span>\n<span><span>            \"appendOnly\"</span></span>\n<span><span>        ]</span></span>\n<span><span>    }</span></span>\n<span><span>}</span></span></code></pre>\n<p>This time we see that Delta Spark has upgraded the table to <code>\"minReaderVersion\": 3</code> and <code>\"minWriterVersion\": 7</code>, which are the final legacy protocol versions that enable support for the new Table Features versioning scheme, which Deletion Vectors belong to.</p>\n<p>We also see that new fields appear in the protocol action, <code>readerFeatures</code> and <code>writerFeatures</code>, which contain the list of features as they apply to both reading and writing of the table, respectively.</p>\n<p>We didn’t explicitly add a number of the features in the list. This is because they are bundled to the legacy protocol version upgrade we inherited when enabling Change Data Feed. The image below matches the features listed above, and captures which protocol versions each feature came from.</p>\n<p><img src=\"https://delta.io/_astro/image2.Cpl-kndc_RXDgs.webp\"></p>\n<p>Some features appear in both <code>readerFeatures</code> and <code>writerFeatures</code> of the protocol action while others only appear in one of the two. This is because not all features require changes to both write and read behavior. The table below summarizes which features apply to one or both of <code>readerFeatures</code> and <code>writerFeatures</code>.</p>\n<div>\n<table><thead><tr><th>Feature</th><th>Name</th><th>Readers or Writers?</th></tr></thead><tbody><tr><td>Append-only Tables</td><td><code>appendOnly</code></td><td>Writers only</td></tr><tr><td>Column Invariants</td><td><code>invariants</code></td><td>Writers only</td></tr><tr><td>CHECK constraints</td><td><code>checkConstraints</code></td><td>Writers only</td></tr><tr><td>Change Data Feed</td><td><code>changeDataFeed</code></td><td>Writers only</td></tr><tr><td>Generated Columns</td><td><code>generatedColumns</code></td><td>Writers only</td></tr><tr><td>Column Mapping</td><td><code>columnMapping</code></td><td>Readers and writers</td></tr><tr><td>Identity Columns</td><td><code>identityColumns</code></td><td>Writers only</td></tr><tr><td>Deletion Vectors</td><td><code>deletionVectors</code></td><td>Readers and writers</td></tr></tbody></table>\n</div>\n<h3 id=\"as-a-developer-of-delta-lake-clients\">As a developer of Delta Lake clients</h3>\n<p>Developers of Delta Lake clients should implement the table features semantics detailed in the <a target=\"_blank\" href=\"https://github.com/delta-io/delta/blob/master/PROTOCOL.md\">PROTOCOL</a>, the <a target=\"_blank\" href=\"https://docs.google.com/document/d/1UZ4W4nnKH4x9t3hy0eh68P0RFRAchoHihdXftdnycDQ/edit?usp=sharing\">design document</a>, upgrade their minimum supported protocol versions to reader version 3, writer version 7, and implement the features desired.</p>\n<p>For new clients which have not yet implemented support for previous protocol versions, claiming support for the latest protocol versions and adding support for the <code>appendOnly</code> and <code>invariants</code> features is sufficient. Those two features are required by the earliest protocol versions, reader version 1 and writer version 2.</p>\n<p>The client must maintain a list of features it supports and implement the correct logic to confirm if the client can read and/or write a Delta Lake table. For example, by enabling Table Features with protocol reader version 3 and writer version 7, you can selectively develop a feature like Change Data Feed without having to also develop all features between writer version 2 and 4.</p>\n<p>Below is an excerpt from the <a target=\"_blank\" href=\"https://docs.google.com/document/d/1UZ4W4nnKH4x9t3hy0eh68P0RFRAchoHihdXftdnycDQ/edit?usp=sharing\">Table Features design document</a> of the semantics of Table Features to follow when developing a Delta Lake client:</p>\n<ul>\n<li>When <strong>reading</strong> a table, a reader compares if\n<ul>\n<li>The table’s <code>readerFeatures</code> is a subset of the client’s <code>supportedReaderFeatures</code></li>\n</ul>\n</li>\n<li>When <strong>writing</strong> a table without reading data, a writer compares if\n<ul>\n<li>The table’s <code>writerFeatures</code> is a subset of the client’s <code>supportedWriterFeatures</code></li>\n</ul>\n</li>\n<li>When <strong>reading &amp; writing</strong> a table, a writer compares if\n<ul>\n<li>The table’s <code>readerFeatures</code> is a subset of the client’s <code>supportedReaderFeatures</code>, and</li>\n<li>The table’s <code>writerFeatures</code> is a subset of the client’s <code>supportedWriterFeatures</code></li>\n</ul>\n</li>\n</ul>\n<p>Delta Lake clients that would like to continue to support legacy table versions (reader version &lt; 3 and writer version &lt; 7) should use the <a target=\"_blank\" href=\"https://docs.delta.io/latest/versioning.html#features-by-protocol-version\">map of legacy protocol versions to the table features they bundle</a> to transparently determine what table features must be supported by the client to allow safe use of the table.</p>\n<p>You can refer to the reference implementation in the Delta Spark connector <a target=\"_blank\" href=\"https://github.com/delta-io/delta/blob/master/spark/src/main/scala/org/apache/spark/sql/delta/TableFeature.scala#L36-L56\">here</a>.</p>\n<h2 id=\"next-steps\">Next steps</h2>\n<p>Table features support is currently only available in the reference Delta Spark connector. Support for Table features in Delta Standalone and other non-Spark clients is currently in progress.</p>\n<h2 id=\"conclusion\">Conclusion</h2>\n<p>In this post we introduced Table Features, which replaces the legacy integer-based protocol versioning scheme in the Delta Lake protocol. Table Features are enabled by the final protocol versions, reader version 3 and writer version 7, which will no longer be used to manage or introduce new features to the Delta Lake protocol.</p>\n<p>Users and administrators can now enable only the features they need instead of inheriting all the features bundled to specific protocol versions before reader version 3 and writer version 7. This simplifies the table management lifecycle by making table features distinct and explicitly listed, removing the dependency on obtuse numbered protocol versions which arbitrarily bundle many features.</p>\n<p>Developers too can now implement Delta Lake clients to only support the features they require. By stating compatibility with the protocol versions that enable Table Features (reader version 3, writer version 7), developers can now more clearly express which features the client supports and simultaneously remove the burden of implementing features that may not be required, as was the case with the legacy integer-based protocol versioning scheme.</p>\n<p>Table Features marks a significant milestone for the Delta Lake protocol, and highlights the pace of innovation and adaptability of the protocol to changing requirements. We’re excited to see the speed of that innovation increase even further thanks to this feature!</p>\n<h3 id=\"further-reading\">Further Reading</h3>\n<ul>\n<li><a target=\"_blank\" href=\"https://docs.delta.io/latest/versioning.html#what-are-table-features\">How does Delta Lake manage feature compatibility?</a></li>\n<li><a target=\"_blank\" href=\"https://docs.google.com/document/d/1UZ4W4nnKH4x9t3hy0eh68P0RFRAchoHihdXftdnycDQ/edit?usp=sharing\">Delta Table Features Design Doc</a></li>\n<li><a target=\"_blank\" href=\"https://github.com/delta-io/delta/blob/master/PROTOCOL.md\">Delta Lake Transaction Protocol</a></li>\n</ul>  </div>"
