contentHtml: "<div>  <p>The data ecosystem is moving toward a catalog-centric model for managing open table formats. As open catalogs gain\nadoption, the catalog has emerged as the system of record for table identity, discovery, and authorization.</p>\n<p>With <a target=\"_blank\" href=\"https://github.com/delta-io/delta/releases/tag/v4.1.0\">Delta Lake 4.1.0</a>, Delta introduces\n<strong>catalog-managed tables</strong>, which establish the catalog as the coordinator of table access and source of truth for\ntable state. This simplifies how tables are discovered and secured, enables consistent governance across engines, and\nunlocks faster performance. The design also aligns Delta with the catalog-managed model pioneered by Iceberg, creating\na shared foundation for interoperable, high-performance lakehouse tables.</p>\n<p><a target=\"_blank\" href=\"https://github.com/unitycatalog/unitycatalog/releases/tag/v0.4.0\">Unity Catalog</a> is the first open lakehouse catalog\nto support catalog-managed tables, extending unified governance across any format.</p>\n<h2 id=\"what-are-catalog-managed-tables\">What are Catalog-Managed Tables?</h2>\n<p>Catalog-managed tables are tables for which the catalog brokers table access as well as stores the table’s latest\nmetadata and commits. Clients reference the table by name, not by path, and use the catalog to resolve the table’s\nstorage location. The catalog also manages concurrency control for proposed writes to a table. Writers leverage the\ncatalog, not object store APIs, for atomic commits.</p>\n<p>For more details, see the Delta protocol <a target=\"_blank\" href=\"https://github.com/delta-io/delta/blob/master/PROTOCOL.md#catalog-managed-tables\">RFC on Github here</a>.\nSee how Unity Catalog implements support for the <a target=\"_blank\" href=\"https://github.com/unitycatalog/unitycatalog/blob/main/spec/protocols/ManagedTablesSpec.md\">Catalog-Managed Tables specification here</a>.</p>\n<h2 id=\"before-challenges-with-delta-tables-that-were-managed-by-the-filesystem\">Before: Challenges with Delta tables that were managed by the filesystem</h2>\n<p>Before catalog-managed tables, the filesystem – not the catalog – was the primary authority for table access and\nchanges to table state.</p>\n<p>To access filesystem-managed Delta tables, Delta clients first look at the transaction log (<code>_delta_log</code>) stored with\nthe table to determine the latest version. Clients then reconstruct the current state of the table by replaying the log\nentries, which describe the table’s schema and data files that belong to the table. Once the table state is known, the\nsystem reads the relevant data files to answer the query. When writing to the table, clients write new data files to\nstorage and then atomically commit a new transaction log entry via filesystem APIs to advance the table to a new\nversion.</p>\n<p>Historically, data teams have faced the following challenges with filesystem-managed Delta tables:</p>\n<ol>\n<li><strong>Brittle path-based access</strong>: Delta clients have to know the exact path of the filesystem-managed table they are accessing, and credentials have to be provisioned directly by the storage system. This tightly couples applications to physical storage locations, so routine changes like table relocation, storage reorganization, or credential rotation could break pipelines and queries.</li>\n<li><strong>Risky coarse-grained authorization</strong>: Filesystems lack fine-grained access control, so complying with data privacy requirements often requires splitting datasets across multiple tables or storage paths to isolate sensitive fields or records. This leads to duplicated data, fragmented governance, and fragile pipelines.</li>\n<li><strong>Unsafe schema changes</strong>: Path-based writes can modify table schemas or metadata without validation, potentially introducing incompatible changes that break downstream workloads. This occurs because storage credentials cannot distinguish between clients authorized to write data and those authorized to modify table metadata.</li>\n<li><strong>Bottlenecked performance</strong>: Replaying the Delta transaction log to resolve a table’s latest state requires multiple calls to the filesystem, which can add 100+ ms to query execution.</li>\n</ol>\n<h2 id=\"now-catalog-managed-delta-tables-address-these-challenges\">Now: Catalog-Managed Delta Tables address these challenges</h2>\n<p>Catalog-managed tables address the governance and performance challenges by involving the catalog in read, write, and\nauthorization coordination. This way, teams can unlock:</p>\n<ol>\n<li><strong>Standardized table discovery</strong>: The catalog provides stable logical table identifiers (such as <a target=\"_blank\" href=\"https://docs.unitycatalog.io/quickstart/#unity-catalog-structure\">Unity Catalog’s three-level namespace</a>), eliminating the need for clients to depend on physical storage paths for discovery.</li>\n<li><strong>Unified governance</strong>: The catalog is responsible for granting clients access to data, rather than teams needing to manage fragmented access policies across their storage systems. This dramatically simplifies how data teams ensure engines access their data in a governed manner.</li>\n<li><strong>Enforceable constraints</strong>: The catalog can authoritatively validate or reject schema and constraint changes, preventing incompatible updates that could compromise data integrity or break downstream workloads.</li>\n<li><strong>Faster query planning and faster writes</strong>: If a Delta client is trying to access a table, the catalog can directly inform it of the table-level metadata. This skips cloud storage entirely and removes a major source of metadata latency. This feature also opens the door for “inline commits” where the (metadata) content of the commit is sent directly to the catalog.</li>\n</ol>\n<p>Catalog-managed Delta tables dramatically simplify how engines discover and access data under consistent governance,\nall while improving read and write performance. Table state updates are flushed to the filesystem, reinforcing Delta’s\nopenness and portability.</p>\n<h2 id=\"how-do-catalog-managed-tables-work\">How do Catalog-Managed Tables work?</h2>\n<p>The Catalog-Managed Tables Delta feature fundamentally changes how Delta tables are discovered, read, and committed to.</p>\n<h3 id=\"table-discovery\">Table Discovery</h3>\n<p>For catalog-managed tables, Delta tables are discovered and accessed through the catalog, not by filesystem paths.\nEngines must first resolve a table by name via the catalog, establishing table identity, location, and access\ncredentials. This resolution step occurs before the Delta client interacts with the filesystem and determines the rules\nthe client must follow for subsequent reads and writes.</p>\n<h3 id=\"reads\">Reads</h3>\n<p>A catalog-managed table may have commits that have been ratified by the catalog but not yet flushed, or “published”,\nto the filesystem. Reads therefore begin by getting these latest commits from the catalog, typically via a\n<span>get_catalog_commits</span> API exposed by the catalog.</p>\n<p>If additional history is required, such as older published commits or checkpoints, Delta clients can\n<span>LIST</span> the filesystem and merge those published commits with the catalog-provided\ncommits to construct a complete snapshot. This split view allows catalogs to always provide the most recent table state\nwhile offloading long-term commit storage to the filesystem.</p>\n<p><img alt=\"From FileSystem Reads to Catalog Managed Reads\" src=\"https://delta.io/_astro/figure-1a_1b.BmisypGi_275SA9.webp\"></p>\n<h3 id=\"writes\">Writes</h3>\n<p>Previously, writing to a Delta table involved calling filesystem <strong>“PUT-if-absent”</strong> APIs to perform atomic writes with\nmutual exclusion. In this model, the filesystem determined which writes win. While simple and scalable, this approach\ntreated commits as opaque blobs: the filesystem could not inspect commit contents, enforce constraints, or coordinate\nwrites across tables.</p>\n<p>For catalog-managed tables, clients propose commits to the catalog, typically by first staging commits in the\nfilesystem’s <span>&lt;table_path&gt;/_delta_log/_staged_commits</span> directory and then requesting\nratification. Staging ensures that readers never observe unapproved commits. The protocol also allows for “inline”\ncommits, where the contents of the commit are sent directly to the catalog, skipping the 100ms+ filesystem write.\nStaged commits are still performed using optimistic concurrency control to provide transactional guarantees.</p>\n<p>Catalogs can also define their own commit APIs, allowing them to accept richer commit payloads, inspect actions and\nmetadata, enforce constraints, and apply catalog-level policies before ratifying a commit.</p>\n<p>To unburden catalogs from having to store these ratified commits indefinitely, ratified commits can be periodically\n“published” to the <span>_delta_log</span> in the filesystem. Once published, catalogs no longer\nneed to retain or serve those commits because clients can easily discover them by listing.</p>\n<p><img alt=\"From FileSystem Writes to Catalog Managed Writes\" src=\"https://delta.io/_astro/figure-2a_2b.BrINp9Qo_2ktTTm.webp\"></p>\n<h2 id=\"evolving-open-table-formats\">Evolving open table formats</h2>\n<p>Catalog-managed Delta tables represent a critical convergence between how data is stored and how it is governed.\nOpen table formats and open catalogs are evolving together so that governance becomes a native property of the table\nitself rather than an external overlay.</p>\n<p>As an added benefit, Delta’s new catalog-oriented design closely resembles that of Iceberg tables. Ultimately, this\nmakes it simpler for practitioners to discover and govern data consistently, regardless of table format.</p>\n<p>We are excited to continue collaborating with the ecosystem to evolve Delta with open catalogs so that they deliver\nperformant commits, efficient metadata management, multi-engine interoperability, and unified governance.</p>\n<h2
