Delta is a foundational <a target=\"_blank\" href=\"https://docs.delta.io/\">open table format and toolset</a> for building and managing data lakes, related to Iceberg and other lakehouse formats. DuckDB supports Delta tables via its <a target=\"_blank\" href=\"https://duckdb.org/docs/current/core_extensions/delta.html\">Delta Extension</a>.</p>\n<p>In that last update we highlighted performance wins, particularly file skipping via filter pushdowns, and metadata caching with snapshot pinning. The big addition since we last chatted is <code>INSERT</code> support! It works as simply as you expect. Let’s assume you have a Delta table ready to go. <code>INSERT</code> away, it’s that simple:</p>\n<pre><code><span><span>-- Schema: (text VARCHAR, code BIGINT)</span></span>\n<span><span>ATTACH</span><span> './path/to/my_table'</span><span> AS</span><span> my_table (</span><span>TYPE</span><span> delta);</span></span>\n<span></span>\n<span><span>INSERT INTO</span><span> my_table</span></span>\n<span><span>VALUES</span><span> (</span><span>'Question 2'</span><span>, </span><span>2</span><span>), (</span><span>'The Answer'</span><span>, </span><span>42</span><span>);</span></span>\n<span></span>\n<span><span>-- Bulk insert from a query</span></span>\n<span><span>INSERT INTO</span><span> my_table</span></span>\n<span><span>FROM</span><span> (</span><span>SELECT</span><span> text</span><span> ||</span><span> ' (copy)'</span><span>, code </span><span>+</span><span> 100</span><span> FROM</span><span> my_table);</span></span></code></pre>\n<p>Also worth calling out – multiple <code>INSERT</code>s within a <code>BEGIN</code> / <code>COMMIT</code> block are stored as a single Delta version: one atomic commit, one new log entry. Any Delta table can be queried as of a particular version. DuckDB supports binding to a specific <code>VERSION</code> either at <code>ATTACH</code> time, or as part of an individual query.</p>\n<p>Let’s assume that we have built up the above <code>my_table</code> incrementally, with versions 0, 1, and 2 containing:</p>\n<table><thead><tr><th>Version</th><th>Contents</th></tr></thead><tbody><tr><td>0</td><td>(‘Question 1’, 1)</td></tr><tr><td>1</td><td>+ (‘Question 2’, 2), (‘The Answer’, 42)</td></tr><tr><td>2</td><td>+ (‘Question 1 (copy)’, 101), (‘Question 2 (copy)’, 102), (‘The Answer (copy)’, 142)</td></tr></tbody></table>\n<p>You can attach normally and query arbitrary versions inline as needed.  </span><span>-- → 6</span></span></code></pre>\n<h3 id=\"growing-up-no-longer-a-kit\">Growing Up: No Longer a Kit 🦫</h3>\n<p>The DuckDB Delta extension is no longer a <a target=\"_blank\" href=\"https://duckduckgo.com/?q=what+is+a+baby+beaver+called\">kit</a> and has grown\nup quite a bit since a year ago. As you just saw, we added writes and time travel. These features open the door to something bigger: Unity Catalog coordination.</p>\n<h2 id=\"unity-catalog-support-atop-the-delta\">Unity Catalog Support atop the Delta</h2>\n<p>Data lake systems excel at scale. As your data assets multiply, you need a way to discover what exists, control who can access it, audit how it’s being used, and coordinate writes across multiple engines. Data catalogs have evolved to address exactly these needs, sitting above the storage layer to manage the metadata, governance, and transactional bookkeeping that make large-scale data lakes effective. The OSS Unity Catalog team has a <a target=\"_blank\" href=\"https://unitycatalog.io/blogs/what-is-a-data-catalog-and-why-do-i-need-one/\">good overview</a> if you’d like to go deeper; the concepts apply broadly regardless of which catalog you use.</p>\n<h3 id=\"what-is-unity-catalog\">What is Unity Catalog?</h3>\n<p>Unity Catalog (UC for short) is an open standard for governing data and AI assets, including tables, volumes, models, and functions, across engines and clouds. It turns your data lake into a lakehouse, and gives you a single place to discover, audit, and control access to your data, regardless of what’s reading or writing it. DuckDB’s Unity Catalog extension is built upon the <a target=\"_blank\" href=\"https://go.unitycatalog.io/apidocs\">Unity Catalog Open API</a>. There are two main implementations: <a target=\"_blank\" href=\"https://unitycatalog.io/\">OSS Unity Catalog</a>, which you can self-host (and Docker-ify in minutes), and <a target=\"_blank\" href=\"https://docs.databricks.com/aws/en/data-governance/unity-catalog/\">Databricks Unity Catalog</a>, the managed version. Like Delta, the DuckDB Unity Catalog extension has shed its experimental tag. This is available today in both <a target=\"_blank\" href=\"https://www.unitycatalog.io/\">OSS</a> and <a target=\"_blank\" href=\"https://docs.databricks.com/aws/en/data-governance/unity-catalog/\">Databricks</a> Unity Catalog.</p>\n<p>The big feature in CMT is Catalog Commits, which enables coordinated concurrent writes. Without Catalog Commits, DuckDB writes go directly to the Delta log. While modern storage backends prevent outright lost writes, UC is left out of the loop entirely. Its metadata, audit trail, and statistics fall out of sync with the actual table state, and other engines querying through UC may see a stale view.</p>\n<p>Catalog Commits (CC) fixes this: every write is staged and registered through UC before it becomes visible. UC acts as the commit arbiter, preserving first writer commits, and sending a conflict error to later writers. This matters wherever multiple writers are appending simultaneously, e.g., parallel ETL pipelines, partitioned bulk loads, and concurrent analytical inserts. Each writer works independently; UC ensures exactly one commit lands per version and keeps its own catalog in sync with every one of them.</p>\n<p>Consistent reads and audit history are already inherent to Delta and UC respectively. CC doesn’t add functionality, it just ensures UC stays in sync with every commit. And Catalog Commits coordinate per table; there is no cross-table atomicity. If you write to two tables in the same <code>BEGIN</code> / <code>COMMIT</code> block, each table commits independently.</p>\n<p>To opt a table into CMT (and therefore CC), set the <code>delta.feature.catalogManaged</code> table property at creation time. This is done via Spark or the UC CLI, as DuckDB’s Unity Catalog extension does not yet support <code>CREATE TABLE</code> DDL:</p>\n<pre><code><span><span>-- Via Spark</span></span>\n<span><span>CREATE</span><span> TABLE</span><span> my_catalog</span><span>.</span><span>my_schema</span><span>.</span><span>concurrent_tbl</span><span> (</span></span>\n<span><span>    uuid    STRING  </span><span>NOT NULL</span><span>,</span></span>\n<span><span>    name</span><span>    STRING  </span><span>NOT NULL</span><span>,</span></span>\n<span><span>    age     </span><span>INT</span><span>     NOT NULL</span><span>,</span></span>\n<span><span>    adopted </span><span>BOOLEAN</span><span> NOT NULL</span></span>\n<span><span>)</span></span>\n<span><span>TBLPROPERTIES (</span><span>'delta.feature.catalogManaged'</span><span> =</span><span> 'supported'</span><span>);</span></span></code></pre>\n<p>Once enabled, DuckDB writes go through UC’s commit staging automatically, the <code>INSERT</code> syntax is unchanged:</p>\n<pre><code><span><span>INSERT INTO</span><span> my_catalog</span><span>.</span><span>my_schema</span><span>.concurrent_tbl</span></span>\n<span><span>    (uuid, </span><span>name</span><span>, age, adopted)</span></span>\n<span><span>VALUES</span><span> (gen_random_uuid()::</span><span>VARCHAR</span><span>, </span><span>'Luna'</span><span>, </span><span>3</span><span>, true);</span></span></code></pre>\n<p>Now each DuckDB writer stages its commit to a <code>_staged_commits/</code> directory and registers it with UC before that data becomes visible. UC arbitrates: exactly one writer wins each version in a race, the others get a conflict error and can retry. Consider a table where some initial queries are made against version 16:</p>\n<pre><code><span><span>ATTACH</span><span> './path/to/table'</span><span> AS</span><span> t (</span><span>TYPE</span><span> delta, </span><span>VERSION</span><span> 16</span><span>);</span></span>\n<span><span>SELECT</span><span> count</span><span>() </span><span>FROM</span><span> t;  </span><span>-- → 17</span></span></code></pre>\n<p>And now some work needs to be done against version 20. If we peek under the hood (warning: sneaky code follows), we’ll see that none of the previously loaded Delta log metadata files were re-loaded:</p>\n<pre><code><span><span>SET</span><span> enable_logging </span><span>=</span><span> true;</span></span>\n<span><span>SET</span><span> delta_kernel_logging </span><span>=</span><span> true;</span></span>\n<span><span>CALL</span><span> enable_logging(</span><span>'DeltaKernel'</span><span>, </span><span>level</span><span> =</span><span> 'trace'</span><span>);</span></span>\n<span></span>\n<span><span>ATTACH</span><span> './path/to/table'</span><span> AS</span><span> t (</span><span>TYPE</span><span> delta, </span><span>VERSION</span><span> 20</span><span>);</span></span>\n<span><span>SELECT</span><span> count</span><span>() </span><span>FROM</span><span> t;  </span><span>-- → 21</span></span>\n<span></span>\n<span><span>-- Delta kernel logs 'Provisionally selecting ... &lt;version&gt;.json'</span></span>\n<span><span>-- whenever it reads a log file from scratch.
