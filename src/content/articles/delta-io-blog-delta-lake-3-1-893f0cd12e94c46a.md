contentHtml: "<div>  <p>We are pleased to announce the release of Delta Lake 3.1 (<a target=\"_blank\" href=\"https://github.com/delta-io/delta/releases/tag/v3.1.0\">release notes</a>) on <a target=\"_blank\" href=\"https://spark.apache.org/releases/spark-release-3-5-0.html\">Apache Spark 3.5</a>, with features that make it easier to use and standardize on Delta Lake.</p>\n<p>This release includes many improvements and bug fixes, but we’d like to highlight the following:</p>\n<ul>\n<li><code>MERGE</code> with Deletion Vectors: Up to 3.7x reduction in merges</li>\n<li>Optimized Write and Auto Compaction: Two features to automatically optimize file sizes for best out-of-the-box read performance</li>\n<li>Improvements to the Delta Kernel read APIs: Updates to improve read performance, through table state reconstruction and support for query predicate-based data skipping</li>\n<li>UniForm Iceberg compatibility: Support for MAP and LIST data types and improved compatibility with popular Iceberg reader clients</li>\n<li>(Preview) Liquid clustering: A more performant, flexible table layout.</li>\n<li>Delta Sharing integration with Delta-Spark: You can now use Delta-Spark to query Delta Lake tables that have been shared using the Delta Sharing protocol.</li>\n<li>Min/Max query optimization: Uses metadata statistics to speed up min/max aggregate queries by up to 100x</li>\n</ul>\n<h2 id=\"whats-new-in-delta-lake-31\">What’s new in Delta Lake 3.1?</h2>\n<p>Building on the features released in Delta Lake 3.0, Delta Lake 3.1 introduces a host of performance enhancements and optimizations.</p>\n<h2 id=\"merge-with-deletion-vectors\">MERGE with Deletion Vectors</h2>\n<p>The Delta Lake 3.0 release included some major performance upgrades for <code>UPDATE</code> and <code>DELETE</code> statements, through their support of <a target=\"_blank\" href=\"https://docs.delta.io/latest/delta-deletion-vectors.html#enable-deletion-vectors\">Deletion Vectors</a>. With this release, <code>MERGE</code> now also supports Deletion Vectors. This reduces the write overhead for <code>MERGE</code> operations and improves their performance by up to 3.7x. The graph below shows how small updates on a very large table are faster with Deletion Vectors with almost no impact on read performance after merge.</p>\n<p><img src=\"https://delta.io/_astro/image1.BI1XTAU4_284OYA.webp\"></p>\n<h2 id=\"optimized-write-and-auto-compaction\">Optimized Write and Auto Compaction</h2>\n<p>Frequent writes to a table can lead to fragmentation in the file layout. Lots of small files in a table can lead to slower read performance due to higher overheads of opening and closing small files. Offline operations like Optimize reduce this problem by compacting, and Z-Ordering if needed, small files into larger files. The number of small files in the table can keep growing until these operations are explicitly run. Delta 3.1.0 adds two features that can significantly improve the out-of-the-box performance - <a target=\"_blank\" href=\"https://docs.delta.io/3.1.0/optimizations-oss.html#optimized-write\">Optimized Write</a> and <a target=\"_blank\" href=\"https://docs.delta.io/3.1.0/optimizations-oss.html#auto-compaction\">Auto Compaction</a>.</p>\n<p>Optimized Write forces any distributed write operation (that is, only with Delta on Spark operations) to rebalance the data using a data shuffle prior to writing the files in the table. This significantly reduces the chances of generating small files on write operations. It is highly recommended to enable this on partitioned tables as partitioning has a significantly higher chance of data fragmentation across partitions.</p>\n<p><img src=\"https://delta.io/_astro/image2.B2c4IxW__2pDX1V.webp\"></p>\n<p>However, Optimize Write by itself can only go so far. For example, in a streaming pipeline that continuously appends data to a Delta Lake table, each write may only include a small amount of data. Optimizing each write individually may still lead to small files accumulating over 1000s of writes. Auto Compaction solves that problem by running a “mini Optimize” operation after every write operation to compact any small files from all previous writes. So when this feature is explicitly enabled on a table, it will prevent any backlog of small files from ever building up.</p>\n<p>Note that both features incur slightly higher write latencies for a better out-of-the-box read performance. Hence, these are not enabled by default and you have to enable them based on your workload requirements.</p>\n<h2 id=\"data-skipping-support-in-delta-kernel\">Data skipping support in Delta Kernel</h2>\n<p><a target=\"_blank\" href=\"https://docs.delta.io/3.1.0/api/java/kernel/index.html\">Delta Kernel</a>, a new project to make it easier to build and maintain Delta connectors, was released as part of <a target=\"_blank\" href=\"https://delta.io/blog/delta-lake-3-0/\">Delta Lake 3.0</a>. Based on community feedback, a number of new features, API improvements, and bug fixes have been added. The most notable are related to read performance.</p>\n<p>For any given query predicate, Delta Kernel can restrict the list of files to scan, using file-level statistics stored in Delta Lake metadata. By skipping data, less data is scanned for these queries, resulting in faster read performance.</p>\n<p>Delta Kernel can now also read the table metadata (that is, schema, properties, etc.) much faster due to improved table state reconstruction. Delta Flink Sink in 3.1.0 includes an experimental Kernel integration that reduced the Flink pipeline initialization time by 45x (that is, by faster table metadata fetch) when writing to an 11 PB table with 7M files.</p>\n<p>Delta Kernel also now supports reading tables with column mapping <code>id</code> mode.</p>\n<p>For more information, please see:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://docs.delta.io/3.1.0/api/java/kernel/index.html\">Delta Kernel API Documentation</a></li>\n<li><a target=\"_blank\" href=\"https://github.com/delta-io/delta/blob/branch-3.0/kernel/USER_GUIDE.md\">User guide</a> on the step-by-step process to use Kernel in a standalone Java program or in a distributed processing connector.</li>\n<li><a target=\"_blank\" href=\"https://docs.google.com/presentation/d/1PGSSuJ8ndghucSF9GpYgCi9oeRpWolFyehjQbPh92-U/edit\">Slides</a> that explain the rationale behind Kernel and the API design.</li>\n<li>Example <a target=\"_blank\" href=\"https://github.com/delta-io/delta/tree/branch-3.0/kernel/examples/table-reader/src/main/java/io/delta/kernel/examples\">Java programs</a> that illustrate how to read Delta tables using the Kernel APIs.</li>\n</ul>\n<h2 id=\"uniform-iceberg-compatibility\">UniForm Iceberg Compatibility</h2>\n<p>Delta 3.1.0 extends the UniForm support originally released in Delta Lake 3.0.</p>\n<p>Delta 3.1.0 includes a new Iceberg support mode, IcebergCompatV2, which adds support for Map and List data types and offers better compatibility for timestamps, writing timestamps as int64, consistent with the <a target=\"_blank\" href=\"https://iceberg.apache.org/spec/#schemas-and-data-types\">Iceberg spec</a>. File statistics (column min, max, rowCount and nullCount) are now converted to Iceberg format.</p>\n<p>Furthermore, you can now upgrade existing Delta Lake tables to UniForm, using the <code>UPGRADE UNIFORM</code> command:</p>\n<pre><code><span><span>REORG TABLE table APPLY (UPGRADE</span></span>\n<span><span>UNIFORM(ICEBERG_COMPAT_VERSION=2))</span></span></code></pre>\n<p>For more information about these new features, check out UniForm’s <a target=\"_blank\" href=\"https://docs.delta.io/3.1.0/delta-uniform.html\">documentation</a>.</p>\n<h2 id=\"liquid-clustering\">Liquid Clustering</h2>\n<p><a target=\"_blank\" href=\"https://delta.io/blog/pros-cons-hive-style-partionining/\">Hive-style partitioning</a> is commonly used to increase read performance in data lakes, but it can cause maintenance and performance headaches if you have columns with high cardinality, have a lot of data skew, or if your data changes fairly frequently. Depending on the distribution of your data, the partitioning strategy that you start out with may end up causing inconsistencies in file sizes and partition sizes, ultimately resulting in slower performance. If you want to change your partitions to accommodate new data, you have to rewrite your table, a time-consuming and expensive process.</p>\n<p><a target=\"_blank\" href=\"https://github.com/delta-io/delta/releases/tag/v2.0.0\">Delta Lake 2.0</a> introduced the concept of <a target=\"_blank\" href=\"https://delta.io/blog/2023-06-03-delta-lake-z-order/\">Zorder</a>, a multi-dimensional clustering technique. The <code>OPTIMIZE ZORDER BY</code> command applies <code>ZORDER</code> clustering and improves the performance of queries that utilize<code> ZORDER BY</code> columns in their predicates. However, it has the following limitations:</p>\n<ul>\n<li><code>OPTIMIZE ZORDER BY</code> always reclusters (that is, rewrites) all data in the table resulting in high write amplification. Also, no partial results are saved when execution fails.</li>\n<li><code>ZORDER BY</code> columns are not persisted and the user is required to remember the previous<code> ZORDER BY</code> columns, often causing user errors.</li>\n</ul>\n<p><a target=\"_blank\" href=\"https://docs.delta.io/3.1.0/delta-clustering.html\">Liquid clustering</a>, a preview feature available in Delta Lake 3.1.0, introduces a new <em>incremental</em> clustering approach. The key changes are as follows:</p>\n<ul>\n<li>Liquid uses <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Hilbert_curve\">Hilbert Curve</a>, a continuous fractal space-filling curve as a multi-dimensional clustering technique, which significantly improves data skipping over <code>ZORDER</code>.</li>\n<li>Incremental clustering is built around a new concept of ZCubes. A ZCube is a group of files with Hilbert-clustered data produced by the same <code>OPTIMIZE</code> command. Already clustered files are tagged in the file metadata (that is, in the Delta log) by ZCube id and new <code>OPTIMIZE</code> commands will only rewrite unclustered files. This significantly limits the write amplification.</li>\n<li>Finally, the clustering column information is stored in the table, so users are not required to specify the clustering columns every time in the <code>OPTIMIZE</code> command thus avoiding errors.</li>\n</ul>\n<p>Note that Delta 3.1.0 only provides a preview of Liquid clustering with major <a target=\"_blank\" href=\"https://docs.delta.io/3.1.0/delta-clustering.html#limitations\">limitations</a> In order to use clustering, you need to enable the Spark session configuration flag <code>spark.databricks.delta.clusteredTable.enableClusteringTablePreview</code>.</p>\n<p>Liquid clustering is enabled at table creation with the <code>CLUSTER BY</code> statement:</p>\n<pre><code><span><span>-- Create an empty table</span></span>\n<span><span>CREATE TABLE table1(col0 int, col1 string) USING DELTA CLUSTER BY (col0);</span></span>\n<span><span></span></span>\n<span><span>-- Using a CTAS statement</span></span>\n<span><span>CREATE TABLE table2 CLUSTER BY (col0)  -- specify clustering after table name, not in subquery</span></span>\n<span><span>AS SELECT * FROM table1;</span></span>\n<span><span></span></span>\n<span><span>-- Optimize / cluster the table without specifying the columns</span></span>\n<span><span>OPTIMIZE table1</span></span></code></pre>\n<p>See the <a target=\"_blank\" href=\"https://docs.delta.io/3.1.0/delta-clustering.html\">documentation</a> and the <a target=\"_blank\" href=\"https://github.com/delta-io/delta/blob/branch-3.1/examples/scala/src/main/scala/example/Clustering.scala\">example</a> for more details. For more in-depth understanding, please see the <a target=\"_blank\" href=\"https://docs.google.com/document/d/1FWR3odjOw4v4-hjFy_hVaNdxHVs4WuK1asfB6M6XEMw/edit#heading=h.skpz7c7ga1wl\">original design doc</a>.</p>\n<h2 id=\"delta-sharing-spark-connector\">Delta Sharing Spark connector</h2>\n<p>With Delta 3.1.0, we have migrated the <code>delta-sharing-spark</code> Maven artifact from the <a target=\"_blank\" href=\"https://github.com/delta-io/delta-sharing\">delta-io/delta-sharing</a> Github repository to the <a target=\"_blank\" href=\"https://github.com/delta-io/delta/\">delta-io/delta</a> repository. Using this you can use <a target=\"_blank\" href=\"https://spark.apache.org/releases/spark-release-3-5-0.html\">Apache Spark</a> to read Delta Lake tables that have been shared using the Delta Sharing protocol. The connector supports reading a snapshot of the table, incrementally reading the table via streaming, and <a target=\"_blank\" href=\"https://docs.delta.io/latest/delta-change-data-feed.html\">Change Data Feed</a> queries. Existing users of <code>delta-sharing-spark</code> Maven artifact have to upgrade their version from &lt;= 1.0 to 3.1.</p>\n<p>Along with migration, Delta Sharing has also added support for Delta Lake tables with advanced features like <a target=\"_blank\" href=\"https://docs.delta.io/3.1.0/delta-deletion-vectors.html\">Deletion Vectors</a> and <a target=\"_blank\" href=\"https://docs.delta.io/3.1.0/delta-column-mapping.html\">Column Mapping</a>. To use these features, you must set the configuration in SparkSession to use the Delta Sharing read format. Batch data can be read as is, but for streaming and CDF queries against tables with Deletion Vectors or Column Mapping, you also need to set <code>responseFormat=delta</code>. Please see the <a target=\"_blank\" href=\"https://docs.delta.io/3.1.0/delta-sharing.html\">documentation</a> for more details.</p>\n<h2 id=\"minmax-query-optimization\">Min/Max query optimization</h2>\n<p>Seemingly simple aggregation queries like MIN and MAX can be prohibitively time-intensive for large tables. These operations have been made faster by using the table metadata, reducing the need for full table scans and improving performance by up to 100x.</p>\n<h2 id=\"additional-features-in-delta-lake-31\">Additional Features in Delta Lake 3.1</h2>\n<p>This release is full of even more features.
