contentHtml: "<div>  <p>This blog shows you how to optimize your Delta Lake table to reduce the number of small files.</p>\n<p>Small files can be a problem because they slow down your query reads. Listing, opening and closing many small files incurs expensive overhead. This is called “the Small File Problem”. You can reduce the Small File Problem overhead by combining the data into bigger, more efficient files.</p>\n<p>There are 3 ways you can optimize your Delta Lake table:</p>\n<ol>\n<li>Offline Optimize</li>\n<li>Optimized Write</li>\n<li>Auto Compaction</li>\n</ol>\n<blockquote>\n<p><code>Optimized Write</code> and <code>Auto Compaction</code> are new Delta Lake features, available since Delta 3.1.0.</p>\n</blockquote>\n<p>Choosing the right optimization method for your use case can save you lots of compute at query runtime.</p>\n<h2 id=\"small-files-cause-slow-reads\">Small files cause slow reads</h2>\n<p>Suppose you have a Delta Lake table with many small files. Running a query on this dataset is possible, but not efficient.</p>\n<p>The code below runs a query on a Delta table with 2 million rows. The Delta table is partitioned on the <code>education</code> column and has 1440 files per partition:</p>\n<pre><code><span><span>    %%time</span></span>\n<span><span>    df = spark.read.format(\"delta\").load(\"test/delta_table_1440\")</span></span>\n<span><span>    res = df.where(df.education == \"10th\").collect()</span></span>\n<span><span></span></span>\n<span><span>    CPU times: user 175 ms, sys: 20.1 ms, total: 195 ms</span></span>\n<span><span>    Wall time: 16.1 s</span></span></code></pre>\n<p>Now compare this to the same query on the same 2M-rows of data stored in a Delta table with only 1 optimized file per partition:</p>\n<pre><code><span><span>    %%time</span></span>\n<span><span>    df = spark.read.format(\"delta\").load(\"test/delta_table_1\")</span></span>\n<span><span>    res = df.where(df.education == \"10th\").collect()</span></span>\n<span><span></span></span>\n<span><span>    CPU times: user 156 ms, sys: 16 ms, total: 172 ms</span></span>\n<span><span>    Wall time: 4.62 s</span></span></code></pre>\n<p>This query runs much faster.</p>\n<p>Storing data in an optimized number of files will improve your out-of-the-box read performance. The optimized number of files is not always 1 file; depending on the size of your dataset, it might be more than 1. Read more in the <code>maxFileSize</code> section below.</p>\n<h2 id=\"what-causes-the-small-file-problem\">What causes the Small File Problem?</h2>\n<p>Small data files can be caused by:</p>\n<ul>\n<li><strong>User error:</strong> Users can repartition datasets and write out data with many small files.</li>\n<li><strong>Working with immutable files:</strong> Immutable file formats like Parquet cannot be overwritten. This means that updates to these datasets will create new files, possibly leading to a small file problem.</li>\n<li><strong>Partitioning:</strong> Partitioning a table on a high-cardinality column can lead to disk partitions with many small files.</li>\n<li><strong>Frequent incremental updates:</strong> Tables with frequent, small updates are likely to have many small files. A table that is updated every 2 minutes will generate 5040 files per week.</li>\n</ul>\n<p>It’s best to design systems to avoid creating many small files.</p>\n<p>But sometimes this is unavoidable, for example when you’re working with a table in an immutable file format like Parquet that needs to be updated frequently.</p>\n<p>Let’s take a look at how you can use offline optimization to optimize your Delta Lake table in this case.</p>\n<h2 id=\"delta-lake-optimize-manual-optimize\">Delta Lake Optimize: Manual Optimize</h2>\n<p>Suppose you have an ETL pipeline that ingests some data every day. The data is streamed into a partitioned Delta table that gets updated every minute.</p>\n<p>This means you will end up with 1440 files per partition at the end of every day.</p>\n<pre><code><span><span>    &gt; # get n files per partition</span></span>\n<span><span>    &gt; !ls test/delta_table/education\\=10th/*.parquet | wc -l</span></span>\n<span><span>    1440</span></span></code></pre>\n<p>Running a query on a Delta table with many small files is not efficient, as we saw above.</p>\n<p>You can manually run the Delta OPTIMIZE command to optimize the number of files. This is done by compacting all the inefficient small files into larger files that are more efficient to read. The default file size written in each partition after this operation is 1 GB.</p>\n<p>You can perform a compaction manually using:</p>\n<pre><code><span><span>    from delta.tables import *</span></span>\n<span><span>    deltaTable = DeltaTable.forPath(spark, \"test/delta_table\")</span></span>\n<span><span>    deltaTable.optimize().executeCompaction()</span></span></code></pre>\n<p>Downstream queries on this optimized Delta table will now be faster.</p>\n<p>Read more in the dedicated <a target=\"_blank\" href=\"https://delta.io/blog/2023-01-25-delta-lake-small-file-compaction-optimize/\">Small File Compaction post</a>.</p>\n<h2 id=\"delta-lake-optimize-optimized-write\">Delta Lake Optimize: Optimized Write</h2>\n<p>You don’t have to manually run the OPTIMIZE command. You can also configure optimizations to run automatically on your Delta Table. These automatic optimizations are: Optimized Write and Auto Compaction.</p>\n<p><a target=\"_blank\" href=\"https://docs.delta.io/3.1.0/optimizations-oss.html#optimized-write\">Optimized Write</a> combines all the small writes to the same partition into a single write command before executing. This is great when multiple processes are writing to the same partitioned Delta table, i.e. a distributed write operation.</p>\n<p><img src=\"https://delta.io/_astro/image1.B_cvKRuY_1JzoRa.webp\"></p>\n<p>Optimized Write rebalances the data using a data shuffle before writing the files to the table. This way you will reduce the number of small files.</p>\n<p>You can enable Optimized Write by setting the <code>optimizeWrite</code> option in your Delta Lake writer:</p>\n<pre><code><span><span>df.write.format(\"delta\").option(\"optimizeWrite\", \"True\").save(\"path/to/delta\")</span></span></code></pre>\n<p>You can also enable the Optimized Write functionality:</p>\n<ul>\n<li>for your whole Delta table by setting the <code>delta.autoOptimize.optimizeWrite</code> table property.</li>\n<li>for your whole Spark SQL session by setting the <code>spark.databricks.delta.optimizeWrite.enabled</code> SQL configuration</li>\n</ul>\n<p>Optimized Writes take a bit longer to execute because of the data shuffle that is performed before the data gets written. That’s why the feature is not enabled by default.</p>\n<h3 id=\"optimized-write-example\">Optimized Write Example</h3>\n<p>Let’s look at an example. You can run this code for yourself in <a target=\"_blank\" href=\"https://github.com/delta-io/delta-examples/blob/master/notebooks/pyspark/delta-lake-optimize.ipynb\">this notebook</a>.</p>\n<p>Spin up a local Spark cluster with 4 workers to simulate a distributed write setting:</p>\n<pre><code><span><span>import pyspark</span></span>\n<span><span>from delta import *</span></span>\n<span><span></span></span>\n<span><span>builder = pyspark.sql.SparkSession.builder.master(\"local[4]\").appName(\"parallel\") \\</span></span>\n<span><span>    .config(\"spark.sql.extensions\", \"io.delta.sql.DeltaSparkSessionExtension\") \\</span></span>\n<span><span>    .config(\"spark.sql.catalog.spark_catalog\", \"org.apache.spark.sql.delta.catalog.DeltaCatalog\")</span></span>\n<span><span></span></span>\n<span><span>spark = configure_spark_with_delta_pip(builder).getOrCreate()</span></span></code></pre>\n<p>Then let’s start with a dataset with 2 millions rows of data:</p>\n<pre><code><span><span>df = spark.read.csv(\"data/census_2M.csv\", header=True)</span></span></code></pre>\n<p>Repartition this to simulate a situation with many small files:</p>\n<pre><code><span><span>df = df.repartition(1440)</span></span></code></pre>\n<p>Write the data to a Delta table. Each of the 4 local processes will be writing many partitions in parallel:</p>\n<pre><code><span><span>df.write.format(\"delta\").partitionBy(\"education\").save(\"delta/census_table_many/\")</span></span></code></pre>\n<p>Let’s see how many files we have on disk per partition:</p>\n<pre><code><span><span>&gt; # get n files per partition</span></span>\n<span><span>&gt; !ls delta/census_table_many/education\\=10th/*.parquet | wc -l</span></span>\n<span><span></span></span>\n<span><span>1440</span></span></code></pre>\n<p>There are 1440 files per partition on disk.</p>\n<p>Let’s run a query on this Delta table with many small files:</p>\n<pre><code><span><span>&gt; df_small = spark.read.format(\"delta\").load(\"delta/census_table_many\")</span></span>\n<span><span></span></span>\n<span><span>&gt; %%time</span></span>\n<span><span>&gt; df_10th = df_small.where(df_small.education == \"10th\").collect()</span></span>\n<span><span></span></span>\n<span><span>CPU times: user 175 ms, sys: 20.1 ms, total: 195 ms</span></span>\n<span><span>Wall time: 16.1 s</span></span></code></pre>\n<p>Now let’s write the same data out using an Optimized Write. This will execute a data shuffle <em>before</em> the write operation and should avoid the Small File Problem:</p>\n<pre><code><span><span>df.write.format(\"delta\").partitionBy(\"education\").option(\"optimizeWrite\", \"True\").save(\"delta/census_table_optimized/\")</span></span></code></pre>\n<p>Let’s see how many files we have on disk per partition:</p>\n<pre><code><span><span>&gt; # get n files per partition</span></span>\n<span><span>&gt; !ls delta/census_table_optimized/education\\=10th/*.parquet | wc -l</span></span>\n<span><span></span></span>\n<span><span>1</span></span></code></pre>\n<p>All the data has been combined into 1 file per partition. This toy dataset is small (~250MB) so one file per partition makes sense here.</p>\n<p>Now let’s run a query on this optimized Delta table:</p>\n<pre><code><span><span>&gt; df_opt = spark.read.format(\"delta\").load(\"delta/census_table_optimized\")</span></span>\n<span><span></span></span>\n<span><span>&gt; %%time</span></span>\n<span><span>&gt; df_10th = df_opt.where(df_opt.education == \"10th\").collect()</span></span>\n<span><span></span></span>\n<span><span>CPU times: user 146 ms, sys: 30.3 ms, total: 177 ms</span></span>\n<span><span>Wall time: 3.66 s</span></span></code></pre>\n<p>This is a 4.5x performance gain.</p>\n<h2 id=\"delta-lake-optimize-auto-compaction\">Delta Lake Optimize: Auto Compaction</h2>\n<p>Optimized Write is great for distributed write situations with many different processes writing to the same Delta table.</p>\n<p>But sometimes that is not enough to solve the Small File Problem, for example when you are writing frequent small updates to a table. In this case, the files will still be small, even after an Optimized Write.</p>\n<p><a target=\"_blank\" href=\"https://docs.delta.io/3.1.0/optimizations-oss.html#auto-compaction\">Auto Compaction</a> solves this problem by automatically running a small <code>optimize</code> command after every write operation. Data from files under a certain threshold size is automatically combined into a larger file. This way, your downstream queries can benefit from a more optimal file size.</p>\n<p>You can enable Auto Compaction for your Delta table or your entire Spark session:</p>\n<ul>\n<li>Table property: <code>delta.autoOptimize.autoCompact</code></li>\n<li>SparkSession setting: <code>spark.databricks.delta.autoCompact.enabled</code></li>\n</ul>\n<p>Auto Compaction is only triggered for partitions or tables that have at least a certain number of small files. The minimum number of files required to trigger auto compaction can be configured with <code>spark.databricks.delta.autoCompact.minNumFiles.</code></p>\n<p>Let’s look at a quick example.</p>\n<p>We’ll start with the same 2-million row dataset we used above and repartition it to simulate a situation with a write performed every minute:</p>\n<pre><code><span><span>df = spark.read.csv(\"data/census_2M.csv\", header=True)</span></span>\n<span><span>df = df.repartition(1440)</span></span></code></pre>\n<p>Then let’s enable the Auto compaction feature for our Spark session:</p>\n<pre><code><span><span>spark.sql(\"SET spark.databricks.delta.autoCompact.enabled=true\")</span></span></code></pre>\n<p>Now let’s write the data to our Delta table:</p>\n<pre><code><span><span>df.write.format(\"delta\").partitionBy(\"education\").save(\"delta/census_table_compact/\")</span></span></code></pre>\n<p>Then perform a query:</p>\n<pre><code><span><span>df_comp = spark.read.format(\"delta\").load(\"delta/census_table_compact\")</span></span>\n<span><span></span></span>\n<span><span>%%time</span></span>\n<span><span>df_10th = df_comp.where(df_comp.education == \"10th\").collect()</span></span>\n<span><span>CPU times: user 205 ms, sys: 39.2 ms, total: 244 ms</span></span>\n<span><span>Wall time: 4.69 s</span></span></code></pre>\n<p>Again we see a nice performance gain after optimizing the Delta table.</p>\n<h2 id=\"delta-lake-optimize-vacuum\">Delta Lake Optimize: Vacuum</h2>\n<p>Because Auto Compaction optimizes your Delta Table <em>after</em> the write operations, you may still have many small files on disk.</p>\n<pre><code><span><span>&gt; # get n files per partition</span></span>\n<span><span>&gt; !ls delta/census_table_compact/education\\=10th/*.parquet | wc -l</span></span>\n<span><span></span></span>\n<span><span>1441</span></span></code></pre>\n<p>In this case we have 1440 files (one per partition) and 1 final file that contains all the data.</p>\n<p>Delta Lake has iteratively combined all the small writes into a larger file. It has also recorded in the transaction log the path to the latest file. Downstream data reads will look at the transaction log and access only the last, largest file.</p>\n<p>But as you can see the older, smaller files are still on disk. This doesn’t affect your read performance because Delta Lake knows that you only need to access the latest file. But you might still want to remove these files, for example to save on storage costs.</p>\n<p>You can remove these older files with a VACUUM command. The parameter is the number of preceding hours you want to preserve.</p>\n<pre><code><span><span>deltaTable.vacuum(0)</span></span></code></pre>\n<p>The VACUUM command removes old files that are no longer actively referenced in the transaction log. By default, VACUUM only affects files older than the default retention duration which is 7 days.</p>\n<p>You can override this default setting using:</p>\n<pre><code><span><span>spark.sql(\"SET spark.databricks.delta.retentionDurationCheck.enabled=false\")</span></span></code></pre>\n<p>Read more in <a target=\"_blank\" href=\"https://delta.io/blog/remove-files-delta-lake-vacuum-command/\">the dedicated VACUUM post</a>.</p>\n<h2 id=\"optimized-write-vs-auto-compaction\">Optimized Write vs Auto Compaction</h2>\n<p>Optimized Write combines many small writes to the same partition into one larger write operation. It is an optimization performed <em>before</em> the data is written to your Delta table.</p>\n<p>Auto Compaction combines many small files into larger, more efficient files. It is an optimization performed <em>after</em> the data is written to your Delta table. You may need to perform a VACUUM operation afterwards to clean up the remaining small files.</p>\n<h2 id=\"delta-lake-optimize-maxfilesize\">Delta Lake Optimize maxFileSize</h2>\n<p>You can set the maximum file size of your files with the <code>maxFileSize</code> config option:</p>\n<p><code>spark.databricks.delta.optimize.maxFileSize</code></p>\n<p>The default setting of 1GB files works best in most scenarios. You don’t usually need to play with this.</p>\n<p>The 1 GB default file size was selected from years of customer usage showing that this file size works well on common computational instances.</p>\n<h2 id=\"delta-lake-optimize-tradeoffs\">Delta Lake Optimize: Tradeoffs</h2>\n<p>All forms of optimization require computation and take time. Depending on your use case, one approach may be better suited than another.</p>\n<p>Running optimizations usually makes sense if you have many downstream queries that will benefit from the faster read performance.</p>\n<p>Delta Lake optimizations may not make sense for you if you need the lowest write latency possible.</p>\n<h2 id=\"optimize-your-delta-lake-tables\">Optimize your Delta Lake tables</h2>\n<p>Small files can cause slow downstream queries. Optimizing your Delta Lake table to avoid the Small File Problem is a great way to improve your out-of-the-box performance.</p>\n<p>You can optimize your Delta Lake tables:</p>\n<ul>\n<li>Manually with the <code>optimize().executeCompaction()</code> command</li>\n<li>Before writing with the Optimized Write functionality</li>\n<li>After writing with the Auto Compaction functionality</li>\n</ul>\n<p>Check out <a target=\"_blank\" href=\"https://github.com/delta-io/delta-examples/blob/master/notebooks/pyspark/delta-lake-optimize.ipynb\">the notebook on Github</a> to run the sample code for yourself.</p>  </div>"
