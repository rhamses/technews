This accelerates the search for matches by using target-only MATCHED conditions for data skipping. For example, in the following query, predicates <code>target.value = 5 OR target.value = 7</code> can exclude unnecessary scans of any file that is known not to contain those values:</p>\n<h3 id=\"enhanced-handling-of-insert-only-merges\">Enhanced Handling of Insert-Only Merges</h3>\n<p>In Delta Lake 3.0 insert-only <code>MERGE</code> statements support any number of <code>NOT MATCHED</code> clauses, whereas previously only a single <code>NOT MATCHED</code> clause was allowed. This improvement allows consolidation of diverse <code>MERGE … INSERT</code> operations into fewer steps, increasing overall efficiency. We now also switch to insert-only <code>MERGE</code> if the <code>MATCHED</code> clause(s) do not have any matches.</p>\n<h3 id=\"efficient-row-change-writing\">Efficient Row Change Writing</h3>\n<p>We’ve refined the row change writing process for improved efficiency. Rather than processing individual partitions separately, we construct a single dataframe with all the rows to be written, using a comprehensive expression that applies the correct <code>MERGE</code> action to each row.</p>\n<h3 id=\"efficient-metrics-counter\">Efficient Metrics Counter</h3>\n<p>When updating metrics during <code>MERGE</code>/<code>UPDATE</code>/<code>DELETE</code> actions we replaced the UDFs previously used with dedicated native expressions. This change optimizes code generation, resulting in a more efficient and streamlined method of incrementing metrics.</p>\n<h3 id=\"benchmarking-merge-performance\">Benchmarking MERGE Performance</h3>\n<p>We created a small new benchmark to test the improvement to <code>MERGE</code>.
