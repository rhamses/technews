contentHtml: "<div>  <p>This article shows you how to use Delta Lake with the AWS S3 object store.</p>\n<p>Delta Lake is a great storage format for reliable and fast data storage. It provides features like ACID transactions, scalable metadata handling, high-performance query optimizations, schema enforcement and time travel. With these features you can build a performant lakehouse architecture on top of your data lake.</p>\n<p>S3 is a popular place to store data objects in the cloud. Storage on S3 is cheap and accessing it is efficient, especially for batch workloads. Many organizations use S3 to build a data lake, for example with Parquet files.</p>\n<p>This article will show you how to read and write Delta tables from and to S3. We will cover code examples with Spark and Polars.</p>\n<p>You will learn:</p>\n<ul>\n<li>Why Delta Lake is a great choice for S3 workloads</li>\n<li>How to configure your Spark session for proper S3 access with Delta Lake</li>\n<li>How to set up your Python environment for proper S3 access with Delta Lake</li>\n</ul>\n<p>Let’s jump in! 🪂</p>\n<h2 id=\"why-delta-lake-is-great-for-s3\">Why Delta Lake is great for S3</h2>\n<p>Cloud object stores are slow at listing files. This can become a serious problem when you’re working with large volumes of data. Delta Lake makes your queries on data in object stores much more efficient.</p>\n<p>Cloud-based file systems use a flat namespace rather than a hierarchical file system. This means that there are no real directories. Directories are simulated by attaching prefixes to object keys. Listing operations require the engine to scan <em>all</em> of the files and filter based on these prefixes.</p>\n<p>Cloud-based file systems also impose API rate limits. This means you have to make many API calls to list your files. Together, these two factors can cause bottlenecks when you’re listing many files.</p>\n<p>Suppose you have a table stored in a data lake on S3. The data in this table is spread over many files in a directory. To run a query on this table, your engine will first need to list all the files and then filter for the relevant ones. On S3, a LIST operation is limited to 1000 objects. If your table has millions of files, this will result in high latency and slower queries.</p>\n<p>Delta Lake stores all the file paths in a separate transaction log. This way you can avoid expensive file listing operations. Your engine only needs to perform a single operation to get the paths to all the relevant files for your query. This is much more efficient.</p>\n<p><img src=\"https://delta.io/_astro/image1.hFpS6BCH_29GFBx.webp\"></p>\n<p>Delta Lake has many more benefits compared to data lakes on S3. You can read about them in the <a target=\"_blank\" href=\"https://delta.io/blog/delta-lake-vs-data-lake/\">Delta Lake vs Data Lake</a> blog.</p>\n<h2 id=\"how-to-use-delta-lake-on-s3\">How to use Delta Lake on S3</h2>\n<p>Many query engines support reading and writing Delta Lake on S3.</p>\n<p>For example, you can read Delta Lake tables with Spark using:</p>\n<pre><code><span><span>    df </span><span>=</span><span> spark.read.format(</span><span>\"delta\"</span><span>).load(path</span><span>/</span><span>to</span><span>/</span><span>delta)</span></span></code></pre>\n<p>And you can write data to Delta Lake table with Spark using:</p>\n<pre><code><span><span>\tdf.write.format(</span><span>\"delta\"</span><span>).save(path</span><span>/</span><span>to</span><span>/</span><span>delta)</span></span></code></pre>\n<p>You can also use <a target=\"_blank\" href=\"https://delta.io/blog/delta-lake-without-spark/\">Delta Lake without Spark</a>.</p>\n<p>Some query engines require a few extra configuration steps to get up and running with Delta Lake. The following two sections will walk you through working with Delta Lake on S3 with Spark (using <a target=\"_blank\" href=\"https://docs.delta.io/latest/index.html\">delta-spark</a>) and Python engines (using <a target=\"_blank\" href=\"https://delta-io.github.io/delta-rs/\">python-deltalake</a>).</p>\n<p>Let’s look at an example of using Delta Lake on S3 with the Spark engine.</p>\n<h2 id=\"delta-lake-on-s3-with-spark\">Delta Lake on S3 with Spark</h2>\n<p>Your Spark session will need additional configuration to read/write Delta Lake tables. This is because S3 currently does not provide mutual exclusion. There is no way to ensure that only one writer is able to create a file, potentially leading to data corruption.</p>\n<p>You can enable multi-cluster concurrent write support by explicitly configuring Delta Lake to use a LogStore. In this case, DynamoDB will be used to guarantee the mutual exclusion that S3 does not provide. Read more in the <a target=\"_blank\" href=\"https://delta.io/blog/2022-05-18-multi-cluster-writes-to-delta-lake-storage-in-s3/\">Multi-Cluster Writes</a> blog post.</p>\n<p>Next, let’s look at an example of using Delta Lake on S3 with a python-deltalake query engine like Polars.</p>\n<h2 id=\"delta-lake-on-s3-with-delta-rs\">Delta Lake on S3 with delta-rs</h2>\n<p>You don’t need to install extra dependencies to write Delta tables to S3 with engines that use the <code>delta-rs</code> implementation of Delta Lake. You do need to configure your AWS access credentials correctly.</p>\n<p>Many Python engines use <a target=\"_blank\" href=\"https://boto3.amazonaws.com/v1/documentation/api/latest/index.html\">boto3</a> to connect to AWS. This library supports reading credentials automatically from your local <code>.aws/config</code> or <code>.aws/creds</code> file.</p>\n<p>For example, if you’re running locally with the proper credentials in your local <code>.aws/config</code> or <code>.aws/creds</code> file then you can write a Parquet file to S3 like this with pandas:</p>\n<pre><code><span><span>    import</span><span> pandas </span><span>as</span><span> pd</span></span>\n<span><span>    df </span><span>=</span><span> pd.DataFrame({</span><span>'x'</span><span>: [</span><span>1</span><span>, </span><span>2</span><span>, </span><span>3</span><span>]})</span></span>\n<span><span>    df.to_parquet(</span><span>\"s3://avriiil/parquet-test-pandas\"</span><span>)</span></span></code></pre>\n<p>The <code>delta-rs</code> writer does not use <code>boto3</code> and therefore does not support taking credentials from your <code>.aws/config</code> or <code>.aws/creds</code> file. If you’re used to working with writers from Python engines like Polars, pandas or Dask, this may mean a small change to your workflow.</p>\n<p>You can pass your AWS credentials explicitly by using:</p>\n<ul>\n<li>the <code>storage_options </code>kwarg</li>\n<li>Environment variables</li>\n<li>EC2 metadata if using EC2 instances</li>\n<li>AWS Profiles</li>\n</ul>\n<p>Let’s work through an example with Polars. The same logic applies to other Python engines like Pandas, Daft, Dask, etc.</p>\n<p>Follow the steps below to use Delta Lake on S3 with Polars:</p>\n<ol>\n<li>\n<div><p>Install Polars and deltalake. </p><p>\nFor example, using: </p><p>\n<code>pip install polars deltalake</code></p></div>\n</li>\n<li>\n<p>Create a dataframe with some toy data.</p>\n<p><code>df = pl.DataFrame({'x': [1, 2, 3]})</code></p>\n</li>\n<li>\n<p>Set your <code>storage_options</code> correctly.</p>\n</li>\n</ol>\n<pre><code><span><span>storage_options </span><span>=</span><span> {</span></span>\n<span><span>    \"AWS_REGION\"</span><span>:</span><span>&lt;</span><span>region_name</span><span>&gt;</span><span>,</span></span>\n<span><span>    'AWS_ACCESS_KEY_ID'</span><span>: </span><span>&lt;</span><span>key_id</span><span>&gt;</span><span>,</span></span>\n<span><span>    'AWS_SECRET_ACCESS_KEY'</span><span>: </span><span>&lt;</span><span>access_key</span><span>&gt;</span><span>,</span></span>\n<span><span>    'AWS_S3_LOCKING_PROVIDER'</span><span>: </span><span>'dynamodb'</span><span>,</span></span>\n<span><span>    'DELTA_DYNAMO_TABLE_NAME'</span><span>: </span><span>'delta_log'</span><span>,</span></span>\n<span><span>}</span></span></code></pre>\n<ol>\n<li>\n<p>Write data to Delta table using the <code>storage_options</code> kwarg.</p>\n<pre><code><span><span>df.write_delta(</span></span>\n<span><span>    \"s3://bucket/delta_table\"</span><span>,</span></span>\n<span><span>    storage_options</span><span>=</span><span>storage_options,</span></span>\n<span><span>)</span></span></code></pre>\n</li>\n</ol>\n<p>Just like the Spark implementation, <code>delta-rs</code> uses DynamoDB to guarantee safe concurrent writes. If for some reason you don’t want to use DynamoDB as your locking mechanism you can choose to set the <code>AWS_S3_ALLOW_UNSAFE_RENAME</code> variable to <code>true</code> in order to enable S3 unsafe writes.</p>\n<h2 id=\"delta-lake-on-s3-safe-concurrent-writes\">Delta Lake on S3: Safe Concurrent Writes</h2>\n<p>You need a locking provider to ensure safe concurrent writes when writing Delta tables to S3. This is because S3 does not guarantee mutual exclusion.</p>\n<p>A locking provider guarantees that only one writer is able to create the same file. This prevents corrupted or conflicting data.</p>\n<p>You can use a DynamoDB table as your locking provider for safe concurrent writes.</p>\n<p>Run the code below in your terminal to create a DynamoDB table that will act as your locking provider.</p>\n<pre><code><span><span>    aws dynamodb create-table \\</span></span>\n<span><span>    --table-name delta_log \\</span></span>\n<span><span>    --attribute-definitions AttributeName=tablePath,AttributeType=S AttributeName=fileName,AttributeType=S \\</span></span>\n<span><span>    --key-schema AttributeName=tablePath,KeyType=HASH AttributeName=fileName,KeyType=RANGE \\</span></span>\n<span><span>    --provisioned-throughput ReadCapacityUnits=5,WriteCapacityUnits=5</span></span></code></pre>\n<p>Delta-spark supports safe concurrent writes by default from a single cluster. Multi-cluster writes require additional configuration. See the “Delta Lake on S3 with Spark” section above for more detail on both cases.</p>\n<p>delta-rs supports safe concurrent writes. You will need a DynamoDB table. You can disable the safe concurrent writes guarantee if you don’t want to use a DynamoDB table. See the “Delta Lake on S3 with delta-rs” section for more detail.</p>\n<h2 id=\"delta-lake-on-s3-required-permissions\">Delta Lake on S3: Required permissions</h2>\n<p>You need to have permissions to get, put and delete objects in the S3 bucket you’re storing your data in. Please note that you must be allowed to delete objects even if you’re just appending to the Delta Lake, because there are temporary files into the log folder that are deleted after usage.</p>\n<p>In AWS S3, you will need the following permissions:</p>\n<ul>\n<li>s3</li>\n<li>s3</li>\n<li>s3</li>\n</ul>\n<p>In DynamoDB, you will need the following permissions:</p>\n<ul>\n<li>dynamodb</li>\n<li>dynamodb</li>\n<li>dynamodb</li>\n<li>dynamodb</li>\n</ul>\n<h2 id=\"using-delta-lake-on-s3\">Using Delta Lake on S3</h2>\n<p>You can read and write Delta Lake tables from and to AWS S3 cloud object storage.</p>\n<p>Using Delta Lake with S3 is a great way to make your queries on cloud objects faster by avoiding expensive file listing operations.</p>\n<p>You can use Delta Lake with S3 using many different query engines. Some of these engines require some additional configuration to get up and running.</p>\n<p>Whichever query engine you choose to use, you will gain the benefits of Delta Lake’s core performance and reliability features like query optimization, efficient metadata handling and transaction guarantees.</p>  </div>"
