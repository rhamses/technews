When updating or deleting rows, instead of eagerly rewriting the Parquet data files containing to-be-deleted rows, we simply mark those rows to be ignored while reading. This read-time filtering based on a simple bitmap/vector (that is, a “deletion” vector) can be very fast. With deletion vectors enabled on a table, delete, update, and merge operations can be up to 10x faster, without making subsequent reads any slower. This breaks the conventional trend in the performance tradeoffs that other formats make between write-optimized “merge-on-read” and read-optimized “copy-on-write” approaches. Now you can have the fastest update performance without sacrificing read performance. Although DVs were first proposed in 2022, in 2023 we updated the DELETE (<a target=\"_blank\" href=\"https://github.com/delta-io/delta/releases/tag/v2.4.0\">Delta 2.4</a>), UPDATE (<a target=\"_blank\" href=\"https://github.com/delta-io/delta/releases/tag/v3.0.0\">Delta 3.0</a>), and MERGE (<a target=\"_blank\" href=\"https://github.com/delta-io/delta/releases/tag/v3.1.0\">Delta 3.1</a>) operations to use deletion vectors. See the <a target=\"_blank\" href=\"https://github.com/delta-io/delta/issues/1367\">issue and design</a> for a more in-depth understanding, and the <a target=\"_blank\" href=\"https://docs.delta.io/latest/delta-deletion-vectors.html\">documentation</a> for how to use it.</p>\n<h3 id=\"liquid-clustering\"><a target=\"_blank\" href=\"https://docs.delta.io/latest/delta-clustering.html\">Liquid clustering</a></h3>\n<p><a target=\"_blank\" href=\"https://delta.io/blog/pros-cons-hive-style-partionining/\">Hive-style partitioning</a> is commonly used to increase read performance in data lakes, but it can cause maintenance and performance headaches if you have columns with high cardinality, have a lot of data skew, or if your data changes fairly frequently. In 2022, <a target=\"_blank\" href=\"https://github.com/delta-io/delta/releases/tag/v2.0.0\">Delta Lake 2.0</a> introduced the command <code>OPTIMIZE ZORDER</code> which allows better data layouts with multi-dimensional clustering. However, it required reclustering data many times, resulting in higher write amplification. In 2023, we introduced a new approach called <a target=\"_blank\" href=\"https://docs.delta.io/latest/delta-clustering.html\">Liquid clustering</a> which can solve the limitations of Zorder. It has (i) better data layout with <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Hilbert_curve\">Hilbert curves</a>, with more data skipped on read than with <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Z-order_curve\">Z-order curves</a>, (ii) Z-cubes to make clustering incremental and reduce write amplification, and (iii) pluggability for you to plug in your data layout policy that works best for your data. While it’s still in preview, you can kick the tires with <a target=\"_blank\" href=\"https://github.com/delta-io/delta/releases/tag/v3.1.0\">Delta 3.1</a>.</p>\n<h3 id=\"v2-checkpoints-and-minor-log-compactions\">V2 checkpoints and minor log compactions</h3>\n<p>The transaction log in Delta was designed from the beginning to treat the metadata as “big data”. Any transaction having millions of files (that is, 100 TBs of data) can be processed in a distributed manner. The demands of data continue to grow further and require tables to scale further to PBs. The transaction log (that is, table metadata) itself can exceed 10 GBs. <a target=\"_blank\" href=\"https://github.com/delta-io/delta/issues/1793\">V2 checkpoints</a> and <a target=\"_blank\" href=\"https://github.com/delta-io/delta/issues/2072\">minor log compactions</a> are two new log optimizations (introduced in <a target=\"_blank\" href=\"https://github.com/delta-io/delta/releases/tag/v3.0.0\">Delta 3.0</a>) that allow the logs to be updated incrementally and read faster, thus allowing a single table to reliably contain 100M+ files (that is, 100 PB+ data).</p>\n<h3 id=\"row-tracking\">Row tracking</h3>\n<p>While <a target=\"_blank\" href=\"https://docs.delta.io/latest/delta-change-data-feed.html\">Change Data Feed (CDF</a>) provides the ability to query row-level differences between versions, it requires additional resources during writes to explicitly save the row-level change information. This higher overhead is the reason why CDF needs to be explicitly enabled by the user. <a target=\"_blank\" href=\"https://github.com/delta-io/delta/issues/2111\">Row Tracking</a> is a new feature that gives each data row a unique identifier. This allows each row to be tracked precisely as it gets rewritten during updates and merges from one file to another with very little overhead. This allows row-level changes to be identified with no cost to write performance.</p>\n<h3 id=\"column-defaults\"><a target=\"_blank\" href=\"https://docs.delta.io/latest/delta-default-columns.html\">Column Defaults</a></h3>\n<p>Similar to the popular feature <a target=\"_blank\" href=\"https://delta.io/blog/2023-04-12-delta-lake-generated-columns/\">Generated Columns</a>, this new feature introduced in <a target=\"_blank\" href=\"https://github.com/delta-io/delta/releases/tag/v3.1.0\">Delta 3.1</a> allows default values to be automatically inserted when data writes / updates do not explicitly provide values for the columns. This expands Delta’s capabilities to allow more data warehousing workloads than ever before.</p>\n<h3 id=\"table-features\">Table features</h3>\n<p>While not a user-facing feature in itself, it is a revolutionary internal mechanism in the protocol that powers all the above innovations. In the past, we (just like other formats) used protocol versions, and each version <em>bundled</em> multiple new functionalities together. It was not possible to upgrade Delta tables to enable one capability at a time in order to minimize compatibility issues between various engines reading the same table. “<a target=\"_blank\" href=\"https://delta.io/blog/2023-07-27-delta-lake-table-features/\">Table features</a>” refines this rigid “version” approach into a more flexible approach - each table can enable/disable individual capabilities (that is, “features” like deletion vectors) as needed and engines can add support for each feature incrementally.</p>\n<p>Delta on Spark already supports creating, writing, and reading tables with the above features, and support for engines is coming via the Delta Kernel project (to be discussed further in part 2 of this blog post).
