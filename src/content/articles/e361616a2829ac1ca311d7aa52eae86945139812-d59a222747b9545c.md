contentHtml: "<p>Have you ever searched for something like “low fat yogurt” at any online grocery store and noticed how the results seem to understand what you mean? Instead of only showing items with an exact match, the top-ranked products are often semantically related. You might see items like “Greek yogurt” or “yogurt with 0.5% fat,” even when only one word matches lexically. This is the power of semantic search, and when combined with traditional lexical search, it creates a hybrid search experience that delivers both precision and recall.</p> \n<p><a href=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/06/26/BDB-5826-1.png\"><img loading=\"lazy\" class=\"alignnone wp-image-92329 size-large\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/06/26/BDB-5826-1-474x1024.png\" alt=\"Semantic search returning products semantically related to a low fat yogurt query\" width=\"474\" height=\"1024\"></a></p> \n<p>At Delivery Hero, one of the world’s leading online food delivery platforms, the search team has been using semantic search for grocery verticals since 2024. What started as a proof-of-concept has evolved into a production-grade hybrid search system powered by Amazon OpenSearch Service. This system combines radial vector search with lexical retrieval to deliver highly relevant product results at scale.</p> \n<p>In this post, we walk through how Delivery Hero migrated their semantic search infrastructure to <a href=\"https://aws.amazon.com/opensearch-service/\" target=\"_blank\" rel=\"noopener\">Amazon OpenSearch Service</a>, why they chose radial search over traditional k-nearest neighbor (k-NN) search, and the optimizations that made the system fast, cost-effective, and flexible for experimentation.</p> \n<h2 id=\"legacy-system-overview\">Legacy system overview</h2> \n<p>The original semantic search system was built as a standalone service using SpringBoot and Apache Lucene 9.9, deployed on Kubernetes. The retrieval flow worked as follows:</p> \n<ol type=\"1\"> \n <li>A user starts a search on the application.</li> \n <li>The semantic search system retrieves the top 50 nearest-neighbor candidates from a static in-memory Lucene index.</li> \n <li>These candidates passed through a filtering layer to remove out-of-stock items.</li> \n <li>The filtered semantic results were merged with a parallel set of lexical search results.</li> \n <li>A final ranking step combined both candidate sets to produce the response.</li> \n</ol> \n<p>The team iterated on this system over seven versions and conducted multiple A/B tests to refine the approach. The initial system performed well, however as the business scaled, several pain points emerged:</p> \n<ul> \n <li>Scalability limitations: Running vector indices as static, in-memory structures inside Kubernetes pods meant that scaling required provisioning larger pods or adding replicas. Both options were expensive and operationally complex.</li> \n <li>Multi-model experimentation was difficult: Running A/B/C tests with three different product embedding model variants required fitting all models within a Kubernetes stateless workload. This created memory pressure and complicated deployment pipelines.</li> \n <li>Operational overhead: Managing index builds, deployments, and version rollouts for a custom Lucene-based service required significant engineering effort compared to a managed service.</li> \n</ul> \n<h2 id=\"architecture-modernization-with-opensearch-service\">Architecture modernization with OpenSearch Service</h2> \n<p>By the end of 2025, Delivery Hero had migrated their entire search infrastructure from self-managed Elasticsearch 7.x on Google Kubernetes Engine (GKE) to the fully managed Amazon OpenSearch Service 3.x. This migration created a natural opportunity to consolidate the legacy semantic search service into OpenSearch as well.</p> \n<p>The new architecture separates concerns into two distinct pipelines: an ingestion pipeline for indexing product embeddings, and an inference pipeline for real-time hybrid retrieval.</p> \n<h3 id=\"ingestion-pipeline\">Ingestion pipeline</h3> \n<p>For the ingestion pipeline, Delivery Hero chose <a href=\"https://docs.aws.amazon.com/opensearch-service/latest/developerguide/ingestion.html\" target=\"_blank\" rel=\"noopener\">Amazon OpenSearch Ingestion (OSIS)</a> to sync product embedding data from Amazon Simple Storage Service (Amazon S3) to the OpenSearch domain.</p> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/06/26/BDB-5826-2.jpg\" alt=\"Ingestion pipeline syncing product embeddings from Amazon S3 to Amazon OpenSearch Service through OpenSearch Ingestion\" width=\"600\"></p> \n<p>The flow works as follows:</p> \n<ol type=\"1\"> \n <li><strong>ML model</strong></li> \n <li><strong>Airflow job:</strong> An existing Apache Airflow job periodically generates product embeddings using an external machine learning (ML) model and periodically dumps the results (product parent ID + embedding vector) to an S3 bucket.</li> \n <li><strong>OpenSearch Ingestion pipeline:</strong> An OpenSearch Ingestion pipeline is configured with a scheduled S3 scan that performs a nightly scan from S3 and updates the new k-NN index in OpenSearch Service.</li> \n</ol> \n<div class=\"hide-language\"> \n <pre><code class=\"language-yaml\">version: '2'\nembedding-pipeline:\n  source:\n    s3:\n      acknowledgments: true\n      scan:\n        buckets:\n          - bucket:\n              name: my-bucket-name\n              filter:\n                include_prefix:\n                  - vector-search/json-index/latest\n        range: PT24H\n        scheduling:\n          interval: PT24H\n      aws:\n        region: eu-central-1\n        sts_role_arn: arn:aws:iam::&lt;aws-account-id&gt;:role/osis-pipeline-role\n      codec:\n        ndjson: {}\n      compression: none\n  workers: '1'\n  sink:\n    - opensearch:\n        hosts:\n          - \"https://&lt;search-domain&gt;.&lt;aws-region&gt;.es.amazonaws.com\"\n        aws:\n          serverless: false\n          region: eu-central-1\n          sts_role_arn: arn:aws:iam::&lt;aws-account-id&gt;:role/search-xxx\n        index_type: custom\n        index: emb_products_v1\n        template_content: ...\n        template_type: index-template\n        routing: '${global_entity_id}'\n        document_id: '${global_entity_id}:${master_code}'\n        max_retries: '3'</code></pre> \n</div> \n<p>Because the index stores product parent IDs and embeddings are regenerated in batch, there is no need for real-time updates. This allows the team to refresh and <a href=\"https://docs.opensearch.org/latest/api-reference/index-apis/force-merge/\" target=\"_blank\" rel=\"noopener\">force-merge</a> the index once per day, resulting in highly optimized segment structures and fast retrieval speeds (p99 &lt; 35 ms during peak hours).</p> \n<p>Setting up the OSIS pipeline required only a few lines of Terraform, making it straightforward to provision and maintain as infrastructure-as-code.</p> \n<h3 id=\"inference-pipeline\">Inference pipeline</h3> \n<p>On the retrieval side, the system runs a hybrid search strategy that combines radial vector search with lexical search in parallel:</p> \n<p><img src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/06/26/BDB-5826-3.png\" alt=\"Hybrid inference pipeline running radial vector search and lexical search in parallel before merging and re-ranking results\" width=\"600\"></p> \n<ol type=\"1\"> \n <li><strong>Query embedding</strong>: A user’s search query first reaches the Query Understanding (QU) service, where it is encoded into an embedding using the same live ML model employed for product embeddings. To optimize performance, embeddings for top queries are cached.</li> \n <li><strong>Parallel lexical and semantic retrieval</strong>: \n  <ul> \n   <li>A radial k-NN search runs against the product embeddings index using <code>min_score</code> to retrieve all semantically similar products above a similarity threshold.</li> \n   <li>A lexical BM25 search runs against the product catalog index. <p></p>\n    <div style=\"width: 610px\" class=\"wp-caption alignnone\">\n     <img loading=\"lazy\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/06/26/BDB-5826-4.png\" alt=\"Chart comparing p95 OpenSearch take-time for lexical and semantic search\" width=\"600\" height=\"441\">\n     <p class=\"wp-caption-text\">Comparing p95 OpenSearch time for both lexical and semantic search.</p>\n    </div></li> \n  </ul> </li> \n</ol> \n<ol start=\"3\" type=\"1\"> \n <li><strong>ID resolution and inventory filter:</strong> Because the k-NN index stores product parent IDs, a resolution step maps these to individual product IDs via a secondary index that maintains near real-time inventory updates. This approach satisfies two key business requirements within a single retrieval call: product-id resolution and real-time availability filtering.</li> \n <li><strong>Merge and re-rank:</strong> A custom post-processing step combines results from both lexical and radial search, applies re-ranking logic, and returns the final result set.</li> \n</ol> \n<h3 id=\"why-radial-search\">Why radial search?</h3> \n<p>Traditional k-NN search in OpenSearch uses a top-k approach: you ask for the k nearest neighbors, and you get exactly k results regardless of how similar they actually are. This works well for many use cases, but it has a fundamental limitation for product search. It always returns a fixed number of results, even when some of those results are not semantically relevant.</p> \n<p><a href=\"https://docs.opensearch.org/latest/vector-search/specialized-operations/radial-search-knn/\" target=\"_blank\" rel=\"noopener\">Radial search</a> solves this by flipping the paradigm. Instead of asking “give me the 50 closest items,” you ask “give me all items that are at least this similar.” This is done using the <code>min_score</code> parameter in the k-NN query:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-json\">GET product-embeddings/_search\n{\n  \"query\": {\n    \"knn\": {\n      \"embedding\": {\n        \"vector\": [0.12, 0.45, 0.78, ...],\n        \"min_score\": 0.72\n      }\n    }\n  }\n}</code></pre> \n</div> \n<p>When using radial search with cosine similarity as the space type, OpenSearch normalizes scores using the related formula (<em>score = (1 + cosine_similarity) / 2)</em>, as documented in the <a href=\"https://docs.opensearch.org/latest/mappings/supported-field-types/knn-spaces/\" target=\"_blank\" rel=\"noopener\">OpenSearch knn-spaces</a> reference.</p> \n<p>This means a min_score of 0.72 in the query example, does not directly correspond to cosine similarity. Instead, 0.72 is the normalized OpenSearch score which translates to 44% cosine similarity <em>(that is, cosine_similarity = 2 × 0.72 – 1 = 0.44)</em>.</p> \n<p>If you need results with at least 90% cosine similarity, apply the formula:</p> \n<p><em>min_score = (1 + 0.90) / 2 = 0.95</em>. So, you would set <em>“min_score”: 0.95</em> in your query.</p> \n<p>This approach offers several advantages for product search:</p> \n<ul> \n <li><strong>Quality over quantity</strong>: Low-relevance results are excluded at the retrieval stage rather than relying on downstream re-ranking to filter them out.</li> \n <li><strong>Variable result set size</strong>: The system naturally adapts to query specificity. Niche queries return fewer, more precise results. Broad queries return more candidates for the re-ranker to work with. For example, a highly specific query like “Oatly oat milk barista edition” might return 5 results, while a broader query like “milk” might return 200.</li> \n <li><strong>Better recall-precision trade-off</strong>: By tuning the <code>min_score</code> threshold, the team can directly control the balance between returning too many irrelevant results and missing relevant ones.</li> \n</ul> \n<h3 id=\"how-delivery-hero-selected-the-threshold-for-radial-search\">How Delivery Hero selected the threshold for radial search</h3> \n<p>Choosing the right <code>min_score</code> threshold is important. Set it too high and you miss relevant products. Set it too low and you flood the re-ranker with noise.</p> \n<p>Delivery Hero approaches threshold selection through systematic experimentation. To achieve optimal precision across diverse markets, a tailored <code>min_score</code> threshold is assigned to each country and query type. These thresholds are meticulously determined through rigorous offline evaluations, which use historical user interaction and manually labeled data to establish a rough estimate. This initial estimate is then further refined and validated through a series of live A/B experiments.</p> \n<h2 id=\"evaluation-of-the-new-search-system\">Evaluation of the new search system</h2> \n<p>One of the key advantages of the new architecture is how naturally it supports experimentation. At Delivery Hero, we store three variants of product embeddings within a single document:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-json\">PUT product-embeddings/_doc/1?routing=FP_DE\n{\n  \"master_product_code\": \"abc123\",\n  \"embedding_variant_1\": [0.12, 0.45, 0.78, ...],\n  \"embedding_variant_2\": [0.21, 0.4, 0.98, ...],\n  \"embedding_variant_3\": [0.13, 0.65, 0.58, ...],\n  \"global_entity_id\": \"FP_DE\"\n}</code></pre> \n</div> \n<p>In this example, embedding_variant_1, embedding_variant_2, and embedding_variant_3 are generated from three different models for A/B/C testing. After each test, the winning variant is designated as the control, while the other two are replaced with new models for further experimentation. With this approach, the team can iterate continuously while maintaining constant space complexity.</p> \n<h2 id=\"optimizations-of-large-scale-production-system\">Optimizations of large scale production system</h2> \n<h3 id=\"engine-upgrade-opensearch-2.17-to-3.3\">Engine upgrade: OpenSearch 2.17 to 3.3</h3> \n<div style=\"width: 610px\" class=\"wp-caption alignnone\">\n <img loading=\"lazy\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/06/26/BDB-5826-5.png\" alt=\"Production k-NN query latency metrics from one of the busiest countries after the OpenSearch 3.3 upgrade\" width=\"600\" height=\"606\">\n <p class=\"wp-caption-text\">Production metrics from one of the busiest countries.</p>\n</div> \n<p>OpenSearch 3.x introduced significant <a href=\"https://opensearch.org/blog/opensearch-3-3-performance-innovations-for-ai-search-solutions/\" target=\"_blank\" rel=\"noopener\">performance improvements</a> for vector search workloads. Post-upgrade to OpenSearch 3.3, we observed a <strong>~18% reduction in p95 latency</strong> for k-NN queries.</p> \n<p>For Delivery Hero’s use case, the k-NN search latency was already very low on OpenSearch 2.17 (p99 of 20–30 ms), which meant the upgrade to 3.3 was not strictly necessary for all clusters. The cluster serving the control group in A/B tests still runs on OpenSearch 2.17.</p> \n<h3 id=\"shard-routing\">Shard routing</h3> \n<p>To minimize cross-shard overhead during k-NN queries, Delivery Hero implemented custom shard routing based on geographic market. Because each market (for example, Germany, Sweden, and Finland) has its own product catalog, routing queries to market-specific shards avoids unnecessary fan-out across the entire index.</p> \n<p>This is an example of how to configure routing at index time and search time using the <code>_routing</code> field:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-json\">PUT product-embeddings/_doc/1?routing=FP_DE\n{\n  \"master_product_code\": \"abc123\",\n  \"embedding_variant_1\": [0.12, 0.45, 0.78, ...],\n  \"embedding_variant_2\": [0.21, 0.4, 0.98, ...],\n  \"embedding_variant_3\": [0.13, 0.65, 0.58, ...],\n  \"global_entity_id\": \"FP_DE\"\n}</code></pre> \n</div> \n<p>And at query time:</p> \n<div class=\"hide-language\"> \n <pre><code class=\"language-json\">GET product-embeddings/_search?routing=FP_DE\n{\n  \"query\": {\n    \"knn\": {\n      \"embedding_variant_2\": {\n        \"vector\": [0.12, 0.45, 0.78, ...],\n        \"min_score\": 0.72\n      }\n    }\n  }\n}</code></pre> \n</div> \n<p>This ensures that a query for the German market only hits shards containing German products, reducing latency and compute overhead.</p> \n<h3 id=\"refresh-interval\">Refresh interval</h3> \n<p>Because the product embedding index is updated only once per day via the OSIS batch pipeline, there is no need for the default 1-second refresh interval. Delivery Hero configured the index with a longer refresh interval during ingestion and triggers a manual refresh + force merge after the nightly batch completes.</p> \n<h2 id=\"impact-on-the-business\">Impact on the business</h2> \n<p>The migration from self-managed Lucene on Kubernetes to Amazon OpenSearch Service achieved a <strong>~50% reduction in p95 latency</strong>, dropping response times from a variable 200ms+ to a stable 100ms baseline. This transition significantly improved system consistency by eliminating the high variance and rhythmic latency spikes seen in the previous architecture.</p> \n<div style=\"width: 610px\" class=\"wp-caption alignnone\">\n <img loading=\"lazy\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/06/26/BDB-5826-6.png\" alt=\"End-to-end service latency dropping to a stable 100 ms baseline after rolling out semantic search on OpenSearch for foodpanda and yemeksepeti\" width=\"600\" height=\"640\">\n <p class=\"wp-caption-text\">End service latency after rolling out semantic search with OpenSearch for foodpanda and yemeksepeti.</p>\n</div> \n<p>Beyond raw latency, the operational benefits were significant:</p> \n<ul> \n <li>Reduced infrastructure complexity: Eliminating the standalone Lucene service removed an entire deployment pipeline, monitoring stack, and on-call rotation.</li> \n <li>Faster experimentation: New embedding models can be tested by creating a new index and adjusting query routing, without requiring code deployments.</li> \n <li>Cost efficiency: Using OpenSearch’s managed infrastructure and the batch ingestion pattern (refresh once per day) reduced compute costs compared to running always-on Kubernetes pods with in-memory indices.</li> \n</ul> \n<h2 id=\"conclusion\">Conclusion</h2> \n<p>By combining radial search with lexical retrieval, Delivery Hero’s team built a system that adapts dynamically to query intent. It returns precise results for specific queries and broader candidate sets for general ones.</p> \n<p>The migration to Amazon OpenSearch Service demonstrates how a managed search platform can simplify the operational complexity of vector search while improving performance.</p> \n<p>To get started with vector search on Amazon OpenSearch Service, see the <a href=\"https://docs.opensearch.org/latest/vector-search/ai-search/index/\" target=\"_blank\" rel=\"noopener\">AI search documentation</a> and the <a href=\"https://docs.opensearch.org/latest/vector-search/specialized-operations/radial-search-knn/\" target=\"_blank\" rel=\"noopener\">OpenSearch radial search guide</a>.</p> \n<hr> \n<h2>About the authors</h2> \n<footer> \n <div class=\"blog-author-box\"> \n  <div class=\"blog-author-image\"> \n   <p><img loading=\"lazy\" class=\"alignleft size-full\" src=\"https://d2908q01vomqb2.cloudfront.net/b6692ea5df920cad691c20319a6fffd7a4a766b8/2026/06/26/BDB-5826-7.png\" alt=\"Sayan Das\" width=\"100\" height=\"100\"></p> \n  </div> \n  <h3 class=\"lb-h4\">Sayan Das</h3> \n  <p>Sayan is Staff Software Engineer at Delivery Hero specializing in high-performance search infrastructure and large-scale distributed systems.
