Simply adding more GPUs does not translate to proportional speedup. In distributed training, E2E latency per training step is determined by:&#160;</span></p>\n<p><b>E2E Latency = Max across GPU Rank (Max(Local Compute Time, Communication Time))</b><b><br>\n</b></p>\n<p><span>Near-linear scaling requires four conditions:&#160;</span></p>\n<ul>\n<li><span>Total compute time &gt;&gt; total communication time.&#160;</span></li>\n<li><span>Communication hidden behind compute without contention.&#160;&#160;</span></li>\n<li><span>Minimal recomputation from memory pressure.&#160;&#160;</span></li>\n<li><span>Good load balancing across ranks.</span><span><br>\n</span></li>\n</ul>\n<p><span>&#160;GEM’s workload threatens every one of these:&#160;</span></p>\n<ul>\n<li><span>O(Trillion) sparse parameters and O(Billion) dense parameters drive heavy communication with mixed compute patterns.</span></li>\n<li><span>Architecture diversity across layers makes overlap windows uneven; resource contention between communication and computation makes hiding communication non-trivial.</span></li>\n<li><span>Long sequences with large activations push memory usage toward its limit, forcing activation recomputation that erodes efficiency.</span></li>\n<li><span>Jagged sequences across samples create data-driven load skew that varies across ranks. </span></li>\n</ul>\n<h2><span>Our Approach and Efficiency Framework</span></h2>\n<p><span>Given the challenges outlined above, we needed a framework that turned a sprawling co-design effort into a small number of technical levers. We measure training efficiency through E2E MFU, which decomposes into two factors:</span></p>\n<p><b>E2E MFU = Local MFU (compute efficiency) × Scaling Ratio (scaling efficiency)</b></p>\n<p><span>These factors describe two related but distinct optimization problems.&#160;&#160;</span></p>\n<p><b>Local MFU (compute efficiency) </b><span>&#160;measures how well a single GPU’s compute units are utilized — how close the workload runs to the hardware roofline. It is determined by kernel design, numerical precision, and how well the workload’s compute patterns (data dimensions, sequence lengths) map onto GPU architecture (Tensor cores, memory hierarchy, streaming multiprocessor scheduling).</span></p>\n<p><b>Scaling Ratio (scaling efficiency)</b><span> measures how much single-GPU performance is retained when distributing across thousands of GPUs. A scaling ratio of 1.0 means perfect linear scaling; in practice, communication overhead, load imbalance, straggler effects, and activation recomputation from memory pressure all erode it.</span></p>\n<p><span>To isolate local MFU, we run model layers individually on a single GPU and compute a weighted average MFU without activation recomputation or communication exposure. The scaling ratio is derived as the ratio between local and E2E MFU.</span></p>\n<p><span>This decomposition matters because it lets us treat compute efficiency and scaling efficiency as related but distinct optimization problems, each with its own dedicated set of techniques:</span></p>\n<ul>\n<li><b>Compute efficiency</b><span> is a kernel-level and numerical-precision problem. The levers are kernel design and ultra-low-precision training — both targeting the per-GPU roofline.</span></li>\n<li><b>Scaling efficiency</b><span> is a distributed-systems problem. The levers are parallelism strategy, network topology mapping, networking efficiency, memory management, and load balancing — all targeting the gap between single-GPU and multi-GPU throughput.</span></li>\n</ul>\n<p><span>Both must be addressed to maximize end-to-end MFU. </span></p>\n<h2><span>Optimizing Compute Efficiency With Recommendation Kernels and Ultra-Low-Precision Training</span></h2>\n<p><span>To address the recommendations-system-specific challenges mentioned above and push up GPU FLOPS utilization, we built a custom kernel library and an ultra-low-precision training recipe custom-built and optimized for recommendation workloads on the latest GPU hardware.&#160;</span></p>\n<ul>\n<li><b>JFA — eliminates</b><span> the up-to-50% compute waste from padding jagged inputs.</span></li>\n<li><b>BlockAttention</b><span> — reduces long user-history self-attention cost from O(L²) to O(L) while preserving model quality and efficiency&#160;</span></li>\n<li><b>GDPA</b><span> — unifies and accelerates GEM’s diverse, asymmetric attention modules where FlashAttention’s dense long-sequence assumptions break down</span></li>\n<li><b>MXFP8 attention + MLP</b><span> — turns lower-precision Tensor Core throughput into real end-to-end speedups without regressing precision-sensitive CTR/CVR objectives&#160; </span></li>\n</ul>\n<h3><span>Inside the Customized Kernel Library for Recommendation&#160;&#160;&#160;</span></h3>\n<h4><span>Jagged Sequence Flash Attention&#160;</span></h4>\n<p><span>FlashAttention is designed for dense, fixed-length sequences common in LLMs. In recommendation models, user sequences are inherently jagged — varying from hundreds to tens of thousands of tokens per sample — and padding to max length could waste up to 50% of compute.&#160;</span></p>\n<p><span>Standard FlashAttention implementations assume uniform sequence lengths for efficient tiling and parallelization; with jagged inputs, naive approaches either pad (wasting compute) or leave SMs idle when short sequences finish early. We replaced this with a novel subtraction scheme — masking Query/Key with zeros (which the Tensor Memory Accelerator (TMA) does for free) and subtracting the extra exponents — producing numerically equivalent results without the masking overhead.</span></li>\n</ul>\n<ul>\n<li><b>Backward parallelization</b><span>: FlashAttention’s backward pass requires accumulating dQ across sequence tiles, typically via costly atomic adds. We unify these modules under a single GDPA kernel optimized for production RecSys training workloads on latest generation GPUs.</span></p>\n<p><span>Existing FlashAttention kernels are designed for LLM-style dense, long-sequence inputs and perform poorly under real production traffic. We observed a </span><b>2.6x forward performance gap</b><span> and up to </span><b>4x worst-case gap</b><span> between real-world workloads and synthetic benchmarks driven by short/asymmetric K/V sequences, jagged inputs, and large batch sizes that break pipeline occupancy assumptions.</span></p>\n<p><img src=\"https://engineering.fb.com/wp-content/uploads/2026/07/image7.png\" alt=\"\" srcset=\"https://engineering.fb.com/wp-content/uploads/2026/07/image7.png 767w, https://engineering.fb.com/wp-content/uploads/2026/07/image7.png?resize=96,59 96w, https://engineering.fb.com/wp-content/uploads/2026/07/image7.png?resize=192,119 192w\"> <img src=\"https://engineering.fb.com/wp-content/uploads/2026/07/image6.png\" alt=\"\" srcset=\"https://engineering.fb.com/wp-content/uploads/2026/07/image6.png 813w, https://engineering.fb.com/wp-content/uploads/2026/07/image6.png?resize=768,452 768w, https://engineering.fb.com/wp-content/uploads/2026/07/image6.png?resize=96,57 96w, https://engineering.fb.com/wp-content/uploads/2026/07/image6.png?resize=192,113 192w\"></p>\n<p><span>We</span><a target=\"_blank\" href=\"https://pytorch.org/blog/generalized-dot-product-attention-tackling-real-world-challenges-in-gpu-training-kernels/\"><span> redesigned the kernel pipeline, scheduling, and math</span></a><span> to close the performance gap between real-world traffic and hardware roofline.</span><span><br>\n</span></p>\n<ul>\n<li><b>Pipeline redesign for non-softmax activations</b><span>: Eliminating the softmax correction stage frees four warps and their registers. We first moved the layer from full self-attention to sliding-window attention, limiting each token to nearby events and reducing complexity from O(L</span><span>2</span><span>) to O(L * window). This made longer sequences practical. The Sliding Window Attention (SWA) kernel skipped off-window tiles in JFA and </span><a target=\"_blank\" href=\"https://pytorch.org/blog/tlx-block-attention-a-warp-specialized-blackwell-kernel-for-fixed-block-sparse-self-attention/\"><span>reduced long-sequence self-attention latency by up to 68% </span><span>with neutral NE (normalized entropy, a model-quality metric)</span></a><span>.</span></p>\n<p><span>We then pushed the structure further with block-aligned attention. For the latest generation GPU, FP8 delivers 2x peak FLOPS over FP16, and FP4 delivers 4x. We expect the peak FLOPS of low precision to increase faster in next-generation GPUs. This makes low-precision training increasingly attractive as hardware vendors scale low-precision FLOPS faster than FP16.&#160;</span></p>\n<p><span>However, making low-precision training work without quality regression — addressing both numerical stability and quantization overhead — remains an industry-wide challenge. We developed MXFP8 Attention and MLP with numerical stability enhancement, which addressed both training stability and quantization overhead.&#160;&#160;&#160;&#160;&#160;</span></p>\n<h4><span>Low Precision Flash Attention&#160;&#160;</span></h4>\n<p><span>We extended the FA4 kernel with end-to-end MXFP8 blockscaled MMA for both forward and backward passes leveraging latest generation GPUs’ native support for low precision. The main challenge is that low precision attention is not just a datatype swap. Scale factors must be generated along each GEMM’s (General Matrix Multiplications) K dimension, staged through shared memory (SMEM) / tensor memory (TMEM) despite FA4’s already full TMEM footprint, and computed online for intermediates such as softmax P and backward dS.&#160;</span></p>\n<p><span>To make the Tensor core speedup survive at module level, quantization was fused into upstream normalization and projection kernels, emitting FP8 activations and tensor-core-friendly scale layouts directly while avoiding extra BF16 global-memory traffic. For GEM’s jagged recommendation workloads, FP8 data stays at unpadded positions and only compact scale factors are scattered/padded for TMA. This turns MXFP8 block-scaled MMA support into practical E2E attention speedups without introducing model quality regressions.</span></p>\n<p><img src=\"https://engineering.fb.com/wp-content/uploads/2026/07/image4.png\" alt=\"\" srcset=\"https://engineering.fb.com/wp-content/uploads/2026/07/image4.png 1430w, https://engineering.fb.com/wp-content/uploads/2026/07/image4.png?resize=916,459 916w, https://engineering.fb.com/wp-content/uploads/2026/07/image4.png?resize=768,385 768w, https://engineering.fb.com/wp-content/uploads/2026/07/image4.png?resize=1024,513 1024w, https://engineering.fb.com/wp-content/uploads/2026/07/image4.png?resize=96,48 96w, https://engineering.fb.com/wp-content/uploads/2026/07/image4.png?resize=192,96 192w\"></p>\n<p><span>To meet our unique requirements we had to develop three new innovations at the kernel level:</span><span><br>\n</span></p>\n<ul>\n<li><b>TMEM scale factor placement:</b><span> The original FA4 fully utilized 512-column TMEM for accumulators, leaving no room for block-scale factors. We solve this by overlapping scale factors with temporarily-unused TMEM regions (e.g., placing S(i) scale factors in the S(1-i) accumulator region), requiring only one additional lightweight barrier that is hidden behind existing GEMM latency.&#160;&#160;&#160;</span></li>\n<li><b>Online P-to-MXFP8 conversion:</b><span> Softmax output (P) is quantized to MXFP8 in-place within the softmax warp, reusing the row-max already computed for softmax normalization to avoid redundant reductions. For the backward kernel, we achieved &gt;1.5x speedup with MXFP8.</span></p>\n<p><img src=\"https://engineering.fb.com/wp-content/uploads/2026/07/image11.png\" alt=\"\" srcset=\"https://engineering.fb.com/wp-content/uploads/2026/07/image11.png 1200w, https://engineering.fb.com/wp-content/uploads/2026/07/image11.png?resize=916,566 916w, https://engineering.fb.com/wp-content/uploads/2026/07/image11.png?resize=768,475 768w, https://engineering.fb.com/wp-content/uploads/2026/07/image11.png?resize=1024,633 1024w, https://engineering.fb.com/wp-content/uploads/2026/07/image11.png?resize=96,59 96w, https://engineering.fb.com/wp-content/uploads/2026/07/image11.png?resize=192,119 192w\"> <img src=\"https://engineering.fb.com/wp-content/uploads/2026/07/image15.png\" alt=\"\" srcset=\"https://engineering.fb.com/wp-content/uploads/2026/07/image15.png 1200w, https://engineering.fb.com/wp-content/uploads/2026/07/image15.png?resize=916,566 916w, https://engineering.fb.com/wp-content/uploads/2026/07/image15.png?resize=768,475 768w, https://engineering.fb.com/wp-content/uploads/2026/07/image15.png?resize=1024,633 1024w, https://engineering.fb.com/wp-content/uploads/2026/07/image15.png?resize=96,59 96w, https://engineering.fb.com/wp-content/uploads/2026/07/image15.png?resize=192,119 192w\"></p>\n<h4><span>Handling Quantization Overhead&#160;</span></h4>\n<p><span>Quantization overhead mainly comes from two sources, model parameters (weights) and intermediate tensors (activations). If handled naively, the extra casting, scaling, and data movement can offset the compute speedup from low-precision Tensor cores.</span></p>\n<ul>\n<li><b>Weight – quantization on Fully Sharded Data Parallel (FSDP) shard</b></li>\n</ul>\n<ul>\n<li>\n<ul>\n<li><span>Pre-all-gather shard quantization: quantize each rank’s local shard </span><i><span>before</span></i><span> FSDP all-gather to amortize the quantization cost across ranks, this avoids re-quantizing the fully gathered weight on every rank.</span></li>\n<li><span>Quantized FSDP communication: communicate low-precision payloads (vs. BF16) to reduce all-gather volume and cut all-gather latency which further neutralizes the quantization overhead.&#160; </span></li>\n</ul>\n</li>\n</ul>\n<ul>\n<li><b>Activation – kernel fusion</b></li>\n</ul>\n<ul>\n<li>\n<ul>\n<li><span>Linear modules: Instead of doing a separate quantization step with extra kernel launch + HBM traffic, we fused activation quantization into the preceding normalization (PreNorm fusion) to avoid the overhead.&#160;</span></li>\n<li><span>Attention modules: In addition to PreNorm fusion, we also fused quantization into the preceding projection so the attention kernel consumes low-precision activations directly with no extra quantization step.</span></li>\n</ul>\n</li>\n</ul>\n<h4><img src=\"https://engineering.fb.com/wp-content/uploads/2026/07/image8.png\" alt=\"\" srcset=\"https://engineering.fb.com/wp-content/uploads/2026/07/image8.png 1868w, https://engineering.fb.com/wp-content/uploads/2026/07/image8.png?resize=916,477 916w, https://engineering.fb.com/wp-content/uploads/2026/07/image8.png?resize=768,400 768w, https://engineering.fb.com/wp-content/uploads/2026/07/image8.png?resize=1024,533 1024w, https://engineering.fb.com/wp-content/uploads/2026/07/image8.png?resize=1536,799 1536w, https://engineering.fb.com/wp-content/uploads/2026/07/image8.png?resize=96,50 96w, https://engineering.fb.com/wp-content/uploads/2026/07/image8.png?resize=192,100 192w\"></h4>\n<h4><span>Addressing Numerical Stability&#160;&#160;</span></h4>\n<p><span>Quantization errors, outliers, and rounding bias can make low-precision training&#160; numerically fragile, especially for gradient computation. We addressed these challenges with:</span></p>\n<ul>\n<li><span>Outlier mitigation:</span>\n<ul>\n<li><span>We applied Random Hadamard Transforms spread outliers and smooth distributions prior to low precision quantization.</span></li>\n</ul>\n</li>\n<li><span>Recipe tuning (fine-grained controls):</span>\n<ul>\n<li><span>We used stochastic rounding to eliminate deterministic rounding bias.</span></li>\n<li><span>Skipping / higher-precision weight-gradient (WGrad): We observed activations and gradients can exhibit more severe outlier behavior; selectively skipping WGrad or using higher precision can materially improve model quality.</span></li>\n</ul>\n</li>\n<li><span>Mixed precision:&#160;</span>\n<ul>\n<li><span>We use ultra low precision&#160; where it will have the most benefit&#160; (e.g., large GEMMs) and fall back to BF16 (e.g., later layers in the model are more sensitive to quantization errors) where ultra low&#160; precision is insufficient to meet model quality targets.</span></li>\n</ul>\n</li>\n</ul>\n<h2><span>Scaling Efficiency: 5D Parallelism, Networking, Memory, And Load Balancing&#160;</span></h2>\n<p><span>As mentioned above, for large scale distributed training:&#160;&#160;</span></p>\n<p><b>E2E Latency = Max across GPU Rank (Max(Local Compute Time, Communication Time))&#160;</b></p>\n<p><span>Near-linear scaling requires four conditions: total compute time &gt; communication time, compute / communication overlapping without contention, minimal recomputation, and good load balancing.&#160; Our optimizations address each condition to push up GEM’s scaling efficiency.&#160; </span></p>\n<table>\n<thead>\n<tr>\n<th>Condition</th>\n<th>GEM’s Challenges</th>\n<th>Optimizations</th>\n</tr>\n</thead>\n<tbody>\n<tr>\n<td>Total compute time &gt; total communication time</td>\n<td><span>O(Trillion) sparse parameters and O(Billion) dense parameters drive heavy communication with mixed compute patterns.</span></td>\n<td>Topology-aware 5D Parallelism</td>\n</tr>\n<tr>\n<td><span>Communication hidden behind compute without contention</span></td>\n<td><span>Resource contention between communication and computation </span></td>\n<td>SM Free Communication</td>\n</tr>\n<tr>\n<td><span>Minimal recomputation from memory pressure&#160; </span></td>\n<td><span>Long sequences with large activations push memory usage toward its limit, forcing activation recomputation </span></td>\n<td>Automatic Activation Checkpointing with Quantization</td>\n</tr>\n<tr>\n<td>Good load balancing across ranks</td>\n<td><span>Jagged sequences across samples create data-driven load skew that varies across ranks</span></td>\n<td>Sequence length aware load balancing</td>\n</tr>\n</tbody>\n</table>\n<h3><span>5D Parallelism, Optimized with Meta’s Network Topology</span></h3>\n<p><span>GEM’s hybrid architecture requires distinct parallelism strategies for each component as dense and sparse parameters have different compute and communication patterns. We use 5D parallelism to scale GEM’s training efficiently across thousands of GPUs: 2D FSDP with Expert Parallelism (EP) for dense parameters, and Fully Sharded 2D Model Parallelism for sparse parameters.&#160;</span></p>\n<p><span>The design principle is to match communication volume to available bandwidth across the topology hierarchy. When a collective becomes a bottleneck on a given tier, we introduce a new parallelism dimension that reduces message volume or group size on that tier.</span></p>\n<p><span>Meta’s training cluster used by GEM has a three-tier network hierarchy: Eight GPUs per host connected via NVLink , hosts within an </span><a target=\"_blank\" href=\"https://engineering.fb.com/2024/08/05/data-center-engineering/roce-network-distributed-ai-training-at-scale/\"><span>AI zone connected via RoCE</span></a><span>, and AI zones connected via oversubscribed RoCE with bandwidth reduction.&#160; </span></p>\n<p><img src=\"https://engineering.fb.com/wp-content/uploads/2026/07/image14.png\" alt=\"\" srcset=\"https://engineering.fb.com/wp-content/uploads/2026/07/image14.png 1964w, https://engineering.fb.com/wp-content/uploads/2026/07/image14.png?resize=916,523 916w, https://engineering.fb.com/wp-content/uploads/2026/07/image14.png?resize=768,439 768w, https://engineering.fb.com/wp-content/uploads/2026/07/image14.png?resize=1024,585 1024w, https://engineering.fb.com/wp-content/uploads/2026/07/image14.png?resize=1536,877 1536w, https://engineering.fb.com/wp-content/uploads/2026/07/image14.png?resize=96,55 96w, https://engineering.fb.com/wp-content/uploads/2026/07/image14.png?resize=192,110 192w\"></p>\n<h4><span>Dense Parallelism Evolution: From 1D to 3D Parallelism</span><span>&#160;&#160;</span></h4>\n<p><span>GEM’s O(Billion) dense parameters are sharded using FSDP. Parameters are distributed across GPUs and reconstructed via all-gather before computation, with gradients synchronized via reduce-scatter. We add two dimensions on top of FSDP — a replica (DDP) dimension (making it 2D FSDP) and EP — for a total of three dense parallelism dimensions (3D dense parallelism).</span><span><br>\n</span></p>\n<table>\n<thead>\n<tr>\n<th>Parallelism Dimension</th>\n<th>Collectives</th>\n<th>Topology Tier</th>\n<th>Bandwidth</th>\n</tr>\n</thead>\n<tbody>\n<tr>\n<td>EP (Expert Parallelism)</td>\n<td>All-gather / reduce-scatter</td>\n<td>Intra-node NVLink</td>\n<td><span>High</span></td>\n</tr>\n<tr>\n<td>FSDP (within group)</td>\n<td>All-gather / reduce-scatter</td>\n<td>Inter-node (within AI zone)</td>\n<td><span>Medium </span></td>\n</tr>\n<tr>\n<td>DDP (across groups)</td>\n<td>All-reduce</td>\n<td>Inter-node (potentially cross zone)</td>\n<td><span>Low(Oversubscribed)</span></td>\n</tr>\n</tbody>\n</table>\n<p><span><br>\nThis topology-aware distributed training is what makes 3D dense parallelism efficient — each dimension’s communication cost is matched to the bandwidth available at its topology level.<br>\n</span></p>\n<p><b>Why 2D FSDP: Reducing Group Size for Better Bandwidth</b></p>\n<p><span>At several thousands GPU scale, standard FSDP requires collectives across the full rank count, where effective bandwidth degrades with group size —&#160; particularly when spanning multiple AI zones. 2D FSDP solves this by splitting the communication into two topology-aware tiers:</span></p>\n<ul>\n<li><b>FSDP shard group :</b><span> Parameters are sharded and reconstructed via all-gather / reduce-scatter across a much smaller group (e.g., 128-256 GPUs). The reduced group size achieves higher effective bandwidth.&#160;</span></li>\n<li><b>DDP replica group </b><span>: Gradients are synchronized via all-reduce across replica groups. Because parameters are already sharded by FSDP, each rank sends only a fraction — the message size is small enough to even tolerate the lower cross-zone bandwidth.</span></li>\n</ul>\n<p><span>We aggressively pre-fetch parameter all-gathers, pipelining each module’s communication with the previous module’s compute to maximize overlap. This works well for most modules — however, large modules like DHEN (Deep Hierarchical Ensemble Network) experts have parameter sizes where communication time still outweighs neighboring compute time, becoming exposed and slowing down E2E efficiency.</span></p>\n<p><b>Adding Expert Parallelism: Pushing Heavy Communication to the Fastest Links</b></p>\n<p><span>To address communication exposure from large dense expert modules, we layer EP on top of 2D FSDP. With EP, each rank holds only one expert, shrinking the FSDP all-gather to a single expert’s parameters — reducing both group size and message size.</span></p>\n<p><span>The extra EP communication is placed on intra-node NVLink with high bandwidth&#160; making it easily hidden. The forward and backward passes coordinate FSDP and EP collectives:</span></p>\n<ul>\n<li><b>Forward</b><span>: FSDP all-gather expert params (16-way, inter-node) → EP all-gather activations (2-way, intra-node NVLink) → compute local experts on full batch → EP reduce-scatter outputs (2-way, intra-node NVLink).&#160;</span></li>\n<li><b>Backward</b><span>: FSDP all-gather expert params (16-way, inter-node) → EP all-gather output gradients (2-way, intra-node NVLink) → compute expert gradients → EP reduce-scatter input gradients (2-way, intra-node NVLink) → FSDP reduce-scatter param gradients (16-way, inter-node). </span></li>\n</ul>\n<h4><img src=\"https://engineering.fb.com/wp-content/uploads/2026/07/image16.png\" alt=\"\" srcset=\"https://engineering.fb.com/wp-content/uploads/2026/07/image16.png 1978w, https://engineering.fb.com/wp-content/uploads/2026/07/image16.png?resize=916,508 916w, https://engineering.fb.com/wp-content/uploads/2026/07/image16.png?resize=768,426 768w, https://engineering.fb.com/wp-content/uploads/2026/07/image16.png?resize=1024,568 1024w, https://engineering.fb.com/wp-content/uploads/2026/07/image16.png?resize=1536,853 1536w, https://engineering.fb.com/wp-content/uploads/2026/07/image16.png?resize=96,53 96w, https://engineering.fb.com/wp-content/uploads/2026/07/image16.png?resize=192,107 192w\"></h4>\n<h4><span>Sparse Parallelism Evolution: From 1D to 2D memory overhead free parallelism&#160;</span></h4>\n<p><span>GEM’s sparse parameters (O(Trillion) embedding tables) present unique scaling challenges distinct from dense parameters. Embedding tables require model-parallel sharding with all-to-all communication for feature distribution, and their sheer size makes memory overhead a primary constraint. We evolved through three generations of sparse parallelism to address these challenges.</span></p>\n<table>\n<thead>\n<tr>\n<th></th>\n<th>Load imbalance</th>\n<th>Memory overhead</th>\n<th>Communication cost</th>\n</tr>\n</thead>\n<tbody>\n<tr>\n<td><strong>V1: 1D Model Parallelism</strong></td>\n<td>Poor</td>\n<td>None</td>\n<td>Very high – full rank</td>\n</tr>\n<tr>\n<td><strong>V2: 2D Model Parallelism</strong></td>\n<td>Good</td>\n<td>High — each replica group maintains a full copy of sparse parameters O(Trillion)</td>\n<td>Moderate — reduced group size</td>\n</tr>\n<tr>\n<td><strong>V3: Fully Sharded 2D Model Parallelism</strong></td>\n<td>Good</td>\n<td>Near zero</td>\n<td>Moderate — extra comm through fast NVLink</td>\n</tr>\n</tbody>\n</table>\n<p><b>V1 → V2: Solving Imbalance and Communication Bottlenecks</b></p>\n<p><span>At several thousands GPU scale, 1D model parallelism hits two fundamental bottlenecks for good efficiency:&#160;</span></p>\n<ul>\n<li><b>Load imbalance:</b><span> Distributing embedding table shards across thousands of ranks results in severe workload skew — each rank holds too few shards for balanced partitioning.</span></li>\n<li><b>Communication latency:</b><span> All-to-all collective group size scales with total rank count. Cross-node bandwidth degrades rapidly with group size, particularly when jobs span multiple AI zones where bandwidth is oversubscribed&#160;</span></li>\n</ul>\n<p><span>2D model parallelism addresses both by partitioning ranks into smaller model-parallel groups (e.g., 256 GPUs), with multiple replica groups performing data parallelism. Each replica group independently shards and communicates within a much smaller scope, reducing all-to-all latency and improving load balance — delivering significant QPS gains over 1D at large scale.</span><b></b></p>\n<p><b>V2 → V3: Eliminating Memory Overhead</b></p>\n<p><span>The tradeoff of V2 is memory: each replica group must hold a full copy of its assigned shard’s parameters. For GEM’s trillion-parameter sparse tables, this O(T) overhead can consume significant HBM — blocking further model scaling.&#160;&#160;</span></p>\n<p><span>Fully Sharded 2D removes this overhead by further sharding each replica’s parameter copy across its groups. Each rank stores only a fraction of the shard, and parameters are reconstructed on-demand:</span></p>\n<ul>\n<li><b>Forward:</b><span> All-gather table shards → all-to-all feature distribution → embedding lookup → all-to-all embedding return</span></li>\n<li><b>Backward:</b><span> All-gather table shards → all-to-all gradient exchange → local update → reduce-scatter parameters</span></li>\n</ul>\n<p><span>The extra all-gather and reduce-scatter from V3 are mapped to intra-node NVLink. We overlap these collectives with concurrent dense compute through pipelining, and schedule the all-gather to release reconstructed copies before peak memory usage.</span></p>\n<p><span>With these optimizations, we’re able to make sparse scaling nearly overhead-free at GEM’s training scale with very minimal communication exposure. </span></p>\n<p><img src=\"https://engineering.fb.com/wp-content/uploads/2026/07/image3.png\" alt=\"\" srcset=\"https://engineering.fb.com/wp-content/uploads/2026/07/image3.png 1996w, https://engineering.fb.com/wp-content/uploads/2026/07/image3.png?resize=916,438 916w, https://engineering.fb.com/wp-content/uploads/2026/07/image3.png?resize=768,367 768w, https://engineering.fb.com/wp-content/uploads/2026/07/image3.png?resize=1024,489 1024w, https://engineering.fb.com/wp-content/uploads/2026/07/image3.png?resize=1536,734 1536w, https://engineering.fb.com/wp-content/uploads/2026/07/image3.png?resize=96,46 96w, https://engineering.fb.com/wp-content/uploads/2026/07/image3.png?resize=192,92 192w\"></p>\n<h3><span>Networking Efficiency : Getting Communication Off the SMs</span></h3>\n<p><span>With 5D parallelism, GEM hides most communication behind compute kernels through pipelining. However, communication collectives could also occupy SMs, which creates SM contention. Communication kernels occupy SMs (e.g. ~24 SMs for all-gather, reduce-scatter) that would otherwise be utilized by compute kernels running in parallel, costing up to 15% efficiency. What makes it worse is that compute kernel performance could drop more than SM occupancy loss, since wave scheduling could end up with more waste.&#160;</span></p>\n<p><span>Hence, our primary networking efficiency push is SM-free communication — offloading data movement from SMs to dedicated hardware engines.</span></p>\n<p><img src=\"https://engineering.fb.com/wp-content/uploads/2026/07/image5.png\" alt=\"\" srcset=\"https://engineering.fb.com/wp-content/uploads/2026/07/image5.png 1999w, https://engineering.fb.com/wp-content/uploads/2026/07/image5.png?resize=916,420 916w, https://engineering.fb.com/wp-content/uploads/2026/07/image5.png?resize=768,352 768w, https://engineering.fb.com/wp-content/uploads/2026/07/image5.png?resize=1024,469 1024w, https://engineering.fb.com/wp-content/uploads/2026/07/image5.png?resize=1536,704 1536w, https://engineering.fb.com/wp-content/uploads/2026/07/image5.png?resize=96,44 96w, https://engineering.fb.com/wp-content/uploads/2026/07/image5.png?resize=192,88 192w\"></p>\n<p><span>For pure data-movement collectives (e.g., all-gather), we use </span><a target=\"_blank\" href=\"https://arxiv.org/abs/2510.20171\"><span>NCCLX </span></a><span>— Meta’s extension to the NCCL library — for copy-free, SM-free communication. NCCLX leverages hardware features to move data without SM involvement: the Copy Engine (CE) handles intra-node NVLink transfers and RDMA handles inter-node transfers, reducing SM usage from 24 to 1 for all-gather. This reclaims ~23 SMs for compute, yielding ~5% E2E QPS gain at full training scale.</span></p>\n<p><span>For collectives that require reduction (e.g., All-Reduce), we found NVLink SHARP with in-network reduction a viable option to reduce SM usage by offloading the reduction computation from SMs to the network switch hardware.</span></p>\n<h3><span>Memory Efficiency: Large Local Batches Without Paying the Full Memory Bill&#160;</span></h3>\n<p><span>Per-GPU memory breaks down into three categories: activations, embedding tables, and dense parameters (including optimizer states). After parallelism shards embedding tables and dense parameters across GPUs, activations dominate per-GPU memory and scale with model and batch size.&#160;</span></p>\n<p><span>We used two techniques to address this:</span></p>\n<p><b>Compiler-based Automatic Activation Checkpointing (AutoAC)&#160;</b></p>\n<p><span>PyTorch’s compiler-based activation checkpointing already beats traditional all-or-nothing recompute by reasoning over individual nodes in the joint forward–backward graph — saving expensive ops, recomputing cheap pointwise ops. But it still applies a single memory budget across the whole model, which leaves performance on the table when regions (compiled subgraphs between graph breaks) differ in recompute ROI (latency saved per GB of activation). We replaced the global budget with a customized per-region budget schedule, so memory flows to the regions with the highest payoff. This pushes the memory–latency tradeoff past what any uniform budget can achieve.</span><span><br>\n</span></p>\n<p><b>Activation Quantization</b></p>\n<p><span>On top of AutoAC, we further squeeze the memory usage via activation quantization. It operates on the checkpointed tensors — the set of intermediate activation tensors that AutoAC has already determined need to be stowed for the backward pass. When enabled, it quantizes these saved activation nodes (e.g., from BF16 to FP8/MX4) at the boundary between the forward and backward graphs.&#160;</span></p>\n<p><span>With these optimizations, we’re able to use large local batch sizes (up to 1K+ samples) with modest activation recompute cost to train the GEM model efficiently. This is important for scaling since small batch size and heavy activation recompute both hurt MFU.</span></p>\n<p><img src=\"https://engineering.fb.com/wp-content/uploads/2026/07/image17.png\" alt=\"\" srcset=\"https://engineering.fb.com/wp-content/uploads/2026/07/image17.png 1934w, https://engineering.fb.com/wp-content/uploads/2026/07/image17.png?resize=916,478 916w, https://engineering.fb.com/wp-content/uploads/2026/07/image17.png?resize=768,401 768w, https://engineering.fb.com/wp-content/uploads/2026/07/image17.png?resize=1024,535 1024w, https://engineering.fb.com/wp-content/uploads/2026/07/image17.png?resize=1536,802 1536w, https://engineering.fb.com/wp-content/uploads/2026/07/image17.png?resize=96,50 96w, https://engineering.fb.com/wp-content/uploads/2026/07/image17.png?resize=192,100 192w\"></p>\n<h3><span>Load Balancing: A Recommendation-Specific Straggler Problem</span></h3>\n<p><span>LLM training could avoid load balancing by padding all sequences to fixed length. For GEM, user sequences are inherently jagged, and padding wastes 50%+ of compute. Jagged kernels avoid per-rank waste but create a new problem – data-driven compute skew that varies every iteration.</span></p>\n<p><img src=\"https://engineering.fb.com/wp-content/uploads/2026/07/image9.png\" alt=\"\" srcset=\"https://engineering.fb.com/wp-content/uploads/2026/07/image9.png 1640w, https://engineering.fb.com/wp-content/uploads/2026/07/image9.png?resize=916,494 916w, https://engineering.fb.com/wp-content/uploads/2026/07/image9.png?resize=768,414 768w, https://engineering.fb.com/wp-content/uploads/2026/07/image9.png?resize=1024,552 1024w, https://engineering.fb.com/wp-content/uploads/2026/07/image9.png?resize=1536,828 1536w, https://engineering.fb.com/wp-content/uploads/2026/07/image9.png?resize=96,52 96w, https://engineering.fb.com/wp-content/uploads/2026/07/image9.png?resize=192,103 192w\"></p>\n<p><span>The heaviest rank consistently exceeds the average by ~15% each iteration. </span></p>\n<p><b>Choosing the Right Rebalancing Strategy&#160;</b></p>\n<p><span>We considered local and global rebalancing strategies to address workload imbalance:</span></p>\n<table>\n<thead>\n<tr>\n<th>Approach</th>\n<th>Mechanism</th>\n<th>Balancing Quality</th>\n<th>Overhead</th>\n</tr>\n</thead>\n<tbody>\n<tr>\n<td><strong>Local (Intra-Rank)</strong></td>\n<td>Each rank independently rebalances its own batches.</td>\n<td>High: 90% of optimal</td>\n<td>None (zero cross-rank communication).</td>\n</tr>\n<tr>\n<td><strong>Global (Cross-Rank)</strong></td>\n<td>Ranks exchange samples via all-to-all.</td>\n<td>Near-perfect</td>\n<td>Introduces new all-to-all collective per training step.</td>\n</tr>\n</tbody>\n</table>\n<p><span><br>\nThe overhead associated with the global approach — a collective on every training step — negates the very efficiency gains it aims to deliver. We developed a new technique that we call Base Batch Shuffling (BBS), where distributed readers generate small sub-batches (128 samples), which are sorted by total sequence length and interleaved (heaviest paired with lightest) when merged into full training batches (1k+ samples per rank) — capturing most of the theoretical optimal balance with zero cross-rank communication. </span></p>\n<p><img src=\"https://engineering.fb.com/wp-content/uploads/2026/07/image10.png\" alt=\"\" srcset=\"https://engineering.fb.com/wp-content/uploads/2026/07/image10.png 1999w, https://engineering.fb.com/wp-content/uploads/2026/07/image10.png?resize=916,494 916w, https://engineering.fb.com/wp-content/uploads/2026/07/image10.png?resize=768,414 768w, https://engineering.fb.com/wp-content/uploads/2026/07/image10.png?resize=1024,552 1024w, https://engineering.fb.com/wp-content/uploads/2026/07/image10.png?resize=1536,828 1536w, https://engineering.fb.com/wp-content/uploads/2026/07/image10.png?resize=96,52 96w, https://engineering.fb.com/wp-content/uploads/2026/07/image10.png?resize=192,104 192w\"></p>\n<p><b>BBS delivered 4% efficiency gain</b><span> on GEM training, comprising 4% QPS improvement and 4% peak memory reduction. Upon activation, the maximum-over-average workload gap immediately dropped.</span></p>\n<h2><span>On to the Next Level of Scale and Efficiency &#160; </span><span>&#160;&#160;&#160;</span></h2>\n<p><span>Training a foundation model at the intersection of LLMs and recommendation systems is a co-design problem, not a software problem or a hardware problem alone.
