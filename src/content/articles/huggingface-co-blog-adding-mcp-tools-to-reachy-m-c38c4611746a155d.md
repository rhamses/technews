You can give your robot a new ability, like checking the weather or searching the web, by adding a Space from the Hub instead of editing the app. The tool keeps running in the Space itself, so no code is downloaded onto your machine. And you can publish your own tools for other people to use.</p>\n<p>Adding a tool takes one command:</p>\n<pre><code>reachy-mini-conversation-app tool-spaces add pollen-robotics/reachy-mini-weather-tool\n</code></pre>\n<p>Then start the app as usual:</p>\n<pre><code>reachy-mini-conversation-app\n</code></pre>\n<p>Now you can just ask:</p>\n<pre><code>What's the weather in Paris today?\n</code></pre>\n<p>Below, we look at what a tool is, how profiles control what the robot can use, and the current limits of the remote path.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#built-in-tools\">\n\t</a>\n\t<span>\n\t\tBuilt-in tools\n\t</span>\n</h2>\n<p>When you talk to the robot, what you get back isn't only a voice, it's a system that reacts to the conversation: the robot can move and respond non-verbally, when it's applicable. The part we want to focus on here is the tools that make that possible. A tool is something the model can do during a conversation: play an emotion, move the head, look through the camera. Each tool has a name and a short description. The model reads those, decides when one is useful, calls it, and uses what comes back.</p>\n<p>Today every tool is local and ships inside the app, and most of them are about the robot's body:</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>Tool</th>\n<th>What it does</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td><code>move_head</code></td>\n<td>Queue a head pose change</td>\n</tr>\n<tr>\n<td><code>dance</code> / <code>stop_dance</code></td>\n<td>Play or clear a dance from the dances library</td>\n</tr>\n<tr>\n<td><code>play_emotion</code> / <code>stop_emotion</code></td>\n<td>Play or clear a recorded emotion clip</td>\n</tr>\n<tr>\n<td><code>head_tracking</code></td>\n<td>Toggle head-tracking offsets</td>\n</tr>\n<tr>\n<td><code>camera</code></td>\n<td>Capture a frame and analyze it</td>\n</tr>\n<tr>\n<td><code>idle_do_nothing</code></td>\n<td>Explicitly stay idle on an idle turn</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#how-profiles-control-tools\">\n\t</a>\n\t<span>\n\t\tHow profiles control tools\n\t</span>\n</h2>\n<p>A tool in the code isn't usable until it's enabled in <strong>a profile</strong>, a folder with two files that matter here: <code>instructions.txt</code> (the prompt) and <code>tools.txt</code> (the tools that are turned on).</p>\n<p>The <code>default</code> profile enables the full set:</p>\n<pre><code># profiles/default/tools.txt\ndance\nstop_dance\nplay_emotion\nstop_emotion\ncamera\nidle_do_nothing\nhead_tracking\nmove_head\n</code></pre>\n<p>If a name isn't in <code>tools.txt</code>, the model can't call it.</p>\n<p>You can also write your own tool: add a Python file to the profile (or <code>external_tools/</code>), give it a name and description, and list that name in <code>tools.txt</code>.</p>\n<p>Today there are built-in tools and custom local tools, and <code>tools.txt</code> decides which are active. This works well for the robot's body and keeps the trusted core small.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#the-limits-of-local-tools\">\n\t</a>\n\t<span>\n\t\tThe limits of local tools\n\t</span>\n</h2>\n<p>The constraint here is that every tool has to be local Python. For <code>move_head</code> or <code>play_emotion</code> that's right: they talk to the hardware and belong in the app but a lot of useful things have nothing to do with the body, like web search, weather, or lookups. For those, keeping everything local is mostly friction:</p>\n<ul>\n<li>sharing a tool means handing someone your Python files</li>\n<li>updating it means sending those files again</li>\n<li>changing it means editing the app, even though the capability is really separate from it</li>\n</ul>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#calling-tools-from-spaces\">\n\t</a>\n\t<span>\n\t\tCalling tools from Spaces\n\t</span>\n</h2>\n<p>Remote tools add a third kind, alongside the built-in and custom local tools you already have, for capabilities that are easier to publish, share, and update on their own:</p>\n<ul>\n<li>built-in robot tools stay local and trusted</li>\n<li>shareable remote tools can live in public Hugging Face Spaces</li>\n<li>you can still use custom one-off tools from <code>external_tools/</code>\nIt's a good fit for stateless capabilities like search, weather, and lookups: anything you want to iterate on without touching the app itself. And because anyone can publish a compatible Space, it's easy to share tools and build on each other's work.</li>\n</ul>\n<p>We started with two canary tools, small test tools to exercise the new flow:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://huggingface.co/spaces/pollen-robotics/reachy-mini-search-tool\">pollen-robotics/reachy-mini-search-tool</a></li>\n<li><a target=\"_blank\" href=\"https://huggingface.co/spaces/pollen-robotics/reachy-mini-weather-tool\">pollen-robotics/reachy-mini-weather-tool</a></li>\n</ul>\n<p>They're enough to exercise the whole feature: install from the Hub, discover the remote tools, enable them per profile, and let the realtime backend call them exactly like built-in tools.</p>\n<p>To use both at once, add each Space and their tools stack in the same profile:</p>\n<pre><code>reachy-mini-conversation-app tool-spaces add pollen-robotics/reachy-mini-search-tool\nreachy-mini-conversation-app tool-spaces add pollen-robotics/reachy-mini-weather-tool\n</code></pre>\n<p>Now the robot can search the web and check the weather in the same conversation, which is exactly what the <code>canary_web_search_weather</code> profile below does.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#install-list-remove\">\n\t</a>\n\t<span>\n\t\tInstall, list, remove\n\t</span>\n</h2>\n<pre><code># install + enable in active profile\nreachy-mini-conversation-app tool-spaces add &lt;owner/space-name&gt;\n# enable in a specific profile\nreachy-mini-conversation-app tool-spaces add &lt;owner/space-name&gt; --profile &lt;NAME&gt;\n# install without enabling\nreachy-mini-conversation-app tool-spaces add &lt;owner/space-name&gt; --install-only\n# list installed spaces\nreachy-mini-conversation-app tool-spaces list\n# remove an installed space\nreachy-mini-conversation-app tool-spaces remove &lt;owner/space-name&gt;\n</code></pre>\n<p><code>add</code> validates the Space on the Hub, probes the MCP endpoint, discovers its tools, and by default appends the tool IDs to the active profile's <code>tools.txt</code>. The active profile is <code>default</code> unless you've set <code>REACHY_MINI_CUSTOM_PROFILE</code>. Use <code>--install-only</code> to skip that step.</p>\n<blockquote>\n<p><code>tools.txt</code> is the gatekeeper: a remote tool is only active if its ID appears in the profile's <code>tools.txt</code>, alongside whatever built-in tools you want.</p>\n</blockquote>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#where-the-manifest-lives\">\n\t</a>\n\t<span>\n\t\tWhere the manifest lives\n\t</span>\n</h3>\n<p>Installed sources are persisted in:</p>\n<ul>\n<li><code>installed_tool_spaces.json</code> in managed app mode</li>\n<li><code>external_content/installed_tool_spaces.json</code> in terminal mode</li>\n</ul>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#tool-naming\">\n\t</a>\n\t<span>\n\t\tTool naming\n\t</span>\n</h2>\n<p>Each installed Space gets a local alias derived from its slug, with hyphens, dots, and slashes collapsing to underscores:</p>\n<pre><code>pollen-robotics/reachy-mini-search-tool → pollen_robotics_reachy_mini_search_tool\n</code></pre>\n<p>Remote tools are then namespaced with a double underscore:</p>\n<pre><code>pollen_robotics_reachy_mini_search_tool__search_web\npollen_robotics_reachy_mini_weather_tool__get_day_brief\n</code></pre>\n<p>This keeps remote tool names from colliding with built-in ones and lets multiple Spaces coexist in the same profile.</p>\n<p>The implementation also strips redundant Space-name prefixes when possible, so a verbose remote tool name becomes a cleaner local ID. If stripping would cause a collision between two tools from the same Space, the code falls back to the fully namespaced name.</p>\n<p>There is also a duplicate safety check at registry level: <code>Tool.name</code> values must be unique across the entire merged tool set. The app fails fast if two sources claim the same name.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#example-profiles\">\n\t</a>\n\t<span>\n\t\tExample profiles\n\t</span>\n</h2>\n<p>For this work we created two focused canary profiles to isolate the MCP experiment from the full embodied tool set.</p>\n<p>The first keeps a few expressive tools (emotions, head movement) and adds web search on top:</p>\n<pre><code># profiles/canary_web_search/tools.txt\nplay_emotion\nstop_emotion\nidle_do_nothing\nmove_head\npollen_robotics_reachy_mini_search_tool__search_web\n</code></pre>\n<p>The second is the same, plus the weather tool alongside search:</p>\n<pre><code># profiles/canary_web_search_weather/tools.txt\nplay_emotion\nstop_emotion\nidle_do_nothing\nmove_head\npollen_robotics_reachy_mini_search_tool__search_web\npollen_robotics_reachy_mini_weather_tool__get_day_brief\n</code></pre>\n<p>The small physical tool set means Reachy Mini can still react expressively while answering current questions from the web.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#why-the-prompts-matter\">\n\t</a>\n\t<span>\n\t\tWhy the prompts matter\n\t</span>\n</h2>\n<p>The remote-tool plumbing gets the tools into the model. The prompts decide how the model uses them.</p>\n<p>That was especially visible in the search-plus-weather canary. A combined question like:</p>\n<pre><code>Should I bring a jacket in Bordeaux today, and is there anything major happening downtown tonight?\n</code></pre>\n<p>can be handled in at least three ways: weather first then search, search first then weather, or both in the same turn. If the prompt is vague, the model serialises the calls and creates unnecessary latency. So the canary prompts became part of the feature, not just incidental configuration.</p>\n<h4>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#canary_web_searchinstructionstxt\">\n\t</a>\n\t<span>\n\t\t<code>canary_web_search/instructions.txt</code>\n\t</span>\n</h4>\n<pre><code>[default_prompt]\n## CANARY WEB SEARCH RULES\nYou have one remote tool for current web information.\nUse it when the user asks for up-to-date facts, news, live availability, or anything else that may have changed recently.\nWhen the search result already answers the question, answer directly in plain language.\nLead with the answer, not with tool chatter.\nFor remote lookups that may take a moment, you may give one very short English acknowledgment such as \"Let me check that and I'll be right back,\" then continue.\nAnswer in English unless the user explicitly asks for another language.\nMention uncertainty briefly if the result snippet is incomplete or ambiguous.\nOnly mention links when they add value or the user asks for sources.\nKeep responses short and spoken-style, as if read aloud by a voice assistant. One or two sentences is usually enough. Skip preamble, lists, headers, and filler. Give just the fact or direct answer the user needs.\n</code></pre>\n<h4>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#canary_web_search_weatherinstructionstxt\">\n\t</a>\n\t<span>\n\t\t<code>canary_web_search_weather/instructions.txt</code>\n\t</span>\n</h4>\n<pre><code>[default_prompt]\n## CANARY SEARCH AND WEATHER RULES\nYou have two remote tools:\n- a weather brief tool for compact day weather at a location\n- a web search tool for broader current web information\nUse the weather tool for today's conditions, temperature, rain chance, sunrise, sunset, or simple advice like whether to bring a jacket.\nUse web search for news, events, business hours, travel information, severe alerts, or broader current context.\nWhen the user's question mixes a weather part and a current-info part (for example, \"should I bring a jacket in Bordeaux today, and is there anything major happening downtown tonight?\"), call both tools in parallel in the same turn. Do not wait for one result before starting the other unless the weather result is needed to narrow the search.\nThen merge the results into a single short answer. Cover the weather part first, then the events or news part, in plain connected sentences. Do not label the sections or mention which tool gave which piece.\nWhen the user asks about events, news, or what is happening, give them the actual answer from the search results: name specific events, venues, or headlines. Do not tell the user to check websites, visit listing sites, or look something up themselves. If the search returns nothing concrete, say plainly that you didn't find any notable events, rather than redirecting them elsewhere.\nFor remote lookups that may take a moment, you may give one very short English acknowledgment such as \"Let me check that and I'll be right back,\" then continue.\nAnswer in English unless the user explicitly asks for another language.\nDo not talk about tool usage unless the user asks.\nKeep responses short and spoken-style, as if read aloud by a voice assistant. One or two sentences is usually enough. Skip preamble, lists, headers, and filler. Give just the fact or direct answer the user needs.\n</code></pre>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#what-works-today-and-what-doesnt\">\n\t</a>\n\t<span>\n\t\tWhat works today, and what doesn't\n\t</span>\n</h2>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>Capability</th>\n<th>Supported</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Install by slug for public, MCP-compatible Gradio Spaces (standard <code>/gradio_api/mcp/</code> endpoint)</td>\n<td>✅</td>\n</tr>\n<tr>\n<td>Multiple Spaces at once</td>\n<td>✅</td>\n</tr>\n<tr>\n<td>Per-profile enablement via <code>tools.txt</code></td>\n<td>✅</td>\n</tr>\n<tr>\n<td>Namespaced remote tool IDs</td>\n<td>✅</td>\n</tr>\n<tr>\n<td>Backend-agnostic registration (OpenAI, Gemini, Hugging Face)</td>\n<td>✅</td>\n</tr>\n<tr>\n<td>No arbitrary code downloaded into the local app</td>\n<td>✅</td>\n</tr>\n<tr>\n<td>Private or authenticated Spaces</td>\n<td>❌</td>\n</tr>\n<tr>\n<td>Non-Gradio Spaces</td>\n<td>❌</td>\n</tr>\n<tr>\n<td>Arbitrary raw MCP URLs or non-Hugging Face MCP servers</td>\n<td>❌</td>\n</tr>\n<tr>\n<td>Guaranteed parallel tool orchestration</td>\n<td>❌</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>Two things are worth calling out. First, the Space has to actually behave like an MCP server; if tool discovery fails, the install fails. Second, prompt instructions can encourage parallel calls but cannot guarantee them. If deterministic orchestration matters for a use case, that logic should move from the prompt into code.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#tips-for-publishing-a-tool-space\">\n\t</a>\n\t<span>\n\t\tTips for publishing a tool Space\n\t</span>\n</h2>\n<p>If you want others to use your tool, publish it as a public Gradio Space that exposes the standard MCP endpoint, and keep the tools stateless so they work well over the network. Whether a Space installs depends on this runtime behavior, not on tags.</p>\n<p>Tags aren't required for installation, but they help people find compatible Spaces:</p>\n<ul>\n<li><code>reachy-mini-tool</code></li>\n<li><code>mcp</code></li>\n</ul>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/adding-mcp-tools-to-reachy-mini#conclusion\">\n\t</a>\n\t<span>\n\t\tConclusion\n\t</span>\n</h2>\n<p>The app now has three kinds of tools sharing one registry: built-in, local custom, and remote MCP tools, and profiles still decide which of them a given assistant can reach. A small, trusted core stays at the center while the optional capabilities around it can be added, tested, and swapped without touching the app itself.</p>\n<p>What we're most curious about now is what people build. If you publish a tool Space, tag it <code>reachy-mini-tool</code> and <code>mcp</code> so others can find it. We'd love to see what Reachy Mini ends up able to do!</p>\n<p><em>Acknowledgements: Many thanks to <a target=\"_blank\" href=\"https://huggingface.co/FabienDanieau\">Fabien Danieau</a> for proofreading this post and helping test the workflow, to <a target=\"_blank\" href=\"https://huggingface.co/andito\">Andres Marafioti</a> for helping test it, and to <a target=\"_blank\" href=\"https://huggingface.co/RemiFabre\">Remi Fabre</a> and the Pollen Robotics team for the ideas and feedback that shaped the remote tools workflow.</em></p>\n<!----></div>"
