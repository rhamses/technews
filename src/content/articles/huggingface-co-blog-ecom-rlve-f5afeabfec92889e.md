A customer who asks <em>\"find me a USB-C charger under $25 that ships in two days\"</em> needs an agent that invokes the right catalog search, filters on three hard constraints, avoids hallucinating product IDs it never retrieved, and handles follow-ups when the top result goes out of stock.</p>\n<p>Supervised fine-tuning can teach surface-level tool use from demonstrations, but it cannot scale to the combinatorial space of constraint configurations, partial-information dialogues, and multi-step transactional workflows that real e-commerce demands.</p>\n<p>Reinforcement learning with verifiable rewards (RLVR) offers an alternative: the agent optimises for <em>outcomes</em> — did the products satisfy the constraints? Was the cart correct? Was the return initiated for the right order line? The challenge is constructing reward functions that are both <strong>verifiable</strong> (no LLM-as-a-judge subjectivity) and <strong>adaptive</strong> (difficulty that grows with the policy's capability).</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/ecom-rlve#from-rlve-gym-to-ecomrlve-gym\">\n\t</a>\n\t<span>\n\t\tFrom RLVE-Gym to EcomRLVE-GYM\n\t</span>\n</h3>\n<p>RLVE-Gym provides 400 environments for sorting, multiplication, Sudoku, and other algorithmic-reasoning tasks; however, those are all <strong>single-turn, text-in / text-out</strong> puzzles — extending to agentic domains was left as future work.</p>\n<p>EcomRLVE-GYM fills that gap: we stay in the <strong>verifiable</strong> regime (e-commerce outcomes <em>can</em> be checked algorithmically) while extending to <strong>multi-turn, tool-augmented, agentic</strong> conversations — environments where the agent must <em>act</em> (call tools, modify world state) rather than merely <em>reason</em> (produce a text answer) and compensates for the deficiency of the search system.</p>\n<p>EcomRLVE-GYM transforms customer-service outcomes structurally verifiable:</p>\n<p><a target=\"_blank\" href=\"https://cdn-uploads.huggingface.co/production/uploads/6893dd21467f7d2f5f358a95/dA0i6ZB3JDG-rqQtLRCy0.png\"><img src=\"https://cdn-uploads.huggingface.co/production/uploads/6893dd21467f7d2f5f358a95/dA0i6ZB3JDG-rqQtLRCy0.png\" alt=\"verifiable_signals_dark\"></a></p>\n<p>Every signal above can be evaluated by a program with access to the hidden ground-truth goal. No human annotation or LLM-as-a-judge is needed.</p>\n<hr>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/ecom-rlve#what-a-training-episode-looks-like\">\n\t</a>\n\t<span>\n\t\tWhat a training episode looks like\n\t</span>\n</h2>\n<p>Before we explain the framework, here is what a single EcomRLVE episode looks like at difficulty <code>d = 4</code>. The environment generates a hidden goal, a simulated user opens the chat, and the agent must use tools to satisfy the request. Every action is verified algorithmically — no LLM judge required.</p>\n<p>The reward is fully computed by code: F1 over <code>(product, variant, qty)</code> tuples, an efficiency bonus for finishing in fewer turns, and a hallucination check that every recommended product ID was actually retrieved. If the agent had picked the Lightning variant instead of USB-C, the simulated user would have corrected it mid-dialogue — and the F1 would have dropped.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/ecom-rlve#the-eight-environments\">\n\t</a>\n\t<span>\n\t\tThe eight environments\n\t</span>\n</h2>\n<p>Each environment covers a distinct real-world shopping scenario. The agent must complete the task using tools (catalog search, cart operations, order lookups, policy queries) and is scored by a program — not a human or another LLM.</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>Environment</th>\n<th>What the agent must do</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td><strong>Product Discovery</strong></td>\n<td>Find products that satisfy all the user's constraints</td>\n</tr>\n<tr>\n<td><strong>Substitution</strong></td>\n<td>An item is out of stock — find a similar, compatible alternative</td>\n</tr>\n<tr>\n<td><strong>Cart Building</strong></td>\n<td>Add the exact products, variants, and quantities the user asked for</td>\n</tr>\n<tr>\n<td><strong>Return + Replacement</strong></td>\n<td>Identify the right order line, initiate a return, suggest a replacement</td>\n</tr>\n<tr>\n<td><strong>Order Tracking</strong></td>\n<td>Resolve which order the user means and report its current status</td>\n</tr>\n<tr>\n<td><strong>Policy QA</strong></td>\n<td>Answer a deterministic question about store policy (return window, shipping rules, etc.)</td>\n</tr>\n<tr>\n<td><strong>Bundle Planning</strong></td>\n<td>Recommend a complete shopping list for a project within a budget</td>\n</tr>\n<tr>\n<td><strong>Multi-Intent Journey</strong></td>\n<td>Handle a conversation that chains 2–5 of the above tasks in sequence</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>Every environment uses the same three-part reward signal:</p>\n<ul>\n<li><strong>Task reward</strong> — did the agent actually complete the goal? (e.g., were the right products recommended, was the cart correct, was the right order tracked?)</li>\n<li><strong>Efficiency reward</strong> — did the agent complete it without wasting turns? Turns the <em>user</em> caused (asking a follow-up, confirming an action) don't count against the agent — only turns caused by agent mistakes do.</li>\n<li><strong>Hallucination penalty</strong> — did the agent only recommend products it actually retrieved during the session? Recommending product IDs that were never looked up is penalised, so the agent cannot invent results from memory.</li>\n</ul>\n<p>Invalid outputs (malformed JSON, illegal tool calls) trigger an immediate failure score, creating a strong incentive for well-formed responses from step one.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/ecom-rlve#adaptive-difficulty-curriculum\">\n\t</a>\n\t<span>\n\t\tAdaptive difficulty curriculum\n\t</span>\n</h2>\n<p>A single difficulty number <code>d</code> controls 12 independent aspects of a task simultaneously. This is important because e-commerce conversations are hard in many different ways at once — not just along one dimension.</p>\n<p><a target=\"_blank\" href=\"https://cdn-uploads.huggingface.co/production/uploads/6893dd21467f7d2f5f358a95/SALZRvBC6TP1HG1ZxqWsh.png\"><img src=\"https://cdn-uploads.huggingface.co/production/uploads/6893dd21467f7d2f5f358a95/SALZRvBC6TP1HG1ZxqWsh.png\" alt=\"Screenshot 2026-03-08 at 11.27.11\"></a></p>\n<p>Here are four representative difficulty axes:</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>What changes</th>\n<th>Easy (<code>d = 0</code>)</th>\n<th>Medium (<code>d = 6</code>)</th>\n<th>Hard (<code>d = 12</code>)</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td><strong>How many constraints</strong> the user has</td>\n<td>2</td>\n<td>5</td>\n<td>8</td>\n</tr>\n<tr>\n<td><strong>How often the user omits</strong> a constraint</td>\n<td>5%</td>\n<td>70%</td>\n<td>~80%</td>\n</tr>\n<tr>\n<td><strong>Fraction of search results</strong> that are distractors</td>\n<td>0%</td>\n<td>12%</td>\n<td>24%</td>\n</tr>\n<tr>\n<td><strong>Items that go out of stock</strong> mid-conversation</td>\n<td>0%</td>\n<td>30%</td>\n<td>50%</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>The other eight axes cover turn budget, input noise (typos, slang), context switches, retrieval depth, order-history size, policy complexity, and tool budget. The full breakdown is in the <a target=\"_blank\" href=\"https://github.com/owlgebra-ai/EcomRLVE-Gym\">technical report</a>.</p>\n<p><strong>Adaptive scheduling.</strong> Each environment tracks the agent's success rate independently and only advances to harder problems once the agent is passing the current level reliably. This keeps every environment training at the agent's capability frontier — avoiding both \"too easy to learn from\" and \"too hard to make progress on\".</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/ecom-rlve#deep-dive-cart-building-e_cart\">\n\t</a>\n\t<span>\n\t\tDeep dive: Cart Building (E_CART)\n\t</span>\n</h2>\n<p>Cart building is a good showcase because it requires the full search → inspect → clarify → act loop, has a binary ground truth, and introduces a challenge absent from most recommendation benchmarks: <strong>variant selection</strong>.</p>\n<p>To succeed, the agent must develop five distinct skills:</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>Skill</th>\n<th>What it means in practice</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td><strong>Product Discovery</strong></td>\n<td>Search the catalog with well-formed queries to find the right items</td>\n</tr>\n<tr>\n<td><strong>Variant Selection</strong></td>\n<td>Identify the correct color, size, or connector type — not just the right product</td>\n</tr>\n<tr>\n<td><strong>Cart Management</strong></td>\n<td>Add items with the exact variant and quantity the user asked for</td>\n</tr>\n<tr>\n<td><strong>Clarification Dialogue</strong></td>\n<td>Ask the user a focused follow-up when a request is ambiguous (e.g., missing size)</td>\n</tr>\n<tr>\n<td><strong>Multi-Item Orders</strong></td>\n<td>Handle shopping lists with several different products in a single conversation</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>The agent uses six tools to accomplish this:</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>Tool</th>\n<th>What it does</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td><code>catalog_search</code></td>\n<td>Searches the product catalog with a natural-language query</td>\n</tr>\n<tr>\n<td><code>catalog_get_variants</code></td>\n<td>Returns available variants (color, size, connector, etc.) for a product</td>\n</tr>\n<tr>\n<td><code>cart_add</code></td>\n<td>Adds a product to the cart with a specific variant and quantity</td>\n</tr>\n<tr>\n<td><code>cart_view</code></td>\n<td>Reads the current cart so the agent can verify it matches the request</td>\n</tr>\n<tr>\n<td><code>user_get_visit_history</code></td>\n<td>Fetches recently viewed products by user</td>\n</tr>\n<tr>\n<td><code>ask_user</code></td>\n<td>Sends a clarification question to the customer when a detail is missing</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/ecom-rlve#the-problem\">\n\t</a>\n\t<span>\n\t\tThe problem\n\t</span>\n</h3>\n<p>The generator samples 1–5 target products (scaling in difficulty with <code>d</code>), each potentially requiring a specific variant (USB-C vs Lightning, Matte vs Glossy) and a quantity &gt; 1. The agent must:</p>\n<ol>\n<li>Search the catalog to find each product</li>\n<li>Call <code>catalog.get_variants</code> to see available options</li>\n<li>Add the correct <code>(product_id, variant_id, qty)</code> tuples to the cart</li>\n</ol>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/ecom-rlve#why-variants-matter\">\n\t</a>\n\t<span>\n\t\tWhy variants matter\n\t</span>\n</h3>\n<p>Real product catalogs have sparse variant data — many products have none, and those that do typically vary only by colour or size. To create a richer discrimination task, we <strong>synthesize variants at episode initialization</strong>:</p>\n<ul>\n<li>A per-category priority list picks the most natural attribute to vary (electronics → <code>connector_type</code>; clothing → <code>size</code>; kitchen → <code>material</code>).</li>\n<li>For each target product, we generate 3 variants: 1 target + 2 plausible distractors. An \"Anker 65W USB-C Charger\" produces <code>{USB-C, Lightning, HDMI}</code>.</li>\n<li>The verifier checks <strong>composite keys</strong> <code>(product_id, variant_id)</code> — correct product but wrong variant means the unit is unmatched.</li>\n</ul>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/ecom-rlve#difficulty-scaling\">\n\t</a>\n\t<span>\n\t\tDifficulty scaling\n\t</span>\n</h3>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>Axis</th>\n<th>d = 0</th>\n<th>d = 3</th>\n<th>d = 6</th>\n<th>d = 9</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td><strong>Distinct items</strong></td>\n<td>1</td>\n<td>2</td>\n<td>3</td>\n<td>4</td>\n</tr>\n<tr>\n<td><strong>Variant required</strong></td>\n<td>21%</td>\n<td>66%</td>\n<td>93%</td>\n<td>99%</td>\n</tr>\n<tr>\n<td><strong>Multi-quantity</strong></td>\n<td>0%</td>\n<td>30%</td>\n<td>50%</td>\n<td>50%</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>At <code>d = 0</code> the agent adds a single product with no variant complexity — learning the basic <code>catalog.search → cart.add</code> workflow. At <code>d = 6</code> it juggles 3 items, nearly all requiring a specific variant, with half needing qty &gt; 1.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/ecom-rlve#scoring\">\n\t</a>\n\t<span>\n\t\tScoring\n\t</span>\n</h3>\n<p>The cart must be exactly right — correct product, correct variant, correct quantity. Partial credit is given for partially correct carts, but a perfect score requires every item to match. If the agent adds the wrong variant, the simulated user corrects it mid-dialogue (<em>\"that's the Lightning version, but I need USB-C\"</em>), giving the agent a chance to self-correct before the episode ends.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/ecom-rlve#trajectories-easy-vs-hard\">\n\t</a>\n\t<span>\n\t\tTrajectories: easy vs. hard\n\t</span>\n</h3>\n<p>Two real E_CART episodes from a Qwen 3 8B agent. At d=8 it spirals — picking Bamboo instead of Charcoal, XL instead of XS, never fixing the air fryer despite two user corrections, then hallucinating that the variant doesn't exist. This is exactly the kind of multi-step error cascade that the difficulty curriculum surfaces, and that adaptive training should teach the agent to recover from.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/ecom-rlve#user-simulation\">\n\t</a>\n\t<span>\n\t\tUser simulation\n\t</span>\n</h2>\n<p>A verifiable environment needs a user simulator that behaves realistically. We use <strong>Qwen3.5 (9.7B)</strong> to generate natural, varied user messages rather than canned templates — covering everything from typo-filled requests to mid-conversation topic switches.</p>\n<p>Two design choices matter for training quality:</p>\n<p><strong>Preferences match stated constraints.</strong> Each simulated user has a hidden set of preferences (price sensitivity, brand loyalty, shipping speed, etc.). These are deliberately biased toward whatever constraints the user communicated — so if the user said \"under $25\", the reward function actually cares about price. Without this, an agent could be penalised for correctly following the user's instructions.</p>\n<p><strong>Strategic omission.</strong> The LLM deliberately withholds some constraints from the opening message to force the agent to ask clarifying questions. The system tracks exactly what was and wasn't mentioned, so the agent is never penalised for information it was never given.</p>\n<h2>\n\t<a target=\"_blank\" collections:</p>\n<p><strong>C1 ⊂ C2 ⊂ C4 ⊂ C8</strong></p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>Collection</th>\n<th>Environments</th>\n<th>Skills
