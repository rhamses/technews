When the library gets in the way, it will\nhappily bypass it and rewrite the logic from scratch. This introduces a new concept in library development:\nthe code should not only be correct and fast, but should be designed so that an agent can drive it effectively. A clunky API\nor stale docs annoy us developers, but it now also sends the agent down a longer, more expensive path.</p>\n<p>Most benchmarks just look at the final answer. We wanted the whole process instead: not just whether the agent got\nit right, but how much work it took to get there, and how that shifts across models, library revisions, and\ntasks. We measured exactly that, using <code>transformers</code> as our case study.</p>\n<p>Here, we will introduce a tool specific benchmark focusing on how the answer was found, and provide a simple \nimplementation of one such harness, running entirely on open models driven by the\n<a target=\"_blank\" href=\"https://www.npmjs.com/package/@mariozechner/pi-coding-agent\">pi</a> coding agent, with the full sweep of\nmodels × revisions × tasks fanned out across <a target=\"_blank\" href=\"https://huggingface.co/docs/huggingface_hub/guides/jobs\">Hugging Face Jobs</a>\nso every run sees identical hardware.</p>\n<p>\n    But, <b><i>how do you optimize software for agents?</i></b>\n</p>\n<p>We're strong believers in the following two software principles:</p>\n<ul>\n<li>If it isn't tested, then it doesn't work</li>\n<li>If it isn't documented, then it doesn't exist</li>\n</ul>\n<p>This remains the same within the realm of agentic-optimized tooling, and, for once, the two are directly tied to\neach other.</p>\n<p>You want your tool to exist for an agent: it needs to be discoverable. The API needs to be clear and the docs\nneed to be extensive. They need to be structured in a way that the agent has rapid access to the useful files and\nexamples. If you want your tool to work for an agent, then you should test it for agentic-use. </p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/is-it-agentic-enough#testing-software-for-agentic-use\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tTesting software for agentic-use\n\t</span>\n</h2>\n<p>We'll use <code>transformers</code> as an example throughout this blogpost: agents <em>using</em> it to solve ML tasks (classifying\ntext, captioning images, transcribing audio), not contributing code to it; though the harness was designed to work\nwith any tool that can be operated from the command line.</p>\n<p>Our intuition on <code>transformers</code> was that usage could be dramatically simplified\nwith a few changes: a CLI, a Skill, and self-contained, task-specific examples. This is the same recipe\nrecently applied to the <a target=\"_blank\" href=\"https://huggingface.co/blog/hf-cli-for-agents\"><code>hf</code> CLI, redesigned to be agent-optimized</a>,\nwhere agents used 1.3–1.8× (and up to 6×) fewer tokens. We wanted to know whether that kind of win generalizes, and\nwhether it could be useful for transformers as well.</p>\n<p>Intuition is a powerful tool, but we wanted more evidence before we opened PRs that add several thousand lines of code to such a widely used codebase as <code>transformers</code>. We set out to measure what success looks like.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/is-it-agentic-enough#not-all-successes-are-equal\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tNot all successes are equal\n\t</span>\n</h3>\n<p>Two agents can both produce the correct label for a sentiment-classification task,\nbut one:</p>\n<ul>\n<li>writes a 40-line Python script, imports <code>transformers</code>, debugs a shape error,\nre-runs twice, and finally prints the answer;</li>\n</ul>\n<p>while the other</p>\n<ul>\n<li>types <code>transformers classify --model ... --text \"...\"</code> and is done in one call.</li>\n</ul>\n<p>Both reach <code>POSITIVE (0.9999)</code>, and here are the two paths an agent actually took on this exact task:</p>\n<pre><code># Task: classify the sentiment of \"I absolutely loved the movie, it was fantastic!\"\n<span>- # one agent: pipe a script into python and parse the output</span>\n<span>- python - &lt;&lt;'PY'</span>\n<span>- from transformers import AutoTokenizer, AutoModelForSequenceClassification</span>\n<span>- import torch</span>\n<span>- import torch.nn.functional as F</span>\n<span>-</span>\n<span>- model = AutoModelForSequenceClassification.from_pretrained(\"distilbert/distilbert-base-uncased-finetuned-sst-2-english\")</span>\n<span>- tokenizer = AutoTokenizer.from_pretrained(\"distilbert/distilbert-base-uncased-finetuned-sst-2-english\")</span>\n<span>- inputs = tokenizer(\"I absolutely loved the movie, it was fantastic!\", return_tensors=\"pt\")</span>\n<span>- with torch.no_grad():</span>\n<span>-     logits = model(**inputs).logits</span>\n<span>- probs = F.softmax(logits, dim=1)</span>\n<span>- idx = torch.argmax(probs, dim=1).item()</span>\n<span>- print(model.config.id2label[idx], probs[0][idx].item())</span>\n<span>- PY</span>\n<span>+ # the other agent: one command</span>\n<span>+ transformers classify \\</span>\n<span>+   --model distilbert/distilbert-base-uncased-finetuned-sst-2-english \\</span>\n<span>+   --text \"I absolutely loved the movie, it was fantastic!\"</span>\n</code></pre>\n<p>Both methods reach the same result. But they have very different profiles in <strong>cost, latency, token usage, and failures</strong>.</p>\n<p>If your evaluation only checks the final string, you're blind to these as well as\nwhether a change you shipped to the library (a CLI improvement, better error messages, a\nSkill) actually helped agents.</p>\n<p>Our goal with this harness is to evaluate how much work\nan agent has to do to perform a given task, and whether changes to the library improve performance.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/is-it-agentic-enough#how-do-we-run-evaluations\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tHow do we run evaluations?\n\t</span>\n</h3>\n<p>A few words on how we'll evaluate agents here.</p>\n<p>We run every task under three variants (or \"tiers\"); three different ways an agent can come at <code>transformers</code>:</p>\n<pre><code>bare     pip install transformers, and nothing else\nclone    the full transformers source, checked out in the working directory\nskill    a packaged Skill: the CLI's docs + task examples, loaded in context\n</code></pre>\n<p>These aren't nested: <code>skill</code> doesn't contain <code>clone</code> (it ships curated docs, not the source tree), and neither\nstrictly contains the other, each gives the agent a different kind of help. As we'll see, a model can sometimes \ndo better on <code>clone</code> than on <code>skill</code>.</p>\n<p>A few more choices:</p>\n<ul>\n<li>For now we only focus on deterministic tasks which can provide an exact match, as they provide a very nice ground for experimentation. Model-as-a-judge and other schemes are the obvious next steps for other tasks.</li>\n<li>Every run is its own Hugging Face Job: one per (model × revision × task), so the whole sweep runs in parallel on identical hardware, which keeps the comparison fair at scale.</li>\n<li>Results and traces land in a Hugging Face Bucket: fast, no versioning needed, and handles very high write concurrency.</li>\n</ul>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/is-it-agentic-enough#which-models-to-benchmark-against\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tWhich models to benchmark against?\n\t</span>\n</h3>\n<p>Not all models driving agents are equal, and their difference changes what you should look at when running them.</p>\n<p><em>Large open models</em></p>\n<p>At one end, you have the largest, most capable open models. On reasonably common tasks,\nthese should get the right answer, eventually. For them, task completion saturates near\n100% and stops telling you much about your tool; a more relevant benchmark is the effort\nit took the agent to get there: how many turns, tokens and seconds it took, and whether they walked a clean\npath or used deprecated APIs.</p>\n<p><em>Local</em></p>\n<p>Local models vary widely in size, and so do their abilities.\nMetrics such as <strong>\"match %\"</strong> are more relevant than for their larger counterparts,\nas you can see how model sizes/capabilities affect results on your specific\ntool.</p>\n<p>This harness not only provides guidance to library maintainers on how to improve a repository for agent interactions, it also helps assess how different agents and models perform on the tasks users care about.</p>\n<p>The harness scores every run on several axes, so that you can ask what actually matters\nfor each class of model:</p>\n<ul>\n<li><strong>match %</strong>: did the final answer contain the expected result (per-task,\ncase-insensitive substring / regex / exact, all explicit in the report);</li>\n<li><strong>median time</strong> and <strong>median tokens</strong> (new vs. cached vs. generated);</li>\n<li><strong>runs with error %</strong>: including a guard that flags runs which produced <em>nothing</em>\n(0 output tokens, no tool calls, no answer) so silent failures don't masquerade\nas \"0\";</li>\n<li><strong>marker adoption</strong>: tool-defined behavior markers; see below for an explanation\nof what this is.</li>\n</ul>\n<p>All of it lands in a report you can directly examine:</p>\n<p>\n<br>\n  <em>The live report: Overview, Coverage, and Results, all client-side.</em>\n</p>\n<p>And because it captures the native agent trace of every run, numbers are just the beginning: you\ncan read exactly what the agent did, command by command. The traces are shareable\nthrough the Hub's <a target=\"_blank\" href=\"https://huggingface.co/docs/hub/agent-traces\">agent-traces viewer</a>:</p>\n<p>\n  <img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_11.png\" alt=\"A run rendered in the Hub's agent-traces viewer: MiniMax-M2.7 on the answer-question task\"><br>\n  <em>A run rendered in the Hub's agent-traces viewer: MiniMax-M2.7 on the answer-question task.</em><br>\n  <a target=\"_blank\" href=\"https://huggingface.co/buckets/lysandre/transformers-agentic-use/tree/traces/22404f7951/pi/MiniMaxAI--MiniMax-M2.7/bare__answer-question__run1.jsonl\"><b>Open this trace on the Hub ↗</b></a>\n</p>\n<p>Before the results, a quick recap of the setup. Each run varies four things: the <strong>model</strong> driving the agent,\nthe <strong><code>transformers</code> revision</strong> it runs against, the <strong>task</strong>, and the <strong>tier</strong> (<code>bare</code> / <code>clone</code> / <code>skill</code>).\nAs discussed, we look at different metrics for the two different model categories.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/is-it-agentic-enough#large-open-models-hold-the-model-vary-the-revision\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tLarge open models: hold the model, vary the revision\n\t</span>\n</h3>\n<p>Since a large open model will usually get to the correct result, what you're really\nmeasuring is the effort it took to do so. Did it take ten turns or one? Did it follow\nan API path you deprecated because it trusted obsolete documentation? Did it hit an\nerror you hadn't foreseen?</p>\n<p>The natural experiment is to fix one strong model and vary the tool's\nrevisions: the successive git versions of <code>transformers</code> we test against, from released tags like\n<code>v5.8.0</code> and <code>v5.9.0</code> to the specific commit that introduces the CLI and Skill. We want to watch whether the load\nit puts on the agent goes up or down. We used the harness on <code>transformers</code> to check\nwhether adding a dedicated CLI and Skill actually lightened the agents' work.</p>\n<p>For the three large models we used in our tests, the average time spent on all tasks indicates that the Skill commit\nresults in less time spent working on the tasks:</p>\n<p>\n  <img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_13.png\" alt=\"Median time per revision, by tier\"><br>\n  <em>Median time per revision, by tier: the skill commit (green dot) is the fastest.</em>\n</p>\n<p>On the other hand, in the experiments in which we cloned the repository, we can see a significant increase\nin token consumption due to the commit that introduced the CLI and examples, as we'll see in a moment.</p>\n<p>\n  <img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_12.png\" alt=\"Median new tokens per revision, by tier\"><br>\n  <em>Median new tokens per revision, by tier: the clone variant jumps once the CLI lands in the repo.</em>\n</p>\n<p>Reading the clone-variant traces explains why. The commit adds a command, but it also ships the\nCLI's implementation and a set of <code>cli/agentic/*.py</code> usage examples into the repository directly. </p>\n<p>On the <code>clone</code> variant the agent has a full transformers checkout in front of it, and roughly a third of the runs go read the new\nsurface (the <code>/cli/</code> tree and the example scripts) to learn the interface before calling it. This raises the\nmedian input from ~4k to ~6.4k tokens. </p>\n<p>The two charts are then two sides of one tradeoff: the commit buys the large models less time \n(they reach for the CLI instead of debugging Python) at the cost of more\ntokens (they read the code that taught them the CLI). A tradeoff worth knowing about before merging PRs.</p>\n<p>One caveat works in the CLI's favor, though, which isn't benchmarked yet: the cost of reading it is amortized \nwith successive runs. Our setup is built for one-off experiments. Each run is a fresh agent that rediscovers \nthe CLI from scratch, so it pays the discovery cost every time. In real usage an agent learns the interface \nonce and then solves task after task within the same session, amortizing that cost across many requests. The\ntoken bump we measure here is closer to a worst case than to what a user would see day to day.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/is-it-agentic-enough#small-models-hold-the-revision-vary-the-model\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tSmall models: hold the revision, vary the model\n\t</span>\n</h3>\n<p>Open models give us fine-grained control over the variables that matter most here: size, configuration, quantization,\nprovider, training, and anything that would differ from one model to the next. They're also where a good tool surface\nmatters most: a small model asked to \"use <code>transformers</code> to do X\" on a <code>bare</code> environment can\nguess an API that changed some releases ago, may do unnecessary tool calls, and can\nget the wrong answer.</p>\n<p>So here the experiment is the opposite of the above: hold the revision and sweep the model. This helps\nsee which models actually take care of the task, not just by token count and time,\nbut down to which ones can't reliably handle the tool calls. Our intuition is\nthat the smaller the model, the harder both tool use and the task get; we ran the\nharness across a range of model sizes to test exactly that:</p>\n<p>\n  <img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_14.png\" alt=\"Match % across models, by tier\"><br>\n  <em>Match % across models, by tier: the skill tier lifts the larger models but drops the smaller ones.</em>\n</p>\n<p>which also seems to be correlated with the number of tokens ingested</p>\n<p>\n  <img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_15.png\" alt=\"Median new tokens across models, by tier\"><br>\n  <em>Median new tokens across models, by tier.</em>\n</p>\n<blockquote>\n<p>A note on fair comparison: naively averaging across tasks is misleading when\ncoverage is uneven (a model that only finished the quick tasks looks fast). The\nreport has a <strong>\"shared tasks only\"</strong> toggle (across models and/or revisions) so\nyou compare like-for-like, and a <strong>Coverage</strong> heatmap so you can see exactly which\ntask × revision × model cells actually ran.</p>\n</blockquote>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/is-it-agentic-enough#tweaking-the-tool-markers-and-results\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tTweaking the tool: markers and results\n\t</span>\n</h2>\n<p>Two things come together here: how to look past whether the agent succeeded to what it did and how it\ndid it; as well as the first results we pulled out of the harness.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/is-it-agentic-enough#whats-a-marker\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tWhat's a marker?\n\t</span>\n</h3>\n<p>Match %, tokens, and time tell you the cost of a run but don't tell you much about what happened under the hood.</p>\n<p>This is why we've introduced the concept of markers. A marker is a named pattern the profile (the\nsmall per-tool plugin that teaches the harness how to build and drive a given library) matches against\na run. </p>\n<p>It is a one-line label for a behavior you care about, checked against the shell\ncommands the agent ran, the code it wrote, the files it read, or its final\nanswer. A run can fire several markers or none; the report shows how often each one fired,\nper model and per revision.</p>\n<p>For <code>transformers</code> we declare a handful but we'll only look at the two most relevant ones:</p>\n<ul>\n<li><strong><code>cli</code></strong>: the agent invoked the <code>transformers</code> command-line tool (e.g.\n<code>transformers classify …</code>) instead of writing Python.</li>\n<li><strong><code>pipeline</code></strong>: it reached for the high-level <code>pipeline(...)</code> Python API.</li>\n</ul>\n<p>These are what we watch to see whether a change actually shifted the agent's behavior. Interestingly here,\nthe larger the model, the more it leverages the new context instead of using its memory; therefore leveraging\nthe newly introduced CLI.</p>\n<p>\n  <img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_16.png\" alt=\"CLI adoption by tier across models\"><br>\n  <em>CLI adoption by tier across models: only the skill tier reaches for it, and more so as models grow.</em>\n</p>\n<p>CLI adoption is new: the CLI lands in a single commit, isn't in any model's training data, and is only\nlightly documented. The effect is clear: it's the Skill variant, the one that ships the CLI's\ndocumentation, that actually reaches for it, at 55.3%.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/is-it-agentic-enough#is-the-cli--skill-commit-helping\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tIs the CLI + Skill commit helping?\n\t</span>\n</h3>\n<p>Comparing the commit across model sizes, the CLI + Skill helps the bigger models: on the <code>skill</code> tier, Kimi and the other large agents reach for the CLI and finish in fewer turns. (On <code>clone</code> they spend <em>more</em> input tokens first, reading the new CLI code, as we saw above, so the win shows up in time and turns, not raw tokens.)</p>\n<p>\n  <img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_5.png\" alt=\"Kimi-K2.6, GLM-5.1, and MiniMax-M2.7 across revisions\"><br>\n  <em>Kimi-K2.6, GLM-5.1, and MiniMax-M2.7 across revisions</em>\n</p>\n<p>But in some smaller-model settings, it appears to hurt performance. One plausible explanation is that small\nmodels lean on memorized API patterns, reproducing <code>pipeline(...)</code> snippets\nthey've seen in their training data. The new concepts are then a larger\nsurface for them to get wrong. You can watch this directly on the harness: lower\nmatch %, more retries, the <code>cli</code> marker barely firing. It is particularly striking on the Qwen3-4B model:\nthe Skill barely changes its match rate yet its cost distribution is significantly affected. </p>\n<p>Almost all of that comes from the <code>clone</code> tier. The checkout now contains\nthe CLI's implementation and <code>cli/agentic/*.py</code> examples, and the 4B agent reads them in bulk: its median new\ntokens jump from ~2.4k to ~23k, with time and output skyrocketing as well, for no gain in\naccuracy.</p>\n<p>\n  <img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_7.png\" alt=\"Qwen3-4B cost distributions across revisions: elapsed, new tokens, repeat tokens, out tokens\"><br>\n  <em>Qwen3-4B across revisions. The CLI + Skill commit fans the cost distribution wide open, on the <code>clone</code> tier the agent reads the newly-shipped CLI source in bulk (~10× the new tokens), for no gain in match %. (<code>repeat tokens</code> stays flat: this setup uses no prompt caching.)</em>\n</p>\n<p>Sometimes, though, the Skill breaks correctness outright. Reading the traces shows how, for example for Qwen3-14B: \nadding the Skill drops its overall match rate from 67% (bare) to 43%, and on the simplest tasks the collapse is very\nvisible: <code>classify-sentiment</code> goes from 100% on the <code>clone</code> variant to <strong>0%</strong> with the Skill. </p>\n<p>\n  <img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_17.png\" alt=\"Qwen3-14B classify-sentiment match % by tier across revisions\"><br>\n  <em>Qwen3-14B on <code>classify-sentiment</code>, by tier: <code>clone</code> (blue) holds at 100% across revisions, but the Skill variant (green) collapses to 0% at the CLI + Skill revision.</em>\n</p>\n<p>Looking at the traces, the model mistakes the CLI for a <em>tool it can call directly</em> (as in an agentic-harness\ntool, like web-search). The Skill is <strong>not</strong> an executable tool: it's documentation loaded\ninto the agent's context, and the <code>transformers</code> CLI is only ever meant to be run from the shell (via <code>bash</code>); so this\nwill not work.</p>\n<p>Qwen3-14B reads the Skill and, in 39 of its 56 Skill runs, either emits a <code>transformers(command=\"classify\", ...)</code>\ntool call (a tool that was never registered) or, finding nothing like it among its <code>read</code>/<code>bash</code>/<code>edit</code>/<code>write</code>\ntools, concludes it <em>can't</em> run a model and gives up. Either way, rather than fall back to the one-line\n<code>pipeline(...)</code> that scored 100% on the <code>clone</code> checkout, it declares the task impossible.</p>\n<p>\n  <img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_10.png\" alt=\"Qwen3-14B gives up on classify-sentiment under the Skill variant\"><br>\n  <em>Qwen3-14B on classify-sentiment (Skill variant): it reasons that read/bash/edit/write can't run a model, and gives up.</em>\n</p>\n<p>This is exactly what we built the harness to catch: the same change that speeds the large models\nends up breaking the small ones, which seemed a bit counterintuitive to us at first and something we'd likely have\nshipped as-is.
