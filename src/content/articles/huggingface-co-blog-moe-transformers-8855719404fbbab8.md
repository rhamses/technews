href=\"https://huggingface.co/blog/moe-transformers#introduction\">\n\t</a>\n\t<span>\n\t\tIntroduction\n\t</span>\n</h2>\n<p>Over the past few years, scaling dense language models has driven most progress in LLMs. From early models like the original <a target=\"_blank\" href=\"https://nlp.fast.ai/classification/2018/05/15/introducing-ulmfit.html\">ULMFiT</a> (~30M parameters) or GPT-2 (1.5B parameters, which at the time was considered \"too dangerous to release\" 🧌), and eventually to today’s hundred-billion–parameter systems, the recipe was simple:</p>\n<blockquote>\n<p>More data + more parameters gives better performance.</p>\n</blockquote>\n<p><a target=\"_blank\" href=\"https://huggingface.co/papers/2001.08361\">Scaling laws</a> reinforced this trend, but dense scaling has practical limits:</p>\n<ul>\n<li>Training becomes increasingly expensive.</li>\n<li>Inference latency grows.</li>\n<li>Deployment requires significant memory and hardware.</li>\n</ul>\n<p>This is where Mixture of Experts (MoEs) enter the picture.</p>\n<blockquote>\n<p>If you're already familiar with MoEs and want to jump straight into the engineering work done in transformers, you can head directly to <a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#transformers-and-moes\">Transformers and MoEs</a>.</p>\n</blockquote>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#from-dense-to-sparse-what-are-moes\">\n\t</a>\n\t<span>\n\t\tFrom Dense to Sparse: What Are MoEs?\n\t</span>\n</h2>\n<p>A Mixture of Experts model keeps the Transformer backbone, but replaces certain dense feed-forward layers with a set of <strong>experts</strong>. An “expert” is not a topic-specialized module (e.g., \"math expert\", \"code expert\"). It is simply a learnable sub-network. For each token, a <strong>router</strong> selects a small subset of experts to process it.</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/moe_routing.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/moe_routing.png\" alt=\"MoE routing diagram\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 1: Expert 1 among 4 experts is activated (Source: <a target=\"_blank\" href=\"https://newsletter.maartengrootendorst.com/p/a-visual-guide-to-mixture-of-experts\">Maarten Grootendorst</a>)</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>Different tokens activate different experts, based on their hidden representations.</p>\n<blockquote>\n<p>Model capacity depends on total parameters, but inference speed depends on active parameters.</p>\n</blockquote>\n<p>This is the key idea.</p>\n<p>For example, take <a target=\"_blank\" href=\"https://huggingface.co/openai/gpt-oss-20b\"><code>gpt-oss-20b</code></a>. It has 21B total parameters, but uses 4 active experts per token, out of a total of 32 experts. Considering the shared components plus the active experts, this model uses ~3.6B active parameters per token. Running this model on an M3 Ultra Mac, which has a memory bandwidth of about 800 GB, we could estimate generation speed as ~ <code>800 / (3.6 * 2)</code> in <code>bfloat16</code>, where each parameter takes 2 bytes. This yields about <strong>111 tokens per second</strong>. The actual performance number we get is ~115 tok/s, which is very close to the back-of-the-envelope calculation.</p>\n<video controls>\n  <source src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/gpt-oss-20-inference.mp4\" type=\"video/mp4\">\n  Your browser does not support the video tag.\n</video>\n<p>This super fast speed confirms the model works approximately as a 3.6B parameter one, but it has the same capacity (or quality) as a 21B parameter model.</p>\n<p><em>(Note: speed would be even faster if we used kernels for the native mxfp4 quantization the model uses).</em></p>\n<p>MoEs are attractive for these reasons:</p>\n<ol>\n<li><p>Better Compute Efficiency</p>\n<p> Given a fixed training FLOP budget, MoEs often outperform dense counterparts.</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/faster_training.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/faster_training.png\" alt=\"MoE vs Dense training graphs\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 2: Dense vs. MoE training curves (Source: <a target=\"_blank\" href=\"https://huggingface.co/papers/2409.02060\">OLMoE: Open Mixture-of-Experts Language Models</a>)</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p> This means faster iteration and better scaling efficiency.</p>\n</li>\n<li><p>A Natural Parallelization Axis</p>\n<p> Experts provide a structural boundary in the computation graph. Since different tokens engage different experts, we can parallelize across experts (we discuss this later in <a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#expert-parallelism\">Expert Parallelism</a>).</p>\n</li>\n<li><p>Industry Adoption</p>\n<p> Recent major MoE releases of open models that happened in the past few weeks include <a target=\"_blank\" href=\"https://huggingface.co/collections/Qwen/qwen35\">Qwen 3.5</a>, <a target=\"_blank\" href=\"https://huggingface.co/collections/MiniMaxAI/minimax-m2\">MiniMax M2</a>, <a target=\"_blank\" href=\"https://huggingface.co/collections/zai-org/glm-5\">GLM-5</a>, or <a target=\"_blank\" href=\"https://huggingface.co/collections/moonshotai/kimi-k25\">Kimi K2.5</a>.</p>\n<p> The trend accelerated after the success of <a target=\"_blank\" href=\"https://huggingface.co/deepseek-ai/DeepSeek-R1\">DeepSeek R1</a> in January 2025, building on earlier systems like <a target=\"_blank\" href=\"https://huggingface.co/deepseek-ai/DeepSeek-V2\">DeepSeek V2</a>. Another early MoE was <a target=\"_blank\" href=\"https://huggingface.co/mistralai/Mixtral-8x7B-v0.1\">Mixtral-8x7B</a>, released in December 2023.</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/moe_2y_timeline.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/moe_2y_timeline.png\" alt=\"2-year timeline of MoE model addition in the transformers package\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 3: 2-year timeline of MoE model addition to the <code>transformers</code> library. DeepSeek R1 marks a clear inflection point.</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p> Closed labs use MoEs too. ChatGPT has long been <a target=\"_blank\" href=\"https://x.com/soumithchintala/status/1671267150101721090\"><em>rumored</em></a> to use a sparse architecture, and the open <a target=\"_blank\" href=\"https://huggingface.co/collections/openai/gpt-oss\">gpt-oss models</a> certainly do.</p>\n</li>\n</ol>\n<blockquote>\n<p>If you want to learn more about MoEs in general, we strongly suggest reading <a target=\"_blank\" href=\"https://huggingface.co/blog/moe\">this blog</a> and watching our recent <a target=\"_blank\" href=\"https://youtu.be/CDnkFbW-uEQ\">YouTube video on routing</a>.</p>\n</blockquote>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#transformers-and-moes\">\n\t</a>\n\t<span>\n\t\tTransformers and MoEs\n\t</span>\n</h2>\n<p>Most tooling in the ecosystem, including model loading, device placement, quantization, and backend execution was originally designed for <strong>dense</strong> models. MoEs challenge these assumptions.</p>\n<p>Making MoEs <strong>first-class citizens</strong> in <code>transformers</code> means redesigning parts of the loading pipeline, execution model, and distributed abstractions, not just adding new model classes. We’ll focus on how the <code>transformers</code> library has evolved to support sparse architectures across:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#weight-loading-refactor\">Weight Loading Refactor</a></li>\n<li><a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#expert-backend\">Expert Backend</a></li>\n<li><a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#expert-parallelism\">Expert Parallelism</a></li>\n<li><a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#training-moes-with-transformers\">Training MoEs with transformers</a></li>\n</ul>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#weight-loading-refactor\">\n\t</a>\n\t<span>\n\t\tWeight Loading Refactor\n\t</span>\n</h2>\n<p><a target=\"_blank\" href=\"https://huggingface.co/docs/transformers/main/en/model_doc/auto#transformers.AutoModelForCausalLM.from_pretrained\"><code>AutoModelForCausalLM.from_pretrained(\"model_id\")</code></a> downloads and loads model weights into a PyTorch model. For dense models, loading is relatively straightforward where each tensor in the checkpoint maps one-to-one to a parameter in the runtime module.</p>\n<p>For MoEs, it’s more complicated. In most MoE checkpoints, each expert is serialized independently. If you peek inside the <a target=\"_blank\" href=\"https://huggingface.co/deepseek-ai/DeepSeek-V3/raw/main/model.safetensors.index.json\">DeepSeek-V3 checkpoint index</a>, you’ll see keys like:</p>\n<pre><code>model.layers.3.mlp.experts.0.gate_proj.weight\n...\nmodel.layers.3.mlp.experts.255.gate_proj.weight\n</code></pre>\n<p>Each expert has its own set of weight matrices, essentially 256 (0 to 255 total, taking DeepSeek-V3 as an example) small feed-forward networks saved side by side. At runtime, however, GPUs execute optimized kernels. Modern MoE kernels such as <a target=\"_blank\" href=\"https://huggingface.co/kernels-community/megablocks\">grouped GEMMs and fused MoE implementations</a> are designed to process <em>all experts in a single operation</em>, not by looping over them one at a time.</p>\n<p>To do that efficiently, they require expert weights to be packed into a single <strong>contiguous tensor</strong>.</p>\n<p>So we have a mismatch:</p>\n<ul>\n<li><strong>Checkpoint:</strong> 256 separate tensors</li>\n<li><strong>Runtime:</strong> 1 packed tensor</li>\n</ul>\n<p>Bridging this gap systematically is what the <a target=\"_blank\" href=\"https://github.com/huggingface/transformers/pull/41580\">weight loading refactor</a> enables.</p>\n<p>With the introduction of a <a target=\"_blank\" href=\"https://huggingface.co/docs/transformers/main/en/weightconverter\">generic WeightConverter</a>, the mental model shifted from:</p>\n<blockquote>\n<p>A checkpoint already matches my runtime layout; loading is mostly a key-by-key copy.</p>\n</blockquote>\n<p>to:</p>\n<blockquote>\n<p>A checkpoint is just a serialized source of tensors. Loading is a <strong>conversion pipeline</strong> that transforms them into the runtime layout we want.</p>\n</blockquote>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#dynamic-weight-loading-with-weightconverter\">\n\t</a>\n\t<span>\n\t\tDynamic Weight Loading with <code>WeightConverter</code>\n\t</span>\n</h3>\n<p>The central abstraction introduced by this refactor is <strong>dynamic weight loading</strong> via a <a target=\"_blank\" href=\"https://huggingface.co/docs/transformers/main/en/internal/weight_converter\"><code>WeightConverter</code></a>.</p>\n<p><code>WeightConverter</code> lets us define:</p>\n<pre><code>source key patterns → target key(s) + operations\n</code></pre>\n<p>Primitive operations (chunk, concatenate, etc.) are composable. Two that are particularly useful for MoEs:</p>\n<ul>\n<li><p><a target=\"_blank\" href=\"https://github.com/huggingface/transformers/blob/main/src/transformers/core_model_loading.py\"><code>MergeModulelist</code></a> merges a list of tensors into a single tensor. For example, you can compose <code>MergeModulelist</code> with <code>Concatenate</code> to stack the experts in a MoE and pack them into one tensor.</p>\n<pre><code>WeightConverter(\n    [<span>\"block_sparse_moe.experts.*.w1.weight\"</span>, <span>\"block_sparse_moe.experts.*.w3.weight\"</span>,],\n    <span>\"mlp.experts.gate_up_proj\"</span>,\n    operations=[\n        MergeModulelist(dim=<span>0</span>),\n        Concatenate(dim=<span>1</span>),\n    ],\n)\n</code></pre>\n</li>\n<li><p><a target=\"_blank\" href=\"https://github.com/huggingface/transformers/blob/b71de73468429eb02da18caa50e9b5200400a4ed/src/transformers/core_model_loading.py#L208\"><code>SplitModulelist</code></a> splits a tensor back into a list of tensors. For example, you can split a stack of experts back into individual experts.</p>\n<pre><code>WeightConverter(\n    <span>\"mlp.experts.down_proj\"</span>,\n    <span>\"block_sparse_moe.experts.*.w2.weight\"</span>,\n    operations=[SplitModulelist(dim=<span>0</span>)],\n)\n</code></pre>\n</li>\n</ul>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#lazy-materialization-of-tensors\">\n\t</a>\n\t<span>\n\t\tLazy Materialization of Tensors\n\t</span>\n</h3>\n<p>The refactor improves not just <em>what</em> conversions exist, but <em>how</em> they’re scheduled.</p>\n<p>The loader scans checkpoint keys once, matches them against converter patterns, and groups tensors per converter. Once a key is identified as needed, it’s registered as a <em>future</em> and materialized via a thread pool. Conversion operations run only once their dependencies are ready. For example, <code>MergeModulelist</code> waits until all experts for a layer are loaded.</p>\n<p>This avoids repeated scans and reduces memory peaks.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#benchmark-weight-loading-pipeline-improvements\">\n\t</a>\n\t<span>\n\t\tBenchmark: Weight-Loading Pipeline Improvements\n\t</span>\n</h3>\n<p>To evaluate the improvements introduced by the new weight-loading pipeline, we benchmarked the v4 vs v5 versions of <code>transformers</code>. The focus is on loading speed of large MoE models, which is often a bottleneck in training and inference.</p>\n<p>We benchmarked v4 vs v5 using:</p>\n<ul>\n<li>v4 branch: <a target=\"_blank\" href=\"https://github.com/ariG23498/transformers/tree/bench-v4\">https://github.com/ariG23498/transformers/tree/bench-v4</a></li>\n<li>v5 branch: <a target=\"_blank\" href=\"https://github.com/ariG23498/transformers/tree/bench-v5\">https://github.com/ariG23498/transformers/tree/bench-v5</a></li>\n</ul>\n<p>Example:</p>\n<pre><code><span>from</span> transformers <span>import</span> AutoModelForCausalLM\nmodel_id = <span>\"Qwen/Qwen1.5-110B-Chat\"</span>\nmodel = AutoModelForCausalLM.from_pretrained(model_id)\n</code></pre>\n<p>Two relevant environment variables:</p>\n<ul>\n<li><p><code>HF_ENABLE_PARALLEL_LOADING</code>: Enables parallel shard loading via threads.</p>\n</li>\n<li><p><code>HF_DEACTIVATE_ASYNC_LOAD</code>:Disables the new async pipeline (v5 escape hatch).</p>\n</li>\n</ul>\n<h3>\n\t<a target=\"_blank\" the combination of <strong>Single-pass routing</strong>, <strong>Async materialization</strong>, and <strong>Conversion-aware scheduling</strong> which together avoid unnecessary materialization and memory peaks while enabling expert packing and projection fusion at load time.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#where-quantization-fits-in\">\n\t</a>\n\t<span>\n\t\tWhere Quantization Fits In\n\t</span>\n</h3>\n<p>With this refactor we can now create the runtime module structure first and then convert the weights into the structure. We can now optionally attach quantization within the conversion pipeline, making quantization part of the weight loading pipeline itself. This is crucial because quantizing “per expert” only makes sense once experts exist in a predictable packed layout.</p>\n<p>This end to end pipeline was not possible earlier and now it comes to the users as an exposed API.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#expert-backend\">\n\t</a>\n\t<span>\n\t\tExpert Backend\n\t</span>\n</h2>\n<p>Once experts are packed into a single runtime tensor, another question arises:</p>\n<blockquote>\n<p>How do you actually route through them efficiently?</p>\n</blockquote>\n<p>In a Mixture of Experts model, each token is routed to different experts. This means the runtime must dispatch tokens to their selected expert weights, execute the projections efficiently, apply the routing weights and then collect and reorder the results.</p>\n<p>This is what the <a target=\"_blank\" href=\"https://huggingface.co/docs/transformers/experts_interface\">Experts Backend system</a> (introduced in <a target=\"_blank\" href=\"https://github.com/huggingface/transformers/pull/42697\">PR #42697</a>) addresses. The Experts Backend introduces a <strong>pluggable execution architecture</strong> that decouples expert computation from the model implementation. Instead of hardcoding one dispatch strategy inside each MoE model, the system allows expert layers to dynamically select a backend at runtime.</p>\n<p>This is implemented via a decorator pattern:</p>\n<pre><code><span>@use_experts_implementation</span>\n</code></pre>\n<p>The decorator wraps expert classes and dispatches computation to the selected backend automatically.</p>\n<p>Three backends are currently provided:</p>\n<ol>\n<li><p><code>eager</code> which loops over the selected experts and applies projections per expert. This is used for correctness reference and debugging.</p>\n</li>\n<li><p><code>batched_mm</code> uses the <a target=\"_blank\" href=\"https://docs.pytorch.org/docs/stable/generated/torch.bmm.html\"><code>torch.bmm</code></a> API. This duplicate selected expert weights per token and performs a single batched GEMM. This backend is very well suited for small batch, GPU-heavy workloads where memory is available.</p>\n</li>\n<li><p><code>grouped_mm</code> uses <a target=\"_blank\" href=\"https://docs.pytorch.org/docs/stable/generated/torch.nn.functional.grouped_mm.html\"><code>torch._grouped_mm</code></a> API. Here we sort tokens by expert ID, group them, and then perform a single grouped GEMM. This backend shines with large batches or memory-constrained setups.</p>\n</li>\n</ol>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/expert_backend.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/expert_backend.png\" alt=\"\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure: Expert backend illustration</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#expert-parallelism\">\n\t</a>\n\t<span>\n\t\tExpert Parallelism\n\t</span>\n</h2>\n<p>Mixture of Experts (MoE) models can have hundreds of billions of parameters (far more than what fits on a single GPU). Expert parallelism (EP) addresses this by distributing experts across multiple devices. Each device loads only its assigned subset of experts, computes for those experts and then participates in result aggregation. This approach scales models to far larger parameter counts without increasing computation cost because each token activates only a few experts.</p>\n<p>Expert parallelism is enabled via <code>enable_expert_parallel</code>:</p>\n<pre><code><span>import</span> torch\n<span>from</span> transformers <span>import</span> AutoModelForCausalLM, AutoTokenizer\n<span>from</span> transformers.distributed.configuration_utils <span>import</span> DistributedConfig\ndistributed_config = DistributedConfig(enable_expert_parallel=<span>True</span>)\nmodel = AutoModelForCausalLM.from_pretrained(\n    <span>\"openai/gpt-oss-120b\"</span>,\n    dtype=<span>\"auto\"</span>,\n    distributed_config=distributed_config,\n)\n</code></pre>\n<p>Launch with:</p>\n<pre><code>torchrun --nproc-per-node N script.py\n</code></pre>\n<p>Where <code>N</code> evenly divides the total number of experts, and possibly matches the number of GPUs in your node.</p>\n<p>When <code>enable_expert_parallel=True</code>, the model switches from the standard tensor-parallel (TP) plan to an expert-parallel (EP) plan with specialized sharding strategies.</p>\n<p>Core components of EP lie in:</p>\n<ol>\n<li><p><a target=\"_blank\" href=\"https://github.com/huggingface/transformers/blob/b71de73468429eb02da18caa50e9b5200400a4ed/src/transformers/integrations/tensor_parallel.py#L934\"><code>GroupedGemmParallel</code></a>: This splits the expert weights along the expert dimension (<code>dim=0</code>). Here each device loads only <code>num_experts / num_devices</code>. </p>\n</li>\n<li><p><a target=\"_blank\" href=\"https://github.com/huggingface/transformers/blob/b71de73468429eb02da18caa50e9b5200400a4ed/src/transformers/integrations/tensor_parallel.py#L977\"><code>RouterParallel</code></a>: This remaps global expert indices to local indices, masks out experts not assigned to the current rank, ensures each device computes only with its local experts and uses an all-reduce to combine partial outputs across devices.</p>\n</li>\n</ol>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#training-moes-with-transformers\">\n\t</a>\n\t<span>\n\t\tTraining MoEs with Transformers\n\t</span>\n</h2>\n<p>MoEs are excellent for scaling inference, but training them is significantly more complex.</p>\n<p>MoEs have a Massive parameter count, the distributed expert communication is complicated, there are routing in-stabilities that need to be handled. To address this, we collaborated with <strong>Unsloth</strong> to enable significantly faster Mixture-of-Experts training:</p>\n<ul>\n<li>~12× faster MoE training</li>\n<li>&gt;35% VRAM reduction</li>\n<li>~6× longer context</li>\n<li>12–30× overall speedup compared to v4</li>\n</ul>\n<p>We leverage the Expert Backend abstraction, standardize around PyTorch’s <code>torch._grouped_mm</code> API and use custom Triton grouped-GEMM + LoRA kernels. Unsloth builds on top of the Transformers (and TRL) optimizations to push performance further.</p>\n<blockquote>\n<p>For full details, we recommend reading: <a target=\"_blank\" href=\"https://unsloth.ai/docs/new/faster-moe\">Unsloth’s official guide</a></p>\n</blockquote>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/moe-transformers#conclusion\">\n\t</a>\n\t<span>\n\t\tConclusion\n\t</span>\n</h2>\n<p>As sparse architectures continue to evolve, we want the transformers library to evolve with them.
