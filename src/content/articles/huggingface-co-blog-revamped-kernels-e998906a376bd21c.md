This enables us to cater to users with compute-related specificities. For example, a user can get a sense of which accelerators, operating systems, and backend versions are supported for a given kernel:</p>\n<figure>\n    <img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/revamped-kernels/flash-attn3.png\" alt=\"Flash Attention 3 Kernel Page\">\n    <figcaption>Kernel page: <a target=\"_blank\" href=\"https://huggingface.co/kernels/kernels-community/flash-attn3\">kernels-community/flash-attn3</a></figcaption>\n</figure>\n<p>One can browse all available kernels on the Hub here: <a target=\"_blank\" href=\"https://huggingface.co/kernels\">https://huggingface.co/kernels</a>. </p>\n<p>Making these kernels first-class citizens of the Hub also benefits the AI ecosystem. Users can now see trends across kernels, models, and the applications that use them. The kernels become more discoverable to users.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/revamped-kernels#improved-security\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tImproved security\n\t</span>\n</h2>\n<p>Kernels run native code with the same privileges as the Python process that loads them, so a malicious kernel can do real harm. Therefore, security has always been of utmost importance to the Kernels project.</p>\n<p>This is why we focused early on reproducibility: you should be able to recompile a kernel yourself and verify that it matches the publicly available source. We use Nix to make this possible, since it keeps builds pure through hermetic evaluation of the build recipe and a strongly isolated sandbox. We further improve provenance by embedding the source Git SHA1 into the kernel itself.</p>\n<p>In recent months, we have added additional layers of defense: trusted kernel publishers and code signing.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/revamped-kernels#trusted-kernel-publishers\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tTrusted kernel publishers\n\t</span>\n</h3>\n<p>With the new repo type, we also introduced “trusted publishers”. Since kernels execute code on a machine with the same privileges as the Python process they are used in, an attacker could compromise machines by uploading a malicious kernel and coaxing you to use that kernel. To help you avoid such malicious kernels, the kernels package will now only load kernels by <em>trusted publishers</em> by default. A trusted publisher is an organization that is trusted by the community to act in good faith.</p>\n<p>We still want to support loading kernels from organizations or users that are not trusted publishers, but you have to explicitly opt in using the <code>trust_remote_code</code> argument when loading a kernel from the Hub:</p>\n<pre><code><span>from</span> kernels <span>import</span> get_kernel\nkernel_module = get_kernel(  \n   “Atlas-Inference/gdn”, version=<span>1</span>, trust_remote_code=<span>True</span>  \n)  \n</code></pre>\n<p>By default, users cannot publish kernel repositories on the Hub. They have to request to be a kernel publisher. Users and organizations can request for access from their account settings. This gives us time to treat these requests on a case-by-case basis.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/revamped-kernels#kernel-signing\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tKernel signing\n\t</span>\n</h3>\n<p>An additional layer of security that we are adding is code signing. Code signing protects against the scenario where an attacker uploads a malicious kernel to a kernel repo from a trusted publisher whose Hub credentials were compromised. In code signing, a kernel is signed with a private key known only to the kernel developer and validated with a public key that is generally available. In the Hub compromise scenario, an attacker cannot sign the malicious kernel since they do not own the private key needed for signing.</p>\n<p>To further improve security, we use Sigstore’s cosign to sign using ephemeral private keys. Since these signing keys are only valid for a limited time, an attacker typically cannot use the private key, even when it is leaked. We also verify that the kernel was signed by a trusted GitHub workflow from a trusted GitHub repository.</p>\n<p>Kernel signing is already supported by <code>kernel-builder</code> and we have provided the <code>kernels verify-signature</code> to verify a kernel. Kernels does not verify the signature upon loading a kernel yet, since we would like to test this new functionality more before fully rolling it out. Preliminary notes on setting up code signing for your own kernels can be found in the kernels 0.16.0 release notes: <a target=\"_blank\" href=\"https://github.com/huggingface/kernels/releases/tag/v0.16.0\">https://github.com/huggingface/kernels/releases/tag/v0.16.0</a>. </p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/revamped-kernels#revamped-clis\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tRevamped CLIs\n\t</span>\n</h2>\n<p>Previously, a bunch of utilities were intertwined between <code>kernels</code> and <code>kernel-builder</code>. We have established a better separation of concern between the CLI of <code>kernels</code> and <code>kernel-builder</code>. The mental model here is that <code>kernels</code> is a library for loading and preparing kernels for use. Therefore, it should not include anything related to “building” kernels. </p>\n<p>As a result of this, both <code>kernels</code> and <code>kernel-builder</code> are now much leaner and more specific. Refer to the documentation to learn more about this:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://huggingface.co/docs/kernels/en/cli\"><code>kernels</code> CLI</a>  </li>\n<li><a target=\"_blank\" href=\"https://huggingface.co/docs/kernels/en/builder-cli\"><code>kernel-builder</code> CLI</a></li>\n</ul>\n<p>This improved CLI experience also lets us cater to the rise of agentic kernel\ndevelopment in a better manner. More on this <a target=\"_blank\" href=\"https://huggingface.co/blog/revamped-kernels#foundation-for-agentic-kernel-development\">later</a>.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/revamped-kernels#more-coverage-of-frameworks-and-backends\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tMore coverage of frameworks and backends\n\t</span>\n</h2>\n<p>We have extended support for frameworks, the most visible changes are:</p>\n<ul>\n<li>We added support for the Torch Stable ABI to kernels and kernel-builder. The Torch Stable ABI allows kernel developers to target a particular Torch version or any version that is released after it for roughly two years. For instance, a kernel that targets the Torch 2.9 Stable ABI support Torch &gt;= 2.9.  </li>\n<li>Apache TVM FFI is the first framework to be supported besides Torch. TVM FFI is standardized ABI for kernels that interoperates with other frameworks such as PyTorch, Jax and CuPy. This allows kernel developers to make kernels that runs across frameworks.</li>\n</ul>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/revamped-kernels#foundation-for-agentic-kernel-development\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tFoundation for agentic kernel development\n\t</span>\n</h2>\n<p><code>kernel-builder</code> and <code>kernels</code> complement the rise of agentic kernel development wherein an agent is leveraged to come up with an (optimized) kernel from scratch. Together, they support a workflow in which agents can scaffold, build, benchmark, and iteratively optimize kernels.</p>\n<p>Agentic kernel development is still nascent, and the right development loops will continue to evolve. That makes simple, clear fundamentals especially important where the tools should be easy to compose into whichever agent workflows or frameworks people choose to use.</p>\n<p><code>kernel-builder</code> helps enforce a structure in how kernel source code should be scaffolded and used to perform reproducible builds. This gives agents a predictable project layout and repeatable workflow to operate within. Its CLI is also meant to be <a target=\"_blank\" href=\"https://huggingface.co/blog/is-it-agentic-enough\">agent-optimized</a>. For example, this can mean non-interactive commands and outputs that are straightforward for an agent to interpret programmatically. To this end, we also have <a target=\"_blank\" href=\"https://huggingface.co/docs/kernels/en/cli-skills\">backend-specific skills</a> to help agents navigate the idiosyncrasies of different backends. These skills can capture backend-specific toolchains, compilation paths, and performance considerations.</p>\n<p>Building a kernel successfully isn’t the only goal, we need to ensure that it delivers actual speedups over a baseline on the target hardware. A successful build is therefore only the first validation step. Usually, this target hardware can include many different accelerators, even different families of the same accelerator.</p>\n<p> This makes it important to evaluate results across hardware vendors and generations where relevant. Our tight <a target=\"_blank\" href=\"https://huggingface.co/docs/kernels/en/builder/github-actions\">integration with HF Jobs</a> can make this benchmarking process easy. Agents can use this integration to run benchmark suites, collect performance results, and compare them against a defined baseline.</p>\n<p>This way, agents can run tests across different hardware configurations to get reliable feedback on the performance of the generated kernels and identify what needs to be done. That feedback can then inform the next optimization iteration.</p>\n<p>Below are some examples of agent-augmented kernels. These illustrate the kinds of kernels that can be developed and evaluated through this workflow: </p>\n<ul>\n<li><a target=\"_blank\" href=\"https://huggingface.co/kernels/drbh/yamoe\">https://huggingface.co/kernels/drbh/yamoe</a>   </li>\n<li><a target=\"_blank\" href=\"https://huggingface.co/kernels/sayakpaul/qk-norm-rope\">https://huggingface.co/kernels/sayakpaul/qk-norm-rope</a></li>\n</ul>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/revamped-kernels#misc\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tMisc\n\t</span>\n</h2>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/revamped-kernels#environment-setup\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tEnvironment setup\n\t</span>\n</h3>\n<p>The environment setup for building kernels with <code>kernel-builder</code> can be daunting. To make it easier for users, we now have an <a target=\"_blank\" href=\"https://huggingface.co/docs/kernels/en/builder/writing-kernels#quick-install\">installation script</a> for setting up an environment in one click. If you prefer working with ephemeral instances, our <a target=\"_blank\" href=\"https://github.com/huggingface/kernels/tree/main/terraform\">Terraform setup guide</a> is worth following. </p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/revamped-kernels#system-card-for-kernels\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tSystem card for kernels\n\t</span>\n</h3>\n<p>After the kernels are built, we create a system card for each kernel to expose useful information, including how to use it and its exposed interfaces. When the kernel is pushed to the Hub, this system card becomes the front matter for the kernel:</p>\n<figure>\n    <img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/revamped-kernels/kernel-card.png\" alt=\"System card for a kernel\">\n    <figcaption>System card for <a target=\"_blank\" href=\"https://huggingface.co/kernels/kernels-community/flash-attn3\">kernels-community/flash-attn3</a></figcaption>\n</figure>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/revamped-kernels#is-a-kernel-compatible-on-my-system\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tIs a kernel compatible on my system?\n\t</span>\n</h3>\n<p>Is a question one would ask multiple times to plan things better. Use the <a target=\"_blank\" href=\"https://huggingface.co/docs/kernels/main/en/api/kernels#kernels.has_kernel\"><code>has_kernel()</code></a> method for this purpose:</p>\n<pre><code><span>from</span> kernels <span>import</span> has_kernel\n<span>print</span>(has_kernel(<span>\"kernels-community/activation\"</span>, version=<span>1</span>))  \n</code></pre>\n<p>It returns a <code>bool</code>. If you’re looking for more explanations around why a given kernel isn’t supported then use <a target=\"_blank\" href=\"https://huggingface.co/docs/kernels/main/en/api/kernels#kernels.get_kernel_variants\"><code>get_kernel_variants()</code></a>:</p>\n<pre><code> <span>from</span> kernels <span>import</span> get_kernel_variants, VariantAccepted\n<span>for</span> decision <span>in</span> get_kernel_variants(<span>\"kernels-community/activation\"</span>, version=<span>1</span>):  \n    name = decision.variant.variant_str  \n    <span>if</span> <span>isinstance</span>(decision, VariantAccepted):  \n        <span>print</span>(<span>f\"<span>{name}</span>: compatible\"</span>)  \n    <span>else</span>:  \n        <span>print</span>(<span>f\"<span>{name}</span>: rejected (<span>{decision.reason}</span>)\"</span>)  \n</code></pre>\n<p>It should print (depends on the machine you’re on):</p>\n<pre><code>torch212-cxx11-cu130-aarch64-linux: compatible  \ntorch210-cu128-x86_64-windows: rejected (CPU (x86_64) does not match system CPU (aarch64))  \ntorch211-cu128-x86_64-windows: rejected (CPU (x86_64) does not match system CPU (aarch64))  \ntorch212-metal-aarch64-darwin: rejected (OS (darwin) does not match system OS (linux))  \ntorch211-metal-aarch64-darwin: rejected (OS (darwin) does not match system OS (linux))  \ntorch210-metal-aarch64-darwin: rejected (OS (darwin) does not match system OS (linux))  \ntorch29-metal-aarch64-darwin: rejected (OS (darwin) does not match system OS (linux))  \n…  \n</code></pre>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/revamped-kernels#improved-manylinux_2_28-support\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tImproved manylinux_2_28 support\n\t</span>\n</h3>\n<p>Kernel-builder has targeted <code>manylinux_2_28</code> almost since the beginning. We used to target <code>manylinux</code> by using a modern gcc toolchain compiled with glibc 2.28. To avoid compatibility issues with older versions of <code>libstdc++</code>, we statically linked libstdc++.</p>\n<p>However, this approach recently resulted in some issues. Some <code>libstdc++</code> functionality uses global initialization. This can lead to corrupted data when multiple <code>libstdc++</code> versions come into play, such as the <code>libstdc++</code> that is linked dynamically by PyTorch and the <code>libstdc++</code> that is linked statically by a kernel. Some recent kernels use functionality (e.g. C++ regexes) that trigger global initializations, leading to such corrupted data, causing segfaults and other issues.</p>\n<p>To solve this issue, kernels now link <code>libstdc++</code> dynamically. To ensure compatibility with old <code>libstdc++</code> versions, we now compile kernels with the official <code>manylinux_2_28</code> toolchain.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/revamped-kernels#conclusion\">\n\t\t<span></span>\n\t</a>\n\t<span>\n\t\tConclusion\n\t</span>\n</h2>\n<p>Our goal with the Kernels project is to serve both kernel developers and users of custom kernels. We’re always keen on receiving feedback from the community on how we can improve it. Don’t hesitate to contribute!</p>\n<p><em>Acknowledgements: Thanks to <a target=\"_blank\" href=\"https://huggingface.co/blog/ariG23498\">Aritra</a> for reviewing the post.</em></p>\n<!----></div>"
