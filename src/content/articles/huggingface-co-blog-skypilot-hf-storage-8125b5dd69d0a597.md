The GPUs you can get, whether for development, training, or serving, increasingly sit on a different cloud than your data. The moment those two come apart, you pay a cross-cloud transfer tax just to read your own data onto your own GPUs.</p>\n<p>Together with Hugging Face, we've joined the two halves: your models and datasets stay on the Hub, and SkyPilot runs the compute (dev, training, or serving) on whatever cluster has the GPUs. Mount a Hugging Face Bucket or any Hub repo into a SkyPilot job with one <code>hf://</code> URL and the <code>HF_TOKEN</code> you already have, then launch it wherever capacity is. Hugging Face charges no egress, so reading your data onto those GPUs costs nothing, on any cloud.</p>\n<p>Here's what's new:</p>\n<ul>\n<li><strong>Your Hub data in any job.</strong> <code>store: existing <code>HF_TOKEN</code>, via <code>MOUNT</code> or <code>COPY</code>.</li>\n<li><strong>Run it on any GPU, on any cloud.</strong> <a target=\"_blank\" available, on any vendor.</li>\n<li><strong>No egress to read your data.</strong> Hugging Face Storage charges <a target=\"_blank\" href=\"https://huggingface.co/pricing\">no egress or CDN fees</a>, backend\n\t</span>\n</h2>\n<p><a target=\"_blank\" href=\"https://huggingface.co/blog/assets/skypilot-hf-storage/architecture.png\"><img src=\"https://huggingface.co/blog/assets/skypilot-hf-storage/architecture.png\" alt=\"SkyPilot mounts Hugging Face models, datasets, and checkpoints into jobs running on reserved GPU clusters across CoreWeave, Nebius, GCP, and 20+ more, with zero-egress reads.\"></a></p>\n<p>SkyPilot tasks already read and write cloud object stores (S3, GCS, Azure, R2, and many more) by mounting them at a local path. Hugging Face Storage now joins that list as <code>store: hf</code>, reached through the <code>hf://</code> scheme:</p>\n<pre><code><span>file_mounts:</span>\n  <span># A Hugging Face Bucket, read-write, for checkpoints, logs, processed data.</span>\n  <span>/checkpoints:</span>\n    <span>source:</span> <span>hf://buckets/my-org/qwen-sft</span>\n    <span>store:</span> <span>hf</span>\n    <span>mode:</span> <span>MOUNT</span> <span># or COPY</span>\n  <span># A model repo, mounted read-only.</span>\n  <span>/base-model:</span>\n    <span>source:</span> <span>hf://Qwen/Qwen3.5-4B</span>\n    <span>store:</span> <span>hf</span>\n    <span>mode:</span> <span>MOUNT</span>\n  <span># A dataset repo, pinned to a revision, read-only.</span>\n  <span>/data:</span>\n    <span>source:</span> <span>hf://datasets/my-org/my-dataset@main</span>\n    <span>store:</span> <span>hf</span>\n    <span>mode:</span> <span>MOUNT</span>\n</code></pre>\n<p>That one <code>hf://</code> scheme covers the whole lifecycle: read the <strong>model</strong> and <strong>dataset</strong> from their repos, write <strong>checkpoints</strong> to a Bucket while you train, publish the finished model back to a repo, and pull it onto inference servers when you serve. Most teams already keep their models and datasets on the Hub, so there is no migration step and no new storage account to create.</p>\n<p><code>MOUNT</code> uses Hugging Face's <a target=\"_blank\" href=\"https://github.com/huggingface/hf-mount\"><code>hf-mount</code></a> FUSE backend, so a bucket or repo shows up as a local path next to SkyPilot's other FUSE mounts (<code>gcsfuse</code>, <code>blobfuse2</code>, <code>rclone</code>, <code>goofys</code>). The fetching happens at the filesystem layer: when your code issues a <code>read()</code>, the driver pulls just those bytes from the Xet backend, so only the data you actually touch crosses the network, and <code>hf-mount</code> keeps an on-disk cache so repeat reads stay local. That on-disk cache is the behavior SkyPilot gives its other backends under <a target=\"_blank\" href=\"https://docs.skypilot.co/en/latest/reference/storage.html\"><code>MOUNT_CACHED</code></a>, where a plain <code>MOUNT</code> instead streams every read from the bucket with nothing kept locally. For the <code>hf</code> store, <code>MOUNT</code> and <code>MOUNT_CACHED</code> behave the same, so either mode keeps the cache.</p>\n<p>Because reads are lazy, a process can start working through a large file before the whole file has downloaded, instead of blocking on a full copy first. That keeps the GPU busy almost immediately, training on data as it streams in rather than sitting idle (and billing) while a dataset or checkpoint copies down. It pays off most on the first epoch, when nothing is cached yet. <code>COPY</code> takes the other route and downloads through <code>huggingface_hub</code> up front, with no special requirements.</p>\n<p>Authentication is the token you already have. Set <code>HF_TOKEN</code> in your environment and hand it to a run with <a target=\"_blank\" href=\"https://docs.skypilot.co/en/latest/running-jobs/environment-variables.html\"><code>--secret HF_TOKEN</code></a>; SkyPilot uses it for the mount on whatever cloud the job lands. One token works whether the job lands on AWS, GCP, Azure, Nebius, Lambda, or your own Kubernetes cluster, so there are no per-cloud bucket keys to juggle.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/skypilot-hf-storage#no-egress-storage-stops-deciding-where-you-run\">\n\t</a>\n\t<span>\n\t\tNo egress: storage stops deciding where you run\n\t</span>\n</h2>\n<p>GPU capacity rarely comes from one place anymore. To get enough H100s and H200s, teams hold reserved and committed capacity across several vendors at once (a block on a hyperscaler, a cluster on a neocloud, maybe an on-prem rack) and run wherever they have allocation. SkyPilot is built for this: one job spec, scheduled across 20+ clouds, Kubernetes, and on-prem, landing on whichever reserved cluster is free.</p>\n<p>Object storage has been the catch. Object stores are regional and per-cloud, so feeding a GPU or an inference server that sits in a different vendor's data center means either keeping a copy of your data in every vendor's bucket or paying to pull it across. Most clouds charge egress (around $0.09/GB out of AWS) the moment data leaves their network, and often between regions inside one cloud. Pulling a base model onto every inference node, or iterating a dataset for several epochs from a cluster on another cloud, adds a hefty bill on top of GPUs you have already reserved. Teams end up pinning each run to whichever vendor holds the data and leaving the rest of their capacity idle.</p>\n<p>Hugging Face Storage takes that cost off the table where it bites: the read side. With <a target=\"_blank\" href=\"https://huggingface.co/pricing\">no egress or CDN fees</a> and storage at $12-18/TB/month (versus AWS S3 at roughly $23/TB plus egress), the same bucket is reachable from every one of those clusters, and reading from it is free no matter where the GPUs run. Writing back still costs your compute cloud's usual egress, the same as it would to any off-cloud store, but for most AI work the reads dominate: a dataset streamed over many epochs, or model weights pulled onto every new training or inference node. So you stop pinning each run to whichever vendor holds a copy of the data.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/skypilot-hf-storage#a-quick-benchmark\">\n\t</a>\n\t<span>\n\t\tA quick benchmark\n\t</span>\n</h2>\n<p>To collect some benchmark numbers, we ran a small fine-tune: <a target=\"_blank\" href=\"https://huggingface.co/Qwen/Qwen3.5-4B\"><code>Qwen/Qwen3.5-4B</code></a> on the <a target=\"_blank\" href=\"https://huggingface.co/datasets/HuggingFaceH4/Multilingual-Thinking\"><code>HuggingFaceH4/Multilingual-Thinking</code></a> dataset with TRL's <a target=\"_blank\" href=\"https://huggingface.co/docs/trl/sft_trainer\"><code>SFTTrainer</code></a>, mounting the model read-only from its Hub repo and writing every checkpoint to a Hugging Face Bucket. The same SkyPilot YAML ran on AWS, GCP, and Lambda, changing only <code>--infra</code>. SkyPilot placed each job wherever GPUs were free, and all three read and wrote the same bucket.</p>\n<pre><code><span># qwen-sft.yaml. Launch anywhere: sky launch qwen-sft.yaml --infra aws|gcp|...</span>\n<span>resources:</span>\n  <span>accelerators:</span> <span>H100:1</span> <span># or whatever the cloud has</span>\n<span>file_mounts:</span>\n  <span>/base-model:</span>\n    <span>source:</span> <span>hf://Qwen/Qwen3.5-4B</span> <span># read-only, lazy-mounted from the Hub</span>\n    <span>store:</span> <span>hf</span>\n    <span>mode:</span> <span>MOUNT</span>\n  <span>/checkpoints:</span>\n    <span>source:</span> <span>hf://buckets/my-org/qwen-sft</span> <span># read-write Bucket</span>\n    <span>store:</span> <span>hf</span>\n    <span>mode:</span> <span>MOUNT</span>\n<span>run:</span> <span>|</span>\n  <span>python</span> <span>train.py</span> <span>--model</span> <span>/base-model</span> <span>--output_dir</span> <span>/checkpoints</span>\n</code></pre>\n<p>What we measured:</p>\n<ul>\n<li><strong>The model loaded free on every cloud.</strong> Lazy reads pull only what <code>from_pretrained</code> touches, so it was ready to train in about 30 seconds (up to ~500 MB/s). Because Hugging Face charges no egress, that pull cost nothing; had the model lived in S3, every read to a GPU on another cloud would have been billed egress (~$0.09/GB on AWS).</li>\n<li><strong>Checkpoints streamed straight to the bucket</strong> at up to ~170 MB/s (8.43 GB of weights each) and persisted past the GPU instance.</li>\n</ul>\n<p>Per cloud, checkpoints wrote to the bucket at:</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>Cloud</th>\n<th>GPU</th>\n<th>Checkpoint write</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>AWS (us-east-2)</td>\n<td>L40S</td>\n<td>~168 MB/s</td>\n</tr>\n<tr>\n<td>GCP (us-central1)</td>\n<td>L4</td>\n<td>~123 MB/s</td>\n</tr>\n<tr>\n<td>Lambda (us-west-3)</td>\n<td>H100</td>\n<td>~112 MB/s</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/skypilot-hf-storage#xet-backed-storage-dedup-for-checkpoints-and-model-variants\">\n\t</a>\n\t<span>\n\t\tXet-backed storage: dedup for checkpoints and model variants\n\t</span>\n</h2>\n<p>Hugging Face Buckets are built on <a target=\"_blank\" href=\"https://huggingface.co/docs/hub/xet/overview\">Xet</a>, which uses <a target=\"_blank\" href=\"https://huggingface.co/docs/hub/xet/deduplication\">content-defined chunking</a> to split files into ~64 KB chunks and store each unique chunk once. Because the boundaries follow the content, an edit changes only the chunks it touches and the rest are recognized as already stored. This pays off in a few places:</p>\n<ul>\n<li><strong>Incremental and adapter checkpoints.</strong> When you freeze layers, train adapters, or otherwise leave most weights untouched between saves, only the changed chunks upload instead of the whole checkpoint.</li>\n<li><strong>Model variants that share a base.</strong> Fine-tunes and quantizations of one base model overlap heavily, so the shared chunks are stored once across all of them.</li>\n<li><strong>Datasets you append to.</strong> Logs like conversation traces or inference outputs grow by appending rows to large Parquet files. The existing row groups stay byte-identical, so only the new rows transfer: in Hugging Face's <a target=\"_blank\" href=\"https://huggingface.co/blog/parquet-cdc\">test</a>, appending 10K rows to a 100K-row table moved about 10 MB instead of the full ~106 MB. (If you edit or delete rows in place, write with <code>use_content_defined_chunking=True</code> to keep changes local.)</li>\n<li><strong>Re-uploads skip what's already stored.</strong> In our test, re-uploading an 8.43 GB blob already in the bucket took about 8 seconds, versus 24 seconds for the first upload, because only chunk hashes move. The same mechanism lets server-side <code>hf buckets cp</code> between repos and buckets copy by reference instead of re-uploading bytes.</li>\n</ul>\n<p>How much you save depends on how much your artifacts overlap, but the deduplication is automatic: you write a checkpoint as usual, and only the new chunks leave the machine.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/skypilot-hf-storage#get-started\">\n\t</a>\n\t<span>\n\t\tGet started\n\t</span>\n</h2>\n<pre><code>pip install <span>\"skypilot[huggingface]\"</span>\nhf auth login  <span># or: export HF_TOKEN=&lt;your-token&gt;</span>\n</code></pre>\n<p>Add an <code>hf://</code> mount to any SkyPilot task and launch. <code>MOUNT</code> needs a base image with glibc 2.34+ and <code>/dev/fuse</code>.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/skypilot-hf-storage#built-together-hugging-face-and-skypilot\">\n\t</a>\n\t<span>\n\t\tBuilt together: Hugging Face and SkyPilot\n\t</span>\n</h2>\n<p>The initial <code>store: hf</code> support <a target=\"_blank\" href=\"https://github.com/skypilot-org/skypilot/pull/9418\">started as a contribution</a> from Nikhil Jha. The Hugging Face team <a target=\"_blank\" href=\"https://github.com/skypilot-org/skypilot/pull/9698\">carried it forward</a> and upstreamed the <code>hf-mount</code> FUSE fixes that let it mount in unprivileged containers, the default on many Kubernetes clusters. The SkyPilot team wired it into the storage backend. The whole path is open source: SkyPilot, Hugging Face's <code>hf-mount</code>, and the <code>huggingface_hub</code> client.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/skypilot-hf-storage#resources\">\n\t</a>\n\t<span>\n\t\tResources\n\t</span>\n</h2>\n<ul>\n<li><a target=\"_blank\" href=\"https://docs.skypilot.co/en/latest/reference/storage.html\">SkyPilot storage docs</a></li>\n<li><a target=\"_blank\" href=\"https://huggingface.co/docs/hub/storage-buckets\">Hugging Face Storage Buckets guide</a></li>\n<li><a target=\"_blank\" href=\"https://github.com/huggingface/hf-mount\"><code>hf-mount</code></a></li>\n<li><a target=\"_blank\" href=\"https://huggingface.co/docs/hub/xet/deduplication\">Xet: content-defined chunking and deduplication</a></li>\n<li><a target=\"_blank\" href=\"https://slack.skypilot.co/\">SkyPilot Slack community</a></li>\n</ul>\n<!----></div>"
