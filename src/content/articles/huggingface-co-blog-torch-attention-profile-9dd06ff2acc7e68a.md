The interaction between them can be written as a short sequence of steps:</p>\n<ol>\n<li>Build the attention scores <code>scores</code>: <code>matmul(q, k.T)</code></li>\n<li>Scale the scores: <code>scores * scale</code></li>\n<li>Apply a causal mask to the scores: <code>scores.masked_fill(mask, \"-inf\")</code></li>\n<li>Normalize the scores with softmax to get the attention weights <code>attn</code>: <code>softmax(scores)</code></li>\n<li>Reweight the values with those weights: <code>matmul(attn, v)</code></li>\n</ol>\n<p>So attention is really a collection of primitive operations. Some of them we already know (the matmuls), and the rest are easy to spot. Let's write a naive attention module in PyTorch and profile it.</p>\n<pre><code><span>class</span> <span>NaiveCausalAttention</span>(nn.Module):\n    <span>def</span> <span>__init__</span>(<span>self, head_dim</span>):\n        <span>super</span>().__init__()\n        self.scale = <span>1.0</span> / math.sqrt(head_dim)\n    <span>def</span> <span>forward</span>(<span>self, q, k, v, mask</span>):\n        scores = torch.matmul(q, k.transpose(-<span>2</span>, -<span>1</span>))\n        scores = scores * self.scale\n        scores = scores.masked_fill(mask, <span>float</span>(<span>\"-inf\"</span>))\n        attn = torch.softmax(scores, dim=-<span>1</span>)\n        out = torch.matmul(attn, v)\n        <span>return</span> out\n</code></pre>\n<p>Before opening the trace, let's do our usual exercise and guess what we should see. The memory copy is the odd one out, so where does this come from? The clue is that PyTorch has in-place operations. When you operate on a tensor the ordinary (out-of-place) way, PyTorch often makes a copy, applies the requested operation to it, and returns the copy. Following the sequence of operations, the culprit here is our <a target=\"_blank\" href=\"https://docs.pytorch.org/docs/2.13/generated/torch.Tensor.masked_fill.html\"><code>masked_fill</code></a>.</p>\n<p>What if we replaced this with an in-place operation?</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-attention-profile#naive-attention-with-inplace-causal-masking\">\n\t</a>\n\t<span>\n\t\tNaive attention with inplace causal masking\n\t</span>\n</h2>\n<p>All we change is <code>masked_fill</code> to <code>masked_fill_</code> (note the trailing underscore, PyTorch's convention for in-place operations), and we run the same script.</p>\n<pre><code>def forward(self, q, k, v, mask):\n    # q, k, v: [batch, heads, seq, head_dim]\n    scores = torch.matmul(q, k.transpose(-2, -1))  # [batch, heads, seq, seq]\n    scores = torch.mul(scores, self.scale)\n<span>-    scores = scores.masked_fill(mask, float(\"-inf\"))</span>\n<span>+    scores.masked_fill_(mask, float(\"-inf\"))</span>\n    attn = torch.softmax(scores, dim=-1)\n    out = torch.matmul(attn, v)  # [batch, heads, seq, head_dim]\n    return out\n</code></pre>\n<p>Let's look at the trace and see if something changed.</p>\n<pre><code>uv run 04_b_inplace_ops_attention.py\nuvx trace-util -f traces/ -b &lt;hf_uname&gt;/traces\n</code></pre>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>Type</th>\n<th>CPU stream</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 4: Naive masking</td>\n<td><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/cpu-profile-naive.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/cpu-profile-naive.png\" alt=\"CPU lane of naive attention with out-of-place `masked_fill`, showing several dispatch ops for the masking step\"></a></td>\n</tr>\n<tr>\n<td>Figure 5: In place masking</td>\n<td><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/cpu-profile-inplace.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/cpu-profile-inplace.png\" alt=\"CPU lane of naive attention with in-place `masked_fill_`, showing fewer dispatch ops for the masking step\"></a></td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>The in-place version (Figure 5) wraps far fewer CPU ops inside the masking step than the out-of-place version (Figure 4). With a one line change we shaved a whole kernel off each forward pass. This may not look like much on its own, but remember this is a single attention operation. In the context of a transformer based large model (LLMs, Diffusion models, etc.), it repeats once per layer, and there are many layers, so the saving adds up quickly (and if it earns you a raise, sharing at least 10% with us feels only fair).</p>\n<blockquote>\n<p>Out-of-place is PyTorch's default for a reason. To compute gradients, autograd has to remember the tensor values it saw on the forward pass, because many backward formulas reuse them. An in-place operation overwrites those values in memory, so the backward pass would read the wrong numbers. Due to the fact that we run <code>forward</code> under <code>torch.no_grad</code>, in-place is safe for us, with no backward pass and nothing to corrupt. It is also noteworthy that in-place operations do not only save time (like we see in our case) but also memory (due to no extra copy) which is great for large tensors like logits!</p>\n</blockquote>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-attention-profile#scaled-dot-product-attention\">\n\t</a>\n\t<span>\n\t\tScaled Dot Product Attention\n\t</span>\n</h2>\n<p>We just built attention from primitives, and even shaved off a <code>Memcpy</code>. The good news is that the PyTorch team has done all of this for us, and packaged the whole pipeline into a single function:</p>\n<pre><code><span>from</span> torch.nn <span>import</span> functional <span>as</span> F\nF.scaled_dot_product_attention(q, k, v, is_causal=<span>True</span>)\n</code></pre>\n<p>This one line replaces our hand written module, and <code>is_causal=True</code> even saves us from building the mask by hand. It is worth pausing to appreciate how much this one call hides. And it hides more than just code lines. Scaled Dot Product Attention (SDPA) does not have a single implementation. Under the hood it <em>dispatches</em> to one of the several backends and picks the fastest one that supports our inputs (dtype, head dimension, mask, hardware, etc.).</p>\n<p>The <a target=\"_blank\" href=\"https://docs.pytorch.org/tutorials/intermediate/scaled_dot_product_attention_tutorial.html\">official SDPA tutorial</a> walks us through this selection, and the backends themselves are listed in the <code>torch.nn.attention.SDPBackend</code> enum:</p>\n<pre><code><span>from</span> torch.nn.attention <span>import</span> SDPBackend\nBACKENDS = {\n    <span>\"math\"</span>: SDPBackend.MATH,\n    <span>\"flash\"</span>: SDPBackend.FLASH_ATTENTION,\n    <span>\"efficient\"</span>: SDPBackend.EFFICIENT_ATTENTION,\n    <span>\"cudnn\"</span>: SDPBackend.CUDNN_ATTENTION,\n}\n</code></pre>\n<p>Normally SDPA chooses for us, but we can pin a specific backend with the <code>torch.nn.attention.sdpa_kernel</code> context manager. To see why that matters here, it helps to know what lives inside a GPU. A Streaming Multiprocessor (SM) is the compute unit of a GPU, and each SM has two kinds of arithmetic units, the CUDA cores and the Tensor Cores. CUDA cores are general purpose and process a handful of elements at a time, while Tensor Cores multiply and accumulate a whole small matrix tile in a single instruction. So the question is simple, \"Is each backend actually using the fast path?\"</p>\n<p>The kernel names answer it. The <code>s16816</code> in the naive kernel (Figure 10) is the signature of a <code>bfloat16</code> Tensor Core matmul (the <code>16x8x16</code> Tensor Core instruction), so the naive version is on the fast path. <code>sgemm</code> (Figure 11) is the classic single precision (<code>FP32</code>) matmul that runs on the ordinary CUDA cores. In other words, the math backend never touches the Tensor Cores at all: to trade speed for numerical accuracy it upcasts tensors to <code>FP32</code> (doubling the data moved, even when the inputs are in <code>bf16</code>) and falls back to the slower CUDA cores.</p>\n<h4>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-attention-profile#causal-masks-built\">\n\t</a>\n\t<span>\n\t\tCausal masks built\n\t</span>\n</h4>\n<p>In the naive version we built the causal mask once and reused it. Here we passed <code>is_causal=True</code> and the math backend materialized one for us, on <em>every</em> single call. You can watch it happen on the CPU lane:</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/mask-math.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/mask-math.png\" alt=\"CPU lane of the SDPA math backend showing the ops that rebuild the causal mask: aten::ones, aten::tril, aten::scalar_tensor, aten::fill_ and aten::where\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 12: CPU lane showing the ops for masking</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>Here is what we see in Figure 12</p>\n<pre><code>aten::ones -&gt; aten::tril            build a [<span>seq</span>, <span>seq</span>] lower-triangular matrix\naten::scalar_tensor -&gt; aten::fill_  make the -inf fill value\naten::<span>where</span>                         turn it into an additive bias (0 or -inf)\n</code></pre>\n<p>On the GPU this shows up as a <code>triu_tril_kernel</code>, several <code>where</code> kernels, and an <code>add_</code>. The convenience flag that let us stop thinking about the mask did not remove the work, it just moved it one layer down, where the mask is rebuilt from scratch every forward.</p>\n<h4>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-attention-profile#the-safe-softmax\">\n\t</a>\n\t<span>\n\t\tThe safe softmax\n\t</span>\n</h4>\n<p>Our hand written version called plain <code>aten::softmax</code>. The math backend calls <code>aten::_safe_softmax</code>, and the difference is again visible as extra kernels (Figure 13):</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/safe-softmax-extra-kernels.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/safe-softmax-extra-kernels.png\" alt=\"GPU lane of the SDPA math backend showing the extra kernels that aten::_safe_softmax launches compared to a plain softmax\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 13: Safe softmax highlighting the extra kernels compared to generic softmax</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>A row that is fully masked (every entry <code>-inf</code>) would make an ordinary softmax compute <code>exp(-inf)/sum(exp(-inf)) = 0/0 = NaN</code>. <code>_safe_softmax</code> guards against exactly that. Our naive kernel never bothered, and would have quietly produced <code>NaN</code>s in that corner case.</p>\n<h4>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-attention-profile#so-what-is-the-math-backend-for\">\n\t</a>\n\t<span>\n\t\tSo what is the math backend for?\n\t</span>\n</h4>\n<p>Put together, the math backend is the reference implementation. It is a straightforward, dtype-safe, NaN-safe decomposition of attention into primitive ATen ops. It is essentially the naive attention we wrote by hand, but more careful. That carefulness is exactly what makes it extremely slow.</p>\n<p>Its job is not to be fast, but to <em>always</em> work. This makes it the perfect baseline. Every backend we profile next (flash, efficient, cudnn) is trying to collapse the <code>20</code> GPU kernels into essentially one fused kernel that stays in bf16 and never materializes the intermediate matrices at all.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-attention-profile#efficient-backend\">\n\t</a>\n\t<span>\n\t\tEfficient backend\n\t</span>\n</h3>\n<pre><code>uv run 04_c_sdpa_attention.py --backend efficient\nuvx trace-util -f traces -b &lt;hf_uname&gt;/traces\n</code></pre>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/efficient-backend.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/efficient-backend.png\" alt=\"Profiler trace of the SDPA efficient backend showing a backend</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>Where the math backend launched 20 kernels across one profiler step, the efficient backend launches only one <code>fmha_cutlassF_bf16_aligned_64x64_rf_sm80</code> (as seen in Figure 14).</p>\n<p>Let's decode the name of the kernel:</p>\n<ul>\n<li><code>fmha</code> (fused multi-head attention): All the primitive ops in attention is \"fused\" in one op now.</li>\n<li><code>cutlassF</code>: built on CUTLASS (NVIDIA's open-source templates for tensor-core GEMMs), <code>F</code> for forward.</li>\n<li><code>bf16_aligned</code>: runs in bfloat16 (no FP32 upcast, unlike math).</li>\n<li><code>64x64</code>: the tile size.</li>\n<li><code>rf</code> (register file): the working set is kept in registers, the fastest memory on the chip.</li>\n<li><code>sm80</code>: compiled for Ampere (the A100's compute capability 8.0).</li>\n</ul>\n<p>This is the memory efficient attention kernel that grew out of Meta's <a target=\"_blank\" href=\"https://github.com/facebookresearch/xformers\">xformers</a> library and was upstreamed into PyTorch. When people say \"the xformers backend,\" this <code>fmha_cutlassF</code> kernel is what they mean.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-attention-profile#flash-backend\">\n\t</a>\n\t<span>\n\t\tFlash backend\n\t</span>\n</h3>\n<pre><code>uv run 04_c_sdpa_attention.py --backend flash\nuvx trace-util -f traces -b &lt;hf_uname&gt;/traces\n</code></pre>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/flash-backend.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/flash-backend.png\" alt=\"Profiler trace of the SDPA flash backend\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 15: The flash backend trace, one fused <code>pytorch_flash</code> kernel per forward</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>The <code>void pytorch_flash</code> kernel (Figure 15) is <a target=\"_blank\" href=\"https://arxiv.org/abs/2307.08691\">FlashAttention-2</a> (Tri Dao's implementation), vendored into PyTorch.</p>\n<p>Before we read the trace any further, it is worth answering the question you should be asking by now: <em>why is there a whole backend named \"flash\", and why does it matter so much?</em></p>\n<h4>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-attention-profile#why-flash-attention-exists\">\n\t</a>\n\t<span>\n\t\tWhy flash attention exists?\n\t</span>\n</h4>\n<p>Let's go back to the math backend for a moment. Its real problem was not the count of 20 kernels, it was what those kernels handed to each other.</p>\n<p>Step 1 builds the full score matrix <code>attn = q . k.T</code>, which is <code>[seq, seq]</code> <strong>per head</strong>. For a sequence length of 4096 that is <code>4096 x 4096 ≈ 16 million</code> numbers for a single head. That matrix is written out to the HBM (the GPU's main memory), if there is even enough space to do so. Then, it is read back to be scaled, written again for the mask, read again for the softmax, and so on. Attention's cost is dominated by this <strong>back and forth traffic to HBM</strong>, not by the matmuls themselves.</p>\n<p>FlashAttention attacks exactly this. Instead of computing the whole <code>s</code> matrix and only then reducing it, it walks over <code>k</code> and <code>v</code> in <strong>tiles</strong>, keeps a running softmax as it goes (the \"online softmax\" trick), and accumulates the output one tile at a time. The full <code>[seq, seq]</code> score matrix is <strong>never written to HBM</strong>, it only ever lives on-chip. This is the single idea that lets the entire attention pipeline collapse into one fused kernel that stays in bf16 on the Tensor cores.</p>\n<h4>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-attention-profile#why-flash-looks-wrong-under-the-profiler\">\n\t</a>\n\t<span>\n\t\tWhy flash looks \"wrong\" under the profiler\n\t</span>\n</h4>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/flash-occupancy.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/flash-occupancy.png\" alt=\"Perfetto footprint of the flash kernel reporting an estimated achieved occupancy of 13%\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 16: Estimated occupancy of flash kernel is seen to be 13%</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>Here is where flash surprises people who read profiler footprints. It is the fastest backend, yet the profiler reports it with very <strong>low occupancy</strong> (shown in Figure 16). To see why that is fine, we need three quick definitions.</p>\n<p>A GPU kernel is essentially a series of instructions executed by many small execution units. These individual execution units (threads) take care of loading variables, adding them together, storing them back, etc. For each kernel, we launch many, many threads, and to keep track of them, we group them by blocks.</p>\n<p>Blocks are scheduled onto Streaming Multiprocessors (SMs), the main compute units of a GPU. A block lives entirely on one SM, and an SM can host multiple blocks at once <em>if it has enough resources</em>. Those resources include registers, shared memory, maximum resident threads, and maximum resident warps. So when we say a kernel has low <strong>occupancy</strong>, we mean each SM has fewer resident warps than it could theoretically support.</p>\n<blockquote>\n<p>If you want to know more about threads, blocks, grids, etc. here is a <a target=\"_blank\" href=\"https://huggingface.co/blog/mi300kernels#a-quick-introduction-to-the-mi300x\">great resource</a>.</p>\n</blockquote>\n<p>If you click the flash kernel in the trace, its footprint tells the story (Figure 17).</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/flash-reg-count.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/flash-reg-count.png\" alt=\"Resource footprint of the pytorch_flash kernel in Perfetto, showing a high per-thread register count and large shared memory usage per block\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 17: The flash kernel footprint, heavy on registers and shared memory per block.</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>Flash uses a lot of per-thread registers and a large amount of shared memory per block. For example, if a block has 128 threads and each thread uses 255 registers, that block needs <code>128 × 255 = 32,640</code> registers. On an Ampere SM with 65,536 registers, only two such blocks fit at once. Each 128-thread block has <code>128 / 32 = 4</code> warps, so two blocks give only 8 resident warps. Against a maximum of 64 resident warps, that is roughly 13% occupancy. Flash has low occupancy not because it is poorly optimized, but because each block is deliberately very \"heavy\" in on-chip resource usage.</p>\n<p>And that is the whole point. High occupancy helps <em>hide latency</em> by keeping many warps ready to run, but it does not make the work itself efficient. Flash spends those registers and that shared memory on purpose, to keep attention tiles on-chip, reuse data aggressively, and avoid ever materializing the full attention matrix in global memory.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-attention-profile#cudnn-backend\">\n\t</a>\n\t<span>\n\t\tcuDNN backend\n\t</span>\n</h3>\n<pre><code>uv run 04_c_sdpa_attention.py --backend cudnn\nuvx trace-util -f traces -b &lt;hf_uname&gt;/traces\n</code></pre>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/cudnn-backend.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/cudnn-backend.png\" alt=\"Profiler trace of the SDPA cuDNN backend showing a single cudnn_generated attention kernel per forward\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 18: The cuDNN backend trace, a single generated attention kernel per forward.</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>By now the pattern is familiar. Like flash and efficient, cuDNN gives us one fused, flash-style kernel per forward (Figure 18). So the natural question is: <strong>if flash already fuses attention, why does PyTorch ship yet another flash backend?</strong> The answer is <em>who writes the kernel and how it is built</em>, and that difference is what makes the trace look different.</p>\n<h4>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-attention-profile#how-is-cudnn-kernel-different\">\n\t</a>\n\t<span>\n\t\tHow is cuDNN kernel different\n\t</span>\n</h4>\n<p>Flash and efficient are <strong>fixed, pre-compiled kernels</strong> vendored into PyTorch. You get the same binary every time. cuDNN is NVIDIA's own deep learning library, and its attention kernel is <strong>generated and tuned for the specific problem</strong> at hand. It is closer in spirit to <code>torch.compile</code>'s codegen than to a fixed cuBLAS binary. You can read that straight off the (very long) kernel name:</p>\n<pre><code>cudnn_generated_fort_native_sdpa_sm80_flash_fprop_wmma_f16_knob_6_128x64x64_4x1x1_cga1x1x1_kernel0_0\n</code></pre>\n<ul>\n<li><code>cudnn_generated</code>: not a pre-shipped binary, it was generated by cuDNN.</li>\n<li><code>flash_fprop</code>: a flash attention style forward pass. So the algorithm is the same family as the flash backend.</li>\n<li><code>wmma_f16</code>: it uses the warp-level matrix multiply-accumulate (WMMA) API, the Tensor-core path on the 16-bit float pipeline.</li>\n<li><code>knob_6</code>: cuDNN picks from a set of pre-tuned configurations (\"knobs\"). Different shapes select different knobs, much like cuBLAS picking a tile variant.</li>\n<li><code>128x64x64</code>: the tile dimensions it chose.</li>\n</ul>\n<p>That one fact, <em>generated per problem</em>, explains everything else that looks unusual in the trace.</p>\n<ol>\n<li><p>No transposes: The CPU lane goes from <code>_cudnn_attention_forward</code> straight to a couple of <code>aten::empty</code> allocations and then the kernel, with zero <code>aten::transpose</code> (Figures 19, 20 and 21).
