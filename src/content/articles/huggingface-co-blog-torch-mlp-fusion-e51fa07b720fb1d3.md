Most of the PyTorch overhead you see in a profiler trace is this scheduling work.</li>\n</ol>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#from-matmul-add-to-linear\">\n\t</a>\n\t<span>\n\t\tFrom matmul-add to Linear\n\t</span>\n</h2>\n<p><code>nn.Linear</code> is a module wrapper around the same matrix multiplication and addition we already profiled in <a target=\"_blank\" href=\"https://huggingface.co/blog/torch-profiler\">Part 1</a>. The only difference is that it owns its weight and bias as parameters and exposes a <code>forward</code> method that PyTorch users have grown familiar with.</p>\n<pre><code><span># bias=True would truly emulate the multiplication and addition</span>\n<span># operations we have seen in part 1 of the series</span>\nlinear_layer = nn.Linear(in_dim, out_dim, bias=<span>True</span>)\ny = linear_layer(x)\n</code></pre>\n<p>The operation at hand can be written as:</p>\n<pre><code>y = x @ w.T + b\n</code></pre>\n<p>Where <code>x</code> is the input, <code>w</code> is the weight and <code>b</code> is the bias. Let's run <a target=\"_blank\" href=\"https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/02_linear.py\"><code>02_linear.py</code></a> and check the profile.</p>\n<pre><code>uv run 02_linear.py --batch 1024 --in_dim 32 --out_dim 64\nuvx trace-util -f traces -b &lt;hf_uname&gt;/traces\n</code></pre>\n<blockquote>\n<p><a target=\"_blank\" href=\"https://x.com/ariG23498/status/2054811716727517374\"><code>trace-util</code></a> is a utility that will sync your traces to a <a target=\"_blank\" href=\"https://huggingface.co/storage\">Hugging Face bucket</a> and then provide the <a target=\"_blank\" href=\"https://perfetto.dev/\">Preffeto URLs</a> on your terminal.</p>\n</blockquote>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/linear-profile-trace.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/linear-profile-trace.png\" alt=\"PyTorch profiler trace of an `nn.Linear` forward pass: three short Profile Steps and `linear_fwd` annotations on the CPU lane, a tiny kernel on the GPU lane, and a long `cudaDeviceSynchronize` bar at the end\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 1: Profiler trace of <code>nn.Linear</code></td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>Figure 1 shows the profiler trace of a forward call of the linear layer. This is why we see three Profile Steps in the CPU and GPU lanes.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#what-is-the-transpose-doing\">\n\t</a>\n\t<span>\n\t\tWhat is the transpose doing?\n\t</span>\n</h3>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/transpose-cpu-dispatch.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/transpose-cpu-dispatch.png\" alt=\"Zoomed in CPU dispatch chain showing the aten::t transpose op nested before aten::addmm inside aten::linear, with no matching activity on the GPU lane\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 2: The transpose CPU row</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>If we zoom into the profiler trace, as we do in Figure 2, we notice an <code>aten::t</code> (transpose) op before the <code>aten::addmm</code> (multiplication and addition) op. We can already figure out that <code>nn.Linear</code> transposes the weight parameter and then multiplies it with the input. This is the reason we see an <code>aten::t</code> op.</p>\n<p>An important thing to notice is that <code>aten::t</code> does not really copy or reorganize data: it only rewrites tensor metadata (shape and stride) on the CPU to represent the transposed matrix. It does not launch a kernel on the GPU. One can verify this two ways: by looking at the GPU lane in the trace, or by checking the <code>aten::t</code> row in the profiler table and the time it took on CUDA.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#why-are-there-no-separate-mul-and-add-kernels\">\n\t</a>\n\t<span>\n\t\tWhy are there no separate <code>mul</code> and <code>add</code> kernels?\n\t</span>\n</h3>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/no-aten-add.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/no-aten-add.png\" alt=\"Profiler trace of the linear layer with the dispatch chain highlighted, showing aten::linear, aten::t and aten::addmm but no separate aten::add op\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 3: No <code>aten::add</code> in the profile of a linear layer</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>There is no <code>aten::add</code> (the bias addition) in the dispatch chain of the linear layer, as seen in Figure 3. This is because the bias addition has been <em>folded</em> into the matrix multiplication kernel, using what is called an <strong>epilogue</strong>.</p>\n<p>An <strong>epilogue</strong> is a small computation that a GEMM (GEneral Matrix Multiply) kernel does at the very end, just before it writes its result back to HBM (High Bandwidth Memory, the GPU's main memory). Adding a bias, applying an activation, or scaling by a constant are all classic epilogues. The point of an epilogue is to avoid loading or writing to HBM a second time, since memory traffic makes an operation expensive.</p>\n<p><code>nn.Linear</code> calls <code>torch.nn.functional.linear</code>, which, in turn, calls <code>aten::linear</code>. <code>aten::linear</code> looks at the inputs, notices that a bias was passed, and dispatches <code>aten::addmm(bias, x, weight)</code> instead of doing a matmul and an add separately. <code>addmm</code> computes:</p>\n<pre><code>out = x @ weight.T + bias\n</code></pre>\n<p>The cuBLAS GEMM kernel that runs on the GPU has a bias-add variant built in, and that's the kernel <code>aten::addmm</code> picks. The add never appears as a separate kernel because it is <strong>part of the matmul kernel's writeback</strong>, which is exactly what an epilogue is.</p>\n<p>This is the moment to notice something subtle. The kernel you saw in <a target=\"_blank\" href=\"https://huggingface.co/blog/torch-profiler#did-we-fuse-the-matmul-and-add-kernels-into-one\">Part 1 under <code>--compile</code></a> (<code>addmm</code>) is the kernel that eager <code>nn.Linear</code> already uses. There is nothing left for <code>torch.compile</code> to fuse here, which is the next thing we will verify.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#can---compile-help-a-single-linear\">\n\t</a>\n\t<span>\n\t\tCan --compile help a single Linear?\n\t</span>\n</h3>\n<p>Let's compile the forward call and look at the profiler trace. (The profiler trace is visualized in the <a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#where-did-the-transpose-go-kernel-layouts-and-pre-ops\">next section</a>)</p>\n<pre><code>uv run 02_linear.py --batch 1024 --in_dim 32 --out_dim 64 --compile\nuvx trace-util -f traces -b &lt;hf_uname&gt;/traces\n</code></pre>\n<p>If you compare the eager and compiled traces for a single <code>nn.Linear</code>'s <code>forward</code>, you will find:</p>\n<ul>\n<li>The same cuBLAS GEMM kernel on the GPU.</li>\n<li>The same <code>aten::addmm</code> op on the CPU.</li>\n<li>A few extra rows on the CPU lane unique to compile.</li>\n</ul>\n<p>This is worth internalizing. A common reflex is to reach for <code>torch.compile</code> whenever a model feels slow. For a single GEMM-with-bias, compile has very little to do. This is not a bug, this is just that compile needs more than one operation to possibly do any fusing. Let's prove that by <a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#stacking-two-linears-the-mlp\">looking at an MLP</a>.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#where-did-the-transpose-go-kernel-layouts-and-pre-ops\">\n\t</a>\n\t<span>\n\t\tWhere did the transpose go? Kernel layouts and pre-ops\n\t</span>\n</h3>\n<p>A careful reader of the two traces (eager vs compile) will notice that the eager CPU dispatch chain has more in it than the compiled one.</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/eager.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/eager.png\" alt=\"Eager CPU dispatch chain with the aten::t transpose and aten::addmm boxed separately under aten::linear\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 4: Eager dispatch chain where <code>aten::linear</code> walks through <code>aten::t</code> (transpose) and then <code>aten::addmm</code></td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/compile.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/compile.png\" alt=\"Compiled CPU dispatch chain showing a Torch-Compiled Region and a single aten::addmm call, with no transpose op\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 5: Compiled dispatch chain where <code>aten::addmm</code> is called directly, with no transpose</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>The eager CPU dispatch chain inside <code>aten::linear</code> is <code>aten::t</code> followed by <code>aten::addmm</code> (Figure 4). To understand what <code>aten::t</code> actually does, we need a quick detour into <em>strides</em> and <em>views</em>.</p>\n<p>A tensor stores its data as one flat, contiguous run of numbers in memory. The <code>shape</code> and <code>stride</code> are metadata that sit on top of that run and tell PyTorch how to walk it: a stride of <code>(s0, s1)</code> means \"step <code>s0</code> elements to move one row, step <code>s1</code> to move one column\". Change the metadata and you get a different <em>view</em> of the <em>same</em> raw data, with no copy:</p>\n<pre><code><span>&gt;&gt;&gt; </span>M = torch.tensor([[<span>0</span>, <span>1</span>],\n<span>... </span>                  [<span>2</span>, <span>3</span>],\n<span>... </span>                  [<span>4</span>, <span>5</span>]])\n<span>&gt;&gt;&gt; </span>M.shape, M.stride()\n(torch.Size([<span>3</span>, <span>2</span>]), (<span>2</span>, <span>1</span>))   <span># two steps per row, one step per column</span>\n<span>&gt;&gt;&gt; </span>T = M.t()                  <span># transpose</span>\n<span>&gt;&gt;&gt; </span>T.shape, T.stride()\n(torch.Size([<span>2</span>, <span>3</span>]), (<span>1</span>, <span>2</span>))   <span># shape and stride swapped, data untouched</span>\n<span>&gt;&gt;&gt; </span>T\ntensor([[<span>0</span>, <span>2</span>, <span>4</span>],\n        [<span>1</span>, <span>3</span>, <span>5</span>]])\n<span>&gt;&gt;&gt; </span>T.flatten()                <span># forced to materialize, so the data is reordered</span>\ntensor([<span>0</span>, <span>2</span>, <span>4</span>, <span>1</span>, <span>3</span>, <span>5</span>])\n</code></pre>\n<p><code>M.t()</code> did not move a single number. It returned a new view whose strides are swapped, so reading it row-by-row now walks the original buffer <code>0, 1, 2, 3, 4, 5</code> in transposed order. The underlying data is identical; only the metadata differs.</p>\n<p>This is exactly what <code>aten::t</code> does inside the linear layer: it does not allocate a new tensor or copy any data, it produces a <em>view</em> of the weight with rewritten strides.</p>\n<p>As we can see in Figure 5, compile did not remove a GPU kernel: it removed the <em>CPU overhead</em> of dispatching that view. Inductor traced through the view chain at compile time, computed the resulting strides once, and emitted a direct <code>aten::addmm</code> call with those strides hard-coded. A few microseconds of CPU work disappear while the GPU does identical math. </p>\n<p>As one would expect, when the input data violates the strides precomputed by the compiler, it will throw an error.</p>\n<p>If you look at the GPU lane in both traces, there is exactly one kernel per forward, and it is the <em>same</em> kernel both times:</p>\n<pre><code>cutlass_80_wmma_tensorop_bf16_s161616gemm_bf16_32x32_32x1_tn_align8\n</code></pre>\n<p>If no transpose kernel ran, who taught the GEMM to read the weight matrix in transposed order? The answer is in the kernel's name. Look at the suffix:</p>\n<pre><code>cutlass_80_wmma_tensorop_bf16_s161616gemm_bf16_32x32_32x1_tn_align8\n                                                          ^^\n</code></pre>\n<p>That <code>tn</code> is the layout descriptor. cuBLAS and CUTLASS precompile a <em>separate kernel binary</em> for each combination of input layouts.</p>\n<p><code>n</code> (non-transposed) and <code>t</code> (transposed) describe how a kernel walks its input during the inner loop. The dispatcher's job is to look at the input strides, decide which suffix combination matches, and pick the right precompiled kernel.</p>\n<blockquote>\n<p>The kernel name in a profiler trace is a hash dump of the kernel's identity. If two runs show the same kernel name, the GPU is doing the same work. If they differ (e.g., <code>_tn_</code> vs <code>_nn_</code>, <code>bf16</code> vs <code>fp16</code>, or <code>s16816gemm</code> vs <code>s161616gemm</code>) then the GPU is doing different work, and the dispatcher took a different branch. Learning to read this name is one of the most useful habits when comparing traces.</p>\n</blockquote>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#stacking-three-linears-the-mlp\">\n\t</a>\n\t<span>\n\t\tStacking three Linears: the MLP\n\t</span>\n</h2>\n<p>In this section, we will profile a Multilayer Perceptron (MLP). To make this more interesting, we will profile a feed-forward network with the GeGLU activation variant (which is quite heavily used in practice). This is also our way of paying tribute to one of the greatest lines ever written in the history of deep learning research (Figure 6).</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/geglu-paper.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/geglu-paper.png\" alt=\"Conclusions section of the GLU Variants Improve Transformer paper, with the closing sentence attributing the architectures' success to divine benevolence highlighted\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 6: The conclusion section of the <a target=\"_blank\" href=\"https://arxiv.org/abs/2002.05202\">GLU Variants Improve Transformer</a> paper.</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<pre><code><span>class</span> <span>SimpleGeGLUMLP</span>(nn.Module):\n    <span>def</span> <span>__init__</span>(<span>self, dim, hidden</span>):\n        <span>super</span>().__init__()\n        self.gate_proj = nn.Linear(dim, hidden, bias=<span>False</span>)\n        self.up_proj = nn.Linear(dim, hidden, bias=<span>False</span>)\n        self.down_proj = nn.Linear(hidden, dim, bias=<span>False</span>)\n    <span>def</span> <span>forward</span>(<span>self, x</span>):\n        g = self.gate_proj(x)\n        u = self.up_proj(x)\n        h = F.gelu(g, approximate=<span>\"tanh\"</span>)\n        m = h * u\n        y = self.down_proj(m)\n        <span>return</span> y\n</code></pre>\n<p>You will find the entire script here: <a target=\"_blank\" href=\"https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/03_simple_mlp.py\"><code>03_simple_mlp.py</code></a>. Execute it like so:</p>\n<pre><code>uv run 03_simple_mlp.py --batch 64 --<span>seq</span> 128 --dim 768 --hidden 3072\nuvx trace-util -f traces -b &lt;hf_uname&gt;/traces\n</code></pre>\n<p>Before we open the trace, let's think together about what we should expect to see. The <code>forward</code> function does a fair amount of computation, but most of it is already familiar to us.</p>\n<p>We should expect three <code>aten::linear</code> dispatches, one for each <code>nn.Linear</code> layer. We should also expect two pointwise kernel launches, one for the GeLU and one for the multiplication. Forming this expectation before looking is the single most useful habit in the profiling journey: you read the trace to <em>confirm or break</em> a guess, not to form one from scratch.</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/simple-mlp-eager.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/simple-mlp-eager.png\" alt=\"Profiler trace of the GeGLU MLP forward pass, with five boxed groups on the CPU lane labelled linear, linear, gelu, mul, linear\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 7: The profiler trace for a GeGLU MLP</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/occupancy-queries.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/occupancy-queries.png\" alt=\"Occupancy Queries highlighted in the linear projection traces\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 8: The occupancy queries highlighted in the linear projection CPU lane</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>From Figure 7 we can pat ourselves on the back, as our intuition was correct. Per forward pass (one <code>mlp_fwd</code>), the GPU runs exactly 5 kernels. Figure 8 highlights the \"occupancy query\" as seen in the CPU lane for the linear projection layers.</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>Op</th>\n<th>CPU op</th>\n<th>GPU kernel</th>\n<th>launches</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td><code>gate_proj</code></td>\n<td><code>aten::linear</code></td>\n<td><code>ampere_bf16_s16816gemm_bf16_128x128_...</code></td>\n<td>occupancy query + cudaLaunchKernel</td>\n</tr>\n<tr>\n<td><code>up_proj</code></td>\n<td><code>aten::linear</code></td>\n<td><code>ampere_bf16_s16816gemm_bf16_128x128_...</code></td>\n<td>occupancy query + cudaLaunchKernel</td>\n</tr>\n<tr>\n<td><code>gelu</code></td>\n<td><code>aten::gelu</code></td>\n<td><code>vectorized_elementwise_kernel&lt;4, GeluCUDAKernelImpl...&gt;</code></td>\n<td>cudaLaunchKernel</td>\n</tr>\n<tr>\n<td><code>h * u</code></td>\n<td><code>aten::mul</code></td>\n<td><code>vectorized_elementwise_kernel&lt;4, ...MulFunctor...&gt;</code></td>\n<td>cudaLaunchKernel</td>\n</tr>\n<tr>\n<td><code>down_proj</code></td>\n<td><code>aten::linear</code></td>\n<td><code>ampere_bf16_s16816gemm_bf16_128x256_...</code></td>\n<td>occupancy query + cudaLaunchKernel</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>The three GEMMs each do an extra <code>cudaOccupancyMaxActiveBlocksPerMultiprocessor</code> call before the launch. We have a separate section on this in Part 1, <a target=\"_blank\" href=\"https://huggingface.co/blog/torch-profiler#why-does-matmul-have-an-extra-cuda-runtime-call\">you can find it here</a>. That is cuBLAS sizing the grid. The pointwise ops (GeLU and mul) launch directly, with no occupancy query. So \"a linear\" is actually query + launch, while \"a pointwise op\" is just launch.</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/simple-mlp-table.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/simple-mlp-table.png\" alt=\"Profiler table for the GeGLU MLP listing op names and their CUDA times, where metadata ops like aten::transpose and aten::as_strided show 0.000us of CUDA time\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 9: The table shows that some ops launch zero kernels</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>The <code>aten::t</code>, <code>aten::transpose</code>, <code>aten::reshape</code>, <code>aten::view</code>, <code>aten::as_strided</code>, and <code>aten::_unsafe_view</code> ops launch zero kernels. They show <code>0.000us</code> of CUDA time in the table (Figure 9) because they only rewrite tensor metadata (shape and stride) on the CPU. A reader scanning the table sees around six op names per linear, but only one of them (<code>mm</code>) ever reaches the GPU.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#why-are-there-two-types-of-gemm-kernels\">\n\t</a>\n\t<span>\n\t\tWhy are there two types of GEMM kernels?\n\t</span>\n</h3>\n<p>The MLP flattens <code>[batch, seq, dim]</code> to <code>[batch * seq, dim]</code> for the matmul. In our command-line invocation we used 64 for <code>batch</code> and 128 for <code>seq</code>, so that's where the <code>8192</code> (<code>batch * seq = 64 * 128</code>) below comes from.</p>\n<p>From the trace:</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>Linear</th>\n<th><code>aten::mm</code> input dims</th>\n<th>M·K·N</th>\n<th>cuBLAS kernel</th>\n<th>avg CUDA</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td><code>gate_proj</code></td>\n<td><code>[8192,768] x [768,3072]</code></td>\n<td><code>8192·768·3072</code></td>\n<td><code>…128x128…stages_32x5_tn</code></td>\n<td>0.19ms</td>\n</tr>\n<tr>\n<td><code>up_proj</code></td>\n<td><code>[8192,768] x [768,3072]</code></td>\n<td><code>8192·768·3072</code></td>\n<td><code>…128x128…stages_32x5_tn</code></td>\n<td>0.19ms</td>\n</tr>\n<tr>\n<td><code>down_proj</code></td>\n<td><code>[8192,3072] x [3072,768]</code></td>\n<td><code>8192·3072·768</code></td>\n<td><code>…128x256…stages_64x3_tn</code></td>\n<td>0.17ms</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>All three GEMMs have the same FLOP count, <code>2·8192·768·3072 ≈ 38.7 GFLOP</code> each, yet <code>down_proj</code> is about <code>10%</code> faster. Same work, different shape (<code>N=768</code> instead of <code>3072</code>), so cuBLAS picks a different tile (<code>128×256</code>, with a deeper <code>stages_64x3</code> pipeline) that gets better reuse for that shape.</p>\n<blockquote>\n<p>If you want to learn more about tiling in depth, <a target=\"_blank\" href=\"https://alvinwan.com/how-to-tile-matrix-multiplication/\">here is a great resource</a> to get started with.</p>\n</blockquote>\n<p>This is exactly why the table had two GEMM rows (Figure 9): the <code>128x128</code> row is gate+up and the <code>128x256</code> row is down.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#what-does-torchcompile-do\">\n\t</a>\n\t<span>\n\t\tWhat does torch.compile do?\n\t</span>\n</h3>\n<p>Before compiling the <code>forward</code> method and visualizing it, let's do the mental exercise again of asking ourselves what we expect to see in the trace. This is a fun experiment, and an important one to repeat every time you profile something yourself. Always build on your intuition, and the moment something does not match, stop and figure out why.</p>\n<pre><code>uv run 03_simple_mlp.py --batch 64 --<span>seq</span> 128 --dim 768 --hidden 3072 --compile\nuvx trace-util -f traces -b &lt;hf_uname&gt;/traces\n</code></pre>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/simple-mlp-compile-trace.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/simple-mlp-compile-trace.png\" alt=\"Profiler trace of the compiled GeGLU MLP showing three aten::mm calls and one fused triton kernel on the CPU lane, labelled mm, mm, fused, mm\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 10: The profiler trace for the compiled GeGLU MLP</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>In eager mode, each <code>nn.Linear</code> was expanded into a chain of dispatcher ops (<code>aten::linear</code> → <code>aten::t</code> → <code>aten::transpose</code> → <code>aten::matmul</code> → <code>aten::reshape</code> → <code>aten::mm</code>). Those are the high-level wrappers that ATen walks through before reaching the real GEMM. <code>torch.compile</code> removes that chain.</p>\n<p>By the time the compiled graph runs, there is no linear, no matmul, no transpose or reshape and those metadata ops were folded into how <code>mm</code> is called. We can see three bare <code>aten::mm</code> external calls (Figure 10). The proof that it is the same GEMM is that the kernel names are byte-for-byte identical to eager: <code>...128x128...stages_32x5_tn</code> for gate and up, and <code>...128x256...stages_64x3_tn</code> for down.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#the-fused-triton-kernel\">\n\t</a>\n\t<span>\n\t\tThe fused Triton kernel\n\t</span>\n</h3>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/fused.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/fused.png\" alt=\"Compiled MLP trace with the triton_poi_fused__unsafe_view_gelu_mul_0 kernel boxed on the CPU lane, replacing the separate gelu and mul kernels from the eager run\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 11: The fused Triton kernel</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>This is the headline of the whole compile lesson. The two eager pointwise kernels (GeLU and mul) plus a reshape collapsed into one kernel, <code>triton_poi_fused__unsafe_view_gelu_mul_0</code> (Figure 11). Let's decode the name:</p>\n<ul>\n<li><code>triton</code>: generated by Inductor's Triton backend (not cuBLAS, not ATen).</li>\n<li><code>poi</code>: pointwise (Inductor tags pointwise kernels <code>poi</code>, reductions <code>red</code>, and persistent reductions <code>per</code>).</li>\n<li><code>fused__unsafe_view_gelu_mul</code>: the ops it merged: the <code>_unsafe_view</code> (reshape), the GeLU, and the mul.</li>\n<li><code>0</code>: the unique id within the graph.</li>\n</ul>\n<p>Why is this a win? In eager mode, the intermediate <code>h = gelu(g)</code> is a full <code>[8192, 3072]</code> bf16 tensor (around 50 MB) that the GeLU kernel writes to HBM and the mul kernel immediately reads back. Fusion keeps it in registers (memory that resides inside the chip and are closer than the HBM). The Triton kernel reads <code>g</code> and <code>u</code> once, computes <code>gelu(g) * u</code>, and writes the result once. One whole round trip of the intermediate through global memory is gone.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#lets-use-hand-tuned-kernels\">\n\t</a>\n\t<span>\n\t\tLet's use hand tuned kernels\n\t</span>\n</h2>\n<p>So far we have let PyTorch (eager) and the compiler (<code>torch.compile</code>) pick our kernels. Now we plug in a kernel that a human expert wrote and tuned by hand. We use the <code>LigerGEGLUMLP</code> layer, that we can easily fetch from the <a target=\"_blank\" href=\"https://huggingface.co/kernels/kernels-community/liger-kernels\">Hugging Face Hub</a> with the <code>kernels</code> library.</p>\n<pre><code><span>from</span> kernels <span>import</span> get_kernel\nkernels_layers = get_kernel(<span>\"kernels-community/liger-kernels\"</span>, version=<span>1</span>).layers\nkernels_geglu_mlp = kernels_layers.LigerGEGLUMLP(Config()).to(device, dtype=torch.bfloat16).<span>eval</span>()\n</code></pre>\n<p>The full script is here: <a target=\"_blank\" href=\"https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/03_kernels_mlp.py\"><code>03_kernels_mlp.py</code></a>.</p>\n<pre><code>uv run 03_kernels_mlp.py --batch 64 --<span>seq</span> 128 --dim 768 --hidden 3072\nuvx trace-util -f traces -b &lt;hf_uname&gt;/traces\n</code></pre>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/kernels-profile.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/kernels-profile.png\" alt=\"Profiler trace of the LigerGEGLUMLP forward pass showing three aten::linear groups and a single LigerGELUMulFunction group on the CPU lane\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 12: The profiler trace for the <code>LigerGEGLUMLP</code> layer</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>Figure 12 shows the profile for the <code>LigerGEGLUMLP</code> layer using the Liger kernels from the Hub.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#why-use-the-kernels-library\">\n\t</a>\n\t<span>\n\t\tWhy use the kernels library\n\t</span>\n</h3>\n<p>Writing kernels in Triton or CUDA is one problem and <em>shipping</em> them is another. The kernel has to be compiled for your exact combination of GPU architecture, CUDA version, and PyTorch version. This is the step that usually breaks (\"works on my machine\", missing <code>nvcc</code>, wrong Triton version).</p>\n<p>The <a target=\"_blank\" href=\"https://github.com/huggingface/kernels\"><code>kernels</code></a> library moves that build step off your machine. <code>get_kernel(\"kernels-community/liger-kernels\", version=1)</code> downloads a <strong>pre-built, version-pinned</strong> kernel package from the Hugging Face Hub and caches it locally (here under <code>~/.cache/...kernels-community--liger-kernels</code>). The benefits are:</p>\n<ul>\n<li>The kernels are compiled once, in CI, for many architectures and version combinations. You download the right binary instead of compiling it yourself.</li>\n<li><code>version=1</code> pins the exact build, so everyone running your script gets the same kernel. There is no \"it got slower after I updated a package\".</li>\n<li>The package exposes a <code>.layers</code> attribute with drop-in <code>nn.Module</code>s (like <code>LigerGEGLUMLP</code>). You swap your module for theirs and nothing else in your model changes.</li>\n</ul>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#why-tuned-kernels-are-better\">\n\t</a>\n\t<span>\n\t\tWhy tuned kernels are better\n\t</span>\n</h3>\n<p>When we say \"tuned\", we mean two concrete things, and both are visible in the trace.</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/compile-preops.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/compile-preops.png\" alt=\"Compiled MLP trace with the TorchDynamo, prologue and guard pre-ops boxed on the CPU lane before the compiled graph runs\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 13: The compiled run pays for pre-ops (Dynamo, guards, prologue) before any GEMM runs</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/no-preops.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/no-preops.png\" alt=\"LigerGEGLUMLP trace with an empty box where the compile pre-ops would be, showing the hand-written kernel has no Dynamo or guard overhead\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 14: The Liger kernel has no pre-ops — the box where they would be is empty</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<ol>\n<li><p><strong>The fusion is baked in.</strong> The <a target=\"_blank\" href=\"https://huggingface.co/kernels/kernels-community/liger-kernels/blob/v1/build/torch-cuda/layers.py#L307\"><code>LigerGEGLUMLP</code></a> forward is <code>down_proj(LigerGELUMulFunction.apply(gate_proj(x), up_proj(x)))</code>. The <a target=\"_blank\" href=\"https://huggingface.co/kernels/kernels-community/liger-kernels/blob/v1/build/torch-cuda/geglu.py#L130\"><code>LigerGELUMulFunction</code></a> runs a single Triton kernel, <a target=\"_blank\" href=\"https://huggingface.co/kernels/kernels-community/liger-kernels/blob/v1/build/torch-cuda/geglu.py#L97\"><code>_geglu_tanh_forward_kernel</code></a>, that computes <code>gelu(gate) * up</code> in one pass. This is exactly what we saw from <code>torch.compile</code>, where the intermediate never makes a round-trip through HBM. We get it here <strong>without the compiler</strong>, as shown in Figures 13 and 14 (no Dynamo guards, no compile latency, no recompilation risk).</p>\n</li>\n<li><p><strong>The launch parameters were chosen for the hardware.</strong> The kernel does not guess its block size at random. Liger's <a target=\"_blank\" href=\"https://huggingface.co/kernels/kernels-community/liger-kernels/blob/v1/build/torch-cuda/geglu.py#L95\"><code>calculate_settings</code></a> picks them from the column count.</p>\n</li>\n</ol>\n<p>It is worth being honest about the trade-off here, because the raw numbers can be misleading. The Liger kernel runs in <strong>92.8 µs</strong>, while Inductor's fused kernel from the compile run was <strong>89.4 µs</strong>. At first glance the hand-written kernel looks slightly slower, but that comparison hides the cost that makes it worthwhile.</p>\n<p><code>torch.compile</code> specializes for a <strong>static shape</strong>. Inductor's <code>89.4 µs</code> kernel is fast precisely because it was generated for <em>this exact</em> <code>[8192, 3072]</code> problem. Change the batch size, the sequence length, or the hidden dimension, Dynamo re-traces, and you pay the compile cost all over again to get a new specialized kernel.</p>\n<p>So the real choice is not \"slow human kernel vs fast compiled kernel\". It is <strong>a fast generic kernel vs a kernel specialized for one particular input shape</strong>. The Liger kernel takes one set of launch parameters and runs them for <em>any</em> shape with no recompilation. It gives up the last few microseconds that per-shape specialization would buy, in exchange for being robust to changing shapes.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-mlp-fusion#conclusion\">\n\t</a>\n\t<span>\n\t\tConclusion\n\t</span>\n</h2>\n<p>The table below collects what each step changed on the GPU and what it left untouched.</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>Setup</th>\n<th>What changed</th>\n<th>What stayed the same</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Eager <code>nn.Linear</code></td>\n<td>Baseline: bias add is already folded into the GEMM epilogue (<code>addmm</code>), so it is <em>one</em> cuBLAS kernel, not a matmul plus an add</td>\n<td>—</td>\n</tr>\n<tr>\n<td>Compiled <code>nn.Linear</code></td>\n<td>A few CPU dispatch ops (the <code>aten::t</code> view bookkeeping) disappear</td>\n<td>Same single cuBLAS GEMM kernel, byte-for-byte.
