cannot profile, you cannot optimize.</em></p>\n</blockquote>\n<p>Whether you are trying to squeeze more tokens per second out of a Large Language Model (LLM), shave milliseconds off inference, or just understand why your training loop runs slower than the spec sheet promises, the path eventually runs through profiling.</p>\n<p>The catch is that profiling has a <strong>steep</strong> on-ramp. The traces are dense walls of colored rectangles. The events carry intimidating names. Most tutorials assume you can already read them. So even when we <em>know</em> we should be profiling, opening a trace can feel like a chore best left for later (or for someone else). This post, and the series it kicks off, is our attempt to lower that on-ramp.</p>\n<p>We document the journey from a beginner's point of view. No prerequisites apart from basic PyTorch. Treat this as a leisurely read with some \"Aha!\" moments. The structure of the post is intentionally question-led: we open a trace, ask \"wait, why is <em>that</em> happening?\", and chase the answer until something clicks. By the end you should know:</p>\n<ul>\n<li>how to set up <code>torch.profiler</code> and what it actually hands back,</li>\n<li>how to read the profiler table and the trace (CPU lane, GPU lane, and the suspicious gaps in between),</li>\n<li>the chain of events from a Python call all the way down to a CUDA kernel,</li>\n<li>what changes (and, more interestingly, what does <strong>not</strong> change) when you slap <code>torch.compile</code> on top.</li>\n</ul>\n<p>Before we begin, two definitions that will make everything below read better:</p>\n<ol>\n<li>A GPU <strong>kernel</strong> is a program that runs in parallel on many threads of the GPU.</li>\n<li>The CPU <strong>schedules and launches</strong> these kernels.</li>\n</ol>\n<p>You don't usually have to write GPU kernels yourself; when you use a PyTorch operation, it is automatically translated to one or more kernels that do the job on GPU.</p>\n<p>With those two ideas in your back pocket, let's start asking questions.</p>\n<blockquote>\n<p>Here is the entire script that we use for the post: <a target=\"_blank\" href=\"https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py\"><code>01_matmul_add.py</code></a>. We recommend opening this script in a separate tab and walk through the code step by step. We use the <code>NVIDIA A100-SXM4-80GB</code> GPU to run the scripts. It is really easy to setup a GPU on the Hugging Face infrastructure and experiment with the scripts using the <a target=\"_blank\" href=\"https://huggingface.co/docs/hub/spaces-dev-mode\">Dev Mode with Spaces</a>. One could also run the scripts with the <a target=\"_blank\" href=\"https://huggingface.co/docs/huggingface_hub/en/guides/jobs\">Hugging Face Jobs pipeline</a>.</p>\n</blockquote>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-profiler#the-matrix-multiplication-and-addition-operation\">\n\t</a>\n\t<span>\n\t\tThe matrix multiplication and addition operation\n\t</span>\n</h2>\n<p>As correctly <a target=\"_blank\" href=\"https://youtu.be/7knwihgj0fU?si=uvzGH-J9bsCHP4Nn&t=2199\">quipped by Dr. Sara Hooker</a>, just as we are primarily made up of water, Deep Neural Networks are primarily made up of matrix multiplies. As fundamental as they are, it would be a shame to start our profiling journey with anything else.</p>\n<pre><code><span>def</span> <span>fn</span>(<span>x, w, b</span>):\n  <span>return</span> torch.add(torch.matmul(x, w), b)\n</code></pre>\n<blockquote>\n<p>The matrix addition along with the matrix multiplication mimics how weights and biases interact in a neuron. This addition (pun intended) will help us understand how it paves the way for compilation <a target=\"_blank\" href=\"https://huggingface.co/blog/torch-profiler#lets-see-some-torch-compile-at-work\">later in the post</a>.</p>\n</blockquote>\n<p>To profile, we will be using the <code>torch.profiler</code> module. The steps involved are:</p>\n<ol>\n<li>Have the <a target=\"_blank\" href=\"https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L26-L27\">code to profile ready</a> (here <code>def fn</code>, which wraps the matrix multiplication and matrix addition)</li>\n<li><a target=\"_blank\" href=\"https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L32\">Annotate</a> the algorithm. While this is completely optional, we recommend doing this. The <code>record_function</code> annotates our function as <code>matmul_add</code>, which will be easy to navigate in the traces (as we note later)</li>\n</ol>\n<pre><code><span>def</span> <span>step</span>():\n  <span>with</span> torch.profiler.record_function(<span>\"matmul_add\"</span>):\n    <span>return</span> fn(x, w, b)\n</code></pre>\n<ol>\n<li>Wrap the code with the <code>torch.profiler.profile</code> <a target=\"_blank\" href=\"https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L53-L62\">context manager</a></li>\n</ol>\n<pre><code>  <span>with</span> torch.profiler.profile(\n    activities=[\n        torch.profiler.ProfilerActivity.CPU,  <span># the cpu activities</span>\n        torch.profiler.ProfilerActivity.CUDA, <span># the gpu activities</span>\n    ],\n  ) <span>as</span> prof:\n    <span># it is recommended to run events multiple times to warm up the GPUs</span>\n    <span>for</span> _ <span>in</span> <span>range</span>(<span>5</span>):\n      step()\n      prof.step()\n</code></pre>\n<ol>\n<li>Export the <a target=\"_blank\" href=\"https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L70\">profile</a></li>\n</ol>\n<pre><code><span># the profiler table</span>\nprof.key_averages().table(sort_by=<span>\"cuda_time_total\"</span>, row_limit=<span>15</span>)\n<span># the profiler trace</span>\nprof.export_chrome_trace(trace_path)\n</code></pre>\n<p>The profiler exports two distinct artifacts:</p>\n<ol>\n<li>The profiler table: Provides the statistical summary of the algorithm. It answers \"What is taking the most time\". This becomes really helpful to figure out hotspots. A hotspot would be events that take the most amount of time, can be a bottleneck of the pipeline, or an event that is triggered a lot of times.</li>\n<li>The profiler trace: Provides the temporal execution view. Answers \"When and Why an operation happened\", depicting the activities taking place on the CPU and the GPU. This is helpful when we want to investigate the kernel(s) that were launched, any delays in launching them, any overlap between CPU and GPU activities, etc.</li>\n</ol>\n<p>Let's see the two in action with our first execution. (<a target=\"_blank\" href=\"https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py\">Here is the entire <code>01_matmul_add.py</code> script</a>)</p>\n<blockquote>\n<p>It is recommended to run this script on a machine with a GPU.</p>\n</blockquote>\n<pre><code>uv run 01_matmul_add.py --size 64\n</code></pre>\n<p>If you run the above script (on a GPU machine) you will find a folder <code>traces/01_matmul_add</code> with the two artifacts:</p>\n<pre><code>64_bf16_cold_eager.json\n64_bf16_cold_eager.txt\n</code></pre>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/profile-table-64.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/profile-table-64.png\" alt=\"Profiler table for matmul add on 64 sized matrices\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 1: Profiler table for matmul add on 64 sized matrices</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>The <code>.txt</code> file holds the profiler table. Upon opening the file, as shown in Figure 1, one would be greeted with a big table with the first column consisting of the events that were triggered inside the scope of profile.</p>\n<p>The other columns are related to the time the event takes on the CPU or GPU or any other device(s) specified in <code>activities</code> within <code>torch.profiler.profile</code>. Look at which events take the most amount of time, and try to intuitively understand if that event should in fact take that time. It is also important to look at the column \"# of Calls\" which dictates how many times the event was triggered.</p>\n<p>While we are at it, let's also talk about \"Self CPU/CUDA\" vs \"CPU/CUDA total\". The \"Self\" columns measure time spent only inside the event itself, excluding its children. The \"total\" columns include the event and all of its children together. So if you look at the \"CPU total\" of <code>matmul_add</code>, it consists of the time it took on self plus the children events it triggered. This is an important nuance to note.</p>\n<p>If you look at the last two lines out of the table you would notice that the profiler tells us that</p>\n<pre><code>Self CPU time total: 2.314ms\nSelf CUDA time total: 23.104us\n</code></pre>\n<p>The CPU time is in <code>ms</code> while the GPU time is in <code>us</code>. To put things in perspective, the time spent on GPUs (the kernel <code>ampere_bf16_s16816gemm...</code>) is less than 1% of the time spent on the CPU (the <code>matmul_add</code> operation).  The GPU stays idle most of the time, which is an immediate red flag. The reason this happens is that the GPU can compute a small matmul very quickly, so our code spends most of the time preparing the kernels, launching them on the GPU, sending the data to multiply and gathering the results. This concept is known as an <em>overhead-bound</em> algorithm.</p>\n<p>The easiest way to move out of this regime is to use bigger matrix multiplications.</p>\n<pre><code>uv run 01_matmul_add.py --size 4096 \n</code></pre>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/profiler-table-4096.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/profiler-table-4096.png\" alt=\"Profiler table for matmul add algorithm on 4096 sized matrices\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 2: Profiler table for matmul add on 4096 sized matrices</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>The last two lines in Figure 2 are:</p>\n<pre><code>Self CPU time total: 4.908ms\nSelf CUDA time total: 4.495ms\n</code></pre>\n<p>Both times are in ms, which means we have materialized more GPU time just by increasing the size of the matrix multiplications. If you look at Figure 2 you would also notice that the most CUDA time is now taken by the GPU kernel (<code>ampere_bf16_s16816gemm_..</code>) and not by the CPU operation that launched it (<code>matmul_add</code>). This means that we were indeed able to move from overhead bound to compute bound.</p>\n<p>We now move into visualising the dispatch chain, which lives inside the <code>.json</code> artifacts. You can upload them to <a target=\"_blank\" href=\"https://ui.perfetto.dev/\">Perfetto UI</a> and see the traces, or you can use <code>uvx trace-util -f traces -b &lt;hf_uname&gt;/traces</code> to generate the Perfetto links directly.</p>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-profiler#64x64-traces\">\n\t</a>\n\t<span>\n\t\t64x64 traces\n\t</span>\n</h2>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/64-matmul-add.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/64-matmul-add.png\" alt=\"PyTorch profiler trace of a 64×64 bf16 matmul followed by an add on a CUDA GPU\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 3: Profiler trace for matmul and add on 64 sized matrices</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>In Figure 3, we see the profiler trace for the matrix multiplication and addition. Here the bar width indicates the duration of an event, the vertical nesting is the call hierarchy, the CPU lane denotes the events that happen on the CPU, while the GPU lane shows the actual kernel executions. One might also notice the empty spaces which are the waiting or idle time.</p>\n<p>The script was run with default configurations which are:</p>\n<ul>\n<li>size 64: The inputs, weights and biases are sized (64, 64)</li>\n<li>dtype bf16: The data type is bfloat16</li>\n<li>no compile: We have not compiled the torch operations</li>\n<li>no warmup: We have not warmed up the GPU before profiling</li>\n</ul>\n<blockquote>\n<p>With Perfetto we suggest using the keyboard for quicker access to the trace. One could use \"W A S D\" for navigating the trace.</p>\n</blockquote>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/gpu-cpu-trace.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/gpu-cpu-trace.png\" alt=\"PyTorch profiler trace with the CPU lane and GPU lane labelled side by side in Perfetto\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 4: The CPU and GPU lanes of a PyTorch profiler trace</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>There are two lanes in Figure 4, one for the CPU activity and one for the GPU activity. In the CPU lane one would notice three profile steps (starting from <code>ProfilerStep#2</code>). This comes from the <code>schedule</code>.</p>\n<pre><code>schedule = torch.profiler.schedule(wait=<span>1</span>, warmup=<span>1</span>, active=<span>3</span>, repeat=<span>1</span>)\n</code></pre>\n<p>The <code>wait</code> skips noisy initializations (<code>ProfilerStep#0</code>), <code>warmup</code> runs through the profiler without recording (<code>ProfilerStep#1</code>), and <code>active</code> is what shows up in trace. One can find the schedule being used in the <a target=\"_blank\" href=\"https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L58\">script here</a>.</p>\n<p>Let's put on our detective hats and investigate the trace and ask some questions.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-profiler#why-does-the-profilerstep2-take-so-long\">\n\t</a>\n\t<span>\n\t\tWhy does the ProfilerStep#2 take so long?\n\t</span>\n</h3>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/why-is-step-2-big.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/why-is-step-2-big.png\" alt=\"ProfileStep#2 in a PyTorch profiler trace appears wider than ProfileStep#3 and ProfileStep#4\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 5: <code>ProfileStep#2</code> is visibly wider than the steps that follow it</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>In Figure 5, we notice that <code>ProfileStep#2</code> takes more time compared to the other steps, and upon looking closely you would see a similar pattern with the <code>matmul_add</code> annotation as well. The smoking gun is inside the annotation, not the annotation itself:</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>Step</th>\n<th><code>matmul_add</code> start</th>\n<th><code>aten::matmul</code> start</th>\n<th>gap</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>#2</td>\n<td>138.736</td>\n<td>366.493</td>\n<td>227.757 µs</td>\n</tr>\n<tr>\n<td>#3</td>\n<td>517.926</td>\n<td>523.447</td>\n<td>5.521 µs</td>\n</tr>\n<tr>\n<td>#4</td>\n<td>610.039</td>\n<td>614.527</td>\n<td>4.488 µs</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/gap-227.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/gap-227.png\" alt=\"228 microsecond gap between record_function matmul_add and the aten::matmul dispatch in profile step 2\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 6: The ~228 µs dead window between <code>record_function(\"matmul_add\")</code> and <code>aten::matmul</code></td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>That ~228 µs shown in Figure 6 is the \"dead window\" between entering <code>record_function(\"matmul_add\")</code> and PyTorch actually dispatching <code>aten::matmul</code>. This can happen for multiple reasons, including workspace allocations, <a target=\"_blank\" href=\"https://developer.nvidia.com/cublas\">cuBLAS</a> (NVIDIA’s proprietary, GPU-accelerated library for performing fundamental linear algebra operations) heuristics, or lazy module loading. We can either look away or run <a target=\"_blank\" href=\"https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L35-L39\">some more warmup steps</a> before we profile (which is the standard)</p>\n<p>In terms of profiling, warmup is when you run the events a couple of times before actually profiling it. The pre-work done by the GPU (including the above pointers) are one time efforts which we do not want to profile. In our example, we have two warmup stages, one where we actually loop over the function before entering the profiler, and two inside the profiler which is achieved by the <code>warmup</code> argument. In this section, we have enabled the actual iterations along with the schedule.</p>\n<pre><code>uv run 01_matmul_add.py --warmup\n</code></pre>\n<p><a target=\"_blank\" href=\"https://ui.perfetto.dev/#!/?url=https://huggingface.co/buckets/ariG23498/traces/resolve/01_matmul_add/64_bf16_warm_eager.json\">Perfetto Trace for 64x64 with Warmup</a></p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th><a target=\"_blank\" href=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/warmup.png\"><img src=\"https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/warmup.png\" alt=\"PyTorch profiler trace after warmup steps where ProfileStep#2 no longer shows cold-start overhead\"></a></th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>Figure 7: After warming up, every profile step takes a similar amount of time</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p>In Figure 7 we see that each profile step takes a similar time, but this does not mean we were able to optimize the one time overheads. We warmed up the runs so that the overheads were not profiled. Let's look at the CPU-side hierarchy which reflects <code>torch.compile</code>'s runtime architecture.</p>\n<p><strong>TorchDynamo Cache Lookup</strong> is where Dynamo checks that the current call still matches what was compiled with the same input shapes, dtypes, devices, and tensor metadata. This observation was directly contradicting what we were seeing in the GPU trace. There were still two kernels being launched per step, namely the <code>Memcpy DtoD (Device -&gt; Device)</code> and the GEMM. Going back to the CPU trace, we noticed that we had completely missed the <code>cudaMemcpyAsync</code> dispatch.</p>\n<p><code>addmm</code> computes <code>out = α·A·B + β·C</code>, and cuBLAS's GEMM-with-bias-add epilogue writes into a destination buffer that needs to already contain the bias. An epilogues can be thought of all the operations that happen <em>after</em> a GEMM. In the world of deep-learning we constantly come up with GEMM-Epilogues like activations, bias addition, normalization and many more. This is why there are cuBLAS GEMM-with- kernel variants.</p>\n<blockquote>\n<p>If you use different <code>mode</code>s for <code>torch.compile</code> you would notice different kernel variants being launched. You can try it for yourself and add a comment below about your observations!</p>\n</blockquote>\n<p>So Inductor-generated code does:</p>\n<ul>\n<li><code>out = copy(C)</code> ← that's the DtoD memcpy (32 MB, takes ~33 µs)</li>\n<li><code>out = α·(A·B) + β·out</code> ← GEMM with <code>α=β=1</code>, fusing the bias add into the writeback</li>\n</ul>\n<p>The result is mathematically still the same. The bias add isn't free, as we pay a memcpy upfront plus a slightly more expensive GEMM epilogue.</p>\n<p>The fusion one might have hoped for, where <code>x·w + b</code> (here <code>out = α·A·B + β·C</code>) collapses into a single kernel with no extra memory traffic, isn't what happened. Inductor preserved the two memory-touching operations, it just relabeled the bias copy as a memcpy and the addition as a GEMM epilogue.</p>\n<p>A truly fused implementation would skip the memcpy. That's what FlashAttention-style hand-written kernels do, and what Inductor can do via Triton codegen, but for a <code>4096×4096 bf16 matmul</code>, Inductor evidently decided \"use cuBLAS, do the bias via epilogue setup\" was the best path.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-profiler#cpu-overhead-went-up-not-down\">\n\t</a>\n\t<span>\n\t\tCPU overhead went up, not down\n\t</span>\n</h3>\n<p>This is the easiest thing to miss when comparing an eager and a compiled run:</p>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>step</th>\n<th>eager dur (ms)</th>\n<th>compile dur (ms)</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>#2</td>\n<td>0.1</td>\n<td>0.2</td>\n</tr>\n<tr>\n<td>#3</td>\n<td>0.07</td>\n<td>0.1</td>\n</tr>\n<tr>\n<td>#4</td>\n<td>0.07</td>\n<td>0.1</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<p><code>torch.compile</code> is roughly 2× more expensive on the CPU per step. That's because every call walks the full Dynamo &gt; AOTAutograd &gt; Inductor stack, on top of the same <code>aten::addmm</code> dispatch we have anyway. The compile pipeline is built for ML models with dozens of ops where the per-call overhead amortizes (for a single op it's a tax).</p>\n<blockquote>\n<p><code>torch.compile</code> has a <code>mode</code> argument. It is for the reader to take home as an assignment to read the documentation and come up with a <code>mode</code> that could take the CPU overhead down. 🤗</p>\n</blockquote>\n<h2>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-profiler#trace-reading-cheatsheet\">\n\t</a>\n\t<span>\n\t\tTrace reading cheatsheet\n\t</span>\n</h2>\n<p>A quick reference for the patterns we walked through. The idea is: if you see this in a trace, this is what it usually means.</p>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-profiler#profiler-table\">\n\t</a>\n\t<span>\n\t\tProfiler table\n\t</span>\n</h3>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>What you see</th>\n<th>What it usually means</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td><code>Self CPU time total</code> ≫ <code>Self CUDA time total</code> (CPU in ms, GPU in µs)</td>\n<td>Overhead-bound. The CPU spends more time dispatching than the GPU spends computing. Make the work bigger (larger matrices, batched ops) or fuse calls.</td>\n</tr>\n<tr>\n<td><code>Self CPU time total</code> ≈ <code>Self CUDA time total</code>, both in ms</td>\n<td>Compute-bound. The GPU is the bottleneck, which is usually what you want.</td>\n</tr>\n<tr>\n<td>One event dominates <code>CUDA total</code></td>\n<td>That's your hotspot. Start the optimization there.</td>\n</tr>\n<tr>\n<td>One event has a huge <code># of Calls</code></td>\n<td>A potential bottleneck even if each call is cheap. Check whether it can be fused or batched.</td>\n</tr>\n<tr>\n<td><code>CPU total</code> ≫ <code>Self CPU</code> for a row</td>\n<td>Most of the cost lives in children. Drill into the nested events, not the parent.</td>\n</tr>\n</tbody>\n\t</table>\n</div>\n<h3>\n\t<a target=\"_blank\" href=\"https://huggingface.co/blog/torch-profiler#cpu-lane\">\n\t</a>\n\t<span>\n\t\tCPU lane\n\t</span>\n</h3>\n<div>\n\t<table>\n\t\t<thead><tr>\n<th>What you see</th>\n<th>What it usually means</th>\n</tr>\n\t\t</thead><tbody><tr>\n<td>First <code>ProfileStep</code> much wider than the rest</td>\n<td>Cold-start overhead: workspace allocation, cuBLAS heuristics, lazy module loading. Add warmup iterations and/or the schedule's <code>warmup</code> argument.</td>\n</tr>\n<tr>\n<td>Big gap between <code>record_function(\"...\")</code> start and the first <code>aten::*</code> inside it</td>\n<td>Same cold-start tax, just zoomed in. The annotation entered, but the dispatch hadn't happened yet.</td>\n</tr>\n<tr>\n<td><code>cudaOccupancyMaxActiveBlocksPerMultiprocessor</code> before a <code>cudaLaunchKernel</code></td>\n<td>A heavyweight, adaptively-launched kernel (GEMM, conv, etc.). cuBLAS is asking the driver how many blocks fit on an SM so it can pick a kernel variant.</td>\n</tr>\n<tr>\n<td><code>cudaLaunchKernel</code> with no preceding occupancy query</td>\n<td>An elementwise or reduction kernel with a fixed, resource-light footprint. A sync covering tiny GPU work is a classic overhead-bound symptom.</td>\n</tr>\n<tr>\n<td>A <code>cudaMemcpyAsync</code> you didn't write</td>\n<td>Often a hidden Device-to-Device copy. The first one usually accounts for the initial CPU↔GPU lane offset.</td>\n</tr>\n<tr>\n<td>A gap between two kernels in a single step</td>\n<td>Likely another buffer request mid-execution. Confirm by running more iterations: if it appears only once, it's the profiler, not your code.</td>\n</tr>\n<tr>\n<td>The same kernel timing differently across steps</td>\n<td>GPU clocks, thermals, power management, driver housekeeping. Read the trace, not just the mean.</td>\n</tr>\n<tr>\n<td>A kernel named like <code>ampere_bf16_s16816gemm_...</code></td>\n<td>The actual cuBLAS GPU work for a matmul. The kernel name is typically the same in eager and compiled mode for the same shapes/dtypes.</td>\n</tr>\n<tr>\n<td><code>Memcpy DtoD</code> immediately before a GEMM</td>\n<td>The bias copy for an <code>addmm</code> epilogue.
