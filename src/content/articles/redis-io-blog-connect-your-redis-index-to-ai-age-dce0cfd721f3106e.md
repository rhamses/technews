contentHtml: "<div><p>If you already use Redis for search, retrieval, or application memory, the RedisVL MCP is a practical next step: making that data available to agents without rebuilding your integration for every framework.</p><p>As teams connect indexed data to agents, the work shifts to integration. Different clients need access to the same retrieval surfaces, search behavior needs to stay consistent, and platform teams still need control over how that access works. The Model Context Protocol (MCP) addresses this by giving agent systems a standard way to discover and invoke tools. Instead of building a custom Redis integration for every agent stack, teams can expose a smaller, stable interface and reuse it across any MCP-compatible client -- Claude Desktop, Cursor, OpenAI Agents SDK, LangChain, or whatever comes next.</p><p>Redis already provides the <a target=\"_blank\" href=\"https://redis.io/docs/latest/integrate/redis-mcp/\">official Redis MCP Server</a> for broad agent access to Redis data structures, query-engine capabilities, and server-management workflows. RedisVL MCP is complementary and more focused: it exposes existing Redis Search indexes as governed retrieval surfaces with predictable tool contracts. Use the official Redis MCP Server when an agent should work with Redis generally. Use RedisVL MCP when the goal is application retrieval with configured search behavior, schema-aware filters, controlled return fields, runtime limits, and optional read-only mode.</p><p>For developers, that means less framework-specific glue code. For platform teams, it means a manageable surface for governance, security, and operational control. For Redis users specifically, it means the indexes you already have can become a shared tool layer across your AI stack.</p><h2>What the RedisVL MCP exposes</h2><p>The RedisVL MCP sits at the RedisVL layer, not the raw Redis command layer. It exposes a higher-level interface around existing Redis Search indexes with two tools:</p><p><code>search-records</code> -- Search the index by text query. The server handles embedding, query construction, and result normalization. Agents supply query text, pagination, filters, and return fields. They do not decide the search mode (vector, full-text, or hybrid) or tuning parameters -- those are owned by configuration.</p><p><code>upsert-records</code> -- Write records to the index. The server validates each record against the index schema, embeds text fields server-side when the record lacks a vector (or always, depending on config), and writes to Redis. Disabled in read-only mode.</p><p>Under the hood, the server:</p><ul><li>Binds to one existing Redis index at startup today, with multi-index support planned</li><li>Inspects the index via <code>FT.INFO</code> and reconstructs its schema automatically -- no need to redeclare field definitions</li><li>Uses a configured vectorizer when vector search or server-side embedding requires one</li><li>Supports stdio, SSE, and streamable-http transports -- run locally for development or behind the right network and authentication controls for remote deployments</li><li>Keeps search mode and tuning parameters in config, not in the request contract</li></ul><h3>Schema introspection and overrides</h3><p>One design choice worth highlighting: the server reconstructs the full index schema from Redis at startup rather than requiring a separate schema file. This means you point the MCP at an existing index and it can infer the fields it should expose.</p><p>For cases where <code>FT.INFO</code> does not expose all vector field attributes (e.g., older Redis versions), the config supports <code>schema_overrides</code> to patch in missing metadata like dimensionality or distance metric for fields that were already discovered. This keeps the common path simple without blocking edge cases.</p><h2>Filtering</h2><p>Agents can pass structured filters without writing raw Redis query syntax. The filter contract supports tag, text, and numeric fields with logical combinators:</p><p>Supported operators include <code>eq</code>, <code>ne</code>, <code>like</code>, and <code>in</code> for tag and text fields. Numeric fields support <code>eq</code>, <code>ne</code>, <code>gt</code>, <code>gte</code>, <code>lt</code>, <code>lte</code>, and <code>in</code>. The exists operator is available for any known schema field. Filters can be composed with <code>and</code>, <code>or</code>, and <code>not</code>. Agents can also pass raw Redis filter strings if they need full control.</p><h2>Upsert with server-side embedding</h2><p>When ingestion is enabled, agents send records as plain objects. The server handles the rest:</p><p>The server reads the <code>content</code> field (configurable via <code>default_embed_text_field</code>), generates the embedding using the configured vectorizer, validates the record against the index schema, and writes it to Redis. If a record already includes a vector, the server skips embedding by default (<code>skip_embedding_if_present: true</code>) -- useful when pre-computed embeddings are available.</p><p>Batch size is capped by <code>max_upsert_records</code> (default: 64) to prevent runaway writes.</p><h2>Runtime governance</h2><p>The MCP server exposes several knobs that platform teams care about:</p><div><table><thead><tr><th><span>Setting</span></th><th><span>Default</span></th><th><span>Purpose</span></th></tr></thead><tbody><tr><td><span>default_limit</span></td><td><span>10</span></td><td><span>Default result count when caller omits limit</span></td></tr><tr><td><span>max_limit</span></td><td><span>100</span></td><td><span>Hard cap on results per request</span></td></tr><tr><td><span>max_result_window</span></td><td><span>1000</span></td><td><span>Maximum offset + limit to prevent deep pagination</span></td></tr><tr><td><span>max_upsert_records</span></td><td><span>64</span></td><td><span>Maximum records per upsert call</span></td></tr><tr><td><span>max_concurrency</span></td><td><span>16</span></td><td><span>Concurrent request limit</span></td></tr><tr><td><span>request_timeout_seconds</span></td><td><span>60</span></td><td><span>Per-request timeout</span></td></tr></tbody></table></div><p>Combined with read-only mode (<code>--read-only flag</code> or <code>REDISVL_MCP_READ_ONLY=true</code>), these give platform teams fine-grained control over what agents can and cannot do.</p><h3>Error contract</h3><p>Errors follow a typed contract with stable error codes (<code>invalid_request</code>, <code>invalid_filter</code>, <code>dependency_missing</code>, <code>backend_unavailable</code>, <code>internal_error</code>) and a <code>retryable</code> flag. This lets agent frameworks distinguish between bad requests that should not be retried, missing dependencies that need operator action, and transient backend failures that should.</p><h2>Running the server</h2><p>Install the MCP extra:</p><p>The server supports three transport modes. <strong>stdio</strong> is the default and works with local MCP clients like Claude Desktop and Cursor. <strong>SSE</strong> and <strong>streamable-http</strong> run the server as a persistent HTTP service for remote or multi-client deployments.</p><p>SSE and streamable-http endpoints are unauthenticated by default. Only bind them to public interfaces on trusted networks or behind an authenticating reverse proxy. If you do not need agent-driven writes, run with <code>--read-only</code> so <code>upsert-records</code> is not exposed.</p><h3>Server configuration</h3><p>A minimal config looks like this:</p><p>The <code>redis_name</code> field points to the existing Redis index. The server discovers index details such as prefix and field definitions from Redis at startup.</p><p>The <code>search.type</code> field (<code>vector</code>, <code>fulltext</code>, or <code>hybrid</code>) determines how the server builds queries. Query tuning parameters like <code>linear_text_weight</code> or <code>text_scorer</code> live under <code>search.params</code>, not in the request contract. This separation keeps agent requests simple while letting operators tune behavior.</p><p>The <code>vectorizer</code> block names a RedisVL vectorizer class and its model. The server instantiates it when vector search or server-side embedding requires it. API keys are resolved from environment variables (e.g., <code>OPENAI_API_KEY</code>). Full-text-only deployments can omit vector-only settings and the vectorizer entirely.</p><h3>Client configuration</h3><p>For Claude Desktop, add to your <code>claude_desktop_config.json</code>:</p><p>For Cursor, add to <code>.cursor/mcp.json</code>:</p><p>For clients connecting to a remote SSE or streamable-http server, use a URL instead of a command:</p><h2>A concrete example</h2><p>Suppose you have a Redis index called <code>knowledge_base</code> with <code>title</code> (text), <code>content</code> (text), <code>category</code> (tag), <code>year</code> (numeric), and <code>embedding</code> (vector) fields. The vector field is excluded from results by default. Score types are labeled so the agent (or downstream logic) knows how to interpret them.</p><h2>What is next</h2><p><strong>Multiple indexes</strong> -- Today, each MCP server instance binds to one index. Multi-index support will let a single server expose multiple indexes as separate tools -- for example, <code>search-knowledge-base</code> and <code>search-products</code> from one process. The config already uses <code>indexes</code> as a dict, and this is the natural next step.</p><h2>Getting started</h2><p>If you have an existing Redis index, you can have the MCP server running in under five minutes:</p><ol><li><code>pip install redisvl[mcp]</code></li><li>Write a YAML config pointing at your index</li><li>Run <code>rvl mcp --config mcp.yaml</code></li><li>Add the server to your MCP client config</li></ol><p>The index schema is introspected automatically. The search mode, vectorizer, and runtime limits are all in config. The request contract stays simple.</p><p>For the full configuration reference and more examples, see the <a target=\"_blank\" href=\"https://docs.redisvl.com/\">RedisVL documentation</a>.</p></div>"
