contentHtml: "<div><p>Your agent passes every test you throw at it. The demo is clean, the eval suite is green, and you ship. Then a week later, the support tickets start: agents looping, costs spiking, responses that confidently cite facts that were never true. The model didn't change. The context around it did.</p><p>Context engineering is the set of strategies for curating and maintaining the optimal set of tokens, or information, during LLM inference. That sounds tidy until you're running thousands of sessions a day and watching token bills climb for reasons your prompt-level thinking never accounted for. The principles that keep context reliable under real traffic don't show up in demos. They show up in production, when sessions get long, tool outputs pile up, and retrieval starts pulling in noise. This article covers five of them: how to budget cost across a whole run, where to filter tool outputs, how to layer static and dynamic context, why retrieval is a budget decision, and why evals often miss context failures.</p><h2><strong>Principle 1: Treat the whole run as the cost unit, not the turn</strong></h2><p>You optimize a prompt, shave 30% off its token count, and your bill barely moves. That's the first sign you're budgeting the wrong unit. The cost that matters isn't the turn, it's the whole run.</p><p>Here's why. Each API call is billed separately, but every turn re-sends the full conversation history as input. So per-turn input grows linearly while cumulative run cost grows much faster: <a target=\"_blank\" href=\"https://online.stevens.edu/blog/hidden-economics-ai-agents-token-costs-latency\">one cost model</a> shows that doubling conversation length roughly quadruples the spend. As sessions lengthen, the main cost driver becomes re-processing history, not producing new tokens.</p><p>Tool outputs make this worse. File reads, terminal output, and search results from earlier turns get re-sent on every call too. By turn 10, your context can carry thousands of tokens of old tool output the agent may never reference again, and you pay to reprocess all of it each turn.</p><p>Not all of that cost is unavoidable. Some of it is repeated work: the same question, or a paraphrase of it, hitting the model again. Semantic caching targets that slice. It recognizes when a new query means the same thing as a cached one, even if the wording differs, and returns the stored response instead of calling the model again. Run as a managed layer, this can take a real bite out of inference spend on repetitive traffic. <a target=\"_blank\" href=\"https://redis.io/langcache\">Redis LangCache</a>, the semantic caching service in the Redis Iris context engine, reported up to <a target=\"_blank\" href=\"https://redis.io/blog/llm-token-optimization-speed-up-apps\">73% lower inference costs</a> in Redis benchmarks on high-repetition workloads.</p><div><p><img alt=\"Redis Iris\" src=\"https://cdn.sanity.io/images/sy1jschh/production/82df1fa7f210a2b005d5ebbf3429a53a0ebccce0-64x64.svg\"></p><div><h2>Redis Iris serves agent context in milliseconds</h2><p><span>Redis Iris connects memory, live data, and retrieval in one place.</span></p></div></div><p>Caching has limits worth knowing up front. For multi-turn agents, cache keys and similarity thresholds need to account for session state, because follow-up questions can otherwise be falsely matched to earlier, unrelated prompts. It works best for repeated standalone intents or normalized sub-requests.</p><h2><strong>Principle 2: Filter tool outputs at ingestion, not after they bloat the window</strong></h2><p>Once you're thinking about the whole run, the next question is where the tokens go. More often than not, the answer is tool outputs. Search and API responses are often the biggest single cost in an agent's context.</p><p>APIs predate LLMs and were built for deterministic systems, so they often return more than the model needs. A single API call can dump a wall of nested JSON when the agent needed three fields. Multiply that across a multi-step loop and you've buried the signal under accumulated noise.</p><p>The instinct is to compress later: summarize the conversation once it gets long. That's the wrong order of operations. Filtering at ingestion is more effective, because you only keep what's needed for the next step. Compressing after the fact risks losing details that mattered and does little to stop bad data from entering the context at all. It also reduces the risk of context poisoning, where an early error gets preserved as truth and compounds across later reasoning. Production teams use a few concrete patterns:</p><ul><li><strong>Offload large responses.</strong> Store oversized tool responses outside the prompt and substitute a pointer plus a short preview.</li><li><strong>Truncate noisy content.</strong> Bound tool outputs with a token policy and trim long text before it enters the next turn.</li><li><strong>Clear stale results.</strong> Once a tool result sits deep in the message history, the agent rarely needs the raw result again.</li></ul><p>These share the same logic: cut at the source, keep the working set lean. When trimming, preserving whole turns usually keeps coherence better than cutting through the middle of a message.</p><h2><strong>Principle 3: Keep static &amp; dynamic context in separate layers</strong></h2><p>Filtering tells you what to keep. Layering tells you how to organize it. A lot of agent reliability problems trace back to one thing: instructions, retrieved data, and history all get collapsed into a single undifferentiated blob.</p><p>The cleaner pattern separates context into distinct layers. The simplest split is static versus dynamic. Static context is the fixed, cacheable part: system instructions, persona, and behavioral rules. Dynamic context is the task-dependent part: retrieved knowledge, conversation history, and working state. The practical motivation is straightforward. Some context rarely changes and benefits from caching, while other context needs to be fresh every turn.</p><p>Production teams often go further and run three layers: static, dynamic, and session. When everything is one string, you can't tell whether a failure came from a bad instruction, a stale retrieval, or a corrupted history. Separate layers let you update and debug each one independently.</p><p>Stateful agent architectures can model this directly. Short-term, thread-scoped memory tracks the ongoing conversation within a session, while long-term memory survives across sessions. The key move is that storing something and sending it to the model are separate decisions. The agent can hold everything it's tracking in a structured state, then expose only the relevant part to the LLM on a given turn, keeping the rest available without paying to put it in the prompt.</p><p>This is also where a unified data layer helps. The same store can hold conversation history, structured working state, and long-term semantic memory through <a target=\"_blank\" href=\"https://redis.io/nosql/search-engine-databases/\">vector search</a>, keeping the layers distinct without scattering them across separate systems to sync. <a target=\"_blank\" href=\"https://redis.io/iris\">Redis Iris</a> is built around this idea, bringing agent memory, context retrieval, and data integration into a single platform so the layers stay coherent as the agent runs.</p><div><p><img alt=\"Redis Stack\" src=\"https://cdn.sanity.io/images/sy1jschh/production/f21278431baa8511e060e03b929bc8664fd23341-64x64.svg\"></p><div><h2>Build agents that remember, not agents that guess</h2><p><span>Redis Iris gives every agent fresh context and long-term memory.</span></p></div></div><h2><strong>Principle 4: Retrieval is a budget decision, not a fetch-everything default</strong></h2><p>Layering organizes what you have. Retrieval decides what comes in. And the default instinct, pull as much relevant context as possible, is backwards. More retrieved documents don't guarantee better answers. They can make answers worse.</p><p>The foundational finding here is the <a target=\"_blank\" href=\"https://cs.stanford.edu/~nfliu/papers/lost-in-the-middle.tacl2023.pdf\">lost in the middle</a> problem: model performance is highest when relevant information sits at the start or end of the input, and degrades when the model has to use information buried in the middle. Stuffing more into the window pushes the good stuff toward that dead zone. And the reason extra documents backfire is counterintuitive: related-but-wrong documents do more damage than obviously irrelevant ones, because they look plausible. One <a target=\"_blank\" href=\"https://arxiv.org/html/2401.14887v3\">study of RAG retrieval</a> found that adding documents semantically close to the query, but not actually answering it, degraded accuracy more than adding random noise. Stronger retrievers can make this worse by surfacing <a target=\"_blank\" href=\"https://redis.io/blog/quality-context-ai-agents\">hard negatives</a>, semantically close but factually wrong passages.</p><p>The cost side reinforces the relevance side. Longer windows cost more to process, and accuracy can drop as the window fills. You can pay more to get less reliable answers. That's the opposite of what fetching everything is supposed to buy you.</p><p>A structural mitigation is to retrieve broadly for recall, then re-rank tightly for precision. A <a target=\"_blank\" href=\"https://redis.io/blog/quality-context-ai-agents\">cross-encoder re-orders</a> candidate documents by relevance before they enter the context window, filtering out the hard negatives before they reach the model. In a <a target=\"_blank\" href=\"https://redis.io/glossary/retrieval-augmented-generation/\">retrieval-augmented generation pipeline</a> (RAG), your app embeds the query, the vector store returns a broad candidate set, a re-ranker trims it to the few that matter, and only those reach the model.</p><p>The retrieval layer fetches and ranks; the app decides the budget. Redis supports <a target=\"_blank\" href=\"https://redis.io/nosql/search-engine-databases/\">vector search</a>, <a target=\"_blank\" href=\"https://redis.io/blog/redis-8-4-open-source-ga/\">full-text search</a>, and <a target=\"_blank\" href=\"https://redis.io/blog/from-demo-to-dependable-ai-in-context\">hybrid retrieval</a> with metadata filtering. For vector search, Redis supports FLAT and Hierarchical Navigable Small World (HNSW) <a target=\"_blank\" href=\"https://redis.io/blog/searching-1-billion-vectors-with-redis-8/\">index types</a> for exact and approximate nearest-neighbor search, plus <a target=\"_blank\" href=\"https://redis.io/blog/fall-release-2025/\">SVS-VAMANA indexes</a> for larger-scale vector workloads, depending on dataset size, index configuration, and latency budget.</p><h2><strong>Principle 5: Context failures can be invisible to standard evals</strong></h2><p>Here's the principle that ties the rest together: even if you nail cost, filtering, layering, and retrieval, your test suite probably won't tell you when they start to fail. Context degradation is easy to miss in standard evaluations.</p><p>The reason is structural. Most LLM benchmarks focus on short-form questions and rarely test performance when context is near capacity. Your agent passes because the test is short. Then it degrades over a long session, and nothing in your eval suite catches it. Some agent behaviors only emerge over multiple turns: the agent maintains context correctly for five turns and fails on turn six.</p><p>The numbers on this gap are stark. One evaluation covered web-agent sessions spanning <a target=\"_blank\" href=\"https://arxiv.org/html/2512.04307v1\">25,000 to 150,000 tokens</a>, where success rates dropped from 40–50% to under 10%, with agents getting stuck in loops and losing track of the original task. A separate <a target=\"_blank\" href=\"https://arxiv.org/html/2505.07897v1\">long-context evaluation</a> raised context length from 32K to 256K tokens and watched accuracy fall from 29% to 3%.</p><p>This is context rot, the <a target=\"_blank\" href=\"https://redis.io/blog/context-rot\">performance degradation</a> that happens when models process increasingly long inputs. What makes it dangerous is that it's silent. The model keeps running without error while its accuracy declines, losing track of guidelines and variables across long sessions. No exception, no failed assertion, just slowly worse output.</p><p>Catching it means watching context quality in production, not just in pre-deployment tests. Most observability setups instrument spans and traces but don't track <a target=\"_blank\" href=\"https://blog.langchain.com/agent-observability-powers-agent-evaluation/\">session-level quality</a>, which is exactly where degradation hides. A better pattern is to evaluate at the session level across dimensions like coherence, context retention, and goal achievement, and to feed real production traces back into your offline test sets.</p><div><p><img alt=\"Redis Vector Database\" src=\"https://cdn.sanity.io/images/sy1jschh/production/ba774ea6ad5d6bf132ab3ef194b6a1ad7d7c914f-64x64.svg\"></p><div><h2>Fresh context, every call</h2><p><span>Redis Iris keeps agent data current so answers stay accurate.</span></p></div></div><h2><strong>Context engineering is mostly a data problem</strong></h2><p>The five principles share a root cause. That makes these data problems, not model problems, and a bigger context window doesn't solve them. It just raises the ceiling on how much you can get wrong before it shows.</p><p>That makes the data layer the place reliability is won or lost.
