contentHtml: "<div><p>A customer asks your support agent whether their refund went through. The agent checks, says yes, and cites a confirmation number. The refund actually bounced back twenty minutes ago, but the lookup the agent ran hit a store that only syncs overnight. You tighten the system prompt: \"always confirm the latest transaction status before answering.\" Next ticket, same failure, because the prompt was never the problem. The data the agent reached for was already stale.</p><p>This is the trap that catches most teams shipping agents. When the output is wrong, the reflex is to rewrite the prompt, but the prompt is rarely where the failure lives. It lives in everything around the prompt: the data and history the agent draws on at the moment it answers.</p><p>Prompt engineering earned its reputation on single-turn, bounded tasks, where everything the model needed fit in one well-worded request. Production <a target=\"_blank\" href=\"https://redis.io/blog/what-is-an-ai-agent/\">AI agents</a> broke that assumption. This guide covers what context engineering and prompt engineering mean, why better prompts stopped moving the needle on production agents, and why stale or fragmented context is an infrastructure problem that prompt changes alone usually won't fix.</p><p>Prompt engineering is the craft of writing what you hand a model: the system message, examples, and formatting cues that steer its behavior. Done well, it reliably improves output, and it's still worth doing. The catch is scope. A prompt steers a single model call, but an agent strings many calls together.</p><p><a target=\"_blank\" href=\"https://university.redis.io/course/vsgabnbkd3f5cd?tab=details\">Context engineering</a> is broader. It's the set of strategies for <a target=\"_blank\" href=\"https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents\">curating and maintaining tokens</a> during LLM inference, covering everything in the context window outside the prompt: retrieved documents, memory, tool outputs, and user state. The line is clean: prompt engineering is about <em>how</em> you instruct the model; context engineering is about <em>what</em> the model knows when it answers. The prompt is one input among many, which makes prompt engineering a piece of context engineering, not the reverse.</p><div><p><img alt=\"Redis Iris\" src=\"https://cdn.sanity.io/images/sy1jschh/production/82df1fa7f210a2b005d5ebbf3429a53a0ebccce0-64x64.svg\"></p><div><h2>Redis Iris serves agent context in milliseconds</h2><p><span>Redis Iris connects memory, live data, and retrieval in one place.</span></p></div></div><h2><strong>Why prompt engineering stops scaling for production AI agents</strong></h2><p>Prompting was great when tasks were single-turn and everything the model needed fit in one prompt. Multi-step agents blew right past that. An agent orchestrates many LLM calls and tool invocations, and when something goes wrong, you're not tuning a sentence anymore. You're debugging how the whole system behaved across steps.</p><p>A prompt is also written once, at build time, but the agent runs against inputs you never saw when you wrote it. You can tune the instructions perfectly for the phrasings in your test set, yet real users won't phrase things that way. The same underlying request arrives a hundred different ways, and models can be <a target=\"_blank\" href=\"https://arxiv.org/abs/2602.16666\">sensitive to superficial paraphrasing</a>, so an agent that handles \"I want to cancel my subscription\" can still stumble on \"please end my plan.\" No fixed wording anticipates every variant. The same goes for what the prompt depends on: schemas and tool interfaces change, so an agent that breaks when a <a target=\"_blank\" href=\"https://redis.io/glossary/databases/\">database query</a> returns columns in a different order has a structural weakness, not a wording one. And prompts drift as models get updated, so tuning work rarely survives the next version bump.</p><p>The failures that show up most often in production aren't ones a better prompt can touch. They live in the machinery around it:</p><ul><li><strong>Bloated tool sets:</strong> Hand an agent too many tools and it often picks the wrong one because the decision surface is too wide.</li><li><strong>Missing memory:</strong> For agents that converse or act over multiple steps, prompt engineering alone falls short, because the model doesn't remember anything beyond its context window.</li><li><strong>Broken retrieval:</strong> Even a perfect prompt can't compensate for a broken retrieval system or an incomplete information pipeline.</li></ul><p>The throughline: when a production agent breaks, the cause usually sits in the context around the prompt, not the model.</p><h2><strong>The three parts of an agent's context window</strong></h2><p>Context is more than the documents you retrieve. It breaks into three buckets, each filling the window for a different reason:</p><ul><li><strong>Instructions:</strong> Prompts, system messages, few-shot examples, and tool descriptions, the standing rules that shape how the agent behaves.</li><li><strong>Knowledge:</strong> Facts and retrieved information the model wasn't trained on, including <a target=\"_blank\" href=\"https://university.redis.io/course/ihjs7iip0gpkrw\">retrieval-augmented generation</a> (RAG) results.</li><li><strong>Tools:</strong> Definitions of the external functions, APIs, and Model Context Protocol (MCP) servers the agent can call.</li></ul><p>Together these three are everything the model has to reason with on a given call. It knows nothing else: not the request it handled a minute ago, not the record that changed since the window was built. So where does all of it come from?</p><h2><strong>Context is assembled at runtime, not written at design time</strong></h2><p>Context comes from code that runs just before the model does. On every call, that code assembles the window fresh: it retrieves the relevant documents, loads the right slice of memory, attaches the tools the agent might need, and trims whatever won't fit. A prompt is fixed the moment you write it, so it can't do any of this on its own. The assembly step is what reaches live sources, like <a target=\"_blank\" href=\"https://redis.io/docs/latest/integrate/\">vector databases</a>, APIs, and memory stores, and turns them into the window the model actually reasons over. Done well, it's as much about what you leave out as what you include, and doing it fast enough to stay inside an agent's latency budget is its own <a target=\"_blank\" href=\"https://redis.io/blog/ai-agent-context\">infrastructure problem</a>.</p><div><p><img alt=\"Redis Vector Database\" src=\"https://cdn.sanity.io/images/sy1jschh/production/ba774ea6ad5d6bf132ab3ef194b6a1ad7d7c914f-64x64.svg\"></p><div><h2>Build agents that remember, not agents that guess</h2><p><span>Redis Iris gives every agent fresh context and long-term memory.</span></p></div></div><h2><strong>Stale &amp; fragmented context is an infrastructure problem</strong></h2><p>Assembling good context is harder than it sounds, because the data an agent needs is rarely fresh, fast, or in one place. The failures look like this: agents make confident, coherent-sounding decisions based on data that's three days old, or rerun expensive workflows they already completed. These are data problems, and they show up in two ways.</p><p>The first is freshness. Most data stacks were built for human consumers: batch analytics, periodic dashboards, daily refreshes. Agents need <a target=\"_blank\" href=\"https://redis.io/glossary/cache-invalidation/\">fresher data</a> than that. In an observe-decide-act loop, when the second observation returns outdated state, the agent re-plans and burns tokens. An agent making a purchasing decision on stale inventory data is an expensive business risk.</p><p>The second is fragmentation. Customer records, policies, and product details each live in a different system, and fast-changing operational data is <a target=\"_blank\" href=\"https://redis.io/blog/faq-real-time-context-engine-agent-memory-and-retrieval\">spread across APIs, databases</a>, and software-as-a-service (SaaS) tools. Pulling all of it into one coherent window, fast enough and for thousands of <a target=\"_blank\" href=\"https://redis.io/blog/scaling-microservices/\">concurrent users</a> at once, is a concurrency, consistency, and durability problem. None of that is solved at the prompt or the model. It's solved in the layer that does the assembling.</p><h2><strong>What a context engine does for AI agents</strong></h2><p>A context engine is the infrastructure layer that does the assembly. Production agent performance depends as much on it as on the model itself, spanning retrieval, memory, caching, and freshness. The pattern looks like User → Context Engine → Agents → Tools, with the engine on the hook for memory management across sessions and agents, task routing, tool boundary enforcement, token budget management with automatic pruning, and consistency, so a decision made by one agent is visible to all the others. <a target=\"_blank\" href=\"https://redis.io/iris/\">Redis Iris</a> is built for exactly this, bringing Context Retriever, Agent Memory, LangCache, Redis Data Integration, and Redis Search together as one runtime for agent context.</p><p>A few capabilities matter most. In a semantic retrieval flow, the app embeds the query, uses <a target=\"_blank\" href=\"https://university.redis.io/course/1npvvtfft2agew\">vector search</a> to pull the most similar chunks, and passes those chunks to the model as context, the job Context Retriever handles. LangCache adds <a target=\"_blank\" href=\"https://redis.io/langcache/\">semantic caching</a>: it matches incoming queries against previous ones using vector embedding similarity instead of exact string matching, so a sufficiently similar query returns a cached response <a target=\"_blank\" href=\"https://redis.io/blog/from-demo-to-dependable-ai-in-context\">without another LLM call</a>, which lowers cost and tail latency. One evaluation reported that semantic caching cut API calls by <a target=\"_blank\" href=\"https://arxiv.org/abs/2411.05276\">up to 68.8%</a> across tested query categories. Agent Memory handles the short-term and long-term split, with consolidation rules deciding what gets promoted.</p><p>The consolidation argument is what makes this an engine rather than a checklist. Memory and retrieval depend on each other, and keeping them on one layer avoids the dual-write problem and the drift that creeps in when two stores fall out of step. It also addresses a failure no prompt can reach: an agent that remembers your name but fabricates account balances.</p><h2><strong>Context, not prompts, is the bottleneck in production AI</strong></h2><p>The practitioner workflow has shifted. Teams stopped asking \"how do I phrase this better?\" and started asking \"what does this model need to know at every step to behave the way I want?\" A new role has emerged, the context engineer, whose work spans retrieval pipelines, memory systems, tool design, and evaluation, closer to systems engineering than to prompt writing. The reliability gains tend to follow from that architecture work rather than from sharper phrasing.</p><p>Prompt engineering still matters as one input, but in production agents, most of what breaks happens outside the prompt, in retrieval, memory, tool selection, and data freshness. Fixing those means working on the infrastructure that assembles context, not the wording fed in.</p><p><a target=\"_blank\" href=\"https://redis.io/iris/\">Redis Iris</a> is built as a <a target=\"_blank\" href=\"https://redis.io/blog/what-is-a-context-engine\">real-time context engine</a> for fast context assembly across vector search, semantic caching, agent memory, and fresh operational data.
