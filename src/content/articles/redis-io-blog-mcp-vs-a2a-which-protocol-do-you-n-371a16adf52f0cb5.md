contentHtml: "<div><p>Somewhere around your third agent, someone in a design review asks, \"Shouldn't we be using A2A for this?\" It's a fair question that most teams can't answer well, because the two big agent protocols keep getting lumped together when they solve different problems at different layers. The Model Context Protocol (MCP) connects an agent to its tools and data. The Agent2Agent (A2A) protocol connects independent agents to each other. Whether you need one, both, or neither depends less on how many agents you have and more on who owns them. This guide covers what MCP and A2A each do, why the two are designed to work together, and a decision rule for telling whether your system needs A2A or just a good orchestration framework.</p><h2><strong>What MCP does &amp; how it works</strong></h2><p>MCP is an open standard for connecting LLM apps to external tools and data. Its architecture defines three roles:</p><ul><li><strong>Hosts:</strong> the LLM app coordinating everything</li><li><strong>Clients:</strong> the connectors inside the host</li><li><strong>Servers:</strong> the endpoints that expose capabilities</li></ul><p>Servers expose those capabilities through three primitives: tools the model can call, resources that supply context, and prompts that template workflows. Under the hood it uses JSON-RPC, a lightweight request-response format, sent over a local connection or HTTP, and it can stream results back as they arrive.</p><p>MCP spread fast once the major AI providers lined up behind it. OpenAI <a target=\"_blank\" href=\"https://techcrunch.com/2025/03/26/openai-adopts-rival-anthropics-standard-for-connecting-ai-models-to-data\">adopted MCP</a> in March 2025 in its Agents SDK, with ChatGPT desktop support announced as coming soon. Google added <a target=\"_blank\" href=\"https://thenewstack.io/google-embraces-mcp\">native MCP support</a> to the Gemini API and SDK. MCP later moved under the <a target=\"_blank\" href=\"https://blog.modelcontextprotocol.io/posts/2025-11-25-first-mcp-anniversary\">Agentic AI Foundation</a> at the Linux Foundation.</p><p>In production, MCP shows up most clearly in three places:</p><ul><li><strong>Developer tooling and observability:</strong> during an incident, an agent pulls logs and metrics from systems like Grafana and Datadog in one place, instead of an engineer tabbing between dashboards at 2 a.m.</li><li><strong>Knowledge-worker copilots:</strong> a chat assistant reaches into systems of record like Salesforce and meeting notes to prep for a call.</li><li><strong>Self-serve analytics:</strong> non-technical teams query an internal data warehouse in plain language instead of filing a ticket to the data team.</li></ul><p>Those uses are appealing, but governance is the gating question, and MCP provides little of it on its own. Enterprises split into two camps: those building their own access control, audit logging, and middleware now because they can't wait, and those holding sensitive workloads back until the protocol matures.</p><p>Two traits define MCP's shape, and both resurface when you weigh it against A2A. First, the interaction is hierarchical: an agent calls down to a passive server that answers and waits. Second, there's no built-in discovery; you point each client at a preconfigured server endpoint.</p><div><p><img alt=\"Redis Iris\" src=\"https://cdn.sanity.io/images/sy1jschh/production/82df1fa7f210a2b005d5ebbf3429a53a0ebccce0-64x64.svg\"></p><div><h2>The protocol debate, minus the marketing</h2><p><span>A panel of agent-infrastructure engineers on how the two protocols fit together.</span></p></div></div><h2><strong>What A2A does &amp; where it came from</strong></h2><p>That hierarchical, preconfigured model is exactly what A2A isn't. A2A is built for communication between independent, potentially opaque agents owned by different teams, vendors, or companies. It defines three core pieces:</p><ul><li><strong>Agent Cards:</strong> <a target=\"_blank\" href=\"https://a2a-protocol.org/latest/topics/key-concepts\">JSON documents</a> served at /.well-known/agent.json that declare an agent's identity, endpoint, authentication requirements, and skills.</li><li><strong>Tasks:</strong> stateful units of work with a defined lifecycle, including human-in-the-loop pauses.</li><li><strong>Artifacts:</strong> the concrete outputs a remote agent returns.</li></ul><p>Like MCP, A2A runs JSON-RPC 2.0 over HTTP, but it adds Server-Sent Events (SSE) streaming and push notifications for tasks that can run for hours or days.</p><p>Google introduced A2A, then donated it to the Linux Foundation in June 2025 with founding members including AWS, Microsoft, Salesforce, and SAP. One year in, <a target=\"_blank\" href=\"https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year\">more than 150 organizations</a> supported the standard, and it had landed in major cloud and agent platforms.</p><p>For all that surface adoption, A2A is still mostly exploratory in practice. Real cross-organization, cross-framework agent traffic remains rare, and most systems described as \"multi-agent\" today are really one team's orchestrator calling tools in sequence, not independent agents crossing a trust boundary. That gap between ambition and practice is worth keeping in mind.</p><h2><strong>Complementary, not competing</strong></h2><p>None of this makes the two protocols rivals. A2A complements MCP by drawing a line between agents partnering on tasks and agents using capabilities. That tool-vs-agent split shapes the dimensions that typically drive architecture decisions:</p><div><table><thead><tr><th><span>Dimension</span></th><th><span>MCP</span></th><th><span>A2A</span></th></tr></thead><tbody><tr><td><span>Purpose</span></td><td><span>Agent-to-tool integration</span></td><td><span>Agent-to-agent collaboration</span></td></tr><tr><td><span>Communication model</span></td><td><span>Client-server; agent calls a passive tool</span></td><td><span>Peer-to-peer; agent delegates to another agent</span></td></tr><tr><td><span>Interaction pattern</span></td><td><span>Request-response per the spec (servers may hold state)</span></td><td><span>Stateful, multi-turn, long-running tasks</span></td></tr><tr><td><span>Discovery</span></td><td><span>Explicitly configured endpoints</span></td><td><span>Agent Cards at a well-known URL</span></td></tr><tr><td><span>Core primitives</span></td><td><span>Tools, resources, prompts</span></td><td><span>Tasks, messages, artifacts, Agent Cards</span></td></tr></tbody></table></div><p>The split looks like an auto repair shop: a customer's agent talks to the shop manager agent over A2A, the manager runs a multi-turn diagnostic conversation with a mechanic agent over A2A, and the mechanic invokes its diagnostic tools over MCP. With MCP under the Agentic AI Foundation and A2A under the Linux Foundation, the governance story is converging too.</p><p>In practice, the tool-versus-agent line is blurrier than the table suggests. Ask an assistant to shorten a paragraph in a shared document: it sounds like a simple tool call. But to make the edit, the document's API needs to know a document ID, a section ID, and where in the text to cut, none of which the user provided. The \"tool\" has to work those out on its own, which is the kind of reasoning we associate with agents. What you label a component matters less than what the task actually requires of it.</p><h2><strong>The real question: do you own your agents?</strong></h2><p>The question that trips teams up is easy to ask and easy to get wrong: should we be using A2A? A2A gets read as the multi-agent protocol, so any system with more than one agent starts to feel like it needs one. It usually doesn't. A network protocol like A2A adds real cost in setup, authentication, and moving parts, and that cost only pays off when your agents have to work with software you don't own or control. Inside a codebase you do own, a framework like <a target=\"_blank\" href=\"https://redis.io/blog/ai-agent-orchestration-platforms/\">LangGraph or CrewAI</a> can coordinate your agents without a protocol in the middle.</p><p>A2A's design backs this up. The protocol is built so agents can work together without exposing their \"internal memory, <a target=\"_blank\" href=\"https://a2a-protocol.org/latest/\">tools, or proprietary logic</a>\" to each other. That secrecy is the whole point when you're handing work to a partner's agent or a vendor's black box. When you own the agent on the other side, there's little to hide, so you pay the protocol's overhead without getting much interoperability in return.</p><p>So the useful question isn't how many agents you have, but whether they cross a real boundary. Do they sit behind separate security and permission scopes, or do they all run under one team's control? Several agents built by the same team, sharing the same permissions, rarely need a formal protocol between them. A2A earns its place when an agent brings its own identity and permissions that yours has to respect, not simply when there's more than one agent in play.</p><p>None of this is a knock on A2A; it's about fit. The case for it is strongest exactly where simple tool-calling breaks down: work that hands off between agents asynchronously, waits on human approval, or runs as a long back-and-forth instead of a single request and response. Large teams tend to land here in practice. LinkedIn, for one, adopted MCP and A2A together for its enterprise agents while still treating A2A as <a target=\"_blank\" href=\"https://www.infoq.com/news/2025/09/linkedin-multi-agent\">the more experimental</a> of the two.</p><p>So it comes down to one question: who owns the agents? That splits the decision two ways:</p><ul><li><strong>Reach for A2A</strong> when work delegates across a boundary you don't control and neither side can expose internal tools or memory, when tasks run long enough to need a stateful lifecycle with approval gates, or when agents on different frameworks must interoperate without custom glue.</li><li><strong>Stick with in-framework orchestration</strong> when all your agents are white-box components in a codebase you own. That's a classical orchestration problem, not an interoperability one.</li></ul><p>Like most architecture guidelines, this one bends with your workload, but it catches the common mistake: adopting a cross-organization protocol for a single-team system.</p><h2><strong>The problems neither protocol fully addresses</strong></h2><p>Whichever side of that line you land on, both protocols leave the same work to you. They carry messages between agents; they don't manage the state, visibility, speed, or memory underneath.</p><h3><strong>Correlating state across a workflow</strong></h3><p>Neither spec ties the pieces of a workflow together. Even with A2A's contextId for grouping related tasks, nothing links an agent's internal context, MCP server state, and A2A task identifiers into one traceable thread. It's part of a broader class of multi-agent problems: task allocation, <a target=\"_blank\" href=\"https://arxiv.org/html/2601.11369v2\">context management, and memory</a> all get harder than they are in single-agent designs.</p><h3><strong>Observability &amp; performance</strong></h3><p>Watching what your system does gets harder too. Once one agent starts calling others, it's tough to tell which agent or tool actually produced a given answer, and the more they call each other, the tougher it gets. Agents are also less predictable than a plain tool, so even confirming that one ran and did its job well is real work. And piecing together a single, end-to-end picture of what happened across both MCP and A2A is still something every team hacks together on its own.</p><p>Speed is the other half of this. In one analysis of agent workloads, the model's own thinking took <a target=\"_blank\" href=\"https://arxiv.org/html/2506.04301v2\">69.4% of the time</a> on average, and running tools took another 30.2%. You can't overlap the two much, since each waits on the other. MCP adds its own catch: every tool you connect has to be described to the model, and those descriptions eat into its context window. Past a point, adding more tools <a target=\"_blank\" href=\"https://redis.io/blog/from-reasoning-to-retrieval-solving-the-mcp-tool-overload-problem\">makes agents worse</a>, not better, with the model picking the wrong tool more often and responses slowing down and costing more.</p><h3><strong>No standard for agent memory</strong></h3><p>There's also no common interface for agent memory itself. Teams improvise how agents store and recall state, and whether that memory is a flat file or something more structured, because no protocol standardizes it. That's the layer that decides whether work survives a crash or a returning user, and it sits below whichever protocol carries the messages.</p><h3><strong>Where Redis fits</strong></h3><p><a target=\"_blank\" href=\"https://redis.io/iris/\">Redis Iris</a> is built for exactly this layer: a real-time context engine that sits between your agents and the data they act on, on the same Redis many teams already use for <a target=\"_blank\" href=\"https://redis.io/blog/cache-layer-architecture-guide/\">caching and sessions</a>. Reach for A2A when your agents cross a boundary you don't own, and lean on orchestration and shared state when they don't.</p><p>Either way, the protocol only moves the messages.
