contentHtml: "<div><p>Your monitoring looks fine but your answers are getting worse. That pairing is common in AI apps, because retrieval and serving systems are usually built to degrade gracefully under load: search a cached subset instead of the full index, fall back to a cheaper ranking model, skip the reranking step. Requests still succeed, so error rates stay flat. The answers behind them are just built on thinner context than they should have been. Latency is what connects those two facts, which is why it's worth tracking as a measure of answer quality rather than only of speed.</p><p>The stakes climb with every hop. A single request now touches a vector embedding model, a <a target=\"_blank\" href=\"https://university.redis.io/course/i3fv2hbhqnpni8\">vector index</a>, maybe a reranker, one or more LLM calls, and a handful of tools, each one adding latency and each one a place where the pipeline can start trading accuracy for availability. This guide covers what latency means in an AI network, where it hides, what to instrument, and how a faster retrieval layer helps keep it in check.</p><h2><strong>What latency in an AI network actually means</strong></h2><p>Before you can monitor latency, it helps to stop thinking of it as one number. LLM serving splits latency into several metrics, and each one tells you about a different phase of the pipeline.</p><ul><li><strong>Time to first token (TTFT):</strong> The elapsed time from request submission until the first output token arrives. It usually includes request queuing, prefill, and network latency, so longer prompts mean longer TTFT.</li><li><strong>Inter-token latency (ITL):</strong> The gap between consecutive output tokens during generation. This is what makes a streaming response feel smooth or stuttery, and for chat interfaces it should stay near or below normal reading speed.</li><li><strong>End-to-end latency:</strong> The full request path, wrapping around both prefill and decode plus everything else the request touches.</li><li><strong>Tail latency (P95/P99):</strong> What your slowest users actually experience.</li></ul><p>Two phases sit behind those first two metrics: prefill and decode. Prefill reads your whole prompt in one pass, so longer prompts cost more. Decode then writes the answer one token at a time. The two matter separately because each slows down for different reasons under load.</p><p>Tails matter most here, because a deployment can hold a healthy median while <a target=\"_blank\" href=\"https://arxiv.org/html/2510.14392v1\">one request in a hundred</a> waits nearly two seconds for its first token. That's why teams set a target per metric instead of watching one number: hold TTFT under half a second, hold inter-token latency in the tens of milliseconds, and a regression in one can't hide inside the other.</p><div><p><img alt=\"Redis Iris\" src=\"https://cdn.sanity.io/images/sy1jschh/production/82df1fa7f210a2b005d5ebbf3429a53a0ebccce0-64x64.svg\"></p><div><h2>Redis Iris serves agent context in milliseconds</h2><p><span>Redis Iris connects memory, live data, and retrieval in one place.</span></p></div></div><h2><strong>Why latency is a correctness property, not just speed</strong></h2><p>Those targets exist because latency and answer quality are linked. When an AI system runs out of time, it rarely fails outright; it just quietly hands back a worse answer.</p><p>This is a site reliability engineering (SRE) problem. Overloaded search systems often degrade gracefully by searching a <a target=\"_blank\" href=\"https://sre.google/sre-book/addressing-cascading-failures\">subset of data</a> in an in-memory cache instead of the full on-disk store, or by switching to a faster but less accurate ranking algorithm. Retries make things worse in a different way, because retried requests can amplify server overload into cascading failures.</p><p><a target=\"_blank\" href=\"https://university.redis.io/course/ihjs7iip0gpkrw\">Retrieval-augmented generation (RAG)</a> pipelines carry the same tradeoff in the retrieval step. Approximate nearest-neighbor indexes, caching, and lighter-weight retrievers can <a target=\"_blank\" href=\"https://arxiv.org/html/2507.18910v1\">lower latency</a> at the cost of some accuracy. And when retrieval gets less precise, the model works from worse context, so even small drops can <a target=\"_blank\" href=\"https://arxiv.org/html/2511.12869v1\">produce wrong answers</a>.</p><p>Agents show the failure even more directly. In a multi-agent benchmark, a self-correcting architecture kept its accuracy advantage while throughput stayed under roughly 25,000 documents per day. Past that volume, <a target=\"_blank\" href=\"https://arxiv.org/html/2603.22651v1\">timeout constraints</a> cut short the correction iterations the architecture depended on, and most of its advantage over a simpler pipeline disappeared. The system didn't crash. It just got dumber.</p><p>For teams that define service level objectives (SLOs), a missed latency target counts as a failed request, not just a slow one. A slow answer and a wrong answer end up in the same bucket.</p><h2><strong>Where latency hides in the system</strong></h2><p>If slowness degrades quality, the next question is where it accumulates. In an AI pipeline the answer tends to be several places at once, and rarely where you'd guess. The usual suspects are retrieval, model-and-tool execution, and the cross-service hops between them.</p><h3><strong>The retrieval layer</strong></h3><p>Retrieval eats a bigger share of the budget than most teams expect. In one characterization study of RAG serving pipelines, retrieval <a target=\"_blank\" href=\"https://arxiv.org/html/2412.11854v1\">accounted for 41%</a> of end-to-end latency. That share is spread across stages that behave differently under load.</p><p>Vector embedding generation swings with concurrency, because queueing turns a fast embedding request into a slow one even when the model and input haven't changed.</p><p>Reranking is usually the biggest variable. Cross-encoder rerankers score query-document pairs more deeply than first-pass retrieval, so cost scales with how many candidates you feed them. The same step can be trivial or dominant depending on candidate count, batching, and hardware, and you won't know which you're paying without measuring it separately.</p><h3><strong>Model inference &amp; tool calls</strong></h3><p>Downstream of retrieval, the model and its tools take over, and the balance shifts with the workload. In agentic coding tasks, tool execution can <a target=\"_blank\" href=\"https://arxiv.org/html/2603.18897v1\">dominate the budget</a> instead, because data dependencies force generation and tool calls to run in sequence. Your bottleneck won't necessarily match anyone else's published breakdown, which is the argument for measuring your own.</p><p>Agent workflows take this furthest. A real agent turn often involves several LLM hops plus tool calls, which stack up latency well beyond what per-API benchmarks suggest. Request-level metrics quietly lie to you here: they <a target=\"_blank\" href=\"https://arxiv.org/html/2502.13965v1\">overlook end-to-end latency</a> for agentic programs, which is why some teams measure at the program level instead.</p><h3><strong>Cross-service hops</strong></h3><p>Then there's the plumbing between services, where fan-out multiplies tail latency. Say a server is slow on 1% of requests (a 1-second P99). A request that fans out to 100 such servers finishes only when the slowest one returns, so it's slow if even one of them is. That pushes the odds of a slow request to <a target=\"_blank\" href=\"https://cacm.acm.org/research/the-tail-at-scale\">63%</a>: a 1-in-100 problem per server becomes nearly 2-in-3 for the whole request.</p><p>AI pipelines are exactly this kind of fan-out system: embedding service, vector index, feature store, model gateway, tool APIs. Every remote procedure call adds serialization, transport, and queueing overhead, and minor variations in communication patterns can <a target=\"_blank\" href=\"https://arxiv.org/pdf/2404.06581\">shift the bottleneck</a> between data transformation, the network stack, and HTTP header processing.</p><div><p><img alt=\"Redis Vector Database\" src=\"https://cdn.sanity.io/images/sy1jschh/production/ba774ea6ad5d6bf132ab3ef194b6a1ad7d7c914f-64x64.svg\"></p><div><h2>Build agents that remember, not agents that guess</h2><p><span>Redis Iris gives every agent fresh context and long-term memory.</span></p></div></div><h2><strong>What to monitor</strong></h2><p>Knowing where latency hides tells you what to instrument. Two bodies of guidance help here: OpenTelemetry's GenAI conventions and the SRE golden signals.</p><p>OpenTelemetry's GenAI semantic conventions define named metrics for AI workloads, though all GenAI metrics are currently experimental. A few signals are worth wiring up first:</p><ul><li>gen_ai.client.operation.duration: a histogram of LLM call latencies you can filter by model.</li><li>gen_ai.server.time_per_output_token: decode-phase latency, calculated by subtracting time to first token from request duration and dividing by remaining output tokens.</li></ul><p>The spec isn't complete, though. Some useful signals, like a client-side view of time to first token, still aren't standardized, so production teams track those themselves.</p><p>This is where reliability practice helps. Latency is the first of the four <a target=\"_blank\" href=\"https://sre.google/sre-book/monitoring-distributed-systems\">golden signals</a> SRE teams watch, and one rule matters even more for streaming AI apps: measure how slow your failed requests are, not just your successful ones. A slow failure hurts more than a fast one.</p><p>When you watch latency, look at percentiles, not the average. Averages hide your slowest users. One Google service averaged around 50 ms, but <a target=\"_blank\" href=\"https://sre.google/sre-book/service-level-objectives\">5% of requests</a> ran 20 times slower, and average-based monitoring showed no change. The median (P50) tells you the typical experience; the tail (P95 and P99) tells you the worst.</p><p>And if you're running a RAG pipeline, measure each retrieval step on its own: embedding, search, and reranking. Seen separately, a single slow stage stands out instead of hiding inside one end-to-end number, so you catch it early.</p><h2><strong>How a faster retrieval layer keeps latency in check</strong></h2><p>Monitoring tells you where the budget goes; a faster retrieval layer is often how you claw it back. In AI apps, that usually means shrinking retrieval before it forces compromises later. Two techniques do most of the work: <a target=\"_blank\" href=\"https://redis.io/docs/latest/develop/ai/context-engine/langcache/\">semantic caching</a> and low-latency vector search.</p><p>Semantic caching creates a vector embedding for each incoming query and checks whether a semantically similar prompt has already been answered. If the similarity score clears a threshold, the cached response comes back without a new LLM call, which takes retrieval <a target=\"_blank\" href=\"https://arxiv.org/html/2603.02206v1\">close to zero</a> on a hit. The number that decides whether that matters is your hit rate: repetitive FAQ-style traffic caches well, open-ended conversation doesn't, so measure the rate before you budget for the benefit.</p><p>This is where <a target=\"_blank\" href=\"https://redis.io/docs/latest/develop/ai/context-engine/\">Redis Iris</a> comes in. On the caching side, LangCache benchmarks report up to <a target=\"_blank\" href=\"https://redis.io/blog/context-window-management-llm-apps-developer-guide/\">15x faster responses</a> for cache hits and up to <a target=\"_blank\" href=\"https://redis.io/blog/llm-token-optimization-speed-up-apps/\">73% lower</a> LLM inference costs.</p><div><p><img alt=\"Redis Cloud\" src=\"https://cdn.sanity.io/images/sy1jschh/production/5f60e1427a8be962bb08ee8764c012b5e1f654f4-64x64.svg\"></p><div><h2>Fresh context, every call</h2><p><span>Redis Iris keeps agent data current so answers stay accurate.</span></p></div></div><h2><strong>Latency monitoring is a reliability requirement, not a dashboard</strong></h2><p>None of this works as a wall of charts someone glances at on Fridays. SRE practice formalizes <a target=\"_blank\" href=\"https://university.redis.io/course/sdm9uvjmd0iedp\">latency monitoring</a> through service level indicators (SLIs), SLOs, and error budgets. That formalization matters.</p><p>Request latency is a standard SLI, usually with layered thresholds: a loose one covering most requests and a stricter one covering the tail. The error budget is 100% minus the SLO, and burning it has consequences. Exhausting the budget can trigger a <a target=\"_blank\" href=\"https://sre.google/static/pdf/SloAdoptionAndUsageInSre.pdf\">30-day feature freeze</a> where only reliability fixes ship to production. Alerts hang off budget burn rate rather than raw thresholds, so a slow drift and a sudden spike both surface right away.</p><p>Production AI teams already treat latency this way. GitHub cut Copilot's default toolset from 40 tools to 13 and measured a <a target=\"_blank\" href=\"https://github.blog/ai-and-ml/github-copilot/how-were-making-github-copilot-smarter-with-fewer-tools\">400 millisecond reduction</a> in average latency in A/B testing. Removing capability to protect a latency budget is a product decision that starts as a reliability one.</p><h2><strong>Keep latency in check with Redis Iris</strong></h2><p>Latency in an AI network is a family of signals: TTFT, inter-token latency, end-to-end duration, and tail percentiles. When any of them slips, systems tend to degrade quality to stay available: shallower retrieval, truncated agent iterations, timed-out context.
