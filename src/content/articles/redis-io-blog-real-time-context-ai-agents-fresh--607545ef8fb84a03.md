contentHtml: "<div><p>Your AI agent issued the refund. It read the customer's tier, checked the return window, confirmed the policy, and processed it in seconds. The problem: the return window had closed four minutes earlier when a batch job updated the order status, and the agent was reading a snapshot from before the change. Now you have a refund you can't reverse, a policy exception you didn't approve, and no error log to point at.</p><p>This is the shift that catches teams off guard as they move from <a target=\"_blank\" href=\"https://redis.io/blog/ai-agent-orchestration-platforms/\">agentic systems</a> that answer questions to ones that take actions. A stale answer is embarrassing. A stale action writes to your database, calls your payment provider, or triggers a downstream workflow that another agent will read as ground truth ten seconds later. Staleness stops being a quality issue and becomes a state-management issue, and it compounds fastest in the systems you're most likely to build next: multi-step agents whose outputs feed other agents' inputs. This article covers why agents act on outdated information even when retrieval succeeds, which parts of an agent's context have to stay current between steps, why getting fresh data in is only half the problem, and where a real-time context engine fits underneath the agent loop.</p><h2><strong>Why agents act on stale data even when retrieval \"worked\"</strong></h2><p>The failure starts with a simple mismatch: retrieval working and context being fresh aren't the same thing. One agent-memory <a target=\"_blank\" href=\"https://arxiv.org/html/2605.06527v1\">diagnostic study</a> tested how well long-term memory systems surface up-to-date information when facts change over time, measuring whether retrieval prioritizes the latest version of an entry or serves whatever ranks highest by similarity. The top-3 recalled memory entries still contained old evidence 60.5% of the time, and only 3.3% of those old entries were flagged as needing an update. Stale and updated memories sit side by side with nothing telling the agent which one to trust, which means outdated evidence stays visible even after newer evidence shows up.</p><p>That's one way stale context sneaks in. There are several more, and they stack on top of each other:</p><ul><li><strong>Cached answers skip the live tool.</strong> Session memory can return a previous answer without re-invoking the tool that was supposed to fetch live data, so the agent responds from a snapshot while believing it checked. Cache invalidation is hard enough in apps; in agents, a cached answer also skips a decision point.</li><li><strong>Prompt caching keeps its own clock.</strong> Anthropic prompt caching entries have a cache lifetime of about five minutes, refreshed each time the cached content is used, so cached context gets re-served even if the underlying data changed a second later.</li><li><strong>Early errors turn into ground truth.</strong> Agents build each step on the history of previous steps, so a stale fact absorbed early gets integrated into state instead of isolated, and every later step builds on it as if it were fact.</li><li><strong>Truncation drops context silently.</strong> When the prompt exceeds the token limit, many frameworks trim older content with no error raised, and the model answers from an incomplete picture.</li></ul><p>None of these are retrieval bugs in the classic sense. The retriever did what it was asked. The system just wasn't given a reliable way to separate fresh information from stale information, or it never asked for fresh information to begin with.</p><div><p><img alt=\"Redis Iris\" src=\"https://cdn.sanity.io/images/sy1jschh/production/82df1fa7f210a2b005d5ebbf3429a53a0ebccce0-64x64.svg\"></p><div><h2>Redis Iris serves agent context in milliseconds</h2><p><span>Redis Iris connects memory, live data, and retrieval in one place.</span></p></div></div><h2><strong>Freshness is a context engineering problem, not just a RAG problem</strong></h2><p>These failure modes point to a bigger idea: the fix lives above retrieval, in how the whole context window gets managed. Context engineering is the practice of <a target=\"_blank\" href=\"https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents\">curating and maintaining</a> the right set of tokens during LLM inference, meaning everything that lands in the context window, not just the prompt. Those strategies fall into four categories:</p><ul><li><strong>Write:</strong> saving context outside the window so it can be recalled later.</li><li><strong>Select:</strong> pulling the right context into the window at the right time.</li><li><strong>Compress:</strong> keeping only what's needed as context accumulates.</li><li><strong>Isolate:</strong> splitting context across sub-agents or scoped memory.</li></ul><p>Retrieval-augmented generation (RAG) mostly handles the select step. You can have a perfectly tuned retriever and still ship stale context, because freshness failures happen in what gets written, what gets kept, and what conflicts with what. Staleness is what makes those failures show up as recognizable patterns:</p><ul><li>Context poisoning is when a bad fact keeps getting referenced.</li><li>Context distraction is when long history pulls focus away from the current task.</li><li>Context confusion is when irrelevant content degrades the response.</li><li>Context clash is when a fresh fact and a stale fact sit together with no trust signal.</li></ul><p><a target=\"_blank\" href=\"https://redis.io/blog/context-rot\">Context-length tests</a> show a related effect: as token count grows, accuracy and recall degrade well before you hit the window limit, and stale entries add to that pressure when they stick around in the prompt.</p><h2><strong>What has to update in real time</strong></h2><p>If freshness is a context engineering problem, the next question is which parts of an agent's context actually need to stay current between steps. It's more than the vector index. Six components carry freshness requirements:</p><ul><li><strong>Working memory:</strong> the active state inside the context window during a run. LangGraph reads this state <a target=\"_blank\" href=\"https://docs.langchain.com/oss/python/langchain/short-term-memory\">at each step</a> and updates it when the step completes, so anything stale at the start of a step stays stale for that step.</li><li><strong>Session state:</strong> the saved conversation thread across turns. The OpenAI Agents SDK <a target=\"_blank\" href=\"https://openai.github.io/openai-agents-python/sessions\">prepends session history</a> to the input before each run and stores new items after, so whatever sits in that store is what the agent sees.</li><li><strong>Long-term memory:</strong> the facts and preferences carried across sessions. Combining a memory tool with context editing <a target=\"_blank\" href=\"https://www.anthropic.com/news/context-management\">improved performance by 39%</a> over baseline in an internal agentic search evaluation, which suggests actively managing this tier pays off.</li><li><strong>Tool results:</strong> the live external data pulled in at invocation time. Clearing already-used tool results is a common light-touch form of compaction, because a result that's already been consumed is noise on the next step.</li><li><strong>Retrieved documents:</strong> the RAG index that snapshots your sources at last ingestion. Many batch pipelines refresh on hourly or daily schedules, so teams often turn to <a target=\"_blank\" href=\"https://redis.io/blog/knowledge-graph-rag-structured-retrieval-ai-agents\">change data capture</a> and incremental, near-real-time updates instead of periodic rebuilds.</li><li><strong>Machine learning (ML) features:</strong> the pre-computed signals about users, products, or devices. Online feature stores often serve dozens of features per inference call inside a <a target=\"_blank\" href=\"https://redis.io/docs/latest/develop/use-cases/feature-store\">millisecond request budget</a>, depending on workload, while batch and streaming pipelines update those same features on very different cadences.</li></ul><p>Each component fails differently when it goes stale. Stale working memory buries the current task. Stale session state serves yesterday's answer. Stale features leave a fast model reasoning over a slow-moving view of the world. Treating all six as one undifferentiated \"context\" is how freshness problems hide.</p><div><p><img alt=\"Redis Vector Database\" src=\"https://cdn.sanity.io/images/sy1jschh/production/ba774ea6ad5d6bf132ab3ef194b6a1ad7d7c914f-64x64.svg\"></p><div><h2>Build agents that remember, not agents that guess</h2><p><span>Redis Iris gives every agent fresh context and long-term memory.</span></p></div></div><h2><strong>Getting fresh data in is only half the problem</strong></h2><p>Keeping those six components updated is the write path, and a lot of teams stop there. But a system can have a fast ingestion pipeline and still fail the agent, because the agent needs to read fresh state before each step, and <a target=\"_blank\" href=\"https://redis.io/blog/database-performance-optimization-guide/\">read latency</a> compounds in a way single-query systems never prepared us for.</p><p>To see why read latency matters, look at how often agents actually read. Every iteration of an agent loop re-reads context, memory, and tool results before deciding the next action, and the iteration count adds up fast. One data-question-agent benchmark measured <a target=\"_blank\" href=\"https://arxiv.org/html/2603.20576v1\">6.1 iterations</a> and 7.3 tool calls per request for GPT-5.2, with the hardest queries pushing that to 17.6 tool calls and one model averaging over 60 tool calls on its hardest query. That's dozens of reads per user request, and each one has to hit fresh state to be worth doing.</p><p>Those reads dominate the latency budget, and the numbers show why freshness checks can't be a free operation. One benchmark measured an agentic RAG pipeline at <a target=\"_blank\" href=\"https://arxiv.org/html/2607.07858v1\">4.72 seconds</a> end-to-end against a 1.64-second single-LLM baseline, with the loop itself driving the difference. In another analysis, tool execution alone accounted for <a target=\"_blank\" href=\"https://arxiv.org/html/2603.18897v1\">60% of latency</a> in coding tasks. Both point to the same thing: the read path, not the model, is where agent time goes.</p><p>That's the trap. An agent that reads session context and long-term knowledge at every step pays that retrieval latency multiplied by the iteration count, so a read path that's \"fast enough\" for a single query becomes the bottleneck when the agent hits it dozens of times per task. Teams notice the slowdown and respond by caching more aggressively or skipping freshness checks—which is exactly how stale context sneaks back in. Fast reads aren't a nice-to-have; they're what makes checking for fresh state on every step affordable in the first place.</p><p>So real-time context has two halves. Fresh data has to flow in continuously, and reads have to be fast enough that checking for fresh data on every step doesn't blow the latency budget. Skip the first half and you get confident wrong answers.
