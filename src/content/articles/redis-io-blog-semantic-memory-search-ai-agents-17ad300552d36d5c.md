contentHtml: "<div><p>Your <a target=\"_blank\" href=\"https://redis.io/blog/what-is-an-ai-agent/\">AI agent</a> handles a long onboarding conversation. The next day, it asks the same user for their name. That's not a bug. A language model keeps no memory of earlier calls, so without an external memory layer, each request starts fresh and the agent forgets what it just learned. Semantic memory search gives agents durable recall instead, with facts stored outside the model and retrieved by meaning when the app invokes memory search. Below, we cover what semantic memory search is, why keyword search often falls short, and why speed and freshness determine whether memory helps or hurts.</p><p>Semantic memory search is how an agent retrieves facts from a long-term store by meaning rather than exact wording. It has two parts: semantic memory (the store) and the search process that pulls from it when the app needs context.</p><p>Start with the store, a long-term collection of facts about the user and the agent's domain, like preferences, prior decisions, and background details worth carrying forward. In the standard reference architecture for language agents, semantic memory is the store of <a target=\"_blank\" href=\"https://arxiv.org/html/2309.02427v3\">\"facts about the world\"</a>, which in practice means facts about a user and their domain.</p><p>Retrieval comes next. To make those facts retrievable by meaning, apps commonly represent them as vector embeddings: numerical representations where two pieces of text with similar meanings get mathematically similar vectors, even when the actual words differ. On the write side, the app extracts a fact from a conversation, embeds it, and stores the vector in a <a target=\"_blank\" href=\"https://redis.io/redis-for-ai/\">vector database</a> alongside metadata like timestamps and the source message. On the read side, the app embeds the incoming query, runs a similarity search against the stored vectors, and passes the closest matches to the LLM as context.</p><div><p><img alt=\"Redis Iris\" src=\"https://cdn.sanity.io/images/sy1jschh/production/82df1fa7f210a2b005d5ebbf3429a53a0ebccce0-64x64.svg\"></p><div><h2>Redis Iris serves agent context in milliseconds</h2><p><span>Redis Iris connects memory, live data, and retrieval in one place.</span></p></div></div><p>It's worth being precise about the layers here. The database stores, indexes, and retrieves vectors; the app decides what to remember and when to look it up. This pattern is already common in production, where many AI-native apps use some form of vector-based retrieval before inference to surface context for the agent.</p><h2>Why AI agents forget without a memory layer</h2><p>That retrieval layer exists because the model itself doesn't retain context between calls. Unless the app or a provider-managed conversation service persists and resupplies that state, the next call starts without it. An external memory entry, by contrast, can survive across sessions.</p><h3>Conversation history doesn't persist between calls</h3><p>The app must supply all session-specific information in the model's current context or let the model retrieve it through tools, so the obvious workaround is to keep re-sending history. That approach runs into three problems as agents scale:</p><ul><li><strong>The ceiling is finite.</strong> Context windows are large but finite. When input exceeds the limit, Anthropic's API returns a <a target=\"_blank\" href=\"https://docs.anthropic.com/en/docs/build-with-claude/context-windows\">400 invalid_request_error</a> rather than trimming gracefully.</li><li><strong>You pay for it every turn.</strong> You pay for <a target=\"_blank\" href=\"https://platform.openai.com/docs/guides/conversation-state\">every previous input token</a> on every request in a chain, so carrying full history gets more expensive the longer the relationship lasts.</li><li><strong>Recall degrades before you hit the limit.</strong> Accuracy tends to drop as token count grows. Models also struggle with information buried in the <a target=\"_blank\" href=\"https://arxiv.org/abs/2307.03172\">middle of long contexts</a>, and performance <a target=\"_blank\" href=\"https://arxiv.org/html/2510.05381v1\">degraded 13.9%–85%</a> across one multi-model evaluation as input length grew, even when the models could retrieve every relevant fact.</li></ul><p>Stuffing everything into context also invites two related failure modes: <a target=\"_blank\" href=\"https://redis.io/blog/context-engineering-best-practices-for-an-emerging-discipline/\">context distraction</a>, where a model over-focuses on a long context, and <a target=\"_blank\" href=\"https://redis.io/blog/quality-context-ai-agents/\">context confusion</a>, where superfluous information drags down response quality. Selective retrieval from an external memory store helps address these problems by aiming to surface a smaller set of relevant facts instead of the whole history.</p><h2>How semantic search recalls by meaning, not keywords</h2><p>An external store only helps if the agent can find the right memory when it matters, and that's where keyword search tends to fall short. Lexical ranking methods like Best Matching 25 (BM25) score documents on term overlap, so the same idea expressed in different words can produce zero matches.</p><p>Agent memory hits this constantly. A user says \"I'm stressed about money\" in one session and \"worried about finances\" weeks later. There's no keyword overlap, yet semantic search maps both phrases to nearby vector positions and retrieves the earlier memory anyway. That doesn't make keyword search obsolete: it still performs better for exact identifiers, product codes, and rare domain terms, which vector embeddings tend to handle poorly. Because each mode covers the other's blind spots, many production systems run hybrid search, combining vector similarity with full-text ranking and metadata filters so no single miss breaks retrieval.</p><h3>Semantic vs. episodic &amp; procedural memory in AI agents</h3><p>Semantic memory is one of three long-term memory types agents typically use. They differ in what they preserve and how they shape behavior:</p><ul><li><strong>Semantic memory</strong> stores facts, like user preferences and domain knowledge.</li><li><strong>Episodic memory</strong> stores experiences, like how the agent solved a problem before, often captured as examples distilled from longer interactions.</li><li><strong>Procedural memory</strong> stores instructions: the combination of agent code, model weights, and prompts that determines how the agent behaves.</li></ul><p>Which type matters most depends on the agent. Personal assistants often lean on semantic memory for user preferences and profiles, while software engineering agents may also rely on procedural memory like verified code patterns.</p><h2>Why memory search must be fast &amp; fresh</h2><p>Knowing what to retrieve is half the problem. The other half is doing it quickly enough, with data current enough, that memory improves the answer instead of degrading it.</p><h3>Memory retrieval can run on every agent turn</h3><p>Memory search isn't always an occasional lookup. In systems configured to consult memory on each turn, retrieval runs before one or more LLM calls, and a multi-step agent may retrieve many times per task, so retrieval latency gets multiplied rather than paid once. For many interactive interfaces, 0.1-second responses <a target=\"_blank\" href=\"https://www.nngroup.com/articles/response-times-3-important-limits\">feel instantaneous</a>, while delays approaching one second start to interrupt a user's flow. Voice agents push the bar further. Some evaluations target <a target=\"_blank\" href=\"https://arxiv.org/html/2603.02206v1\">sub-200-millisecond latency</a> to support natural turn-taking. The acceptable threshold varies by interface and pipeline.</p><p>When retrieval runs on every turn, the data layer underneath it has to keep up, and that's where Redis fits. For many core data operations, it supports sub-millisecond latency: in an Amazon Web Services (AWS) benchmark of a <a target=\"_blank\" href=\"https://redis.io/blog/redis-enterprise-extends-linear-scalability-200m-ops-sec/\">20-node deployment</a>, Redis reported more than 100 million operations per second at sub-millisecond latency.</p><p>Vector search is a separate question, since raw throughput on core operations doesn't predict it. Latency there depends on the index, dataset, recall target, and deployment. On a <a target=\"_blank\" href=\"https://redis.io/blog/searching-1-billion-vectors-with-redis-8/\">billion-vector dataset</a> retrieving the top 100 nearest neighbors under 50 concurrent queries, Redis reported 90% precision at about 200 milliseconds median latency, round-trip time included. Redis Search also supports hybrid search: <a target=\"_blank\" href=\"https://redis.io/blog/redis-8-4-open-source-ga/\">Redis 8.4's</a> FT.HYBRID fuses full-text relevance and vector-similarity scores in one execution plan and can apply metadata filters, so covering the keyword blind spot doesn't mean standing up a second search system. Redis publishes connectors for the major agent frameworks.</p><div><p><img alt=\"Redis Vector Database\" src=\"https://cdn.sanity.io/images/sy1jschh/production/ba774ea6ad5d6bf132ab3ef194b6a1ad7d7c914f-64x64.svg\"></p><div><h2>Build agents that remember, not agents that guess</h2><p><span>Redis Iris gives every agent fresh context and long-term memory.</span></p></div></div><h3>Why freshness matters as much as speed</h3><p>Fast retrieval only helps if the memory it surfaces is still true, and staleness is a bigger problem than it looks. Users change jobs, cancel orders, update preferences, and drop old habits, so a fact that was accurate last month may quietly poison this month's response.</p><p>Two data points show how easily this slips through. One agent-memory diagnostic found that the top three recalled entries <a target=\"_blank\" href=\"https://redis.io/blog/real-time-context-ai-agents-fresh-inputs\">contained old evidence 60.5%</a> of the time, yet the same diagnostic flagged only 3.3% of those stale entries as needing an update. The memory layer surfaced outdated facts and rarely noticed. Models don't catch it reliably either: the best model evaluated on the memory-validity benchmark STALE reached only <a target=\"_blank\" href=\"https://huggingface.co/papers/2605.06527\">55.2% overall accuracy</a> at recognizing when memories were no longer valid, barely better than a coin flip.</p><p>The takeaway is that freshness has to be handled at the memory layer, not left to the model to sort out at inference time. And the stakes are concrete: an agent approving a refund needs the customer's current order status, not last week's.</p><p>Apps handle this in two ways. They can write memory during a live interaction for immediate availability, or extract it in the background to reduce per-turn latency, accepting a short delay before new facts become available. A background extraction process promotes important information between tiers without blocking the live interaction.</p><h2>How better memory search improves the user experience</h2><p>All of this infrastructure work pays off in something users actually feel: not having to start over.
