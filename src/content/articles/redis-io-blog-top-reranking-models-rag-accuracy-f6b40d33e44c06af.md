contentHtml: "<div><p>Your Slack pings mid-afternoon: a product manager says the <a target=\"_blank\" href=\"https://university.redis.io/course/ihjs7iip0gpkrw\">retrieval-augmented generation (RAG)</a> assistant keeps citing a deprecated API version in its answers to developer questions. You pull the trace and find the retriever grabbed 50 chunks, with the current docs page sitting at position 23, buried under near-misses the LLM latched onto first. Retrieval did its job; ranking didn't. Reranking is one layer in the broader context engineering stack—the infrastructure that assembles the right context for the model at inference time, alongside retrieval, semantic caching, agent memory, and tool outputs. Get the ranking step wrong and the rest of that stack can't compensate. </p><p>This guide covers what a reranker does in a RAG pipeline, the main model types, how to choose between them, and how to keep production costs under control.</p><h2><strong>What a reranker does in a RAG pipeline</strong></h2><p>That buried-at-position-23 problem is exactly what the reranker layer addresses. RAG retrieval typically runs in two stages, each optimizing for something different:</p><ul><li><strong>First-stage retrieval (recall).</strong> A fast, wide sweep across the full corpus that returns a shortlist of candidates (often the top 50 or 100) using cheap scoring like Best Matching 25 (BM25), vector search, or both. It's built for speed, but compressing each document into a single vector or bag of terms loses detail.</li><li><strong>Second-stage reranking (precision).</strong> A slower, more accurate model rescues that shortlist and reorders it so the most relevant chunks sit at the top of the prompt sent to the LLM. It examines a small pool closely and catches distinctions the first stage misses.</li></ul><p>The gains can be large. Cross-encoder rerankers were the approach that first topped the Microsoft MAchine Reading COmprehension (MS MARCO) passage-ranking leaderboard, <a target=\"_blank\" href=\"https://arxiv.org/abs/1901.04085\">outperforming BM25</a> by a wide relative margin. Reranking also works around a known LLM quirk: performance is highest when relevant information sits at the start or end of the context and <a target=\"_blank\" href=\"https://ar5iv.labs.arxiv.org/html/2307.03172\">degrades</a> when it's buried in the middle, a failure mode often called <a target=\"_blank\" href=\"https://redis.io/blog/context-rot\">context rot</a>. Reranking counteracts context rot by moving the best chunks into those high-attention positions. That's what would have rescued the deprecated-API answer: the correct docs page was in the candidate pool at position 23, but without reranking it never reached a position the LLM paid attention to.</p><div><p><img alt=\"Redis Iris\" src=\"https://cdn.sanity.io/images/sy1jschh/production/82df1fa7f210a2b005d5ebbf3429a53a0ebccce0-64x64.svg\"></p><div><h2>Redis Iris serves agent context in milliseconds</h2><p><span>Redis Iris connects memory, live data, and retrieval in one place.</span></p></div></div><h2><strong>The main types of reranking models</strong></h2><p>A few architectures dominate reranking today, and they mostly differ in where they spend your latency and infrastructure budget. Pick based on that trade-off, not leaderboard rank.</p><h3><strong>Cross-encoder rerankers</strong></h3><p>A cross-encoder reads the query and one document together and scores how well they match. Both go into the same transformer, so every query token can \"see\" every document token, and the model spits out a single relevance score for the pair.</p><p>This design shows up across most mainstream rerankers today, including Cohere's and Voyage AI's rerank models, BAAI's bge-reranker family, and Mixedbread's mxbai-rerank family.</p><p>That per-pair cost is why cross-encoders only rank a small pool. Scoring 10,000 sentences pairwise for a clustering task would take a cross-encoder <a target=\"_blank\" href=\"https://sbert.net/examples/cross_encoder/applications/README.html\">about 65 hours</a> to work through roughly 50 million pairs. A bi-encoder generates vector embeddings for the same sentences in about 5 seconds. Smaller cross-encoders soften the cost: cross-encoder/ms-marco-MiniLM-L6-v2 measured 74.30 normalized discounted cumulative gain (nDCG@10) on Text REtrieval Conference Deep Learning 2019 (TREC DL19) and processed <a target=\"_blank\" href=\"https://www.sbert.net/docs/pretrained_cross-encoders.html\">1,800 documents per second</a>.</p><h3><strong>LLM-based rerankers</strong></h3><p>LLM-based rerankers skip the dedicated scoring model and just ask a generative model to order the documents. RankGPT-style approaches feed passages to a general-purpose LLM and ask it to spit out a ranked list, sliding a window across larger candidate sets. Open models like RankZephyr distill that behavior into a smaller model, so you don't need a frontier LLM at query time. The Qwen3 Reranker family, available in 0.6B, 4B, and 8B sizes, scores relevance from the probability of generating \"yes\" versus \"no\" for each pair.</p><p>The trade-off is steep on both speed and cost. LLM rerankers can run substantially slower than a compact cross-encoder, and a general-purpose LLM used as a reranker often makes per-query cost a bigger problem than latency. Zero-shot LLM rerankers also tend to underperform fine-tuned rerankers on out-of-domain data, so \"just use a big LLM\" isn't an automatic win.</p><h3><strong>Late-interaction &amp; multi-vector models</strong></h3><p>Late-interaction models like ColBERT split the difference between the two approaches above. They encode queries and documents into per-token vector sets independently, so document vectors can be precomputed, then score relevance with a cheap maximum-similarity operation at query time. ColBERT reported speedups of <a target=\"_blank\" href=\"https://arxiv.org/abs/2004.12832\">two orders of magnitude</a> over prior BERT-based rankers while staying competitive on quality.</p><p>The catch is storage: you keep a vector for every token in the collection, though residual compression in later versions cuts that footprint sharply. Multilingual variants extend the approach across many languages.</p><h3><strong>Lightweight open-weight vs. API-hosted</strong></h3><p>Cutting across all three architectures is a deployment question: run the model yourself or call an API. The open-weight 0.6B class has gotten good enough to hold its own, often matching rerankers several times its size, so bigger isn't automatically better. API-hosted rerankers save you the infrastructure work, but check licenses before self-hosting an open-weight model, since commercial and non-commercial terms vary across the category.</p><h2><strong>How to choose a reranker</strong></h2><p>Knowing the categories narrows the field. Matching a model to your latency budget, context length, and language coverage gets you down to one or two candidates.</p><h3><strong>Accuracy vs. latency budget</strong></h3><p>Measure reranker latency against your app's budget, not in isolation. Speeds vary a lot: a mid-size cross-encoder usually adds tens to low-hundreds of milliseconds per query, while LLM rerankers can take seconds, depending on how many candidates you're ranking and how big the model is. Numbers also shift with hardware, batch size, and quantization, so treat any published figure as a starting point.</p><p>A few hundred milliseconds is often fine for user-facing chat. Passing fewer, sharper chunks to the LLM shortens generation enough to offset the reranking step, so you often break even on total latency. But hand tests rarely catch the tail latency that shows up with long chunks, busy hardware, and real traffic. Measure on your own workload before you commit.</p><h3><strong>Context length &amp; multilingual needs</strong></h3><p>Model-card limits vary widely across reranker families. Check both the stated maximum and the recommended working context, which is often well below the hard ceiling. If your chunks are around 512 tokens, most mainstream rerankers have plenty of headroom for common RAG workloads. If you're reranking whole pages or transcripts, context length becomes a hard filter.</p><p>Language coverage deserves the same scrutiny. Some hosted and open-weight rerankers are multilingual out of the box. Others (usually smaller open models) cover only one or two languages. Test against your actual query mix, not just what's advertised on the model card.</p><h3><strong>Score calibration</strong></h3><p>Reranker scores rank documents; they don't measure absolute relevance. Neural rankers optimize for relative order, so a 0.7 from one model doesn't mean the same thing as a 0.7 from another. Swap rerankers and any threshold you've set needs recalibrating.</p><p>Domain mismatch makes it worse. A cross-encoder trained on one kind of data and applied to a very different task can score relevant and irrelevant items almost the same, which makes a fixed cutoff meaningless.</p><p>In practice, evaluate score floors alongside top-N cutoffs rather than keeping the same number of chunks for every query. And evaluate on your own data before deploying—reranking doesn't always earn its keep, and a meaningful share of queries see no benefit at all.</p><div><p><img alt=\"Search\" src=\"https://cdn.sanity.io/images/sy1jschh/production/aa307e0dd69103a86569000deb7f7d4a237d7ded-64x64.svg\"></p><div><h2>Turn search into a real-time experience</h2><p><span>Build fast, relevant search with Redis.</span></p></div></div><h2><strong>Reranking only works if retrieval feeds it good candidates</strong></h2><p>Calibration only helps when the right document actually reaches the reranker in the first place. Reranking is bounded by first-stage recall: a reranker can't promote a document that never appears in the candidate pool.</p><p>Candidate quality matters as much as quantity. Adding distracting documents can measurably cut answer accuracy, and deeper pools don't automatically help. Past a certain point, piling on more candidates can pull recall below what retrieval alone would return. The right pool size depends on your corpus, your query patterns, and your reranker.</p><p>One reliable way to raise the recall ceiling is hybrid retrieval: combine keyword and vector search, then fuse the results. A stronger first stage gives the reranker a better candidate pool, and it consistently beats keyword-only or vector-only retrieval on recall.</p><p>All of that (retrieval, reranking, caching) needs a data layer fast enough to run on every request. If you already run Redis for caching or sessions, the reranker's candidate pool lives on infrastructure your team already operates.</p><h2><strong>Keeping reranking affordable in production</strong></h2><p>Once retrieval and reranking work, the last problem is the bill: spend expensive model calls only where they actually improve answers. A few patterns keep per-query cost under control:</p><ul><li><strong>Over-fetch, then truncate.</strong> Retrieve more candidates than you'll pass downstream, rerank the lot, and send only the strongest chunks to the LLM. Tune the number against answer quality and context budget.</li><li><strong>Tier your models.</strong> Some hosted providers offer speed-optimized tiers for lower-risk workloads. Route queries to the cheaper model where your evaluation shows little quality risk.</li><li><strong>Self-host when volume justifies it.</strong> Smaller open-weight rerankers can be practical to self-host when sustained volume keeps the hardware busy and you can absorb the ops overhead.</li><li><strong>Cache repeated queries.</strong> Semantic caching generates vector embeddings for incoming prompts and serves a stored response when a new query is close enough in meaning to a previous one.
