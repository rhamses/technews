contentHtml: "<div><p>If you've shipped an AI agent that connects to tools, you've probably felt the relief of having one standard way to wire it all up. Model Context Protocol (MCP) handles that part well. But there's a gap that catches a lot of teams off guard: your agent can call a tool through MCP, complete the action, and still walk into the next session knowing nothing about what just happened.</p><p>That's not a bug. It's the boundary of what the protocol was built to do. MCP standardizes how agents talk to tools and data. It doesn't standardize memory, freshness, or reliability. Those still live below the protocol, and they're still yours to build.</p><p>This article covers what MCP standardizes, why tool calls are stateless by design, the three problems MCP leaves on your plate, and where a fast data layer fits underneath it all.</p><h2><strong>What does Model Context Protocol standardize?</strong></h2><p>MCP is an open protocol that connects LLM apps to external tools and data. Think of it like a USB-C port for AI apps: one standardized connector, many devices.</p><p>Before MCP, every agent-to-tool connection was its own project. Wiring up an agent to a new tool meant a custom integration for each pairing, which led to fragmentation and duplicated work. Build MCP into your agent once, and you can talk to any compatible MCP server without writing fresh glue code. That's the whole pitch: a universal, open standard for connecting AI systems to data.</p><p>The protocol pins down a few specific things:</p><ul><li><strong>Wire format:</strong> <a target=\"_blank\" href=\"https://modelcontextprotocol.io/specification/2025-11-25\">JSON-RPC 2.0 messages</a> with capability negotiation.</li><li><strong>Architecture:</strong> Three roles. Hosts (the LLM apps), clients (the connectors), and servers (the services that provide context and capabilities).</li><li><strong>Server primitives:</strong> Three building blocks. Resources for context and data, prompts for templated messages, and tools as executable functions the AI can call.</li></ul><p>Tools are model-controlled, so the LLM picks which one to call based on what the user asked.</p><p>Governance sits outside any single vendor, which matters for a standard like this. Anthropic <a target=\"_blank\" href=\"https://thenewstack.io/why-the-model-context-protocol-won\">introduced MCP</a> in November 2024, then donated it to the Agentic AI Foundation, a Linux Foundation fund co-founded with Block and OpenAI, with support from Google, Microsoft, Amazon Web Services (AWS), Cloudflare, and Bloomberg. Adoption looks healthy too: MCP reported 97 million <a target=\"_blank\" href=\"https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation\">monthly SDK downloads</a> and 10,000 active servers when the donation was announced. MCP is a real standard with real momentum. The interesting question is what it standardizes, and what it pointedly doesn't.</p><div><p><img alt=\"Redis Iris\" src=\"https://cdn.sanity.io/images/sy1jschh/production/82df1fa7f210a2b005d5ebbf3429a53a0ebccce0-64x64.svg\"></p><div><h2>Redis Iris serves agent context in milliseconds</h2><p><span>Redis Iris connects memory, live data, and retrieval in one place.</span></p></div></div><h2><strong>Does MCP handle agent memory?</strong></h2><p>MCP lets your agent act, but it doesn't standardize how your agent remembers. Tool calls are stateless by design, and the spec is moving harder in that direction.</p><p>A tools/call request is just a JSON-RPC message with a name and arguments. The response returns content and an error flag. That's the whole contract. Memory and context management are explicitly out of scope for MCP, which focuses on context exchange, not on how AI apps manage what they're given.</p><p>Recent drafts double down on this. Proposed changes remove protocol-level session state from the transport, including protocol-level sessions and the Mcp-Session-Id header from the Streamable HTTP transport. The intent is stateful agentic apps running on top of a sessionless protocol.</p><p>The reason sessions are getting cut: no two clients agreed on what a session even was. ChatGPT opened a fresh one per tool call, desktop clients opened one per app launch, web clients opened one per page load, and almost none <a target=\"_blank\" href=\"https://modelcontextprotocol.io/seps/2567-sessionless-mcp\">resumed a session</a> after a disconnect. With the concept meaning something different everywhere, the spec is handing state management back to the app. In its place comes explicit handle passing: a tool returns an identifier like a basket_id, and the model passes that identifier back as an argument on later calls.</p><p>The takeaway is simple. Cross-session agent memory belongs at the app or data layer, not in the protocol. MCP gives you the wire format for invoking a tool, nothing more.</p><h2><strong>What MCP leaves to you: memory, freshness &amp; reliability</strong></h2><p>The protocol stops at the tool call. That leaves three problems for you to solve: memory, freshness, and reliability.</p><h3><strong>How do AI agents remember across sessions?</strong></h3><p>Agent memory typically splits into two types. Short-term, or working memory, is thread-scoped and tracks the ongoing conversation. In frameworks like LangGraph, that's handled by checkpointers that <a target=\"_blank\" href=\"https://docs.langchain.com/oss/python/langgraph/persistence\">persist graph state</a>. Long-term memory persists across sessions, scoped to namespaces rather than single thread IDs.</p><p>Most production agents use both. MCP can expose memory services through shared tools or resources, but there are <a target=\"_blank\" href=\"https://www.newamerica.org/insights/ai-agents-and-memory\">no memory standards</a> governing how memory is stored, segmented, or reused.</p><h3><strong>Why does retrieved context go stale?</strong></h3><p>Stale data quietly poisons agent outputs. <a target=\"_blank\" href=\"https://redis.io/glossary/retrieval-augmented-generation/\">Retrieval-augmented generation (RAG)</a> helps with freshness and factuality, but keeping retrieval indices current takes ongoing effort as your data changes. Systems retrieving by cosine similarity alone can <a target=\"_blank\" href=\"https://arxiv.org/html/2509.19376\">surface stale context</a> or fail to tell apart novel updates from redundant information: a vendor's deprecated guidance, say, or last month's roster.</p><p>Some domains feel this more than others. In cybersecurity, today's attack vector is far more urgent than the same one from a year ago. In healthcare, <a target=\"_blank\" href=\"https://arxiv.org/pdf/2507.18910\">outdated studies pose risks</a> when systems repeat findings that have since been disproven. And keeping an index fresh is real work: <a target=\"_blank\" href=\"https://arxiv.org/html/2603.10765v1\">new source data</a> has to be converted into vector embeddings, and some index structures involve costly rebuild paths.</p><p>Staleness eventually hits the model layer as <a target=\"_blank\" href=\"https://redis.io/blog/context-rot\">context rot</a>, the performance degradation that happens when LLMs process increasingly long input contexts. A bigger context window doesn't save you. When stale or excessive retrieved content fills the window, the relevant signal gets buried and the model struggles to act on it.</p><div><p><img alt=\"Redis Search\" src=\"https://cdn.sanity.io/images/sy1jschh/production/d4f38741624677cf37133114f041712038fd728d-64x64.svg\"></p><div><h2>Build agents that remember, not agents that guess</h2><p><span>Redis Iris gives every agent fresh context and long-term memory.</span></p></div></div><h3><strong>Why do long agent chains fail?</strong></h3><p>Long agent chains fail more often than people expect, because each step has to clear the one before it. If every step is 95% reliable on its own, a 10-step chain succeeds end to end only about 60% of the time, since you multiply 0.95 by itself for each step. Drop per-step reliability to 85% and that same 10-step chain lands around 20%. Add more steps and the number falls faster.</p><p>The raw math actually understates the problem, because the output of one step becomes the input to the next. One bad result early breaks everything downstream. This is a systems problem, not a model problem, and retrieval is one of the steps most likely to drag the chain down.</p><p>Every retrieval an agent makes is a step that can fail. Slow tools add latency to every query that touches them, and degraded or stale results push low-quality context into the window, which the next step then treats as fact. The more a chain depends on data it has to fetch mid-run, the more its end-to-end reliability rides on how fast and how current that data layer is. None of that is handled at the protocol layer.</p><h2><strong>How a real-time data layer fills the gaps MCP leaves</strong></h2><p>Memory, freshness, and reliability all need the same thing: somewhere to persist, retrieve, and refresh state, fast. That's the job of an in-memory data layer.</p><p>Redis is built for that job. As a real-time data platform, enterprise-grade Redis reported over <a target=\"_blank\" href=\"https://redis.io/blog/redis-enterprise-extends-linear-scalability-200m-ops-sec/\">100 million operations</a> per second at sub-millisecond latency on a 20-node AWS cluster. That matters because agents can make <a target=\"_blank\" href=\"https://redis.io/blog/build-smarter-ai-agents-manage-short-term-and-long-term-memory-with-redis\">multiple context retrievals</a> in a single reasoning loop, and that latency stacks up. Beyond caching, Redis brings <a target=\"_blank\" href=\"https://university.redis.io/course/1npvvtfft2agew\">vector search</a>, semantic caching, and the data structures agents lean on for state. Your app can support RAG retrieval, agent memory, and real-time coordination in <a target=\"_blank\" href=\"https://redis.io/blog/more-than-a-vector-database\">one system</a> instead of stitching together a separate tool for each.</p><p>That maps cleanly to the three problems above. For memory, Redis supports <a target=\"_blank\" href=\"https://redis.io/blog/ai-agent-memory-stateful-systems\">agent memory tiers</a>: short-term working memory with in-memory data structures, long-term semantic memory through vector search, and episodic memory with streams as logs of past tool calls and outcomes. For reliability, the same low-latency layer keeps retrieval fast and current, so fewer steps fail on slow or stale data in the first place.</p><p>MCP solves tool connectivity, but it <a target=\"_blank\" href=\"https://redis.io/blog/from-demo-to-dependable-ai-in-context\">doesn't solve context fragmentation</a>. Closing that gap is the job of Redis Iris, a context engine that sits between an agent and the data it needs, feeding the right context in the right form at the right time. Memory, retrieval, and fresh data stop being three systems your agent has to reconcile and become one fast layer it reads and writes against.</p><div><p><img alt=\"Redis Copilot\" src=\"https://cdn.sanity.io/images/sy1jschh/production/271bdf12954e5a8b98fccce65278c76f1d130472-64x64.svg\"></p><div><h2>Fresh context, every call</h2><p><span>Redis Iris keeps agent data current so answers stay accurate.</span></p></div></div><h2><strong>MCP connects agents to tools, the data layer makes them work</strong></h2><p>MCP does its job well, and the sessionless direction makes it cleaner still.
