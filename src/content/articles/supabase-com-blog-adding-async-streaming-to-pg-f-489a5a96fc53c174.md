But FDWs have long shared one limitation: they tend to fetch all results, or fixed-size batches, using a <strong>synchronous</strong> approach.</p>\n<p>With <a target=\"_blank\" href=\"https://github.com/supabase/wrappers\">Supabase Wrappers</a>, we’ve been exploring how to bring Postgres FDWs into the modern era with Rust. The latest release introduces something new to the Postgres world: <strong>asynchronous streaming between databases</strong>.</p>\n<p>Most FDWs, including <code>postgres_fdw</code>, <code>mysql_fdw</code> and many others, operate in a <strong>synchronous, pull-based model</strong>:</p>\n<ol>\n<li>\n<p>Execute a query on the remote source.</p>\n</li>\n<li>\n<p>Fetch rows either <strong>all at once</strong> or in <strong>fixed-size batches</strong> (e.g., using cursors).</p>\n</li>\n<li>\n<p>Block the Postgres backend while waiting for each batch to arrive.</p>\n</li>\n<li>\n<p>Convert the fetched rows into Postgres tuples before continuing.</p>\n</li>\n</ol>\n<p>While batched fetching avoids loading all data into memory upfront, Postgres still blocks during I/O, and the executor can’t proceed until each batch is fully received and processed. For analytical workloads against systems like ClickHouse, designed to scan billions of rows, this leads to:</p>\n<ul>\n<li>\n<p>High memory pressure - especially if batch sizes are large or unbounded</p>\n</li>\n<li>\n<p>Poor interactivity - users wait for the first row until the first batch returns</p>\n</li>\n<li>\n<p>Inefficient resource usage - the backend is idle during network waits</p>\n</li>\n</ul>\n<p>In short, traditional FDWs were designed for <strong>batch-oriented integration</strong>, not <strong>streaming data pipelines</strong>. They lack true non-blocking I/O and can’t start returning results until remote data begins flowing—and even then, they stall between batches.</p>\n<p>The latest version of our ClickHouse FDW introduces <strong>asynchronous streaming</strong>, enabling efficient, memory-safe queries, even over massive result sets.</p>\n<p>Here’s how it works:</p>\n<ol>\n<li>\n<p>A background async task fetches rows from ClickHouse incrementally, as they arrive over the network.</p>\n</li>\n<li>\n<p>These rows are passed to the Postgres backend through a <strong>bounded, size-limited channel</strong> (default capacity: 1024 rows).</p>\n</li>\n<li>\n<p>The FDW consumes rows from this channel one at a time, converting and emitting them to Postgres <strong>without buffering the full result set in memory</strong>.</p>\n</li>\n</ol>\n<p>This means Postgres can start returning results <strong>as soon as the first rows are available</strong>, dramatically reducing memory pressure and improving query responsiveness, even for massive analytical workloads.</p>\n<p>By combining Rust’s memory safety and async runtime capabilities with Postgres’s FDW interface, Wrappers delivers true streaming semantics while respecting Postgres’s synchronous execution model.</p>\n<h2 id=\"why-its-unique-in-the-postgres-ecosystem\">Why it’s unique in the Postgres ecosystem<a target=\"_blank\" href=\"https://supabase.com/blog/adding-async-streaming-to-pg-fdw#why-its-unique-in-the-postgres-ecosystem\">#</a></h2>\n<p>This streaming capability isn’t just a ClickHouse feature, it’s the first implementation of a reusable pattern built into Wrappers.</p>\n<p>Unlike traditional C-based FDWs that operate within Postgres’s synchronous model—often loading full result sets or blocking during batched fetches—Wrappers enables FDWs to stream data incrementally from remote sources. By offloading I/O to Rust’s async runtime and feeding rows to Postgres through a bounded channel, it delivers:</p>\n<ul>\n<li>\n<p>Predictable, bounded memory usage—even for billion-row scans,</p>\n</li>\n<li>\n<p>Faster time-to-first-result,</p>\n</li>\n<li>\n<p>Consistent performance across diverse backends like BigQuery, Snowflake, S3, and REST APIs.</p>\n</li>\n</ul>\n<p>With
