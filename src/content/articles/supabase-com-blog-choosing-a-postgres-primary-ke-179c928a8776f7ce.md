contentHtml: "<article><div>\n<p>Primary keys are important. They uniquely identify rows of data in tables, and make it easy to fetch data. The job of a database is to archive and recall data and you're going to have a hard time finding data without a good primary key or a good index.</p>\n<p>Sometimes it makes sense to use a <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Natural_key\">“natural key”</a> (like an <code>email</code> column in a <code>users</code> table) and sometimes it's better to use a “<a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Surrogate_key\">surrogate key”</a>, a value made <em>for the purpose</em> of identifying a row (and has no other meaning).</p>\n<p>At first glance, the question of <em>which</em> primary key to use is easy! Just throw a <code>integer</code>/<code>serial</code> on there, right? Numeric IDs are cool, but what about random value IDs or <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Uuid\">Universally Unique IDentifiers (UUIDs)</a>?</p>\n<p>Turns out the question of which identifier (and in this case, UUID) to use is complicated -- we're going to dive into some of the complexity and inherent trade-offs, and figure things out:</p>\n<ul>\n<li>What are the choices for identifiers?</li>\n<li>If we choose to use/add UUIDs, which ones should we choose?</li>\n<li>How can we get these UUIDs into postgres?</li>\n<li>Which UUIDs perform best?</li>\n</ul>\n<p>But first, a quick history lesson.</p>\n<h2 id=\"a-brief-history-of-identifiers-and-why-we-use-them\">A brief history of identifiers and why we use them<a target=\"_blank\" href=\"https://supabase.com/blog/choosing-a-postgres-primary-key#a-brief-history-of-identifiers-and-why-we-use-them\">#</a></h2>\n<h3 id=\"integerbiginteger\"><code>integer</code>/<code>biginteger</code><a target=\"_blank\" href=\"https://supabase.com/blog/choosing-a-postgres-primary-key#integerbiginteger\">#</a></h3>\n<p>Let's think about identifying rows of data from first principles. What's the first way you might think of identifying things? Assigning them numbers!</p>\n<p>We can set up a table like this:</p>\n<div><p><code><br><div><p><span>_<!-- -->12</span></p><p><span>-- Let's enable access to case-insensitive text</span></p></div><div><p><span>_<!-- -->12</span></p><p><span>CREATE EXTENSION IF NOT EXISTS citext;</span></p></div><div><p><span>_<!-- -->12</span></p></div><div><p><span>_<!-- -->12</span></p><p><span>-- Heres a basic users table</span></p></div><div><p><span>_<!-- -->12</span></p><p><span>CREATE TABLE users (</span></p></div><div><p><span>_<!-- -->12</span></p><p><span>  id integer PRIMARY KEY,</span></p></div><div><p><span>_<!-- -->12</span></p><p><span>  email citext NOT NULL CHECK (LENGTH(email) &lt; 255),</span></p></div><div><p><span>_<!-- -->12</span></p><p><span>  name text NOT NULL</span></p></div><div><p><span>_<!-- -->12</span></p><p><span>);</span></p></div><div><p><span>_<!-- -->12</span></p></div><div><p><span>_<!-- -->12</span></p><p><span>-- Let's assume we don't want two users with the exact same email</span></p></div><div><p><span>_<!-- -->12</span></p><p><span>CREATE UNIQUE INDEX users_email_uniq ON users USING BTREE (email);</span></p></div><br></code></p></div>\n<p>This looks great, but what should <code>id</code> be on new rows? I don't know -- maybe the application can figure it out? If they store some value in memory? That doesn't seem right.</p>\n<p>Maybe we could figure out the next integer from what's in the table itself -- we just need to be able to \"count\" upwards. We <em>do</em> have all the <code>users</code> tables rows in there, so we should be able to do it:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>insert into users</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  (id, email, name)</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>select count(*) + 1, 'new@example.com', 'new_user' from users;</span></p></div><br></code></p></div>\n<p>After running that query, we can double check our results:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>select * from users;</span></p></div><br></code></p></div>\n<table><thead><tr><th>id</th><th>email</th><th>name</th></tr></thead><tbody><tr><td><code>1</code></td><td><code>new@example.com</code></td><td><code>new user</code></td></tr><tr><td><code>2</code></td><td><code>new2@example.com</code></td><td><code>new user</code></td></tr></tbody></table>\n<p>Using <code>COUNT(*)</code> in our query is not the most efficient (or even easiest) solution though, and hopefully it's clear why -- <strong>counting a sequence of numbers for primary keys is a feature built in to Postgres</strong>!</p>\n<p><a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/datatype-numeric.html#DATATYPE-SERIAL\">serial/bigserial</a> is the right tool in our toolbox to maintain a shared, auto-incrementing sequence of numbers. Let's pretend we read the <a target=\"_blank\" href=\"https://www.postgresql.org/docs\">postgres documentation</a> and use those instead.</p>\n<h3 id=\"serialbigserial\"><code>serial</code>/<code>bigserial</code><a target=\"_blank\" href=\"https://supabase.com/blog/choosing-a-postgres-primary-key#serialbigserial\">#</a></h3>\n<p><code>serial</code> is essentially a convenient macro for using <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/sql-createsequence.html\">Postgres sequences</a>, a database-managed auto-incrementing stream of <code>integer</code>.</p>\n<p>Let's hear it from the docs:</p>\n<blockquote>\n<p>The data types <code>smallserial</code>, <code>serial</code> and <code>bigserial</code> are not true types, but merely a notational convenience for creating unique identifier columns (similar to the <code>AUTO_INCREMENT</code> property supported by some other databases).</p>\n</blockquote>\n<p>Using a <code>serial</code> column to create the <code>users</code> table would look like this:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>create table users (</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  id serial primary key,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  email citext not null check (length(email) &lt; 255),</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  name text not null</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>);</span></p></div><br></code></p></div>\n<p>OK, now let's try inserting into it - we shouldn't have to specify <code>id</code>:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>insert into users_serial</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  (email, name)</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>values</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  ('user@example.com', 'new user');</span></p></div><br></code></p></div>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>select * from users;</span></p></div><br></code></p></div>\n<table><thead><tr><th>id</th><th>email</th><th>name</th></tr></thead><tbody><tr><td><code>1</code></td><td><code>user@example.com</code></td><td><code>new user</code></td></tr></tbody></table>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>(1 row)</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>INSERT 0 1</span></p></div><br></code></p></div>\n<p>It works, as you might expect - now the application doesn't have to <em>somehow magically know</em> the right ID to use when inserting.</p>\n<p>But what does <code>serial</code> actually do? Using a serial column is operationally similar to the following SQL:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>CREATE SEQUENCE tablename_colname_seq AS integer;</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>CREATE TABLE tablename (</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    colname integer NOT NULL DEFAULT nextval('tablename_colname_seq')</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>);</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>ALTER SEQUENCE tablename_colname_seq OWNED BY tablename.colname;</span></p></div><br></code></p></div>\n<p>Back in application land, the <code>INSERT</code> statement returns, and provides the new <code>id</code> the database assigned our new row. Multiple application instances don't need to coordinate what ID to use -- they just <em>don't</em>, and find out from the database.</p>\n<p><strong>We've taken a somewhat meandering path to get here, but this is the standard solution for most reasonable database schemas.</strong></p>\n<h3 id=\"why-not-stop-at-serial\">Why not stop at <code>serial</code>?<a target=\"_blank\" href=\"https://supabase.com/blog/choosing-a-postgres-primary-key#why-not-stop-at-serial\">#</a></h3>\n<p>There are few issues with sequences:</p>\n<ul>\n<li>When writing automation that simply iterates through id values, note that <code>serial</code> columns can have gaps, even if you never <code>DELETE</code> (e.x. if an <code>INSERT</code> was rolled back — sequences live <em>outside</em> transactions).</li>\n<li>When used from outside code <code>serial</code> may leak some data or give attackers an edge (e.x., if <code>yoursite.com/users/50</code> works, how about <code>yoursite.com/users/51</code>?).</li>\n<li><code>serial</code> is PostgreSQL specific (i.e. not SQL standards compliant)</li>\n</ul>\n<p>Don't be too put off by these reasons -- <code>serial</code> is still the go-to for most use-cases.</p>\n<p>Even the last point about <code>serial</code> not being standards compliant is solved in Postgres 10+ by using...</p>\n<h3 id=\"integerbiginteger-again\"><code>integer</code>/<code>biginteger</code> (again!)<a target=\"_blank\" href=\"https://supabase.com/blog/choosing-a-postgres-primary-key#integerbiginteger-again\">#</a></h3>\n<p>Postgres 10 <a target=\"_blank\" href=\"https://www.postgresql.org/docs/10/release-10.html#id-1.11.6.26.5.7\">added support</a> for the <code>IDENTITY</code> column syntax in <code>CREATE TABLE</code> (EDB has a great writeup on the <a target=\"_blank\" href=\"https://www.enterprisedb.com/blog/postgresql-10-identity-columns-explained\">addition</a>).</p>\n<p>This means we can happily go back to using <code>integer</code>/<code>biginteger</code>:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>CREATE TABLE (</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  id integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  email citext NOT NULL CHECK (LENGTH(email) &lt; 255),</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  name text NOT NULL</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>)</span></p></div><br></code></p></div>\n<p>So how does <em>this</em> work? Postgres does the same thing under the covers -- it generates a <code>sequence</code>. As this syntax is standards compliant, it's generally recommended practice for DBAs going forward, for the sake of the realm.</p>\n<p><strong>So <code>integer</code>s are great, but information leakage is still a problem. How do we fix that?</strong> Well, make the numbers random, obviously.</p>\n<h3 id=\"random-numeric-ids\">Random Numeric IDs<a target=\"_blank\" href=\"https://supabase.com/blog/choosing-a-postgres-primary-key#random-numeric-ids\">#</a></h3>\n<p>Let's say the application using the DB has some <a target=\"_blank\" href=\"https://python.org/\">Python</a> code like the following:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>from random import randrange</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>from models import User</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>MAX_RANDOM_USER_ID = 1_000_000_000</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>def create_user():</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    \"\"\"</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    Add new user to the database</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    \"\"\"</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    user_id = randrange(1, MAX_RANDOM_USER_ID)</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    user = User(id=user_id, email=\"new@example.com\", name=\"new user\")</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    db.save(user)</span></p></div><br></code></p></div>\n<p>That <em>looks</em> good, but there's a problem -- <a target=\"_blank\" href=\"https://docs.python.org/3/library/random.html\">random</a> is a <em>pseudorandom</em> generator.</p>\n<p><a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Pseudorandomness\">Pseudo-random</a> numbers are <em>not</em> what we want for ensuring user IDs cannot be easily guessed/collide. It's possible to get the exact same sequence of values out of a pseudo-random number generator by using the same <em>seed value</em>.</p>\n<p>Sometimes you <em>want</em> pseudo-random behavior (let's say for testing or fuzzing), but it's generally not desired for production systems that might run from a duplicated identical application image, since they <em>could</em> have weak pseudo-random seed initialization.</p>\n<h3 id=\"secure-random-numeric-ids\">(Secure) Random Numeric IDs<a target=\"_blank\" href=\"https://supabase.com/blog/choosing-a-postgres-primary-key#secure-random-numeric-ids\">#</a></h3>\n<p><strong>At the very least</strong> we need a properly secure random numbers -- we need Python's <a target=\"_blank\" href=\"https://docs.python.org/3/library/secrets.html\">secrets</a> module:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>from secrets import randbelow</span></p></div><div><p><span>_<!-- -->10</span></p><p><span># ...</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>def create_user():</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    \"\"\"</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    Add new user to the database (using secure random numbers)</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    \"\"\"</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    user_id = randbelow(1, MAX_RANDOM_USER_ID)</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    user = User(id=user_id, email=\"new@example.com\", name=\"new user\")</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    db.save(user)</span></p></div><br></code></p></div>\n<p>Now we have a secure random value coming in for our user IDs. But having values like <code>583247</code> and <code>8923916</code> get generated are cool and all, but there are a few problems:</p>\n<ul>\n<li>These numbers are random <em>and</em> quite inscrutable</li>\n<li>The keyspace is fairly small (maybe good for comments on a popular website, but not for IDs!)</li>\n<li>People can still <em>technically</em> check them all (the guessing space is 1 to <code>MAX_RANDOM_USER_ID</code>!)</li>\n</ul>\n<p>We need something better.</p>\n<h3 id=\"secure-random-uuids\">(Secure) Random UUIDs<a target=\"_blank\" href=\"https://supabase.com/blog/choosing-a-postgres-primary-key#secure-random-uuids\">#</a></h3>\n<p>Along comes UUIDs -- you're probably used to seeing them now, values like this UUIDv4:</p>\n<p><code>468e8075-5815-4fe2-80d3-45a31827954b</code> .</p>\n<p>They're <em>very</em> random (almost always generated with secure random sources), and while they're even worse for remembering, they're near impossible to practically guess -- the search space is just too large!</p>\n<p>More importantly, UUIDs introduce methodology to the madness -- different versions of UUID are derived different ways -- combined with other sources of randomness or known values.</p>\n<p>There are a lot of <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Universally_unique_identifier#Versions\">versions of UUID</a>, but let's discuss the ones we're more likely to use/see day to day.</p>\n<h3 id=\"uuidv1\">UUIDv1<a target=\"_blank\" href=\"https://supabase.com/blog/choosing-a-postgres-primary-key#uuidv1\">#</a></h3>\n<p><a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Universally_unique_identifier#Version_1_(date-time_and_MAC_address)\">Version 1 UUIDs</a> have three two components:</p>\n<ul>\n<li>a 60 bit date-time (at nanosecond precision)</li>\n<li>a 48 bit <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/MAC_address\">MAC address</a></li>\n</ul>\n<p>But where's the randomness? Well v1s assume that you <em>won't</em> generate a ton of values in the same nanosecond (and there are some extra bits reserved for differentiating even when you do), but another source is the MAC address. MAC addresses uniquely (usually) identify network cards -- which is a security risk -- and those bits can be made random.</p>\n<p>Here's what a UUIDv1 looks like:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>a9957082-0b47-11ed-8a91-3cf011fe32f1</span></p></div><br></code></p></div>\n<p>You can generate v1 UUIDs in Postgres natively thanks to the <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/uuid-ossp.html\">uuid-ossp contrib module</a>. Here's how to generate a v1 UUID with random MAC address:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>CREATE EXTENSION IF NOT EXISTS \"uuid-ossp\";</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>CREATE EXTENSION</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>SELECT uuid_generate_v1mc();</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>          uuid_generate_v1mc</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>--------------------------------------</span></p></div><div><p><span>_<!-- -->10</span></p><p><span> dd1bbf10-0b47-11ed-80de-db48f6faaf86</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>(1 row)</span></p></div><br></code></p></div>\n<h3 id=\"uuidv4\">UUIDv4<a target=\"_blank\" href=\"https://supabase.com/blog/choosing-a-postgres-primary-key#uuidv4\">#</a></h3>\n<p>Version 4 UUIDs use <em>all</em> the available bits for randomness -- <em>122 bits worth</em>!.</p>\n<p>UUIDv4s look like this:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>ce0b897d-03a0-4f54-8c97-41d29a325a23</span></p></div><br></code></p></div>\n<p>These don't have a time component, but they don't have in time they make up for in randomness -- it is <em>very</em> unlikely for them to collide, so they make for excellent Global Unique IDentifiers (\"GUID\"s).</p>\n<p>We can generate them in Postgres like this (with <code>uuid-ossp</code>):</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>SELECT gen_random_uuid();</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>           uuid_generate_v4</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>--------------------------------------</span></p></div><div><p><span>_<!-- -->10</span></p><p><span> 6ca93dde-81d4-4ea0-bfe1-92ecb4d81ee4</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>(1 row)</span></p></div><br></code></p></div>\n<p>Since Postgres would catch a collision on a <code>PRIMARY KEY</code> or <code>UNIQUE INDEX</code> column, we're done right? If we want to generate UUIDs all we need to do is choose UUID v1 or V4, and we won't leak any schema structure information to the outside world, right?</p>\n<p>This is a workable solution, but as you might expect, it's not that easy.</p>\n<h3 id=\"the-post-uuidv1v4-era-a-cambrian-explosion-of-identifiers\">The Post-UUIDv1/v4 era: A Cambrian explosion of identifiers<a target=\"_blank\" href=\"https://supabase.com/blog/choosing-a-postgres-primary-key#the-post-uuidv1v4-era-a-cambrian-explosion-of-identifiers\">#</a></h3>\n<p>UUIDv1 and v4 were a start, but weren't enough for <em>many</em> companies out there. There are a couple shortcomings that plague both v1 and v2:</p>\n<ul>\n<li>UUIDs are twice the size of <code>bigint</code>/<code>bigserial</code></li>\n<li>UUIDv1s contain a time element but they're <em>not</em> lexicographically sortable (this means they <code>SORT</code> terribly, relative to <code>integer</code> or a <code>timestamp</code> column)</li>\n<li>UUIDv1s are less random than UUIDv4, and can collide/overlap in close enough time intervals, at large scale</li>\n<li>UUIDv4s index <em>terribly</em>, as they're essentially random values (obviously, they <code>SORT</code> terribly as well)</li>\n</ul>\n<p>Many of the world's biggest companies generated UUIDs at speeds that made all of these deficiencies a problem.</p>\n<p>A cambrian explosion of UUIDs resulted, as noticed by the IETF -- this resulted in the <a target=\"_blank\" href=\"https://www.ietf.org/archive/id/draft-peabody-dispatch-new-uuid-format-01.html\">new UUID formats</a> (v6,v7,v8) being published in 2021.</p>\n<p>Here's a quick list (from that IETF document):</p>\n<ul>\n<li>LexicalUUID by <a target=\"_blank\" href=\"https://blog.twitter.com/engineering\">Twitter</a></li>\n<li><a target=\"_blank\" href=\"https://blog.twitter.com/engineering/en_us/a/2010/announcing-snowflake\">Snowflake</a> by <a target=\"_blank\" href=\"https://blog.twitter.com/engineering\">Twitter</a></li>\n<li><a target=\"_blank\" href=\"https://github.com/boundary/flake\">Flake</a> by <a target=\"_blank\" href=\"http://www.bmc.com/\">Boundary (now BMC TrueSight Pulse)</a></li>\n<li>ShardingID by <a target=\"_blank\" href=\"http://instagram-engineering.com/\">Instagram</a></li>\n<li><a target=\"_blank\" href=\"https://github.com/segmentio/ksuid\">KSUID</a> by <a target=\"_blank\" href=\"https://segment.com/blog/engineering/\">Segment</a></li>\n<li><a target=\"_blank\" href=\"https://github.com/ppearcy/elasticflake\">Elasticflake</a> by <a target=\"_blank\" href=\"https://github.com/ppearcy/elasticflake\">P. Chilton</a></li>\n<li><a target=\"_blank\" href=\"https://firebase.googleblog.com/2015/02/the-2120-ways-to-ensure-unique_68.html\">pushID</a> by <a target=\"_blank\" href=\"https://google.com/\">Google</a></li>\n<li><a target=\"_blank\" href=\"https://github.com/rs/xid\">XID</a> by <a target=\"_blank\" href=\"https://github.com/rs\">O. Poitrey</a></li>\n<li><a target=\"_blank\" href=\"https://www.mongodb.com/docs/manual/reference/method/ObjectId/\">ObjectID</a> by <a target=\"_blank\" href=\"https://www.mongodb.com/blog/channel/engineering-blog\">MongoDB</a></li>\n<li><a target=\"_blank\" href=\"https://github.com/ericelliott/cuid\">CUID</a> by <a target=\"_blank\" href=\"https://github.com/ericelliott\">E. Elliott</a></li>\n</ul>\n<p>That's... A lot of UUIDs. They're all slightly different, but the innovation was summed up by the IETF:</p>\n<blockquote>\n<p>An inspection of these implementations details the following trends that help define this standard:</p>\n<ul>\n<li>Timestamps MUST be k-sortable. That is, values within or close to the same timestamp are ordered properly by sorting algorithms.</li>\n<li>Timestamps SHOULD be big-endian with the most-significant bits of the time embedded as-is without reordering.</li>\n<li>Timestamps SHOULD utilize millisecond precision and Unix Epoch as timestamp source. Although, there is some variation to this among implementations depending on the application requirements.</li>\n<li>The ID format SHOULD be Lexicographically sortable while in the textual representation.</li>\n<li>IDs MUST ensure proper embedded sequencing to facilitate sorting when multiple UUIDs are created during a given timestamp.</li>\n<li>IDs MUST NOT require unique network identifiers as part of achieving uniqueness.</li>\n<li>Distributed nodes MUST be able to create collision resistant Unique IDs without a consulting a centralized resource.\n<strong>The IETF went on to introduce three 3 new types of UUIDs</strong> that have these properties these companies were looking for: UUIDv6, UUIDv7, and UUIDv8.</li>\n</ul>\n</blockquote>\n<p>So what's the difference you ask?</p>\n<ul>\n<li><strong>UUIDv6</strong> - 62 bits of <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Gregorian_calendar\">gregorian</a> time + 48 bits of randomness</li>\n<li><strong>UUIDv7</strong> - 36 bits of big endian unix timestamp (seconds since epoch + leapseconds w/ optional sub-second precision) + variable randomness up to 62 bits</li>\n<li><strong>UUIDv8</strong> - variable size timestamp (32/48/60/64 bits) + variable size clock (8/12 bits) + variable randomness (54/62 bits)</li>\n</ul>\n<p>It's not quite easy to work out what this all <em>means</em> but let's boil it down:</p>\n<ul>\n<li>All of these UUIDs sort properly (the \"high bits\" of time are first, like putting the year before the month -- \"2022/07\")</li>\n<li>UUIDv6 <em>requires</em> randomness</li>\n<li>The data contained in the UUID can be variable (ex. UUIDv8), this means you can bytes that mean something else (ex. an encoding of the compute region you're running in)</li>\n</ul>\n<p>Alright, done hearing about UUIDs?
