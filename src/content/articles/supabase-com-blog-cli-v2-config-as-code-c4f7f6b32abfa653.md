contentHtml: "<article><div>\n<p>We have released Supabase CLI v2 today, adding support for Configuration as Code.</p>\n<p>This means you can commit the configuration for all of your Projects and Branches into version control (like git) for reproducible environments for your entire team.</p>\n<p>The Supabase CLI started as a way to bootstrap the entire Supabase stack on your local machine. It uses exactly the same infra as our hosted platform, giving you unlimited Supabase projects for local testing and offline usage.</p>\n<p>In the last 2 years, the CLI has grown to more than 180,000 weekly installs. Nearly 85% of these come from Continuous Integration/Deployment environments like GitHub Actions. Some of the popular CI/CD use cases include migrating production databases, deploying functions, and running pgTAP tests. With this in mind, we started focusing on the CLI as a deployment tool for the v2 release.</p>\n<p>Our CLI’s Configuration as Code feature is an opinionated setup using a human readable <code>config.toml</code> file.</p>\n<p>You can make deployments consistent and repeatable by promoting Edge Functions, Storage objects, and other services from preview environments to staging and production.</p>\n<p>To demonstrate this workflow, let’s use the <code>supabase.com</code> website as an example. It’s hosted on Vercel with <a target=\"_blank\" href=\"https://supabase.com/docs/guides/deployment/branching\">Supabase Branching</a> enabled for development. If you are not using Branching, a similar setup can be achieved using GitHub Actions.</p>\n<h3 id=\"managing-auth-config\">Managing Auth Config<a target=\"_blank\" href=\"https://supabase.com/blog/cli-v2-config-as-code#managing-auth-config\">#</a></h3>\n<p>We use Vercel Previews for our frontend. To configure the Auth service of Supabase branches to support login for any Vercel preview URL, we declare a wildcard for the <code>additional_redirect_urls</code> in auth config:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>[auth]</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>additional_redirect_urls = [</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  \"https://*-supabase.vercel.app/*/*\",</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  \"https://supabase.com/*/*\",</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  \"http://localhost:3000/*/*\",</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>]</span></p></div><br></code></p></div>\n<p>View the <a target=\"_blank\" href=\"https://supabase.com/docs/guides/local-development/cli/config#auth-config\">Auth config</a> docs.</p>\n<h3 id=\"managing-edge-functions\">Managing Edge Functions<a target=\"_blank\" href=\"https://supabase.com/blog/cli-v2-config-as-code#managing-edge-functions\">#</a></h3>\n<p>The Supabase website uses several <a target=\"_blank\" href=\"https://github.com/supabase/supabase/tree/master/supabase/functions\">Edge Functions</a> for AI docs, search embeddings, and image generation for launch week tickets. To configure automatic deployment of <code>search-embeddings</code> function, we add the following block to <code>config.toml</code>:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>[functions.search-embeddings]</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>verify_jwt = false</span></p></div><br></code></p></div>\n<p>If you are using a monorepo (like the <a target=\"_blank\" href=\"https://github.com/supabase/supabase\">@supabase/supabase</a> GitHub repository), you may also want to customize the paths to your function’s entrypoint and import map files. This is especially useful for code sharing between your frontend application and Edge Functions.</p>\n<p>View the <a target=\"_blank\" href=\"https://supabase.com/docs/guides/local-development/cli/config#edge-functions-config\">Edge Functions config</a> docs.</p>\n<h3 id=\"managing-storage-objects\">Managing Storage Objects<a target=\"_blank\" href=\"https://supabase.com/blog/cli-v2-config-as-code#managing-storage-objects\">#</a></h3>\n<p>The <a target=\"_blank\" href=\"https://supabase.com/dashboard/project/xguihxuzqibwxjnimxev/storage/buckets/images\">images and fonts</a> for all launch week tickets are stored in Supabase Storage. These assets are distributed to CDNs around the world to improve latency for visitors to our website.</p>\n<p>When developing locally, we can add a <code>[storage.buckets]</code> block to <code>config.toml</code> so that files in <code>supabase/assets</code> directory are automatically uploaded to Supabase Storage.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>[storage.buckets.assets]</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>objects_path = \"./assets\"</span></p></div><br></code></p></div>\n<p>In our case, the assets are small enough (&lt; 1MB) to be committed and tracked in git. This allows branching to automatically seed these objects to Supabase Storage for preview. Larger files like videos are best uploaded to Supabase Storage via AWS S3 CLI.</p>\n<p>View the <a target=\"_blank\" href=\"https://supabase.com/docs/guides/local-development/cli/config#storage-config\">Storage config</a> docs.</p>\n<h3 id=\"managing-database-settings-and-webhooks\">Managing Database Settings and Webhooks<a target=\"_blank\" href=\"https://supabase.com/blog/cli-v2-config-as-code#managing-database-settings-and-webhooks\">#</a></h3>\n<p>While Supabase manages the Postgres default settings based on your database compute size, sometimes you need to tweak these settings yourself. Using the <code>config.toml</code> file, we can easily update and keep track of database settings.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>[db.settings]</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>track_commit_timestamp = true</span></p></div><br></code></p></div>\n<p>Our Management API automatically figures out if one or more parameters require restarting the database. If not, the config will be applied by simply sending <code>SIGUP</code> to Postgres process.</p>\n<p>Moreover, you can now enable database webhooks using <code>[experimental]</code> config block. This feature allows your database to call HTTP endpoints directly from Postgres functions.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>[experimental.webhooks]</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>enabled = true</span></p></div><br></code></p></div>\n<p>To create a webhook, simply add a new <a target=\"_blank\" href=\"https://github.com/supabase/supabase/tree/master/supabase/migrations\">schema migration</a> file with the before or after triggers for the tables you want to listen on.</p>\n<p>View the <a target=\"_blank\" href=\"https://supabase.com/docs/guides/local-development/cli/config#database-config\">Database config</a> docs.</p>\n<p>If you have <a target=\"_blank\" href=\"https://supabase.com/docs/guides/deployment/branching#enable-supabase-branching\">Branching</a> enabled in your project, your settings in <code>config.toml</code> are automatically synced to all your ephemeral branches. This works because we maintain a one-to-one mapping between your git branch and Supabase branch.</p>\n<p>To make a config change to your Supabase branch, simply update config.toml and push to GitHub. Our runner will pick up the diff and apply it to the corresponding Supabase branch.</p>\n<p>If you need to configure specific settings for a single persistent branch, you can declare them using <code>[remotes]</code> block of your config by providing its project ID. For example, the following config declares a separate seed script just for your staging environment.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>[remotes.staging]</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>project_id = \"your-project-ref\"</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>[remotes.staging.db.seed]</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>sql_paths = [\"./seeds/staging.sql\"]</span></p></div><br></code></p></div>\n<p>Since the <code>project_id</code> field must refer to an existing branch, you won’t be able to provision and configure a persistent branch in the same commit. Instead, always provision a persistent branch first using the CLI command so you can add the project ID returned to <code>config.toml</code>.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>$ supabase --experimental branches create --persistent</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>Do you want to create a branch named develop? [Y/n]</span></p></div><br></code></p></div>\n<p>When merging a PR to any persistent branch, our runner checks and logs any configuration changes before applying them to the target remote. If you didn’t declare any remotes or provided the wrong project ID, the whole configuration step would be skipped.</p>\n<p>All other config options are also available in the remotes block.</p>\n<p>To start using configuration as code, you may follow <a target=\"_blank\" href=\"https://supabase.com/docs/guides/deployment/branching#how-to-use-supabase-branching\">our guide</a> to connect a GitHub repository to your Supabase project and enable Supabase Branching.</p>\n<p>Alternatively, you can get started with the Supabase CLI today: <code>supabase config push</code></p>\n<h3
