evaluating dependencies and reducing npm package section size<a target=\"_blank\" href=\"https://supabase.com/blog/edge-functions-faster-smaller#lazy-evaluating-dependencies-and-reducing-npm-package-section-size\">#</a></h3>\n<p>We use <a target=\"_blank\" href=\"https://github.com/denoland/eszip\">eszip format</a> to bundle your function code and its dependencies when you deploy a function.</p>\n<p>This binary format extracts the dependencies a function references from Deno's module graph and serializes them into a single file. It eliminates network requests at run time and avoids conflicts between dependencies.</p>\n<p>This approach worked reasonably well until we added npm support. When functions started using npm modules, bundle sizes and boot times increased.</p>\n<p>When a function is invoked, Edge Runtime loads the eszip binary for the function and passes it to a JavaScript worker (ie. isolate). The worker then loads the necessary modules from the eszip.</p>\n<p>In the original implementation, before passing an eszip binary to the worker's module loader, we first checked the integrity of its contents. Each entry in it will have a checksum computed with the SHA-256 function immediately following the body bytes. By reading this and comparing it, we ensure that the eszip binary isn’t corrupted.</p>\n<p>The problem is that calculating a checksum for every entry using SHA-256 is quite expensive, and we were pre-checking the integrity of all entries at a time when the worker doesn't even need that particular entry.</p>\n<p>It is possible that some items that have been checked for integrity will not be referenced even if the worker reaches the end of its lifetime and reaches the end state.</p>\n<p>Instead of performing the costly integrity check of all entries before passing it to the module loader, edge runtime lazily performs the integrity check whenever there is a request to load a specific entry from the eszip by the module loader.</p>\n<p>This helped to significantly to reduce the boot times.</p>\n<p>Another issue was that while serializing npm packages for embedding into eszip binaries, we used the JSON format. The entries in individual npm packages, which were already represented as bytes (<code>Vec&lt;u8&gt;</code>), were encoded as an array representation in JSON format (<code>[255, 216, 255, 224, 0, ...]</code>) instead of passing on as bytes, causing the outputs to bloat by up to 2x or more.</p>\n<p>We refactored the serialization using the <a target=\"_blank\" href=\"https://github.com/rkyv/rkyv\"><code>rkyv</code> crate</a> to encode this to lower to the byte level, which helped reducing the bundle sizes of eszip binaries containing npm packages.</p>\n<p>You can find full details of the implementation in this PR <a target=\"_blank\" href=\"https://github.com/supabase/edge-runtime/pull/343\">https://github.com/supabase/edge-runtime/pull/343</a></p>\n<h3 id=\"using-a-more-computationally-efficient-hashing-function\">Using a more computationally efficient hashing function<a target=\"_blank\" href=\"https://supabase.com/blog/edge-functions-faster-smaller#using-a-more-computationally-efficient-hashing-function\">#</a></h3>\n<p>There was a <a target=\"_blank\" href=\"https://github.com/denoland/eszip/pull/181\">recent change</a> in the eszip crate, which allowed the configuration of the source checksum.</p>\n<p>This allowed us to switch to xxHash-3 over SHA_256 for the source checksums. Given that the checksums are used to ensure the integrity of sources in eszip, we could rely on a non-cryptographic hash algorithm that’s more computationally efficient.</p>\n<p>To get the advantage of these optimizations, follow these steps:</p>\n<ul>\n<li><a target=\"_blank\" href=\"https://supabase.com/docs/guides/cli/getting-started#updating-the-supabase-cli\">Update Supabase CLI</a> to version is v1.195.2 or later.</li>\n<li>Then, redeploy your functions by running <code>supabase functions deploy [FUNCTION_NAME]</code></li>\n</ul>\n<p><a target=\"_blank\" href=\"https://github.com/supabase/edge-runtime\">Supabase Edge Runtime</a> is fully open-source, and we value community contributions.
