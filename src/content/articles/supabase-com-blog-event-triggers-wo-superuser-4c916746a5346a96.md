In cloud environments, granting superuser access isn't an option.</p>\n<p>But thanks to Postgres' extensibility, we can allow regular users to create Event Triggers, in a safe way.</p>\n<p>In this blog post, we’ll explain how we do this in the <code>supautils</code> extension, using a combination of the Utility Hook and the Function Manager Hook.</p>\n<!-- -->\n<p>The core of <code>supautils</code> is the “privileged role”, which is a role that serves as proxy to superuser. It provides a safe subset of superuser capabilities and it’s accessible to regular users.</p>\n<p>When the privileged role does a <code>create event trigger</code>, we intercept the statement with a Utility Hook (<code>ProcessUtility_hook</code>).\nHere we elevate the role to a superuser, continuing the usual flow and allowing the creation on Postgres core. As a last step, we downgrade to the privileged role and make\nit the event trigger owner <sup><a target=\"_blank\" href=\"https://supabase.com/blog/event-triggers-wo-superuser#user-content-fn-1\">1</a></sup>.</p>\n<p>Creating an event trigger like this is not safe though, as it would allow privilege escalation.</p>\n<p>Here, a problem arises. Once an Event Trigger is created:</p>\n<ul>\n<li>It targets every role.</li>\n<li>It runs using the target role privileges <sup><a target=\"_blank\" href=\"https://supabase.com/blog/event-triggers-wo-superuser#user-content-fn-2\">2</a></sup>.</li>\n</ul>\n<p>This means that a malicious user can create an Event Trigger like:</p>\n<div><p><code><br><div><p><span>_<!-- -->11</span></p><p><span>create or replace function become_super()</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    returns event_trigger</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    language plpgsql as</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>$$</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>begin</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    alter role malicious SUPERUSER;</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>end;</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>$$;</span></p></div><div><p><span>_<!-- -->11</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>create event trigger bad_event_trigger on ddl_command_end</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>execute procedure become_super();</span></p></div><br></code></p></div>\n<p>And once a superuser trips on the event trigger, it will fire with its privileges. Postgres doesn’t provide a noop function, but we can use the existing <code>version()</code> function for the same purpose.</p>\n<p>Besides superusers, we also want to skip user event triggers for “reserved roles” <sup><a target=\"_blank\" href=\"https://supabase.com/blog/event-triggers-wo-superuser#user-content-fn-3\">3</a></sup>.
