id=\"authentication\">Authentication<a target=\"_blank\" href=\"https://supabase.com/blog/graphql-now-available#authentication\">#</a></h3>\n<p>The GraphQL types exposed by <code>pg_graphql</code> are filtered according to the SQL role's <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/sql-grant.html\">INSERT/UPDATE/DELETE permissions</a>. At Supabase, each API request is resolved in the database using the role in the request's JWT.</p>\n<p>Anonymous users receive the <code>anon</code> role, and logged in users get the <code>authenticated</code> role. In either case, pg_graphql resolves requests according to the SQL permissions.\nThe <a target=\"_blank\" href=\"https://graphql.org/learn/introspection/\">introspection schema</a> is similarly filtered to limit exposed types and fields to those that the user has permission to access.\nThat means we can serve multiple GraphQL schemas for users of differing privilege levels from a single endpoint!</p>\n<h3 id=\"authorization\">Authorization<a target=\"_blank\" href=\"https://supabase.com/blog/graphql-now-available#authorization\">#</a></h3>\n<p>Another nice side effect of making PostgreSQL do the heavy lifting is that GraphQL queries respect your existing\n<a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/ddl-rowsecurity.html\">row level security policies</a> right out-of-the-box. No additional configuration required.</p>\n<p>To squeeze the most out of limited hardware we had to make a few significant optimizations:</p>\n<p><strong>GraphQL queries are always transpiled into exactly one SQL query</strong></p>\n<p>The SQL queries select and aggregate requested data into the shape of the GraphQL JSON response.\nIn addition to solving the <a target=\"_blank\" href=\"https://medium.com/the-marcy-lab-school/what-is-the-n-1-problem-in-graphql-dd4921cb3c1a\">N+1 query problem</a>, a common issue with GraphQL resolvers,\nGraphQL queries requiring multiple joins typically produce significantly less IO due to reduced data duplication.</p>\n<p>For example, when selecting all comments for a blog post:</p>\n<div><p><code><br><div><p><span>_<!-- are cached as prepared statements</strong></p>\n<p>After a GraphQL query is transpiled to SQL, it is added to the <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/sql-prepare.html\">prepared statement</a> cache so subsequent requests with the same structure (think pagination) can skip the transpilation
