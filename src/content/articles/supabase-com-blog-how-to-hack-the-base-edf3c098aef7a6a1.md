Making a curl request directly would have returned the raw html that you could have grep’ed, making the request through burp suite would have allowed you to inspect the html under “Proxy”, “HTTP History”, but perhaps an even easier way is to use the inspect tool of our browser.</p>\n<p>Within your browser, right click the home page and select “Inspect”. This will bring up the DevTools panel where it will present the current DOM. From here use the search function (CMD + F) and type “flag::”</p>\n<!-- -->\n<p>Did I deliberately include the world’s largest SVG on the page to throw you off? To find it, you needed to find the path by navigating to <code>/robots.txt</code>. The flag could be found at <code>/super-private-do-not-enter</code></p>\n<!-- -->\n<p>The Domain Name System (DNS) is the system that startups use to register .io websites. It is also a great source of information. Reverse lookups of IP addresses can tell us what hosting service an app is using, MX records can tell us what email provider they are using, and TXT records can give us some insight into supporting services they are using that aren’t necessarily obvious.</p>\n<p>For this flag we just needed to query the domains TXT records like so:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>dig TXT miskatonicuniversity.us</span></p></div><br></code></p></div>\n<p>This would return the flag in the “Answer Section” of the result.</p>\n<h3 id=\"scoped-bulletins\"><strong>scoped bulletins</strong><a target=\"_blank\" href=\"https://supabase.com/blog/how-to-hack-the-base#scoped-bulletins\">#</a></h3>\n<p>This one was a little more involved. If you were observing the requests that the web app was making you would have seen a request to the apps PostGREST endpoint. So decided to throw in a little extra spice.</p>\n<p>If you had explored the “Sign Up” page, you would have noticed the message that only Miskatonic University staff can register, if you didn’t have a miskatonicuniversity.us email address you couldn’t register.</p>\n<p>Unfortunately being a consultant first and developer second, I chose to only validate this requirement on the client side, meaning we can “Inspect” the DOM of the button and re-enable the button action.</p>\n<p>Fill out the form with your account information, check the hCaptcha, find the button element in the DOM, double click the “disabled” property and delete it. Simple!</p>\n<!-- -->\n<p>Or at least it would have been simple if you did this during a quiet period. For reasons known only to my coffee levels that morning, this Supabase project did not have Custom SMTP setup, meaning a very strict rate limit of two emails per hour.</p>\n<p>If you tried this during a busy period there was an extra step of setting up a script to bot the registration. The hCaptcha field was checked for but didn’t need to be valid so this was slightly easier than it sounds.</p>\n<p>Unfortunately, more than half of the successful registrations were for people trying to register a miskatonicuniveristy.us email account, so I needed to apply an emergency fix to filter out these attempts so they wouldn’t consume the SMTP limit (and Supabase’s bounce rate).</p>\n<p>I won’t go into details about how you could have scripted this, you could have used your language of choice (i.e. java), or used the Intruder feature of Burp Suite.</p>\n<p>Regardless of how hard your registration journey was, once you receive the confirmation email in your inbox the hunt is almost over. Clicking the link in the email will confirm your account with the Supabase project, optionally you could change the redirect link to the real URL of the app but your account will be registered regardless.</p>\n<p>From here you just needed to login to the app and be presented the flag.</p>\n<h3 id=\"open-schema\"><strong>open schema</strong><a target=\"_blank\" href=\"https://supabase.com/blog/how-to-hack-the-base#open-schema\">#</a></h3>\n<p>If you had got this far, you may have noticed an error message when querying the PostGREST API of the project. We can change the schema we are querying via the “Accept-Profile” header, when changing this to a schema that hasn’t been exposed to the API or doesn’t exist, we would be presented with an error message.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>curl 'https://ubssibzsnwtwbbvbhbvb.supabase.co/rest/v1/bulletins?select=*' \\</span></p></div><div><p><span>_<!-- -->10</span></p><p><span> -H 'accept-profile: other_schema' \\</span></p></div><div><p><span>_<!-- -->10</span></p><p><span> -H \"apikey: $ANON_KEY\" \\</span></p></div><div><p><span>_<!-- -->10</span></p><p><span> -H \"authorization: Bearer $ANON_KEY\"</span></p></div><br></code></p></div>\n<p>“The schema must be one of the following: public, information_schema, storage”</p>\n<p>It would appear that the information_schema schema is exposed on this project. Information schemas, you should be aware, are a really bad thing to expose publicly. This is where all of the information about our database can be queried, including tables, and roles.</p>\n<p>Lets check out the tables table in the information schema, specifically the tables in the public schema. To do this we modify our cURL command like this, noting the changes to the accept-profile header, and the parameters in the url:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>curl 'https://ubssibzsnwtwbbvbhbvb.supabase.co/rest/v1/tables?select=table_name,table_schema&amp;table_schema=eq.public' \\</span></p></div><div><p><span>_<!-- -->10</span></p><p><span> -H 'accept-profile: information_schema' \\</span></p></div><div><p><span>_<!-- -->10</span></p><p><span> -H \"apikey: $ANON_KEY\" \\</span></p></div><div><p><span>_<!-- -->10</span></p><p><span> -H \"authorization: Bearer $ANON_KEY\"</span></p></div><br></code></p></div>\n<p>This returns a JSON array that containing all the table names in the public schema:</p>\n<p><code>[{\"table_name\": \"bulletins\",\"table_schema\":\"public\"}, {\"table_name\":\"staff\",\"table_schema\":\"public\"}, {\"table_name\":\"staff_only\",\"table_schema\":\"public\"}]</code></p>\n<p>The bulletins table we already knew about, but staff and staff_only are new to us. The staff_only table will be relevant for the next flag, here we are interested in the staff table.</p>\n<p>We are almost there, and now that we understand how to query the schema with our cURL commands, its as simple as updating our request to query the staff table in the public schema:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>curl 'https://ubssibzsnwtwbbvbhbvb.supabase.co/rest/v1/staff' \\</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>-H 'accept-profile: public' \\</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>-H \"apikey: $ANON_KEY\" \\</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>-H \"authorization: Bearer $ANON_KEY\"</span></p></div><br></code></p></div>\n<p>This will return the full contents of the staff table, which includes our first intermediate flag!</p>\n<h3 id=\"weak-password\"><strong>weak password</strong><a target=\"_blank\" href=\"https://supabase.com/blog/how-to-hack-the-base#weak-password\">#</a></h3>\n<p>This was the last flag to be found. Despite the clues I had placed throughout the site, no one chose to try to brute force the password of <a target=\"_blank\" href=\"mailto:herbert.west@miskatonicuniversity.us\">herbert.west@miskatonicuniversity.us</a>. This can be attributed to my failure to anticipate the honesty of our hackers who fairly thought that a dictionary attack would have been considered a Denial of Service technique.</p>\n<p>Despite the clue we left on social media, finding this flag was easier said then done, lets use Burp Suite’s Intruder tool for this demonstration. Sorry Burp Suite Community Edition users!</p>\n<p>Using Burps inbuilt browser (the “Open Browser” button in the “Proxy”, “Intercept” menu), navigate to /sign-in, enter <a target=\"_blank\" href=\"mailto:herbert.west@miskatonicuniversity.us\">herbert.west@miskatonicuniversity.us</a> as the email, and anything as the password, press the Sign in button.</p>\n<p>Under Burp Suites “Proxy” “HTTP History” panel, find the POST request of this form. Your headers may look different based on your environment.</p>\n<!-- -->\n<p>Right click this and “Send to Intruder”. In the Intruder panel. Find the password you entered and highlight the whole text. Click the “Add $” button to add the field as your Intruder target.</p>\n<!-- -->\n<p>If you are a dinosaur like me, you would load a password file like “Rockyou.txt”.</p>\n<p>Supabase Auth has a rate limit for sign in requests based on certain heuristics so we need to throttle our requests to about one request per 2000 milliseconds. You can do this in the “Resource Pool” section, create a new resource pool with maximum concurrent requests of 1 and delay between requests of 2000 milliseconds. From here on it is just a waiting game for Intruder to return us a valid result.</p>\n<p>Should I have included a password higher up on most wordlists? Yes, yes I should have.</p>\n<p>Once you have found the right password (Password123), it’s not over yet. Logging in with these credentials will only show you the old client side validation flag.</p>\n<p>Remember the staff_only table we discovered in the “open schema” flag previously? Well now is our chance to exploit this. The last thing we need to do is leverage our staff authorisation to query this table.</p>\n<p>In your browser with DevTools open and while logged in as Herbert West refresh the home page to get the request to bulletins we used in the “scoped bulletins” flag above. In the Network panel, right click and “copy as curl”. In the command line, modify the path from <code>/bulletins?select=*&amp;date=gt.2001-01-01</code> to <code>/staff_only</code> this will return our second intermediate flag.</p>\n<h3 id=\"internet-archive\"><strong>internet archive</strong><a target=\"_blank\" href=\"https://supabase.com/blog/how-to-hack-the-base#internet-archive\">#</a></h3>\n<p>While not the last flag to be captured, this was the least captured flag until <a href=\"https://x.com/supabase/status/1866750434435539221\" target=\"_blank\">this tweet</a> tipped off our competition leaders.</p>\n<p>The Internet Archives Wayback Machine is a great resource for information gathering when assessing a website.</p>\n<p>To find this flag, hackers needed to search the Wayback Machine for URLs. This is as simple as entering the domain in the Wayback Machines search bar and navigating to the “URLs” section.</p>\n<p>This will bring up a list of all the URLs that the Internet Archive has captured for that domain.</p>\n<p>There is usually a lot of noise in here, and being a nextjs app ours is no different. Looking closely at the results however we can see a path called <code>/even-more-super-private-do-not-enter</code> . Navigating here will reward us with the last intermediate flag</p>\n<!-- -->\n<h3 id=\"expert-flag\"><strong>expert flag</strong><a target=\"_blank\" href=\"https://supabase.com/blog/how-to-hack-the-base#expert-flag\">#</a></h3>\n<p>The expert flag gets its label based on the number of hoops hackers need to jump through to retrieve it.</p>\n<p>Our journey for this flag starts with the other schema we found in the “open schema” flag error message - storage.</p>\n<p>If you are familiar with Supabase, you will know that the storage schema is the same across every project. Each Supabase project has a table in the storage schema called objects, querying this will return all the files in all the buckets.</p>\n<p>For some reason the owners of this project (read: me) have decided to expose this table, allowing anyone to see the full list of objects within all the projects buckets.</p>\n<!-- -->\n<p>Lets query this table using our handy dandy cURL technique:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>curl '&lt;https://ubssibzsnwtwbbvbhbvb.supabase.co/rest/v1/objects?select=name&gt;' \\</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>-H 'accept-profile: storage' \\</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>-H \"apikey: $ANON_KEY\" \\</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>-H \"authorization: Bearer $ANON_KEY\"</span></p></div><br></code></p></div>\n<p>The results we get should be mostly familiar to us. These are the images associated with the bulletins on the home page. There are two README.md files in there however that we haven’t seen before. Lets download them to see whats in them.</p>\n<p>This is a public bucket so we don’t need to worry about crafting a cURL command with authorisation headers. Just copy the URL of one of the images (right click → “Copy Image Address”) and substitute the filename for our readme file. We will be using README.md (1) for the rest of this tutorial because it has more information in it. Your URL should look something like this: <code>/storage/v1/object/public/university-news/README (1).md</code></p>\n<p>Viewing this directly in our browser reveals some information its clear we shouldn’t be allowed to see. At the bottom of the file is a reference about how to log into a database server.</p>\n<!-- -->\n<p>Lets try to connect to this database. We will need to translate the information in the README into a connection string. Looking at an example connection string in our example Supabase project we can see a pooler connection string has the pattern:</p>\n<p><code>postgresql://[USER].[PROJECT_ID]:[PASSWORD]@[REGION].pooler.supabase.com:6543/postgres</code></p>\n<p>So after plugging in the details from the README file into this connection string and prepending it with “psql” (our postgres client) we will be presented with an error message that our IP address is restricted.</p>\n<p>The hint in the readme suggests we can only connect from an EC2 in ap-southeast-2. So the owners of this database were smart enough to apply IP restrictions but dumb enough to open up the full IP range of every EC2 in the Sydney AWS region? Trust me, just go with it.</p>\n<p>Thankfully AWS has a generous free tier, so signing up for another account using address plussing (allegedly) is all we need to spin up an EC2 in Sydney.</p>\n<p>I will not go into detail about this step, check out AWS’s documentation for creating one <a target=\"_blank\" href=\"https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/EC2_GetStarted.html\">here</a>, login to the instance and install a postgres client. I recommend using an Ubuntu image as its slightly easier to install the psql client using <code>sudo apt install postgres-client-15</code></p>\n<p>Now that we have our EC2 setup, lets use our connection string to successfully connect to the database.</p>\n<p>Our quest is not over yet however. Checking out the data in the database using <code>\\\\dt</code> will reveal a table called “secrets”. Trying to query that data only get us a permission denied error.</p>\n<p>Now we need to do some database spelunking. Cutting to the chase, we are able to query the available roles in the pg_roles table: <code>SELECT * FROM pg_roles;</code> this will reveal all the roles within the db including a lot of built in and default roles. One that should have caught our eyes is the “devotee” role. Assume this role using the command <code>SET ROLE devotee;</code> , we can now query the secrets table using <code>SELECT * FROM secrets;</code></p>\n<p>And with that you have now collected all the flags. Congratulations!</p>\n<p>Now that you are a seasoned hacker, take a look at our <a target=\"_blank\" href=\"https://supabase.com/.well-known/security.txt\">security.txt</a> file to take part in our hackerone program to help make Supabase a safer place!</p>\n<p>Once again, thanks to all of those that participated and we will see you in the next one!</p>\n<hr></div></article>"
