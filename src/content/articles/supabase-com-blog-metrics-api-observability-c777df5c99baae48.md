contentHtml: "<article><div>\n<p>We've published <a target=\"_blank\" href=\"https://supabase.com/docs/guides/telemetry/metrics\">enhanced documentation for the Metrics API</a> so that you can stream your Supabase database telemetry into any Prometheus-compatible observability stack. Whether you use Grafana Cloud, Datadog, AWS Managed Prometheus, or a self-hosted setup, the Metrics API gives you full control over how you monitor, visualize, and alert on your database infrastructure.</p>\n<p>Supabase Studio includes built-in observability dashboards. They work well for quick health checks. But production systems rarely exist in isolation.</p>\n<p>Your application probably already has an observability stack. APM traces flow into Datadog. Application logs land in Grafana Loki. Infrastructure metrics feed Prometheus. When your database metrics live in a separate silo, you lose context. You cannot correlate a spike in API latency with database connection saturation. You cannot overlay query performance against deployment events.</p>\n<p>The Metrics API fixes this. It exposes roughly 200 Postgres performance and health metrics in Prometheus exposition format. One scrape job. One unified view of your entire stack.</p>\n<p>Every Supabase project has a metrics endpoint:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>https://&lt;project-ref&gt;.supabase.co/customer/v1/privileged/metrics</span></p></div><br></code></p></div>\n<p>Authentication uses HTTP Basic Auth with your service role credentials. The endpoint emits metrics covering:</p>\n<ul>\n<li>\n<p><strong>CPU and memory utilization.</strong> Track resource pressure before it becomes a problem.</p>\n</li>\n<li>\n<p><strong>Disk I/O and WAL statistics.</strong> Identify storage bottlenecks and replication lag.</p>\n</li>\n<li>\n<p><strong>Connection pool metrics.</strong> Monitor Supavisor and Postgres connection saturation.</p>\n</li>\n<li>\n<p><strong>Query performance data.</strong> Catch slow queries and index regressions.</p>\n</li>\n</ul>\n<p>The full metric set refreshes every minute. Scrape it once per minute to stay in sync.</p>\n<p>We chose Prometheus exposition format deliberately. It is the lingua franca of cloud-native observability. This single decision unlocks compatibility with:</p>\n<ul>\n<li>\n<p><strong>Grafana Cloud.</strong> Their managed Prometheus instance scrapes your endpoint directly. Works on Free and Pro tiers.</p>\n</li>\n<li>\n<p><strong>Datadog.</strong> Configure the Datadog Agent with OpenMetrics integration, or use Prometheus remote write.</p>\n</li>\n<li>\n<p><strong>AWS Managed Prometheus (AMP).</strong> Native AWS integration for teams already in that ecosystem.</p>\n</li>\n<li>\n<p><strong>Grafana self-hosted.</strong> For teams running their own metrics storage.</p>\n</li>\n<li>\n<p><strong>Any Prometheus-compatible backend.</strong> If it speaks PromQL, it works with Supabase.</p>\n</li>\n</ul>\n<p>This is what playing well with open standards looks like. We do not lock your telemetry into a proprietary format. You own your data. You choose your tools.</p>\n<p>With 200 metrics available, where do you start? Here are the signals and <a target=\"_blank\" href=\"https://github.com/supabase/supabase-grafana/blob/main/docs/example-alerts.md\">alerts</a> that matter most:</p>\n<ul>\n<li>\n<p><strong>Connection saturation.</strong> Monitor active connections against your pool limits. Alert before you hit the ceiling.</p>\n</li>\n<li>\n<p><strong>CPU and memory pressure.</strong> Sustained high utilization indicates workload growth or inefficient queries. Correlate with slow query logs to find the culprit.</p>\n</li>\n<li>\n<p><strong>Disk I/O wait.</strong> High I/O wait times suggest storage bottlenecks. This often points to missing indexes or queries that scan too much data.</p>\n</li>\n<li>\n<p><strong>Replication lag.</strong> If you use read replicas, monitor lag to ensure consistency. Alert when lag exceeds acceptable thresholds.</p>\n</li>\n<li>\n<p><strong>Spikes in client connections.</strong> If you see connection metrics crowding your limits or frequent saturation, review how your applications connect. Consider using the <a target=\"_blank\" href=\"https://supabase.com/docs/guides/database/connecting-to-postgres#dedicated-pooler\">dedicated pooler</a> (PgBouncer) with sane pool sizes instead of many direct connections, especially for chatty or bursty workloads.</p>\n</li>\n<li>\n<p><strong>Spiky workloads.</strong> You may find that you are running periodic jobs during peak traffic hours, use the charts to determine if these spikes are within acceptable bounds or if you could optimise your job scheduling.</p>\n</li>\n<li>\n<p><strong>Development and Maintenance.</strong> Were you running an expensive query on every page load of your app? Use the time range filters to confirm if your optimisations have improved performance and reduced strain on your instance.</p>\n</li>\n</ul>\n<p>Metrics without alerts are just pretty graphs. The real value comes from automated detection.</p>\n<ul>\n<li>\n<p><strong>Right-sizing alerts.</strong> Trigger when CPU or memory consistently exceeds 80% utilization. This gives you time to upgrade before users notice degradation.</p>\n</li>\n<li>\n<p><strong>Saturation alerts.</strong> Fire when connection pools approach capacity. A few minutes of warning lets you investigate before connections start failing.</p>\n</li>\n<li>\n<p><strong>Index regression alerts.</strong> Monitor query performance metrics after deployments. Catch missing indexes before they slow down production traffic.</p>\n</li>\n<li>\n<p><strong>Anomaly detection.</strong> Tools like Datadog can learn normal patterns and alert on deviations. This catches problems you did not anticipate.</p>\n</li>\n<li>\n<p>Some more example configurations for alerts on database down, replication lag, and database size can be found in our <a target=\"_blank\" href=\"https://github.com/supabase/supabase-grafana/blob/main/docs/example-alerts.md\">GitHub repo</a>.</p>\n</li>\n</ul>\n<p>The Metrics API reflects how we think about infrastructure. Supabase is built on open source: Postgres, PostgREST, GoTrue, Realtime. Our observability follows the same philosophy.</p>\n<p>Prometheus exposition format is an open standard. The <code>supabase-grafana</code> repository is MIT licensed. You can fork it, modify it, run it anywhere. No vendor lock-in. No proprietary agents. No data trapped in systems you do not control.</p>\n<p>When you outgrow Grafana Cloud, migrate to self-hosted Mimir. When your team standardizes on Datadog, reconfigure the scrape target. Your metrics remain portable because we chose open standards from the start.</p>\n<p>The Metrics API is available now on all hosted Supabase projects. Check the <a target=\"_blank\" href=\"https://supabase.com/docs/guides/telemetry/metrics\">updated documentation</a> for integration guides covering:</p>\n<ul>\n<li>\n<p>Grafana Cloud setup</p>\n</li>\n<li>\n<p>Self-hosted Prometheus configuration</p>\n</li>\n<li>\n<p>Datadog Agent integration</p>\n</li>\n<li>\n<p>Vendor-agnostic options</p>\n</li>\n</ul>\n<p>You will also notice a new banner in Studio's Observability views. It surfaces these options directly in the interface, making it clear that built-in dashboards are just one choice among many.</p>\n<p>Share your dashboards online and tag us on Twitter. We love the inspiration that comes from a cool dashboard layout.</p></div></article>"
