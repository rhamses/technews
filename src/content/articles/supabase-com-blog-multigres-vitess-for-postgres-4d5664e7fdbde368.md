contentHtml: "<article><div><p>Today we’re welcoming <a target=\"_blank\" href=\"https://www.linkedin.com/in/sougou/\">Sugu</a>, the co-creator of Vitess, to the Supabase team. He is joining Supabase to build <strong>Multigres: Vitess for Postgres</strong>.</p>\n<p>Vitess is a database clustering system for scaling <strong>MySQL</strong> (it doesn’t work for Postgres). Vitess adds:</p>\n<ul>\n<li>Sharding</li>\n<li>Connection pooling</li>\n<li>Query routing</li>\n<li>Resiliency and failover</li>\n<li>Cloud-native orchestration (Kubernetes)</li>\n</ul>\n<p>Sugu originally built Vitess at YouTube. This (outdated) video explains some of the concepts and motivation:</p>\n<p></p>\n<p><small><p>* The video mentions 3-5ms latency. This was for hard disks. SSDs now provide sub-millisecond\nlatency.</p></small></p>\n<p>Multigres is a new proxy that sits in front of your Postgres database. It shares the same goals as Vitess but it will be focused on the Postgres ecosystem. The ultimate goal of a sharded solution is scale:</p>\n<!-- -->\n<p>Sharding inevitably requires tradeoffs, so one of the top priorities for this project is <strong>compatibility:</strong> something that the Postgres community values above almost everything else.</p>\n<p>We plan to give developers a gradual on-ramp, providing simple connection pooling on the lower-end, high-availability on the top end, all the way through to a sharded solution as you grow into petabyte-scale.</p>\n<h2 id=\"why-multigres-for-postgres\">Why Multigres for Postgres?<a target=\"_blank\" href=\"https://supabase.com/blog/multigres-vitess-for-postgres#why-multigres-for-postgres\">#</a></h2>\n<p>Sugu <a target=\"_blank\" href=\"https://x.com/ssougou/status/1932445665512284645\">shared</a> some of his personal thoughts on the project and timing:</p>\n<blockquote><p>For some time, I've been considering a Vitess adaptation for Postgres, and this feeling had been\ngradually intensifying. The recent explosion in the popularity of Postgres has fueled this into\na full-blown obsession. As these databases grow, users are going to face a hard limit once they\nmax out the biggest available machine.</p><p>The project to address this problem must begin now, and I'm convinced that Vitess provides the\nmost promising foundation. After exploring various environments, I found the best fit with\nSupabase. I'm grateful for how they welcomed me. Furthermore, their open-source mindset and\nfully remote work culture resonated with me.</p><p>Now, it's time to make this happen.</p><div><p><img alt=\"Sugu, co-creator of Vitess. avatar\" src=\"https://supabase.com/_next/image?url=%2Fimages%2Fblog%2Favatars%2Fsugu.jpg&w=64&q=75\"></p><figcaption><p>Sugu, co-creator of Vitess.</p></figcaption></div></blockquote>\n<p>There will be no fundamental changes to the way Supabase operates today, especially for smaller workloads.</p>\n<p>That said, there are some overlapping initiatives at Supabase and we will assess how to build the same experience with Multigres. The largest overlap is with <a target=\"_blank\" href=\"https://supabase.com/blog/supavisor-1-million\">Supavisor</a> (Vitess has vttablet and vtgate). We’ll spend some time assessing the viability of building Vitess around existing Postgres poolers and then decide the best steps forward.</p>\n<p>Another important initiative at Supabase is OrioleDB, which is a scalable storage engine for Postgres. OrioleDB and Multigres are complementary and we will work on both simulateneously. Both are extremely important to us.</p>\n<p>And importantly, one non-goal: Supabase will be 100% focused on Postgres. If you are using MySQL then we recommend that you use Vitess.</p>\n<p>Like Vitess, Multigres will be open source using the same license: Apache 2. You can follow the repo <a target=\"_blank\" href=\"https://github.com/multigres/multigres\">here</a>.</p>\n<p>Remember to “Watch” the repo to follow our releases. Note: we will initially be focused on getting the project to a stable state and then we will open it up to contributions.</p>\n<p>We are looking for partners who would like to use Multigres - either with self-hosting or on the Supabase platform. If you already use Postgres and you are hitting scaling limits, <a target=\"_blank\" href=\"https://forms.supabase.com/multigres\">get in touch</a>.</p>\n<p>We are assembling a team to build Multigres. If you are a Go programmer consider applying <a target=\"_blank\" href=\"https://jobs.ashbyhq.com/supabase/2e718684-4f75-4a99-8d6b-3b6bd44e4228\">here</a>.</p></div></article>"
