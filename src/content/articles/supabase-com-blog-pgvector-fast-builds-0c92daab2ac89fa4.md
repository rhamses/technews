contentHtml: "<article><div>\n<p>pgvector 0.6.0 was released today, with a significant improvement: parallel builds for HNSW indexes. Building an HNSW index is now up to 30x faster for unlogged tables.</p>\n<p>This release is a huge step forward for pgvector, making it easier to tune HNSW build parameters and increase search accuracy and performance.</p>\n<p>We explored <a target=\"_blank\" href=\"https://supabase.com/blog/increase-performance-pgvector-hnsw#how-does-hnsw-work\">how HNSW works</a> in an earlier post, so as a quick recap: HNSW is an algorithm for approximate nearest neighbor search. It uses proximity graphs and consists of two parts: hierarchical and navigatable small world. It operates over multiple layers with different densities or distances between nodes, where layers represent different connection lengths between nodes. Thus allowing HNSW to search, insert, and delete in linearithmic time.</p>\n<p>Prior to 0.6.0, pgvector only supported building indexes using a single thread - a big bottleneck for large datasets. For example, building an index for 1 million vectors of 1536 dimensions would take around 1 hour and 27 minutes (with <code>'m'=16, 'ef_construction'=200</code>).</p>\n<p>With parallel index builds you can build an index for the same dataset in 9.5 minutes - 9 times faster:</p>\n<p>We tested index build time with the <a target=\"_blank\" href=\"https://huggingface.co/datasets/KShivendu/dbpedia-entities-openai-1M\">dbpedia-entities-openai-1M</a> dataset (1 million vectors, 1536 dimensions) to compare the performance of parallel and single-threaded index HNSW builds. At the same time, we verified that the resulting indexes are the same in terms of accuracy and queries per second (QPS).</p>\n<p>We ran benchmarks on various database sizes to see the impact of parallel builds:</p>\n<ul>\n<li>4XL instance (16 cores 64GB RAM)</li>\n<li>16XL instance (64 cores 256GB RAM)</li>\n</ul>\n<h3 id=\"4xl-instance-16-cores-64gb-ram\">4XL instance (16 cores 64GB RAM)<a target=\"_blank\" href=\"https://supabase.com/blog/pgvector-fast-builds#4xl-instance-16-cores-64gb-ram\">#</a></h3>\n<p>This benchmark used the following parameters:</p>\n<table><thead><tr><th></th><th>0.5.1</th><th>0.6.0</th></tr></thead><tbody><tr><td>mainenance_work_mem</td><td>30GB</td><td>30GB</td></tr><tr><td>max_parallel_maintenance_workers</td><td>-</td><td>15</td></tr></tbody></table>\n<p><code>max_parallel_maintenance_workers</code> controls how many parallel threads are used to build an index. In further sections we will refer to the total number of workers, including the leader.</p>\n<p>The index build time is 7-9 times faster for 0.6.0, while queries per second and accuracy stay the same for both versions:</p>\n<ul>\n<li><code>v0.5.1</code>: averaged 938 QPS and 0.963 accuracy across all benchmarks.</li>\n<li><code>v0.6.0</code>: averaged 950 QPS and 0.963 accuracy across all benchmarks.</li>\n</ul>\n<h3 id=\"16xl-instance-64-cores-256gb-ram\">16XL instance (64 cores 256GB RAM)<a target=\"_blank\" href=\"https://supabase.com/blog/pgvector-fast-builds#16xl-instance-64-cores-256gb-ram\">#</a></h3>\n<p>You can further improve index build performance using a more powerful instance (up to 13.5x for these parameters).</p>\n<p>The index build time is not linearly proportional to the number of cores used. A sensible default for <code>max_parallel_maintenance_workers</code> is <code>CPU count / 2</code> , the default we set on the Supabase platform. Accuracy and QPS are not affected by <code>max_parallel_maintenance_workers</code>.</p>\n<h3 id=\"embeddings-with-unlogged-tables\">Embeddings with unlogged tables<a target=\"_blank\" href=\"https://supabase.com/blog/pgvector-fast-builds#embeddings-with-unlogged-tables\">#</a></h3>\n<p>Building time can be reduced <em>even further</em> using unlogged tables.</p>\n<p>An unlogged table in Postgres is a table whose modifications are not recorded in the write-ahead log (trading performance for data reliability). Unlogged tables are a great option for embeddings because the raw data is often stored separately and the embeddings can be recreated from the source data at any time.</p>\n<p>One of the steps of index creation is the final scan and WAL writing. This is generally short but not parallelizable.
