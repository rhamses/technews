We'll show you how to run 1 million Open AI embeddings at ~1800 queries per second with 91% accuracy, or 670 queries per second with 98% accuracy.</li>\n</ol>\n<p>We've used the <a target=\"_blank\" href=\"https://github.com/erikbern/ann-benchmarks\">ANN Benchmarks</a> methodology, a standard for benchmarking vector databases.</p>\n<p>The key elements are:</p>\n<ul>\n<li><strong>Helper scripts:</strong> a Python test runner which is responsible for data upload, index creation, and query execution. Both of these help with RAM utilization.</li>\n</ul>\n<p>All compute add-ons available on Supabase were used to run our benchmarks. We'll release those benchmarks as soon as we have them.</p>\n<p>It's been about 5 months since we <a target=\"_blank\" href=\"https://supabase.com/blog/openai-embeddings-postgres-vector\">added</a> pgvector to the platform. Since then we've discovered a few other important things to keep in mind.</p>\n<h3 id=\"increasing-lists-improves-performance\">Increasing lists improves performance<a target=\"_blank\" href=\"https://supabase.com/blog/pgvector-performance#increasing-lists-improves-performance\">#</a></h3>\n<p>Another way to improve performance without throwing more compute would be to increase <code>lists</code>.</p>\n<p>We ran a test to measure the impact of list size: we uploaded 90,000 vectors from the Wikipedia dataset and then queried 10,000 vectors from the same dataset. The documentation recommends to use <code>lists</code> constant of <code>number of vectors / 1000</code>. In this case, it would be 90.</p>\n<p>But as our experiment shows, we can improve QPS if we increase <code>lists</code> (i.e. with more lists in the index we need to get less index data to get the same accuracy). So for 95% accuracy, we can take any of:</p>\n<ul>\n<li>3% of index data = 270 lists</li>\n<li>6% of index data = 90 lists</li>\n<li>13% of index data = 30 lists</li>\n</ul>\n<p>This also has an important caveat: building the index takes longer with more lists. Here we measure the index build time for a dataset containing 900,000 vectors:</p>\n<p>So if you can afford an index build time of 1 hour or more, you can go with <code>lists=5000</code> (<code>number of vectors / 200</code>) or more!</p>\n<div><p>You may need to increase <code>maintenance_work_mem</code> to be able to create an index with high values for <code>lists</code>. In other words, real embeddings are very far from being randomly distributed. This might seem obvious, but it's an important call-out for benchmarks.</p>\n<p>Embeddings generated for similarity search using “real world data” will be more correlated, so the accuracy will be higher as well. You can see the difference in this chart using 10,000 Wikipedia embeddings, vs 10,000 randomly-generated embeddings:</p>\n<p>Armed with all this information, we can safely give you a few tips and strategies for optimizing your pgvector workloads.</p>\n<h3 id=\"tips\">Tips<a target=\"_blank\" href=\"https://supabase.com/blog/pgvector-performance#tips\">#</a></h3>\n<p>First, a few generic tips which you can pick and choose from:</p>\n<ol>\n<li><strong>Adjust your Postgres config.</strong> It should be aligned with RAM &amp; CPU cores. <a target=\"_blank\" href=\"https://gist.github.com/egor-romanov/323e2847851bbd758081511785573c08\">Find more details here</a>.</li>\n<li>Prefer <code>inner-product</code> to <code>L2</code> or <code>Cosine</code> distances if your vectors are normalized (like <code>text-embedding-ada-002</code>). If embeddings are not normalized, <code>Cosine</code> distance should give the best results with an index.</li>\n<li><strong>Pre-warm your database.</strong> Implement the warm-up technique we described earlier before transitioning to production.</li>\n<li><strong>Establish your workload.</strong> Increasing the lists constant for the pgvector index can accelerate your queries (at the expense of a slower build). For instance, for benchmarks with OpenAI embeddings, we employed a <code>lists</code> constant of 2000 (<code>number of vectors / 500</code>) as opposed to the suggested 1000 (<code>number of vectors / 1000</code>).</li>\n<li><strong>Benchmark your own specific workloads.</strong> Doing this during cache warm-up helps gauge the best value for the <code>probes</code> constant, balancing accuracy with QPS.</li>\n</ol>\n<h3 id=\"going-into-production\">Going into production<a target=\"_blank\" href=\"https://supabase.com/blog/pgvector-performance#going-into-production\">#</a></h3>\n<p>Before running your pgvector workload in production, here are a few steps you can take to maximize performance.</p>\n<ol>\n<li>Over-provision RAM during preparation. You can scale down in step <code>5</code>, but it's better to start with a larger size to get the best results for RAM requirements. (We'd recommend at least 8XL if you're using Supabase.)</li>\n<li>Upload your data to the database. If you use <a target=\"_blank\" href=\"https://supabase.com/docs/guides/ai/python/api\"><code>vecs</code></a> library, it will automatically generate an index with default parameters.</li>\n<li>Run a benchmark using randomly generated queries and see the results. Again, you can use <code>vecs</code> library with the <code>ann-benchmarks</code> tool. Do it with probes set to 10 (default) and then with probes set to 100 or more, so QPS will be lower than 10.</li>\n<li>Take a look at the RAM usage, and save it as a note for yourself. You would likely want to use compute add-on in the future that would have the same amount of RAM as used at the moment (both actual RAM usage and RAM used for cache and buffers).</li>\n<li>Scale down your compute add-on to the one that would have the same amount of RAM as used at the moment.</li>\n<li>Repeat step 3. to load the data into RAM. You should see that QPS is increased on subsequent runs, and stop when it no longer increases. Then repeat the benchmark with probes set to a higher value as well if you didn't do it before on that compute add-on size.</li>\n<li>Run a benchmark using real queries and see the results. You can use <code>vecs</code> library for that as well with <code>ann-benchmarks</code> tool. Do it with probes set to 10 (default) and then gradually increase/decrease probes value until you see that both accuracy and QPS match your requirements.</li>\n<li>If you want higher QPS and you don't expect to have frequent inserts and reindexing, you can increase <code>lists</code> constantly. Higher <code>lists</code> mean that index will build slower, but you can achieve better QPS and accuracy. Higher probes mean that select queries will be slower, but you can achieve better accuracy.</li>\n</ol>\n<p>pgvector is still early in development.
