contentHtml: "<article><div>\n<p>Today we're releasing <a target=\"_blank\" href=\"https://github.com/supabase/wrappers\">Supabase Wrappers</a>, a framework for building Postgres Foreign Data Wrappers (FDW) which connects Postgres to external systems.</p>\n<p>Foreign Data Wrappers are a core feature of PostgreSQL. We've extended this feature to query other databases or any other external system (including third-party APIs), using SQL.</p>\n<p>We're releasing Wrappers today in Alpha, with support for <a target=\"_blank\" href=\"https://supabase.github.io/wrappers/firebase/\">Firebase</a> and <a target=\"_blank\" href=\"https://supabase.github.io/wrappers/stripe/\">Stripe</a>. Wrappers for Clickhouse, BigQuery, and Airtable are under development.</p>\n<p>Let's step through a full example using the Stripe Wrapper.</p>\n<h3 id=\"connecting-to-stripe\">Connecting to Stripe<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-foreign-data-wrappers-rust#connecting-to-stripe\">#</a></h3>\n<p>First, let's give your Postgres database some authentication details to access your Stripe account:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>create server stripe_server</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>foreign data wrapper stripe_wrapper</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>options (api_key 'sk_test_xxx');</span></p></div><br></code></p></div>\n<h3 id=\"creating-a-foreign-table\">Creating a Foreign Table<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-foreign-data-wrappers-rust#creating-a-foreign-table\">#</a></h3>\n<p>Now we can map your Stripe data to Foreign Tables, which are just like normal tables except that the data exists <em>outside</em> of your database.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>-- Create a foreign table for your Stripe products</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>create foreign table products (</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  id text,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  name text,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  description text,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  default_price text</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>)</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>server my_stripe_server</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>options ( object 'products' );</span></p></div><br></code></p></div>\n<h3 id=\"accessing-remote-data\">Accessing remote data<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-foreign-data-wrappers-rust#accessing-remote-data\">#</a></h3>\n<p>After setting up your foreign table, you can query you Stripe products directly from your database:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>-- Fetch all your stripe products in Postgres</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>select *</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>from products</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>limit 10;</span></p></div><br></code></p></div>\n<p>Or from your application, using one of our client libraries:</p>\n<div><p><code><br><div><p><span>_<!-- -->11</span></p><p><span>import { createClient } from '@supabase/supabase-js'</span></p></div><div><p><span>_<!-- -->11</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>const SUPABASE_URL = 'https://xyzcompany.supabase.co'</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>const SUPABASE_KEY = 'public-anon-key'</span></p></div><div><p><span>_<!-- -->11</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>const supabase = createClient(SUPABASE_URL, SUPABASE_KEY)</span></p></div><div><p><span>_<!-- -->11</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>const { data: stripeCustomers, error } = supabase</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  .from('products')</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  .select('id, name, description, default_price')</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  .limit(10)</span></p></div><br></code></p></div>\n<p><em>Note: we kept this example simple, however for API security and code organization, you should store your foreign data in a <a target=\"_blank\" href=\"https://supabase.com/docs/reference/javascript/initializing#api-schemas\">separate schema</a>.</em></p>\n<p>Once we've added more Wrappers, they enable various possibilities:</p>\n<ul>\n<li><strong>On-demand Big Data:</strong> Query your Data Warehouse on demand using Wrappers for Clickhouse, BigQuery, Snowflake, Oracle, and S3.</li>\n<li><strong>Simplified Onboarding:</strong> Migrate to Postgres from systems like Firebase, Microsoft SQL Server, and Airtable.</li>\n<li><strong>Simplified Development:</strong> Create a new Stripe customer object within a Postgres function.</li>\n<li><strong>AI capabilities:</strong> Run AI queries from your database using OpenAI's API.</li>\n<li><strong>Caching:</strong> use Postgres triggers to insert data into in-memory databases like Redis.</li>\n<li><strong>SRE and DevOps:</strong> Query your infrastructure state, like AWS and DNS records.</li>\n<li><strong>Web3 Apps:</strong> integrate with IPFS and blockchains like Ethereum.</li>\n<li><strong>Financial Apps:</strong> Build Financial applications using wrappers around Finance APIs.</li>\n<li><strong>Community analytics:</strong> Analyze your community engagement with GitHub, Slack, Discord, and Twitter wrappers.</li>\n</ul>\n<p>In their 2017 <a target=\"_blank\" href=\"https://www.sciencedirect.com/science/article/abs/pii/S0169023X1730438X\">paper</a>, researchers from the University of Bologna investigated an approach to on-demand ETL:</p>\n<blockquote>\n<p>In traditional OLAP systems, the ETL process loads all available data in the data warehouse before users start querying them. In some cases, this may be either inconvenient (because data are supplied from a provider for a fee) or unfeasible (because of their size); on the other hand, directly launching each analysis query on source data would not enable data reuse, leading to poor performance and high costs. The alternative investigated in this paper is that of fetching and storing data on-demand.</p>\n</blockquote>\n<p>Their paper outlines the foundation for QETL (pronounced \"kettle\"): Query, Extract, Transform, Load. This differs from a more traditional ETL/ELT approach, where data is moved from one place to another. In QETL, the “Query” function allows data engineers to access data in a remote system even before moving it. This approach reduces the reliance on data engineering infrastructure, allowing teams to access operational insights faster.</p>\n<h3 id=\"the-benefits-of-qetl\">The benefits of QETL<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-foreign-data-wrappers-rust#the-benefits-of-qetl\">#</a></h3>\n<p>We've built upon this concept using PostgreSQL's FDW system. This a new tool for developers and data engineers, with several benefits:</p>\n<ol>\n<li><strong>Simplicity:</strong> the Wrappers API is just SQL, so data engineers don't need to learn new tools and languages.</li>\n<li><strong>On-demand:</strong> analytical data is available within your product without any additional infrastructure, and the time it takes to retrieve that data is close to executing a query on the source.</li>\n<li><strong>Always in sync:</strong> data which isn't moved will always be in sync. Developers can set up local views which re-map remote data into clean local schemas.</li>\n<li><strong>Integrated:</strong> large datasets are available within your application, and can be joined with your operational/transactional data.</li>\n<li><strong>Save on bandwidth:</strong> only extract/load what you need.</li>\n<li><strong>Save on time:</strong> avoid setting up additional data pipelines.</li>\n<li><strong>Save on Data Engineering costs:</strong> less infrastructure to be managed.</li>\n</ol>\n<h3 id=\"qetl--postgres\">QETL + Postgres<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-foreign-data-wrappers-rust#qetl--postgres\">#</a></h3>\n<p>How does this look in action? Assuming that all of your analytical data is stored in Snowflake, you could create a foreign table inside your Supabase database:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>create foreign table snowflake.order_history (</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  id bigint,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  ts timestamptz,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  event text,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  user_id uuid</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>)</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>server my_snowflake_warehouse</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>options (table 'order_history', rowid_column 'id');</span></p></div><br></code></p></div>\n<p>Now from your Supabase database you can query your Snowflake data directly:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>select * from snowflake.order_history limit 1000;</span></p></div><br></code></p></div>\n<p>You can even join remote data with your local tables to enrich existing operational data. For example, to figure out how many times a user has purchased something from your store:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>select</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  users.id,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  count(order_history.event)</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>from</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  snowflake.order_history</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  join auth.users on auth.users.id = snowflake.order_history.user_id</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>where order_history.event = 'purchase' and order_history.user_id = '&lt;some_user_id&gt;';</span></p></div><br></code></p></div>\n<p>We can either run these queries on demand or, for better query performance, we can run them in the background (using something like <a target=\"_blank\" href=\"https://supabase.com/docs/guides/database/extensions/pgcron\">pg_cron</a>), and materialize the data into a local table.</p>\n<p>This gives us the basis of QETL:</p>\n<ul>\n<li>Query: run on-demand SQL queries, directly from your Postgres database.</li>\n<li>Extract: run SQL <code>select</code> statements on external systems, either on demand or on a recurring basis.</li>\n<li>Transform: use SQL aggregations and CTEs to transform the data.</li>\n<li>Load: store transformed data into local tables for faster access.</li>\n</ul>\n<p>This is a two-way process. It's equally useful to offload large datasets from your Postgres database to your Data Warehouse. With FDWs, this can be as simple as:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>insert into snowflake.analytics</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>select * from analytics</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>where ts &gt; (now() - interval '1 DAY');</span></p></div><br></code></p></div>\n<p>On-demand ETL is a strong compliment for current ETL practices, and another tool in the toolbelt for Data Engineering and Developers that works with immediately with tools that interface with Postgres.</p>\n<h2 id=\"postgres-the-everything-interface\">Postgres, the everything interface<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-foreign-data-wrappers-rust#postgres-the-everything-interface\">#</a></h2>\n<p>In a recent Software Engineering <a target=\"_blank\" href=\"https://podcasts.apple.com/us/podcast/software-engineering-daily/id1019576853?i=1000580384354\">episode</a> Andy Pavlo (database Professor at Carnegie Mellon and Co-Founder of OtterTune), explored the future between “better databases” and “better interfaces” [00:37:18]:</p>\n<blockquote><p>Specialized engines are always going to outperform general-purpose ones. The question is whether\nthe specialized engine is going to have such a significant difference in performance that it can\novercome the limitations of a general purpose one.</p><p>...</p><p>The challenge oftentimes is this: is the benefit you're getting from a specialized engine\nbecause the <em>Engine</em> is different or the <em>API</em> is different?.</p><div><p><img alt=\"Andy Pavlo avatar\" src=\"https://supabase.com/_next/image?url=%2Fimages%2Fblog%2Favatars%2Fandy-pavlo.jpeg&w=64&q=75\"></p><figcaption><p>Andy Pavlo</p></figcaption></div></blockquote>\n<p>He goes on to explore the benefits of a Graph database vs a Relational database.</p>\n<p>Our recent release of <a target=\"_blank\" href=\"https://github.com/supabase/pg_graphql/\">pg_graphql</a> closes the gap on the graph use-case by building a GraphQL API directly into Postgres as an extension. While a specialized graph database might provide performance benefits over Postgres, perhaps one of the largest benefits is simply the Graph API which makes it easier to reason about the data.</p>\n<p>With the introduction of Wrappers, we're hoping to close the gap on even more of these type of workloads.</p>\n<p>An exciting part of the FDW approach is that it provides a common interface to the world: SQL. While it has many shortcomings, SQL is the lingua franca of data. Postgres' FDWs transform any API into a data set with a common interface. This “interface aggregator” is similar to the <a target=\"_blank\" href=\"https://medium.com/vicetech/graphql-the-great-aggregator-bcf52fe390d9\">promise</a> of GraphQL engines. The benefit of embedding this functionality in the database is that it exists at the <em>lowest level of the tech stack</em>. Everything that is built on top can leverage it. While Postgres cannot easily access the functionality of a GraphQL server, a GraphQL server can easily access the functionality of Postgres.</p>\n<p>The FDW interface also future-proofs Postgres. Instead of keeping up with the latest technological advances, Postgres can instead act as an interface whenever they develop. The recent advance in AI and ML is a great example of this: AI technology is developing faster than the time it would take to build a new “AI database”. With a FDW, Postgres can become the interface to this technology and many other technological advances in the future.</p>\n<p>Postgres has a builtin “Postgres FDW” allows querying one Postgres database from another. We've extended this functionality to support a variety of data sources, from Data Warehouses to APIs.\nThis release includes two initial wrappers: Stripe and Firebase</p>\n<table><thead><tr><th>Integration</th><th>Platform</th><th>Self-hosted</th><th><span>select</span></th><th><span>insert</span></th><th><span>update</span></th><th><span>delete</span></th></tr></thead><tbody><tr><td>Firebase</td><td>🚧</td><td>✅</td><td>✅</td><td>🚧</td><td>🚧</td><td>🚧</td></tr><tr><td>Postgres</td><td>✅</td><td>✅</td><td>✅</td><td>✅</td><td>✅</td><td>✅</td></tr><tr><td>Stripe</td><td>🚧</td><td>✅</td><td>✅</td><td>🚧</td><td>🚧</td><td>🚧</td></tr></tbody></table>\n<p>With several more <a target=\"_blank\" href=\"https://github.com/supabase/wrappers/tree/main/wrappers/src/fdw\">under development</a>:</p>\n<table><thead><tr><th>Integration</th><th><span>select</span></th><th><span>insert</span></th><th><span>update</span></th><th><span>delete</span></th></tr></thead><tbody><tr><td>Airtable</td><td>✅</td><td>🚧</td><td>🚧</td><td>🚧</td></tr><tr><td>BigQuery</td><td>✅</td><td>✅</td><td>✅</td><td>✅</td></tr><tr><td>ClickHouse</td><td>✅</td><td>✅</td><td>✅</td><td>✅</td></tr></tbody></table>\n<p>Wrappers used <a target=\"_blank\" href=\"https://github.com/tcdi/pgx\">pgx</a>, extending it with FDW support. pgx is a Postgres extension framework written in Rust. Wrappers is very similar to <a target=\"_blank\" href=\"https://steampipe.io/\">Steampipe</a> or <a target=\"_blank\" href=\"https://multicorn.org/\">Multicorn</a>. We opted to develop our own framework for several reasons:</p>\n<ul>\n<li>The current state of FDWs is in disarray. It's hard to know which FDWs are supported and functional. We think there's a benefit to colocating all FDWs in a single repository using modern tooling. This makes contributing simpler and maintenance faster.</li>\n<li>Wrappers has async support, which enables the development of RESTful API-based FDWs, like Stripe.</li>\n<li>It's written in Rust, which provides reliable performance, strong typing, data security, and “push down” is supported through the framework.</li>\n</ul>\n<p>Wrappers <a target=\"_blank\" href=\"https://github.com/supabase/wrappers/blob/83887dcc2ddcf972ca1b1eec4a598cd7bff947de/supabase-wrappers/src/interface.rs#L11\">supports</a> a variety of types, including:\n<code>bool</code>, <code>i8</code>, <code>i16</code>, <code>f32</code>, <code>i32</code>, <code>f64</code>, <code>i64</code>, <code>String</code>, <code>Date</code>, <code>Timestamp</code>, and <code>JsonB</code>.</p>\n<p>Foreign Data Wrappers have a concept of \"push down\". This means that the FDW runs the query on <em>remote</em> data source. This is useful for performance reasons, as the remote data source can often perform the query more efficiently than Postgres. Push down is also useful for security reasons, as the remote data source can enforce access control. Limited push-down support has been added as a Proof of Concept, but this will be a key focus of Wrappers.</p>\n<p>You can follow development of all the Wrappers in the official <a target=\"_blank\" href=\"https://github.com/supabase/wrappers\">GitHub Repo</a>.</p>\n<p>We're not \"officially\" releasing Wrappers onto the platform yet, although the brave and curious might be able to figure out how to use it \"unofficially\". Caveat emptor: there will be breaking changes.</p>\n<p>We're excited to see what the community does with Wrappers. We're hoping that Wrappers will help to accelerate the adoption of Postgres as a data hub.\nIf you're interested in getting involved or building your own Wrapper, don't hesitate to jump into the code and start developing with us.</p>\n<ul>\n<li>Star &amp; Watch the GitHub repo: <a target=\"_blank\" href=\"https://github.com/supabase/wrappers\">github.com/supabase/wrappers</a></li>\n<li>View the documentation: <a target=\"_blank\" href=\"https://supabase.github.io/wrappers/\">supabase.github.io/wrappers</a></li>\n<li>Supabase Launch Week: <a target=\"_blank\" href=\"https://supabase.com/launch-week\">supabase.com/launch-week</a></li>\n</ul>\n<p></p>\n<ul>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/new-supabase-docs-built-with-nextjs\">Day 1: New Supabase Docs, built with Next.js</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/storage-image-resizing-smart-cdn\">Day 2: Supabase Storage v2: Image resizing and Smart CDN</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/mfa-auth-via-rls\">Day 3: Multi-factor Authentication via Row Level Security Enforcement</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/vault-now-in-beta\">Day 5: Supabase Vault is now in Beta</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/launch-week-6-community-day\">Community Day</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/postgres-point-in-time-recovery\">Point in Time Recovery is now available</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/custom-domain-names\">Custom Domain Names are now available</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/launch-week-6-wrap-up\">Wrap Up: everything we shipped</a></li>\n</ul></div></article>"
