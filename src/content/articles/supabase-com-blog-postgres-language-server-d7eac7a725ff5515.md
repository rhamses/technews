We would love for the community’s support by reporting issues and contributing documentation.</p>\n<p>Getting to the initial release has been a 2-year-long journey. We have learned Rust, spent weeks on research and iterations, dug our way out of rabbit holes, and made friends along the way. We have also discarded most of what we so proudly wrote about in the previous blog post <a target=\"_blank\" href=\"https://supabase.com/blog/postgres-language-server-implementing-parser\">Postgres Language Server: implementing the Parser</a> – but more on that later.</p>\n<p>Below is a mix of what we've come up with, challenges we've encountered, and where we'll go from here.</p>\n<p>Let's dive in.</p>\n<p>The most important decision when implementing a Language Server is the architecture of the underlying data model, which greatly depends on the language itself.</p>\n<p>For example, C++ supports header files and has a declaration-before-use rule. That's why the Language Server can compile headers once and cache them. When you type within a file, the compiler restarts from just after the header section of that file. All other files and headers are read from cache, so the compilation unit is reasonably small.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>// start of header. iostream is parsed and analyzed once.</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>#include &lt;iostream&gt;</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>// end of header</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>// if the user types below, we just have to re-analyze three lines.</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>// Everything else, including types and definitions from other files,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>// can be read from cache.</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>void main() {</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  std::cout &lt;&lt; \"Hello, World!\" &lt;&lt; std::</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>}</span></p></div><br></code></p></div>\n<p>Types are usually defined within the codebase and resolved from there. In the TypeScript example below, the Language Server first has to compile <code>foo.ts</code>&#160;and launch a database containing&#160;<code>Foo</code>&#160;so it can resolve the type of&#160;<code>bar</code>.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>// foo.ts</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>export type Foo = {</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  bar: string</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>}</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>// bar.ts</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>import { Foo } from './foo'</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>const bar: Foo = { bar: 'I am a string' }</span></p></div><br></code></p></div>\n<p>Many languages use variations of this.</p>\n<p>But for most parts of Postgres (or any SQL dialect, really), the rules are different: While types can be defined within the source code (e.g., within a migration file by using <a target=\"_blank\" href=\"https://supabase.com/docs/guides/local-development/declarative-database-schemas\">declarative schema management</a>), the database itself is the single source of truth, and there is no relation between files.</p>\n<p>Besides, the variety of schema and migration management tools employed today means we cannot make assumptions about how the source code is structured and whether it reflects the current state.</p>\n<p>For our Postgres Language Server, we can therefore assume that</p>\n<ul>\n<li>The smallest unit of compilation is a single statement</li>\n<li>The database schema is the single source of truth for any type information</li>\n<li>All statements are independent: To make sense of any statement, we only need to parse said statement, and nothing else</li>\n</ul>\n<p>For this project, the most challenging part is the parser – both when initially parsing the document and when processing user input.</p>\n<p>As laid out in a <a target=\"_blank\" href=\"https://supabase.com/blog/postgres-language-server-implementing-parser\">previous blog post</a>, implementing a parser for Postgres is hard because of the ever-evolving and complex syntax of Postgres. It's also one of the reasons why existing Postgres tooling is scarce, hardly maintained, and often does not work very well.</p>\n<p>This is why we decided not to create a custom parser. Instead, we leverage the existing&#160;<a target=\"_blank\" href=\"https://github.com/pganalyze/libpg_query\">libpg_query</a>&#160;library to parse SQL code reliably. The pganalyze team has published a great blog post on&#160;<a target=\"_blank\" href=\"https://pganalyze.com/blog/parse-postgresql-queries-in-ruby\">why this approach is preferred</a>.</p>\n<p>However, <code>libpg_query</code> is designed to parse <em>executable</em>&#160;SQL — not to provide language intelligence. This limitation posed several challenges, requiring us to find pragmatic solutions along the way. The biggest challenge of this project has been (and continues to be) resisting the urge to chase perfection, avoiding unnecessary complexity, and prioritizing practical solutions instead.</p>\n<p>Let’s explore some of these solutions by walking through the document lifecycle.</p>\n<p>The document lifecycle is at the core of every Language Server. It describes how we turn raw text input into a model of the code, provide language-specific smarts back to the client, and then efficiently process changes to do it all again, and fast.</p>\n<p>To understand how everything works, let’s see how a document is processed.</p>\n<p>Whenever a user opens a new document, we first run it through our custom statement splitter.</p>\n<p>It is responsible for cutting a SQL file with potentially invalid or incomplete statements into individual statements. We need this because the <code>libpg_query</code> parser is built to parse <em>executable</em> SQL – it will return an error on the first invalid token it encounters. When we first cut the SQL file, we can run the parser on each statement individually. If a statement cannot be parsed, we report the syntax error to the user.</p>\n<p>At first, we spend months trying to chase perfection by implementing a “light” Postgres parser.</p>\n<p>The idea was to just care about the tokens that are distinct for a specific statement. For example, if we saw a <code>CREATE</code> token followed by a <code>FUNCTION</code> token, we could be relatively sure this was going to be a <code>CREATE FUNCTION</code> statement, and we could expect <code>(</code> and <code>)</code> to follow it. This approach almost worked, but eventually became a rabbit hole of never ending edge-cases (damn you, recursion!).</p>\n<p>We had once again learned an important lesson: If anything requires an implementation per statement type or per syntax element, we better find another way.</p>\n<p>After some time off, we decided to make another attempt focusing on the simplest approach.</p>\n<p>The goal was to make the statement splitter work well for 80% of cases, and to provide a reasonable fallback for the rest. Inspired by <a target=\"_blank\" href=\"https://matklad.github.io/2020/04/13/simple-but-powerful-pratt-parsing.html\">this blog post by matklad</a>, we implemented a simple Pratt Parser.</p>\n<p>The splitter now tries to be “smart” about common statement types. For example, it knows that a <code>SELECT</code> cannot be followed by another <code>SELECT</code>, unless the latter is within a sub-statement. Hence, the following is cut into two statements:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>SELECT a FROM (SELECT a FROM b) sub WHERE</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>SELECT 1;</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>-- is cut into</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>SELECT a FROM (SELECT a FROM b) sub WHERE</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>--</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>SELECT 1;</span></p></div><br></code></p></div>\n<p>We hope that this custom implementation will suffice for 80% of use cases.</p>\n<p>For everything else, we’ve built a simple fallback: We always split statements at semi-colons or double newlines. This means that the following works, too – it will be cut into two statements, and we report a syntax error for the first.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>i like to use my sql file as a notepad -- Error!</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>select 1;</span></p></div><br></code></p></div>\n<p>There might still be cases we did not think about - which is where we need your help: please try it out and report any issues you find. If our solution is not good enough, we will go back to the drawing board.</p>\n<p>After we split the SQL source into separate statements, we store each statement's range and assign it an identifier that is unique within the document. Outside a document, a statement is then identified by the path of the document and its statement ID.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>/// Globally unique statement</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>#[derive(Hash)]</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>pub(crate) struct Statement {</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  /// Path of the document</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  pub(crate) path: PgTPath,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  /// Unique id within the document</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  pub(crate) id: StatementId,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>}</span></p></div><br></code></p></div>\n<p>We use a hash of the <code>Statement</code> struct to cache per-statement results (e.g. diagnostics) in our workspace. Since the statement can change over time, the cache key does not include the text or the range of the statement.</p>\n<p>Now that we have identified the document's statements, we can parse them into workable data structures.</p>\n<p>To do this, we run both <code>tree-sitter</code> and <code>libpg_query</code> on them.</p>\n<p><code>libpg_query</code> provides precise parsing, helps to detect syntax errors, extracts statement types, and analyzes their structure for diagnostics and linting. But it cannot handle invalid or incomplete SQL, which often appears during live editing.</p>\n<p>This is where <code>tree-sitter</code> comes in. While not as precise, it can always produce a syntax tree, even for malformed statements. This is very useful, especially for handling incomplete statements in autocompletion.</p>\n<p>With both parsers combined, we get accurate results for valid SQL and can also deal with incomplete input. The idea to use <code>tree-sitter</code> in addition to <code>libpg_query</code> came from <a target=\"_blank\" href=\"https://news.ycombinator.com/item?id=38570680\">a comment on our previous Hacker News post</a>, so thank you for that:</p>\n<p>Ironically, the parser we wrote <a target=\"_blank\" href=\"https://supabase.com/blog/postgres-language-server-implementing-parser\">an entire blog post about</a> isn't even in use anymore.</p>\n<p>It did enable us to pin-point the exact location of a node within the abstract syntax tree (AST). For example, in the following statement, we could show the diagnostics only on <code>DROP COLUMN test</code> instead of the entire <code>ALTER TABLE</code> statement:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>ALTER TABLE contact</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>\tDROP COLUMN test,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>\tALTER COLUMN another DROP NOT NULL;</span></p></div><br></code></p></div>\n<p>While that is certainly a nice feature, the implementation effort was simply not justified. We might revisit it later, but for now, we've decided that the combination of <code>libpg_query</code> and <code>tree-sitter</code> is good enough.</p>\n<p>With this and the statement splitter, we are coming out of a deep rabbit hole with a clearer path ahead of us.</p>\n<p>Now that we have opened a document and parsed its statements, the missing piece for analysis is schema information.</p>\n<p>To provide this, we lazily populate a schema cache. Similar to PostgREST, this cache is a simple in-memory data structure that stores details about tables, columns, functions, and other schema elements.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>pub struct SchemaCache {</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  pub schemas: Vec&lt;Schema&gt;,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  pub tables: Vec&lt;Table&gt;,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  pub functions: Vec&lt;Function&gt;,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  pub types: Vec&lt;PostgresType&gt;,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  pub versions: Vec&lt;Version&gt;,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  pub columns: Vec&lt;Column&gt;,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>}</span></p></div><br></code></p></div>\n<p>We only load the schema cache when it is first needed (e.g. for autocompletion). Once loaded, we keep it in memory, ensuring that schema data is available without unnecessary overhead. If no database connection is configured, we can't load any schema information, so we simply disable features requiring that.</p>\n<p>When the client asks for diagnostics, we load all statements alongside their ranges and text content from a document. With the statement identifier, we check if the <code>libpg_query</code> AST is available. If it is not available, we collect the emitted syntax errors instead. If it is available, on the other hand, we pass it to both the type checker and the linter.</p>\n<p>Again, the type checker is very simple: Since we maintain a database connection, we can just ask Postgres to do the heavy lifting by <code>PREPARE</code>-ing the statement. If the statement contains a type issue, such as a missing column, the error is returned as diagnostics to the user.</p>\n<p>Our linter is heavily inspired by <a target=\"_blank\" href=\"https://squawkhq.com/\">Squawk</a>. It takes the AST emitted by <code>libpg_query</code> and runs all configured rules on them. We spent some time optimizing the infrastructure of the linter in order to lower the barrier of contributing new rules and ask that the community <a target=\"_blank\" href=\"https://github.com/supabase-community/postgres_lsp/issues/131\">can support us there</a>.</p>\n<p>In the end, providing diagnostics happens without noticeable delay for the user (we promise the GIF was not edited 🤞):</p>\n<p>Now that we've successfully reported diagnostics, the user will want to fix the issues.</p>\n<p>For an IDE to feel responsive, these changes must be processed within milliseconds. To achieve this, we take advantage of the fact that all SQL statements are independent of each other, which allows us to invalidate only those statements that have actually changed.</p>\n<p>Let’s look at an example.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>select first from test;</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>select seond from test; -- a typo we want to fix</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>select third from test;</span></p></div><br></code></p></div>\n<p>The last time we checked, \"second\" was spelled somewhat differently, so that's a typo we need to fix. Before going ahead and adding the missing <code>c</code>, we need to understand how text files are usually stored and processed in IDEs.</p>\n<p>From the user’s perspective, inserting a character simply makes the current line longer. However, an IDE doesn’t inherently work with lines—it instead processes raw strings that may contain&#160;<code>\\n</code>&#160;characters. When a character is inserted, everything after the cursor position shifts to the right, affecting not only the current line, but the subsequent lines as well.</p>\n<p>In our case, this means we need to update the ranges of all affected statements. Since SQL statements are independent, we know that:</p>\n<ul>\n<li>Statements before the change remain unaffected.</li>\n<li>The modified statement expands to fit the new character.</li>\n<li>Statements after the modification are shifted \"to the right\" by one character.</li>\n</ul>\n<p>When we fix the typo, this is the corresponding diff:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>--- old.sql\t2025-03-27</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>+++ new.sql\t2025-03-27</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>@@ -1,3 +1,3 @@</span></p></div><div><p><span>_<!-- -->10</span></p><p><span> select first from test; -- no changes</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>-select seond from test;</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>+select second from test; -- range extended by 1 character</span></p></div><div><p><span>_<!-- -->10</span></p><p><span> select third from test; -- moved right by 1 character</span></p></div><br></code></p></div>\n<p>As mentioned before, each statement in the document is assigned a unique ID, and we store only their ranges. So, when processing this change, we do need to create a new entry for the modified statement, since its content has changed – but for the third statement, simply updating its stored range is enough, meaning we don’t need to invalidate its cache! The AST does not need to be re-parsed.</p>\n<p>The above example is intentionally simplified. There are other cases to consider, such as edits occurring <strong>between</strong> two statements, or merging two statements into one. However, the basic gist remains: identify all modified statements, replace the affected ones, and for those that come afterward, simply update their ranges.</p>\n<p>The one feature where developers will truly notice efficient change processing is autocompletion, so we try to be as efficient as possible providing suggestions.</p>\n<p>When you change a character in your <code>SELECT</code> clause, we update the existing <code>tree-sitter</code> Concrete Syntax Tree (CST) instead of re-parsing it. We then read the relevant suggestion types (columns, tables, etc.) from our <code>SchemaCache</code> , so no database query is necessary. This approach of updating and reading from existing data structures lets us provide suggestions without any noticeable delay. (Some would call it&#160;– drumroll – \"blazingly fast\".)</p>\n<p>In order to choose which suggestions are the most relevant, we take the changed node and the CST and then iterate over the possible items using a simple scoring algorithm.</p>\n<p>Some examples:</p>\n<ul>\n<li>If the changed node is within a <code>SELECT</code> clause, it would not make sense to suggest a table name. We reduce those items' score.</li>\n<li>If the changed node contains the \"public\" schema name, it would not make sense to suggest a table from the \"private\" schema. We reduce those items' score.</li>\n<li>If the CST contains a <code>FROM</code> clause, it would make sense to suggest columns belonging to the queried table. We increase those columns' scores.</li>\n</ul>\n<p>While the hard part is gathering the information about the current statement, the actual scoring code is as simple as it gets:</p>\n<div><p><code><br><div><p><span>_<!-- -->20</span></p><p><span>fn check_matches_schema(</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>  /// `self` is the currently investigated suggestion item.</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>\t&amp;mut self,</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>  /// `ctx` contains the information about the changed CST node and the</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>  /// containing statement.</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>\tctx: &amp;CompletionContext</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>) {</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>  let schema_name = match ctx.schema_name.as_ref() {</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>    None =&gt; return,</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>    Some(n) =&gt; n,</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>  };</span></p></div><div><p><span>_<!-- -->20</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>  let data_schema = self.get_schema_name();</span></p></div><div><p><span>_<!-- -->20</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>  if schema_name == data_schema {</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>    self.score += 25;</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>  } else {</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>    self.score -= 10;</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>  }</span></p></div><div><p><span>_<!-- -->20</span></p><p><span>}</span></p></div><br></code></p></div>\n<p>Once we've investigated all relevant items, we filter out those not meeting a threshold, sort them by score, and return the first 50 to the user.</p>\n<p>It will take some time to dial in the scoring mechanism so that the completion suggestions feel intuitive and relevant, but this approach will take us there.</p>\n<p>This entire blog post (and the first 18 months of the project) focused primarily on the Language Server. It's arguably the most prominent use case and remains our highest priority.</p>\n<p>However, our vision for this project is larger: We want to create a home for all the great Postgres tooling out there, build the missing pieces, and make everything as accessible as possible. Therefore, the Language Server is just one out of many entry points. We've already built a client-server architecture that allows our workspace API to be used anywhere:</p>\n<ul>\n<li>from the CLI by running <code>postgrestools check test.sql</code></li>\n<li>behind a HTTP API</li>\n<li>(hopefully soon) from Wasm right in your browser.</li>\n</ul>\n<p>This approach is&#160;<em>heavily</em>&#160;inspired by (and borrows a lot from)&#160;<a target=\"_blank\" href=\"https://github.com/biomejs/biome\">Biome</a>. Without their sophisticated and well-structured codebase, we wouldn’t have been able to implement an entire toolchain infrastructure this quickly over the past months. Cheers to Open Source!</p>\n<p>Over the next few weeks, we'll focus on improving reliability.</p>\n<p>The Language Server still has a few hiccups, so we want to make the current toolset as frictionless as possible before we work on any more features.</p>\n<p>Once we're happy with the results, we'll try to make the Postgres LSP accessible to more people by:</p>\n<ul>\n<li>writing installation guides</li>\n<li>publishing extensions for other editors</li>\n<li>writing documentation to enable future contributors</li>\n</ul>\n<p>If you want, you can already help us by installing the Language Server and reporting any issues we might have overlooked, or you could suggest features that we should implement later on (we're currently planning PL/pgSQL support, a Wasm build for <a target=\"_blank\" href=\"https://github.com/electric-sql/pglite\">pglite</a>, and parsing SQL function bodies).</p>\n<p>We also added a few <a target=\"_blank\" href=\"https://github.com/supabase-community/postgres_lsp/issues?q=sort%3Aupdated-desc+is%3Aissue+is%3Aopen\">issues</a> to our <a target=\"_blank\" href=\"https://github.com/supabase-community/postgres_lsp\">repository</a> for anybody who wants to contribute by writing code. Any kind of help is highly appreciated!</p>\n<p>Happy coding! 🧀</p></div></article>"
