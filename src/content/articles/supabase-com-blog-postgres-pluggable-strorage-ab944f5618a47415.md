contentHtml: "<article><div><p>You might have recently read “<a target=\"_blank\" href=\"https://ottertune.com/blog/the-part-of-postgresql-we-hate-the-most/\">The Part of PostgreSQL We Hate the Most</a>” which highlights some of the deficiencies with Postgres storage. Fortunately, there is ongoing work in the Postgres ecosystem to solve this using “pluggable storage”.</p>\n<p>This article explores the history of Postgres pluggable storage and the possibility of landing it in the Postgres core.</p>\n<p>Pluggable storage gives developers the ability to use different storage engines for different tables within the same database.</p>\n<p>Developers will be able to choose a storage method that is optimized for their specific needs. Some tables could be configured for high transactional loads, others for analytics workloads, and still others for archiving.</p>\n<p>Something like this is already <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Comparison_of_MySQL_database_engines\">available in MySQL</a>, which uses the <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/InnoDB\">InnoDB</a> as the default storage engine since MySQL 5.5. This replaced <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/MyISAM\">MyISAM</a> which had it’s own <a target=\"_blank\" href=\"https://www.percona.com/blog/using-myisam-in-production/\">set of problems</a>.</p>\n<p>The “pluggable” part refers to the ability for developers to develop their own storage methods, similar to Postgres Extensions. While some databases offer multiple built-in storage methods by default, Postgres follows a core philosophy of flexibility and extensibility, and using a pluggable approach makes a lot of sense.</p>\n<p>In version 12, PostgreSQL introduced basic support for pluggable storage with the goal of <a target=\"_blank\" href=\"https://anarazel.de/talks/2019-05-30-pgcon-pluggable-table-storage/pluggable.pdf\">adding ZHeap</a>. Andres Freund and several contributors enabled that feature by refactoring and expanding a variety of table access method (TAM) APIs.</p>\n<p>ZHeap <a target=\"_blank\" href=\"https://github.com/EnterpriseDB/zheap\">was released</a> with <a target=\"_blank\" href=\"https://www.pgcon.org/2018/schedule/attachments/501_zheap-a-new-storage-format-postgresql-5.pdf\">promising results</a>, providing an undo log and solving some long-term table bloat issues in Postgres.</p>\n<p>While it was a great start, unfortunately it appears that the work on ZHeap and the TAM API <a target=\"_blank\" href=\"https://twitter.com/andy_pavlo/status/1590703943176589312\">has stalled</a>.\nThis leaves a few holes in that need to be fixed before the community can use the TAM API for pluggable storage. In particular:</p>\n<ul>\n<li>The TAM API doesn’t provide much flexibility for working with indexes. For example, when you update a row an index update is an all-or-nothing procedure.</li>\n<li>Row versions need to be identified by the pairing of a block number and offset number. This means you can’t implement some useful functions, like an index-organized table or undo-based versioning.</li>\n</ul>\n<p>Even without a full API for pluggable storage, there are a couple of solutions available on the market today:</p>\n<ul>\n<li><strong>Citus’s</strong> <a target=\"_blank\" href=\"https://docs.citusdata.com/en/v11.1/admin_guide/table_management.html#columnar-storage\">Columnar Storage</a>, which powers Microsoft’s <a target=\"_blank\" href=\"https://azure.microsoft.com/en-us/updates/azure-database-for-postgresql-hyperscale-citus-is-now-available/\">Hyperscale</a> offering. Citus has a few <a target=\"_blank\" href=\"https://docs.citusdata.com/en/v11.1/admin_guide/table_management.html#limitations\">limitations</a> due to the restrictions of the current API.</li>\n<li>EDB’s <a target=\"_blank\" href=\"https://www.infoworld.com/article/3681112/3-key-features-in-edb-postgresql-15.html\">Advanced Storage Pack</a>, which is appears to provide some enhancements to heap storage, although the source is not available for us to confirm.</li>\n</ul>\n<p>Right now, pluggable storage requires a fork of Postgres. But there are several initiatives in the Postgres community that we’re excited about.</p>\n<ul>\n<li>There have been community updates for <a target=\"_blank\" href=\"https://git.postgresql.org/gitweb/?p=postgresql.git;a=commitdiff;h=5c279a6d350205cc98f91fb8e1d3e4442a6b25d1\">custom resource managers</a> that expand <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/wal-intro.html\">write-ahead log (WAL)</a> support for TAM.</li>\n<li>The creators at <a target=\"_blank\" href=\"https://github.com/orioledb/orioledb\">OrioleDB</a> started with a fork of Postgres and have been quietly upstreaming code that would make pluggable storage a reality. In Postgres 14 their patchset was ~5,000 lines of code, representing the total number of changes required in their fork. In the upcoming Postgres 16 release, it is ~2,000 lines of code. That means that around 60% of the code is already committed to the Postgres core. (Disclosure: Supabase started <a target=\"_blank\" href=\"https://supabase.com/blog/supabase-series-b#where-were-going\">sponsoring OrioleDB</a> in 2022).</li>\n</ul>\n<p>Alexander Korotkov, the maintainer of OrioleDB, will be talking at PGCON 23 about some of the <a target=\"_blank\" href=\"https://www.pgcon.org/events/pgcon_2023/schedule/session/470-future-of-table-access-methods/\">changes</a> they are making. They are solving many <a target=\"_blank\" href=\"https://www.slideshare.net/AlexanderKorotkov/solving-postgresql-wicked-problems\">\"wicked Postgres problems\"</a> with <a target=\"_blank\" href=\"https://www.orioledata.com/blog/buffer-management/\">dual pointers</a> instead of buffer mapping, row-level WAL instead of block-level WAL, undo logs instead of bloat-prone MVCC, and index-organized tables instead of heap.</p>\n<p>Ambitiously, many of the changes required for pluggable storage could land in Postgres 17. If that happens, new storage engines like OrioleDB would be available as a simple extension for developers to use in any Postgres instance. This paves the way for other Pluggable Storage Engines, just like MySQL’s <a target=\"_blank\" href=\"https://dev.mysql.com/doc/refman/5.7/en/storage-engines.html\">support for multiple storage engines</a>.</p>\n<p>As a community project, Postgres requires support for these initiatives. You can support pluggable storage by getting involved during Postgres <a target=\"_blank\" href=\"https://supabase.com/blog/postgresql-commitfest\">Commitfests</a>. Postgres is already one of the best database engines in the world, and pluggable storage would make it even more attractive and maintainable.</p>\n<h2 id=\"more-postgres-content\">More Postgres content<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-pluggable-strorage#more-postgres-content\">#</a></h2>\n<ul>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/openai-embeddings-postgres-vector\">Storing OpenAI embeddings in Postgres with pgvector</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/choosing-a-postgres-primary-key\">Choosing a Postgres Primary Key</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/sql-or-nosql-both-with-postgresql\">SQL or NoSQL?
