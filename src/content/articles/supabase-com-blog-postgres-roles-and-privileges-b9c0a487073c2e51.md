contentHtml: "<article><div>\n<p>Controlling access to data in Postgres is paramount for data security. Postgres provides a robust and flexible permissions model for users to manage access to their data. The permissions model is based on the familiar object, privilege, role model but has subtleties which must be understood by a database administrator to create airtight access. In this post we will take a detailed look at how roles and permissions work in Postgres.</p>\n<p>Let's first understand some basic concepts which will be used throughout the rest of the post.</p>\n<p>A database object is any entity created in the database. Tables, foreign tables, views, materialized views, types, domains, operators, functions, triggers etc. are database objects. Objects allow operations on them which vary for each object. For example, you can <em>select</em> data from a table and you can <em>execute</em> a function.</p>\n<p>A privilege controls what operation is allowed to be run on a database object. For example, the <code>select</code> privilege on a table controls the ability to read data from the table. Similarly, the <code>execute</code> privilege controls the ability to execute a function. Privileges are assigned to roles. A role must have the permission for the operation it is performing on an object.</p>\n<p>A role is a user or a group. A user is someone who can login to the database. A group is a collection of users to make it easier to manage privileges for users. Unlike a user, a group can't login to the database. The distinction between a user and a group doesn’t matter to Postgres for the most part as they are both roles, but it is still useful to think of them as separate concepts for ease of understanding.</p>\n<p>Every database object has an owner. The owner has complete control over the object. They can modify or delete the object or grant privileges to other users and groups. When a user creates a new object, they become the owner of the object. An owner can also transfer the ownership of objects to other roles. A role cannot be deleted before all its owned objects’ ownership is transferred to another role.</p>\n<p>With these basic terms defined, let's take a look at the permissions model in Postgres in depth. The rest of the post will be more like a tutorial, so you can follow along. I'll be using a hosted Supabase project, but you are free to use any Postgres installation.</p>\n<p>Create a new Supabase project (or use an existing one) and copy its connection string URI from the <a target=\"_blank\" href=\"https://supabase.com/dashboard/project/_/database/settings\">Database Settings page</a>. The URI looks like the following:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>postgres://[USER].[YOUR-PROJECT-REF]:[YOUR-PASSWORD]@[REGION-SUBDOMAIN].pooler.supabase.com:5432/postgres</span></p></div><br></code></p></div>\n<p>Where <code>USER</code> is the user to connect as. <code>YOUR-PROJECT-REF</code> is a string uniquely identifying your project. <code>YOUR-PASSWORD</code> is the database password for the <code>USER</code> user and <code>REGION-SUBDOMAIN</code> is the subdomain where your database is hosted.</p>\n<p>Use the <a target=\"_blank\" href=\"https://www.postgresql.org/download/\"><code>psql</code> command line tool</a> to connect to the database:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>➜ psql postgres://postgres.[YOUR-PROJECT-REF]:[YOUR-PASSWORD]@[REGION-SUBDOMAIN].pooler.supabase.com:5432/postgres</span></p></div><br></code></p></div>\n<p>Once connected, confirm that you are connected as the <code>postgres</code> user by running <code>select current_role</code> command:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span># as postgres</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>postgres=&gt; select current_role;</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>┌──────────────┐</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>│ current_role │</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>├──────────────┤</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>│ portgres     │</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>└──────────────┘</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>(1 row)</span></p></div><br></code></p></div>\n<p>Now, let's create two users named <code>junior_dev</code> and <code>senior_dev</code>. Think of the <code>postgres</code> role as an admin role, although it is not a superuser. We can use this role to grant appropriate permissions.</p>\n<p>So, let’s switch to the <code>postgres</code> user connection and grant <code>junior_dev</code> the permission to create objects in the <code>public</code> schema. A <code>superuser</code> is like a root user on the *nix OSes. It is very powerful and bypasses all privilege checks except authentication during login. For this reason, you should avoid working with this role as much as possible.
