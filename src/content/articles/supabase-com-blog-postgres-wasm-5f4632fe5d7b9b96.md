contentHtml: "<article><div>\n<p>Today we're open sourcing <a target=\"_blank\" href=\"https://github.com/snaplet/postgres-wasm\"><code>postgres-wasm</code></a> with our friends at <a target=\"_blank\" href=\"https://www.snaplet.dev/\">Snaplet</a>.</p>\n<p>postgres-wasm is a PostgreSQL server that runs inside a browser. It provides a full suite of features, including persisting state to browser,\nrestoring from pg_dump, and logical replication from a remote database.</p>\n<p>We're not the first to run Postgres in the browser - that title belongs to the team at <a target=\"_blank\" href=\"https://www.crunchydata.com/\">Crunchy Data</a> who shared their\nversion of this <a target=\"_blank\" href=\"https://news.ycombinator.com/item?id=32498435\">on HN</a> a month ago. It's awesome, and we wanted\nan <a target=\"_blank\" href=\"https://staltz.com/time-till-open-source-alternative.html\">open source version</a>, so we teamed up with Snaplet build it.\nLet's explore how it's built, and some extra features we've added.</p>\n<div><p>🐈 Who's Snaplet?</p><p>Snaplet gives developers production-accurate data and preview databases that they can code against, so they can focus on shipping.</p><p>Checkout out how you can <a target=\"_blank\" href=\"https://docs.snaplet.dev/tutorials/supabase-clone-environments\">use Snaplet to clone Supabase environments</a>.</p></div>\n<p>Before we get into the technical details, try it out yourself (warning: it will download ~30MB):</p>\n<p><a target=\"_blank\" href=\"https://wasm.supabase.com/\">wasm.supabase.com</a></p>\n<p>To run it locally:</p>\n<div><p><code><br><div><p><span>_<!-- -->11</span></p><p><span># From Snaplet features!</p>\n<ul>\n<li>Postgres 14.5, psql, pg_dump, etc.</li>\n<li>Save &amp; restore state to/from a file.</li>\n<li>Save &amp; restore Postgres state to/from the browser storage (IndexedDB).</li>\n<li>Quick start from a state file or fully reboot the emulator.</li>\n<li>Memory configuration options from 128MB to 1024MB.</li>\n<li>Adjust the font size for the terminal.</li>\n<li>Upload files to the emulator (including database dumps and CSVs).</li>\n<li>Download files from the emulator.</li>\n<li>Outgoing network connectivity from the emulator to the internet.</li>\n<li>Incoming network tunnel to postgres port 5432 inside the emulator.</li>\n</ul>\n<p>That's a good question. <code>postgres-wasm</code> is currently about 30mb. So at this stage, running Postgres in the browser isn't great for general use-cases.\nIt has a lot of potential though. Some ideas we'll be playing with over the next few months:</p>\n<ul>\n<li><strong>Documentation:</strong> for tutorials and demos.</li>\n<li><strong>Offline data:</strong> running it in the browser for an offline cache, similar to <a target=\"_blank\" href=\"https://sql.js.org/#/\">sql.js</a> or <a target=\"_blank\" href=\"https://github.com/jlongster/absurd-sql\">absurd-sql</a>.</li>\n<li><strong>Offline data analysis:</strong> using it in a dashboard for offline data analysis and charts.</li>\n<li><strong>Testing:</strong> testing PostgreSQL functions, triggers, data modeling, logical replication, etc.</li>\n<li><strong>Dev environments:</strong> use it as a development environment — pull data from production or push new data, functions, triggers, views up to production.</li>\n<li><strong>Snapshots:</strong> create a test version of your database with sample data, then take a snapshot to send to other developers.</li>\n<li><strong>Support:</strong> send snapshots of your database to support personnel to demonstrate an issue you're having.</li>\n</ul>\n<p>We've divided in our repository into three folders: a virtual machine, a web application, and a network proxy.</p>\n<h3 id=\"virtual-machine-vm\">Virtual Machine (VM)<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-wasm#virtual-machine-vm\">#</a></h3>\n<p>We create an embeddable Virtual Machine (VM) using <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Buildroot\">Buildroot</a>.\nOur VM is a stripped-down Linux build with Postgres installed.</p>\n<p>See <a target=\"_blank\" href=\"https://github.com/snaplet/postgres-browser/tree/main/packages/buildroot\">source code</a>.</p>\n<h3 id=\"web-application\">Web application<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-wasm#web-application\">#</a></h3>\n<p>Next, we need to run the VM inside our browser. How? <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/WebAssembly\">WASM</a>.\nWe use <a target=\"_blank\" href=\"https://github.com/copy/v86\">v86</a> to run our VM inside the browser. Our demo application is very simple - plain HTML and some basic styling.</p>\n<p>See <a target=\"_blank\" href=\"https://github.com/snaplet/postgres-wasm/tree/main/packages/runtime\">source code</a>.</p>\n<h3 id=\"network-proxy\">Network proxy<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-wasm#network-proxy\">#</a></h3>\n<p>Running Postgres in a browser is great, but connecting to it with PgAdmin is even better. Unfortunately browsers block TCP network access to the VM.\nTo circumvent this, we proxy the traffic through websockets. We run a fork of <a target=\"_blank\" href=\"https://github.com/benjamincburns/websockproxy\">Websockproxy</a>\nwhich allows the emulator to talk to the internet by converting data sent over a websocket port into TCP packets.\nOur fork of Websockproxy adds the ability to tunnel into the Postgres server.</p>\n<p>See <a target=\"_blank\" href=\"https://github.com/snaplet/postgres-wasm/tree/main/packages/websockproxy\">source code</a>.</p>\n<p>There were a lot of hurdles that we discovered throughout the development of postgres-wasm.</p>\n<h3 id=\"wasm\">WASM<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-wasm#wasm\">#</a></h3>\n<p>The first thing to point out is that our implementation isn't <em>pure</em> WASM. We attempted to compile Postgres for WASM directly from source,\nbut it was more complicated that we anticipated.</p>\n<p>Crunchy's HN post provided some hints about the approach they took, which was to virtualize a machine in the browser. We pursued this strategy too, settling on v86\nwhich emulates an x86-compatible CPU and hardware in the browser.</p>\n<h3 id=\"postgresql-14-segfault-errors\">PostgreSQL 14 segfault errors<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-wasm#postgresql-14-segfault-errors\">#</a></h3>\n<p>We quickly had PostgreSQL 13.3 running using an outdated version of Buildroot. But version PG14+ wouldn't start, giving a segfault during initialization. We tried:</p>\n<ul>\n<li>manually copying build files for PG14 into the older version(s) of Buildroot</li>\n<li>building with (many) newer copies of Buildroot</li>\n<li>adjusting kernel parameters and environment settings such as the amount of memory allocated to the emulator, etc.</li>\n</ul>\n<p>Eventually, Fabian, the creator of v86 suggested we turn off JIT compilation for v86 and that solved the issue.\nHe narrowed it down to a bug in v86 and is pushing an update that will fix it.\nSwitching Postgres from posix to sysv memory management also solved the issue for the current release of V86.</p>\n<h3 id=\"optimizing-startup-time-and-image-size\">Optimizing startup time and image size<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-wasm#optimizing-startup-time-and-image-size\">#</a></h3>\n<p>With PG14 running in the emulator, we shifted our focus to performance. The image size for the emulator was too big for a browser-based tool.\nEven with our best efforts, a compressed snapshot was over 30mb - a fairly large payload to download before you can see any interaction.</p>\n<p>We solved this by booting only a minimal Linux image and then dynamically loading the rest of the VM over HTTPS after initialization.</p>\n<p>We achieve this by mounting a compressed <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/9P_(protocol)\">9P filesystem</a> in the VM.\n9P provides a <a target=\"_blank\" href=\"https://github.com/supabase-community/postgres-wasm/tree/main/packages/buildroot/tools\">Python script</a> which takes a filesystem folder,\nrenames every file an 8-character name and produces a <code>filesystem.json</code> file representing a nested structure with files, original file names, sizes, etc.\nWe then <a target=\"_blank\" href=\"https://github.com/supabase-community/postgres-wasm/blob/main/packages/buildroot/config/board/pg-browser/post-image.sh\">copy this compressed output</a> to the VM.\nWe modified the kernel command line and v86 boot parameters to boot directly from the 9P filesystem, and even put our kernel file into the p9 filesystem.\nAll non-essential files are loaded asynchronously over HTTPS in the browser as needed.</p>\n<p>The initial state was smaller, but still 15-20mb in size. We discussed this with Fabian who pointed us towards the <code>page_poison=on</code> kernel parameter.\nThis parameter allowed us to clear caches before creating the snapshots, by forcing Linux to write arbitrary bytes on freed memory instead of random bytes,\nso unused memory is compressed much more efficiently.</p>\n<p>The end result of all these changes? The compressed initial state file is about 12mb - including a <em>running network state and Postgres 14.4 running with psql loaded.</em></p>\n<p>We experimented without Postgres started too - this produced an even smaller initial state but the time to initialize\nPostgres was usually longer than the time to download a few extra megabytes. We opted for a faster startup time.</p>\n<p>Additionally, without a running state you'd hit a performance penalty every time you refreshed the page,\nsince Postgres would need to be initialized each time. In our current version, after the initial state is\ndownloaded and cached by the browser the VM feels almost instant on refresh.</p>\n<h3 id=\"networking\">Networking<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-wasm#networking\">#</a></h3>\n<p>Networking was particularly difficult to solve. For security reasons, browsers only support access to a nominal set of ports.\nIn short, browsers speak “80/443” and Postgres speaks “5432” so there was no way for our Postgres to communicate with the outside world.</p>\n<p>WASM isn't much help here - a WebAssembly module running in the browser is generally not able to do anything outside itself,\nexcept for calling functions exposed from JavaScript.</p>\n<p>Browsers provide another connection option for us however: Websockets. The nice thing about websocket connections is that they are <em>persistent</em>,\nso all we needed was to figure out how to proxy the virtual machine traffic through a websocket connection.</p>\n<p>The VM includes an emulated network card (<code>ne2k-pci</code>) and a <code>proxy_url</code> startup parameter which points to an external server\nrunning a websocket proxy (i.e. on the internet). The websocket proxy establishes connections via a websocket port, then accepts raw ethernet packets.\nIt turns those raw packets into TCP/IP packets and routes them between the Internet and the VM.</p>\n<p>With our tunnel established, we could now send network traffic to the outside world. For example, try “starting” the network on the VM,\n\"exiting\" out of psql (<code>cmd</code>+<code>D</code>), and then run <code>ping 1.1.1.1</code>.</p>\n<p>Most v86 VM's use an open proxy at <code>wss://relay.widgetry.org/</code> based on <a target=\"_blank\" href=\"https://github.com/benjamincburns/websockproxy\">websockproxy</a>.\nThis proxy allows the VM to communicate with the outside world. It can handle all the basic use-cases like loading\ndata from other PostgreSQL databases using <code>pg_dump</code> and <code>psql</code>, or operating as read-only replica of another database.</p>\n<p>However, this proxy doesn't allow incoming traffic to be routed into a VM running locally on a laptop.\nFor instance, you can't connect a local <code>PgAdmin4</code> to the PostgreSQL instance running inside your browser.\nSo we <a target=\"_blank\" href=\"https://github.com/snaplet/postgres-wasm/tree/main/packages/websockproxy\">forked</a> the <a target=\"_blank\" href=\"https://github.com/benjamincburns/websockproxy\">proxy</a> and\nadded nginx to provide a reverse proxy.</p>\n<p>The reverse proxy listens on a range of ports, mapping each port to the VM at a specific private address you want to reach.\nThe simple solution was to take the last 2 segments of the private IP and map it to a port number. So if your private IP is 10.5.6.123,\nyou connect to the proxy on port 6123 and that points you to PostgreSQL (running on port 5432) on private IP 10.5.6.123. Shortened addresses are padded,\nso 10.5.6.2 maps to port 6002 and 10.5.6.44 to port 6044.</p>\n<h3 id=\"sending-commands-to-the-emulator-from-the-browser-ui\">Sending commands to the emulator from the browser UI<a target=\"_blank\" href=\"https://supabase.com/blog/postgres-wasm#sending-commands-to-the-emulator-from-the-browser-ui\">#</a></h3>\n<p>Once the emulator is running, in the words of Fabian, “it runs as a black box process”, and the only way to communicate between the\nUI and the operating system running in the emulator is through <code>serial0_send</code> to send keystrokes over the emulated serial port,\nor through the <code>create_file</code> function which uploads a file to the running emulator.</p>\n<p>To restart the network after restoring a state file, we need to run a short script to unbind and re-bind the emulated network card\n(so it gets a new mac address and thus a unique private IP address at the proxy), and then a standard network restart command.\nWe could run this script by sending keystrokes to the emulator, but that's clumsy. What if the user is at a <code>psql</code> prompt? Then we'd send <code>\\! script_command</code>.\nBut if they're at an OS prompt, that won't work.</p>\n<p>We solved the issue by creating a folder called <code>\\inbox</code> and added a listener to the folder. When files arrive there, if the file ends in <code>.sh</code> (a shell script),\nwe <code>chmod +x</code> that file, execute it, then delete it. That allows us to run commands “in the background” without upsetting the UI.</p>\n<p>If you want to do something very cool, you can connect to another user's Postgres instance that they are running in their browser.\nHere are the steps:</p>\n<ol>\n<li>Find a friend (sometimes the first step is the hardest)</li>\n<li>Tell them to go to <a target=\"_blank\" href=\"https://wasm.supabase.com/\">wasm.supabase.com</a></li>\n<li>Tell them to “Start Network” and get their Network URL</li>\n<li>Have them set a password on their database <code>ALTER ROLE postgres WITH PASSWORD 'my_password';</code></li>\n<li>On your own machine, open a terminal and run\n<code>psql postgres://postgres:my_password@proxy.wasm.supabase.com:&lt;PORT&gt;</code></li>\n<li>And you're in! You're now connecting to a remote Postgres instance, inside a VM, inside a browser, from a terminal on your own computer.</li>\n</ol>\n<p><strong>Database Replication</strong></p>\n<p>Even more mind-blowing - it's possible to replicate data from an online PostgreSQL database (for example, a Supabase project) to PostgreSQL running inside your browser,\nand vice-versa using Postgres's logical replication. The steps are no different than any other Postgres database - just use the proxy URL as the target.</p>\n<p>For now, this is very experimental - but it has a lot of potential. If you want to get involved, please reach out to us or\nthe team at <a target=\"_blank\" href=\"https://www.snaplet.dev/\">Snaplet</a>. The work they're doing over at Snaplet is incredible, and we've had a blast collaborating with them.</p>\n<ul>\n<li>Snaplet repo: <a target=\"_blank\" href=\"https://github.com/snaplet/postgres-wasm\">https://github.com/snaplet/postgres-wasm</a></li>\n<li>Supabase fork: <a target=\"_blank\" href=\"https://github.com/supabase-community/postgres-wasm\">https://github.com/supabase-community/postgres-wasm</a></li>\n</ul></div></article>"
