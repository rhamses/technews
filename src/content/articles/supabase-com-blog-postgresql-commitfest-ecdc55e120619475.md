summary: "A time-tested method for contributing to the core Postgres code"
contentHtml: "<article><div>\n<p>The PostgreSQL community has a specific, effective, and time-tested method for contributing to the core code.</p>\n<p>Proposals and changes to PostgreSQL (called patches) are submitted via email to the common Postgres hackers' mailing list <a target=\"_blank\" href=\"mailto:pgsql-hackers@postgresql.org\">pgsql-hackers@postgresql.org</a>. Then you can track all activity simply by reading your mailbox. You can also follow this mailing list online at <a target=\"_blank\" href=\"https://www.postgresql.org/list/pgadmin-hackers/\">postgresql.org/list/pgadmin-hackers</a>.</p>\n<p>The mailing list contains a lot of different discussions. Some of the patches are preliminary POCs (proof-of-concept) not to be committed to the core directly, and some are urgent bug fixes. When a feature is intended for merging this should be done by creating a Commitfest entry, which resembles a pull request.</p>\n<p>Commitfest is a month-long activity where Postgres contributors and core staff (committers) dedicate to looking at the patches, reviewing them, improving, and committing to the master branch. Effectively these are the months you most probably get feedback on your patches.</p>\n<p>There are 5 commitfests each year. You can see the schedule at <a target=\"_blank\" href=\"https://commitfest.postgresql.org/\">commitfest.postgresql.org</a>. You can only attach a patch to a commitfest <strong>that hasn't started yet</strong> (i.e. before 1st day of a commitfest month).</p>\n<p>There are numerous benefits:</p>\n<ul>\n<li>You gain knowledge of PostgreSQL internals by reviewing other hackers' patches, and grow your profile within the community.</li>\n<li>The process of reviewing involves more senior PostgreSQL experts and as a rule, the code proposed becomes better.</li>\n<li>Lower risk for your code. If you're running a fork or extension that diverges from PG core then only you are responsible for its maintenance. Once it is merged, the entire community will help with maintenance and the API becomes the \"official\" way to do it.</li>\n<li>PostgreSQL commits are likely to survive longer than you do. Like a book manuscript, you get to leave a small history in the world.</li>\n<li>To re-enforce the community. Many features, like performance, have diverse options and many people discuss how to make them better. This is more effective when you join the party.</li>\n</ul>\n<p>Generally, all patches that touch the core code are welcome. It's not necessary that they are complex. In fact, it's an excellent strategy to start by fixing or improving something small.</p>\n<p>The main topics to propose are: bugfixes, performance, server features, clients, security, SQL commands, testing improvements, replication and recovery, procedural languages, code refactoring (yes, it's very important!), monitoring and control, and documentation.</p>\n<p>Some ideas on what to submit:</p>\n<ul>\n<li>Very small and uncontroversial fixes (especially bug fixes) have a good chance to be reviewed and committed even before Commitfest. If they aren't, just attach it to commitfest.</li>\n<li>If you make your feature an extension, the chance of committing it to the core is small. There are nice extensions like Pageinspect and Amcheck, that are committed into PG code as contribs but it is rare (contribs - are extensions that are inside the main PG package)</li>\n<li>There is no need to propose patches to refine translations, .po files etc. This is done by specialists. If you have user-visible messages in your patch just leave it English-only.</li>\n<li>Refining documents, readmes, and comments are welcome if they are clear and precise enough. You can propose a fix for only one line of comment but please don't do nitpicking.</li>\n<li>Performance-related features should better demonstrate performance increase at least in some use cases and no performance degradation in others.</li>\n<li>If your patch changes user behavior be ready to discuss and rework the interface. It's not easy to reach an agreement among many hackers with varying opinions.</li>\n</ul>\n<p>You can find a list of patches for the upcoming commitfest here: <a target=\"_blank\" href=\"https://commitfest.postgresql.org/40/\">commitfest.postgresql.org/40</a></p>\n<p>Make a git branch that is based on the most recent master branch (<a target=\"_blank\" href=\"https://github.com/postgres/postgres\">github.com/postgres/postgres</a>):</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>git clone https://github.com/postgres/postgres</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>git checkout master</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>git checkout -b your_branch_name</span></p></div><br></code></p></div>\n<p>Add your code to the branch (i.e. cherry-pick your commits from another branch).</p>\n<p>Rebase and squash your patch code to be 1 commit against master:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>git rebase -i HEAD~5</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span># This will take the last 5 commits in a branch</span></p></div><div><p><span>_<!-- -->10</span></p><p><span># and you can do anything with them:</span></p></div><div><p><span>_<!-- -->10</span></p><p><span># squash, change order, change commit message, etc</span></p></div><br></code></p></div>\n<p>Edit your commit message to be meaningful and clear. Be concise, but don't be too short. Reviewers enjoy understanding the purpose of a patch and what it does. This is especially important if the patchset consists of several patches. The first line of the commit message will become the patch name on a step later so make that line particularly clear and concise.</p>\n<p>Don't forget to add all the patch authors with their emails to the commit message.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>git format-patch -1 -v13</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span># 1   = patch depth.</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>#       The number of topmost patches to include</span></p></div><div><p><span>_<!-- -->10</span></p><p><span># v13 = the patch version.</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>#       Make new version number anytime you want to</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>#       send updated patch to the same thread)</span></p></div><br></code></p></div>\n<p>Attach the file(s) to an email message (they look like <code>v13-0001-Naming-of-a-patch.patch</code>)</p>\n<p>Compose email message to <a target=\"_blank\" href=\"mailto:pgsql-hackers@postgresql.org\">pgsql-hackers@postgresql.org</a>. Write all rationale and details of your proposal. The main thing to bear in mind is that attracting attention to your proposal is like 50% of success. Also, please be polite.</p>\n<p>It's encouraged to split complicated patches into several independently working parts as it's much easier to review (although not all complicated patches are easy to decompose).</p>\n<p>After you have created a patch, you can attach it to a Commitfest thread:</p>\n<ul>\n<li>Make sure that you have sent email with your patch to the <a target=\"_blank\" href=\"mailto:pgsql-hackers@postgresql.org\">pgsql-hackers@postgresql.org</a> mailing list</li>\n<li>Open commitfests page <a target=\"_blank\" href=\"https://commitfest.postgresql.org/\">commitfest.postgresql.org</a> and choose the nearest commitfest with the status \"Open\"</li>\n<li>Click \"New patch\" button.</li>\n<li>Create a concise description, chose the relevant topic, and fill in the msgid in the hackers mailing list to attach a thread (which can be found in a full header of a mail message e.g.<code>Message-ID: &lt;CANbhV-FG-1ZNMBuwhUF7AxxJz3u5137dYL-o6hchK1V_dMw86g@mail.gmail.com&gt;</code>)</li>\n<li>Click \"Create patch\" button.</li>\n</ul>\n<p>That's all. Congrats!</p>\n<p>After you have a submitted your patch, several things will happen:</p>\n<ul>\n<li>It will appear on CI page <a target=\"_blank\" href=\"http://cfbot.cputube.org/\">cfbot.cputube.org</a> which will check its health against several architectures and OSes. If the patch has any errors then you should fix/rebase it. New versions of patches sent in messages replying to the mail thread are taken by CFBot automatically. Send updated versions of all patches in a patchset even if only one changed, otherwise cfbot will not take it properly. Clean status patches will attract reviewers' and committers' attention first.</li>\n<li>It will get \"Needs review\" status and anyone could add a review and change it to \"Ready for committer\" or \"Waiting on author\".</li>\n<li>You are supposed to <strong>answer the questions</strong> and communicate on your patch regularly during commitfest. That includes fixing the things the other hackers propose. It's likely better to follow their opinion and it almost always takes much less effort than arguing. Be polite, even if comments seem like nitpicking (probably they are not, actually).</li>\n<li>Give back. You are supposed to <strong>review</strong> the same number of patches that you proposed to commitfest and with similar complexity. You can choose what to review based on your interest, your knowledge of a particular part of Postgres (e.g. indexes or planner things), or even your personal acquaintance with the author. As a rule of thumb, you are supposed to specify if you are from the same company as the author (it is not prohibited but this should be clear, the best way is just to add your company to the email signature).</li>\n</ul>\n<p>The commit process is a two-step:</p>\n<ol>\n<li>Preliminary review. It could be done by anyone (including you). A detailed guide on how to do this <a target=\"_blank\" href=\"https://wiki.postgresql.org/wiki/Reviewing_a_Patch\">wiki.postgresql.org/wiki/Reviewing_a_Patch</a> If there are no doubts reviewer sets the status to \"Ready for committer\". If the patch needs some changes a reviewer can set \"Waiting on author\". Reviewers can leave a favorable review but that's only a signal. After other reviewers join the conversation, if there are no objections then one of them will make it \"Ready for committer\". It's pretty normal if there is more than one reviewer. In fact the more reviewers, the better.</li>\n<li>Final review by a committer. Committers are the most senior members of a community and it's a formal status. The list of committers: <a target=\"_blank\" href=\"https://wiki.postgresql.org/wiki/Committers\">wiki.postgresql.org/wiki/Committers</a> As a result a committer can commit it or push back to \"Waiting on author\", or \"Need review\".</li>\n</ol>\n<p>The time and attention of committers are limited, which is why there is a two-step process. Some patches that pass the initial review won't receive reviewers' attention. In that case, they will be transferred to the next commitfest automatically.</p>\n<p>CF finishes around the 1st day of the next month (i.e. November CF starts on November 1 and finishes on December 1). For any patches that do not get merged:</p>\n<ul>\n<li>Patches with the status \"Ready for committer\" or \"Need review\" will be transferred to the next CF.</li>\n<li>Patches with the status \"Waiting on author\" are transferred automatically if the questions and proposals in the thread are not unaddressed for more than 2 weeks. Otherwise, it will be dropped from CF with \"Returned with feedback\".</li>\n</ul>\n<p>All these \"automatic\" things are actually done by commitfest managers (volunteers), so if you have any requests, doubts, or questions you can write them personally.</p>\n<p>Please note that hackers almost never reject patches! They just return it and the author if he is still willing and has time to work on the patch further can attach it (the same thread) to the next commitfest anytime.</p>\n<p>Feature-freeze is an annual event that targets patches released into a major PostgreSQL version. Feature-freeze for the \"current-year\" release is at the end of a March commitfest. All patches committed on and before will be released in the PG major release (in October). Everything committed after March (July, September, etc) will go into next year's major release.</p>\n<p>For that reason, the March Commitfest takes <strong>10-15 days longer</strong> than the usual 1 month, finishing in mid-April. It's important for the author to continue watching your patches and feedback until that time. Commits in early April are big!</p>\n<ul>\n<li>If you want to discuss something with hackers without a thread overhead (which makes it more difficult to read by other hackers) you can wipe out <a target=\"_blank\" href=\"mailto:pgsql-hackers@postgresql.org\">pgsql-hackers@postgresql.org</a> from the reply list and leave only the participants you want. If you do this, you should add <code>[offlist]</code> to the message subject to prevent confusion.</li>\n<li>The hackers mail list receives <em>a lot</em> of messages. It's advisable to set up mail filtering so that hackers' messages are sorted into separate places and shown as threads. But ensure that all messages that contain <strong>your address</strong> will NOT go into this place so that you can read all answers to your proposal among your prioritized emails.</li>\n<li>Patches that need minor rework like rebase or comments refine are pushed back to \"Waiting on author\". Therefore, almost-ready patch very often stall, waiting for a new review, during which it will need another rebase and it goes into a vicious circle. If you are certain that the change is minor and doesn't affect functionality, you can return the patch to the same state it had before (if it was \"Ready-for-committer\" it should be ready for committer even after rebase). It's good manners to mention this change in a hacker's thread to remove suspicions that you want to hijack the patch status.</li>\n<li>It’s very good to be proactive with your patch not only change something on request. Sometimes it’s hard to describe in detail what needs improving and hackers may give only approximate direction of work. If you see criticism it’s very good to answer this with possible proposals on how can you change the code, or what measurements you can do to drop possible doubts about functionality or performance.</li>\n<li>It’s also very nice to keep watching activity in the patch thread after it is committed. Sometimes small problems arise later and you can propose a separate fix and get a reputation as a responsible contributor. Also, you know your code better and it would be very valuable for everyone though other hackers could help you with this.</li>\n</ul>\n<p>If you're interested in contributing to PostgreSQL full time, <a target=\"_blank\" href=\"https://boards.greenhouse.io/supabase/jobs/4307456004\">Supabase is hiring Postgres Core Contributors</a>.</p>\n<h2 id=\"more-postgres-resources\">More Postgres resources<a target=\"_blank\" href=\"https://supabase.com/blog/postgresql-commitfest#more-postgres-resources\">#</a></h2>\n<ul>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/postgres-full-text-search-vs-the-rest\">Postgres Full Text Search vs the rest</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/postgres-wasm\">Postgres WASM by Snaplet and Supabase</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/choosing-a-postgres-primary-key\">Choosing a Postgres Primary Key</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/seen-by-in-postgresql\">Implementing \"seen by\" functionality with Postgres</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/partial-postgresql-data-dumps-with-rls\">Partial data dumps using Postgres Row Level Security</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/postgresql-views\">Postgres Views</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/realtime-row-level-security-in-postgresql\">Realtime Postgres RLS on Supabase</a></li>\n</ul></div></article>"
