Creating a view does not involve new tables or data. When run, an underlying query is executed, returning its results to the user.</p>\n<h3 id=\"basic-example\">Basic example<a target=\"_blank\" university:</p>\n<p><strong>students</strong></p>\n<table><thead><tr><th>id</th><th>name</th><th>type</th></tr></thead><tbody><tr><td>1</td><td>Arun</td><td>undergraduate</td></tr><tr><td>2</td><td>Zack</td><td>graduate</td></tr><tr><td>3</td><td>Joy</td><td>graduate</td></tr></tbody></table>\n<p><strong>courses</strong></p>\n<table><thead><tr><th>id</th><th>title</th><th>code</th></tr></thead><tbody><tr><td>1</td><td>Introduction to Postgres</td><td>PG101</td></tr><tr><td>2</td><td>Authentication Theories</td><td>AUTH205</td></tr><tr><td>3</td><td>Fundamentals of Supabase</td><td>SUP412</td></tr></tbody></table>\n<p><strong>grades</strong></p>\n<table><thead><tr><th>id</th><th>student_id</th><th>course_id</th><th>result</th></tr></thead><tbody><tr><td>1</td><td>1</td><td>1</td><td>B+</td></tr><tr><td>2</td><td>1</td><td>3</td><td>A+</td></tr><tr><td>3</td><td>2</td><td>2</td><td>A</td></tr><tr><td>4</td><td>3</td><td>1</td><td>A-</td></tr><tr><td>5</td><td>3</td><td>2</td><td>A</td></tr><tr><td>6</td><td>3</td><td>3</td><td>B-</td></tr></tbody></table>\n<p>Creating a view consisting of all the three tables will look like this:</p>\n<div><p><code><br><div><p><span>_<!-- -->11</span></p><p><span>create view transcripts as</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  select</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    students.name,</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    students.type,</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    courses.title,</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    courses.code,</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    grades.result</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  from</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    grades</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    left join students on grades.student_id = students.id</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    left join courses on grades.course_id = courses.id;</span></p></div><br></code></p></div>\n<p>Once done, we can now access the underlying query with:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>select * from transcripts;</span></p></div><br></code></p></div>\n<p>For additional parameters or options, refer <a benefits:</p>\n<ul>\n<li>Simplicity</li>\n<li>Consistency</li>\n<li>Logical Organization</li>\n<li>Security</li>\n</ul>\n<h3 id=\"simplicity\">Simplicity<a target=\"_blank\" href=\"https://supabase.com/blog/postgresql-views#simplicity\">#</a></h3>\n<p>As a query becomes complex it becomes a hassle to call it. Especially when we run it at regularly. In the example above, instead of repeatedly running:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>select</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  students.name,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  students.type,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  courses.title,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  courses.code,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  grades.result</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>from</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  grades</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  left join students on grades.student_id = students.id</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  left join courses on grades.course_id = courses.id;</span></p></div><br></code></p></div>\n<p>We can run this instead:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>select * from transcripts;</span></p></div><br></code></p></div>\n<p>Additionally, a view behaves like a typical table. We can safely use it in table <code>JOIN</code>s or even create new views using existing views.</p>\n<h3 id=\"consistency\">Consistency<a target=\"_blank\" href=\"https://supabase.com/blog/postgresql-views#consistency\">#</a></h3>\n<p>Views ensure that the likelihood of mistakes decreases when repeatedly executing a query. In our example above, we may decide that we want to exclude the course <em>Introduction to Postgres</em>. The query would become:</p>\n<div><p><code><br><div><p><span>_<!-- -->11</span></p><p><span>select</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  students.name,</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  students.type,</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  courses.title,</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  courses.code,</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  grades.result</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>from</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  grades</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  left join students on grades.student_id = students.id</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  left join courses on grades.course_id = courses.id</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>where courses.code != 'PG101';</span></p></div><br></code></p></div>\n<p>Without a view, we would need to go into every dependent query to add the new rule. This would increase in the likelihood of errors and inconsistencies, as well as introducing a lot of effort for a developer. With views, we can alter just the underlying query in the view <strong>transcripts</strong>. The change will be applied to all applications using this view.</p>\n<h3 id=\"logical-organization\">Logical organization<a target=\"_blank\" href=\"https://supabase.com/blog/postgresql-views#logical-organization\">#</a></h3>\n<p>With views, we can give our query a name. This is extremely useful for teams working with the same database. Instead of guessing what a query is supposed to do, a well-named view can easily explain it. For example, by looking at the name of the view <strong>transcripts</strong>, we can infer that the underlying query might involve the <strong>students</strong>, <strong>courses</strong>, and <strong>grades</strong> tables.</p>\n<h3 id=\"security\">Security<a target=\"_blank\" href=\"https://supabase.com/blog/postgresql-views#security\">#</a></h3>\n<p>Views can restrict the amount and type of data presented to a user. Instead of allowing a user direct access to a set of tables, we provide them a view instead. We can prevent them from reading sensitive columns by excluding them from the underlying query.</p>\n<p>A <a target=\"_blank\" href=\"https://www.postgresql.org/docs/12/rules-materializedviews.html\">materialized view</a> is a form of view but with the added feature of physically storing the results. In subsequent reads of a materialized view, the time taken to return its results would be much faster than a conventional view. This is because the data is readily available for a materialized view while the conventional view executes the underlying query each time it is called.</p>\n<h3 id=\"basic-example-1\">Basic example<a target=\"_blank\" href=\"https://supabase.com/blog/postgresql-views#basic-example-1\">#</a></h3>\n<p>Using our example above, a materialized view can be created like this:</p>\n<div><p><code><br><div><p><span>_<!-- -->11</span></p><p><span>create materialized view transcripts as</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  select</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    students.name,</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    students.type,</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    courses.title,</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    courses.code,</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    grades.result</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  from</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    grades</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    left join students on grades.student_id = students.id</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>    left join courses on grades.course_id = courses.id;</span></p></div><br></code></p></div>\n<p>Reading from the materialized view is the same as a conventional view:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>select * from transcripts;</span></p></div><br></code></p></div>\n<p>For additional parameters or options, refer <a target=\"_blank\" href=\"https://www.postgresql.org/docs/12/sql-creatematerializedview.html#:~:text=parameters\">here</a>.</p>\n<h3 id=\"refreshing\">Refreshing<a target=\"_blank\" href=\"https://supabase.com/blog/postgresql-views#refreshing\">#</a></h3>\n<p>Unfortunately, there is a trade-off - data in materialized views are not always up to date. We need to refresh it regularly to prevent the data from becoming too stale. To do so:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>refresh materialized view transcripts;</span></p></div><br></code></p></div>\n<p>It's up to you how regularly refresh your materialized views, and it's probably different for each view depending on its use-case.</p>\n<p>Materialized views are useful when execution times for queries or views become unbearable or exceed the service level agreements of a business. These could likely occur in views or queries involving multiple tables and millions of rows. When using such a view, however, there should be tolerance towards data being outdated. Some use-cases for materialized views are internal dashboards and analytics.</p>\n<p>Creating a materialized view is not a solution to inefficient queries. You should always seek to optimize a slow running query even if you are implementing a materialized view.</p>\n<p>Postgres views and materialized views are a great way to organize and view results from commonly used queries. Although similar to one another, each has its purpose. Views simplify the process of running queries. Materialized views are usually faster at returning results, with the trade-off of having stale data.</p>\n<h2 id=\"more-postgres-resources\">More Postgres resources<a target=\"_blank\" href=\"https://supabase.com/blog/postgresql-views#more-postgres-resources\">#</a></h2>\n<ul>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/seen-by-in-postgresql\">Implementing \"seen by\" functionality with Postgres</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/partial-postgresql-data-dumps-with-rls\">Partial data dumps using Postgres Row Level Security</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/audit\">Postgres Auditing in 150 lines of SQL</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/cracking-postgres-interview\">Cracking PostgreSQL Interview Questions</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/postgresql-templates\">What are PostgreSQL Templates?</a></li>\n<li><a target=\"_blank\" href=\"https://supabase.com/blog/realtime-row-level-security-in-postgresql\">Realtime Postgres RLS on Supabase</a></li>\n</ul></div></article>"
