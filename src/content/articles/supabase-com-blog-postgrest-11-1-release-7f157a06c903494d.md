contentHtml: "<article><div>\n<p>PostgREST 11.1 is now available on the Supabase platform. Besides the <a target=\"_blank\" href=\"https://supabase.com/blog/postgrest-11-prerelease\">pre-release</a> features, we’ve added configuration and querying improvements. Here is what's new:</p>\n<p>Every role that passes <a target=\"_blank\" href=\"https://postgrest.org/en/stable/references/auth.html#jwt-based-user-impersonation\">PostgREST JWT Authentication</a> is an <em>impersonated role</em>. On the Supabase platform, these are the <code>anon</code>, <code>authenticated</code> and <code>service_role</code> roles.</p>\n<p>These roles can now have settings applied with a regular <code>ALTER ROLE .. SET</code>. This is useful, for example, to prevent web users from running expensive queries.</p>\n<p>Let’s try it by setting a statement timeout and cost limit.</p>\n<h3 id=\"statement-timeout\">Statement timeout<a target=\"_blank\" href=\"https://supabase.com/blog/postgrest-11-1-release#statement-timeout\">#</a></h3>\n<p><code>statement_timeout</code> aborts any statement that takes more than the specified amount of time. Let’s set it for the <code>anon</code>, <code>authenticated</code> and <code>service_role</code> roles:</p>\n<div><p><code><br><div><p><span>_<!-- -->17</span></p><p><span>-- anonymous users can run queries that take 100 milliseconds max</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>alter</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>  role anon</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>set</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>  statement_timeout = '100ms';</span></p></div><div><p><span>_<!-- -->17</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>-- authenticated users can run queries that take 5 seconds max</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>alter</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>  role authenticated</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>set</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>  statement_timeout = '5s';</span></p></div><div><p><span>_<!-- -->17</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>-- backend-only users can run queries that take 15 seconds max</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>alter</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>  role service_role</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>set</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>  statement_timeout = '15s';</span></p></div><br></code></p></div>\n<p>You need to reload PostgREST config cache to apply these changes.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>NOTIFY pgrst,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>'reload config';</span></p></div><br></code></p></div>\n<p>Now, suppose you do an expensive query with the <code>anon</code> role. Like filtering on a big table's unindexed column (this will cause a full table scan):</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>const { data, error } = await supabase.from('big_table').select().eq('unindexed_column', 'value')</span></p></div><br></code></p></div>\n<p>Then, after 5 seconds, the request will be aborted with the response:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>{</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  \"hint\": null,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  \"details\": null,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  \"code\": \"57014\",</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  \"message\": \"canceling statement due to statement timeout\"</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>}</span></p></div><br></code></p></div>\n<p>Which is what we wanted. Note that there's already a global <code>statement_timeout</code> set but you can be more fine-grained with this feature. See <a target=\"_blank\" href=\"https://supabase.com/docs/guides/database/timeouts\">timeouts</a> for more details.</p>\n<h3 id=\"statement-cost-limit\">Statement Cost Limit<a target=\"_blank\" href=\"https://supabase.com/blog/postgrest-11-1-release#statement-cost-limit\">#</a></h3>\n<p>With a statement timeout, expensive queries will still get executed for a length of time. They'll consume resources until they’re terminated.</p>\n<p>The <a target=\"_blank\" href=\"https://github.com/pgexperts/pg_plan_filter\">pg_plan_filter</a> extension (available on the Supabase platform), brings a statement cost limit. This abort queries at the planning phase, before they get executed.</p>\n<p>You can use it like:</p>\n<div><p><code><br><div><p><span>_<!-- -->22</span></p><p><span>-- anonymous users can only run cheap queries</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>ALTER</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>  USER anon</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>SET</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>  plan_filter.statement_cost_limit = 10000;</span></p></div><div><p><span>_<!-- -->22</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>-- authenticated users can run more expensive queries</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>ALTER</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>  USER authenticated</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>SET</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>  plan_filter.statement_cost_limit = 1e6;</span></p></div><div><p><span>_<!-- -->22</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>-- backend-only users can run any query</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>ALTER</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>  USER service_role</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>SET</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>  plan_filter.statement_cost_limit = 0;</span></p></div><div><p><span>_<!-- -->22</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>NOTIFY pgrst,</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>'reload config';</span></p></div><div><p><span>_<!-- -->22</span></p></div><div><p><span>_<!-- -->22</span></p><p><span>-- reload postgREST config cache to apply changes</span></p></div><br></code></p></div>\n<p>Let’s repeat the previous expensive query with the <code>anon</code> role.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>const { data, error } = await supabase.from('big_table').select().eq('unindexed_column', 'value')</span></p></div><br></code></p></div>\n<p>Then, immediately, the request will be aborted and the response will be:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>{</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  \"hint\": null,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  \"details\": null,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  \"code\": \"54001\",</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  \"message\": \"plan cost limit exceeded\"</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>}</span></p></div><br></code></p></div>\n<p>Note that tuning is required to get the cost limit right. You should use the <code>plan_filter.statement_cost_limit</code> with care as it can invalidate legitimate queries.</p>\n<p>By default, all queries run in a transaction with the default <em>read committed</em> isolation level.</p>\n<p>You can now modify this with the <code>default_transaction_isolation</code> setting.</p>\n<p>If you want a function to run with <em>repeatable read</em> isolation level:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>create function hello()</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>returns text as $$</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  select 'hello';</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>$$ language sql</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>set default_transaction_isolation = 'repeatable read';</span></p></div><br></code></p></div>\n<p>Or if you want an impersonated role to run its queries with a <em>serializable</em> isolation level:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>alter</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  role service_role</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>set</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  default_transaction_isolation = 'serializable';</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>NOTIFY pgrst,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>'reload config';</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>-- reload postgREST config cache</span></p></div><br></code></p></div>\n<p>Note that the default <em>read committed</em> is good enough for almost all use cases. Higher isolation levels incur in overhead as they use more sophisticated locking. They're only needed in special cases.</p>\n<p>A long wanted feature was bulk inserting JSON while considering columns' default values.</p>\n<p>Having the following sample table.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>create table</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  foo (</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>    baz int default 100</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  );</span></p></div><br></code></p></div>\n<p>You can now do it like this:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>const { error } = await supabase</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  .from('foo')</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  .insert([</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>\t  { \"bar\": -->10</span></p><p><span>\t  , \"baz\": 15</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>\t  }</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>\t], defaultToNull: false)</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  .select()</span></p></div><br></code></p></div>\n<p>And the response will be:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>[</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  { \"id\": 1, \"bar\": \"val1\", \"baz\": 100 },</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  { \"id\": 2, \"bar\": \"val2\", \"baz\": 15 }</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>]</span></p></div><br></code></p></div>\n<p>As you can see, <code>id</code> and <code>baz</code> took their default values.</p>\n<p>As a shortcut to <code>OR</code> filters, you can now use <code>any</code> modifiers on various filters. Take the <code>like</code> filter as an example:</p>\n<!-- -->\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>const res = await postgrest</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  .from('users')</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  .select()</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  .likeAnyOf('username', ['%supa%', '%kiwi%'])</span></p></div><br></code></p></div>\n<p>This is equivalent to the following in SQL.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>select *</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>from users</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>where username like ANY('{%supa%,%kiwi%}');</span></p></div><br></code></p></div>\n<p><code>any</code> modifiers are available for the <code>eq,like,ilike,gt,gte,lt,lte,match,imatch</code> filters.</p>\n<p>For completeness, the <code>all</code> modifier is also included.</p>\n<p>If you only use PostgREST through Supabase client libraries (like <a target=\"_blank\" href=\"https://supabase.com/docs/reference/javascript/introduction\"><code>supabase-js</code></a>) then it's safe to upgrade to v11. If you use PostgREST with other HTTP clients (like <code>curl</code>), consider the breaking changes for this version:</p>\n<ul>\n<li>The <code>Range</code> header is now only considered on GET requests and is ignored for any other method. Previously PostgREST responded with an error but <a target=\"_blank\" href=\"https://www.rfc-editor.org/rfc/rfc9110.html#name-range\">RFC 9110</a> dictates that we should ignore the <code>Range</code> header instead.</li>\n<li>RPC requests no longer consider the <code>Prefer: params=multiple-objects</code> header. This header was already deprecated on <a target=\"_blank\" href=\"https://github.com/PostgREST/postgrest/releases/tag/v10.1.0\">v10.1.0</a>.</li>\n</ul>\n<p>By making use of <a target=\"_blank\" href=\"https://logflare.app/\">Logflare</a>, we detected that out of 20 thousands of projects:</p>\n<ul>\n<li>Only 7 projects used <code>Range</code> for HTTP methods other than GET. In these cases all responses were errors so in fact this breaking change is a fix for those requests.</li>\n<li>None were using <code>Prefer: params=multiple-objects</code>.</li>\n</ul>\n<p>So overall the breaking changes are minimal.</p>\n<p>There you have it, now you can make your API more secure with role settings and use higher isolation levels without resorting to direct PostgreSQL connections.</p>\n<p>PostgREST v11.1 is available for all Supabase projects created after 5 July 2023.
