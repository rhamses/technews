Previously, you could only use aggregate functions <em>indirectly</em> with PostgREST, for instance, by using them in a view, but with the latest release, you can now use aggregate functions on the fly, dynamically slicing-and-dicing data directly through the PostgREST API.</p>\n<p>In this post, we’ll go through a few examples of some of the neat things you can do with this new feature. We’ll also discuss the importance of ensuring you have the appropriate safeguards in place to prevent potential performance issues that may arise when using aggregate functions.</p>\n<p>For the most complete information, please be sure to refer to <a target=\"_blank\" href=\"https://postgrest.org/en/v12.0/references/api/aggregate_functions.html\">the section on aggregate functions in the documentation</a>.</p>\n<p>PostgREST supports a handful of the most-common aggregate functions from PostgreSQL: <code>avg()</code>, <code>count()</code>, <code>max()</code>, <code>min()</code>, and <code>sum()</code>. These functions more or less do what their names suggest, but you can always take a deeper look at the <a target=\"_blank\" href=\"https://www.postgresql.org/docs/current/functions-aggregate.html\">PostgreSQL documentation</a> to learn more.</p>\n<p>Let’s take a look at an example. Because of the potential performance risks with aggregate functions, we have <a target=\"_blank\" href=\"https://postgrest.org/en/stable/references/configuration.html#db-aggregates-enabled\"><strong>disabled</strong> aggregate functions by default</a>. As you might imagine, higher costs are associated with slower queries, and therefore setting an upper bound can limit your exposure to performance problems or even denial-of-service attacks. <code>pg_plan_filter_module</code> enables you to easily set this upper bound using PostgreSQL configuration.</p>\n<p>You can even change this limit on a per-role basis, allowing more privileged roles free rein in the queries they run, while less-privileged roles — perhaps external users of your public API, for instance — could have tighter limits.</p>\n<!-- -->\n<div><p><code><br><div><p><span>_<!-- -->11</span></p><p><span>-- anonymous users can only run cheap queries</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>ALTER</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  USER anon</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>SET</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  plan_filter.statement_cost_limit = 10000;</span></p></div><div><p><span>_<!-- -->11</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>-- authenticated users can run more expensive queries</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>ALTER</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  USER authenticated</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>SET</span></p></div><div><p><span>_<!-- -->11</span></p><p><span>  plan_filter.statement_cost_limit = 1e6;</span></p></div><br></code></p></div>\n<p>You can take a look at an example of using per-role configuration with PostgREST <a target=\"_blank\" href=\"https://postgrest.org/en/stable/references/transactions.html#impersonated-role-settings\">in the documentation</a>.</p>\n<p>PostgREST v12 now has aggregate functions, giving you a lot more flexibility in how you work with your data. Even better, it’s deeply integrated with other PostgREST features you already know, providing you with a powerful new abstraction that fits in frictionlessly with existing features.</p>\n<p>While we are excited to bring aggregate functions to PostgREST, it’s important for administrators and users to understand the risks that come with them, hence why this feature comes as opt-in only. Make sure to have a strategy in place — like using <code>pg_plan_filter_module</code> — before enabling aggregate functions to ensure maximum protection.</p></div></article>"
