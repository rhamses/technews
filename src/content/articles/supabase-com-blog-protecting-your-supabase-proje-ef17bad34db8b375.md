contentHtml: "<article><div>\n<p>There has been a growing trend of supply chain attacks on Node Package Manager (NPM). In addition, we have seen other creative attacks, including a typosquat package named <code>supabase-javascript</code> that appeared on npm, copying our name to phish developers. We reported it. npm took it down a few hours later, long enough that the package picked up real downloads.</p>\n<p>If you build on Supabase, this matters to you. Edge Functions pull from npm. The Supabase CLI is on npm. <code>supabase-js</code>, <code>@supabase/ssr</code>, and <code>@supabase/server</code> are all on npm. Any of these is a credential leak waiting for the wrong update to land.</p>\n<p>This post lays out what we are doing about it and what you should do today.</p>\n<p>We kicked off a <a target=\"_blank\" href=\"https://supabase.com/docs/guides/security/npm-security#what-supabase-does-on-its-side\">coordinated response</a> across the company. The work in flight:</p>\n<ul>\n<li><strong>Publishing a <a target=\"_blank\" href=\"https://supabase.com/docs/guides/security/npm-security\">canonical security guide</a> in our docs.</strong> A single, agent-readable page that tells you exactly what to do.</li>\n<li><strong>Hardening our own GitHub Actions.</strong> Our security team finished a pass on <code>pull_request_target</code> usage across the Supabase org months ago and is close to enforcing pinned action SHAs across every repo.</li>\n<li><strong>Adding security notes to secret-handling APIs.</strong> TSDoc and JSDoc on functions like <code>createClient</code> so editor hovers warn when you are working with sensitive credentials.</li>\n<li><strong>Comms across every channel.</strong> Our goal is to educate as many people as we can, whether or not they are Supabase customers.</li>\n</ul>\n<p>Supply chain attacks share a shape. The attacker does not break into your computer. They get you to invite their code in, and they do that by getting their code into a package you already trust. The recipes vary, but the three most common patterns are these:</p>\n<ul>\n<li><strong>Maintainer compromise.</strong> An attacker steals an npm publish token or phishes a maintainer, then publishes a new version of a popular package with malicious code added. The next time you run <code>npm install</code> against that range, you are running their code.</li>\n<li><strong>Typosquatting.</strong> An attacker registers a package name a few letters away from a real one, like <code>supabase-javascript</code> instead of <code>@supabase/supabase-js</code>. They wait for a developer or, increasingly, an AI coding agent to mistype the name. AI agents hallucinate package names regularly, and that is now a primary attack vector against teams that vibe-code their dependencies.</li>\n<li><strong>Build pipeline compromise.</strong> This is what hit TanStack. An attacker found a vulnerable GitHub Actions workflow, poisoned the build cache from a fork PR, and waited for the next legitimate release run to pick up the poisoned cache and publish their code under the real maintainer's identity. No stolen tokens. No compromised laptops. The attacker rode the official release train.</li>\n</ul>\n<p>Once the malicious code lands on disk in your <code>node_modules</code>, npm's lifecycle scripts run it. By the time <code>npm install</code> returns, the attacker has already read your environment variables, your AWS instance metadata, your kubeconfig, your <code>.npmrc</code> token, your <code>.git-credentials</code>, and your SSH private keys. The TanStack payload exfiltrated through the Session messenger network, which is end-to-end encrypted and has no fixed command-and-control address. You cannot block it at the firewall.</p>\n<p><a target=\"_blank\" href=\"https://tanstack.com/blog/npm-supply-chain-compromise-postmortem\">The TanStack postmortem</a> describes the full chain and is worth reading if you maintain a public open source project. The short version: every link in the chain (a <code>pull_request_target</code> workflow, an unsecured Actions cache, a long-lived OIDC publish token) was a known issue with public mitigations. The attack worked because nobody had connected the dots in advance.</p>\n<p>Most of what follows takes minutes. The goal is layered defense: no single mitigation stops every attack, but together they raise the cost enough that attackers go bother someone else.</p>\n<h3 id=\"upgrade-to-pnpm-11-or-the-npm-v11-equivalent\">Upgrade to pnpm 11 (or the npm v11 equivalent)<a target=\"_blank\" href=\"https://supabase.com/blog/protecting-your-supabase-projects-from-npm-supply-chain-attacks#upgrade-to-pnpm-11-or-the-npm-v11-equivalent\">#</a></h3>\n<p>pnpm 11 sets <code>minimumReleaseAge</code> to 24 hours by default, blocks exotic subdependencies by default, and ships a new Allow Builds model that controls which dependencies are permitted to run install scripts. <strong>If your AI coding agent picked pnpm 10.x for you, fix that.</strong> Tell it to use pnpm 11.</p>\n<p>Then set <code>minimumReleaseAge</code> higher than the default. <strong>Three to seven days is a reasonable starting point</strong> for most projects. Most malicious npm packages are caught and pulled within twenty-four to forty-eight hours, so a three-day window catches the long tail of detections without throttling legitimate updates too much. Configure it in your project's <code>pnpm-workspace.yaml</code> or <code>.npmrc</code>:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>minimumReleaseAge: 4320 # minutes, equals 3 days</span></p></div><br></code></p></div>\n<h3 id=\"pin-versions-especially-for-security-sensitive-dependencies\">Pin versions, especially for security-sensitive dependencies<a target=\"_blank\" href=\"https://supabase.com/blog/protecting-your-supabase-projects-from-npm-supply-chain-attacks#pin-versions-especially-for-security-sensitive-dependencies\">#</a></h3>\n<p>The <code>^</code> and <code>~</code> ranges in your <code>package.json</code> are a polite way of telling npm \"trust me, take the next minor or patch version.\" Supply chain attacks exploit exactly that trust. <strong>Pin exact versions for anything that touches authentication, secrets, networking, or user data.</strong> Use <code>^</code> only where you actively want updates and have a process to vet them.</p>\n<h3 id=\"commit-your-lockfile-and-review-changes-to-it\">Commit your lockfile and review changes to it<a target=\"_blank\" href=\"https://supabase.com/blog/protecting-your-supabase-projects-from-npm-supply-chain-attacks#commit-your-lockfile-and-review-changes-to-it\">#</a></h3>\n<p>A lockfile records exactly which version of which package, with which hash, you installed. If an attacker republishes a tarball under the same version number, the hash mismatch fails the install. Commit <code>pnpm-lock.yaml</code>, <code>package-lock.json</code>, or <code>yarn.lock</code> to your repo. <strong>Treat lockfile diffs as code review surface, not noise.</strong> A pull request that bumps fifty transitive dependencies for no obvious reason deserves a careful read before it merges.</p>\n<h3 id=\"disable-npm-install-scripts-where-you-can\">Disable npm install scripts where you can<a target=\"_blank\" href=\"https://supabase.com/blog/protecting-your-supabase-projects-from-npm-supply-chain-attacks#disable-npm-install-scripts-where-you-can\">#</a></h3>\n<p>Most supply chain payloads run through <code>preinstall</code>, <code>install</code>, or <code>postinstall</code> lifecycle scripts. If your project does not need them, turn them off globally:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>npm config set ignore-scripts true</span></p></div><br></code></p></div>\n<p>Or scope it to the project via <code>.npmrc</code>:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>ignore-scripts=true</span></p></div><br></code></p></div>\n<p>The trade-off is that some packages with native code (<code>bcrypt</code>, <code>sharp</code>, and similar) will not build without scripts. Use pnpm's Allow Builds model to allowlist the specific packages you actually need rather than allowing every package on the registry to run code at install time.</p>\n<h3 id=\"verify-package-names-every-single-time-you-install\">Verify package names every single time you install<a target=\"_blank\" href=\"https://supabase.com/blog/protecting-your-supabase-projects-from-npm-supply-chain-attacks#verify-package-names-every-single-time-you-install\">#</a></h3>\n<p>Typosquats target the moment of carelessness. Before you <code>pnpm add</code> anything, especially anything an AI agent suggested, check that:</p>\n<ul>\n<li><strong>The scope is correct.</strong> Official Supabase packages live under <code>@supabase/</code>. A package named <code>supabase-javascript</code> or <code>supabase-server</code> without the scope is not ours and never has been.</li>\n<li><strong>The maintainer is the expected one.</strong> The npm page lists current maintainers; a brand-new maintainer on a long-established package is a signal worth a closer look.</li>\n<li><strong>The download counts and the linked GitHub repo match what you expect</strong> for a real, established package.</li>\n</ul>\n<h3 id=\"pin-your-github-actions-to-commit-shas-not-tags\">Pin your GitHub Actions to commit SHAs, not tags<a target=\"_blank\" href=\"https://supabase.com/blog/protecting-your-supabase-projects-from-npm-supply-chain-attacks#pin-your-github-actions-to-commit-shas-not-tags\">#</a></h3>\n<p>If you maintain a public repo, this is the single biggest change you can make. A tag like <code>@v5</code> is a moving target. The maintainer of that action (or an attacker who compromised that maintainer) can republish the tag with new code, and your workflow will pick it up on the next run. Pin to the full commit SHA instead:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>- uses: actions/checkout@1f9a0c22da41e6ebfa534300ef656b67ce0c5b94 # v6.0.2</span></p></div><br></code></p></div>\n<p>Renovate and Dependabot both understand this syntax and will update the comment when a new release is published, so you still get visibility without giving up safety.</p>\n<h3 id=\"avoid-pull_request_target-with-code-checkout\">Avoid <code>pull_request_target</code> with code checkout<a target=\"_blank\" href=\"https://supabase.com/blog/protecting-your-supabase-projects-from-npm-supply-chain-attacks#avoid-pull_request_target-with-code-checkout\">#</a></h3>\n<p>If your workflow uses <code>pull_request_target</code> and then checks out code from the PR, you are running attacker-controlled code in a context that has access to your repo's secrets and cache. <strong>This is the exact pattern that compromised TanStack.</strong> Use <code>pull_request</code> for anything that touches PR code. Reserve <code>pull_request_target</code> for trusted, no-checkout operations like labeling or commenting on the PR.</p>\n<h3 id=\"rotate-credentials-if-you-think-you-were-exposed\">Rotate credentials if you think you were exposed<a target=\"_blank\" href=\"https://supabase.com/blog/protecting-your-supabase-projects-from-npm-supply-chain-attacks#rotate-credentials-if-you-think-you-were-exposed\">#</a></h3>\n<p>If you ran <code>npm install</code> on a day when a package you depend on turned out to be compromised, treat the install host as potentially compromised too. Rotate everything reachable from that machine: AWS, GCP, Kubernetes, Vault, GitHub, npm, SSH, and any Supabase service-role keys. Audit your service-role key usage in the Supabase dashboard for access patterns you do not recognize. <strong>It is an annoying afternoon. It is not as annoying as a customer breach.</strong></p>\n<h3 id=\"consider-a-scanner-as-a-second-line-of-defense\">Consider a scanner as a second line of defense<a target=\"_blank\" href=\"https://supabase.com/blog/protecting-your-supabase-projects-from-npm-supply-chain-attacks#consider-a-scanner-as-a-second-line-of-defense\">#</a></h3>\n<p>Tools like <a target=\"_blank\" href=\"https://socket.dev/\">Socket.dev</a>, npq, and Snyk monitor the npm registry and flag suspicious package behavior in real time. None of them are a silver bullet, and none of them substitute for the practices above. They are a useful second line of defense for teams that already have the basics in place.</p>\n<p>This kind of attack will keep happening. The cost of pulling one off keeps dropping; the payoff (credentials to dozens of production systems in a single shot) keeps rising. The good news is that the defenses are well understood, cheap to implement, and effective when stacked. Pin your versions. Wait for the dust to settle on new releases. Lock your CI down. Verify what you install. Tell your AI agents to do the same.</p>\n<p>If you have suggestions, requests, or your own war stories about how you handle this on your team, find me on Discord or on Twitter.</p>\n<p>Paste this into Claude Code, Codex, Cursor, or whatever agent you use.
