contentHtml: "<article><div><p>Both <a target=\"_blank\" href=\"https://supabase.com/docs/guides/realtime\">Supabase Realtime</a> and <a target=\"_blank\" href=\"https://supabase.com/docs/guides/database/replication/pipelines\">Supabase Pipelines</a> read changes from your Postgres database. They both use <a target=\"_blank\" href=\"https://supabase.com/docs/guides/database/replication\">logical replication</a> under the hood. They even look similar when you squint. But they solve very different problems, and choosing the wrong one will frustrate you.</p>\n<p>This post explains what each product does, how they differ, and when you should pick one over the other.</p>\n<p>Here is the simplest way to think about it:</p>\n<ul>\n<li><strong>Realtime</strong> sends database changes to your users' browsers and apps, right now, as they happen. It is built for live experiences.</li>\n<li><strong>Pipelines</strong> sends database changes in near real time to supported analytical destinations. It is built for reliable data movement.</li>\n</ul>\n<p>Realtime answers the question: \"How do I show my users what just happened?\"</p>\n<p>Pipelines answers the question: \"How do I get my production data into my analytics warehouse?\"</p>\n<p>If you mix these up, you will run into problems. We see it happen regularly, and the rest of this post will help you avoid that.</p>\n<p><a target=\"_blank\" href=\"https://supabase.com/docs/guides/realtime\">Realtime</a> is three features in one product:</p>\n<ol>\n<li><a target=\"_blank\" href=\"https://supabase.com/docs/guides/realtime/broadcast\"><strong>Broadcast.</strong></a> Send messages between connected clients in real time. No database required. Think cursor positions, typing indicators, or game state.</li>\n<li><a target=\"_blank\" href=\"https://supabase.com/docs/guides/realtime/presence\"><strong>Presence.</strong></a> Track who is online and what they are doing. Also no database required. Think \"3 users are editing this document\" or \"Jane is typing...\"</li>\n<li><a target=\"_blank\" href=\"https://supabase.com/docs/guides/realtime/postgres-changes\"><strong>Postgres Changes.</strong></a> Listen to INSERT, UPDATE, and DELETE events on your database tables and deliver them to subscribed clients over WebSocket.</li>\n</ol>\n<p>Two of these three features, Broadcast and Presence, can work without any database interaction. Client-to-client Broadcast sends messages purely over WebSocket with nothing stored. However, <a target=\"_blank\" href=\"https://supabase.com/blog/realtime-broadcast-from-database\">Broadcast from Database</a> lets you trigger broadcasts from database changes using triggers, giving you control over which events reach which channels. This matters because Realtime is not just a database change listener. It is a real-time communication layer for your application.</p>\n<h3 id=\"how-postgres-changes-works\">How Postgres Changes works<a target=\"_blank\" href=\"https://supabase.com/blog/realtime-or-pipelines-how-to-choose-the-right-tool#how-postgres-changes-works\">#</a></h3>\n<p>When a client subscribes to a table, Realtime uses a PostgreSQL replication slot to read changes from the Write-Ahead Log (WAL). For each change, it checks <a target=\"_blank\" href=\"https://supabase.com/docs/guides/database/postgres/row-level-security\">Row Level Security (RLS)</a> policies against every subscribed user. If a user is authorized to see the change, Realtime sends it over their WebSocket connection.</p>\n<p>This is designed for live UI updates. A user inserts a message into a chat table. Other users see it appear instantly. A row updates in a dashboard table. The chart refreshes automatically.</p>\n<h3 id=\"what-realtime-does-not-guarantee\">What Realtime does not guarantee<a target=\"_blank\" href=\"https://supabase.com/blog/realtime-or-pipelines-how-to-choose-the-right-tool#what-realtime-does-not-guarantee\">#</a></h3>\n<p>Realtime's Postgres Changes feature does not guarantee delivery. If a client disconnects for 30 seconds and reconnects, the changes that happened during those 30 seconds are gone. Realtime does not queue them and does not track how far each client has read.</p>\n<p><a target=\"_blank\" href=\"https://supabase.com/blog/realtime-broadcast-replay\">Broadcast Replay</a> offers limited catch-up for Broadcast from Database messages: clients can request up to 25 messages from the last 3 days using a <code>since</code> timestamp. But this only works on private channels, only for database-sourced broadcasts, and is currently in public alpha. It is not a general-purpose replay mechanism for all Realtime events.</p>\n<p>Postgres Changes uses temporary replication slots. When no clients are subscribed, it stops replicating data entirely. When clients subscribe again, a new slot is created.</p>\n<p>The Realtime team built it this way on purpose. Guaranteed delivery requires persistent state tracking, message queuing, and acknowledgment protocols. Those things add latency and complexity that would make Realtime worse at its actual job: delivering live updates as fast as possible.</p>\n<p>If another system needs a durable, recoverable copy of selected database data, Realtime is not the right tool.</p>\n<p>Pipelines creates managed change-data-capture (CDC) pipelines. A pipeline reads the operations, rows, and columns selected by your Postgres publication and writes them to a supported destination.</p>\n<p>Pipelines keeps the current state of selected Postgres data synchronized with a supported destination in near real time. It maps source names and values to destination-compatible representations and retries transient delivery failures.</p>\n<h3 id=\"how-pipelines-works\">How Pipelines works<a target=\"_blank\" href=\"https://supabase.com/blog/realtime-or-pipelines-how-to-choose-the-right-tool#how-pipelines-works\">#</a></h3>\n<p>When you create a pipeline, it connects to your database through a persistent replication slot. First, it performs an initial sync of the existing rows in the publication. It then begins ongoing replication, processing changes in batches. Latency depends on source activity, network conditions, pipeline configuration, and destination throughput.</p>\n<p>Row Level Security does not apply to Pipelines. A pipeline can read all rows and columns selected by its publication. Use publication row filters and column lists to limit the replicated data.</p>\n<p>Changes are batched and written to your destination. After a restart, the pipeline resumes from its last acknowledged position while Postgres still retains the required WAL. BigQuery supports a limited set of schema changes in beta; other changes require manual handling.</p>\n<h3 id=\"what-pipelines-guarantees\">What Pipelines guarantees<a target=\"_blank\" href=\"https://supabase.com/blog/realtime-or-pipelines-how-to-choose-the-right-tool#what-pipelines-guarantees\">#</a></h3>\n<p>Pipelines uses at-least-once processing. A retry or restart can process the same change more than once, so destination writes must be idempotent. BigQuery uses the replicated source primary key to apply current-state upserts and deletes.</p>\n<p>Pipelines uses persistent replication slots. Postgres retains WAL until the pipeline confirms it has been processed, subject to the database's WAL retention limit. If you stop and restart a pipeline while its slot remains valid, it continues from the retained WAL. A long stop can increase disk usage or invalidate the slot; recovering from a lost slot requires a new initial sync.</p>\n<p>This is the opposite of Realtime's approach. Pipelines prioritizes durable progress tracking and recovery over millisecond delivery to end users.</p>\n<h3 id=\"delivery-guarantees\">Delivery guarantees<a target=\"_blank\" href=\"https://supabase.com/blog/realtime-or-pipelines-how-to-choose-the-right-tool#delivery-guarantees\">#</a></h3>\n<table><thead><tr><th></th><th><strong>Realtime</strong></th><th><strong>Pipelines</strong></th></tr></thead><tbody><tr><td>Guarantee</td><td>Best effort</td><td>At-least-once</td></tr><tr><td>Disconnected changes</td><td>Not replayed</td><td>Read from retained WAL while the slot remains valid</td></tr><tr><td>Replication slot</td><td>Temporary</td><td>Permanent</td></tr><tr><td>Resume after disconnect</td><td>No</td><td>Yes, while the replication slot remains valid</td></tr></tbody></table>\n<p>This is the most important difference. Use Pipelines when another system needs a durable, monitored copy of your selected data. Use Realtime when client applications need live updates and can tolerate gaps while disconnected.</p>\n<h3 id=\"where-data-goes\">Where data goes<a target=\"_blank\" href=\"https://supabase.com/blog/realtime-or-pipelines-how-to-choose-the-right-tool#where-data-goes\">#</a></h3>\n<p>Realtime sends data to client applications over WebSocket connections. Your users' browsers and mobile apps are the destination.</p>\n<p>Pipelines sends data to supported analytical systems.</p>\n<p>These are fundamentally different targets with fundamentally different needs. Client apps need low latency. Analytical systems need completeness.</p>\n<h3 id=\"database-dependency\">Database dependency<a target=\"_blank\" href=\"https://supabase.com/blog/realtime-or-pipelines-how-to-choose-the-right-tool#database-dependency\">#</a></h3>\n<p>Realtime's Broadcast and Presence features can work without touching the database. You can build an entire collaborative experience (cursors, presence indicators, ephemeral messaging) without writing a single database query. However, Postgres Changes and <a target=\"_blank\" href=\"https://supabase.com/blog/realtime-broadcast-from-database\">Broadcast from Database</a> both require database interaction.</p>\n<p>Pipelines is entirely database-driven. Every byte of data it moves comes from your Postgres tables.</p>\n<h3 id=\"scale-characteristics\">Scale characteristics<a target=\"_blank\" href=\"https://supabase.com/blog/realtime-or-pipelines-how-to-choose-the-right-tool#scale-characteristics\">#</a></h3>\n<p>Realtime's Broadcast and Presence features are built for high throughput and low latency. They do not run per-subscriber database queries and scale well across many concurrent connections.</p>\n<p>Postgres Changes works differently. It processes changes sequentially to maintain ordering. For each change, it runs an RLS authorization check against every subscribed client. With 100 subscribers watching a table, one INSERT generates 100 authorization queries. This is a deliberate design choice that prioritizes correctness and low latency for typical workloads over raw throughput.</p>\n<p>Pipelines processes changes in configurable batches with tunable parallelism. It does not need to authorize individual users because it is moving data to a system, not to end users.</p>\n<p>Use Realtime when you need to push live updates to your users:</p>\n<ul>\n<li><strong>Chat applications.</strong> Messages appear instantly for all participants.</li>\n<li><strong>Collaborative editing.</strong> See other users' cursors and changes in real time.</li>\n<li><strong>Live dashboards.</strong> Charts and metrics update without page refresh.</li>\n<li><strong>Notifications.</strong> Alert users when something relevant happens.</li>\n<li><strong>Multiplayer features.</strong> Synchronize game state or shared experiences.</li>\n<li><strong>Presence tracking.</strong> Show who is online, who is typing, who is viewing a document.</li>\n</ul>\n<p>The common thread: a human is watching and needs to see changes as they happen.</p>\n<p>Use Pipelines when you need reliable data movement to analytical systems:</p>\n<ul>\n<li><strong>Analytics and reporting.</strong> Move production data to an analytical destination for querying without impacting your production database.</li>\n<li><strong>Data warehousing.</strong> Replicate your operational data to a columnar format optimized for analytical queries.</li>\n<li><strong>ML pipelines.</strong> Feed fresh data to training or feature stores without querying production.</li>\n<li><strong>Workload isolation.</strong> Run heavy analytical queries against your warehouse instead of your production database.</li>\n</ul>\n<p>The common thread: a system needs the current state of selected production data in an analytical destination. Pipelines does not automatically create a queryable history of every row version.</p>\n<p>Some developers discover Realtime's Postgres Changes feature and think: \"I can use this to replicate data from one system to another.\" They write 20 lines of code with supabase-js, subscribe to table changes, and pipe them into another system.</p>\n<p>It works great in development. It even works fine in production for a while. Then a WebSocket connection drops for a few seconds and data goes missing. Or the subscribing process restarts and misses a batch of changes. Or load spikes and the sequential RLS authorization checks cannot keep up.</p>\n<p>The problem is not that Realtime is broken. The problem is that Realtime was not designed for this job.</p>\n<p>If you are maintaining a durable copy of database data in another system, use Pipelines. It persists replication progress and resumes from Postgres WAL after reconnecting.</p>\n<p>Yes. In fact, many applications should.</p>\n<p>Consider an e-commerce platform. You might use Realtime to push order status updates to customers in real time (\"Your order has shipped!\"). At the same time, you use Pipelines to replicate all order data to a supported analytical destination for daily sales reports and trend analysis.</p>\n<p>Same database. Same tables. Different tools for different jobs.</p>\n<p>Realtime handles the live experience. Pipelines handles the analytical pipeline.
