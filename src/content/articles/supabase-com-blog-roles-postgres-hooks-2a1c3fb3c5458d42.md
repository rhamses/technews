contentHtml: "<article><div>\n<p>PostgreSQL manages permissions through roles. To create these roles, a database user needs the&#160;<code>CREATEROLE</code>&#160;privilege,\nwhich not only allows role creation but also <em>modification</em> of any role (except superusers).</p>\n<p>At Supabase, we use dedicated roles for each of our customers' backend services. For instance, our&#160;<a target=\"_blank\" href=\"https://supabase.com/storage\">Storage API</a>&#160;\nuses the&#160;<code>supabase_storage_admin</code>&#160;role for connecting to the database. Giving the&#160;<code>CREATEROLE</code>&#160;privilege to our customers would allow them to\ndrop this role and take their own Storage API down.</p>\n<p>And yet, we want to give our customers the ability to manage roles the same as they do it in on-premises databases,\nwith the usual&#160;<code>CREATE ROLE</code>,&#160;<code>ALTER ROLE</code>, and&#160;<code>DROP ROLE</code>&#160;statements.</p>\n<p>So, how do we grant them the&#160;<code>CREATEROLE</code>&#160;privilege and, at the same time, protect our own roles? In this blog post,\nwe explain how we managed to do this by using PostgreSQL Hooks in our <a target=\"_blank\" href=\"https://github.com/supabase/supautils\">SupaUtils</a> extension.</p>\n<p>PostgreSQL has a list of&#160;<a target=\"_blank\" href=\"https://www.postgresql.org/docs/14/predefined-roles.html\">predefined roles</a> — all prefixed\nwith \"pg_\" — that cannot be dropped or altered. Attempting to do so will throw an error mentioning that the role is \"reserved\".</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>alter role pg_monitor createdb;</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>ERROR:  role name \"pg_monitor\" is reserved</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>DETAIL:  Cannot alter reserved roles.</span></p></div><br></code></p></div>\n<p>This mechanism is an internal implementation detail. Unfortunately Postgres doesn't allow us to define our own reserved roles.</p>\n<h3 id=\"rds-reserved-roles\">RDS reserved roles<a target=\"_blank\" href=\"https://supabase.com/blog/roles-postgres-hooks#rds-reserved-roles\">#</a></h3>\n<p>Amazon RDS has a similar defense mechanism, all of its predefined roles — prefixed with \"rds\" — cannot be modified.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>alter role rdsadmin rename to another;</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>ERROR: The \"rdsadmin\" role cannot be renamed.</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>DETAIL: The \"rdsadmin\" role cannot be renamed because either the source</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>        or the target name refer to an Amazon RDS reserved role name.</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>LOCATION:  handle_rename, rdsutils.c:1534</span></p></div><br></code></p></div>\n<p>Again, the error mentions that the role is \"reserved\".</p>\n<p>Also note the&#160;<code>rdsutils.c</code>&#160;mention. That's not a stock Postgres source file. This means that the logic comes\nfrom an RDS extension. We can confirm this is the case by showing the preloaded libraries.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>show shared_preload_libraries;</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  shared_preload_libraries</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>-----------------------------</span></p></div><div><p><span>_<!-- -->10</span></p><p><span> rdsutils,pg_stat_statements</span></p></div><br></code></p></div>\n<p><code>rdsutils</code>&#160;can be seen there. Naturally this lead us into thinking we can achieve the same logic with an extension\nof our own, and thus the SupaUtils idea was born.</p>\n<h2 id=\"extending-postgresql-with-hooks\">Extending PostgreSQL with Hooks<a target=\"_blank\" href=\"https://supabase.com/blog/roles-postgres-hooks#extending-postgresql-with-hooks\">#</a></h2>\n<p>PostgreSQL hooks allow us to extend internal functionality. Hooks can modify behavior at different places,\nincluding when running SQL statements.</p>\n<p>For example, if we wanted to enforce our own password restrictions whenever a user changes passwords, we could\nuse the <code>check_password_hook</code> to verify the password. We would write out our own Custom Logic, and raise an error\nif the password fails the password requirements.</p>\n<p>For <code>SupaUtils</code>, we're particularly interested in the&#160;<code>ProcessUtility_hook</code>, which allows us to hook into&#160;<strong>utility statements:</strong> every statement except&#160;<code>select</code>,&#160;<code>insert</code>,&#160;<code>delete</code>&#160;or&#160;<code>update</code>. They include&#160;<code>alter role</code>&#160;and&#160;<code>drop role</code>, which are the statements we want to hook on.</p>\n<h3 id=\"hooks-are-global-function-pointers\">Hooks are global function pointers<a target=\"_blank\" href=\"https://supabase.com/blog/roles-postgres-hooks#hooks-are-global-function-pointers\">#</a></h3>\n<p>To use hooks, we can override functions pointers that are global. On the Postgres codebase, the&#160;<code>ProcessUtility_hook</code>&#160;is basically used<sup><a target=\"_blank\" href=\"https://supabase.com/blog/roles-postgres-hooks#user-content-fn-1\">1</a></sup>&#160;like this:</p>\n<div><p><code><br><div><p><span>_<!-- -->16</span></p><p><span>// src/backend/tcop/utility.c</span></p></div><div><p><span>_<!-- -->16</span></p></div><div><p><span>_<!-- -->16</span></p><p><span>// ProcessUtility_hook is NULL by default</span></p></div><div><p><span>_<!-- -->16</span></p><p><span>ProcessUtility_hook_type ProcessUtility_hook = NULL;</span></p></div><div><p><span>_<!-- -->16</span></p></div><div><p><span>_<!-- -->16</span></p><p><span>// This function is used for processing all the utility statements</span></p></div><div><p><span>_<!-- -->16</span></p><p><span>void</span></p></div><div><p><span>_<!-- -->16</span></p><p><span>ProcessUtility(PARAMS_OMITTED_FOR_BREVITY)</span></p></div><div><p><span>_<!-- -->16</span></p><p><span>{</span></p></div><div><p><span>_<!-- -->16</span></p><p><span>// call the ProcessUtility_hook if it's not NULL</span></p></div><div><p><span>_<!-- -->16</span></p><p><span>if (ProcessUtility_hook)</span></p></div><div><p><span>_<!-- -->16</span></p><p><span>  (*ProcessUtility_hook)(PARAMS_OMITTED_FOR_BREVITY);</span></p></div><div><p><span>_<!-- -->16</span></p><p><span>// otherwise call the standard function used to process utility statements</span></p></div><div><p><span>_<!-- -->16</span></p><p><span>else</span></p></div><div><p><span>_<!-- -->16</span></p><p><span>  standard_ProcessUtility(PARAMS_OMITTED_FOR_BREVITY);</span></p></div><div><p><span>_<!-- -->16</span></p><p><span>}</span></p></div><br></code></p></div>\n<p>As you can see,&#160;<code>ProcessUtility_hook</code>&#160;is <code>NULL</code> by default, so our extension should set it for the hook to run. Also, the&#160;<code>standard_ProcessUtility</code>&#160;function is the one that actually does the job of creating or modifying the roles (among other things) so our hook should also call it.</p>\n<h3 id=\"loading-and-running-the-hook\">Loading and running the hook<a target=\"_blank\" href=\"https://supabase.com/blog/roles-postgres-hooks#loading-and-running-the-hook\">#</a></h3>\n<p>Each extension set in&#160;<code>shared_preload_libraries</code>&#160;will get its&#160;<code>_PG_init</code>&#160;function called.
