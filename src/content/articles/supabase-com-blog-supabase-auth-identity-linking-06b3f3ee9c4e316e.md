contentHtml: "<article><div>\n<p>We're excited to announce four new features for Supabase Auth:</p>\n<ol>\n<li>Identity Linking</li>\n<li>Session Control</li>\n<li>Leaked Password Protection</li>\n<li>Auth Hooks with Postgres functions</li>\n</ol>\n<p></p>\n<p>When a user signs in, an identity is created with the authentication method and sign-in provider. Historically, <a target=\"_blank\" href=\"https://supabase.com/docs/guides/auth\">Supabase Auth</a> has been automatically linking identities to a user if the identity shares the same verified email as the user. This is convenient to de-duplicate user accounts. However, some developers also need the flexibility to link accounts that don’t share the same email.</p>\n<p>Today we are launching Identity Linking, which developers can use to manually link two separate identities. We’ve added two new endpoints for developers to manage the identity linking process:</p>\n<p>Once a user is signed in, use <code>linkIdentity()</code> to <a target=\"_blank\" href=\"https://supabase.com/docs/reference/javascript/auth-linkidentity\">link an OAuth identity</a>:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>const { data, error } = await supabase.auth.linkIdentity({</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  provider: 'google',</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>})</span></p></div><br></code></p></div>\n<p>Use <code>unlinkIdentity()</code> to <a target=\"_blank\" href=\"https://supabase.com/docs/reference/javascript/auth-unlinkidentity\">unlink an identity</a>:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>// retrieve all identities linked to a user</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>const {</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  data: { identities },</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>} = await supabase.auth.getUserIdentities()</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>// find the google identity linked to the user</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>const googleIdentity = identities.find(({ provider }) =&gt; provider === 'google')</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>// unlink the google identity from the user</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>const { data, error } = await supabase.auth.unlinkIdentity(googleIdentity)</span></p></div><br></code></p></div>\n<p>Currently, these methods support linking an OAuth identity. To link an email or phone identity to the user, you can use the <a target=\"_blank\" href=\"https://supabase.com/docs/reference/javascript/auth-updateuser\"><code>updateUser()</code></a>method.</p>\n<p>Manual linking is disabled by default. You can enable it for your project in <a target=\"_blank\" href=\"https://supabase.com/dashboard/project/_/auth/providers\">the dashboard Auth settings</a>.</p>\n<!-- -->\n<p>Supabase Auth manages the full session lifecycle from the moment your user signs into your application. This involves the following steps:</p>\n<ol>\n<li>Creating the session for the user.</li>\n<li>Refreshing the session to keep it active.</li>\n<li>Revoking the session upon expiry or logout.</li>\n</ol>\n<p>For developers who want finer control over their users’ sessions, we have exposed 3 new settings:</p>\n<ul>\n<li><strong>Time-box user sessions</strong>: Force users to sign in again after a time interval.</li>\n<li><strong>Inactivity Timeout</strong>: Force users to sign in again if they’re inactive for a time interval.</li>\n<li><strong>Single session per user</strong>: Restrict users to a single session. The most recently active session is kept, and all others are terminated.</li>\n</ul>\n<p>These session control settings are available on the Pro Plan and above.</p>\n<!-- -->\n<p>Passwords can be inherently insecure due to common user behaviors like choosing guessable passwords or reusing them across different platforms.</p>\n<p>Even though OAuth and magiclinks are more secure, we recognize passwords are here to stay. We want to make the potential pitfalls less user-prone. To accomplish that, we have integrated the <a target=\"_blank\" href=\"https://haveibeenpwned.com/\">HaveIBeenPwned.org</a> <em>Pwned Passwords API</em> in Supabase Auth to prevent users from using leaked passwords.</p>\n<p>As an additional step, we have added the ability to specify password requirements for your users. This can be configured from your project’s Auth settings in <a target=\"_blank\" href=\"https://supabase.com/dashboard/project/_/auth/providers\">the dashboard</a>:</p>\n<!-- -->\n<p>We’ve received a ton of feedback asking for ways to customize Auth, like:</p>\n<ul>\n<li>Add custom claims to the access token JWT</li>\n<li>Log the user out after multiple failed MFA verification attempts</li>\n<li>Apply custom rules for password validation attempts</li>\n</ul>\n<p>We aim to maintain a straightforward and seamless Supabase Auth experience. It should work effortlessly for most developers, requiring no customization. However, recognizing the diversity of apps, you can now extend standard Auth features through Auth Hooks.</p>\n<p>Auth Hooks are simply Postgres functions that run synchronously at key points in the Auth lifecycle, to change the outcome of the action.</p>\n<p>For example, to customize the JWT claims with Auth Hooks, you can create a Postgres function that accepts the JWT claims in the first argument and returns the JWT you wish to be used by Supabase Auth.</p>\n<p>Suppose you’re creating a gamified application and you wish to attach the user’s level to the JWT as a custom -->22</span></p><p><span>$$</span></p></div><br></code></p></div>\n<p>Once you’ve created the function in the database, you only need to register it with Supabase Auth:</p>\n<!-- -->\n<p>Currently, you can register an Auth Hook for the following points in the flow:</p>\n<ul>\n<li><strong>Custom access token:</strong> called each time a new JWT is generated.</li>\n<li><strong>MFA verification attempt</strong>: called each time an MFA factor is verified, allowing finer control over detecting and blocking attempts.</li>\n<li><strong>Password verification attempt</strong>: called each time a password is used to sign-in a user, allowing finer control over the security of the user’s accounts.</li>\n</ul>\n<p>And if writing PL/pgSQL functions is not your forte, you can always use <a target=\"_blank\" href=\"https://supabase.com/docs/guides/database/extensions/pg_net\">pg_net</a> to send out requests to your backend APIs instead, or use <a target=\"_blank\" self-hosting and will be rolled out to the platform next month. Reach out to us via <a target=\"_blank\" href=\"https://supabase.help/\">support</a> if you need access sooner!</p>\n<p>That’s not all! Postgres functions aren’t the only way to write hooks.</p>\n<p>Supabase is a founding contributor of <a target=\"_blank\" href=\"https://www.standardwebhooks.com/\">Standard Webhooks</a>, a set of open source tools and guidelines about sending and receiving webhooks easily, securely, and reliably. Naturally, Auth Hooks will be supporting webhooks in Q1 of 2024.</p>\n<p>If you’ve been following us from <a target=\"_blank\" href=\"https://supabase.com/blog/supabase-auth\">the start</a>, you will know that Supabase Auth started by forking <a target=\"_blank\" href=\"https://github.com/netlify/gotrue\">Netlify’s GoTrue server</a>. A lot has changed since then and we’ve diverged from the upstream repository. At this stage it makes sense to rename the project to something else (<em>cues drumroll</em>) — Auth.</p>\n<p>This simply means that the repositories will be renamed from using <code>gotrue</code> to <code>auth</code>. But don’t worry! Docker images and libraries like <code>@supabase/gotrue-js</code> will continue to be published and you can use <code>@supabase/auth-js</code> interchangeably for the current v2 version for as long as it is supported. All of the classes and methods remain in place. No breaking changes here!</p>\n<p>Thanks for reading till the end!
