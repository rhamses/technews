contentHtml: "<article><div>\n<p>Javascript Frameworks like <a target=\"_blank\" href=\"https://nextjs.org/\">Next.js,</a> <a target=\"_blank\" href=\"https://redwoodjs.com/\">Redwood</a>, <a target=\"_blank\" href=\"https://blitzjs.com/\">Blitz</a>, and tools\nlike <a target=\"_blank\" href=\"https://www.prisma.io/docs/guides/deployment/deployment#pgbouncer\">Prisma</a> are all moving in one direction. Serverless.</p>\n<p>Serverless functions work great for developers using the Supabase API because we manage a <a target=\"_blank\" href=\"https://postgrest.org/en/v7.0.0/\">PostgREST</a>\nserver for every project. Supabase also provides direct access to the Postgres database, so that developers can connect any tool they want.\nUnfortunately, Serverless function don't work well for direct Postgres connections (for reasons we'll discuss soon).</p>\n<p>Jamstack developers make up a large portion of the Supabase Community. While we'd love for developers to use PostgREST, we mostly want\ndevelopers to use Postgres. This means supporting the tools which they already love.</p>\n<p>So today we are adding <a target=\"_blank\" href=\"https://www.pgbouncer.org/\">PgBouncer</a>, an open source connection pooler for Postgres.</p>\n<p>Typically when a client connects to a PostgreSQL database, they need to open and manage their own database connection. With a connection pool,\nconnections are already opened and available for use. When a client makes a request, they use a connection from the pool. When the transaction\nor session is completed the underlying connection is simply returned to the pool and is once again free to be used by another user or application.</p>\n<h3 id=\"handling-connection-surges\">Handling connection surges<a target=\"_blank\" href=\"https://supabase.com/blog/supabase-pgbouncer#handling-connection-surges\">#</a></h3>\n<p>In a traditional architecture, middleware servers (e.g. APIs) manage a small number of connection to a Postgres database.\nEssentially, the middleware server is a connection pool.</p>\n<p>In a Serverless environment, there is no middleware server to maintain a connection, so they create a <strong>new</strong> connection for\neach concurrent request. Since Serverless functions are typically used for bursty workloads, this can end up opening a lot of\nconnections to the database and overwhelm your Postgres server.</p>\n<p>Connection pools mitigate this. Connections are opened beforehand and recycled across users and applications. What's more,\n<a target=\"_blank\" href=\"https://medium.com/@k.wahome/database-connections-less-is-more-86c406b6fad\">connection pools are specialized for this task</a>.\nA small number of connections is sufficient to handle demand ten, twenty times its size, or even more. Whenever a new connection\nis required it is taken from a pool of open and available connections instead of initializing an entirely new one. This eliminates\nthe need to spawn a new process.</p>\n<p>It's a common misconception that PgBouncer increases the number of connections a Postgres instance can open.\nThis is not the case. If Postgres is configured for a maximum of 50 connections before connection pooling, it\nwill still only be able to open 50. Connection pooling simply keeps connections open and idle, ready to accept clients. Nevertheless,\nas mentioned above, PgBouncer allows your database to be able to handle more than it can without a connection pool.</p>\n<p>PgBouncer is like a Queue. With regular Postgres, when you hit your connection limit, new connections are rejected. PgBouncer overcomes this\nlimitation. When all connections in the pool are in-use, it doesn't reject any incoming requests. Instead,\n<a target=\"_blank\" href=\"https://www.percona.com/blog/connection-queuing-in-pgbouncer-is-it-a-magical-remedy/\">PgBouncer queues them</a> until a\nconnection is returned to the pool and made available. This doesn't mean connection pooling is a magic bullet. If your clients is\nrunning expensive queries then the connections might take a long time before they are returned to the pool. The natural solution to\nthis is to increase your database resources so that it processes queries faster or PgBouncer can open more connections.</p>\n<p>From today, all new projects will include connection pooling. In the <code>Database</code> section of our dashboard, you will notice a new section for it.\nUnder the hood, we utilise PgBouncer which is installed in the same server as PostgreSQL. Through the dashboard, we provide you with the\nnecessary connection details to start using the connection pool as well as the ability to modify <code>Pool Mode</code>. Not sure which mode to use?\nBelow is a quick primer on each mode.</p>\n<p><code>Pool Mode</code> determines how PgBouncer handles a connection.</p>\n<h3 id=\"session\">Session<a target=\"_blank\" href=\"https://supabase.com/blog/supabase-pgbouncer#session\">#</a></h3>\n<p>When a new client connects, a connection is assigned to the client until it disconnects. Afterward, the connection is returned back to the pool. All PostgreSQL features can be used with this option.</p>\n<h3 id=\"transaction\">Transaction<a target=\"_blank\" href=\"https://supabase.com/blog/supabase-pgbouncer#transaction\">#</a></h3>\n<p>This is the suggested option for serverless functions. With this, the connection is only assigned to the client for the duration of a transaction. Once done, the connection is returned to the pool. Two consecutive transactions from the same client could be done over two, different connections. Some session-based PostgreSQL features such as prepared statements are not available with this option. A more comprehensive list of incompatible features can be found <a target=\"_blank\" href=\"https://www.pgbouncer.org/features.html\">here</a>.</p>\n<h3 id=\"statement\">Statement<a target=\"_blank\" href=\"https://supabase.com/blog/supabase-pgbouncer#statement\">#</a></h3>\n<p>This is the most granular option. Connections are returned to the pool after every statement. Transactions with multiple statements are not allowed. This is best used when <code>AUTOCOMMIT</code> is in use.</p>\n<p>Try out connection pooling now with a new project in the <a target=\"_blank\" href=\"https://supabase.com/dashboard\">dashboard.</a> For now, we do not have any plans to port this over to older projects.</p>\n<p>Eventually, we will expose more PgBouncer settings to the UI such as <code>Pool Size</code>. At the moment it is set to <code>15</code>.</p>\n<p>We are still working towards getting the latest version of Supabase Postgres to both the AWS and Digital Ocean marketplaces. Follow us on <a target=\"_blank\" href=\"https://twitter.com/supabase\">Twitter</a> to be informed once it's released!</p></div></article>"
