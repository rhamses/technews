You can view one month of data, including\nAPI requests across all of Supabase's core pillars:\nDatabase, Auth and Storage. We've included two instance health metrics, CPU usage and Memory usage,\nwith a lot more on the way.</p>\n<p>All charts are built with <a target=\"_blank\" href=\"https://recharts.org/en-US\">Recharts</a>, an MIT-licensed React chart library chosen for its ease of use.\nWe'll add customizable charts in the future, so we'd love to hear which libraries you'd like to see in Supabase.</p>\n<p>We support one configurable report per project, accessible and editable by all team members. In the next few weeks,\nwe'll expand to unlimited reports, with longer date range options, new layout configurations, report templates,\nstacked charts and private/public visibility across your project's members.</p>\n<h2 id=\"new-project-home-page\">New project home page<a target=\"_blank\" href=\"https://supabase.com/blog/supabase-reports-and-metrics#new-project-home-page\">#</a></h2>\n<p>Every project has a new home page with a weekly overview of important metrics. We've included usage bars for Database storage,\nnumber of Auth users, and Storage space.</p>\n<p>And we're just getting warmed up. Over the next few months you'll see more project information, notifications, and highlights to\nmonitor your project health at a glance.</p>\n<p>Backend as a Service? Infrastructure as a Service? We don't care about the label, but we do care about giving developers the relevant\nobservability metrics. Supabase gives you a full Postgres cluster for every project, and now we give you the tools to diagnose and manage\nimportant infrastructure anomalies.</p>\n<p>All databases are now launched with <code>pg_stat_statements</code> enabled, so you can expect some useful query statistics in the future too.</p>\n<p>\"If you can't measure it, you can't improve it.\"</p>\n<h3 id=\"full-control-full-responsibility\">Full control, full responsibility<a target=\"_blank\" href=\"https://supabase.com/blog/supabase-reports-and-metrics#full-control-full-responsibility\">#</a></h3>\n<p>When developers build services and applications on top of Supabase, relying on the platform's reliability and performance.\nProduct observability is critical, as it allows developers to make decisions on where to spend their optimization dollars,\nand to get ahead of possible issues before they become showstoppers.</p>\n<p>At Supabase, each project is provisioned with a Postgres cluster, and a suite of associated services that add, ahem,\nsupa-powers to the database.</p>\n<p>Our users get liberal access to each of these services - you can use PostgREST for a RESTful API,\nRealtime to listen to changes in your Postgres instance, or even just open a raw connection to the database.\nWhile this makes for an extremely flexible offering, it presents a diverse cast of <a target=\"_blank\" href=\"https://en.wiktionary.org/wiki/footgun\">foot-guns</a>.\nWant to mess with Realtime? Why not bulk-insert millions of records on tables you've configured it to watch?\nFeel like taking out your entire database? Just connect to it and run a wildly inefficient query!</p>\n<p>We're continuously rolling out protections to mitigate failure scenarios and to minimize the blast radius.\nHowever, given the power and flexibility exposed via our services and the diverse workloads they support,\nour users remain best positioned to make the call on what's reasonable for their project.\nAs such, we're also working on exposing as much data as possible to them.</p>\n<h3 id=\"gathering-relevant-metrics\">Gathering relevant metrics<a target=\"_blank\" href=\"https://supabase.com/blog/supabase-reports-and-metrics#gathering-relevant-metrics\">#</a></h3>\n<p>Given the setup described above, there are two major categories of metrics that we care about.\nThere are metrics pertinent to the services mentioned (\"Project Metrics\") that get spun up for each project\n(e.g. the number of active connections to the db), and there are metrics for the underlying infrastructure\n(e.g. system health). Most of the time, our users shouldn't have to care about the latter,\nthough the nature of leaky abstractions dictates that sometimes they become relevant to Project Metrics as well.</p>\n<p>In order to build a comprehensive view of the project's health, each service needs to be instrumented along with its\nunderlying infrastructure. We're looking at hundreds of thousands of targets at our current scale\n(likely approaching millions in the near future) each of them presenting hundreds of metrics of interest (every minute!).</p>\n<p>To buy ourselves some headroom, we built a federated approach: we run instances of our monitoring systems in each\ngeographical region we operate in. This provides a natural dimension for sharding, while reducing the latency for everyone.\nWe run <a target=\"_blank\" href=\"https://prometheus.io/\">Prometheus</a> out of inertia, soon to be <a target=\"_blank\" href=\"https://victoriametrics.com/\">VictoriaMetrics</a>.\nThe monitoring instances scrape data from a number of exporters that are bundled into each of our projects.\nA small subset of the metrics collected gets aggregated to a centralized VictoriaMetrics instance for easier cohort analysis.</p>\n<h3 id=\"available-sources-and-metrics\">Available sources and metrics<a target=\"_blank\" href=\"https://supabase.com/blog/supabase-reports-and-metrics#available-sources-and-metrics\">#</a></h3>\n<p>To start with, we're focusing on metrics a few of the most pertinent metrics:</p>\n<ul>\n<li>Database metrics: CPU and RAM usage</li>\n<li>API Requests: Ingress, Egress, <code>GET</code>, <code>POST</code>, <code>PATCH</code>, <code>PUT</code>, <code>OPTIONS</code>, and all requests.</li>\n<li>Storage Requests: Ingress, Egress, <code>GET</code>, <code>POST</code>, <code>PATCH</code>, <code>PUT</code>, <code>OPTIONS</code>, and all requests.</li>\n<li>Auth Requests: Ingress, Egress, <code>GET</code>, <code>POST</code>, <code>PATCH</code>, <code>PUT</code>, <code>OPTIONS</code>, and all requests.</li>\n</ul>\n<p>Where to begin?</p>\n<ul>\n<li>Multiple <code>pg_stat_database_conflicts</code>.</li>\n<li>System level metrics like CPU, memory and disk utilization.</li>\n</ul>\n</li>\n<li>Granularity: project statistics will come down to hourly.</li>\n<li>Longer time periods: view historical data going back several months.</li>\n<li>Interactive widgets: view-only reports are fine, but we wouldn't be a Postgres company if we didn't
