contentHtml: "<article><div>\n<p>This week we <a target=\"_blank\" href=\"https://supabase.com/blog/supabase-storage\">launched Supabase Storage</a>, which leaves one other huge piece of the\nstack that everyone is asking for: Functions.</p>\n<p>We're not releasing Functions today. Trust us, we know you want them. They are coming, just not today.</p>\n<p>But we are building something that we think you're going to like: Workflows. We haven't finished building it yet, but Workflows are\na \"piece\" of the Function story and arguably an even more exciting feature.</p>\n<p>Firebase functions are relatively simple. If you use Serverless, AWS Lambda, Cloudflare Workers, Next.js API routes, or\nNetlify Functions, then you know how they work. A Firebase function executes some code which you provide, without you managing a server.</p>\n<p>Specifically for Firebase, they have another key feature - they can be triggered by database events. For example, you can\ntrigger a function whenever a Firestore Document is updated.</p>\n<p>This is great, but it is still limited for a few real-world use cases. For example, what if you want to send an email to a user\none day after a user signs up. Or one year? There is no queuing functionality in Firebase. You'd have to manage a process like\nthis yourself, probably using a cron-job.</p>\n<p>We searched for some open source tools which we think are solving this problem well. We looked at\n<a target=\"_blank\" href=\"https://supabase.com/blog/supabase-storage#designing-the-storage-middleware\">NodeRed</a>, <a target=\"_blank\" href=\"https://n8n.io/\">n8n</a>,\n<a target=\"_blank\" href=\"http://airflow.apache.org/blog/airflow-two-point-oh-is-here/\">Airflow</a>, and about 10 other tools. They are amazing tools on their\nown, but for the Supabase Stack they ultimately had the\n<a target=\"_blank\" href=\"https://supabase.com/blog/supabase-storage#integration-with-the-supabase-ecosystem\">same shortcomings</a> that we found\nwith Storage providers - most of them lacked deep Postgres integration.</p>\n<p>We went back to the drawing board and asked, \"if we could wave a wand and get the perfect solution, what would it look like?\".\nThe tool that came very close is <a target=\"_blank\" href=\"https://aws.amazon.com/step-functions/\">AWS Step Functions</a>. The only problem: it's not open source.\nLuckily, their <a target=\"_blank\" href=\"https://states-language.net/spec.html\">state language</a> is.</p>\n<p>Using this states language, we are <a target=\"_blank\" href=\"https://github.com/supabase/workflows\">building an open source orchestration engine</a> for\nmanaging very complex Workflows with queueing, etc. It will be built with Elixir.</p>\n<p>This engine won't execute code. Instead, it will coordinate and execute existing functions wherever they live: AWS, GCP, Azure,\nOpenFaas, and of course Postgres.</p>\n<p>We plan to add \"modules\" which work natively: email services, notification services, and other platforms.</p>\n<p>The engine is deeply integrated with Postgres. <code>Jobs</code>, <code>queues</code>, and <code>logs</code> will be stored and accessible by SQL. We'd like to give a shoutout to the <a target=\"_blank\" href=\"https://getoban.pro/\">Oban</a> team here, their robust job processing was a big missing piece for the engine. And most importantly, it's backed by Postgres!</p>\n<p>Once ready, we will make this available in the Supabase Dashboard with a Zapier-like interface.</p>\n<p>Workflows orchestrate and execute functions in response to a database event (insert, update, delete) or a HTTP call (direct invocation).</p>\n<p>You can use them to rapidly develop microservices (once we have functions) without worrying about servers.</p>\n<p>Workflows are stateless - the output of a state becomes the input of the next state.</p>\n<p>Workflows are defined using Amazon States Languages, so you can import your workflows from AWS (although we are still building handlers\nfor most AWS resources).</p>\n<p>Workflows can be <em>persistent</em> (the default). This means they are tolerant to server restarts, but it also means they need to use\nthe database to store their state.</p>\n<p>Workers can be <em>transient.</em> These are fully in-memory if you don't want to store the execution state (for example, IoT\napplications that trigger workflows very often). Transient workflows are not restarted if the server crashes or is restarted.</p>\n<p>A typical use-case for workflows is sending emails. For example, you might want to send a user an email one day after they\nsign up.
