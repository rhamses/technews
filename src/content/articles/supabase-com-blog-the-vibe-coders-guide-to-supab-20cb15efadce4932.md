contentHtml: "<article><div>\n<p>Setting up separate development and production environments does not have to be painful. This guide shows you how to build a professional deployment workflow for your Supabase project. <strong>You will learn the essential patterns that prevent the 3am \"I dropped production\" panic attacks</strong> while keeping your workflow fun, simple, and safe.</p>\n<p>Supabase is the open source <a target=\"_blank\" href=\"https://supabase.com/database\">Postgres</a> development platform. At its core, it is just Postgres, but with an integrated suite: <a target=\"_blank\" href=\"https://supabase.com/auth\">Auth</a>, <a target=\"_blank\" href=\"https://supabase.com/storage\">Storage</a>, <a target=\"_blank\" href=\"https://supabase.com/edge-functions\">Edge Functions</a>, <a target=\"_blank\" href=\"https://supabase.com/realtime\">Realtime</a>, and <a target=\"_blank\" href=\"https://supabase.com/modules/vector\">Vector</a> search. That means you can start hacking in minutes and also scale to millions when your app takes off.</p>\n<p>With this post, we'll explore how to setup a professional development and staging environment for our projects to prevent those late night panics.</p>\n<p>The fastest way to ruin your night is to treat your one Supabase project as both your playground and your live app. One wrong <code>DROP TABLE</code> and your users are gone. The simple fix is to create at least two projects: one for breaking things (development) and one for your users (production). Larger teams often add a staging project as well, but the minimum is two.</p>\n<p>Create them in the Supabase Dashboard and give them obvious names like <code>myapp-dev</code> and <code>myapp-prod</code>. Boring names reduce mistakes. Grab the Project Reference IDs from <strong>Settings &gt; General</strong> and stash them in a safe place.</p>\n<p>Then set up the Supabase CLI:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>npm install supabase --save-dev</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>supabase init</span></p></div><br></code></p></div>\n<p>This creates a <code>supabase/</code> directory, your single source of truth for migrations, functions, and seed data. Treat it like a ledger of every database change. Because it is just files, you can track it with Git, roll changes forward, and keep environments in sync. The flow should always be one direction: local development → dev project → production project. That is how you avoid the pain of trying to sync in multiple directions later.</p>\n<p>Migrations are your safety net. Each one is a timestamped SQL file in <code>supabase/migrations/</code>. They record what changed and when, just like Git commits. This is how you avoid schema drift, where dev and prod quietly diverge until one day you cannot deploy without breaking things.</p>\n<p>Here is the basic workflow:</p>\n<ol>\n<li>\n<p>Create a migration whenever you need to change the schema:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>supabase migration new add_user_profiles</span></p></div><br></code></p></div>\n</li>\n<li>\n<p>Fill in the SQL, and always enable <a target=\"_blank\" href=\"https://supabase.com/docs/guides/database/postgres/row-level-security\">Row Level Security</a>. Without RLS, anyone with your project URL can read all your data.</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>CREATE TABLE public.profiles (</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  id UUID REFERENCES auth.users ON DELETE CASCADE,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  username TEXT UNIQUE,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  avatar_url TEXT,</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  created_at TIMESTAMPTZ DEFAULT NOW()</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>);</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>ALTER TABLE public.profiles ENABLE ROW LEVEL SECURITY;</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>CREATE POLICY \"Users can view own profile\" ON profiles</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  FOR SELECT USING (auth.uid() = id);</span></p></div><br></code></p></div>\n</li>\n<li>\n<p>Test locally before touching any remote environment:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>supabase db reset</span></p></div><br></code></p></div>\n</li>\n<li>\n<p>If you make changes in the Dashboard instead of SQL, capture them:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>supabase db diff -f capture_dashboard_changes</span></p></div><br></code></p></div>\n</li>\n</ol>\n<p>Because migrations must run in order on a fresh database, always reset locally to prove they work. If <code>supabase db reset</code> works, production will too. This habit prevents the subtle drift that causes late night panics.</p>\n<p>Every developer hits the same landmines once. Knowing them up front means you only hit them once.</p>\n<ul>\n<li><strong>Forgetting to enable RLS.</strong> Without it, your tables are wide open. Always add <code>ALTER TABLE ... ENABLE ROW LEVEL SECURITY;</code>.</li>\n<li><strong>Deploying to the wrong environment.</strong> Give production a different terminal theme, never store its credentials locally, and run <code>supabase status</code> to check before you push.</li>\n<li><strong>Migration conflicts.</strong> If two migrations collide after a Git merge, rename one with a later timestamp and rerun <code>supabase db reset</code> to verify the order.</li>\n<li><strong>Exposed service role keys.</strong> If one leaks, rotate it immediately in the Dashboard, update every environment, and scrub your Git history.</li>\n</ul>\n<p>Mistakes are inevitable. Guardrails keep them from becoming disasters.</p>\n<p>Manual deploys are risky. Automating them with GitHub Actions removes the human error. The idea is simple: push to <code>develop</code> to deploy to staging, merge to <code>main</code> to deploy to production.</p>\n<p>Add your secrets in <strong>Settings &gt; Secrets and variables &gt; Actions</strong>. Then create <code>.github/workflows/deploy.yml</code>:</p>\n<div><p><code><br><div><p><span>_<!-- -->21</span></p><p><span>name: Deploy Supabase</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>on:</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>  push:</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>    branches: [main, develop]</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>jobs:</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>  deploy:</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>    runs-on: ubuntu-latest</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>    steps:</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>      - uses: actions/checkout@v4</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>      - uses: supabase/setup-cli@v1</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>        with: { version: latest }</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>      - name: Deploy to staging</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>        if: github.ref == 'refs/heads/develop'</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>        run: |</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>          supabase link --project-ref ${{ secrets.STAGING_PROJECT_ID }}</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>          supabase db push</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>      - name: Deploy to production</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>        if: github.ref == 'refs/heads/main'</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>        run: |</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>          supabase link --project-ref ${{ secrets.PRODUCTION_PROJECT_ID }}</span></p></div><div><p><span>_<!-- -->21</span></p><p><span>          supabase db push</span></p></div><br></code></p></div>\n<p>Now deployments happen automatically with every push. You do not have to remember commands or worry about sending them to the wrong project. Larger teams often extend this with integration tests that run against staging before code can be promoted, but even this simple setup eliminates most accidents.</p>\n<p>Every production app needs a backup plan. The best plans run without you thinking about them. Set up a GitHub Action to dump your database nightly.</p>\n<p>Backups are only useful if you know they work. Schedule a monthly drill: restore a backup to a new project, run through your app, and confirm the data is intact. If you cannot restore, you do not have a backup.</p>\n<p>For high stakes apps, combine PITR with read replicas and multi region deployments. That way you can recover from mistakes without downtime or lost data.</p>\n<p>Secrets are a common leak. The rule is simple: anything with <code>NEXT_PUBLIC_</code> is visible in browser code. Only use anon keys there.</p>\n<p>Keep secrets like service role keys in <code>.env.local</code>, and never commit that file. Document what is required in <code>.env.example</code>. Then in your code, create two Supabase clients: one safe for the browser, one for server side code.</p>\n<p>For bigger teams, a secrets manager like Doppler, Vault, or GitHub's encrypted environment variables makes rotation and auditing easier.</p>\n<p>Your Git branches should map to your environments. Keep it simple: <code>main</code> for production, <code>develop</code> for staging, and <code>feat/*</code> for features. Supabase will even create preview branches for you automatically when you open a PR. Each one is a fully isolated Supabase instance with unique credentials, perfect for testing features before they hit staging.</p>\n<p>This structure keeps your workflow clean and prevents confusion about which branch is safe to merge.</p>\n<p>With all the pieces in place, you need habits to tie them together.</p>\n<p>For daily development:</p>\n<ul>\n<li>Start Supabase locally with <code>supabase start</code></li>\n<li>Branch from <code>develop</code></li>\n<li>Make schema changes with migrations</li>\n<li>Test with <code>supabase db reset</code></li>\n<li>Commit and push</li>\n</ul>\n<p>For deployments:</p>\n<ul>\n<li>Open a pull request from your feature branch into <code>develop</code></li>\n<li>Test your changes in staging</li>\n<li>Open a pull request from <code>develop</code> into <code>main</code></li>\n<li>Merge to deploy to production</li>\n<li>Monitor production for 15 minutes to catch issues quickly</li>\n</ul>\n<p>Pull requests are not just ceremony. They create an audit trail, trigger preview branches, and give you a chance to test before you touch production. That small delay saves hours of recovery work later.</p>\n<p>Let's say your weekend project took off and people are using it. Let's build separate dev and prod environments. To start, you will create two Supabase projects instead of one. Use the dev project for breaking things, keep the production project for your users. After that, you'll set up Vercel to automatically use the right database for each environment.</p>\n<h3 id=\"separate-your-environments\">Separate your environments<a target=\"_blank\" href=\"https://supabase.com/blog/the-vibe-coders-guide-to-supabase-environments#separate-your-environments\">#</a></h3>\n<p>Create a development project in the Supabase Dashboard and name it <code>yourapp-dev</code>. Rename your existing project to <code>yourapp-prod</code> for clarity. Now you have a safe place to experiment.</p>\n<p>Extract your production schema and turn it into migration files:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>npm install supabase --save-dev</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>supabase init</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span># Capture your production schema</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>supabase link --project-ref YOUR_PROD_PROJECT_ID</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>supabase db pull</span></p></div><div><p><span>_<!-- -->10</span></p></div><div><p><span>_<!-- -->10</span></p><p><span># Apply the same schema to development</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>supabase link --project-ref YOUR_DEV_PROJECT_ID</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>supabase db push</span></p></div><br></code></p></div>\n<p>This creates migration files in <code>supabase/migrations/</code> that represent your current database structure. These files are your new source of truth for schema changes.</p>\n<h3 id=\"configure-vercel-environments\">Configure Vercel environments<a target=\"_blank\" href=\"https://supabase.com/blog/the-vibe-coders-guide-to-supabase-environments#configure-vercel-environments\">#</a></h3>\n<p>Tell Vercel which database to use for each deployment. Go to your Vercel project settings and add environment variables:</p>\n<p><strong>Production environment</strong> (only <code>main</code> branch):</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>NEXT_PUBLIC_SUPABASE_URL = https://yourapp-prod.supabase.co</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>NEXT_PUBLIC_SUPABASE_ANON_KEY = your_prod_anon_key</span></p></div><br></code></p></div>\n<p><strong>Preview environment</strong> (all other branches):</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>NEXT_PUBLIC_SUPABASE_URL = https://yourapp-dev.supabase.co</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>NEXT_PUBLIC_SUPABASE_ANON_KEY = your_dev_anon_key</span></p></div><br></code></p></div>\n<p>Update your local <code>.env.local</code> to point to the dev project so you never accidentally test against production data.</p>\n<h3 id=\"your-new-daily-workflow\">Your new daily workflow<a target=\"_blank\" href=\"https://supabase.com/blog/the-vibe-coders-guide-to-supabase-environments#your-new-daily-workflow\">#</a></h3>\n<p>The workflow stays almost identical to what you know, with one key difference: you never touch the production Supabase Dashboard again.</p>\n<p><strong>For regular features:</strong></p>\n<ul>\n<li>Code locally (automatically uses dev database)</li>\n<li>Push any branch to get a Vercel preview: <code>git push origin feature/new-comments</code>. Vercel automatically creates a preview URL like <code>yourapp-git-feature-new-comments.vercel.app</code> that connects to your dev database with safe test data.</li>\n<li>Test the preview URL with fake data</li>\n<li>Merge to <code>main</code> when ready: Create a pull request on GitHub, review your changes, then merge. Vercel automatically deploys to your production domain using the production database.</li>\n</ul>\n<p><strong>For database changes:</strong></p>\n<ul>\n<li>Create a migration: <code>supabase migration new add_comments_table</code></li>\n<li>Write SQL in the generated file</li>\n<li>Test on dev: <code>supabase db push</code></li>\n<li>Commit the migration file and push: <code>git add supabase/migrations/</code> then <code>git commit -m \"Add comments table\"</code> then <code>git push origin feature/comments</code>. The migration file gets committed to your repo like any other code.</li>\n<li>Production gets the same changes automatically</li>\n</ul>\n<h3 id=\"automate-production-deployments\">Automate production deployments<a target=\"_blank\" href=\"https://supabase.com/blog/the-vibe-coders-guide-to-supabase-environments#automate-production-deployments\">#</a></h3>\n<p>Without automation, you would need to manually apply database changes to production every time you merge code. That means remembering to run <code>supabase db push</code> against your production project, which is error-prone and easy to forget.</p>\n<p>GitHub Actions solves this by watching your repository and automatically running commands when specific events happen. Set up GitHub Actions to handle production database changes. Create <code>.github/workflows/deploy.yml</code>:</p>\n<div><p><code><br><div><p><span>_<!-- -->17</span></p><p><span>name: Deploy to Production</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>on:</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>  push:</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>    branches: [main]</span></p></div><div><p><span>_<!-- -->17</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>jobs:</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>  deploy:</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>    runs-on: ubuntu-latest</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>    steps:</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>      - uses: actions/checkout@v4</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>      - uses: supabase/setup-cli@v1</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>      - name: Apply migrations to production</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>        run: |</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>          supabase link --project-ref ${{ secrets.PRODUCTION_PROJECT_ID }}</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>          supabase db push</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>        env:</span></p></div><div><p><span>_<!-- -->17</span></p><p><span>          SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}</span></p></div><br></code></p></div>\n<p>This file tells GitHub: \"Every time someone merges code into the <code>main</code> branch, automatically connect to the production Supabase project and apply any new migration files.\" Vercel handles your frontend deployment, but your database changes need this extra step.</p>\n<p>Here is what happens when you merge a pull request:</p>\n<ol>\n<li>Vercel automatically deploys your new frontend code to production</li>\n<li>GitHub Actions triggers and connects to your production Supabase project</li>\n<li>Any new migration files get applied to the production database</li>\n<li>Your frontend and database stay in perfect sync</li>\n</ol>\n<p>Add your project IDs and access token to GitHub secrets. Now every merge to <code>main</code> automatically applies your migrations to production. No more forgetting to update the database. No more manual steps that can go wrong at 2am.</p>\n<h3 id=\"the-safety-net-effect\">The safety net effect<a target=\"_blank\" href=\"https://supabase.com/blog/the-vibe-coders-guide-to-supabase-environments#the-safety-net-effect\">#</a></h3>\n<p>Every branch you push creates a preview deployment that uses development data. You can test destructive changes, experiment with new features, and invite others to try things without any risk to production.</p>\n<p>The key insight is that your development and production environments stay perfectly in sync through migrations. When a migration works in development, it will work in production. No more schema drift, no more surprise failures.</p>\n<h3 id=\"enable-row-level-security-immediately\">Enable Row Level Security immediately<a target=\"_blank\" href=\"https://supabase.com/blog/the-vibe-coders-guide-to-supabase-environments#enable-row-level-security-immediately\">#</a></h3>\n<p>Your weekend project probably skipped RLS. Fix this now before you ship new features:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>ALTER TABLE your_table ENABLE ROW LEVEL SECURITY;</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>CREATE POLICY \"Users can only access their own data\" ON your_table</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  FOR ALL USING (auth.uid() = user_id);</span></p></div><br></code></p></div>\n<p>Apply these policies to both environments. RLS is your last line of defense against data breaches.</p>\n<p>This setup takes one afternoon to implement but eliminates the fear of breaking production. You can move fast again while your users stay protected. The same tools, the same workflow, just organized safely.</p>\n<p>The path from vibe coder to confident deployer is not about memorizing every DevOps buzzword. It is about a handful of patterns that keep you safe: separate environments, migrations as save points, automated deployments, tested backups, and strict RLS. Supabase makes this easy because everything is Postgres, deeply integrated, and scalable from weekend project to millions of users.</p></div></article>"
