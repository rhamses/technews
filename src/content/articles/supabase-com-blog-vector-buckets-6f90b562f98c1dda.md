contentHtml: "<article><div>\n<p>Today, we're introducing <a target=\"_blank\" href=\"https://supabase.com/docs/guides/storage/vector/introduction\">Vector Buckets</a>, a new storage option that gives you the durability and cost efficiency of Amazon S3 with built-in similarity search.</p>\n<p>Vector search is becoming a core primitive for modern apps: semantic search, recommendations, RAG, image and audio similarity, and more.</p>\n<p>Supabase already gives you powerful tools for vectors, such as <code>pgvector</code> in Postgres. With Vector Buckets, you now have more options for how you store vectors:</p>\n<ul>\n<li>Use pgvector for smaller, latency-sensitive datasets that belong tightly in your database.</li>\n<li>Use Vector Buckets when you need to store a large amount of vectors—up to tens of millions—on a durable storage layer with similarity search built in.</li>\n</ul>\n<p><strong>Vector Buckets</strong> are a new bucket type in Supabase Storage.</p>\n<p>Conceptually:</p>\n<ul>\n<li>A <strong>Vector Bucket</strong> is where your vector indexes live.</li>\n<li>Inside each bucket, you define one or more <strong>vector indexes</strong> (for example: <code>documents-openai</code>).</li>\n<li>Each index stores high-dimensional vectors plus optional metadata.</li>\n<li>You query those indexes using Supabase clients or directly from Postgres via a foreign data wrapper.</li>\n</ul>\n<h3 id=\"scalable-vector-storage-for-large-datasets\">Scalable vector storage for large datasets<a target=\"_blank\" href=\"https://supabase.com/blog/vector-buckets#scalable-vector-storage-for-large-datasets\">#</a></h3>\n<p>Embeddings add up quickly: thousands of floats per vector, multiplied by millions of items.</p>\n<p>Instead of putting everything in Postgres, Vector Buckets store your embeddings in S3-backed object storage, which gives you:</p>\n<ul>\n<li>Capacity for tens of millions of vectors per index</li>\n<li>A storage layer designed for large, durable datasets</li>\n<li>Room to keep full archives of vectors without over-optimising your Postgres schema or worrying about table bloat</li>\n</ul>\n<p>Your vectors live in a storage layer built for large datasets, while you still query them through Postgres.</p>\n<h3 id=\"built-in-similarity-search\">Built-in similarity search<a target=\"_blank\" href=\"https://supabase.com/blog/vector-buckets#built-in-similarity-search\">#</a></h3>\n<p>Vector Buckets are not just blobs of float arrays. Each index supports similarity search out of the box.</p>\n<p>Similarity search lets you find items that are conceptually related based on their vector representations, not just exact keyword matches. That’s what powers:</p>\n<ul>\n<li>Semantic document search (“find content about this topic, even if the keywords differ”)</li>\n<li>Product and content recommendations (“find items similar to this one”)</li>\n<li>Image, audio, or video similarity (“find assets that look or sound like this”)</li>\n<li>De-duplication and near-duplicate detection across large media libraries</li>\n</ul>\n<p>With Vector Buckets, you can:</p>\n<ul>\n<li>Insert vectors with a key, a float32 vector, and metadata</li>\n<li>Run k-NN queries (for example, “return the 20 closest vectors to this embedding”)</li>\n<li>Use a familiar distance metric such as cosine similarity</li>\n<li>Ask for distances and metadata along with the results</li>\n</ul>\n<p>No extra vector database to run, no new query language. Just vector indexes with search, available from the same Supabase SDKs you already use or directly via Postgres.</p>\n<h3 id=\"performance-that-fits-most-app-workflows\">Performance that fits most app workflows<a target=\"_blank\" href=\"https://supabase.com/blog/vector-buckets#performance-that-fits-most-app-workflows\">#</a></h3>\n<p>Vector Buckets are designed to provide sub-second similarity search over large datasets, which is more than enough for:</p>\n<ul>\n<li>Backend workflows and batch processing</li>\n<li>AI agents and background jobs</li>\n<li>Dashboards and internal tools</li>\n<li>Many user-facing features where “fast” means hundreds of milliseconds, not single-digit milliseconds</li>\n</ul>\n<p>If you’re chasing ultra-low latency at very high QPS, <code>pgvector</code> in a tuned Postgres cluster (or a dedicated vector database) remains the best place to push performance. Vector Buckets focus on simple, scalable similarity search at large scale, not on being the absolute fastest option.</p>\n<h3 id=\"metadata-filtering\">Metadata filtering<a target=\"_blank\" href=\"https://supabase.com/blog/vector-buckets#metadata-filtering\">#</a></h3>\n<p>Each vector can include an arbitrary metadata object, for example:</p>\n<div><p><code><br><div><p><span>_<!-- -->10</span></p><p><span>metadata: {</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  title: 'Getting started with Vector Buckets',</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  type: 'doc',</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  language: 'en',</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>  project_id: '1234',</span></p></div><div><p><span>_<!-- -->10</span></p><p><span>}</span></p></div><br></code></p></div>\n<p>You can:</p>\n<ul>\n<li>Filter by metadata during similarity search (e.g. <code>type = 'doc' AND language = 'en'</code>)</li>\n<li>Query through Postgres and join the results with your relational tables</li>\n<li>Build multi-tenant or multi-project search just by encoding tenant/project IDs into metadata</li>\n</ul>\n<p>This makes it easy to build domain-aware, tenant-aware semantic search.</p>\n<p>Vector Buckets and <code>pgvector</code> are complementary. They serve different roles and work best together.</p>\n<h3 id=\"use-pgvector-when\">Use <code>pgvector</code> when…<a target=\"_blank\" href=\"https://supabase.com/blog/vector-buckets#use-pgvector-when\">#</a></h3>\n<ul>\n<li>You’re optimizing for <strong>lowest possible latency</strong> on user-facing queries</li>\n<li>Vectors are <strong>part of your core relational model</strong> (for example, a column on <code>documents</code> or <code>products</code>)</li>\n<li>You want <strong>transactional guarantees</strong> (data and embeddings written together)</li>\n<li>Your vector dataset is <strong>small to medium</strong> and you’re comfortable scaling Postgres specifically for vector workloads</li>\n</ul>\n<h3 id=\"use-vector-buckets-when\">Use Vector Buckets when…<a target=\"_blank\" href=\"https://supabase.com/blog/vector-buckets#use-vector-buckets-when\">#</a></h3>\n<ul>\n<li>You want <strong>S3-style durability and scale</strong> for embeddings</li>\n<li>You’re dealing with a <strong>large amount of vectors</strong> (up to tens of millions) that you don’t want sitting in Postgres</li>\n<li>You’re building <strong>AI-heavy Supabase apps</strong> (semantic search, recommendations, RAG, media similarity) and want a managed vector storage tier</li>\n<li>You prefer a clear split between:<!-- -->\n<ul>\n<li><strong>Hot vectors</strong> in <code>pgvector</code> for the highest-traffic / most latency-sensitive queries</li>\n<li><strong>Warm or cold vectors</strong> in Vector Buckets for everything else</li>\n</ul>\n</li>\n</ul>\n<p>In practice, many apps will use both:</p>\n<ul>\n<li>Keep your most frequently queried vectors (for example, current content, top products) in <code>pgvector</code>.</li>\n<li>Store the full archive (older content, long tail SKUs, historical embeddings, large media corpora) in Vector Buckets.</li>\n</ul>\n<p>At a high level, here’s what happens under the hood:</p>\n<p><strong>1.
