contentHtml: "<article>\n<p>Posted on August 4, 2026\n\t\t<span>by Sabith K Soopy, Principal Engineer at StackGen</span>\n\t\t</p>\n<p><em>This article reflects practical experience building and operating production AI agent systems.</em></p>\n<p>Traditional APM can’t tell you why your agent spent far more than usual asking the same question three times. We’ve been running AI agents in production for months. The hardest part isn’t building them, it’s understanding what they’re doing when they go wrong. Agents don’t crash with stack traces. They loop, hallucinate, burn tokens, and produce plausible-looking output that’s subtly wrong.</p>\n<p>Here’s what we learned about seeing inside.</p>\n<h2>Why Standard Monitoring Falls Short</h2>\n<p>Standard application monitoring answers questions like:</p>\n<ul>\n<li>Is the service up?</li>\n<li>How fast are responses?</li>\n<li>Are there errors?</li>\n</ul>\n<p>Agent monitoring needs to answer different questions:</p>\n<ul>\n<li><strong>Why did this task cost dramatically more than usual?</strong></li>\n<li><strong>Why did the agent call the same tool repeatedly?</strong></li>\n<li><strong>Did the agent actually do what it said it did?</strong></li>\n<li><strong>Which model is best for this task type?</strong></li>\n<li><strong>Is the agent learning, or is it making the same mistakes?</strong></li>\n</ul>\n<p>These are fundamentally different questions. Prometheus counters and Grafana dashboards alone won’t answer them.</p>\n<h2>The Three Pillars for Agents</h2>\n<h3>1. Traces — The Session Timeline</h3>\n<p>Every agent session should produce a trace — not a generic APM trace, but an <strong>agent trace</strong> that captures the full decision history: each model call, each tool invocation, each sub-agent delegation, with timing and cost attached.</p>\n<p>We use <a target=\"_blank\" href=\"https://langfuse.com/\">Langfuse</a> as our trace backend. Every LLM call, tool execution, and sub-agent delegation is a span. Traces nest — sub-agent work appears as children of the parent trace, so you can follow delegation without losing the thread.</p>\n<p>Trace delivery must be non-blocking. Tool execution should never wait on a synchronous HTTP POST to a tracing backend. Use a batch exporter pipeline so spans buffer in memory and flush periodically. On shutdown, drain remaining spans gracefully. If the trace backend is temporarily unreachable, you lose telemetry — not availability.</p>\n<h3>2. Costs — The Unit Economics Question</h3>\n<p>Token costs are the unit economics of agents. You need visibility at two levels:</p>\n<ul>\n<li><strong>Per session</strong> — total cost, token breakdown, which model did what</li>\n<li><strong>Per agent over time</strong> — daily burn rate, session count, cost trends</li>\n</ul>\n<p><strong>Why this matters:</strong> An agent that loops — calling the same tool repeatedly because it can’t make progress — burns tokens geometrically. Without cost monitoring, you discover this when the invoice arrives, not when the loop starts.</p>\n<p><strong>Proactive guardrails:</strong> Reactive alerting alone isn’t fast enough — a tight loop in a parallel agent can burn through budget in seconds before a webhook fires. Hard iteration caps, per-tool call budgets, and loop detection that blocks identical consecutive calls all act as <strong>pre-flight circuit breakers</strong>. Alerts are the second line of defense, not the first.</p>\n<p><strong>Alerting:</strong> Alert when a single session exceeds a multiple of the rolling average cost for that agent. This catches slower-burning anomalies — hallucination spirals, model routing errors, gradually accumulating context — that slip past hard limits.</p>\n<h3>3. Audit — The Immutable Record</h3>\n<p>Every tool call, governance decision, and memory operation should log to an append-only record — structured, timestamped, searchable. Tool outputs that contain sensitive data get sanitized before logging. You need to reconstruct what happened without exposing credentials in the process.</p>\n<h2>The Diagnostic Command</h2>\n<p>We built a doctor-style diagnostic command (think brew doctor) that checks agent health in one shot: model connectivity, vector store reachability, pending approvals, memory counts, trace backend status, and integration health.</p>\n<p>One command tells you if the agent’s dependencies are healthy. No digging through five dashboards to find which dependency is down.</p>\n<h2>Automated Session Reviews</h2>\n<p>Raw traces are useful for debugging individual sessions. But with many agents running hundreds of sessions daily, you can’t review them all manually.</p>\n<p>We run automated analysis on completed traces: duration, cost, tool count, loop detection, and token efficiency flags. Anomalous sessions — loops, high cost, tool errors — get flagged for human review. Humans review the flags, not every session.</p>\n<h2>Metrics vs Traces</h2>\n<p>For real-time dashboards and alerting, export bounded metrics to Prometheus (or similar): tool success/failure rates by tool name, per-agent session costs, approval latency histograms, classification counts.</p>\n<p>These complement traces — they don’t replace them.</p>\n<p><strong>A warning on cardinality:</strong> Keep Prometheus labels low-cardinality. Tool names and agent names are safe — they have bounded values. Never put unique identifiers like session IDs into Prometheus labels. A production system running thousands of agent sessions daily will cause a cardinality explosion that crashes the metrics server. Leave per-session details to your tracing backend or structured logs.</p>\n<h2>What to Watch</h2>\n<figure><table><tbody><tr><td><strong>Signal</strong></td><td><strong>Why it matters</strong></td></tr><tr><td>Session cost vs rolling average</td><td>Catches loops and runaway context early</td></tr><tr><td>Identical consecutive tool calls</td><td>Loop detection before cost explodes</td></tr><tr><td>Approval latency</td><td>Stale approvals mean blocked agents</td></tr><tr><td>Model error rate</td><td>Provider issues vs agent bugs</td></tr><tr><td>Vector store/integration health</td><td>Silent dependency failures</td></tr><tr><td>Daily token burn vs budget</td><td>Invoice surprises</td></tr><tr><td>Audit log growth rate</td><td>Potential runaway execution</td></tr></tbody></table></figure>\n<h2>Lessons Learned</h2>\n<ol>\n<li><strong>Cost is your canary.</strong> Sudden cost spikes almost always indicate a bug — loops, model routing errors, or unbounded context accumulation. Alert on cost first, debug second.</li>\n<li><strong>Traces are for debugging, metrics are for alerting.</strong> Don’t try to alert on traces (too detailed) or debug with metrics (too aggregated). Use both.</li>\n<li><strong>Audit PII-redaction is non-negotiable.</strong> Your audit trail will be queried during incident reviews. If it contains credentials or PII, your observability tool becomes a liability.</li>\n<li><strong>Build a diagnostic command.</strong> One command, all dependencies, clear pass/fail — saves more time than any dashboard.</li>\n<li><strong>Automate trace analysis.</strong> You can’t review hundreds of sessions a day manually. Let the analyzer flag anomalies; humans review the flags.</li>\n</ol>\n\t</article>"
