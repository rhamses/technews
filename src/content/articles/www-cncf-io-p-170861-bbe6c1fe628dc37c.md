You&#8217;ve just added a 30-second loop that continuously wakes your workload.</p>\n\n\n\n<p class=\"wp-block-paragraph\">This problem appears in three distinct forms:</p>\n\n\n\n<ol class=\"wp-block-list\">\n<li>Cloud Load Balancers<br>AWS ALB, GCP Load Balancer, Azure Application Gateway — they all require periodic health checks to route traffic safely. A service that&#8217;s scaled to zero but registered with an uptime monitor will trigger requests.</li>\n\n\n\n<li>Platform Monitoring<br>Internal developer platforms, service meshes like Istio, and observability stacks like Prometheus Blackbox Exporter continuously probe endpoints to assert availability. Cloud load balancers check the IP and port your service is registered on. You can&#8217;t tell an AWS ALB to use a different backend for /healthz.</p>\n\n\n\n<p class=\"wp-block-paragraph\">Second, separating routing creates operational complexity that teams never maintain. Over time, drift happens. Health checks start hitting your application endpoints anyway.</p>\n\n\n\n<p class=\"wp-block-paragraph\">Third, and most importantly: the health check endpoint IS your application endpoint. The /healthz path is the path. Rerouting it defeats the purpose.</p>\n\n\n\n<p class=\"wp-block-paragraph\">Other tools solve this by keeping a proxy permanently in the request path — even when the service is running. You trade latency for the ability to intercept health checks at all times. ProbeResponse lets you define rules that the resolver evaluates before deciding whether to trigger a scale-up.</p>\n\n\n\n<p class=\"wp-block-paragraph\">If a request matches a probe rule, the resolver answers it directly — with the status code and body you define — and never notifies the operator. The workload stays at zero. The health check receives a 200 OK. Everyone is happy.</p>\n\n\n\n<p class=\"wp-block-paragraph\">Here&#8217;s what the configuration looks like:</p>\n\n\n\n<pre class=\"wp-block-code\"><code class=\"\">probeResponse:\n  - method: GET\n    path:\n      type: PathPrefix\n      value: /healthz\n    response:\n      status: 200\n      body: '{\"ok\":true}'\n  - method: HEAD\n    path:\n      type: Exact\n      value: /ready\n    response:\n      status: 204\n      body: '{}'\n</code></pre>\n\n\n\n<p class=\"wp-block-paragraph\">The matching rules support:</p>\n\n\n\n<ul class=\"wp-block-list\">\n<li>HTTP method (GET, HEAD, POST, etc.)</li>\n\n\n\n<li>Path matching: Exact, PathPrefix, or RegularExpression</li>\n\n\n\n<li>Header matchers (all ANDed)</li>\n\n\n\n<li>Query parameter matchers (all ANDed)</li>\n</ul>\n\n\n\n<p class=\"wp-block-paragraph\">Rules are evaluated top to bottom. First match wins. If no rule matches, normal behavior applies — the request queues and triggers a scale-up.</p>\n\n\n\n<p class=\"wp-block-paragraph\">This design is intentional. ProbeResponse is a gate, not a replacement for scaling. Real traffic still wakes your service. Synthetic health traffic stays synthetic.</p>\n\n\n\n<h2 class=\"wp-block-heading\"><strong>The Architecture Insight</strong></h2>\n\n\n\n<p class=\"wp-block-paragraph\">What makes ProbeResponse different from hacks like &#8220;route /healthz to a separate always-on pod&#8221; is where the intelligence lives.</p>\n\n\n\n<p class=\"wp-block-paragraph\">In KubeElasti&#8217;s architecture, the resolver is already the interception layer during proxy mode. Adding probe matching here costs nothing architecturally — no extra hop, no additional component, no always-on proxy overhead.</p>\n\n\n\n<p class=\"wp-block-paragraph\">When your service has active pods, the resolver is completely out of the request path. KubeElasti switches to serve mode and routes traffic directly to your pods. ProbeResponse rules only apply when the resolver is active, which is only when your service is at zero replicas.</p>\n\n\n\n<p class=\"wp-block-paragraph\">This means:</p>\n\n\n\n<ul class=\"wp-block-list\">\n<li>No latency penalty when your service is running</li>\n\n\n\n<li>No infrastructure overhead to maintain probe handling</li>\n\n\n\n<li>No separate deployment or service for health check routing</li>\n</ul>\n\n\n\n<p class=\"wp-block-paragraph\">The same resolver that queues real requests and triggers scale-up simply checks an in-memory rule set before deciding what to do with a request. It&#8217;s genuinely zero-cost when your service is active.</p>\n\n\n\n<h2 class=\"wp-block-heading\"><strong>Real-World Implications</strong></h2>\n\n\n\n<p class=\"wp-block-paragraph\">Consider a few scenarios where this changes the economics:</p>\n\n\n\n<h3 class=\"wp-block-heading\"><strong>Internal Development Services</strong></h3>\n\n\n\n<p class=\"wp-block-paragraph\">Teams often run internal tools — CI preview environments, internal dashboards, test services — that need to exist but only get real traffic sporadically.
