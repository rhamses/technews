A worker pod may sit idle from a CPU perspective while thousands of messages pile up in an Amazon SQS queue. In other cases, pods may continue running long after a traffic spike has passed.</p>\n<p>For asynchronous, queue-based workloads, backlog is the true scaling signal – not infrastructure utilization.</p>\n<p>In this article, you’ll learn:</p>\n<ul>\n<li>How Amazon SQS queue depth can work as an autoscaling metric  for event-driven workers</li>\n<li>How to scale workloads on Amazon EKS using<a target=\"_blank\" href=\"https://keda.sh/\"> KEDA</a> with AWS pod identity</li>\n<li>How KEDA calculates desired replicas from queue depth</li>\n<li>How to tune queueLength, activationQueueLength, cooldowns, and HPA behavior</li>\n<li>How to validate scaling behavior and troubleshoot common issues</li>\n</ul>\n<p><strong>Why this matters:</strong><strong><br></strong>In queue-driven systems, delayed message processing directly impacts users and downstream systems. Scaling based on SQS depth aligns autoscaling with actual demand, enabling faster burst handling and lower idle costs when queues are empty.</p>\n<figure><img src=\"https://www.cncf.io/wp-content/uploads/2026/07/Technology-7-1024x538-1.jpg\" alt=\"A graphic featuring KEDA, Kubernetes and Itigix logos \" srcset=\"https://www.cncf.io/wp-content/uploads/2026/07/Technology-7-1024x538-1.jpg 1024w, https://www.cncf.io/wp-content/uploads/2026/07/Technology-7-1024x538-1-300x158.jpg 300w, https://www.cncf.io/wp-content/uploads/2026/07/Technology-7-1024x538-1-768x404.jpg 768w, https://www.cncf.io/wp-content/uploads/2026/07/Technology-7-1024x538-1-194x102.jpg 194w, https://www.cncf.io/wp-content/uploads/2026/07/Technology-7-1024x538-1-388x204.jpg 388w, https://www.cncf.io/wp-content/uploads/2026/07/Technology-7-1024x538-1-776x408.jpg 776w, https://www.cncf.io/wp-content/uploads/2026/07/Technology-7-1024x538-1-900x473.jpg 900w, https://www.cncf.io/wp-content/uploads/2026/07/Technology-7-1024x538-1-381x200.jpg 381w, https://www.cncf.io/wp-content/uploads/2026/07/Technology-7-1024x538-1-761x400.jpg 761w, https://www.cncf.io/wp-content/uploads/2026/07/Technology-7-1024x538-1-590x310.jpg 590w\"></figure>\n<h3>1. Prerequisites</h3>\n<p>Before implementing KEDA-based autoscaling with Amazon SQS, ensure you have:</p>\n<ul>\n<li>An Amazon EKS cluster running a supported Kubernetes version</li>\n<li>KEDA installed in the cluster (for example, via the kedacore Helm chart)</li>\n<li>An AWS authentication method selected (IRSA or EKS Pod Identity)</li>\n<li>An existing Amazon SQS queue</li>\n<li>A worker deployment designed to consume messages from the queue</li>\n</ul>\n<h3>2. Architecture and Request Flow</h3>\n<p>This architecture relies on KEDA observing Amazon SQS queue metrics and managing a Kubernetes Horizontal Pod Autoscaler (HPA) based on backlog.</p>\n<p><strong>Request flow:</strong></p>\n<ol>\n<li>Producers send messages to the Amazon SQS queue</li>\n<li>KEDA polls queue attributes to determine backlog</li>\n<li>KEDA updates the target metrics in the HPA</li>\n<li>The HPA scales the worker Deployment</li>\n<li>Kubernetes schedules additional Pods to process messages</li>\n<li>As the queue drains, replicas scale back down</li>\n</ol>\n<p>This model keeps autoscaling decisions tied directly to outstanding work.</p>\n<h3>3. Implementation Steps</h3>\n<h4><strong>Install KEDA via Helm</strong></h4>\n<p>The recommended way to install KEDA is via Helm:</p>\n<pre><code># Add the KEDA Helm repository\nhelm repo add kedacore https://kedacore.github.io/charts\nhelm repo update\n# Install KEDA into a dedicated namespace\nhelm install keda kedacore/keda \\\n  --namespace keda \\\n  --create-namespace\n</code></pre>\n<p><strong>What this does:</strong><strong><br></strong>Deploys the KEDA operator and metrics API server, along with CRDs such as ScaledObject and TriggerAuthentication.</p>\n<h4><strong>Deploy the Worker with AWS Identity Attached</strong></h4>\n<p>An SQS consumer typically requires permissions such as:</p>\n<ul>\n<li>GetQueueAttributes</li>\n<li>GetQueueUrl</li>\n<li>ReceiveMessage</li>\n<li>DeleteMessage</li>\n<li>ChangeMessageVisibility</li>\n</ul>\n<p><strong>Example IAM policy:</strong></p>\n<pre><code>{\n  \"Version\": \"2012-10-17\",\n  \"Statement\": [\n    {\n      \"Sid\": \"ConsumeFromQueue\",\n      \"Effect\": \"Allow\",\n      \"Action\": [\n        \"sqs:GetQueueAttributes\",\n        \"sqs:GetQueueUrl\",\n        \"sqs:ReceiveMessage\",\n        \"sqs:DeleteMessage\",\n        \"sqs:ChangeMessageVisibility\"\n      ],\n      \"Resource\": \"arn:aws:sqs:us-east-1:123456789012:orders-queue\"\n    }\n  ]\n}\n</code></pre>\n<p><strong>What this does:</strong><strong><br></strong>Enforces least-privilege access by granting permissions only for the required SQS queue.</p>\n<h4><strong>Configure KEDA Authentication and ScaledObject</strong></h4>\n<p>KEDA connects the deployment to the SQS queue using TriggerAuthentication and ScaledObject. Using queueURLFromEnv avoids hardcoding the queue URL.</p>\n<pre><code>apiVersion: keda.sh/v1alpha1\nkind: TriggerAuthentication\nmetadata:\n  name: sqs-processor-auth\n  namespace: workers\nspec:\n  podIdentity:\n    provider: aws\n---\napiVersion: keda.sh/v1alpha1\nkind: ScaledObject\nmetadata:\n  name: sqs-processor\n  namespace: workers\nspec:\n  scaleTargetRef:\n    name: sqs-processor\n  pollingInterval: 10\n  cooldownPeriod: 120\n  minReplicaCount: 0\n  maxReplicaCount: 30\n  advanced:\n    horizontalPodAutoscalerConfig:\n      behavior:\n        scaleDown:\n          stabilizationWindowSeconds: 60\n  triggers:\n    - type: aws-sqs-queue\n      authenticationRef:\n        name: sqs-processor-auth\n      metadata:\n        queueURLFromEnv: QUEUE_URL\n        awsRegion: us-east-1\n        queueLength: \"10\"\n        activationQueueLength: \"1\"\n</code></pre>\n<p><strong>What this does:</strong><strong><br></strong>Defines how KEDA authenticates with AWS and how replicas are calculated. Each pod targets 10 messages, and scale-to-zero is enabled when the queue is empty.</p>\n<h3>4. Replica Calculation Logic</h3>\n<p>KEDA calculates outstanding work as:</p>\n<p>ApproximateNumberOfMessages<br>+ ApproximateNumberOfMessagesNotVisible<br>(+ delayed messages, if enabled)</p>\n<p>Replica calculation:</p>\n<p>desired replicas = ceil(outstanding messages / queueLength)</p>\n<p><strong>Example (queueLength: “10”):</strong></p>\n<ul>\n<li>0 messages → 0 pods</li>\n<li>8 messages → 1 pod</li>\n<li>25 messages → 3 pods</li>\n<li>95 messages → 10 pods</li>\n</ul>\n<p>Final replica counts are bounded by minReplicaCount and maxReplicaCount.</p>\n<h3>5. Verification</h3>\n<p>After applying the manifests:</p>\n<p>1. Send 50 messages to the SQS queue</p>\n<p>2. Inspect the ScaledObject:</p>\n<p>kubectl get scaledobject sqs-processor -n workers</p>\n<p>3. Watch pod scaling:</p>\n<p>kubectl get pods -n workers -w</p>\n<p>4. Confirm pods scale back to zero after processing completes</p>\n<h3>6. Troubleshooting Common Issues</h3>\n<p><strong>No scale-out</strong></p>\n<ul>\n<li>Cause: Incorrect queue URL or IAM permissions</li>\n<li>Check: kubectl describe scaledobject, KEDA operator logs</li>\n</ul>\n<p><strong>Too many pods</strong></p>\n<ul>\n<li>Cause: In-flight messages counted</li>\n<li>Check: scaleOnInFlight, SQS visibility timeout</li>\n</ul>\n<p><strong>Never scales to zero</strong></p>\n<ul>\n<li>Cause: Delayed or unacknowledged messages</li>\n<li>Check: Queue attributes and application behavior</li>\n</ul>\n<p><strong>HPA exists but no scaling</strong></p>\n<ul>\n<li>Cause: Authentication or metric fetch errors</li>\n<li>Check: KEDA logs and fallback status</li>\n</ul>\n<h3>7. Production Tuning Tips</h3>\n<ul>\n<li><strong>Choose queueLength based on throughput</strong>, not guesswork</li>\n<li><strong>Tune cooldown and HPA behavior separately</strong> – they control different scale-down paths</li>\n<li><strong>Enable fallback replicas</strong> for resilience if metrics become unavailable</li>\n<li><strong>Decide whether in-flight messages should count</strong> based on visibility timeout behavior</li>\n</ul>\n<h2><strong>Conclusion</strong></h2>\n<p>Queue-based workloads benefit most when autoscaling is driven by the amount of work waiting to be processed rather than traditional infrastructure metrics. Backlog-aware scaling enables applications to react more quickly to changing demand while reducing unnecessary resource consumption during quieter periods.</p>\n<p>Although this article demonstrated the approach using Amazon SQS, Amazon EKS, and KEDA, the same design pattern applies across many event-driven architectures and messaging platforms. The key is selecting a scaling signal that accurately represents workload demand and tuning the autoscaling behaviour to match the characteristics of the application.</p>\n<p>As organisations increasingly adopt asynchronous, event-driven systems, workload-aware autoscaling becomes an important part of building resilient, efficient, and cost-effective Kubernetes deployments.</p>\n\t</article>"
