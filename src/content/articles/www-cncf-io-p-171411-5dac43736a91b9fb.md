contentHtml: "<p class=\"wp-block-paragraph\">The widely used container supply chain verification tools today operate at the Kubernetes API layer as admission webhooks (such as Kyverno, OPA Gatekeeper, and Sigstore Policy Controller). They intercept pod creation, check signatures and attestations, and either admit or reject the pod.</p>\n\n\n\n<p class=\"wp-block-paragraph\">However, admission webhooks depend on explicit configuration and network connectivity. Misconfigured namespace selectors can silently skip verification. An admission webhook outage forces a choice between cluster lockup and silent bypass. Static pods and direct kubelet API access bypass admission webhooks entirely.</p>\n\n\n\n<p class=\"wp-block-paragraph\">What if verification moved one layer lower—to the container runtime itself—where every container must pass through regardless of how it was scheduled?</p>\n\n\n\n<p class=\"wp-block-paragraph\">That is what the Supply Chain NRI Plugin does. Originally proposed as an in-tree CRI-O feature, community feedback favored a plugin approach: it works with both CRI-O and containerd, ships on its own release cycle, and keeps the runtime&#8217;s critical path simple.</p>\n\n\n\n<h2 class=\"wp-block-heading\"><strong>The Gap Below the API Server</strong></h2>\n\n\n\n<p class=\"wp-block-paragraph\">Kubernetes documents these bypass paths explicitly. For example, static pods are managed directly by the kubelet. Even when their mirror pod fails admission, the container still runs. A static pod with an invalid namespace name becomes invisible to the API entirely. None of these containers pass through admission webhooks, so any image verification configured at that layer simply does not apply.</p>\n\n\n\n<p class=\"wp-block-paragraph\">These are not theoretical risks. Techniques using mutating webhook manipulation to confuse validating webhooks have been disclosed, meaning verification can be silently bypassed.</p>\n\n\n\n<p class=\"wp-block-paragraph\">There is also the availability side: OPA Gatekeeper&#8217;s documentation on failing closed describes a deadlock scenario where fail-closed webhooks prevent node recovery after a cluster-wide node deletion. Admission webhooks can both miss containers (a security gap) and block recovery (an availability gap).</p>\n\n\n\n<p class=\"wp-block-paragraph\">Admission webhooks are a necessary first layer, but they are not sufficient as the only layer. Defense-in-depth means enforcing policy at a point that cannot be skipped, no matter how the container was scheduled.</p>\n\n\n\n<h2 class=\"wp-block-heading\"><strong>Verification at the Runtime Level</strong></h2>\n\n\n\n<p class=\"wp-block-paragraph\">The Node Resource Interface (NRI) is a plugin API supported by both CRI-O (1.28+) and containerd (1.7+, enabled by default since 2.0). It lets long-lived plugins (persistent daemons, not per-container one-shot hooks) hook into container lifecycle events. When a plugin subscribes to CreateContainer, the runtime calls it synchronously before the container starts. If the plugin returns an error, the container is rejected.</p>\n\n\n\n<p class=\"wp-block-paragraph\">The Supply Chain NRI Plugin uses this exact hook point. On every CreateContainer call, it:</p>\n\n\n\n<ul class=\"wp-block-list\">\n<li>Extracts the image reference and digest from runtime annotations.</li>\n\n\n\n<li>Fetches supply chain attestations from the OCI registry.</li>\n\n\n\n<li>Verifies them against a per-namespace policy.</li>\n\n\n\n<li>Allows or rejects the container.</li>\n</ul>\n\n\n\n<p class=\"wp-block-paragraph\">This complements CRI-O&#8217;s existing containers-policy.json, which validates image signatures but does not cover attestation content like provenance, vulnerability status, or verification summaries.</p>\n\n\n\n<pre class=\"wp-block-code\"><code class=\"\">+-------------------------------------------------------------------+\n|                         Kubernetes API                            |\n|  (Bypassed by static pods, direct kubelet access, or outages)      |\n+-------------------------------------------------------------------+\n                                  |\n                                  v\n+-------------------------------------------------------------------+\n|                        Container Runtime                          |\n|                     (CRI-O / containerd)                          |\n+-------------------------------------------------------------------+\n                                  |\n                      Synchronous NRI Hook Call\n                                  v\n+-------------------------------------------------------------------+\n|                    Supply Chain NRI Plugin                        |\n|   (Verifies SLSA, VEX, &amp; VSA attestations before container start) |\n+-------------------------------------------------------------------+\n</code></pre>\n\n\n\n<figure class=\"wp-block-image size-full\"><img loading=\"lazy\" decoding=\"async\" width=\"1999\" height=\"490\" src=\"https://www.cncf.io/wp-content/uploads/2026/07/image1.png\" alt=\"API SERVER TO ADMISSION WEBHOOKS GRAPH\" class=\"wp-image-171416\" srcset=\"https://www.cncf.io/wp-content/uploads/2026/07/image1.png 1999w, https://www.cncf.io/wp-content/uploads/2026/07/image1-300x74.png 300w, https://www.cncf.io/wp-content/uploads/2026/07/image1-1024x251.png 1024w, https://www.cncf.io/wp-content/uploads/2026/07/image1-768x188.png 768w, https://www.cncf.io/wp-content/uploads/2026/07/image1-900x221.png 900w, https://www.cncf.io/wp-content/uploads/2026/07/image1-1800x441.png 1800w, https://www.cncf.io/wp-content/uploads/2026/07/image1-600x147.png 600w, https://www.cncf.io/wp-content/uploads/2026/07/image1-1200x294.png 1200w\" sizes=\"auto, (max-width: 1999px) 100vw, 1999px\" /></figure>\n\n\n\n<p class=\"wp-block-paragraph\">Admission webhooks can be skipped, but the NRI hook cannot be bypassed from the API layer because the runtime calls it synchronously for every container. This includes containers from pre-pulled or cached images. Verification happens at container creation, not at image pull, so even images pulled hours ago without an attestation check get verified before running.</p>\n\n\n\n<p class=\"wp-block-paragraph\">Every container on the node passes through the runtime. There is no label to forget, no webhook network path to disrupt, and no gap between namespaces.</p>\n\n\n\n<p class=\"wp-block-paragraph\"><strong>Note on Threat Model:</strong> This approach assumes node integrity. An attacker with root access can kill the plugin process, replace policy files on disk, or disable NRI in the runtime configuration entirely (e.g., nri: { disable: true } in containerd, <code>--enable-nri=false</code> in CRI-O). Runtime verification closes the gap between the API server and the container, but it does not defend against a fully compromised node.</p>\n\n\n\n<h2 class=\"wp-block-heading\"><strong>What Gets Verified</strong></h2>\n\n\n\n<p class=\"wp-block-paragraph\">The plugin verifies three types of attestations, each answering a distinct question about the container image:</p>\n\n\n\n<p class=\"wp-block-paragraph\"><strong>SLSA (Supply-chain Levels for Software Artifacts) Provenance (How was this built?):</strong> Proves the image was produced by a specific builder, from specific source code, in a specific build environment. The plugin verifies the attestation signature, checks the builder identity against a trusted list, validates the source repository, and confirms the build type using the SLSA Provenance v1 predicate type.</p>\n\n\n\n<p class=\"wp-block-paragraph\"><strong>VEX (Vulnerability Exploitability eXchange) (Are known vulnerabilities actually exploitable?):</strong> A VEX document states whether a known CVE is not_affected, under_investigation, fixed, or affected. Any affected status blocks the container in enforce mode. When multiple VEX documents exist, the most restrictive status wins. The implementation follows the OpenVEX v0.2.0 specification.</p>\n\n\n\n<p class=\"wp-block-paragraph\"><strong>VSA (Verification Summary Attestation) (Has someone trusted already verified this?):</strong> A VSA comes from a trusted verification service that has already performed full SLSA and VEX verification. If the plugin finds a valid, passing VSA from a trusted verifier, it short-circuits all other checks and admits the image right away. This allows verification to scale across large clusters without repeating cryptographic work per node.</p>\n\n\n\n<p class=\"wp-block-paragraph\">All three attestation types are discovered through a single OCI Referrers API call per image digest (with a cosign tag-based fallback). Attestation signatures are verified cryptographically using sigstore-go, supporting both keyless (Fulcio/OIDC) and key-based verification.</p>\n\n\n\n<h2 class=\"wp-block-heading\"><strong>Verification Flow &amp; Resilience</strong></h2>\n\n\n\n<p class=\"wp-block-paragraph\">The flow starts when the container runtime calls the plugin&#8217;s CreateContainer hook. The plugin extracts the image digest, looks up the per-namespace policy, checks the local cache, and (on a cache miss) fetches attestations from the registry.</p>\n\n\n\n<figure class=\"wp-block-image size-full is-resized\"><img loading=\"lazy\" decoding=\"async\" width=\"850\" height=\"1999\" src=\"https://www.cncf.io/wp-content/uploads/2026/07/image2.png\" alt=\"Graph container runtime calls\" class=\"wp-image-171415\" style=\"aspect-ratio:0.4252128140304596;width:421px;height:auto\" srcset=\"https://www.cncf.io/wp-content/uploads/2026/07/image2.png 850w, https://www.cncf.io/wp-content/uploads/2026/07/image2-128x300.png 128w, https://www.cncf.io/wp-content/uploads/2026/07/image2-435x1024.png 435w, https://www.cncf.io/wp-content/uploads/2026/07/image2-768x1806.png 768w, https://www.cncf.io/wp-content/uploads/2026/07/image2-85x200.png 85w, https://www.cncf.io/wp-content/uploads/2026/07/image2-170x400.png 170w\" sizes=\"auto, (max-width: 850px) 100vw, 850px\" /></figure>\n\n\n\n<p class=\"wp-block-paragraph\">Design decisions embedded in the workflow:</p>\n\n\n\n<ul class=\"wp-block-list\">\n<li><strong>VSA Priority:</strong> Checked first. A failed VSA results in a hard rejection with no fallback.</li>\n\n\n\n<li><strong>Parallel Execution:</strong> If no trusted VSA exists, SLSA provenance and VEX checks run in parallel.</li>\n</ul>\n\n\n\n<p class=\"wp-block-paragraph\"><strong>Caching &amp; Pre-warming:</strong> Results are cached per image digest and namespace with configurable TTLs. On startup, the plugin receives all running containers via NRI&#8217;s Synchronize callback and pre-warms the cache in the background, so restarts don&#8217;t cause a thundering herd of registry requests.</p>\n\n\n\n<p class=\"wp-block-paragraph\">The plugin also deduplicates concurrent requests: when multiple containers reference the same image, only one verification runs and the rest share its result. Per-registry circuit breakers prevent cascading failures when a registry goes down. A concurrency semaphore limits parallel fetches, and retry with exponential backoff handles transient errors.</p>\n\n\n\n<h2 class=\"wp-block-heading\"><strong>Configuration: two layers by design</strong></h2>\n\n\n\n<p class=\"wp-block-paragraph\">An operator tuning cache TTL shouldn&#8217;t need to dig through trust root definitions in the same file. The plugin intentionally separates operational settings from security policy.</p>\n\n\n\n<p class=\"wp-block-paragraph\">The <a href=\"https://github.com/saschagrunert/nri-supply-chain/blob/main/docs/config.md#operational-config\"><strong>operational config</strong></a> is a TOML file that controls the plugin&#8217;s behavior: verification mode, timeouts, cache TTL, metrics endpoint, circuit breaker settings.</p>\n\n\n\n<pre class=\"wp-block-code\"><code class=\"\">verification = \"enforce\"\nfetch_timeout = \"30s\"\nfetch_failure_policy = \"warn\"\ncache_ttl = \"24h\"\ncache_failure_ttl = \"5m\"\npolicy_dir = \"/etc/nri-supply-chain/policies\"</code></pre>\n\n\n\n<p class=\"wp-block-paragraph\">The <a href=\"https://github.com/saschagrunert/nri-supply-chain/blob/main/docs/config.md#policy-files\"><strong>policy files</strong></a> are JSON documents in a directory, one per Kubernetes namespace. default.json applies to all namespaces unless overridden. A file named production.json applies to the production namespace. Namespace policies can inherit from the default and override specific sections, or replace it entirely.<br></p>\n\n\n\n<pre class=\"wp-block-code\"><code class=\"\">{\n  \"trust\": {\n    \"issuers\": [\"https://token.actions.githubusercontent.com\"],\n    \"sanPatterns\": [\"https://github.com/saschagrunert/nri-supply-chain/**\"],\n    \"sources\": [\"github.com/saschagrunert/*\"]\n  },\n  \"slsa\": { \"missingPolicy\": \"deny\" },\n  \"vex\": { \"missingPolicy\": \"deny\" }\n}\n</code></pre>\n\n\n\n<p class=\"wp-block-paragraph\">Operational settings like cache size and timeouts change with infrastructure. Security policy, who you trust and what you require, changes with compliance requirements. Keeping them apart means they can be managed by different teams with different change cadences.</p>\n\n\n\n<h2 class=\"wp-block-heading\"><strong>Try it out</strong></h2>\n\n\n\n<p class=\"wp-block-paragraph\">The plugin binary supports a <code>--verify-image</code> flag to test a single image against the configured policy without connecting to NRI. The <code>--validate flag </code>checks config and policy files for errors without contacting any registry.</p>\n\n\n\n<p class=\"wp-block-paragraph\">Using the policy from the previous section:</p>\n\n\n\n<pre class=\"wp-block-code\"><code class=\"\">$ nri-supply-chain --config config.toml \\\n    --verify-image ghcr.io/saschagrunert/nri-supply-chain:0.1.5\n\n\n{\n  \"image\": \"ghcr.io/saschagrunert/nri-supply-chain:0.1.5\",\n  \"digest\": \"sha256:1a8b39eeff74b8bb3e20c7f9fa773d4a9935241f7cc4e1217067c8186c2cee3c\",\n  \"namespace\": \"default\",\n  \"allowed\": true,\n  \"checkResults\": [\n    {\n      \"type\": \"slsa\",\n      \"passed\": true,\n      \"status\": \"pass\",\n      \"detail\": \"SLSA provenance verified\"\n    },\n    {\n      \"type\": \"vex\",\n      \"passed\": true,\n      \"status\": \"pass\",\n      \"detail\": \"VEX verification passed\"\n    }\n  ]\n}\n</code></pre>\n\n\n\n<p class=\"wp-block-paragraph\">The output confirms two things: the image was built by a trusted builder from a trusted source (SLSA), and no known exploitable vulnerabilities were found (VEX). allowed: true means the image passes verification.</p>\n\n\n\n<p class=\"wp-block-paragraph\">To enable VSA-accelerated verification, add a trust.verifiers entry to the policy:</p>\n\n\n\n<pre class=\"wp-block-code\"><code class=\"\">{\n  \"trust\": {\n    \"issuers\": [\"https://token.actions.githubusercontent.com\"],\n    \"sanPatterns\": [\"https://github.com/saschagrunert/nri-supply-chain/**\"],\n    \"sources\": [\"github.com/saschagrunert/*\"],\n    \"verifiers\": [\n      {\n        \"id\": \"https://github.com/saschagrunert/nri-supply-chain/.github/workflows/release.yml\"\n      }\n    ]\n  },\n  \"slsa\": { \"missingPolicy\": \"deny\" },\n  \"vex\": { \"missingPolicy\": \"deny\" }\n}</code></pre>\n\n\n\n<p class=\"wp-block-paragraph\">With this policy, the output changes:</p>\n\n\n\n<pre class=\"wp-block-code\"><code class=\"\">{\n  \"image\": \"ghcr.io/saschagrunert/nri-supply-chain:0.1.5\",\n  \"digest\": \"sha256:1a8b39eeff74b8bb3e20c7f9fa773d4a9935241f7cc4e1217067c8186c2cee3c\",\n  \"namespace\": \"default\",\n  \"allowed\": true,\n  \"reason\": \"VSA verification passed, skipping direct verification\",\n  \"checkResults\": [\n    {\n      \"type\": \"vsa\",\n      \"passed\": true,\n      \"status\": \"pass\",\n      \"detail\": \"VSA verification passed\"\n    }\n  ]\n}</code></pre>\n\n\n\n<p class=\"wp-block-paragraph\">The difference: instead of two separate checks (SLSA and VEX), a single VSA from a trusted verifier short-circuits the entire verification chain. The reason field confirms that direct verification was skipped. For production at scale, a CI/CD pipeline can verify images during build, attach a signed VSA, and push it alongside the image. Nodes then validate the VSA instead of fetching and verifying SLSA and VEX separately, reducing per-node registry traffic and verification latency.</p>\n\n\n\n<h2 class=\"wp-block-heading\"><strong>Deployment</strong></h2>\n\n\n\n<p class=\"wp-block-paragraph\">The plugin ships as a single static binary, a multi-arch container image, and DEB/RPM packages. There are three ways to deploy it:</p>\n\n\n\n<p class=\"wp-block-paragraph\">As a <strong>Kubernetes DaemonSet</strong>, which is the most common path. The provided manifests include a security-hardened container with a NetworkPolicy restricting egress to DNS and HTTPS only. The container runs non-root with a read-only rootfs, no capabilities, a seccomp profile, and system-node-critical priority. Policies come from ConfigMap entries, volume-mounted into the container&#8217;s policy_dir.</p>\n\n\n\n<p class=\"wp-block-paragraph\">As a <strong>systemd service</strong> for non-Kubernetes hosts or traditional Linux infrastructure. The unit file applies strict sandboxing: ProtectSystem=strict, memory limits, empty CapabilityBoundingSet, syscall filtering.</p>\n\n\n\n<p class=\"wp-block-paragraph\">As a <strong>pre-installed NRI plugin</strong> (binary in /opt/nri/plugins/), auto-launched by the container runtime with no external process management. Best for immutable node images.</p>\n\n\n\n<p class=\"wp-block-paragraph\">The plugin authenticates to registries using the standard Docker credential chain (~/.docker/config.json and configured credential helpers), so it works with any registry credentials available on the node.</p>\n\n\n\n<h2 class=\"wp-block-heading\"><strong>A practical rollout</strong></h2>\n\n\n\n<p class=\"wp-block-paragraph\">Supply chain verification is not something you flip on overnight. The plugin ships with verification = &#8220;disabled&#8221; by default, meaning it does nothing until explicitly configured. From there, it supports a gradual path from observation to enforcement.</p>\n\n\n\n<p class=\"wp-block-paragraph\"><strong>Phase 1: Observe.</strong> Create a default.json policy with permissive settings (missingPolicy: &#8220;allow&#8221;) and set verification = &#8220;warn&#8221;. The plugin runs verification on every container but never blocks anything. Failed verifications get logged and counted. The nri_supply_chain_verification_total{result=&#8221;fail&#8221;} Prometheus metric counts how many containers would be blocked. The repo includes <a href=\"https://github.com/saschagrunert/nri-supply-chain/blob/main/docs/operations.md\">example alerting rules</a> for circuit breaker trips, fetch error rates, and verification failures. This phase answers a question: what is our supply chain posture right now?</p>\n\n\n\n<p class=\"wp-block-paragraph\"><strong>Phase 2: Tighten per namespace.</strong> Add namespace-specific policy files. Production namespaces get missingPolicy: &#8220;deny&#8221; for SLSA provenance, while dev namespaces stay permissive. Infrastructure images (pause containers, node-local images) can be excluded via glob patterns. This phase reveals which images in which namespaces lack attestations.</p>\n\n\n\n<p class=\"wp-block-paragraph\"><strong>Phase 3: Enforce.</strong> Switch to verification = &#8220;enforce&#8221;. The plugin will log warnings at startup if permissive defaults are still in place, like fetch_failure_policy set to warn or any missingPolicy set to allow. It actively tells you what to tighten. Containers failing verification are now rejected, and the error shows up in pod events as a structured message:</p>\n\n\n\n<p class=\"wp-block-paragraph\">supply chain verification failed: SLSA provenance: builder &#8220;X&#8221; not in trusted builders list</p>\n\n\n\n<p class=\"wp-block-paragraph\">At this point, the runtime-level enforcement is active. Admission webhooks remain as the first layer, and the NRI plugin is the second. All configuration changes across every phase are hot-reloaded via SIGHUP and filesystem watching, with no pod restarts needed. The cache only gets cleared when policy-affecting fields actually change.</p>\n\n\n\n<h2 class=\"wp-block-heading\"><strong>Failure modes and trade-offs</strong></h2>\n\n\n\n<p class=\"wp-block-paragraph\">Every verification system has to decide what happens when things go wrong. The plugin makes these trade-offs explicit and configurable.</p>\n\n\n\n<p class=\"wp-block-paragraph\">When a registry is unreachable, the fetch_failure_policy setting controls the behavior. The default is warn: containers pass, a warning gets logged, and the fetch error counter increments. This is explicitly fail-open, and the documentation calls it out. Setting it to deny trades availability for security: registry outages prevent new containers from starting.</p>\n\n\n\n<p class=\"wp-block-paragraph\">The circuit breaker amplifies this trade-off. After consecutive failures to a registry host, all fetches to that host short-circuit for a configurable cooldown period. In warn mode, this means new, never-verified images from that registry bypass verification during the cooldown. Images verified before the outage are still served from cache. In deny mode, the circuit breaker prevents cascading timeouts from blocking the entire node.</p>\n\n\n\n<p class=\"wp-block-paragraph\">Missing attestations are controlled per type. You might require SLSA provenance (missingPolicy: &#8220;deny&#8221;) but tolerate missing VEX documents (missingPolicy: &#8220;allow&#8221;) if your organization hasn&#8217;t adopted VEX in its build pipeline yet.</p>\n\n\n\n<h2 class=\"wp-block-heading\"><strong>What&#8217;s next</strong></h2>\n\n\n\n<p class=\"wp-block-paragraph\">The SLSA specification also defines a Source Track alongside the Build Track, covering how source revisions are created and protected. Unlike the Build Track, the Source Track is still maturing and tooling support is limited. It will be a natural addition once the ecosystem catches up.</p>\n\n\n\n<p class=\"wp-block-paragraph\">Vulnerability scan result attestations and test result attestations are defined in the in-toto/cosign ecosystem but not yet widely produced. Once adoption grows, support will follow.</p>\n\n\n\n<p class=\"wp-block-paragraph\"><a href=\"https://github.com/notaryproject/notation\">Notation/Notary v2</a> support alongside <a href=\"https://sigstore.dev\">Sigstore</a> would cover organizations using Microsoft&#8217;s signing infrastructure (common in Azure environments).</p>\n\n\n\n<p class=\"wp-block-paragraph\">The plugin currently requires registry connectivity to fetch attestations at container creation time, which means air-gapped environments are not yet supported. Local attestation caching would let attestations be bundled alongside images in local registries or on-disk stores.</p>\n\n\n\n<p class=\"wp-block-paragraph\">Further out, extending CRI error types upstream in Kubernetes would let the kubelet surface precise attestation failure reasons instead of a generic CreateContainerError. This requires changes to the CRI API itself and is a separate upstream effort.</p>\n\n\n\n<h2 class=\"wp-block-heading\"><strong>The bottom line</strong></h2>\n\n\n\n<p class=\"wp-block-paragraph\">Admission webhooks verify what the API server sees. An NRI plugin verifies what the container runtime actually executes. If your threat model includes admission webhook bypasses, static pods, or direct node access, runtime-level verification offers a robust defense-in-depth layer.</p>\n\n\n\n<p class=\"wp-block-paragraph\">To learn more about the Node Resource Interface and container runtime ecosystem, check out the documentation on landscape.cncf.io.</p>"
