That means two things for authentication:</p><ul><li><p>Credentials <b>must be secure.</b></p></li><li><p>Credentials <b>must be changeable without downtime.</b></p></li></ul><p>If you’re using SASL PLAIN or SASL SCRAM in Kafka, both goals are achievable, but only if you understand what’s really going on under the hood: <b>which login module you use, where credentials are stored, and whether that mechanism supports hot‑reloading configuration.</b></p><p>This post walks through:</p><ul><li><p>What SASL PLAIN and SCRAM actually are (beyond “auth mechanisms”)</p></li><li><p>How different Kafka login modules handle credentials</p></li><li><p>Why some combinations support hot‑reload and others do not</p></li><li><p>A concrete, end‑to‑end example using three listeners and three login modules</p></li><li><p>Practical recommendations for production deployments</p></li></ul><h2>SASL PLAIN and SCRAM in Kafka: The “What”</h2><p><b>\nSASL PLAIN</b> is the simplest SASL mechanism: it sends a username and password to the server, typically protected by TLS in production. In Kafka, it’s commonly used for straightforward client authentication when ease of configuration is the top priority.</p><p>On the broker, PLAIN uses a <b>login module</b> to validate credentials. The most common is: PlainLoginModule – usernames and passwords are defined in JAAS config (or backed by LDAP).</p><p>On the client, you configure something like:</p><!--$--><div><pre><span>security.protocol=SASL_PLAINTEXT\nsasl.mechanism=PLAIN\nsasl.jaas.config= \\\n  org.apache.kafka.common.security.plain.PlainLoginModule required \\\n  username=<span>\"alice\"</span> \\\n  password=<span>\"alice-secret\"</span>;\n</span></pre></div><!--/$--><p>\n<b>SASL SCRAM (Salted Challenge Response Authentication Mechanism)</b> is a more secure SASL method. Instead of sending raw passwords, it uses a challenge‑response protocol based on salted password hashes and cryptographic proofs (e.g., SCRAM-SHA-256, SCRAM-SHA-512).</p><p>Compared to PLAIN, SCRAM provides stronger protection against credential theft and replay attacks, and in Kafka it comes with an additional operational benefit we’ll explore: <b>native hot‑reload of credentials</b> via cluster metadata.</p><p>On the client side, a typical SCRAM config looks like:</p><!--$--><div><pre><span>security.protocol=SASL_PLAINTEXT\nsasl.mechanism=SCRAM-SHA<span>-512</span>\nsasl.jaas.config= \\\n  org.apache.kafka.common.security.scram.ScramLoginModule required \\\n  username=<span>\"alice\"</span> \\\n  password=<span>\"alice-secret\"</span>;\n</span></pre></div><!--/$--><h2>Why “Hot-Reload” Matters for Authentication</h2><p>Hot‑reload means a running broker can detect and apply authentication config changes without a restart. In the context of SASL auth, that implies:</p><ul><li><p>You can <b>add new users.</b></p></li><li><p>You can <b>rotate passwords</b> or keys.</p></li><li><p>You can <b>revoke or update credentials.</b></p></li></ul><p>…...all while brokers stay online and continue serving traffic.</p><p>This is not a “nice to have” in production; it directly affects:</p><ul><li><p><b>Zero‑downtime credential rotation</b> – rotate passwords or keys regularly, without rolling restarts.</p></li><li><p><b>Incident response </b>– quickly revoke compromised credentials.</p></li><li><p><b>Operational simplicity</b> – fewer restarts, fewer chances to disrupt clients.</p></li></ul><p>Whether hot‑reload is possible depends entirely on:</p><ol><li><p><b>Where credentials are stored</b>, and</p></li><li><p><b>How the chosen login module reads and refreshes them.</b></p></li></ol><p>That’s where the key differences between PlainLoginModule, ScramLoginModule, and a file‑backed module come in.</p><h2>The Three Login Modules: Plain, SCRAM, and File-Based</h2><p>To understand hot‑reload behavior, you need to look at <b>credential storage and refresh semantics.</b></p><!--$--><p><span></span><span>Credential source and hot-reload behavior across Kafka's three SASL login modules</span></p><!--/$--><h3><b>PlainLoginModule (Static JAAS, No Hot-Reload)</b></h3><ul><li><p><b>Mechanism: </b>SASL/PLAIN</p></li><li><p><b>Credential source:</b> Static JAAS configuration (or LDAP in some setups)</p></li><li><p><b>Behavior:</b></p><ul><li><p>Credentials are typically loaded <b>once at broker startup.</b></p></li><li><p>No built‑in file watching or reload.</p></li></ul></li><li><p><b>Result: No hot‑reload</b> - changing credentials in JAAS requires a broker restart unless an external system like LDAP provides dynamic validation.</p></li><li><p><b>Why:</b> The module assumes configuration immutability and keeps credentials in memory after initialization.</p></li></ul><h3><b>ScramLoginModule (Cluster Metadata, Native Hot-Reload)</b></h3><ul><li><p><b>Mechanism:</b> SASL/SCRAM (SCRAM-SHA-256, SCRAM-SHA-512)</p></li><li><p><b>Credential source: Cluster metadata</b></p><ul><li><p>Historically ZooKeeper, now the KRaft metadata log in modern Kafka/Confluent Platform.</p></li></ul></li><li><p><b>Behavior:</b></p><ul><li><p>Credentials are stored as metadata records.</p></li><li><p>Brokers <b>fetch and update SCRAM credentials dynamically</b> from the quorum.</p></li><li><p>When you use Admin APIs to add/alter users, brokers learn the changes automatically.</p></li></ul></li><li><p><b>Result: Hot‑reload is naturally supported</b> - no broker restart required.</p></li><li><p><b>Why:</b> Credentials aren’t tied to static files; they live in the distributed metadata managed by the cluster itself.</p></li></ul><h3><b>FileBasedLoginModule (Watched File, Hot-Reload)</b></h3><ul><li><p><b>Mechanism:</b> SASL/PLAIN (but with a different backend)</p></li><li><p><b>Credential source:</b> An <b>external credential file</b> (e.g., JSON) on disk.</p></li><li><p><b>Behavior:</b></p><ul><li><p>The module periodically checks or reloads the credential file.</p></li><li><p>Updates to users/passwords can be applied while brokers are running.</p></li></ul></li><li><p><b>Result: Hot‑reload is supported.</b></p></li><li><p><b>Why:</b> The module is explicitly designed with <b>file‑watching / reload semantics</b>, unlike PlainLoginModule.</p></li></ul><h3><b></b></h3><h2>A Concrete Example: Three Listeners, Three Behaviors</h2><p>To make this real, let’s look at a single Confluent Platform (CP) Kafka broker configured with <b>three SASL listeners:</b></p><ul><li><p>CUSTOMER_PLAIN – SASL/PLAIN via PlainLoginModule (static JAAS)</p></li><li><p>CUSTOMER_SCRAM – SASL/SCRAM via ScramLoginModule (metadata‑backed)</p></li><li><p>CUSTOMER_FILE – SASL/PLAIN via FileBasedLoginModule (file‑backed, hot‑reload)</p></li></ul><h3><b>Listener Setup in server.properties</b></h3><p>First, define advertised listeners and security protocol mappings:</p><!--$--><div><pre><span>advertised.listeners=INTERNAL<span>:</span>\nCUSTOMER_PLAIN<span>:</span>\nCUSTOMER_SCRAM<span>:</span>\nCUSTOMER_FILE<span>:</span>\nlistener.security.protocol.map=CONTROLLER<span>:</span>PLAINTEXT<span>,</span>INTERNAL<span>:</span>PLAINTEXT<span>,</span>\\\nBROKER<span>:</span>PLAINTEXT<span>,</span>\\\nCUSTOM<span>:</span>PLAINTEXT<span>,</span>\\\nCUSTOMER_PLAIN<span>:</span>SASL_PLAINTEXT<span>,</span>\\\nCUSTOMER_SCRAM<span>:</span>SASL_PLAINTEXT<span>,</span>\\\nCUSTOMER_FILE<span>:</span>SASL_PLAINTEXT\nlisteners=INTERNAL<span>:</span>\nCUSTOMER_PLAIN<span>:</span>\nCUSTOMER_SCRAM<span>:</span>\nCUSTOMER_FILE<span>:</span>\n</span></pre></div><!--/$--><p>Then configure each listener’s SASL settings.</p><h4><b>PLAIN (Static JAAS, PlainLoginModule)</b></h4><!--$--><div><pre><span>listener.name.customer_plain.sasl.enabled.mechanisms=PLAIN\nlistener.name.customer_plain.plain.sasl.jaas.config= \\\n  org.apache.kafka.common.security.plain.PlainLoginModule required \\\n  username=<span>\"broker\"</span> \\\n  password=<span>\"broker-secret\"</span> \\\n  user_alice=<span>\"alice-secret\"</span> \\\n  user_bob=<span>\"bob-secret\"</span>;\n</span></pre></div><!--/$--><h4><b>SCRAM (Metadata-backed, ScramLoginModule)</b></h4><!--$--><div><pre><span>listener.name.customer_scram.sasl.enabled.mechanisms=SCRAM-SHA<span>-512</span>\nlistener.name.customer_scram.scram-sha<span>-512</span>.sasl.jaas.config= \\\n  org.apache.kafka.common.security.scram.ScramLoginModule required;\n</span></pre></div><!--/$--><h4><b>FILE-Based PLAIN (FileBasedLoginModule)</b></h4><!--$--><div><pre><span>listener.name.customer_file.sasl.enabled.mechanisms=PLAIN\nlistener.name.customer_file.plain.sasl.jaas.config= \\\n  io.confluent.kafka.server.plugins.auth.FileBasedLoginModule required \\\n  config_path=<span>\"/etc/kafka/apikeys.json\"</span> \\\n  refresh_ms=<span>\"10000\"</span>;  \n</span></pre></div><!--/$--><p><b>Important gotcha:</b> If you configure both CUSTOMER_PLAIN (PlainLoginModule) and CUSTOMER_FILE (FileBasedLoginModule) using overlapping settings, the file‑based It’s best to test them <b>one at a time</b> when validating behavior.</p><h3><b>File-Based Credentials: apikeys.json</b></h3><p>For the file‑based PLAIN listener, credentials reside in a JSON file, e.g.:</p><!--$--><div><pre><span><span>{</span>\n<span>\"keys\"</span><span>:</span> <span>{</span>\n  <span>\"customer\"</span><span>:</span> <span>{</span>\n    <span>\"sasl_mechanism\"</span><span>:</span> <span>\"PLAIN\"</span><span>,</span>\n    <span>\"hashed_secret\"</span><span>:</span> <span>\"customer-secret\"</span><span>,</span>\n <span>\"user_id\"</span><span>:</span> <span>\"customer\"</span><span>,</span>\n    <span>\"service_account\"</span><span>:</span> <span>false</span>\n    <span>}</span><span>,</span>\n  <span>\"alice\"</span><span>:</span> <span>{</span>\n    <span>\"sasl_mechanism\"</span><span>:</span> <span>\"PLAIN\"</span><span>,</span>\n    <span>\"hashed_secret\"</span><span>:</span> <span>\"alice-secret\"</span><span>,</span>\n    <span>\"hash_function\"</span><span>:</span> <span>\"none\"</span><span>,</span>\n    <span>\"logical_cluster_id\"</span><span>:</span> <span>\"my-cluster\"</span><span>,</span>\n    <span>\"user_id\"</span><span>:</span> <span>\"alice\"</span><span>,</span>\n    <span>\"service_account\"</span><span>:</span> <span>false</span>\n    <span>}</span>\n  <span>}</span>\n<span>}</span>\n</span></pre></div><!--/$--><h3><b>Client Configs\n</b></h3><h4><b>PLAIN Client</b></h4><!--$--><div><pre><span># username=<span>\"customer\"</span> \\\n  password=<span>\"customer-secret\"</span>;\n</span></pre></div><!--/$--><h2><b>Scenarios: How Each Auth Path Handles Changes</b></h2><p>With the above setup, you can run simple operations like listing topics to validate behavior:</p><!--$--><div><pre><span>\nkafka-topics.sh --bootstrap-server broker-host:9096 <span>\\</span>\n<span>--list</span> --command-config plain_client.properties\nkafka-topics.sh --bootstrap-server broker-host:9095 <span>\\</span>\n<span>--list</span> --command-config scram_client.properties\n</span></pre></div><!--/$--><p>Now compare how each mechanism behaves when credentials change.</p><h3><b>SASL PLAIN (PlainLoginModule → No Hot-Reload)</b></h3><p><b>Scenario:</b></p><ol><li><p>alice/alice-secret is present in server.properties at broker startup.</p></li><li><p>Client connects via CUSTOMER_PLAIN as alice → <b>SUCCESS</b>.</p></li><li><p>You add a new user customer/customer-secret to the JAAS section <b>without broker restart.</b></p></li><li><p>Client attempts to connect as customer → <b>FAILS</b>.</p></li><li><p>You restart the broker.</p></li><li><p>Client connects as customer → <b>SUCCESS</b>.</p></li></ol><p><b>Takeaway:</b> PlainLoginModule reads credentials once; <b>changes only take effect after broker restart.</b></p><h3><b>SASL SCRAM (ScramLoginModule → Hot-Reload)</b></h3><p>With SCRAM, you manage users via Kafka’s Admin APIs, e.g.:</p><!--$--><div><pre><span># Add or reset SCRAM user\nkafka-configs.sh \\\n--bootstrap-server broker-host<span>:</span><span>9093</span> \\\n--alter \\\n--add-config\n'SCRAM-SHA<span>-512</span>=<span>[</span>iterations=<span>8192</span><span>,</span>password=customer-secret<span>]</span>' \\\n--entity-type users \\\n--entity-name customer\n</span></pre></div><!--/$--><p><b>Scenario:</b></p><ol><li><p>alice/alice-secret exists in cluster metadata.</p></li><li><p>Client connects via CUSTOMER_SCRAM as alice → <b>SUCCESS</b>.</p></li><li><p>You add customer/customer-secret using kafka-configs.sh (no broker restart).</p></li><li><p>Client connects as customer → <b>SUCCESS</b>.</p></li></ol><p>You can even inspect SCRAM credentials in the KRaft metadata log with kafka-dump-log for full transparency.</p><p><b>Takeaway:</b> Because SCRAM credentials live in <b>cluster metadata</b>, brokers automatically pick up changes. <b>No restart, full hot‑reload.</b></p><h3><b>SASL PLAIN (FileBasedLoginModule → Hot-Reload)</b></h3><p>For the file‑based PLAIN listener:</p><p><b>Scenario:</b></p><ol><li><p>alice/alice-secret is present in apikeys.json.</p></li><li><p>Client connects via CUSTOMER_FILE as alice → <b>SUCCESS</b>.</p></li><li><p>You add customer/customer-secret to apikeys.json and save the file; the broker keeps running.</p></li><li><p>After the refresh_ms interval (or next file check), client connects as customer → <b>SUCCESS</b>.</p></li></ol><p><b>Takeaway: </b>FileBasedLoginModule is designed to <b>watch and reload the credential file</b>, so you can add/remove users without touching the broker process.</p><h2>Operational Recommendations</h2><p>Based on the behaviors above, here are practical guidelines for production:</p><ol><li><p><b>Prefer SCRAM for strong security + native hot‑reload</b></p><ol><li><p>Use ScramLoginModule with SCRAM-SHA-256 or SCRAM-SHA-512.</p></li><li><p>Manage users via kafka-configs.sh or Admin APIs.</p></li><li><p>Let credentials live in cluster metadata; avoid static JAAS for users.</p></li></ol></li><li><p><b>If you must use PLAIN, avoid static JAAS for dynamic users</b></p><ol><li><p>Static PLAIN via PlainLoginModule is acceptable only that:</p><ol><li><p>Update credentials through SCRAM Admin APIs or file‑backed stores.</p></li><li><p>Do <b>not</b> rely on cluster restarts.</p></li></ol></li><li><p>Test scenarios in lower environments that mirror production listeners and modules.</p></li></ol></li><li><p><b>Observe and debug via metadata and logs</b></p><ol><li><p>Use kafka-configs.sh and kafka-dump-log to verify SCRAM users in metadata.</p></li><li><p>For file‑based PLAIN, monitor broker logs around file reload and auth failures.</p></li></ol></li></ol><p>Done right, you get <b>stronger security and smoother operations</b>: secure mechanisms, controlled storage, and <b>hot‑reload</b> as a first‑class property of your Kafka authentication layer.</p><hr><h2>Call to Action</h2><h3><b>Who is the target
