contentHtml: "<div><p><a target=\"_blank\" href=\"https://www.getdbt.com/blog/what-exactly-is-dbt\"><u>dbt</u></a> is the most commonly used tool by data engineers to define SQL transformations (as models), write tests, generate documentation, and deploy through CI/CD and now it’s available with Confluent Cloud too! The magic of dbt is that it brings the engineering rigor to modern data work and data engineering, regardless of the underlying compute source - Snowflake, BigQuery, Databricks, Redshift or Confluent. You can find out more about the launch in our <a target=\"_blank\" href=\"https://www.confluent.io/blog/2026-q2-confluent-cloud-launch/\"><u>Q2 Confluent Cloud Launch post</u></a> and the <a target=\"_blank\" href=\"https://youtu.be/aWM2veQm3ZY?si=MWcYC8rYH2ADgxkJ&t=3792\"><u>keynote</u></a>.</p><h2>Why Streaming</h2><p>The trend today, largely driven by AI, as well as customer demand for fresh data is driving processing closer to the source. The source, for many organizations, is a stream, so as a result, batch transformations need to get turned into streaming jobs that deliver fresher data and reduce pipeline latency. As a knock-on effect, this shift tends to reduce architectural complexity. This pattern, that we call \"<a target=\"_blank\" href=\"https://www.youtube.com/watch?v=FiZmyl1Npg0\"><u>shifting left</u></a>,\" positions stream processing as the primary transformation layer rather than purely a loading and ingestion mechanism.</p><p>Confluent Cloud for Apache Flink provides the streaming engine with a declarative SQL API and Table API. The engine and API’s alone aren't enough. Data engineers also need the developer experience around it: a way to manage SQL as code, test it before it reaches production, and deploy it through the same review process they use for everything else.</p><p>When we set out to build the dbt-confluent adapter, we focused on three things data engineers told us matter most: a familiar interface for managing transformations, reliable and deterministic testing, and seamless CI/CD integration.&#160;</p><p>We built the adapter from the ground up to suit production workloads on Confluent Cloud. The dbt-confluent adapter is backed by confluent-sql, an open source purpose-built DB-API v2 compliant Python driver that communicates directly with the Confluent Cloud REST API. This eliminated the need for a proxy or middleware layer. Statement lifecycle management, result pagination, type conversion, and automatic retry on transient infrastructure issues are built into the driver. The result is an adapter that behaves the way data engineers expect a dbt adapter to behave.</p><!--$--><div><p>Note: The <a target=\"_blank\" href=\"https://github.com/confluentinc/dbt-confluent\">adapter</a> and the <a target=\"_blank\" href=\"https://github.com/confluentinc/confluent-sql\">driver</a> are open source under the Apache 2.0 license and available on GitHub. It currently supports dbt Core 1.11 and is in active development.</p></div><!--/$--><h2>Streaming-Native Materializations</h2><p>Most dbt adapters are built for batch: you run a query, it produces a table, and you're done. Streaming is fundamentally different in that queries run continuously and results keep updating. The adapter needed new materializations to account for that:</p><ul><li><p><b>view</b> — Standard Flink SQL views (default).</p></li><li><p><b>streaming_table</b> — Creates a table with a continuous INSERT INTO...SELECT statement, providing explicit control over changelog semantics.</p></li><li><p><b>streaming_source</b> — Creates a Kafka topic-backed source table with schema defined in the model SQL. If you are using connectors, this would be the materialization you use to define the schema of the model for that topic.</p></li></ul><!--$--><div><p>Note: Future materializations like materialized_tables (the newest Flink abstraction) and standard tables (generated with snapshot queries) are on the roadmap.&#160;</p></div><!--/$--><p>Data engineers configure these materializations through dbt's standard config() block. Under the hood, the adapter manages the distinct execution modes. The complexity of the materialization stays behind the interface. It’s only a config option. This also separates the SQL logic from the table creation which is what allows dbt to have unit test capabilities.</p><h2>Deterministic Testing for Streaming Pipelines</h2><p>Testing has historically been one of the biggest challenges with streaming SQL. When a query runs continuously and results are unbounded, how do you write a test with a deterministic pass/fail?</p><p>The adapter solves this by automatically switching to bounded execution mode (<a target=\"_blank\" href=\"https://docs.confluent.io/cloud/current/flink/concepts/snapshot-queries.html\"><u>snapshot queries</u></a>) for tests. Rather than setting a timeout and hoping enough data arrives before it expires, which can produce false positives when no data means a silent pass, the adapter runs tests against finite, deterministic result sets. The outcome is reliable and repeatable, and your CI/CD pipeline won't hang waiting on an unbounded stream. This functionality is available via the native dbt unit tests. You can provide mock input data, run your model logic, and verify the output matches expectations. For example, in the configuration below, we are testing the stg_orders model. The revenue model then runs continuously on Flink: as new orders arrive on the Kafka topic, the tumbling window aggregates them into one-minute revenue buckets. This is a live, always-updating pipeline, deployed with the same command a data engineer would use to materialize a batch table on any data warehouse.</p><h3><b>Integrating with the Broader Ecosystem</b></h3><p>The integration doesn't stop at deployment. Because you are using dbt, the rest of your standard workflow naturally extends to your streaming data:</p><ul><li><p><b>Validation:</b> Running dbt test validates data quality against the live, running pipeline.</p></li><li><p><b>Documentation:</b> Running dbt docs generate produces data lineage and documentation across all your models.</p></li><li><p><b>Automation:</b> The entire lifecycle of model changes, test runs, and deployments integrates seamlessly with GitHub Actions or any other CI/CD system.</p></li></ul><p>Ultimately, your streaming pipelines move through the exact same pull request, review, and deploy process as any standard software code.</p><h2>Getting Started</h2><p>The adapter is available today for teams already on Confluent Cloud:</p><ol><li><p><b>Install</b>: <code>pip install dbt-confluent</code></p></li><li><p><b>Initialize</b>: <code>dbt init my_project</code> and select <code>confluent</code></p></li><li><p><b>Configure</b>: Set your Confluent Cloud credentials in <code>profiles.yml</code></p></li><li><p><b>Deploy</b>: dbt run</p></li></ol><p>Full documentation is in the <a target=\"_blank\" href=\"https://docs.confluent.io/cloud/current/flink/operate-and-deploy/deploy-flink-dbt.html\"><u>Confluent Cloud docs</u></a>. Get in touch to let us know how you get on and discuss any features you’d like to see!</p></div>"
