contentHtml: "<div><article><div><p>Safely route a subset of production data to pre-production clusters by leveraging UDP’s fire-and-forget functionality</p><p><img src=\"https://static-www.elastic.co/v3/assets/bltefdd0b53724fa2ce/blteecf39f99ef12947/66c2a4722f80d2944ef35edb/158175_-_Blog_header_image_V1.jpg\" alt=\"\"></p><div><p><span>In a well-architected system, it is a best practice to completely separate pre-production and production environments. Distinct environments ensure that issues in one environment will not affect the other, especially when it comes to testing new features or configurations in a pre-production environment.&#160;</span></p><div><p><span>However, for organizations with limited resources or operational constraints, maintaining separate end-to-end environments can sometimes be impractical. In such cases, workarounds are necessary to ensure that data can flow to both production and pre-production clusters without risk of disruption.</span></p><p><span>This blog post explores a solution that is intended for such constrained environments. Using Logstash in combination with UDP, the solution that is presented allows you to route a </span><span><strong>random subset</strong></span><span> of data to a pre-production cluster without a risk of interfering with the data flow to the production cluster. This is a lightweight and low-risk alternative to more complex patterns such as the </span><a target=\"_blank\" href=\"https://www.elastic.co/guide/en/logstash/current/pipeline-to-pipeline.html#output-isolator-pattern\"><span>output isolator</span></a><span> pattern, which requires the use of a </span><a target=\"_blank\" href=\"https://www.elastic.co/guide/en/logstash/8.15/persistent-queues.html\"><span>persistent queue</span></a><span>.</span></p></div></div><div><p></p><h2 id=\"risks-of-driving-data-into-multiple-destinations\">Risks of driving data into multiple destinations</h2><p></p><p><span>By default, if a Logstash pipeline routes data to multiple outputs, if one of the destinations goes down then the pipeline will be blocked for all destinations. For example, if you send data to both a production and to an pre-production cluster from a single Logstash pipeline with multiple outputs, if the pre-production cluster fails then Logstash will stop sending data to the production cluster as well.</span><span>&#160;</span></p></div><div><p></p><h2 id=\"overcoming-the-drawbacks-of-the-output-isolator-pattern\">Overcoming the drawbacks of the output isolator pattern</h2><p></p><p><span>The </span><a target=\"_blank\" href=\"https://www.elastic.co/guide/en/logstash/current/pipeline-to-pipeline.html#output-isolator-pattern\"><span>output isolator</span></a><span> pattern is a common approach that leverages the </span><a target=\"_blank\" href=\"https://www.elastic.co/guide/en/logstash/8.15/persistent-queues.html\"><span>persistent queue</span></a><span> feature to solve the aforementioned problem. The persistent queue allows Logstash to buffer data until the issue is resolved, ensuring that data is not lost.</span></p><p><span>However, the persistent queue can introduce operational risks (e.g., disk getting full) and </span><a target=\"_blank\" href=\"https://www.elastic.co/blog/using-parallel-logstash-pipelines-to-improve-persistent-queue-performance\"><span>performance overhead</span></a><span>. For scenarios where only a subset of data needs to be sent to a pre-production environment, this overhead and risk may not be justified.</span></p><p><span>The solution presented in this article offers a simpler approach: routing a random subset of production events to a pre-production cluster by leveraging UDP for internal pipeline-to-pipeline communications within Logstash. Because UDP operates on a fire-and-forget basis and doesn't require acknowledgement from the receiver, even if the pre-production cluster encounters issues, the production data pipeline remains unaffected.</span></p><p><span><em><strong>Acknowledgment: </strong></em></span><span><em>Thank you to </em></span><em></em><a href=\"https://www.linkedin.com/in/honzakral/\" target=\"_blank\"><em></em><span><em>Honza Král</em></span><em></em></a><em></em><span><em> for sharing this UDP solution!</em></span></p></div><div><p></p><h2 id=\"caveats-when-to-use-the-pipeline-to-pipeline-with-udp-solution\">Caveats: When to use the pipeline-to-pipeline with UDP solution</h2><p></p><p><span>While this pipeline-to-pipeline with UDP solution is a practical workaround for constrained environments, it’s important to note that production and pre-production environments should be fully separated if possible. Separation would ensure cleaner boundaries between environments, mitigating potential risks. Such a setup would obviate the need for the solution presented in this article.</span></p><p><span>However, sometimes resources are limited, or separating environments isn’t feasible. In this case, the approach described in this article will allow your organization to populate your pre-production environment with a random subset of live production data, without introducing additional risk to the production data flow.&#160;</span></p><p><span>If using the solution presented in this article, it is also important to keep in mind that UDP does not guarantee delivery. If we are sampling a random subset of production data and sending it into the pre-production environment, we probably don’t care if a few events are lost. However, if you set the sampling rate to 100%, there is still no guarantee that UDP might drop some events — and therefore this solution should always be thought of as sampling rather than duplicating the production data.</span></p></div><div><p></p><h2 id=\"pipeline-to-pipeline-with-udp-overview\">Pipeline-to-pipeline with UDP overview</h2><p></p><p><span>In the pipeline-to-pipeline with UDP approach, you send a random subset of events from your production Logstash pipeline to the pre-production pipeline using UDP. UDP’s fire-and-forget nature ensures that even if the pre-production pipeline is blocked (e.g., if the pre-production cluster becomes unavailable), it won’t block data flow to the production cluster.</span></p><p><span>Unlike the output-isolator pattern, this approach does not require the use of a persistent queue, thereby reducing both risks and performance overhead. This solution is lightweight and effective, particularly for scenarios where only a subset of data needs to be routed to pre-production for testing purposes.</span></p></div><div><p></p><h2 id=\"sampling-the-production-data-with-the-ruby-filter\">Sampling the production data with the Ruby filter</h2><p></p><p><span>The method presented in this section allows us to control which events are sent to the pre-production pipeline before they leave the production pipeline, which ensures that only the selected random subset of events is forwarded via UDP.</span></p><p><span>The code that is demonstrated below makes use of a </span><a target=\"_blank\" href=\"https://www.elastic.co/guide/en/logstash/current/plugins-inputs-generator.html\"><span>generator input</span></a><span> and </span><a target=\"_blank\" href=\"https://www.elastic.co/guide/en/logstash/current/plugins-outputs-stdout.html\"><span>stdout output</span></a><span> with the </span><a target=\"_blank\" href=\"https://www.elastic.co/guide/en/logstash/current/plugins-codecs-rubydebug.html\"><span>rubydebug codec</span></a><span>. This makes it simple to demonstrate the UDP functionality without relying on external data sources or external destinations. In a real-world pipeline, the generator would be replaced by your actual data inputs (such as Kafka or Beats), and the stdout/rubydebug would be replaced by an </span><a target=\"_blank\" href=\"https://www.elastic.co/guide/en/logstash/current/plugins-outputs-elasticsearch.html\"><span>Elasticsearch output</span></a><span> or another destination of your choice. Furthermore, this pipeline uses </span><a target=\"_blank\" href=\"https://www.elastic.co/guide/en/logstash/current/event-dependent-configuration.html\"><span>metadata</span></a><span> to temporarily store values that will not appear in the output events.</span></p></div><div><p></p><h3 id=\"pipeline-configuration\">Pipeline configuration</h3><p></p><p><span>The following configuration can be stored in your </span><a target=\"_blank\" href=\"https://www.elastic.co/guide/en/logstash/current/multiple-pipelines.html\"><span>pipelines file</span></a><span> located in </span><span><span>config/pipelines.yml</span></span><span>:</span></p></div><div><pre><code>- pipeline.id: common\n  path.config: ./config/common.conf\n- pipeline.id: pre-production\n  path.config: ./config/pre-production.conf</code></pre></div><p><span>And store the following code in </span><span><span>config/common.conf</span></span><span>:</span></p><div><pre><code>input {\n    generator {\n        lines =&gt; [\n            '{\"message\": \"message number 1\", \"@timestamp\": \"2020-08-18T19:42:42.000Z\"}',\n            '{\"message\": \"message number 2\", \"@timestamp\": \"2020-08-18T19:43:43.000Z\"}',\n            '{\"message\": \"message number 3\", \"@timestamp\": \"2020-08-18T20:44:40.000Z\"}'\n        ]\n        count =&gt; 1\n        codec =&gt; \"json\"\n    }\n}\nfilter {\n    ruby {\n    code =&gt; \"\n        sampling_rate = 0.3 # 30% sampling rate\n        if rand() &lt;= sampling_rate\n            event.set('[@metadata][include_this_doc]', true)\n        else\n            event.set('[@metadata][include_this_doc]', false)\n        end\n    \"\n    }\n}\noutput {\n    if [@metadata][include_this_doc] {\n        udp {\n            id =&gt; \"my_udp_output\"\n            host =&gt; \"localhost\"\n            port =&gt; 9999\n        }\n    }\n    stdout { codec =&gt; \"rubydebug\" } # Replace with production Elasticsearch output\n}</code></pre></div><p><span>And the following code in </span><span><span>config/pre-production.conf</span></span><span>:</span></p><div><pre><code>input { \n    udp { \n        port =&gt; 9999 \n        codec =&gt; json\n    } \n}\nfilter {\n    mutate {\n        add_field =&gt; {\"dest\" =&gt; \"PRE-PRODUCTION CLUSTER\"} # add a field so we can see which events were hypothetically sent to pre-production - this can be removed without any consequence\n    }\n}\noutput {\n    stdout { codec =&gt; \"rubydebug\" } # Replace with pre-production Elasticsearch cluster\n}</code></pre></div><div><p></p><h3 id=\"running-the-code\">Running the code</h3><p></p><p><span>If you are running a Logstash locally, you can run the above example by executing </span><span><span>./bin/logstash</span></span><span>, which will read </span><span><span>pipelines.yml</span></span><span> by default.</span></p></div><div><p></p><h2 id=\"example-output\">Example output</h2><p></p><p><span>Below are some examples of what the output might look like for the above configuration:</span></p></div><div><p></p><h3 id=\"common-pipeline-output-simulating-production-data-flow\">Common pipeline output (simulating production data flow)</h3><p></p><p><span>The output will look as follows, which simulates the documents that would be sent to the production cluster.</span></p></div><div><pre><code>{\n      \"@version\" =&gt; \"1\",\n         \"event\" =&gt; {\n        \"original\" =&gt; \"{\\\"message\\\": \\\"message number 2\\\", \\\"@timestamp\\\": \\\"2020-08-18T19:43:43.000Z\\\"}\",\n        \"sequence\" =&gt; 0\n    },\n          \"host\" =&gt; {\n        \"name\" =&gt; \"Alexs-MBP-2.lan\"\n    },\n       \"message\" =&gt; \"message number 2\",\n    \"@timestamp\" =&gt; 2020-08-18T19:43:43.000Z\n}</code></pre></div><div><p></p><h3 id=\"pre-production-pipeline-output-simulating-pre-production-data-flow\">Pre-production pipeline output (simulating pre-production data flow)</h3><p></p><p><span>If the document is selected for inclusion based on the sampling rate, it will be sent to the pre-production pipeline and will (also) use the stdout/rubydebug output to simulate the pre-production cluster destination. Keep in mind that due to the random nature of selection of documents to send to the pre-production cluster and the small number of sample documents, you may need to execute more than once to see a document from this pipeline.</span></p><p><span>These documents include a “dest” field that was added by the pre-production pipeline to indicate that the event is being routed to the pre-production cluster. In a real scenario, this output would be sent to the pre-production Elasticsearch cluster rather than printed to the console, and therefore this field could be removed.</span></p><p><span>Events that are sent to the stdout/rubydebug of the pre-production pipeline would appear as follows.</span></p></div><div><pre><code>{\n      \"@version\" =&gt; \"1\",\n         \"event\" =&gt; {\n        \"original\" =&gt; \"{\\\"message\\\": \\\"message number 1\\\", \\\"@timestamp\\\": \\\"2020-08-18T19:42:42.000Z\\\"}\",\n        \"sequence\" =&gt; 0\n    },\n       \"message\" =&gt; \"message number 1\",\n          \"host\" =&gt; {\n        \"name\" =&gt; \"Alexs-MBP-2.lan\",\n          \"ip\" =&gt; \"127.0.0.1\"\n    },\n          \"dest\" =&gt; \"PRE-PRODUCTION CLUSTER\",\n    \"@timestamp\" =&gt; 2020-08-18T19:42:42.000Z\n}</code></pre></div><div><p></p><h2 id=\"benefits-of-the-pipeline-to-pipeline-with-udp-solution\">Benefits of the pipeline-to-pipeline with UDP solution</h2><p></p><ol><li><p><span><strong>Non-blocking production flow: </strong></span><span>The use of UDP ensures that production data flow is not blocked by issues in the pre-production cluster.</span></p></li><li><p><span><strong>Efficiency:</strong></span><span> The Production-side Sampling with Ruby filter ensures that only the sampled events are sent to the pre-production pipeline, reducing pipeline-to-pipeline traffic and processing overhead.</span></p></li><li><span><strong>Simplified architecture:</strong></span><span> Without the need for a persistent queue, this approach reduces complexity, operational risks, and the performance overhead associated with managing queues.</span></li></ol></div><div><p></p><h2 id=\"easy-debugging\">Easy debugging</h2><p></p><p><span>The use of generator input and rubydebug output allows for testing and debugging of Logstash pipelines, without relying on external data sources or external destinations. This makes it easy to demonstrate and validate this solution or any other solution that you may wish to test.</span></p></div><div><p></p><h2 id=\"alternative-approach-sampling-with-the-drop-filter\">Alternative approach: Sampling with the Drop filter</h2><p></p><p><span>An alternative approach is to do the Sampling with </span><a target=\"_blank\" href=\"https://www.elastic.co/guide/en/logstash/current/plugins-filters-drop.html\"><span>Drop filter</span></a><span>, where all events are sent to the pre-production pipeline, and a </span><a target=\"_blank\" href=\"https://www.elastic.co/guide/en/logstash/current/plugins-filters-drop.html#plugins-filters-drop-percentage\"><span>percentage</span></a><span> of these events are then dropped. This method may be more intuitive for some, but it is less efficient because all events are sent to the second pipeline, increasing inter-pipeline traffic and processing requirements.</span></p></div><div><p></p><h2 id=\"discover-efficient-sampling-and-fire-and-forget-pipelines\">Discover efficient sampling and fire-and-forget pipelines</h2><p></p><p><span>While it is generally a best practice to separate production and pre-production environments, the solution presented in this article provides a valuable workaround for scenarios where resources are limited or separation is impractical. By leveraging the fire-and-forget nature of UDP and applying efficient sampling using the Ruby filter, this method allows for seamless testing in pre-production with real production data, while minimizing the risk of impacting your production data flow.</span></p><p><span>For more insights on managing Elasticsearch, Logstash, and other Elastic Stack components, be sure to explore </span><a target=\"_blank\" href=\"https://www.elastic.co/guide/index.html\"><span>Elastic’s official documentation</span></a><span>.</span></p></div><p><span><em>The release and timing of any features or functionality described in this post remain at Elastic's sole discretion.
