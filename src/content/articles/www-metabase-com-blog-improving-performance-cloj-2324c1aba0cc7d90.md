contentHtml: "<p>Development tools can sometimes struggle when dealing with large codebases. This gives performance nerds like me a reason to investigate. In this case, I ended up cutting clojure-lsp’s startup time in half and memory allocation by two thirds.</p>\n<h2 id=\"part-1-the-mystery-of-heap-headroom\">Part 1: The mystery of heap headroom</h2>\n<p>Devs working on Metabase were complaining about LSP taking too long to boot, so I wondered how long it could be. A few seconds? Half a minute? Imagine my surprise when I saw this:</p>\n<pre><code class=\"language-clojure\">(time (clojure-lsp.api/analyze-project-only!\n  {:project-root (clojure.java.io/file \"/path/to/metabase\")}))\n\n\"Elapsed time: 178981.918417 msecs\"\n</code></pre>\n<p>Three minutes is a long time.</p>\n<p>The first suspect was heap size. There is a good rule of a thumb: if some process in Clojure (or any JDK language) takes longer to complete than anticipated, or doesn’t finish at all, you should check the heap.</p>\n<p>I used <a href=\"https://visualvm.github.io/\">VisualVM</a> to inspect our Clojure process and ran the benchmarking command, which gave us something like this:</p>\n<p><img src=\"/images/posts/engineering-2026/heap-usage-before.png\" alt=\"Profile of heap usage before changes\"></p>\n<p>What’s going on here? My laptop has 16 GB of RAM. By default, Java will take 25% of total RAM as the maximum heap size for the process. In my case, that means 4GB max heap, as you see in the screenshot. Clojure-lsp’s analysis fills up the heap with more and more unfreeable data, meaning objects that don’t get garbage-collected. The heap headroom (the amount of free heap space after garbage collection) becomes smaller and smaller, which means garbage collection has to run more often, to the point where a GC run has to start up before the last run can complete.</p>\n<p>Giving more heap space to the process by adding an <code>-J-Xmx6g</code> argument to the REPL command line shows a different picture:</p>\n<pre><code class=\"language-clojure\">(time (clojure-lsp.api/analyze-project-only!\n  {:project-root (clojure.java.io/file \"/path/to/metabase\")}))\n\n\"Elapsed time: 115370.613041 msecs\"\n</code></pre>\n<p><img src=\"/images/posts/engineering-2026/heap-usage-after.png\" alt=\"Profile of heap usage before changes, showing much more headroom\"></p>\n<p>Still almost two minutes, but we’ve shaved off a minute by just giving the process more space to breathe. The heap plot shows that “used heap” no longer hugs the “max heap” threshold so tightly, so GCs trigger less often.</p>\n<h2 id=\"part-2-profiling-and-optimizations\">Part 2: Profiling and optimizations</h2>\n<p>My next step was to use <a href=\"https://github.com/clojure-goes-fast/clj-async-profiler\">clj-async-profiler</a> to obtain a flamegraph of the benchmark above. I took an <a href=\"https://clojure-goes-fast.com/kb/profiling/clj-async-profiler/allocation-profiling/\">allocation profile</a> instead of a regular CPU profile because I’ve found that optimizing allocation hotspots results in roughly the same execution time savings, but allocation profiles have less variance and skew.</p>\n<pre><code class=\"language-clojure\">(clj-async-profiler.core/profile {:event :alloc}\n  (clojure-lsp.api/analyze-project-only! {:project-root (clojure.java.io/file \"/path/to/metabase\")}))\n</code></pre>\n<center>\n<figure>\n<div style=\"height:400px; width: 150%; -moz-transform: scale(0.666); -moz-transform-origin: 0 0; -o-transform: scale(0.666); -o-transform-origin: 0 0; -webkit-transform: scale(0.666); -webkit-transform-origin: 0 0;\">\n\n</div>\n<figcaption>\n    Allocation flamegraph before improvements. <a href=\"https://flamebin.dev/ciWxK6\" target=\"_blank\">Click to open</a>.\n</figcaption>\n</figure>\n</center>\n<p>A flamegraph is a good way to spot the hot code in stack traces (see <a href=\"https://clojure-goes-fast.com/kb/profiling/clj-async-profiler/exploring-flamegraphs/\">this tutorial</a> for more on flamegraphs). On the Y axis, you have stacks that grow from bottom to top. The position of the frame signifies which function calls which, and the height of the flamegraph shows the stack’s depth (which usually doesn’t matter).</p>\n<p>On the X-axis, the width of a frame shows how much total time each function call takes (or, in this case, the number of allocations of a particular object class). The coordinate of the frame on the X-axis doesn’t imply its <em>position</em> in time; in fact, the X-axis coordinate doesn’t mean anything (just its width).</p>\n<p>Looking at the flamegraph, most of clojure-lsp’s initialization is taken up by <a href=\"https://github.com/clj-kondo/clj-kondo\">clj-kondo</a>. If you search in the embedded graph for “kondo,” you’ll find that 95.41% of all frames match, meaning almost all work is kondo-related.</p>\n<p>After massaging the flamegraph and pruning irrelevant pieces, I found several significant inefficiencies and solutions for them.</p>\n<h3 id=\"deep-merge\">deep-merge</h3>\n<p>The <a href=\"https://github.com/clj-kondo/clj-kondo/pull/2779\"><code>deep-merge</code></a> function is similar to <code>clojure.core/merge</code>, but when <code>deep-merge</code> merges maps, it also merges values with duplicate keys in those maps. There were a few things to be improved here:</p>\n<ul>\n<li>If the value in the resulting map doesn’t change, don’t perform the <code>assoc</code> operation. So if <code>m</code> already has <code>{:k1 someval}</code>, we can skip <code>(assoc m :k1 someval)</code>.</li>\n<li>Before merging two sets, check if they’re equal. If they are, there’s no need to merge them; just return one of them.</li>\n<li>Only use Clojure transients for large collections, as transients bear some static upfront overhead, which can be less efficient than using simple vectors for small collections.</li>\n</ul>\n<h3 id=\"rewrite-clj-improvements\">rewrite-clj improvements</h3>\n<p><a href=\"https://github.com/clj-commons/rewrite-clj\">rewrite-clj</a> is a library that Kondo and LSP use to read and parse Clojure. I’ve applied several optimizations to it, but the most impactful change was dropping a <a href=\"https://github.com/clj-commons/rewrite-clj\">dynamic variable</a> on a hot path.</p>\n<p>In Clojure, dynamic variables (usually <code>*earmuffed*</code>) allow for passing “hidden” context to other functions instead of adding explicit arguments. In a sense, this hidden context is global state, but restricted to stack scope. A simple example:</p>\n<pre><code class=\"language-clojure\">(def ^:dynamic *honorific* nil)\n\n(defn hello [name]\n  (if *honorific*\n    (str *honorific* \" \" name)\n    name))\n\n(hello \"John\")\n=> \"John\"\n\n(binding [*honorific* \"Mrs.\"]\n  (hello \"Smith\"))\n=> \"Mrs. Smith\"\n</code></pre>\n<p>Here, having <code>*honorific*</code> as a dynamic variable saved us the trouble of adding another argument to <code>hello</code>. But setting a value for a dynamic variable with <code>binding</code> involves creating a new hashmap every time, and <code>assoc</code>-ing the value to it. That means allocations and spent cycles. So, if you care about the performance of a particular hot function, make sure to pass all arguments explicitly.</p>\n<h3 id=\"better-memoization\">Better memoization</h3>\n<p>Clojure kindly provides the <code>clojure.core/memoize</code> function, which caches the outputs of a function for the given inputs.<code>memoize</code>’s implementation, however, is quite simplistic and unoptimized:</p>\n<ul>\n<li>To accept functions of <em>any</em> arity, <code>clojure.core/memoize</code> uses a list of arguments as the cache key. Rolling arguments into the list triggers additional allocations.</li>\n<li><code>memoize</code> also uses <code>find</code> to look up the value for the key in the cache. When the map contains the key, <code>find</code> returns a key-value pair, a MapEntry object, which again needs to be allocated in the heap.</li>\n</ul>\n<p>Because clj-kondo only needs memoization for one- and two-argument functions, <a href=\"https://github.com/clj-kondo/clj-kondo/pull/2780\">a more specialized implementation</a> was warranted. For a single argument, the code is straightforward. For two arguments, the main trick is to structure the cache as a nested map <code>{arg1 {arg2 cached-value}}</code> instead of <code>{[arg1 arg2] cached-value}</code>. Nesting the map avoids wrapping arguments into a vector during the lookup.</p>\n<h2 id=\"part-3-measuring-total-allocations\">Part 3: Measuring total allocations</h2>\n<p>I proposed each optimization as a separate PR to clj-kondo, because I thought it would be helpful for the maintainer, the venerable <a href=\"https://github.com/borkdude\">Michiel Borkent</a>, to see the impact of each optimization. The timing differences for each improvement separately were too flaky to observe a meaningful difference, so I came up with another metric: the total number of allocated bytes during the benchmark.</p>\n<p>The following script does the work of hooking into GC events and captures how many bytes were freed each time. In the end, we add up all those bytes to calculate the total allocated value.</p>\n<pre><code class=\"language-clojure\">(import\n '[com.sun.management GarbageCollectionNotificationInfo GcInfo]\n '[javax.management NotificationEmitter]\n '[java.lang.management ManagementFactory MemoryUsage]\n '[javax.management NotificationListener]\n '[javax.management.openmbean CompositeData])\n\n(def memory-bean (ManagementFactory/getMemoryMXBean))\n(def gc-collections (atom []))\n\n(defn calc-freed\n  \"Return the number of bytes reclaimed by a given GC run.\"\n  [^GcInfo gc-info]\n  (let [before (.getMemoryUsageBeforeGc gc-info)\n        after  (.getMemoryUsageAfterGc gc-info)]\n    (reduce (fn [total pool]\n              (let [used-before (.getUsed ^MemoryUsage (get before pool))\n                    used-after  (.getUsed ^MemoryUsage (get after pool))]\n                (if (> used-before used-after)\n                  (+ total (- used-before used-after))\n                  total)))\n            0\n            (keys before))))\n\n(defn install-gc-listener!\n  \"Add a hook that runs on every GC invocation to intercept and remember how\n  much heap space the GC freed.\"\n  []\n  (doseq [gc-bean (ManagementFactory/getGarbageCollectorMXBeans)]\n    (.addNotificationListener\n     ^NotificationEmitter gc-bean\n     (reify NotificationListener\n       (handleNotification [_ notification _]\n         (when (= (.getType notification)\n                  GarbageCollectionNotificationInfo/GARBAGE_COLLECTION_NOTIFICATION)\n           (let [info (GarbageCollectionNotificationInfo/from\n                       ^CompositeData (.getUserData notification))\n                 gc-info (.getGcInfo info)\n                 freed   (calc-freed gc-info)]\n             (swap! gc-collections conj freed)))))\n     nil nil)))\n\n(install-gc-listener!)\n\n(def used-heap-before (.getUsed (.getHeapMemoryUsage memory-bean)))\n\n(time (clojure-lsp.api/analyze-project-only! {:project-root (clojure.java.io/file \"/path/to/metabase\")}))\n\n(defn print-allocation-stats []\n  (let [used-heap-after (.getUsed (.getHeapMemoryUsage memory-bean))\n        total-allocated (+ (reduce + @gc-collections)\n                           used-heap-after\n                           (- used-heap-before))]\n    (println (format \"Allocation stats: %s GC collections, allocated %.1fGB\"\n                     (count @gc-collections)\n                     (double (/ total-allocated 1e9))))))\n\n(print-allocation-stats)\n</code></pre>\n<p>With this script, I got the following numbers before and after the applied optimizations:</p>\n<pre><code class=\"language-clojure\">;; Before\n\"Elapsed time: 89335.263292 msecs\"\nAllocation stats: 245 GC collections, allocated 145.0GB\n\n;; After\n\"Elapsed time: 46784.39225 msecs\"\nAllocation stats: 117 GC collections, allocated 51.6GB\n</code></pre>\n<p>We see a 2x improvement in the elapsed time and almost 3x reduction of the number of bytes allocated on the heap.</p>\n<p>To see where exactly the improvements manifested in the code, I took a second allocation profile using clj-async-profiler to generate a <a href=\"https://clojure-goes-fast.com/kb/profiling/clj-async-profiler/diffgraphs/\">diffgraph</a>.</p>\n<center>\n<figure>\n<div style=\"height:400px; width: 150%; -moz-transform: scale(0.666); -moz-transform-origin: 0 0; -o-transform: scale(0.666); -o-transform-origin: 0 0; -webkit-transform: scale(0.666); -webkit-transform-origin: 0 0;\">\n\n</div>\n<figcaption>\n    Allocation diffgraph after improvements. <a href=\"https://flamebin.dev/qBGwfE\" target=\"_blank\">Click to open.</a>\n</figcaption>\n</figure>\n</center>\n<p>A diffraph is a type of flamegraph that combines two profiles and shows differences between them. Color represents the direction and intensity of change. Blue frames mean that the second profile contains fewer samples for that code path (which means faster, fewer allocations, etc.). Red frames show more samples than before.</p>\n<p>Highlighting the diffgraph’s base shows that we reduced allocations by ~66% (which matches the benchmark results above). If you scroll up to stacks of more saturated blue, you’ll see which parts of the code were the most affected. For instance, <code>clj-kondo.impl.analyzer.namespace/analyze-ns-decl</code> has almost completely disappeared from the profile (-96% allocations on that codepath), <code>clj-kondo.impl.rewrite-clj.parser.core/parse-delim</code> performs 93% fewer allocations than before, and so on. When you see a sea of blue on the diffgraph, you know you are doing something right.</p>\n<h2 id=\"conclusions\">Conclusions</h2>\n<p>Being able to do something in a development tool is the main part, but speed and ergonomics matter just as much. A tool that is “almost instant” when employed in a small project may become unwieldy in an industrial-scale one like the Metabase codebase.</p>\n<p>We significantly improved clojure-lsp’s initialization time and memory pressure. <a href=\"https://github.com/ericdallo\">Eric Dallo</a>, the maintainer of clojure-lsp, has kindly provided <a href=\"https://github.com/clj-kondo/clj-kondo/issues/2778\">his own benchmark results and analysis of the optimizations</a>, and has independently confirmed the speed-ups on codebases comparable to Metabase. Our proposed changes are already merged, and will ship in the new release of clojure-lsp.</p>\n<p>There is still plenty to be done to improve the clojure-lsp experience. The server still keeps a weighty amount of heap when loaded (around 2-3 GB) and there are probably a lot more opportunities to reduce this number. But that’s a story for another blog post.</p>\n<h2 id=\"more-from-metabase-engineering\">More from Metabase Engineering</h2>\n<ul>\n<li><a href=\"/blog/librechat-self-hosted\">How we picked LibreChat — and ended up with a Slack agent</a></li>\n<li><a href=\"/blog/reprobot-github-issue-triage-agent\">Meet Repro-Bot, our GitHub issue triage agent</a></li>\n<li><a href=\"/blog/lessons-learned-building-ai-analytics-agents\">Lessons learned from building AI analytics agents: build for chaos</a></li>\n<li><a href=\"/blog/ten-custom-subagents\">How we built ten custom subagents to tame a 500K-line Clojure codebase</a></li>\n<li><a href=\"/blog/improving-performance-clojure-development-tools\">Improving the performance of the popular Clojure development tool clojure-lsp</a></li>\n</ul>"
