contentHtml: "<div>\r\n                        <p><strong>A modified salting technique that cuts P99 write latency 22x for large blobs</strong></p>\n<p>Storing huge blobs in any database has always been, and still is, very challenging. Large allocations required for storing, reading, compacting, and repairing such cells always create significant pressure on the memory allocation sub-system. In addition, receiving a write request or sending a read response with a huge payload on a shared connection creates a “head of line” issue impacting the latency of other requests.</p>\n<p>This is true for every database!</p>\n<p>Consequently, by splitting the blob into smaller chunks and processing them in parallel, we can achieve latencies comparable to a single chunk read/write operation.</p>\n<p>Naturally, when all your data consists of huge blobs, you are probably not going to use CQL or SQL databases to store them. You will use S3-like storage for blobs and will use CQL/SQL DB to store references to those blobs.</p>\n<p>However, if your data is mostly reasonably small but has a small part of the population that are huge blobs, you may want to be able to serve both small and large blobs from the same database.</p>\n<p>While working with ScyllaDB, we found that a modified salting technique can address the latency impact of storing large blobs. In this post, we present that salting technique, then explain when/how to apply it.</p>\n<h2>Background: Large Blobs in ScyllaDB</h2>\n<p>For a better idea of how storing large blobs impacts performance, let’s look at an example.</p>\n<p>In our testing of ScyllaDB version 2026.1.1 with cassandra-stress tool, we observed that writing key-value rows with a 60MB blob cell results in an average latency of about 568ms and P99 latencies of 1.4s. In contrast, writing K/V data of 1MB yields an average latency of 2.2ms, with a P99 of approximately 4.5ms.</p>\n<p>When writing 60MB cells, ScyllaDB could not go any faster because its memory high-performance requirements.</p>\n<p>However, 1MB results show that if we can split the blob into smaller chunks and write/read them in parallel we can achieve latencies close to a single chunk read/write operation. Perhaps salting can help us achieve this?</p>\n<h2>Classic Salting Technique</h2>\n<p>The classic “salting” technique, used to break down large partitions consisting of too many rows, introduces an additional “salt” column to the partition key. It selects a random value from a known range (e.g., an integer between 0 and 99) to store the next row.</p>\n<p>This will distribute what once was a single large partition for a key KEY<sub>1</sub> into 100 smaller partitions with partition keys (KEY<sub>1</sub>, 0), (KEY<sub>1</sub>, 1) …, (KEY<sub>1</sub>, 99) each of about 1/100 the size of the original one.</p>\n<p>The primary drawback of this technique for large partitions is the necessity of using “salting” for every row, as the system does not inherently know if a row belongs to a large partition. Consequently, reading data for any original key KEY<sub>n</sub> requires reading all 100 partitions (KEY<sub>n</sub>, k), where k=0, 1, …, 99. And this may be very wasteful because large partitions normally represent a very small part of the total partition population. Similarly, large blobs typically represent only a small fraction of the total blob population.</p>\n<p>Another “weak spot” of the classic “salting” is that you can’t reduce the SALT cardinality — you can only increase it. This means that if the size of your large partitions got smaller, you would still need to use the same “salt” cardinality you already used before.</p>\n<h2>Modified Salting Technique for Storing Blobs</h2>\n<p>We found that improving the original “salting” algorithm for a blob case can eliminate both of those drawbacks. Let’s look at how we modified that classic salting technique.</p>\n<h3>Schema</h3>\n<p>Let’s assume that the original table schema is as follows:</p>\n<pre><code>CREATE TABLE keyspace1.standard1 (\r\n    key blob,\r\n    value blob,\r\n    PRIMARY KEY (key)\r\n)</code></pre>\n<p>For our algorithm, we modify it to:</p>\n<pre><code>CREATE TABLE keyspace1.standard1 (\r\n    key blob,\r\n    salt int,\r\n    chunk_id int,\r\n    chunk blob,\r\n    total_chunks int,\r\n    salt_cardinality int\r\n    PRIMARY KEY ((key, salt), chunk_id)\r\n)</code></pre>\n<h3>Algorithm</h3>\n<h4>Write</h4>\n<p>On a write path, we are going to store the used “max_salt” (<em>salt_cardinality</em>) and the total number of chunks (<em>total_chunks</em>) in every row in addition to the rest of the chunk-specific data for simplicity. If you want to optimize the storage to a bitter end, you can store <em>salt_cardinality</em> and <em>total_chunks</em> only in the “metadata row” (see below).</p>\n<pre><code>def write_key_blob(key, blob, max_salt=100, max_chunk_size=4096):\r\n    # Split blob into chunks; last chunk may be smaller\r\n    split_blob_chunks: List[bytes] = split_blob(blob, max_chunk_size)\r\n    num_chunks = len(split_blob_chunks)\n    salted_partition_chunks = [[]] * min(num_chunks, max_salt)\r\n    for chunk_id, chunk in enumerate(split_blob_chunks):\r\n        salted_partition_chunks[chunk_id % max_salt].append(\r\n            (chunk_id, chunk)\r\n        )\n    for salt, chunks in enumerate(salted_partition_chunks):\r\n        # Inserts salted partition in one or a few UNLOGGED BATCHes\r\n        insert_async_batch(\r\n            key=key,\r\n            salt=salt,\r\n            chunks=chunks,\r\n            total_chunks=num_chunks,\r\n            salt_cardinality=max_salt\r\n        )</code></pre>\n<h4>Complexity</h4>\n<ul>\n<li>Memory: <strong>O(sizeof(blob))</strong></li>\n<li>CPU: <strong>O(num_chunks)</strong></li>\n<li>DB: <strong>O(num_salted_partitions)</strong>, where num_salted_partitions = min(num_chunks, max_salt)</li>\n</ul>\n<h4>Latency</h4>\n<ul>\n<li>Maximum batches concurrency divided by the num_salted_partitions times the single batch latency.</li>\n<li>If all batches can be sent out in parallel, the whole write is going to take the time it takes to write a single salted partition data.</li>\n</ul>\n<h4>Read</h4>\n<p>On a read path, we are going to start with reading <em>total_chunks</em> and <em>salt_cardinality</em> from the “metadata row” of a specific Key: row with (key=Key, salt=0, chunk_id=0) primary key. If we have stored any data for the Key, this row should exist.</p>\n<p>Once we have <em>total_chunks</em> and <em>salt_cardinality</em> values, we can calculate primary key values for every chunk of the original blob we stored before, and read them all in parallel.</p>\n<p>Below you can find a pseudo-code implementing this idea.</p>\n<pre><code>def read_key_blob(key: bytes):\r\n    # SELECT (total_chunks, salt_cardinality) FROM keyspace1.standard1\r\n    # WHERE key=key AND salt=0 AND chunk_id=0\r\n    total_chunks, max_salt = get_num_chunks(key=key)\n    if not total_chunks:\r\n        return None  # No data for this key\n    salted_results_futures = []\r\n    for i in range(min(total_chunks, max_salt)):\r\n        # Full partition read\r\n        salted_results_futures.append(\r\n            async_read(device_id=device_id, salt=i)\r\n        )\n    # Poll for completions; can also use async callbacks\r\n    salted_partition_data = []\r\n    while salted_results_futures:\r\n        not_finished = []\r\n        for fut in salted_results_futures:\r\n            if fut.done():\r\n                salted_partition_data.append(fut.result())\r\n            else:\r\n                not_finished.append(fut)\r\n        salted_results_futures = not_finished\n    # Reassemble blob in correct order\r\n    chunks: List[bytes] = [None] * total_chunks\r\n    for partition_data in salted_partition_data:\r\n        for row in partition_data:\r\n            chunks[row['chunk_id']] = row['chunk']\n    # Zero-copy binary iterator over the original chunk\r\n    return itertools.chain.from_iterable(chunks)</code></pre>\n<h4>Complexity</h4>\n<ul>\n<li>Memory: <strong>O(sizeof(original blob))</strong></li>\n<li>CPU: <strong>O(num_chunks)</strong></li>\n<li>DB: <strong>O(num_salted_partitions)</strong>, where num_salted_partitions = min(num_chunks, max_salt)</li>\n</ul>\n<h3>Solving Different Blobs’ Version Problem</h3>\n<p>As with regular large partition salting, there are some challenges:</p>\n<ul>\n<li>How to ensure the chunks you read belong to the same version of the blob?</li>\n<li>How to ensure concurrent writers of different blob versions to the same Key don’t leave the database’s data in an inconsistent state?</li>\n</ul>\n<p>A rather common approach to solving the first issue is to add a ‘version’ non-key column:</p>\n<ul>\n<li>Writers must guarantee that every time they write a new version of the blob, they assign the same cluster-unique version identifier to every chunk (in order to ensure that all chunks of that specific version share the same identifier).</li>\n<li>A reader would always verify that the versions of each chunk (row) he/she reads for a specific Key match. And if they don’t — one needs to retry a read.</li>\n</ul>\n<p>Solving the second issue on the DB level is not recommended. It would require using atomic transactions like CQL LWT, which would introduce a performance overhead of their own.</p>\n<p>A better approach is to ensure the atomicity of writes on the application level by ensuring that there is always a single writer to the same (original) Key at any given point in time. One way to implement this is to have writer Agents manage specific Shard Key ranges. Each Agent acts as a consumer for an MPSC queue and is responsible for writing new versions of blobs belonging to its assigned keys.</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/MPSC.png\"><img src=\"https://www.scylladb.com/wp-content/uploads/MPSC.png\" alt=\"\" srcset=\"https://www.scylladb.com/wp-content/uploads/MPSC.png 1123w, https://www.scylladb.com/wp-content/uploads/MPSC-300x94.png 300w, https://www.scylladb.com/wp-content/uploads/MPSC-1100x344.png 1100w, https://www.scylladb.com/wp-content/uploads/MPSC-768x240.png 768w\"></a></p>\n<p>In general, solving these problems is outside the scope of this blog.</p>\n<h3>Benefits Compared to Classic Salting</h3>\n<ul>\n<li>One can choose any blob chunk size (<code>MAX_CHUNK_SIZE</code>) and any salting cardinality (<code>MAX_SALT</code>) for every key without impacting other keys writes or reads.</li>\n<li>Unnecessary reads of empty partitions in the read path are eliminated at the price of an additional small read of 8 bytes.</li>\n</ul>\n<h3>Examples of Approaches When Choosing MAX_CHUNK_SIZE and MAX_SALT</h3>\n<table>\n<thead>\n<tr>\n<th>Approach</th>\n<th>How to configure</th>\n<th>Pros</th>\n<th>Cons</th>\n</tr>\n</thead>\n<tbody>\n<tr>\n<td>Fixed maximum chunk size</td>\n<td>Always use the same <code>MAX_CHUNK_SIZE</code> for all blobs. Choose different <code>MAX_SALT</code> values per key depending on the blob size to control the size and the number of salted partitions.</td>\n<td>Use it if you want to create a predictable load on the internal memory allocation system.</td>\n<td>The number or the size of salted partitions may grow large for big blobs.</td>\n</tr>\n<tr>\n<td>Fixed maximum number of salted partitions per original key</td>\n<td>Always use the same <code>MAX_SALT</code> for each key. You may choose to pick a different <code>MAX_CHUNK_SIZE</code> to control the number of rows in each salted partition.</td>\n<td>Same CPU complexity for read and write operations.</td>\n<td>Some partitions or cells can get big for big blobs.</td>\n</tr>\n<tr>\n<td>Control the number of single-row/single-shard partitions to be above a particular portion of the total population</td>\n<td>Choose <code>MAX_SALT</code> to be 1 for blobs below a certain size, e.g. P99 blob sizes in the data population.</td>\n<td>Control the amount of data loss in case of losing a quorum.</td>\n<td>If the threshold is chosen to be some big value, it may create huge partitions, which will in turn create bottlenecks on corresponding shards (CPUs).</td>\n</tr>\n</tbody>\n</table>\n<h4>Clarifications About the Last Policy</h4>\n<p>One of the reasons that we want to salt large partitions (in this particular case, we are effectively salting a “large partition that has all the chunks of our original blob”) is to avoid creating a bottleneck on a single shard. By salting, we are distributing its data among many shards. That not only allows reading and writing its smaller parts in parallel, but also distributes the corresponding overhead among multiple shards of the ScyllaDB database.</p>\n<p>However, this same distribution is going to become our nemesis when we try to estimate the “blast radius” of data consistency loss when we lose a quorum.</p>\n<p>Let’s do a quick estimation. Assume the following configuration:</p>\n<ul>\n<li><strong>Cluster:</strong> 3 racks (A, B, and C), each rack having 2 nodes A<sub>1</sub>, A<sub>2</sub>, B<sub>1</sub>, B<sub>2</sub>, C<sub>1</sub>, C<sub>2</sub> correspondingly.</li>\n<li><strong>Keyspace:</strong> NetworkTopologyStrategy with RF=3 in the current DC.</li>\n<li><strong>Write consistency:</strong> LOCAL_QUORUM (this is a common consistency setting that, when paired with a LOCAL_QUORUM read, ensures immediate visibility of all writes)</li>\n</ul>\n<p>When we write with a LOCAL_QUORUM, we always write to all 3 replicas — however, the write request is reported as a success when 2 out of 3 replicas acknowledge the write.</p>\n<p>Therefore, when we estimate potential consistency loss, we should always assume the worst case scenario of when <strong>every</strong> write has only reached 2 out of 3 replicas.</p>\n<p>Let’s now assume that nodes A<sub>1</sub> and B<sub>1</sub> are lost, and so is all their data.</p>\n<p>If blobs are stored as-is (no chunking) as a single key-value row/partition, then this would mean that we lost a guaranteed consistency for about <strong>25% of our data set</strong>: A<sub>1</sub> has data of ~50% of the population and there is a ~50% probability that keys replicated on A<sub>1</sub> are also replicated on B<sub>1</sub>.</p>\n<p>To reduce this number, one should provision more nodes per-rack.</p>\n<table>\n<thead>\n<tr>\n<th>Number of nodes per rack</th>\n<th>Possible data loss amount when losing 1 node in each of 2 racks</th>\n</tr>\n</thead>\n<tbody>\n<tr>\n<td>3</td>\n<td>~11%</td>\n</tr>\n<tr>\n<td>4</td>\n<td>~6.25%</td>\n</tr>\n<tr>\n<td>5</td>\n<td>~4%</td>\n</tr>\n<tr>\n<td>…</td>\n<td>…</td>\n</tr>\n</tbody>\n</table>\n<p>If blobs are chunked and salted — each with <code>MAX_SALT</code> of at least as the number of nodes in a single rack — then statistically, each node in the cluster is going to have some chunks of each blob. For the above scenario, we would have to assume that we lost consistency of every key: <strong>100% data loss</strong>.</p>\n<p>Total data consistency loss is a critical scenario that database administrators strive to avoid.</p>\n<p>So, how can this risk be reduced? One option is to use a hybrid salting strategy, as presented above.</p>\n<ul>\n<li><strong>If all your blobs are large or blob sizes are uniformly distributed</strong>, then you may want to chunk them and store each blob’s chunks as a single partition: always use <code>MAX_SALT=1</code>.</li>\n<li><strong>If your blob size distribution has a high tail</strong> (e.g. P99 is 10MB while the average blob size is 300 bytes), then add only 1% to the value in the table above. To do this, you can use <code>MAX_SALT=1</code> for all blobs below 10MB and use a larger <code>MAX_SALT</code> (e.g. 100) for all blobs that are larger or equal than 10MB.\n<ul>\n<li>It allows for effective management of the data loss blast radius.</li>\n<li>It enables the distribution of the largest blobs across multiple shards, fulfilling the primary goal of chunking.</li>\n</ul>\n</li>\n</ul>\n<h2>Demo</h2>\n<p>Here is a small demonstration of the idea described above.
