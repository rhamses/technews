contentHtml: "<div>\r\n                        <p><strong>By transitioning from separate summary and index files to a prefix tree, we optimized cache efficiency, reduced disk I/O, and reduced memory overhead</strong></p>\n<p>Trie-based SSTable index format was added in <a target=\"_blank\" href=\"https://forum.scylladb.com/t/release-scylladb-2025-4-0/5222\">ScyllaDB 2025.4</a>. Since then, it has evolved and matured to become the default index format in ScyllaDB 2026.2.</p>\n<p>In this post, we deep dive into the format change, present its pros and cons, and show our latest benchmark results of the legacy vs. Trie index formats.</p>\n<p>For benchmarking, we chose four different read workloads that would benefit from the Trie index format in different degrees. For all four, Trie indexes demonstrated better performance. They achieved <strong>30% to 230% higher throughput and 31% to 63% lower latency</strong> compared to legacy indexes. The impact of Trie index on the write path is negligible.</p>\n<h2>Trie Index Usage in ScyllaDB</h2>\n<p>Before explaining the new format, we will cover the legacy index format and its challenges.</p>\n<h3>Legacy Three-Layer Lookup (me/md format)</h3>\n<p>Until ScyllaDB 2026.2 the default storage format was the <a target=\"_blank\" href=\"https://docs.scylladb.com/manual/stable/architecture/sstable/\">SSTable version md and me</a>.</p>\n<p>Every SSTable lookup in the me/md format traverses three or four structures:</p>\n<ul>\n<li><code>Summary.db</code> (entirely in RAM)</li>\n<li>Binary search in <code>Index.db</code></li>\n<li>Sequential read in <code>Data.db</code></li>\n</ul>\n<p>Both the partition index and the clustering-row index are stored in <code>Index.db</code>. The partition index is partially represented in memory by the sampled <code>Summary.db</code>, while the clustering-row index exists as a promoted index for large partitions.</p>\n<pre><code>┌──────── MEMORY ──────────────────────────────┐\r\n│                                              │\r\n│  Summary.db  (entirely in RAM)               │\r\n│  ─────────────────────────────               │\r\n│  Sampled at ~<span>1</span> byte per ~<span>2000</span> bytes of       │\r\n│  Data.db                                     │\r\n│                                              │\r\n│  <span>\"aardvark\"</span> → Index.db byte        <span>0</span>         │\r\n│  <span>\"kangaroo\"</span> → Index.db byte  <span>1</span>,<span>048</span>,<span>576</span>       │\r\n│  <span>\"platypus\"</span> → Index.db byte  <span>2</span>,<span>097</span>,<span>152</span>       │\r\n│  <span>\"zebra\"</span>    → Index.db byte  <span>3</span>,<span>145</span>,<span>728</span>       │\r\n│                                              │\r\n└──────────────────┬───────────────────────────┘\r\n                   │\r\n       binary search → window in Index.db\r\n                   │\r\n                   ▼\r\n┌──────── DISK ────────────────────────────────┐\r\n│                                              │\r\n│  Index.db                                    │\r\n│  ─────────                                   │\r\n│  <span>\"kangaroo\"</span>   → Data.db: <span>4</span>,<span>096</span>,<span>000</span>           │\r\n│  <span>\"koala\"</span>      → Data.db: <span>4</span>,<span>097</span>,<span>280</span>           │\r\n│  <span>\"kookaburra\"</span> → Data.db: <span>4</span>,<span>098</span>,<span>560</span>           │\r\n│  <span>\"lemur\"</span>      → Data.db: <span>4</span>,<span>099</span>,<span>840</span>  ← found  │\r\n│  ... The storage format is compatible with Apache Cassandra’s BTI (Big Trie Index) format, implemented using ScyllaDB’s Seastar architecture.</p>\n<p>Trie indexes are used for both partition indexes and clustering key indexes.</p>\n<h3>What Is a Trie?</h3>\n<p>A trie (prefix tree) stores keys character-by-character. Shared prefixes occupy a single path, eliminating redundancy:</p>\n<pre><code>Keys: <span>\"kangaroo\"</span>, <span>\"koala\"</span>, <span>\"kookaburra\"</span>, <span>\"lemur\"</span>, <span>\"lion\"</span>\n            [root]\r\n            /    \\\r\n          <span>'k'</span>    <span>'l'</span>\r\n           |      |\r\n          [k]    [l]\r\n          / \\    / \\\r\n        <span>'a'</span> <span>'o'</span><span>'e'</span> <span>'i'</span>\r\n         |   |  |   |\r\n        <span>'n'</span> [o]<span>'m'</span> <span>'i'</span>\r\n         |  / \\ |   |\r\n        <span>'g'</span><span>'a'</span> <span>'o'</span><span>'u'</span> <span>'o'</span>\r\n         |  |  |  |   |\r\n        <span>'a'</span><span>'l'</span> <span>'k'</span><span>'r'</span> <span>'n'</span>\r\n         |  |  |  *\r\n        <span>'r'</span><span>'a'</span> <span>'a'</span>    * = leaf node\r\n         |  *  |       (payload: Data.db offset)\r\n        <span>'o'</span>   <span>'b'</span>\r\n         |     |\r\n        <span>'o'</span>   <span>'u'</span>\r\n         *     |\r\n              <span>'r'</span>\r\n               |\r\n              <span>'r'</span>\r\n Files</h3>\n<p>The ms/mt format replaces <code>Summary.db</code> and <code>Index.db</code> with two purpose-built files:</p>\n<pre><code>SSTable (ms format)\r\n├── Data.db\r\n│     unchanged — partition and row data,\r\n│     same binary layout as me/md\r\n│\r\n├── Partitions.db                     ← NEW\r\n│     Trie index:\r\n│       partition key → Data.db offset\r\n│         (small partitions)\r\n│       partition key → Rows.db offset\r\n│         (large partitions)\r\n│\r\n│     ┌── Page <span>0</span> (<span>4,096</span> <span>bytes</span>) ───────┐\r\n│     │  trie root node [<span>1</span>]           │\r\n│     │  + children (fan-out ≤ <span>256</span>)   │\r\n│     │  + their children (packed)    │\r\n│     └───────────────────────────────┘\r\n│     ┌── Page <span>1</span> (<span>4,096</span> <span>bytes</span>) ───────┐\r\n│     │  subtree for keys <span>'a'</span>–<span>'g'</span>     │\r\n│     └───────────────────────────────┘\r\n│     ...\r\n│     ┌── Footer ─────────────────────┐\r\n│     │  first_key      (raw <span>bytes</span>)   │\r\n│     │  last_key       (raw <span>bytes</span>)   │\r\n│     │  partition_count (<span>uint64</span>)     │\r\n│     │  trie_root_pos  (<span>uint64</span>)      │\r\n│     └───────────────────────────────┘\r\n│\r\n├── Rows.db                            ← NEW\r\n│     Per-partition clustering-key\r\n│     tries, concatenated.\r\n│     Each sub-trie:\r\n│       clustering key → byte-offset\r\n│         within partition\r\n│     (replaces flat <span>\"promoted index\"</span>\r\n│      in Index.db)\r\n│\r\n├── Filter.db     bloom filter — unchanged\r\n├── Statistics.db statistics  — unchanged\r\n└── Scylla.db     ScyllaDB metadata — unchanged</code></pre>\n<p>[1] Parent nodes are always written after their child nodes. Parents point to children, so child positions must be known before parents are written.</p>\n<h3>How a Partition Lookup Works</h3>\n<pre><code>Query: SELECT * FROM orders\r\n       WHERE order_id = <span>'ORD-20240611-98765'</span>\n┌─────────────────────────────────────────┐\r\n│  Step <span>1</span> — Key Translation               │\r\n│                                         │\r\n│  <span>'ORD-20240611-98765'</span>                   │\r\n│         ↓  bti_key_translation.cc       │\r\n│  comparable byte sequence               │\r\n│  (lexicographic order matches           │\r\n│   CQL semantic order)                   │\r\n└──────────────────┬──────────────────────┘\r\n                   │\r\n┌──────────────────▼──────────────────────┐\r\n│  Step <span>2</span> — Trie Traversal                │\r\n│           in Partitions.db              │\r\n│                                         │\r\n│  Read root page (<span>4</span> KB)                  │\r\n│    ← usually in OS page cache           │\r\n│                                         │\r\n│  [root] ──<span>'O'</span>──&gt; [node]  (page <span>0</span>)       │\r\n│  [node] ──<span>'R'</span>──&gt; [node]  (page <span>0</span>)       │\r\n│  [node] ──<span>'D'</span>──&gt; [node]  (fetch page <span>1</span>) │\r\n│  [node] ──<span>'-'</span>──&gt; [node]  (page <span>1</span>)       │\r\n│  ...                                    │\r\n│  [leaf] payload = Data.db or            │\r\n│                   Rows.db pos <span>2</span>,<span>097</span>,<span>152</span> │\r\n│                                         │\r\n│  Typical: <span>2</span>–<span>6</span> page fetches.             │\r\n│  Top pages cached → often <span>0</span>–<span>1</span> disk I/Os │\r\n└──────────────────┬──────────────────────┘\r\n                   │\r\n┌──────────────────▼──────────────────────┐\r\n│  Step <span>3</span> — Read Data.db                  │\r\n│  Seek <span>to</span> offset <span>2</span>,<span>097</span>,<span>152</span>               │\r\n│  → read partition header                │\r\n│  For large partitions: read Rows.db     │\r\n└──────────────────┬──────────────────────┘\r\n                   │  (range/clustering queries only)\r\n┌──────────────────▼──────────────────────┐\r\n│  Step <span>4</span> — Read Data.db at position      │\r\n│           returned from index           │\r\n└─────────────────────────────────────────┘</code></pre>\n<h3>Page Layout: Packing Parent and Children Together</h3>\n<p>The most critical write-time optimization is ensuring that a node and its children land on the <strong>same 4 KB page</strong>. This means an entire trie neighborhood is readable in a single I/O, even on the first (cold) access.</p>\n<pre><code>┌──────── <span>4,096-byte</span> page ────────────────┐\r\n│                                         │\r\n│  [A] ──<span>'p'</span>──&gt; [B] ──<span>'p'</span>──&gt; [C]         │\r\n│         │                │              │\r\n│         └──<span>'r'</span>──&gt; [D]    ├──<span>'l'</span>──&gt;[E]* │\r\n│                          │              │\r\n│                          └──<span>'y'</span>──&gt;[F]* │\r\n│                                         │\r\n│  (* = leaf node with payload)           │\r\n│  (padding <span>bytes</span> <span>to</span> align next subtree         │\r\n│   to page boundary)                     │\r\n└─────────────────────────────────────────┘\ntrie_writer algorithm (trie_writer.hh):\n  <span>1</span>. Maintain rightmost path root → current\r\n     node (_stack)\r\n  <span>2</span>. On each new key: branch off rightmost\r\n     path, add new nodes\r\n  <span>3</span>. Accumulate nodes until a finished\r\n     subtree exceeds a page\r\n  <span>4</span>. Flush child subtrees with padding so\r\n     each subtree fits within one page\nScyllaDB vs. Cassandra reference impl:\n  Cassandra: one character per node\r\n  ScyllaDB:  characters grouped into\r\n             <span>\"chains\"</span> (up <span>to</span> <span>300</span> <span>bytes</span>)\r\n  → dramatically faster writes for long\r\n    keys, same read-side page structure</code></pre>\n<h3>Old vs. New: Side-by-Side Summary</h3>\n<table>\n<thead>\n<tr>\n<th></th>\n<th>Legacy me/md</th>\n<th>Trie ms/mt</th>\n</tr>\n</thead>\n<tbody>\n<tr>\n<td><strong>On-disk files</strong></td>\n<td><code>Summary.db</code> + <code>Index.db</code></td>\n<td><code>Partitions.db</code> + <code>Rows.db</code></td>\n</tr>\n<tr>\n<td><strong>In-memory component</strong></td>\n<td>Summary (always loaded, never evicted)</td>\n<td>None. This is especially true for large partitions, often seen in materialized view workloads.</li>\n<li><strong>CPU efficiency:</strong> less CPU is needed to process the index during reads.</li>\n</ul>\n<p>A possible downside is that more CPU is needed to create the index during memtable flush and compaction. However, this is more than offset by the read-side advantages.</p>\n<p>For proof of Avi’s first point, see the Disk Read panels from ScyllaDB Monitoring’s OS metric dashboard for legacy vs. Trie index format. Each step represents increasing workload throughput.</p>\n<p>For the first load, using the same throughput, Disk Reads for legacy indexes is ~240 MB/s; for Trie indexes, it is ~33 MB/s. The Trie index consumes only ~1/7th of the storage bandwidth.</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/trie2.png\"><img src=\"https://www.scylladb.com/wp-content/uploads/trie2-1100x646.png\" alt=\"\" srcset=\"https://www.scylladb.com/wp-content/uploads/trie2-1100x646.png 1100w, https://www.scylladb.com/wp-content/uploads/trie2-300x176.png 300w, https://www.scylladb.com/wp-content/uploads/trie2-768x451.png 768w, https://www.scylladb.com/wp-content/uploads/trie2-1536x902.png 1536w, https://www.scylladb.com/wp-content/uploads/trie2.png 2048w\"></a> <a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/trie1.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/trie1-1100x646.png 1100w, https://www.scylladb.com/wp-content/uploads/trie1-300x176.png 300w, https://www.scylladb.com/wp-content/uploads/trie1-768x451.png 768w, https://www.scylladb.com/wp-content/uploads/trie1-1536x902.png 1536w, https://www.scylladb.com/wp-content/uploads/trie1.png 2048w\" src=\"https://www.scylladb.com/wp-content/uploads/trie1-1100x646.png\" alt=\"\"></a></p>\n<p>Note that the Trie index has a negligible effect for 100% cache hit rate or 0% cache hit rate workloads. For both, the in-memory index representation is irrelevant. Write workload is also only marginally affected by the index format change.</p>\n<h2>Summary</h2>\n<p>ScyllaDB 2026.2 has adopted a Trie-based index format as its new default, replacing the legacy index structure to significantly enhance read path performance. By transitioning from separate summary and index files to a prefix tree, this design optimizes cache efficiency, reduces disk I/O, and reduces memory overhead. Benchmarks indicate that this architectural change delivers throughput improvements ranging up to 3x across various workloads, offering a more scalable and efficient solution than the legacy index format.</p>\n<p><strong>As always, actual results depend on your workload. To evaluate the gain of Trie index, we highly recommend testing it yourself with the latest ScyllaDB releases.</strong></p>\n<h2>Appendix: The Full Test Setup</h2>\n<p>All tests compare me (legacy) vs. ms (trie) format on identical code, hardware, and dataset.
