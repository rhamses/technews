contentHtml: "<div>\r\n                        <p><strong>ScyllaDB successfully mitigated performance-degrading connection storms by optimizing caching, throttling, and password hashing to achieve a 1000x reduction in tail latency</strong></p>\n<p>The story begins with a customer-visible problem: node restarts spiked P99 latency to <strong>5 seconds</strong> for a full minute, while typical latency for the cluster was only <strong>4 milliseconds</strong>. The cause was a flood of new connections. For ScyllaDB to achieve ultra-low latency, new client connections go directly to each CPU core. For instance, on clusters with 9 nodes and 64 cores (vCPUs), that’s 500+ connections per client. The number of client processes can also range from a few processes to tens of thousands of processes (in large k8s systems). Then, the effective number of connections can range from tens of thousands to millions. This isn’t a problem in a steady state, but – during topology operations or a customer’s application restart – it could trigger massive surges of new connections.</p>\n<p>While ScyllaDB can handle millions of operations per second without any problem, we couldn’t do the same with connections. Establishing a new connection requires additional work and triggers code paths that can become problematic at scale, as we’ll discuss later.</p>\n<p>Clients could create new connections gradually; this way, no excessive strain would be put on the database. But ScyllaDB needs to handle even cases where clients are not behaving well. Worse, the problem can quickly snowball: a surge bloats the task queues, connections miss their timeouts, and clients retry… which means even more connections and additional pressure on the system. We don’t want to contribute to a cascading failure when graceful startup sequences aren’t implemented or fail for any reason. Moreover, we try to be as fast as possible; deployment changes should not be delayed by the database warming up when it’s not absolutely necessary.</p>\n<p>For all the above reasons, we decided to improve efficiency around connection creation. This led us to investigate and optimize the code on multiple fronts.</p>\n<h2>From TCP SYN to Query-Ready</h2>\n<p>The flow of establishing a new connection looks like this:</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/hardening1.png\"><img src=\"https://www.scylladb.com/wp-content/uploads/hardening1.png\" alt=\"\" srcset=\"https://www.scylladb.com/wp-content/uploads/hardening1.png 1707w, https://www.scylladb.com/wp-content/uploads/hardening1-300x162.png 300w, https://www.scylladb.com/wp-content/uploads/hardening1-1100x593.png 1100w, https://www.scylladb.com/wp-content/uploads/hardening1-768x414.png 768w, https://www.scylladb.com/wp-content/uploads/hardening1-1536x829.png 1536w\"></a></p>\n<p>We introduced improvements at nearly every stage of this process. Each tackles connection load differently:</p>\n<ul>\n<li>Throttling limits how many connections work at once</li>\n<li>Caching removes redundant work</li>\n<li>Hashing makes unavoidable CPU work yield</li>\n<li>A dedicated service level isolates background traffic</li>\n</ul>\n<p>In the next sections, we’ll walk through this pipeline step by step.</p>\n<h2>Connection throttling</h2>\n<p>To fully utilize the CPU, ScyllaDB divides work into tasks, and the CPU scheduler switches between them. Tasks live in queues, from which they are picked for execution. A much more in-depth dive into our CPU scheduler can be found <a target=\"_blank\" href=\"https://www.p99conf.io/session/the-gory-details-of-a-full-featured-userspace-cpu-scheduler/\">in this P99 CONF talk by our co-founder/CTO Avi Kivity</a>.</p>\n<p>When a new connection request arrives, we create a task to handle it. The scheduler gives it some CPU time, then — after it depletes or we need to wait for some I/O – we switch to another task. When many new connections are attempted, units of CPU are sent to the scheduler’s task queue. The scheduler tries to divide the work across time slices, but its task queue is bloated. We strive to fairly progress all connections at once. However, in the end, most of them are not fully established within the timeout. That leads to client retries and even more overload.</p>\n<p>As a first line of defense, we added a connection throttling mechanism. We already had request throttling and shedding, but nothing that controlled connection admission. The main design objective was that it should work automatically; we didn’t want the user to benchmark their system and put some rigid number in the configuration.</p>\n<p>We split new connection work into two states: “CPU” state and “networking” state. A connection is marked as being in a networking state while sending or receiving packets from the driver. And since our bottleneck is CPU, we look at how many connections are in a CPU state when we’re accepting new connections, and we allow only a small fixed number (the default is 8). Although this limit can be configured via the <code>uninitialized_connections_semaphore_cpu_concurrency</code> option in scylla.yaml, we don’t expect that users will need to adjust it.</p>\n<p>In practice, there may be more connections in “CPU” state than this fixed number (because once a connection is admitted, it can switch the states without blocking). Once we spend some CPU on handling the connection, it’s more important to continue with it than to switch focus to some newer connection. This ensures that the system can make progress and we don’t hit timeouts.</p>\n<p>When new connections are waiting over 1 minute to be admitted, we start shedding them. In the end, there is a certain number of new connections we can handle.</p>\n<p>The result is that the system keeps making progress under a storm instead of thrashing across thousands of half-finished handshakes and timing them all out.</p>\n<h2>A unified permissions cache</h2>\n<p>We noticed that, in some cases, the cluster generated ~3k ops/s of internal reads just to refresh the permissions cache. Moreover, role information – which is only needed during connection setup (unlike permissions) – was not cached at all.</p>\n<p>We started with low-hanging fruits. The roles table was queried redundantly because permissions form a tree of inherited grants; to populate a single cache entry, we issued several selects on the roles table. By improving the way inherited roles were gathered, we decreased the load for the roles table by <strong>50%</strong>.</p>\n<p>But there shouldn’t be any load at all; roles and permissions tables are usually very small compared to users’ tables. There is no need to involve the full database query machinery.</p>\n<p>We already had a cache for permissions, but it had several drawbacks. The primary one was that it was based on a periodic refresh of entries. This was causing the internal load mentioned above, together with some unpredictable latency. And our cache didn’t cover per-connection authentication, since it didn’t store the roles table.</p>\n<p>We decided to create a unified cache. A typical problem to tackle with any cache is <em>cache coherence</em>. Luckily, we already solved this when we changed the replication of auth tables to Raft. Writes to those tables are linearized by the Raft consensus protocol, and they are applied in the same order on all nodes. Tapping into this mechanism allowed us to have a coherent, write-updated cache. It also eliminated the need for periodic refresh.</p>\n<p>After the change, the internal load spikes briefly during loading and then disappears completely.</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/hardening2.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/hardening2.png 1145w, https://www.scylladb.com/wp-content/uploads/hardening2-300x159.png 300w, https://www.scylladb.com/wp-content/uploads/hardening2-1100x581.png 1100w, https://www.scylladb.com/wp-content/uploads/hardening2-768x406.png 768w\" src=\"https://www.scylladb.com/wp-content/uploads/hardening2.png\" alt=\"\"></a></p>\n<h2>Making hashing yield</h2>\n<p>For one of our customers, we noticed that node restarts were causing elevated latency for a short period of time.</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/hardening3.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/hardening3.png 924w, https://www.scylladb.com/wp-content/uploads/hardening3-300x75.png 300w, https://www.scylladb.com/wp-content/uploads/hardening3-768x192.png 768w\" src=\"https://www.scylladb.com/wp-content/uploads/hardening3.png\" alt=\"\"></a></p>\n<p>The P95 latency spiked to 5 seconds for around a minute, while the typical latency for this cluster was only 4 milliseconds. We take latency seriously at ScyllaDB, so we had to fix this.</p>\n<p>After investigation, we realized that our next improvement target has to be password hashing. The CQL protocol has this odd property that, during connection authentication, passwords are sent and hashed on the server side. We can’t cache hashing because we don’t want to store raw passwords in memory for security reasons.</p>\n<p>The problem wasn’t CPU usage by itself, but rather how it was allocated. ScyllaDB uses futures-based execution with cooperative scheduling. This allows us to write asynchronous code easily. Typically, yield points are triggered by an IO operation. But when CPU-intensive code (such as hashing) runs, we need to manually insert yield points into the code. Otherwise, the scheduler can’t fairly switch CPU execution to other tasks, hence elevated request latency. Unfortunately, we can’t do that easily: we use libcrypt, an external library.</p>\n<p>Maintaining our own hashing function in such a security-sensitive context is not something we were keen on doing. Initially, we tried to use something we call an alien thread. It’s a standard OS thread where execution is subject to preemptive scheduling. We decided to have a single thread per instance. Otherwise, we’d proportionally decrease OS time for our own internal scheduler, defeating its purpose. But the cure was worse than the disease. In our tests with just 10 CPUs, we reduced connection-per-shard rates 6X. And on larger nodes, the decline would be even bigger.</p>\n<p>Our second solution was to fork hashing code from the musl library and then add yield points. This is a middle ground between writing our own hashing code and an ineffective attempt to use library code without modifications.</p>\n<p>Connections per second per shard were measured as follows:</p>\n<table>\n<tbody>\n<tr>\n<th>Configuration</th>\n<th>Rate</th>\n</tr>\n<tr>\n<td>Initially</td>\n<td>244 conns/s</td>\n</tr>\n<tr>\n<td>Alien thread</td>\n<td>41 conns/s</td>\n</tr>\n<tr>\n<td>Modified musl</td>\n<td>198 conns/s</td>\n</tr>\n</tbody>\n</table>\n<p>We sacrificed around <strong>20%</strong> of the hashing speed, since musl is less efficient than libcrypt. It impacted only our connection rate, not our request throughput. That’s an easy trade to kill a multi-second latency cliff.</p>\n<h2>Isolating startup traffic</h2>\n<p>ScyllaDB has a workload prioritization feature where multiple workloads can be isolated so they don’t affect one another’s performance. More information about it can be found <a target=\"_blank\" href=\"https://docs.scylladb.com/manual/stable/features/workload-prioritization.html\">here in the documentation</a>. But, as described in the <em>From TCP SYN to Query-Ready</em> section, service level assignment happens quite late during connection establishment. It needs an authenticated role to find an appropriate service level.&#160; Any work done before that runs with the main scheduling group and can compete with user workloads.</p>\n<p>Moreover, each driver instance keeps a control connection for tracking schema changes, topology, heartbeats, etc. Historically, such work was done in the main scheduling group. With the default setup, it could affect user workloads. That’s why we introduced a new driver service level that has reduced the number of shares. This service level is automatically selected at connection startup and then switched to the appropriate level once it is known.</p>\n<p>Our synthetic tests showed that, during heavy connection storms, this change alone reduced the maximum latency of CQL requests from <strong>225</strong> ms to <strong>41</strong> ms.</p>\n<h2>Benchmarking</h2>\n<p>We measured the performance gains at two levels: targeted micro-benchmarks that stress individual parts of the implementation, and cluster-wide load tests for the final result.</p>\n<p>Here is the impact of just the cache optimizations:</p>\n<table>\n<tbody>\n<tr>\n<th>Metric</th>\n<th>BEFORE new cache</th>\n<th>AFTER new cache</th>\n<th>Delta</th>\n</tr>\n<tr>\n<td>Instructions / Conn</td>\n<td>4,226,658</td>\n<td>3,861,944</td>\n<td>-8.63%</td>\n</tr>\n<tr>\n<td>Allocs / Conn</td>\n<td>~407.0</td>\n<td>~182.5</td>\n<td><strong>-55.16%</strong></td>\n</tr>\n<tr>\n<td>Tasks / Conn</td>\n<td>~139.3</td>\n<td>~82.0</td>\n<td><strong>-41.13%</strong></td>\n</tr>\n</tbody>\n</table>\n<p>This benchmark runs a single ScyllaDB node and then floods it with connections. For each connection, it performs a CQL startup sequence (including authentication), and then closes the connection.</p>\n<p>We see that stress caused by connection storms to the memory subsystem is reduced by half, and stress to task queues was reduced by almost half.</p>\n<p>The following charts show the final result of <em>all</em> the improvements to mitigate connection storm impact on the cluster:</p>\n<p>Before&#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160; &#160;After</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/hardening4.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/hardening4.png 1302w, https://www.scylladb.com/wp-content/uploads/hardening4-300x87.png 300w, https://www.scylladb.com/wp-content/uploads/hardening4-1100x320.png 1100w, https://www.scylladb.com/wp-content/uploads/hardening4-768x224.png 768w\" src=\"https://www.scylladb.com/wp-content/uploads/hardening4.png\" alt=\"\"></a><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/hardening5.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/hardening5.png 1302w, https://www.scylladb.com/wp-content/uploads/hardening5-300x87.png 300w, https://www.scylladb.com/wp-content/uploads/hardening5-1100x320.png 1100w, https://www.scylladb.com/wp-content/uploads/hardening5-768x224.png 768w\" src=\"https://www.scylladb.com/wp-content/uploads/hardening5.png\" alt=\"\"></a></p>\n<p>Here, we evaluated ScyllaDB’s ability to maintain availability and performance during a node restart under sustained, production-like load. The benchmark was conducted on a nine-node cluster of i4i.2xlarge instances deployed in a single availability zone and distributed across three racks, with a replication factor of three. To simulate a demanding client workload, 20 c7i.2xlarge loader instances generated approximately 380,000 concurrent connections—around 6,000 per shard. The load was 74,000 read operations per second and 12,000 write operations per second. Client request timeout was set to 10 seconds, connection timeout to 11 seconds, and control connection timeout to 6 seconds.</p>\n<p>Prior to the benchmark, the cluster was populated with approximately 65 GB of data. The workload was then executed continuously for 10 minutes, after which one randomly selected node was restarted while the load remained active, allowing us to observe the cluster’s behavior and recovery characteristics during a node restart.</p>\n<p>The red lines denote the time the node was restarting; since all the driver instances need to reconnect, this is a common case which causes connection storms. Latency is now <strong>1000x</strong> lower than it was before, making the impact of new connections barely visible to the cluster.</p>\n<h2>Add it to your ScyllaDB deployment</h2>\n<p>Our goal is simple: you should be able to focus on your application logic, not on babysitting database connection parameters. With these changes, you should be able to deploy and restart with confidence, knowing that your cluster is designed to handle traffic spikes gracefully.</p>\n<p>All these improvements are in the new 2026.2 release; we strongly encourage you to upgrade and share how it’s working in your environment.</p>\n                    </div>"
