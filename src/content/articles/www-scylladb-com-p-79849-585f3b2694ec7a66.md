contentHtml: "<div>\r\n                        <p><strong>We moved I/O off application cores to dedicated cores to give compute-heavy workloads more breathing room</strong></p>\n<p>Modern high-throughput systems often run on machines with many cores. At that scale, one practical problem becomes increasingly visible: CPU time spent on low-level I/O handling competes directly with CPU time needed for application-level work.</p>\n<p>In this post, we explore how shifting more I/O related work away from cores focused on computations onto a dedicated subset of cores can improve the overall balance of the system. Specifically, we share how we approached <a target=\"_blank\" href=\"https://github.com/scylladb/seastar\">Seastar</a>‘s new <code>asymmetric_io_uring</code> backend: the design decisions behind it, what it aims to free up on application cores, and how it compares to <a target=\"_blank\" href=\"https://man7.org/linux/man-pages/man7/aio.7.html\">linux-aio</a> (Seastar’s existing backend).</p>\n<h3>Seastar’s Shared-Nothing Architecture</h3>\n<p>Seastar – the open source C++ framework that underpins high-performance distributed systems like ScyllaDB, Redpanda, and Ceph Crimson – is built from the ground up around a <strong>shared-nothing architecture</strong>.</p>\n<p>To maximize multi-core performance, it usually spawns a single thread (referred to as a <strong>shard</strong>) per application core. Each shard runs its own cooperative scheduler (the reactor) managing lightweight tasks and fibers, and owns its memory and data structures. This eliminates the need for expensive cross-shard locking and atomic operations. Explicit message passing relies on inter-shard communication instead.</p>\n<h3>How the Symmetric reactor_backend_uring Works</h3>\n<p>In the existing symmetric <code>io_uring</code> backend, every shard initializes its own private <code>io_uring</code> instance. The reactor loop is structured to perform computations first and then invoke pollers to check for I/O events.</p>\n<p>To optimize performance, this symmetric model implements a heuristic-based <strong>fast track</strong> for networking I/O. When a shard initiates a read or write on a network socket, the backend checks speculation flags. If the socket is speculated to be ready (i.e., we expect the operation to be non-blocking), the shard executes a synchronous system call directly on its own core (bypassing the <code>io_uring</code> submission path). If the speculation fails or the socket blocks, it falls back to the <strong>slow track </strong>(submitting the operation to <code>io_uring</code>).</p>\n<p>This design forces application cores to divide their time between running high-level application logic and executing low-level synchronous I/O system calls, resulting in:</p>\n<ul>\n<li>Context switching overhead between user space and kernel space.</li>\n<li>Cache pollution on application cores due to kernel-level I/O processing.</li>\n<li>Higher latency variance and potential scheduler preemption.</li>\n</ul>\n<h3>What Are Networking Cores?</h3>\n<p>On systems optimized with Seastar’s tuning script (<code>perftune.py</code>), CPUs can be partitioned into <strong>application cores</strong> (where Seastar shards run) and <strong>networking cores</strong> (also known as IRQ cores). This is because modern servers often have more CPUs than hardware queues on network interface cards. The goal of this partitioning is to only allow a subset of cores to handle these queues – to eliminate a situation when multiple cores compete for a single queue.</p>\n<p>Using the script, network interface card (NIC) hardware interrupts (IRQs) are routed exclusively to the networking cores. This ensures that application cores are not disturbed by high-priority hardware interrupts and SoftIRQ processing of incoming packets. This however causes the networking stack to run on multiple cores: the application cores (processing syscalls and outgoing packets) and the networking cores (processing interrupts and incoming packets). No application shards are spawned on these networking cores.</p>\n<h3>The Challenge: Offloading More I/O to Networking Cores</h3>\n<p>Since the system already contains dedicated networking cores that handle “some part of I/O” (NIC IRQs) and do not run any user-level application shards, we wondered: <em>What if we give them more of the I/O workload?</em></p>\n<p>By utilizing <code>io_uring</code> features like Submission Queue (SQ) polling and kernel worker thread affinity, we can offload the entire asynchronous I/O execution pipeline to these underutilized networking cores. The compute-bound application shards would simply place requests on their submission queues without making synchronous system calls, while kernel workers and polling threads pinned to the networking cores process the requests. This asymmetry promises to offload application cores, improving computation throughput and cache locality.</p>\n<p>Additionally, we explore the usage of other features in order to improve performance. For example, we utilize kernel worker sharing. Furthermore, we investigate the possibility of utilizing buffer rings along with each request split into a linked chain of smaller requests.</p>\n<p><strong>Note:</strong> If you are not yet familiar with <code>io_uring</code>, see the explanation in the Appendix.</p>\n<h2>Designing the Architecture</h2>\n<p>Now that we know <em>why</em> we want an asymmetric backend, let’s talk about <em>how </em>such a backend works. At first, we looked at the big picture — the architecture of our solution.</p>\n<h3>Dividing Cores into Groups</h3>\n<p>Because application cores typically outnumber the available networking cores, we decided to organize application cores into groups. Each group is assigned to a dedicated networking core that handles all I/O operations for the shards in that group. Each group operates independently. Kernel workers and polling threads pinned to a group’s networking core only process I/O from shards within that group.</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/image4-21.png\"><img src=\"https://www.scylladb.com/wp-content/uploads/image4-21.png\" alt=\"\" srcset=\"https://www.scylladb.com/wp-content/uploads/image4-21.png 1992w, https://www.scylladb.com/wp-content/uploads/image4-21-300x111.png 300w, https://www.scylladb.com/wp-content/uploads/image4-21-1100x406.png 1100w, https://www.scylladb.com/wp-content/uploads/image4-21-768x284.png 768w, https://www.scylladb.com/wp-content/uploads/image4-21-1536x568.png 1536w\"></a></p>\n<p>When designing this group-based architecture, we evaluated three potential approaches:</p>\n<ul>\n<li>Master/proxy shards via <code>smp::submit_to</code></li>\n<li>Shared <code>io_uring</code> instance per group</li>\n<li><code>io_uring</code> instance per shard</li>\n</ul>\n<h3>Option 1: Master/Proxy Shards via smp::submit_to</h3>\n<p>This design designates one <strong>master shard</strong> per group with direct, exclusive access to a local <code>io_uring</code> instance. The remaining shards in the group act as <strong>proxy shards</strong>. When a proxy shard needs to execute a network I/O operation, it uses Seastar’s inter-shard message-passing functionality (<code>smp::submit_to</code>) to submit the request to the master shard. The master shard places the request onto its <code>io_uring</code> submission queue, reaps the completion events from the kernel, and resolves the appropriate future.</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/image2-28.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/image2-28.png 1746w, https://www.scylladb.com/wp-content/uploads/image2-28-256x300.png 256w, https://www.scylladb.com/wp-content/uploads/image2-28-938x1100.png 938w, https://www.scylladb.com/wp-content/uploads/image2-28-768x901.png 768w, https://www.scylladb.com/wp-content/uploads/image2-28-1310x1536.png 1310w\" src=\"https://www.scylladb.com/wp-content/uploads/image2-28.png\" alt=\"\"></a></p>\n<ul>\n<li><strong>Benefits</strong>: Straightforward implementation. Only one shard ever directly interacts with the <code>io_uring</code> instance.</li>\n<li><strong>Drawbacks</strong>: The performance cost of <code>smp::submit_to</code> is unacceptable, as it relies on polling and can take up to several milliseconds to complete.</li>\n</ul>\n<h3>Option 2: Shared io_uring Instance per Group</h3>\n<p>The second alternative we evaluated was to share a single <code>io_uring</code> instance among all shards in a CPU group. Shards would concurrently submit requests to the same queue and reap completion events from the same completion queue.</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/io_uring2.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/io_uring2.png 2048w, https://www.scylladb.com/wp-content/uploads/io_uring2-300x225.png 300w, https://www.scylladb.com/wp-content/uploads/io_uring2-1100x827.png 1100w, https://www.scylladb.com/wp-content/uploads/io_uring2-768x577.png 768w, https://www.scylladb.com/wp-content/uploads/io_uring2-1536x1154.png 1536w\" src=\"https://www.scylladb.com/wp-content/uploads/io_uring2.png\" alt=\"\"></a></p>\n<ul>\n<li><strong>Benefits</strong>: Eliminates the inter-shard message-passing overhead of the master/proxy model. Potentially minimizes the number of syscalls, as SQEs from multiple shards can be submitted by a single syscall.</li>\n<li><strong>Drawbacks</strong>: Because <code>liburing</code> is not thread-safe, access to the shared instance requires synchronization. Introducing mutexes or other lock mechanisms would lead to high contention. That would end up violating Seastar’s shared-nothing philosophy and hurting performance. A lock-free mechanism was deemed technically unfeasible.</li>\n</ul>\n<h3>Option 3: io_uring Instance per Shard</h3>\n<p>To combine the performance of direct queue access with Seastar’s lock-free design, we chose a model where <strong>each shard maintains its own private </strong><strong><code>io_uring</code></strong><strong> instance</strong>. Each shard has exclusive access to its ring, avoiding any user-space synchronization or inter-shard message passing.</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/image3-26.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/image3-26.png 2048w, https://www.scylladb.com/wp-content/uploads/image3-26-300x225.png 300w, https://www.scylladb.com/wp-content/uploads/image3-26-1100x827.png 1100w, https://www.scylladb.com/wp-content/uploads/image3-26-768x577.png 768w, https://www.scylladb.com/wp-content/uploads/image3-26-1536x1154.png 1536w\" src=\"https://www.scylladb.com/wp-content/uploads/image3-26.png\" alt=\"\"></a></p>\n<p>To prevent spawning a redundant pool of kernel worker threads for each shard – which would overload the networking cores and lead to CPU contention – we share worker pools:</p>\n<ol>\n<li><strong>Shared Worker Pools</strong>: We initialize a <strong>master </strong><strong><code>io_uring</code></strong><strong> instance</strong> for each networking core and register its kernel worker thread affinity using <code>io_uring_register_iowq_aff</code>. The remaining shards in the group initialize <strong>proxy </strong><strong><code>io_uring</code></strong><strong> instances</strong> using the <code>IORING_SETUP_ATTACH_WQ</code> flag, passing the file descriptor of the master instance. This makes the kernel attach the proxy rings to the master ring’s thread pool, sharing the same worker threads.</li>\n<li><strong>Shared Polling</strong>: By using the <code>IORING_SETUP_ATTACH_WQ</code> flag, we also share the kernel submission queue polling thread (<code>SQPOLL</code>) of the master ring with all attached proxy rings. A single kernel thread pinned to the networking core polls submissions for the entire group.</li>\n</ol>\n<p>This approach successfully achieves asymmetric offloading while preserving Seastar’s shared-nothing design. It moves all sharing logic to the kernel level, where it can be handled efficiently.</p>\n<h3>Why the Fast-Track Had to Go</h3>\n<p>In Seastar’s existing symmetric <code>io_uring</code> backend, a <strong>fast track</strong> speculation path is used to optimize networking I/O. If a socket is expected to be ready (non-blocking), the shard bypasses <code>io_uring</code> entirely and executes a synchronous system call directly on its own core.</p>\n<p>While this is effective in a symmetric model, it is counterproductive for our asymmetric architecture. If application shards continue executing synchronous I/O system calls directly, it defeats the purpose of offloading I/O to networking cores.</p>\n<p>To guarantee that all low-level I/O is executed by the networking cores, we removed the fast-track speculation from our asymmetric backend. This ensures that all networking I/O operations are done exclusively through the <code>io_uring</code> submission queue.</p>\n<h2>Implementation</h2>\n<h3>NUMA and SMT</h3>\n<p>Modern multi-core servers often utilize <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Non-uniform_memory_access\"><strong>Non-Uniform Memory Access (NUMA)</strong></a> and <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Simultaneous_multithreading\"><strong>Simultaneous Multithreading (SMT)</strong></a> architectures. In NUMA systems, memory is partitioned into nodes; accessing memory local to a node is significantly faster than traversing an interconnect to a remote node. In SMT systems (such as <a target=\"_blank\" href=\"https://en.wikipedia.org/wiki/Hyper-threading\">Intel’s Hyper-Threading</a>), logical sibling cores share physical resources and low-level caches.</p>\n<p>Because shards and their offloaded <code>io_uring</code> kernel threads must frequently exchange data through shared ring buffers, the physical topology of where threads are pinned may have an impact on cache coherence and memory latency. Our asymmetric backend addresses this by employing a topology-aware worker allocation algorithm.</p>\n<h3>The NUMA-Aware Allocation Algorithm</h3>\n<p><strong>Topology Detection</strong>: The backend uses the <a target=\"_blank\" href=\"https://www.open-mpi.org/projects/hwloc/\"><strong>Portable Hardware Locality (hwloc)</strong></a> library to discover the layout of NUMA nodes, physical cores, and SMT siblings. If <code>hwloc</code> is not available, the backend automatically falls back to a topology-agnostic greedy round-robin assignment.</p>\n<p><strong>Three-Pass Greedy Assignment</strong>: The backend maps the available worker cores (provided via <code>--async-workers-cpuset</code>) to the application shards using a three-pass greedy process:</p>\n<ul>\n<li><strong>Pass 1 (SMT Siblings)</strong>: First, it assigns worker cores to shards running on application cores that are direct SMT siblings of those worker cores. This maximizes cache sharing at the physical core level.</li>\n<li><strong>Pass 2 (NUMA Locality)</strong>: Next, it assigns worker cores to shards residing within the same NUMA node. To distribute load evenly, it greedily assigns each unassigned shard to the least loaded worker core (the one with the fewest shards assigned) in that NUMA node.</li>\n<li><strong>Pass 3 (Cross-NUMA Node)</strong>: Finally, for any shards that do not have any worker cores in their own NUMA node, it greedily assigns them to the least loaded worker core in other nodes.</li>\n</ul>\n<h3>Buffer Rings</h3>\n<p>Buffer rings are a newer alternative to the provided buffers mechanism of <code>io_uring</code>. They allow the user to pre-register a pool of buffers, which will be later used when completing operations. Utilizing buffer rings provided a possible avenue for improvement; consequently, we attempted to integrate them into our backend.</p>\n<p>We considered the following approaches for adding buffer rings:</p>\n<ul>\n<li>fixed-size buffer ring</li>\n<li>splitting operations into smaller, linked chunks with <code>IOSQE_IO_LINK</code></li>\n<li>splitting operations to cover multiple buffers with <code>IORING_RECVSEND_BUNDLE</code></li>\n<li>differently sized buffer pools</li>\n</ul>\n<p>While none of them were selected for our implementation, buffer rings remain a possible future improvement for the asymmetric backend.</p>\n<h4>Fixed-Size Buffer Ring</h4>\n<p>In this approach, operations prioritize using a pre-allocated buffer from a buffer ring, if possible.</p>\n<p>The size of the buffer ring – as well as the size of the buffers in the buffer ring – are chosen with command line options.</p>\n<p>We considered both variants with and without additional runtime allocations.</p>\n<h4><code>IOSQE_IO_LINK</code></h4>\n<p>In this approach, we allocate a single buffer ring with many 8kB buffers. Larger operations are split into a number of smaller 8kB buffers. The resulting operations are linked together with <code>IOSQE_IO_LINK</code>. All but the first <code>SQE</code> in the chain have <code>MSG_DONTWAIT</code>, which makes them fail if they cannot be instantly executed.</p>\n<p>When using buffer rings, buffers from the pool are only assigned to an operation when necessary. As a result, smaller operations will only take as many 8kB buffers as needed.</p>\n<p>At the same time, larger operations can still be handled. For example, a 128kB operation can be executed in a single reactor loop. It would be split into sixteen 8kB completions.</p>\n<h4><code>IORING_RECVSEND_BUNDLE</code></h4>\n<p>This approach is similar to the one utilizing <code>IOSQE_IO_LINK</code>. However, instead of linking multiple operations together, only one would be issued. The operations could utilize multiple buffers from the buffer rings. At the same time, this approach significantly reduces the overhead related to issuing multiple requests per operation and linking them.</p>\n<h4>Differently Sized Buffer Pools</h4>\n<p>This approach is similar to the first one. However, instead of maintaining one buffer ring with fixed size buffers, we maintain multiple, each one with buffers doubling in size. The buffer ring that an operation uses would be determined by how much the previous operation on the same descriptor filled the previously assigned buffer size. This reduces wasted buffer space by better adjusting to a given operation’s characteristics.</p>\n<h4>Summary of the Buffer Ring Options</h4>\n<p>All of the aforementioned approaches offer unique advantages and disadvantages. While each approach might be better than the others in some aspects, each also has some notable drawbacks. Risk of buffer exhaustion</td>\n</tr>\n</tbody>\n</table>\n<h4>Implementation Issues</h4>\n<p>After careful consideration of how buffer rings would need to be integrated into Seastar, we decided that their use is outside the scope of this project. The way that Seastar handles buffer allocation is not compatible with a reactor-backend managed buffer pool for operations and would require larger architecture changes. For the project, it was more important to comprehensively test the performance and correctness of the solution than to possibly integrate buffer rings. However, buffer rings remain a possible future enhancement.</p>\n<h2>Benchmarking</h2>\n<p>When the backend was ready, we proceeded with benchmarks. We evaluated disk I/O and networking I/O separately, as their internal implementation differs.</p>\n<h3>Networking</h3>\n<p>Evaluations were run on the AWS EC2 <a target=\"_blank\" href=\"https://aws.amazon.com/ec2/instance-types/c8g/\">c8gn.4xlarge</a> instances, primarily for their</p>\n<p>advanced networking capabilities. As specified by AWS, these 16-vCPU instances deliver up to 50 Gbps of network bandwidth.</p>\n<p>We used <em>rpc_tester</em> for benchmarking purposes. The client side used&#160; the<code>linux-aio</code> backend with 7/8 shards, where the server used either the <code>linux-aio</code> or <code>asymmetric_io_uring</code> backend with N shards and 1 networking core.</p>\n<p>The client was stressing the server. 2000 fibers were run on each shard, each sending data in a loop in a request-response manner. In each fiber, it sent a fixed-sized message, waited for the response, and looped – all using <em>RPC</em> API.</p>\n<p>The server was just handling the connections, while sometimes performing computations during request processing. This will be explained on the first use.</p>\n<p><strong>Spoiler:</strong> During our work with rpc_tester, we extended its capabilities by implementing an RPC streaming mechanism. Throughout this implementation process, we uncovered a subtle race condition within the framework. A detailed analysis of this bug is documented in Appendix B.</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/image16-2.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/image16-2.png 632w, https://www.scylladb.com/wp-content/uploads/image16-2-215x300.png 215w\" src=\"https://www.scylladb.com/wp-content/uploads/image16-2.png\" alt=\"\"></a></p>\n<h4>Server with 1 Shard</h4>\n<p>In this test, the server was running with a single shard. This was a really optimistic start for the benchmarks.</p>\n<p>The results show that the <code>asymmetric_io_uring</code> backend outperforms the <code>linux-aio</code> one in terms of throughput by around 15%. Each bar is a result measured separately on a different client shard.<a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/image28.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/image28.png 700w, https://www.scylladb.com/wp-content/uploads/image28-300x214.png 300w\" src=\"https://www.scylladb.com/wp-content/uploads/image28.png\" alt=\"\"></a></p>\n<p><em>Throughput ([B/s]) for server with 1 shard</em></p>\n<p>Additionally, the latencies look really promising. p50 latencies show a non-negligible improvement (lower is better).<a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/image20-2.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/image20-2.png 700w, https://www.scylladb.com/wp-content/uploads/image20-2-300x214.png 300w\" src=\"https://www.scylladb.com/wp-content/uploads/image20-2.png\" alt=\"\"></a><em>p0.5 latency ([usec]) for server with 1 shard</em></p>\n<h4>Server with 4 Shards</h4>\n<p>With the increasing number of shards, results become less favorable for the new backend.<a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/image18-2.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/image18-2.png 700w, https://www.scylladb.com/wp-content/uploads/image18-2-300x214.png 300w\" src=\"https://www.scylladb.com/wp-content/uploads/image18-2.png\" alt=\"\"></a></p>\n<p><em>Throughput ([B/s]) for server with 4 shards</em></p>\n<p>Unfortunately, in this scenario the new <code>asymmetric_io_uring</code> backend seems unable to achieve as high throughput as <code>linux-aio</code>. Let’s find out why.</p>\n<p>For our investigation, we used <a target=\"_blank\" href=\"https://perfwiki.github.io/main/\"><em>perf</em></a>, which is a Linux tool for profiling. We re-ran the server side with the tool profiling, which gave us powerful insights. It turns out that the single networking core spends around 40-50% of its cycles on memory copying. This is the necessary buffer copying that the Linux kernel performs while handling I/O related operations.</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/image29.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/image29-1092x1100.png 1092w, https://www.scylladb.com/wp-content/uploads/image29-298x300.png 298w, https://www.scylladb.com/wp-content/uploads/image29-150x150.png 150w, https://www.scylladb.com/wp-content/uploads/image29-768x773.png 768w, https://www.scylladb.com/wp-content/uploads/image29-1525x1536.png 1525w, https://www.scylladb.com/wp-content/uploads/image29.png 1678w\" src=\"https://www.scylladb.com/wp-content/uploads/image29-1092x1100.png\" alt=\"\"></a></p>\n<p><em>Output from perf showing lots of memory copying on the network core</em></p>\n<p>The networking core becoming the bottleneck was bad news. Previously, all the memory copying was distributed mostly among the application cores during syscalls for performing the operations. Now, the amount of data to be copied exhausts the <em>sq_poll</em> thread capabilities.</p>\n<h4>Let’s Add Artificial Processing</h4>\n<p>We learned that the backend is bound in the pure I/O workflows. However, applications like ScyllaDB – apart from doing I/O – perform computations or await different operations. To simulate this, the artificial processing was added to the request’s processing pipeline on the server side. When the server receives the message, it busy-loops for a set amount of time before responding.</p>\n<p><strong>Spoiler</strong>: If your workload does more than a few microseconds of compute per request alongside network I/O — and you’re running roughly multiple application cores per networking core — then strongly consider benchmarking this against your current setup.</p>\n<p>We evaluated different compute times: <em>1, 2, … μs</em>. At intervals of <em>1, 2, 4 μs,</em> the <code>asymmetric_io_uring</code> backend consistently outperformed <code>linux-aio</code>. At a delay of <em>8 μs</em> or higher, the performance delta converged within the standard error margin, reducing statistical variance between the two backends.</p>\n<p>Under these simulated conditions, with the compute time <em>2 </em><em>μs</em>, the <code>asymmetric_io_uring</code> backend provides an advantage in terms of throughput and latencies.</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/image27.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/image27.png 700w, https://www.scylladb.com/wp-content/uploads/image27-300x214.png 300w\" src=\"https://www.scylladb.com/wp-content/uploads/image27.png\" alt=\"\"></a><em>Throughput ([B/s]) for server with 4 shards and 2 usec of request processing time</em><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/image33.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/image33.png 700w, https://www.scylladb.com/wp-content/uploads/image33-300x214.png 300w\" src=\"https://www.scylladb.com/wp-content/uploads/image33.png\" alt=\"\"></a></p>\n<p><em>p0.5 latency ([usec]) for server with 4 shards and 2 usec of request processing time</em></p>\n<h4>Server with 7 Shards</h4>\n<p>Usually, the ratio between the application cores and networking cores is 7:1. Pass the <code>--enable-io_uring</code> flag during configuration:</p>\n<pre><code>./configure.py --enable-io_uring [other compilation options]</code></pre>\n<h3>Tuning</h3>\n<p>To get the full performance benefits of the asymmetric architecture, it is essential to align the <code>io_uring</code> worker cores with the system’s NIC interrupt handling. This is done using Seastar’s <code>perftune.py</code> script. Run the script with network tuning enabled. You can specify a custom ratio for auto-detecting the number of IRQ cores:</p>\n<pre><code>sudo ./scripts/perftune.py --tune net --nic ens5 --irq-core-auto-detection-ratio <span>8</span></code></pre>\n<p><em>(In this example, an auto-detection ratio of 8 allocates 1 networking core for every 7 application cores).</em></p>\n<h3>Running</h3>\n<p>To run a Seastar application with the asymmetric backend, select the backend and define the CPU set reserved for the async kernel workers:</p>\n<pre><code>./your_seastar_app --reactor-backend=asymmetric_io_uring --async-workers-cpuset=<span>14-15</span></code></pre>\n<ul>\n<li><code>--reactor-backend=asymmetric_io_uring</code>: Selects the asymmetric backend.</li>\n<li><code>--async-workers-cpuset</code>: Specifies the cores dedicated to <code>io_uring</code> workers and pollers. <strong>This option is mandatory when using this backend.</strong></li>\n</ul>\n<h3>Tips</h3>\n<ul>\n<li><strong>Use Automatic Taskset Calculation</strong>: You can use <code>taskset</code> to select all the cores you want to dedicate to it (both application and networking cores) and specify which of them should be <code>io_uring</code> workers with <code>--async-workers-cpuset</code>. For example:</li>\n</ul>\n<pre><code>taskset -c <span>0-15 </span>./your_seastar_app --reactor-backend=asymmetric_io_uring --async-workers-cpuset=<span>14-15</span></code></pre>\n<p>Under this configuration, Seastar resolves the worker cores as <code>14-15</code> and automatically spawns the compute shards on the remaining set (<code>0-13</code>), avoiding resource contention.</p>\n<ul>\n<li><strong>Manual Core Selection</strong>: If you want to manually select the set of application cores (with <code>--cpuset</code>), ensure it does not overlap with the <code>--async-workers-cpuset</code>.</li>\n</ul>\n<h2>Summary</h2>\n<h3>Pros and Cons of the Asymmetric Backend</h3>\n<p>Like any architectural decision, the asymmetric backend comes with trade-offs:</p>\n<ul>\n<li><strong>Pros</strong>:\n<ul>\n<li><strong>Core Isolation</strong>: Reclaims valuable CPU cycles on application shards by offloading the entire networking I/O to dedicated networking cores.</li>\n<li><strong>Improved Latency Consistency</strong>: Minimizes scheduler preemption and context switches on application shards, resulting in more predictable latency under hybrid compute-and-I/O workloads.</li>\n</ul>\n</li>\n<li><strong>Cons</strong>:\n<ul>\n<li><strong>No Direct I/O-Bound Speedup</strong>: In purely I/O-bound benchmarks, the asymmetric backend does not outperform the traditional <code>linux-aio</code> backend.</li>\n<li><strong>Memory Copying Bottleneck</strong>: The networking cores spend a significant amount of execution time copying data between kernel and user space (via <code>copy_to_user</code>). Without a zero-copy receive pipeline, the benefits of avoiding system calls are partially mitigated by memory transfer overhead.</li>\n</ul>\n</li>\n</ul>\n<h3>Current Status</h3>\n<p>The core asymmetric backend has been successfully merged into the official Seastar repository.</p>\n<p>We highly recommend testing the asymmetric backend on your own workloads – especially those with significant compute requirements combined with high-throughput networking – to see how much compute capacity can be recovered on your application shards.</p>\n<h3>Useful Links</h3>\n<p>For more details on the implementation, benchmarking tools, and the development process, check out the following resources:</p>\n<ul>\n<li><strong>Asymmetric Backend Pull Request</strong>:<a target=\"_blank\" href=\"https://github.com/scylladb/seastar/pull/3297\"> Seastar PR #3297</a></li>\n<li><strong>NUMA and SMT (HT) Awareness Pull Request</strong>:<a target=\"_blank\" href=\"https://github.com/scylladb/seastar/pull/3405\"> Seastar PR #3405</a></li>\n<li><strong>Contributions to </strong><strong><code>rpc_tester</code></strong>:\n<ul>\n<li><a target=\"_blank\" href=\"https://github.com/scylladb/seastar/pull/3173\">Streaming API Job Type (PR #3173)</a></li>\n<li><a target=\"_blank\" href=\"https://github.com/scylladb/seastar/pull/3358\">Throughput &amp; Metric Exposure (PR #3358)</a></li>\n</ul>\n</li>\n<li><strong>Benchmarking &amp; Visualizer Tools</strong>:\n<ul>\n<li><a target=\"_blank\" href=\"https://github.com/zpp-2025-io-uring/visualizer-script\">`visualizer-script` Repository</a></li>\n<li><a target=\"_blank\" href=\"https://github.com/zpp-2025-io-uring/visualizer-remote\">`visualizer-remote` Repository</a></li>\n</ul>\n</li>\n</ul>\n<h2>Appendix A – io_uring</h2>\n<h3>What Is <code>io_uring</code>?</h3>\n<p><code>io_uring</code> is a Linux-specific interface for scheduling asynchronous I/O operations. It shares memory between the userspace and the kernel to create two cyclic buffers – the <code>Submission Queue</code> (<code>SQ</code>) and the <code>Completion Queue</code> (<code>CQ</code>). The application initiates an operation by placing a <code>Submission Queue Entry</code> (<code>SQE</code>) into the <code>SQ</code>. Afterwards, the kernel executes entries pending in the <code>SQ</code> and places <code>Completion Queue Entries</code> (<code>CQE</code>) into the <code>CQ</code>. By default, <code>io_uring</code> does not have to execute operations in the order that they were scheduled.</p>\n<p><code>io_uring</code> is a low-level interface, but <strong>liburing</strong> provides a higher-level abstraction.</p>\n<h3><code>io_uring</code> Features</h3>\n<p>Apart from its basic form of operations, <code>io_uring</code> has several more advanced features that open the door to optimizations.</p>\n<p>For example:</p>\n<ul>\n<li>Kernel side polling</li>\n<li>Configuring kernel worker CPU affinity</li>\n<li>Attaching <code>io_uring</code> instances</li>\n<li>Provided buffers</li>\n<li>Operation ordering</li>\n</ul>\n<p>Let’s analyze each one in more detail.</p>\n<h4>Kernel Side Polling</h4>\n<p>By default, adding an SQE to the SQ doesn’t trigger kernel processing. The application must issue an io_uring_enter syscall to notify the kernel.</p>\n<p>Despite being an improvement over regular I/O handling (where each I/O operation is a separate syscall), the performance implications are not negligible. Context switches are computationally expensive.</p>\n<p>io_uring offers a different mode of operation: kernel side <code>Submission Queue</code> polling (<code>SQPOLL</code>). It can be enabled by setting the <code>IORING_SETUP_SQPOLL</code> flag during <code>io_uring</code> creation.</p>\n<p>When configured in this way, the kernel creates a dedicated kernel thread which polls the io_uring for new entries. Instead of a system call, SQPOLL only requires modifying atomic variables to inform the kernel of new submissions.</p>\n<p>When creating an <code>io_uring</code> instance with the <code>IORING_SETUP_SQPOLL</code> flag, the <code>sq_thread_idle</code> should also be specified. It dictates after what amount of time the poller thread goes to sleep and has to be woken up with a system call.</p>\n<p>Additionally, by specifying the <code>IORING_SETUP_SQ_AFF</code> flag and the <code>sq_thread_cpu</code> field, the user can define on which CPU the kernel polling thread should operate.</p>\n<h4>Configuring Kernel Worker CPU Affinity</h4>\n<p>Some of the operations that can be scheduled with <code>io_uring</code> require instantiating a separate kernel thread to complete. Similarly to the kernel polling thread, the CPU affinity of these worker threads can be controlled. This can be achieved with <code>io_uring_register_iowq_aff</code>, which accepts a cpu set to which it should limit the kernel worker affinity.</p>\n<h4>Attaching io_uring Instances</h4>\n<p>If an application has several <code>io_uring</code> instances, it can combine them with <code>IORING_SETUP_ATTACH_WQ</code> during creation. This results in sharing kernel worker and poller threads (if kernel side <code>SQ</code> polling is used). By doing so, kernel threads from separate <code>io_uring</code> instances no longer compete for CPU time, thus potentially improving performance.</p>\n<h4>Provided Buffers</h4>\n<p>Instead of specifying a buffer for each I/O operation that requires it, it is possible to pre-register a pool of buffers beforehand. The kernel assigns a buffer to an operation when it is actually executed. By utilizing this feature, the number of simultaneously allocated buffers can be reduced, as it is only necessary to maintain as many as the number of in-flight operations.</p>\n<p>Providing buffers can be achieved in two ways: using the older provided buffers interface <code>io_uring_prep_provide_buffers</code> or the newer buffer rings feature.</p>\n<h4>Operation Ordering</h4>\n<p>The operations added to the <code>SQE</code> can be ordered by utilizing the <code>IOSQE_IO_LINK</code> flag.</p>\n<p>When set in an <code>SQE</code>, it ensures the next operation (next submitted <code>SQE</code>) will not be started until the current one finishes executing. It is possible to link multiple <code>SQE</code>s together and form a chain.</p>\n<h2>Appendix B – Our Contributions to the rpc_tester</h2>\n<p><em>rpc_tester</em> is a Seastar app used for benchmarking the performance of Seastar’s networking using its RPC API. It functions in one of two modes:</p>\n<ul>\n<li>Server, which listens for and processes incoming requests.</li>\n<li>Client, which initiates connections to a specified address to execute RPC calls.</li>\n</ul>\n<p>A <a target=\"_blank\" href=\"https://github.com/scylladb/seastar/blob/master/apps/rpc_tester/sample-conf.yaml\">configuration file</a> is required to define the job’s parameters, which can be configured to either stream data or simulate a specific computational load.</p>\n<p>At the start of the project, we decided to introduce a new job type based on RPC streaming, which supports continuous sending and receiving of data. This can be done by a <em>sink</em> and <em>source</em>, which can be thought of as two ends of the same stream. When the application wants to stream data, it puts it into the <em>sink</em>, and the other party can read it from the <em>source</em>. The main difference between this and the previous RPC jobs is that you don’t need to wait for the response on the RPC level (since the stream is continuous).</p>\n<p>The newly introduced <em>rpc_streaming</em> job type works in a similar way to the existing <em>rpc</em> type. On each client shard, it creates a <em>parallelism</em> number of fibers – each of them sending some data in a loop. Each iteration just executes <em>co_await sink(payload); (</em>instead of a send-and-wait flow). This resolves when the data is sent, but does not wait for a response.</p>\n<p><em>rpc_streaming</em> distinguishes two verbs: unidirectional and bidirectional. The former is used when the client is the only one sending data, and the server just receives it. The latter is used when both parties send data to each other; apart from the client sending data to the server, the server echoes back each portion of the received data:</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/image34.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/image34.png 936w, https://www.scylladb.com/wp-content/uploads/image34-300x151.png 300w, https://www.scylladb.com/wp-content/uploads/image34-768x387.png 768w\" src=\"https://www.scylladb.com/wp-content/uploads/image34.png\" alt=\"\"></a></p>\n<p><em>C++ code snippet: The result of a co_await on the source is assigned to a variable and subsequently moved into a sink</em></p>\n<p>This way, we can measure both types of workloads: one with a lot of data being sent, and the other with a lot of data being sent and received.</p>\n<h3>Hunting the Race Condition</h3>\n<p>The <em>rpc_tester</em> runs all jobs for a specified amount of time, and then stops them and collects the results. However, it’s vital to ensure the proper closing of all opened RPC connections and streams.</p>\n<p>While developing the <em>rpc_streaming</em> job, we noticed that sometimes the client side crashed due to an <em>rpc::closed_error</em> being raised. It was weird at first because all the connections seemed to be closed properly.</p>\n<p>After some investigation, we discovered that the problem was in the way we were closing the streams. When using the streaming RPC API, a new TCP connection is established for each stream. However, they are grouped together in the same <strong>parent</strong> connection.</p>\n<p>Previously, the resources were released in the following order:</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/image26.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/image26.png 734w, https://www.scylladb.com/wp-content/uploads/image26-300x112.png 300w\" src=\"https://www.scylladb.com/wp-content/uploads/image26.png\" alt=\"\"></a></p>\n<p><em>C++ code snippet: Awaiting the closure of the sink followed by the termination of the RPC client into a sink</em></p>\n<p>Here, <em>sink</em> is associated with the stream connection, and the <em>_client</em> is associated with the parent connection. We were closing the stream connection before the parent one. The problem comes down to the exact timing of when the <em>sink.close()</em> future resolves. It is resolved when the EOF is sent to the peer, but it does not guarantee that the peer has received it. If the parent connection is closed before the peer receives the EOF, it can cause the <em>rpc::closed_error</em> to be raised on the client side.</p>\n<p>The race condition was more likely to happen when the streaming connection was overloaded with data. If the underlying TCP connection was congested, the EOF could be delayed, and the parent connection could be closed before the peer received it.</p>\n<p>This race condition is clearly visible in the packet capture (see screenshot below), where port <em>50199</em> is the streaming connection and <em>52538</em> is the parent connection:</p>\n<p><a target=\"_blank\" href=\"https://www.scylladb.com/wp-content/uploads/image32.png\"><img srcset=\"https://www.scylladb.com/wp-content/uploads/image32.png 2048w, https://www.scylladb.com/wp-content/uploads/image32-300x38.png 300w, https://www.scylladb.com/wp-content/uploads/image32-1100x138.png 1100w, https://www.scylladb.com/wp-content/uploads/image32-768x96.png 768w, https://www.scylladb.com/wp-content/uploads/image32-1536x192.png 1536w\" src=\"https://www.scylladb.com/wp-content/uploads/image32.png\" alt=\"\"></a></p>\n<p><em>TCP Teardown Race Condition on ports 50199 and 52538: parent connection closes before streaming connection</em></p>\n<ol>\n<li>The client attempts to close the stream connection by sending a packet with the <em>FIN, ACK </em>flags.</li>\n<li>Immediately after, before the stream handshake completes, the client closes the parent connection by sending another <em>FIN, ACK</em>.</li>\n<li>The server responds with <em>FIN, ACK</em> for the parent connection, and the client replies with <em>ACK</em>. <strong>The parent connection is now closed.</strong></li>\n<li>Because the streaming connection was congested, the initial stream <em>FIN, ACK</em> packet was lost. The client attempts to retransmit it, but the parent connection is already gone, resulting in the <em>rpc::closed_error</em>.</li>\n</ol>\n<p>This is not the expected behavior, because the parent connection should be closed only after all the streams are properly closed.</p>\n<h4>The Fix</h4>\n<p>To mitigate this issue, we changed the order of closing the connections. For each stream, we enforce a strict 4-step closure sequence:</p>\n<ol>\n<li>Client sends EOF for a stream.</li>\n<li>Server receives EOF for a stream.</li>\n<li>The server sends EOF for their stream.</li>\n<li>Client receives EOF for the stream.</li>\n</ol>\n<p>This way, after closing all streams for a given parent connection, we can be absolutely sure it’s safe to close the parent connection because all the EOFs have been definitively sent and received.</p>\n<h3>Exposing Additional Metrics</h3>\n<p>Beyond just adding streaming capabilities, we also wanted to improve overall benchmarking visibility. When benchmarking and using the <em>rpc</em> job type with the <em>write</em> verb, we wanted to measure the throughput in terms of bytes per second, but only the number of messages was available.</p>\n<p>To address this limitation, we decided to expose additional metrics for the <em>write</em> verb: <em>total duration</em>, <em>messages per second</em>, <em>total bytes</em>, <em>message size</em>, and <em>throughput</em>. These additions are included alongside the original data, all of which are formatted as YAML and printed to stdout upon completion of the run.</p>\n                    </div>"
